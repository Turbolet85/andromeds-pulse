# Security Rules

Universal security requirements. Apply to all files in this project. This rule file has no `paths:` frontmatter — it loads unconditionally.

**Authoritative source:** `.andromeda/security-plan.md` (tier=Minimal — local-first Tauri 2 desktop app, loopback-only OTLP, in-memory DuckDB). For full threat model, vector list, and bootstrap phasing, read the plan.

## Loopback-only network surfaces
- OTLP receivers MUST bind to `127.0.0.1` only — `:4317` (tonic 0.14 gRPC) and `:4318` (axum 0.8 HTTP). Loopback is the de-facto authorization boundary; no auth model.
- NEVER bind to `0.0.0.0` or any non-loopback interface — invalidates the entire Minimal-tier risk model.
- OTLP HTTP `:4318` MUST have Host-header allowlist middleware (reject non-`{127.0.0.1, localhost, [::1]}:configured-port`); DNS rebinding lesson from Coder Agent CVE-2025-09-19 + MCP TypeScript SDK CVE-2025-66414.
- OTLP HTTP `:4318` MUST have CORS deny-by-default — no `CorsLayer::permissive()` / `allow_origin(Any)`; no browser context should ever post OTLP.
- OTLP `:4318` MUST set `axum::DefaultBodyLimit::max(8 * 1024 * 1024)`; OTLP `:4317` MUST set `.max_decoding_message_size(8 * 1024 * 1024)` per `*ServiceServer` builder. JFrog axum-core advisory + tonic 1 GB-default issue are the anchors.

## Input validation at every boundary
- Post-`prost`-decode invariant checks REQUIRED on every OTLP payload — `span_id` is 8 bytes, `trace_id` is 16 bytes, attribute keys/values bounded. `prost` only validates wire format; semantic invariants are the `ingest` crate's job.
- DuckDB queries MUST use `Connection::prepare` + `?` placeholders + `Statement::execute([&param])` — NEVER `format!("SELECT … WHERE service_name = '{}'", user_input)`. 2026 DuckDB CVE cluster (Dagster GHSA-mjw2-v2hm-wj34, Vanna CVE-2024-5827, dagster-duckdb CVE-2026-41490).
- **Product-binary** path env vars (`ANDROMEDA_PULSE_*_PATH` / `*_DIR`) MUST canonicalize via `std` both-sides-canonicalize on the `workspace_detector::contract::publish_workspace_key` precedent — the project's SINGLE path primitive since chunk `2026-08-29-advisory-backlog` (`strict-path` was declined at the 2026-08-26 P4 review and then DROPPED from the dependency graph, having had zero `.rs` users) — and assert the resolved path lives under the resolved data dir before use. CWE-22 path traversal class defense. **Carve-out (harness/xtask-only tool locators):** a path var NOT consumed by the production binary that resolves an external tool living outside the data dir by design — `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` (plus the pre-existing `_PIDFILE` / `_LOGFILE`) — is guarded by whitespace-trim + `is_file()` + clean skip instead; confinement is inapplicable because the tool is deliberately out-of-tree, and the var never reaches the shipped binary. The carve-out is scoped exactly to that shape. A sibling harness-only class — STATE FILES, not env vars: the `scripts/agent-run.{sh,ps1}` boot waiting wrapper writes `run/andromeda-pulse.spawn` (the app pid) and `run/andromeda-pulse.exit` (the app's one-line end; ps1 since chunk `2026-09-30-perf-budget-gate-reads-real-samples`), read only by `boot` and by `cargo xtask harness:status` through `read_ended`'s bounded grammar (one line, ≤ 48 printable ASCII); the product binary never reads them. **NARROWED EXCEPTION (guard landed 2026-08-26, chunk `2026-08-26-l4-runtime-security-residuals`) — the rule is still NOT categorical, but it is no longer a convention:** `ANDROMEDA_PULSE_MODEL_PATH` · `_LLAMA_CUDA_BIN_PATH` · `_LLAMA_CPU_BIN_PATH` are read by the SHIPPED binary (`pulse-app/src/llamacli_inference.rs::validate_path_input`), so the harness carve-out does not reach them. **Always-on now:** trim + reject-empty · reject a `..` traversal component BEFORE canonicalizing (canonicalization erases `..`, so a post-check can never see it) · reject over `MAX_PATH_INPUT_BYTES` (4096) · `canonicalize()` · assert regular-file. **Confinement is OPT-IN** via `ANDROMEDA_PULSE_L4_ALLOW_ROOT`, comparing the canonicalized candidate against the canonicalized root — **both sides canonicalized**, because Windows `canonicalize()` yields a `\\?\` prefix and a one-sided compare fails regardless of the true relationship. A root that is SET but unresolvable **fails closed** (every candidate rejected), so a typo cannot silently disable the guard. Opt-in rather than data-dir-default because the GGUF and `llama-cli.exe` live outside the data dir BY DESIGN — a default would reject every configuration that has run L4. **Residual consequence, scoped:** on a host that leaves the root unset, an actor who can set these vars can still point the product at an arbitrary on-disk file — read as a model, or EXECUTED as the inference binary. Accepted under this tier's local-single-user trust boundary, and no longer silent: the unconfined posture emits one WARN per boot on `interpretation.model.allow_root`. **The primitive here — and now project-wide — is `std` both-sides-canonicalize on the `publish_workspace_key` precedent** (`strict-path` declined at the 2026-08-26 P4 review, then dropped from the graph at `2026-08-29-advisory-backlog`). The sibling argv-prompt residual is CLOSED: `validate_prompt_bounded` bounds the `-p` value before `Command` assembly.
- TauRPC procedure args MUST go through `serde` deserialization on every `#[taurpc::procedure]` argument struct; `TryFrom<u16>` on every port; `serde`-friendly enums on every settings field.
- Plugin file paths MUST canonicalize + confine under the resolved plugin dir before `wasmtime` load. Pair with the path-env-var canonicalization above.

## Tauri capability gating (negative-default)
- Every TauRPC procedure MUST have its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` (what `capability-drift` diffs — against the worktree AND, since 2026-08-30-staged-bindings-assertion, the staged git-index bindings, with the staged `capabilities/*.json` grants asserted vs `staged_gate::EXPECTED_GRANTS`) plus a validated argument struct — NOT a per-procedure `pulse-app/capabilities/` entry, which does not exist in this project (TauRPC dispatches every method through one invoke handler; measured 2026-08-21). Tauri capabilities remain NEGATIVE-DEFAULT at the IPC-layer and per-CORE-API granularity: `fs` / `shell` / `dialog` / `http` and each `core:window:*` permission require an explicit grant with rationale, and ARE silently rejected at runtime when missing.
- Two enforcement pieces required for a NEW procedure: (1) router registration in the owning crate, AND (2) its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`. The `xtask capability-drift` check enforces the pair in CI — and since 2026-08-30-staged-bindings-assertion it ALSO asserts the STAGED (git-index) copies: bindings vs `EXPECTED_PROCEDURES` + every `pulse-app/capabilities/*.json` vs `staged_gate::EXPECTED_GRANTS` in both directions (`cargo xtask check:staged-artifacts` is the direct verb; exit 0 staged-clean / 1 staged-drift / 2 cannot-evaluate). (A capability JSON edit is the enforcement pair for a new CORE API / `core:window:*` grant, not for a procedure.)
- NEVER grant Tauri core APIs (`fs`, `shell`, `dialog`, `http`) to `pulse:default` without an explicit per-feature capability addition with stated rationale.
- NEVER expose `pulse:updater` to webview JavaScript — bound to `tauri-plugin-updater` flow only.
- `pulse:notification` and `pulse:tray` MUST be outbound-emit-only — input-event handlers (notification action callbacks, tray menu IPC re-entry) require a separately-named capability.
- `pulse:plugin-fs` MUST stay scoped to the host's read of the canonicalized plugin dir — never widened to webview / write / execute.
- **Static analysis test gap (documented; not yet implemented):** the 3 NEVER-widen bans above (`pulse:notification` / `pulse:tray` / `pulse:plugin-fs`) currently rely on manual review and runtime IPC rejection (`xtask capability-drift` chunk #27 verifies TauRPC ↔ capability JSON sync only — it does NOT detect permission widening on the 3 named capabilities). Runtime IPC rejection is insufficient because by the time it fires, the widening has already been deployed; static analysis on `pulse-app/capabilities/*.json` is the appropriate gate. Test trigger documented for next `/andromeda-tests` re-run as `security-vector-coverage: Capability widening static analysis` per `.claude/rules/testing.md` §Pending coverage triggers + amendment `2026-05-08T17-28-29Z-document-capability-widening-test-gap` (`.andromeda/runs/2026-05-08T17-28-29-spec-amendment-document-capability-widening-test-gap/amendment.md`).

## Plugin host + WASM sandbox
- WASM Component Model guests receive ONLY host imports declared in their WIT — no syscalls, file, or socket access unless explicitly granted.
- `wasmtime::Config` MUST set `epoch_interruption(true)` for plugin call timeouts (2-3× faster than fuel). The canonical wasi-http header field-size bound is the `MAX_WASM_HTTP_FIELDS_SIZE_BYTES` const in `crates/plugins/src/engine.rs` (chunk #45 substrate; CVE-2026-27572 anchor); actual enforcement attaches via `wasmtime_wasi_http::WasiHttpCtxBuilder::max_field_size` (or equivalent) when wasi-http imports are introduced in subsequent chunks (#46+). Per security-plan.md §Security Decisions Log 2026-05-11 — `Config::max_wasm_http_fields_size` is NOT a method on `wasmtime::Config` in any wasmtime version; the bound lives at the wasi-http context, not the Config struct.
- Per-Store `wasmtime::ResourceLimiter` MUST cap memory (e.g., 64 MB), tables, instances.
- Cranelift backend on x86_64 MUST stay enabled — was the unaffected configuration for April 2026 Critical sandbox escapes (CVE-2026-34941, CVE-2026-35195). NEVER add a non-Cranelift wasmtime feature flag on x86_64 builds.
- NEVER use the `wasmtime::Linker` to expose host functions outside the WIT contract — bypasses capability scoping.
- NEVER trust plugin-returned Arrow IPC bytes without an 8 MB size cap before re-emit on the Tauri Channel API.

## MCP feature double-gate
- MCP stdio surface MUST require BOTH compile-time `--features mcp-server` AND runtime `ANDROMEDA_PULSE_MCP_ENABLED=true`. Single-gate is a regression of the architecture-declared double-gate.
- The graceful-degrade `warn` (env var set against a binary built without the feature) MUST be preserved — do not regress to fail-startup.

## Error sanitization at boundaries
- Every `#[taurpc::procedure]` returns `Result<T, AppError>` — `AppError` is the `serde`-friendly enum (`Validation { field, reason }` / `NotFound { resource }` / `Internal { message }` / `Plugin { plugin_id, message }` / `Storage { message }` / `Ingest { message }`).
- Module-internal `thiserror` 2.x enums convert at the bridge via `From` impls. NEVER serialize `anyhow::Error` directly across the bridge.
- `AppError::Internal { message }` carries a sanitized one-liner — strip stack traces, file paths, library versions, Rust struct names. Full chain stays in internal log via `tracing-error` SpanTrace.
- OTLP receiver errors collapse to standard `tonic::Status` codes / `Status` proto in body per OTLP HTTP spec.
- MCP server errors use standard JSON-RPC 2.0 error object (numeric `code`, `message`, optional `data`).

## Logging & redaction (snapshot/clipboard/MCP hygiene)
- NEVER log raw OTLP attribute values, span/log/metric content payloads, snapshot file contents, clipboard contents, or MCP tool response bodies — incidentally captured secrets from instrumented host apps. The `snapshot.generate`/`snapshot.copy_to_clipboard` resolver arm of this ban is UNVERIFIED (its only canary was dead-by-construction and was deleted at chunk 2026-08-30-dead-lib-src-test-migration — a test binary linking the resolver aborts at load; owed via test-plan §1 `snapshot-resolver-level-coverage`); the webview copy route IS wire-measured.
- NEVER log a full product-consumed filesystem path — basename of the canonicalized path only. Covers the plugin dir, the three L4 model/binary path vars, and the `ANDROMEDA_PULSE_L4_ALLOW_ROOT` root (`path_basename` / `root_basename` plus the env-var NAME, which is safe — only `*_SECRET` / `*_TOKEN` / `*_KEY` / `*_PASSPHRASE` names redact). Measured at the wire 2026-08-26: the model path's containing directory 0× across 11,251 lines, basename 1×, full root 0×. The rule is CATEGORICAL since chunk 2026-08-30-diagnostics-un-muting-harness-truth-sweep — the two boot records that carried a standing exception (`app.boot.tracing.init`, `app.boot.pid`) now emit basenames via `pulse_app::observability::log_basename` (boot smoke: 0 full paths).
- NEVER log DuckDB query parameter values — use `query_id` + `param_count` + `param_types` instead.
- NEVER expose internal hostnames / IPs / library versions in OTLP error responses or MCP error objects.
- `snapshot.copy_to_clipboard` MUST emit a `pulse://stream/snapshot-progress` event at clipboard-write time so the UI can show a non-suppressible "X bytes copied" toast.
- `ui.ipc.rejection` (chunk 2026-08-30-acl-rejection-logging) is a deliberate NO-SCRUB log boundary — the §Logging & Monitoring "capability-rejected IPC" record: a WARN once per rejection behind its own exact allowlist leaf, carrying ONLY the bounded triple `{error_category (closed enum acl_rejected|other), window_label (coerced 4+unknown), payload_bytes (u32, bounded)}`; the copied markdown, the command string and the raw rejection text are excluded by construction (wire-measured 0× across the revoked-run log). The clipboard NEVER-log ban covers EVERY clipboard-payload path, including this webview copy-failure route — never just `snapshot.copy_to_clipboard`.
- `ui.webgpu.adapter` (chunk 2026-09-30-perf-instruments-measure-their-budgets; a Boundary widening the founder ratified at P4 2026-09-30, «Да, делай») is a second deliberate NO-SCRUB webview-originated log boundary: one record per canvas-mount adapter request (INFO on `obtained`, WARN otherwise) behind its own exact allowlist leaf, carrying ONLY `{outcome (closed WebgpuAdapterOutcome enum; unknown rejected at deserialization), window_label (coerced 4+unknown)}`; the raw adapter / rejection error text is excluded by construction. Its procedure `telemetry.frontend.record_webgpu_adapter` is pinned in `EXPECTED_PROCEDURES` with no capability-JSON change.
- `app.exit` (chunk 2026-10-01-conductor-return) is a deliberate NO-SCRUB product-originated log boundary: exactly one record per process end behind its own exact allowlist leaf beside `app.panic.fatal`, carrying ONLY `{exit_class, exit_code, exit_code_known, signal}` — two closed labels, an `i32` (0 when unknown), a bool; a panic payload, an error `Display`, a native message and every path are excluded by construction (re-exec arms: 0 full paths, 0 planted canary). Its stated failure mode is the set of ends it cannot see: SIGKILL, `_exit`, Windows `TerminateProcess`, a Rust `std::process::exit` on Windows (`ExitProcess`, no `atexit`), pre-sink failures. No TauRPC procedure, port or capability is involved.
- NEVER log, or run code that needs thread-locals, from a C `atexit` handler or a signal handler on the thread ending the process — glibc runs that thread's TLS destructors before `atexit` handlers, and a `LocalKey::with` panic in an `extern "C"` handler aborts. The `libc` exit FFI (`pulse-app/src/observability.rs`) hands off to a thread spawned at install (`pulse-exit-reporter`, a bounded wait), and the Unix signal path records from a runtime task, then restores `SIG_DFL` and re-raises the SAME signal — never an exit code standing in for it.
- The P-047 catalog is **8 categories** (JWT · bearer · api_key · secret_kv · **provider_key** · email · credit_card · ssn). `provider_key` (2026-08-22) is the BARE-credential arm: the four credential arms before it require a key name, so a standalone `sk_live_…` / `sk-proj-…` / `ghp_…` / `AKIA…` token matched nothing and was stored verbatim. It is anchored-prefix + length-floor — never entropy scoring, which false-positives on trace ids and hashes; the false-positive corpus in `crates/security/src/scrubber.rs` is what bounds it, so any new arm must keep ordinary high-entropy identifiers `Allowed`.
- The `credit_card` arm is **precision-gated** (chunk `2026-09-29-scrubber-path-false-positive`, founder-ratified). It matches a candidate run of ASCII digit groups joined by single ` `/`-` only when some window of consecutive WHOLE groups carrying 13–19 digits passes Luhn, so a date-time stamp (`rm-20260923-093840`, a harness data-dir basename) or a 19-digit nanosecond timestamp is `Allowed`. The accepted recall trade: a Luhn-invalid (mistyped) card number, or one fused into a longer single digit group, is not redacted. Windows are whole groups only, NEVER arbitrary digit offsets — a long digit run offers so many offset windows that most non-card runs would pass Luhn by chance.
- **Span-level masking, not whole-value replacement** (chunk `2026-09-30-span-level-redaction`, a Boundary widening the founder ratified at P4 2026-10-01, «Ок давай по типу правила»): every scrub site except `metrics_points.labels` calls `security::scrubber::mask_secret_spans(value, placeholder)`, which masks each secret where it sits and keeps the rest of the value byte-identical — one card number no longer blanks a digest. The extent is CLASS-AWARE and is what keeps never-weaken: keyed arms (`bearer` · `api_key` · `secret_kv`) mask from the key word to the END OF THE LINE (a multi-word value after `password:` or a base64 bearer tail past `+`/`/` lies outside the regex match); bare arms (`jwt` · `provider_key` · `email` · `ssn`) mask the whole whitespace-delimited token; `credit_card` masks the Luhn-qualifying digit-group run; overlapping or touching spans merge under the earliest arm in catalog order. `scrub_attribute` stays the detection VERDICT (it gates the mask; a flagged value with no locatable span masks whole — fail closed) and stays the only call at `encode_labels`. Masking re-runs to a bounded fixpoint (≤ 4 extra passes) because a mask can expose a match its neighbour hid (a Luhn-valid run fused to a key word). Each consumer passes its own placeholder spelling (`[REDACTED:{c}]` · `[redacted:{c}]` · `[redacted: {c}]`), never unify them in passing. A JSON payload is masked PER STRING LEAF, never as serialized text — `secret_kv`'s `\S+` runs across compact-JSON delimiters (`scrubbed_l4_json`, the training export's `interpretation`); a count of redacted fields looks for a placeholder ANYWHERE in the field, never at its start.
- **Scrubber coverage on the OTLP path is now complete for every column a producer can reach** (measured 2026-08-23): `log_records.body` · `exception_message` / `exception_stacktrace` on `span_events` + `log_records` · since chunk `2026-08-23-ingestion-scrub-coverage`, `spans.service_name` · `span_events.name` · `metrics_points.metric_name` · `log_records.severity_text` · and, since chunk `2026-08-23-metrics-points-labels`, a FIFTH cell `metrics_points.labels` (a data point's attribute set). **That fifth cell uses a THIRD scrub SHAPE** — the scrub input is the JOINED `key=value` form UNIONED with the bare value, because `secret_kv` and `api_key` are key-name-anchored and structurally unreachable on a split value: a label `{password: "hunter2"}` presents only `hunter2` to a value-only scrub and matches NOTHING, so the whole keyed class would store verbatim. Label KEYS are stored verbatim; only the VALUE becomes `[REDACTED:{category}]`, so two distinct keys never collapse into one placeholder. Accepted failure mode: over-redaction when the KEY alone trips a match (`password=1`), per the key-anchored arms' recall-over-precision posture. `service_name` is scrubbed INSIDE `extract_service_name`, not at the column push — that fn feeds three consumers (the `spans` column, the storm `FingerprintObserver`, the baseline `SpanObserver` tap) and scrubbing only the column would leave two raw paths into `triage` and desync DuckDB identity from the baseline registry. The tap drives one `CompositeSpanObserver` (baseline, restart, and since chunk `2026-09-30-p-027-discovery-bound` the first-sighting `DiscoveryObserverAdapter`), so its scrubbed name now also keys the lifecycle `ServiceRegistry` directly at a service's first span — the choke point still has THREE consumers; what grew is the tap's fan-out, and the desync argument covers the lifecycle registry too. `metrics_points.metric_name` is the one target inside a PRIMARY KEY. That collision is **CLOSED** since chunk `2026-08-23-metrics-points-identity`: the key gained a `seq` ordinal, so two distinct credential-shaped names redacting identically at the same `ts_unix_nano` + `resource_hash` no longer collide — both rows persist and no batch fails. The discriminator is content-INDEPENDENT (a per-table monotonic counter, never derived from the secret), so the rejected alternative still stands. **Residual:** two names that differ only inside a masked span still mask to one text (a multi-word name keeps its non-secret words under span masking), so those rows land indistinguishable — redaction holds and nothing new leaks, but the whole-batch ERROR was the only signal that such a collision had happened, and closing it removed that signal. Still NOT covered, by construction: `span_events.exception_type` (a DELIBERATE exclusion — class identifier, not user content). The producer-less `instrumentation_scopes` (with `resources` / `span_links`) no longer exists — its CREATE was deleted at chunk 2026-08-30-diagnostics-un-muting-harness-truth-sweep, so every reserved ring-buffer table has a producer and no scrub target is vacuous. The DuckDB ring buffer remains UNENCRYPTED, so redaction at the write boundary is the control, not confidentiality at rest. Before claiming a column is scrubbed, still check the call site.

## Self-observation discipline
- Self-observation runtime is `tracing` + `tracing-subscriber` JSON + `tracing-appender` daily file sink ONLY. NO OTel SDK linked into the product binary for self-observation.
- NEVER instrument the product's own telemetry with an OTLP network exporter pointed at the product's own `:4317`/`:4318` — infinite loop + bypasses loopback authorization model.

## Code-signing key custody
- Tauri updater Minisign Ed25519 verification cannot be disabled — never override.
- NEVER ship the Minisign **private** key in the repo or in any build artifact — only the public key belongs in `tauri.conf.json`.
- Windows EV signing cert lives in Azure Key Vault HSM (DigiCert / GlobalSign HSM-RSA only); key never leaves HSM.
- GitHub Actions reaches Azure Key Vault via OIDC federation — NEVER store a long-lived Azure service principal secret in GitHub Actions secrets.

- 2026-05-23: EXTENSION to the 2026-05-16 / 2026-05-18 / 2026-05-19 cross-crate state delivery family — handles ASYNC traits with `Arc<dyn Trait>` injection WITHOUT adding the `async-trait` workspace dep. Rust 1.85's native `async fn` in traits is NOT dyn-compatible by default (the implicit `impl Future` return is not object-safe via the `dyn` keyword unless wrapped through `#[trait_variant::make]` or `async-trait` macro). Workspace v0.2.0 chunks operate under a "Workspace deps delta: none" discipline (per pulse-v0_2_0-route §80 + analogous chunk callouts), so adding `async-trait` to enable a single trait's dyn-compat is over-cost. Resolution: declare async-trait methods with **manual `Pin<Box<dyn Future + Send + 'a>>` return types** — object-safe by construction, no macro magic, no extra dep:

  ```rust
  type SqlFuture<'a, T> = Pin<Box<dyn Future<Output = Result<T, SqlAggregationError>> + Send + 'a>>;
  pub trait SqlQueryRunner: Send + Sync {
      fn run_q1<'a>(&'a self, window: Duration) -> SqlFuture<'a, Vec<Q1RedRow>>;
      // ...
  }
  // Concrete impl at binary boundary:
  impl SqlQueryRunner for CadenceSqlRunner {
      fn run_q1<'a>(&'a self, window: Duration) -> SqlFuture<'a, Vec<Q1RedRow>> {
          Box::pin(async move { run_q1(&self.state, window).await })
      }
  }
  ```

  Cost: one `Box::pin(async move { ... })` per method body (small allocation per call; acceptable for non-hot-path orchestration like cadence coordinator). Type alias `type SqlFuture<'a, T> = ...` keeps signatures readable. The `'a` lifetime on `&'a self` flows through to the future so the closure can borrow `&self.state`. Tests use the same shape — a stub impl returning canned data follows the same `Box::pin(async move { ... })` pattern. Verified at chunk #80 `crates/triage/src/cadence/coordinator.rs::SqlQueryRunner` (declaration) + `pulse-app/src/cadence_runner.rs::CadenceSqlRunner` (concrete impl over chunk #79 `TriageSqlState`); 14 colocated tests use a `CountingSqlRunner` stub mock following the same pattern.

- 2026-08-30: `npm audit`'s `fixAvailable` FIELD IS RESOLVER OUTPUT, NOT UPGRADE GUIDANCE — its named target can drift between consecutive runs and can point at a major DOWNGRADE, and a bare `true` can stand against a range where no in-range fix exists. Measured at `2026-08-30-npm-advisory-coverage`: the webdriverio cluster's suggested "fix" moved 8.14.6 → 7.40.0 (two majors BACKWARD) across runs, and lighthouse read `fixAvailable: true` while its entire installed major was inside the vulnerable range (the real fix was the next major). Rule for npm disposition work: never plan upgrades from `fixAvailable` — measure with `npm audit fix --dry-run`, then APPLY and re-audit (the residual is the truth); treat a downgrade-shaped suggestion as "no forward fix" (exception-with-closing-condition class, never a downgrade of a harness driver). Extended 2026-09-30: when a transitive advisory's patched release lies inside every dependent's semver range, first confirm the release exists with `npm view {pkg} versions`, then close it with a targeted `npm update {pkg}`. That moves only those lockfile entries and leaves `package.json` untouched. Extended 2026-10-01: when every dependent's range EXCLUDES the patched major (no upgrade path reaches it), check that the API the dependent actually calls is unchanged in the patched major, then pin it with a `package.json` `overrides` entry and prove it with `npm audit` plus `check:npm-supply-chain`; take a documented exception only when no fixed path exists at all.

- 2026-08-30: `package-lock.json` IS THE CANONICAL ENUMERATION FOR npm SUPPLY-CHAIN TOOLING — its entries carry `license` fields (906/909 coverage measured here) and `dev` class flags, so license and dependency-class checks read the COMMITTED lockfile alone: deterministic across environments, no `npm ci` needed, and it covers platform-conditional optional packages that are never installed on the current host. A blind `node_modules` walk is the wrong basis twice over — it hits name-less nested test-fixture stubs (measured: `test-fixtures`/`baz`/`browser_field` inside installed packages) and misses the non-installed platform variants. The few field-less lockfile entries become explicit policy exceptions, never silent skips.
