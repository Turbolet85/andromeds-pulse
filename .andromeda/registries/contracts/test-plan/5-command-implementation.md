### 5-command implementation

**`boot`** — start the product for testing:
- **Command body:** PRE-BUILD under the verb's own exported env (`cargo build --bin pulse-app --release`, then `cargo build -p xtask` — the readiness poll shells `cargo xtask`, so a stale xtask would otherwise rebuild inside the timed window), then spawn `target/release/pulse-app[.exe]` BY PATH in background — the `cargo run` wrapper is GONE, and the app's own `write_pid_file` writes the canonical pid (chunk 2026-08-30-agent-harness-teardown-truth; sh live-proven, ps1 mirrored — its boot/`ended` leg driven live once by hand at chunk 2026-09-30-perf-budget-gate-reads-real-samples, a committed leg still owed via the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger). The sh verb runs the app under a waiting subshell — the subshell's own stdin, stdout and stderr are `/dev/null`; the app's stdout and stderr go to `logs/boot.log` under the data dir — that writes the app pid to `run/andromeda-pulse.spawn` and, on reaping the app, its end to `run/andromeda-pulse.exit` (`exit N` or `signal N (NAME)`) — once `boot` returns, the app is otherwise an orphan whose end status nothing can read; `boot` takes the app pid from the spawn record, and none within 5 s is `boot: the app did not start (no spawn record)`, exit 1 (chunk 2026-09-29-ci-wall-time-and-round-trips). `agent-run.ps1 boot` mirrors the recorder since chunk 2026-09-30-perf-budget-gate-reads-real-samples: a hidden `powershell -EncodedCommand` wrapper launches the app, writes `run/andromeda-pulse.spawn` (the app pid) and on the app's exit `run/andromeda-pulse.exit` (`exit N`, ASCII, no BOM); `boot` polls the spawn record ≤ 5 s (50 × 100 ms), else prints `boot: the app did not start (no spawn record)` and exits 1, and on a failed readiness poll prints `app ended: {record}` or `app still running (pid N) but never reported healthy` before cleanup. Since chunk 2026-10-09-boot-smoke-s-early-exit-found-and-closed its readiness poll goes through `Invoke-Ready` (`cargo xtask harness:ready`) and its still-running arm carries the sh verb's conditional `the receivers never both accepted: …` line (Exit code, below); that edit was parsed by `pwsh` with 0 parse errors and has never run — no CI job and no dev host runs the script. Env vars unchanged: `ANDROMEDA_PULSE_DATA_DIR=$TMPDIR/andromeda-test-$$` (per-test isolation), `RUST_LOG=debug`, optional `ANDROMEDA_PULSE_OTLP_GRPC_PORT=0 ANDROMEDA_PULSE_OTLP_HTTP_PORT=0` (ephemeral ports)
- **Readiness signal:** Poll `cargo xtask harness:ready` (`xtask/src/harness_ready.rs`, since chunk `2026-10-09-boot-smoke-s-early-exit-found-and-closed`; the scripts thread `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` into the xtask child as they did for the status poll) until its verdict is `ready`: the `cargo xtask harness:status` verdict the `status` verb uses reads `running-healthy` AND a TCP connection is accepted on `127.0.0.1` at each port resolved from `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT` (defaults 4317 / 4318), each attempt bounded at one second. One pretty-JSON object on stdout — `{verdict: ready | not-ready | ended | cannot-evaluate, pid, ended, otlp_grpc, otlp_http}`, each receiver label `accepting` | `refusing` (`null` on `cannot-evaluate`), `ended` the exit record when the verdict is `ended` — exit 0 `ready` · 1 `not-ready` or `ended` · 2 `cannot-evaluate` (paths unresolvable, or a port variable that is not 1 to 65535). The pure `decide_ready` is pinned per arm, and the probe against a real loopback listener and a closed port. **The gap recorded at chunk `2026-10-09-supply-chain-job-same-on-push-and-pull-request` is CLOSED:** until this chunk the sh verb reported ready on the `running-healthy` verdict alone and confirmed no handshake (on `ci#37964887106` ready printed 12 ms after the app's first log record, before `app.boot.otlp.grpc.bind`); as measured at chunk `2026-10-09-boot-smoke-s-early-exit-found-and-closed`, ready follows both bind records — by 0.097 s on the dev host and by 0.453 s on `ci#37979648967`. The ps1 verb polls the same verdict through `Invoke-Ready`; that edit is parsed, never run. What stays open is not readiness: the cause of the app ending by itself shortly after ready on a runner is not named, and stays with the route's P-129 record
- **Exit code:** 0 on `ready`; non-zero when no `ready` verdict arrives inside the window. On that failure path the sh verb names how the app ended — `app ended: {record}` from the exit record, or `app still running (pid N) but never reported healthy`, followed, only when the last readiness verdict held a `refusing` label, by `the receivers never both accepted: OTLP gRPC 127.0.0.1:{port}, OTLP HTTP 127.0.0.1:{port}` (chunk 2026-10-09-boot-smoke-s-early-exit-found-and-closed; driven once by hand, no committed test — the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger) — and runs `bash "$0" cleanup` (chunk 2026-09-29-p-025-hue-shift-observable-made-gradable — the script is git mode 100755 since then; at 100644 the self-invocation died with exit 126 on a checkout, so the branch never ran)
- **Timeout:** 10s default for process boot + readiness, and since chunk 2026-08-30-agent-harness-teardown-truth the default is HONEST: the release build AND the xtask build run BEFORE the timed window (the pre-build split), so neither a cold compile nor the env-triggered thin-LTO relink is inside it (measured boot-to-ready 1.953s on a warm target under the untouched 10s default, when ready was the status verdict alone; under `harness:ready`, as measured at chunk 2026-10-09-boot-smoke-s-early-exit-found-and-closed, `boot` returned 0.296 s after the app's first log record on the dev host, and on `ci#37979648967` ready printed 0.596 s after it — both inside the untouched default). `HARNESS_STATUS_TIMEOUT` remains the override. History: before the split, the exported `ANDROMEDA_PULSE_*` set re-fingerprinted the release build INSIDE the window — a 180s override died at SIGTERM mid-rustc, 900s succeeded (measured 2026-08-30-acl-rejection-logging) — which is the relink the pre-build now absorbs

**`run`** — invoke test suites:
- **Command body:** `cargo nextest run --workspace --message-format libtest-json --profile ci 2>&1 | tee target/test-run.log` (via `cargo-nextest` 0.9.x per test-research; for per-unit invocation: `cargo test --lib ingest` or `cargo nextest run --filter-expr 'ingest'`)
- **Exit code semantics:** 0 on all-pass; non-zero = failure count (e.g., 5 failures → exit 5)
- **Output format:** JUnit XML (nextest `--message-format junit --output-file target/nextest/junit.xml`) + final-line regex `test result: ok. ([0-9]+) passed` for structured parsing
- **Test selection:** `cargo nextest run --filter-expr 'package(ingest) and test(::grpc::)' ` for fast iteration
- **Narrow a `pulse-app` run with `--filter-expr` / `-E` under `--workspace`, not with `-p`.** Measured 2026-08-15: `cargo nextest run -p pulse-app -E 'binary(…)'` failed to link the pulse-app test binaries with `crate X required to be available in rlib format` naming dependency crates (`muda`, `wasmtime_internal_cache`, `libduckdb_sys`, `arrow_cast`) **immediately after a green `cargo build --workspace --tests`** — `--workspace` unifies features across members while `-p` resolves a narrower subgraph, so the artifacts the build produced are not the ones the `-p` resolution wants. Re-running the same selection under `--workspace` compiled and passed clean. This does not make every `-p` form unusable (`cargo test --test <name> -p pulse-app` remains the documented single-binary path for the rlib family); it means a `-p` selection must not be assumed compatible with artifacts a `--workspace` build produced — match the scope of the run to the scope of the build.

**`status`** — query product state (REAL-PROCESS verdict since chunk `2026-08-30-diagnostics-un-muting-harness-truth-sweep`):
- **Command body:** `cargo xtask harness:status` (`xtask/src/harness_status.rs`), invoked by both `scripts/agent-run.{sh,ps1}` `status` verbs, which thread `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` into the xtask child. The verdict derives OUT-of-process from the registered `run/andromeda-pulse.pid` file, a liveness probe of the pid it holds (`ps -o stat=` on Unix, where a zombie `Z` counts as dead; `tasklist` on Windows), and the log family's newest-member mtime — a dead pid is `not-running` whatever the log's freshness says (chunk 2026-09-29-p-025-hue-shift-observable-made-gradable; before it, a crashed app read `running-healthy` for up to 60 s, measured on a CI boot smoke whose app panicked in 12 ms). The pure `classify(pid, alive, newest_log)` is pinned per arm, dead-pid and exited-child included, with its probe parsers pinned too. It is NOT a TauRPC `health` envelope and NOT computed in-script. It REPLACES the prior in-xtask-process `current_health()` call, which exited 0 unconditionally and could never say "not running" (the wrong-reason-pass this section previously recorded).
- **Verdict JSON (stdout):**
  ```json
  {
    "verdict": "running-healthy" | "stale" | "not-running" | "cannot-evaluate",
    "pid": 12345,
    "ended": null | "exit 0" | "signal 11 (SEGV)",
    "log_file_basename": "agent-latest.jsonl.2026-08-30",
    "last_write_age_seconds": 4,
    "stale_after_seconds": 60
  }
  ```
- **Exit code semantics:** 0 `running-healthy` (live pid + log written within `STALE_AFTER_SECONDS` 60) · 1 `stale` (live pid, log silent past the threshold) · 1 `not-running` (no live pid — a dead or zombie pid is `not-running` whatever the log says) · 2 `cannot-evaluate` (paths unresolvable). `classify(pid, alive, newest_log)` is a pure fn unit-pinned per arm, the dead-pid and exited-child cases included. `ended` (chunk 2026-09-29-ci-wall-time-and-round-trips) is the `run/andromeda-pulse.exit` record beside the pidfile, bounded to one line of ≤ 48 printable ASCII chars (anything else reads as no record, unit-pinned), reported only when the verdict is not `running-healthy`; real under both scripts since chunk 2026-09-30-perf-budget-gate-reads-real-samples, when the ps1 wrapper began writing the record (measured `"ended": "exit -1"`, `not-running`, exit 1, after `Stop-Process -Force`, whose `TerminateProcess(-1)` code the grammar accepts). The arms and exit codes are unchanged.

**`cleanup`** — tear down:
- **Command body:** Read the pid from `$PID_FILE` (the app's own `write_pid_file` value is canonical; the boot-time spawn pid covers only the crashed-before-write window); probe liveness across both pid spaces (msys `kill -0` first, then a genuinely-probing PowerShell `Get-Process` fallback — never `taskkill`/`tasklist /X` forms, never a `||` branch that manufactures the answer); TERM, bounded liveness-poll wait, KILL escalation
- **Idempotency:** safe to call twice — an absent pidfile with both ports refusing is `clean`
- **Verification:** the verdict derives ONLY from independent probes — pid liveness + TCP handshake on the RESOLVED `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT` at `127.0.0.1` — never from the terminate call's own status. **The 2026-08-30-acl-rejection-logging wrong-reason-pass is CLOSED** (chunk 2026-08-30-agent-harness-teardown-truth, measured RED→GREEN on the sh script: RED at HEAD reproduced cleanup-exit-0 with the app alive and both ports accepting; GREEN shows non-zero on every survival shape and zero on verified teardown; ps1 mirrored in lockstep, its live leg owed via the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger).
- **Exit code:** ONE bounded stdout token — `cleanup: clean | app-survived | ports-lingering | no-pid-ports-accepting` — exit 0 ONLY on `clean` (pid gone or never present, both ports refusing); exit 1 otherwise. The exit code is again evidence of teardown

**`logs`** — fetch product logs:
- **Command body:** resolve the ROTATED log FAMILY `agent-latest.jsonl*` across three precedence-ordered bases — the env override (`ANDROMEDA_PULSE_LOGFILE`, else `$ANDROMEDA_PULSE_DATA_DIR/logs/agent-latest.jsonl`), then `~/.andromeda-pulse/logs/agent-latest.jsonl`, then the data-dir `logs/` — taking the NEWEST match within the first base that resolves (the glob expands in lexical order and the date suffix sorts ascending), and `tail -F` it; exit 1 with a diagnostic when no base resolves. **The `*` is load-bearing, not cosmetic:** the sink is `tracing_appender::rolling::daily(log_dir, "agent-latest.jsonl")`, which DATE-SUFFIXES every file (`agent-latest.jsonl.YYYY-MM-DD`), so a bare-name reader — or the `*.log` glob this line carried until 2026-08-26 — silently finds nothing and the caller then false-reports an empty log on a perfectly healthy boot. Matches obs-plan §3 Log file location (daily rotation; previous day's file read when the current one does not yet exist) and the shipped `scripts/agent-run.sh`.
- **Format:** JSON lines from `tracing-subscriber` with `{"timestamp":"2026-05-02T16:18:34.567Z","level":"INFO","target":"ingest::grpc","message":"…","fields":{…}}`
- **Retention window:** all on-disk logs for test session (not auto-purged within test harness; agent may tail last 1000 lines)
- **Agent parsing:** `jq 'select(.level == "ERROR") | .message' logs.jsonl | head -20` for errors; `grep -o "rows_ingested: [0-9]*" logs.jsonl | tail -1` for last ingest count
