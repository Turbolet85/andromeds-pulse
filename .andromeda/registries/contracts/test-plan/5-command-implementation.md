### 5-command implementation

**`boot`** — start the product for testing:
- **Command body:** PRE-BUILD under the verb's own exported env (`cargo build --bin pulse-app --release`, then `cargo build -p xtask` — the readiness poll shells `cargo xtask`, so a stale xtask would otherwise rebuild inside the timed window), then spawn `target/release/pulse-app[.exe]` BY PATH in background — the `cargo run` wrapper is GONE, and the app's own `write_pid_file` writes the canonical pid (chunk 2026-08-30-agent-harness-teardown-truth; sh live-proven, ps1 mirrored — its boot/`ended` leg driven live once by hand at chunk 2026-09-30-perf-budget-gate-reads-real-samples, a committed leg still owed via the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger). Since chunk 2026-10-10-agent-harness-drives-the-console-engine the sh `boot` takes one optional word — none is the window app, as above; `engine` is the console engine; any other word is usage, exit 2, before a directory is made: `boot engine` pre-builds `cargo build --bin andromeda-pulse-engine --release` and xtask, spawns `target/release/andromeda-pulse-engine run` BY PATH under the same waiting wrapper (spawn record and exit record as for the window app) and polls `cargo xtask harness:ready --program console`. The word is sh only (`agent-run.ps1` is unchanged, so the two scripts no longer take the same words), has no committed shell-level test (the same §1 trigger), and is read end to end by `cargo xtask harness:engine-cycle` (§3 → Per-chunk gate discipline, Engine cycle gate form). The sh verb runs the app under a waiting subshell — the subshell's own stdin, stdout and stderr are `/dev/null`; the app's stdout and stderr go to `logs/boot.log` under the data dir — that writes the app pid to `run/andromeda-pulse.spawn` and, on reaping the app, its end to `run/andromeda-pulse.exit` (`exit N` or `signal N (NAME)`) — once `boot` returns, the app is otherwise an orphan whose end status nothing can read; `boot` takes the app pid from the spawn record, and none within 5 s is `boot: the app did not start (no spawn record)`, exit 1 (chunk 2026-09-29-ci-wall-time-and-round-trips). `agent-run.ps1 boot` mirrors the recorder since chunk 2026-09-30-perf-budget-gate-reads-real-samples: a hidden `powershell -EncodedCommand` wrapper launches the app, writes `run/andromeda-pulse.spawn` (the app pid) and on the app's exit `run/andromeda-pulse.exit` (`exit N`, ASCII, no BOM); `boot` polls the spawn record ≤ 5 s (50 × 100 ms), else prints `boot: the app did not start (no spawn record)` and exits 1, and on a failed readiness poll prints `app ended: {record}` or `app still running (pid N) but never reported healthy` before cleanup. Since chunk 2026-10-09-boot-smoke-s-early-exit-found-and-closed its readiness poll goes through `Invoke-Ready` (`cargo xtask harness:ready`) and its still-running arm carries the sh verb's conditional `the receivers never both accepted: …` line (Exit code, below); that edit was parsed by `pwsh` with 0 parse errors and has never run — no CI job and no dev host runs the script. The exit-witness arm, sh only and the window program's alone (since chunk 2026-10-10-boot-smoke-s-self-end-named-from-a-run; `scripts/agent-run.ps1` unchanged; `boot engine` never reads the variable, sets no preload, and neither removes nor creates the witness file): bare `boot` reads the harness-only `ANDROMEDA_PULSE_EXIT_WITNESS_LIB`, trimmed — unset or blank, the app is spawned as before; a regular file, the window app's spawn command runs with `LD_PRELOAD` set to it and `ANDROMEDA_PULSE_EXIT_WITNESS_FILE` set to `{data dir}/logs/exit-witness.jsonl`, neither exported, so the pre-build and every other verb run without them; a stale `logs/exit-witness.jsonl` of the same data dir is removed before the spawn; set and not a regular file is refused before the pre-build (Exit code, below). The library is `scripts/exit-witness.c` (built by `cc -shared -fPIC -O2`; it interposes `exit`, `_exit`, `_Exit`, `quick_exit`, `abort`, removes `LD_PRELOAD` and its file variable from the process environment at load, and is inert when the file variable is unset). Neither variable is read by `pulse-app`'s own code. The arm has no committed shell-level test (the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger). The 5-command set is unchanged: no sixth verb. Env vars unchanged: `ANDROMEDA_PULSE_DATA_DIR=$TMPDIR/andromeda-test-$$` (per-test isolation), `RUST_LOG=debug`, optional `ANDROMEDA_PULSE_OTLP_GRPC_PORT=0 ANDROMEDA_PULSE_OTLP_HTTP_PORT=0` (ephemeral ports)
- **Readiness signal:** Poll `cargo xtask harness:ready` (`xtask/src/harness_ready.rs`, since chunk `2026-10-09-boot-smoke-s-early-exit-found-and-closed`; the scripts thread `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` into the xtask child as they did for the status poll; since chunk 2026-10-10-agent-harness-drives-the-console-engine the sh script asks `--program window` under bare `boot` and `--program console` under `boot engine`) until its verdict is `ready`: the `cargo xtask harness:status` verdict the `status` verb uses reads `running-healthy` AND a TCP connection is accepted on `127.0.0.1` at each port resolved from `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT` (defaults 4317 / 4318), each attempt bounded at one second. One pretty-JSON object on stdout — `{verdict: ready | not-ready | wrong-program | ended | cannot-evaluate, pid, ended, program, otlp_grpc, otlp_http}`, six members since chunk 2026-10-10-agent-harness-drives-the-console-engine (pinned by set equality), each receiver label `accepting` | `refusing` (`null` on `cannot-evaluate`), `ended` the exit record when the verdict is `ended`, `program` the status verdict's own member — exit 0 `ready` · 1 `not-ready`, `wrong-program` or `ended` · 2 `cannot-evaluate` (paths unresolvable, or a port variable that is not 1 to 65535). `wrong-program` is the status verdict for the program asked (the log family's last `app.boot.engine` record names the other program, or none) and holds whatever the receivers answer; a dead pid is `ended` whatever was asked; with no flag, as the ps1 verb calls it, the verdict reads as before plus the member. - **Exit code:** 0 on `ready`; non-zero when no `ready` verdict arrives inside the window, and — in the sh verb, since chunk 2026-10-10-boot-smoke-s-self-end-named-from-a-run — exit 1 with `boot: exit witness library not found` on stderr, before the pre-build, when `ANDROMEDA_PULSE_EXIT_WITNESS_LIB` is set and names no regular file (driven once by hand, no committed test — the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger). **`run`** — invoke test suites:
- **Command body:** `cargo nextest run --workspace --message-format libtest-json --profile ci 2>&1 | tee target/test-run.log` (via `cargo-nextest` 0.9.x per test-research; for per-unit invocation: `cargo test --lib ingest` or `cargo nextest run --filter-expr 'ingest'`)
- **Exit code semantics:** 0 on all-pass; non-zero = failure count (e.g., 5 failures → exit 5)
- **Output format:** nextest's `libtest-json` stream (the Command body's `--message-format libtest-json`, teed to `target/test-run.log`) + final-line regex `test result: ok. ([0-9]+) passed` for structured parsing; no JUnit XML is written (as measured at chunk 2026-10-10-no-ci-step-reads-nothing: `.config/nextest.toml` holds no `junit` key)
- **Test selection:** `cargo nextest run --filter-expr 'package(ingest) and test(::grpc::)' ` for fast iteration
- **Narrow a `pulse-app` run with `--filter-expr` / `-E` under `--workspace`, not with `-p`.** Measured 2026-08-15: `cargo nextest run -p pulse-app -E 'binary(…)'` failed to link the pulse-app test binaries with `crate X required to be available in rlib format` naming dependency crates (`muda`, `wasmtime_internal_cache`, `libduckdb_sys`, `arrow_cast`) **immediately after a green `cargo build --workspace --tests`** — `--workspace` unifies features across members while `-p` resolves a narrower subgraph, so the artifacts the build produced are not the ones the `-p` resolution wants. Re-running the same selection under `--workspace` compiled and passed clean. This does not make every `-p` form unusable (`cargo test --test <name> -p pulse-app` remains the documented single-binary path for the rlib family); it means a `-p` selection must not be assumed compatible with artifacts a `--workspace` build produced — match the scope of the run to the scope of the build.

**`status`** — query product state (REAL-PROCESS verdict since chunk `2026-08-30-diagnostics-un-muting-harness-truth-sweep`):
- **Command body:** `cargo xtask harness:status [--program window|console]` (`xtask/src/harness_status.rs`), invoked by both `scripts/agent-run.{sh,ps1}` `status` verbs, which thread `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` into the xtask child. Since chunk 2026-10-10-agent-harness-drives-the-console-engine the sh `status` takes one optional word — none passes `--program window`, `engine` passes `--program console`, any other word is usage, exit 2 — while `agent-run.ps1 status` takes no word and passes no flag. The verdict derives OUT-of-process from the registered `run/andromeda-pulse.pid` file, a liveness probe of the pid it holds (`ps -o stat=` on Unix, where a zombie `Z` counts as dead; `tasklist` on Windows), and the log family's newest-member mtime — a dead pid is `not-running` whatever the log's freshness says (chunk 2026-09-29-p-025-hue-shift-observable-made-gradable; before it, a crashed app read `running-healthy` for up to 60 s, measured on a CI boot smoke whose app panicked in 12 ms). The pure `classify(pid, alive, newest_log)` is pinned per arm, dead-pid and exited-child included, with its probe parsers pinned too. It is NOT a TauRPC `health` envelope and NOT computed in-script. It REPLACES the prior in-xtask-process `current_health()` call, which exited 0 unconditionally and could never say "not running" (the wrong-reason-pass this section previously recorded).
- **Verdict JSON (stdout):**
  ```json
  {
    "verdict": "running-healthy" | "stale" | "wrong-program" | "not-running" | "cannot-evaluate",
    "pid": 12345,
    "ended": null | "exit 0" | "signal 11 (SEGV)",
    "program": "window" | "console" | "unknown",
    "log_file_basename": "agent-latest.jsonl.2026-08-30",
    "last_write_age_seconds": 4,
    "stale_after_seconds": 60
  }
  ```
- **Exit code semantics:** 0 `running-healthy` (live pid + log written within `STALE_AFTER_SECONDS` 60) · 1 `stale` (live pid, log silent past the threshold) · 1 `wrong-program` (since chunk 2026-10-10-agent-harness-drives-the-console-engine: with `--program`, a `running-healthy` or `stale` run whose log family records another program, or none) · 1 `not-running` (no live pid — a dead or zombie pid is `not-running` whatever the log says) · 2 `cannot-evaluate` (paths unresolvable). `not-running` and `cannot-evaluate` stand whatever program was asked, and with no flag the verdict is as before plus the `program` member: the label of the LAST `app.boot.engine` record of the log family, `unknown` when the family holds no such record or a label that is neither `window` nor `console`. The object has seven members since that chunk, pinned by set equality. `classify(pid, alive, newest_log)` is a pure fn unit-pinned per arm, the dead-pid and exited-child cases included; its signature is unchanged, and the program read beside it (`program_of`, `graded_arm`, `for_program`) is pinned per arm too. `ended` (chunk 2026-09-29-ci-wall-time-and-round-trips) is the `run/andromeda-pulse.exit` record beside the pidfile, bounded to one line of ≤ 48 printable ASCII chars (anything else reads as no record, unit-pinned), reported only when the verdict is not `running-healthy`; real under both scripts since chunk 2026-09-30-perf-budget-gate-reads-real-samples, when the ps1 wrapper began writing the record (measured `"ended": "exit -1"`, `not-running`, exit 1, after `Stop-Process -Force`, whose `TerminateProcess(-1)` code the grammar accepts). The `ended` member changed no arm and no exit code.

**`cleanup`** — tear down:
- **Command body:** Read the pid from `$PID_FILE` (the app's own `write_pid_file` value is canonical; the boot-time spawn pid covers only the crashed-before-write window); probe liveness across both pid spaces (msys `kill -0` first, then a genuinely-probing PowerShell `Get-Process` fallback — never `taskkill`/`tasklist /X` forms, never a `||` branch that manufactures the answer); TERM, bounded liveness-poll wait, KILL escalation
- **Idempotency:** safe to call twice — an absent pidfile with both ports refusing is `clean`
- **Verification:** the verdict derives ONLY from independent probes — pid liveness + TCP handshake on the RESOLVED `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT` at `127.0.0.1` — never from the terminate call's own status. **The 2026-08-30-acl-rejection-logging wrong-reason-pass is CLOSED** (chunk 2026-08-30-agent-harness-teardown-truth, measured RED→GREEN on the sh script: RED at HEAD reproduced cleanup-exit-0 with the app alive and both ports accepting; GREEN shows non-zero on every survival shape and zero on verified teardown; ps1 mirrored in lockstep, its live leg owed via the §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage` trigger).
- **Exit code:** ONE bounded stdout token — `cleanup: clean | app-survived | ports-lingering | no-pid-ports-accepting` — exit 0 ONLY on `clean` (pid gone or never present, both ports refusing); exit 1 otherwise. The exit code is again evidence of teardown

**`logs`** — fetch product logs:
- **Command body:** resolve the ROTATED log FAMILY `agent-latest.jsonl*` across three precedence-ordered bases — the env override (`ANDROMEDA_PULSE_LOGFILE`, else `$ANDROMEDA_PULSE_DATA_DIR/logs/agent-latest.jsonl`), then `~/.andromeda-pulse/logs/agent-latest.jsonl`, then the data-dir `logs/` — taking the NEWEST match within the first base that resolves (the glob expands in lexical order and the date suffix sorts ascending), and `tail -F` it; exit 1 with a diagnostic when no base resolves. **The `*` is load-bearing, not cosmetic:** the sink is `tracing_appender::rolling::daily(log_dir, "agent-latest.jsonl")`, which DATE-SUFFIXES every file (`agent-latest.jsonl.YYYY-MM-DD`), so a bare-name reader — or the `*.log` glob this line carried until 2026-08-26 — silently finds nothing and the caller then false-reports an empty log on a perfectly healthy boot. Matches obs-plan §3 Log file location (daily rotation; previous day's file read when the current one does not yet exist) and the shipped `scripts/agent-run.sh`.
- **Format:** JSON lines from `tracing-subscriber` with `{"timestamp":"2026-05-02T16:18:34.567Z","level":"INFO","target":"ingest::grpc","message":"…","fields":{…}}`
- **Retention window:** all on-disk logs for test session (not auto-purged within test harness; agent may tail last 1000 lines)
- **Agent parsing:** `jq 'select(.level == "ERROR") | .message' logs.jsonl | head -20` for errors; `grep -o "rows_ingested: [0-9]*" logs.jsonl | tail -1` for last ingest count
