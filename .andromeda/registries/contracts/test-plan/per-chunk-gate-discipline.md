### Per-chunk gate discipline

Every `/andromeda-phase`-authored chunk plan's `## Test Commands` section MUST include the **standard gate set** (unconditional, regardless of webview-only / Rust-only / mixed scope):

```
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo xtask capability-widening-check
cargo xtask check:ingest-progress
cargo xtask check:staged-artifacts        # staged bindings + capability grants vs pins (exit 0/1/2; also runs inside capability-drift)
cargo xtask capability-drift              # BEFORE the workspace nextest — see the ordering note below
cargo nextest run --workspace --profile ci
cargo nextest run -p pulse-app --features mcp-server --bin pulse-app -E 'test(emit_taurpc_bindings)'   # bindings regen: the last cargo-adjacent step
git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts   # the close, for a chunk adding no procedure
npm run lint --prefix pulse-app/ui        # webview gates: only when pulse-app/ui/** touched
npm run typecheck --prefix pulse-app/ui
npm run test --prefix pulse-app/ui
```

`cargo xtask check:ingest-progress` (added 2026-08-26) fails a run whose buffer consumer stopped draining. It keys on PROGRESS, not liveness — the stall definition at obs-plan §3/§10 is tick ABSENCE >45s, which the measured 2026-08-26 wedge satisfied throughout while persisting nothing. Four arms: a `buffer.consumer.stalled` record whose `reason` is not `recovered` ⇒ exit 1 · a recovery record ⇒ green · advancing ticks ⇒ PASS · no `buffer.tick` at all ⇒ NEUTRAL. The NEUTRAL arm is what makes it safe unconditionally — a chunk that booted nothing has no stream to judge, exactly like the in-process `perf_budget` grader, whose all-empty verdict with no arm required is NEUTRAL, never PASS.

`cargo xtask smoke:gap-resume` (added 2026-08-28) is a **SCENARIO leg, deliberately NOT a member of the standard gate set above.** It drives the ingest wedge's real shape — seed → GAP long enough that every service crosses its bootstrap window and the silence family escalates to tier1 → resume — under the direct-binary smoke form below (fresh `ANDROMEDA_PULSE_DATA_DIR` + `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` + `ANDROMEDA_PULSE_L4_DETERMINISTIC` set into the spawned app), and takes its verdict from the shipped `ingest_progress::evaluate` rather than a second detector. ~13 min, dev-host only, not CI-wired. **THREE arms, and they are different tests** (a third was added 2026-08-28 by chunk `2026-08-28-ingest-consumer-block-under-gap-resume`): `--sustained` (arm B — continuous feed, no gap, so no storm can form) is gate-grade; **arm A became gate-grade on 2026-08-28** (chunk `2026-08-28-duplicate-span-replay-fails-loudly`) when the consumer-wedge defect it reproduced was closed by the `duckdb`/`libduckdb-sys` 1.10502 → 1.10505 bump — it now exits 0 under a **TWO-HALF precondition**: the silence storm must have formed AND at least one append must have been REJECTED on replayed identities (`StormEvidence.append_rejections`, fed by `duckdb.append` records carrying `reject_reason`). Both halves are required because arm A drives the injector with `--replay`: without the rejection half a clean drain would prove the collision was ABSENT rather than survived, which is a pass for the wrong reason. Measured at promotion: 120 of 2270 appends rejected, consumer draining across 54 buffer ticks. `--reconnect-only` (`conflicts_with = "sustained"`) seeds, then reconnects IMMEDIATELY with no idle gap, which is what established that the idle window is NOT the operative variable. **A red on arm A is now a REAL REGRESSION, not a designed state** — and the standing instruction survives the promotion: arm A must **never** be weakened, removed, or `--expect-absent`'d to obtain a green wrap. It is the only on-demand reproduction of this defect class, so the guard is what keeps a future red diagnosed rather than hidden. (The repair-route ownership pointer is discharged.) **Each arm carries its OWN precondition, and no arm may borrow another's:** a gap-arm pass with no silence storm in the log reports INCONCLUSIVE, not PASS; a storm in the control arm is likewise INCONCLUSIVE; and the reconnect arm — which has no storm by construction — instead requires FEED evidence (at least one `duckdb.append`, via `StormEvidence::fed()`), so a run where the producer never delivered cannot report a vacuous pass. **Known gap — CLOSED 2026-08-28** (chunk `2026-08-28-duplicate-span-replay-fails-loudly`): the leg now guards `observe_minutes` against the stall threshold its verdict reads, via `observe_window_supports_verdict()` and `const STALL_ANNOUNCEMENT_SECONDS: u64 = 450` in `xtask/src/gap_resume.rs` — a window below the threshold is refused as INCONCLUSIVE before the run starts, rather than producing a structurally-impossible PASS. Unit-pinned at the boundary (7 m refused / 8 m accepted / the 9 m default accepted). The original measurement stands as the reason the guard exists: `--observe-minutes=3` reported PASS over a consumer that had in fact stopped, because 180 s cannot reach the 450 s announcement (chunks `2026-08-28-ingest-consumer-initiating-freeze`, `2026-08-28-ingest-consumer-block-under-gap-resume`).

`cargo xtask smoke:external-resolve` (added 2026-08-29, chunk `2026-08-29-app-registry-reconciliation`) is the **second SCENARIO leg** in that family — likewise **NOT a member of the standard gate set**, dev-host only, not CI-wired, `xtask/src/external_resolve.rs` with `--bootstrap-seconds` / `--observe-seconds`. `cargo xtask capability-drift` runs BEFORE the default-features `cargo nextest run --workspace` (the overseer's founder-delegated directive of 2026-09-30, first run at chunk 2026-09-30-dual-license). That workspace run rewrites `pulse-app/ui/src/bindings/index.ts` to the no-mcp shape (`taurpc`'s `export_types()` on every `Router::into_handler()`), so a drift read placed after it read a clobbered worktree; before it, the worktree bindings are still the committed mcp shape. The `--features mcp-server` `emit_taurpc_bindings` regen then follows the workspace run as the LAST cargo-adjacent step, repairing what that run rewrote, and a probe named against the chunk base closes the sequence: `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts`, exit 0 meaning the bindings end byte-identical to the base. That close is what was measured, for a chunk that adds no TauRPC procedure. A chunk that CHANGES the procedure set closes instead with (first run at chunk 2026-09-30-perf-instruments-measure-their-budgets, approved by the operator at its wrap): the `--features mcp-server` regen after the workspace run → two content probes on the worktree bindings (the new procedure's name; `grep -c '"mcp":'` ≥ 1) → `git add` of the regenerated bindings WITH the `EXPECTED_PROCEDURES` pin (index only, no commit) → `check:staged-artifacts`, then `capability-drift` LAST — both read the staged copy, and before the regen the committed bindings lack the pinned procedure, so drift cannot run earlier. The regen must also PRECEDE the `ui/dist` build and every release build a live leg drives: the taurpc proxy resolves methods against the `ARGS_MAP` bundled into `ui/dist`, so a dist built before the regen ships without the new method and a fire-and-forget caller no-ops silently (measured at that chunk: 1 bundle occurrence — the caller's own property access — vs 2 once rebuilt after the regen). `cargo xtask check:staged-artifacts` (added 2026-08-30-staged-bindings-assertion, `xtask/src/staged_gate.rs`) makes the staged assertion CODE inside the gate itself: it reads the git-INDEX copies of `pulse-app/ui/src/bindings/index.ts` + all `pulse-app/capabilities/*.json` (via a `git ls-files --stage` health probe then `git show :<path>` per subject) against `EXPECTED_PROCEDURES` + `staged_gate::EXPECTED_GRANTS`, with one pretty-JSON verdict on stdout (`{gate:"staged-artifacts", arm, verdict, bindings{…}, grants{…}}`), arms `staged-clean`/`staged-drift`/`cannot-evaluate` at exit 0/1/2, report twin `target/staged-artifacts/report.json`, and a staged DELETION of a subject or an UNPINNED `pulse-app/capabilities/*.json` file findings-RED (no neutral arm) — and `capability_drift()` RUNS that same staged assertion after its unchanged worktree diff, folding ANY non-clean staged outcome into its existing 0/1 failure exit. **Boot-smoke gate (conditional).** Chunks whose plan touches a boot/setup path — `pulse-app/src/main.rs`, `crates/ui-bridge/src/`, `pulse-app/src/observability.rs` (boot-time subscriber/allowlist init, before the OTLP bind), `pulse-app/src-tauri/tauri.conf.json`, or `pulse-app/capabilities/*.json` — MUST additionally include a runtime smoke gate: `cd pulse-app && npx @tauri-apps/cli dev` with a 60-second timeout, watching stdout for boot-completion signals (`Local:` / `ready in` / `Compiled successfully`) before SIGTERM.

**Direct-binary smoke variant (accepted alternative form).** When the verification needs runtime state neither `npx @tauri-apps/cli dev` nor the harness `run` verb can express — a fresh `ANDROMEDA_PULSE_DATA_DIR`, an env-gated mode such as `ANDROMEDA_PULSE_L4_DETERMINISTIC=true`, or a sustained OTLP load from `inject_demo` — launch the product binary directly under those env vars in EITHER profile (`target/debug/pulse-app.exe` or `target/release/pulse-app.exe`; the harness `boot` verb itself IS the direct-binary form since chunk 2026-08-30-agent-harness-teardown-truth — it pre-builds then launches `target/release/pulse-app[.exe]` by path, no `cargo run` wrapper), seed over the real receiver, then assert from the run's own artifacts: 0 `app.panic.fatal` / 0 `ERROR` in `<data_dir>/logs/agent-latest.jsonl*`, and clean shutdown by SPECIFIC pid (`powershell -NoProfile -Command "Stop-Process -Id <pid> -Force"`) with `:4317`/`:4318` confirmed released. **The clean-log assertion binds the GREEN leg only.** A MEASURE-FIRST chunk runs the same form twice — once at HEAD to witness the defect, once after the fix — and the RED leg is by construction an unhealthy run. **What the RED leg PRODUCES depends on the defect's shape, and only one of the two shapes emits an ERROR.** A REJECT-shaped defect (a write refused, a batch failed) emits the ERROR it is measuring, so asserting 0 ERROR over it would contradict the measurement. A **BLOCK-shaped** defect emits nothing at all — nothing returns, so nothing reports — and a RED leg over it carries **0 `ERROR` and 0 `app.panic.fatal`**, which makes the clean-log assertion pass **VACUOUSLY** (the same wrong-reason-pass hazard this section already records for the `status` verb). For that shape the evidence of record is **absence of progress**: a frozen `rows_ingested`, consecutive zero-delta `buffer.tick`s, `buffer.consumer.stalled`, `ingest.channel.full`. Measured 2026-08-28 (chunk `2026-08-28-ingest-consumer-initiating-freeze`): a RED leg reproduced a 450 s consumer stall with 0 ERROR and 0 panics throughout. Decide which shape the leg is measuring BEFORE choosing its evidence. Each leg gets its OWN fresh data dir so neither reads the other's residue, and the RED leg records its expected ERROR (target + `reject_reason`) as evidence rather than as a gate failure. (Codified 2026-08-23 at chunk `2026-08-23-metrics-points-identity`, whose RED leg recorded one `duckdb.append` ERROR with `reject_reason: "append_failed"` by design.) `bash scripts/agent-run.sh status` still runs as the listed harness gate — and since chunk `2026-08-30-diagnostics-un-muting-harness-truth-sweep` it is TRUTHFUL about liveness: the verb delegates to `cargo xtask harness:status`, so a no-app run exits non-zero with `verdict: "not-running"` (live-proven 2026-08-30 — the 2026-08-23 "exits 0 and emits a full payload even when nothing is running" measurement described the retired in-process form); the direct-binary artifacts remain the evidence of record for run-specific claims. Measured 2026-08-15 (chunk 2026-08-15-tier-1-incident-path-investigation): two full boots on separate fresh data dirs verified a boot-time allowlist change that no in-process form could observe, since the fields under test are only produced by a live storm. **Process-end witness form (integration tier).** A claim that a record SURVIVES THE PROCESS ENDING is cross-process, so it is witnessed by re-exec children, never in-process (chunk `2026-10-01-conductor-return`, `pulse-app/tests/integration_exit_cause_record.rs`): the parent re-runs the test binary with `--exact <fn>` and an arm name in the environment; each child calls `observability::init` on its OWN TempDir data dir, ends its process through ONE class, and the parent reads the child's `agent-latest.jsonl*` family only after the child has ended — exactly one `app.exit` per loggable class, its fields rendered, 0 full paths, 0 planted canary. Child-ran proof is IN-ARM: each arm requires the child's `app.boot.tracing.init` record, because child stdout is discarded (`Stdio::null()`) and a `--no-capture` read shows nothing from children. A once-flag whose sink's only drain is a guard drop is pinned by the emitter's RETURN value reported through the child's exit code, never by a file read — the first flush closes the sink, so a second record can never reach the file and a file read passes with the flag removed (measured: the whole once-guard neutralized left every file-reading arm green). Arms that only Unix can run (`std::process::exit` reaching `atexit`; SIGTERM ending the child BY signal 15) are `cfg(unix)` — run natively by `cargo nextest run --workspace` on the Linux dev host (Omarchy, since the 2026-10-03 host move; measured 2575 = 2573 + these two arms at chunk `2026-10-02-incident-events-readable-through-mcp`) and by CI lint-test Linux/macOS; on a Windows host they are unrunnable. The form cannot reach the ends unloggable by construction (SIGKILL, `_exit`, Windows `TerminateProcess`, a Rust `std::process::exit` on Windows, pre-sink failures); RED at base is the block-shaped absence of the record (§3 Direct-binary smoke variant's shape rule).
