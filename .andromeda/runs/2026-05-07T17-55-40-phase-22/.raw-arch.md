## Constraints

- Workspace placement: chunk #25 wires bindings emitted from each crate's TauRPC router; the routers themselves live in their owning library crates (`ui-bridge`, `viz`, `snapshot`, `plugins`, `mcp-server`, `workspace-detector`) per the one-router-per-module-crate rule, and the binding generation invocation is mounted in `pulse-app/` (the binary that wires the workspace) — no new crate, no rename of any reserved workspace name (per arch §Conventions "Workspace API style — internal Rust↔webview" + §Occupied Resources Cargo workspace crate names + §Project Intent Template patterns).
- TauRPC procedure naming MUST conform to one of two authorized shapes — top-level bare `snake_case` verbs for the cross-cutting envelope (`app_info`, `health`, `ready`, `get_settings`, `update_settings`); `<router>.<verb>` dotted namespaces for per-crate routers (`traces.query`, `snapshot.generate`, etc.). Both segments are `snake_case` (per arch §Conventions "Endpoint naming"). Generated `.d.ts` MUST preserve this shape verbatim; binding generation must not invent variant naming (e.g., camelCase, prefixing).
- Every type that appears in any `#[taurpc::procedure]` arg or return MUST be `serde::Serialize` (and `Deserialize` for inputs) — enforced at compile time by the TauRPC derive macros (per arch §Cross-cutting Patterns "Cross-bridge data shape"). Chunk #25's binding generation depends on this constraint already being satisfied across the existing routers; any unserializable type is a hard compile error, not a runtime issue.
- AppError serde envelope: every TauRPC procedure must already return `Result<T, AppError>` per arch §Conventions "Error response schema (Tauri IPC)" with the stable variants enumerated there; chunk #25 generates bindings against this contract but does NOT introduce or modify the AppError surface (chunk #26 owns AppError + From impls per the route plan — chunk #25 must not pre-empt #26's design).
- The `tsc --noEmit` typecheck step is the Inherited-Defaults-locked typecheck gate for the webview side (per arch §Stack "Code quality (lint/typecheck)" + §Infrastructure Patterns Build system + §Inherited Defaults Code quality). Chunk #25 wires this command into the local agent harness AND CI; webview TS sources consume only the generated `.d.ts` (no manual TS re-declaration of command signatures).
- Generated bindings MUST cover the canonical procedure list in arch §Occupied Resources Tauri IPC routes (top-level `app_info` / `health` / `ready` / `get_settings` / `update_settings` plus `traces.*` / `metrics.*` / `logs.*` / `snapshot.*` / `plugins.*` / `workspace.*` / `mcp.*` when feature-gated). The `mcp.*` router is feature-gated `--features mcp-server` per arch §Inherited Defaults + §Occupied Resources, so its bindings are conditionally included — generation must respect feature-gate hygiene (per arch §Cross-cutting Patterns "Feature-gate hygiene": flag-specific dependencies only enter the build graph when the feature is enabled).
- Webview IPC capability policy: the main webview window runs under `pulse:default`, which permits exactly the procedures enumerated in §Occupied Resources and nothing else. Adding a new TauRPC procedure requires both router registration in the owning crate AND an entry in `pulse-app/capabilities/` (per arch §Cross-cutting Patterns). Chunk #25 generates bindings for the existing surface — it does not add new procedures — but the `streams.*` namespace introduced in chunk #23 is NOT in §Occupied Resources (D3 drift carry-over per state.yaml.drift_warnings); chunk #25 will surface this as a typed binding with no canonical-resources backing if it enumerates router namespaces. Defer remediation to chunk #27 (xtask capability-drift) per the route#23 wrap recommendation; flag in plan implementation notes only.

## Patterns to follow

- Per-crate TauRPC router + `pulse-app/` mount pattern: each library crate exposes a router type via its public contract module; `pulse-app/src/main.rs` (or a sibling module per the chunk #23 precedent of `pulse-app/src/streams.rs`) instantiates and merges them into the single TauRPC IPC handler. Binding generation runs over the merged router surface (per arch §Project Intent "Template patterns" + §Cross-cutting Patterns "Module dependency direction": dependencies flow toward `pulse-app`).
- Feature-gate hygiene for `mcp-server`: `mcp.*` router bindings are only emitted when `--features mcp-server` is enabled at build/generate time; do not include them in the default-build `.d.ts` artifact (per arch §Cross-cutting Patterns "Feature-gate hygiene" + §Conventions "Feature flags": Cargo features are `kebab-case`, default features are minimal). The double-gate (compile-time `--features mcp-server` + runtime `ANDROMEDA_PULSE_MCP_ENABLED=true`) is enforced at the rmcp boundary; chunk #25 only handles the compile-time gate at binding generation.
- TypeScript binding emission location under `pulse-app/ui/`: per arch §Infrastructure Patterns project directory tree, `pulse-app/ui/` is the webview source root; emitted `.d.ts` lives under that tree (the precise path is implementation detail owned by the chunk plan, not arch). Webview source files follow the design specialist's convention per arch §Conventions "File naming".
- TauRPC IPC handler is a single integrated invoke handler: per the session-handoff curated learning (`.claude/rules/security.md` §Session Additions 2026-05-03), `taurpc::create_ipc_handler(...)` dispatches all router methods at the channel level — chunk #25's binding generation runs over this same merged surface. Per-procedure capability JSON entries are NOT generated by TauRPC (only `core:default` + plugin-level perms appear in capabilities/JSON). Chunk #27 (xtask capability-drift) will introspect at router-level granularity, not per-procedure.
- Module visibility discipline: each crate's TauRPC router type and its procedure traits must be `pub` from the crate's contract module (the only `pub` surface), with internals `pub(crate)`; no `pub use` re-export across crate boundaries except in the explicit contract module (per arch §Conventions "Module visibility discipline").

## Anti-patterns to avoid

- Manual TypeScript re-declaration of any TauRPC command signature in webview sources — direct violation of arch §Conventions "Workspace API style — internal Rust↔webview" ("no manual TypeScript re-declaration of command signatures. Frontend consumes only TauRPC-generated `.ts` bindings") and §Established Decisions [Tauri IPC Bridge — Surface 2] rationale ("eliminating the drift bugs that an 8-module monolith with 30+ commands would otherwise produce"). Webview must consume only the generated bindings.
- Inventing a new IPC procedure naming shape (e.g., `streams_subscribe_spans` flat snake_case, or `streamsSubscribeSpans` camelCase) — only the two authorized shapes from arch §Conventions "Endpoint naming" are permitted (top-level bare `snake_case` for the cross-cutting envelope; `<router>.<verb>` dotted for per-crate routers). The carried-over `streams.*` namespace from chunk #23 already follows the dotted-namespace shape and is not the issue; the issue is its absence from §Occupied Resources, which chunk #27 owns.
- Bypassing the TauRPC bridge by exposing stock `#[tauri::command]` handlers alongside TauRPC procedures — TauRPC was chosen explicitly over stock `#[tauri::command]` per arch §Established Decisions [Tauri IPC Bridge — Surface 2] (per-procedure capability JSON pairing for stock commands does not match TauRPC's router-level granularity; mixing the two creates capability-policy ambiguity).
- Coupling chunk #25 binding generation to OTLP receiver wire shape, DuckDB schema, or any other §Standard-Contracts external surface — chunk #25 is internal-IPC only. The OTLP `:4317`/`:4318` and MCP stdio surfaces are spec-fixed (per arch §Standard Contracts "OTLP receiver — spec-conformant" + "MCP server — spec-conformant"); they are not bound to TauRPC bindings and any conflation breaks Standards-track-at-the-edges discipline (per arch §Design Philosophy).
