# security extract

## Relevance
Partial — a corpus **write-path** change to persisted user-content under the scrubber mandate, the encrypted-at-rest substrate, and a parameterized-SQL boundary; no auth/network/dependency surface is added, but the folded `cargo audit` PREREQ is squarely mine.

## Constraints
1. **Every corpus write path must scrub before write.** security-plan §Security Anti-Patterns → Logging (Uniform scrubber coverage) states the intended posture that any attribute value crossing into persistent storage (`corpus.db`) passes `scrub_attribute()` first, and enumerates the incident-summary boundary explicitly — `Incident.resolution_summary_text` at three paths including the resolution-summary final write. Whichever remedy P4 picks (status-guarded UPDATE re-reading at write, or delta-persist), it must not introduce a corpus write that bypasses that. Whether the write path this chunk edits already routes through `scrub_attribute` at HEAD is research's question.
2. **New SQL predicates bind, never interpolate.** security-plan §Input Validation (query-parameter row) mandates prepared statements with `?` placeholders and "reject identifier interpolation entirely"; §Security Anti-Patterns → Input bans `format!("SELECT … WHERE x = '{}'")` as the dominant 2026 vuln class. The status/CAS predicate added to `update_incident_status` must be a bound `?N` parameter, and the status literal must not be spliced into the statement text.
3. **The at-rest posture must not be relaxed to make the guard expressible.** security-plan §Data Protection → At rest → Persistent incident corpus requires cell-level AES-256-GCM with only table and column *names* plaintext and BLOB cell payloads opaque without the key. No column may be demoted from encrypted cell to plaintext (or to a deterministic ciphertext) so that a WHERE predicate can compare it. Whether `incidents.status` / `updated_unix_nano` are already stored in a SQL-comparable form — and therefore whether a status guard is expressible without such a demotion — is research's question, and it gates the P4 shape choice.
4. **The new failure/no-op arm must sanitize at all three boundaries.** security-plan §Error Handling requires TauRPC procedures to collapse internal `thiserror` enums to `AppError::{Storage,Internal,…}` with a sanitized one-liner, OTLP to `tonic::Status`, and MCP to a JSON-RPC 2.0 error object, with no stack traces, file paths, Rust struct names, or library versions crossing. A conditional UPDATE inverts today's semantics — `rows == 0` becomes the *normal* refused-stale-write path — so whatever replaces the existing sole error arm must stay a bounded, sanitized category, including on the cross-process MCP read surface (§Threat Model Summary → MCP stdio vector).
5. **RED/GREEN evidence carries counts and categories, not content.** security-plan §Logging &amp; Monitoring → What NEVER to log bans OTLP attribute values, DuckDB query parameter values ("log query identifier + parameter count instead"), snapshot contents, and MCP tool response bodies. The corpus read-back leg and any stale-write diagnostic must emit counts / status / bounded ids, not incident payload or resolution-summary text.
6. **Dependency gates hold, and the standing deferral's between-point discipline is owed.** security-plan §Dependency Security → CI integration requires `cargo deny check bans licenses sources` green and forbids relaxing `multiple-versions = "deny"` or skipping the `tonic` canary; the Standing deferral clause requires that a between-interval wrap re-verify basis + overlap first-hand and record `probe skipped per ratified interval (next: {point})` — never a silent skip. The plan's clause names session 52 as the next full-form point.
7. **Conditional — a new IPC surface for the read-back leg carries two obligations.** If the verification leg adds a TauRPC procedure, security-plan §Security Anti-Patterns → API requires its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` *and* a validated argument struct (capability JSON does not gate per-procedure); §API Security → TauRPC capability authorization is the same rule from the control side. The chunk scope states no new instrumentation is needed for VERIFY, so the expected shape is that this constraint discharges as a no-op.

## Patterns to follow
- **`scrubbed_clone` / `scrubbed_l4_json` projection shape** — the established form for producing a scrubbed projection at a corpus write boundary (`BaselineState::scrubbed_clone`, `StormStateSnapshot::scrubbed_clone`, `scrubbed_l4_json`), per security-plan §Security Anti-Patterns → Logging enumeration. If the remedy re-reads or re-projects an incident at write time, reuse this rather than minting a new path.
- **Bounded-category error surfacing** — `PromptRejection::label()` is the only thing that reaches the log on the L4 argv boundary, and `interpretation.inference.error` carries bounded categories with no payload bytes (security-plan §Input Validation → L4 inference argv prompt row). Same shape for a "stale write refused" signal.
- **Count-only allowlisted observable** — `incidents.list_active.request` → `item_count` is an EXACT-allowlist count leaf; keep the write-race evidence at that granularity per §Logging &amp; Monitoring → What NEVER to log.
- **Fail-closed rather than silent degrade** — `ANDROMEDA_PULSE_L4_ALLOW_ROOT` rejects every candidate when set-but-unresolvable rather than falling through to the unguarded path (security-plan §Security Anti-Patterns → Input, NARROWED EXCEPTION). Applied here: if the guard predicate cannot be evaluated, the write should refuse, not fall back to today's unconditional UPDATE.
- **Both-sides / choke-point discipline** — where one function feeds several consumers, the control attaches at the choke point (`extract_service_name` feeding three consumers, per §Security Anti-Patterns → Logging). The scope notes persist and auto-resolve call the *same* trait method; a guard placed at that shared method covers both writers, a guard placed at one call site does not.

## Anti-patterns to avoid
- NEVER build the guarded UPDATE by string-interpolating the status or id into the SQL — per security-plan §Security Anti-Patterns → Input (`format!("SELECT … WHERE … = '{}'")` ban; prepared statement + `?` binding is mandatory).
- NEVER log raw incident payload / resolution-summary content, DuckDB or corpus query parameter values, or MCP tool response bodies in the RED-arm or read-back diagnostics — per security-plan §Security Anti-Patterns → Logging (bullets 1 and 3).
- NEVER let the new failure arm expose Rust struct names, SQL text, stack traces, or file paths in `AppError::Internal { message }` surfaced to the webview — per security-plan §Security Anti-Patterns → Logging (bullet 4) and §Error Handling.

## Contract bindings
- **PII scrubbing ↔ obs + tests.** The scrubber mandate (security-plan §Security Anti-Patterns → Logging) binds to the obs plan's PII-scrubbing section and to the tests harness: RED-arm fixtures must not carry real PII/secrets — the house pattern is a canary literal counted at 0 occurrences in the log, and mutation checks proving the pins discriminate.
- **Observable allowlist ↔ tests harness.** The `incidents.list_active.request` → `item_count` leaf named in the chunk scope is guarded by `pulse-app/tests/unit_observability_allowlist_incident_diagnostics.rs` (six pins, incl. `no_widening_prefix_key_shadows_the_incident_leaves`); any field added to that target for the VERIFY leg is an allowlist edit the obs domain owns and this domain's no-content rule constrains.
- **CI security gate ↔ tests §CI Integration.** `cargo deny check bans licenses sources` runs as a job in the one workflow per security-plan §Dependency Security → CI integration; the standing-deferral record belongs in this chunk's report, not in a new workflow.
- **At-rest posture ↔ arch.** security-plan §Data Protection → At rest cross-references arch §Occupied Resources Corpus SQLite §At-rest posture as the locked-schema master; the chunk's "no DDL / `SCHEMA_VERSION` bump expected" boundary is an arch escalation if the P4 shape breaks it, and the encryption-posture half is mine.
