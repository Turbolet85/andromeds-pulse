# obs extract

## Relevance
Relevant — a corpus write-path repair whose whole signature is "every write succeeds and nothing logs", verified at the wire against registered self-observation observables; obs owns the leaf/field contract for anything the fix emits and the log side of the VERIFY leg.

## Constraints
- Any NEW target the fix emits (e.g. a stale-write-rejected or writes-applied signal) requires an **EXACT** allowlist leaf enumerating **every** field its emit site emits, and **no bare `triage` / `triage.incident` / `incidents` prefix key may exist** — a partial leaf redacts some fields while siblings render fine, and every gate passes (per obs-plan §8 Default-deny posture → Incident-path diagnostic leaves).
- Any leaf guard must live under `pulse-app/tests/`, not in `observability.rs`'s own `mod tests` — `[lib] test = false` compiles a src-level guard but never runs it; the family's existing guard is `pulse-app/tests/unit_observability_allowlist_incident_diagnostics.rs` (per obs-plan §8, bootstrap-window / cue-tick leaf entries).
- Dual-site rule: a new WARN/INFO target must be registered at **both** §6 (log-level mapping, with its emission discipline stated) and §8 (allowlist leaf); a §8-only apply leaves §6 stale (per obs-plan §6 Log levels mapping `warn` row + §8).
- Hot-path ban: the persist cycle writes **every** active row, so no per-incident-row emission is permitted; counts fold once per cycle and ride out as FIELDS on the existing per-cycle record (per obs-plan §11 Telemetry Strategy hot-path rule + §11 Logs "never log in hot path at info"; §5 tick-aggregated-as-FIELDS convention).
- Identity/query bans: incident identity, `scope_id`, title/detail, payload and workspace are never loggable on this family (the registered leaves are counts + bounded static labels only), and the UPDATE's SQL text and bound parameter values are barred — `query_id` + `param_count` only (per obs-plan §8 Incident-path leaves + Data classification rules Vector 5; §11 Spans/Logs).
- Module-boundary error discipline: a genuine write-path failure must surface at WARN/ERROR with a **bounded** `error_category` and no stack trace, struct names or paths; a predicate that legitimately declines a stale write is an expected outcome, not a module-boundary error (per obs-plan §10 Standard+ invariants → Module-boundary error logging; §7 Error classes; Vector 2).
- Every emitted line must satisfy the NDJSON contract — `timestamp` / `level` / `target` / `message` / `fields` plus the default subscriber identity fields — since that schema is binding *from* the test plan (per obs-plan §3 Log format JSON schema; §6 Required fields).

## Patterns to follow
- **Liveness-vs-progress precedent (nearest analogue):** the 2026-08-26 wedge was the same silent-success shape — every signal healthy while nothing landed. The remedy shape the plan records is a companion **progress** field on an existing record plus a once-per-**transition** WARN (`buffer.consumer.stalled`: `reason` / `consequence` / bounded numerics), never per batch, with the threshold sited above the in-spec cap (per obs-plan §1 Heartbeat ticks; §3 Stall detection; §10 Standard+).
- **Fold at the POST-write site:** the `redactions_applied` precedent requires a counter to be folded after the write actually succeeds, so a rejected/skipped write contributes zero — otherwise the counter asserts work that did not persist (per obs-plan §5 Metric Coverage, `redactions_applied` Counter row, persisted-cells-only rule).
- **Exact leaf + fallback discriminator, mutation-checked:** guards must assert the field SET in both directions **and** pin that the prefix-fallback set cannot serve the target; a resolve-only probe passes vacuously (per obs-plan §8 `buffer.consumer.stalled` and `triage.cue.tick` leaf entries).
- **Existing registered observables for the VERIFY leg:** §8 registers `incidents.list_active.request` → `item_count` and `triage.incident.persist` → `incident_count`, `persist_kind`, `duration_ms` as EXACT leaves. Whether both emit unredacted at HEAD, and whether their counts alone are sufficient to witness in-app/corpus divergence, is research's question (per obs-plan §8 Incident-path diagnostic leaves).
- **Measurement surface:** RED and GREEN arms are read from `~/.andromeda-pulse/logs/agent-latest.jsonl` by `jq`/tail, not argued; any new xtask check script over that file must be NEUTRAL-tolerant and scoped to the run window (per obs-plan §3 Self-observation paste-to-AI; §10 CI gates + Load-profile constraints).

## Anti-patterns to avoid
- Emitting one record per incident row inside the persist cycle or per resolve decision — the plan's own counter-example is `cadence.trigger` at one record per cycle driving a 131 MB log (per obs-plan §11 Telemetry Strategy / Logs hot-path bans).
- Adding a field or target without its exact leaf, or shipping a guard that only asserts `for_target(...).is_some()` — the plan records both failure modes as measured (per obs-plan §8 muted-diagnostic backlog + the mutation proof in the `interpretation.incident.created` entry).
- Putting the incident id, `scope_id`, payload, workspace, or the UPDATE's SQL/bound values into a diagnostic field "for debuggability" (per obs-plan §11 Logs + PII Scrubbing; §8 Vector 5).

## Contract bindings
- **obs ↔ tests harness:** the NDJSON log schema in §3/§6 is verbatim from the test plan's Test Harness Contract — obs aligns to tests, not vice versa; the chunk's wire proof consumes that format (per obs-plan §3 Log format JSON schema).
- **obs ↔ corpus read-back (scope in-scope item 2):** obs owns only the log half of the VERIFY pair (`incidents.list_active.request` → `item_count`, §8); the corpus read-back leg itself is arch/domain, and obs asserts only that the two are compared on registered, unredacted fields.
- **obs ↔ security:** §8 Vectors 2 and 5 govern what an `AppError` arising from a guarded UPDATE may carry across the IPC bridge (no struct names, paths, versions, or query parameters).
- **obs ↔ the "Diagnostics un-muting + harness-truth sweep" entry:** §8's muted-diagnostic backlog records `triage.incident.auto_resolve.tick` → `duration_ms`, `evaluated_count`, `resolved_count` as resolving to **no** allowlist entry (the one target the original census mechanism describes correctly), owned by that sweep entry — i.e. the *direct writer's* own tick observable is required-but-unregistered, and un-muting it is explicitly another entry's item. Whether this chunk's RED/GREEN measurement needs those fields is research's question.

## Acceptance criteria contributions
- (obs) Any emission the fix adds or changes carries an EXACT §8 leaf enumerating every field its emit site emits, guarded under `pulse-app/tests/` with field-set-both-ways plus a prefix-fallback discriminator, and introduces no bare `triage` / `triage.incident` / `incidents` key (per obs-plan §8 Default-deny posture → Incident-path diagnostic leaves).
- (obs) RED and GREEN arms are both read from `agent-latest.jsonl` as NDJSON carrying the required fields (`timestamp` / `level` / `target` / `message` / `fields` + service identity defaults) — measured, not argued (per obs-plan §6 Required fields; §3 Log format JSON schema).
- (obs) No per-incident-row log line is introduced on the persist cycle or the resolve path, and no new field carries incident identity, `scope_id`, payload, workspace, or the UPDATE's SQL text / bound values (per obs-plan §11 hot-path + Logs bans; §8 Vector 5).
- (obs) The GREEN leg shows zero `app.panic.fatal` and no new ERROR line for a write the guard legitimately declines — a skipped stale write is an expected outcome, not a module-boundary error (per obs-plan §10 Always-required SLO invariant + Standard+ Module-boundary error logging).
