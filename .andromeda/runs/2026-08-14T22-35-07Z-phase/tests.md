# tests extract

## Relevance
Relevant — the chunk moves a derivation into a shared crate, touches a boot path, and drives the MCP sidecar, all of which the test plan governs directly.

## Constraints
- Standard tier applies: unit tests are the primary layer with module-boundary coverage, and the coverage gate is ≥ 75% line / ≥ 70% branch / ≥ 85% function on new code (per test-plan §1 Test Scope Summary, §10 Quality Gates & Coverage Targets).
- The chunk plan's `## Test Commands` MUST carry the unconditional standard gate set (fmt / clippy `-D warnings` / `cargo nextest run --workspace --profile ci` / `cargo xtask capability-drift`); the three `pulse-app/ui` webview gates are excludable only if the final Files-to-modify + New-files lists touch zero `pulse-app/ui/**` paths — which the scope's Surfaces table currently suggests, but the exclusion is decided from the final file list, not the surface table (per test-plan §3 Per-chunk gate discipline).
- The boot-smoke gate is mandatory here: the scope names `pulse-app/src/main.rs:688` as a modified site, which is an enumerated boot/setup path, so a 60s `@tauri-apps/cli dev` smoke leg watching for boot-completion stdout before SIGTERM is required in addition to the standard set (per test-plan §3 Boot-smoke gate (conditional)).
- Test-home rule for the derivation: library crates take co-located `#[cfg(test)] mod tests`, but `pulse-app` is the exception — its `[lib] test = false` means co-located tests compile and never run, so any pulse-app-side probe must be a separate target under `pulse-app/tests/*.rs` reaching internals via `pub` + `#[doc(hidden)]` (per test-plan §2 Test directory + naming conventions, §4 Conventions → Test file location). This decides where deliverable 3's normalization unit can live depending on which crate P4 picks as the home.
- Any leg that drives the MCP sidecar must satisfy BOTH gates — compile-time `--features mcp-server` and runtime `ANDROMEDA_PULSE_MCP_ENABLED=true` — and is driven as a subprocess over JSON-RPC 2.0 stdin/stdout, asserting a `result` (not `error`) envelope (per test-plan §1 coverage-scope `mcp-server` row + coverage trigger "MCP feature + runtime gating"; §5 Module ↔ MCP sidecar; §6 P3).
- The observation leg's incident corpus must be self-bootstrapped at test runtime (OTLP ingest / Rust builders) inside a `tempfile::TempDir` + `ANDROMEDA_PULSE_DATA_DIR` isolate — no pre-baked DB, `.sql` seed, or committed corpus snapshot (per test-plan §1 agent-driven-discipline: self-bootstrapping test data; §7 Test Data & Fixtures).
- Every leg — including the before-evidence observation — must emit a deterministic machine-parseable signal (exit code + structured stdout/JSON/log-line match), with no human-read checkpoint (per test-plan §1 agent-driven-discipline: no manual verification; §2 Agent-runnable invariants). The Conductor arm re-run's operator-headful half is the shape §6 P5 handles as a *documented residual*, not a silent coverage claim — mirror that framing rather than asserting agent coverage of it.

## Patterns to follow
- workspace-detector ↔ filesystem boundary pattern: stage a temp dir carrying the `.andromeda/` marker, override the data dir by env, invoke detection, assert the *canonical* path (`assert_fs` / `assert_cmd`, per test-plan §5 Boundary types covered). This is the existing home for the canonicalization assertions deliverable 3 needs.
- `rstest` `#[fixture]` + builder factories (`MockTraceSpan::builder()` etc.) for reusable seed data, composed rather than hand-rolled per test (per test-plan §7 Test Data & Fixtures; §4 Fixture pattern at unit level).
- MCP subprocess driver shape from §6 P3: `tokio::process::Command` with piped stdio, write a `tools/call` frame, parse line-delimited stdout, assert the result array's schema — the same shape a `query_incident_list` read leg would take.
- Readiness by polling the harness `status`/`health` signal rather than fixed waits when a leg needs the app up (per test-plan §3 5-command implementation → `boot` readiness signal).
- The scope names `pulse-app/tests/integration_constellation_severity_workspace_key.rs` (P-079) as the existing regression guard, which is the `pulse-app/tests/*.rs` target shape §2/§4 require; whether that guard already asserts both-end (app + sidecar) key parity, or only the app side, is research's question.

## Anti-patterns to avoid
- No `sleep(N)` for synchronization anywhere in the observation or smoke legs — wait on an explicit signal (per test-plan §11 E2E).
- No mid-test `std::env::set_var`-style monkey-patching to fake the data dir or workspace key; inject via fixture/constructor (per test-plan §11 Mocking).
- Do not assert against crate-private internals of the relocated derivation — the assertion surface must be the new home crate's public boundary (per test-plan §11 Unit).

## Contract bindings
- **tests ↔ obs (log format):** the harness `logs` leg reads NDJSON `tracing` output and greps agent-parseable signals; the arm-zero discriminators the chunk relies on (`span_events_seen` / `fingerprints_computed` / `observer_invocations`, plus `buffer.tick`) are obs-declared field names that the tests-side assertion must key off exactly as obs specifies (per test-plan §3 Log format; §3 bootstrap phase "log-format-bind-with-obs").
- **tests ↔ obs (status shape):** `status` polls the `health` JSON subsystem shape, which is obs-owned (per test-plan §3 Status endpoint shape).
- **tests ↔ arch (capability drift):** `cargo xtask capability-drift` runs in the standard gate set even though the scope anticipates no new TauRPC procedure (per test-plan §3 Per-chunk gate discipline; §1 coverage trigger "Tauri IPC capability gating").
