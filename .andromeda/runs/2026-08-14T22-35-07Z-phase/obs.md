## Constraints
- Workspace detection is a must-trace path: the boot key-resolution path must carry the P7 span set (`app.boot` → `app.boot.workspace.detect` → `workspace.marker.check` → `workspace.identity.resolve`) with `workspace.root_path` (canonicalized), `workspace.project_name`, `vcs_type`, `vcs_root`, `marker_present`, `detection_latency_ms` (per obs-plan §4 P7). Whether the existing app-side and sidecar-side resolution sites already emit these is research's question.
- Any NEW field this chunk introduces (e.g. a resolved-key field or a `key_source` discriminator) must be added to the per-module allowlist for the exact emitting target, and a dotted target needs its own leaf entry — obs-plan §8's default-deny posture redacts unlisted fields, and `for_target`'s prefix fallback resolves a dotted target to an unrelated field set (per obs-plan §8 default-deny posture; precedent: the `app.boot.buffer.degraded` leaf entry).
- Path-shaped env vars (`ANDROMEDA_PULSE_*_PATH` / `*_DIR`, which includes the sidecar's data-dir input) must be canonicalized and validated at load, with traversal rejected and only the basename logged in errors (per obs-plan §5 telemetry triggers, logging-sensitive Vector 6). This is the obs-side mandate that the chunk's "normalization proven, not assumed" deliverable must satisfy; whether the code already canonicalizes that env var is research's question.
- obs-plan §5 Vector 5 requires workspace-detector *output* not be logged as-is, while §4 P7 and §8's `workspace-detector` allowlist name `workspace.root_path` / `workspace.project_name` as required/permitted fields. Which rule governs the full derived key string (a filesystem path) at each emitting target is unresolved in the plan and must be settled by research before a key value is logged anywhere.
- The rmcp stdio sidecar must force its subscriber to stderr-JSON with no TTY check, because stdout is reserved for JSON-RPC 2.0 framing (per obs-plan §3 Logging stack; §4 MCP stdio row). Any diagnostic added to `andromeda-pulse-mcp.rs` while observing the key mismatch falls under this.
- The sidecar carries a distinct service identity `andromeda-pulse-mcp` versus the app's `com.andromeda.pulse`, registered as default subscriber fields (per obs-plan §3 Service identity) — this is what makes app-emitted vs sidecar-emitted key lines attributable in the before-evidence.
- Every emitted line must satisfy the binding log schema: `timestamp` / `level` / `target` / `message` / `fields` (with `service.name` / `service.version` / `deployment.environment` as default fields); `workspace-detector` sits at `info` for detection summary, `debug` for scan detail (per obs-plan §6 required fields + per-module log levels).

## Patterns to follow
- Single-source-registered identity: obs-plan §3 Service identity registers identity once as default subscriber fields rather than repeating it per call site — the same shape the chunk's "one derivation, both ends" deliverable wants for the workspace key.
- `#[tracing::instrument]` on workspace-detect / config-load functions under the `app.boot` root span, per obs-plan §4 instrumentation table (CLI / main binary row) — the natural home for a relocated derivation's span.
- Counters folded once per batch and ridden out as FIELDS on the existing 15s `buffer.tick` rather than as separate `metric.buffer.*` targets (per obs-plan §5 conceptual instrument types, tick-aggregated counter row) — this is the shape the arm-zero classification reads (`span_events_seen` / `fingerprints_computed` / `observer_invocations`). Whether HEAD already emits these three is research's question.
- MCP tool call span chain `mcp.tools.call.request` → `duckdb.query.*` → `mcp.tools.call.response` emitting `result_type` + `result_count` (per obs-plan §4 P3) — the observation leg's `query_incident_list` read produces exactly this shape, and `result_count` is the zero-vs-nonzero before-evidence.
- Check scripts over `agent-latest.jsonl` must be NEUTRAL-tolerant (absent stream ≠ failure) and scoped to the run window via `write_run_window_log` (per obs-plan §10 load-profile constraints) — applies to any script run over the Conductor-arm evidence so a cross-session heartbeat gap does not false-FAIL.

## Anti-patterns to avoid
- Never write to stdout from any subsystem running as the rmcp stdio sidecar — no `println!` / `dbg!` / library stdout writes; any accidental write corrupts JSON-RPC framing and silently disconnects the client (per obs-plan §11 Universal).
- Never log MCP tool response bodies; only `result_type` + `result_count` metadata (per obs-plan §11 Project-specific + §8 `mcp-server` allowlist) — the observe leg records counts, not the incident rows it did or did not get back.
- Never log full canonicalized paths where the plan mandates basename-only, and never emit unstructured stderr text for the evidence capture (per obs-plan §11 Spans/Traces + Logs).

## Contract bindings
- obs ↔ tests: the JSON log schema in obs-plan §3 / §6 is verbatim from the tests harness contract (obs aligns to tests, not vice versa) — the existing regression guard named in the chunk's surface table and any new key-parity assertion consume that field shape.
- obs ↔ tests (smoke/heartbeat): the arm-zero classification depends on `buffer.tick` presence and its three feed-counter fields (obs-plan §1 Heartbeat ticks, §5); the >45s stall rule and the CI gap check are the same signal source.
- obs ↔ security: logging-sensitive Vectors 5 and 6 (workspace-detector output; path env-var CWE-22 canonicalization + basename-only errors) are enforced at logger/instrument config (obs-plan §5 telemetry triggers, §8 integration points).
- obs ↔ MCP protocol surface: stdout reservation for JSON-RPC framing constrains all sidecar instrumentation (obs-plan §3 Logging stack, §11 Universal).
