## Constraints

- **(IPC capability JSON enforcement)** per security plan §API Security TauRPC capability authorization + §Anti-Patterns API row 3: `snapshot.generate` resolver implementation MUST be backed by a corresponding entry under `pulse-app/capabilities/` (chunk #43 substrate added `clipboard.json` + `notification.json`); xtask `EXPECTED_PROCEDURES` MUST include `snapshot.generate` + `snapshot.copy_to_clipboard` + `workspace.detect` to keep the capability-drift gate green when chunk #44 lands.
- **(Clipboard capability scope discipline)** per security plan §Anti-Patterns API row 6 (NEVER widen `pulse:notification` / `pulse:tray` / `pulse:plugin-fs` beyond outbound emit) — by symmetric reasoning + arch §Architecture Registry Updates 2026-05-11 marker noting "write-only outbound; NEVER allow-read-*", `pulse:clipboard` MUST stay scoped to `clipboard-manager:allow-write-text` only. The AppHandle runtime invocation MUST call `app.clipboard().write_text(...)` (write path) only; NEVER add `allow-read-text` to clipboard.json for the snapshot-paste-to-AI flow, and NEVER add a read-clipboard IPC procedure under this chunk.
- **(Notification capability scope discipline)** per security plan §Anti-Patterns API row 6 — `pulse:notification` is outbound-emit-only. Chunk #44's runtime MUST invoke the notification dispatch as a fire-and-forget out-channel (no `on_action` callback wiring that re-enters Rust with arbitrary payload). If a future "Open snapshot" notification action is needed, it goes through a separately-named capability with stated rationale — NOT this chunk.
- **(Clipboard-write visible signal mandate)** per security plan §Logging & Monitoring snapshot/clipboard/MCP-tool-response hygiene bullet 2: `snapshot.copy_to_clipboard` MUST emit a `pulse://stream/snapshot-progress` event at clipboard-write time so the UI can show a non-suppressible "X bytes copied" toast (visible signal that data left the app's address space). The chunk #44 AppHandle injection runtime MUST `app_handle.emit("pulse://stream/snapshot-progress", payload)` immediately around the clipboard-write call.
- **(NEVER-log list at runtime boundary)** per security plan §Logging & Monitoring "What NEVER to log" bullets 1-5 + §Anti-Patterns Logging rows 1-2: the chunk #44 snapshot.generate resolver MUST NOT log snapshot file contents, clipboard contents (markdown payload), raw OTLP attribute values, or full plugin/workspace file paths (basename only). The existing AllowList scrubber (chunk #43 substrate) is the enforcement primitive; chunk #44 MUST NOT bypass it when wiring AppHandle-emitted progress events or notification body strings (notification title/body MUST use `bytes_written` / `services_count` / `snapshot_id` keys only — never inline a markdown excerpt or attribute value).
- **(Workspace path canonicalization)** per security plan §Input Validation row 4 + §Anti-Patterns Input row 4 + §Code Patterns row 2: `workspace.detect` resolver implementation MUST canonicalize via `strict-path` and assert the resolved path lives under the resolved data dir (CWE-22 defense). Chunk #44 runtime body MUST NOT pass user-supplied workspace paths into any `std::fs` / `tokio::fs` / `tokio::process::Command` call without canonicalize-and-confine; basename-only is the logged form.
- **(AppError sanitization at TauRPC bridge)** per security plan §Error Handling TauRPC bridge bullet + §Anti-Patterns Logging row 4 + Code Patterns row 4: all paths through `snapshot.generate` runtime that surface failures (clipboard.write failure / notification dispatch failure / event.emit failure / workspace canonicalize rejection / PII scrubber error) MUST collapse to `AppError::{Internal, Storage, Validation}` variants with sanitized one-line messages — NO stack traces, NO Rust struct names, NO library versions, NO absolute file paths in the `message` field. Convert at the `From<thiserror::Error> for AppError` impl boundary; never serialize `anyhow::Error` directly across the bridge.

Chunk #43 substrate landed `clipboard.json` + `notification.json` following this pattern; chunk #44 runtime MUST consume them as-is (no per-procedure capability JSON expansion).
- **xtask EXPECTED_PROCEDURES extension coupled with consuming chunk** per `.claude/rules/security.md` §Session Additions 2026-05-10 entry: chunk #43 substrate already added `workspace.detect` to xtask EXPECTED_PROCEDURES (D3 drift cleared in the same commit that landed the substrate). Chunk #44 is the natural-coupling consumer for `snapshot.generate` end-to-end exercise — IF xtask EXPECTED_PROCEDURES has not yet legitimized any newly-surfaced procedure name from #44 (e.g., a `snapshot.list_recent` or `snapshot.copy_to_clipboard` introspection), couple the extension into this chunk's commit rather than a standalone xtask housekeeping commit.
- **Settings-shape extension preferred over new namespace** per `.claude/rules/security.md` §Session Additions 2026-05-09 entry: chunk #44 introduces operations (clipboard write / notification dispatch / event emit), NOT additional get/set state — so the new-namespace path (`snapshot.*` / `workspace.*`) is appropriate (cannot fit into the existing `Settings` struct). This pattern note confirms chunk #44 doesn't have a lower-cost alternative to the new-namespace approach; the cost of the triple binding (capability JSON + xtask EXPECTED_PROCEDURES + arch §Occupied Resources) is already paid by chunk #43 substrate, so chunk #44 ONLY needs to fill the runtime bodies.
- **Tracing self-observation via `tracing-subscriber` JSON only** per security plan §Logging & Monitoring deprecation note + §Cross-cutting Patterns Self-observation: chunk #44 runtime logging emissions (clipboard.write success, notification dispatched, event emitted) use `tracing::info!` / `tracing::warn!` with structured fields scrubbed via the AllowList — NEVER bind an OTel SDK in chunk #44; NEVER point a network exporter at the product's own `:4317`/`:4318` (infinite recursion).

## Anti-patterns to avoid

- **NEVER add `clipboard-manager:allow-read-text` to `clipboard.json` for this chunk** per arch §Architecture Registry Updates 2026-05-11 marker rationale ("write-only outbound; NEVER allow-read-* per security plan §Anti-Patterns API row 6 — clipboard read is exfiltration surface needing separately-named capability") + security plan §Anti-Patterns API row 6 widening ban. The InvestigationModalForm "paste my draft back" flow is NOT in chunk #44 scope.
- **NEVER inline raw snapshot markdown content into the `pulse://stream/snapshot-progress` event payload** per security plan §Logging & Monitoring "NEVER log snapshot file contents / clipboard contents" — payload SHALL carry only `bytes_written` / `services_count` / `snapshot_id` / `timestamp` shape (numeric + ID-only); the markdown body is delivered via the clipboard write call, NOT via the Tauri Channel API event.
- **NEVER serialize the underlying `clipboard.write_text(...)` / `notification.builder().show()` raw error chain across the bridge** per security plan §Anti-Patterns Code Patterns row 4: chunk #44 runtime catches the library error at the resolver, converts at `From` impl into `AppError::Internal { message: "Clipboard write failed" }` (sanitized one-liner), and leaves the full error chain ONLY in the `tracing` JSON log (where the subscriber-layer scrubber redacts sensitive fields).
