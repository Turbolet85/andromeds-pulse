# layouts extract

## Relevance
partial — the chunk creates, modifies and removes no surface, so no wireframe, placement, focus-order or responsive mandate of the plan applies to its output; the plan is relevant only as the inventory of what "the window" and the tray are, which the classification of the 82 ids reads.

## Constraints
- The plan describes two surfaces and no other: a webview window and an OS-native tray/notification surface (per layout-templates §Surface: desktop-webview and §Surface: desktop-native). It holds no console, CLI or engine surface, so an id claimed "in a changed form" by the 0.4.0 engine has no layout mandate in this plan; nothing here can be cited as the layout of a claimed id's new form.
- What counts as "the window" in the plan's terms is the set of screens it enumerates (per layout-templates §Surface: desktop-webview → Primary screens): an id whose text is about any of those screens is about a window surface as the plan defines it. Whether a given id's text is about one of them is research's question, read against the 82 texts.
- The plan anchors ten capability ids to window or tray components by number: P-080 and P-082 and P-070 (per layout-templates §Surface: desktop-webview → Primary screens), P-068 and P-069 (per layout-templates §Wireframe — Full dashboard (Traces primary screen), wireframe notes), P-081 (per layout-templates §Component — Trace data table (primary content block)), P-067 (per layout-templates §Component — Footer (read-only status bar)), P-025 (per layout-templates §Component — Halo State Pulse canvas (hero / signature)), P-063 and P-066 (per layout-templates §Component — Notifications (OS-native)). The plan requires each of these to exist as a layout element of the window or tray; the record's disposition for each is therefore a statement about a surface this plan owns.
- P-063 and P-066 sit in the tray/notification surface, not in the webview window (per layout-templates §Surface: desktop-native → Primary screens). P-117's requirement names "the window, the model or the desktop"; under which of the three a tray or OS-notification id is retired — or whether it is a doubtful id for P4 — is research's question, not answered by this plan.
- P-025 is bound by the plan to the constellation dot hue, and the plan states that the Halo State Pulse layer is deferred and renders on neither surface (per layout-templates §Component — Halo State Pulse canvas (hero / signature)). A record entry for P-025 that names its surface must not name the Halo layer as the thing claimed or retired; whether the code still matches that status note is research's question.
- Several capabilities reach the window only as a control while their function lives elsewhere: the MCP toggle, retention and snapshot actions (per layout-templates §Component — Settings modal (form) and §Component — Tray menu (OS-native)). The plan requires only the control; it says nothing about the function behind it, so the plan supports a "partly about the window" reading for such ids and cannot support retiring the whole id on layout grounds alone.
- The plan is a foundation document that is not edited during implementation runs (per layout-templates preamble, "Do not edit during implementation runs"); the chunk's own boundary that spec masters are read-only at phase agrees with it. The record may cite the plan's sections; it does not rewrite them.

## Patterns to follow
- Name a retired id's surface in the plan's own vocabulary — the screen or component heading — so the record and the plan stay joinable by a reader outside the project (per layout-templates §Surface: desktop-webview → Primary screens; §Surface: desktop-native → Primary screens).
- Treat the plan's `(P-0NN)` parentheticals as the layout-side evidence that an id is window-bound, and treat an id the plan never cites as carrying no layout evidence either way (per layout-templates §Wireframe — Full dashboard (Traces primary screen), wireframe notes; §Component — Trace data table (primary content block)).
- Where the plan marks a section as a status note that governs over its own sketch, read the note, not the ASCII (per layout-templates §Component — Halo State Pulse canvas (hero / signature); §Wireframe — Full dashboard (Traces primary screen), wireframe notes on sketch lag).

## Anti-patterns to avoid
- Reading a deferred or sketch-only element as a shipped surface when naming what an id is retired with: the Halo layer on both surfaces, and the wireframe footer and per-dot label detail the plan itself flags as lagging (per layout-templates §Component — Halo State Pulse canvas (hero / signature); §Surface: desktop-native → Signature placement).
- Folding the tray/notification surface into "the window" without saying so: the plan keeps them as separate surfaces with separate tooling (per layout-templates §Surface: desktop-native, Tooling context).
- Using the plan's per-platform notes for macOS and Windows as a ground to retire an id "with another operating system": those notes are conventions of the tray surface, not capabilities, and whether a retirement may name any surface beyond P-117's three is closed at P3 against the requirement's wording (per layout-templates §Surface: desktop-native → IA notes, Platform-specific notes).

## Contract bindings
- layouts ↔ a11y: P-081 and the Traces hero landmark are bound in the plan to keyboard and landmark behaviour (per layout-templates §Component — Trace data table (primary content block), Keyboard / focus; §Wireframe — Full dashboard (Traces primary screen), wireframe notes). A retired window id of this kind also has an a11y-plan side and a gate that drives the window; what guards it between this chunk and the removal entry is the a11y and tests extractors' and research's to state.
- layouts ↔ design: the Halo deferral is recorded in both the layout plan and the design system's amendments (per layout-templates §Component — Halo State Pulse canvas (hero / signature)); P-025's disposition should read the same in both.
- layouts ↔ architecture/security: the tray menu and notification items are specified as firing IPC commands (per layout-templates §Component — Tray menu (OS-native), Implementation details); an id split between a tray control and its backing procedure crosses into the architecture record of IPC routes.
- layouts ↔ tests: none added by this chunk — no surface changes, so no layout-driven E2E or a11y harness path is created or altered.
