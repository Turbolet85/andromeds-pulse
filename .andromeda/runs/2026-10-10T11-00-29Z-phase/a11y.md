Whether P-117's "the window" covers the tray and the notification, or "the desktop" does, is not answerable from this plan — research closes it against the requirement's wording, and an id that fits neither is P4's.

- a11y-plan §10 SLO Invariants & A11y Budgets requires zero WCAG AA violations on the must-be-accessible paths and zero new violation tuples per PR against the baseline committed in the tree. Both stand unchanged through this chunk; they are what the plan offers as the guard of a retired window id between this chunk and its removal entry. Whether a given id's acceptance is in fact covered by a spec that runs is research's question, per id.

The chunk edits the same `xtask` crate for `verify:capability-matrix`; whether that edit touches code the `test:a11y` verb shares is research's question, and the verb's behaviour must come out unchanged.

An accessibility id recorded as still `claimed` needs such a path named; the plan holds no entity for an engine with a console (a11y-plan §1 A11y Scope Summary, entity table), so whether any accessibility id can be claimed in a changed form cannot be settled from this plan — it is a doubtful id for P4.

## Patterns to follow
- A guard is nameable at spec granularity: a11y-plan §1 A11y Scope Summary (Surface set extension) gives one axe spec per must-be-accessible surface (`p1`–`p14`) plus the keyboard-focus spec, so "its tests still run" can cite a spec, not the job as a whole.
- A gate that reads a file committed in the tree treats an absent file as an error, never as an empty set, and pins that with tests: a11y-plan §3 Harness wiring & conventions (Regression baseline). The same shape fits the old capability gate once it reads the record.
- Surface vocabulary is closed and reused: a11y-plan §3 Structured violation JSON schema carries a `surface` field with three fixed values. A record that names a retired id's surface from a closed set follows the same discipline; the mapping from the plan's three names to P-117's three is research's, not this extract's.
- WCAG SC ids are the primary cross-section anchor: a11y-plan §2 A11y Strategy (Naming conventions). Where the plan states what guards an accessibility id, it cites the SC and the path by those anchors.

## Anti-patterns to avoid
- Never soften, skip or defer the a11y gate: a11y-plan §11 A11y Anti-Patterns (CI) bans a soft gate and a post-merge fix. Recording an id as retired is not a reason to quarantine or delete its spec in this chunk — the surface and its tests stand (scope Boundaries).
- Never claim conformance without machine-verifiable evidence: a11y-plan §11 A11y Anti-Patterns (Strategy; Universal). A `claimed` row for an accessibility id that rests on prose alone is that claim.
- Never drop the per-PR regression diff: a11y-plan §11 A11y Anti-Patterns (SLO). The committed baseline is not this chunk's to edit.

## Contract bindings
- a11y ↔ tests / CI: a11y-plan §9 CI Integration places the `a11y` job in the same `ci.yml` as the `lint-test` job whose step runs `verify:capability-matrix`; both go through `xtask` (a11y-plan §3 CI integration). An edit to the workflow or to `xtask` for the gate must leave the a11y job's steps as they are.
- a11y ↔ the capability record: a11y-plan §1 A11y Scope Summary (Critical paths, P4 row) cites P-081 by id. The masters are read-only at phase (scope Boundaries); if P-081's disposition changes how that sentence reads, the amendment is the wrap's, not this chunk's edit.
- a11y ↔ design, layouts, obs: (none) — no token, layout, focus order or violation-JSON emission is in this chunk's scope.
