partial — the plan places the gate (the `xtask` crate, the `lint-test` job, the xtask CLI-surface register) and names the old spec as a registered scope's supporting document; it holds no entry for the capability record, the verification matrices or the verb `verify:capability-matrix` (0 mentions in the plan body and in its four keyed contracts), and its target state still carries the window, the model and the desktop distribution, so it is no authority for any id's disposition.

## Constraints
- The gate's code stays in the `xtask` crate: architecture.md §Established Decisions [CI Task Runner] requires CI tasks to be Rust binaries in the same workspace, and §Infrastructure Patterns → CI/CD approach requires all shared CI logic that needs Rust to live in `xtask`, so a contributor runs the identical command locally with `cargo xtask <task>`. A record reader written as a workflow-inline script would break that requirement.
- No workspace member is added or renamed: architecture.md §Occupied Resources → Cargo workspace crate names reserves the sixteen names, and §Design Philosophy (single-process modular monolith) makes that list the canonical member count every count word defers to. A record-reading helper is a module inside `xtask`, not a crate.
- No dependency edge is added toward a product crate for the record's sake: architecture.md §Cross-cutting Patterns → Module dependency direction requires the dependency graph to stay a DAG rooted at `pulse-app`, with no library crate depending on a sibling its declared contract does not need. Whether the gate today parses the matrix with dependencies `xtask` already holds is research's question.
- The gate keeps running as a step of the `lint-test` job among the xtask gates: architecture.md §Infrastructure Patterns → CI/CD approach requires `ci.yml` to be six independent jobs on `ubuntu-22.04` with no matrix and no `needs:` edge, and names the self-lint tests that pin the workflow as it stands. Whether one of those pins (or another test in `pulse-app/tests/quality_gate_workflow.rs`) holds the `verify:capability-matrix` step's text or the old matrix path is research's question.
- A changed gate contract is registered: architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates) registers each formalized xtask verb with its implementing file, its exit codes, its named arms and its output line. The plan holds no entry for `verify:capability-matrix` today; if this chunk changes what the verb reads (its input file, its expected id set, its `{n}/60` line), the plan requires that contract to be stated and the entry lands at wrap, not at phase (scope §Boundaries: the masters are read-only here).
- File and symbol naming follows the workspace convention: architecture.md §Conventions → File naming requires `snake_case.rs` for any new module under `xtask/src/`, and §Conventions → Variable / function naming requires `SCREAMING_SNAKE_CASE` for a constant such as an expected-id set, enforced by the clippy `style` group in CI.
- The old spec is a registered scope's supporting document: architecture.md §Existing Scopes names `docs/v0_2_0/pulse-capability-spec.md` under the scope `pulse-v0_2_0-route`. A move, a rename or a deletion of that file would leave that registration pointing at nothing; the scope's own boundary (the two old records are not deleted here) keeps the registration true, and any "superseded" marking that changes what the file is goes to the wrap as an amendment candidate.

## Patterns to follow
- The registered gate-contract shape: the entries of architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates) state exit 0 pass · 1 findings · 2 cannot-evaluate, a closed set of named arms and one machine-readable verdict. A re-based gate that reads a record file follows that shape, a missing or unreadable record included.
- No pass over an absent or empty input: the `ci-gates` and `quarantine-tracking` entries of architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates) require a gate to fail, never read NEUTRAL or green, when its input is absent or empty. A gate whose expected set now comes from the record must not pass on a record that yields zero claimed ids or cannot be read. Whether the gate already fails on an absent matrix file is research's question.
- A leaving thing names the route entry that removes it: architecture.md §Stack and Technologies ties a member that leaves to its route entry by name (the Xlib thread-support row, "leaves with the window", the entry `Window retired`). A retired id's "removed by" field follows the same form — the route entry's name, not a date or an epoch number.
- Schema-stable, machine-parseable surfaces for an outside reader: architecture.md §Cross-cutting Patterns → Development Style (agent-driven) requires deterministic harness invocations, machine-parseable outputs and schema-stable contracts on `cargo xtask` task surfaces. The record's fields for "claimed" and "retired" are stated once, as a closed vocabulary, so the external harness reads the file without a second derivation.
- Policy input as a committed data file read by an xtask gate: the `check:npm-supply-chain` entry of architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates) shows a gate reading one committed policy file whose parser rejects an entry with blank provenance. A retired id with no named surface is the same class of rejected entry.

## Anti-patterns to avoid
- Reading the plan's target state as a disposition: architecture.md §Project Intent, §Design Philosophy and §Established Decisions ([Platform], [WebGPU Visualization Surface], [LLM Inference Runtime — L4 interpretation layer], [Deployment / Release Pipeline], [Distribution Channels]) still describe the window, the model and the desktop distribution as what the product is. None of them is a ground for claiming an id, and none is rewritten by this chunk; an id's disposition comes from the 0.4.0 requirements, and the plan's own re-description belongs to the entries that remove each surface.
- Conflating two meanings of "capability": architecture.md §Occupied Resources → Tauri capability identifiers (reserved at arch level) and §Cross-cutting Patterns → Webview IPC capability policy are about Tauri grants and the `capability-drift` gate with its `EXPECTED_PROCEDURES` pin. The capability record is about product ids P-001…P-082. No capability JSON, no procedure pin and no `capability-drift` input is this chunk's to touch, and a retired product id is not a revoked Tauri grant.
- A second home for CI logic: architecture.md §Established Decisions [CI Task Runner] rejects a DSL runner beside `cargo-xtask`. A shell or Python reader of the record added to `ci.yml` beside the verb would give the record two readers inside this project with two readings.

## Contract bindings
- arch ↔ tests: the `lint-test` step and the workflow self-lint pins named in architecture.md §Infrastructure Patterns → CI/CD approach bind to the test plan's gate inventory; a changed step text or input path is the test plan's row as well as this plan's CLI-surface entry.
- arch ↔ security: the word "capability" in architecture.md §Cross-cutting Patterns → Webview IPC capability policy belongs to the security plan's Tauri gating; the record must not be read by, or named as an input of, `capability-drift` or the staged-artifacts gate.
- arch ↔ obs: (none) — the gate reads a committed file, no log family.
- arch ↔ the external harness: architecture.md §Cross-cutting Patterns → Development Style is the only plan text that binds a surface read outside this project (schema-stable contracts); the plan registers no cross-repository contract, so the record's form for Conductor is the chunk plan's to state and the wrap's to register.
