## Constraints
- The entities this chunk touches are classified **Not-assertable** in the a11y scope table (Tauri IPC bridge / backend storage / backend services have no UI surface), so no new WCAG assertion is owed for the keyring/keychain/encryption work itself (per a11y-plan.md §1 A11y scope — entity assertability table).
- The per-PR regression gate applies to **every** PR regardless of domain: the current violation-tuple set must contain no tuple absent from `baselines/a11y-violations-summary.json`, and the baseline is regenerated only from a clean full-chain pass — never widened to absorb a new finding (per a11y-plan.md §3 Harness wiring & conventions — Regression baseline; §10 Zero new violations per PR). This is the same owned-channel discipline the scope §E demands of `deny.toml`.
- Standing rule: **every new route/modal ships one axe spec in the same chunk**, with fixtures in `helpers/v02-fixtures.ts`, and any new TauRPC procedure a fixture consumes mocked via the `TauRPC__<router.path>` command shape. If §C/§D resolves to an operator-invoked disposition action or a fallback-warning banner, that surface owes its spec here, not later (per a11y-plan.md §3 Harness wiring & conventions — Adding a surface).
- Any status/warning this chunk surfaces in the webview must use the live-region pattern — `role="status"` / `aria-live="polite"` for non-blocking outcomes, `role="alert"` / `aria-live="assertive"` for blocking failures — satisfying SC 4.1.3 (per a11y-plan.md §7 Screen Reader Support — Live regions; §4 ARIA Patterns — Status / Alert row).
- A11y violation records are emitted in the obs Section 6 structured-log format with the required field set (`wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` / `remediation` / `tool` / `tool_result_id`) into `~/.andromeda-pulse/logs/` as the `a11y-*.jsonl` / `a11y-violations-summary.json` artifacts the CI gate parses; an obs-allowlist change in this chunk must not shadow or drop those fields (per a11y-plan.md §1 Structured Violation JSON Schema; §3 Structured violation JSON schema; §9 CI Integration artifact table).
- The a11y chain is invoked from the same CI pipeline and reuses the tests 5-command E2E driver (`boot` / `run` / `status` / `cleanup` / `logs`) via `npm run test:a11y` / `cargo xtask test:a11y` — a workspace-manifest or transitive-dependency change must leave that invocation buildable and runnable (per a11y-plan.md §3 CI integration; §9 Pipeline integration).
- Machine-verifiable evidence is mandatory: no WCAG conformance claim for any affordance added here may rest on manual screen-reader/keyboard inspection alone (per a11y-plan.md §2 Agent-runnable invariants; §11 Universal).

## Anti-patterns to avoid
- NEVER defer a11y to post-merge or soft-gate it — if this chunk ships any user-facing affordance, its assertion ships with it (a11y-plan.md §11 CI).
- NEVER convey a state by color alone — an "orphaned" / "degraded" / "fallback engaged" indicator needs a text label or icon supplement (a11y-plan.md §11 Visual; §6 State color tokens).
- NEVER skip the per-PR regression diff at Standard tier, and never retry-once to get past an a11y failure (a11y-plan.md §11 SLO).
