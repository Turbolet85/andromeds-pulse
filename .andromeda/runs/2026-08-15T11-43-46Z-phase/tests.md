# tests extract

## Relevance
Relevant — this chunk touches a library-crate surface (`crates/corpus` keychain), the pulse-app boot path, and the app→sidecar cross-process boundary that test-plan.md §5 and its `workspace-key-cross-process-coverage` pending trigger name explicitly as unblocking with the "Corpus key persistence" route entry.

## Constraints
- Standard tier (1) governs breadth: unit coverage is "comprehensive" per crate, integration is "required" for every cross-module boundary, and each surface driver must be exercised against a live boundary rather than a stub (per test-plan.md §1 Test Scope Summary, §2 Test pyramid).
- `crates/corpus` is a library crate, so its tests must be co-located `#[cfg(test)] mod tests { … }` under `src/`; any pulse-app-side boot-wiring probe must instead live as a separate integration target under `pulse-app/tests/*.rs`, reaching internals through `pub` + `#[doc(hidden)]`, because `pulse-app`'s `[lib] test = false` makes co-located modules compile but never run (per test-plan.md §2 Test directory + naming conventions, §4 Conventions → Test file location).
- The app-boot → `<data_dir>/run/workspace-key` → mcp-server cross-process handoff is a declared boundary that must be tested by publishing, reading back, asserting byte-equality with the app's filter key, and asserting the absent/invalid-file fallback on both ends — with the sidecar-subprocess leg driven by `tokio::process::Command` per the Module ↔ MCP sidecar driver (per test-plan.md §5 Boundary types covered, §5 Drivers).
- Every chunk plan's `## Test Commands` must carry the unconditional standard gate set (`cargo fmt --check`; `cargo clippy --workspace --all-targets --all-features -- -D warnings`; `cargo nextest run --workspace --profile ci`; `cargo xtask capability-drift`; `cargo xtask capability-widening-check`), with the three `--prefix pulse-app/ui` webview gates excluded only when zero `pulse-app/ui/**` paths are touched — which this chunk's Surfaces table indicates (per test-plan.md §3 Per-chunk gate discipline).
- Because the chunk's expected surfaces include `pulse-app/src/main.rs`, the conditional boot-smoke gate is required in addition: `npx @tauri-apps/cli dev` from `pulse-app` with a 60s timeout, watching stdout for `Local:` / `ready in` / `Compiled successfully` before SIGTERM; a smoke failure surfaces "green per scope; runtime blocked" rather than blocking commit (per test-plan.md §3 Boot-smoke gate (conditional)).
- Per-test isolation is mandatory and must not leak into shared global state: `tempfile::TempDir` + `ANDROMEDA_PULSE_DATA_DIR` per test, no shared mutable state across parallel tests, and dependency injection through the constructor rather than runtime patching — the `Corpus::open(path, Arc<dyn KeychainBackend>)` shape the scope expects to keep unchanged is exactly what this discipline requires (per test-plan.md §7 Test data lifecycle, §8 Anti-monkey-patching). A real OS credential store is process-global, so the scope's test-scoped-service-name + cleanup constraint is the harness-side expression of this rule.
- Zero-flakiness is a hard gate — one flake means immediate quarantine plus root-cause, never a retry policy — and `#[ignore]` may not be committed without a tracking issue; `#[ignore]` is reserved for flake quarantine, with env-gated real-dependency legs instead modeled on the `env-gated-runtime` verification mode (per test-plan.md §10 Zero-flakiness budget, §11 Quality, §9 Capability verification matrix).

## Patterns to follow
- Subprocess-boundary shape from the MCP sidecar E2E scenario: spawn under its feature flag + env gate with piped stdin/stdout, assert on the parsed structured response, then SIGTERM and assert exit code 0 with no zombie process (test-plan.md §6 Scenario P3, §5 Module ↔ MCP sidecar).
- Real-filesystem-not-mocked pattern for path/round-trip work: `tempfile::TempDir` / `assert_fs` against real temp dirs (test-plan.md §8 What to mock → Filesystem; §5 workspace-detector → filesystem row).
- `rstest` 0.26.1 `#[fixture]` builders plus `#[test] fn test_<entity>_<scenario>()` naming, flat per-module functions (test-plan.md §4 Fixture pattern at unit level, §4 Conventions).
- Mock only traits you own via constructor-injected `Arc<dyn Trait>` — the existing `FakeKeychainBackend` occupies exactly that slot; `mockall` is barred for third-party libraries (test-plan.md §8 Mocking libraries, §8 Anti-monkey-patching).
- Feature-gate build verification is already an in-scope unit concern for the `mcp-server` crate, which is the pattern for asserting a compile-time-gated backend selection (test-plan.md §4 What unit tests cover → mcp-server crate).

## Anti-patterns to avoid
- Never skip `cargo deny check bans` — `multiple-versions = "deny"` is enforced and a deny-bans violation is a build-failure condition, so the anticipated `windows-sys`-class transitive churn must be reconciled inside the gate, not around it (test-plan.md §11 Test Strategy, §9 Build failure conditions + Cargo deny enforcement).
- Never expose secrets in test output; the harness's own data-leakage signal is a negative grep over the log stream, so no key material may appear in assertions, fixtures, or emitted log fields (test-plan.md §11 Universal, §3 Log format → agent-parseable signals).
- Never share mutable state across parallel tests, and never `std::env::set_var` mid-test without cleanup — both apply directly to any leg that mints a real credential-store entry or flips backend selection by environment (test-plan.md §11 Test Data, §11 Mocking).

## Contract bindings
- **tests ↔ obs:** §3 Log format is bound to the obs-plan JSON schema (bootstrap phase "log-format-bind-with-obs"), and §3's agent-parseable signals include the negative data-leakage grep. Any backend-kind / fallback-warning field the scope anticipates for `pulse-app/src/observability.rs` must therefore stay greppable in the harness's log surface while carrying no key value — the same `agent-latest.jsonl` grep surface the `AppError sanitization` and `MCP response body redaction` pending triggers assert against (test-plan.md §3, §1 Pending coverage triggers).
- **tests ↔ security/CI:** `cargo deny check` sits in §9 Build failure conditions, so the security domain's owned-channel `deny.toml` discipline is enforced through the tests domain's gate list, not separately (test-plan.md §9, §11 Test Strategy).
- **tests ↔ arch:** §8's constructor-injection mandate is what makes `Corpus::open(path, Arc<dyn KeychainBackend>)` testable; if the trait/constructor signature the scope expects to leave unchanged does change, §8 becomes a binding constraint on the new shape (test-plan.md §8 Anti-monkey-patching).
