# obs extract

## Relevance
**Partial** — the capability grant and the gate mechanics are arch/tests; obs owns (a) whatever discriminating observable in-scope items 3–4 select if it is an obs record, and (b) the module-boundary-error-logging requirement that applies to the swallowed rejection regardless of which observable wins.

## Constraints
- **Any new self-observation target requires an EXACT §8 allowlist leaf enumerating every field its emit site emits.** obs-plan §8 (Default-deny posture) makes `for_target`'s first-`.`-segment fallback the hazard: it either resolves to nothing (no bare `app` key is registered) or resolves into a set never meant for the target (a bare `metric` key exists and keeps `value` while silently redacting every label). Without a leaf, a copy-outcome record reaches the log with its fields as `"<redacted>"` and the gate matches nothing (per obs-plan §8).
- **Frontend signals reach observability only through the TauRPC `telemetry.frontend.*` bridge.** obs-plan §1 (Telemetry surfaces → desktop-webview) and §3 (Logging stack → Frontend bridge) require that the webview links no browser OTel SDK and has no direct file access; every frontend observable is a TauRPC command whose backend handler emits `tracing::info!`. The single JSON file at `~/.andromeda-pulse/logs/agent-latest.jsonl` is the unified surface (per obs-plan §1, §3). Note the tension with this chunk's own boundary ("no new TauRPC procedure") — whether an existing frontend-telemetry command can carry a copy outcome is research's question.
- **Module-boundary errors must be logged at WARN or ERROR with an error CATEGORY, not a stack trace.** obs-plan §10 (Standard+ invariants) requires this of every module-boundary error, and §7 (Error classes captured) names the IPC bridge as such a boundary. Whether the clipboard ACL rejection produces any product-side `tracing` record today — or is denied inside the Tauri runtime before product code runs — is research's question, and it decides whether the "obs record" observable in item 3 is cheap or new.
- **A new WARN target must be registered at BOTH §6 and §8.** obs-plan §6 (Log levels mapping → `warn` row) enumerates every once-per-boundary WARN alongside its emission discipline, and §8 registers its leaf; the dual-site rule means a §8-only application leaves §6 stale (per obs-plan §6, §8).
- **The copied report markdown is High-classification content and may never enter the self-observation log.** obs-plan §8 (Data classification → raw OTLP telemetry payloads) and §11 (Project-specific) forbid conflating the curated external-client surface with `agent-latest.jsonl`; only bounded static labels and aggregate numerics are admissible fields (per obs-plan §8, §11).
- **Any new record must conform to the §3 log-format JSON schema.** `timestamp` / `level` / `target` / `message` / `fields` is a binding contract taken verbatim from the tests plan — obs aligns to tests, not the reverse — and it is the shape a headful stage matches against (per obs-plan §3, §6).
- **A per-press emission is off the hot path**, so §11's per-event emission ban (which forces tick-aggregation for the buffer/cue/cadence counters) does not constrain a user-gesture-cadence record (per obs-plan §11 Logs, §5).

## Patterns to follow
- **`tray.signpost.shown` → `window_label` (obs-plan §8, chunk 2026-08-23-headful-leg-extension).** A previously fieldless emission was given exactly ONE bounded field so the harness could assert a FIELD rather than record presence, with its wire-proof being the webview-drive widget-close stage matching the record BY that label. This is the same shape item 3 needs: a stage-matchable field on the very window (`report`) this chunk touches. §8 records `window_label` as produced by `sanitize_window_label`, bounded to the 4-window-label set plus `unknown`.
- **`app.boot.window.navigation` (obs-plan §8 + §6, chunk 2026-08-24).** Dual-site registration; three fields (`window_label`, `navigated`, `reason`); the field most tempting "for debuggability" (the URL) banned outright; guard under `pulse-app/tests/` and mutation-checked. §8 records `report` as the victim window in that chunk's WARN arm — the closest prior instrumentation of this exact window.
- **The three delegated-timing leaves — `metric.constellation.hue_update_ms` / `metric.constellation.discovery_ms` / `metric.findings.counter_refresh_ms` (obs-plan §5 naming, §8).** The precedent for a webview UI event becoming an obs record through the TauRPC bridge, and the source of the `metric.*`-family rule: each target needs its OWN leaf because the legitimate bare `metric` key keeps `value` and drops every label.
- **Bounded static `reason` / `error_category` label sets.** `app.boot.window.navigation`'s `navigated | blank | window_absent | url_unavailable` and `interpretation.model.load.error`'s six-value category set (obs-plan §6 `warn` row, §8) are the shape for encoding *why* a copy failed without carrying a message string across the bridge.
- **Count-not-content fields.** `app.boot.workspace_key` emits `key_bytes` (a byte count) plus a basename and never the value (obs-plan §8) — the admissible shape if the chunk wants to attest that content of some size reached the clipboard.

## Anti-patterns to avoid
- **NEVER use unstructured console/stderr text as the diagnostic** (obs-plan §11 Logs: "always JSON-per-line to file sink"; §2 agent-readable invariants). A bare `console.error` in the webview satisfies neither — it is not in the agent-readable surface at all. If item 4 adds a diagnostic, it must land in the JSON log via the bridge.
- **NEVER echo the report markdown, an excerpt, or a preview of it into `agent-latest.jsonl`** (obs-plan §11 Project-specific: the external curated surface and the self-observation surface are independent; §8 Vector 1).
- **NEVER serialize the raw rejection across the IPC bridge** — sanitize per Vector 2: no Rust struct names, file paths, library versions, or stack traces in what the frontend receives or logs (obs-plan §11 Spans/Traces, §8 data classification).

## Contract bindings
- **obs ↔ tests harness (§3 Log format JSON schema).** The schema is verbatim from the tests plan and binding in that direction; a headful stage that asserts a COPY-SUCCEEDED obs record consumes `target` + `fields`, and §8's `tray.signpost.shown` entry names the webview-drive stage as the live consumer of exactly that shape.
- **obs ↔ tests/CI gate design (§10 Load-profile constraints).** §10 requires every xtask check script over `agent-latest.jsonl` to be NEUTRAL-tolerant (absent stream ≠ failure). A copy-succeeded assertion implemented as such a script would therefore read NEUTRAL, not FAIL, when the record is missing — precisely the regression the gate exists to catch. The assertion belongs inside the headful stage, where the app is definitionally booted.
- **obs ↔ security (§8 Vectors 1–2).** The clipboard payload is external-client OTLP-derived content and the ACL rejection is an `AppError`-class boundary error; both carry security-plan-derived redaction obligations discharged at obs's logger/allowlist config.
