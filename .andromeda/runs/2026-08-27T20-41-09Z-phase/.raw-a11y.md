# a11y extract

## Relevance
Partial — the ACL widening and the xtask headful stage are outside the domain, but scope items 3 (which observable proves the copy succeeded) and 4 (keeping the failure legible) land squarely on SC 4.1.3 status messages / SC 4.1.2 name-role-value / SC 1.4.1 on the `report` window, which is a must-be-accessible surface (p9) in the P1–P14 set.

## Constraints
- The `report` window is a `role="dialog"` surface with a focus trap and cross-window Esc/✕ restoration to the `findings` window (via first-party Tauri events, not `focus-trap-react`) — any change to the Copy control must leave that contract intact, and pressing Copy must not steal focus out of the dialog (per a11y-plan §5 Keyboard Navigation → report-window + Focus restoration).
- An async action's outcome is a status message, not a label mutation: §7 Live regions requires non-blocking results under `aria-live="polite"` and failures under `role="alert"` / `aria-live="assertive"`; §1 P6 states the same shape for the completion path (`status[aria-live]` + `aria-busy` on the acting button). A button that only relabels itself to `Copy failed — retry` is the pattern this rule exists to catch. Whether the code already exposes any live region for the Copy result is research's question.
- Per §4 ARIA Patterns (Button row), the Copy control must carry `aria-busy` while the write is in flight and remain Enter/Space activatable with a stable accessible name/role/state (SC 4.1.2) — a name that flips between "Copy markdown" / "Copy failed — retry" / a copied state is the accessible name changing under the user, and must be reasoned about, not assumed benign.
- §3 Harness wiring &amp; conventions ("Adding a surface", standing rule) requires that error and in-flight states be auditable, not only the settled-success one — the `__mockReject` and `__mockDelayMs` response sentinels exist for exactly this, and any new/changed copy-result surface belongs in the p9 report axe spec in the SAME chunk.
- §2 agent-runnable invariant + §11 CI require machine-verifiable evidence for the WCAG claim: the xtask headful press is a product gate, not an a11y evidence path; if this chunk changes the report surface's semantics, the a11y evidence must still be axe/Playwright JSON emitted through the normal chain.
- §6 State color tokens + §6 contrast pairs require the failure state to be conveyed by text/icon alongside `--color-accent`, with error text meeting SC 1.4.3 4.5:1 against `--color-base` (§11 Visual restates the ban).
- §10 SLO invariants: zero WCAG AA violations on must-be-accessible paths and zero NEW violation tuples versus `baselines/a11y-violations-summary.json`; no retry-once, no soft gate.

## Patterns to follow
- The P6 async-action shape (Generate → `aria-busy` on the button → completion announced via a `status` live region) is the nearest shipped analog for Copy → success/failure, per §1 Critical paths P6.
- The p14 Investigate result/error/progress specs plus the `__mockReject` / `__mockDelayMs` sentinels are the template for auditing a rejected and an in-flight Copy, per §3 Harness wiring &amp; conventions.
- Accessible-name-first selector binding (the measured-per-surface convention adopted for P1 after the headful-leg re-pointing) rather than fresh `data-testid` handles, per §1 P1 row + §3.
- The §7 landmark precedent for announcement restraint: a live-summary element deliberately ships WITHOUT `role="status"` where it would stack announcements — a documented, reversible choice. If the copy-result observable adds a region, apply the same explicit reasoning.
- Semantic HTML first, ARIA second — a native `&lt;button&gt;` plus a real live region, never ARIA bolted onto a non-semantic node, per §4 naming convention + §2.

## Anti-patterns to avoid
- NEVER convey the copy failure by color alone; `--color-accent` needs a text/icon supplement (§11 Visual, SC 1.4.1).
- NEVER hide the outcome from assistive tech or add redundant/noisy ARIA in the fix (§11 Screen Reader) — a diagnostic that is `console.error`-only satisfies the developer but leaves SC 4.1.3 unmet for the user.
- NEVER defer the a11y consequence to a follow-up or gate it on a manual/human-only check; a11y is a fail-fast PR gate with machine output (§11 CI + §11 Universal).

## Contract bindings
- **a11y ↔ obs (§3 Structured violation JSON schema → obs §6):** the `wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` envelope is for WCAG ASSERTION violations only. If scope item 4 chooses an obs record as the copy-failure diagnostic, that is a product event and must NOT be shaped as an a11y violation record — flagging so P3 does not conflate the two.
- **a11y ↔ tests (§3 CI integration + §9):** `npm run test:a11y` runs in the same `ci.yml` and reuses tests' 5-command E2E driver (`boot`/`run`/`status`/`cleanup`/`logs`); the a11y specs live in `pulse-app/ui/tests-a11y`, a different harness from `xtask/src/webview_drive.rs::STAGES` where scope item 2's gate lands.
- **a11y ↔ design (§6):** `--color-accent` / `--color-base` (error text 4.5:1) and `--border-focus` (focus ring on the Copy button, ≥3:1 non-text) are design-token pairs verified by the colorjs.io token checker.
- **a11y ↔ layouts (§5):** report-window focus order and cross-window restoration to `findings`.

## Acceptance criteria contributions
- (a11y) The Copy outcome — success AND failure — is programmatically announced via a live region (`aria-live="polite"` for success, `role="alert"` / assertive for failure), not by the button's own label swap alone; whether such a region already exists on the report surface is research's question (per a11y-plan §7 Live regions + §1 Critical paths P6).
- (a11y) The Copy button exposes `aria-busy` during the in-flight write and keeps a programmatically determinable name/role/state throughout, activatable by Enter/Space (per a11y-plan §4 ARIA Patterns &amp; Roles, Button row).

- (a11y) The failure state carries a text/icon supplement (not `--color-accent` alone) and its text meets SC 1.4.3 4.5:1; the run adds zero new violation tuples versus the regression baseline (per a11y-plan §6 State color tokens + §10 SLO Invariants).
