## Relevance
Relevant — arch owns the capability-policy rule this defect instantiates, the registry classes a window-label widening does and does not touch, and the harness Role cell the new gate lands in.

## Constraints
- Tauri capabilities are negative-default, but the granularity is the **IPC layer**, not the procedure: TauRPC dispatches through one invoke handler, so no per-procedure capability entries exist. What DOES require an explicit per-feature grant **with a stated rationale** is a core-API / plugin-permission surface — and those are **silently rejected at runtime when missing**, which is exactly the failure class this chunk fixes (per arch §Cross-cutting Patterns → Webview IPC capability policy). Whether `clipboard.json`'s existing `description` already carries a rationale in the required shape, and what form satisfies it for an added window label, is research's question.
- `pulse:clipboard` is already a reserved capability identifier and concrete capability JSON lives under `pulse-app/capabilities/` — this chunk adds no identifier, so the reserved set is unchanged (per arch §Occupied Resources → Tauri capability identifiers).
- Adding a TauRPC procedure costs a router registration in the owning crate + an §Occupied Resources entry + an `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` (what `capability-drift` diffs) — **not** a capability-JSON edit (per arch §Cross-cutting Patterns → Webview IPC capability policy). This is the price tag on any option in scope items 3–4 that reaches for a new IPC surface.
- A webview-originated observable has exactly ONE sanctioned route to the obs log: a `telemetry.frontend.*` ui-bridge procedure with a bounded input type and its **own exact obs allowlist leaf** (per arch §Occupied Resources → Tauri IPC routes, `telemetry.frontend.*` entry). So the "obs-log record" candidate for scope item 3/4 implies a new procedure — colliding with the chunk's own no-new-procedure boundary; the DOM/label-observable candidates carry no arch cost.
- The GUI harness is ONE CLI (`cargo xtask webview-drive [--expect-absent &lt;STAGE&gt;] [--no-inject]`) over an assembled 15-stage path under the deterministic-L4 gate, each stage `--expect-absent`-eligible and asserting against the app's own obs log and/or the driver's DOM report, with telemetry entering only over real OTLP (per arch §Stack and Technologies → GUI verification harness (dev-only) row). That Role cell is the ONLY site stating the stage count.
- Workspace placement: capability JSON and window declarations in the `pulse-app` binary crate, webview code under `pulse-app/ui`, harness stages in the reserved `xtask` crate — all shared CI logic needing Rust lives in `xtask` (per arch §Occupied Resources → Cargo workspace crate names; §Infrastructure Patterns → Build system).

## Patterns to follow
- Per-feature capability JSON files under `pulse-app/capabilities/`, each scoped to the windows and permissions it needs and carrying its own rationale — `pulse:tray` / `pulse:notification` / `pulse:updater` / `pulse:plugin-fs` / `pulse:clipboard` are the established shape (per arch §Occupied Resources → Tauri capability identifiers; §Cross-cutting Patterns → Webview IPC capability policy).
- Harness stage growth as a single Role-cell amendment with the CLI shape untouched and every new id `--expect-absent`-eligible — the 7 → 13 → 15 lineage is the precedent (per arch §Stack → GUI verification harness row).
- Cross-window coordination through first-party `@tauri-apps/api/event` emit/listen gated by `core:event` in `pulse:default`, a class distinct from the `pulse://stream/*` Rust→webview broadcast topics — the `report:open` / `report:closed` pair the report window already participates in (per arch §Occupied Resources → Tauri IPC events).
- Verification drives the real surface an external actor would drive, with no in-process bypass and no test-only back door (per arch §Cross-cutting Patterns → Test-time telemetry injection) — the same discipline scope item 2 states for pressing the real Copy control rather than a `writeText` proxy.

## Anti-patterns to avoid
- Do not add a per-procedure capability entry, and do not treat a capability-JSON edit as the gate for an IPC-layer change — the 2026-08-21 correction measured that requirement false (per arch §Cross-cutting Patterns → Webview IPC capability policy).
- Do not open a new registry class for this fix — no new env var, capability identifier, TauRPC procedure, DuckDB table or workspace crate is implied by widening one window list (per arch §Occupied Resources).
- If a diagnostic observable is added, do not target a bare `metric.*` key without its own exact allowlist leaf — a leaf-less target keeps `value` and has every label silently redacted (per arch §Occupied Resources → Tauri IPC routes, `telemetry.frontend.*` entry).

## Contract bindings
- **arch ↔ security**: arch reserves the `pulse:clipboard` identifier only; the write-only posture (clipboard READ excluded) is security-plan §Anti-Patterns API row 6, cited when the capability was registered. The chunk's ban on `allow-read-text` / `allow-read-image` is security's mandate, not arch's.
- **arch ↔ tests**: arch's §Stack Role cell states the assembled stage count and CLI shape; the stage's assertion design is tests' domain. A stage added or re-scoped by this chunk makes that cell stale and is an arch amendment due at wrap.
- **arch ↔ obs**: if research picks an obs-log record as the discriminating COPY-SUCCEEDED observable, the `telemetry.frontend.*` route + per-target allowlist-leaf binding applies (arch §Occupied Resources → Tauri IPC routes, deferring to obs-plan §1/§4 for the target name).

## Acceptance criteria contributions
- The widening adds only the `report` window label to an existing grant, with a stated rationale in the capability file — no new permission, no new capability identifier, and `pulse-app/capabilities/` gains no new file (per arch §Cross-cutting Patterns → Webview IPC capability policy; §Occupied Resources → Tauri capability identifiers).
- No new TauRPC procedure, no `EXPECTED_PROCEDURES` delta, and no new env var or workspace crate — if the chosen diagnostic (scope item 4) would require any of these, that cost is stated and paid explicitly rather than absorbed (per arch §Cross-cutting Patterns → Webview IPC capability policy; §Occupied Resources → Environment variables).
