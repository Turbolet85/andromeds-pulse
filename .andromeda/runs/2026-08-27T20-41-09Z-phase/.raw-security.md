## Constraints
- A capability grant that unlocks a silently-rejected runtime surface MUST carry an explicit per-feature addition with a stated rationale; security-plan §Security Anti-Patterns → API names this exact failure mode ("a hard-to-diagnose dead-affordance bug"). Note the ban enumerates core APIs (`fs`/`shell`/`dialog`/`http`) and `core:window:*` — it does **not** name plugin ACL permissions such as `clipboard-manager:*`, which are silently rejected the same way; whether that enumeration should be extended to plugin permissions is an amendment candidate this chunk may owe (per security-plan §Security Anti-Patterns → API; §API Security → TauRPC capability authorization).
- The widening MUST stay minimum-scope: one window label joins an existing **outbound write-text** grant, no permission added. Security-plan §Security Anti-Patterns → API classifies outbound surfaces (`pulse:notification`, `pulse:tray`) as requiring the capability JSON to list only the outbound subset, with any inbound handler forced into a separately-named capability with its own rationale — the same discipline governs adding `allow-read-text`/`allow-read-image` here (per §Security Anti-Patterns → API).
- Clipboard is a declared OTLP-attribute leakage path: `snapshot.copy_to_clipboard` is required to emit a visible clipboard-write signal ("X bytes copied") so the user sees data leave the app's address space. This chunk introduces a SECOND clipboard-write path; whether the plan's mandate reaches the report-window Copy control (it is written against the snapshot TauRPC procedure, and the report path calls `writeText` from the webview) and whether the existing UI already surfaces such a signal is research's question (per security-plan §Logging &amp; Monitoring → Snapshot/clipboard/MCP-tool-response hygiene).
- Security-plan §Logging &amp; Monitoring → "What to log" REQUIRES Tauri capability-rejected IPC calls to be logged, precisely because such rejections are silent at runtime. Scope item 4 ("whether this chunk adds a diagnostic") is therefore answered by the plan in the affirmative — only the FORM of the diagnostic is a research call. Whether any such logging exists on this path today is research's question (per §Logging &amp; Monitoring → What to log).
- No artifact of this chunk — log record, obs field, gate assertion, status detail, or user-visible error — may carry the copied markdown payload or an excerpt; byte counts and bounded categories are the permitted shapes (per §Security Anti-Patterns → Logging, NEVER-log bullet 1; §Logging &amp; Monitoring → What NEVER to log, "Clipboard contents (`snapshot.copy_to_clipboard` MUST NOT log the markdown payload)").
- Any user-visible error text on the Copy path MUST be sanitized — no stack traces, file paths, Rust struct names, or library versions (per §Error Handling → External responses; §Security Anti-Patterns → Logging, `AppError::Internal` bullet). Full product-consumed filesystem paths must not appear in the new gate's or diagnostic's records — basename only (per §Security Anti-Patterns → Logging, basename bullet).
- The new headful stage lands in the harness that owns the `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` carve-out; its guard (trim + `is_file()`, unset/not-a-file ⇒ clean SKIP exit 0, resolved value never logged — only the var NAME and the fetch URL) MUST be preserved, not bypassed or hardened into a hard fail (per §Input Validation → CLI/env var inputs, harness-only path boundary).
- The folded `cargo audit` PREREQ: this wrap is a BETWEEN-point session (49 ran, next point 52), so the owed action is re-verify basis + overlap and record `probe skipped per ratified interval (next: 52)` — never a silent skip (per §Dependency Security → CI integration, Standing deferral — `cargo audit` unrunnable).

## Patterns to follow
- Rationale-in-the-capability-file: the grant's own `description` states why the surface is admitted, matching how `clipboard.json` already documents its chunk-#43 origin (per §Security Anti-Patterns → API, rationale-on-grant).
- Bounded error category on an existing named leaf, carrying no payload bytes: the `interpretation.inference.error` precedent, where formerly-silent failure sites became bounded categories (`io_error`, `stdout_utf8_invalid`) with no output bytes or offending substring (per §Input Validation → L4 inference argv prompt row; §Security Anti-Patterns → Logging).
- Visible-signal-not-sanitization: the project's chosen posture for clipboard/snapshot leakage is a user-visible signal plus README warning rather than payload sanitization (per §Logging &amp; Monitoring → hygiene; §Security Anti-Patterns → Logging).
- Identifier-not-content logging: permission ids, window labels, and env-var NAMES are safe to record; values and payloads are not (per §Security Anti-Patterns → Logging, basename/name-only bullet).
- Drift gates as enforcement: `xtask capability-drift` / `EXPECTED_PROCEDURES` is the per-procedure enforcement mechanism and must stay green; the scope's claim that no procedure is added means this gate is untouched, which research should confirm rather than assume (per §API Security → TauRPC capability authorization).

## Anti-patterns to avoid
- NEVER grant `clipboard-manager:allow-read-text` / `allow-read-image` — that converts an outbound write surface into an inbound read vector, the same conversion §Security Anti-Patterns → API bans for `pulse:notification` / `pulse:tray`. **This directly constrains scope item 3:** an in-app clipboard read-back as the "did it copy" observable would require exactly the permission this chunk bans; only a harness-side (OS/WebDriver) read avoids that.
- NEVER log clipboard contents, snapshot file contents, or raw OTLP attribute values in the new diagnostic, obs record, or gate output (per §Security Anti-Patterns → Logging, bullet 1).
- NEVER widen `pulse:notification` / `pulse:tray` / `pulse:plugin-fs` as collateral of this change — the scope already fences them and §Security Anti-Patterns → API bans it independently.
