# a11y extract

## Relevance
partial — one item of the chunk sits in the a11y domain: the `a11y` job's `a11y-violations` upload and its three path members (scope, third `CARRY:`). No UI surface, WCAG criterion, ARIA role, focus order, keyboard sequence, contrast pair or motion token is touched; a11y-plan §4–§8 contribute nothing.

## Constraints
- a11y-plan §3 CI integration → Pipeline integration requires the `a11y` job to upload its artifacts `if: always()` under two names and requires each upload to fail its step when it finds no file. The requirement is stated per UPLOAD, not per path member: the plan carries no sentence about one member of several being absent. Whether `ci.yml:258-268` fails on one missing member is research's question (the scope's hypothesis is that it does not).
- a11y-plan §9 CI Integration → Per-pipeline-stage a11y artifacts (E2E row and Aggregation row) names the result files the E2E stage emits and names the uploaded artifact as their consumer. Which of those named files each of the three path members matches, and whether every named file has a producer on a run, is research's question; the plan names files, not globs.
- a11y-plan §3 CI integration → Per-PR regression detection requires the regression detector's own output file to be uploaded with the per-run results "for audit". A settlement that drops or narrows a path member is read against this sentence.
- a11y-plan §10 SLO Invariants → Standard+ invariants requires the per-PR diff to run against the baseline file committed in the tree and states that no artifact is compared. The upload is therefore an audit channel, not an input to any comparison the plan mandates: no a11y gate in the plan reads the uploaded artifact back. This is the plan's own basis for the P4 question of whether a missing member is "a gate reading nothing".
- a11y-plan §2 A11y Strategy → A11y signal pyramid (Agent-driven row) lists the CI artifact upload among the machine-verifiable evidence paths, and §2 → Agent-runnable invariants requires machine-verifiable evidence behind every conformance claim. If the upload (or a member) leaves, the plan needs to say where the per-run machine output is kept; the plan today names no second home.
- a11y-plan §10 SLO Invariants → Build / deploy failure conditions lists four hard conditions for the a11y run. None of them is the upload; the chunk's edit of the upload step must leave all four deciding the job as before.
- a11y-plan §3 Harness wiring & conventions → Regression baseline names two pins in `pulse-app/tests/a11y_perf_workflow.rs` that hold the committed-baseline and absent-baseline arms. The scope lists that file among what reads the edited steps: those two pins are outside this chunk's edit and stay reading what makes them fail. Which further pins in the file read the upload step is research's question.

## Patterns to follow
- The absent-input arm as an error with a named message and exit 1, pinned in the tree: a11y-plan §3 Harness wiring & conventions → Regression baseline is the domain's settled instance of "reads something or fails", and the shape a kept upload member would follow.
- Upload-level failure on no file, stated once in the plan and pinned by a workflow-reading test: a11y-plan §3 CI integration → Pipeline integration. A per-member form, if the P4 dialog chooses repair, extends this sentence rather than adding a parallel mechanism.
- The domain's recorded precedents of a pass over nothing — unpopulated fixtures auditing a blank region, and a list-time import failure that silently disabled the whole suite, with the config-named `--list` as the cheap health read: a11y-plan §3 Harness wiring & conventions → Adding a surface (standing rule). The scope names only the upload inside the `a11y` job; whether P-128's third clause, read at P5, is taken to cover the a11y suite's own empty-selection arm is the dialog's question, not a mandate of this plan.
- Tuple-keyed regression detection against the tree file, with no download: a11y-plan §3 CI integration → Per-PR regression detection. The scope's re-read of "the first two clauses still holding" covers this leg on the chunk's run.

## Anti-patterns to avoid
- No soft a11y gate: a settlement that makes any a11y step warn instead of fail (a `continue-on-error`, a NEUTRAL arm) is banned by a11y-plan §11 A11y Anti-Patterns → CI ("NEVER skip a11y on CI failure") and §11 → SLO ("NEVER define soft a11y SLO").
- No loss of the per-PR diff while settling the upload: a11y-plan §11 A11y Anti-Patterns → SLO bans skipping regression detection at this tier, including on an absent baseline.
- No conformance evidence that exists only as a human reading: a11y-plan §11 A11y Anti-Patterns → Strategy and §11 → Universal ban a conformance claim without machine output; removing the artifact without a kept machine record moves toward that.

## Contract bindings
- a11y ↔ tests: the `a11y` job is a job of the same `ci.yml` as the test jobs and reuses the tests harness (a11y-plan §9 CI Integration → Pipeline integration); the pins that read its steps live in a test file the tests domain owns (a11y-plan §3 Harness wiring & conventions → Regression baseline). An edit of the upload step binds to whatever test-plan says about that file's pins.
- a11y ↔ obs: the uploaded files are emitted in the obs log format with the obs resource attributes (a11y-plan §3 Structured violation JSON schema; §9 CI Integration → CI-specific resource attributes). A change in which files the upload carries binds to any obs-plan sentence that lists the CI artifacts that exist; whether obs-plan lists the members is the obs extract's.
- a11y ↔ route: the plan carries no sentence that the `a11y` job leaves; its mandates read as standing. The job's leaving at `Window's gates retired` is the scope's and the route's, so "what the job loses before it leaves" is weighed against a plan that still requires the upload.
- Expected wrap-amendment sites in this plan, if the upload's members or failure rule change (phase amends none): §1 A11y Scope Summary → CI Integration (the Output file list); §3 CI integration → Pipeline integration (the no-file sentence) and → Per-PR regression detection (the "uploaded … for audit" clause); §9 CI Integration → Per-pipeline-stage a11y artifacts (E2E and Aggregation rows).
