## Constraints
- obs-plan §10 → CI gates (the perf-budget bullet) requires the perf gate to fail on an arm over budget, on a graded field that is not a JSON number, and on a `--require`d arm with no sample, and to be "never PASS over empty input"; the same bullet states as designed that `ci-gates` grades the boot-smoke log with NO arm required and prints `perf-budget NEUTRAL` over it. The chunk's standard (a gate printing NEUTRAL over nothing is the defect) and that designed posture do not both hold for gate (4): whichever way the P4 fork falls, that sentence is an expected amendment site, not something phase edits.
- obs-plan §10 → DuckDB Connection Isolation & Load-Profile Operational Constraints (the Load-profile constraints paragraph) requires any xtask check over `agent-latest.jsonl` to be NEUTRAL-tolerant for an UNREQUIRED arm so headless and full-app sessions share one grader, and names `ci-gates` and `perf:load-profiles` as the two callers that grade with no arm required; a caller that expects samples names the arm with `perf:budget --require`. A repair of gate (4) that keeps `ci-gates` therefore goes through naming required arms, not through making the shared grader fail on every absent stream — `perf:load-profiles` rides the same grader and is outside this chunk.
- obs-plan §10 → Performance budgets (the buffer-memory row) requires a REQUIRED memory arm holding only zeros to fail (a 0 sample is the placeholder before the first retention sweep) and locates the enforced memory and snapshot arms in the lint-test job over the `perf_budget_samples` producer log. Whether a boot of the length the boot job runs can hold a non-zero memory sample or any snapshot sample at all is research's question; the plan's frame row records one measured app life of 5.494 s on `ci#37979648967`, against a 15 s tick.
- obs-plan §10 → CI gates (the heartbeat bullet) requires the build to fail on a gap above 45000 ms between CONSECUTIVE ticks per target (`ingest.tick` / `buffer.tick` / `viz.tick` / `plugins.tick`) "during the test run", and names `xtask/ci/heartbeat-gap-check.sh` as the concrete script. The bullet is silent on a log holding fewer than two ticks of a target (no consecutive delta exists). What the check in the tree does on such a log, whether that script exists, and how many ticks per target the boot-smoke log holds are research's questions — the "max gap 0ms … PASS" line in the scope is the reading to reproduce.
- obs-plan §3 Heartbeat ticks (Tick interval; Stall detection) fixes the interval at 15 s and the stall signal at a missing tick for more than 45 s, and states that tick presence is LIVENESS only; obs-plan §10 → Standard+ invariants (Heartbeat ticks) adds that progress is asserted separately by `cargo xtask check:ingest-progress`. A gap check can only read something on a log spanning more than one interval per target; the boot smoke, its series and its length are not this chunk's to change (scope Boundaries), so "make the boot longer" is not an available repair.
- obs-plan §10 → CI gates (the zero-span bullet) requires the build to fail when `xtask test` produces zero spans in the log file, "enforced by `xtask test` step exit code validation", while obs-plan §9 → Pipeline integration (the `xtask test` row) records that the lint-test job boots no app and that no step of it writes a log family under its data dir (as measured on `ci#38031822696`). Read together, the plan itself gives the lint-test home of gate (5) no log to read; whether `xtask test` validates anything of the kind, and what the zero-span arm inside `ci-gates` counts as a span on the boot-smoke log, are research's questions.
- obs-plan §10 → Always-required SLO invariant (Zero unlogged panics) and obs-plan §10 → CI gates (the `app.panic.fatal` bullet) require a CI check that fails the build on a panic record in the log. The scope does not name it among the five; whether that check lives inside the same `cargo xtask ci-gates` step as gate (4) and the home of gate (5) is research's question, and if it does, a fall that removes the step whole removes an always-required invariant's only CI reader — that arm reads a log that exists on every run that reaches the step.

## Patterns to follow
- The two-state arm posture — per obs-plan §10 → Performance budgets (the frame row): an unrequired arm with no samples reads NEUTRAL, never FAIL and never PASS; a required empty arm fails; a zero-sample arm prints `cannot-evaluate` with a cause derived from the log's own records. A kept arm of gate (4) follows the required form.
- A record that cannot be graded fails the run, it is never dropped — per obs-plan §10 → Performance budgets (the L4 row), which records the prior vacuous pass ("gate trivially passes") and its closure, with the witness shape the scope asks for: the same samples shown failing at a budget they cannot meet.
- One producer, one grader, one named log — per obs-plan §10 → CI gates (the perf-budget bullet) and obs-plan §9 → Telemetry artifact handling (the Log file row): the lint-test job runs the `perf-samples` producer, then `perf:budget --require memory,snapshot` over that producer's data dir, and uploads that log as `logs-perf-samples-Linux`. A gate that is kept and has no producer in its job gets one this way or leaves.
- A later owner is named on the route, not assumed — per obs-plan §10 → CI gates (the perf-budget bullet, its closing sentences) and obs-plan §9 → Telemetry artifact handling (the Snapshot markdown row): the engine's memory and load readings are owned by named route entries, and the unmet §11 CI bans by `Engine end-to-end gate reachable`. For gate (4) and the home of gate (5), the plan's "does a later entry already own the same reading" answer cites those rows; none of them names a heartbeat-gap, zero-span or panic reading over the engine, so that ownership is not established by the obs plan.
- Measured claims carry their run — per obs-plan §9 → Telemetry artifact handling and obs-plan §10 → Performance budgets (the frame row): each statement about what a CI step read names the run id and how many runs were read. The expected-amendment sentences the plan drafts follow that form.

## Anti-patterns to avoid
- NEVER define a soft SLO budget with no enforcement — per obs-plan §11 → SLO: memory max above 512 MB or snapshot p99 above 500 ms must fail lint-test through `perf:budget`. Retiring the boot job's unrequired arms is not a soft budget only while the lint-test `--require memory,snapshot` gate stays as it is; the chunk does not touch that step except to re-read it.
- NEVER skip the zero-unlogged-panics invariant — per obs-plan §11 → SLO: a fall that removes `cargo xtask ci-gates` from the boot job without placing the panic read elsewhere (or showing another step already makes it) is this ban.
- NEVER lose telemetry artifacts — per obs-plan §11 → CI: no fall of this chunk removes or weakens the `logs-boot-Linux` or `logs-perf-samples-Linux` upload or its `if-no-files-found: error`; the snapshot-on-failure half of that ban stands unmet with its owner (obs-plan §9 → Telemetry artifact handling, the Snapshot markdown row) and is not this chunk's.
