## Patterns to follow
- Shared CI logic that needs Rust lives in the `xtask` crate, so the command a job runs is the command a contributor runs locally. A gate that is kept and must gain a failing arm on empty input gains it in an xtask verb, wired as a plain `run:` step (per architecture.md §Infrastructure Patterns → CI/CD approach). Whether the coverage thresholds step is inline shell in ci.yml today, and whether moving it is in this chunk's reach, is research's question.
- The formalized CLI contract: every registered verb states its exit codes, its closed verdict arms and its output shape, on the three-code form 0 green · 1 red · 2 cannot-evaluate, where an absent or unreadable input is `cannot-evaluate` and "never a pass" (`check:english-sources`), with "no neutral arm" where a subject is missing (`check:staged-artifacts`). A verb arm the chunk adds or changes follows that form and is registered at wrap (per architecture.md §Occupied Resources → xtask CLI surfaces).
- A required arm is the existing way to make an empty input fail: `perf:budget --require <arm,arm>` reads a `--require`d arm with no sample as FAIL, and `lint-test` already runs it that way over the `perf_budget_samples` producer log. It is the in-plan precedent for a gate that "reads something or fails" where a producer exists (per architecture.md §Occupied Resources → xtask CLI surfaces; the `lint-test` wiring per §Infrastructure Patterns → CI/CD approach).
- A test-only or harness-only tool a job or a test needs is a Stack row of its own, with "a missing tool FAILS the test, never skips it" (the `node` row, the exit-witness `cc` row). A witness that runs a gate on a constructed empty input follows the `node` row's shape (per architecture.md §Stack and Technologies, A11y regression-detector pin row).
- Workflow steps are held by tests in `pulse-app/tests/quality_gate_workflow.rs` and by self-lint tests named in the plan; a step that goes takes its pin with it and a step that stays keeps one (per architecture.md §Infrastructure Patterns → CI/CD approach).

## Anti-patterns to avoid
- An xtask arm that exits 0 over an absent, unreadable or empty input. The registered verbs class that input as `cannot-evaluate` or red; a new PASS-or-NEUTRAL-with-exit-0 arm contradicts the registered form (per architecture.md §Occupied Resources → xtask CLI surfaces).
- Wiring a gate through a third-party action, a token or a widened `permissions:` block. The plan's registered CI steps are plain `run:` steps with the workflow's permissions untouched, and `cargo audit` left its action for that reason (per architecture.md §Infrastructure Patterns → CI/CD approach; the `check:staged-artifacts` wiring per §Occupied Resources → xtask CLI surfaces).
- Feeding a kept gate through an in-process bypass. Telemetry a test needs enters over the real OTLP receiver; no test-mode ingest, feature flag or mock channel (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection). A producer that binds the default ports on the dev host needs the override variables the same section names.
