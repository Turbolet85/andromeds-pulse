# tests extract

## Relevance
relevant — the chunk edits CI gates, the `cargo xtask test` / `test:coverage` / `perf:slo-load` / `ci-gates` verbs and the workflow-reading pins, all of which test-plan §9, §10 and §3 govern (tier: Standard, per test-plan §1 Test Scope Summary).

## Constraints
- test-plan §10 Coverage thresholds requires three thresholds for the Standard tier (line, branch, function) and test-plan §9 Build failure conditions requires the build to fail below any of them; retiring gate (2)'s branch arm therefore removes a stated build-failure condition, and producing a branch count keeps it. Whether the pinned toolchain and `cargo-llvm-cov` release named in test-plan §4 Unit Test Strategy (Coverage tool) can write a branch count into `lcov.info` is research's question; the plan states the threshold, never how the count is produced.
- test-plan §11 Test Anti-Patterns → CI bans lowering a coverage threshold to pass a build. The P4 fork on gate (2) has to say whether retiring the branch arm is that ban's case or a correction of a threshold nothing ever read; the extract cannot rule it, and the ban's wording is about lowering, not about an arm with no input.
- test-plan §10 Coverage thresholds requires `xtask/` to stay excluded from the coverage measure, temporarily, under a founder ruling; a repair of gate (1) or gate (2) that changes what `cargo xtask test:coverage` measures must not move that exclusion in passing.
- test-plan §9 Pipeline structure (MCP-feature tests row) spells the `mcp-test` job's command with `--no-tests=pass` in it, and the lint-test row describes `cargo xtask perf:slo-load` as selecting one test by a `binary(...)` expression under `--workspace`. Whether any of the five literals can meet an empty selection on a run of the tree, and what each selects today, is research's question; the plan states the commands, not a reading of an empty selection.
- test-plan §9 Pipeline structure (Boot smoke row) requires `cargo xtask ci-gates` to run in the `boot` job only, over the log the smoke wrote, and to be skipped when the smoke or the series fails; the smoke and `Boot series (equal source)` steps stay gating as that row and test-plan §9 Build failure conditions state. Gate (4) and gate (5)'s one home are settled inside that order without touching the two steps before them.
- test-plan §9 Build failure conditions requires that no step of `ci.yml` carries `continue-on-error` and that none downloads an artifact without a producer, held by workflow-reading pins in `pulse-app/tests/quality_gate_workflow.rs`; a step this chunk edits or removes keeps those pins true, and the pin whose listed-gate arm counts commands follows any gate command that leaves. Which pins read the edited steps today is research's list.
- test-plan §3 Per-chunk gate discipline requires the plan's `## Test Commands` to carry the standard gate set unconditionally, with `capability-drift` before the workspace nextest and the bindings regen as the last cargo-adjacent step, closed by the chunk-base diff probe (a chunk adding no TauRPC procedure); the webview gates are excluded only when no `pulse-app/ui/**` path is touched.
- test-plan §3 Per-chunk gate discipline → The merge-base probe requires every plan that lists a build-branch push to list the probe directly before it, on the operator leg, with a red brought to the operator before any push and never cleared by the pass itself.

## Patterns to follow
- An arm that reads no input is told apart from a pass by a named verdict and its own exit code: test-plan §3 Per-chunk gate discipline describes the `perf:budget` exit contract (a required-but-empty arm fails; every arm empty with none required is cannot-evaluate) and test-plan §1 Pending coverage triggers (`perf-slo-check-arm-coverage` row) describes the grader's per-arm rule. A kept gate of this chunk takes that shape (required input, a failing arm on its absence) rather than a new one; whether `ci-gates` in the boot job passes `--require` today is research's question.
- A leg proves its own preconditions: test-plan §3 Per-chunk gate discipline describes scenario legs that report INCONCLUSIVE, never PASS, when the input a verdict rests on never arrived, and refuse a window in which the failing reading is unreachable. The chunk's "witness that cannot pass vacuously" follows it: a kept gate is shown red on an empty or absent input.
- Red before green, then a mutation: test-plan §3 Per-chunk gate discipline → Direct-binary smoke variant records the wrong-reason-pass hazard (a clean assertion passing vacuously over a run that produced nothing) and requires the evidence shape to be chosen before the leg runs; the pins of a kept gate are mutation-checked so the absent-input arm is the one that reds.
- Workflow steps are pinned by tests that read `ci.yml` as text: test-plan §9 Pipeline structure and test-plan §9 Build failure conditions name them in `pulse-app/tests/quality_gate_workflow.rs` and `pulse-app/tests/a11y_perf_workflow.rs`. A step that stays gets or keeps a pin that reads what makes it fail; a step that goes takes its pin with it. New pins of `pulse-app` live under `pulse-app/tests/*.rs`, and `xtask` arms are pinned in-crate, per test-plan §2 Test Strategy (Test directory + naming conventions).
- A CI run is read by exit code and the job log: test-plan §9 Test report format states that no machine-read test report exists, so the gate-by-gate reading of the pre-CI commit's run is taken from each job's step conclusions and log text.

## Anti-patterns to avoid
- NEVER lower a coverage threshold to pass the build (test-plan §11 Test Anti-Patterns → CI); see the second constraint for how it bears on gate (2).
- NEVER soften a gate with a retry, a soft-fail key or a quarantine without a tracked reason (test-plan §11 Test Anti-Patterns → Quality; test-plan §10 Zero-flakiness budget): a gate that cannot read its input leaves or fails, it is not made tolerant.
- NEVER a manual verification step and NEVER a third-party action by floating tag (test-plan §11 Test Anti-Patterns → Universal; test-plan §11 Test Anti-Patterns → CI): the proof is a run read by exit codes, and a repair that would need a new action stops at the scope's boundary before it reaches the SHA-pin rule.

## Contract bindings
- tests ↔ tests (the local pre-push check): test-plan §3 Per-chunk gate discipline describes `cargo xtask pre-push:linux`, whose `test` stage runs `cargo xtask test` and whose last stage runs `ci-gates` over a data dir holding only a seed log of non-metric records. A `ci-gates` arm that starts failing on empty input, or a `cargo xtask test` that stops passing an empty selection, changes what those two stages read. Whether the seed log satisfies the edited arms is research's question, and the plan must keep that check green or say what changes in it.
- tests ↔ tests (the standard gate set): test-plan §3 Per-chunk gate discipline describes `cargo xtask check:ingest-progress` with a NEUTRAL arm on a run with no `buffer.tick`, stated there as what makes the check safe unconditionally. Whether that verb is a step of `ci.yml` (and so a gate in the scope's sense) is research's question; if it is, it is a sixth reading for the P4 dialog, not something the plan settles silently.
- tests ↔ obs: test-plan §10 Performance budgets (Frame-budget assertion note) defers the asserted budgets to obs-plan §10, and requires the CI frame arm to print a named cannot-evaluate line, never PASS. The zero-span build failure and the heartbeat read are obs-plan §10's statements: test-plan §9 Pipeline structure names no zero-span step in the lint-test row. `ci-gates` reads the log family whose shape test-plan §3 `logs` (Format) and test-plan §3 Log format bind to obs-plan §3.
- tests ↔ a11y: test-plan §9 Pipeline structure (A11y suite row) and test-plan §9 Build failure conditions state the a11y upload as failing only when none of its three path members matches; the gate conditions of the suite itself are a11y-plan's.
- tests ↔ security: test-plan §9 Pipeline structure (Staged artifacts row) is the precedent for a plain `run:` step with the workflow's `permissions:` untouched; any step this chunk adds takes that form (security-plan's supply-chain rules own the rest).
- Sites of test-plan that state the edited gates as designed, for the plan's expected-amendments list (phase amends none): the branch threshold in test-plan §4 Unit Test Strategy (Coverage target), test-plan §9 Pipeline structure (Quality gates row), test-plan §9 Build failure conditions, test-plan §10 Coverage thresholds, test-plan §10 Build failure conditions and test-plan §3 Bootstrap phases (item 8); the `--no-tests=pass` literal in test-plan §9 Pipeline structure (MCP-feature tests row); the `ci-gates` position and the NEUTRAL-reading frame line in test-plan §9 Pipeline structure (Boot smoke row) and test-plan §1 Test Scope Summary (the WebGPU performance-budget row); the `ci-gates` stage in test-plan §3 Per-chunk gate discipline.
