## Patterns to follow
- The formalized xtask CLI contract (architecture.md §Occupied Resources → xtask CLI surfaces: one verdict on stdout, exit 0/1/2 arms, registered in Occupied Resources) applies if the red-before/green-after witness is realized as a new xtask verb or a new arm on an existing one. A new verb must be registered there, which is a wrap-time amendment.
- "All shared CI logic that needs Rust lives in the `xtask` crate" (architecture.md §Infrastructure Patterns → CI/CD approach). A license-consistency witness that is wired into CI belongs in `xtask` (beside `Cmd::DenyBans` / `check:npm-supply-chain`), not in ad-hoc workflow shell.
- Supply-chain checks run as plain `run:` steps in ci.yml's `supply-chain` job (architecture.md §Occupied Resources → xtask CLI surfaces, the `check:npm-supply-chain` wiring; §Infrastructure Patterns → CI/CD approach, seven-job layout). Any new or changed license gate rides that job rather than adding an eighth job.
- Root-level repo files sit beside `Cargo.toml` / `Cargo.lock` / `rust-toolchain.toml` in architecture.md §Infrastructure Patterns → Project directory structure. `LICENSE-MIT` / `LICENSE-APACHE` land at that root. The tree lists a `README.md` that does not exist at HEAD, and scope excludes it.

## Anti-patterns to avoid
- Do not create a new workspace member, crate or reserved name to host license tooling (architecture.md §Occupied Resources → Cargo workspace crate names are reserved; §Project Intent → reserved crate names cannot be re-purposed). The witness lives in the existing `xtask`.
- Do not add a new env var or config key for license behavior (architecture.md §Cross-cutting Patterns → Config management, where precedence is env > config.toml > defaults). The license is static manifest metadata, not runtime config.
