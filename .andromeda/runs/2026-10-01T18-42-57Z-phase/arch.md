# arch extract

## Relevance
partial. Arch governs where the PREREQ exit-cause code lives (the `pulse-app` binary boundary), which sink it may write to (the self-observation file sink), and the registered surfaces the external P-075 round consumes (the MCP sidecar wire, the deterministic-L4 env gate, the delegated timing observables, binary identity). The exit-class enumeration, the record's fields, the allowlist leaf and the round's assertions belong to obs, tests and security, not arch.

## Constraints
- The exit-cause hook (a panic, explicit-exit, event-loop-exit or `atexit`-class observer) belongs at the `pulse-app` binary boundary, which owns the tokio runtime and boot wiring. Library crates must not depend on the binary, and a helper placed in a lib crate must not add a sibling edge its contract does not require (per architecture §Cross-cutting Patterns → Module dependency direction; §Established Decisions [Module Boundaries]; §Inherited Defaults → Module boundaries). Research decides which crate owns today's tracing init and panic hook.
- The cause record goes only through the product's own self-observation sink: the `tracing` file sink under the resolved data dir's `logs/` subpath. No new exporter or channel, and never the product's own `:4317`/`:4318` (per architecture §Established Decisions [Self-Observation]; §Cross-cutting Patterns → Self-observation discipline; §Occupied Resources → Filesystem locations). Whether that sink drains a line written just before process end is research's question. Arch states no flush guarantee.
- Error-handling layering stays in place: `main.rs` and non-IPC top-level code use `anyhow::Result`, module code uses `thiserror` enums, and nothing new crosses the TauRPC bridge for this PREREQ (per architecture §Conventions → Error response schema (Tauri IPC); §Inherited Defaults → Error handling).
- The harness-written end records `run/andromeda-pulse.spawn` / `run/andromeda-pulse.exit` (`exit N` / `signal N (NAME)`) come from the `scripts/agent-run.{sh,ps1}` wrapper and never from the production binary. `cargo xtask harness:status` reports them as `ended` under a bounded grammar. The product's exit-cause record is a separate, product-side channel. It must not write those state files or change the `harness:status` four-arm contract (per architecture §Occupied Resources → Filesystem locations / run state files; §Occupied Resources → xtask CLI surfaces → `harness:status`, `scripts/agent-run.{sh,ps1}`).
- No new env var is expected. If the witness needs a knob to induce an exit (a fault-injection gate), it must be registered in Occupied Resources and classified as product-consumed or harness-only. A product-consumed knob inherits the bounded-parse, never-panic shape of its siblings (per architecture §Occupied Resources → Environment variables (reserved at arch level); §Cross-cutting Patterns → Config management). Prefer harness/xtask-side induction over a product env var.
- P-075 reads back through the existing MCP stdio surface: the `andromeda-pulse-mcp` sidecar, JSON-RPC 2.0, the 8 named tools. That surface exists only under `--features mcp-server` (off by default), so the binary named at the round's sha must be built with that feature. This chunk adds no tool or method (per architecture §Conventions → External wire — MCP server; §Established Decisions [MCP Server Surface]; §Cross-cutting Patterns → Feature-gate hygiene; §Occupied Resources → MCP stdio surface, Process / service identity).
- The binary the round runs against is named by its real path. The dev build is `target/{profile}/pulse-app[.exe]`, the bundled binary is `andromeda-pulse[.exe]`, and the two are not interchangeable. `target/{profile}/andromeda-pulse*` names only the MCP sidecar (per architecture §Occupied Resources → Process / service identity).

## Patterns to follow
- The deterministic incident source is the registered `ANDROMEDA_PULSE_L4_DETERMINISTIC` gate, which exists for external (Conductor) verification. Its canned arrays are populated on purpose, so a content-fidelity assertion has something to compare. The same entry records that `trace_id` / `span_ids` / `timestamps_unix_nano` are empty in EVERY mode. An assertion that they are absent passes for the wrong reason, so the concretized P-075 acceptance must not lean on those fields (per architecture §Occupied Resources → Environment variables → `ANDROMEDA_PULSE_L4_DETERMINISTIC`).
- The P-025 / P-027 / P-045 budgets reach the log only through the delegated timing observables `telemetry.frontend.record_constellation_hue_latency` / `_discovery_latency` / `record_findings_counter_refresh`. Each has its own exact allowlist leaf. P-025 measures the constellation DOT hue, not a Halo canvas. The re-authored P-075 acceptance names those emitted quantities (per architecture §Occupied Resources → Tauri IPC routes → `telemetry.frontend.*`).
- The external driver injects telemetry over OTLP to the running receiver. There is no in-process test bypass and no mock-channel back door. Non-default ports resolve through `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT`, which bears on the shared-host 4317/4318 constraint (per architecture §Cross-cutting Patterns → Test-time telemetry injection; §Occupied Resources → Network ports).
- Any new xtask verb this chunk adds (an exit-induction witness, for example) registers under the formalized-CLI-contract rule: exit 0 / 1 / 2 (pass / fail / cannot-evaluate or inconclusive), one JSON verdict on stdout, and an artifact under `target/`, like the existing dev-host-only `smoke:*` legs (per architecture §Occupied Resources → xtask CLI surfaces; §Cross-cutting Patterns → Development Style).

## Anti-patterns to avoid
- Do not route the exit-cause record, or any self-telemetry, through an OTLP network exporter aimed at the product's own receivers. That is infinite recursion and sits outside the self-observation discipline (per architecture §Established Decisions [Self-Observation]).
- Do not make the production binary write the harness-only `run/andromeda-pulse.exit` record, or read it. That would merge two classes arch keeps separate: product log versus harness state file (per architecture §Occupied Resources → Filesystem locations / run state files).
- Do not add a library-crate dependency on `pulse-app`, or a reverse sibling edge, to reach the exit hook (per architecture §Cross-cutting Patterns → Module dependency direction).

## Contract bindings
- arch ↔ obs: the cause record's tracing target needs its own exact allowlist leaf. Arch records that a leaf-less target has its labels silently redacted (§Occupied Resources → Tauri IPC routes, the delegated-timing entry). The record's shape and level are obs-plan's to decide.
- arch ↔ security: the record carries no full path, only a basename through `log_basename`. Any new env knob follows the product-vs-harness path-var split (§Occupied Resources → Environment variables). The security plan owns both rules.
- arch ↔ tests: the CI `boot` job (Linux mcp-feature release build plus the agent-harness boot smoke) is the runner-side observation of the next unexplained exit (§Infrastructure Patterns → CI/CD approach). The P-075 round is `dynamic-external`. Arch registers the surfaces the round consumes (MCP wire, deterministic gate, timing observables), and the test plan owns the claim mechanics.
- arch ↔ Conductor (external): Conductor consumes the MCP wire contract and the binary identity. Both stay unchanged in this chunk.

## Acceptance criteria contributions
- The exit-cause code sits in `pulse-app` (or a lib crate without a new reverse or sibling edge), and the `Cargo.toml` dependency graph stays a DAG rooted at `pulse-app` (per architecture §Cross-cutting Patterns → Module dependency direction).
- The cause record lands in the data dir's `logs/` tracing sink, and no OTLP exporter or new output channel is introduced (per architecture §Cross-cutting Patterns → Self-observation discipline).
- Every env var or xtask verb the chunk adds appears in Occupied Resources with its consumer class, or none is added. The `harness:status` four-arm contract and the `run/andromeda-pulse.exit` grammar are unchanged (per architecture §Occupied Resources → Environment variables; §Occupied Resources → xtask CLI surfaces).
- The P-075 evidence names the binary by its real path and its build features (`--features mcp-server`). No MCP tool, TauRPC procedure or capability grant is added (per architecture §Occupied Resources → Process / service identity, MCP stdio surface; §Conventions → External wire — MCP server).
