## Patterns to follow
- **Basename + env-var-NAME emission shape** — the existing L4 records (`path_basename`, `root_basename`, env-var NAME only) are the precedent A7 should adopt rather than invent a new redaction form (per security-plan §Security Anti-Patterns → Logging).
- **Bounded-category error leaf with no payload** — `interpretation.inference.error` carries a bounded category label with no prompt text, excerpt, or offending substring; this is the model for C1's `reject_reason` and for any new rejection surface B1's honest-failure arm adds (per security-plan §Input Validation → L4 inference argv prompt row; §Error Handling).
- **Three recorded scrub shapes** — choke-point (`extract_service_name`, one fn feeding three consumers), push-site (`scrub_otlp_field` on a bare column value), and joined `key=value` UNIONed with the bare value (labels). Any new client-controlled cell C3/C5 introduces picks from these, and the joined form is mandatory where key-name-anchored catalog arms are in play (per security-plan §Security Anti-Patterns → Logging).
- **Harness-only path-var carve-out** — a path var not consumed by the shipped binary is guarded by trim + `is_file()` + clean skip, never data-dir confinement; `ANDROMEDA_PULSE_PIDFILE` / `_LOGFILE` are named as exactly that class, which is the class B1's PID-file-based `status` fix and B2's log readers sit in (per security-plan §Security Anti-Patterns → Input, carve-out clause).
- **Body-is-current-truth / sidecar-is-history** for the D-family wrap amendments to this plan: the body holds only current truth, the append-only sidecar holds superseded guidance plus a pointer to where the substance now lives (per security-plan preamble; §Dependency Security amendment precedent).

## Anti-patterns to avoid
- **NEVER un-mute a leaf into carrying raw OTLP attribute values, DuckDB query parameter values, clipboard/snapshot payloads, or full product-consumed paths** — the five NEVER bullets are the rules the scrubber enforces wherever invoked, and an allowlist edit is a direct route around them (per security-plan §Security Anti-Patterns → Logging).
- **NEVER attach a scrub emitter to a producer-less column** — the plan explicitly rejects this as shipping an emitter that never fires; scrub coverage follows a real producer, not a schema row (per security-plan §Security Anti-Patterns → Logging → "Two different fives").
- **NEVER add a TauRPC procedure without its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` AND a validated argument struct** — relevant if C6's "wire a consumer" or B1's honest-`status` fix reaches the bridge; per-procedure capability entries do not exist here, so the pin plus the arg struct ARE the enforcement (per security-plan §Security Anti-Patterns → API; §API Security → TauRPC capability authorization).
