## Constraints
- **The canonicalize half is not negotiable; only the confinement half is in play.** Per security-plan §Security Anti-Patterns → Input (MEASURED EXCEPTION block), the three product-consumed path vars must resolve `..`/symlink chains via `canonicalize()` and assert a REGULAR FILE. The plan records this as measured on 2026-08-26; whether it still holds at HEAD is research's question. Whatever guard lands must keep that half intact and may only alter the omitted data-dir confinement assert.
- **A guard that is not data-dir confinement obliges an amendment in the same chunk.** §Security Anti-Patterns → Input states of the exception "Until it lands, this is the current truth, not a target state" and names this entry as owner; §Input Validation (CLI / env var inputs row) carries the same three vars as "canonicalized but NOT confined". Landing a narrower guard without narrowing/retiring both statements leaves the plan measurably false.
- **`strict-path` is the plan's NAMED primitive for canonicalize-and-confine** (security-plan §Bootstrap phases → `input-validation-library-install`, and the closing sentence of §Security Anti-Patterns → Input). Choosing the `std` route instead is a deviation from a named mandate, not a free implementation choice — it owes an amendment. Whether `strict-path` has any user in the tree, and whether it can express confine-to-root, are research's questions (scope P-2).
- **A new env var (e.g. P-1's operator-declared allow-root) must be registered in §Input Validation → CLI / env var inputs with its bounded-parse rule.** That row asserts itself as the complete boundary enumeration; per security-plan §Input Validation it must state the parse bound, the unset/empty/invalid disposition, and whether the value is path-class.
- **The argv-prompt residual is governed by a categorical ban, not a judgement call:** security-plan §Security Anti-Patterns → Code Patterns bans `tokio::process::Command::new(...).arg(user_input)` "against any string sourced from an OTLP attribute, MCP tool argument, or workspace-detector output". Whether the prompt is genuinely OTLP-derived at runtime (scope P-4) determines whether the ban binds directly or by analogy — that is research's question.
- **Rejection paths must not leak the path or the payload.** §Logging & Monitoring (What NEVER to log) forbids raw OTLP attribute values and full file paths (canonicalized basename only); §Anti-Patterns → Logging repeats both as NEVER bullets; §Error Handling requires that no file paths, struct names, or stack traces cross a boundary to the webview. An observable rejection therefore carries a basename and a reason code, never the rejected path in full and never the prompt text.
- **Any workspace `Cargo.toml` touch inherits the dependency gate.** Per §Dependency Security → CI integration and §Bootstrap phases → `dep-audit-tooling-install`: `cargo deny check bans licenses sources` must stay green, `multiple-versions = "deny"` is never relaxed, and any duplicate carve-out must be ID-scoped, owner-named and reasoned.

## Patterns to follow
- **`read_published_workspace_key` bounded-read shape** (security-plan §Input Validation, published-workspace-key row): named byte-cap const, UTF-8 check, trim, reject empty + control characters, failure yields `None` and falls back — never a panic. This is the plan's own precedent for the bound Deliverable B needs.
- **`publish_workspace_key` canonicalize-and-confine-on-write** (same row): canonicalize both sides and refuse if the child escapes the parent. The plan's one stated confinement discipline outside the plugin loader.
- **Bounded env-var parse with a documented default** (§Input Validation, CLI / env var inputs row — the `L4_DETERMINISTIC`, `BASELINE_BOOTSTRAP_SECONDS`, `CORPUS_PASSPHRASE` entries): unset / empty / unparseable / out-of-range all fall to a stated default; never a panic, never silent adoption of an unintended bound.
- **Boundary error collapse + graceful degrade** (§Error Handling): module-internal `thiserror` enums convert at the boundary to sanitized, `Serialize`-able variants (`AppError::Validation { field, reason }`); the `Internal { message }` one-liner is sanitized while the full chain stays in the internal log.
- **Canonicalization-rejection is a logged security event** (§Logging & Monitoring, What to log): the plugin-loader entry explicitly lists "file path canonicalization rejection" as loggable — the plan's precedent for the scope's observable-rejection requirement.

## Anti-patterns to avoid
- **NEVER widen the harness-only carve-out to cover these three vars.** §Security Anti-Patterns → Input scopes the carve-out to vars "NOT consumed by the production binary"; these are read by the shipped binary, and the 2026-08-25 amendment records widening as explicitly REJECTED because it would bless the exception as policy and drop the CWE-22 consequence from view.
- **NEVER pass an OTLP-sourced string as a `Command` argv value** (§Security Anti-Patterns → Code Patterns) — the ban is on the SHAPE, anchored to the MCP STDIO command-injection CVE cluster.
- **NEVER log the rejected full path, the prompt text, or any raw OTLP attribute value** in the new rejection observable (§Security Anti-Patterns → Logging, bullets 1–2 and 4; §Logging & Monitoring NEVER-log list).
