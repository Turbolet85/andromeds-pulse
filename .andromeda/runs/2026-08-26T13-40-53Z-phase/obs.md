## Relevance
Relevant — both deliverables emit into the self-observation log (path-rejection diagnostics, prompt-bound rejections), and both touch paths/OTLP-derived content that obs-plan classifies scrub-required.

## Constraints
- The guard's rejection must be **observable at WARN/ERROR carrying an error CATEGORY**, not a stack trace — obs-plan §10 (Standard+ "Module-boundary error logging") requires every module-boundary error logged at WARN or ERROR with trace context + error category; §6's `warn` row names `config.load.path_validation` ("path canonicalization rejected") as the plan's designated shape for exactly this CWE-22 rejection class (per obs-plan §10, §6).
- **Path values are scrub-required: basename only, never the canonicalized full path.** §8's data-classification table marks file paths High/scrub-required with `path.file_name()`-style basename extraction before field emission; §1's Vector-6 telemetry trigger requires the `ANDROMEDA_PULSE_*_PATH` / `*_DIR` load site to emit a `*_basename` field and reject traversal, logging only the base name. Note §8's env-var row classifies the *names* `ANDROMEDA_PULSE_*` as OK-to-log while redacting only `*_SECRET`/`*_TOKEN`/`*_KEY`/`*_PASSPHRASE` — these three vars end in `_PATH`, so nothing name-based protects them; the value-level basename discipline is the whole guard (per obs-plan §8, §1).
- **Any field emitted on `interpretation.model.load` (the scope's named site) needs an EXACT §8 allowlist leaf enumerating EVERY field the emit site emits**, or the target is partly redacted while its siblings render fine. §8 records that leaf as carrying `model_identity`/`tier`/`file_size_bytes`/`load_status` with `inference_mode` absent — a PARTIAL-redaction backlog item owned by the "Diagnostics un-muting + harness-truth sweep" entry. Whether that leaf still has exactly those four fields at HEAD, and whether a rejection field added here would land inside or outside it, is research's question (per obs-plan §8).
- **A NEW `interpretation.*` target is the most dangerous shape available to this chunk.** §8 states the invariant "no bare `interpretation` key may exist" and simultaneously records it as VIOLATED IN CODE (measured 2026-08-26) — a bare key carrying `model_profile`/`model_tier`/… means a new sibling target *resolves* (so an `is_some()` probe passes) while every one of its fields vanishes into a set never meant for it. §8 requires the invariant as written; whether the breach is still present at HEAD is research's question (per obs-plan §8).
- **The prompt-bound rejection may carry no prompt text and no excerpt of it.** §8's first classification row (raw OTLP payloads: High, scrub-required) and §11 Logs ban raw OTLP attribute values outright; §1 Vector 1 requires counts/tags in their place. Bounded statics, numerics, or a digest only — §6's boundary table sanctions `argument_digest` (hash, not content) as the identify-without-emitting form (per obs-plan §8, §11, §6).
- **The error crossing the IPC bridge must be sanitized**: no `source()` chain, no canonicalized paths, no Rust struct names or library versions; `tracing-error` SpanTrace over user-defined spans rather than a backtrace, and never a direct `anyhow::Error` serialization across the boundary (per obs-plan §7 "Error classes captured" + §1 Vector 2; §11 Spans/Traces).
- **A new once-per-boot WARN target must be registered at BOTH §6 and §8** (the dual-site rule the §6 `warn` row and §8 whitelist jointly enforce for every sibling: `app.boot.buffer.degraded`, `corpus.keychain.fallback`, `triage.baseline.bootstrap_window.override`, `app.boot.window.navigation`, `buffer.consumer.stalled`) — a §8-only apply leaves §6 stale (per obs-plan §6, §8).

## Patterns to follow
- `app.boot.workspace_key` — §8's exact leaf permitting `workspace_root_basename` + `key_bytes` and nothing else: the plan's precedent for *describing* a path in a record without emitting it (per obs-plan §8, §4 Scenario P7).
- `app.boot.window.navigation` — §8 exact leaf + §6 `warn` row: a bounded-`reason` static, a bool, a sanitized label, and an outright ban on the very value the check compares (the URL), because that is the field most likely to be added "for debuggability". Directly analogous to the rejected path here (per obs-plan §8, §6).
- `triage.baseline.bootstrap_window.override` — the env-override WARN shape: `resolved_seconds` / `default_seconds` / bounded `reason` (`env_override` | `env_rejected_out_of_range` | `env_rejected_unparseable`), once per boot, only when the resolved bound differs from default. The nearest existing shape for an operator-declared allow-root (scope P-1) (per obs-plan §8, §6).
- `config.load.path_validation` at WARN — §6's named example for CWE-22 canonicalization rejection; §1 Vector 6 pairs it with the basename-only field discipline (per obs-plan §6, §1).
- Aggregate counters ride existing ticks as FIELDS, never per-event targets — if a rejection/redaction count is added, §5's tick-aggregated Counter convention and §11's hot-path emission ban apply, with labels bounded to enumerated values (per obs-plan §5, §11 Metrics).

## Anti-patterns to avoid
- NEVER log a full canonicalized file path — basename only (per obs-plan §11 Spans/Traces; §8 Data classification).
- NEVER log raw OTLP attribute values or content payloads — the digest-derived prompt, any excerpt of it, and any "offending substring" of a rejected prompt are all covered (per obs-plan §11 Logs; §1 Vector 1).
- NEVER ship a guard whose rejection leaves no trace, nor a soft/unenforced budget — and (per the 2026-08-16 amendment precedent) never site its allowlist guard in a src-level `mod tests`, which `[lib] test = false` compiles but never runs (per obs-plan §11 SLO; §8 guard-siting notes).

## Contract bindings
- **obs ↔ tests harness:** obs-plan §3's log-format JSON schema is verbatim from the tests §5 Test Harness Contract and is binding in that direction (obs aligns to tests) — any new field this chunk emits must ride inside the `fields` map, not as a new top-level key (per obs-plan §3, §6).
- **obs ↔ security:** §8 is the logger-config half of security vectors 1 / 2 / 3 / 6; the five security artifacts this chunk must leave self-consistent are the same rule stated on the security side, so a wording change there (e.g. the `strict-path` fork, P-2) has an obs-side counterpart wherever §8 or §1 restates the basename/canonicalization mandate (per obs-plan §8, §1).
- **obs ↔ CI:** §9/§10 gates read `agent-latest.jsonl` post-run (`jq` over targets/levels), and §10's load-profile rule requires any new xtask check script over that file to be NEUTRAL-tolerant — absent stream ≠ failure (per obs-plan §9, §10).

## Acceptance criteria contributions
- (obs) The path-guard rejection emits a WARN/ERROR record carrying a bounded error category plus a `*_basename` field, and the full canonicalized path appears zero times in `agent-latest.jsonl` (per obs-plan §8 Data classification + §1 Vector 6).
- (obs) Every field the guard and the prompt bound emit resolves to an EXACT §8 allowlist leaf enumerating all of them — no partial redaction, no reliance on `for_target` prefix fallback — with the guard test under `pulse-app/tests/` where it actually runs (per obs-plan §8 Default-deny posture).
- (obs) A prompt-bound rejection record contains no prompt text, excerpt, or offending substring — bounded statics / numerics / digest only; a canary planted in the prompt appears 0 times in the log (per obs-plan §11 Logs + §8 Data classification row 1).
- (obs) The degraded-boot path (`ModelStatus::Error` → `ModelNotConfigured`) is visible in the log and produces zero `app.panic.fatal` records (per obs-plan §10 always-required invariant + §7 Panic hook).
