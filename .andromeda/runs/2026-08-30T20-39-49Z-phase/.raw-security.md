## Constraints
- `ANDROMEDA_PULSE_PIDFILE` / `_LOGFILE` are named members of the **harness-only tool-locator carve-out**: not consumed by the production binary, guarded by trim + `is_file()` + clean skip instead of canonicalize-and-confine. The carve-out is scoped to exactly that — "harness-only, not-production-consumed, existence-guarded." Any fix that lets either var reach the shipped binary voids the carve-out and pulls the var under the categorical canonicalize-and-confine ban (per security-plan §Security Anti-Patterns → Input). **Whether the product binary already reads `ANDROMEDA_PULSE_PIDFILE` — and whether `write_pid_file` honours it — is research's question (chunk Q1), not something this extract can attest.**
- Anything the PRODUCT writes under `&lt;data_dir&gt;/run/` must follow the `publish_workspace_key` precedent: canonicalize `data_dir` + `run/`, refuse if `run/` escapes the data dir, atomic `.tmp`+rename — with `std` both-sides-canonicalize as the project's single path primitive (`strict-path` retired/DROPPED) (per security-plan §Input Validation, published-workspace-key row + §Bootstrap phases → `input-validation-library-install`). Chunk Q1 candidate (c) — "the app's canonicalize guard warn-returned and never wrote" — lands squarely on this guard.
- The never-log-full-product-consumed-path rule is **CATEGORICAL** — basename of the canonicalized path only — and `app.boot.pid` is one of the two boot records whose standing exception was deleted to make it so (per security-plan §Security Anti-Patterns → Logging + §Logging &amp; Monitoring → What NEVER to log). A pid-path change or new pid diagnostics on the product side must not reintroduce a full path.
- The loopback-only OTLP binding on `:4317`/`:4318` IS the de facto authorization boundary at this tier — any local process can post to a live receiver, with no auth at that surface (per security-plan §Threat Model Summary → Attack surface / Auth model). A teardown that returns success while a listener survives leaves that boundary open under a false all-clear; the plan requires the receivers stay bound to `127.0.0.1` only, so any liveness probe the fix adds must target loopback (per §Security Anti-Patterns → API).
- The scripts export `ANDROMEDA_PULSE_*` env; `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` is secret-class and inherits "never logged, never exported" (per security-plan §Secret Management → What counts as secret). Any diagnostic that dumps or fingerprints the exported env set to explain the relink must exclude secret-class names by value.
- The PREREQ probe is defined in full form by the plan: probe `cargo audit` DIRECTLY (exit read never through a pipe), basis byte-identical or the deferral ENDS; re-enumerate `cargo deny check advisories` findings FROM SCRATCH as DISTINCT `RUSTSEC-` ids (counting rule (a): error BLOCKS are not the ID count); `bans licenses sources` exit 0; NO "Nth consecutive" ordinal (rule (c)); and the interval point belongs to the wrap that actually occurs, so an inserted wrap moves it (rule (b)) (per security-plan §Dependency Security → CI integration → Standing deferral).

## Patterns to follow
- **Harness path-var guard shape** — trim + `is_file()` + clean SKIP on absence (exit 0 with a recipe, never a panic or hard fail), resolved value never logged (only the variable NAME). `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` is the registered exemplar (per security-plan §Input Validation, CLI/env-var row + §Security Anti-Patterns → Input).
- **Cross-process file read validated as untrusted even when Rust-owned and self-written** — bounded byte ceiling, UTF-8 checked, trailing newline trimmed, empty + control chars rejected, any failure ⇒ `None` and a defined fallback rather than a panic. This is the `&lt;data_dir&gt;/run/workspace-key` shape, and its sibling file is the pidfile this chunk targets (per security-plan §Input Validation, published-workspace-key row).
- **Bounded-category rejection surfacing** — a validation rejection emits a bounded category label only, never the offending value, excerpt, or substring (per security-plan §Input Validation, L4-argv row; §Security Anti-Patterns → Logging).
- **Basename emission via `observability::log_basename`** with the allowlist leaf renamed to match, as landed for `log_dir_basename` / `path_basename` / `run_dir_basename` / `data_dir_basename` (per security-plan §Security Anti-Patterns → Logging).

## Anti-patterns to avoid
- NEVER read a **product-binary** `ANDROMEDA_PULSE_*_PATH` / `*_DIR` env var without `canonicalize()` plus the data-dir confinement assert — the harness carve-out does not stretch to a var that reaches the shipped binary; the plan already records one round of that claim being measurably false for three product-consumed vars (per security-plan §Security Anti-Patterns → Input).
- NEVER log a full product-consumed filesystem path — basename only, categorical, no reintroduced exception on the pid record (per security-plan §Security Anti-Patterns → Logging).
- NEVER bind or probe the OTLP receivers on any interface other than `127.0.0.1` (per security-plan §Security Anti-Patterns → API).
