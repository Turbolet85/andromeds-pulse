# arch extract

## Relevance
Relevant — the chunk edits harness surfaces (`scripts/agent-run.{sh,ps1}`, possibly `xtask`) whose PID path, env vars, ports, binary names and CLI verdict contracts are all arch-registered resources.

## Constraints
- `ANDROMEDA_PULSE_PIDFILE` is registered in the **harness-only** env class — explicitly "NOT consumed by production binary", with exactly two readers (`scripts/agent-run.{sh,ps1}` and `xtask/src/harness_status.rs`, which the scripts thread it into) (per architecture.md §Occupied Resources → Environment variables). A Q1 fix that made the app honor the override would be both a production-binary change and a reclassification of that entry — outside the scope's declared boundary and owing an amendment.
- `run/andromeda-pulse.pid` is a registered data-dir subpath whose registered writer is the production binary at boot (`pulse-app/src/main.rs`), read by `cargo xtask harness:status` and by the scripts for cleanup; `ANDROMEDA_PULSE_DATA_DIR` overrides the root and the subpath layout under the override is required to be identical (per architecture.md §Occupied Resources → Filesystem locations). Whether the app's write actually lands at the string the scripts read — Q1's premise — is research's question, not something the plan can attest.
- `:4317` / `:4318` are spec-fixed and bound on `127.0.0.1` only, with `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `_HTTP_PORT` as the sanctioned overrides (per architecture.md §Occupied Resources → Network ports; §Cross-cutting Patterns → Test-time telemetry injection, which requires tests to speak the real receiver surface with no in-process bypass). A "ports released" assertion must dial loopback at the *resolved* ports, not hardcoded literals.
- The dev-build binary every local `cargo run`/`cargo build` emits is `target/{profile}/pulse-app` / `pulse-app.exe`; `target/{profile}/andromeda-pulse` exists on no host and `andromeda-pulse[.exe]` is the bundler artifact (per architecture.md §Occupied Resources → Process / service identity, recorded 2026-08-26 precisely because a chunk plan named the nonexistent path). Any process-identification, pre-build or kill-by-path step must name the `pulse-app` form.
- Rust-side work lands in the reserved `xtask` crate; the workspace crate-name set is LOCKED and the dependency DAG flows toward `pulse-app` only (per architecture.md §Occupied Resources → Cargo workspace crate names; §Cross-cutting Patterns → Module dependency direction; §Inherited Defaults → Module boundaries). §Infrastructure Patterns → CI/CD further requires that shared logic needing Rust live in `xtask` so the same command runs locally and in CI.
- Release-profile build discipline (`lto = "thin"`, `codegen-units = 1`, `strip = true`) is arch-owned (per architecture.md §Infrastructure Patterns → Build system) — the relink cost Q3 must absorb is a consequence of it; relaxing the profile to shrink the boot ceiling would be an arch decision, not a harness edit. Arch registers exactly ONE build-script-read env var, `ANDROMEDA_LLAMA3_TOKENIZER_PATH` (`crates/triage/build.rs`, per §Occupied Resources → Environment variables) — the natural first probe for *which* exported var re-fingerprints the build.

## Patterns to follow
- **One Rust derivation site, two script callers** — `cargo xtask harness:status` is the registered precedent: the scripts reach the status verdict only THROUGH that verb, threading `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` into the child (architecture.md §Occupied Resources → xtask CLI surfaces + Filesystem locations). This is the cheapest available answer shape for Q4's sh/ps1 parity question.
- **Formalized dev-CLI contract shape** — named verdict arms + a fixed exit taxonomy + one machine-parseable object on stdout (`harness:status` 0/1/1/2 with four arms; `check:npm-supply-chain` 0/1/2 with six arms; `check:staged-artifacts` 0/1/2 with three) per architecture.md §Occupied Resources → xtask CLI surfaces. Q2's "distinguishable exit for app-survived vs ports-lingered" should be expressed in that shape.
- **Harness-only env class** — `ANDROMEDA_PULSE_*` prefix, marked NOT consumed by the production binary, with readers enumerated by file and line (architecture.md §Occupied Resources → Environment variables: `_PIDFILE`, `_LOGFILE`, `_DATA_DIR_KEEP`, `_MSEDGEDRIVER_PATH`, plus the `PULSE_*` xtask→node relay set for names that never cross into the product).
- **Data-dir root override with identical subpath layout** — the contract both the app and the scripts must agree on for Q1 is `<resolved root>/run/andromeda-pulse.pid`, where the root comes from `ANDROMEDA_PULSE_DATA_DIR` (architecture.md §Occupied Resources → Filesystem locations).
- **Agent-driven development style** — deterministic harness invocations, machine-parseable outputs, schema-stable contracts, `cargo xtask` task surfaces (architecture.md §Cross-cutting Patterns → Development Style).

## Anti-patterns to avoid
- Making the production binary read a harness-only variable (or otherwise touching `pulse-app`) to close Q1 — that inverts the registered classification of `ANDROMEDA_PULSE_PIDFILE` and contradicts the scope's "does NOT touch the production binary" boundary (architecture.md §Occupied Resources → Environment variables).
- Landing a new env var, a new `PULSE_*`/`ANDROMEDA_PULSE_*` name, or a newly formalized CLI contract without registering it in §Occupied Resources — the `PULSE_*` prefix is claimed and a collision would be silent (architecture.md §Occupied Resources → Environment variables + xtask CLI surfaces).
- Naming `target/{profile}/andromeda-pulse*` for the app binary, or duplicating divergent verdict logic in the two shells where a single Rust site is the established parity mechanism (architecture.md §Occupied Resources → Process / service identity; §Infrastructure Patterns → CI/CD).

## Contract bindings
- **arch ↔ tests** — test-plan §3 owns the cleanup Verification/Exit + PID-lifecycle spec and §1 the harness summary; arch owns the `run/andromeda-pulse.pid` path entry, the harness env-var class and the xtask CLI-contract registry. The scope's wrap obligation therefore splits: test-plan/`rules/verification-harness.md` re-alignment is tests' amendment, while any change to the pid-file **writer set** or to a `cleanup`/`harness:status` contract is an arch §Occupied Resources amendment.
- **arch ↔ security** — harness-only path env vars are the declared carve-out from the canonicalize-and-confine-under-data-dir rule (architecture.md §Occupied Resources → Environment variables, `_MSEDGEDRIVER_PATH` entry cross-referencing security-plan §Input Validation). If the fix introduces or re-points a path-bearing harness var, security owns whether the carve-out still applies.
- **arch ↔ obs** — `harness:status`'s verdict derives from the log family named by `ANDROMEDA_PULSE_LOGFILE` plus the registered `logs/` data-dir destination (architecture.md §Occupied Resources → Filesystem locations + Environment variables); the verdict object itself is stdout, not the obs log, so no obs-allowlist leaf is implied by a scripts-only change.

## Acceptance criteria contributions
- (arch) Any teardown/verdict logic requiring Rust lives in the `xtask` crate and follows the registered dev-CLI contract shape — named arms, fixed exit taxonomy, one machine-parseable object on stdout — rather than two divergent shell implementations (per architecture.md §Occupied Resources → xtask CLI surfaces; §Infrastructure Patterns → CI/CD).
- (arch) Zero new env vars and zero workspace crate/dep delta; `ANDROMEDA_PULSE_PIDFILE` / `_LOGFILE` / `_DATA_DIR_KEEP` remain harness-only and unconsumed by the production binary, and any deviation is registered at wrap (per architecture.md §Occupied Resources → Environment variables + Cargo workspace crate names).
- (arch) The port-release assertion dials loopback `127.0.0.1` at the resolved OTLP ports, honoring `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `_HTTP_PORT`, over the real receiver surface with no in-process bypass (per architecture.md §Occupied Resources → Network ports; §Cross-cutting Patterns → Test-time telemetry injection).
- (arch) Every app-binary path or process identity the scripts name is the dev-build `target/{profile}/pulse-app[.exe]` form, never `target/{profile}/andromeda-pulse` (per architecture.md §Occupied Resources → Process / service identity).
