# a11y extract

## Relevance
Partial — the chunk ships no UI surface, ARIA, contrast, motion, or keyboard change, but it rewrites the exact 5-command harness (`boot`/`run`/`status`/`cleanup`/`logs`) that a11y's focus/keyboard harness, manual SR pass, and CI step contractually reuse.

## Constraints
- a11y-plan §3 "Focus management test harness → Contract binding" requires the a11y focus/keyboard harness to reuse tests' E2E driver under the 5-command discipline (`boot`, `run`, `status`, `cleanup`, `logs`); any teardown/ceiling change must leave those five command names and their consumer-visible contract intact for the a11y suite.
- a11y-plan §9 "Pipeline integration" requires `npm run test:a11y` to reuse the same `boot`/`run`/`status`/`cleanup`/`logs` harness inside `ci.yml`; the new non-zero cleanup exit taxonomy (scope Q2) must be legible to that step — neither reddening a green a11y leg for a non-a11y reason nor being swallowed by it.
- a11y-plan §3 "Screen reader test pattern" step 1 requires the manual SR pass (NVDA / VoiceOver / Orca) to "Launch app via `boot` command"; a `boot` ceiling that cannot absorb the env-triggered relink (scope item 3) makes that spec unlaunchable. Whether the three SR spec files pin a specific boot invocation or timeout that the ceiling change would stale is research's question.
- a11y-plan §1 "CI Integration → Output" requires the a11y JSON artifacts (`a11y-axe-core-results.jsonl`, `a11y-lighthouse-results.json`, `a11y-pa11y-results.json`, `a11y-keyboard-focus-results.jsonl`, `a11y-violations-summary.json`) to land in `~/.andromeda-pulse/logs/` — the same data-dir root the scope's Q1 pidfile-path divergence (MSYS view vs native Windows resolution) implicates. Whether the a11y chain resolves that dir independently of the harness scripts is research's question.
- a11y-plan §10 "Always-required SLO invariant" + "Build / deploy failure conditions" require zero WCAG AA violations on the must-be-accessible set and hard (non-soft, non-retry) gates; no a11y assertion may be relaxed or made conditional to accommodate a teardown-verdict change.
- a11y-plan §3 "Adding a surface (standing rule)" requires one axe spec per NEW route/modal in the same chunk — this chunk adds no route or modal, so it owes no new axe spec and the `p1`–`p14` set stays as-is.

## Patterns to follow
- 5-command reuse rather than a private lifecycle: the a11y harness taps the tests' driver session (per a11y-plan §3 "Focus management test harness"), so the fix's shape should be observable through the same commands rather than a new side channel.
- Self-contained server lifecycle for the audit chain: a11y-plan §3 "Harness wiring & conventions" describes the SPA served via `helpers/static-server.mjs` (SPA fallback) with pa11y-ci lifecycle in `pa11y/run-pa11y.mjs` and Tauri IPC mocked (`TauRPC__<router.path>`) — i.e. the audit legs have their own boot/teardown path. Whether that makes them fully independent of `scripts/agent-run.*` is research's question.
- Cheap suite-health probe before trusting a green run: `npx playwright test --list` (per a11y-plan §3 "Harness wiring & conventions") — a list-time import failure once silently disabled the whole a11y suite.
- Baseline-tuple comparison as the regression check: `baselines/a11y-violations-summary.json`, where a clean full-chain pass = 0 violation tuples (per a11y-plan §3 "Regression baseline"); a harness-only change should reproduce that tuple set unchanged.
- Verify a claimed absence against the artifact that actually owns the surface (amendments 2026-08-23-a11y-verification) — the same discipline the scope applies when re-verifying the folded entry's coordinates at P1.

## Anti-patterns to avoid
- a11y-plan §11 "CI" — NEVER skip a11y on CI failure and NEVER use soft gates: the new cleanup exit taxonomy must not become a condition that lets the a11y step be skipped or downgraded to a warning.
- a11y-plan §11 "SLO" — NEVER apply a retry-once policy to a11y violations: if the teardown change makes an a11y leg flaky (surviving app, lingering `:4317`/`:4318`), quarantine and investigate, never retry.
- a11y-plan §11 "Strategy" — NEVER claim conformance without machine-verifiable evidence: a green `boot`/`cleanup` pair is harness evidence, not WCAG evidence, and cannot stand in for an axe/Lighthouse/pa11y artifact.

## Contract bindings
- **a11y ↔ tests (primary):** a11y-plan §3 "Focus management test harness → Contract binding" and §9 "Pipeline integration" both bind a11y to tests' 5-command harness. This chunk edits that harness; test-plan §3 (cleanup Verification/Exit + PID lifecycle) owns the verdict contract, a11y is a downstream consumer — a11y adds no requirement on the exit-code taxonomy itself, only that the commands stay tappable and `cleanup` genuinely releases the app and ports before a subsequent audit leg.
- **a11y ↔ CI:** a11y-plan §9 artifact table requires the E2E-stage a11y JSON artifacts to be uploaded from the same `ci.yml`; a re-ordering or early-exit introduced by the new taxonomy must still let the upload step run.
- **a11y ↔ obs:** a11y-plan §3 "Structured violation JSON schema" binds `target: "a11y::assertion"` records to obs §6 — NOT implicated here; the scope states the harness scripts are not obs-allowlist emitters, and no a11y assertion runs in them.

## Acceptance criteria contributions
- After the script change, the a11y chain still launches through the same harness commands it taps — no rename or contract change that would require re-pointing the focus/keyboard suite (per a11y-plan §3 "Focus management test harness → Contract binding" + §9 "Pipeline integration").
- A post-change `cleanup` releases `:4317`/`:4318` and the app process such that a subsequent full a11y chain run completes with ZERO new violation tuples vs `baselines/a11y-violations-summary.json` (per a11y-plan §3 "Regression baseline" + §10 "Zero new violations per PR").
- The manual SR pass spec's step-1 launch path via `boot` remains valid under the new ceiling; if the three SR spec files name a boot invocation or timeout, they are corrected in step (per a11y-plan §3 "Screen reader test pattern").
- No new route or modal ships, so no new axe spec is owed and the `p1`–`p14` set plus the hard a11y CI gate are unchanged (per a11y-plan §3 "Adding a surface (standing rule)" + §10 "Build / deploy failure conditions").
