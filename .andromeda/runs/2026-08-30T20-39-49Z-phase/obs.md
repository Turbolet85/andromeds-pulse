# obs extract

## Relevance
**Partial** — the chunk touches harness scripts, not obs emitters (scope §Boundaries), but obs owns the harness contract those scripts bind to: the log/data-dir resolution (`obs-plan` §3 Log file location), the boot-readiness `health` probe (§3 Heartbeat ticks), and the rules governing any log-consuming verdict (§10).

## Constraints
- The self-observation log path derives from `ANDROMEDA_PULSE_DATA_DIR` with per-platform mapping (`%APPDATA%\Andromeda Pulse\logs\` on Windows), and it is the SINGLE agent-readable surface — per `obs-plan` §3 (Log file location) + §3 (Tracing init). The scripts export `ANDROMEDA_PULSE_*` env into a native app process; whether the exported data-dir value resolves to the SAME directory for the Git Bash script and the native app — which decides whether the log the check scripts read is the app's log at all — is research's question, and it is the same root as scope Q1(b) for the sibling `{data_dir}/run/` pidfile.
- Boot readiness must stay the SYNCHRONOUS `health`/status probe; tick presence is retroactive liveness only, and §3 requires the two mechanisms stay unconflated ("the test harness polls synchronously until status ok") — per `obs-plan` §3 (Heartbeat ticks → Complementarity with the `health` command). Raising the boot ceiling must not redefine readiness as "log line appeared" or "tick seen".
- Any xtask check script over `agent-latest.jsonl` must be NEUTRAL-tolerant (absent stream ≠ failure) and run-window scoped via `write_run_window_log` — per `obs-plan` §10 (Load-profile constraints; frame-budget two-state posture). A teardown-side arm in `xtask/src/harness_status.rs` inherits this: the cleanup verdict may not derive FAIL from log absence.
- Zero unlogged panics is an always-required invariant at every tier, captured at `app.panic.fatal` by the boot-installed hook — per `obs-plan` §10 (Always-required SLO invariant) + §7 (Panic hook). A new teardown path must not introduce an unlogged panic or an ERROR-shaped shutdown.
- Path-bearing env vars are basename-only at every emission site, and the `*_PATH` / `*_DIR` naming convention is explicitly NOT exhaustive — per `obs-plan` §1 (logging-sensitive Vector 6 row, as broadened 2026-08-26) + §8 (Data classification, plugin-file-path row). If the fix causes any app-side record to name the pidfile or data dir, basename only; the full path never appears.
- Every emitting target needs an EXACT §8 allowlist leaf enumerating EVERY field its emit site emits; for an `app.`-prefixed target no bare `app` key exists, so a missing leaf redacts all fields silently — per `obs-plan` §8 (Default-deny posture). Whether the app today emits any record naming the PID file it writes (an `app.boot.*` publish analogous to `app.boot.workspace_key`) is research's question.
- The machine-readable signal must be structured, never terminal text — per `obs-plan` §11 (Logs: "NEVER use unstructured stderr text"; CI: "NEVER rely on colored terminal output for CI parsing"). The measured defect (stderr warning + exit 0) is exactly this ban.

## Patterns to follow
- Consume the existing detector rather than adding a parallel one: `cargo xtask smoke:gap-resume` takes `buffer.consumer.stalled` + `check:ingest-progress` as its verdict instead of introducing a second signal (per `obs-plan` §10, drain-progress-detector paragraph). The cleanup verdict should be assembled from process/port probes plus the existing status contract.
- Two-signal discipline — presence is not proof: tick presence is LIVENESS, drain progress is the companion PROGRESS signal (per `obs-plan` §3 Stall detection + §10 Standard+ invariants). "cleanup ran" is the liveness analogue; the verdict must assert the terminal state (app PID gone, ports released).
- `{data_dir}/run/` sidecar publish shape: `app.boot.workspace_key` publishes a run-directory sidecar for an out-of-process consumer with INFO on success / WARN on failure, carrying `workspace_root_basename` + `key_bytes` only (per `obs-plan` §1 P7 row, §4 Scenario P7, §8 leaf). This is the precedent shape if the app must advertise its PID file to the harness.
- Bounded static-label reason/consequence fields for verdict taxonomies — e.g. `buffer.consumer.stalled {reason, consequence, …}` with closed token sets (per `obs-plan` §6 warn row). Scope Q2's "distinguishable exit for app-survived vs ports-lingered" maps to a bounded label set, not free text.
- Dual-site registration for any new target: §6 log-levels mapping AND §8 allowlist leaf (per `obs-plan` §6 + §8; the dual-site rule as applied to `app.boot.window.navigation` and `ui.ipc.rejection`).

## Anti-patterns to avoid
- NEVER let unstructured stderr text carry the verdict — `obs-plan` §11 (Logs / CI). The warning-with-exit-0 shape the chunk removes is the canonical instance.
- NEVER lose telemetry artifacts — `obs-plan` §11 (CI) + §9. §3 (Tracing init) builds the file sink on a `tracing_appender::non_blocking` writer held by a `_guard`, so a hard kill can drop buffered lines; whether the current teardown gives the app a graceful window before escalating is research's question.
- NEVER log a full canonicalized path — `obs-plan` §11 (Spans/Traces + Logs, Vectors 3/5/6). Applies to any pidfile / data-dir / log-path field the fix introduces on either side.

## Contract bindings
- **obs §3 (harness contract: log format §6, log file location, `health` readiness probe) ↔ tests §3** (cleanup Verification/Exit + PID lifecycle) — tests consume obs's structured log format and the status/`health` readiness shape; test-plan §3 is the consumer named in the chunk's spec re-alignment item (scope §What it builds #4).
- **obs §10 check-script rules ↔ xtask harness/check scripts** (`check:ingest-progress`, `xtask/ci/heartbeat-gap-check.sh`, `write_run_window_log`) — binds if `xtask/src/harness_status.rs` gains the teardown-side arm the scope conditions on.
- **obs §8 / §1 Vector 6 ↔ security (path handling, CWE-22)** — basename-only discipline is the whole guard for path-bearing env vars; binds only if a new path-naming emission lands.

## Acceptance criteria contributions
- The GREEN leg's run window contains zero `app.panic.fatal` records, and the new teardown path emits no ERROR-shaped shutdown (per `obs-plan` §10 Always-required SLO invariant + §7 Panic hook).
- Any teardown-side check over `agent-latest.jsonl` is NEUTRAL-tolerant (absent stream ≠ FAIL) and scoped to the run window, so a headless leg and a full-app leg share one script set (per `obs-plan` §10 Load-profile constraints).
- The teardown verdict is carried by the process exit code — and, where an app-side record is added, by a structured JSON line with bounded static labels — never by stderr prose alone (per `obs-plan` §11 Logs + §11 CI).
- If the fix adds or changes any emission naming a path or env var (pidfile, data dir, log dir), it emits basename only and lands an EXACT allowlist leaf enumerating every field its emit site emits, registered at BOTH §6 and §8 (per `obs-plan` §1 Vector 6 + §8 Default-deny posture).
