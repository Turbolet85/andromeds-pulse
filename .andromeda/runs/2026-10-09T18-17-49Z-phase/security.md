# security extract

## Relevance
partial — the chunk is harness, CI and exit-cause work with no new IPC, auth or data surface; security binds on what an exit-cause surface may carry, on the exit and signal code path, on the harness state files, on the loopback bind the readiness probe touches, and on `ci.yml` if it changes.

## Constraints
- security-plan §Security Anti-Patterns → Logging (the `app.exit` paragraph) requires the process-end record to be exactly one per process end, behind its own exact allowlist leaf, carrying only closed labels and bounded scalars, with a panic payload, an error `Display`, a native message and every path excluded. A cause the chunk adds to that record (a new field, a new `exit_class` label, a second record) changes a deliberate no-scrub boundary: it has to stay closed-vocabulary and be pinned the same way, and whether it counts as a Boundary widening that halts for the founder's word is the plan's to decide at P4.
- security-plan §Logging & Monitoring → What NEVER to log requires that no full product-consumed filesystem path, no OTLP attribute value and nothing on the §Secret Management secret list reaches a log; the same section's Log format clause places field redaction at the subscriber layer. A surface outside that layer (the boot wrapper's capture of the app's standard error, `boot.log`, anything the job uploads) has no redaction of its own, so what the chunk makes the job keep has to be bounded by construction. Whether the app's standard error on an early exit already carries a full path or an unbounded message is research's question.
- security-plan §Secret Management → What counts as secret classes `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` and the corpus key as secret, never logged and never exported. A diagnostic that dumps the process environment or the credential-store state into what the job keeps would break it; an env-var NAME is the only safe form (per §Security Anti-Patterns → Logging, the full-path bullet).
- security-plan §Security Anti-Patterns → Universal bans logging, or running any code that needs thread-locals, from a C `atexit` handler or a signal handler on the thread ending the process, and requires the Unix signal path to end the process BY the same signal, never by an exit code standing in for it. Any instrumentation the chunk adds to see the early exit goes through the existing hand-off, not into those handlers.
- security-plan §Security Anti-Patterns → Input (the harness carve-out and its sibling state-file class) scopes `run/andromeda-pulse.spawn` and `run/andromeda-pulse.exit` as harness-written, harness-read through a bounded one-line grammar, and never read by the product binary. A new file the wrapper writes for this chunk stays inside that class only while the product never reads it; a product read of a new path or env var falls under the canonicalize-and-confine ban of the same section, and a new product-written location outside the data dir would be a fourth beside the three that section enumerates.
- security-plan §Security Anti-Patterns → API bans binding the OTLP receivers to anything but `127.0.0.1`. The readiness probe the chunk adds confirms a handshake on the loopback bind as it stands; the bind address and the receivers' startup posture are not what gets changed to make the probe pass.
- security-plan §Security Anti-Patterns → Secrets requires every third-party GitHub Action to be referenced by 40-char commit SHA and workflow-level `permissions` to stay `contents: read`; §Bootstrap phases (`dep-security-ci-gate`) requires `step-security/harden-runner` as the first step of every job. These apply if the chunk touches `ci.yml` (a changed upload step, a new step in the boot job). Whether `ci.yml` changes at all is the plan's to decide from the cause.

## Patterns to follow
- The deliberate no-scrub log boundary shape: an exact allowlist leaf of its own, closed enums and bounded scalars only, free text excluded by construction, no bare parent key, pinned by an allowlist test in both directions with a fallback discriminator (per security-plan §Security Anti-Patterns → Logging, the `app.exit`, `ui.ipc.rejection` and `ui.webgpu.adapter` paragraphs).
- The exit hand-off: the record is handed to a reporter thread spawned at install under a bounded wait, and the signal path records from a runtime task before restoring the default disposition and re-raising (per security-plan §Security Anti-Patterns → Universal).
- The stated-failure-mode form: the `app.exit` paragraph names the ends the record cannot see by construction (among them SIGKILL, `_exit`, and failures before the sink exists, which reach standard error and `boot.log` only). The scope's reading that the red logs hold no `app.exit` is to be read against that list first; whether the early exit is one of those ends is research's question (per security-plan §Security Anti-Patterns → Logging).
- Basename-only path fields through the shared basename helper for any boot or exit record that names a location (per security-plan §Security Anti-Patterns → Logging, the full-path bullet).
- A CI step that needs no third-party action is a plain named `run:` step, which does not trigger the SHA-pinning convention and carries no token input (per security-plan §Dependency Security → CI integration).

## Anti-patterns to avoid
- NEVER put a panic payload, an error `Display`, a native message or a full path into a process-end record or into evidence the job keeps to explain an end (per security-plan §Security Anti-Patterns → Logging).
- NEVER log or touch thread-locals from an `atexit` or signal handler on the exiting thread, and never let an exit code stand in for the signal that ended the process (per security-plan §Security Anti-Patterns → Universal).
- NEVER reference a third-party Action by a floating tag or raise workflow-level permissions above `contents: read` while changing the boot job (per security-plan §Security Anti-Patterns → Secrets).

## Contract bindings
- security ↔ obs: the `app.exit` record's field set, its allowlist leaf and its unloggable ends are stated in security-plan §Security Anti-Patterns → Logging and owned as an event schema by the obs plan; a change to either side needs the other.
- security ↔ tests: the harness state files and the `harness:status` read of them (security-plan §Security Anti-Patterns → Input) are the same objects as test-plan §3's 5-command contract, whose readiness clause the chunk closes; the boot job is one job of the single `ci.yml` the security workflow rules cover (security-plan §Bootstrap phases, `dep-security-ci-gate`).
- security-plan sites that describe the smoke and would need correcting at the wrap, not in this chunk: the `ui.webgpu.adapter` paragraph's statement about what the CI boot job witnesses, which depends on how long the smoke lets the app live, and the `app.exit` paragraph's list of unseeable ends if the cause turns out to be a new one (both in security-plan §Security Anti-Patterns → Logging).
- security ↔ arch: a new env var, a new product-read path or a new product-written location outside the data dir is an Occupied Resources change and a boundary widening on the precedents security-plan §Threat Model Summary (the CLI input vector) records as founder-ratified.
- If the chunk adds a dependency: security-plan §Dependency Security → CI integration (`cargo audit`, `cargo deny check bans licenses sources`, `multiple-versions = "deny"` never relaxed) binds to the `supply-chain` job.

## Acceptance criteria contributions
- Any record the chunk adds or changes for the app's end carries only closed labels and bounded scalars behind an exact allowlist leaf, and an allowlist test pins the field set in both directions (per security-plan §Security Anti-Patterns → Logging).
- The log family and every artifact the boot job keeps from a reproduced early exit read 0 full data-dir paths and 0 secret-class values (per security-plan §Logging & Monitoring → What NEVER to log).
- The readiness probe connects to `127.0.0.1` on the configured ports only, and the diff against the chunk base changes no receiver bind address (per security-plan §Security Anti-Patterns → API).
- If `ci.yml` is in the diff: every `uses:` line is pinned by 40-char commit SHA, workflow-level `permissions` reads `contents: read`, and the boot job's first step is still `step-security/harden-runner` (per security-plan §Security Anti-Patterns → Secrets).
