## Constraints
- test-plan §3 5-command implementation → `boot` → Readiness signal requires two conditions before ready: the `cargo xtask harness:status` verdict reads `running-healthy`, AND a TCP handshake succeeds on the bound ports. The same clause records the handshake half as a measured gap, OPEN, owned by this entry. The clause carries the words "(log parse)" beside the handshake: how the bound ports are resolved (the resolved `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT`, as §3 `cleanup` → Verification does, or the bind record in the log, which is the only source under the optional port-0 env of §3 `boot` → Command body) is the plan's to decide. Whether the ps1 verb has the same gap is research's question: the clause says it was not re-read.
- test-plan §3 5-command implementation → `boot` → Timeout requires process boot plus readiness inside the 10 s default (`HARNESS_STATUS_TIMEOUT` the override), with both builds outside the timed window. A handshake wait sits inside that window; a readiness that needs more than the default is a contract change, not a script detail.
- test-plan §3 5-command implementation → `boot` → Exit code requires 0 on ready and non-zero on timeout or a non-`running-healthy` verdict, and on that failure path the verb names how the app ended (the exit record, or still running) and runs `cleanup`. A handshake that never succeeds is a new failure reason on this path and must be named the same way.
- test-plan §3 5-command implementation → `status` → Exit code semantics fixes the four verdict arms and their exit codes, and bounds `ended` to one line of at most 48 printable ASCII characters read from `run/andromeda-pulse.exit`, reported only when the verdict is not `running-healthy`. A richer "says why" surface either fits that grammar or changes the pinned parser and its unit pins; whether today's record already distinguished the two red runs' ends is research's question.
- test-plan §9 CI Integration → Pipeline structure → Boot smoke (harness) row requires the stage to stay GATING (no `continue-on-error`), the three verbs to run inside one `xvfb-run` sharing one `ANDROMEDA_PULSE_DATA_DIR`, `cargo xtask ci-gates` to read the log the smoke wrote, and `logs-boot-${{ runner.os }}` to upload `if: always()`. Whatever makes a self-ended run say why must land inside what that upload carries; whether the upload's path set holds the `run/` state files, and what `ci-gates` reads differently once the app lives past the receivers' bind, are research's questions.
- test-plan §10 Quality Gates → Zero-flakiness budget requires root-cause investigation on the first flake and admits no retry budget; test-plan §2 Test Strategy → Agent-runnable invariants requires determinism with no flaky retries. The chunk's "no run re-run for a green" and "cause named from evidence" are these two rules applied to the smoke.
- test-plan §3 Per-chunk gate discipline requires the standard gate set in the plan's `## Test Commands` unconditionally, with `capability-drift` before the workspace nextest and the bindings regen as the last cargo-adjacent step closed by the chunk-base `git diff --quiet` probe (base `277d65d`, a chunk adding no procedure). Its Boot-smoke gate (conditional) clause additionally requires a runtime smoke gate if the fix touches `pulse-app/src/main.rs`, `pulse-app/src/observability.rs`, `crates/ui-bridge/src/`, `tauri.conf.json` or `pulse-app/capabilities/*.json`; whether the cause lands in one of those is P3's finding.

## Patterns to follow
- Measure-first, two legs: test-plan §3 Per-chunk gate discipline → Direct-binary smoke variant requires a RED leg at the base and a GREEN leg after the fix, each on its OWN fresh data dir, with the evidence form chosen from the defect's shape BEFORE the leg runs. The carried reading (red logs hold no ERROR, no `app.panic.fatal`, no `app.exit`) is the BLOCK-shaped case that clause names: a clean-log assertion over it passes vacuously, so the RED evidence of record is the absence or the end record, never "0 ERROR". The same per-leg isolation applies to each boot of the rate measurement.
- Pure decision logic in xtask, pinned per arm; the shell stays thin: test-plan §3 5-command implementation → `status` → Command body describes the verdict as a pure `classify(pid, alive, newest_log)` unit-pinned per arm with its probe parsers pinned too, and the scripts as callers that thread `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` into the xtask child. A readiness decision added for the handshake follows that shape.
- A verdict derives only from independent probes: test-plan §3 5-command implementation → `cleanup` → Verification requires pid liveness plus a TCP handshake on the resolved ports at `127.0.0.1`, never the acting call's own status. The readiness handshake is the same probe read in the other direction.
- A record that must survive the process ending is witnessed cross-process: test-plan §3 Per-chunk gate discipline → Process-end witness form requires re-exec children, each on its own TempDir, child-ran proof in-arm, and the parent reading the log family only after the child ended; it also lists the ends the form cannot reach by construction. If the chunk adds or changes an end-of-process record in the product, this is its test form.
- The sh and ps1 verbs move in lockstep on record: test-plan §3 5-command implementation → `boot` → Command body describes each sh change as "ps1 mirrored", and test-plan §9 CI Integration → Matrix builds states the `.ps1` halves have no CI witness. A ps1 change in this chunk is unwitnessed by CI; a deliberate sh-only change is a stated divergence, not a silent one.

## Anti-patterns to avoid
- No retry, re-run or soft-fail around the smoke to obtain a green: test-plan §11 Test Anti-Patterns → Quality bans retry-once policies, and test-plan §11 Test Anti-Patterns → CI bans ignoring a flake.
- No fixed sleep to buy the app life or to stand in for readiness: test-plan §11 Test Anti-Patterns → E2E bans `sleep(N)` for synchronization and requires an explicit signal. The plan states it under E2E; the smoke's wait for the receivers is the same shape.
- No one-time live proof standing in for a gate without saying so: test-plan §1 Pending coverage triggers → `harness-cleanup-verdict-and-boot-spawn-shell-coverage` records that the `boot` spawn arm, its failure-diagnosis branch and the waiting wrapper ship with no committed test and owes a harness-level assertion per boot failure-reason arm. A new readiness arm either carries a committed assertion or widens that trigger at the wrap.
