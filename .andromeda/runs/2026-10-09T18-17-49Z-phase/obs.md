# obs extract

## Relevance
relevant — the chunk's subject is a process end that left no record in the self-observation log, read through the CI boot job's log artifact; the readiness half touches obs only at the tick / `health` split.

## Constraints
- obs-plan §7 Error classes captured (Process-end cause) requires every LOGGABLE process end to write exactly one `app.exit` record before the process goes, and lists the ends that are unloggable by construction (stderr / `boot.log` at most). The two red logs hold neither `app.exit` nor `app.panic.fatal` (scope, freight), so either the end belongs to the listed unloggable class or the code does not satisfy the mandate on that path — which of the two is research's question, and it is the first cut of "the exit path that writes no record is itself the finding".
- obs-plan §6 Log levels mapping (`app.exit`, warn row) requires the record EXACTLY ONCE per process end behind a process-wide once-flag, with the level set by exit class (WARN signal · ERROR non-zero `event_loop` and every `outside_event_loop` · INFO zero-code `event_loop`) and the `atexit` path handing off to the `pulse-exit-reporter` thread under a bounded wait. Any exit path the chunk adds or repairs keeps one record, one emitter, the same level rule.
- obs-plan §3 Tracing init (Init order) requires the `WorkerGuard` to sit in the process-wide slot, the at-exit hook and the Unix signal listener to be installed between panic-hook install and app spawn, the app to run through `run_return`, and every exit path that can log to drain the sink after its one record (`WorkerGuard::drop` is the only drain). A record emitted but not drained is indistinguishable in the artifact from no record; whether the path the app took on the runner drains is research's question.
- obs-plan §3 Logging stack (Sink) requires the app to have ONE sink, the JSON file, with no stderr `tracing` layer; obs-plan §7 Panic hook requires stderr to carry only what the chained prior hook prints. So what the boot wrapper captures on standard error is non-`tracing` output by design, and no fix may add a stderr `tracing` layer to make the cause visible.
- obs-plan §8 PII Scrubbing (Default-deny posture, `app.exit` leaf) requires `app.exit` to resolve to its own EXACT leaf carrying exactly `exit_class`, `exit_code`, `exit_code_known`, `signal`, with no bare `app` key, and bans a path, a panic payload, an error `Display` or any native message on it. A new field, a new closed-label value, or a new exit-cause target needs its own exact leaf whose field set equals the emit site's, guarded where the guard runs (`pulse-app/tests/`).
- obs-plan §9 Telemetry artifact handling requires the Linux `boot` job to upload the boot smoke's log family as `logs-boot-${{ runner.os }}` under `if: always()` with 14-day retention. "What the job keeps" is this artifact; what it contains beyond `logs/agent-latest.jsonl*` (the wrapper's `boot.log`, its exit state line) is research's question before anything is added to it.
- obs-plan §3 Heartbeat ticks (Complementarity with the `health` command) requires ticks (15 s, retroactive) and `health` (synchronous, active probing during boot) to stay separate mechanisms. A readiness signal is never derived from tick presence, and a smoke that lives under one tick interval certifies nothing through ticks.

## Patterns to follow
- The "otherwise indistinguishable" pattern of obs-plan §6 Log levels mapping (warn row): a condition no other signal separates from a healthy boot gets ONE bounded record per event, off any hot path, closed labels only (`app.boot.buffer.degraded`, `app.boot.window.navigation`, `app.boot.render.posture`, `app.exit`). If the cause needs a new record to be nameable from a run, it takes this shape.
- Existing per-boot diagnostics to read a red log against before adding anything: `app.boot.window.navigation` (at most once per window per boot, post-settle), `app.boot.render.posture`, `ui.webgpu.adapter`, `ui.ipc.rejection` — per obs-plan §6 Log levels mapping. Whether the red logs reached the post-settle navigation record bears on "the window's or the engine's".
- Leaf guards assert the field SET by equality in both directions plus the no-bare-prefix discriminator, never only that the target resolves — per obs-plan §8 PII Scrubbing (Default-deny posture, the `app.exit` and `triage.cue.tick` entries).
- CI triage reads the artifact, not the terminal: `gh run download` of the log artifact, then `jq` over JSON lines — per obs-plan §9 CI failure → artifact triage workflow. Per obs-plan §9 CI-specific default fields the plan requires `ci.run.id` and `git.commit.sha` on every CI line; whether the boot-smoke log carries them (they would tie a reading to its source) is research's question.
- A grader over `agent-latest.jsonl` stays NEUTRAL-tolerant for an unrequired arm — per obs-plan §10 Load-profile constraints; `ci-gates` grades the boot-smoke log with no arm required.

## Anti-patterns to avoid
- NEVER make unstructured stderr text the signal where the end is loggable — the "why" belongs as a JSON line in the file sink; stderr / `boot.log` is the surface only for the unloggable class (per obs-plan §11 Logs; obs-plan §7 Error classes captured).
- NEVER add a retry-once policy that masks the failure, and never lose the telemetry artifact of a failed run (per obs-plan §11 SLO; obs-plan §11 CI) — the obs-side twin of "no run is re-run for a green".
- NEVER widen a record with a path, a native message or raw error text "for debuggability" (per obs-plan §11 Logs; obs-plan §8 PII Scrubbing, `app.exit` leaf).

## Contract bindings
- obs ↔ tests: the `boot` readiness signal (a TCP handshake on the bound ports) is test-plan §3, 5-command implementation — not an obs-plan key; the obs side is only obs-plan §3 Heartbeat ticks (ticks vs `health`). The obs-plan names no receiver-bind record: obs-plan §4 Instrumentation per surface (CLI / main binary) requires receiver-startup child spans under `app.boot` and specifies no target or field set for them, so `app.boot.otlp.grpc.bind` (scope, freight) is not an obs contract and readiness must not be redefined as its presence.
- obs ↔ security: `app.exit` is a deliberate NO-SCRUB log boundary (security-plan §Logging); a new field or a second exit-cause record is a boundary widening, which the scope's Boundaries halt for the founder's word. The `atexit` / signal-handler logging restriction that shapes the `pulse-exit-reporter` handoff is security's rule, mirrored in obs-plan §6 Log levels mapping.
- obs ↔ CI (arch CI/CD): the `logs-boot-${{ runner.os }}` upload and the `ci-gates` read of that log (obs-plan §9 Telemetry artifact handling; obs-plan §10 CI gates).
- Wrap-owned obs-plan sites if the outcome changes them (phase amends none): the unloggable-ends list (obs-plan §7 Error classes captured; obs-plan §6 Log levels mapping; obs-plan §3 Tracing init) if the cause is an end not yet listed or wrongly listed; and the boot-job timing readings "0.57 s to 1.40 s before `cleanup`" with the some-runs-witness wording (obs-plan §10 Performance budgets, frame row; obs-plan §10 CI gates, perf-budget bullet; obs-plan §1 Telemetry triggers, multi-platform-exporter-compat row; obs-plan §8 PII Scrubbing, `ui.webgpu.adapter` leaf) if the smoke's sequence or the app's lifetime in it changes.

## Acceptance criteria contributions
- A run in which the app ends by itself through a loggable end holds exactly one `app.exit` record, drained to the uploaded log family, with all four fields rendered and none `<redacted>` (per obs-plan §7 Error classes captured; obs-plan §6 Log levels mapping; obs-plan §3 Tracing init).
- If the named cause is an unloggable end, the boot job's kept artifact holds the non-`tracing` evidence that names it, and the report records the end against the plan's unloggable list for the wrap (per obs-plan §7 Error classes captured; obs-plan §9 Telemetry artifact handling).
- Every target or field the chunk adds resolves to its own exact allowlist leaf, pinned by a field-set-equality guard under `pulse-app/tests/`, and carries no path, payload or native text (per obs-plan §8 PII Scrubbing, Default-deny posture).
- The boot-smoke log still holds zero `app.panic.fatal`, shows no heartbeat gap over 45 s if the app now lives past a tick, and its `ci-gates` perf read stays NEUTRAL with no arm required (per obs-plan §10 CI gates; obs-plan §10 Load-profile constraints).
