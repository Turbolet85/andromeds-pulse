# arch extract

## Relevance
relevant — the chunk works on two CLI contracts architecture.md registers (`scripts/agent-run.{sh,ps1}` and `cargo xtask harness:status`), on the harness state files and ports it reserves, and on the `boot` job its CI/CD key describes.

## Constraints
- **Workspace placement.** The harness driver is the `scripts/agent-run.{sh,ps1}` pair, the status verdict lives in the `xtask` crate (`xtask/src/harness_status.rs`), and any product-side exit or boot change lives in the `pulse-app` binary crate. architecture.md §Occupied Resources → Cargo workspace crate names reserves the sixteen names, so the chunk adds no crate; §Cross-cutting Patterns → Module dependency direction requires that no library crate come to depend on `pulse-app` or `xtask` for this work.
- **Both harness surfaces are formalized CLI contracts.** architecture.md §Occupied Resources → xtask CLI surfaces registers `scripts/agent-run.{sh,ps1}` (five verbs, sh and ps1 in lockstep, the `boot` failure lines, the bounded `cleanup` token) and `cargo xtask harness:status` (one verdict JSON object, four arms, their exit codes, callers exactly the two harness legs). A change to a verb's output, an arm, an exit code or the verdict object's fields is a contract change, listed for the wrap amendment. The registered `boot` text describes readiness as the status poll and registers the TCP handshake for `cleanup` only, so the readiness change this chunk makes alters registered text. Whether `agent-run.ps1 boot` has the same gap is research's question; a sh-only change departs from the lockstep clause and the plan must say so.
- **What the status verdict is derived from.** architecture.md §Occupied Resources → Filesystem locations (the `run/andromeda-pulse.pid` clause) requires the verdict to come from the product-written pid file, the liveness of the pid it holds, and the log family's mtime. Receiver bind is not among its inputs, so `running-healthy` does not by contract assert the ports accept. Whether the port probe is added in the script or in the xtask verb is the plan's choice; the second changes the verdict contract of the item above.
- **Ports and bind address.** architecture.md §Occupied Resources → Network ports fixes the receivers on `127.0.0.1`, and §Occupied Resources → Environment variables reserves `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT` as their overrides. A readiness handshake therefore targets the RESOLVED ports on loopback, both of them, never the literals 4317 / 4318.
- **Harness state files.** architecture.md §Occupied Resources → Filesystem locations requires `run/andromeda-pulse.spawn` and `run/andromeda-pulse.exit` to be harness-written and never written by the production binary, with the end record one line that `harness:status` reports as `ended`. architecture.md §Occupied Resources → xtask CLI surfaces bounds that record to 48 printable ASCII characters and registers the sh waiting subshell as sending the app's stdin, stdout and stderr to `/dev/null`. If the chunk makes the job keep the app's standard error, that clause changes, and any new kept file is a new data-dir subpath to register at the wrap.
- **The `boot` job's shape.** architecture.md §Infrastructure Patterns → CI/CD approach requires `ci.yml` to stay six independent jobs on `ubuntu-22.04` with no matrix and no `needs:` edge, with `boot` composed of the mcp-feature release build, the boot smoke, then `cargo xtask ci-gates`, and names the self-lint tests that pin the trigger block, the Linux-only property and the two release-build witnesses. It also records the Actions cache as over the repository cap, so the chunk adds no cache key.
- **Designed ends of the process.** architecture.md §Cross-cutting Patterns → Tray icon policy requires that closing the main window minimize to tray and that the process end only on the explicit Quit item or an OS-level kill. An app that ends by itself after ready is outside both designed ends. Whether the code honours this under a virtual display with no tray host is research's question, and it bears on the scope's open point of whether the end is the window's or the engine's.

## Patterns to follow
- **The independent-probe shape `cleanup` already has.** architecture.md §Occupied Resources → xtask CLI surfaces registers `cleanup` as judging from pid liveness plus a TCP handshake on the resolved OTLP ports at `127.0.0.1`, ending in one bounded stdout token. A readiness handshake in `boot` follows that shape and that port resolution.
- **How `boot` reports a failed readiness poll.** architecture.md §Occupied Resources → xtask CLI surfaces registers the outcomes of a failed poll (the end record, or still running but never healthy, then `cleanup`), the no-spawn-record arm, and the timeout default it calls honest against a measured warm boot-to-ready. A "ports never accepted" outcome takes the same one-line, exit-1 form, and the timeout is re-checked once ready waits for the receivers.
- **Local reproduction names the dev binary and may move the ports.** architecture.md §Occupied Resources → Process / service identity requires a harness or plan invocation to name `target/{profile}/pulse-app`, never the bundled name. architecture.md §Cross-cutting Patterns → Test-time telemetry injection sends a run that needs non-default ports through the two port variables, which is the registered way around the shared 4317 / 4318 on this host.
- **A record-less Linux end has a registered precedent.** architecture.md §Occupied Resources → Environment variables (the `__NV_DISABLE_EXPLICIT_SYNC` entry) records a launch that died about two seconds into boot through a native-toolkit `_exit(1)`, measured on one host under native Wayland. It is a precedent for the class of end, not evidence of this cause, and the virtual display here is a different surface. The same entry requires `render_posture::apply_linux_default()` to stay the first statement of `main()`, ahead of the runtime build, so any product-side boot or exit instrumentation goes after it.
- **Shared CI logic in Rust goes in `xtask`, with machine-parseable output.** architecture.md §Infrastructure Patterns → CI/CD approach places Rust-needing CI logic in the `xtask` crate so the same command runs locally, and architecture.md §Cross-cutting Patterns → Development Style asks for deterministic invocations and schema-stable, machine-parseable outputs. Whatever the job is made to keep about an app's end follows that.

## Anti-patterns to avoid
- **Softening the gate instead of closing the cause.** architecture.md §Occupied Resources → xtask CLI surfaces registers the "Boot pulse-app smoke" step as GATING since `continue-on-error` was dropped. Restoring it, or adding a retry around the smoke, hides the end this chunk has to name.
- **A status that cannot say "not running".** architecture.md §Occupied Resources → xtask CLI surfaces records that the out-of-process verdict replaced an in-process health envelope that exited 0 unconditionally, and that a dead pid reads `not-running` whatever the log's freshness says. Readiness is not moved back to an in-process answer, and log freshness never stands in for liveness or for bound ports.
- **A product-side switch for the harness's benefit.** architecture.md §Occupied Resources → Environment variables keeps `ANDROMEDA_PULSE_PIDFILE`, `ANDROMEDA_PULSE_LOGFILE` and `ANDROMEDA_PULSE_DATA_DIR_KEEP` harness-only and not product-consumed. A new product-consumed variable or CI-only product mode that keeps the app alive or skips the window is a new reserved resource and a boundary widening, not a fix; the production binary also never writes the harness's spawn or exit record (architecture.md §Occupied Resources → Filesystem locations).

## Contract bindings
- **arch ↔ tests.** The `boot` readiness clause is owned by test-plan §3 (5-command implementation), while architecture.md §Occupied Resources → xtask CLI surfaces registers the same verb's contract text. Both change together at the wrap, and the registered arch text currently names no handshake at ready.
- **arch ↔ tests (CI pins).** The self-lint tests named in architecture.md §Infrastructure Patterns → CI/CD approach live in the `xtask` crate and pin `ci.yml` as it stands. A changed smoke step or a new upload step must leave them green or amend them with their stated reason.
- **arch ↔ security.** The exit record's bounded grammar and the harness-only state-file class in architecture.md §Occupied Resources → Filesystem locations are what security-plan's harness carve-out rests on. A wider record, or a kept standard-error file, is a security question on what it may carry (paths, native messages).
- **arch ↔ obs.** architecture.md registers no product exit record of its own; the `app.exit` record and its unloggable ends are the obs and security plans'. The arch side is only the harness-written `run/andromeda-pulse.exit` and the `ended` verdict field. If the cause is an end the product cannot log, the harness record is the surface arch already has.
- **arch ↔ obs (engine readiness).** If the chunk touches what the engine itself reports before the receivers bind, architecture.md §Standard Contracts → `health` and → `ready` fix those envelopes, including the two receiver subsystem keys and a bind failure as a degraded reason. Whether the code's envelopes reflect bind state today is research's question.

## Acceptance criteria contributions
- `boot` prints ready only after a TCP handshake succeeds on both resolved OTLP ports at `127.0.0.1`, with the ports taken from `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT` when set (per architecture.md §Occupied Resources → Network ports and → Environment variables).
- `cargo xtask harness:status` keeps its verdict object's fields, four arms and exit codes, and its callers stay the two harness legs; any departure is listed by name for the wrap amendment (per architecture.md §Occupied Resources → xtask CLI surfaces).
- The chunk adds no product-consumed environment variable, port, TauRPC procedure or capability; every new file the harness or job keeps sits under the resolved data dir, is never read or written by the production binary, and is listed for registration at the wrap (per architecture.md §Occupied Resources → Filesystem locations and → Environment variables).
- `ci.yml` still holds six independent jobs on `ubuntu-22.04` with no `needs:` edge and no new cache key, the boot smoke step carries no `continue-on-error`, and the workflow self-lint tests pass (per architecture.md §Infrastructure Patterns → CI/CD approach and §Occupied Resources → xtask CLI surfaces).
