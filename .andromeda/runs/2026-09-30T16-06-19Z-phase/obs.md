## Constraints
- Snapshot budget scope: obs-plan §10 (Performance budgets, snapshot row) bounds "Snapshot generation (25k token budget)" at p99 500 ms, and obs-plan §5 (per-surface metric table, snapshot row) names the instrument "Snapshot generation". Both sections currently RECORD, as measured at the predecessor, that `duration_ms` times `format_markdown` only and name this chunk's route entry as owner. The chunk must make the graded value span the whole generation (load + curate + format). Whether HEAD still times formatting only is research's question; scope.md reports it verified at `markdown.rs:43`.
- One p99 rule: obs-plan §10 (snapshot row, "The p99 rule") fixes nearest-rank, ⌈0.99·n⌉-th smallest, as the single rule for every perf arm. A whole-generation sample is graded by that rule unchanged. Neither the rule nor the 500 ms / 33 ms values may move (this matches scope Boundaries).
- Gate semantics are preserved: obs-plan §10 (CI gates, perf-budget bullet) requires `perf:budget` to FAIL on an arm over budget, on a non-numeric graded field (Unreadable), and on a `--require`d arm with no sample, and never to PASS over empty input. CI lint-test Linux keeps `--require memory,snapshot` over the `perf_budget_samples` producer log (obs-plan §10 snapshot row + CI gates).
- Metric emission convention: obs-plan §5 (Metric emission convention + Naming conventions) requires every metric to be a `tracing::info!` event under `metric.{module}.{measure}` with raw per-event values, and it bans precomputed quantiles in the emission path (§11 Metrics). A second, whole-generation timer (if P3 picks that over re-scoping the existing one) must follow this naming, and the grader must read THAT target/field.
- Frontend→backend telemetry: obs-plan §3 (Logging stack → Frontend bridge) makes the hand-rolled TauRPC `telemetry.frontend.*` commands, which call `tracing::info!` on the backend, the DECIDED mechanism for webview-originated telemetry. The adapter-request result belongs on that path, not a browser SDK or a new sink. Whether an existing `telemetry.frontend.record_*` procedure can carry it (reuse vs new) is research's question.
- Bounded, once-per-state diagnostic records: obs-plan §6 (Log levels mapping, `warn` row) sets the precedent that a state which is otherwise indistinguishable from health (`app.boot.window.navigation`, `ui.ipc.rejection`, `interpretation.model.allow_root`) gets ONE record per state/boot, off any hot path, with a CLOSED enum field (`error_category` / `reason`). It is INFO on the healthy arm and WARN on the degraded arm. The adapter record fits this shape: once per adapter request, never per frame.
- Label cardinality: obs-plan §5 (Metric label cardinality discipline) bounds label fields to enumerated values. `wgpu_backend` is already closed to {vulkan, metal, dx12} and `webview_backend` to {WebView2, WKWebView, GTKWebKit}. The adapter cause/outcome field must therefore be a closed enum, with no raw adapter vendor/description strings.

## Patterns to follow
- `ui.ipc.rejection` via `telemetry.frontend.record_ipc_rejection` (obs-plan §6 `warn` row): the webview classifies into a closed serde enum, the backend emits one bounded-field record, and the reach is proven by a measured world contrast (granted 0× vs revoked 1×). This is the direct template for the adapter-state record.
- `app.boot.window.navigation` (obs-plan §6 `warn` row): one record per window per boot, post-settle, INFO when healthy and WARN when degraded. Use this shape if the adapter record is boot-scoped.
- P2 must-trace pipeline (obs-plan §4, Scenario P2): `snapshot.generate.request` / `session.snapshot` wraps the whole pipeline, with children `duckdb.query.aggregation` → `snapshot.render.markdown` → `snapshot.token.count.validate`. A whole-generation timer that aligns with the parent span's boundary (not the render child's) matches the plan's decomposition.
- Two-state NEUTRAL posture (obs-plan §10, frame row + Load-profile constraints): an UNREQUIRED empty arm reads NEUTRAL and a REQUIRED empty arm fails. The named frame cause refines the CI `frame: cannot-evaluate` text but must keep that posture. The frame arm stays unrequired on CI; the gate stays `perf:frame-sample` on the dev host.
- CI log artifacts (obs-plan §9, Telemetry artifact handling): the lint-test Linux perf-samples log (`logs-perf-samples-*`) and the boot log (`logs-boot-*`, read by `ci-gates`) are the agent-readable surfaces. The cause line must derive from the app's own JSON log in whichever of these the frame line reads.

## Anti-patterns to avoid
- Soft or mis-scoped SLO (obs-plan §11 SLO, "NEVER define soft SLO budgets"): a budget that grades a sub-stage while naming the whole operation is the defect this chunk closes. Do not swap it for an ungraded second timer; the gate must read the value that spans the budget.
- Hot-path spam (obs-plan §11 Logs + Telemetry Strategy): never emit the adapter record per frame or per rAF tick. Never format heavy adapter-info payloads at `info` inside the frame loop.
- Raw or unbounded content (obs-plan §11 Metrics, unbounded label cardinality): no raw adapter strings (vendor, architecture, description, error message text) in event fields; closed enum or bounded label only.

## Contract bindings
- obs ↔ tests: the producer `pulse-app/tests/perf_budget_samples.rs` (`--profile perf-samples`) and the grader `xtask::perf_budget` are the snapshot row's enforcement (obs-plan §10 snapshot row + CI gates). If the graded target/field changes, the producer, the grader's arm definition and its pins (test-plan side) move together. The §5 and §10 snapshot rows that record "formatting only" are then owed an amendment at wrap.
- obs ↔ security: a new `telemetry.frontend.*` procedure (if P3 chooses new over reuse) binds to security-plan's `EXPECTED_PROCEDURES` pin + validated argument struct, plus a tracing allowlist leaf with a bounded field set. The no-raw-strings rule above is the obs half.
- obs ↔ CI (§9): the named-cause `frame: cannot-evaluate` line is computed from the log artifact the frame line already reads. Which job/log that is (lint-test perf-samples vs boot smoke `ci-gates`) is research's question.
- obs ↔ a11y/frontend: the adapter-request site is webview code (`webview-adapter.ts`); the record crosses via the §3 frontend bridge only.

## Acceptance criteria contributions
- The value `perf:budget`'s snapshot arm grades spans the whole generation (load + curate + format), not formatting alone. The resulting nearest-rank p99 over the producer's samples is MEASURED and recorded against the 500 ms budget, and the lint-test Linux `--require memory,snapshot` gate stays green or red on that value (per obs-plan §10 snapshot row + CI gates; §5 snapshot row).
- The app's own JSON log carries one adapter-request record per request (never per frame), with a closed-enum outcome field. The enum distinguishes at least no `navigator.gpu` / request null-or-threw / adapter obtained, and carries no raw adapter strings. It is INFO when healthy and WARN when degraded (per obs-plan §6 `warn` row pattern; §5 cardinality discipline).
- A 0-frame CI run's `frame: cannot-evaluate` line names its cause from that record, including the "no adapter record at all" case. The frame arm stays unrequired on CI (NEUTRAL posture intact), and `perf:frame-sample` stays the dev-host gate (per obs-plan §10 frame row + Load-profile constraints).
- `perf:budget` still FAILs on a non-numeric graded field and on a required-empty arm after the change, and still applies the unchanged nearest-rank rule (per obs-plan §10 CI gates, perf-budget bullet).
