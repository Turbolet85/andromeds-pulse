# a11y extract

## Relevance
partial — no new UI surface is scoped; the domain is touched only where Part B's adapter-result record runs inside the webview canvas path the a11y suite audits (`webgpu-adapter.ts`, mounted under the constellation canvas wrapper), and where Part C edits `ci.yml`, which hosts the blocking `a11y` matrix job.

## Constraints
- Tier is Standard, WCAG 2.1 AA with the SC 2.3.3 AAA motion escalation (per a11y-plan §1 A11y Scope Summary); the TauRPC bridge itself is classed Not-assertable (per a11y-plan §1 entity table, "Tauri IPC bridge"), so a new or reused adapter-record procedure adds no a11y assertion of its own. What it can do is change what the audited webview renders or rejects.
- The WebGPU canvas has no built-in semantics; its accessible context lives on the wrapper `<section aria-label="Telemetry traces chart">` with a STABLE literal name and an `aria-describedby` summary that is aggregate-only (per a11y-plan §7 Landmark roles). If the adapter-result arm changes what the wrapper renders (for example an `unavailable` reason shown to the user), the landmark name must stay the stable literal, and no raw adapter string may reach the accessible tree. Whether the `unavailable` arm renders anything user-visible today is research's question.
- The a11y Playwright suite mocks every TauRPC procedure a rendered surface calls, via the `TauRPC__<router.path>` shape in `tests-a11y/helpers/mock-tauri.ts` (per a11y-plan §3 Harness wiring & conventions, "Adding a surface (standing rule)"). If Part B adds a NEW procedure invoked on the canvas mount path, the mock must answer it, or the audited surface's settled state changes under the sweep. Whether the adapter request runs during the a11y specs, and what Playwright chromium's `navigator.gpu` returns there, is research's question.
- The `a11y` job in `ci.yml` is a blocking, fail-fast matrix job (Linux/macOS/Windows) that runs `npm run build --prefix pulse-app/ui` → Playwright chromium → the PR-only `a11y-violations-base` download → `cargo xtask test:a11y`, with artifacts uploaded `if: always()` (per a11y-plan §3 CI integration and §9 CI Integration). The Part C cache edit on the `release` job must leave that job's steps, gating and artifact flow unchanged.
- The a11y CI run budget is `total a11y CI run + tests E2E < 10 min` (per a11y-plan §10 SLO Invariants & A11y Budgets, "Performance budget per a11y CI run"). This agrees with the chunk's CI-speed ruling: no Part C change may add a cold rebuild or a step to the a11y job.
- Zero new violation tuples against `baselines/a11y-violations-summary.json` (per a11y-plan §10 Standard+ invariants and §3 Harness wiring & conventions, "Regression baseline"). A webview edit in Part B must not introduce a new `{surface, wcag_criterion, selector, severity}` tuple.

## Patterns to follow
- The mock-layer sentinels `__mockReject` and `__mockDelayMs` exist so the error and in-flight states can be audited, not only settled success (per a11y-plan §3 Harness wiring & conventions). If the adapter record is fire-and-forget, a rejected call must leave the rendered DOM unchanged. The sentinel is how to prove that.
- Use `npx playwright test --list` as the cheap suite-health check after touching a module the specs import (per a11y-plan §3 Harness wiring & conventions). A list-time import failure once silently disabled the whole suite.
- The constellation summary deliberately omits `role="status"` so it does not stack announcements with the dashboard's existing live region (per a11y-plan §7 Landmark roles). Any adapter-state text surfaced to the user should follow the same rule: no new live region is added only to announce a diagnostic.

## Anti-patterns to avoid
- NEVER skip, soften or `continue-on-error` the a11y job, and never defer it to a follow-up, as a side effect of a CI-speed or cache edit (per a11y-plan §11 CI, "NEVER skip a11y on CI failure" / "NEVER defer a11y to post-merge").
- NEVER hide essential content from assistive tech or add ARIA noise when surfacing adapter state. That covers `aria-hidden` on meaningful content and redundant labels (per a11y-plan §11 Screen Reader).
- NEVER use a retry-once policy on an a11y spec that becomes flaky because of adapter-request timing (per a11y-plan §11 SLO).

## Contract bindings
- a11y ↔ tests: the a11y job shares `ci.yml` with the test jobs, and Part C's `release`-key `cache-on-failure` edit sits in the same workflow file (per a11y-plan §3 CI integration + §9 CI Integration; binds to test-plan §9).
- a11y ↔ security/arch (IPC): a new adapter-record procedure lands its `EXPECTED_PROCEDURES` pin on the backend. On the a11y side, the matching `TauRPC__` mock entry must land in the same chunk if the audited surfaces call it (per a11y-plan §3 Harness wiring & conventions).
- a11y ↔ design: if an adapter-unavailable state becomes visible, it is a state indicator and must be not-color-alone, paired with text or icon (per a11y-plan §11 Visual; binds to design-system §Color Palette).

## Acceptance criteria contributions
- (a11y) `cargo xtask test:a11y` passes on the chunk's webview change with zero new violation tuples against `baselines/a11y-violations-summary.json`, and the `a11y` job stays green and blocking on all three OSes (per a11y-plan §10 Standard+ invariants and §3 CI integration).
