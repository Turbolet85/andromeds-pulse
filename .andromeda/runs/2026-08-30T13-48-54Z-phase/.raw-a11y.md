## Constraints
- `--color-accent / --color-base` is a 4.5:1 pair **only for non-text** use (border/icon at ≥3:1 per SC 1.4.11); body-size text in that token must instead meet SC 1.4.3 4.5:1, which the plan's contrast-pair table assigns to `--color-text-primary / --color-base` (per a11y-plan §6 Color contrast pairs). The scope's CARRY (`~3.8:1`) is a measured claim it flags for re-verification — whether HEAD's `ErrorState` still has that shape is research's question.
- The error state must carry a text label and/or icon supplement, not color alone (SC 1.4.1); axe-core does **not** detect this, so a custom DOM assertion is required (per a11y-plan §6 State color tokens (not-color-alone) + §11 Anti-Patterns → Visual).
- Token names must be reproduced verbatim from the design source of truth; inventing a token or substituting a raw hex is banned (per a11y-plan §6 Source-of-truth + §2 Naming conventions).
- Error and in-flight states are only auditable through the IPC mock's `__mockReject` / `__mockDelayMs` sentinels, and fixtures must be POPULATED — an empty/never-rendered state makes the sweep audit nothing and pass by comparing nothing (per a11y-plan §3 Harness wiring &amp; conventions). Whether the existing p9 spec already drives the report LOAD-error path is research's question.
- Zero WCAG AA violations on must-be-accessible paths and zero new violation tuples vs `baselines/a11y-violations-summary.json`; contrast-token mismatch is a hard build-failure condition, with no retry-once and no soft gate (per a11y-plan §10 SLO Invariants + §3 Regression baseline).
- Every WCAG claim needs machine-verifiable output (axe-core JSON / Lighthouse JSON / pa11y JSON / colorjs.io token assertion); a visual eyeball of the recolored error text is not evidence (per a11y-plan §2 Agent-runnable invariants + §11 Anti-Patterns → Universal).
- If the Copy-path retro-fit (scope item 4) renders any NEW user-visible failure text, it inherits the same not-color-alone + 4.5:1 constraints plus SC 4.1.3 status-message announcement requirements for the `role="dialog"` report window (per a11y-plan §7 Live regions + §5 report-window entry).

## Patterns to follow
- The identical remediation shape is already the plan's established treatment for severity/error text on this surface family: text → `--color-text-primary`, the state color retained on borders/icons (per a11y-plan §11 Anti-Patterns → Visual; recorded as applied at sibling sites in the 2026-06-10 amendment).
- Reaching a rejected/failed state in the audit via `installTauriIpcMock`'s `__mockReject` sentinel — the p14 Investigate result/error/progress specs are the template (per a11y-plan §3 Harness wiring &amp; conventions → Adding a surface).
- The report window is already an enumerated surface (p9 diagnostic report modal, within P1–P14), so the standing "one axe spec per new route/modal" rule is satisfied by extending existing coverage rather than adding a surface (per a11y-plan §1 Surface set extension + §3 standing rule).
- Selectors for harness/headful assertions bind accessible-name-first wherever an accessible anchor ships, falling back to `data-testid` only where none does (per a11y-plan §1 Critical paths → P1 row, measured-per-surface convention).
- Any `Report.tsx` edit must preserve the window's `role="dialog"` fill-variant focus trap and Esc/✕ close with cross-window focus restore to the findings window (per a11y-plan §5 Keyboard Navigation → report-window).

## Anti-patterns to avoid
- Shipping a foreground/background pair below the WCAG minimum, or conveying the error identity by color alone (per a11y-plan §11 Anti-Patterns → Visual).
- Deferring the a11y fix to a follow-up chunk or landing it behind a lint-only/soft gate — a11y is a fail-fast merge gate with no "fix in follow-up" (per a11y-plan §11 Anti-Patterns → CI).
- Bolting ARIA onto non-semantic markup or adding redundant labels if the Copy-failure retro-fit introduces new error UI — semantic HTML first, ARIA second (per a11y-plan §11 Anti-Patterns → ARIA + Screen Reader).

## Contract bindings
- **a11y ↔ design:** the CARRY fix's token swap binds to the design-system color palette — `--color-text-primary / --color-base` (4.5:1 text) and `--color-accent / --color-base` (3:1 non-text only), verbatim names (a11y-plan §6 Color contrast pairs).
- **a11y ↔ tests:** verification runs through `npm run test:a11y` / `cargo xtask test:a11y` reusing tests' 5-command E2E driver (`boot`/`run`/`status`/`cleanup`/`logs`) in the same `ci.yml` pipeline; if the headful `report-copy` stage grows a half, its selectors follow the accessible-name-first convention (a11y-plan §3 CI integration + §9 Pipeline integration).
- **a11y ↔ obs:** a11y violation records use `target: "a11y::assertion"` with the obs §6-aligned field set (`wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` / `remediation` / `tool` / `tool_result_id`) (a11y-plan §3 Structured violation JSON schema). This chunk edits the obs allowlist and its pins for a *different* target; whether the exact-leaf allowlist edit can affect the a11y assertion emission path at all is research's question — the a11y artifacts are CI-emitted JSON, not necessarily runtime-allowlisted.
