## Relevance
Relevant — this chunk exists to satisfy a security-plan §Logging & Monitoring mandate, and (in the frontend arm) crosses the TauRPC input-validation + capability-drift boundaries the plan governs.

## Constraints
- security-plan §Logging & Monitoring → "What to log" names **Tauri capability-rejected IPC calls** as a required operationally-relevant security event, with the parenthetical rationale that such rejections are silent at runtime. This is the requirement this chunk must satisfy; **whether the code already emits any such record today is research's question** (the plan states target state only).
- The record must carry **bounded fields only**. security-plan §Logging & Monitoring → "What NEVER to log" and §Security Anti-Patterns → Logging (bullet 1) ban clipboard contents, snapshot contents, MCP tool response bodies, and raw OTLP attribute values. The measured-cost site is the report window's **clipboard write** path, so the rejected call's own payload is squarely on the never-log list — the scope's "byte count, never the payload" is the plan's rule, not a stylistic choice.
- No full product-consumed filesystem path may appear in the new record or its leaf — basename of the canonicalized path only, and per security-plan §Security Anti-Patterns → Logging the rule is **CATEGORICAL** since `2026-08-30-diagnostics-un-muting-harness-truth-sweep` (the last carried exception was retired there). Any window/target/path-ish field must follow that shape.
- If the frontend arm wins: security-plan §Input Validation (TauRPC bridge row) requires `serde` deserialization on every `#[taurpc::procedure]` argument plus a bounded validator per field, and security-plan §Security Anti-Patterns → API bans adding a TauRPC procedure **without both** its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` and a validated argument struct — extended since `2026-08-30-staged-bindings-assertion` to any STAGED-index disagreement.
- The chunk must not touch grants. security-plan §API Security → TauRPC capability authorization records that capability gating admits the webview to the IPC layer **as a whole** (no per-procedure entries exist), while `core:window:*` / core-API grants ARE per-feature and are now asserted against `staged_gate::EXPECTED_GRANTS` with set equality in BOTH directions — an added grant is as red as a revoked one. This mechanically backs the scope's "no permission widening" line.
- Error text crossing to the webview stays sanitized: security-plan §Error Handling requires `Result<T, AppError>` with `AppError::Validation { field, reason }` for rejections, and §Security Anti-Patterns → Logging bans stack traces / Rust struct names / file paths / library versions in `AppError::Internal { message }`, sanitized at the `From` impl. Relevant if the runtime's `… not allowed by ACL` string is captured or forwarded rather than mapped to a bounded category.
- PREREQ pin #22 rides security-plan §Dependency Security → CI integration → *Standing deferral — `cargo audit` unrunnable*: at a between-point, re-verify basis + overlap first-hand and record `probe skipped per ratified interval (next: {point})` — never a silent skip — and per **counting rule (c)** carry no "Nth consecutive" ordinal. Note a live discrepancy for the wrap to reconcile: the plan body's trailing pointer currently reads *next interval point: session 61*, while the scope pins the next full-form probe at **64** — whether the body owes a staleness correction is a wrap-time question, and the `2026-08-28-ingest-consumer-block-under-gap-resume` amendment is the precedent for exactly that class.

## Patterns to follow
- **Bounded-category rejection on an existing error leaf** — security-plan §Input Validation (L4 inference argv prompt row) + §Security Anti-Patterns → Logging describe `validate_prompt_bounded` → a bounded `PromptRejection` whose `label()` is the only thing that reaches the log, surfaced on `interpretation.inference.error` with **no prompt text, excerpt, or offending substring**. That is the exact shape a bounded `error_category` for an ACL rejection should copy.
- **De-silencing precedent** — the same row records the two formerly-SILENT `InferenceError::InferenceFailed` sites folded onto that existing leaf as bounded categories (`io_error`, `stdout_utf8_invalid`), with the no-output-bytes guarantee load-bearing. Same problem shape as a swallowed webview `catch`.
- **Basename emission helper** — §Security Anti-Patterns → Logging names `pulse_app::observability::log_basename` and the `*_basename` field-naming convention (`log_dir_basename` / `path_basename` / `run_dir_basename` / `data_dir_basename`). The scope's `sanitize_window_label` is the analogous sanitizer; whether it exists under that name at HEAD is research's question.
- **`telemetry.frontend.*` validator precedent** — §Input Validation (TauRPC row) records `validate_duration_ms`, `validate_discovered_count` (bound 10_000) and the closed `HueSeverityTier` enum, **each rejection unit-tested by name**. A byte-count argument on a new frontend procedure should carry the same bounded-parse + named-rejection-test shape.
- **Two-piece TauRPC enforcement** — §API Security → TauRPC capability authorization: router registration + `EXPECTED_PROCEDURES` pin, checked by `xtask capability-drift` against BOTH the worktree and the git-INDEX copy of the generated bindings.

## Anti-patterns to avoid
- NEVER log the rejected call's payload — clipboard contents, snapshot contents, or raw OTLP attribute values (per security-plan §Logging & Monitoring "What NEVER to log" + §Security Anti-Patterns → Logging).
- NEVER add a TauRPC procedure without both a validated argument struct and its `EXPECTED_PROCEDURES` pin, and NEVER add or widen a core-API / `core:window:*` grant in this observe-only chunk (per security-plan §Security Anti-Patterns → API).
- NEVER let unsanitized internals (Rust struct names, file paths, library versions, stack traces) ride the webview-facing `AppError::Internal { message }` or the new record (per security-plan §Security Anti-Patterns → Logging).

## Contract bindings
- **obs** — security-plan §Logging & Monitoring ("Log format") places field redaction at the `tracing-subscriber` layer, not at call sites, writing JSON to `agent-latest.jsonl`. The exact allowlist leaf itself (`pulse-app/src/observability.rs` + `pulse-app/tests/observability_pins.rs`) is obs-plan's surface; security's binding is only that the leaf be EXACT (a leaf-less target redacting every field would destroy the security event the plan requires) and that its fields stay bounded.
- **tests / CI** — security-plan §Dependency Security → CI integration + §Bootstrap phases → `dep-security-ci-gate`: `capability-drift` and `cargo xtask check:staged-artifacts` (exit 1 staged-drift / exit 2 cannot-evaluate) are named build-failure conditions in the one CI workflow; the pin edit + regenerated bindings must be STAGED together or the gate reds.
- **design / a11y** — the CARRY (`Report.tsx` `ErrorState` accent-as-error-text) is outside security's domain; no security binding.

## Acceptance criteria contributions
- A capability-rejected webview IPC call leaves a structured record on the wire (`agent-latest.jsonl`) carrying only a bounded error category, the sanitized window label, and a byte count — with **0 occurrences of the rejected call's payload** across the run's log lines (per security-plan §Logging & Monitoring "What to log" + §Security Anti-Patterns → Logging).
- The new record and its allowlist leaf emit **0 full product-consumed filesystem paths** and no clipboard / snapshot / OTLP-attribute content; any path-shaped field is basename-only (per security-plan §Security Anti-Patterns → Logging, categorical basename rule).
- If a `telemetry.frontend.*` procedure lands: its argument struct is `serde`-deserialized with a bounded validator and a rejection unit-tested by name, and `cargo xtask capability-drift` + `cargo xtask check:staged-artifacts` both exit 0 against worktree AND git-index (per security-plan §Input Validation TauRPC row + §Security Anti-Patterns → API).
- `pulse-app/capabilities/*.json` grants are unchanged and `staged_gate::EXPECTED_GRANTS` set-equality holds in both directions — no grant added, widened, or revoked by this observe-only chunk (per security-plan §API Security → TauRPC capability authorization).
