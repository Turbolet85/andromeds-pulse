# arch extract

## Relevance
Relevant — the chunk lands a new observability surface that, on one of its two candidate arms, is a new TauRPC procedure (arch-registered resource) and on either arm lives in locked workspace crates and touches the capability policy arch owns.

## Constraints
- The webview runs under `pulse:default` and Tauri capabilities are **negative-default**, but the granularity is the IPC LAYER, not the individual TauRPC procedure — TauRPC dispatches every router method through one invoke handler that `core:default` admits. What DOES require an explicit per-feature grant, and IS silently rejected at runtime when missing, is a Tauri **core API** surface (fs / shell / dialog / http, and each `core:window:*` permission individually). That silent-rejection clause is arch's own statement of the failure mode this chunk observes (arch §Cross-cutting Patterns → Webview IPC capability policy).
- Adding a TauRPC procedure requires exactly three arch-side places — a router registration in the owning crate, an entry in §Occupied Resources, and its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` — and **not** a capability-JSON edit; since `2026-08-30-staged-bindings-assertion` the pin edit must be STAGED together with the regenerated `pulse-app/ui/src/bindings/index.ts` or the gate reds (arch §Cross-cutting Patterns → Webview IPC capability policy; arch §Occupied Resources → xtask CLI surfaces).
- Procedure naming is one of two authorized shapes only: top-level bare `snake_case` envelope verbs, or `&lt;router&gt;.&lt;verb&gt;` dotted namespaces with both segments `snake_case`; §Occupied Resources is the canonical enumeration, the Convention defines only the shape (arch §Conventions → Endpoint naming). A frontend-arm procedure therefore belongs under the already-registered `telemetry.frontend.*` namespace.
- Every `#[taurpc::procedure]` must return `Result&lt;T, AppError&gt;` over the stable `AppError` variant set, and any type crossing the bridge or appearing in an MCP response must be `serde::Serialize` — the TauRPC keystone forces `Serialize`-able error types (arch §Conventions → Error response schema (Tauri IPC); arch §Cross-cutting Patterns → Cross-bridge data shape; arch §Established Decisions → [Tauri IPC Bridge — Surface 2]).
- arch's registry records, on the existing `telemetry.frontend.*` entry, that **each target carries its OWN exact obs allowlist leaf** — a bare `metric` key exists carrying only `value`/`unit`/`module`, so a leaf-less `metric.*` target keeps `value` and has every label silently redacted. This is the arch-side statement of the scope's item-2 requirement (arch §Occupied Resources → Tauri IPC routes, `telemetry.frontend.*`).
- Code must land in a reserved workspace crate — `ui-bridge` for a frontend-arm resolver (the namespace's established home per the registry) or `pulse-app` for a runtime-hook-arm builder/window hook; no new crate, and the reserved names cannot be re-purposed (arch §Occupied Resources → Cargo workspace crate names; arch §Cross-cutting Patterns → Module dependency direction: the DAG roots at `pulse-app`, no library crate depends on the binary).
- The product's own telemetry goes only to the stdout/file exporter under `&lt;data_dir&gt;/logs/`; the OTLP network exporter is never pointed at the app's own `:4317`/`:4318` (arch §Cross-cutting Patterns → Self-observation discipline; arch §Established Decisions → [Self-Observation]).

## Patterns to follow
- The three delegated-timing observables (`telemetry.frontend.record_constellation_hue_latency` / `record_constellation_discovery_latency` / `record_findings_counter_refresh`, `crates/ui-bridge/src/telemetry.rs`) are the registered precedent for the frontend arm: a bounded input type with explicit validation bounds, one named `metric.*` target, one exact allowlist leaf each — sanctioned precisely because the bound ends somewhere the backend cannot see (arch §Occupied Resources → Tauri IPC routes).
- The dev-only GUI verification harness row records the assembled **17-stage** path driven by `cargo xtask webview-drive [--expect-absent &lt;STAGE&gt;] [--no-inject]`, each stage id `--expect-absent`-eligible, with `report-copy` sitting between `report-window` and `investigate` and asserting against the app's own obs log and/or the driver's DOM report — the shape any new or extended stage must match (arch §Stack and Technologies → GUI verification harness (dev-only)).
- `cargo xtask check:staged-artifacts` is the registered gate contract: one pretty-JSON verdict on stdout, arms `staged-clean` / `staged-drift` / `cannot-evaluate` at exits 0/1/2, `EXPECTED_GRANTS` as a semantic-triple pin `{identifier, windows, permissions}` over the capability files with set equality in BOTH directions; `capability-drift` runs it and folds any non-clean outcome into its own failure exit (arch §Occupied Resources → xtask CLI surfaces).
- Cross-window webview↔webview coordination is a registered class distinct from `pulse://stream/*` — `findings:dismissed` / `report:open` / `report:closed` via `@tauri-apps/api/event`, gated by `core:event` in `pulse:default`, carrying no telemetry. If a rejection record must cross windows, this is the existing shape (arch §Occupied Resources → Tauri IPC events).
- Config layering, if the mechanism gains any knob: env vars (`ANDROMEDA_PULSE_*`) &gt; `&lt;data_dir&gt;/config.toml` &gt; built-in defaults, with every new env var an arch-registry item (arch §Cross-cutting Patterns → Config management; arch §Occupied Resources → Environment variables).

## Anti-patterns to avoid
- Do not add a per-procedure capability JSON entry or widen/add a reserved capability identifier — the reserved set is `pulse:default`, `pulse:tray`, `pulse:notification`, `pulse:updater`, `pulse:plugin-fs`, `pulse:clipboard`, and `EXPECTED_GRANTS` set-equality means an ADDED grant reds the gate exactly as a revoked one does (arch §Cross-cutting Patterns → Webview IPC capability policy; arch §Occupied Resources → Tauri capability identifiers + xtask CLI surfaces).
- Do not hand-write or hand-edit TypeScript command signatures: the frontend consumes only TauRPC-generated `.ts` bindings, and a custom error envelope in place of `AppError` is banned (arch §Conventions → Workspace API style; arch §Established Decisions → [Tauri IPC Bridge — Surface 2]).
- Do not emit the record through an OTLP exporter aimed at the app's own receiver ports, and do not introduce an "outbound observer" variable that is not explicitly distinguished from the inbound receiver-port variables (arch §Established Decisions → [Self-Observation]).

## Contract bindings
- **arch ↔ obs** — arch's `telemetry.frontend.*` registry entry states the exact-leaf requirement and the leaf-less-target silent-redaction hazard; the target name, field set and allowlist leaf itself are obs-plan-owned. Whether an exact leaf for a new ACL/IPC-rejection target already exists in `pulse-app/src/observability.rs` is research's question.
- **arch ↔ tests** — the `EXPECTED_PROCEDURES` pin and `EXPECTED_GRANTS` triple pin are arch-registered gate contracts; the pins themselves and the headful-leg stage set live in test-owned files (`xtask/src/main.rs`, `xtask/src/staged_gate.rs`, `pulse-app/tests/observability_pins.rs`). Whether the leg grows a stage is not arch's call.
- **arch ↔ security** — negative-default capability policy plus the bounded-field wire shape: arch fixes the envelope (`Result&lt;T, AppError&gt;`, `Serialize`-able), security-plan fixes what may appear inside it (bounded `error_category`, sanitized window label, byte count, never payload).
- **arch ↔ design/a11y** — the CARRY fix in `pulse-app/ui/src/report/Report.tsx` is entirely design/a11y-owned; arch commits only the dark-default, dense developer-tool surface framing (arch §Design Philosophy → Developer-tool surface) and asserts no token values.
