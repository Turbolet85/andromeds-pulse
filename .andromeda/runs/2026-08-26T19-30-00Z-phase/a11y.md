# a11y extract

## Relevance
Partial — the chunk's substance is backend (report assembly, L4 persistence, prompt assembly), but its output renders in the diagnostic-report surface (`p9` report modal / report-window), which a11y-plan §1 holds in the must-be-accessible set P1–P14; the render class changing from "degraded notice" to "full six-section brief" is an a11y-relevant surface change.

## Constraints
- The diagnostic-report surface is a named must-be-accessible surface (`p9`, extended set P1–P14 per a11y-plan §1 "Surface set extension"), so the universal minimums SC 2.1.1 Keyboard / SC 2.4.3 Focus Order / SC 4.1.2 Name, Role, Value apply to whatever the brief renders (per a11y-plan §10 Standard+ invariants).
- Every surface/state change carries its own axe coverage in the SAME chunk, and fixtures must be POPULATED — an empty fixture renders nothing and the sweep passes by comparing nothing (per a11y-plan §3 "Harness wiring & conventions → Adding a surface"). Because this chunk creates a second render class (parsed brief vs genuinely-degraded notice), both classes need populated fixtures; the mock sentinels `__mockReject` / `__mockDelayMs` exist for the failure/in-flight states (same §3). Whether the existing `p9` spec already exercises a parsed, fully-populated brief is research's question.
- The six-section brief must satisfy heading hierarchy: one `h1` per surface, sequential `h2`/`h3`, no skipped levels (SC 1.3.1 + SC 2.4.6, per a11y-plan §7 "Heading hierarchy"). Replacing "_Interpretation pending_" with four populated sections is exactly where a level can be skipped.
- Any severity / degraded-state indicator in the brief must pair its color with a text label or icon — information never by color alone (SC 1.4.1, per a11y-plan §6 "State color tokens (not-color-alone)").
- New brief text (Timeline / Hypotheses / Investigation Steps / Evidence refs, incl. monospace id strings) must use token pairs meeting SC 1.4.3 4.5:1 normal text / 3:1 large text; `--color-text-tertiary` is only valid for large text (per a11y-plan §6 "Color contrast pairs").
- The report window's keyboard contract is fixed: `role="dialog"` fill variant, focus trap, Esc/✕ closes with cross-window focus restore to the findings window (per a11y-plan §5 "report-window"). If the fuller brief adds interactive controls (e.g. a retained "retry interpretation" affordance), they join that Tab order and must not nest reachable tab stops (per a11y-plan §11 Keyboard, incl. the grid-lite carve-out).
- A11y is a hard, non-deferrable merge gate: zero new WCAG AA violation tuples vs `baselines/a11y-violations-summary.json`, Lighthouse a11y ≥ 90, no "fix in follow-up" (per a11y-plan §9 CI Integration + §10 "Build / deploy failure conditions" + §11 CI).

## Patterns to follow
- Add/extend the axe spec alongside the render change in the same chunk, using the `p8`–`p14` specs as the template and `helpers/v02-fixtures.ts` (report payload fixture already enumerated there) for the populated brief (per a11y-plan §3 "Harness wiring & conventions").
- Drive the two states through the TauRPC IPC mock (`TauRPC__<router.path>` command shape) rather than real backend wiring; use `__mockReject` / `__mockDelayMs` for the genuinely-failed and in-flight interpretation states (per a11y-plan §3).
- Cheap suite-health check before trusting a green run: `npx playwright test --list` — a list-time import failure once silently disabled the whole suite (per a11y-plan §3).
- Semantic HTML first, ARIA second for the new brief sections (native headings/lists/`<table>`; ARIA only where HTML semantics are insufficient) (per a11y-plan §4 "Naming convention" + §2 agent-runnable invariants).
- If the brief's arrival is announced rather than statically rendered on open, the status pattern is `aria-live="polite"` for non-blocking completion, `assertive`/`role="alert"` only for errors (SC 4.1.3, per a11y-plan §7 "Live regions"). Whether the report surface today renders statically on open or updates in place is research's question.

## Anti-patterns to avoid
- NEVER convey the degraded-vs-complete distinction (or evidence severity) by color alone — text or icon supplement required (per a11y-plan §11 Visual + §6).
- NEVER audit an unpopulated fixture or claim conformance without machine-verifiable evidence (axe/Lighthouse/pa11y JSON); a vacuous pass over an empty brief is the specific failure mode §3 names (per a11y-plan §11 Strategy + §3).
- NEVER hide newly-rendered brief content from assistive tech (`aria-hidden="true"` / `display:none` on essential sections, or evidence ids exposed only visually) (per a11y-plan §11 Screen Reader).

## Contract bindings
- **A11y violation JSON → obs §6**: violations emit in the obs structured-log shape with `wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` / `remediation` / `tool` / `tool_result_id`, tagged `service.name="com.andromeda.pulse"` (per a11y-plan §3 "Structured violation JSON schema" + §9).
- **CI a11y gate → tests**: `npm run test:a11y` runs in the same `ci.yml` pipeline and reuses the tests' 5-command E2E harness (`boot` / `run` / `status` / `cleanup` / `logs`); the per-PR regression diff runs against `baselines/a11y-violations-summary.json` (per a11y-plan §3 CI integration + §9).
- **Contrast + severity tokens → design**: brief text and severity indicators bind to `--color-text-primary` / `--color-text-secondary` / `--color-accent` / `--color-feedback-success` pairs verbatim; no invented tokens (per a11y-plan §6 + §2 naming conventions).
- **Report-window focus order → layouts**: `role="dialog"`, Esc/✕, cross-window restore via first-party Tauri events (`report:closed`), not `focus-trap-react` (per a11y-plan §5 "Focus restoration").
