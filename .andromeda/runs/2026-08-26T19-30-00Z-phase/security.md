## Constraints
- **Real-id injection must stay inside the L4 argv prompt bound.** Per security-plan §Input Validation (L4 inference argv prompt row), the assembled `-p` operand is required to pass `validate_prompt_bounded` before the `Command` is built: ≤ `MAX_PROMPT_BYTES` (16384), NUL and remaining C0/C1 rejected with `\n`/`\r`/`\t` whitelisted, and **over-long must reject, never truncate** (the digest is skipped instead). Scope's [inferred] headroom bullet is the same requirement seen from the size side. Whether the id-injecting assembly path still flows through that single production caller after the change is research's question.
- **Prompt content sourced from telemetry must arrive already scrubbed.** §Threat Model Summary classifies OTLP attribute values as user-controlled content, and §Security Anti-Patterns → Code Patterns admits the one argv path *only* because the OTLP-derived substring is PII-scrubbed upstream (`Digest::scrubbed_clone`) — the bound is a shape/length control, explicitly **not** a confidentiality fix. Any NEW field carrying telemetry-derived text into the prompt (fingerprint strings, span-id-adjacent context, exception text) is therefore required to come from a scrubbed projection; whether the chosen real-id source already is one is research's question.
- **Any earlier-lifecycle L4Output persistence must land in the encrypted corpus substrate, pre-scrubbed.** §Data Protection → At rest → Persistent incident corpus requires cell-level AES-256-GCM with the OS-credential-store key and states that **no plaintext runtime state survives on disk**; §Security Anti-Patterns → Logging (uniform scrubber coverage) requires `security::scrubber::scrub_attribute` at every corpus write path. Deliverable A's "whatever earlier-lifecycle persistence the fix requires" is squarely inside both mandates. A new plaintext sidecar file for parsed L4Output would violate §Data Protection directly.
- **The report surface crossing the TauRPC bridge is a validated boundary.** §Input Validation (TauRPC row) requires a `serde`-deserialized, validated argument struct per procedure, and §API Security (TauRPC capability authorization) requires the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` as the per-procedure enforcement — capability JSON does **not** enumerate procedures. Any signature/procedure change on `incidents.get_report` or a new retrieval procedure inherits both.
- **Errors from the degraded/retry path must be sanitized at the bridge.** §Error Handling requires `Result<T, AppError>` with `Validation { field, reason }` / `Internal { message }` as a sanitized one-liner, full chain staying in the internal log; §Security Anti-Patterns → Logging bans stack traces, Rust struct names, file paths and library versions in `AppError::Internal` content reaching the webview. A "genuinely failed interpretation" notice is exactly this class.
- **No prompt text, excerpt, or offending substring in logs.** §Logging & Monitoring (What NEVER to log) plus §Security Anti-Patterns → Logging require raw OTLP attribute values and payload content stay out of the log, and §Input Validation (L4-argv row) requires an argv rejection to surface only a bounded category on `interpretation.inference.error`. New leaves around the degraded-mode branch and id injection inherit this.
- **Full product-consumed filesystem paths are basename-only.** §Logging & Monitoring + §Security Anti-Patterns → Logging require basename plus the env-var NAME only, with the two pre-existing boot records (`app.boot.tracing.init` `log_dir`, `app.boot.pid` `path`) recorded as a *carried* exception owned elsewhere — relevant because open question 1 works against a preserved out-of-tree data dir (`D:/dev/evidence/pulse-l4run-171923/`); that path must not become a new logged full path.

## Patterns to follow
- **`scrubbed_clone` pre-write projection** — the established shape at corpus persist paths (`BaselineState::scrubbed_clone`, `StormStateSnapshot::scrubbed_clone`, `Digest::scrubbed_clone`) per §Security Anti-Patterns → Logging (MEASURED reality); a new L4Output persist path should follow it rather than inventing a site-local scrub.
- **Bounded-parse helper returning a named rejection category** — `validate_prompt_bounded` → `PromptRejection::label()` as the only thing reaching the log, per §Input Validation (L4-argv row). The same shape applies to any new bound on injected id counts/lengths.
- **Choke-point vs push-site scrub placement** — §Security Anti-Patterns → Logging documents both (and a third, joined-form, shape for `metrics_points.labels`); if the real-id source fans out to multiple consumers, the choke-point form is the precedent (`extract_service_name` feeding three consumers).
- **`AppError` conversion at the bridge via `From<thiserror::Error>`** with `Validation { field, reason }` for rejections, per §Error Handling — never `anyhow::Error` across TauRPC (§Security Anti-Patterns → Code Patterns).
- **Corpus key custody is OS-credential-store primary with opt-in passphrase fallback** (§Secret Management → Runtime) — the substrate open question 1 probes; the key is per-user-per-machine with no prod/dev separation, and `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` is secret-class.

## Anti-patterns to avoid
- **NEVER widen the argv exception.** §Security Anti-Patterns → Code Patterns bans `Command::new(...).arg(user_input)` on OTLP-, MCP- or workspace-detector-sourced strings and admits exactly ONE product path through `validate_prompt_bounded`; injecting real ids must not add a second unbounded argv operand nor bypass the existing guard.
- **NEVER add a TauRPC procedure without its `EXPECTED_PROCEDURES` pin AND a validated argument struct** (§Security Anti-Patterns → API) — capability JSON will not catch it; `xtask capability-drift` is the enforcement.
- **NEVER log raw evidence/interpretation payload content** — model-generated Timeline/Hypotheses text is OTLP-derived by construction, and §Security Anti-Patterns → Logging bans logging raw OTLP attribute values, content payloads, and DuckDB query parameter values (identifier + parameter count instead).

## Contract bindings
- **PII scrubbing ↔ obs §PII Scrubbing + tests fixtures.** The verification legs read a preserved real-telemetry corpus + a 386k-line real log; per the focus guide's cross-domain binding and §Security Anti-Patterns → Logging, no real telemetry payload content may become a committed test fixture, and the preserved evidence dir must stay out of the repo.
- **Argv bound ↔ obs `interpretation.prompt.assemble`.** The 16 KiB ceiling in §Input Validation was DERIVED from that leaf's recorded byte sizes (154 records, 5947..=6297 B); measuring post-injection headroom means reading the same leaf, so the obs schema is the measurement instrument for this domain's bound.
- **`span_events.exception_type` exclusion ↔ evidence-id sourcing.** §Security Anti-Patterns → Logging records `exception_type` as a deliberate non-scrubbed class identifier while `exception_message` IS scrubbed — if fingerprints are derived from or carry either, the split constrains what may be copied into the prompt.
- **CI security gate ↔ tests §CI Integration.** The `cargo deny` gate runs as a job in the one workflow per §Dependency Security → CI integration; the PREREQ discharge is recorded in this chunk's report.
