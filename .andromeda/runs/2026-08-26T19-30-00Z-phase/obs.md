## Constraints
- Any log target this chunk adds or whose field set it widens in the `interpretation.*` family requires its OWN exact §8 allowlist leaf enumerating **every** field its emit site emits — obs-plan §8 (Default-deny posture, `interpretation.incident.created` entry) records that a bare `interpretation` key **exists in code** at `pulse-app/src/observability.rs:1934` in violation of the stated invariant, so an unregistered sibling *resolves* into a foreign field set (`model_profile`/`model_tier`/…) and renders `"<redacted>"` while a `for_target(...).is_some()` probe still passes. §8 enumerates leaves only for `interpretation.incident.created`, `interpretation.model.load`, `interpretation.model.load.error`, `interpretation.model.allow_root` — **whether `interpretation.prompt.assemble` / `interpretation.constrained.generate` / `interpretation.json.parse` already carry exact leaves (and whether their fields render unredacted) is research's question.**
- The real fingerprint / span ids injected into the prompt are OTLP-derived payload values: per obs-plan §8 (PII Scrubbing, data-classification row 1 — raw OTLP telemetry payloads, scrub-required) and §11 (Logs), raw attribute values must never reach the log; §8's `buffer` whitelist states the family rule as "never service / span / fingerprint identity". Instrumentation of the injection must therefore carry bounded counts/sizes (ref count, prompt bytes) rather than the id values. §6 admits `trace_id` / `span_id` only as W3C-hex correlation fields extracted at receiver entry — whether an injected id qualifies as that or as payload content is research's classification.
- Metric/label cardinality is bounded to enumerated values; no per-trace-ID, per-span-ID or per-fingerprint labels (per obs-plan §5 Metric label cardinality discipline; §11 Metrics).
- A state that is otherwise indistinguishable from a healthy one must be announced with a bounded diagnostic, once per occurrence/transition and never per record — the template §6's `warn` row applies to `app.boot.buffer.degraded`, `corpus.keychain.fallback`, `buffer.consumer.stalled`, `interpretation.model.allow_root`. A degraded verdict rendered over a clean parse is that class; §6 requires the genuine-failure vs. degraded distinction be readable from the log family (per obs-plan §6 Log levels mapping).
- Every emission on the changed path must satisfy the §6 required-field schema (`timestamp` / `level` / `target` / `message` / `fields`, plus the `service.name` / `service.version` / `deployment.environment` default subscriber fields), which obs-plan §3 (Log format JSON schema) states is verbatim-binding **from** the test harness contract — obs aligns to tests, not vice versa.
- Module-boundary errors stay logged at WARN/ERROR with an error *category*, not a stack trace or Rust struct names (per obs-plan §10 Standard+ invariants; §8 Vector 2) — a fix that stops `degraded_mode` from firing must not also silence the genuinely-failed interpretation path.
- Per-incident/per-generation emission is bounded, but per-evidence-ref or per-token emission is barred by the hot-path rule (per obs-plan §11 Telemetry Strategy + Logs). The observed 2-events-per-generation shape on `interpretation.constrained.generate` must be an intentional bounded shape; research confirms it.

## Patterns to follow
- **Exact-leaf + live guard**: register the leaf in `AllowList::production()` and guard it from `pulse-app/tests/` (never `observability.rs`'s own `mod tests`, dead under `[lib] test = false`), asserting exact-resolve, field-set equality in BOTH directions, and a fallback discriminator proving the bare-prefix set contains none of the fields — the `unit_observability_allowlist_l4_path_guard.rs` shape (per obs-plan §8, two-`interpretation.*`-leaves block).
- **Dual/triple restating-site rule**: a once-per-boot or once-per-transition target is stated at BOTH §6 (`warn` row) and §8; a field ridden on an existing tick is stated at all three of §1 / §5 / §8. A §8-only change leaves the sibling sites stale (per obs-plan §6 + §8; amendment precedents below).
- **"Otherwise indistinguishable" WARN template**: bounded static `reason` + `consequence` tokens plus numerics, once per transition, with the rationale recorded as what no other signal distinguishes (per obs-plan §6 `warn` row).
- **Identity-free boundary fields**: `*_basename`, `query_id` + `param_count`, `result_type` + `result_count`, `argument_digest` (hash, not content) — the §6 boundary-call wrapper table's shape for the TauRPC surface (`incidents.get_report`) constrained by §8's `ui-bridge` whitelist.
- **Aggregate-as-field on an existing heartbeat** rather than a new per-event target when the quantity is throughput-shaped (per obs-plan §5 tick-aggregated Counter rows).

## Anti-patterns to avoid
- Never log the assembled prompt body, the model's raw output text, or any raw OTLP attribute value / injected fingerprint / span-id value (per obs-plan §11 Logs; §8 Vector 1) — and never log MCP tool response bodies, which carry the same content (per §11 Project-specific).
- Never add an `interpretation.*` target without its own exact leaf, and never let a guard assert only that the target resolves — the bare-key breach makes a resolver-only probe pass vacuously (per obs-plan §8 `interpretation.incident.created` entry).
- Never emit at `info` per evidence ref / per parse attempt in the generation path (per obs-plan §11 Telemetry Strategy, Logs).
