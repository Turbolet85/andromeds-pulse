## Relevance
Relevant — the chunk changes the primary key of a table whose `metric_name` column the security plan names by name as a scrubbed client-controlled column, and whose PK collision is a *recorded* security decision; corpus-side rules are out of play (scope excludes corpus `pipeline_metrics`).

## Constraints
- The scrub on `metrics_points.metric_name` at the OTLP write boundary is a standing requirement, not an incidental behavior: security-plan §Security Anti-Patterns → Logging requires every client-controlled ring-buffer column a producer can reach to pass through the OTLP-field scrub before write. Any key-shape change must leave that scrub in place — resolving the collision by reverting the column to raw is named in that section as a rejected alternative.
- The discriminator that closes the collision must be **content-independent**. §Security Anti-Patterns → Logging records the uniform-redaction treatment decision and explicitly rejects "a collision-safe discriminator [that] mints a stable derived identifier of the secret" — a hash/suffix of the credential-shaped name is banned; a buffer-global ordinal is not that shape and does not trip this rule.
- If the label half lands this chunk, every persisted label value is an OTLP attribute value and must pass `scrub_attribute` before write per §Security Anti-Patterns → Logging (INTENDED posture: any attribute value crossing into storage or the log sink scrubs first), because §Data Protection → At rest — per medium requires the DuckDB ring buffer to stay unencrypted, making write-boundary redaction the only control. If the label half CARRIES, that CARRY must be minted carrying this mandate.
- §Security Anti-Patterns → Logging currently records the `metric_name` PK collision as an *accepted, LOUD* failure ("ERROR at `flush()`, never a silent one"). A key change that stops the batch from failing removes the behavior that clause asserts, so the plan body requires a matching amendment at that section (and its restating sites, §Threat Model Summary → Data classification sensitivity note and §Data Protection → At rest) per the APPLY-AS-MEASURED discipline the 2026-08-22 amendment established. The security consequence to record: two *distinct* credential-shaped names still redact to one placeholder, and after the ordinal both rows land indistinguishable — no new leak (redaction holds), but the conflation loses its only signal.
- Every read-back query and every fixture `INSERT` touched by the measurement must use `Connection::prepare` with `?` placeholders; §Input Validation (DuckDB query parameters row) and §Security Anti-Patterns → Input ban `format!`-interpolated SQL outright, and table/column names stay spec-fixed.
- Measurement and failure diagnostics must not echo raw OTLP-derived values: §Logging & Monitoring "What NEVER to log" and §Security Anti-Patterns → Logging forbid raw OTLP attribute values and DuckDB query-parameter values in the log sink (log query identifier + parameter count instead). Whether the existing `duckdb.append` ERROR path already echoes the colliding key tuple — i.e. the metric name — into `agent-latest.jsonl` is research's question.
- The chunk's folded PREREQ is a §Dependency Security → CI integration item: the standing `cargo audit` deferral requires the wrap between interval points to re-verify basis + overlap and to record `probe skipped per ratified interval (next: 37)` — never a silent skip — with the overlap signal `cargo deny check advisories` run and its eight owned upgradeable IDs left under a named owner, never ignore-listed.

## Patterns to follow
- Push-site scrub via `scrub_otlp_field` is the established shape for a client-controlled ring-buffer column; the `extract_service_name` choke-point variant is reserved for values with multiple downstream consumers (§Security Anti-Patterns → Logging). A new label/attributes column should follow the push-site form unless it feeds `triage` too.
- The scrub-coverage chunk's evidence shape is the precedent for this chunk's measure-first leg: RED-before / GREEN-after on the real OTLP path, a mutation check proving the pins discriminate, and a live wire run counting redactions plus zero canary occurrences (§Security Anti-Patterns → Logging, MEASURED-reality paragraph).
- Credential-shaped canaries used to force the redacted-name collision must be synthetic literals of the `provider_key` anchored-prefix + length-floor arm (§Security Anti-Patterns → Logging, eight-category catalog) — never real credentials, and never logged raw.
- Advisory findings carry visible, ID-scoped, owner-named dispositions; findings with a stated safe upgrade are never ignore-listed (§Dependency Security → CI integration).
- Only if the label half adds a TauRPC procedure (a response-shape change to an existing one does not): router registration **plus** an `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` **plus** a validated argument struct, per §API Security → TauRPC capability authorization.

## Anti-patterns to avoid
- NEVER make the redacted placeholder collision-safe by deriving it from the secret value (hash/suffix/prefix of the original metric name) — explicitly rejected in §Security Anti-Patterns → Logging.
- NEVER close the collision by dropping or bypassing the `metrics_points.metric_name` scrub — "leaving `metric_name` raw leaves the gap open" is the other rejected alternative in the same section.
- NEVER enable DuckDB at-rest encryption on the in-memory ring buffer while editing its DDL — §Security Anti-Patterns → Data Protection bans it (CVE-2025-64429); the ring buffer's unencrypted posture is deliberate.
