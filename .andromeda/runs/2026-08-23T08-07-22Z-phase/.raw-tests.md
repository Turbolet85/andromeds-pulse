# tests extract

## Relevance
Relevant — this chunk lands new in-crate `buffer` regression coverage, a runtime OTLP measurement leg, and a new fixture-producer, all of which the test plan governs directly.

## Constraints
- Standard tier mandates comprehensive unit depth with **all module boundaries tested** (per test-plan §2 "Test pyramid" Unit row). If the fix adds a public `buffer` boundary (a metrics ordinal allocator generalizing `reserve_log_seq_block`), that boundary requires a **direct** in-crate assertion, not transitive-only proof — §1's open trigger `buffer-log-seq-allocator-unit-coverage` is the standing record of exactly that gap shape being re-minted once already.
- Rust regression coverage for a **library** crate must be co-located `#[cfg(test)] mod tests { … }` inside the crate's `src/` (per test-plan §4 "Conventions → Test file location"). `buffer` is a library crate, so `crates/buffer/src/{schema,appender,state}.rs` are the mandated homes; the `pulse-app` `tests/*.rs` exception does not apply here.
- Fixture data must be self-bootstrapping — generated at test runtime via OTLP ingest or Rust builder factories, never pre-baked (per test-plan §7 "Self-bootstrapping requirement" and §1 trigger `agent-driven-discipline: Self-bootstrapping test data`). The scope's OTLP producer example is the sanctioned form; §3 "Bootstrap phases" item 6 requires a `MockMetricPoint` builder in `viz` — whether that factory already exists is research's question.
- The **standard gate set is unconditional** for every `/andromeda-phase` chunk: `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo nextest run --workspace --profile ci`, `cargo xtask capability-drift`, `cargo xtask capability-widening-check` (per test-plan §3 "Per-chunk gate discipline"). Webview gates drop out only when the Files-to-modify / New-files lists touch zero `pulse-app/ui/**` paths.
- Run-scope must match build-scope: narrow a `pulse-app` selection with `-E` under `--workspace`, never `-p` (per test-plan §3 `run` → "Test selection", measured 2026-08-15). A `-p buffer` invocation for the library crate is the documented precedent form, but the `--workspace --profile ci` run remains the gate of record.
- Every layer must emit a machine-parseable deterministic signal — exit code, structured stdout, or a jq-matchable log line — with no human-in-the-loop step and no flaky-retry budget (per test-plan §2 "Agent-runnable invariants", §1 trigger `agent-driven-discipline: No manual verification checkpoints`, §10 "Zero-flakiness budget"). A RED-then-GREEN narrative must therefore be readable from artifacts, not from prose.
- Integration-level reads go through an ephemeral in-memory DuckDB per test with per-test isolation via `tempfile::TempDir` (per test-plan §5 "Setup / teardown lifecycle" and §7 "Test data lifecycle").

## Patterns to follow
- The `log_records` identity pair is the named in-crate precedent (per test-plan §4 "What unit tests cover" → buffer bullet): the PK contract asserted through `information_schema.key_column_usage` **because a duplicate-INSERT probe is a documented hang on this build**, and the same-tick behavioural test run on a worker thread under a 30s `recv_timeout` so a hang fails rather than wedges. The scope's independently-derived "duplicate-INSERT is not an available measurement" finding converges with this; reuse the shape rather than re-deriving it.
- `appender::tests` is the established home for write-boundary pins, including the four-builder redaction fold (per test-plan §4 buffer bullet). A metrics collision pin belongs alongside them, and per the 2026-08-23 amendment the local bar is a **mutation check** — a pin that stays green when the mechanism is neutralized does not discriminate.
- `rstest` 0.26.1 `#[fixture]` builders plus per-crate factories (`MockArrowBatch` in `buffer`, `MockMetricPoint` in `viz`) are the sanctioned fixture composition (per test-plan §4 "Fixture pattern at unit level", §7 "Fixture library").
- The `ingest → buffer` and `buffer → viz` boundary rows define the end-to-end recipe: drive the live loopback receiver with a native `tonic` client, read back through `Connection::query_map` / `viz` aggregation (per test-plan §5 "Boundary types covered"). Mocking either end is banned (see below).
- The **Direct-binary smoke variant** is the accepted alternative form when a verification needs a fresh `ANDROMEDA_PULSE_DATA_DIR` plus a sustained real-OTLP load that neither `npx @tauri-apps/cli dev` nor the harness `run` verb can express (per test-plan §3 "Per-chunk gate discipline"). Note the tension flagged under Contract bindings: its stock assertion is *zero* ERROR lines, which the chunk's RED leg deliberately expects to violate.

## Anti-patterns to avoid
- NEVER pre-populate a test DB via `.sql` scripts or DB snapshots — all fixture rows generated at runtime (per test-plan §11 "Test Data"). This forecloses the tempting hand-written-INSERT proof of a PK collision, independently of the hang.
- NEVER mock DuckDB at integration level, and NEVER mock the OTLP receiver under test — live `tonic` against loopback `:4317` and an ephemeral in-memory DuckDB (per test-plan §11 "Integration" and §11 "Mocking").
- NEVER assert on raw OTLP protobuf bytes, and NEVER use `sleep(N)` for synchronization — assert decoded fields, and wait on an explicit signal such as a row-count readback or `health` poll (per test-plan §11 "Integration" and §11 "E2E").

## Contract bindings
- **tests ↔ obs (log format).** The RED evidence the scope expects is a `tracing::error!(target: "duckdb.append", …)` NDJSON line; the harness `logs` verb and the `jq 'select(.level == "ERROR") | .message'` recipe are the tests-side read, while obs owns the field schema (per test-plan §3 "Log format" → "Agent-parseable signals"). **Conflict to resolve in the plan:** §3's Direct-binary smoke variant asserts `0 ERROR` in `&lt;data_dir&gt;/logs/agent-latest.jsonl*`; a RED measurement that *requires* an ERROR line must scope which run/window that clean-log assertion applies to (GREEN leg only), or the two mandates contradict.
- **tests ↔ obs (status endpoint).** Ingest confirmation for the end-to-end leg reads `subsystems.buffer.rows_ingested` from the `health` shape, with the ports-ready check as the boot gate (per test-plan §3 "Status endpoint shape" → "Agent reads"). Metric-point ingestion counting toward that field is an obs/arch contract question, not a tests one.
- **tests ↔ arch/buffer (three DDL representations).** §5's `buffer → viz` boundary row is where the `viz` fixture's schema participates in the tested surface; the scope names three `metrics_points` DDL sites, of which only the two `schema.rs` forms are named as guarded by a constants-match test. Whether any test guards the third (`crates/viz/src/query.rs`) against drift is research's question.
- **tests ↔ capability matrix (CI).** `cargo xtask verify:capability-matrix` runs as a CI step after `capability-drift` and fails on dangling ids/paths/anchors; a capability added in a chunk must extend the matrix JSON in that same chunk (per test-plan §9 "Capability verification matrix" + amendment 2026-06-10). Given the scope's no-claim posture, the binding's practical effect is that nothing may be minted silently.

## Acceptance criteria contributions
- (tests) The full standard gate set passes — `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo nextest run --workspace --profile ci`, `cargo xtask capability-drift`, `cargo xtask capability-widening-check` — with webview gates included unless zero `pulse-app/ui/**` paths are touched (per test-plan §3 Per-chunk gate discipline).
- (tests) New `buffer` regression coverage lands **in-crate** under `crates/buffer/src/`, asserting the `metrics_points` key contract via `information_schema.key_column_usage` rather than a duplicate-`INSERT` probe, and exercising the appender path under an explicit timeout so a hang fails rather than wedges (per test-plan §4 What unit tests cover → buffer bullet).
- (tests) Any new public `buffer` boundary introduced by the fix carries a **direct** in-crate assertion of its own contract (monotonicity / block width / one `fetch_add` per batch, for an ordinal allocator); if it ships proven only transitively, a pending coverage trigger must be recorded in the same chunk (per test-plan §2 pyramid Unit row + §1 `buffer-log-seq-allocator-unit-coverage`).
- (tests) Both colliding pairs are exercised with data generated at runtime over the live OTLP receiver or via builder factories — no pre-baked DB, no `.sql` seeding — and the pass/fail signal is exit-code or jq-extractable, not narrative (per test-plan §7 Self-bootstrapping requirement + §1 `agent-driven-discipline` triggers).
