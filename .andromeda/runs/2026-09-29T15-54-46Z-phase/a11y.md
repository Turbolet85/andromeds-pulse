# a11y extract

## Relevance
partial — the chunk adds no UI surface, but it moves the a11y CI gate: `cargo xtask test:a11y` (the "a11y 10 min" slice of the measured ubuntu chain) and the steps it needs before and after it sit inside the serial `lint-test-build` chain that A splits into parallel jobs.

## Constraints
- The a11y CI gate is a hard, fail-fast merge block. The PR fails on an axe-core critical/serious WCAG violation, a Lighthouse a11y score < 90, a focus-order test failure, or a contrast token mismatch. Whichever job runs `test:a11y` after the split has to keep all four blocking (per a11y-plan §3 CI integration + §10 Build / deploy failure conditions).
- Per-PR regression detection is mandatory at Standard tier. The base-branch `a11y-violations-base` download has to run before `test:a11y` in the SAME job, and `regression-set.json` has to be emitted from it (per a11y-plan §3 CI integration "Per-PR regression detection" + §10 Standard+ invariants). The download's name is `a11y-violations-base`, but the upload is named `a11y-violations-${{ runner.os }}`. Whether the baseline resolves at all today is a question for research. The split must not break it, and it does not have to fix it.
- The structured violation JSON (the `a11y-*.json*` logs under `ANDROMEDA_PULSE_DATA_DIR/logs/`, the contrast report and the Playwright report) must stay machine-verifiable, uploaded CI artifacts, including on failure (per a11y-plan §3 Structured violation JSON schema + §9 Per-pipeline-stage a11y artifacts). A new job that runs `test:a11y` carries its own `if: always()` uploads and the env var those paths resolve through.
- The a11y harness runs on tests' build/harness contract (per a11y-plan §3 Focus management test harness "Contract binding" + §9 Pipeline integration). In the serial chain today, `test:a11y` depends on the steps before it: the Vite `dist` build, the Playwright chromium install and `npm ci`. Research should say whether it also needs a compiled xtask or other workspace artifacts from earlier steps. A split job has to rebuild or hand over exactly those, and no more.
- Performance budget: axe-core < 30 s per surface, Lighthouse < 15 s per URL, and the whole a11y run plus tests' E2E < 10 min (per a11y-plan §10 Performance budget per a11y CI run). The measured ~10 min a11y slice sits at that ceiling. The split should not push the a11y job past it; a cold per-job cache or setup is the obvious risk.
- Eslint-plugin-jsx-a11y is the Lint-stage a11y artifact (per a11y-plan §9 Per-pipeline-stage a11y artifacts + §3 A11y testing tool pick). Research should find out whether any current CI step runs it, and which one (typecheck / npm build / none). If one does, it survives the split.
- The plan does not name the OS legs that run `test:a11y`. It requires the gate on the desktop-webview for every PR (per a11y-plan §3 CI integration). Today it runs on all three matrix legs. Dropping any leg's run has to be argued as a true duplicate, under the scope's Boundaries.

## Patterns to follow
- One command owns the whole chain. `cargo xtask test:a11y` runs axe, Lighthouse, pa11y, colorjs.io, the aggregator and the regression check (per a11y-plan §3 CI integration). Relocate that single verb into its job rather than splitting its sub-tools across jobs.
- Artifact names are keyed per OS (`a11y-violations-${{ runner.os }}` / `playwright-a11y-report-${{ runner.os }}`), which matches the per-surface/per-run artifact model (per a11y-plan §9). If the split produces several a11y-bearing jobs on one OS, the names must stay unique, so no upload overwrites another.
- The harness mocks Tauri IPC and serves the static SPA (`helpers/mock-tauri.ts`, `helpers/static-server.mjs`) (per a11y-plan §3 Harness wiring & conventions). By that contract the a11y job needs the built UI `dist`, not a running `pulse-app` or bound `4317`/`4318` ports. Whether the xtask verb holds to that at HEAD is for research. If it does, the a11y gate is also a candidate for the WSL pre-push check (D) that fits the host constraint.
- A cheap health probe for the suite is `npx playwright test --list` (per a11y-plan §3 Harness wiring & conventions). A relocated job, or a pre-push leg, can use it to catch a list-time import failure that would otherwise disable the suite without any error.

## Anti-patterns to avoid
- NEVER make the a11y gate soft. No `continue-on-error`, no retry-once wrapper, no "non-blocking" marking on the relocated `test:a11y` step (per a11y-plan §11 CI "NEVER skip a11y on CI failure" + §11 SLO "NEVER use retry-once policy" / "NEVER define soft a11y SLO").
- NEVER drop the per-PR diff when the job moves (per a11y-plan §11 SLO "NEVER skip per-PR diff (regression detection) at Standard+ tier").
- NEVER leave lint-only a11y behind as the surviving gate: the runtime axe/pa11y/Lighthouse gate has to stay (per a11y-plan §11 CI "NEVER ship lint-only a11y without runtime axe-core / pa11y / Lighthouse").

## Contract bindings
- a11y ↔ tests: the CI a11y gate runs in the same `ci.yml` pipeline as tests' E2E gates and reuses tests' 5-command harness contract (per a11y-plan §3 CI integration + §9 Pipeline integration). The job split changes this binding's shape (same workflow, possibly a different job), so it needs to be restated in test-plan §9 at wrap.
- a11y ↔ obs: the violation JSON lands in `ANDROMEDA_PULSE_DATA_DIR/logs/` in obs's structured format (per a11y-plan §3 Structured violation JSON schema + §9 CI-specific resource attributes). Each new job that runs `test:a11y` needs the `Export ANDROMEDA_PULSE_DATA_DIR` step, or the artifact paths resolve to nothing, and `if-no-files-found: ignore` would hide that.

## Acceptance criteria contributions
- After the split, every PR round runs `cargo xtask test:a11y` as a blocking step, with no `continue-on-error` or retry. A deliberately introduced violation (or reading the step's exit wiring) turns the round red (per a11y-plan §3 CI integration + §11 CI).
- In the job that runs `test:a11y`, the PR-only `a11y-violations-base` download comes before it, and the violations summary, `regression-set.json`, contrast report and Playwright report are uploaded `if: always()` under names unique across jobs. The first post-split run's artifact list shows them populated, not skipped by `if-no-files-found: ignore` (per a11y-plan §3 CI integration "Per-PR regression detection" + §9 Per-pipeline-stage a11y artifacts).
- The a11y job's wall time on the first completed post-split run is read and reported against the §10 budget (a11y + E2E < 10 min). A regression past the pre-split ~10 min is recorded, not hidden (per a11y-plan §10 Performance budget per a11y CI run).
- Any change to which matrix legs run `test:a11y` is argued in the chunk record as a true duplicate, with a stated reason, never as a cost cut (per a11y-plan §3 CI integration + §11 CI "NEVER skip a11y").
