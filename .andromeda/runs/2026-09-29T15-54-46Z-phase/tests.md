## Constraints
- Every build-failure condition in test-plan §9 "Build failure conditions" must still fire after the split: any unit/integration/E2E test failure, the Linux boot-smoke harness cycle failing (`boot` non-zero, `status` not `running-healthy`, `cleanup` emitting any non-`clean` token), coverage below 75 % line / 70 % branch / 85 % function, a flaky test, clippy/fmt/`cargo deny check` bans violations. Splitting the ubuntu leg into parallel jobs changes where each gate runs, never whether it can fail the round (per test-plan §9 Build failure conditions; §10 Build failure conditions).
- The Linux boot smoke stays GATING: one `xvfb-run` wraps `boot` → `status` → `cleanup`, after the Tauri/WebKitGTK/dbus/xvfb library install, and the three invocations share the `ANDROMEDA_PULSE_DATA_DIR` that every job exports to `$GITHUB_ENV` in a step right after harden-runner. A new job that hosts the boot smoke, or any other `ANDROMEDA_PULSE_DATA_DIR` consumer, inherits that export order. `continue-on-error` must not come back (per test-plan §9 Pipeline structure → Boot smoke (harness) row).
- The self-lint guards `workflow_env_references_no_step_only_context` and `data_dir_export_precedes_every_consumer` pin the workflow's env shape (`runner.*` is unavailable in workflow- and job-level `env:`). test-plan §9 requires every new job to satisfy them. Whether their current implementation walks every job, or assumes the old three-job layout, is research's question (per test-plan §9 Boot smoke (harness) row).
- The coverage measure keeps its thresholds and its TEMPORARY `xtask/` exclusion via `COVERAGE_IGNORE_FILENAME_REGEX`. A cache or job restructure must not move the threshold or widen the exclusion (per test-plan §10 Coverage thresholds / Cumulative across workspace; §9 Coverage report row).
- CI tests run parallel and without retries. A job split must not introduce `--test-threads=1`, a retry policy, or an auto-rerun of a failed job as a way to reach green (per test-plan §11 CI; §11 Quality; §10 Zero-flakiness budget).
- The dedup claim (scope §C) has to respect §3's scope-matching rule: `-p`-narrowed nextest selections are not artifact-compatible with a `--workspace` build (measured link failures). So "reuse the build from step X" is only a true dedup when the reused step's cargo scope, profile and feature set match. Whether `test` and `nextest` in ci.yml compile the same unit graph is research's question (per test-plan §3 `run` → "Narrow a `pulse-app` run with `--filter-expr` / `-E` under `--workspace`, not with `-p`").
- `capability-drift` runs after every command that can regenerate `pulse-app/ui/src/bindings/index.ts`, including `nextest --workspace` and any default-features cargo run. In a parallel layout, the job that hosts `capability-drift` / `check:staged-artifacts` must itself follow that ordering, or read the staged copy, which the shipped staged assertion does (per test-plan §3 Per-chunk gate discipline, capability-drift ordering paragraph).

## Patterns to follow
- The 5-command harness is the home for verbs: `scripts/agent-run.{sh,ps1}` verbs plus `cargo xtask …` subcommands, with exit codes as evidence and one bounded verdict on stdout. A local WSL pre-push check should follow that form (a bounded verdict and a meaningful exit code), not be an ad-hoc script with free-text output (per test-plan §3 5-command implementation; §2 Agent-runnable invariants).
- The three-arm exit contract: 0 green · 1 findings/red · 2 cannot-evaluate. `check:npm-supply-chain`, `check:staged-artifacts`, `harness:status` and the scenario smokes all use it. When WSL, the distro or the toolchain is absent, the pre-push verb should report cannot-evaluate, never green (per test-plan §3 status / Per-chunk gate discipline; §9 Supply chain row).
- The scenario-leg registration shape: `smoke:gap-resume` · `smoke:external-resolve` · `smoke:hue-shift` are each a named `cargo xtask` subcommand, dev-host only, not CI-wired and not in the standard gate set. The scope §E CARRY needs these xtask registrations to exist so wrap's arch amendment describes something real (per test-plan §3 Per-chunk gate discipline, smoke paragraphs).
- The boot verb's pre-build split: `cargo build --bin pulse-app --release` then `cargo build -p xtask` BEFORE the timed readiness window, riding the cargo cache. The release build it produces is the natural candidate the "release vs boot binary" dedup (scope §C) must reconcile with (per test-plan §3 `boot` → Command body / Timeout; §9 Boot smoke row, Cache column).

## Anti-patterns to avoid
- NEVER lower a coverage threshold, drop a gate, or make a gate non-gating to cut wall time (per test-plan §11 CI "NEVER lower coverage threshold to pass build"; §11 Quality "NEVER ship release with known test failures — all gates must be green").
- NEVER reference a third-party action by floating tag in a new or split job, including any new cache or artifact-transfer action (`actions/upload-artifact` / `download-artifact`) introduced to share build outputs between parallel jobs. Pin by 40-char SHA (per test-plan §11 CI).
- NEVER let a moved gate pass vacuously. A leg that skips clean when its prerequisite is absent (as the webview-drive leg does without `msedgedriver`) must show that it RAN, not just exit 0. The same applies to the pre-push check's WSL-absent path and to any gate relocated into a job lacking its system deps (per test-plan §9 E2E tests row; §3 Direct-binary smoke variant, vacuous-pass hazard).

## Contract bindings
- tests ↔ security: every new job starts with `step-security/harden-runner`, workflow-level `permissions: contents: read` holds, and `cargo deny check bans` (the tonic canary) stays a CI build-failure condition in whichever job it lands (test-plan §9 Build failure conditions / Cargo deny enforcement ↔ security-plan §Dependency Security; scope Boundaries).
- tests ↔ obs: the boot smoke's `status` verdict derives from the obs log family (`agent-latest.jsonl*`) and the pidfile via `cargo xtask harness:status`. A job split must keep `ANDROMEDA_PULSE_{DATA_DIR,PIDFILE,LOGFILE}` threading intact (test-plan §3 status / logs ↔ obs-plan §3 Log file location). The CI perf-budget gate's vacuousness is obs-owned and stays out of scope (scope Boundaries).
- tests ↔ a11y: `cargo xtask test:a11y` runs inside CI with Playwright chromium installed before it, plus `npm ci` + `npm run build` (the harness serves `ui/dist`) and a base-branch `a11y-violations-summary.json` download on PRs. If it moves to its own job, that job carries all of these (test-plan §9 A11y suite row ↔ a11y-plan §Bootstrap).
