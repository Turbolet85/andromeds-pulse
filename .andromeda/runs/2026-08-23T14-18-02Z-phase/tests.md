# tests extract

## Relevance
Relevant — this chunk IS test-domain work (the headful E2E leg, its stages, and its gate evidence).

## Constraints
- Headful GUI automation is permitted **only** in the agent-driven form: the verdict must come from an exit code plus the app's own obs-log record, never from a human or a screenshot; Playwright/CDP is recorded as UNADOPTED (per test-plan.md §2 Agent-runnable invariants). A staged leg whose stages "did not throw" fails this — each stage needs a signal a machine reads.
- The E2E driver stack is fixed and non-negotiable for this surface: `@crabnebula/tauri-driver` 2.x + `webdriverio` 9.x invoked by `cargo xtask webview-drive`, with **no** `mocha` / `@wdio/*` runner; the `.mjs` presses, the Rust xtask owns assertions and reads the obs log (per test-plan.md §6 Drivers per surface). Adding stages must not introduce a test-runner dependency.
- `msedgedriver` resolves from `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH`; **unset ⇒ clean SKIP with exit 0** (per test-plan.md §6 Drivers per surface). Consequence for this chunk's gate evidence: a green exit code alone does not prove the leg drove a window — the chunk's evidence of record must be the run's own artifacts, mirroring the direct-binary rule that `agent-run.sh status` exits 0 against a dead system (per test-plan.md §3 Per-chunk gate discipline → Direct-binary smoke variant).
- The unconditional standard gate set applies to every chunk plan's `## Test Commands`, and the webview gates (`npm run lint` / `typecheck` / `test --prefix pulse-app/ui`) are excluded only when zero `pulse-app/ui/**` paths are touched (per test-plan.md §3 Per-chunk gate discipline). This chunk names `pulse-app/ui/tests-e2e/webview-drive.mjs`, so the webview gates fire; whether the ui lint/typecheck configs already cover `tests-e2e/**` is research's question.
- Synchronization must be an explicit signal with a bounded wait — status/health polling at a fixed interval up to a stated timeout, or a channel/record event with a timeout (per test-plan.md §3 `boot` readiness + §6 Scenario P1 steps 4–6, §6 Scenario P6 step 4). Never a fixed sleep (§11 E2E).
- Fixture data must self-bootstrap at runtime through the live receiver or runtime builders — no pre-baked DB, no `.sql`, no production telemetry dump (per test-plan.md §7 Self-bootstrapping requirement, §11 Test Data). A storm-stage injector must therefore generate its load at run time; note §1 `test-data-bootstrap-factories-unimplemented` records `MockTraceSpan` / `MockArrowBatch` / `MockMetricPoint` as specified-but-unimplemented, so a new injector must not be planned as depending on them.
- Load-shaped assertions have their own home: the four-profile suite is the release/tag gate under the `load-profiles` nextest profile, `perf_slo_10k_spans.rs` is the per-PR gate, and `#[ignore]` stays reserved for flake quarantine (per test-plan.md §10 Load profiles). The "storm" stage here is an incident-creation trigger, not a throughput budget — it must not silently become one.
- Zero flakiness is a budget, not a guideline: one flake ⇒ immediate quarantine + root cause, never a retry policy (per test-plan.md §10 Quality Gates, §11 Quality). A seven-stage headful leg is the highest flake-risk surface in the suite; bounded polls and per-stage timeouts are how it stays inside this budget.

## Patterns to follow
- **Assertion-ownership split** (per test-plan.md §6 Drivers per surface): the `.mjs` performs the interaction; the Rust caller in `xtask` holds every assertion and the verdict. Extending to stages should preserve this split rather than moving assertions into JS.
- **Press-then-read-your-own-record** (per test-plan.md §6 Scenario P5 Status): the discharged leg is recorded as pressing a production control and asserting an obs record family with *exact field leaves* (`layout_mode_from` / `layout_mode_to`), backed by a discriminating RED arm. Each new stage should bind to a named record family with its exact leaves, on the same shape.
- **Ingest-confirmation pattern** (per test-plan.md §3 `boot` readiness + §6 Scenario P1): poll the status payload on an interval to a deadline and use `subsystems.buffer.rows_ingested` incrementing as the telemetry-arrival signal — the plan's canonical answer for "did the data land" without sleeping.
- **Real-time push assertion shape** (per test-plan.md §6 Scenario P6): subscribe → trigger ingest → await event under timeout → decode → assert schema and row count. Whether this chunk's push stage asserts the channel directly or its DOM/obs consequence is the observable-binding question research owns.
- **Direct-binary run form** (per test-plan.md §3 Per-chunk gate discipline → Direct-binary smoke variant): fresh `ANDROMEDA_PULSE_DATA_DIR`, env-gated mode, load seeded over the real receiver, assertions from the run's own `agent-latest.jsonl*` artifacts, shutdown by specific pid with `:4317`/`:4318` confirmed released. The 0-`app.panic.fatal` / 0-`ERROR` clause binds the GREEN leg only.
- **Colocated Rust unit tests for harness code** (per test-plan.md §4 Conventions → Test file location): `xtask` helpers take `#[cfg(test)] mod tests` in-crate; `pulse-app` is the exception whose probes live in `pulse-app/tests/*.rs`. Narrow a `pulse-app` selection with `-E` **under `--workspace`**, not `-p` (per test-plan.md §3 `run`).

## Anti-patterns to avoid
- NEVER assert by pixel inspection, visual diff, or any screenshot a human approves — canvas pixel inspection is explicitly out of scope, so a "Traces render" assertion must resolve to DOM or an obs record, not to pixels (per test-plan.md §11 E2E + §11 Universal, §6 Drivers per surface).
- NEVER use `sleep(N)` for synchronization anywhere in the staged path (per test-plan.md §11 E2E).
- NEVER add a retry-once / auto-retry policy to stabilize the leg, and NEVER land `#[ignore]` without a tracked reason (per test-plan.md §11 Quality, §10 Zero-flakiness budget).

## Contract bindings
- **tests ↔ obs (verdict channel):** the harness `logs` verb and every xtask assertion read JSON-lines `tracing` output; §3 Log format binds to obs-plan's NDJSON schema and required fields, and §3 Status endpoint binds to the obs status shape (per test-plan.md §3 Log format / Status endpoint shape). The chunk's own note that a bare parent allowlist key redacts every label is the operative risk: any newly asserted observable needs its exact allowlist leaf declared on the obs side before the tests side can assert it. Whether the records the three acceptance assertions need are already emitted **with the needed leaves** is research's question.
- **tests ↔ obs (perf authority):** no test may assert an fps number; the asserted frame budget is obs-plan §10's ms-form `metric.webgpu.frame_duration_ms` p99 ≤ 33 ms (per test-plan.md §10 frame-budget note). Relevant if any stage is tempted to assert render smoothness.
- **tests ↔ security (harness env var):** `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` is carved out of the product-binary canonicalize+confine ban as a harness/xtask-only tool-locator var, guarded instead by trim + `is_file()` + clean skip, with the resolved value never logged (per test-plan.md §1 Coverage-scope → Path canonicalization row + §1 pending trigger `webview-drive-msedgedriver-resolver-unit-coverage`). Making the var fire in the plan's Test Commands must not widen that carve-out.
- **tests ↔ CI:** §9's E2E stage names `cargo xtask webview-drive` and records that the leg is **not wired into any workflow**, the runner-side prerequisite being a matched `msedgedriver` exposed via that env var (per test-plan.md §9 CI Integration). This chunk's boundaries exclude CI wiring, so the leg remains dev-host-only unless the plan says otherwise.
- **tests ↔ tests (CARRY #10 owner):** test-plan.md §1 carries `mcp-incident-read-back-cross-process-coverage` as an open pending trigger and §6 Scenario P3 carries the matching Current-residual line — that trigger is the named owner of the re-pinned MCP cross-process CARRY. Whether the code has since gained a committed subprocess content assertion (which would retire it) is research's question.

## Acceptance criteria contributions
- (tests) The unconditional standard gate set passes, **including** the three `pulse-app/ui` webview gates, since the chunk's file list touches `pulse-app/ui/**` (per test-plan.md §3 Per-chunk gate discipline).
- (tests) Every stage of the leg fails the run when its observable is absent, and each assertion binds to a named observable the driver reads — an obs-log record with its exact allowlist leaf, or a DOM read — with the verdict owned by the Rust caller, not by the press returning (per test-plan.md §6 Drivers per surface + §2 Agent-runnable invariants).
- (tests) Gate evidence comes from a run that actually drove the window: because an unset `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` yields a clean SKIP at exit 0, the chunk records the run's own artifacts (obs records, clean shutdown by specific pid, ports released) rather than the exit code alone (per test-plan.md §6 Drivers per surface + §3 Direct-binary smoke variant).
- (tests) All waits in the staged path are bounded polls on explicit signals with stated timeouts — zero `sleep(N)` — and new Rust helpers added to `xtask` carry colocated `#[cfg(test)]` unit tests, with any `pulse-app` selection run under `--workspace` (per test-plan.md §11 E2E + §4 Conventions + §3 `run`).
