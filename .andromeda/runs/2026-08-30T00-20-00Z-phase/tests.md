## Constraints
- The chunk's `## Test Commands` MUST list the full unconditional standard gate set, and because it touches `pulse-app/ui/**` the three webview gates (`npm run lint` / `typecheck` / `test --prefix pulse-app/ui`) are NOT excludable, with `cargo xtask capability-drift` LAST (per test-plan §3 Per-chunk gate discipline).
- Any command added to the unconditional standard gate set must define a verdict for every arm including the nothing-to-judge case — the `check:ingest-progress` NEUTRAL arm is explicitly "what makes it safe unconditionally"; a leg that cannot satisfy that is registered explicitly OUTSIDE the gate set as a scenario leg, as `smoke:gap-resume` and `smoke:external-resolve` are (per test-plan §3 Per-chunk gate discipline).
- The gate must be agent-runnable: machine-parseable output (exit code + structured stdout/JSON/log line), deterministic, no human-in-loop verification of findings (per test-plan §2 Agent-runnable invariants; §1 coverage trigger `agent-driven-discipline: No manual verification checkpoints`).
- Designed-red / observed signals stay separated from pass/fail, and each arm carries its OWN precondition that no other arm may borrow — a run lacking its evidence reports INCONCLUSIVE, never a vacuous PASS (per test-plan §3 Per-chunk gate discipline, the three-arm `smoke:gap-resume` rule). This is the tests-side form of the two-invocation lesson the scope cites.
- A supply-chain gate that fails must be a **build failure condition**, joining the Rust-side `cargo deny check` clause rather than being advisory-only; and any stage that runs in CI must appear in the §9 pipeline table — an unlisted stage reads as "not CI-wired" (per test-plan §9 Pipeline structure + Build failure conditions; the A11y-suite MEASURED note records that exact failure mode).
- Zero-flakiness budget: no retry-once, no auto-retry, quarantine-and-root-cause on first flake (per test-plan §10 Zero-flakiness budget). A gate whose verdict depends on a remote advisory feed is a flake vector; §11 Universal also bans real network calls without mocks in tests — whether that ban is read as scoping to test bodies rather than supply-chain gates is a research/plan question this chunk must settle explicitly, not silently.

## Patterns to follow
- **Plain named `run:` step in ci.yml's `supply-chain` job** — the shipped precedent for a supply-chain assertion is the "Cranelift-only WASM backend assertion (test-plan §9)" step (grep + explicit `exit 1`), landed at chunk `2026-08-29-advisory-backlog`; the plan records that a plain `run:` step carries no SHA-pin obligation and that no xtask covers it (per test-plan §9 Cranelift-only WASM enforcement). Whether that `supply-chain` job exists at HEAD and what else it holds is research's question.
- **xtask verb delegating to an npm script** — `cargo xtask test:a11y` → `npm run test:a11y --prefix pulse-app/ui`, with its own row in the §9 pipeline table, is the shipped shape for wrapping npm-side tooling behind a project-precedent local invocation (per test-plan §9 A11y suite row). This is the closest existing model for the scope's `[inferred]` xtask-vs-npm-script decision.
- **Documented verdict-arm set for a new xtask gate** — `check:ingest-progress`'s four named arms and `smoke:gap-resume`'s per-arm preconditions are the required documentation shape for any new gate command (per test-plan §3 Per-chunk gate discipline).
- **Pin the new boundary in-crate** — xtask parse/verdict boundaries get co-located `#[cfg(test)] mod tests` pins (per test-plan §4 Conventions → Test file location). §1's recurring pending-trigger class (`webview-drive-msedgedriver-resolver-unit-coverage`, and `inject-demo-arg-parse-unit-coverage` before its discharge) is exactly what happens when a new xtask surface ships live-exercised only.

## Anti-patterns to avoid
- NEVER reference a third-party GitHub Action by floating tag — pin by 40-char commit SHA (per test-plan §11 CI). Applies if the npm scan arrives as an action rather than a `run:` step.
- NEVER add a retry-once policy or tolerate a flaking gate to keep CI green (per test-plan §11 CI + §11 Quality; §10 Zero-flakiness budget).
- NEVER weaken, remove, or threshold-lower a gate to obtain a pass — the plan's standing form of this is "NEVER lower coverage threshold to pass build" plus the arm-A never-weaken/never-`--expect-absent` instruction (per test-plan §11 CI; §3 Per-chunk gate discipline).
