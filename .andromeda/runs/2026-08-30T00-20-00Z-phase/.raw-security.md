## Constraints
- The npm channel at `pulse-app/ui` must gain advisory/license/ban scanning, not version bumps alone: security-plan §Dependency Security → CI integration (the MEASURED 2026-08-23 entry) records that `cargo audit` / `cargo deny` / `cargo-auditable` all stop at the Rust boundary and `ci.yml` runs `npm ci` but no `npm audit`, and names the owning route entry — this chunk is that owner. That entry also requires the scan reach the lockfile-delivered native binary shipped through an npm package, which no cargo-side gate inspects.
- **Visible-disposition rule, mandatory on the npm side too** (per security-plan §Dependency Security → CI integration): a finding WITH a stated safe upgrade is NEVER ignore-listed — it gets a named owner and stays red; only no-safe-upgrade findings take an ID-scoped `ignore` entry. Whether the chosen npm tool can express an ID-scoped, reasoned exception at all is a plan-time selection criterion, not an afterthought.
- **Exception hygiene**: per security-plan §Dependency Security → Duplicate-version carve-outs, every carve-out is ID-scoped, owner-named, and reasoned with a stated closing condition, and a stale exception is **pruned, never kept** (a stale skip hides the finding's return). Port this shape to whatever npm allowlist mechanism is chosen.
- Any third-party GitHub Action introduced by the new CI step MUST be referenced as `&lt;owner&gt;/&lt;repo&gt;@&lt;40-char-SHA&gt; # vX.Y.Z` — security-plan §Security Anti-Patterns → Secrets bans `@v2`/floating tags (tj-actions/changed-files CVE-2025-30066), and §Bootstrap phases → `dep-security-ci-gate` states the same convention with Dependabot bumping SHA + comment together.
- Workflow-level permissions stay `contents: read`, elevated per-job only on a publish step (security-plan §Security Anti-Patterns → Secrets); §Bootstrap phases → `dep-security-ci-gate` further requires `step-security/harden-runner` (SHA-pinned) as the first step of every job in `ci.yml`. Whether the existing `ci.yml` jobs already carry these — and therefore whether a NEW job inherits or must add them — is research's question.
- The scanner is itself a new dependency and inherits security-plan §Dependency Security → Pinning: a resolved version recorded in the manifest, never `"*"` or unbounded `"latest"` (the §API Security `tower_governor` row states this convention explicitly).
- The folded PREREQ is a plan mandate, not chunk bookkeeping: security-plan §Dependency Security → Standing deferral (`cargo audit` unrunnable) requires that at a BETWEEN-point the basis and the named overlap are re-verified first-hand and the report records `probe skipped per ratified interval (next: 61)` — never a silent skip. Counting rule (a): enumerate DISTINCT `RUSTSEC-` ids, never report an error-block count as a set size. Counting rule (c): no running "Nth consecutive" ordinal.

## Patterns to follow
- **The cargo triad's shape is the template** (security-plan §Bootstrap phases → `dep-audit-tooling-install` + `dep-security-ci-gate`): pinned tool install + a config file at a fixed root path carrying `[bans]`-equivalent / license-allowlist / source-restriction sections + a wired `ci.yml` step. The license half is load-bearing for the distribution channels per §Dependency Security → CI integration.
- **Two-invocation split** (security-plan §Dependency Security → CI integration + Standing deferral): the pass/fail gate (`cargo deny check bans licenses sources`) is invoked SEPARATELY from the observed signal (`cargo deny check advisories`), so a designed-red signal never blocks the green gate and a green gate never masks the signal. The scope's "2026-08-17 two-invocation lesson" is this pattern.
- **`xtask` is the project's precedent gate surface**: security-plan §API Security (TauRPC capability authorization) + §Bootstrap phases → `dep-security-ci-gate` wire the `xtask capability-drift` check as a CI-failing gate, which is the nearest in-repo analogue for the scope's `[inferred]` local-invocation decision (xtask subcommand vs npm script).
- **`cargo-auditable`'s pairing model** (security-plan §Dependency Security → Minimal-tier additions): embed/enumerate the dependency tree so post-release advisory scans can identify what shipped. The npm runtime dependencies that Vite bundles into the shipped webview are the analogous post-release surface.

## Anti-patterns to avoid
- NEVER reference a third-party Action by floating tag or `@v2`, and NEVER set `permissions: { contents: write }` at workflow level (security-plan §Security Anti-Patterns → Secrets).
- NEVER turn the new gate green by ignore-listing a finding that has a stated safe upgrade — it stays red under a named owner (security-plan §Dependency Security → CI integration); and never leave an exception standing once its closing condition is met (§Dependency Security → Duplicate-version carve-outs, prune-not-keep).
- NEVER let the new gate's failure output carry values from the `[licenses]`/exception config or environment that are secret-class per security-plan §Secret Management → What counts as secret; §Logging &amp; Monitoring's NEVER-log list applies to CI output as it does to the app.
