## Constraints
- **Task runner is locked to `cargo-xtask`** — architecture.md §Established Decisions [CI Task Runner] mandates that shared CI logic live as a Rust binary in the workspace's `xtask` crate; `just` and `cargo-make` are explicitly rejected there ("add DSL surface area without buying anything"). The scope's `[inferred]` invocation-shape decision (xtask subcommand vs npm script vs both) must resolve inside that mandate, not around it.
- **Local/CI parity is a requirement, not a nicety** — architecture.md §Infrastructure Patterns → CI/CD approach requires "All shared CI logic that needs Rust lives in the `xtask` crate so contributors can run identical commands locally with `cargo xtask <task>`." The npm gate must therefore be invocable by one identical command in CI and locally.
- **No new workspace crate** — architecture.md §Occupied Resources → Cargo workspace crate names locks the 16 members (`ingest` … `pulse-app`, `xtask`); the names are reserved and cannot be re-purposed, and new first-party crates are a `/andromeda-scope-arch` event per §Project Intent → How new functionality is added. Gate code belongs in `xtask/src/`.
- **CI workflow placement and matrix shape** — architecture.md §Infrastructure Patterns → CI/CD approach requires per-PR gates in `.github/workflows/ci.yml` (runs on every PR + push to main, matrix over Linux/macOS/Windows), with `release.yml` reserved for tag pushes. A lockfile-scoped scan is host-independent, so whether it runs once or on all three matrix legs is a plan-time decision the matrix constraint forces.
- **Agent-driven development style** — architecture.md §Cross-cutting Patterns → Development Style requires deterministic harness invocations, machine-parseable outputs, schema-stable contracts and `cargo xtask` task surfaces. This is the arch-side source of the scope's "deterministic, machine-parseable invocation" bullet.
- **Zero-infrastructure / no product-runtime coupling** — architecture.md §Design Philosophy (Local-first, zero-infrastructure: no Docker, no collector, no cloud backend) plus §Cross-cutting Patterns → Feature-gate hygiene (minimal default features; flag-specific deps enter the graph only when enabled) require the gate to add no service, container, or product-runtime dependency. Note the scope's measured 9 Vite-bundled runtime `dependencies` in `pulse-app/ui/package.json` — that class IS a product-bundle path, so a scanner must not be added there.
- **arch's own CI enumeration may be incomplete at HEAD** — architecture.md §Infrastructure Patterns enumerates ci.yml as fmt → clippy → `cargo xtask test` → `cargo build --workspace` and names no npm steps, while the scope measured `npm ci` (:92) and `npm run build` (:114). Whether ci.yml carries steps arch does not enumerate is research's question; if so, the enumeration is a wrap-time amendment candidate, not an in-chunk code change.

## Patterns to follow
- **`cargo xtask <kebab-subcommand> [--kebab-flag <VALUE>]`** — the registered harness CLI shape at architecture.md §Stack and Technologies → GUI verification harness row (`cargo xtask webview-drive [--expect-absent <STAGE>] [--no-inject]`), including its **clean-SKIP disposition** for a missing external prerequisite (unset/not-a-file ⇒ exit 0 printing the fetch recipe, never a hard failure) — the model for how a gate behaves when its precondition is absent, as distinct from a real finding.
- **Pinned-expectation drift gate** — architecture.md §Cross-cutting Patterns → Webview IPC capability policy describes `xtask capability-drift` diffing against the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`. That is the in-repo precedent for a pass/fail xtask gate backed by a maintained, reviewable expectation list — directly applicable to the scope's exception/allowlist mechanism.
- **Requirement-plus-resolved version recording** — architecture.md §Stack and Technologies records duckdb / wasmtime / rmcp as "requirement `X` (manifest, untouched), lockfile-resolved `Y` as of DATE". If this chunk records any npm resolved version in an arch-touching artifact, that is the established shape, not a bare version string.
- **Offline/air-gapped accommodation via a registered env var** — architecture.md §Occupied Resources → Environment variables registers `ANDROMEDA_LLAMA3_TOKENIZER_PATH` as a build-script-only var letting a pre-downloaded artifact substitute for a network fetch. If the npm gate needs network access to an advisory source, that is arch's precedent shape for a local-artifact escape hatch — and any such var must be registered (harness-only class, per the `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` / `PULSE_*` relay-set entries).

## Anti-patterns to avoid
- **Introducing a second task-runner surface** (Makefile, `just`, `cargo-make`, or a bare shell script as the canonical entrypoint) — architecture.md §Established Decisions [CI Task Runner] rejected exactly these by name.
- **Reaching for product surfaces this gate does not need** — no new TauRPC procedure and therefore no `EXPECTED_PROCEDURES` pin edit for the gate itself, and no `pulse-app/capabilities/` edit: architecture.md §Cross-cutting Patterns → Webview IPC capability policy establishes that capability JSON changes are for Tauri **core API** surfaces only, and a CI task is neither.
- **Repeating the whole-channel dev-only claim** — architecture.md §Stack and Technologies' GUI-harness row closes with "Dev-only: devDeps only, no runtime/bundle impact". As written that clause scopes to the harness pair; it must not be generalized to the npm channel, which the scope measured as carrying 9 Vite-bundled runtime dependencies.

Whether arch's §Infrastructure Patterns ci.yml step enumeration also needs correcting depends on what research measures in ci.yml at HEAD.

## Acceptance criteria contributions
- (arch) Any new task-runner surface is a subcommand of the existing `xtask` workspace crate, invoked as `cargo xtask <kebab-subcommand>`; no new workspace crate and no non-Cargo task runner is introduced (per architecture.md §Established Decisions [CI Task Runner] + §Occupied Resources → Cargo workspace crate names).
- (arch) The gate runs per-PR from `.github/workflows/ci.yml` and the identical command runs locally with no CI-only wrapper logic (per architecture.md §Infrastructure Patterns → CI/CD approach).
- (arch) The invocation is deterministic and its output machine-parseable, with a defined non-failure disposition for a missing precondition rather than an ambiguous crash (per architecture.md §Cross-cutting Patterns → Development Style + §Stack and Technologies → GUI verification harness SKIP precedent).
- (arch) The change adds no product-runtime dependency (no entry in `pulse-app/ui/package.json` runtime `dependencies`, no non-dev Rust dep), no container/service, no TauRPC procedure and no `pulse-app/capabilities/` edit; any new env var is registered in §Occupied Resources → Environment variables in the harness-only class (per architecture.md §Design Philosophy → Local-first, zero-infrastructure + §Cross-cutting Patterns → Feature-gate hygiene + §Occupied Resources).
