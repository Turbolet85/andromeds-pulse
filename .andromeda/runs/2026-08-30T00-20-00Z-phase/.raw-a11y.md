## Relevance
Partial — no UI surface, no WCAG criterion is triggered by this chunk, but the npm channel being gated (`pulse-app/ui`) is where the entire a11y harness and the a11y-mandated runtime libraries live, so a11y contributes toolchain-integrity and CI-coexistence constraints only.

## Constraints
- The scan's ban/license/deny configuration must not remove, block, or downgrade any package the plan mandates: a11y-plan §3 "A11y testing tool pick" pins the axe/Lighthouse/pa11y/pa11y-ci majors and §3 "Contrast verification harness" pins colorjs.io; §3.5 "Bootstrap phases" additionally mandates the focus-management, ARIA-component, lint, and motion packages; §3 "Harness wiring &amp; conventions" adds the static-server devDep. These pins are a11y-plan authority, not incidental versions.
- Any advisory disposition in this chunk that moves an a11y harness package across a major line invalidates the regression baseline — a11y-plan §3 "Harness wiring &amp; conventions" defines the baseline as a clean full-chain pass, and §10 "Standard+ invariants" gates zero new violation tuples per PR. Rule-set drift across axe/Lighthouse/pa11y majors surfaces as new violations, so the upgrade and the re-baseline are one unit of work.
- The new gate lands in the same `.github/workflows/ci.yml` that a11y-plan §3 "CI integration" and §9 "Pipeline integration" require the a11y gate to run in. Step placement must not short-circuit the a11y gate; a designed-red scan step ahead of it would skip a11y on every run, which §11 "CI" forbids. Whether the a11y gate is currently wired into `ci.yml` at all is research's question — the plan states it as a requirement, not an observation.
- npm advisory output is not a11y violation output. a11y-plan §3 "Structured violation JSON schema" scopes `target: "a11y::assertion"` + `wcag_criterion` + a fixed `tool` enum to WCAG findings, and §9's artifact table enumerates the a11y artifact set; the npm gate needs its own artifact and its own disposition ledger.
- The scan step consumes the same wall-clock budget a11y-plan §10 "Performance budget per a11y CI run" caps for the combined a11y + tests E2E run.
- a11y-plan §11 "Universal" bans running two ARIA component libraries simultaneously. The scope's own dependency enumeration names only one of them among the 9 runtime deps, so the rule appears satisfied; a bans/duplicate mechanism must not be configured in a way that reintroduces the mix, and whether the lockfile carries the second library transitively is research's question.
- The a11y toolchain (Playwright + Lighthouse + pa11y, each with a browser-automation tail) is a large share of the 910 lockfile packages, so first-scan findings are likely concentrated there; the pinned versions per a11y-plan §3 "A11y testing tool pick" and §3.5 "Bootstrap phases" constrain what "safe upgrade" can mean for those findings.

## Patterns to follow
- `npx playwright test --list` as the cheap post-dependency-change suite-health check (a11y-plan §3 "Harness wiring &amp; conventions") — a list-time import failure is the plan's recorded silent-death mode for this suite.
- Per-PR baseline-diff gating shape already specified for a11y: machine-parseable JSON, artifact upload/download of a base-branch summary, tuple-set comparison, and an auditable `regression-set.json` (a11y-plan §3 "CI integration"). The npm gate's disposition/exception mechanism can mirror this rather than invent a new one.
- Hard-gate discipline with no soft threshold and no retry (a11y-plan §10 "Build / deploy failure conditions", §11 "SLO") — the same posture the chunk's disposition rules describe for the npm side.
- Version pins carried as named bootstrap phases rather than ambient lockfile state (a11y-plan §3.5), so a version move is a recorded plan-level event.

## Anti-patterns to avoid
- Never route npm advisory findings into a11y artifacts, `a11y-violations-summary.json`, or the regression baseline (a11y-plan §3 "Structured violation JSON schema" + §3 "Harness wiring &amp; conventions" + §9 artifact table).
- Never let the new gate soften, skip, or defer the a11y gate — a11y-plan §11 "CI" states a11y is fail-fast, not a warning, and bans deferring it post-merge.
- Never silently drop, downgrade, or allowlist away a plan-mandated a11y package; a11y-plan §11 "Strategy" requires an explicit Decisions Log entry for configuration changes that narrow a11y coverage, and §12 routes that record to the amendment sidecar.

## Contract bindings
- a11y ↔ security: the npm channel this chunk gates carries a11y-plan §3 / §3.5 mandated packages; finding disposition is security-plan-owned, but the version floor for those packages is a11y-plan-owned, so a "safe upgrade" that crosses a pinned major is a joint decision.
- a11y ↔ tests: shared `ci.yml` and shared Playwright/E2E 5-command harness per a11y-plan §3 "Focus management test harness" contract binding and §9 "Pipeline integration" — step ordering and job budget are shared surface.
- a11y ↔ obs: a11y violation JSON is aligned to obs's structured log format per a11y-plan §3 "Structured violation JSON schema"; the npm scan's records must not borrow that target/field vocabulary.
