# design extract

## Relevance
**Partial** — no UI is authored here, but three design mandates (titlebar drag region, window resizability, WebView2 context-menu suppression) are precisely what Half A's stages would pin, and Half B's blank-window failure mode lands on the dark-first surface envelope.

## Constraints
- The drag stage's synthesized press must land inside the titlebar drag region as the design defines it — a custom-drawn 32px titlebar whose drag region is the full titlebar width **except** the app icon, settings icon and window-control buttons (per design-system §Surface: desktop-webview → Component Patterns → Navigation / App Shell). Whether the shipped `data-tauri-drag-region` extent matches that spec is research's question; a probe that presses over a control measures the wrong surface.
- design-system §Anti-Patterns → Per-Surface Bans → desktop-webview requires that the compact widget and the full dashboard both stay user-resizable. The 1.4–2.1 aspect clamp is an *envelope*, not a lock; the resize stage's RED arm (neutralising `clamp_to_aspect_bounds`) must leave the window resizable at HEAD after restore.
- The same per-surface ban requires that no visible WebView2 artifact ship — the right-click context menu is to be hidden and text selection disabled on non-text elements (per design-system §Anti-Patterns → Per-Surface Bans → desktop-webview). This is the design requirement the CARRY 4 suppression-side assertion (`defaultPrevented`) would pin; whether the code already suppresses it is research's question.
- Any window that can become visible before it navigates must still present the dark envelope: Base `#1A1D24` is the page/app background (per design-system §Color Palette → Surface Scale), and design-system §Anti-Patterns → Rejected Defaults explicitly rejects bright/high-contrast surfaces. A blank `findings`/`report` victim must not surface as an undesigned bright webview — this constrains Half B path (b) regardless of which hook it uses.
- A re-navigate guard must not introduce motion: design-system §Motion → This project's values sets **Entrance animations: none** ("components render instantly; motion confirms state changes only, not arrivals"), and §Motion → Hard limits bans opacity fades beyond 200ms. No reveal/fade may be added to mask a re-navigation.
- design-system §Surface: desktop-native → Navigation Pattern states the tray surface is OS-controlled with **no keyboard navigation at the tray level** (menu interaction handled by the OS). That is the design-side basis for CARRY 5's tray-restore mechanic being potentially undrivable and therefore declinable; whether WebDriver reaches it in practice is research's question (scope §8 premise 3).
- Any webview-side change must use the `@theme` custom properties (`--color-*`, `--spacing-*`, `--radius-*`, `--font-*`, `--duration-*`, `--easing-*`) rather than literal hex/px (per design-system §Surface: desktop-webview → Tokens (platform-specific) and §Self-Validation Protocol → 4. Token Test).

## Patterns to follow
- Custom frameless titlebar (32px height; app icon 16px, title, settings aperture icon 20px, platform-appropriate window controls; drag region = full width minus buttons) — per design-system §Surface: desktop-webview → Component Patterns → Navigation / App Shell. This is the surface both the drag stage and the boot-geometry sub-part act on.
- Borders-only depth: elevation via raised surface lightness plus a 1px `rgba(74, 144, 226, 0.3)` border, never shadows (per design-system §Depth Strategy). Applies to any container touched incidentally by a landed stage.
- The shared `EmptyState` primitive and its distinct honest-error variant — checked *before* the empty branch, static "Couldn't load …" copy, no actionable hint (per design-system §Surface: desktop-webview → Component Patterns → Loading / Empty States). This is the designed answer to "a window with nothing in it"; a bare blank webview is not.
- Desktop-native notification/signpost shape: terse, 2 lines max, data-driven, contemplative-observational voice (per design-system §Surface: desktop-native → Component Patterns → Notifications, and §Tray Menu → Tone). Applies if CARRY 5's repetition proof touches the signpost's user-visible text rather than only the `tray.signpost.shown` record.

## Anti-patterns to avoid
- Do **not** un-suppress the native WebView2 context menu (or re-enable non-text selection) to make the CARRY 4 stage observable — that trades a design ban for a test verdict (per design-system §Anti-Patterns → Per-Surface Bans → desktop-webview). Decline the stage instead; the scope's own "no vacuous stage" rule and this ban agree.
- Do **not** make the window non-resizable, shrink the drag region, or pin geometry to make a stage deterministic (per design-system §Anti-Patterns → Per-Surface Bans → desktop-webview: "NEVER make the window non-resizable without strong justification"). The harness adapts to the designed window, not the reverse.
- Do **not** add gradients, glassmorphic effects, shadows, or a fade/entrance to chrome as part of a Half B guard — the Halo State Pulse canvas is the sole gradient/blur exception, and it is out of this chunk's scope (per design-system §Anti-Patterns → Universal Bans and §Motion → Hard limits).

## Contract bindings
- **design ↔ tests harness:** the CARRY 3 and CARRY 4 assertions are the *measurement instrument* for two design per-surface bans (window stays resizable; native context menu stays suppressed). The durable boundary text lives at test-plan §6 per scope §4 — design owns the ban, tests own the wording of what was established.
- **design §Motion ↔ a11y §Animation (SC 2.3.3 / `prefers-reduced-motion`):** binds only if the Half B guard adds any transition; design's "entrance: none" already forecloses one, so the reduce-motion override should have nothing new to cover.
- **design §Color Palette / Text Hierarchy ↔ a11y §Contrast (SC 1.4.3):** no new color pairs are expected; if the guard renders any user-visible text (a re-navigation notice), its pair must meet 4.5:1 at body size — `--color-text-secondary` (#B4BCCB, ~6.8:1), never Tertiary.
- **design §Surface: desktop-native ↔ CARRY 5 tray mechanic:** the tray menu is an OS-native surface by design mandate; its drivability question is shared with a11y (OS-owned keyboard interaction) and with the harness's decline path.
- **design ↔ layouts:** P-082's multi-window-size internal-scroll half is per-screen layout (layouts' distiller). Design contributes only the resize envelope (1.4–2.1 aspect band as the designed window shape) and the ban on unstyled web-style scrollbars.

## Acceptance criteria contributions
- (design) The drag stage presses inside the titlebar drag region as specified — full titlebar width excluding the app icon, settings icon and window controls — not over a control (per design-system §Surface: desktop-webview → Component Patterns → Navigation / App Shell).
- (design) After the resize stage and its RED-arm restore, the compact widget and full dashboard remain user-resizable within the 1.4–2.1 aspect envelope; no landed stage leaves the window fixed-size (per design-system §Anti-Patterns → Per-Surface Bans → desktop-webview).
- (design) If the native-menu stage lands on its fallback, it asserts the *suppression* side (context menu hidden / `defaultPrevented`) and does not require the native menu to be visible; if suppression cannot be observed, the stage is declined with a recorded reason rather than un-suppressed (per design-system §Anti-Patterns → Per-Surface Bans → desktop-webview).
- (design) Any UI or window-surface change shipped by Half B uses only design tokens (no hardcoded hex or px), keeps the pre-navigation window on Base `#1A1D24`, and adds no entrance/fade animation (per design-system §Surface: desktop-webview → Tokens, §Color Palette → Surface Scale, §Motion → This project's values).
