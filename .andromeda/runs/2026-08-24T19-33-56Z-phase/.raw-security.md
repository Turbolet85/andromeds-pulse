## Relevance
Partial — the chunk is harness/verification work, but it mutates `pulse-app/capabilities/default.json`, may add a product-side navigation guard and new obs records, and carries a security-owned PREREQ (`cargo audit` standing deferral).

## Constraints
- The drag stage's RED lever revokes `core:window:allow-start-dragging`. Per security-plan §API Security (TauRPC capability authorization) and §Security Anti-Patterns → API, `core:window:*` permissions are the class that IS silently rejected at runtime when absent — so the mutation arm must restore the capability file exactly, and any *new* `core:window:*` / `core:webview:*` permission the Half B guard needs requires an explicit per-feature capability addition with a stated rationale. No shipped gate catches a stale revoke (the drift gate pins TauRPC procedures, not core permissions), so the restore verification is the chunk's own obligation.
- If Half B path (b) routes through Rust, any new TauRPC procedure requires BOTH an `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` AND a `serde`-validated argument struct — per security-plan §Input Validation (TauRPC bridge row) and §Security Anti-Patterns → API. Per-procedure capability-JSON entries do not exist in this project, so those two pieces are the entire per-procedure enforcement.
- Any re-navigation target the guard uses must be the statically declared first-party window URL, never a value read back from the webview or derived from external input — per security-plan §Threat Model Summary (webview content vector) and §API Security (CSP `default-src 'self' ipc: http://ipc.localhost`, no remote content). Whether the existing window creation already fixes the URL statically is research's question.
- Any new harness env var the probe or stages need rides the **harness-only tool-locator carve-out** (trim + `is_file()` + clean skip, resolved value never logged) and must be registered in security-plan §Input Validation's CLI/env-var row; anything the **product binary** reads as `ANDROMEDA_PULSE_*_PATH` / `*_DIR` stays under categorical canonicalize-and-confine per §Security Anti-Patterns → Input.
- New or extended stage/guard records must carry bounded first-party fields only — security-plan §Logging &amp; Monitoring (What NEVER to log) bans raw attribute values, full file paths and clipboard-class content, and §Input Validation (window-geometry.json row) requires that no coordinate values be logged. A drag stage that produces a real window move exercises that geometry-persistence path directly; whether the existing `Moved` handler already logs coordinates is research's question.
- PREREQ per security-plan §Dependency Security → CI integration (Standing deferral — `cargo audit` unrunnable): at a non-interval wrap the basis and the named overlap signal must be re-verified first-hand, the owned upgradeable ID set re-enumerated (never carried forward — it has grown historically), and `probe skipped per ratified interval (next: …)` recorded in the report. A silent skip is not permitted.
- If any stage or probe adds an npm devDependency, security-plan §Dependency Security records as MEASURED that the `pulse-app/ui` channel gets Dependabot version updates but **no** advisory/license/ban scanning (`cargo audit` / `cargo deny` / `cargo-auditable` all stop at the Rust boundary; `ci.yml` runs `npm ci` with no `npm audit`). Any addition widens an already-owned gap and must be recorded, not silently absorbed.

## Patterns to follow
- Harness-only tool-locator env var shape: whitespace-trim + `is_file()` + clean SKIP (exit 0, prints the fetch recipe) rather than panic, with the resolved value never logged (only the variable NAME) — the `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` precedent per security-plan §Security Anti-Patterns → Input carve-out.
- Bounded first-party obs field shape: a labelled record with an exact allowlist leaf and a bounded label field (the `tray.signpost.shown` / `window_label` shape the chunk already targets), with redaction applied at the subscriber layer, not at call sites — per security-plan §Logging &amp; Monitoring (Log format).
- Registry-completeness pattern for any new input boundary landed by this chunk: a code-validated + unit-tested boundary gets a row in security-plan §Input Validation's table rather than an escalation (precedent rows: `window-geometry.json`, `run/workspace-key`, the env-var row).
- Boundary error sanitization if the guard surfaces failure to the webview: `AppError::{Validation{field,reason}, Internal{message}}` with a sanitized one-liner; full chain stays in the internal log — per security-plan §Error Handling (TauRPC bridge) and §Security Anti-Patterns → Logging.
- `xtask capability-drift` is the declared enforcement mechanism for any TauRPC surface change — per security-plan §API Security (TauRPC capability authorization) and §Bootstrap phases (`dep-security-ci-gate`).

## Anti-patterns to avoid
- NEVER grant a Tauri core API (`fs`/`shell`/`dialog`/`http`) or a `core:window:*` permission without an explicit per-feature capability addition with stated rationale (security-plan §Security Anti-Patterns → API) — and by the same mechanism, never leave a revoked core permission unrestored, since absence is silently rejected at runtime and becomes a dead-affordance bug.
- NEVER add a TauRPC procedure without its `EXPECTED_PROCEDURES` pin and a validated argument struct (security-plan §Security Anti-Patterns → API).
- NEVER log raw OTLP attribute values, full file paths, or clipboard-class content in any new stage/probe/guard record (security-plan §Security Anti-Patterns → Logging).

## Contract bindings
- **Capability-JSON mutation arm ↔ tests harness:** the revoke-and-restore RED arm runs inside the tests-owned `webview-drive` leg; security-plan §API Security names `xtask capability-drift` as the CI gate but it pins procedures only — the byte-identical-restore verification is unenforced by any shipped gate (route-owned by the Staged-bindings entry), so tests must carry the check.
- **`cargo deny check bans licenses sources` ↔ tests §CI Integration:** the overlap signal for the `cargo audit` deferral is the pass/fail gate; `cargo deny check advisories` is observed separately as designed-red (security-plan §Dependency Security → CI integration).
- **NEVER-log list ↔ obs PII scrubbing + tests fixtures:** any canary/fixture value a stage introduces must not be real secret material, and any new record's fields fall under the obs schema's scrubbing contract (security-plan §Logging &amp; Monitoring).
