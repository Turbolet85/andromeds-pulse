# arch extract

## Relevance
Relevant — the chunk lands harness code in `xtask` + `pulse-app/ui/tests-e2e`, may touch `pulse-app/src/window.rs` and `capabilities/default.json`, and both halves bear on arch-registered resources (harness env-var relay set, GUI-harness Stack row, capability grants).

## Constraints
- **Harness code lives in `xtask` + `pulse-app/ui` only; both crate names are workspace-reserved and cannot be re-purposed** (per architecture.md §Occupied Resources → Cargo workspace crate names; §Inherited Defaults → Build: Cargo + `cargo-xtask` for release/CI tasks). Any Half B guard, by contrast, is product code and belongs in `pulse-app` (binary crate) — the only root of the dependency DAG (§Cross-cutting Patterns → Module dependency direction).
- **The sanctioned GUI verification harness shape is fixed by arch**: `@crabnebula/tauri-driver` 2.x + `webdriverio` 9.x as `pulse-app/ui` devDependencies, win32 native driver via the napi optional dep (no `cargo install tauri-driver`, no Rust dependency), host `msedgedriver` located via `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` and never committed, driven by `cargo xtask webview-drive [--expect-absent &lt;STAGE&gt;] [--no-inject]` under the deterministic-L4 gate (per architecture.md §Stack and Technologies → GUI verification harness (dev-only)). A probe that needs W3C Actions / `setWindowRect` must go through that transport — adding a second driver stack or a Rust-side WebDriver dep would contradict this row.
- **Any new env var the probe or driver needs must be registered in §Occupied Resources, and harness-only vars are a declared class**: the `PULSE_BIN` · `PULSE_DATA_DIR` · `MSEDGEDRIVER_PATH` · `PULSE_INJECTOR` xtask→node relay set is registered as harness-only, un-prefixed precisely because it never crosses into the product; anything the production binary reads must instead take the `ANDROMEDA_PULSE_*` prefix (per architecture.md §Occupied Resources → Environment variables). Whether the probe/new stages introduce any new relay name is research's question.
- **Test-time telemetry enters only over real OTLP** — no in-process bypass, no test-mode feature flag, no mock back-door; tests needing non-default ports resolve them via `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT` (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection). The `--no-inject` RED arm suppresses the `inject_demo` OTLP producer, which is the arch-conformant way to starve a stage.
- **Capability granularity is the IPC LAYER, not the procedure**: `core:window:*` permissions (including `allow-start-dragging`) ARE granted individually and ARE silently rejected at runtime when missing — that is exactly what makes the §3.1 revoke a live RED lever (per architecture.md §Cross-cutting Patterns → Webview IPC capability policy). Per the same section, `pulse:default` grants `core:default` + seven `core:window:*` + `updater:default` and holds no per-procedure entries; a capability edit is only owed for a core-API surface, never for a TauRPC procedure.
- **A Half B product-side guard must not introduce a new IPC procedure without registration**: any new TauRPC procedure requires a router registration in the owning crate, an entry in §Occupied Resources, and its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` (the `capability-drift` gate's diff basis) — per architecture.md §Cross-cutting Patterns → Webview IPC capability policy + §Conventions → Endpoint naming. Whether the guard can be implemented purely inside existing `pulse-app` window wiring with no new procedure is research's question.
- **Persisted window-position state already has an arch-registered home**: `window-geometry.json` under the resolved data dir root, Rust-owned, atomic `.tmp`+rename, written by `pulse-app/src/window_geometry.rs` (per architecture.md §Occupied Resources → Filesystem locations). A drag stage that reads or a guard that writes window state must use that registered file rather than a new sidecar path; a new data-dir path would owe a §Filesystem-locations registration.

## Patterns to follow
- **`cargo xtask &lt;task&gt;` as the single machine-parseable harness entry point** — all shared logic needing Rust lives in `xtask` so the identical command runs locally and in CI (per architecture.md §Infrastructure Patterns → CI/CD approach; §Cross-cutting Patterns → Development Style: agent-driven, deterministic harness invocations + schema-stable contracts). New probe/stage surface extends the existing `webview-drive` subcommand rather than adding a sibling entry point.
- **Harness-only env-var class with a clean-SKIP guard** — `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` is whitespace-trimmed + `is_file()`-guarded, and unset/not-a-file makes the leg SKIP clean (exit 0) printing the fetch recipe rather than hard-failing (per architecture.md §Occupied Resources → Environment variables). A probe that finds a driver capability absent has the same shape available to it: a recorded, non-failing outcome.
- **Bounded truthy/parse discipline for env gates** — `ANDROMEDA_PULSE_L4_DETERMINISTIC` follows the `crates/mcp-server/src/feature_gate.rs` truthy-parse pattern (`1|true|yes`, default false), and `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` shows the bounded-parse-never-panic shape (per architecture.md §Occupied Resources → Environment variables). Any new probe toggle follows the same shape.
- **Rust error discipline across the two halves** — `thiserror` 2.x for module-internal enums, `anyhow` 1.x at boundaries and `main.rs`, `serde`-friendly `AppError` at the IPC bridge (per architecture.md §Established Decisions → [Error Handling Pattern]; §Conventions → Error response schema (Tauri IPC)). `xtask` is a boundary-style binary; a `pulse-app` guard sits inside the `anyhow`-at-`main.rs` frame.
- **Config precedence when a guard needs a knob** — env vars &gt; `~/.andromeda-pulse/config.toml` &gt; built-in defaults; env-layer-only scoping is a legitimate deliberate choice that avoids a `Settings` field, a TauRPC contract change and a hot-reload delta (per architecture.md §Cross-cutting Patterns → Config management, and the 2026-08-16 baseline-bootstrap precedent).

## Anti-patterns to avoid
- **No in-process test-mode bypass or mock-channel back-door to make a stage observable** — if the driver cannot reach a surface, arch's injection discipline forbids inventing a side channel to fake it; decline instead (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection). This aligns with the chunk's own "no vacuous stage" rule.
- **No unregistered `PULSE_*` / `ANDROMEDA_PULSE_*` name and no un-prefixed name crossing into the product** — `PULSE_*` is a claimed prefix where a collision would be silent, and the relay set was registered as a set for exactly that reason (per architecture.md §Occupied Resources → Environment variables, xtask→node relay entry).
- **No new runtime/bundle dependency for the harness** — the GUI harness row is explicitly dev-only, devDeps only, no runtime or bundle impact, and no Rust dependency (per architecture.md §Stack and Technologies → GUI verification harness (dev-only)). A probe must not pull a driver crate into the workspace graph.

## Contract bindings
- **Capability JSON ↔ security/tests** — the §3.1 RED arm mutates `pulse-app/capabilities/default.json`, whose grant model arch fixes at §Cross-cutting Patterns → Webview IPC capability policy; the chunk's own byte-identical-restore invariant is a tests/security discipline arch does not itself enforce (arch registers capability IDENTIFIERS `pulse:default` etc. in §Occupied Resources, and per the amendment history the individual `core:window:*` grants stay OUT of §Occupied Resources, so a revoke-and-restore owes no arch amendment).
- **Harness Role cell ↔ tests plan §6** — arch's §Stack GUI-harness Role cell is arch's only statement of the assembled path (currently 13 stages, `--expect-absent`-eligible); the test-plan §6 boundary text the chunk corrects describes the same leg. Landing or declining stages changes the count in arch's cell, so an arch amendment is owed at wrap if the stage table moves (precedent: the 7→13 amendment).
- **Half B guard ↔ obs** — if a guard or probe needs a new obs target/leaf (`pulse-app/src/observability.rs`), the allowlist-leaf discipline is obs-plan's; arch binds only in that the emitting code stays in `pulse-app` and any resulting IPC/event surface would need §Occupied Resources registration.
- **Window mechanics ↔ design/a11y** — frameless-window affordances (drag region, resize clamp, tray) are arch-registered only at the capability + tray-policy level (§Cross-cutting Patterns → Tray icon policy); glyphs, labels and keyboard/screen-reader behaviour belong to design and a11y.

## Acceptance criteria contributions
- (arch) Probe + new stage code lives in `xtask/` and `pulse-app/ui/tests-e2e/` with no new workspace crate and no new Rust dependency; the harness stays devDeps-only with zero runtime/bundle impact (per architecture.md §Stack and Technologies → GUI verification harness (dev-only) + §Occupied Resources → Cargo workspace crate names).
- (arch) Any new env var introduced by the probe or the Half B guard is registered in §Occupied Resources with its class stated (harness-only vs production-consumed) and its bounded-parse/guard behaviour; harness-only names stay un-prefixed per the relay-set precedent, production-consumed names take `ANDROMEDA_PULSE_*` (per architecture.md §Occupied Resources → Environment variables).
- (arch) If Half B path (b) ships a guard that adds a TauRPC procedure or a `pulse://stream/*` event, it is registered in §Occupied Resources AND pinned in `xtask/src/main.rs` `EXPECTED_PROCEDURES` so `xtask capability-drift` stays clean; if it adds a data-dir file, it is registered under §Filesystem locations (per architecture.md §Cross-cutting Patterns → Webview IPC capability policy + §Occupied Resources → Filesystem locations).
- (arch) Telemetry for every stage still enters over real OTLP via `inject_demo` — no in-process bypass, no test-only feature flag added to make any stage observable (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection).
