## Constraints
- The native verb stays inside the harness/xtask-only class: anything it reads to locate a tool or label the host is never consumed by the product binary and is existence-guarded with a clean skip, never a new product path input (per security-plan §Security Anti-Patterns → Input, "Carve-out — harness/xtask-only tool-locator vars"). Whether a new read the plan adds fits that shape exactly is P4's to state; a read outside it is not covered by the carve-out.
- A system variable the verb reads (the session bus address, the runtime dir, the display) is read by presence and reported as a closed label; no value of it is printed, written to the verdict or to `target/pre-push/report.json` (per security-plan §Security Anti-Patterns → Input, the xtask-only presence read of `DISPLAY` / `DBUS_SESSION_BUS_ADDRESS` / `XDG_RUNTIME_DIR`).
- The corpus key is one per-user-per-machine entry in the OS credential store, active at developer runtime, and the plan requires that a store failure degrade to absent or to the configured passphrase, never to an invented key (per security-plan §Secret Management → Runtime, and §Secret Management → Development). A stage that runs with the session bus reachable can reach that store; a fresh per-stage data dir does not separate it, because the plan keys the lock on the one per-user credential entry whatever data dir a process resolves (per security-plan §Security Anti-Patterns → Input, "Carve-out — the corpus-key lock dir"). Whether the credential-store test legs address the developer's real entry or a test-scoped one once the bus is reachable is research's question; the scope already holds this as a boundary widening for the founder's word.
- `XDG_RUNTIME_DIR`, when a stage inherits it, is product-read through `Corpus::open` and must be absolute, canonicalize and be a directory or lock-dir resolution fails closed; unset it resolves to the temp dir (per security-plan §Threat Model Summary, vector "CLI input (env vars + binary launch)"). The environment the native stages are given therefore decides where the content-free lock file lands (per security-plan §Data Protection → At rest, "Corpus-key lock file"); the plan states which, and the product-side validation is not changed by this chunk.
- `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` is secret-class: never logged, never exported (per security-plan §Secret Management → What counts as secret). If the native stages inherit the developer's environment rather than a constructed one, the verdict, its twin file and the verb's own stderr framing carry no environment value. Whether today's verdict or stage framing echoes any environment is research's question.
- A stage that resolves a data dir is handed one explicitly, so no stage reads or writes the developer's own corpus, snapshots, config or logs under the default per-platform data dir (per security-plan §Data Protection → At rest — per medium). Whether each of the six stages already receives an explicit data dir when `HOME` is the developer's real home is research's question.
- A crate added to `xtask` for the native path passes `cargo deny check bans licenses sources` and `cargo audit`; `multiple-versions = "deny"` is not relaxed and a new duplicate takes an ID-scoped, owner-named, reasoned skip or none (per security-plan §Dependency Security → CI integration, "Duplicate-version carve-outs").

## Patterns to follow
- Harness-written evidence files carry closed labels, counts and bounded records, no environment value and no path, with a pinned field set (per security-plan §Security Anti-Patterns → Input, the `logs/harness-settled.json` description) — the shape `target/pre-push/report.json` is held to.
- A boundary widening is named as one, put to the founder and recorded with its date and whose word it is; a classification that is the operator's own says so (per security-plan §Security Anti-Patterns → Input, the 2026-10-04 lock-dir ratification and the 2026-10-09 "routine harness evidence" classification).
- A gate's "could not evaluate" is its own exit arm, never folded into a pass (per security-plan §Dependency Security → CI integration, the npm channel's exit contract) — the same discipline the scope keeps for a missing tool.
- `package-lock.json` is the committed basis of the npm channel and in-range closes leave `package.json` and `npm-policy.json` untouched (per security-plan §Dependency Security → CI integration, "npm channel (`pulse-app/ui`)"); the native `npm` stage's writes land in the working tree now, so the plan says what it does when a stage leaves the lockfile modified.

## Anti-patterns to avoid
- NEVER build a spawned stage's argv from an OTLP attribute, an MCP tool argument or workspace-detector output (per security-plan §Security Anti-Patterns → Code Patterns); the stage commands and the probes stay first-party constants and repository pins.
- NEVER treat a native read of a product path variable as covered by the harness carve-out: the carve-out is scoped to not-production-consumed readers only (per security-plan §Security Anti-Patterns → Input, "The carve-out is scoped to exactly that").
- NEVER let a secret-class value reach a log or an exported artifact (per security-plan §Secret Management → What counts as secret).

## Contract bindings
- security ↔ tests: the plan's fail-condition roster includes `capability-drift` and `check:staged-artifacts` over the bindings and the capability grants (per security-plan §Dependency Security → CI integration, the build-fails bullet). With the clone gone the default-features test stage re-emits the bindings in the working tree itself; the order of that stage against any stage that reads the bindings, and what state the tree is left in, binds to test-plan §3. Whether `ci-gates` runs either verb is research's question.
- security ↔ tests: the credential-store legs' skip under a dropped session bus (the scope's fact (c)) binds to the test plan's skip accounting; the security side is only that reaching the store is a widening (per security-plan §Secret Management → Runtime).
- security ↔ obs: none added — the verb emits no product log record; the product's redaction rules (per security-plan §Security Anti-Patterns → Logging) are unchanged by this chunk.
- No coverage in the security plan, stated so it is not read as a mandate: `npm ci` install scripts, the puppeteer browser download and `PUPPETEER_CACHE_DIR` / `PUPPETEER_SKIP_DOWNLOAD`; the Node major a dev host must run; distro package probes (`dpkg-query` / `pacman`). The plan's npm text covers scanning only.
