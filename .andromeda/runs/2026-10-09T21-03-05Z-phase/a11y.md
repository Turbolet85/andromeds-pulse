With the clone gone the check's `npm` stage runs `npm ci` and that same build in the working tree, so it rewrites the install and the build output the a11y chain depends on. Whether the a11y harness reads the output the stage writes, and whether a native run leaves it usable, is research's question (per a11y-plan §3 CI integration).

The scope's stage-by-stage statement of which later entry removes a stage must not remove or soften an a11y-bearing step in this chunk. ## Patterns to follow
- The a11y chain's order (UI build, then the Playwright browser, then the PR-only baseline download, then `cargo xtask test:a11y`) is the reference for how a UI-building step is spelled; the native `npm` stage keeps the same build command form so the two do not diverge (per a11y-plan §3 CI integration).
- A11y reuses tests' five-command harness and adds no verb of its own; the chunk's boundary "no sixth `agent-run` verb" agrees with it (per a11y-plan §9 CI Integration).
- The suite-health probe names its config (`--config=playwright-a11y.config.ts --list`); the bare form reads the inert default config and reports zero tests whatever the suite's state. If research or the plan probes whether a native run left the a11y suite importable, it uses the config-named form (per a11y-plan §3 Harness wiring & conventions).

## Anti-patterns to avoid
- Never treat a non-a11y check as a substitute for the a11y gate, and never defer or soften that gate: the pre-push check stays outside the a11y evidence chain (per a11y-plan §11 A11y Anti-Patterns → CI).
- Never claim conformance without machine-verifiable a11y output: a report or plan line of this chunk states what the six stages ran, not that accessibility was checked (per a11y-plan §11 A11y Anti-Patterns → Strategy).
