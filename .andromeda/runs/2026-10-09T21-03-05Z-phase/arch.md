## Constraints
- The verb's registered contract is the thing kept: the exit triple, one pretty-JSON verdict on stdout and its report twin under `target/pre-push/` (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row). That row's verdict shape names fields that exist for the clone (`tree`, `cache{…}`); whether each stays, changes meaning or leaves is a contract change the plan states explicitly, never a silent drop. The verb's name is registered there too; a rename is the same kind of change.
- A missing tool or an unmet pin reads `cannot-evaluate` with the missing piece named and a remediation line, never green, and the verb never escalates (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row). The row words the remediation for an apt host; what the native check requires of a non-apt host and how it names a missing piece is research's question and the plan's decision.
- The check's pins are read from the repository, not hard-coded: the toolchain channel, ci.yml's Node major, ci.yml's package list (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row). The channel pin is the one architecture §Stack and Technologies (Primary language / runtime row) fixes, held by the xtask test `declared_floor_equals_the_pinned_channel`; whether that test reaches the channel reader that lives in `pre_push.rs` is research's question, and the reader survives if it does.
- The verb binds no port, starts no `pulse-app` and reads no new environment variable (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row). The row rests that on an emptied environment in a second system; natively, every variable the check reads or sets into a stage is a resource to register, with its reader or setter named and marked not product-consumed (per architecture §Occupied Resources → Environment variables).
- The six stages run in the registered order and stop at the first failure (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row). A stage that takes a data dir is given its own; `ANDROMEDA_PULSE_DATA_DIR` is the one override of the resolved root, so a stage left without it resolves the developer's own data dir (per architecture §Occupied Resources → Filesystem locations).
- The check is Rust inside the `xtask` crate; no second task-runner surface and no new workspace member (per architecture §Established Decisions [CI Task Runner]; crate names per architecture §Occupied Resources → Cargo workspace crate names).
- The check is dev-host only and not wired into CI (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row); ci.yml's shape is pinned by self-lint tests and is read here, not edited (per architecture §Infrastructure Patterns → CI/CD approach).

## Patterns to follow
- The formalized-CLI-contract registration: every xtask verb is recorded with its module, its exit contract, its verdict arms and its wiring, and a changed verb's row is re-registered (per architecture §Occupied Resources → xtask CLI surfaces). The `pre-push:linux` row and the `check:english-sources` row (which names the pre-push stage and "the clone") are expected wrap amendments; the plan carries them, phase edits neither.
- Stages call the same verbs CI runs, so a local run and a CI run are the same command (per architecture §Infrastructure Patterns → CI/CD approach, its closing bullet on shared CI logic in `xtask`).
- A harness-only variable SET into a child's environment and never read by the product, registered with its one home module and left outside the `ANDROMEDA_PULSE_` prefix (per architecture §Occupied Resources → Environment variables, the `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` and `PULSE_BIN` relay-set entries) — the precedent for a per-run browser-cache variable given to the `npm` stage.
- A harness-only presence read of a system variable reported as a closed label, no value printed or written (per architecture §Occupied Resources → Environment variables, the `DISPLAY` · `DBUS_SESSION_BUS_ADDRESS` · `XDG_RUNTIME_DIR` entry) — the precedent if the native check says whether a session bus was reachable for its test stage.
- Machine-parseable, schema-stable verdicts for an agent-driven workflow (per architecture §Cross-cutting Patterns → Development Style).

## Anti-patterns to avoid
- A green verdict over something the check could not evaluate, or a remediation the verb runs itself (per architecture §Occupied Resources → xtask CLI surfaces, the `pre-push:linux` row).
- A stage that binds `:4317` / `:4318`, starts the product, or runs against the developer's default data dir (ports per architecture §Occupied Resources → Network ports; the verb's no-port clause per architecture §Occupied Resources → xtask CLI surfaces).
- A stage that reaches the OS credential store or writes the corpus-key lock file as a side effect of inheriting the developer's session, decided inside the chunk: the credential store is the product's primary key source and the lock file is a registered out-of-data-dir location (per architecture §Occupied Resources → Corpus SQLite database / schema names, At-rest posture; per architecture §Occupied Resources → Filesystem locations, the out-of-data-dir lock file). The registered verb reaches neither today; reaching them is a boundary question for the founder, not a plan default.

## Contract bindings
- arch ↔ tests: the verb row sits beside the registered five-verb `scripts/agent-run.{sh,ps1}` contract (architecture §Occupied Resources → xtask CLI surfaces); the check stays an xtask verb and adds no harness verb. The same section places the `capability-drift` slot before the default-features workspace test run and reads bindings from the git index; a native `test` stage re-emits bindings into the working tree itself, which the clone used to absorb — test-plan §3 owns the ordering.
- arch ↔ security: any variable newly read or set, and any native reach to the session bus, the credential store or a location outside the data dir, is classified by security-plan §Security Anti-Patterns → Input (the harness-only class) before architecture §Occupied Resources records it.
- arch ↔ CI: the check's requirements are derived from ci.yml's pins (architecture §Infrastructure Patterns → CI/CD approach); the host's Node major differing from ci.yml's is a requirement the check reports, not one it relaxes.

- With a required tool or pin absent the verb reads `cannot-evaluate`, names what is missing, and never reads green or escalates (per architecture §Occupied Resources → xtask CLI surfaces)
- The check binds no port and starts no `pulse-app`; every environment variable the native path reads or sets is listed in the plan for registration, each marked not product-consumed (per architecture §Occupied Resources → Environment variables)
- The change lives in the `xtask` crate: no new workspace member and no new dependency in a library crate (per architecture §Occupied Resources → Cargo workspace crate names)
