## Constraints

- **WebGPU canvas opacity to SR**: a `<canvas>` has no built-in ARIA — the constellation surface MUST provide equivalent semantics via a wrapper element with an accessible name (e.g., `<section aria-label="Service constellation">…</section>` taking implicit `role="region"`), since the per-service dots are not individually exposed to assistive tech as pixels (per a11y-plan §1 WebGPU-canvas row + §7 Landmark roles `<region aria-label>` for canvas wrapper). The existing surface already uses `role="status"` with a complete-sentence aria-label for the aggregate count; the per-service replacement MUST preserve an off-canvas accessible text summary so dot state (count + per-service activity/severity/lifecycle) is reachable by SR users.
- **Not-color-alone (SC 1.4.1)**: severity hue + activity brightness MUST NOT be the sole carriers of dot state — the equivalent off-canvas text / tooltip MUST convey severity + activity + lifecycle in words, never color alone (per a11y-plan §6 State color tokens + §11 Visual ban "NEVER convey information by color alone"). Axe-core does not detect this; a custom DOM-inspect assertion is required.
- **Reduced-motion override (SC 2.3.3 AAA + SC 2.3.1 A)**: any dot twinkle / brightness pulse / dim animation MUST degrade under `prefers-reduced-motion: reduce` — dots render static (severity hue + brightness still convey state, motion removed), mirroring the Halo's "degrades to static glow, hue still updates" rule (per a11y-plan §6 Motion tokens + §11 Motion bans + CLAUDE.md Critical Warning "every transition MUST respect prefers-reduced-motion"). Use `useReducedMotion` from `motion/react` 12.x in the canvas frame loop (vanilla WebGPU loops require manual `matchMedia` check per §11 Motion last bullet).
- **Contrast (SC 1.4.3 / SC 1.4.11)**: dot colors are graphical objects on the `--color-inset` Halo canvas background — severity hue endpoints (`--color-primary` Earth Blue, `--color-accent` Alert Burgundy) MUST meet ≥3:1 non-text contrast against the canvas background; any visible tooltip text MUST meet 4.5:1 (per a11y-plan §6 Color contrast pairs + §11 Visual contrast ban). Shader colors must be read from CSSOM design tokens, not hardcoded RGB literals (design-tokens.md Session Additions 2026-05-08).
- **Hover tooltip not hover-only (SC 1.4.13 / keyboard)**: the tooltip (service name + activity rate + lifecycle state) MUST NOT be hover-only without a keyboard-reachable equivalent — frontend.md bans "hover-only interactions without keyboard alternatives". If dots are not individually focusable, the off-canvas text summary satisfies the equivalent-information requirement; if dots ARE made focusable, they need focus order + visible focus ring (see Patterns).
- **Status messages (SC 4.1.3)**: if dot state CHANGES are announced (e.g., a service transitions to Silent/Dormant via `pulse://stream/service-lifecycle`), the announcement uses an `aria-live="polite"` region (non-urgent) — live updates MUST NOT steal focus (per a11y-plan §7 Live regions + P4 "live updates do NOT steal focus"). If no announcement is intended, the surface stays a passive `role="status"`/region (no live region) — avoid stacking simultaneous announcements at ~20 services.

## Patterns to follow

- **Canonical canvas wrapper**: `<section aria-label="…"><canvas /></section>` — NOT `<section role="region" aria-label="…">` (explicit `role="region"` on a named `<section>` is redundant per a11y.md Session Additions 2026-05-09 `no-redundant-roles`). The existing `AggregatedBadgeCanvas.tsx` uses `role="status"` + complete-sentence aria-label; the replacement should keep a complete-sentence aria-label summarizing the constellation (e.g., "N services: X active, Y quiet, …") so the abbreviated visible text + opaque canvas remain SR-accessible.
- **Decorative-glyph flip pattern**: any inline icon/decoration carrying only context (not meaning) gets `aria-hidden="true"`, with meaning carried by the accessible name (per existing `AggregatedBadgeCanvas.tsx` comment + a11y-plan §11 ARIA — no excessive ARIA noise / redundant labels).
- **Reduced-motion hook**: `useReducedMotion` from `motion/react` 12.x feeds the WebGPU frame loop to gate dot animation; apply Tailwind v4 `motion-reduce:` variants to any CSS-driven dot transitions (per a11y-plan §3.5 motion-tokens-respect-install + frontend.md WebGPU canvas integration "reduced-motion degrade to static glow"). Note: the hook is non-reactive after mount (testing.md Session Additions 2026-05-04) — capture once at mount.
- **WebGPU fallback message**: when `navigator.gpu` is undefined, render `font-body` text in `color-text-tertiary` ("WebGPU not supported…") wrapped in the accessible region so it is SR-readable (per a11y.md §WebGPU canvas a11y + frontend.md WebGPU canvas integration).
- **Tooltip-as-popover ARIA** (if a custom hover/focus tooltip is built rather than an off-canvas summary): associate via `aria-describedby` from the focusable trigger; do not put interaction handlers on non-interactive wrapper `<div>`s (a11y.md Session Additions 2026-05-09 / 2026-05-10 surface the `no-static-element-interactions` / `click-events-have-key-events` lint traps).

## Anti-patterns to avoid

- **NEVER convey dot state by color/brightness alone** — severity + activity + lifecycle MUST have a text/word equivalent (off-canvas summary or tooltip text); SC 1.4.1 + a11y-plan §11 Visual ban 1. Axe-core will not catch this; custom assertion required.
- **NEVER autoplay dot motion without `prefers-reduced-motion: reduce` respect** — no twinkle/pulse/dim loop that ignores `window.matchMedia('(prefers-reduced-motion: reduce)').matches`; SC 2.3.3 AAA + a11y-plan §11 Motion bans + CLAUDE.md Critical Warning.
- **NEVER hide the constellation's essential meaning from assistive tech** — the canvas pixels are opaque to SR, so omitting the off-canvas accessible summary leaves SR users with no state at all (`aria-hidden`-equivalent outcome); a11y-plan §11 Screen Reader ban "NEVER hide important content from assistive tech".
