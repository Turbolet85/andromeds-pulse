# arch extract

## Relevance
Relevant (bounded) — arch governs workspace placement, the single-tokio-runtime/blocking-pool substrate the attribution targets, and the registration duties of any fix; the forensic log reading itself is outside arch's domain.

## Constraints
- One tokio multi-threaded runtime serves both OTLP ports and the IPC bridge (per architecture.md §Stack and Technologies → Async runtime; §Established Decisions [Backend Framework — OTLP receiver]; §Inherited Defaults). The plan fixes **no `max_blocking_threads` value** — the "512-thread default" in scope §4 is tokio's own default, not an arch mandate, so what the builder in `pulse-app` actually sets is research's question, and arch pre-authorizes no change to it. A fix must not stand up a second runtime to escape the shared pool.
- The ingest→appender hand-off is `tokio::sync::mpsc` (backpressure) and buffer→subscribers is `tokio::sync::broadcast`; `crossbeam-channel` was rejected to keep a pure-tokio stack (per architecture.md §Established Decisions [In-Process Channel Architecture]). A remedy must not introduce a non-tokio channel or bridging sync substrate on the consumer side.
- The four in-scope crates (`buffer`, `triage`, `viz`, `pulse-app`) are LOCKED workspace names; dependencies flow toward `pulse-app` as the sole DAG root, and no library crate may depend on a sibling unless its declared contract requires it (per architecture.md §Occupied Resources → Cargo workspace crate names; §Cross-cutting Patterns → Module dependency direction). Scope §6 anticipates no new crate edge — arch requires that stay true or be amended.
- Buffer storage is direct SQL via the `duckdb` `Connection`/`Appender`, no ORM, in-memory ring buffer with a periodic retention `DELETE` (per architecture.md §Established Decisions [Database], [ORM / Migrations], [Telemetry Retention Surface]; §Conventions → Database entity naming). §Occupied Resources → DuckDB database / schema names still registers `pulse_buffer` as a **single** in-memory connection; whether HEAD still matches that after the predecessor isolated `crates/viz` onto its own connections is research's question, and a divergence obliges a registry amendment rather than a silent contradiction.
- Config layering is env (`ANDROMEDA_PULSE_*`) > `config.toml` > built-in defaults, and every env var is a registered resource with a bounded, never-panicking parse (per architecture.md §Cross-cutting Patterns → Config management; §Occupied Resources → Environment variables). A tunable pool/timeout bound cannot be an ad-hoc `std::env::var` read.
- Module-internal errors use `thiserror`, boundaries use `anyhow`, anything crossing the TauRPC bridge is the `serde`-friendly `AppError` and must be `Serialize` (per architecture.md §Established Decisions [Error Handling Pattern]; §Conventions → Error response schema (Tauri IPC); §Cross-cutting Patterns → Cross-bridge data shape).
- End-to-end telemetry enters only over real OTLP on `:4317`/`:4318` — no in-process bypass, no test-ingest feature flag, no mock-channel back-door; buffer state is read back through the `traces.*`/`metrics.*`/`logs.*` routers (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection). This governs the shape of the discriminating pin if scope §2 outcome 1 holds.

## Patterns to follow
- Repo-wide Rust tooling lives in the `xtask` crate and is invoked as `cargo xtask <task>` so contributors and CI run identical commands (per architecture.md §Infrastructure Patterns → CI/CD approach; §Established Decisions [CI Task Runner]) — the predecessor's `check:ingest-progress` is that pattern; a new forensic/regression probe follows it rather than a standalone script.
- Adding a TauRPC procedure requires router registration in the owning crate + a §Occupied Resources entry + the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`; it does NOT require a `pulse-app/capabilities/` edit, because TauRPC dispatches every method through one invoke handler (per architecture.md §Cross-cutting Patterns → Webview IPC capability policy). This is exactly the pin set scope §6 anticipates but does not expect to need.
- Product self-telemetry goes to the stdout/file exporter under `<data_dir>/logs/` and never to the product's own OTLP ports (per architecture.md §Cross-cutting Patterns → Self-observation discipline; §Established Decisions [Self-Observation]) — any new forensic observable rides the existing log destination, not a new exporter.
- Each library crate exposes only its public contract module; internals stay `pub(crate)` with no cross-crate `pub use` re-exports (per architecture.md §Conventions → Module visibility discipline; §Project Intent → Template patterns) — a bounded-blocking helper stays crate-private unless it genuinely must cross an edge.
- Optional behaviour is gated by a `kebab-case` Cargo feature that is off by default, so its deps stay out of the baseline build graph (per architecture.md §Cross-cutting Patterns → Feature-gate hygiene; §Conventions → Feature flags).

## Anti-patterns to avoid
- Escaping the shared blocking pool by spawning a second tokio runtime, or bridging in a non-tokio channel/sync primitive (per architecture.md §Established Decisions [In-Process Channel Architecture]; §Stack → Async runtime).
- While in `crates/buffer` retention: adding a producer to — or retiring — the three producer-less reserved tables (`resources`, `instrumentation_scopes`, `span_links`) or their dead `DELETE`s. That disposition is explicitly owned by the "Diagnostics un-muting + harness-truth sweep" working-route entry (per architecture.md §Occupied Resources → DuckDB database / schema names → Reserved tables).
- Reproducing or pinning the wedge through an in-process test bypass, a test-only ingest path, or a mock channel (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection).

## Contract bindings
- **arch ↔ obs** — `health`'s `buffer` / `ingest_channel` subsystem strings and `ready`'s `ingest_mpsc_capacity_pct` / `rows_ingested` / `buffer_used_seconds` / `retention_seconds` checks are arch-owned envelopes (§Standard Contracts). Obs owns the exact-leaf allowlist discipline scope §6 names; arch owns the envelope shape — a field added to either envelope is an arch §Standard Contracts change requiring an amendment (2026-07-07 precedent below).
- **arch ↔ tests** — the sanctioned GUI harness's assembled 16-stage path and its `cargo xtask webview-drive` CLI shape are stated in arch §Stack and Technologies → GUI verification harness (dev-only); adding or renaming a stage is an arch amendment, and telemetry into that leg enters only via `crates/ingest/examples/inject_demo` over real OTLP.
- **arch ↔ security** — none anticipated: the confinement/canonicalization rule applies to product-consumed path env vars (§Occupied Resources → Environment variables), and the `D:/dev/evidence/...` forensic corpora are read-only inputs to analysis, not product-resolved paths.

## Acceptance criteria contributions
- (arch) Every changed file sits in `crates/buffer`, `crates/triage`, `crates/viz` or `pulse-app`, with no new workspace member and no new inter-crate dependency edge (per architecture.md §Occupied Resources → Cargo workspace crate names + §Cross-cutting Patterns → Module dependency direction).
- (arch) No second tokio runtime and no non-tokio channel/sync substrate is introduced; blocking work stays on the one runtime's pool (per architecture.md §Established Decisions [In-Process Channel Architecture] + §Stack and Technologies → Async runtime).
- (arch) The chunk lands zero unregistered arch resources: any new env var, TauRPC procedure, or `health`/`ready` envelope field carries its registration + pin set (`EXPECTED_PROCEDURES` for a procedure, a bounded never-panicking parse for an env var) and an amendment; otherwise the resource registry is unchanged (per architecture.md §Occupied Resources → Environment variables / Tauri IPC routes + §Standard Contracts).
- (arch) Any smoke, harness or verification command names the dev-build path `target/{profile}/pulse-app[.exe]`, never `target/{profile}/andromeda-pulse` (which exists on no host) (per architecture.md §Occupied Resources → Process / service identity).
