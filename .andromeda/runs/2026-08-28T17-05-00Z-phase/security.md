Whether the existing `duckdb.append` / `viz.query.traces` / baseline-SQL spans already satisfy this at HEAD is research's question.
- §Security Anti-Patterns → Logging records a **known carried exception**: the two pre-existing full-path boot records `app.boot.tracing.init` (`log_dir`) and `app.boot.pid` (`path`), owned by the "Diagnostics un-muting + harness-truth sweep" entry. This chunk consumes those records forensically; it must not widen the exception, and any NEW boot/runtime-builder record it adds is bound by the basename-only rule, not by the exception.
- If a proportionate fix introduces any `ANDROMEDA_PULSE_*` knob (e.g. a blocking-pool or timeout bound), §Input Validation (CLI / env var inputs row) requires a bounded parse — trimmed, range/enum-checked, unset/empty/unparseable/out-of-range falling back to a stated default, never a panic, never a silent adoption of an unintended bound — plus registration in that row's enumeration so the boundary list stays the complete list it claims to be.
- Any change inside `crates/buffer`'s append path must preserve the five persisted client-controlled scrub cells (`spans.service_name` via the `extract_service_name` choke point, `span_events.name`, `metrics_points.metric_name`, `log_records.severity_text`, `metrics_points.labels` in its joined `key=value` ∪ bare-value form) — the ring buffer remains unencrypted, so write-boundary redaction is the only control (per security-plan.md §Security Anti-Patterns → Logging, uniform scrubber coverage).
- Any DuckDB access touched in `crates/viz` query fns or `crates/triage` baseline SQL must stay on `Connection::prepare` + `?` parameter binding; identifier interpolation is banned outright (per security-plan.md §Input Validation, DuckDB query parameters row).
- The `cargo audit` standing deferral rides this chunk (scope §7 pin #18): §Dependency Security → CI integration requires the full-form probe at the interval point, the basis re-verified first-hand, and the named overlap `cargo deny check advisories` re-enumerated by **DISTINCT `RUSTSEC-` ids**, never by error blocks — with `cargo deny check bans licenses sources` green and `multiple-versions = "deny"` unrelaxed.
- If the fix surfaces a new failure at any boundary, §Error Handling requires sanitized external form (no stack traces, file paths, Rust struct names, library versions) with the full chain confined to the internal `agent-latest.jsonl` sink.

## Patterns to follow
- **Bounded-category error leaf** — §Input Validation's L4-argv row establishes the shape: a formerly-silent failure becomes a named bounded category on an existing error leaf (`io_error`, `stdout_utf8_invalid`) carrying no payload bytes, no offending substring. The right model for naming a blocking-pool abandonment or timeout without emitting query content.
- **Bounded env-var parse with graceful default** — `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` (non-zero, strictly below a named ceiling, every reject path → default) and `ANDROMEDA_PULSE_L4_DETERMINISTIC` (closed truthy set, no unbounded string), per §Input Validation CLI/env row.
- **Choke-point scrub placement** — `extract_service_name` scrubs once at the `pub(crate)` fn feeding three consumers rather than at each column push, precisely so a restructure cannot leave a raw path into `triage` (per §Security Anti-Patterns → Logging). If the consumer/append path is refactored, keep the scrub at the choke point.
- **Basename + env-var NAME logging** — the L4 records emit `path_basename` / `root_basename` and the variable name only; measured 0 occurrences of the containing directory across 11,251 lines (per §Security Anti-Patterns → Logging).
- **Secret-handling instrumentation** — `#[tracing::instrument(skip(key))]` at every corpus-key call site; if the baseline/corpus persist path is touched, the `scrubbed_clone` projection stays in place (per §Secret Management "What counts as secret").

## Anti-patterns to avoid
- NEVER `format!("SELECT … '{}'", user_input)` against the `duckdb` `Connection` when editing baseline or viz query paths — prepared statements with `?` only (per §Security Anti-Patterns → Input).
- NEVER log DuckDB query parameter values, raw OTLP attribute values, or a full product-consumed filesystem path in a new blocking-pool diagnostic (per §Security Anti-Patterns → Logging).
- NEVER add a TauRPC procedure without both its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` and a validated argument struct — conditional, since scope §6 anticipates none but admits one may become necessary (per §Security Anti-Patterns → API).

## Contract bindings
- **obs ↔ security:** scope §6's exact-leaf allowlist discipline for any new target intersects the NEVER-log list — an allowlist leaf may admit a field that security bans (query parameters, attribute values, full paths). §Logging & Monitoring places field redaction at the subscriber layer, not at call sites, so a new target's field-set pin must be checked against both plans.
- **tests ↔ security:** the security gate is a job in the single `ci.yml` (§Dependency Security → CI integration; §Bootstrap phases `dep-security-ci-gate`), which the chunk's discriminating pin shares; and the secret-scanning step (§Secret Management "Secret scanning in CI") fails the build on any credential-shaped literal, which constrains what a forensic report or new fixture may quote from the wedge log.
- **arch ↔ security:** the ring buffer's unencrypted-at-rest posture and the producer-less `instrumentation_scopes` / `resources` state are owned at arch §Occupied Resources; §Data Protection restates them and bans enabling DuckDB at-rest encryption (CVE-2025-64429).
