## Constraints
- The **standard gate set is unconditional regardless of scope** (`cargo fmt --check` · `clippy --workspace --all-targets --all-features -D warnings` · `cargo nextest run --workspace --profile ci` · `cargo xtask capability-widening-check` · `cargo xtask check:ingest-progress` · `cargo xtask capability-drift` **LAST**, since every command above it can regenerate `bindings/index.ts`); webview gates only if `pulse-app/ui/**` is touched — which this scope does not anticipate (per test-plan.md §3 Per-chunk gate discipline).
- `cargo xtask check:ingest-progress` keys on **PROGRESS, not liveness**, with four arms (non-`recovered` `buffer.consumer.stalled` ⇒ exit 1 · recovery ⇒ green · advancing ticks ⇒ PASS · no `buffer.tick` ⇒ NEUTRAL). This is the predecessor's detector that this chunk consumes; the NEUTRAL arm is what makes it safe on a chunk that boots nothing (per test-plan.md §3 Per-chunk gate discipline).
- **Boot-smoke gate is conditional on `pulse-app/src/main.rs`** — scope §6 names the pulse-app runtime builder as a surface this chunk may touch, so a §2-outcome-1 fix landing there requires the additional runtime smoke gate; whether the fix in fact lands there is research's question (per test-plan.md §3 Boot-smoke gate (conditional)).
- If the verification needs runtime state the harness `run` verb cannot express (fresh `ANDROMEDA_PULSE_DATA_DIR`, sustained `inject_demo` load), the **Direct-binary smoke variant** governs: either profile, seed over the real receiver, assert from the run's own `<data_dir>/logs/agent-latest.jsonl*`, clean shutdown by SPECIFIC pid, ports confirmed released — and the **0-ERROR clean-log assertion binds the GREEN leg only**, a measure-first RED leg records its expected ERROR (target + `reject_reason`) as evidence, each leg on its own fresh data dir (per test-plan.md §3 Direct-binary smoke variant).
- A **one-time live observation does not discharge a coverage obligation**: where a fix's production wiring stays unpinned, the owed test must be minted as a §1 pending-coverage-trigger row rather than left standing on smoke evidence — this is the plan's recurring "one-time proof standing in for a gate" class (per test-plan.md §1 Pending coverage triggers).
- **Zero-flakiness is a hard budget** — a verdict that depends on blocking-pool scheduling must be deterministic; no retry-once, no `sleep(N)` for synchronization, and `#[ignore]` is reserved for flake quarantine (per test-plan.md §10 Quality Gates + §11 E2E/Quality).
- **Load-shaped verification joins `[profile.load-profiles]`**, whose binary the default profile EXCLUDES — so a load-shaped pin does not run under the standard `nextest --workspace --profile ci` gate and must be invoked explicitly via `cargo xtask perf:load-profiles` (per test-plan.md §10 Load profiles).

## Patterns to follow
- **Test location split**: library-crate pins (`buffer` / `triage` / `viz`) are co-located `#[cfg(test)] mod tests` under `src/`; `pulse-app` is the exception — its `[lib] test = false` means unit-shaped probes live as `pulse-app/tests/*.rs` reaching internals via `pub` + `#[doc(hidden)]` (per test-plan.md §2 Test directory conventions + §4 Conventions → Test file location).
- **Hang-proof DuckDB/mutex probes**: the `buffer` roster's precedent runs the behavioural half on a worker thread under an explicit `recv_timeout` so a hang FAILS rather than wedges — directly applicable to any pin over a blocking-pool or append-path lock (per test-plan.md §4 buffer crate bullet).
- **Injected clock over ambient clock**: `tokio::time::pause()`/`advance()` for retention-style tests, but where a function already takes the instant as an argument the `triage` precedent passes `now_nanos` explicitly as the stronger form (per test-plan.md §7 Time-sensitive data + §4 triage crate bullet).
- **Isolation-pin shape already landed next door**: `viz::query::tests::read_connection_returns_a_distinct_usable_connection` asserts a DISTINCT `Arc` that still sees the same in-memory DB — the model for a pin that a "returns the same handle" regression would redden, with its scope limitation stated in the plan (per test-plan.md §4 viz crate bullet).
- **Run-scope must match build-scope**: narrow a `pulse-app` run with `--filter-expr` / `-E` **under `--workspace`**, not with `-p` (measured rlib-format link failure) (per test-plan.md §3 `run` → Test selection).

## Anti-patterns to avoid
- NEVER mock DuckDB at the integration level, and NEVER share a connection across tests — ephemeral in-memory instance per test, else order-dependent failures (per test-plan.md §11 Integration).
- NEVER test implementation details — pin public module boundaries; for `pulse-app` that means a `pub` + `#[doc(hidden)]` seam rather than reaching into a private closure (per test-plan.md §11 Unit + §4 Conventions).
- NEVER use `sleep(N)` for synchronization or real time without injection — wait on an explicit signal (`health` polling, obs record, channel event) (per test-plan.md §11 E2E + §11 Universal).

## Contract bindings
- **tests ↔ obs (log format / rotated family)** — §3 `logs` requires resolving the ROTATED `agent-latest.jsonl*` family across three precedence-ordered bases, newest match within the first base that resolves, never a bare name and never a `*.log` glob; this binds to obs-plan §3 daily rotation and is load-bearing for reading this chunk's durable wedge record (`…/logs/agent-latest.jsonl.2026-08-25`) and any new leg's artifacts.
- **tests ↔ obs (status endpoint)** — §3 Status endpoint shape requires `subsystems.buffer.{status,rows_ingested,retention_seconds}` and `subsystems.ingest_channel.{status,broadcast_subscribers}`; agent readiness/progress reads bind to those fields.
- **tests ↔ obs (stall semantics)** — `check:ingest-progress`'s arms bind to the obs-plan §3/§10 stall definition; §3 records that the tick-ABSENCE definition was satisfied throughout the measured wedge while nothing persisted, which is why the gate keys on progress.
- **tests ↔ obs (new fields)** — scope §6's exact-leaf discipline means any new obs field this chunk emits owes a **field-set pin**; that pin is a test artifact, and §1's trigger rows record the failure mode where an allowlist-boundary assertion is mistaken for a behavioural one.
