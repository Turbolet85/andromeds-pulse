## Relevance
Partial — backend-only value-kind repair with no new UI surface; two real ties (the a11y fixture/bindings mirror and the p9 report surface fed by the incident path).

## Constraints
- Backend crates carry no a11y surface: `triage` / `buffer` / the OTLP + IPC layers are classed **not-assertable**; a11y assertions attach only to `desktop-webview` / `desktop-native` / `os-notification` (per a11y-plan.md §1 A11y Scope Summary, assertability table). A pure producer repair owes no ARIA / focus / contrast / motion work.
- Standing rule — every new route/modal adds one axe spec **in the same chunk**, and fixture payloads live in `helpers/v02-fixtures.ts` (per a11y-plan.md §3 Harness wiring & conventions). The scope's expected `triage::contract` type change is the trigger to check: if the IPC-facing incident/report payload shape moves, the hand-mirrored fixtures must move with it in this chunk.
- Suite-health check is mandatory whenever bindings or fixtures shift: `npx playwright test --list` — a list-time import failure once silently disabled the whole suite (per a11y-plan.md §3 Harness wiring & conventions).
- Zero-new-violations-per-PR is a hard gate at Standard tier, compared against `baselines/a11y-violations-summary.json` (clean pass = 0 violation tuples; informational Lighthouse-score tuples allowed) (per a11y-plan.md §3 Harness wiring & conventions + §10 SLO Invariants). This applies to backend-only chunks too — no soft gate, no retry-once.
- The **p9 diagnostic report modal** is inside the must-be-accessible set P1–P12 (per a11y-plan.md §1, surface-set extension note after the Critical paths table). Its "Previously Seen" subsection is rendered from the same `select_previously_seen` path named in this chunk's Known-consequence section; whether repairing the producer changes anything the p9 surface renders (and therefore whether its fixture/axe spec must change) is research's question.
- Any a11y assertion output this chunk produces must use the structured violation JSON shape — `target: "a11y::assertion"` with `wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` / `remediation` / `tool` / `tool_result_id` (per a11y-plan.md §3 Structured violation JSON schema).

## Anti-patterns to avoid
- NEVER claim WCAG conformance without machine-verifiable evidence (per a11y-plan.md §11 Strategy) — "backend-only, a11y unaffected" is not an a11y conclusion unless the suite ran or its scope was demonstrably untouched.
- NEVER skip the per-PR regression diff at Standard+ tier (per a11y-plan.md §11 SLO) — the baseline comparison still runs for a backend chunk.
- NEVER defer a11y to post-merge / "fix in follow-up" (per a11y-plan.md §11 CI) — if the contract change breaks a fixture or spec, it is repaired in this chunk.

## Contract bindings
- **a11y ↔ tests:** the a11y harness reuses tests' 5-command E2E driver and runs in the same `ci.yml` pipeline as tests E2E (per a11y-plan.md §3 Focus management test harness + §9 Pipeline integration) — this chunk's three pinned producer tests share that pipeline; a a11y-suite break surfaces as a tests-pipeline failure.
- **a11y ↔ obs:** violation JSON is emitted in obs's structured log format (`target: "a11y::assertion"`, `level: "ERROR"`, `fields.*`) per obs §6 binding (per a11y-plan.md §3 Structured violation JSON schema).
- **a11y ↔ IPC bindings:** `tests-a11y/helpers/v02-fixtures.ts` mirrors the specta-generated TauRPC binding types by hand, so a `triage::contract` type change is the coupling point. Note the webview-facing incident view is documented in `pulse-app/ui/src/bindings/index.ts` as dropping the fingerprint string ("internal grouping identifier; not user-relevant") — whether that still holds after this chunk's contract change, and therefore whether any fixture/axe spec must change, is research's question.
