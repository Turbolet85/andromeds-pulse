## Constraints
- **Default-deny allowlist governs every field the repaired producer emits.** obs-plan.md §8 (Default-deny posture) requires each target to resolve to an EXACT `for_target` leaf; unlisted fields are redacted, and **no bare `interpretation` / `triage` / `incidents` prefix key may exist** (a prefix key silently widens every sibling target to one field set). If this chunk changes the emitted field set at the incident producer, §8 requires the leaf and an obs amendment.
- **The `interpretation.incident.created` leaf is enumerated as exactly four fields** — `created`, `deduped`, `severity`, `priority_tier` — with an explicit ban on incident identity, `scope_id`, workspace, title/detail, and payload (obs-plan.md §8). A `fingerprint` field is **not** in that leaf today, and §8 mandates the leaf equal what the emit site emits ("ALL FOUR fields … a two-field entry would leave the target PARTLY redacted" is the governing precedent). *Whether the producer already emits any fingerprint-bearing field is research's question.*
- **A 32-char hex hash is an unbounded label.** obs-plan.md §5 (Metric label cardinality discipline) bounds product-internal metric labels to enumerated values, and §4 bars high-cardinality span names. The fingerprint must not become a metric label, a span-name component, or a per-event dimension.
- **Fingerprint-feed health is a tick-aggregated FIELD signal, not a per-event emission.** obs-plan.md §5 (Conceptual instrument types → tick-aggregated counter row) requires `span_events_seen` / `fingerprints_computed` / `observer_invocations` to ride the existing 15s `buffer.tick` as fields rather than separate `metric.buffer.*` targets, folded once per batch; per-span-event emission is barred by the §11 hot-path rule.
- **`buffer`'s allowlist is aggregate-counts-only.** obs-plan.md §8 states the three feed counters carry "aggregate counts only — never service / span / **fingerprint identity**". This directly constrains any instrumentation added along the `crates/buffer/src/fingerprint.rs` → cue → incident path.
- **New WARNs need bounded emission discipline and dual registration.** obs-plan.md §6 (Log levels mapping, `warn` row) requires once-per-boot / once-per-query discipline (never per row) for degraded-state WARNs, and §8 requires a matching EXACT leaf — a §8-only registration leaves §6 stale (the 2026-08-16 duplicate-occurrence rule). Applies if the repair introduces a "cue synthesized without fingerprint" or "fingerprint unavailable" signal.
- **Module-boundary errors log at WARN/ERROR with an error category, not a stack trace** (obs-plan.md §10 Standard+ invariants; §7 Vector-2 sanitization).

## Patterns to follow
- **EXACT-leaf registration with the `for_target` prefix-fallback rationale** — obs-plan.md §8 precedents: `app.boot.buffer.degraded`, `app.boot.workspace_key`, the four corpus leaves, `triage.baseline.bootstrap_window.override`, `interpretation.incident.created`. Each is registered as a full-path leaf precisely because a prefix would resolve to an unrelated field set.
- **Allowlist guards live under `pulse-app/tests/`, not in `observability.rs`'s own `mod tests`** — obs-plan.md §8 records that `[lib] test = false` compiles but never runs src-level guards; `pulse-app/tests/unit_incident_producer.rs` is named there as the **live PII guard for this exact emit site** (title-canary + `scope_id` bans), and the field-completeness half is explicitly recorded as NOT running. The chunk's pinned producer tests land in this neighborhood.
- **Positive-reading counter shape** — obs-plan.md §5 records that equality of `observer_invocations` with `fingerprints_computed` makes a live feed a POSITIVE reading, replacing inference-from-downstream-silence. If this chunk wants evidence the cue arm now carries a real fingerprint, that is the sanctioned shape (tick fields, not new targets).
- **Span naming / kind** — `{module}.{operation}` with `span.kind = "internal"` for internal operations (obs-plan.md §4).
- **Binding log-format schema** — JSON-per-line with `timestamp` / `level` / `target` / `message` / `fields{}` plus default subscriber identity fields (obs-plan.md §3, §6).

## Anti-patterns to avoid
- **Never log the fingerprint's source material** — `exception.type` and stack-frame text are raw OTLP attribute values; obs-plan.md §11 (Spans, Logs) and §8 Vector 1 permit only `attributes_count` + `service_name_tag` at that boundary. The hash may be anonymized; its inputs are not.
- **Never add per-span-event or per-cue instrumentation on the fingerprint path, and never at `info` in a hot path** (obs-plan.md §11 Telemetry Strategy + Logs).
- **Never use the fingerprint as a metric label or high-cardinality span name** (obs-plan.md §11 Metrics; §5 cardinality discipline).

- **obs ↔ security** — obs-plan.md §8 PII vectors 1/5 derive from the security plan; the triage contract's "anonymized fingerprint hash" wording is the property that would make the value PII-safe *in principle*, but §8's default-deny still requires an explicit leaf before any such field is emitted unredacted.
