# a11y extract

## Relevance
partial. The chunk adds no UI surface, component, control, or text or state rendering. Its a11y exposure is limited to three points: it edits `ci.yml`, where the `a11y` matrix job also lives; it edits the shared 5-command harness (`agent-run.ps1` boot/status), which the a11y suites reuse; and a frame-sample run may drive the WebGPU canvas loop, which the SC 2.3.3 reduced-motion mandate governs.

## Constraints
- a11y-plan §9 CI Integration and §3 CI integration require that a11y assertions run in the same `ci.yml` pipeline as their own blocking `a11y` matrix job on Linux, macOS and Windows. Its gate conditions (axe critical/serious, Lighthouse < 90, focus-order failure, contrast mismatch) must stay hard fails. The chunk's `ci.yml` edits (the release-job cache key, any new sample-producing leg) must not weaken or reorder that job. Whether the `a11y` job restores a rust cache key that the cache reallocation touches is a question for research.
- a11y-plan §9 (the "Reuses tests' boot / run / status / cleanup / logs harness" bullet) and §3 Focus management test harness (its contract binding to the 5-command discipline) require the a11y focus and keyboard harness to reuse the tests' `boot`/`status` driver. The `agent-run.ps1` spawn/exit recorder mirror must leave `boot`/`status`/`cleanup` backward-compatible for those consumers. Adding a real `ended` is additive and must not change the other fields they read.
- a11y-plan §10 (Performance budget per a11y CI run) requires the a11y CI run plus the tests' E2E run to finish in under 10 min. If a new sample-producing leg shares a runner or job with the a11y or E2E path, it must not push that path over the budget. The scope's "CI speed is a priority" constraint is the chunk-side twin of this rule.
- a11y-plan §6 Motion tokens and §1 A11y triggers (motion-sensitive row) require every animation, the WebGPU canvas frame loop included, to degrade under `prefers-reduced-motion: reduce` (WCAG 2.1 AAA SC 2.3.3) and to stay within SC 2.3.1 Three Flashes. A run that drives frames to produce `metric.webgpu.frame_duration_ms` samples must get them without disabling or bypassing that override. Two things are open for research: whether the canvas loop emits frame samples when reduce is set, and which reduced-motion state a CI sample run gets.
- a11y-plan §3 Harness wiring & conventions requires fixtures to be POPULATED, because an empty input "passes by comparing nothing". The chunk's vacuous-gate guard (scope item 3) applies the same principle to the perf gate. The a11y suites themselves are not changed.

## Patterns to follow
- The vacuity rule in a11y-plan §3 Harness wiring & conventions: a gate over empty input must not read as a pass. It is the domain precedent for the sample-presence floor or hard fail that P4 chooses.
- The a11y-plan §10 and §11 SLO stance: every a11y gate is a hard build failure with no soft threshold. The perf arms' FAIL-over-budget behaviour follows the same hard-gate posture.
- The a11y-plan §3 CI integration job shape: its own matrix job, blocking, parallel to the test jobs, with artifacts uploaded under per-OS names and `if: always()`. If P4 picks a new dedicated sample leg, the a11y job's shape is the in-repo precedent for adding a parallel job without lengthening the critical path.

## Anti-patterns to avoid
- Never let an animation loop ignore `prefers-reduced-motion: reduce`, and never force motion on to manufacture samples (per a11y-plan §11 Motion and §11 Visual). Frame-sample generation must not strip, stub or override the canvas loop's reduced-motion check.
- Never skip a11y on CI failure, add a soft or retry-once gate, or defer a11y to post-merge (per a11y-plan §11 CI and §11 SLO). The cache and job restructuring must not make the `a11y` job conditional, non-blocking or `continue-on-error`.

## Contract bindings
- a11y ↔ tests harness: the 5-command `boot`/`run`/`status`/`cleanup`/`logs` driver is shared (a11y-plan §3 Focus management test harness, §9). The `agent-run.ps1` recorder mirror changes a binding the a11y harness consumes.
- a11y ↔ tests CI: the `a11y` matrix job shares `ci.yml` and the round's wall-clock with the test jobs (a11y-plan §3 CI integration, §9, §10 performance budget).
- a11y ↔ design motion: this binding applies only if a frame-sample leg drives the canvas. The reduced-motion override for the frame loop binds to design-system §Motion (a11y-plan §6 Motion tokens).

## Acceptance criteria contributions
- The `a11y` matrix job in `ci.yml` is still present, blocking and unconditional on Linux, macOS and Windows after the cache and job changes, with its four hard-fail gate conditions unchanged. It is green on the chunk's CI round (per a11y-plan §3 CI integration and §9 CI Integration).
- `cargo xtask test:a11y` and its harness `boot`/`status` usage still work on Windows after the `agent-run.ps1` recorder change. `status` gains a non-null `ended` without changing the fields the a11y harness reads (per a11y-plan §3 Focus management test harness).
- If a frame-sample leg is added, the canvas loop's reduced-motion handling is unmodified, and the existing reduced-motion Playwright spec still passes (per a11y-plan §6 Motion tokens and §11 Motion).
- Any new sample-producing leg is costed against the a11y + E2E time budget (under 10 min), and the a11y and E2E path does not exceed that budget (per a11y-plan §10 Performance budget per a11y CI run).
