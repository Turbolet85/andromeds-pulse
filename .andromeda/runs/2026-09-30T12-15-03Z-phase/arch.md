# arch extract

## Relevance
partial. The arch domain owns the CI job topology and cache budget, the xtask/harness CLI contracts (`harness:status`, `agent-run.{sh,ps1}`) and the harness-written `run/` records. The perf budgets and sample semantics belong to obs and tests.

## Constraints
- CI topology and cache budget: arch §Infrastructure Patterns → CI/CD approach fixes seven independent `ci.yml` jobs, and a round lasts as long as its longest job. The `boot` job (Linux) runs the mcp-feature release build, the agent-harness boot smoke and then `cargo xtask ci-gates`. `lint-test` runs `perf:slo-load` on Linux. Rust caches are budgeted against the 10 GB repository cap: only `lint-test-{os}` and `boot-Linux` own target caches; `release`, `mcp-test`, `a11y` and `supply-chain` restore one read-only; `coverage` caches the registry only. Any new sample-producing run, and any change to the `release` job's cache allocation, has to fit this budget. When the allocation changes, the text of this section changes with it.
- CI logic lives in xtask: arch §Established Decisions [CI Task Runner] and §Infrastructure Patterns → CI/CD approach (last bullet) require shared CI logic that needs Rust to live in the `xtask` crate, so the same command runs locally with `cargo xtask <task>`. The sample-bearing log hand-off and any vacuity guard belong in `xtask` (`ci-gates` / `perf-slo-check`), not in inline workflow shell.
- The harness pair is one contract: arch §Occupied Resources → xtask CLI surfaces registers `scripts/agent-run.{sh,ps1}` as a formalized CLI contract. The two scripts move "in lockstep" and keep the five verbs `boot`/`run`/`status`/`cleanup`/`logs`. Today the entry records that `agent-run.ps1` "does not mirror the recorder", so `ended` is null under PowerShell. The CARRY 2 mirror must keep the verb set and exit contracts unchanged.
- The `harness:status` contract is fixed: per arch §Occupied Resources → xtask CLI surfaces, it returns one verdict JSON `{verdict, pid, ended, log_file_basename, last_write_age_seconds, stale_after_seconds}` with four arms and fixed exit codes (0/1/1/2). `ended` is one line, `exit N` or `signal N (NAME)`, bounded to 48 printable ASCII chars; anything else reads as no record, and `ended` is reported only when the verdict is not `running-healthy`. The PowerShell recorder must write bytes this reader accepts. Whether the Windows exit status can be put into that grammar is research's question.
- The `run/` records belong to the harness: per arch §Occupied Resources → Filesystem locations, `run/andromeda-pulse.spawn` and `run/andromeda-pulse.exit` are written by the harness and never by the production binary. `run/andromeda-pulse.pid` is written by the production binary, and the app overwrites the provisional pid that `boot` writes. `boot` takes the app pid from the spawn record, and an app with no spawn record within 5 s is a boot failure.
- Environment variables are registered: per arch §Occupied Resources → Environment variables, harness-only vars such as `ANDROMEDA_PULSE_{PIDFILE,LOGFILE,DATA_DIR_KEEP}` are registered along with their reader sites and "NOT consumed by production binary". Any new env var this chunk introduces, whether a sample-log path, a perf-leg knob or a recorder override, needs a registry entry. A harness-only var also carries the harness-only marker.
- Frame samples use the delegated route: per arch §Occupied Resources → Tauri IPC routes, `metric.webgpu.frame_duration_ms` reaches the log only through `telemetry.frontend.record_frame_ms` (ui-bridge, `FrameDurationInput`). That makes the frame arm depend on a live webview calling that procedure. Whether a CI-reachable run exercises it, and whether production emitters exist for the memory and snapshot targets, are research's questions. If an emitter is added, the code sits in its owning crate under §Cross-cutting Patterns → Module dependency direction (deps flow toward `pulse-app`, a DAG with no reverse edges).

## Patterns to follow
- Scenario-leg shape: follow arch §Occupied Resources → xtask CLI surfaces (`smoke:hue-shift`, `smoke:discovery`). The leg drives the release binary directly by path on a fresh data dir, injects over real OTLP and grades emitted `metric.*` records from the log. Its contract is exit 0 PASS / 1 FAIL / 2 INCONCLUSIVE, with the INCONCLUSIVE arm reserved for an unmet precondition, plus an artifact under `target/<leg>/`. A leg that produces perf samples, or a sample-presence guard with a distinct cannot-evaluate arm, follows this shape.
- Waiting-wrapper recorder: follow arch §Occupied Resources → xtask CLI surfaces (`agent-run.sh boot`). A waiting wrapper writes the app pid to `run/andromeda-pulse.spawn` and, when it reaps the app, writes its end to `run/andromeda-pulse.exit`. `boot` reads the pid from the spawn record, and a failed readiness poll reports `app ended: {record}`. The ps1 mirror copies this sequence.
- Telemetry injection: per arch §Cross-cutting Patterns → Test-time telemetry injection, synthetic telemetry enters over OTLP to the running receiver (`crates/ingest/examples/inject_demo`, whose CLI contract is recorded in §Established Decisions). There is no in-process bypass. Non-default ports are resolved through `ANDROMEDA_PULSE_OTLP_{GRPC,HTTP}_PORT`.
- Output shape: per arch §Cross-cutting Patterns → Development Style (agent-driven), gates produce deterministic, machine-parseable output with a named verdict and an exit-code contract. A vacuity guard reports its sample counts per arm, not only an exit status.

## Anti-patterns to avoid
- No in-process shortcut for samples: arch §Cross-cutting Patterns → Test-time telemetry injection bans an in-process test-mode bypass, a separate "test ingest" flag and a mock-channel back door. This applies to any shortcut that seeds frame, memory or snapshot samples straight into the log or buffer.
- No self-export: arch §Cross-cutting Patterns → Self-observation discipline and §Established Decisions [Self-Observation] forbid pointing the product's own telemetry at its own `:4317`/`:4318`. Samples reach the log only through the `tracing` file sink.
- No unregistered CLI verb: shipping a new or changed xtask verb, CI step or harness verb without its §Occupied Resources → xtask CLI surfaces registration (contract, exit arms, CI wiring or "dev-host only") breaks the formalized-CLI-contract rule the registry applies to every sibling verb.

## Contract bindings
- arch ↔ obs: the three targets `metric.webgpu.frame_duration_ms`, `metric.buffer.memory_bytes` and `metric.snapshot.token_count_ms`, and their budgets, are obs-plan §10 content. Their VACUOUS status is obs-plan §1/§10 content. arch owns only the route: the frame target's TauRPC procedure and the job that runs the gate.
- arch ↔ tests: the per-arm tests for `perf-slo-check` close test-plan §1 `perf-slo-check-arm-coverage`. The harness verbs and the `ended` field are shared with test-plan §3's 5-command harness.
- arch ↔ security: CI workflow edits for the `release` cache and any new step come under security-plan's Supply chain + CI rules (SHA-pinned actions, `contents: read` permissions, harden-runner first). A new harness-only path var comes under the security-plan harness carve-out.

- (arch) The sample-producing run injects telemetry only over real OTLP and adds no in-process bypass (per arch §Cross-cutting Patterns → Test-time telemetry injection).
