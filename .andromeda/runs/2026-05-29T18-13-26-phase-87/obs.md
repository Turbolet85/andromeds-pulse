## Constraints

- Frontend instrumentation MUST remain solely via the TauRPC `telemetry.frontend.*` bridge — no browser OTel SDK, no direct file access from the webview, no browser→backend OTLP recursion. The Halo refactor introduces new input props (`connectionState`, `cumulativeSeverity`) that derive from TauRPC IPC channels (`pulse://stream/incidents`, `pulse://stream/connection-state`) already established in chunks #78/#59 — the frontend reads these via existing TauRPC push channels, not by adding new self-observation emission paths. (per obs-plan §1 desktop-webview surface row + §4 Desktop-webview instrumentation row)
- WebGPU frame timing bridge contract (`telemetry.frontend.record_frame_ms`) must be preserved unmodified through this refactor — the Halo canvas drives `device.queue.onSubmittedWorkDone()` frame-time measurement and bridges it via TauRPC `telemetry.frontend.record_frame_ms` → backend `tracing::info!(target: "metric.webgpu.frame_duration_ms", ...)`. The Halo formula refactor changes WHAT drives the hue+breathing, but must NOT remove the WebGPU frame-time instrumentation call from `HaloCanvas.tsx`. (per obs-plan §5 `metric.webgpu.frame_duration_ms` row + §1 WebView2 surface note)
- Metric cardinality discipline applies to any new `tracing` event targets introduced if the webview bridge emits new telemetry for the severity-driven Halo state. Label fields for severity states MUST be bounded to enumerated values (`"info" | "warn" | "error" | "critical"` for `IncidentSeverity`; `"Listening" | "Receiving" | "Idle" | "Stalled" | "ReceiverFailed" | "Unknown"` for `ConnectionState`). (per obs-plan §5 cardinality discipline + §11 Metrics anti-pattern "NEVER use unbounded label cardinality")
- The `metric.webgpu.frame_duration_ms` SLO (p99 ≤ 33ms) covers the Halo canvas render loop. The refactored Halo must not introduce new per-frame synchronous compute that degrades frame time below the SLO — any severity mapping that runs on the JS main thread per frame must be O(1) lookup. (per obs-plan §10 Performance budgets WebGPU canvas row)

## Patterns к follow

- Frontend metric emission via TauRPC bridge: `HaloCanvas.tsx` currently calls `telemetry.frontend.record_frame_ms(duration_ms, wgpu_backend)` after `device.queue.onSubmittedWorkDone()`. The refactored canvas MUST preserve this call — it is the only approved self-observation path from the webview. (per obs-plan §4 Desktop-webview instrumentation row: "WebGPU frame timing via DOM `performance.now()` + `device.queue.onSubmittedWorkDone()` → TauRPC `telemetry.frontend.record_frame_ms` → backend `tracing::info!(target: "metric.webgpu.frame_duration_ms")`")
- Metric target naming convention `metric.{module}.{measure}` — if any NEW telemetry events are bridged for Halo severity state (e.g., a `metric.halo.severity_tier` event), they must follow the `metric.halo.*` target prefix pattern and carry bounded label fields. (per obs-plan §2 Naming conventions + §5 Metric emission convention)
- Self-observation separation: the incident severity + connection state values flowing INTO the Halo come from the external OTLP analysis pipeline (L4 LLM output, incidents corpus, connection FSM) — these are the PRODUCT's outputs, not its self-observation. The Halo simply renders them. No self-observation instrumentation of the OTLP-derived severity value itself is required in this chunk; the existing L4 inference spans + incident lifecycle spans upstream already cover that path. (per obs-plan §3 "Two cleanly separated surfaces" + §11 "NEVER conflate the product's external snapshot pipeline with the self-observation surface")

## Anti-patterns к avoid

- NEVER remove the `telemetry.frontend.record_frame_ms` call from `HaloCanvas.tsx` when refactoring the canvas render loop — this is the WebGPU SLO instrumentation point and its removal would silently defeat the p99 ≤ 33ms frame-time CI gate. (per obs-plan §11 "NEVER skip spans on critical user-facing paths (P1-P7)" + §10 WebGPU canvas frame SLO)
- NEVER add unbounded `tracing` event fields tied to the severity value derived from incident corpus data (e.g., `incident_id` or `trace_id` from individual incidents as label fields on a Halo metric event) — only bounded enumerated severity tier labels are acceptable. (per obs-plan §11 Metrics anti-pattern "NEVER use unbounded label cardinality")
- NEVER hold a `tracing::Span` guard across `.await` points in any new async Rust code that may be introduced on the connection/severity polling path — the chunk is webview-only so this is unlikely, but if any Rust-side polling is added to the severity bridge, it must use `.in_current_span()` for tokio spawn. (per obs-plan §11 Spans anti-pattern "NEVER hold a `tracing::Span` guard across `.await` points without `.in_current_span()`")
