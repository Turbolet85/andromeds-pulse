## Relevance
relevant — the chunk replaces the model behind the locked L4 runtime decision; its crate placement, swap boundary, pin discipline, env-var registry and Fault Identity measured-effect record are all arch-owned.

## Constraints
- The L4 runtime stays `llama.cpp` prebuilt binaries at the b9305-pinned tag, invoked D1 spawn-per-generation; arch §Established Decisions [LLM Inference Runtime — L4 interpretation layer] requires that a build-tag bump be a deliberate chunk-scoped event, never drift, so a candidate that fails to load on b9305 is disqualified rather than answered with a bump (agrees with the scope Boundary; also mirrored at §Stack and Technologies "AI/ML serving" row and §Inherited Defaults "LLM inference runtime").
- The swap boundary is `pub trait LlmInferenceRunner: Send + Sync` in `crates/interpretation/src/contract.rs`; per arch §Established Decisions [LLM Inference Runtime] only the concrete impl at the binary boundary (`pulse-app/src/llamacli_inference.rs`) may change, and per arch §Cross-cutting Patterns → Module dependency direction no model-specific knowledge may push a reverse edge into `interpretation` or `triage`.
- The bounded-invocation discipline is required for every candidate: GBNF `--json-schema-file` constrained sampling, `-st` single-turn, explicit `-n {max_tokens}`, outer `tokio::time::timeout`, `kill_on_drop(true)`, CUDA build `-ngl 99` for gpu tiers / CPU build `-ngl 0` for cpu tiers, selected per `HardwareProfileSource` (per arch §Established Decisions [LLM Inference Runtime]). Whether a candidate's non-thinking configuration can be delivered inside this flag set without new argv shapes is research's question; any added argv flag joins this discipline rather than replacing a bound.
- The model file is selected through the registered env-var `ANDROMEDA_PULSE_MODEL_PATH` (and the CUDA/CPU binaries through `ANDROMEDA_PULSE_LLAMA_{CUDA,CPU}_BIN_PATH`), all under the `ANDROMEDA_PULSE_L4_ALLOW_ROOT` opt-in confinement and fail-closed root posture (per arch §Occupied Resources → environment variables). Shipping a new L4 default must reuse these vars; whether any code-side default model name/path exists beside the env var is research's question (the scope's "model path resolution and defaults" surface).
- Config precedence is env > `config.toml` > built-in defaults (per arch §Cross-cutting Patterns → Config management / §Inherited Defaults); a shipped "default model" must sit in that order and must not introduce a `Settings` field or `config.toml` key unless deliberately decided (the L4 path vars are env-layer only per §Occupied Resources `ANDROMEDA_PULSE_L4_ALLOW_ROOT` entry).
- The model-distribution question is an OPEN caveat in arch §Established Decisions [LLM Inference Runtime] ("prebuilt-binary distribution is unsettled … co-design with the `ANDROMEDA_PULSE_MODEL_PATH` model-file distribution decision"); "ship as the L4 default" must not silently settle bundling/download — it either stays the env-var dev pattern or is surfaced as a decision.
- Local-first, zero-egress (per arch §Design Philosophy "Local-first, zero-infrastructure"): candidate acquisition is a dev-host operator act into gitignored `AI-Model/`; the product binary must gain no network fetch of a model.

## Patterns to follow
- Trait-at-lower-crate / concrete-impl-at-binary-boundary swap (per arch §Established Decisions [LLM Inference Runtime] "Bus-factor / swap paths"): a model change is a data/config change behind the existing `LlamaCliInference`, not a new runner.
- Model identity surfaces through existing contracts only: `ModelIdentity` / `ModelLoadEvent` on `pulse://stream/model-status` and `model.current_profile` → `ModelProfilePayload.model_identity_name` (per arch §Occupied Resources → Tauri IPC routes `model.current_profile`); a changed identity value flows through these without a new procedure, so no `EXPECTED_PROCEDURES` change is expected.
- Measured-effect recording in arch §Established Decisions [Fault Identity]: the record names the v2.5 lineage, its two-slot measured effect (selection vs confirmation, `FAIL · rank1 34/40`) and states the remainder "is owned by the L4 model-replacement route entry" — this chunk is that owner, so its series result is recorded in the same shape (selection slot · confirmation slot · held-out shapes · record-only stem) at wrap.
- Deterministic runner (`ANDROMEDA_PULSE_L4_DETERMINISTIC`, per arch §Occupied Resources → environment variables) stays independent of the real-model choice; the canned `L4Output` path needs no model.

## Anti-patterns to avoid
- Bumping llama.cpp past b9305 or swapping to a sibling impl (`llama-server` D2 / `llama-cpp-2` / `candle`) to make a candidate load (per arch §Established Decisions [LLM Inference Runtime] pin discipline + "only the concrete impl changes").
- Changing the v2.5 prompt framing or folding chat-template/thinking handling silently into the prompt — the framing is framing-not-identity recorded in arch §Established Decisions [Fault Identity] and is the fixed input the candidates are measured against.
- Introducing a new env var outside the `ANDROMEDA_PULSE_*` registry, or a new TauRPC procedure / `Settings` field for model selection, without a registry entry in arch §Occupied Resources.

## Contract bindings
- arch ↔ security: the model/binary path vars' traversal-reject + length bound + canonicalize + regular-file + opt-in confinement guard (arch §Occupied Resources `ANDROMEDA_PULSE_MODEL_PATH` / `_L4_ALLOW_ROOT`; security-plan §Security Anti-Patterns → Input) and the ASCII-only argv template rule bind any new argv flag (e.g. a chat-template or reasoning switch).
- arch ↔ obs: `interpretation.model.load` / `interpretation.model.allow_root` emit basename-only identity; a new model basename rides those records.
- arch ↔ tests: the probe `pulse-app/examples/l4_decision_probe.rs` and the frozen grader are the measurement instrument whose result lands in arch §Established Decisions [Fault Identity].
- arch ↔ build: `ANDROMEDA_LLAMA3_TOKENIZER_PATH` (arch §Occupied Resources → environment variables) shows `crates/triage/build.rs` bakes a Llama-3 `tokenizer.json` into the build; whether that tokenizer feeds L4 prompt/token budgeting (and so mis-sizes a Qwen3.5/Gemma 4 prompt) is research's question.

## Acceptance criteria contributions
- (arch) The `LlmInferenceRunner` trait surface in `crates/interpretation/src/contract.rs` is unchanged and any code delta for the model swap lives in `pulse-app` at the binary boundary; no new crate-to-crate dependency edge (per arch §Established Decisions [LLM Inference Runtime] + §Cross-cutting Patterns → Module dependency direction).
- (arch) The llama.cpp tag stays b9305 for both CUDA and CPU binaries and every candidate generation uses `--json-schema-file` + `-st` + `-n` + outer timeout (per arch §Established Decisions [LLM Inference Runtime]).
- (arch) No new env var, TauRPC procedure, `Settings` field or `config.toml` key unless registered in arch §Occupied Resources at wrap; the shipped default reaches the runtime through `ANDROMEDA_PULSE_MODEL_PATH` (per arch §Occupied Resources → environment variables).
- (arch) At wrap, arch §Established Decisions [LLM Inference Runtime] names the chosen model (or records that none was selected) and §Established Decisions [Fault Identity] records the series' measured effect and closes or re-homes the "owned by the L4 model-replacement route entry" remainder (per arch §Established Decisions [Fault Identity]).
