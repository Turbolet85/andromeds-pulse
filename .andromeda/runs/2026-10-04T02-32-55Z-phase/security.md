# security extract

## Relevance
relevant — the chunk changes how the corpus encryption key is first created in the OS credential store. That key is a secret the plan names (security-plan §Secret Management → What counts as secret, corpus encryption key) and it protects the encrypted corpus (security-plan §Data Protection, persistent incident corpus).

## Constraints
- The corpus key is secret-class. Key bytes (generated, read back or compared) must never be logged or exported. Every key-handling call site the chunk adds or touches (lock acquisition, generate, set, read-back verify) keeps the `#[tracing::instrument(skip(key))]` + scrubber discipline (per security-plan §Secret Management → What counts as secret, corpus encryption key bullet).
- The fail-closed custody posture stays. The passphrase fallback is opt-in, so a transient store failure must never silently switch keys and orphan rows, and a host with no reachable store and no passphrase degrades the corpus to absent instead of inventing a key. A lock that cannot be acquired, or a read-back that disagrees with the write, has to land on this fail-closed side. It must never fall through to an unlocked create or to the fallback when no passphrase is configured (per security-plan §Secret Management → Runtime, the fallback-is-opt-in clause).
- The once-per-machine, cross-process-persistent key is the stated guarantee: "each installation derives an independent per-machine key on first boot and reuses it thereafter". Concurrent first-run processes minting different keys violates it, and the fix restores it for the concurrent case (per security-plan §Secret Management → Production / dev separation and §Secret Management → Runtime "the key persists across processes").
- No plaintext runtime state on disk. A lock file, if one is added, may hold no key material, no passphrase and no key-derived bytes. It is a coordination artifact only, and the passphrase path still writes nothing to disk (per security-plan §Data Protection, the persistent incident corpus bullet "No plaintext runtime state on disk", and §Secret Management → Runtime "nothing written to disk").
- Never log a full product-consumed filesystem path. A lock-file location (data-dir-derived or a per-user fixed location) appears in logs and errors as a basename only (per security-plan §Security Anti-Patterns → Logging, the full-path ban that is categorical since 2026-08-30).
- If the lock location comes from a product-binary `ANDROMEDA_PULSE_*_PATH` / `*_DIR` env var (for example the data dir), it must be canonicalized on both sides and confined under the resolved data dir. A NEW path env var falls under the same ban (per security-plan §Security Anti-Patterns → Input, the product-binary path env var ban). Whether the existing data-dir resolution at the `Corpus::open` construction sites already satisfies this is research's question.
- Errors the new lock/verify arms surface must stay sanitized at any boundary they reach: no file paths, struct names or library versions. Across TauRPC that means `AppError::Storage`, and across the MCP sidecar a JSON-RPC 2.0 error object (per security-plan §Error Handling, the external responses clause).

## Patterns to follow
- The opt-in passphrase fallback stays deterministic. It is BLAKE3-derived with the service id folded in and touches neither the store nor disk, which is why the lock covers only the OS-store create path (per security-plan §Secret Management → Runtime, "The fallback secret source is the environment").
- Prove the key survives a real process boundary by re-executing the test's own binary. An in-process check passed even while the key was broken, because keyring's mock store is process-global. A concurrency witness for this race needs the same real-process shape to be non-vacuous (per security-plan §Secret Management → Runtime, the 2026-08-15 measurement).
- Use the `std` both-sides-canonicalize primitive on the `publish_workspace_key` precedent for any path the lock location derives from. It is the project's single path primitive; `strict-path` was dropped (per security-plan §Security Anti-Patterns → Input, NARROWED EXCEPTION paragraph).
- Leave the boot-time inventory-then-purge disposition (`corpus::disposition`) alone as the way existing orphans are retired. The chunk prevents new orphaning and does not change how existing orphans are recovered (per security-plan §Secret Management → Runtime, last sentence).

## Anti-patterns to avoid
- Never add a workspace dependency (e.g. a third-party file-lock crate) without it passing `cargo deny check bans licenses sources` and `cargo audit`. `multiple-versions = "deny"` is never relaxed for it. The scope prefers the std file lock, so no dep delta is expected (per security-plan §Dependency Security, CI integration and duplicate-version carve-outs).
- Never log key material, the fallback passphrase or a full lock/data-dir path. This includes error `Display` text that embeds a path (per security-plan §Security Anti-Patterns → Logging and §Secret Management → What counts as secret).
- Never read a new or existing product path env var for the lock location without canonicalize + data-dir confinement (per security-plan §Security Anti-Patterns → Input).

## Contract bindings
- security ↔ tests: the race witness must be a real multi-process (or barrier-synchronized) leg that is RED on HEAD's get-then-set. When no platform credential store is present it must print an explicit `[skip]` or use a store the test controls, never a vacuous green. This mirrors the real-process-boundary proof security-plan §Secret Management → Runtime relies on. The test-plan owns the leg's shape.
- security ↔ obs: any new record for lock acquire/contend/fail carries no key bytes and a lock path by basename only (security-plan §Security Anti-Patterns → Logging). The once-per-boot fallback WARN (security-plan §Secret Management → Runtime) is unchanged, and the new arms must not add a second fallback announcement. The obs-plan owns the event name and allowlist leaf.
- security ↔ arch: a lock file at a new on-disk location is an occupied resource. The arch §Occupied Resources entry and the security-plan §Data Protection data-at-rest list both need it named if P4 adds one (location, no key material).

## Acceptance criteria contributions
- (security) Concurrent first-run processes against one empty credential store all return the same 32-byte key, and that key is the one the store holds afterwards. A store or lock failure with no passphrase configured returns the store's error and never a freshly minted unlocked key (per security-plan §Secret Management → Runtime).
- (security) A grep of the chunk's new log and error sites shows no key bytes, no passphrase and no full lock/data-dir path (basename only), and any lock file on disk contains no key material (per security-plan §Security Anti-Patterns → Logging and §Data Protection).
- (security) `cargo deny check bans licenses sources` passes and `cargo audit` exits 0, with no workspace dependency added unless P4 justifies one (per security-plan §Dependency Security).
- (security) If the lock location comes from a product path env var, a `..`-bearing or out-of-data-dir value is rejected before use (per security-plan §Security Anti-Patterns → Input).
