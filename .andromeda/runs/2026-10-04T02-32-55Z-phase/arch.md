# arch extract

## Relevance
relevant: the change sits in the `corpus` crate's key-sourcing path, which architecture owns through the Stack row, the corpus at-rest posture, the data-dir subpath registry and the cross-process topology (the app plus its MCP sidecar).

## Constraints
- The fix stays inside the locked `corpus` workspace crate. Callers that construct the backend (`pulse-app`, the `mcp-server` sidecar, tests) may change only over dependency edges that already exist (`pulse-app → corpus`, `mcp-server → corpus`). No new crate, no reverse edge, no sibling dependency (per architecture §Occupied Resources → Cargo workspace crate names; §Cross-cutting Patterns → Module dependency direction; §Established Decisions [Module Boundaries]).
- Key sourcing stays as declared. The OS credential store via `keyring` 3, with its explicit platform feature set, is the primary source. The opt-in `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` BLAKE3 fallback engages only when configured. On a host with neither, the corpus degrades to absent and never invents a key. A lock that cannot be acquired must not reach an unlocked create or a silent key switch (per architecture §Stack and Technologies → Secret / key storage; §Occupied Resources → Corpus SQLite → At-rest posture).
- The key must persist across processes. The at-rest posture records the cross-process guarantee: a key one process writes is the key every later process decrypts with. This chunk extends that guarantee to concurrent first creation. The two named concurrent consumers are the one Tauri process and the optional `andromeda-pulse-mcp` sidecar (per architecture §Occupied Resources → Corpus SQLite → At-rest posture; §Infrastructure Patterns → runtime topology).
- Any new on-disk artifact, such as a lock file, belongs under the resolved data-dir root, so `ANDROMEDA_PULSE_DATA_DIR` relocates it like every other subpath. It must be recorded as a new subpath in the data-dir registry when the chunk wraps. A fixed per-user location outside that root would be the first data-dir-escaping artifact besides the training-export sink. Whether one is needed is P3/P4's question (per architecture §Occupied Resources → Filesystem locations → Subpaths under the resolved root; `ANDROMEDA_PULSE_DATA_DIR`).
- No new `ANDROMEDA_PULSE_*` env var unless P4 finds one necessary. If one is added, it must be registered in the env-var list with its consumer class (product vs harness) (per architecture §Occupied Resources → env vars; §Cross-cutting Patterns → Config management).
- The key format, the corpus schema, the five reserved tables and the ladder migration are out of scope. No DDL and no `SCHEMA_VERSION` change. The orphan disposition (`corpus::disposition`) stays untouched (per architecture §Occupied Resources → Corpus SQLite / schema names; At-rest posture → orphan retirement).
- Toolchain floor: the arch's stated language baseline is "rustc 1.84+". A std `File::lock` choice needs 1.89. The real floor is set by the pinned toolchain (`rust-toolchain.toml`), and research must confirm that it allows the API. If the API is adopted, the arch baseline line becomes a wrap-time amendment candidate (per architecture §Established Decisions [Primary Language]; §Inherited Defaults → Language / runtime).

## Patterns to follow
- **The cross-process `run/workspace-key` artifact.** It is the existing model for state that the app and the sidecar coordinate through a file under the data dir: an atomic `.tmp`+rename write, a canonicalize-and-confine guard, and a bounded read. A lock file should take the same location discipline (under the data dir, confined, logged by basename only) (per architecture §Occupied Resources → Filesystem locations → `run/workspace-key`).
- **Arbitration at the single choke point every writer passes through.** The Corpus Write Arbitration decision put the guard at the one layer all seven writers share, including the sidecar that bypasses the `triage` trait. By analogy, the create-or-read lock belongs in `OsKeychainBackend`'s fetch path, which both the app and the sidecar call, not at one caller (per architecture §Established Decisions [Corpus Write Arbitration]).
- **The read-back as the authoritative value.** The same decision makes the stored row the truth. A losing write is an expected outcome, not a fault. Here that means the key a process returns is the one the store holds after the set (per architecture §Established Decisions [Corpus Write Arbitration]).
- **Error handling.** Module-internal errors in `corpus` use `thiserror`. Lock-acquisition failure is a new variant (or an existing store-error path) that surfaces to the caller, never a panic. `main.rs` boundaries use `anyhow` (per architecture §Conventions → Error response schema; §Established Decisions [Error Handling Pattern]).

## Anti-patterns to avoid
- An in-process-only `Mutex` / `OnceLock` presented as the fix. The topology has at least two processes sharing one credential-store entry, so an in-process lock leaves the cross-process race open (per architecture §Infrastructure Patterns → runtime topology).
- Falling through to an unlocked generate-and-set, or to an ephemeral per-process key, when the lock or the store fails. Either one reproduces the orphaning that the at-rest posture and the disposition exist to retire (per architecture §Occupied Resources → Corpus SQLite → At-rest posture; §Stack and Technologies → Secret / key storage).
- Building the lock path by joining an unvalidated env-var string. Any data-dir-derived location takes the existing canonicalize-and-confine discipline (per architecture §Occupied Resources → Filesystem locations → `run/workspace-key` guard).

## Contract bindings
- **arch ↔ security.** Key custody and the fail-closed posture belong to architecture's at-rest entry. The basename-only logging of any lock path and the no-key-material ban are enforced by security-plan §Logging and `.claude/rules/security.md` §Logging & redaction.
- **arch ↔ tests.** The two-process topology is what the race witness must reproduce: real processes, or barrier-synchronized ones, against one empty store, with a `[skip]` line when no store is present. The order-sensitive cross-process corpus legs (`pulse-app/tests/e2e_p3_mcp_resolve_content.rs`) depend on the shared-key guarantee.
- **arch ↔ obs.** A lock-acquisition failure or contention outcome, if it is logged, must not carry key bytes or a full path (architecture §Cross-cutting Patterns → Self-observation discipline sets the sink; obs-plan owns the record shape).
- **Wrap-time amendments.** A new data-dir subpath (a lock file) and, if `std` file locking is adopted, the Rust baseline line are architecture-amendment candidates (§Occupied Resources → Subpaths; §Inherited Defaults → Language / runtime).

## Acceptance criteria contributions
- (arch) The change is confined to `crates/corpus` plus constructor call-site updates over the existing `pulse-app → corpus` and `mcp-server → corpus` edges. No new workspace crate and no new crate-to-crate edge (per architecture §Cross-cutting Patterns → Module dependency direction; §Occupied Resources → Cargo workspace crate names).
- (arch) N processes resolving the key concurrently against one empty store all return one 32-byte key, and it equals the key the store holds afterwards. With no store and no passphrase, the outcome is still corpus-absent rather than an invented key (per architecture §Occupied Resources → Corpus SQLite → At-rest posture).
- (arch) Any new on-disk artifact lives under the resolved data-dir root, honours `ANDROMEDA_PULSE_DATA_DIR`, and is listed in the subpath registry at wrap. No new `ANDROMEDA_PULSE_*` var unless P4 records why (per architecture §Occupied Resources → Filesystem locations; env vars).
- (arch) The key format, `SCHEMA_VERSION`, the reserved corpus tables and `corpus::disposition` are byte-unchanged. There is no TauRPC procedure, MCP tool, port or capability delta (per architecture §Occupied Resources → Corpus SQLite / schema names; §Standard Contracts).
