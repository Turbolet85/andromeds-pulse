## Constraints

- Post-`prost`-decode invariant checks are mandatory before any batch leaves the `ingest` crate: `span_id` must be 8 bytes, `trace_id` must be 16 bytes, attribute keys/values must be bounded; `prost` only validates wire format (per security-plan §Input Validation row 1 OTLP/gRPC + §Anti-Patterns Input bullet 3 + §Threat Model Summary "OTLP receivers" trust-boundary entry).
- Every invariant rejection MUST collapse to the `serde`-friendly `AppError::Ingest { message }` variant at the bridge with a sanitized one-liner — no stack traces, file paths, library versions, Rust struct names, internal hostnames, or raw OTLP attribute values in the surfaced message (per security-plan §Error Handling TauRPC bridge bullet + §Anti-Patterns Logging bullet 4 `AppError::Internal`-style sanitization rule, applied identically to `AppError::Ingest`).
- `AppError::Ingest` MUST reach the bridge via a `From<thiserror::Error> for AppError` impl in the `ingest` crate; module-internal errors stay `thiserror` 2.x; never serialize an `anyhow::Error` directly across TauRPC (per security-plan §Error Handling TauRPC bullet + §Anti-Patterns Code Patterns bullet 4).
- The OTLP receiver wire-side error envelope (gRPC `tonic::Status` codes + OTLP HTTP `Status` proto / JSON body) is the OTLP-spec response format; do not invent a new envelope and do not leak invariant details into the `Status.message` (per security-plan §Error Handling OTLP receiver bullet + §Anti-Patterns Logging bullets 4–5).
- Invariant violations are logged as "OTLP request rejection" security events but MUST NOT include raw OTLP attribute values, span/log/metric content payloads, or DuckDB-bound query parameters — log the violated rule + bounded counters (e.g., `field=trace_id_length`, `expected=16`, `actual=N`, `service=<resource.service.name-redacted-or-bounded>`) only (per security-plan §Logging & Monitoring "What to log" + "What NEVER to log" bullets 1, 3 + §Anti-Patterns Logging bullets 1, 3).
- The mpsc hand-off MUST exert backpressure rather than drop/`try_send` silently; uncontrolled drop converts a rate-limit / DoS surface back to the receiver path that the §API Security row 1 `tower_governor` cap is sized against. Channel capacity, drop-on-overflow policy, and any drop counter must surface through the existing observability allowlist — not as raw request bodies (per security-plan §API Security row 1 rate-limit posture + §Logging & Monitoring "What to log" OTLP rejections bullet, applied to ingest-channel saturation).
- `ingest` crate MUST NOT introduce new third-party deps without `cargo deny check bans licenses sources` clean (workspace already enforces); any new candidate (e.g., a different channel crate) MUST be reviewed against the `tonic 0.14 ↔ tonic 0.13` duplicate-version canary rule in `deny.toml` (per security-plan §Dependency Security CI integration + §Anti-Patterns Universal bullet 2).

## Patterns to follow

- Boundary-validation pattern in the `ingest` crate: `prost` decode (wire shape) → invariant validator function (semantic shape) → mpsc hand-off → `buffer::Appender`. Rejected payloads collapse to `tonic::Status` (gRPC) or HTTP error response (axum) AND emit a `tracing` event with bounded fields, mirroring the gRPC + HTTP receiver patterns already wired in chunks #16 + #17 (per security-plan §Input Validation row 1 OTLP/gRPC + row 2 OTLP/HTTP).
- Error-conversion pattern: each crate keeps a `thiserror`-derived module-internal enum; the bridge crate (`ui-bridge`) hosts `From<…> for AppError` impls. For chunk #18, the `ingest::Error` enum gets `Ingest` variant(s) for invariant failures + channel saturation, and `From<ingest::Error> for AppError` collapses them to `AppError::Ingest { message }` with a sanitized constant-ish message (per security-plan §Error Handling TauRPC bullet + Conventions Error response schema referenced from arch).
- Capability-aware logging pattern (already established in handoff Tier 2 Session Additions for chunk #17): tracing events use dotted target names + bounded fields registered in the observability allowlist; the `AllowList::production().ingest` registry already names `http.method`, `http.status_code`, etc. — chunk #18 extends with invariant-specific bounded fields (e.g., `field`, `expected`, `actual`, `op="invariant"`) and channel-specific fields (e.g., `mpsc.capacity_pct`), following the prefix-strip resolver (per security-plan §Logging & Monitoring log-format bullet + project-side observability rules already in place).
- Sanitization-at-the-boundary pattern: convert `From<ingest::Error> for AppError` MUST stamp a fixed sanitized message ("invalid OTLP payload" / "trace_id length mismatch" — never the raw bytes, never the Rust struct path); full chain stays in the local `tracing` log via `tracing-error` SpanTrace (per security-plan §Error Handling Internal logging paragraph).

## Anti-patterns to avoid

- NEVER skip post-`prost`-decode invariant checks on OTLP payloads — `prost` only validates wire format; missing this is the §Anti-Patterns Input bullet 3 violation that chunk #18 exists to close.
- NEVER log raw OTLP attribute values, span/log/metric content payloads, or DuckDB-bound parameters in invariant-rejection events — they may carry incidentally captured secrets from the instrumented host application (per §Anti-Patterns Logging bullets 1, 3).
- NEVER serialize `anyhow::Error` directly across TauRPC; module-internal `thiserror` enums + the `From … for AppError` impl are the only authorized path to surface ingest invariant failures to the webview (per §Anti-Patterns Code Patterns bullet 4).
- NEVER leak Rust struct names, file paths, or library versions into `AppError::Ingest { message }` — sanitize at the conversion site (per §Anti-Patterns Logging bullet 4 applied to `Ingest` variant by parity with `Internal`).
