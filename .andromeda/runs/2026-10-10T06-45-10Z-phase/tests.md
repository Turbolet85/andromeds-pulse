## Patterns to follow
- Workflow pins are `#[test]` fns in `pulse-app/tests/*.rs` integration targets that read the workflow file from the tree; `pulse-app/tests/quality_gate_workflow.rs` is the home §9 names for them. A new or re-pointed pin goes there or beside it, collected by name in the default workspace run (per test-plan §2 Test directory + naming conventions; per test-plan §9 Matrix builds).
- A comparison that stays follows the in-plan producer-plus-require shape: a producer step writes the input in the same workflow, and the grader reads an empty input as cannot-evaluate (red), never as a pass (per test-plan §9 Pipeline structure, lint-test row; per test-plan §3 Per-chunk gate discipline, the `perf:budget` exit contract).
- A step added to CI is a plain named `run:` step with a 0 / 1 / 2 exit contract, no third-party action, no token and the workflow `permissions:` untouched (per test-plan §9 Pipeline structure, Staged artifacts row and Supply chain row).
- A leg that can skip clean is asserted to have RUN, never read by its exit code alone; a missing prerequisite fails rather than skips, since a skip reads as a pass (per test-plan §9 Pipeline structure, E2E tests row; per test-plan §4 Framework).
- Narrow a `pulse-app` test selection with `-E 'binary(...)'` under `--workspace`, not with `-p`, when iterating on the two workflow-pin binaries (per test-plan §3 `run` → Narrow a `pulse-app` run). The `status` smoke is not owed: the chunk does not touch process health.

## Anti-patterns to avoid
- NEVER leave or add a soft-fail on a gating step: no `continue-on-error`, `retry` or `|| true`, and no retry-once policy; the boot smoke and `Boot series (equal source)` steps stay gating as §9 requires (per test-plan §9 Pipeline structure, Boot smoke row; per test-plan §11 Quality).
- NEVER reference a third-party action by floating tag, and never lower a coverage threshold to make a job pass; a pin whose step is removed is deleted, not `#[ignore]`d (per test-plan §11 CI; per test-plan §10 Zero-flakiness budget).
- NEVER let a one-time reading stand in for a per-run gate, and never make a committed test call an external API: the CI-run reading is evidence, the committed pin reads `ci.yml` on disk (per test-plan §1 Pending coverage triggers; per test-plan §11 Universal).

## Contract bindings
- tests ↔ obs: the uploaded `logs-*` artifacts carry the obs log family, and `perf:budget` / `ci-gates` grade obs-plan §10 budgets over it; settling the `logs-${{ runner.os }}` upload touches obs-plan §9's consumer cells the scope names (test-plan §9 Pipeline structure, lint-test and Boot smoke rows; test-plan §3 `logs`).
- tests ↔ a11y: the `a11y` job's base download and regression-detector are stated in both plans; a fall of that comparison amends test-plan §9's A11y suite row together with a11y-plan §3 CI integration.
- tests ↔ security: a baseline producer is bounded by the SHA-pin rule and the workflow's read-only permissions; whether a cross-run baseline fits under them is security's extract and research's question (test-plan §11 CI; test-plan §9 Pipeline structure, Staged artifacts row).
- tests ↔ arch: a producer that keeps a baseline in the Actions cache meets the cache readings test-plan §9's Coverage report row defers to architecture §Infrastructure Patterns → CI/CD approach.
