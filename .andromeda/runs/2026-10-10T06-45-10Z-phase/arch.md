## Constraints
- The workflow's shape is fixed: six independent jobs on `ubuntu-22.04`, no matrix, no `needs:` edge between jobs (per architecture.md §Infrastructure Patterns → CI/CD approach). A baseline producer built as a seventh job, or as a job another job waits on, changes that sentence and is an arch amendment, not a silent edit. Whether `ci.yml` at the chunk base reads as six such jobs is research's question.
- The trigger block (`pull_request`, `push` on `main`) and the Linux-only reading of the workflow are each held by a named self-lint test, and the two release-build witnesses by a third (per architecture.md §Infrastructure Patterns → CI/CD approach). A producer that needs another trigger, another runner system or a matrix value breaks a pin the plan names; scope already halts a new trigger for the founder.
- A pull-request run builds the pull request's merge ref, and `main`'s own workflow stays the old one until the version reaches it (per architecture.md §Infrastructure Patterns → CI/CD approach). A `-base` baseline meant to be produced by a push run on `main` therefore has no producer from this branch's workflow until the merge; the P4 fork must cost each producer against that, and "equal source" for any cross-run comparison means branch tip and `main` tip both unchanged.
- The Actions cache is budgeted against the 10 GB repository cap and the plan's last recorded reading is over it (per architecture.md §Infrastructure Patterns → CI/CD approach). A producer that keeps a baseline in the cache adds to a budget the plan records as already exceeded; that reading is dated and was not re-read, so the current figure is research's question.
- Shared CI logic that needs Rust lives in the `xtask` crate so the same command runs locally (per architecture.md §Infrastructure Patterns → CI/CD approach). Any new or changed comparison logic, or a check that a file to upload exists, belongs in an xtask verb or in a workflow test, not in inline workflow shell that a contributor cannot run.
- An xtask verb that is a dev/CI gate is registered with its exit contract and its verdict arms (per architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates)). The plan holds no entry for `criterion-regression` or `coverage-regression` and so states no contract for their absent-baseline arm; what each does when its baseline is absent is research's question, and a verb that stays with a changed arm is registered there at wrap.
- No new workspace crate, environment variable or product-written path is called for: the canonical crate list and the reserved variable list are closed sets that a landing resource must be added to (per architecture.md §Occupied Resources → Cargo workspace crate names; per architecture.md §Occupied Resources → Environment variables). Every job's data dir comes from the one `ANDROMEDA_PULSE_DATA_DIR` export after harden-runner (per architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates)).

## Patterns to follow
- The three-arm gate contract: exit 0 pass · 1 findings · 2 cannot-evaluate, where an absent or unreadable input is `cannot-evaluate` and never a pass; `perf:budget` states it as "never PASS over empty input" and `check:staged-artifacts` as "no neutral arm" (per architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates)). A comparison that stays takes this shape for its absent-baseline case.
- A gate wired as a plain named `run:` step: no third-party action, no token, workflow `permissions:` untouched, no soft-fail key (per architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates); the `supply-chain` audit step and the boot series step are the same form per architecture.md §Infrastructure Patterns → CI/CD approach).
- A required-arm upload paired with its producer in the same job: `lint-test` runs the `perf_budget_samples` producer, grades it with `--require memory,snapshot`, and uploads `logs-perf-samples-{os}` (per architecture.md §Infrastructure Patterns → CI/CD approach). An upload that stays has a producer step and a gate that fails when the producer wrote nothing; whether that upload finds its file on the newest run is research's question.
- Each workflow step the plan names is held by a workflow test in `pulse-app/tests/quality_gate_workflow.rs` (per architecture.md §Infrastructure Patterns → CI/CD approach). A step this chunk keeps or removes moves its pin with it, in that file or its sibling, inside the existing `pulse-app` crate (per architecture.md §Cross-cutting Patterns → Module dependency direction).
- Agent-driven development: deterministic invocations, machine-parseable output, `cargo xtask` task surfaces (per architecture.md §Cross-cutting Patterns → Development Style). The chunk's run-level witness is read step by step from such output, not from a job's colour.

## Anti-patterns to avoid
- A gate that reports a neutral or passing verdict over input nobody produced. The plan's own text still carries one of this kind: `cargo xtask ci-gates` and `perf:load-profiles` run the perf grader with no arm required and print `perf-budget NEUTRAL (no log file to grade)` (per architecture.md §Occupied Resources → xtask CLI surfaces (dev/CI gates)). It is neither a baseline comparison nor an upload; whether it is of P-128's kind belongs beside the scope's two "read at take-up" items at P4, and it is not changed here without the operator's word.
- Changing the `boot` job's steps while settling uploads. The smoke step's lines, `Build the exit witness`, the series step (gating, `if: always()`, no soft-fail key) and the `logs-boot-Linux` artifact's recorded membership are fixed by the plan and by named tests (per architecture.md §Infrastructure Patterns → CI/CD approach; per architecture.md §Occupied Resources → Filesystem locations).
- Putting a published-check action, a token input or a soft-fail key back on a step to make an absent input survivable: the plan records the `supply-chain` audit step leaving that form so a push run and a pull-request run end the same (per architecture.md §Infrastructure Patterns → CI/CD approach).
