# security extract

## Relevance
partial — the chunk edits `.github/workflows/ci.yml` and the tests that read it; it crosses no runtime trust boundary of security-plan §Threat Model Summary (no OTLP, IPC, plugin, MCP or product env-var surface). What applies is the plan's CI and supply-chain rule set, and the boundary on what the boot job's artifact may carry.

## Constraints
- Every action reference that stays in or enters `ci.yml` (the `upload-artifact` / `download-artifact` steps the chunk keeps, and any a producer adds) is required to be `<owner>/<repo>@<40-char-SHA> # vX.Y.Z`, never a floating tag (per security-plan §Security Anti-Patterns → Secrets). The plan applies the convention to `actions/*` as well (it requires a SHA-pinned setup-node, per security-plan §Dependency Security → CI integration). Whether each `uses:` line at `6df9e95c` already has that shape is research's question.
- Workflow-level `permissions` is required to be `contents: read`, with per-job elevation to `contents: write` only on a publish step (per security-plan §Secret Management → GitHub Environment scoping). `ci.yml` has no publish step, so the plan gives the chunk no elevation to take. The plan states no rule for any other permission key: a producer that needs one (for example a cross-run artifact read) has no plan coverage and is the founder's, as the scope's boundary already says.
- No signing or release secret may be reachable from a pull-request workflow; all of them are required to live in the `production-release` Environment behind its manual approval gate (per security-plan §Security Anti-Patterns → Secrets). A baseline producer therefore takes no secret and no long-lived token into `ci.yml`.
- The plan's build-fail roster is required to stay hard: a `cargo audit` vulnerability or could-not-evaluate exit, any `cargo deny check` failure, `check:npm-supply-chain` exit 1 or 2, `check:staged-artifacts` exit 1 or 2, and capability-drift each fail the build (per security-plan §Dependency Security → CI integration). No edit of this chunk may put a `continue-on-error` key or a `||` on one of those steps. Whether a guard in the tree reads those steps for a soft-fail key today is research's question; the plan names a pin for the audit step alone.
- The audit step's pinned shape is required to survive any rework of `pulse-app/tests/quality_gate_workflow.rs`: a plain `run: cargo audit` step with no `uses:`, no `with:`, no token, no `continue-on-error`, no `||` and no job-level `permissions:` key, held by `ci_workflow_audit_step_is_a_plain_run_step`, and `cargo audit` is required to be a member of the soft-fail ban's gate list (per security-plan §Dependency Security → CI integration). If the self-lint guard is rewritten here, that membership is kept; whether the list holds it at the chunk base is research's question.
- `step-security/harden-runner`, SHA-pinned, is required as the first step of every job in `ci.yml`, starting at `egress-policy: audit` (per security-plan §Bootstrap phases → `dep-security-ci-gate`). A job the chunk adds (a baseline producer) carries it; a job the chunk only trims keeps it first.
- An upload made to "find its file" may not do so by widening what it uploads: `run/` and the boot series' own data dirs are required to stay out of every artifact, and the harness-written files that ride `logs-boot-Linux` pass no scrubber (per security-plan §Security Anti-Patterns → Input). The exit-witness arm's classification is PROVISIONAL there; the chunk changes nothing of it, and if its proof keeps a `logs-boot-Linux` artifact, the operator's standing stop applies to every witness file in it (read whole; a line beyond its shape stops the reading) and to `xvfb.log` (per security-plan §Security Anti-Patterns → Input).

## Patterns to follow
- An input that cannot be read is its own red arm, never a pass: the npm gate's exit contract keeps cannot-evaluate (exit 2) apart from green and from findings (per security-plan §Dependency Security → CI integration). It is the plan's standing shape for a comparison whose baseline is absent.
- A missing prerequisite fails and never skips: the vendored test-only channel's interpreter requirement is stated that way (per security-plan §Dependency Security → CI integration). The same shape fits a pin that reads what makes a kept upload non-empty.
- A gate step is a plain named `run:` step where no action is needed, so the SHA-pinning convention is not triggered and no token is handed over (per security-plan §Bootstrap phases → `dep-security-ci-gate`). A first-party xtask verb as producer or checker follows it.
- A step that takes the workflow token and reads the event can end differently on a `push` and on a `pull_request` under `contents: read`; the plan records that failure for the step `cargo audit` replaced (per security-plan §Dependency Security → CI integration). The three baseline downloads are pull-request-only, so each kept or replacing step is read on both events.
- Dependabot's `github-actions` ecosystem bumps a pinned SHA and its version comment together (per security-plan §Bootstrap phases → `dep-security-ci-gate`); a new or kept `uses:` line keeps the comment form so that bump still works.

## Anti-patterns to avoid
- NEVER reference an action by `@vN` or any floating tag (per security-plan §Security Anti-Patterns → Secrets).
- NEVER grant `contents: write` at the workflow level (per security-plan §Security Anti-Patterns → Secrets).
- NEVER place release or signing credentials outside the `production-release` Environment (per security-plan §Security Anti-Patterns → Secrets): relevant only if P3's reading draws `release.yml` or `update-channels.yml` into the chunk, which the scope leaves to P4.

## Contract bindings
- security ↔ tests: the CI security gate lives in the one workflow the tests plan owns (test-plan §9), and the soft-fail self-lint guard plus `ci_workflow_audit_step_is_a_plain_run_step` sit in the same test file as the pins this chunk moves (per security-plan §Dependency Security → CI integration). The guard's command list is where the plan's fail roster is or is not mechanically held, which bears on the plan's decision whether the guard rides here.
- security ↔ obs: the `logs-${{ runner.os }}`, `logs-perf-samples` and `logs-boot` uploads carry self-observation log families, whose content rules are the never-log list (per security-plan §Logging & Monitoring → What NEVER to log) and obs-plan §9; removing an upload narrows what leaves the runner, changing its path set is a security reading.
- A stated absence, not coverage: the plan holds no rule on which run may produce a baseline that a later run trusts (a pull-request run's artifact read as a baseline). If P4 chooses a producer, that provenance question has no plan answer and goes to the operator with the fork.
