## Patterns to follow

- Token-derivation discipline per §Self-Validation Protocol §4 Token Test: every value the harness reasons about traces back to the NASA Color World palette names (Deep Control Gray / Earth Blue / Alert Burgundy / Status White-Blue / Stellar Indigo / Feedback Cyan); JSON output should label each pair by its semantic role (e.g. `text-primary/base`, `border-focus/raised-1`) so downstream a11y CI gates can correlate (per design-system.md §Self-Validation Protocol §4 + §Color Palette).
- Surface-scoping: harness operates ONLY on the `desktop-webview` surface tokens; `desktop-native` (tray) explicitly defers contrast to OS-native theming and exposes no custom color tokens (per design-system.md §Surface: desktop-native Tokens — "system tray does not expose custom color control").
- Pairing convention from session-handoff "Next Recommended Action" open question: chunk #11's pre-flight values (`text-primary/base 14.46:1`, `feedback-success/inset 7.20:1`, `border-focus/base 5.12:1`) are candidates for retroactive inclusion in the JSON output schema chunk #12 establishes — the harness is the canonical place to record those ratios going forward (per session-handoff, decision deferred to phase-9 plan).
- Tier-decision precedent: spec table values are *target ratios* (≈ 8.5:1 etc.) and the harness must distinguish between "computed exact ratio" and "documented target" — note in JSON output schema rather than fail on small drift; design-system.md §Color Palette Text Hierarchy uses ≈ deliberately (per design-system.md §Color Palette Text Hierarchy + §Self-Validation Protocol §6 "If implementation values diverge from the table, adjust palette or note deviation in Decisions Log").

## Anti-patterns to avoid

- Do NOT introduce new hex values inside the harness for "expected" comparison — the harness reads `tokens.css` and compares to the spec table values; coding additional hexes inside the harness creates a third source of truth and violates §Token Test (per design-system.md §Self-Validation Protocol §4 + §Anti-Patterns Universal Bans "NEVER use ... Tailwind default palette colors").
- Do NOT validate Halo State Pulse colors (Earth Blue ↔ Alert Burgundy LCH interpolation) as a contrast pair in this harness — Halo is a WebGPU canvas signature element exempt from chrome contrast accounting; it encodes data-driven state via hue, not text/background pairing (per design-system.md §Brand Identity Halo State Pulse + §Anti-Patterns "NEVER use gradient overlays ... The Halo State Pulse ... is the ONLY exception").
- Do NOT treat Muted (#56606E) as a text-on-base contrast failure in JSON output — it is "decorative only" per spec, ratio ≈ 2.1:1 is intentional; harness must mark it as informational rather than violation (per design-system.md §Color Palette Text Hierarchy Muted row).

## Contract bindings

- **design ↔ a11y**: Contrast targets per §Color Palette Text Hierarchy bind to a11y plan WCAG SC 1.4.3 (4.5:1 minimum normal text) / SC 1.4.11 (3:1 non-text). Design owns the *target ratios* (≈ 8.5:1, etc.) and *pair enumeration* (which color × which surface); a11y owns the *formal WCAG pass/fail derivation* and any policy on deviations. The JSON emitted by chunk #12 is the artifact a11y consumes downstream (chunk #13 a11y dev stack + future a11y CI gate). Per design-system.md §Downstream Readiness "For a11y specialist" and §Self-Validation Protocol §6 "the a11y specialist owns the formal WCAG conformance derivation downstream."
- **design ↔ tests**: Per §Downstream Readiness "For tests specialist", contrast values in §Color Palette Text Hierarchy table are tests-lint targets — chunk #12 harness becomes the executable form of that lint, replacing per-component manual assertions. Test plan owns CI invocation; design owns spec input.
- **design ↔ a11y (state-color pairing)**: §Anti-Patterns Universal Bans "NEVER use color purely for decoration" + §Color Palette Semantic Colors mandate state-color be paired with text or icon (not color alone) — this is in-domain for a11y SC 1.4.1 but the design constraint is that semantic pairs (Success/Warning/Error/Info) enumerated in the harness MUST match §Semantic Colors table identifiers (per design-system.md §Color Palette Semantic Colors + §Anti-Patterns Universal Bans).

## Acceptance criteria contributions

- (design) The harness reads the 13 `--color-*` tokens from `pulse-app/ui/dist/tokens.css` (chunk #10 output) and matches each hex byte-exact to the §Color Palette / §Surface Scale / §Text Hierarchy / §Semantic Colors / §Border Progression Focus tables (no hardcoded hexes inside the harness itself).
- (design) JSON output schema enumerates at minimum: each Text Hierarchy level on Base (Primary/Secondary/Tertiary/Muted), each Semantic state pair (Success/Warning/Error/Info), Focus ring (Primary on each Surface level Base/Raised-1/Raised-2/Raised-3/Inset), with a `target_ratio` field reflecting the spec value and a `computed_ratio` field from colorjs.io.
- (design) Tertiary text and Muted text entries are flagged in JSON as `usage: "large-text-only"` and `usage: "decorative-only"` respectively so downstream a11y CI does not false-flag them as SC 1.4.3 violations (per §Color Palette Text Hierarchy notes).
- (design) Halo State Pulse colors (Earth Blue #4A90E2 ↔ Alert Burgundy #8B2E3B LCH interpolation) are NOT enumerated as contrast pairs in JSON output (Halo is signature-element-exempt per §Brand Identity); the harness output is scoped to chrome contrast pairs only.
