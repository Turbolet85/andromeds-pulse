Passphrase fallback REQUIRED only when OS keychain unavailable; passphrase MUST be salted-KDF derived (Argon2id or scrypt), not raw-hashed.
- DuckDB encryption MUST remain DISABLED — chunk #68 must NOT flip on DuckDB encryption to handle corpus separately because CVE-2025-64429 (per security plan §Data Protection §At rest line 151 + §Code Patterns Data Protection ban line 394) is documented against DuckDB encryption-at-rest. Corpus = `rusqlite` separate from the existing in-memory `pulse_buffer` DuckDB; the ban on DuckDB encryption-at-rest is unaffected and MUST be preserved.
- All SQL against the corpus MUST use `rusqlite` prepared statements with `?` placeholders + parameter binding — NEVER `format!("INSERT INTO incidents (workspace) VALUES ('{}')", ...)`. Same prepared-statement discipline applied to DuckDB extends to SQLite (per security plan §Input Validation row "DuckDB query parameters" + §Code Patterns Input ban line 382 — the Dagster GHSA-mjw2-v2hm-wj34 / Vanna CVE-2024-5827 cluster is SQL-engine-agnostic; rusqlite has the identical class).
- Corpus file path MUST canonicalize via `strict-path` + assert resolved path lives under the per-platform resolved data dir (`~/.andromeda-pulse/` Linux / `~/Library/Application Support/com.andromeda.pulse/` macOS / `%APPDATA%\andromeda-pulse\` Windows or the `ANDROMEDA_PULSE_DATA_DIR` override) — same canonicalize-and-confine discipline that snapshot dir + plugin dir + config path are required to follow (per security plan §Input Validation row "Configuration values" + §Code Patterns NEVER ban line 384 path traversal CWE-22).
- The PII scrubber primitive MUST run at corpus ingestion BEFORE persistence — never store raw OTLP attribute values that could echo back through `storage.inspect()`, future export (P-046), or LLM retrieval (P-044). Scrubber categories: email addresses, JWT tokens, bearer tokens, API keys, credit card patterns, SSN patterns, key-value pairs where key matches secret-like patterns (per capability spec P-047 + cross-reference to security plan §Logging & Monitoring NEVER-log list line 329 — extends the "NEVER log raw OTLP attribute values" rule to "NEVER persist raw OTLP attribute values to corpus either").
- `storage.inspect` + `storage.path` TauRPC procedures MUST follow the quadruple-binding pattern (per Tier 2 security.md Session Additions 2026-05-12): (1) router registration in `crates/corpus/` (or pulse-app router-glue per the cross-crate state pattern 2026-05-16), (2) capability JSON entry in `pulse-app/capabilities/` (Tauri capabilities are negative-default — silent runtime rejection otherwise per §Code Patterns ban line 400), (3) `xtask/src/main.rs::EXPECTED_PROCEDURES` extension to clear D3 drift, (4) `emit_taurpc_bindings` test in `pulse-app/src/main.rs::tests` extended with the corpus `ApiImpl::new(...).into_handler()` in the `.merge(...)` chain. `storage.inspect` returns sanitized `AppError`-free read-only data only.
- Corpus storage MUST default to per-workspace scoping with no cross-workspace / cross-device / external endpoint sharing (per capability P-050 default-state-fully-local + security plan §Cross-cutting Patterns Self-observation discipline). NO automatic outbound network sync; export (P-046, chunk #85) is explicit per-action user opt-in only.
- The encryption-key custody class (corpus key in OS keychain) MUST be added to the security plan's `§Secret Management "What counts as secret"` list at next /andromeda-security re-run; until then, the new secret class MUST NOT leak into logs, error messages, or `AppError::Internal { message }` (per §Logging NEVER ban line 421 sanitization — sanitize at the `From<thiserror::Error> for AppError` impl in the corpus crate).

## Anti-patterns to avoid

- **NEVER persist raw OTLP attribute values to the corpus** — extends the existing §Logging NEVER-log ban (security plan line 329 + Anti-Patterns §Logging line 418) to a new persistence surface. Corpus stores only post-scrubber fingerprints, normalized identifiers (trace_id / span_id / request_id as opaque), and structural metadata (per capability P-048 "No Raw OTLP Attribute Values Stored"). Bypass-by-mistake = silent persistence of user secrets into a disk-resident DB that survives process termination, retention, AND ring-buffer eviction.
- **NEVER enable DuckDB's built-in encryption-at-rest as a "while we're here" change to handle corpus alongside the ring buffer** — CVE-2025-64429 is documented (per security plan §Code Patterns Data Protection ban line 394). The corpus uses `rusqlite` SEPARATE from DuckDB; preserve the `:memory:` posture on the existing `pulse_buffer` connection.
- **NEVER hardcode the corpus encryption key, derive it from a fixed string, or store it on disk alongside the encrypted DB** — defeats the purpose entirely. Key MUST come from OS keychain (preferred) or user passphrase via Argon2id-class KDF. NEVER commit any test-keychain seed or fallback fixture key to git (per security plan §Code Patterns Secrets ban line 410 + `.gitignore` discipline).
- **NEVER write file-path-to-corpus or scrubber-rejected raw values into `tracing` logs or `AppError::Internal { message }` content surfaced to the webview** — corpus DB path is sensitive (user data dir disclosure) + scrubber-rejected raw values defeat the scrubber by side-channel (per security plan §Logging NEVER list line 332 + Anti-Patterns §Logging ban line 421). Log basename + scrubber-pattern-id + count instead of raw matches.
- **NEVER expose `storage.inspect` write semantics** — the procedure is READ-ONLY by contract (per capability P-051 boundary "Inspection is read-only" + v0.2.0 plan §69 "+1 procedure `storage.inspect()` (read-only corpus query)"). Deletion MUST be a separate procedure with explicit confirmation dialog (per P-051 conductor verification "deletion is preceded by explicit confirmation dialog"). Conflating inspection + mutation collapses the audit-trail discipline.
