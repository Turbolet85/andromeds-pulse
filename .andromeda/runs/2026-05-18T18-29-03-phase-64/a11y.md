# a11y extract — phase-64

## No domain coverage

Chunk #68 is a pure-backend persistence layer: new `crates/corpus/` SQLite scaffold + schema + OS-keychain encryption + PII scrubber primitive. It is structurally identical to the DuckDB columnar storage entity that a11y plan §1 explicitly classifies as "Backend-only; no UI surface, no a11y testing scope" (a11y-plan.md line 27).

**Concrete reasons no a11y coverage applies:**

1. **No new UI surface in this chunk.** Per chunk #68 scope (route §2 Epoch 9 + v0.2.0-route §Phase 5 line 329), the Settings → Storage section enabling inspection / export / deletion is named but its UI implementation is explicitly deferred (export trigger gated to chunk #85 per P-046; deletion/inspection UI not in this chunk's TauRPC surface). The two new TauRPC procedures `storage.inspect()` + `storage.path()` are backend resolvers consumed later. Backend / IPC concerns are explicit out-of-scope per a11y focus guide §"Out-of-scope (do NOT extract)".

2. **OS-keychain first-run prompt is boundary-only.** The macOS Keychain / Linux Secret Service / Windows DPAPI access prompts are OS-native dialogs — the same "vendor-controlled" boundary pattern a11y-plan §5 documents for the native File picker (line 452): "OS picker internals are not asserted (vendor-controlled), but the wrapper's enter/exit focus management is." Since this chunk introduces no Tauri-side wrapper modal (the keychain prompt is invoked directly by the platform crate), there is no Pulse-owned wrapper boundary to assert against. If a future chunk wraps the first-run flow in a Pulse-owned modal (e.g., passphrase-fallback dialog explaining keychain failure), THAT chunk would inherit a11y-plan §5 File-picker-modal boundary pattern + investigation-modal focus management contract (initial focus / Esc-close / focus-restore to trigger).

3. **No design token / motion / contrast / live-region surface introduced.** No new colors, no new animations, no new aria-live announcements, no new focusable elements, no new keyboard shortcuts. The chunk is workspace-dep additions (`rusqlite` bundled + keychain crate), schema DDL, encryption-at-rest, and a security-crate PII scrubber primitive — none of which render to the webview.

4. **PII scrubber is a backend security primitive, not a user-facing setting toggle.** Per route §2 chunk #68 + v0.2.0-route §Phase 5, the PII scrubber is consolidated into the security crate and consumed by corpus on ingestion. There is no settings switch / radio / form input introduced by THIS chunk; if a "scrubber sensitivity" or "redaction preview" UI is added later, that chunk would trigger settings-modal a11y patterns (a11y-plan §3 critical path P7 + §5 settings-modal focus order + §6 form labels + §11 aria-live error announcements).

**Forward-binding note (informational; not actionable this chunk):** The downstream Settings → Storage UI (chunk-deferred — inspection panel + deletion confirmation + export trigger) will inherit critical path P7 settings-modal patterns: `dialog[aria-label="Settings"]` + form labels per a11y-plan §3 Critical Paths table + Esc-close + focus-restore-to-trigger per §5 + deletion confirmation as `role="alertdialog"` with explicit "Delete corpus" button labeling (SC 4.1.2 Name, Role, Value) + aria-live="assertive" announcement on completion (SC 4.1.3 Status Messages). The orchestrator should flag this binding for the chunk that DOES introduce the Storage UI panel — not chunk #68.

**Specialist plan silent-on-corpus note (per extract discipline):** a11y-plan.md does not mention SQLite-specific storage, encryption-at-rest UX, or PII-scrubber UX surfaces. This is correct silence (chunk is out-of-domain), not a plan gap — no surfacing to user required.
