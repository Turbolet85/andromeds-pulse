## Constraints
- Any new or changed emission on a `triage.*` / `baseline.*` target requires an **EXACT** allowlist leaf; a bare `triage` (or new bare `baseline`) prefix key is banned because `for_target`'s prefix fallback would silently widen every sibling target to one field set (per `.andromeda/obs-plan.md` §8 Default-deny posture → Incident-path diagnostic leaves). §8 names the guarding test convention (`pulse-app/tests/unit_observability_allowlist_incident_diagnostics.rs`).
- `triage.cue.tick`'s `bypass_triggered` / `cues_suppressed` are recorded in the **muted-diagnostic backlog** — measured redacted, owner named as the separate "Diagnostics un-muting + harness-truth sweep" route entry (per obs-plan §8 Muted-diagnostic backlog). This chunk must not silently widen them; if the reachability proof needs a field on that same target, the collision with the backlog owner is research's question.
- Warm-up / lifecycle changes are **state transitions**, which §6 maps to `info`, with the JSON-per-line required-field set (`timestamp` / `level` / `target` / `message` / `fields` + default `service.name` / `service.version` / `deployment.environment`) (per obs-plan §6 Required fields + Log levels mapping). Degraded/failed warm-up is `warn` with the plan's stated emission discipline (once per boot / once per pass, never per row).
- Counters that describe throughput toward a warm state must ride as **FIELDS on an existing 15s tick**, not as new `metric.*` targets, and must never be emitted per sample/per span-event (per obs-plan §5 Conceptual instrument types → tick-aggregated counters, and §11 Telemetry Strategy hot-path rule).
- Baseline families are **per-service**, and `service.name` is client-supplied via OTLP: it may not be used as a metric label. §5's unbounded-`service_name` exception is scoped strictly to query-time aggregation events (`metric.trace.*`) and does not extend to triage/baseline emissions (per obs-plan §5 Metric label cardinality discipline).
- Tick cadence is an SLO invariant: no >45s gap between consecutive ticks for any tick target during a run, enforced post-test by `xtask/ci/heartbeat-gap-check.sh` (per obs-plan §10 Standard+ invariants + CI gates). Ticks and the synchronous `health` command are complementary and must not be conflated (per obs-plan §3 Heartbeat ticks → Complementarity).
- If the bound lands config-surfaced (`Settings` / `config-watcher`, as the scope allows), config load + hot-reload require structured success/failure logs with path fields reduced to basename only per Vector 6 (per obs-plan §1 Instrumentation scope → config management, §8 data-classification table).

## Patterns to follow
- **Tick-field folding**: fold aggregate counts once per batch and ride them out as fields on the existing `{module}.tick` (the `buffer.tick` `span_events_seen` / `fingerprints_computed` / `observer_invocations` shape) rather than minting new `metric.buffer.*` targets (per obs-plan §5 Conceptual instrument types).
- **Positive-reading principle**: prefer a signal whose presence *affirms* the state over one where health is inferred from downstream silence — the stated rationale for the feed counters, and directly applicable to "is this service warm yet?" (per obs-plan §5 tick-counter row).
- **Explicit-leaf registration**: the `app.boot.workspace_key` / `corpus.*` / `incidents.*` leaves are the precedent — dotted target, exact field enumeration, bounded static strings or counts, plus a dedicated `pulse-app/tests/unit_observability_allowlist_*.rs` guard (per obs-plan §8 Default-deny posture).
- **Once-per-boot WARN discipline** for a condition that would otherwise be indistinguishable from healthy (`app.boot.buffer.degraded`, `corpus.keychain.fallback` shape) — applicable if a shortened/overridden warm-up bound is a non-default posture worth surfacing at boot (per obs-plan §6 Log levels mapping, `warn` row).
- **NEUTRAL-tolerant, run-window-scoped check scripts**: any xtask check over `agent-latest.jsonl` must treat an absent stream as NEUTRAL, not FAIL, and scope to the run window via `write_run_window_log` (per obs-plan §10 Load-profile constraints).

## Anti-patterns to avoid
- Never emit at `info` on a hot path — per-sample/per-observation baseline updates must not log; aggregate to the tick or gate behind `trace`/`debug` (per obs-plan §11 Logs).
- Never introduce unbounded label cardinality in `tracing` event fields (per-service, per-trace-ID labels on a baseline/cue metric) (per obs-plan §11 Metrics).
- Never let raw OTLP attribute values reach the log via a cue diagnostic — Vector 1 permits only `attributes_count` + a service tag at the *ingest* allowlist, and no equivalent is allowlisted for triage targets (per obs-plan §11 Logs + §8 data-classification table).

## Contract bindings
- **obs ↔ tests harness** — the log-format JSON schema is a binding contract obs aligns *to* (tests owns it); the external verification harness proves family reachability by reading `~/.andromeda-pulse/logs/agent-latest.jsonl`, so the warm-state signal must be greppable JSON-per-line with the §6 required fields (per obs-plan §3 Log format JSON schema, §6).
- **obs ↔ tests harness (readiness)** — the TauRPC `health` command is the synchronous liveness/readiness surface a harness polls; it is complementary to ticks, so a "is this service warm" affordance may belong on either surface but not by conflating them (per obs-plan §3 Heartbeat ticks → Complementarity).
- **obs ↔ security** — Vectors 1 / 5 / 6 (OTLP attribute values, query params, path env vars) are enforced at the logger allowlist config, which is where any new triage/baseline field lands (per obs-plan §8 PII Scrubbing).
- **obs ↔ config / ui-bridge** — only if the bound is config-surfaced: `config.load` structured logging with basename-only path fields (per obs-plan §1 config management row, §8 Vector 6).

## Acceptance criteria contributions
- Every new or changed `triage.*` / `baseline.*` emission has an EXACT allowlist leaf enumerating **all** fields the emit site actually emits, with no bare `triage` / `baseline` prefix key, guarded by an allowlist unit test (per obs-plan §8 Default-deny posture → Incident-path diagnostic leaves).
- The warm/ready state is readable as a POSITIVE, unredacted signal in `agent-latest.jsonl` (INFO state transition and/or a tick field), not inferred from the absence of cues — whether the code already emits such a signal is research's question (per obs-plan §5 Conceptual instrument types + §6 Log levels mapping).
- No new `metric.*` target and no per-sample emission for warm-up progress: counts fold into an existing 15s tick as fields, with labels bounded to enumerated values and no `service_name` label (per obs-plan §5 Conceptual instrument types + Metric label cardinality discipline; §11 Metrics/Logs).
- Tick cadence invariants hold across the change: no >45s gap for any tick target during the run, and any new/edited check script over the log is NEUTRAL-tolerant and run-window-scoped (per obs-plan §10 Standard+ invariants + CI gates + Load-profile constraints).
