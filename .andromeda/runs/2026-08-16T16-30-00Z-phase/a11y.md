## Relevance
Partial — conditional: the chunk's named surfaces (`crates/triage/src/cue/*`, `crates/triage/src/baseline/*`) are backend-only and carry no a11y assertions, but two conditional hooks exist (a config-surfaced bound reaching `ui-bridge::Settings` → settings-modal form; newly-reachable cue families feeding the existing findings live-badge).

## Constraints
- Backend triage/baseline/config crates add no WCAG surface: a11y-plan §1 A11y Scope Summary classifies non-UI backend services as **Not-assertable** ("no UI surface, no a11y testing scope"). Constants, gates and evaluator changes confined to `crates/triage` owe nothing to this domain.
- IF the bound lands as a config-surfaced Settings field that renders in the settings-modal (scope's "Surfaces likely touched" + Open Scope Question 2), a11y-plan §7 Screen Reader Support → Form labels requires a programmatically-associated **visible** `<label htmlFor>` (not `aria-label`) plus `aria-describedby` for any hint text (SC 3.3.2 / SC 4.1.2). Whether the mechanism reaches UI at all is research's question.
- Under that same condition, a11y-plan §1 Critical Path **P7** and §5 Keyboard Navigation (settings-modal focus order) require the declared Tab sequence (theme radio → widget position → retention input → MCP toggle → snapshot preset → Save → Cancel) to absorb any new control in visual top-to-bottom position, with Esc closing the modal and restoring focus to the trigger (SC 2.4.3 / SC 2.1.2).
- A bounded numeric warm-up input would be a bounds-validated field: a11y-plan §1 P7 + §4 Form input pattern require SC 3.3.1 error identification — `aria-invalid="true"` on the invalid input with the error text linked via `aria-describedby`, focus moved to the first invalid input.
- a11y-plan §3 "Harness wiring & conventions" states the standing rule that **every new route/modal adds one axe spec in the same chunk**; a new field inside an existing modal falls under the existing p-spec instead. Which of the two applies depends on whether a new surface (vs. a field) ships — research's question.
- a11y-plan §10 SLO Invariants requires **zero new WCAG AA violations per PR** vs. the base-branch baseline, and §3 Regression baseline fixes that baseline at `baselines/a11y-violations-summary.json` (clean pass = 0 violation tuples, informational Lighthouse-score tuples allowed). Any UI touch in this chunk inherits that gate.
- If making the silence / activity-floor families reachable causes them to emit incidents into the existing findings surface, a11y-plan §5 (findings-window entry) requires the live badge 0→N to announce **once, politely** (SC 4.1.3) and requires cross-window focus restoration via first-party Tauri events. Whether the newly-reachable families route through that existing path unchanged is research's question.

## Patterns to follow
- The existing settings-modal retention input is the template for a numeric bounded control (a11y-plan §1 P7 / §5 settings-modal focus order): native semantic `<input>` + visible label + Save/Cancel button pair, no custom widget.
- a11y-plan §4 Form input row: native `<input>`/`<textarea>` with `aria-describedby` for error/hint and `aria-invalid="true"` on validation failure — semantic HTML first, ARIA second (§2 naming conventions).
- a11y-plan §3 Harness wiring: Playwright a11y specs mock Tauri IPC via `tests-a11y/helpers/mock-tauri.ts` using the `TauRPC__<router.path>` command shape; fixture payloads live in `helpers/v02-fixtures.ts` — any new TauRPC procedure or Settings field a spec consumes must be added there.
- a11y-plan §3 suite-health check: verify the a11y suite still loads with `npx playwright test --list` before trusting a green run (a list-time import failure previously disabled the whole suite silently).
- a11y-plan §6 Focus ring tokens / §11 Keyboard: `--border-focus` outline on every `:focus-visible` element; natural DOM order only (no `tabindex > 0`).

## Anti-patterns to avoid
- Never leave a form input without an associated label, and never substitute `aria-label` where a visible `<label>` is feasible (a11y-plan §11 Screen Reader + §11 ARIA).
- Never defer a11y to a follow-up: a11y is a fail-fast PR gate, and lint-only (eslint-plugin-jsx-a11y) coverage without a runtime axe/pa11y/Lighthouse pass is banned (a11y-plan §11 CI).
- Never claim conformance for a newly surfaced control without machine-verifiable evidence (axe-core / Lighthouse / pa11y JSON); manual SR or keyboard checks are supplemental only (a11y-plan §11 Strategy + §2 agent-runnable invariants).

## Contract bindings
- **a11y ↔ tests:** a11y-plan §3 CI integration + §9 bind `npm run test:a11y` (alt. `cargo xtask test:a11y`) to the tests' 5-command E2E harness (`boot` / `run` / `status` / `cleanup` / `logs`) in the same `ci.yml` pipeline — a11y adds no separate driver.
- **a11y ↔ obs:** a11y-plan §3 Structured violation JSON schema is a binding contract to obs Section 6's structured log format (`wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` / `remediation` / `tool` / `tool_result_id`), emitted to `~/.andromeda-pulse/logs/`.
- **a11y ↔ design:** a11y-plan §6 contrast pairs and `--border-focus` / `--target-*` tokens bind to design-system tokens verbatim — applies only if this chunk renders new text or state.
- All three bind only under the conditional UI branch; if the bound stays Rust-internal, no binding is exercised.

## Acceptance criteria contributions
- (a11y — only if the bound surfaces a settings control) The new control has a programmatically-associated visible label and axe-core reports zero critical/serious violations on the settings-modal surface (per a11y-plan §3 CI gate + §7 Form labels).
- (a11y — same condition) Settings-modal Tab order still matches visual top-to-bottom order including the new control, and Esc closes the modal restoring focus to the "Settings" trigger (per a11y-plan §5 Keyboard Navigation, settings-modal + §1 Critical Path P7).
- (a11y — if any UI file changes) Full `npm run test:a11y` chain is regression-clean against `baselines/a11y-violations-summary.json` — zero new violation tuples on `{surface, wcag_criterion, selector, severity}` (per a11y-plan §3 Per-PR regression detection + §10 zero-new-violations-per-PR).
- (a11y — if the change ships no UI) No a11y criteria are owed and none should be asserted: the touched crates are Not-assertable (per a11y-plan §1 A11y Scope Summary scope table).
