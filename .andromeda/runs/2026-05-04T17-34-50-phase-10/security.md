- Any new GitHub Action introduced for a11y CI integration (e.g., `@axe-core/cli` action wrapper, Lighthouse CI Action, pa11y-ci action) MUST be pinned by 40-char commit SHA with `# vX.Y.Z` comment (per security plan §Anti-Patterns §Secrets "NEVER reference third-party GitHub Actions by `@v2` / floating tag" and §Bootstrap `dep-security-ci-gate` SHA-pinning convention; tj-actions/changed-files CVE-2025-30066 anchor).
- The 7 packages enter `pulse-app/ui/package.json` `devDependencies` only — NEVER `dependencies` (per security plan §Anti-Patterns §Universal scope discipline; runtime webview must not link a11y testing tooling into shipped bundles, which would expand the binary's third-party-code attack surface).

- If chunk introduces violation-JSON output files (axe / pa11y / Lighthouse reports) committed to the repo, ensure paths are added to `.gitignore` if they could capture clipboard / OTLP / plugin content samples during a screen-reader test pass (per security plan §Logging "NEVER log raw OTLP attribute values, snapshot file contents, clipboard contents" — violation-JSON harvests DOM text which during integration tests could inadvertently surface synthetic OTLP attribute fixtures; isolate fixtures from real telemetry).

## Patterns to follow

- **SHA-pinning for new CI Actions**: existing `pulse-app/ui/`-adjacent `.github/workflows/ci.yml` pins every Action by 40-char SHA + version comment (e.g., `step-security/harden-runner@a5ad31d6a139d249332a2605b85202e8c0b78450 # v2.19.1`); follow the same shape for any new a11y CI Action introduced (per security plan §Bootstrap `dep-security-ci-gate`).
- **Lockfile commitment**: `Cargo.lock` is committed for the workspace; existing `pulse-app/ui/package-lock.json` is committed (verified via `ls`); preserve the same posture for the npm install of the 7 new packages (per security plan §Dependency Security pinning row + npm-extension noted under Constraints).
- **`.gitignore` extension precedent**: security plan §Bootstrap `secret-scanning-ci-gate` already requires `.gitignore` entries for `*.p12`, `*.pem`, `*.cer`, `.env*`, `*.key`, `~/.tauri/*.key`; if a11y harness emits machine credentials (none expected for the 7 tools) the same `.gitignore` discipline applies (per security plan §Anti-Patterns §Secrets first bullet).
- **Workflow `permissions: contents: read`**: existing `ci.yml` line 8-9 sets `permissions: contents: read` workflow-level; any new a11y CI job follows the same pattern, elevating to `write` only on a publish step (per security plan §Secret Management "Add `permissions: { contents: read }` at the top of every workflow" + §Anti-Patterns §Secrets fourth bullet).

## Anti-patterns to avoid

- NEVER auto-update the 7 new devDependencies via Dependabot floating-version PRs without verifying RustSec / npm-audit advisory equivalence at merge time — Dependabot opens the PR but a human / CI still runs `npm audit` before merging (per security plan §Dependency Security "Critical CVE response SLA: 72h" + §Anti-Patterns §Secrets SHA-pinning convention extended to package version pins).
- NEVER add a `postinstall` script in `package.json` that downloads, executes, or evaluates remote content as part of the 7-package install (Playwright already runs a controlled `postinstall` for browser binary download — that is an exception with documented egress; do NOT add additional `postinstall` for the other 6 tools) per security plan §Anti-Patterns §Code Patterns "NEVER use `tokio::process::Command::new(...).arg(user_input)` against any string sourced from..." (the principle: untrusted-input → process-spawn ban extends to npm-side `postinstall` discipline by analogy).
- NEVER expose any of the 7 a11y tools' internal output paths (full-path violation-JSON locations, screen-reader transcript paths) in CI logs surfaced as PR comments or webview UI strings — basename only (per security plan §Anti-Patterns §Logging "NEVER log full plugin file paths — basename of canonicalized path only"; the principle generalizes to any file-path emission in user-visible artifacts).
