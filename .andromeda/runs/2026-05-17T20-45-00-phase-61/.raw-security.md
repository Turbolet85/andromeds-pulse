## Constraints

- The new `span_events` Arrow appender path MUST use the existing parameter-binding shape (`Appender::append_record_batch`) — NEVER `format!("INSERT INTO span_events VALUES ('{}', ...)", exception_message)` for the new exception attribute columns; user-controlled telemetry content (especially `exception.message` / `exception.stacktrace`) is the canonical injection vector (per security plan §Input Validation row 5 DuckDB query parameters + §Security Anti-Patterns § Input DuckDB bullet — 2026 CVE cluster anchor).
- Exception attribute values (`exception.type`, `exception.message`, `exception.stacktrace`) MUST never be logged verbatim — these are the highest-density secret-bearing OTLP attribute values in practice (database passwords in connection-error messages; auth tokens in HTTP-error stack frames; file paths from instrumented host processes). Tracing emissions during span-events decode MUST emit counters (e.g., `events_count`, `exception_events_count`, `events_decoded_bytes`) or enum tags (e.g., `decode_status`), NEVER attribute value content (per security plan §Logging & Monitoring "What NEVER to log" rows 1-2 OTLP attribute values + span/log/metric content payloads).
- The `span_events` table cell content (`exception.type` / `exception.message` / `exception.stacktrace` strings stored in DuckDB) is treated as user-content data classification per Threat Model Summary — at-rest disposition matches the existing spans table: in-memory `:memory:` connection only, governed by retention task (`DELETE FROM span_events WHERE ts_unix_nano < ?` already exists in `retention.rs`). No persistence; no encryption layer needed (per security plan §Data Protection at-rest DuckDB ring buffer row).
- The `AppError::Append { reason }` (or equivalent appender-error variant) sanitization MUST NOT include the failing exception attribute value in the `reason` field — error chains crossing the TauRPC bridge through `From<buffer::Error> for AppError` MUST scrub raw exception strings via the existing `short_err` helper or equivalent, never propagate verbatim `exception.message` content into `AppError::Storage { message }` (per security plan §Error Handling TauRPC bridge bullet + §Security Anti-Patterns § Logging "NEVER expose stack traces, Rust struct names, file paths, or library versions in `AppError::Internal { message }`").
- Per-attribute byte-bounds enforcement MUST apply uniformly across `exception.type` / `exception.message` / `exception.stacktrace` — none of the three get а bounded-exception bypass (stacktraces are commonly 4-8KB in real-world OTLP payloads but the security plan's MAX_ATTRIBUTE_VALUE_BYTES = 4096 cap is the boundary; if а chunk-specific raised cap is required, that's an architectural scope amendment via `/andromeda-arch`, not а silent appender bypass) — note: source-of-truth plan declares "redaction layer preserved" without explicit byte-bound carve-out, so default = use existing bound.
