# security extract

## Relevance
partial — the chunk builds no product surface, but its test legs start the loopback receivers on picked ports, its factories mint the client-controlled field values the scrub boundary reads, and a shared port helper or a new dependency would touch the harness-only class and the supply-chain gates.

## Constraints
- **Loopback only, the port is the sole input.** security-plan §Security Anti-Patterns → API bans any receiver bind outside `127.0.0.1`; security-plan §Input Validation (CLI / env var inputs row) requires the two OTLP port variables to yield validated ports only, the bind host being no input in either program. The claimed-port form must hand a test leg a port and nothing else. Whether the in-process arms of `pulse-app/tests/integration_engine_boot.rs` already pass a port alone, and through which input, is research's question.
- **Never 4317 or 4318.** security-plan §Security Anti-Patterns → Input requires every harness member that starts an engine to stay on harness-only ports and to refuse the two product ports. The claimed-port form in this chunk must keep that exclusion. Whether the claim range the two existing twins draw from can yield 4317 or 4318 is research's question.
- **The helper and the factories stay inside the harness-only class.** security-plan §Security Anti-Patterns → Input defines that class by three conditions: never product-consumed, no product input added, nothing run inside a shipped binary's process. A shared port helper that reads a new environment variable, writes a new location, or lands in a product crate's non-test code falls outside it, and that section requires each such addition to carry a named, dated classification that is the operator's or the founder's to give. The plan holds no entry for the claim files the existing twins write; whether a shared helper would write anywhere other than where they write today is research's question.
- **Default data passes the post-decode invariants; the invariants are not relaxed.** security-plan §Input Validation (OTLP/gRPC row) requires an 8-byte `span_id`, a 16-byte `trace_id` and bounded attribute keys and values after decode. Factory defaults must satisfy them, so a malformed record exists only where a test sets one on purpose.
- **Factory field values are scrub inputs.** security-plan §Security Anti-Patterns → Logging requires every client-controlled value reaching the ring buffer's five cells, the log body and the exception fields to be masked at the write boundary under the eight-category catalog. The settable service, version and attributes are those inputs, so factory DEFAULTS must fall outside all eight arms (the key-anchored arms included: an attribute key alone can redact a benign value; a digit-group run can pass the card gate). A credential-shaped value appears only where a test sets it on purpose. Whether any default the chunk's migrated tests rely on trips an arm today is research's question.
- **No real secret or captured telemetry in test data.** security-plan §Secret Management (Never in code; Secret scanning in CI) requires the build to fail on a detected secret; security-plan §Threat Model Summary (data classification, the telemetry sensitivity note) classes real telemetry as able to hold captured secrets. Fixture values are synthetic, never copied from a real capture, and a scrub canary is credential-SHAPED, not a credential. Whether the existing canaries pass the secret scan by shape or by an allow entry is research's question.
- **A new dependency or workspace member meets the supply-chain gates.** security-plan §Dependency Security (CI integration) requires `cargo audit` and `cargo deny check bans licenses sources` to pass, with `multiple-versions = "deny"` never relaxed, the `tonic` canary never skipped and the `licenses` check covering the workspace's own crates; security-plan §Bootstrap phases (`dep-audit-tooling-install`) requires `[sources]` restricted to crates-io. A dev-dependency enters `Cargo.lock` like any other. Whether the factories need anything the hosting crates do not already carry is research's question.

## Patterns to follow
- **Host fixed, port validated, bad value refused without being repeated** — the shape security-plan §Input Validation (CLI / env var inputs row) requires of every port reader, harness readers included.
- **An exact, cleared child environment for any leg that spawns an engine** — security-plan §Security Anti-Patterns → Input requires the spawning harness verbs to pin their child set by set equality, with a per-run passphrase never printed or written and no session bus or runtime dir in the set. A shared helper serving the spawned-binary test binaries must not widen what their children receive.
- **Closed labels out, no value and no path** — security-plan §Security Anti-Patterns → Input requires harness output to carry no environment-variable value and no path; a claim-failure message from the port helper follows the same shape.
- **Key and value stated together for a labelled data point** — security-plan §Security Anti-Patterns → Logging requires `metrics_points.labels` to be scrubbed in the joined `key=value` form, because the key-anchored arms are unreachable on a split value. The metric-point factory's attribute setting must let a test state both, so later scrub tests can drive the keyed class through it.

## Anti-patterns to avoid
- NEVER bind a test receiver to `0.0.0.0` or any non-loopback interface, and never add a host parameter to reach one (security-plan §Security Anti-Patterns → API).
- NEVER relax or route around a product check so that test data becomes buildable — the post-decode invariant checks (security-plan §Security Anti-Patterns → Input) and the scrub choke point for the service name (security-plan §Security Anti-Patterns → Logging). A product constructor or field the factories would need is the operator's question at P4, per the scope.
- NEVER interpolate a factory-supplied value into SQL when a helper writes rows to DuckDB — prepared statements with `?` placeholders only (security-plan §Security Anti-Patterns → Input). Whether any hand-built site the chunk migrates inserts rows by string SQL is research's question.

## Contract bindings
- **security ↔ tests (fixtures):** synthetic, scrub-neutral fixture content binds to the test plan's fixture and factory conventions; the scrub tests' canaries are the one sanctioned credential-shaped data.
- **security ↔ tests (harness):** the claimed-port helper binds to the test plan's harness section and its pending-coverage rows for the port-using test binaries; the harness-only class in security-plan §Security Anti-Patterns → Input is the security side of that contract.
- **security ↔ tests (CI):** the `supply-chain` job and the secret-scanning step (security-plan §Dependency Security; §Secret Management) are the security gates of the one CI workflow the chunk's push is read against.
- **security ↔ obs:** fixture content moves redaction readings in self-observation records, and no log record may carry a factory attribute value (security-plan §Logging & Monitoring, What NEVER to log).
- **security ↔ arch:** a new workspace member, a new location on disk or a product-side constructor is an arch §Occupied Resources change and a scope halt, not a security-plan decision.
