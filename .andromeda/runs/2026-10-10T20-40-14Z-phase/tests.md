## Relevance
relevant — the chunk is test infrastructure itself: the owed test-data factories (test-plan §3 Bootstrap phases item 6) and the port picking the plan's §9 Integration tests row names as owned by this route entry.

## Constraints
- **The factories are an owed mandate with a stated shape, and the chunk's shape differs from it.** test-plan §3 Bootstrap phases (item 6, test-data-bootstrap-wire) requires three named builder factories in three named crates plus `rstest` composition, and records them as unimplemented (a dated measurement, 2026-08-23). The chunk's "one set of factories" for spans, metric points AND log records is not that list: item 6 names no log-record factory and does name an Arrow-batch one the entry does not. The plan states which of item 6's members the chunk builds, which it leaves, and under what names and homes; whether any of the three exists at the chunk base is research's question.
- **The pending row gives two resolutions, and the chunk must land on one.** test-plan §1 Pending coverage triggers (`test-data-bootstrap-factories-unimplemented`) requires either the factories implemented or item 6 amended to drop the ones the project does not want; it classes the gap as ergonomics and consistency, not a coverage hole. A chunk that builds a differently-shaped set leaves that row and the four sites it lists (§3 item 6, §5 Module ↔ DuckDB, §5 buffer → viz, §7 builder-factory list) to be amended at the wrap — the plan says so rather than leaving the row silently half-met.
- **Mechanism: builder factories composed through `rstest` fixtures.** test-plan §3 Test data bootstrap → Mechanism requires the builder form (set what the test states, `build()` the rest from defaults) and fixture composition; test-plan §4 Fixture pattern at unit level requires `#[fixture]` wrappers over the builders. The chunk's settable event time, service, version and attributes are further setters on that form, not a second mechanism.
- **Data is generated at test run time.** test-plan §7 Self-bootstrapping requirement requires every test to seed its own OTLP data, with no pre-populated store; test-plan §1 Coverage triggers (agent-driven-discipline: self-bootstrapping test data) requires fixture data to come from OTLP ingest or Rust builders. The factories produce values; they do not replace the seed paths (the live receiver, per-test in-memory seeding) that §7 names.
- **A factory's defaults are deterministic, event time above all.** test-plan §11 Universal (agent-driven specific) bans real time without injection, and test-plan §2 Agent-runnable invariants requires deterministic tests; test-plan §7 Seed strategies (Time-sensitive data, Randomized data rows) requires time injected per test and generators seeded. A default event time read from the wall clock breaks all three; an unstated event time takes a fixed value.
- **Test code lives where the plan says each package's tests live.** test-plan §2 Test directory + naming conventions requires co-located `mod tests` in library crates, `pulse-app/tests/*.rs` for the binary crate (its lib sources hold zero test attributes, held by a ratchet), and `xtask/tests/` over a shared `common/mod.rs`; it also states that `check:english-sources` and `quarantine-tracking` each read a fixed set of roots. A shared factory home that is a new directory or a new workspace member is outside those roots until they are extended — the plan names the home and says what reads it. test-plan §4 Conventions (Test file location) carries a count of `pulse-app/tests/*.rs` files that a new file there changes.
- **Port-using tests claim their ports.** test-plan §9 Pipeline structure (Integration tests row) requires the port-using binaries to claim each port under an advisory file lock in `target/test-ports/` and records `pulse-app/tests/integration_engine_boot.rs` as the remaining bind-and-release site, owned by this route entry; test-plan §3 Per-chunk gate discipline → Spawned-program witness form fixes the claim's terms (the number range, the two harness ports left out, the lock held for the test, the file never unlinked, the port shown bindable when claimed) and requires that no test bind 4317 or 4318. test-plan §3 Bootstrap phases (item 1) states why: nextest isolates processes, not port numbers.
- **The standard gate set, unconditional.** test-plan §3 Per-chunk gate discipline requires the full gate block in the plan's `## Test Commands` in its stated order (the drift read before the workspace run, the mcp-feature bindings regen as the last cargo-adjacent step, the bindings close named against the chunk base `50216d7e`), and the merge-base probe as an operator entry directly before the push entry. The webview gates are excluded only if no `pulse-app/ui/**` path is touched. The conditional boot-smoke gate applies only if the plan touches a listed boot path; the scope's "no product source changes" would leave it out, and research confirms that.

## Patterns to follow
- **Builder inside a fixture, parameters composed by `rstest`** — the form test-plan §4 Fixture pattern at unit level shows; a migrated test asks the fixture for telemetry and overrides only what it reasons about.
- **Time as an explicit argument, not an ambient clock** — test-plan §4 What unit tests cover (triage crate) records parameter injection of the instant as the stronger form over a paused runtime clock; the factories' event-time setter follows it, since the later event-time entries will drive their checks through it.
- **A shared test module per package, each binary using a part of it** — test-plan §2 Test directory + naming conventions records `xtask/tests/common/mod.rs` in that form. The plan's §9 Integration tests row names three claiming binaries across two packages plus this chunk's file, so "one helper for all" crosses a package boundary; test-plan states no home for a cross-package test helper, so what that costs is the plan's to state (scope, "One shared port helper").
- **The file's two kinds of arm stay distinct** — test-plan §3 Per-chunk gate discipline → Process-end witness form records re-exec children in `integration_engine_boot.rs` that call `engine_boot::init_process` and prove they ran by their own boot records and pid file; the port change concerns the in-process arms that start receivers. How many arms take a picked port is research's count.
- **A repeated-run reading is a count** — test-plan §9 Pipeline structure (Integration tests row) records the before and after hand runs of the port change as counts, explicitly not an exclusion; this chunk's own repeated runs of the moved binary beside its siblings are reported the same way.

## Anti-patterns to avoid
- **Test-data bans** (test-plan §11 Test Data): no production telemetry dumps as test input, no mutable state shared across parallel tests (a factory holds no process-wide counter or cache that two tests can observe), no generator without seed control, no pre-populated store.
- **Assertions that bind to the fixture instead of the contract** (test-plan §11 Unit; test-plan §11 Integration): a migrated test never asserts on a factory's internal default ids, and never on raw encoded OTLP bytes — it asserts on decoded fields. A migration that changes what a test asserts is not a migration.
- **Curing a port collision by weakening the run** (test-plan §10 Zero-flakiness budget; test-plan §11 Quality; test-plan §11 CI): no retry, no committed serial test-thread setting, no `#[ignore]` without a tracking issue; and never a port bound to 0, read and released (test-plan §3 Per-chunk gate discipline → Spawned-program witness form).

## Contract bindings
- **tests ↔ architecture:** a factory home that is a new workspace member changes the member list test-plan §4 Framework counts (the declared Rust floor is inherited by every member and held by a pin) and the canonical crate list architecture §Occupied Resources owns; a home inside existing crates changes neither. The plan names which.
- **tests ↔ security (ports and places on disk):** the claim files under `target/test-ports/` are an existing harness place (test-plan §1 Surfaces under test, console engine row); a fourth binary using it adds no place, while a helper that claims anywhere else is the scope's halt. 4317 and 4318 stay unbound (test-plan §3 Per-chunk gate discipline → Spawned-program witness form).
- **tests ↔ security (scrubber):** test-plan §4 What unit tests cover (buffer crate; security crate) records per-column pins that a legitimate value survives the write boundary byte-identical and a credential-shaped one is stored redacted. Factory defaults for service, version and attributes must therefore be values the scrubber allows, and a canary is something a test sets on purpose; test-plan §11 Universal also bans secrets in test output.
- **tests ↔ CI:** test-plan §9 Pipeline structure (lint-test row) records that the workspace run already needs the advisory lock directory under `target/`, with no setup step and no workflow edit, and that the same tests run in the `mcp-test` and `coverage` jobs; the chunk extends that need to one more binary and is expected to edit no workflow.
- **tests ↔ capability record:** test-plan §9 Capability verification matrix requires every claimed entry's scenario file to exist and its `contains` anchor to be found, read in every workspace test run. Whether any test the chunk migrates or renames is named by the record is research's question; P-089 and P-094 lie outside the record's id set, so "advanced, not claimed" adds no record entry.
- **tests ↔ obs:** (none) — the chunk adds no record and no harness verb; the log-format and status bindings are untouched.

- (tests) The standard gate set passes in its stated order, `cargo nextest run --workspace --profile ci` included with the factories' own tests and every migrated test; the bindings close reads exit 0 against `50216d7e`; the merge-base probe is listed directly before the push entry (per test-plan §3 Per-chunk gate discipline).
- (tests) No `.rs` test binds `127.0.0.1:0` to read and release a port: every port a test hands the engine is claimed under the advisory lock in `target/test-ports/`, inside the stated range, and none is 4317, 4318, 24317 or 24318 (per test-plan §3 Per-chunk gate discipline → Spawned-program witness form; test-plan §9 Pipeline structure, Integration tests row).

- (tests) Workspace coverage stays at or above the line and function thresholds with the factories and migrated tests in place, no test is quarantined or retried to get there, and the moved port-using binary's repeated runs are reported as a count (per test-plan §10 Coverage thresholds; test-plan §10 Zero-flakiness budget).
