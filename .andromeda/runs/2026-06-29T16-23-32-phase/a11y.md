# a11y extract

## Relevance
Partial — the chunk implements window chrome (titlebar drag region) affecting existing interactive controls (buttons) with prior a11y compliance (SC 2.5.8 target-size); primary concern is preserving button accessibility during drag-affordance implementation, not introducing new a11y surfaces.

## Constraints
1. Per a11y-plan §1 trigger "target-size" + §6 Visual Verification: titlebar buttons must maintain ≥24px computed target size (SC 2.5.8 AA minimum), per 2026-06-10 amendment fix
2. Per a11y-plan §5 ARIA Patterns + §4.1.2: titlebar buttons must retain accessible names via aria-label or semantic `<button>` elements
3. Per a11y-plan §1 trigger "visual-focus-appearance" + §2.4.7: if titlebar buttons receive focus, must display `--border-focus` visible focus indicator
4. Per a11y-plan §1 trigger "visual-discrimination": button states must contrast per SC 1.4.3 (4.5:1 text) / SC 1.4.11 (3:1 non-text)
5. Per a11y-plan §5 Keyboard Navigation (P5 compact-widget focus order): minimize button must remain keyboard-accessible via OS-level shortcuts (Esc or Alt+Space/Alt+F4)
6. Per a11y-plan §1 trigger "motion-sensitive" + SC 2.3.3 AAA: any animation during drag or button interaction must respect `prefers-reduced-motion: reduce`

## Patterns to follow
1. Per a11y-plan §1 Critical Path P5: preserve focus restoration — focus returns to triggering element when compact-widget re-expands from tray
2. Per a11y-plan §5 Focus Management: maintain visual DOM tab order (title → expand button → minimize button) with consistent `--border-focus` token on all focusable titlebar elements
3. Per a11y-plan §6 Color Contrast: pair any button-state colors with icon / label per SC 1.4.1 (not-color-alone discipline)

## Anti-patterns to avoid
1. Drag region must not swallow button clicks — interactive controls remain clickable per a11y-plan §1 P5 + chunk scope explicit requirement
2. Do not add redundant ARIA role/attributes to native semantic buttons (per a11y-plan §4 "semantic HTML first, ARIA second")
