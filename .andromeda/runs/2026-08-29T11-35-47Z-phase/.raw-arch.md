## Constraints
- **The reconciler cannot live in `triage`.** architecture.md §Established Decisions [Corpus Write Arbitration] records that `triage` sits BELOW `corpus` in the dependency DAG — that is exactly why `triage::contract::IncidentWriteOutcome` is a deliberate parallel type rather than a re-export, with the `pulse-app` adapter mapping between the two. §Cross-cutting Patterns → Module dependency direction requires a DAG with `pulse-app` as the only root and no sibling dep beyond a declared contract. So any fork-(a) periodic corpus re-read of resolved ids must be owned by `pulse-app` (which arch already places as the site holding both `Arc&lt;dyn CorpusReader&gt;` and the registry wiring), never by a new `triage → corpus` edge.
- **The predecessor's guard and its outcome type are frozen by the same arch entry.** architecture.md §Established Decisions [Corpus Write Arbitration] states the monotonic `AND updated_unix_nano &lt;= ?2` predicate at the `CorpusWriter` choke point and its `Applied | DeclinedStale` outcome as decided; it also states the app-side staleness as an ACCEPTED residual owned elsewhere. This chunk must therefore change the app half only — no re-litigation of the predicate, the existence probe, or `IncidentWriteOutcome`.
- **A cross-process notification path (fork b) has no sanctioned transport in arch.** architecture.md §Design Philosophy (single-process modular monolith, tokio channels not network hops) and §Established Decisions [Mobile / Message Broker / Push Notifications] N/A leave the app↔sidecar boundary with exactly two arch-registered mechanisms: the corpus SQLite file and atomic `.tmp`+rename data-dir files (`run/workspace-key`, `window-geometry.json`, per §Occupied Resources → Filesystem locations). Fork (b) must reuse one of those shapes or it is a new architectural transport requiring its own decision at the P4/P5 gate.
- **Reconciliation must filter on the published workspace key.** architecture.md §Occupied Resources → Filesystem locations records `run/workspace-key` as published by the app at boot and read cross-process by the `andromeda-pulse-mcp` sidecar precisely "so both filter incidents by the identity the app stamps" — bounded ≤4096 bytes, consumed as an opaque filter string, never joined as a path. The scope's "same workspace key" read-back (in-scope item 3) is that identity, not an ad-hoc one.
- **Driving the RED leg requires a feature-gated build.** architecture.md §Established Decisions [MCP Server Surface] + §Cross-cutting Patterns → Feature-gate hygiene put `mcp-server` off by default; §Occupied Resources → Process / service identity names the sidecar binary `andromeda-pulse-mcp` and the dev app binary `target/{profile}/pulse-app.exe` (NOT `andromeda-pulse`). Any smoke command for the external-resolve arm must build `--features mcp-server`, set `ANDROMEDA_PULSE_MCP_ENABLED=true`, and name those two paths correctly.
- **A mid-session corpus read only decrypts because the key is cross-process.** architecture.md §Occupied Resources → Corpus SQLite → At-rest posture requires the AES-256-GCM cell key to come from the OS credential store (keyring 3 with the explicit platform feature set), persisting across processes, with the opt-in `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` fallback. Fork (a) rests on that mandate holding at HEAD on the target host; whether the running app can in fact decrypt rows the sidecar wrote mid-session is research's question.
- **If a fork adds an interval / toggle, arch fixes where it may live.** architecture.md §Cross-cutting Patterns → Config management sets precedence env &gt; `config.toml` &gt; defaults, and §Occupied Resources → Environment variables is the canonical registry every new `ANDROMEDA_PULSE_*` var must join (env-layer-only additions carry no TauRPC/hot-reload delta; a `Settings`/`config.toml` field does, via `config.reload` / `pulse://stream/config-events`).

## Patterns to follow
- **The registered incident surface is `IncidentsApiImpl` over `IncidentRegistry` + `IncidentPersistence` + `IncidentLifecycleBroadcast`** in the `pulse-app` crate — architecture.md §Occupied Resources → Tauri IPC routes (`incidents.list_active` / `acknowledge` / `mark_resolved` / `mark_all_read` / `get_report`). A reconciler driving an existing registry transition rides this trio rather than adding a parallel one.
- **Corpus reads from the app already have a registered pattern**: `storage.inspect` / `storage.path` are backed by `crates/corpus::CorpusReader` from `pulse-app` (architecture.md §Occupied Resources → Tauri IPC routes), and `storage.export_for_training` reads `CorpusWriter::load_all_incidents` from the same crate — precedent that `pulse-app` is the arch-sanctioned place for corpus reads that feed app state.
- **Background periodic work is a tokio task on the single runtime** (architecture.md §Stack → Async runtime; §Inherited Defaults → Channels), matching the existing persist-loop shape; fan-out to subscribers is `tokio::sync::broadcast` per §Established Decisions [In-Process Channel Architecture].
- **Webview-visible state changes go out on a registered `pulse://stream/*` topic** — architecture.md §Standard Contracts → Real-time push contract and §Occupied Resources → Tauri IPC events already reserve `pulse://stream/incidents` for the incident lifecycle. A reconciliation that must reach the UI should reuse it; a new topic is a registry addition.
- **Error shapes**: `thiserror` enums module-internal, `anyhow` at boundaries, `Result&lt;T, AppError&gt;` with the stable variant set at any IPC surface (architecture.md §Conventions → Error response schema (Tauri IPC); §Inherited Defaults → Error handling). Note the [Corpus Write Arbitration] precedent that an expected non-application is modelled as an outcome value, not an `Error` — the same reasoning applies to "row already resolved elsewhere".

## Anti-patterns to avoid
- **Do not add a `triage → corpus` (or any sibling) dependency edge** to let the registry read the corpus itself — architecture.md §Cross-cutting Patterns → Module dependency direction + §Established Decisions [Corpus Write Arbitration] (DAG direction is the stated reason the parallel outcome type exists).
- **Do not invent an unregistered cross-process channel** (socket, port, named pipe, ad-hoc file outside the data dir) for a sidecar→app signal — architecture.md §Design Philosophy (single-process, no network hops) and §Occupied Resources (only `:4317`/`:4318` are reserved ports; the data-dir root is the confinement rule, with the `~/Downloads` training export as the single documented exception).
- **Do not land a new TauRPC procedure, event topic, env var, corpus table or DuckDB table without its §Occupied Resources entry** — architecture.md §Occupied Resources is canonical for all five classes, and §Cross-cutting Patterns → Webview IPC capability policy fixes the exact cost of a procedure: router registration + Occupied-Resources entry + the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` that `capability-drift` diffs, and specifically NOT a capability-JSON edit.

## Contract bindings
- **arch ↔ tests/harness**: the RED and post-fix legs need the `--features mcp-server` sidecar build plus the correct dev binary path (arch §Occupied Resources → Process / service identity; §Cross-cutting Patterns → Feature-gate hygiene). Arch §Cross-cutting Patterns → Test-time telemetry injection also forbids an in-process bypass for any telemetry the leg needs — it must arrive over real OTLP on `:4317`/`:4318`.
- **arch ↔ obs**: the scope's two RED observables (`incidents.list_active.request` → `item_count`, `triage.incident.persist` → `declined_count`) are obs-plan-owned allowlist leaves; arch contributes only that no new IPC/event resource is presumed for them. Whether `declined_count` can in fact be driven above zero by the MCP path is research's question — arch cannot attest it.
- **arch ↔ security**: any reconciliation reading `corpus/corpus.db` mid-session inherits the at-rest key-custody posture (arch §Occupied Resources → Corpus SQLite; security-plan §Data Protection → At rest owns the rest), and the workspace-key file's bounded-read / never-joined-as-a-path handling.

## Acceptance criteria contributions
- (arch) Any reconciliation logic lives in `pulse-app` (or an existing crate that already sits above `corpus`); no new `triage → corpus` or other sibling dependency edge is introduced (per architecture.md §Cross-cutting Patterns → Module dependency direction; §Established Decisions [Corpus Write Arbitration] DAG rationale).
- (arch) `update_incident_status`'s bound monotonic predicate, its existence probe, and `IncidentWriteOutcome` are unchanged in both the `CorpusWriter` and `IncidentPersistence` signatures (per architecture.md §Established Decisions [Corpus Write Arbitration]).
- (arch) Any new TauRPC procedure, `pulse://stream/*` topic, env var, or corpus/DuckDB table the chosen fork lands carries its §Occupied Resources registration and — for a procedure — its `EXPECTED_PROCEDURES` pin, with the cost stated on the P5 card before approval (per architecture.md §Occupied Resources; §Cross-cutting Patterns → Webview IPC capability policy).
- (arch) The app-side and corpus-side active sets are compared for the SAME workspace key as published at `run/workspace-key`, read as an opaque bounded filter string (per architecture.md §Occupied Resources → Filesystem locations).
