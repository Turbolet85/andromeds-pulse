# obs extract

## Relevance
Relevant — the chunk's RED and GREEN evidence is carried entirely by registered self-observation targets (`incidents.list_active.request`, `triage.incident.persist`), and every candidate fork adds or changes an emission that obs-plan governs.

## Constraints
- **The incident-path leaves are EXACT and must enumerate every field their emit site emits.** obs-plan.md §8 (Default-deny posture → Incident-path diagnostic leaves) requires `triage.incident.persist` → `incident_count`, `persist_kind`, `duration_ms`, `declined_count` ("all FOUR, not two and no longer three"), `incidents.list_active.request` → `item_count`, and `triage.incident.corpus_restore` → `kind`, `restored_incident_count`. A leaf naming fewer leaves the target PARTLY redacted — the shape no resolver probe can see. The 2026-08-27 amendment records the 4th field as applied; **whether the shipped `AllowList::production()` still matches the emit site at HEAD is research's question**, and it is load-bearing here because the RED leg reads `declined_count` off the wire.
- **No bare `incidents` or `triage` prefix key may exist** (§8, same block). If a fork adds a new `triage.incident.*` target (e.g. a reconcile record), §8 requires its OWN exact leaf; without one `for_target`'s first-`.`-segment fallback resolves nothing and every field renders `"<redacted>"`, which would make the GREEN measurement read as all-zeroes.
- **Aggregate-and-bounded-labels only on the incident path.** §8 bans, on `triage.incident.persist` verbatim and by extension on any sibling this chunk adds: incident identity, `scope_id`, workspace, title/detail, payload, the UPDATE's SQL text, and its bound parameter values. §8 Data-classification (DuckDB query parameters row) and §11 Spans/Logs restate the query-text ban (`query_id` + `param_count` only).
- **Emission cadence is once per cycle or per transition, never per row.** §11 Telemetry Strategy (hot-path over-instrumentation) and §11 Logs ("never log in hot path at `info`"); §8 records `declined_count` as folded ONCE per persist cycle "never per row and never per declined write… (the cycle writes every active row)". A reconciler that walks the active set inherits exactly that constraint.
- **A new WARN target must be registered at BOTH §6 and §8 (dual-site rule).** §6 Log Coverage → `warn` row holds the once-per-boot / once-per-transition family (`app.boot.buffer.degraded`, `corpus.keychain.fallback`, `buffer.consumer.stalled`, `interpretation.model.allow_root`…); §8 holds the allowlist leaf. Fork (c) — "make the staleness VISIBLE" — is precisely a new diagnostic target and would owe both sites.
- **A new long-running task owes a heartbeat.** §3 Heartbeat ticks + §10 Standard+ invariants require 15s ticks from long-running subsystems, with >45s gap = stall and CI's `xtask/ci/heartbeat-gap-check.sh` gate; §10 additionally warns that **tick presence is LIVENESS, not PROGRESS** — a reconciler that ticks while reconciling nothing is the same failure shape as the 2026-08-26 wedge, so fork (a) (periodic corpus re-read) needs a progress field, not just a tick.
- **Cross-surface calls propagate trace context.** §10 Standard+ ("Trace context propagation") and §11 Spans/Traces ban skipping propagation at a surface boundary. Fork (b) (sidecar → app notification) creates a new cross-process boundary; §3 Service identity gives the sidecar a distinct identity (`andromeda-pulse-mcp`), so correlation across the two processes is not implicit.

## Patterns to follow
- **Leaf COMPLETION over leaf addition when extending an existing record.** §8's `triage.incident.persist` history (`duration_ms` missed by the original two-field entry; `declined_count` added 2026-08-27) is the canonical precedent: add the field at the emit site and complete the leaf in the same change, with the guard asserting the field set **by EQUALITY in both directions** — that is what catches a narrowed leaf.
- **Bounded-token transition diagnostics.** `buffer.consumer.stalled` (§6 warn row + §8 leaf: `reason` / `consequence` bounded static tokens + two numerics, once per healthy→stalled transition and once on recovery) and `interpretation.generation.damper` (§8: 4 bounded fields, once per transition, never per decision) are the shape a "registry disagrees with corpus" signal should take under fork (c).
- **Counters ride existing ticks as FIELDS.** §5 Conceptual instrument types — `rows_ingested_delta`, `redactions_applied`, `cues_latched`, `cycles_executed` are all folded onto an existing 15s tick rather than minted as separate `metric.*` targets, with per-field emission barred by the §11 hot-path rule.
- **Guards live under `pulse-app/tests/`, plus a fallback discriminator.** §8 states the `[lib] test = false` rule repeatedly: a src-level `mod tests` guard compiles but never runs. The incident-path guard is `pulse-app/tests/unit_observability_allowlist_incident_diagnostics.rs`; siblings such as `...allowlist_consumer_stall.rs` and `...allowlist_l4_path_guard.rs` add the mutation-checked fallback-discrimination test that keeps the guard from passing vacuously after a leaf is deleted.
- **`metric.*` targets need their own leaf even though a bare `metric` key legitimately exists** (§8, delegated-timing block) — without one the fallback keeps `value` and silently redacts every label. Applies only if a fork emits a new `metric.*` observable.

## Anti-patterns to avoid
- **Per-incident / per-reconciled-row emission on the reconcile path** — §11 Telemetry Strategy + Logs; the persist cycle's own `declined_count` precedent (§8) exists specifically because the cycle touches every active row.
- **Any incident identity, `scope_id`, workspace, title/detail, payload, SQL text or bound parameter value in a field** — §8 incident-path leaves + §11 Logs/Spans (Vector 5).
- **Fork (b) only:** writing to stdout from the rmcp sidecar (§11 Universal — stdout is reserved for JSON-RPC 2.0 framing; all `tracing` forced to stderr JSON) and logging MCP tool response bodies (§11 Project-specific + §8 `mcp-server` allowlist: `method`, `result_type`, `result_count`, `feature_flag_enabled`, `duration_ms` — never `result_content`).

## Contract bindings
- **obs ↔ tests (harness contract):** §3 Log format JSON schema is verbatim from the tests Test Harness Contract — obs aligns to tests, not vice versa. RED/GREEN is read from `~/.andromeda-pulse/logs/agent-latest.jsonl` (§3 Log file location), so the chunk's measurement legs consume the tests-owned schema.
- **obs ↔ tests (allowlist guards):** every §8 leaf's guard is a test artifact under `pulse-app/tests/` — the obs mandate lands as a test file, so any leaf change in this chunk carries a tests-side deliverable.
- **obs ↔ tests (check scripts):** §10 Load-profile constraints require any xtask check script over `agent-latest.jsonl` to be NEUTRAL-tolerant (absent stream ≠ failure) and run-window-scoped via `write_run_window_log`; §10 also records `cargo xtask check:ingest-progress` / `smoke:gap-resume` as the precedent for a detector consuming an existing WARN rather than adding a second one.
- **obs ↔ arch (`health` IPC):** §3 complementarity paragraph — heartbeat ticks and the synchronous `health` command are distinct and must not be conflated; `health` is tick-derived and therefore reports liveness, not progress. Relevant if a fork exposes reconciliation state through `health`.
- **obs ↔ security:** §8 vectors 4 and 5 govern the sidecar boundary and the corpus read-back respectively (MCP response bodies; DuckDB query params).

## Acceptance criteria contributions
- RED evidence renders **unredacted**: `triage.incident.persist` shows a non-zero `declined_count` and `incidents.list_active.request` shows `item_count`, both as values rather than `"<redacted>"` in `agent-latest.jsonl` (per obs-plan.md §8 Default-deny posture → Incident-path diagnostic leaves).
- Any field added to an existing record, or any new target the chosen fork introduces, has an EXACT allowlist leaf enumerating **every** field its emit site emits, guarded under `pulse-app/tests/` by a field-set-equality-both-directions test plus a fallback discriminator (per obs-plan.md §8 Default-deny posture).
- Reconciliation emissions are once per cycle or per state transition and aggregate-only — no per-incident record, and no incident identity / `scope_id` / workspace / title / detail / SQL text / bound parameter value in any field (per obs-plan.md §11 Telemetry Strategy + §8 Incident-path diagnostic leaves).
- If the chosen fork adds a long-running task or a new WARN diagnostic, it emits a 15s heartbeat with a progress field (not liveness alone) and is registered at BOTH §6 and §8 (per obs-plan.md §3 Heartbeat ticks / §10 Standard+ invariants and §6 Log levels mapping).
