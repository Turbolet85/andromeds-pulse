## Relevance
**Relevant** — the chunk's own scope makes measurement (RED leg, two-truths read-back, cross-process assertion) load-bearing, and every fork lands new production wiring that test-plan.md governs.

## Constraints
- The chunk plan's `## Test Commands` MUST carry the full unconditional standard gate set (`cargo fmt --check` · `clippy --workspace --all-targets --all-features -D warnings` · `nextest run --workspace --profile ci` · `xtask capability-widening-check` · `xtask check:ingest-progress` · `xtask capability-drift` **LAST**, since every command above it can regenerate `bindings/index.ts`), with the three `pulse-app/ui` gates added only if the fork touches `pulse-app/ui/**` — which fork (c) "make staleness VISIBLE" would (per test-plan.md §3 Per-chunk gate discipline).
- A boot/setup-path edit obliges the **conditional boot-smoke gate** (`npx @tauri-apps/cli dev`, 60s, watch for boot-completion signals before SIGTERM) — `pulse-app/src/main.rs` is on that trigger list, and the scope's own coordinates (`main.rs:751` boot restore, `main.rs:1504` persist-loop spawn) sit exactly there; whether the selected fork actually edits a listed boot path is what makes this gate mandatory vs not (per test-plan.md §3 Boot-smoke gate).
- **RED-leg evidence must be chosen by defect SHAPE before the leg runs** (per test-plan.md §3 Direct-binary smoke variant, as qualified 2026-08-28). The 0-`ERROR` / 0-`app.panic.fatal` clean-log assertion binds the **GREEN leg only**; a stale-display defect emits no ERROR (a monotonic-guard DECLINE is not an error), so a RED leg asserting a clean log would pass vacuously as a defect measurement. The evidence of record must be the named field VALUES the scope identifies. Each leg gets its own fresh `ANDROMEDA_PULSE_DATA_DIR`, and `bash scripts/agent-run.sh status` evidences the harness contract only — it exits 0 against a dead system.
- Unit-tier home is fixed by crate: `triage` takes co-located `#[cfg(test)] mod tests` in `crates/triage/src/…`; anything landing in `pulse-app` must be a separate integration-target file under `pulse-app/tests/*.rs` reaching internals via `pub` + `#[doc(hidden)]`, because `[lib] test = false` makes co-located pulse-app tests compile but never run (per test-plan.md §2 Test directory + naming conventions and §4 Conventions → Test file location).
- The cross-process tier has a **named, still-owed debt covering this exact surface**: §6 P3's Current residual and §1 `mcp-incident-read-back-cross-process-coverage` require a subprocess `tools/call` CONTENT assertion for the 4 incident tools — `mark_incident_resolved`'s honest not-applied result is recorded as in-process-only, so a revert to an unconditional shape would pass every committed cross-process assertion. Whether this chunk discharges, narrows, or restates that debt is a P4 decision, not an assumption (per test-plan.md §1 Pending coverage triggers · §6 P3).
- Any new production call site whose revert leaves every test green must be **pinned or a trigger minted** — the plan mints one every time this recurs (`viz-read-connection-router-wiring-coverage`, `cue-latch-emitter-wiring-coverage`, `damper-shared-instance-wiring-coverage`, `l4-path-guard-callsite-wiring-coverage`). A reconciler spawned once from `main.rs` is precisely that class; one live observation is not a per-run gate (per test-plan.md §1 Pending coverage triggers).
- Zero-flakiness is a hard budget (quarantine-and-root-cause, never retry), and coverage stays ≥75% line / ≥70% branch / ≥85% function for new code (per test-plan.md §10).

## Patterns to follow
- **Clock by explicit parameter, not ambient timer, for `triage` surfaces** — §4's triage bullet records the crate's established form (`now_unix_nano`-style injection) as the stronger one precisely because these functions take the instant as an argument; `tokio::time::pause()` / `#[tokio::test(start_paused = true)]` remains the tool where a real tokio interval drives the loop (per test-plan.md §4 triage crate · §8 Time mocking).
- **Real process boundary where an in-process form would pass while the defect is live** — the `corpus` crate precedent (a test that re-executes its own test binary, because the in-process two-instance check would have been green through the defect) is the template for an app-vs-sidecar divergence test; the driver is `tokio::process::Command` + a JSON-RPC 2.0 client (per test-plan.md §4 corpus crate · §5 Module ↔ MCP sidecar).
- **Two independent halves per assertion** — the harness's standing shape is obs-record half + a second, differently-sourced half (DOM in the webview leg; here the scope's corpus read-back), never one combined boolean, so a failure says *which* truth diverged (per test-plan.md §6 Drivers per surface).
- **Narrow a `pulse-app` run with `--filter-expr` / `-E` under `--workspace`, never with `-p`** — measured 2026-08-15 to fail linking with `crate X required to be available in rlib format` immediately after a green `--workspace --tests` build (per test-plan.md §3 `run` → Test selection).
- **Self-bootstrapping fixtures** — seed via OTLP ingest through the live receiver plus per-test in-memory DuckDB inserts and `rstest` fixtures; the three named builder factories (`MockTraceSpan` / `MockArrowBatch` / `MockMetricPoint`) are **specified but unimplemented** (0 workspace hits), so no plan text mandating them may be cited as available (per test-plan.md §7 Self-bootstrapping requirement · §1 `test-data-bootstrap-factories-unimplemented`).

## Anti-patterns to avoid
- NEVER synchronize on `sleep(N)` or read real time without injection — a 60s-cadence reconciler tested by waiting is both flaky and slow; wait on an explicit signal or an injected instant (per test-plan.md §11 E2E · §11 Universal).
- NEVER mock DuckDB or the corpus at the integration tier, and NEVER mock the surface under test — use an ephemeral in-memory instance and the real sidecar boundary (per test-plan.md §11 Integration · §8 What NOT to mock).
- NEVER assert against crate-internal implementation details — pin the public boundary (`IncidentRegistry::mark_resolved` and the corpus read path are declared trait surfaces; whether the existing `ResolutionTrigger` variants already express "resolved externally" is research's question, not something this extract can attest) (per test-plan.md §11 Unit).

## Contract bindings
- **obs ↔ tests (log format + harness `logs`):** both RED observables are read out of the obs NDJSON family, so the leg must resolve the ROTATED `agent-latest.jsonl*` family across the three precedence-ordered bases — a bare-name or `*.log` read silently finds nothing and false-reports an empty log on a healthy boot (test-plan.md §3 `logs` / Log format ↔ obs-plan §3).
- **obs ↔ tests (allowlist pinning):** any NEW record or field a fork adds requires its obs allowlist leaf plus the established `pulse-app/tests/unit_observability_allowlist_*.rs` pin; the scope asserts the two existing observables are already allowlisted and pinned — whether they are, and whether they render the needed fields unredacted, is research's question to confirm (test-plan.md §3 Log format ↔ obs-plan §Log format).
- **security ↔ tests (CI gate):** `cargo deny check bans` must not be skipped and deny violations are a build-failure condition — this is the shared workflow surface the folded `cargo audit` full-form PREREQ (security-owned) touches (test-plan.md §9 Build failure conditions · §11 Test Strategy).
- **a11y/webview ↔ tests (conditional):** only if the fork renders staleness in the UI — then the three `npm run … --prefix pulse-app/ui` gates become mandatory, and the a11y suite (`cargo xtask test:a11y`, CI-wired) plus the 16-stage `cargo xtask webview-drive` leg (dev-host only, NOT CI-wired) become the relevant DOM tiers (test-plan.md §3 gate set · §9 A11y suite / E2E).
- **arch ↔ tests (new TauRPC procedure):** if a fork adds one, `cargo xtask capability-drift` (staged-copy read, run LAST) and the `EXPECTED_PROCEDURES` / bindings-merge cost the scope already flags become part of the gate set (test-plan.md §3 · §9 Capability verification matrix).

## Acceptance criteria contributions
- (tests) The full standard gate set runs green with `cargo nextest run --workspace --profile ci` and `cargo xtask capability-drift` invoked LAST; the three `pulse-app/ui` gates are included iff any `pulse-app/ui/**` path is touched (per test-plan.md §3 Per-chunk gate discipline).
- (tests) Two smoke legs on separate fresh data dirs: the RED leg's verdict rests on the named field values (`triage.incident.persist` → `declined_count > 0`; `incidents.list_active.request` → `item_count`), NOT on a clean-log assertion, which binds the GREEN leg only and would pass vacuously here; the GREEN leg asserts 0 `ERROR` / 0 `app.panic.fatal` and clean shutdown by specific pid with `:4317`/`:4318` released (per test-plan.md §3 Direct-binary smoke variant). If a listed boot path is edited, the boot-smoke gate runs additionally (per test-plan.md §3 Boot-smoke gate).
- (tests) New reconciliation logic carries in-crate `triage` pins at the public boundary with the instant supplied as an explicit parameter, each mutation-checked so it reddens when the behaviour is neutralized; new-code coverage holds ≥75% line / ≥70% branch / ≥85% function (per test-plan.md §4 triage crate · §10).
- (tests) The chunk either lands a cross-process assertion over the sidecar's incident-tool response CONTENT (subprocess + JSON-RPC 2.0), or records on the report why `mcp-incident-read-back-cross-process-coverage` survives — and mints a wiring trigger for any single-call-site reconciler whose revert would leave every test green (per test-plan.md §1 Pending coverage triggers · §6 P3 Current residual).
