# security extract

## Relevance
Partial — relevant on three seams: a possible NEW cross-process input boundary (fork (b)), corpus/SQL parameter binding on any mid-session re-read (fork (a)), and the TauRPC drift gate if a procedure lands; plus the folded `cargo audit` PREREQ, which is squarely this domain.

## Constraints
- If the winning fork adds a sidecar→app notification path, it is a NEW cross-process input boundary and must be validated as untrusted **on the read side** — bounded byte ceiling, encoding/shape checked, empty and control-character values rejected, any failure yielding a graceful fallback rather than a panic — and the boundary must be added as a row to the §Input Validation table (per security-plan.md §Input Validation, `<data_dir>/run/workspace-key` row, which is the same app-writes/sidecar-reads shape inverted).
- Any predicate the reconciler issues against the corpus (or the ring buffer) must bind the workspace key, incident ids and resolved-id sets through prepared-statement `?` placeholders; identifier interpolation is banned entirely and user input never names a table (per security-plan.md §Input Validation, DuckDB-query-parameters row, and §Security Anti-Patterns → Input). Whether `CorpusReader::load_active_incidents` and its siblings already bind rather than interpolate is research's question.
- The workspace key must stay an **opaque filter string** — never opened, joined, or used as a path — which is what closes CWE-22 by construction on that value (per security-plan.md §Input Validation, published-workspace-key row). A reconciler keyed by workspace must not turn the key into a filesystem lookup.
- If a fork lands a TauRPC procedure, the two per-procedure enforcement pieces are its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` **and** a validated argument struct — capability JSON is explicitly not per-procedure here (per security-plan.md §API Security, TauRPC capability authorization; §Security Anti-Patterns → API).
- Nothing on the reconciliation path may log raw OTLP-derived incident content, MCP tool response bodies, or a full product-consumed filesystem path (basename of the canonicalized path only) (per security-plan.md §Logging & Monitoring, "What NEVER to log"; §Security Anti-Patterns → Logging). New or widened fields on `triage.incident.persist` / `incidents.list_active.request` inherit this.
- If the fork **writes** any projection back to the corpus (e.g. a resolution marker or summary), that write path must pass `security::scrubber::scrub_attribute` at the boundary, matching the enumerated incident-summary write paths (per security-plan.md §Security Anti-Patterns → Logging, uniform-scrubber-coverage enumeration). Whether the chosen fork writes at all is a P4 question.
- A mid-session corpus read decrypts AES-256-GCM cells; the 32-byte cell key is secret-class and must remain unlogged with `#[tracing::instrument(skip(key))]` discipline at every key-handling site (per security-plan.md §Secret Management → Storage → Runtime and "What counts as secret"). A new read cadence must not widen key handling.
- Errors surfaced from the reconciler across the bridge must collapse to the `serde`-friendly `AppError` variants with no stack traces, Rust struct names, file paths, or library versions in `Internal { message }`; `anyhow::Error` is never serialized directly (per security-plan.md §Error Handling and §Security Anti-Patterns → Code Patterns).

## Patterns to follow
- The `workspace_detector::contract::{publish_workspace_key, read_published_workspace_key}` cross-process contract — canonicalize-and-confine on write, bounded + encoding-checked + control-char-rejecting read, value consumed only as an opaque filter string (security-plan.md §Input Validation). This is the nearest precedent for any sidecar↔app channel fork (b) would introduce.
- Bounded-parse-with-graceful-default for self-written state read back at runtime: missing / corrupt / out-of-range degrades to the documented default, never a panic and never a silent adoption of an unintended value (security-plan.md §Input Validation, window-geometry and baseline-bootstrap rows).
- Shared prepared-statement query path — the `viz` crate handlers and the MCP `query_*` tools already route through one parameter-bound code path (security-plan.md §Input Validation, DuckDB-query-parameters + MCP-stdio rows); a reconciler read should join that path rather than mint a new query construction site.
- `scrubbed_clone` / `scrubbed_l4_json`-style scrubbed projections at the corpus write boundary, with `Redacted` collapsing to a category marker in place (security-plan.md §Security Anti-Patterns → Logging).

## Anti-patterns to avoid
- NEVER add a TauRPC procedure to a router without its `EXPECTED_PROCEDURES` pin AND a validated argument struct (security-plan.md §Security Anti-Patterns → API).
- NEVER build a SQL predicate with `format!` from a workspace key, incident id, or resolved-id set (security-plan.md §Security Anti-Patterns → Input).
- NEVER emit raw OTLP-derived incident content, MCP response bodies, or full product-consumed paths on the new observables (security-plan.md §Security Anti-Patterns → Logging).

## Contract bindings
- **PII scrubbing ↔ obs + tests:** the RED leg drives a real external resolve through the MCP path; canaries and fixtures must be synthetic, and any new field on `triage.incident.persist` / `incidents.list_active.request` must carry no OTLP-derived value — obs owns the schema, security owns the no-content rule (security-plan.md §Security Anti-Patterns → Logging).
- **CI security gate ↔ tests §CI Integration:** the `cargo deny check bans licenses sources` job is the named overlap signal that must stay exit 0 this chunk, and `cargo deny check advisories` is the designed-red channel whose DISTINCT owned-id set is re-enumerated at the probe (security-plan.md §Dependency Security → CI integration).
- **Drift gate ↔ tests:** if a procedure lands, `xtask capability-drift` plus the `emit_taurpc_bindings` merge are the enforcement, not a capability-JSON edit (security-plan.md §API Security).
