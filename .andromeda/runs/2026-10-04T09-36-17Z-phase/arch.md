# arch extract

## Relevance
partial — arch owns where a launch-posture lever lives (the `pulse-app` binary boot), how a new env read/write is registered, and the config-precedence rule a pre-set value must respect. It says nothing about the WebKitGTK/Wayland mechanism itself; that is research's to measure.

## Constraints
- Code placement: a launch-environment lever is binary-boundary work, so it belongs in `pulse-app` (the only DAG root and the tokio runtime owner). No library crate may gain a `tauri`/GTK concern, and no new crate is warranted. Per architecture §Cross-cutting Patterns → Module dependency direction and §Established Decisions [Module Boundaries]. Whether a GPU/session probe already exists in a lower crate is research's question (e.g. `interpretation::HardwareProfileDetector`'s libcuda probe, per §Occupied Resources env list / CLAUDE.md module map). If one does, reusing it must not invert the DAG.
- Platform scope: the product is cross-platform and ships one codebase to Windows, macOS and Linux (§Project Intent → Product type; §Established Decisions [Platform] Tauri 2). So a Linux-only remedy must leave the other two OS launch paths byte-for-byte unchanged in behaviour. The scope boundary "Linux only" is the arch-consistent reading.
- Config precedence: arch fixes the order as process env > `config.toml` > built-in defaults, highest wins (§Cross-cutting Patterns → Config management; §Inherited Defaults → Config precedence). A lever value the user or a harness has already set must therefore beat any default the binary applies. This makes the scope's [inferred] "honour, never overwrite" a direct consequence of an arch rule, not a free choice.
- Env-var registry completeness: §Occupied Resources → Environment variables is the canonical list of every env var the product reads or SETS. That includes non-`ANDROMEDA_PULSE_*` system vars, which are registered with their reader/setter and posture (precedents: `XDG_RUNTIME_DIR` under §Filesystem locations → corpus-key lock file; `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`). If the remedy reads a detection signal (e.g. a session/driver indicator) or sets a WebKit/GDK var, each needs a registry entry naming product-set vs product-read, its OS scope and its residuals. That entry is a wrap amendment, as the scope already notes.
- GPU-posture precedent: §Occupied Resources → `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` records that a webview GPU-posture var "must stay out of product config", because there it would change the shipped webview's GPU posture. A "default" or "detect and fall back" shape here would deliberately make such a var product-set on Linux. That is a conscious departure from that entry's stated posture, and the registry entry and P4 fork must say so explicitly rather than ride the precedent silently.
- Visualization surface: §Established Decisions [WebGPU Visualization Surface] and §Stack → Visualization surface lock the webview WebGPU canvas. A renderer lever that changes how WebKitGTK composites (DMA-BUF off) must not be assumed neutral to WebGPU frame production. WebGPU frame budgets are out of scope per the scope's Boundaries, so any observed effect is recorded and routed, not absorbed.
- Surfaces untouched: no new port, TauRPC procedure, capability identifier, DuckDB/corpus table or Cargo feature, per §Occupied Resources (ports / IPC routes / capability identifiers / tables) and §Conventions → Feature flags. Any of these appearing would be a scope breach needing its own registry entry.

## Patterns to follow
- Resolve once at boot, with a bounded parse and a closed outcome. The env-layer vars in §Occupied Resources (`ANDROMEDA_PULSE_L4_ALLOW_ROOT`, `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS`) set the shape: trimmed, unset/blank ⇒ default, a non-default posture announced exactly once per boot, never a panic, never blocking boot. A launch posture fits the same shape, and it stays env-layer only, with no `Settings` field, no `config.toml` key, no TauRPC contract and no hot-reload delta.
- Basename-only, closed-label boot records. Boot records carry closed labels and env-var NAMES, never values beyond a closed label and never paths (§Occupied Resources records `interpretation.model.allow_root` as WARN/INFO once per boot, basename-only). A posture record should name the chosen posture as a closed label.
- Out-of-process verifiability through the agent harness. Its contract is `scripts/agent-run.{sh,ps1}` boot by path, `harness:status` verdict and the `run/andromeda-pulse.exit` end record (§Occupied Resources → xtask CLI surfaces). The CI `boot` job runs it under `xvfb-run` (§Infrastructure Patterns → CI/CD approach), so it is an X11 arm by construction. This matches the scope's note that Xvfb is admissible only as a control arm, never as the Wayland witness.

## Anti-patterns to avoid
- Applying the lever unconditionally on every OS, or overwriting a pre-set value. That violates §Cross-cutting Patterns → Config management precedence and the cross-platform intent in §Project Intent.
- Moving launch-posture logic into a library crate, or adding a GTK/tauri dep there to probe the session. That violates §Cross-cutting Patterns → Module dependency direction.
- Landing a product-set or product-read env var without a §Occupied Resources → Environment variables entry. That repeats the unregistered-var class the registry records it has corrected before (`PULSE_*` relay set, `ANDROMEDA_PULSE_MODEL_PATH` "registry completeness").

## Contract bindings
- arch ↔ security: any new product-read env input (a detection signal) falls under the security rule for product-consumed env inputs (trim / bound / fail posture). The registry entry's posture text must agree with security-plan §Security Anti-Patterns → Input. A product-SET var is not a path input, but the entry still states its residuals per the §Occupied Resources precedent.
- arch ↔ obs: the posture boot record is a new self-observation target. It needs its own obs allowlist leaf, or its label fields are silently redacted (pattern recorded in §Occupied Resources → Tauri IPC routes, `telemetry.frontend.*` leaf note). Field shape: closed label + var NAME only.
- arch ↔ tests: the measurement arms (Wayland witness vs Xvfb/X11 control) bind to the agent-harness contract in §Occupied Resources → xtask CLI surfaces and the CI `boot` job in §Infrastructure Patterns → CI/CD approach. The CI boot-smoke WATCH rides that same job but carries no criterion.

## Acceptance criteria contributions
- The remedy's code lives in `pulse-app` (binary boundary), runs before the Tauri builder/GTK initialise, and adds no crate, port, TauRPC procedure, capability identifier or Cargo feature (per architecture §Cross-cutting Patterns → Module dependency direction; §Occupied Resources).
- The macOS and Windows launch paths are behaviourally unchanged: the lever is compiled or gated to Linux only (per architecture §Project Intent → Product type).
- A pre-set value of the lever env var survives launch unmodified: the binary only fills an unset/blank value (per architecture §Cross-cutting Patterns → Config management).
- Every env var the remedy sets or reads is named, at wrap, in a §Occupied Resources → Environment variables entry stating product-set vs product-read, OS scope and residuals. If the shape is a product-set GPU-posture var, the entry explicitly reconciles with the `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` "stay out of product config" posture (per architecture §Occupied Resources → Environment variables).
