# a11y extract

## Relevance
partial — the chunk adds no UI surface, role, key binding, token or animation; its only a11y contact is that a Linux launch-posture lever (a WebKitGTK renderer env var set before GTK init) changes how the desktop-webview surface is hosted on Linux, so the duty is non-regression of the Linux webview's a11y exposure plus accessible wording if the remedy shape is "document".

## Constraints
- The Linux desktop-webview is one of the plan's assertable surfaces, and Orca 48.x is its named screen-reader target. A launch posture that keeps the window alive must not cost Linux users the webview's accessibility tree, which is exposed through the OS a11y API (per a11y-plan §1 A11y Scope Summary, surfaces table; §7 Per-surface SR test pattern, Linux row). Whether disabling the DMA-BUF renderer or applying any other measured lever changes the WebKitGTK a11y tree (ATK / AT-SPI bridge) is a question for research. This extract does not assert it either way.
- `prefers-reduced-motion: reduce` must keep reaching the webview under whatever posture ships (SC 2.3.3 AAA escalation). The renderer lever must not change how the media query resolves inside WebKitGTK (per a11y-plan §6 Motion tokens; §11 Motion). Whether a renderer env var can affect media-query resolution is also for research. The expected answer is no, but nothing here measures it.
- The tier is Standard WCAG 2.1 AA, and its SLO is zero WCAG AA violations on must-be-accessible paths, with no retry-once policy (per a11y-plan §1; §10 SLO Invariants & A11y Budgets). A Linux-only boot change sits inside that invariant. It is not exempt from it.
- The `a11y` CI matrix job (Linux/macOS/Windows) audits the built SPA, which is served statically, through Playwright chromium with a mocked Tauri IPC. It never runs inside the WebKitGTK webview (per a11y-plan §3 CI integration; §3 Harness wiring & conventions). A green a11y job therefore says nothing about the shipped posture's effect on the real Linux webview. It shows only that the SPA did not regress.
- If the remedy shape is "document", the plan's baseline wording disciplines apply to the text a Linux user reads: plain language, plus an actionable recovery step (the workaround) stated with the limitation (per a11y-plan §8 Cognitive Accessibility, baseline disciplines, SC 3.3.3 analogue).

## Patterns to follow
- Keep the a11y suite's health check cheap and config-named. Run `npx playwright test --config=playwright-a11y.config.ts --list`, never the bare `--list`, which reads the inert default config (per a11y-plan §3 Harness wiring & conventions). Use this check only if the chunk touches anything under `pulse-app/ui/`. The expected answer is that it touches nothing there.
- Treat manual screen-reader passes as supplemental, never as the witness. If research finds that the lever could plausibly affect AT-SPI exposure, use an Orca spot-check on the real-display slot (the operator grants the slot; the agent never launches on its own) and record it as supplemental evidence beside the automated gates (per a11y-plan §3 Screen reader test pattern; §11 Universal).
- Leave the regression baseline unchanged. A chunk with no SPA change compares against `baselines/a11y-violations-summary.json` and should produce zero new tuples (per a11y-plan §3 CI integration, per-PR regression detection; §3 Harness wiring & conventions, Regression baseline).

## Anti-patterns to avoid
- Never claim that the shipped Linux posture "keeps the app accessible" without machine-verifiable evidence. The a11y job's chromium audit does not cover WebKitGTK, so it cannot be cited as that evidence (per a11y-plan §11 Strategy; §11 Universal).
- Never soften or skip the a11y CI gate because the chunk is "backend-only". The gate is fail-fast on every PR and has no retry-once policy (per a11y-plan §11 CI; §11 SLO).

- a11y ↔ design: the reduced-motion override binds to design §Motion. The renderer lever must not disturb that path (per a11y-plan §6 Motion tokens).
