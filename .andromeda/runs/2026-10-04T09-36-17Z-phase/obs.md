## Relevance
partial — the chunk is a boot-posture/launch-survival fix, not new instrumentation; obs binds through the one bounded posture boot record the scope proposes, the `app.exit` blind-spot class the death may fall into, and the boot-order constraint on tracing init.

## Constraints
- Any new posture record must be an EXACT allowlist leaf naming ALL fields its emit site emits: obs-plan §8 PII Scrubbing (default-deny posture; the `app.boot.buffer.degraded` / `app.exit` entries) requires this because no bare `app` key is registered, so a target without its own leaf falls through `for_target` and every field redacts silently. Whether an existing `app.boot.*` leaf could carry the record is research's question.
- Posture records follow the once-per-boot, closed-label shape: obs-plan §6 Log Coverage (warn row: `triage.baseline.bootstrap_window.override`, `corpus.keychain.fallback`, `interpretation.model.allow_root`) requires a boot-time choice that would otherwise be invisible to emit EXACTLY ONCE per boot, off any hot path, with fields drawn from a bounded static label set. Level follows the same row: WARN for a degraded or overridden posture, INFO for the expected one.
- Only the env var NAME may be logged, never its value or any path: obs-plan §8 PII Scrubbing (Environment variables row: names are OK to log structurally) plus the §5 trigger Vector 6 basename-only rule (`*_PATH` / `*_DIR` naming is not exhaustive). Whether the lever value needs logging at all is the plan's call, not a given.
- Ordering: obs-plan §3 Tracing init sets the init sequence (env/config, then the subscriber, then the panic hook, then the Tauri spawn). An env lever that must be in place before GTK/WebKit init and before any thread is spawned has to fit that sequence. Notably, `tracing-appender`'s non-blocking writer spawns a worker thread, so a `set_var` placed after `observability::init` would run with a thread already live. Where the lever sits relative to `observability::init`, and how the posture record is emitted if the decision is made before the sink exists (deferred emit), is research's question.
- The death mechanism must be classified against the stated exit-record blind spots: obs-plan §7 Error Capture & Reporting (Process-end cause) lists `_exit`, SIGKILL and pre-sink failures as unloggable by construction, while a C `exit()` from GTK/GDK/WebKitGTK counts as a LOGGABLE `outside_event_loop` end. The Error 71 death with no `app.exit` record is consistent only with an unloggable end, so the GTK-`_exit` hypothesis in scope is measured against §7's list, never assumed. obs-plan §6 `app.exit` row defines the closed `exit_class` set this reading uses.
- Agent-readable evidence only: obs-plan §2 Telemetry Strategy (agent-readable invariants) and §3 Logging stack say the app has ONE sink, `agent-latest.jsonl`, with no stderr `tracing` layer. So the Gdk `Error 71` line, which GTK writes to stderr, is NOT in the JSON log. The half-1 measurement has to capture stderr / `boot.log` separately and cite it as such.

## Patterns to follow
- Env-override boot record precedent: `triage.baseline.bootstrap_window.override` (obs-plan §6 warn row; §8 leaf entry). It fires once per boot, its reason label is bounded, and an exact leaf is guarded by a `pulse-app/tests/unit_observability_allowlist_*.rs` test.
- Allowlist guard-test shape (obs-plan §8, the `buffer.consumer.stalled` and L4 path-guard leaves): the test resolves the exact leaf, checks the field set for equality in both directions, and adds a fallback-set discriminator so the guard cannot pass vacuously once the leaf is deleted. It lives under `pulse-app/tests/`, not lib tests.
- The platform-startup tag vocabulary `webview_backend: "GTKWebKit"` on `app.boot.webview.init` (obs-plan §1 Telemetry triggers, multi-platform-exporter-compat row) is the existing per-platform boot-span convention a Linux posture field could sit beside. Whether that span is emitted today is research's question.
- Closed-enum record by construction (obs-plan §6/§8 `app.exit`, `app.boot.window.navigation`): every field is a closed label or a scalar, and the field most tempting to add "for debuggability" (here, the env value or the compositor/driver string) is banned explicitly.

## Anti-patterns to avoid
- NEVER log full paths or raw values — obs-plan §11 Logs (Vector 3/5 bans) and §8 Environment variables row. An env-detection probe must not emit the compositor socket path (`WAYLAND_DISPLAY`), driver version strings or any user-set lever value.
- NEVER use unbounded label cardinality in event fields — obs-plan §11 Metrics. A detection signal (driver vendor, session type) gets enumerated labels plus `unknown`, never a free string.
- NEVER add retry-once or relaunch-on-crash masking — obs-plan §11 SLO / §10 Always-required invariant. A remedy that silently relaunches after the Wayland death would hide the failure class rather than remove it.

## Acceptance criteria contributions
- If a posture is applied, exactly one boot record per process names the chosen posture with closed-label fields only: no env value, no path, no compositor/driver string. Its target resolves to an EXACT allowlist leaf whose field set equals the emitted set in both directions, pinned by a `pulse-app/tests/` guard with a fallback discriminator (per obs-plan §8 PII Scrubbing, default-deny posture + leaf-entry convention; §6 Log Coverage once-per-boot rows).
- On a real-display launch at the remedied posture, the run's `agent-latest.jsonl` holds no `app.panic.fatal`. If the process ends, it holds exactly one `app.exit` with a closed `exit_class` (per obs-plan §6 `app.exit` row; §10 zero-unlogged-panics).
- The half-1 result states, for each failing launch, which obs-plan §7 Process-end class the death falls in. It cites stderr / `boot.log` for the Gdk line, since that line is outside the JSON sink, and records the absence or presence of `app.exit` as evidence (per obs-plan §7 Error Capture & Reporting, Process-end cause; §3 Logging stack, single sink).
- The env lever is set before the non-blocking log writer's worker thread or any other thread exists. Either that, or the plan explicitly records why the edition-2024 `set_var` precondition still holds at the chosen site (per obs-plan §3 Tracing init, init order).
