# layouts extract

## Relevance
partial — the chunk creates and modifies no surface, region, component, focus order or breakpoint. It is a Linux boot-time env/posture change. It touches layouts only as a no-regression boundary: whatever lever ships (a renderer env var, a backend switch, or a documented workaround) runs under every desktop-webview window, so it must not break the frameless-window layout contract on Linux.

## Constraints
- The desktop-webview windows have to come up whole on Linux under the chosen posture: the compact widget, full dashboard, findings window and report window are all borderless, custom-chrome surfaces (per layout-templates §Surface: desktop-webview → §Primary screens). A launch that "stays up" but drops any of them does not meet this domain's bar. Whether the default posture currently renders all four on the dev host before the death is research's question.
- The custom titlebar needs a working drag region over the full width except the buttons (`data-tauri-drag-region`), with the three Linux window controls (minimize / maximize / close) on the right (per layout-templates §Component — Custom titlebar (desktop-webview specific)). Any lever that changes the GDK backend or compositing path must keep drag + window controls working on Linux. Whether a backend-level lever (e.g. XWayland instead of native Wayland) changes that behaviour is research's or the measurement's question, not a spec claim.
- Window placement depends on geometry. The compact widget snaps to four corners, default top-right (per layout-templates §IA notes → Navigation model). The findings window docks directly below the widget, positioned from the widget's live geometry and clamped to the work area and across monitors. The report window is positioned left of the findings window and clamped (per layout-templates §Primary screens → Findings window / Report window). If the remedy shape changes the windowing backend, the plan must say whether these placement rules still hold. The spec cannot attest how native Wayland versus XWayland positioning behaves today.
- The full dashboard Traces screen requires a bounded flex column with no outer page scrollbar at any window size, and only the table region scrolls (per layout-templates §Wireframe — Full dashboard (Traces primary screen) → Wireframe notes). A renderer lever (DMA-BUF off → a different compositing path) must not change this layout. It is a regression check, not new work.
- Linux tray and windowing must support both X11 and Wayland tray protocols (per layout-templates §Surface: desktop-native → §IA notes → Platform-specific notes → Linux). A "default on every Linux host" remedy must not narrow that, for example by forcing one protocol on a host that never showed the defect (the scope already keeps non-NVIDIA and X11 failures out of scope).

## Patterns to follow
- Platform-scoped behaviour sits in the platform-specific notes and is never folded into the shared surface spec (per layout-templates §Surface: desktop-native → §IA notes → Platform-specific notes). A Linux-only posture stays Linux-only, which matches the scope's "macOS and Windows launch paths are unchanged".
- Graceful in-surface fallback rather than a dead surface: the spec's WebGPU fallback is a `font-body` message in the canvas region when WebGPU is unavailable (per layout-templates §Component — Halo State Pulse canvas (hero / signature) → Fallback). That component is deferred, so the pattern is cited only as precedent: a degraded renderer should give a readable surface, not a blank one.
- Treat a measured status note as the governing truth over older sketch text (per layout-templates §Component — Halo State Pulse canvas, the MEASURED / DEFERRED status note). If the "document" shape ships, the Linux limitation goes where a Linux user meets it, as a measured statement and not a sketch.

## Anti-patterns to avoid
- Do not use this chunk to absorb or revive the deferred Halo State Pulse glow layer, the tray halo overlay window, or WebGPU frame work (per layout-templates §Component — Halo State Pulse canvas → status note, and §Surface: desktop-native → Signature placement, both DEFERRED to the next version). The scope already excludes them.
- Do not treat "the process stayed up" as proof that the layout survived. A blank or unplaced window is a layout regression even when the launch counts as a success (per layout-templates §Primary screens, which defines what each window must show).

## Contract bindings
- layouts ↔ a11y: if the lever changes the rendering or compositing path, the Traces hero must still render as its named landmark region with its visually hidden `aria-describedby` summary, and the roving-tabindex table must keep a single tab stop (per layout-templates §Wireframe — Full dashboard → Wireframe notes and §Component — Trace data table → Keyboard / focus). This binds to a11y-plan §3 harness checks if a real-display run is taken.
- layouts ↔ tests/verification-harness: the real-display measurement launches (operator-granted slot) are the only runs that can witness the windows rendering under native Wayland. The Xvfb/X11 arm is a control only (per the chunk scope, Measurement constraints) and cannot witness the Wayland-side layout.

## Acceptance criteria contributions
- (layouts) On the dev host (NVIDIA + Hyprland, native Wayland) under the shipped posture, the compact widget opens with its custom titlebar (title, settings button, three window controls on the right) and its canvas + footer regions laid out as the compact wireframe specifies. The witness is the operator-granted real-display launch (per layout-templates §Wireframe — Compact widget and §Component — Custom titlebar (desktop-webview specific)).
- (layouts) Under the shipped posture the titlebar drag region and the minimize / maximize / close controls still work on Linux. A drag moves the window and each control acts, observed on the same real-display launch (per layout-templates §Component — Custom titlebar (desktop-webview specific)).
- (layouts) Under the shipped posture the widget boots at its configured corner, and opening the findings window docks it below the widget, clamped to the work area. If the posture makes either impossible, the plan records that as a measured limitation and does not claim the placement holds (per layout-templates §IA notes → Navigation model and §Primary screens → Findings window).
- (layouts) Under the shipped posture the full dashboard Traces screen shows no outer page scrollbar, and only the table region scrolls (per layout-templates §Wireframe — Full dashboard (Traces primary screen) → Wireframe notes).
