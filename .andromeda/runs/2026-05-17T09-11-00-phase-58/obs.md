## Patterns к follow

- **Heartbeat tick event format** per obs-plan §3 Heartbeat ticks: `tracing::info!(target: "triage.tick", cues_evaluated=N, cues_emitted=M, services_tracked=X, "heartbeat")` once per tick interval; rides same JSON file sink.
- **`metric.{module}.{measure}` target prefix** per obs-plan §5 + §2 Naming conventions — chunk #62 contributes new metric event `metric.cue.emit_count_total` (counter, per-emission increment) with labels `kind` (bounded to `CueKind`) + `priority` (bounded to `PriorityTier`). Per route §3 chunk #62 amendment 2026-05-17 this is the explicit expected metric.
- **Level discipline per obs-plan §6 Per-module log levels** — `info` for boundary tick + cue emission summary; `debug` for per-tracker evaluation detail (gated by `ANDROMEDA_PULSE_LOG_LEVEL=debug`); `warn`/`error` not expected on this path unless threshold config load fails.
- **Default subscriber fields automatic** per obs-plan §3 Service identity — `service.name=com.andromeda.pulse` + `service.version` + `deployment.environment=production` ride every event via `Layer::with_default_fields`; no per-call boilerplate in chunk #62.
- **Trace context propagation via `tracing::Span::current()`** per obs-plan §3 Trace context propagation — internal async background task (no external trace_id source); but if cue emission is triggered downstream by an external OTLP ingest path, the existing trace_id should propagate naturally via `tracing::Span::current()` inheritance from the baseline tracker update path.
- **Threshold values logged as event fields** per obs-plan §6 Boundary-call wrappers — emit `error_rate_multiplier=3.0`, `latency_multiplier=2.5`, `source: "config"|"default"` on the evaluation span so agent paste-to-AI can correlate cue counts to threshold tuning.

## Anti-patterns к avoid

- **NEVER over-instrument the per-tracker evaluation loop** per obs-plan §11 Telemetry Strategy anti-pattern — the tick task iterates all trackers per cycle; do NOT emit a `tracing::info!` per tracker inside the loop. Aggregate counters (`cues_evaluated`, `cues_emitted`) emitted once per tick at `info`; per-tracker detail gated to `debug` level inside `if tracing::enabled!(Level::DEBUG) { ... }` block per §11 Metrics anti-pattern "NEVER format expensive `tracing` event payloads inside hot paths without level-gating".
- **NEVER include raw OTLP attribute values or `Incident.detail` content in event fields** per obs-plan §11 Spans/Traces anti-pattern + Vector 1 — only `kind` enum + `priority` enum + bounded `service_name_tag` enter spans; never the user-facing cue title/detail/evidence strings (those go to the product-feature broadcast, not the self-observation JSON log).
- **NEVER use high-cardinality labels on `metric.cue.emit_count_total`** per obs-plan §11 Metrics anti-pattern — bound labels к `kind` enum + `priority` enum + bounded service category; do NOT include `incident_id`, `trace_id`, raw service.name strings, or any unbounded operation identifier.
- **NEVER skip the heartbeat tick** per obs-plan §10 Standard+ invariants — the new 1-2s tick task IS a long-running subsystem; CI gate detects >45s tick gap and fails build per obs-plan §10 CI gates "Build fails if heartbeat tick stalls detected".
- **NEVER hold `tracing::Span` guard across `.await` without `.in_current_span()`** per obs-plan §11 Spans/Traces anti-pattern — the tick task awaits on `tokio::time::interval`; ensure span boundaries don't bleed into the next tick iteration.
- **NEVER log AttentionCue/Incident content payloads on the self-observation path** — the broadcast carries the full payload; the JSON log captures only emission metadata. Cross-cuts obs-plan §11 project-specific anti-pattern "NEVER conflate the product's external snapshot pipeline ... with the self-observation surface".
