## Anti-patterns to avoid

- NEVER spawn the production tick task in unit tests against the real clock — flakes when CI is loaded. Use `tokio::time::pause()` + `advance()` OR extract the synchronous evaluation helper (per test-plan §11 Universal + §Session Additions 2026-05-03 / 2026-05-06).
- NEVER hardcode threshold multipliers (3.0× / 2.5×) as compile-time `const` in test assertions — load from a `Config` fixture so the test reads the same value the production code reads; otherwise threshold-tuning changes in chunk #86 (hot-reload wiring) silently break asserts (per test-plan §11 Quality "NEVER lower coverage threshold to pass build" generalized to "tests must read config the same way production does").
- NEVER drop the `cadence-triggers` mpsc `Receiver` before assertions — causes `Sender::try_send` → `TrySendError::Closed` on subsequent emits in the same test (per §Session Additions 2026-05-05).
- NEVER assert tick count exact-equality (`toHaveBeenCalledTimes(N)`) for the background emitter — multi-thread runtimes plus `advance()` semantics can produce 1-or-2 invocations per nominal tick window depending on scheduling; use `>= 1` semantics OR drive the emitter via direct function call rather than spawned task (per §Session Additions 2026-05-08 vitest-equivalent + agent-driven determinism in test-plan §3).
- NEVER log raw `AttentionCue` payload contents (cue text / detail / evidence field values) in tracing emits — security plan §Logging discipline applies (incidentally captured OTLP attribute values could land in cue evidence); chunk #62 must include PII negative-canary unit test asserting canary strings don't leak into `metric.cue.*` fields (per test-plan §11 Project-specific bans + §Session Additions 2026-05-11 PII negative-canary pattern).
