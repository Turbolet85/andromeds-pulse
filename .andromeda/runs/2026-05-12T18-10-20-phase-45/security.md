## Constraints

- **MCP feature double-gate enforcement is load-bearing**: the rmcp stdio sidecar MUST require BOTH compile-time `--features mcp-server` AND runtime `ANDROMEDA_PULSE_MCP_ENABLED=true`; single-gate is a regression of the architecture-declared double-gate and a §Security Anti-Patterns § Code Patterns ban (per security plan §API Security row 8 "MCP feature double-gate" + §Anti-Patterns Code Patterns ban "NEVER spawn the rmcp sidecar without verifying both ... gates").
- **Graceful-degrade `warn` preservation**: `ANDROMEDA_PULSE_MCP_ENABLED=true` against a binary built WITHOUT `--features mcp-server` MUST emit a `warn`-level log naming the missing feature flag and proceed with MCP disabled — NOT fail-startup (per security plan §API Security row 8 + §Logging & Monitoring "What to log" item 4 — this warn IS the canonical user-feedback path for a misconfigured env var).
- **MCP error envelope is JSON-RPC 2.0 only**: any error crossing the stdio boundary MUST be a standard JSON-RPC 2.0 error object — numeric `code`, string `message`, optional `data` — MCP-spec error codes honored; NO inventing new envelopes; NO leaking stack traces / file paths / library versions / internal hostnames / IPs (per security plan §Error Handling "MCP server" bullet + §Anti-Patterns Logging "NEVER expose internal hostnames or IPs in OTLP error responses or MCP error objects").
- **stderr-forced JSON discipline**: self-observation logs MUST be written to stderr (or `~/.andromeda-pulse/logs/agent-latest.jsonl` via `tracing-subscriber` JSON formatter per 2026-05-08 deprecation reconciliation); stdout is reserved exclusively for JSON-RPC 2.0 framing. NEVER mix non-JSON-RPC bytes onto stdout (per security plan §Logging & Monitoring "Log format" + the deprecation-annotated 2026-05-08 Decisions Log entry: `tracing-subscriber` JSON is the canonical primitive, NO OTel SDK linked).
- **`tonic` / `rmcp` version-pinning reconciliation gate**: Chunk #48 introduces the `rmcp` crate to the dependency graph; this triggers the Inherited Defaults open question "rmcp 1.5.0 vs published 0.3.x line" reconciliation. `cargo deny check bans` with `multiple-versions = "deny"` MUST pass against the resolved `rmcp` version (per security plan §Dependency Security "Pinning" + §Anti-Patterns § Universal "NEVER ship a release without resolving the `tonic` 0.14 vs `opentelemetry-otlp` 0.31 / `tonic` 0.13 duplicate").
- **No subprocess command-injection surface**: the rmcp sidecar binary MUST NOT spawn sub-subprocesses via `tokio::process::Command::new(...).arg(user_input)` against any string sourced from MCP tool arguments — covered prospectively for chunk #49 binding, but applies even at substrate boot if any startup-time arg parsing reads MCP-attributable input (per security plan §Anti-Patterns Code Patterns ban anchored on CVE-2025-49596 / CVE-2025-54994 / CVE-2025-54136 / CVE-2026-22252 MCP STDIO command-injection cluster).
- **MCP stdio surface is a documented attack vector**: stdio caller is whatever process the user launched the sidecar from (typically an LLM client); no network exposure; JSON-RPC framing per MCP spec. The receiver app CANNOT fully sanitize OTLP-derived attribute values flowing through `query_*`/`generate_snapshot` responses — this is an indirect-prompt-injection surface that the calling LLM client must defend against (per security plan §Threat Model Summary "Attack surface" Vector 5 MCP stdio + §Logging & Monitoring snapshot/clipboard/MCP-tool-response hygiene). ## Patterns к follow

- **Runtime env-var validation via `serde` + `TryFrom`**: `ANDROMEDA_PULSE_MCP_ENABLED` parses through smart enum + `TryFrom<&str>` for `bool` values; surface invariant errors as a structured warn-log, not panic. ## Anti-patterns к avoid

- **Single-gate enablement**: do NOT spawn the rmcp sidecar with only `--features mcp-server` (compile-time) OR only `ANDROMEDA_PULSE_MCP_ENABLED=true` (runtime) — both required; single-gate regresses the architecture-declared double-gate (per security plan §Anti-Patterns Code Patterns).
- **Mixing log bytes onto stdout**: do NOT use the default `tracing-subscriber` stdout-writer when the sidecar is running — stdout is exclusively JSON-RPC 2.0 framing; any stray `println!` / log emission to stdout corrupts the JSON-RPC stream and breaks the MCP client (per security plan §Logging & Monitoring + cross-domain ref obs plan §11 stderr discipline anchored in CLAUDE.md universal anti-pattern row 7 "NEVER log raw OTLP attribute values, ... MCP tool response bodies").
- **Hard-fail on env-var-without-feature mismatch**: do NOT fail process startup when `ANDROMEDA_PULSE_MCP_ENABLED=true` is set against a binary built without `--features mcp-server` — must `warn` and proceed with MCP disabled per arch §Occupied Resources graceful-degrade contract (per security plan §API Security row 8 explicit "MUST be preserved" clause).
- **Leaking sidecar paths or PIDs in JSON-RPC error data**: do NOT include sidecar process file path, PID, or Rust struct names in JSON-RPC 2.0 error object `data` field — applies the same sanitization discipline as `AppError::Internal` (per security plan §Anti-Patterns Logging + §Error Handling External-responses sanitization rule).
