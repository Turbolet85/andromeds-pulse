# security extract

## Relevance
Relevant — the chunk persists and reads back client-controlled OTLP attribute values into an unencrypted store, which is squarely the scrub-at-write-boundary mandate.

## Constraints
- Every persisted label VALUE is a client-controlled OTLP attribute value and MUST pass `security::scrubber::scrub_attribute` before it crosses into storage, returning `Allowed`/`Redacted` (per security-plan.md §Security Anti-Patterns → Logging, INTENDED posture). The plan's MEASURED clause enumerates exactly four live client-controlled ring-buffer columns; any new label-bearing column or table extends that enumeration, and the plan requires the enumeration to remain the complete list it claims to be. Label KEYS have no stated disposition in the plan — the chunk must produce one; the plan mandates values, so treating keys as out-of-mandate needs an explicit decision, not silence.
- Redaction at the write boundary is THE control here, not confidentiality at rest: the DuckDB ring buffer is required to stay unencrypted and enabling DuckDB at-rest encryption is banned (CVE-2025-64429) (per security-plan.md §Data Protection → At rest — per medium, DuckDB ring buffer; §Security Anti-Patterns → Data Protection).
- The OTLP attribute set arriving with each data point must be bounds-checked post-decode before it reaches `buffer::Appender` — `prost` validates wire shape only, and "attribute keys aren't 1 GB" is named explicitly (per security-plan.md §Input Validation, OTLP/gRPC `:4317` row; §Security Anti-Patterns → Input). Whether the `ingest` crate already applies attribute-count/size bounds on `p.attributes` is research's question.
- Any identity or discriminator derived from a label set MUST NOT be a stable identifier derived from unredacted secret content — the plan records this as a standing rejected alternative and keeps the current discriminator content-INDEPENDENT (per security-plan.md §Security Anti-Patterns → Logging, `metrics_points` collision clause). This directly constrains the P4 representation choice: a hash over raw attribute VALUES mints exactly the derived identifier the plan rejects; `hash_resource`'s keys-only hashing is cited by the chunk as a cautionary precedent, not a license.
- Read-back must go through `duckdb` prepared statements with `?` placeholders; no `format!` interpolation of any label key/value into SQL, and user input never names a table or column (per security-plan.md §Input Validation, DuckDB query parameters row; §Security Anti-Patterns → Input).
- Errors produced at the label write/read boundary must collapse to the `serde`-friendly `AppError` enum with a sanitized `Internal { message }` — no stack traces, Rust struct names, file paths, or raw `anyhow::Error` across the TauRPC bridge (per security-plan.md §Error Handling; §Security Anti-Patterns → Code Patterns).
- If the chunk adds any dependency (e.g. a hashing crate for the hashed-key shape), `cargo deny check bans licenses sources` gates it with `multiple-versions = "deny"` unrelaxed, and the folded `cargo audit` PREREQ rides the ratified every-3rd-wrap interval with basis + named overlap (`cargo deny check advisories`) re-verified rather than echoed (per security-plan.md §Dependency Security → CI integration, Standing deferral).

## Patterns to follow
- Choke-point vs push-site scrub: the plan records `service_name` scrubbed inside its extractor because that fn feeds three consumers, and the other three columns scrubbed at their push sites through `scrub_otlp_field` (per security-plan.md §Security Anti-Patterns → Logging). Which shape a label set needs — one scrub point per value at the builder, or a choke point if labels feed `triage` taps too — is research's question.
- Reuse the existing eight-category catalog (`JWT · bearer · api_key · secret_kv · provider_key · email · credit_card · ssn`) unchanged; the plan explicitly preserves it as untouched by the preceding two chunks (per security-plan.md §Security Anti-Patterns → Logging). A label-shaped value needs no new arm.
- Uniform redaction treatment across covered columns, with rejected alternatives stated rather than silently re-decided (per security-plan.md §Security Anti-Patterns → Logging).
- Producer-less tables cannot be scrubbed and must not be created: the plan records `instrumentation_scopes`/`resources` as producer-less and notes that attaching a scrub there "would ship an emitter that never fires" (per security-plan.md §Security Anti-Patterns → Logging). A side-table label representation must carry a real producer.
- Boundary error sanitization + bounded validation at the OTLP and TauRPC edges as already wired per security-plan.md §Bootstrap phases (`error-sanitization-wire`, `input-validation-library-install`).

## Anti-patterns to avoid
- NEVER log raw OTLP attribute values (label keys or values), and NEVER log DuckDB query parameter values — log query identifier + parameter count instead (per security-plan.md §Security Anti-Patterns → Logging; §Logging & Monitoring "What NEVER to log"). This includes debug/trace lines added while wiring carriage, and MCP `query_metrics` response bodies.
- NEVER mint a label-set identity from unscrubbed content, and NEVER interpolate a label key/value into SQL text (per security-plan.md §Security Anti-Patterns → Logging + → Input).
- NEVER treat at-rest encryption as the substitute control for the ring buffer (per security-plan.md §Security Anti-Patterns → Data Protection).

## Contract bindings
- security ↔ obs: the persisted-cells-only `redactions_applied` counting rule (obs-plan §5) is the meter for this chunk's scrub; the security mandate says WHAT must be redacted, obs owns the count's semantics. The chunk's acceptance item 2 sits on both.
- security ↔ tests: RED-before-GREEN on the real OTLP path with a synthetic credential-shaped label canary — fixtures must use synthetic, never real, credential material; the discriminating-mutation standard set by the two preceding chunks applies to the new scrub site.
- security ↔ arch: arch §Occupied Resources is named in security-plan.md §Security Anti-Patterns → Logging as "the master that owns the schema enumeration"; a new column/table lands there first, and the security enumeration follows.
- security ↔ tests (CI gate): the folded `cargo audit` PREREQ pin #8 and `cargo deny check advisories` overlap run inside the one CI security gate (per security-plan.md §Dependency Security → CI integration).
- security ↔ ui-bridge/MCP: a new `MetricRow` field regenerates bindings and widens the MCP `query_metrics` response, which security-plan.md §Logging & Monitoring classifies as a documented indirect-prompt-injection surface the receiver cannot fully sanitize — no new mandate, but the scrub-at-write boundary is what keeps that surface bounded.

## Acceptance criteria contributions
- A label value of credential shape is `Redacted` before the DuckDB write, and the corresponding cell reads back redacted — measured on the real OTLP path, not unit-only (per security-plan.md §Security Anti-Patterns → Logging).
- The canary label literal and its bare credential prefix appear 0 times across the self-observation log for the run, and no label key/value is logged at the ingest or query path (per security-plan.md §Security Anti-Patterns → Logging; §Logging & Monitoring "What NEVER to log").
- Whatever label representation P4 picks carries no stable identifier derived from unredacted client content — either content-independent, or computed only over already-scrubbed values, with the choice stated against the rejected alternative (per security-plan.md §Security Anti-Patterns → Logging).
- The data point's attribute set is bounded (count and per-key/value size) before it reaches `buffer::Appender`, and the read path binds all parameters via `?` placeholders with no interpolated identifiers (per security-plan.md §Input Validation, OTLP/gRPC + DuckDB query parameters rows).
