## Patterns to follow
- The per-column redaction pin shape in `appender::tests`: for each client-controlled column, a credential-shaped canary is stored **redacted** while a legitimate value survives **byte-identical**. §4 enumerates this across `spans.service_name` / `span_events.name` / `metrics_points.metric_name` / `log_records.severity_text`; a persisted label column extends the same shape (per test-plan.md §4 → buffer crate).
- The tally pins: `appender::tests::redaction_counter_folds_once_per_batch_across_all_four_builders` (one tally per builder, fold kept separate from `record_feed_counts`) plus the `consumer::tests` post-append pair `dispatch_folds_redactions_after_a_successful_append` / `dispatch_folds_no_redactions_when_the_append_is_rejected`, which §4 notes discriminate **only as a pair**. A fifth scrub site lands on exactly this fold (per test-plan.md §4 → buffer crate).
- The sibling identity chunk's assertion routes: schema/PK contracts asserted via `information_schema.key_column_usage` because a duplicate-INSERT probe is a documented hang on this build, and appender behavioural pins run **on a worker thread under an explicit timeout** so a hang fails rather than wedges (per test-plan.md §4 → buffer crate).
- Boundary drivers already specified for exactly this pipeline: ingest→buffer via `tonic` 0.14.5 on loopback `:4317` then DuckDB read-back; buffer→viz by seeding the in-memory DuckDB and invoking the `viz` query with an Arrow-schema assertion; viz→ui-bridge via `tauri::test::mock_builder()` + `get_ipc_response()`; MCP via JSON-RPC 2.0 `tools/call` (per test-plan.md §5 Boundary types covered; §5 Cross-module patterns covered).
- E2E readiness is polled, not slept: boot, send over the real receiver, poll `health` every 500 ms until `subsystems.buffer.rows_ingested` advances, then query back (per test-plan.md §6 Scenario P1; §3 status endpoint shape).

## Anti-patterns to avoid
- NEVER mock DuckDB at integration level (use an ephemeral in-memory instance), and NEVER assert on raw OTLP protobuf bytes — assert on decoded fields, which is the only valid form for a label-set read-back assertion (per test-plan.md §11 Integration).
- NEVER `sleep(N)` for synchronization, and NEVER pre-populate the test DB via `.sql` scripts or snapshots (per test-plan.md §11 E2E; §11 Test Data).
- NEVER expose secrets in test output — the credential-shaped label canary must not reach logs or raw-payload dumps; and NEVER pin private internals when a public module boundary exists (per test-plan.md §11 Universal; §11 Unit).
