## Relevance
Partial — arch governs crate placement, visibility discipline and gate commands for this migration; the chunk is expected to land no new external surface or Occupied-Resources entry.

## Constraints
- Migrated tests stay inside the locked `pulse-app` binary crate; the 16 workspace member names are reserved and this chunk must add none (per architecture.md §Occupied Resources → Cargo workspace crate names, which arch declares the canonical member list over any count word elsewhere). Integration-test targets under `pulse-app/tests/` are the only sanctioned home given §Cross-cutting Patterns → Module dependency direction: no library crate may depend on the binary crate, so a migrated `pulse-app` test cannot be hosted by a `crates/*` suite.
- Visibility widenings must stay minimal: architecture.md §Conventions → Module visibility discipline requires each crate expose only its public contract via `pub`, cross-crate utilities `pub(crate)`, and no `pub use` re-export across crate boundaries outside the explicit contract module. §Project Intent → Template patterns restates the shape (contract module the only `pub` surface, `pub(crate)` internals). Whether `pulse-app/src/lib.rs` already declares the 14 modules reachable from an integration-test target — and what the minimum widening per migrated test actually is — is research's question.
- No new dependency and no new feature gate may ride this chunk: architecture.md §Stack and Technologies pins the toolchain rows and §Cross-cutting Patterns → Feature-gate hygiene requires flags be off by default with flag-specific deps entering the graph only when enabled. A test-only feature to make dead tests reachable would violate both and the scope's own ban on flipping `[lib] test = false`.
- Six of the 14 files are IPC-adjacent (`diagnostics_router.rs`, `plugins_router.rs`, `storage_router.rs`, `mcp_router.rs`, `connection_router.rs`, `streams.rs`). architecture.md §Cross-cutting Patterns → Webview IPC capability policy requires that adding/removing a TauRPC procedure be reflected in the owning router, §Occupied Resources, and the `EXPECTED_PROCEDURES` pin — and that pin is now diffed against BOTH the worktree and the git-INDEX bindings. Relocating tests must leave the procedure roster and the registered leaf/target set byte-unchanged, so `capability-drift` (which folds `check:staged-artifacts` into its exit) stays green.
- Migrated tests may consume only env vars already registered in architecture.md §Occupied Resources → Environment variables (`ANDROMEDA_PULSE_DATA_DIR`, the harness-only `_PIDFILE`/`_LOGFILE`/`_DATA_DIR_KEEP` class, etc.). A new variable is a registry item requiring an amendment, per the same section's precedent that unregistered harness names are drift.
- Any dev/CI verb this chunk formalizes would become an arch registry item under §Occupied Resources → xtask CLI surfaces (dev/CI gates) with an exit-code + verdict contract; keeping the ratchet as an in-test constant in `pulse-app/tests/unit_observability_allowlist_sweep.rs` avoids that obligation. §Infrastructure Patterns → CI/CD approach also requires shared Rust CI logic live in the `xtask` crate, not in ad-hoc scripts.
- Any binary path a migrated test names must be the dev-build form `target/{profile}/pulse-app[.exe]`, not the bundled `andromeda-pulse` name — architecture.md §Occupied Resources → Process / service identity records that `target/{profile}/andromeda-pulse` exists on no host.

## Patterns to follow
- `pulse-app` is the sole root of the dependency DAG (§Cross-cutting Patterns → Module dependency direction), which bounds the blast radius of every widening this chunk makes: a `#[doc(hidden)] pub` symbol in `pulse-app` is reachable only by `pulse-app`'s own targets, never by a sibling crate.
- File and symbol naming per §Conventions → File naming and → Variable / function naming: Rust files `snake_case.rs`, types `UpperCamelCase`, constants `SCREAMING_SNAKE_CASE` (`LEGACY_DEAD_BASELINE` conforms) — the new `pulse-app/tests/*.rs` target files follow the same shape as the existing suites.
- The gate commands are fixed by §Infrastructure Patterns → Build system: `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo check --workspace --all-targets`, then `cargo xtask test` per §CI/CD approach. `--all-targets` pulls the new integration-test targets into lint scope, so relocated code is linted at deny-warnings where the lib-internal blocks may not have been.
- §Cross-cutting Patterns → Development Style (agent-driven) favours deterministic, machine-parseable, by-name collection over total-count arithmetic — the same discipline the scope's "reconciled ADDED-BY-NAME" outcome states.

## Anti-patterns to avoid
- No test-mode back-door to make a relocated test reachable: architecture.md §Cross-cutting Patterns → Test-time telemetry injection bans an in-process test bypass, a separate "test ingest" feature flag, and mock-channel back-doors — the same class as a `#[cfg(feature = "…")]` shim added purely to expose internals.
- No reverse crate edge: hosting a migrated `pulse-app` test in a library crate would make a `crates/*` member depend on the binary crate, which §Cross-cutting Patterns → Module dependency direction forbids outright.
- No blanket `pub` on module internals and no new cross-crate `pub use` re-export outside a contract module (§Conventions → Module visibility discipline) — widening is per-symbol and per-test-need, not per-module.

## Contract bindings
- arch ↔ tests: arch owns the placement (`pulse-app` crate, `pulse-app/tests/` integration targets) and the gate command set (§Infrastructure Patterns → Build system / CI/CD approach); the tests plan owns collection-by-name discipline, the ratchet baseline and the per-file MIGRATE/DELETE fork.
- arch ↔ obs: the ratchet file is the observability allowlist sweep target, and architecture.md §Occupied Resources → Tauri IPC routes records each telemetry procedure's exact obs target + allowlist leaf (e.g. `ui.ipc.rejection` `{error_category, window_label, payload_bytes}`). A relocated obs assertion must pin the same registered leaf; arch's registry is the naming authority, obs owns the leaf semantics.
- arch ↔ security: architecture.md §Cross-cutting Patterns → Webview IPC capability policy states capability grants are IPC-layer, not per-procedure, and the `EXPECTED_PROCEDURES` pin plus `check:staged-artifacts`' `EXPECTED_GRANTS` triple are the enforcement points this chunk must leave undisturbed.

## Acceptance criteria contributions
- (arch) Every migrated test lands under `pulse-app/tests/` inside the `pulse-app` crate; no workspace member is added and no `crates/* → pulse-app` dependency edge is created (per architecture.md §Occupied Resources → Cargo workspace crate names + §Cross-cutting Patterns → Module dependency direction).
- (arch) Visibility changes are per-symbol widenings only; no module-wide `pub`, no new cross-crate `pub use` outside a contract module (per architecture.md §Conventions → Module visibility discipline).
- (arch) `cargo clippy --workspace --all-targets --all-features -- -D warnings` and `cargo check --workspace --all-targets` stay green with the new integration-test targets in scope (per architecture.md §Infrastructure Patterns → Build system).
- (arch) Occupied Resources is unchanged by this chunk — no new env var, TauRPC procedure, capability file, feature flag, xtask CLI verb or dependency — and `cargo xtask capability-drift` (which folds `check:staged-artifacts` into its exit) stays exit 0 (per architecture.md §Occupied Resources + §Cross-cutting Patterns → Webview IPC capability policy / Feature-gate hygiene).
