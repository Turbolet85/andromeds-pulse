## Anti-patterns to avoid

- **NEVER instrument the Drain assignment inner loop at `info` level or with per-event span creation**: creating a new `tracing::Span` per log event in the appender hot path incurs allocation overhead that would consume the entire 48μs latency headroom. Use `tracing::trace!` for the metric event (level-gated, near-zero cost when disabled) + a single `drain.assign` child span per `duckdb.append` batch call covering the entire assignment pass, not one span per log record. (per obs-plan §11 "NEVER over-instrument hot paths (appender inner loop, per-row DuckDB operations) — span overhead matters")

- **NEVER log template content (even PII-scrubbed) as a structured log field**: the `tracing-subscriber` Layer's default-deny posture means unlisted fields are redacted. Even after the PII scrubber runs, template token strings are derived from user log messages and may carry quasi-identifiers (hostnames, paths, service names). The obs allowlist for `buffer` covers metrics, not content. (per obs-plan §8 "NEVER include PII in logs / spans / metrics by default (default-deny posture)")

- **NEVER pre-aggregate the `drain_assignment_latency_p99_microseconds` metric before emission**: the `jq`-over-jsonl agent-side aggregation convention requires raw per-event `value` fields. Pre-computing p99 in Rust and emitting only the aggregate breaks the "agent computes percentiles from event stream" convention and makes the SLO assertion non-reproducible from CI logs. (per obs-plan §5 "NEVER skip p50/p95/p99 coverage on perf-budget metrics — emit raw per-event value field")
