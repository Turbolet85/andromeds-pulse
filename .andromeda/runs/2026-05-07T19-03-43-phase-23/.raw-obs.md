## Constraints

- `AppError::Internal { message }` carried across the bridge MUST be a sanitized one-liner — strip Rust struct names, library versions, kernel/stdlib file paths, and source() chains; the full chain stays in the local `tracing-error` SpanTrace via the user-defined-span path only (per obs-plan §7 Error Capture & Reporting / §8 PII row "AppError enum variants").
- Every `From<{Module}Error> for AppError` impl MUST emit a `tracing::warn!` or `tracing::error!` at the conversion boundary BEFORE returning the lossy variant — the conversion site is the only place where the rich source-chain still exists; once the `AppError` is returned the structured chain is gone (per obs-plan §10 "Module-boundary error logging — every error at module boundary logged at WARN or ERROR with trace context + error category, not full stack trace per vector 2").
- The `From` impl MUST NOT serialize raw upstream error fields verbatim into the `message` string — fields like full plugin paths (Vector 3 basename-only), DuckDB query parameters (Vector 5 query_id+param_count only), MCP response bodies (Vector 4 result_type+result_count only), and raw OTLP attribute values (Vector 1) collapse to category strings before crossing the `AppError` boundary (per obs-plan §5 logging-sensitive triggers Vector 1-6).
- Errors emitted within an active `tracing` span automatically inherit `trace_id` / `span_id` from the surrounding `#[tracing::instrument]` context — `From` impls MUST emit via `tracing::error!`/`warn!` macros (which auto-attach span context) NOT via raw `eprintln!` or unspanned writers (per obs-plan §7 "Error → span correlation").
- The whitelist for `ui-bridge` module fields per the default-deny posture is `method_name`, `argument_digest` (hash, not content), `result_type`, `latency_ms` — `AppError` boundary logs MUST stay within this allowlist; never include user-controlled argument content, raw error chain text, or library version strings (per obs-plan §8 "Default-deny posture — whitelist per module — ui-bridge").
- `AppError::Validation { field, reason }` `field` MUST be a stable enum-like identifier (`"port"`, `"retention_seconds"`, `"plugin_id"`), NEVER include the rejected user value — value contents may carry secrets per Vector 1 (the boundary log emits `field` + a category-tagged `reason`, the offending value goes only to internal SpanTrace) (per obs-plan §8 Vector 1 + Vector 2 row).

## Patterns to follow

- Module-boundary error pattern: each `From<{Module}Error> for AppError` impl wraps `tracing::warn!(target: "ui-bridge.error.from_{module}", error_category = "validation"|"not_found"|"internal"|"plugin"|"storage"|"ingest", source_kind = ?<thiserror variant discriminant>, "..." )` then returns the sanitized variant — mirrors the existing `From<IngestError>` / `From<BufferError>` / `From<VizError>` impls already in `crates/ui-bridge/src/contract.rs` and `crates/ui-bridge/src/viz_routers.rs` referenced in session-handoff (per obs-plan §3 Tracing init + §10 Module-boundary error logging).
- Sanitized chain capture pattern: where call sites need the rich chain for local debugging, surrounding `#[tracing::instrument]` uses `tracing-error::ErrorLayer` so `SpanTrace::capture()` records user-defined-span breadcrumbs only — NEVER `std::backtrace::Backtrace` (which carries struct names + file paths). The boundary-side `tracing::error!` event embeds `spantrace = ?SpanTrace::capture()` as a structured field; never as a stringified `Debug` of `anyhow::Error` (per obs-plan §3 Tracing init crate set + §7 Panic hook snippet).
- Per-variant `tracing` target convention: emit conversion logs at `target: "ui-bridge.error.{variant}"` (e.g., `"ui-bridge.error.validation"`, `"ui-bridge.error.plugin"`) so `jq` filtering by target groups by error class for SLO regression detection — agent computes error-rate-by-category from the JSON file (per obs-plan §2 Naming conventions span/target prefix `{module}.{operation}`).
- Default subscriber fields propagate identity automatically: every emitted `tracing::error!` JSON line already carries `service.name` / `service.version` / `deployment.environment` from the `Layer::with_default_fields(...)` registered at boot — `From` impls do NOT need to re-emit these (per obs-plan §3 Service identity / §2 Default subscriber fields).

## Anti-patterns to avoid

- NEVER `serialize anyhow::Error` directly across the IPC boundary — `From<anyhow::Error> for AppError` (if introduced) MUST collapse to `AppError::Internal { message: "<sanitized one-liner>" }`, never `Internal { message: format!("{:?}", e) }` (which dumps full chain with struct names + file paths). Anti-pattern listed verbatim per obs-plan §11 Spans/Traces.
- NEVER include `e.to_string()` of an upstream `thiserror`-derived enum directly in `AppError::Internal { message }` if that enum's `Display` impl interpolates user-controlled fields — review each upstream `#[error("…{field}…")]` macro before deciding whether `{e}` is safe; default to category-string mapping (per obs-plan §11 Logs Vector 1-5 row "NEVER log raw OTLP attribute values, stack traces with struct names, full paths, MCP response content, or query parameters").
- NEVER emit conversion telemetry below `WARN` level — module-boundary errors are SLO signals (zero unlogged panic invariant + module-boundary error logging Standard+ requirement); `info` or below dilutes the error stream and breaks `jq` aggregation (per obs-plan §11 Logs "NEVER log in hot path at info level" inverse + §10 Standard+ invariants).
