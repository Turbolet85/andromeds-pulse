## Constraints

- The TauRPC bridge MUST emit only the six stable `AppError` variants (`Validation { field, reason }` / `NotFound { resource }` / `Internal { message }` / `Plugin { plugin_id, message }` / `Storage { message }` / `Ingest { message }`); module-internal `thiserror` 2.x enums convert via `From` impls AT the bridge boundary, not at the call site (per security plan §Error Handling TauRPC bridge bullet + Conventions Error response schema (Tauri IPC)).
- `AppError::Internal { message }` MUST carry a sanitized one-liner — no stack traces, no file paths (absolute or relative), no Rust struct names, no library/crate version strings, no internal hostnames or IPs (per security plan §Error Handling External-responses preamble + §Anti-Patterns Logging line "NEVER expose stack traces, Rust struct names, file paths, or library versions in `AppError::Internal { message }`").
- The full pre-sanitization error chain MUST stay accessible inside `tracing-error` SpanTrace / internal log via the structured logger — sanitization only applies to the surface that crosses the bridge, not to the `tracing` event emitted internally (per security plan §Error Handling Internal-logging bullet + project rules `security.md` §Error sanitization "Full chain stays in internal log via `tracing-error` SpanTrace").
- The DuckDB query parameter values MUST NOT appear in any `AppError::Storage { message }` string — error mappers from `viz`/`buffer` errors include only `query_id` + `param_count` (or equivalent placeholder), never echoed user-controlled telemetry data (per security plan §Logging "NEVER log DuckDB query parameter values" + project rules `security.md` §Logging "use `query_id` + `param_count` + `param_types` instead").
- Plugin path strings MUST NOT appear verbatim in `AppError::Plugin { plugin_id, message }` — only the canonicalized basename or a stable plugin identifier is acceptable (per security plan §Logging "NEVER log full plugin file paths" + §Anti-Patterns Logging line 409).
- OTLP attribute values, snapshot file contents, clipboard contents, and MCP tool response bodies MUST NEVER appear in any `AppError` variant payload — these are user-content with potential incidentally captured secrets (per security plan §Logging NEVER-log list + project CLAUDE.md "Critical Warnings" universal invariant).
- OTLP-receiver and MCP error surfaces are OUT of scope for `AppError` — OTLP errors collapse to `tonic::Status` codes / OTLP `Status` proto in body, MCP errors use JSON-RPC 2.0 error objects; no `AppError` variant crosses those boundaries (per security plan §Error Handling sub-bullets for OTLP receiver + MCP server).

## Patterns to follow

- Boundary conversion via `From<ModuleError> for AppError` impls — already established for `From<IngestError>` / `From<BufferError>` / `From<VizError>` per session-handoff notes; this chunk extends the matrix to whichever sibling crates need it (or stubs the From impls when downstream crates' error enums haven't shipped yet) (per security plan §Error Handling TauRPC bridge bullet + project rules `security.md` §Error sanitization).
- Sanitization happens AT the `From` impl, not at the procedure handler — extract message-shape transformation into the `From<thiserror::Error>` body so every code path that returns the underlying error gets sanitized identically (per security plan §Anti-Patterns Logging line 411 "sanitize at the `From<thiserror::Error> for AppError` impl").
- `AppError::Validation { field, reason }` is the canonical rejection variant for `serde` deserialize failures + `TryFrom<u16>` failures + smart-enum out-of-range failures on TauRPC procedure args (per security plan §Input Validation TauRPC bridge row "Convention-mandated `AppError::Validation { field, reason }` enum variant returned on rejection").
- Module-internal code keeps using `thiserror` 2.x enums (no boundary leakage); `anyhow::Result` is permitted only inside `main.rs` and non-IPC top-level (per security plan §Anti-Patterns Code-Patterns line 419 + project CLAUDE.md "Critical Warnings" boundary rule).

## Anti-patterns to avoid

- NEVER serialize `anyhow::Error` directly across the TauRPC bridge — must convert to `AppError` first via the appropriate variant; direct serialization either fails to compile or, if hand-implemented, leaks the full error chain to the webview (per security plan §Anti-Patterns Code-Patterns line 419).
- NEVER include stack traces, Rust struct names, file paths, library versions, or internal hostnames/IPs in any string field of any `AppError` variant — sanitize at the `From` impl, not in a downstream layer (per security plan §Anti-Patterns Logging lines 411-412).
- NEVER let `Debug` formatting (`{:?}`) of an underlying error leak into `AppError::Internal { message }` — `Debug` typically renders module paths, struct names, source-code spans; use `Display` (`{}`) and pre-vet the upstream `thiserror` `#[error(...)]` strings for the same disclosure classes (per security plan §Error Handling External-responses preamble + §Anti-Patterns Logging line 411).
