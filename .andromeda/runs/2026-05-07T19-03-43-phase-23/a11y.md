## Constraints

- AppError variant message strings (`reason`, `message`) MUST be authored in plain language with simple terminology — no technical jargon, no Rust struct names, no library version strings, no file paths (per a11y-plan §11 Forms & Validation phase-1 baseline disciplines: "Plain language commitment: settings form labels, help text, error messages use simple terminology"; reinforced by WCAG SC 3.3.3 Error Suggestion baseline). This aligns with the security-domain sanitization mandate but adds a separate a11y-readability gate on the surviving sanitized one-liner.
- `AppError::Validation { field, reason }` MUST shape `field` as a stable machine identifier (downstream UI binds it to `aria-describedby` on the offending input per a11y-plan §10 Forms & Validation `aria-label`/`aria-describedby`/`aria-invalid="true"` pattern + SC 3.3.1 Error Identification, SC 3.3.2 Labels or Instructions). A single bag-of-text `reason` field that conflates field name and error message breaks the SC 3.3.1 error-identification pattern downstream.
- The serialized AppError JSON shape MUST be discriminated-union compatible with TypeScript bindings (chunk #25 emitted `AppError` as 6-variant union in `pulse-app/ui/src/bindings/index.ts`) so downstream UI can pattern-match per variant and render context-appropriate aria-live region polarity (SC 4.1.3 Status Messages: `aria-live="polite"` for non-blocking, `role="alert"` / `aria-live="assertive"` for blocking — per a11y-plan §11 Status Messages region-type table). A stringly-typed error blob would force all variants to a single live-region polarity.
- AppError sanitization MUST NOT strip the `field` identifier from `Validation` or the `plugin_id` from `Plugin` — those structured handles are how downstream UI wires aria-describedby + aria-labelledby relationships per a11y-plan §10. Sanitization scope is strictly: stack traces, library versions, file paths, Rust struct names per a11y-plan-aligned security guidance.

## Patterns to follow

- Six-variant stable discriminated-union shape preserved per chunk #25 emitted bindings (`Validation` / `NotFound` / `Internal` / `Plugin` / `Storage` / `Ingest`) — downstream UI consumers (toast, banner, modal) can switch on `AppError.type` and choose ARIA live-region polarity per a11y-plan §11 region-type table without prop-drilling severity from the backend.
- Plain-language `reason` / `message` author convention matching a11y-plan §11 phase-1 baseline ("Save" / "Cancel" / "Invalid field" register, not stack-trace register). Existing `AppError` strings in `crates/ui-bridge/src/contract.rs` are the calibration baseline; new From-impl conversions must preserve this register.

## Anti-patterns to avoid

- Do not author `AppError::Internal { message }` strings that contain Rust panic boilerplate (`thread 'main' panicked at`, `RUST_BACKTRACE=1`, `core::result::Result`) — those leak to a UI surface that screen-readers will then read aloud verbatim, violating SC 3.3.3 Error Suggestion's plain-language baseline (per a11y-plan §11 phase-1 disciplines + Section 11 Anti-patterns spirit). The security-domain mandate "strip stack traces, file paths, library versions, Rust struct names" exists for the same reason on the a11y side.
- Do not collapse `Validation { field, reason }` into a single concatenated `String` — destroys the SC 3.3.1 / SC 3.3.2 binding handle that downstream UI needs for `aria-describedby` association on the offending form input (per a11y-plan §10 Forms & Validation pattern table + Section 11 Form Validation aria-describedby/aria-invalid contract).
