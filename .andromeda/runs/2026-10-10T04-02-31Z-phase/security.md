## Patterns to follow
- An unevaluable harness input reads `cannot-evaluate` (never green, never a silent default), and a verdict document's member set is pinned by a test (per security-plan §Input Validation, the CLI / env var inputs row, harness-only readers).
- Harness-written files carry closed labels, pids and counts only; third-party text files (`xvfb.log`, the witness file) pass no scrubber, so their safety is the bounded shape plus the read-whole stop, not redaction (per security-plan §Security Anti-Patterns → Input, the 2026-10-09 class and the exit-witness arm).
- The witness variables ride the one spawn command only, never exported; the library path is trim + regular-file checked and FAILS CLOSED when set and unusable; the CI step that builds the library carries no `LD_PRELOAD`. Any edit to `scripts/agent-run.sh boot` or the boot step keeps these three (per security-plan §Security Anti-Patterns → Input, the exit-witness arm items (a) and (b)).
- A CI gate step is a plain `run:` step with no `continue-on-error` and no `||` tail, its shape pinned in `pulse-app/tests/quality_gate_workflow.rs` (per security-plan §Dependency Security → CI integration).
- A new harness reading is recorded with who classed it, the date and whether it is the founder's word; code inside the app's process is recorded PROVISIONAL (per security-plan §Security Anti-Patterns → Input).

## Anti-patterns to avoid
- Growing the instrument to find the cause: a new witness member, a new interposed call, a kept copy of the app's stderr or GLib messages as a new file, or more frames or names read from inside the process. Each widens a PROVISIONAL boundary without the founder's word (per security-plan §Security Anti-Patterns → Input, the exit-witness arm).
- Making the product record the ending call from a handler on the thread that is ending the process (an X I/O error hook, an `atexit` or signal handler that logs or touches thread-locals); the plan bans it, and states `_exit` among the ends the `app.exit` record cannot see by construction, so its absence on a witness-named `_exit` boot is the stated failure mode, not a defect to patch in the product (per security-plan §Security Anti-Patterns → Universal; §Security Anti-Patterns → Logging, the `app.exit` boundary).
- Printing or writing a value of `DISPLAY`, `XDG_RUNTIME_DIR`, `PATH`, `HOME` or any full path while diagnosing the X connection; the harness reads them by presence or by value for its own use and lets out closed labels only (per security-plan §Security Anti-Patterns → Input, the 2026-10-09 class).
