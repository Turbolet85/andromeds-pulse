A change to the boot job's steps in that file must leave the `a11y` job's steps, order and artifacts as that section states them.
- a11y-plan §3 CI integration (key file, labels Pipeline integration · CI gate) requires the `a11y` job to be blocking and to run parallel with the test jobs. Where the close lands in the workflow, it must not make the `a11y` job depend on, wait for or be skipped by the boot job.
- a11y-plan §3 Focus management test harness → Contract binding requires the a11y harness to reuse the tests' E2E driver under the 5-command discipline (`boot`, `run`, `status`, `cleanup`, `logs`). A change to `scripts/agent-run.sh boot` (how the display server and the app are started) must keep that verb's contract for an a11y caller. Whether the `a11y` job's commands actually pass through the `boot` verb, or serve the built webview without it, is research's question.
- a11y-plan §10 SLO Invariants & A11y Budgets → Always-required SLO invariant requires zero WCAG AA violations on must-be-accessible paths with no retry-once policy. The chunk's own ban on a retry, a soft-fail key and a filter (scope §Boundaries) must hold for the `a11y` job as well as the boot job if the workflow is edited.
- a11y-plan §10 SLO Invariants & A11y Budgets → Standard+ invariants requires zero new violations per PR against the base branch. A product change in the app's start (window creation, window hints, the display connection) is inside that diff; whether the close touches any rendered surface is P4's to decide from what research names.

The measured ending call sits under a window-manager hint query (scope §What the entry measured); if the close changes a window's hints, visibility or creation order, the P5 contract is the one at risk. - a11y-plan §5 Keyboard Navigation → Focus restoration (Cross-window) requires focus to restore across the separate `findings` / `report` windows through first-party events. A close that alters when or how the app's windows are created must leave that restoration intact; it applies only if the change lands in the app's own start.

## Patterns to follow
- The a11y gate reads by its own artifacts, never by another job's colour: per a11y-plan §9 CI Integration → Per-pipeline-stage a11y artifacts, the `a11y` job's verdict is its uploaded violation files. A red in the boot job is read by the boot job's per-boot verdicts (scope §The CI verdict Setup read) and neither verdict stands in for the other.
- Per-PR regression detection by tuple diff against the base-branch summary, per a11y-plan §3 CI integration → Per-PR regression detection. A chunk that changes no rendered surface expects an empty regression set; a non-empty one is surfaced, not explained away as runner variance.
- Shared harness, unchanged contract: per a11y-plan §9 CI Integration → Pipeline integration, a11y reuses the tests' `boot` / `run` / `status` / `cleanup` / `logs` harness, so a harness edit is made once at the verb and its callers are checked, never forked per job.
- No improvement for a surface on its way out: a11y-plan §1 A11y Scope Summary keeps the desktop-webview and tray surfaces assertable while they exist, and the chunk's scope edge (scope §Boundaries) bars improving them. The a11y contribution here is no-regression only.

## Anti-patterns to avoid
- NEVER a retry-once policy on an a11y check, per a11y-plan §11 A11y Anti-Patterns → SLO. A flake in the `a11y` job seen while this chunk's runs are read is surfaced as its own finding, never retried into green.
- NEVER a soft a11y gate or an a11y step skipped on another failure, per a11y-plan §11 A11y Anti-Patterns → CI. No `continue-on-error`, no conditional skip and no deferral to post-merge enters the `a11y` job through a workflow edit made for the boot job.
- NEVER a conformance claim without machine-verifiable evidence, per a11y-plan §11 A11y Anti-Patterns → Universal (agent-driven specific). "The change is harness-only, so a11y is unaffected" is stated from the `a11y` job's artifacts on the chunk's run, not from the diff's shape.

## Contract bindings
- a11y ↔ tests (CI): the `a11y` job and the boot job share one `ci.yml` (a11y-plan §9 CI Integration → Pipeline integration ↔ test-plan §9 Boot smoke). An edit to the boot job is an edit to the file the a11y gate lives in; the workflow pins in `pulse-app/tests/quality_gate_workflow.rs` are the tests-side holder of that shape.
- a11y ↔ tests (harness): the 5-command harness is one contract with two consumers (a11y-plan §3 Focus management test harness → Contract binding ↔ test-plan §3 `boot` key). A change to the `boot` verb binds both.
- a11y ↔ layouts (focus), conditional: if the close lands in the app's own start, a11y-plan §5 Keyboard Navigation → Focus restoration binds to layout-templates' focus management anchors for the compact widget and the separate windows.
- a11y ↔ obs (violation JSON): not touched. The chunk emits no a11y violation record and changes no field of the schema at a11y-plan §3 Structured violation JSON schema.
