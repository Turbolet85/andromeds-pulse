# arch extract

## Relevance
relevant — the chunk works on three surfaces architecture.md registers by contract (the `harness:boot-series` and `harness:settled` xtask verbs, the `agent-run.sh boot` verb, the `boot` job of `ci.yml`) and on the harness-written files and harness-only variables its §Occupied Resources enumerates; where the close itself lands is not known at take-up, so which of these rows is amended at wrap is open.

## Constraints
- **Workspace placement.** The counting repair lives in the `xtask` crate (the plan names `xtask/src/harness_series.rs` as the verb's home, with `xtask/src/harness_witness.rs` and `xtask/src/harness_ready.rs` beside it); the sixteen workspace member names are reserved and no new crate is licensed (per architecture.md §Occupied Resources → Cargo workspace crate names). CI logic that needs Rust belongs in `xtask` so the local command equals the CI one (per architecture.md §Infrastructure Patterns → CI/CD approach; §Established Decisions [CI Task Runner]).
- **The series verdict is a registered contract.** architecture.md §Occupied Resources → xtask CLI surfaces (the `cargo xtask harness:boot-series --count N` row) requires: one pretty-JSON verdict on stdout with a twin at `logs/boot-series.json`; top-level members `{verdict, boots, settled, ended, other, per_boot}`; per-boot members `{ordinal, cycle, verdict, ended, app_exit_record, windows_settled, exit_witness}`; every value a label of at most 48 printable-ASCII bytes or a count, no value of an environment variable and no path; exit 0 `all-settled` · 1 `self-ended` · 1 `not-all-settled` · 2 `cannot-evaluate`; `cycle` a closed label set; ordinal 1 (`smoke`) listed and kept out of the counts. The same row records, as a measured limit, that a boot ending before the boot verb reads ready takes no settle verdict and is counted `other` with a null `exit_witness`. The repair changes that recorded behaviour, so the row is amended at wrap; whether the repair fits inside the present members and label sets, or needs a new member, a new `cycle` label or a new verdict arm, is research's and design's question, and any of the three is a contract change to that row.
- **The witness is read through the bounded reader, and only a label leaves it.** architecture.md §Occupied Resources → xtask CLI surfaces (the `cargo xtask harness:settled` row) requires `exit_witness` to be one closed label of six (`unset` · `unreadable` · `loaded` · `exit-call` · `runtime-exit` · `no-record`), read from `logs/exit-witness.jsonl` for the app's pid by a reader bounded at 64 lines of at most 4096 printable-ASCII bytes, anything else reading `unreadable` and never a partial record. A series path that labels a boot with no settle verdict needs a pid to read the witness for; where that pid comes from when `harness:settled` did not run is research's question (the same row states nothing of a boot's `run/` is copied, and `harness:settled`'s verdict set, exit codes and eight members are stated unchanged).
- **The kept-file set is enumerated.** architecture.md §Occupied Resources → Filesystem locations names every harness-written file under the data dir's `logs/` (`harness-settled.json`, `xvfb.log`, `exit-witness.jsonl` with its three line kinds and 4096-byte line bound, `boot-series.json`, `logs/series/boot-{ordinal}/` copies) and the per-boot data dirs `series/boot-{ordinal}/`, plus the out-of-data-dir witness source and build output. A new kept file, a new line kind or a new copied member is a new entry there; the same section holds the product-written out-of-data-dir locations at THREE, which a harness change must leave unchanged.
- **The variable set is reserved.** architecture.md §Occupied Resources → Environment variables registers `ANDROMEDA_PULSE_EXIT_WITNESS_LIB` (read solely by `agent-run.sh boot`, value never printed), `ANDROMEDA_PULSE_EXIT_WITNESS_FILE` and `LD_PRELOAD` (set on the app's spawn line alone, never exported, removed by the library at load), `XDG_DATA_HOME` / `XDG_CACHE_HOME` (set by the series on each boot), the presence-only read of `DISPLAY` / `DBUS_SESSION_BUS_ADDRESS` / `XDG_RUNTIME_DIR`, and requires that no `pulse-app` or `crates` code reads the witness variables. Any variable the close reads or sets (in the harness, the workflow or the app's start) is a new row there. The same section records `__NV_DISABLE_EXPLICIT_SYNC=1` as the product's ONE sanctioned launch-posture environment default.
- **The boot job's shape is pinned.** architecture.md §Infrastructure Patterns → CI/CD approach requires the `boot` job's order (mcp-feature release build → `Build the exit witness` → the boot smoke, its lines unchanged → `Boot series (equal source)` as a plain `run: cargo xtask harness:boot-series --count 7` under `if: always()` with no soft-fail key → `cargo xtask ci-gates`), eight boots per run, a boot whose settle verdict reads `ended` failing the job, and the upload still running; six independent jobs on `ubuntu-22.04` with no matrix and no `needs:` edge. A close that lands in the workflow moves these lines and the workflow tests that pin them. The same key defines equal source on a `pull_request` run as the branch tip AND `main`'s tip both unchanged, since such a run builds the merge ref.
- **The boot verb is a formalized CLI contract.** architecture.md §Occupied Resources → xtask CLI surfaces (the `scripts/agent-run.{sh,ps1}` row) requires five unchanged verbs, sh and ps1 in lockstep but for the sh-only exit-witness arm, the app spawned by path under a waiting subshell with its stdout and stderr going to `logs/boot.log`, the readiness poll through `cargo xtask harness:ready`, and the smoke step's four invocations inside one `xvfb-run -e`. A close that lands in how the display server or the app is started changes this row; a sh-only change widens the stated lockstep exception and is recorded as such.
- **Ports stay loopback and resolved.** architecture.md §Occupied Resources → Network ports reserves `:4317` / `:4318` on `127.0.0.1` only; the `harness:boot-series` row (§Occupied Resources → xtask CLI surfaces) requires that the verb binds no port itself and adds no TauRPC procedure, IPC route or capability. The chunk adds none of these.

## Patterns to follow
- **Formalized CLI contract for an xtask verb**: exit 0 pass · 1 red · 2 `cannot-evaluate` (never a pass), one pretty-JSON verdict on stdout with a file twin, closed label sets, no environment value and no path in the verdict (per architecture.md §Occupied Resources → xtask CLI surfaces; machine-parseable, schema-stable outputs per §Cross-cutting Patterns → Development Style).
- **Reuse the harness modules in-process**: `harness:ready` and `harness:settled` reuse `harness_status`'s `classify` and its `pub(crate)` path, liveness and exit-record helpers instead of re-deriving them (per architecture.md §Occupied Resources → xtask CLI surfaces, the `harness:status` and `harness:ready` rows); a series-side witness read follows the same route through `harness_witness`. Whether those helpers are reachable from `harness_series.rs` as they stand is research's question.
- **A workflow step is held by a self-lint test**: each `boot`-job step is pinned by its own test in `pulse-app/tests/quality_gate_workflow.rs` (per architecture.md §Infrastructure Patterns → CI/CD approach); a moved or added step moves or adds its pin in the same change.
- **A harness-only variable is set on the one spawn line, never exported**, so the pre-build and every other verb run without it (per architecture.md §Occupied Resources → Environment variables, the `LD_PRELOAD` and `ANDROMEDA_PULSE_EXIT_WITNESS_FILE` rows).
- **A reading written into the contract names its run and its limits**: the plan records CI readings with the run id, the attempt, the merge commit built and what was not read (per architecture.md §Infrastructure Patterns → CI/CD approach); the wrap's amendment of the `boot` reading and of the series row's measured limit follows that form.

## Anti-patterns to avoid
- **No soft-fail on the boot steps.** The series step carries no soft-fail key and the smoke step is gating since `continue-on-error: true` was dropped (per architecture.md §Infrastructure Patterns → CI/CD approach; §Occupied Resources → xtask CLI surfaces, the `scripts/agent-run.{sh,ps1}` row). A retry loop or a key that lets a self-end read as anything but red contradicts both.
- **No second launch-posture default in the product.** The one sanctioned product launch-posture environment default licenses no other flag in product code or `tauri.conf.json` (per architecture.md §Occupied Resources → Environment variables, the `__NV_DISABLE_EXPLICIT_SYNC` and `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` rows). If research names the cause in the app's own start, a new product-side environment default or display flag is a boundary widening, not an in-plan edit.
- **No product read of a harness variable or harness file.** The witness variables and the harness-written files under `logs/` are read by no `pulse-app` or `crates` code (per architecture.md §Occupied Resources → Environment variables; §Occupied Resources → Filesystem locations).

## Contract bindings
- **arch ↔ security**: the one place harness code runs inside the app's process has its classification owned by security-plan §Security Anti-Patterns → Input (per architecture.md §Occupied Resources → Environment variables, the `LD_PRELOAD` row). A change to the witness line shape, the kept-file set or what is read from inside the app's process is security's boundary before it is an arch row.
- **arch ↔ tests**: the `boot` job's steps are pinned by workflow tests in `pulse-app/tests/quality_gate_workflow.rs` (three for the witness build and the series, four for the smoke step) (per architecture.md §Infrastructure Patterns → CI/CD approach; §Occupied Resources → xtask CLI surfaces). The stack row for the exit witness requires seven Linux-only controls on the built library that FAIL on a missing `cc` (per architecture.md §Stack and Technologies, the Boot-smoke exit witness row).
- **arch ↔ obs**: `harness:settled` takes its verdict from the product's own log family, the `app.boot.window.navigation` records for the four window labels and the `app.exit` record (per architecture.md §Occupied Resources → xtask CLI surfaces, the `harness:settled` row); the app's stdout and stderr land in `logs/boot.log` (the `scripts/agent-run.{sh,ps1}` row). Research question (d), where the app's GLib messages go, is read against that routing.
- **arch ↔ tests (equal source)**: the definition of equal source across pull-request runs is the CI/CD key's (per architecture.md §Infrastructure Patterns → CI/CD approach); the count of consecutive runs the close is read on is not an arch figure.
