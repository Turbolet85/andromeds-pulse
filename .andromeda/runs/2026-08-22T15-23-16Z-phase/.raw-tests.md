## Constraints
- **Standard tier breadth applies (per test-plan.md §1 Test Scope Summary + §2 Test Strategy pyramid).** The pyramid mandates Unit *comprehensive* AND Integration *required* for "cross-module + DB + external boundaries". The claim under test crosses `security` → `buffer` → DuckDB, so the §2 Integration row is not discharged by a unit assertion on the regex — which matches the scope's own MEASURE-FIRST framing.
- **Self-bootstrapping fixtures are mandatory (per test-plan.md §1 coverage trigger `agent-driven-discipline: Self-bootstrapping test data` + §7 Self-bootstrapping requirement).** The bare-key payload must be generated at test runtime via OTLP ingest or Rust builders; §11 Test Data bans pre-populating the DB via `.sql` scripts or snapshots. §7 also bans production telemetry dumps — the credential corpus must be synthetic.
- **The standard gate set is unconditional (per test-plan.md §3 Per-chunk gate discipline).** `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo nextest run --workspace --profile ci`, `cargo xtask capability-drift`, `cargo xtask capability-widening-check` must appear in the plan's Test Commands regardless of scope; the three `--prefix pulse-app/ui` webview gates are excluded only when the Files-to-modify / New-files lists touch zero `pulse-app/ui/**` paths.
- **Boot-smoke is conditional, and the direct-binary variant is the sanctioned form for runtime-state measurement (per test-plan.md §3 Boot-smoke gate + Direct-binary smoke variant).** §3's trigger path list is `pulse-app/src/main.rs`, `crates/ui-bridge/src/`, `pulse-app/src/observability.rs`, `tauri.conf.json`, `pulse-app/capabilities/*.json` — the scope's named files (`crates/security`, `crates/buffer`, `crates/interpretation`, `crates/triage`, `pulse-app/tests/`) are not on it. If the measurement needs live runtime state (fresh `ANDROMEDA_PULSE_DATA_DIR` + sustained `inject_demo` load), §3 requires the direct-binary form: assert from the run's own `&lt;data_dir&gt;/logs/agent-latest.jsonl*` (0 `app.panic.fatal`, 0 `ERROR`), shut down by SPECIFIC pid, confirm `:4317`/`:4318` released, with `bash scripts/agent-run.sh status` still listed.
- **`pulse-app` test targets have a location exception and a run-scope rule (per test-plan.md §2 Test directory conventions + §3 `run` Test selection).** `[lib] test = false` means pulse-app probes live in `pulse-app/tests/*.rs` reaching internals via `pub` + `#[doc(hidden)]`; and a pulse-app selection must be narrowed with `--filter-expr` / `-E` **under `--workspace`**, not with `-p` (measured rlib-format link failure). The scope's natural home `pulse-app/tests/e2e_pii_scrubber_persistence_coverage.rs` sits in exactly this family.
- **Quality gates bind (per test-plan.md §10).** ≥ 75% line / ≥ 70% branch / ≥ 85% function coverage; zero-flakiness (no retry-once, quarantine-and-fix); `#[ignore]` stays reserved for flake quarantine, and any committed `#[ignore]` needs a tracking issue (§11 Quality).
- **Mocking discipline (per test-plan.md §8 What NOT to mock + §11 Integration).** DuckDB must not be mocked at integration level — use an ephemeral in-memory instance; a mocked appender would not prove a "stored fields" claim.

## Patterns to follow
- **§5 boundary row `ingest → buffer (gRPC TraceService.Export → DuckDB rows)`** — drive via `tonic` 0.14.5 client to loopback, read back via `Connection::query_map`. This is the plan's existing shape for exactly the "does the value survive into stored fields" question; §6 Scenario P1 steps 2–6 are the E2E skeleton (builder → gRPC OK → poll `health.subsystems.buffer.rows_ingested` → query → field assertions).
- **§7 rstest fixture + parameterized-case pattern** (`#[fixture]` + `#[rstest]`, builder factories `MockTraceSpan::builder()`). The scope's existing keyed corpus (`scrubber.rs:120–129`) and the Allowed pin `trace_id=abc-123` (`:142`) are this pattern; both the new recall case and the false-positive guard belong as additional cases in it, not as a parallel bespoke harness.
- **§3 Log format → "Data leakage check: `! grep 'query parameters:' test.log`"** — the plan's own assert-by-absence idiom over the NDJSON log. It is the model for asserting a bare provider key never reaches `agent-latest.jsonl`, and it is the same read a CARRY #10 redaction counter would be graded through.
- **§3 Test data bootstrap per-test isolation** — `tempfile::TempDir` + `ANDROMEDA_PULSE_DATA_DIR=$TMPDIR/test-$$` + ephemeral in-memory DuckDB; retention/clock control via `tokio::time::pause()` only where an ambient clock exists.
- **§1 "Pending coverage triggers" table** — the plan's sanctioned mechanism for recording a decided-but-unimplemented leg. If the measurement lands as smoke/manual evidence rather than a committed test, or if the CARRY #10 external-gradeability leg or the Conductor eighth-category witness is deferred, §1 requires it be entered there rather than left in report prose.

## Anti-patterns to avoid
- **§11 Universal: "NEVER expose secrets in test output (log PII, raw OTLP payloads with credentials)."** The recall corpus must use synthetic, non-resolvable `sk_live_`/`sk-proj-`-shaped strings, and the test must not print the unredacted value on failure (assert on absence/shape, not by echoing the payload).
- **§11 Integration/Mocking: never mock DuckDB or the receiver under test, and never assert on raw OTLP protobuf bytes** — assert on decoded stored fields. A stub in the persistence path would make the measurement vacuous against the very claim it tests.
- **§11 E2E: never `sleep(N)` for synchronization** — wait on an explicit signal (`health` polling, channel event) so the measurement stays deterministic under §10's zero-flakiness budget.

## Contract bindings
- **tests ↔ obs (CARRY #10 redaction counter).** test-plan.md §3 Log format binds the harness to the obs NDJSON contract (`{timestamp,level,target,message,fields}`) and to `jq`-parseable agent signals; §3 `logs` tails the obs-declared path. If the plan lands a redaction-count field on `duckdb.append` / `buffer.tick`, its field name/shape is obs-plan's to define and the tests side owns only the assertion that the harness can read it from `&lt;data_dir&gt;/logs/agent-latest.jsonl`.
- **tests ↔ verification ledger (§9 CI Integration, Capability verification matrix).** `cargo xtask verify:capability-matrix` asserts ids / file-refs / grep-anchors resolve and fails CI on dangling ones. The scope notes the legacy `docs/v0_2_0/capability-verification-matrix.json:62` P-047 entry refs `crates/security/src/scrubber.rs` + `pulse-app/tests/e2e_pii_scrubber_persistence_coverage.rs` — whether that xtask still reads the legacy ledger (and so whether renaming/moving that test file breaks the gate) is research's question, not something this extract can attest.
