## Relevance
Partial — the defect itself is liveness, not security, but the repair lands on the ring-buffer write path that carries the plan's scrub mandate, and the chunk folds a security-plan PREREQ (the `cargo audit` standing deferral).

## Constraints
- The span write path's scrub CHOKE POINT is load-bearing and must survive any relocation of the baseline tap: security-plan §Security Anti-Patterns → Logging requires `spans.service_name` to be scrubbed inside `extract_service_name` (`crates/buffer/src/appender.rs`) precisely BECAUSE that one fn feeds three consumers — the `spans` column, the storm `FingerprintObserver`, and the baseline `SpanObserver` tap this chunk may move off the async task. Whether the repair's chosen topology keeps span data downstream of that fn is research's question.
- All five persisted client-controlled ring-buffer cells plus the log/exception fields must still pass `scrub_attribute` at their write boundary after the repair; the plan states this as MEASURED-current posture and it is a requirement any `dispatch_batch` / appender restructuring must preserve (per security-plan §Security Anti-Patterns → Logging).
- Any new or changed log emission on the consumer/retention path must not carry raw OTLP attribute values, span/log/metric content payloads, DuckDB query parameter values (identifier + parameter count only), or a full product-consumed filesystem path (per security-plan §Logging & Monitoring → What NEVER to log, and §Security Anti-Patterns → Logging).
- Any DuckDB statement the repair adds or alters must use `Connection::prepare` with `?` placeholders; string-interpolated SQL is banned outright (per security-plan §Input Validation, DuckDB query parameters row, and §Security Anti-Patterns → Input).
- The ring buffer must remain the in-memory `:memory:` connection with at-rest encryption OFF; if the repair changes connection topology (write/sweep/read split), it must not flip a DuckDB encryption feature (per security-plan §Data Protection → At rest, DuckDB ring buffer, and §Security Anti-Patterns → Data Protection, CVE-2025-64429).
- If the repair adds a dependency, `cargo deny check bans licenses sources` must pass with `multiple-versions = "deny"` unrelaxed, the `tonic` canary unskipped, and any duplicate carve-out ID-scoped + owner-named + reasoned with its closing condition (per security-plan §Dependency Security → CI integration and §Bootstrap phases → `dep-audit-tooling-install`).
- If the attribution forces the TauRPC procedure the scope says it should not need, it requires BOTH router registration and an `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`, plus a validated argument struct — capability JSON is not per-procedure here (per security-plan §API Security → TauRPC capability authorization; §Security Anti-Patterns → API).

## Patterns to follow
- The three sanctioned scrub SHAPES, per security-plan §Security Anti-Patterns → Logging: choke-point (`extract_service_name`), push-site (`scrub_otlp_field` on a bare column value), and joined `key=value` UNION bare-value (`metrics_points.labels`). A repair that reroutes a write path adopts the shape already governing that path rather than inventing a fourth.
- Bounded-parse-with-graceful-default for any new knob (a timeout, pool size, or threshold env var): trimmed, range-bounded, unset/empty/unparseable falls back to a documented default, never panics, never silently adopts an unintended bound — the `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` precedent (per security-plan §Input Validation → CLI / env var inputs).
- Boundary error collapse: module-internal `thiserror` enums convert to the `serde`-friendly `AppError` at the bridge; full chain goes only to the `tracing-subscriber` JSON sink (per security-plan §Error Handling). Relevant because the defect is currently silent — a repair that starts reporting must report through this shape.
- Basename-only for any path that appears in a new record, plus env-var NAME rather than value (per security-plan §Security Anti-Patterns → Logging; the two pre-existing full-path boot records are a named carried exception owned elsewhere, not a licence to add a third).
- Redaction applied at the subscriber layer, not at call sites (per security-plan §Logging & Monitoring → Log format) — a new consumer-stall field is not a place to hand-redact.

## Anti-patterns to avoid
- NEVER dump the blocked batch, its OTLP attribute values, or DuckDB query parameters into a diagnostic log while attributing the stall — the tempting instrumentation is the banned one (per security-plan §Security Anti-Patterns → Logging).
- NEVER route span data around `scrub_attribute` when relocating `observe_spans_for_baseline` or restructuring `dispatch_batch`; scrubbing only the DuckDB column while the tap reads raw is the exact failure the choke-point placement exists to prevent (per security-plan §Security Anti-Patterns → Logging).
- NEVER enable DuckDB at-rest encryption on the in-memory ring buffer as part of a connection-topology change (per security-plan §Security Anti-Patterns → Data Protection).

## Contract bindings
- **security ↔ obs:** PII scrubbing/redaction cross-cuts — obs owns the exact-leaf allowlist and field-set pin for any new `buffer.*` target (scope §6, obs-plan §10), security owns what may never appear in those fields (§Logging & Monitoring). A new stall/attribution field needs both.
- **security ↔ obs/arch:** the DuckDB connection-isolation invariant (write/sweep/read on separate connections) is obs/arch-owned; security's binding to it is the at-rest ban above — a topology change must not become an encryption change.
- **security ↔ triage:** `extract_service_name` is a shared contract — the baseline `SpanObserver` tap this chunk may move is one of its three consumers, so tap placement is jointly a triage-correctness and a scrub-coverage decision (per security-plan §Security Anti-Patterns → Logging).
- **security ↔ tests/CI:** the dependency gate runs as a job in the one CI workflow; the standing-deferral probe/overlap record is produced at wrap, not by a separate pipeline (per security-plan §Dependency Security → CI integration).
