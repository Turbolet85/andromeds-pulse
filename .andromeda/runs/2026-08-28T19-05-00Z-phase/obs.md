# obs extract

## Relevance
Relevant — this chunk is the named owner of an OPEN obs-plan §10 defect, edits the code path that hosts the `buffer.tick` fold sites, and its acceptance test consumes an obs signal as its verdict.

## Constraints
- **The DuckDB reference-connection mandate is the rule this repair must satisfy.** obs-plan §10 (DuckDB Connection Isolation & Load-Profile Operational Constraints) requires write (appender) / sweep (retention) / read (L1a + viz) isolation on the same `:memory:` DB via `Connection::try_clone()`, and requires any DuckDB consumer with a multi-second statement to take a dedicated cloned connection rather than the shared appender connection. §10 defect 4 records this mandate as **correct but NOT fully satisfied by shipped code**, names the working-route entry "Ingest consumer block under gap→resume" as owner, and mandates a reconnect-WITHOUT-gap first arm to separate the trigger — matching the chunk's §4 ordering.
- **Stall semantics are fixed and triple-sited.** obs-plan §10 (Standard+ invariants), §3 (Stall detection) and §1 (Heartbeat ticks) all require: tick presence is LIVENESS, not PROGRESS; the PROGRESS signal is `rows_ingested_delta` staying 0 across consecutive `buffer.tick`s while the ingest channel holds queued work; announced on `buffer.consumer.stalled` after 30 consecutive non-draining ticks (450 s), a threshold §10 requires to sit deliberately ABOVE its own 420 s sustained-drain cap so an in-spec drain cannot trip it. Changing threshold, field set, or definition requires amendment at all three restating sites.
- **Announcement discipline: once per transition, never per batch.** obs-plan §6 (Log levels mapping, `warn` row) requires `buffer.consumer.stalled` at WARN with exactly `reason`, `consequence`, `stalled_seconds`, `buffer_capacity_pct`, emitted once on healthy→stalled and once on recovery.
- **Any new target needs its OWN exact §8 leaf.** obs-plan §8 (Default-deny posture) requires exact-leaf registration enumerating every field the emit site emits; it records that a bare `buffer` key DOES exist, so `for_target`'s first-segment fallback resolves an unregistered `buffer.*` target to the tick field set and silently redacts every field — the failure mode the chunk's own §6 restates. Guards must live under `pulse-app/tests/` (per the `[lib] test = false` rule) and include a fallback discriminator so they cannot pass vacuously.
- **New tick fields are triple-site.** obs-plan §1 (Heartbeat ticks, the 14-field `buffer.tick` list), §5 (tick-aggregated Counter rows) and §8 (`buffer` whitelist) each restate the set; §8 additionally requires all `buffer` fields be aggregate numerics carrying no service / span / fingerprint identity.
- **The consumer loop and appender path are the named hot path.** obs-plan §11 (Telemetry Strategy / Logs / Metrics) bans over-instrumenting the appender inner loop and per-row DuckDB operations, bans `info`-level logging in a hot path, and bans unlevel-gated expensive field formatting there. §11 (Spans/Traces) additionally bans holding a `tracing::Span` guard across `.await` without `.in_current_span()` — load-bearing here, since the chunk moves work between the async task and the blocking pool.
- **Errors on the repaired path must surface.** obs-plan §10 always-required invariant (zero unlogged panics, `app.panic.fatal`) and Standard+ module-boundary error logging require every module-boundary error at WARN/ERROR with error category, not a full stack trace (§7 / Vector 2). Note the defect's shipped signature is 0 ERROR and 0 panics because nothing returns — a repair converting the block into a returnable or timed-out path acquires a boundary that §10 requires to be logged.

## Patterns to follow
- **Warn-on-fallback for a dedicated connection** — obs-plan §10 records the established shape used by `buffer::retention`, `TriageSqlState::new` and `viz::query::read_connection`: take the clone once at construction, emit a target-scoped WARN with `fallback = "shared_connection"` when the clone fails, and verify live at 0 fallback WARNs. If the repair hands the consumer or any task its own connection, this is the shape to copy rather than invent.
- **Counters ride the existing 15 s `buffer.tick` as FIELDS** — obs-plan §5 (tick-aggregated Counter rows) requires folding via `BufferState::record_*` once per batch rather than adding separate `metric.buffer.*` targets, with per-span-event / per-row emission barred by §11.
- **Post-append fold siting inside `dispatch_batch`** — obs-plan §5 (`redactions_applied` row) records as *structural* that each builder returns its per-batch tally and `record_redactions` folds at each table's OWN post-append site in `consumer::dispatch_batch`, so a batch rejected at `flush()` contributes zero, with per-table granularity load-bearing. A repair that restructures `dispatch_batch`'s lock discipline must preserve this property; its pre-2026-08-23 counter-example (`redactions_applied: 2` with `rows_ingested: 0`) is what regression looks like.
- **Exact-leaf guard with mutation check + fallback discriminator** — obs-plan §8 cites `pulse-app/tests/unit_observability_allowlist_consumer_stall.rs` (exact-resolve, complete-set both directions, drain-progress fields on `buffer.tick`, and a `buffer`-fallback discriminator) as the template for registering anything new here.
- **Async span propagation** — obs-plan §3 (Trace context propagation → internal async boundaries) requires `tokio::spawn` sites to use `.in_current_span()`; §4 keeps `duckdb.append` (`span.kind = "internal"`, attributes `duration_ms` / `rows_appended`) in P1's must-trace chain, so a restructured dispatch must not drop it.

## Anti-patterns to avoid
- **Do not weaken the drain-progress detector to green the leg** — obs-plan §11 (SLO) bans soft, unenforced budgets, and §10 records the 450 s / 30-tick siting as deliberate. Retuning the threshold, widening the field set's tolerance, or muting the target to pass `smoke:gap-resume` arm A is the obs-side mirror of the chunk's §5 ban.
- **Do not add a `buffer.*` target or tick field without its exact §8 leaf** — obs-plan §8 requires it; the bare `buffer` key makes the fallback silently redact rather than fail loudly, so an unregistered addition reads as all-zeroes at the wire.
- **Do not instrument per batch, per row, or at `info` inside the consumer loop** — obs-plan §11 (Telemetry Strategy / Logs) bans it; diagnostic appetite during attribution must not ship as permanent hot-path emission (the §5 rows record `cadence.trigger`'s one-record-per-cycle as the reason a wedge log reached 131 MB).

## Contract bindings
- **obs ↔ tests harness (primary):** obs-plan §10 records that `cargo xtask smoke:gap-resume` consumes `buffer.consumer.stalled` + `cargo xtask check:ingest-progress` as its verdict rather than adding a second detector, with the bounded tokens (`rows_static_while_channel_queued`, `accepted_spans_not_persisted`, `stalled_seconds`, `buffer_capacity_pct`) observed at the wire. The obs signal IS the acceptance test's oracle — any change to target, field set, or threshold changes what arm A asserts, which is why §5 of the scope treats loosening either side as one violation.
- **obs ↔ CI:** obs-plan §10 CI gates require the 45 s heartbeat-gap check (`xtask/ci/heartbeat-gap-check.sh`) across `ingest.tick` / `buffer.tick` / `viz.tick` / `plugins.tick`, and the Load-profile constraints require any new xtask check script over `agent-latest.jsonl` to be NEUTRAL-tolerant (absent stream ≠ failure). A new reconnect-without-gap arm that emits a check script inherits both.
- **obs ↔ security / PII:** obs-plan §8 is where this chunk's PII binding lands — `buffer` fields aggregate-only, never service / span / fingerprint identity, and no DuckDB query text or parameters in fields (§8 data classification, Vector 5).
- **obs ↔ `.claude/rules/observability.md`:** the chunk's §8 names obs-plan §10 defect 4 and the rules file's fourth-defect paragraph as the two masters recording the invariant as correct-but-unsatisfied; both need amending OPEN → closed-with-evidence when the repair lands (wrap's drift job, this chunk's evidence obligation).

## Acceptance criteria contributions
- On the GREEN leg, the drain-progress signal reads healthy by its unchanged semantics: `rows_ingested_delta` advances across consecutive `buffer.tick`s after resume, `last_append_age_seconds` stays bounded, and no `buffer.consumer.stalled` record with `reason = rows_static_while_channel_queued` appears — the same detector, same 450 s / 30-tick threshold, same four bounded fields as the RED leg (per obs-plan §10 Standard+ invariants and §6 `warn` row).
- Every new target or field the repair introduces carries its OWN exact §8 allowlist leaf enumerating all fields its emit site emits, guarded under `pulse-app/tests/` with a bare-`buffer`-fallback discriminator, and any new `buffer.tick` field is applied at all three restating sites (§1 / §5 / §8). Whether the repair introduces any new emission at all is research's question (per obs-plan §8 Default-deny posture).
- No new per-batch or per-row emission on the consumer or appender path, and no `info`-level logging inside the loop; any counter added folds once onto the existing 15 s `buffer.tick`, and `dispatch_batch`'s per-table post-append fold still yields zero for a batch rejected at `flush()` (per obs-plan §5 tick-aggregated Counter rows and §11 hot-path bans).
- The repaired path satisfies the reference-connection mandate — no task with a multi-second statement on the shared appender connection — and a dedicated clone, if taken, emits the established `fallback = "shared_connection"` WARN shape with the run recording zero such WARNs. Whether shipped code already takes a dedicated connection for the consumer or retention here is research's question; §10 defect 4 states the mandate is currently not satisfied (per obs-plan §10 DuckDB Connection Isolation).
