partial — the chunk touches one detection arm inside the `interpretation` crate, whose profile output feeds the arch-locked L4 runtime tier selection; it adds no surface, resource or dependency.

## Constraints
- Code lives in the `interpretation` library crate (`crates/interpretation/`), one of the reserved workspace crate names; no new crate and no re-use of a reserved name (per architecture §Occupied Resources → Cargo workspace crate names; §Established Decisions [Module Boundaries]).
- Dependency direction is preserved: `interpretation` gains no dependency on a sibling crate or on `pulse-app`, and the detector keeps reaching consumers through the `triage::contract::HardwareProfileSource` trait it implements, never through a new edge (per architecture §Cross-cutting Patterns → Module dependency direction).
- The detected profile is what selects the CUDA build with `-ngl 99` (gpu-primary / gpu-fallback) versus the CPU build with `-ngl 0` (cpu-primary / cpu-fallback). A widened GPU-present verdict therefore changes which binary and offload setting a Linux host gets. Research must map that downstream effect. Whether the tier→binary mapping in `llamacli_inference.rs` already follows this table is research's question (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer]; §Stack and Technologies → AI/ML serving row).
- No new reserved resource. That means no env var, TauRPC procedure, broadcast topic, capability, table or port. The `ANDROMEDA_PULSE_HARDWARE_PROFILE` override's semantics stay unchanged (per architecture §Occupied Resources → Environment variables, Tauri IPC routes, Tauri IPC events).
- No new workspace dependency for the probe: no driver-loading crate, no NVML binding and no subprocess. The `LlmInferenceRunner` trait surface stays the swap boundary, and the probe stays out of it (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer] → Bus-factor / swap paths; §Inherited Defaults → Module boundaries).
- Crate template shape: the change stays behind the crate's public contract module, with internals `pub(crate)` or private. A testable seam (an injectable candidate list or existence predicate) must not become a new cross-crate `pub` surface or a `pub use` re-export outside the contract module (per architecture §Conventions → Module visibility discipline; §Project Intent → Template patterns).

## Patterns to follow
- Trait-in-lower-crate state delivery: `HardwareProfileDetector` implements `triage::contract::HardwareProfileSource`. Consumers (the `pulse-app` boot wiring, `model.current_profile`, `diagnostics.snapshot`) read the profile only through that trait, so a fix confined to the detector's Linux arm reaches every consumer without touching them (per architecture §Occupied Resources → Tauri IPC routes `model.current_profile` / `diagnostics.snapshot`; §Cross-cutting Patterns → Module dependency direction).
- Pure-fn-over-injected-inputs for testability is consistent with the crate-per-module, `pub(crate)`-internals template. Keep the production arm a thin caller over the real system paths (per architecture §Project Intent → Template patterns; §Conventions → Module visibility discipline).
- Rust naming: a candidate-path set declared as a constant is `SCREAMING_SNAKE_CASE` and functions are `snake_case`, enforced by clippy's style group in CI (per architecture §Conventions → Variable / function naming).
- Config precedence holds: a set env override beats detection, and detection is only the built-in default. Widening the probe changes the default and never the precedence (per architecture §Cross-cutting Patterns → Config management; §Inherited Defaults → Config precedence).

## Anti-patterns to avoid
- Probing by loading the driver or spawning a tool (`dlopen` of `libcuda`, `nvidia-smi` via `tokio::process::Command`). Either would introduce a dependency or subprocess outside the D1 inference-spawn discipline, which bounds only the `llama-cli` generation spawn (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer]).
- Touching the macOS or Windows arms, or the `HardwareProfile` vocabulary and labels, in a Linux-only widening. Those labels are the bounded-`String` wire values consumed by `model.current_profile` and `ModelLoadEvent` (per architecture §Occupied Resources → Tauri IPC routes `model.current_profile`; §Cross-cutting Patterns → Cross-bridge data shape).

## Contract bindings
- arch ↔ security: the detector reads system-level filesystem paths. These are not `ANDROMEDA_PULSE_*_PATH` inputs, so the env-var canonicalize-and-confine rule does not bind them. Arch only registers the resource set. Whether the probe logs any path (basename-only rule) is security/obs territory (per architecture §Occupied Resources → Environment variables).
- arch ↔ obs: the profile label reaches the `pulse://stream/model-status` broadcast and the `model.current_profile` / `diagnostics.snapshot` payloads. A widened verdict changes their values but not their shape, and that shape stays fixed (per architecture §Occupied Resources → Tauri IPC routes, Tauri IPC events).
- arch ↔ tests: `pulse-app/tests/integration_real_llama_cli.rs` and `examples/l4_decision_probe.rs` consume the detector. The real-model legs need the operator's port slot and the absent L4 model, so a unit-level seam proof stays inside the workspace-boundary discipline with no launch. Whether the existing tests pin host-dependent outcomes is research's question (per architecture §Cross-cutting Patterns → Development Style).
- Registry observation for P3: no `HARDWARE_PROFILE` string matched anywhere in architecture §Occupied Resources → Environment variables, so the existing `ANDROMEDA_PULSE_HARDWARE_PROFILE` override (named in CLAUDE.md's `interpretation` module entry) appears unregistered there. This chunk does not change that var. Whether it is product-consumed and owes a registry-completeness entry is for research and the wrap to decide, not for this chunk's scope.
