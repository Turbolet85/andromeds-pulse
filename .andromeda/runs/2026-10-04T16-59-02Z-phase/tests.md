# tests extract

## Relevance
relevant: a unit-tier change in a library crate (`crates/interpretation/src/hardware.rs`). The scope's `[inferred]` testability item (an injectable candidate set or existence predicate) is a test-strategy decision this plan governs.

## Constraints
- The tier is Standard, and new pure or isolated logic is owed unit-tier coverage, with module boundaries tested over injected dependencies (per test-plan §1 Test Scope Summary and §2 Test Strategy, Unit row). `interpretation` is a LIBRARY crate, so its tests go in a co-located `#[cfg(test)] mod tests` in `hardware.rs` and actually execute. The `pulse-app` `[lib] test = false` exception does not apply unless the chunk adds a pin under `pulse-app/` (per test-plan §2 Test directory + naming conventions and §4 Conventions).
- Tests must be deterministic and must not depend on the host (per test-plan §2 Agent-runnable invariants and §11 Universal). A test that observes the REAL `/usr/lib*` layout gives different verdicts on the Omarchy dev host (driver present) and on the CI `lint-test` matrix runners (ubuntu-22.04 / macOS / Windows, no NVIDIA driver; per test-plan §9 Matrix builds). Detection pins therefore have to run over an injected candidate list or existence predicate, or over a `tempfile::TempDir` layout, and never over the host's real paths. Whether the existing tests in `hardware.rs` already avoid this is research's question.
- Filesystem dependencies use a real temp dir and are not mocked: `tempfile::TempDir`, plus the `assert_fs` symlink helpers where the `libcuda.so -> libcuda.so.1 -> libcuda.so.<ver>` chain matters. A pure helper is tested directly and not mocked (per test-plan §8 Mocking & Stubbing Discipline, "What to mock: Filesystem" and "What NOT to mock").
- The test function for the Linux arm is gated with `cfg(target_os = "linux")` if it exercises that arm. A pure helper over an injected list can run on every OS (per test-plan §4, the corpus crate's Linux lock-dir rule precedent).
- The plan's §3 Per-chunk gate discipline requires the standard gate set unconditionally: fmt, clippy `-D warnings`, `capability-widening-check`, `check:ingest-progress`, `check:staged-artifacts`, `capability-drift` BEFORE the workspace nextest, the workspace nextest, the `--features mcp-server` `emit_taurpc_bindings` regen as the last cargo-adjacent step, and the no-procedure close `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts`. The webview gates are excluded only if no `pulse-app/ui/**` path is touched. The boot-smoke gate applies only if `pulse-app/src/main.rs`, `crates/ui-bridge/src/`, `observability.rs`, `tauri.conf.json` or `capabilities/*.json` is touched, and the scope names none of these.
- Quality gates: coverage of at least 75% line, 70% branch and 85% function, a zero-flakiness budget, and any test failure fails the build (per test-plan §10 Quality Gates & Coverage Targets).
- The §1 Pending coverage triggers record a "one-time proof standing in for a gate" class: a helper is pinned while the production call site that must USE it is not, so reverting the call site leaves every test green (see the rows `l4-path-guard-callsite-wiring-coverage` and `render-posture-main-placement-coverage`). If the probe is split into a pure fn plus a production caller over the real paths, the production candidate set needs its own pin. Pinning only the pure fn over a test-supplied list leaves the production arm unguarded.

## Patterns to follow
- Inject the environmental input as an explicit parameter rather than reading ambient state, as the plan does for the triage crate: "The clock is injected as an explicit `now_nanos` parameter … parameter injection is the stronger form" (per test-plan §4, triage crate). Here the analogue is a candidate-path list or an `exists` predicate passed into a pure fn, with the production arm calling it over the real system paths.
- Parameterize the layout cases with `rstest` `#[rstest]` (per test-plan §4 Fixture pattern at unit level and §7 Test Data & Fixtures). The cases are Arch `/usr/lib`, Debian multiarch, the CUDA toolkit `/usr/local/cuda/lib64`, none present, and, if P4 adopts them, soname-only `libcuda.so.1` and `/usr/lib64`.
- Prove each pin discriminates: RED against the unwidened candidate set at the chunk base, then a mutation check showing that removing the new candidate reddens the Arch-layout pin while the existing-layout pins stay green. This follows the mutation-checked discipline the §1 Pending coverage triggers rows and §4 crate entries record ("mutation-checked so each rejection branch discriminates").
- Name tests as the §4 Conventions require (`test_<entity>_<scenario>`, flat per module) and use `expect("…")` rather than a bare `unwrap()` (per test-plan §11 Unit).
- If the dev-host confirmation goes through `pulse-app/examples/l4_decision_probe.rs`, it is evidence and not a gate. That `[[example]]` has zero tests, and nextest collects an example's tests only with `test = true` declared (per test-plan §1, rows `l4-decision-probe-arg-parse-unit-coverage` and `inject-demo-arg-parse-unit-coverage`).

## Anti-patterns to avoid
- NEVER steer detection tests with `std::env::set_var` (for example by setting `ANDROMEDA_PULSE_HARDWARE_PROFILE` mid-test). Use constructor or parameter injection instead (per test-plan §11 Mocking). Under edition 2024, `set_var` is also unsound once more than one thread exists, and nextest runs tests in parallel.
- NEVER assert a host-dependent verdict, such as "this machine reads GPU-present". It passes on the dev host and fails on CI runners, which is a flake by construction and gets quarantined under the zero-flakiness budget (per test-plan §2 Agent-runnable invariants and §10).
- Do not let a one-time dev-host probe stand in for the regression guard on the production candidate set (per test-plan §1 Pending coverage triggers, the "one-time proof standing in for a gate" class).

## Contract bindings
- tests ↔ arch: per the scope's Boundaries, the `ANDROMEDA_PULSE_HARDWARE_PROFILE` override, the profile vocabulary, `profile_label` and the `ModelLoadEvent` broadcast are unchanged. Any existing pins on those surfaces should pass byte-identically and are not rewritten. Whether such pins exist is research's question.
- tests ↔ obs: none new. The scope declares no new log target, and with no boot path touched the §3 boot-smoke gate is not triggered.

## Acceptance criteria contributions
- `cargo nextest run -p interpretation` passes with the new co-located pins (per test-plan §4 Conventions and §2 Agent-runnable invariants). The pins must cover: an Arch layout (`<root>/usr/lib/libcuda.so` present) reads GPU-present; the Debian multiarch and `/usr/local/cuda/lib64` layouts still read GPU-present; no candidate present reads GPU-absent. All verdicts are reached over an injected set or a TempDir and are independent of the host's real filesystem.
- RED before GREEN: the Arch-layout pin fails against the base candidate set. A mutation that removes the new candidate reddens it, while the existing-layout pins stay green (per test-plan §1 Pending coverage triggers, mutation-checked precedent, and §10 Build failure conditions).
- A committed pin covers the PRODUCTION candidate set itself and asserts it contains the two pre-existing paths plus the new `/usr/lib` entry (widen, never narrow). Reverting the production arm must redden a test (per test-plan §1 Pending coverage triggers, `l4-path-guard-callsite-wiring-coverage` class).
- The §3 standard gate set is green, in its stated order, and the bindings close `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts` exits 0 because no procedure is added. Workspace coverage stays at or above 75% line, 70% branch and 85% function (per test-plan §3 Per-chunk gate discipline and §10 Quality Gates & Coverage Targets).
