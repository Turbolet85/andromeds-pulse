## Constraints
- Any OTLP-derived attribute value crossing into `corpus.db` or the self-observation log sink must pass `security::scrubber::scrub_attribute` (→ `Allowed`/`Redacted`) before write (per security-plan.md §Security Anti-Patterns → Logging, uniform-scrubber-coverage framing). The newly-populated det-L4 fields (`evidence_refs` et al.) are in scope of that invariant if they carry attribute content into `incidents`/`incident_events`/`digest_archive`; **whether the deterministic producer's path already routes through the scrubber is research's question.**
- The NEVER-log list governs the drive path and every evidence artifact landed in this repo: no MCP tool response bodies, raw OTLP attribute values, DuckDB query parameter values, snapshot or clipboard contents (per security-plan.md §Logging & Monitoring → What NEVER to log). MCP `query_*` responses are the declared indirect-prompt-injection surface the receiver cannot fully sanitize — documented behavior, not something this chunk may "fix" by sanitizing telemetry (per security-plan.md §Logging & Monitoring → snapshot/clipboard/MCP-tool-response hygiene).
- The published workspace key `<data_dir>/run/workspace-key` — the boundary whose alignment made this read-back reachable — must stay validated as untrusted on the sidecar read (bounded ≤ `MAX_WORKSPACE_KEY_BYTES`, UTF-8, newline-trimmed, empty/control-char rejected → `None` + fall back to `data_dir`), consumed ONLY as an opaque filter string and never as a path, with only the basename logged (per security-plan.md §Input Validation → Published workspace key row).
- Read-back queries (`query_incident_list`, `query_traces`/`query_metrics`/`query_logs`) must bind filters through `Connection::prepare` + `?` placeholders on the shared prepared-statement path; identifier interpolation is rejected entirely and user input never names a table (per security-plan.md §Input Validation → DuckDB query parameters row).
- `ANDROMEDA_PULSE_L4_DETERMINISTIC` must remain a bounded truthy-parse (`1|true|yes`, default false, no unbounded string), and any NEW env var or file input the drive recipe introduces must land in the §Input Validation boundary enumeration with a bounded parse — that enumeration claims to be complete (per security-plan.md §Input Validation → CLI / env var inputs row).
- If P3 answers premise 3 by adding a Pulse-side surface to expose a timing cap, a new TauRPC procedure requires BOTH router registration and a `pulse-app/capabilities/` JSON entry, enforced by the xtask drift check; unlisted IPC is silently rejected at runtime (per security-plan.md §API Security → TauRPC capability authorization).
- The external-harness drive recipe must not widen a trust boundary to become reachable: OTLP receivers stay `127.0.0.1`-only, and the MCP sidecar keeps its double gate (`--features mcp-server` AND `ANDROMEDA_PULSE_MCP_ENABLED=true`, with the graceful-degrade `warn` preserved) (per security-plan.md §API Security → MCP feature double-gate).

## Patterns to follow
- `workspace_detector::contract::{publish_workspace_key, read_published_workspace_key}` — the canonicalize-and-confine write plus bounded-untrusted read pair already declared for the cross-process key (per security-plan.md §Input Validation → Published workspace key row).
- `scrubbed_clone`-style pre-persist projection on corpus-bound snapshot types (precedent: `BaselineState::scrubbed_clone`, `StormStateSnapshot::scrubbed_clone`) — the declared shape if a det-L4-derived struct becomes corpus-persisted (per security-plan.md §Security Anti-Patterns → Logging).
- Bounded env parse with default-on-any-failure and no panic, as required for `ANDROMEDA_PULSE_L4_DETERMINISTIC` and `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` (per security-plan.md §Input Validation → CLI / env var inputs row).
- Boundary error shapes: MCP JSON-RPC 2.0 error object with stable numeric `code`; `AppError::{Validation, NotFound, Internal, …}` at the TauRPC bridge — no stack traces, file paths, Rust struct names, hostnames or IPs across either (per security-plan.md §Error Handling).
- `#[tracing::instrument(skip(key))]` discipline at every key-handling call site, with `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` treated as secret-class (per security-plan.md §Secret Management → What counts as secret).

## Anti-patterns to avoid
- NEVER log or transcribe into evidence artifacts an MCP tool response body, raw OTLP attribute values, snapshot/clipboard contents, or DuckDB parameter values (per security-plan.md §Security Anti-Patterns → Logging).
- NEVER `format!`-interpolate an incident id, workspace key, or service filter into DuckDB SQL on the read-back path (per security-plan.md §Security Anti-Patterns → Input).
- NEVER make the external harness reachable by binding OTLP off `127.0.0.1`, and NEVER single-gate the rmcp sidecar spawn (per security-plan.md §Security Anti-Patterns → API and → Code Patterns).

## Contract bindings
- **PII scrubbing ↔ obs + tests:** the canned deterministic `evidence_refs` values are fixture content — they must be synthetic and must not resemble real credentials/PII, and the scrubber invariant is shared with obs's PII-scrubbing section (per security-plan.md §Security Anti-Patterns → Logging).
- **CI security gate ↔ tests §CI Integration:** one workflow, security as a job — `cargo deny check bans licenses sources` is the pass/fail gate and `cargo deny check advisories` is a separately-recorded observation (per security-plan.md §Dependency Security → CI integration).
- **Timing-cap observables ↔ obs:** if P3 premise 3 resolves to "the obs log" as the surface exposing the four caps, the §Logging & Monitoring redaction rules govern what those events may carry; the cap-observability answer itself is research's, not this domain's.
- **Corpus key custody ↔ the read-back path:** cross-process decryption of incident cells depends on the persisted OS-credential-store key or the opt-in passphrase fallback; a host with neither degrades the corpus to absent rather than inventing a key (per security-plan.md §Secret Management → Storage → Runtime).
