## Relevance
**Relevant** — this is an E2E/`dynamic-external` verification chunk over the MCP read-back path plus timing-cap budget assertions, all squarely in the tests domain (harness contract, E2E path P3, quality gates).

## Constraints
- Every leg — including the external Conductor instrument — must terminate in a deterministic machine-parseable signal (exit code + structured stdout/JSON + log-line match) with no human-in-the-loop step; "operator observed it" is not admissible evidence, and evidence landed in this project must be re-readable by an agent (per test-plan.md §1 coverage trigger `agent-driven-discipline: No manual verification checkpoints`, and the plan's agent-driven invariant preamble).
- The chunk's `## Test Commands` MUST list the full standard gate set unconditionally — `cargo fmt --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo nextest run --workspace --profile ci`, `cargo xtask capability-drift`, `cargo xtask capability-widening-check` — with the three `--prefix pulse-app/ui` webview gates excluded only if the file lists touch zero `pulse-app/ui/**` paths (per test-plan.md §3 Per-chunk gate discipline).
- Because the verification needs runtime state the harness `run` verb cannot express (a fresh `ANDROMEDA_PULSE_DATA_DIR`, the env-gated `ANDROMEDA_PULSE_L4_DETERMINISTIC=true` mode, a sustained OTLP load), the **Direct-binary smoke variant** is the mandated form: launch `target/debug/pulse-app.exe` under those env vars, seed over the real receiver, assert 0 `app.panic.fatal` / 0 `ERROR` in `<data_dir>/logs/agent-latest.jsonl*`, shut down by SPECIFIC pid, confirm `:4317`/`:4318` released — with `bash scripts/agent-run.sh status` still run as the listed harness gate (per test-plan.md §3 Boot-smoke gate → Direct-binary smoke variant).
- The producer fix lands in `pulse-app`, whose `[lib] test = false` makes co-located `#[cfg(test)] mod tests` compile but never run; unit-shaped probes for the populated `L4Output` fields MUST live as separate targets under `pulse-app/tests/*.rs` reaching internals via `pub` + `#[doc(hidden)]` (per test-plan.md §2 Test directory + naming conventions and §4 Conventions → Test file location).
- A narrowed `pulse-app` run must use `--filter-expr` / `-E` **under `--workspace`**, never `-p pulse-app -E …` (measured rlib-format link failure immediately after a green `cargo build --workspace --tests`) (per test-plan.md §3 `run` → Test selection).
- The deterministic incident must be self-bootstrapped at test runtime over the live loopback receivers or Rust builder factories — no pre-baked DuckDB/corpus snapshot, no `.sql` seed, no committed incident fixture DB (per test-plan.md §7 Self-bootstrapping requirement and §1 trigger `agent-driven-discipline: Self-bootstrapping test data`).
- The MCP read-back must be driven as a real subprocess with BOTH gates satisfied (compile-time `--features mcp-server` and runtime `ANDROMEDA_PULSE_MCP_ENABLED=true`), asserting the tool-response data shape/content — external-LLM caller behaviour stays out of harness scope, so the assertion is on payload fidelity, not agent behaviour (per test-plan.md §1 mcp-server row + Surfaces-under-test MCP row, §5 Module ↔ MCP sidecar).
- Any flake in the new legs is quarantine + root-cause, never retry; `#[ignore]` stays reserved for flake quarantine, and load-shaped legs join the nextest `[profile.load-profiles]` profile instead (per test-plan.md §10 Zero-flakiness budget + Load profiles).

## Patterns to follow
- **E2E scenario P3 shape** for the read-back leg: spawn sidecar via `tokio::process::Command` with piped stdio, write a JSON-RPC 2.0 `tools/call` frame to stdin, parse line-delimited stdout, assert the response carries `result` (not `error`) with the contracted field set, then SIGTERM and verify exit code 0 with no zombie (per test-plan.md §6 Scenario P3).
- **The existing cross-process boundary row** — app boot publishes to `<data_dir>/run/workspace-key`, the sidecar's `init_incident_context` reads it, byte-equality asserted, absent/invalid file falls back to `data_dir` on both ends — is the established rung this chunk's read-back sits on; the pending sidecar-subprocess extension is spec'd there (per test-plan.md §5 Boundary types covered, §1 pending trigger `workspace-key-cross-process-coverage`).
- **The corpus crate's real-process-boundary precedent**: a test that re-executes its own test binary, chosen explicitly because the obvious in-process form *would have passed while the defect was live*. That is the same failure shape as this chunk's vacuous-surface hazard, and the plan records the reasoning as the reason to pay for the expensive form (per test-plan.md §4 What unit tests cover → corpus crate).
- **Timing caps asserted from ms-form machine-parseable fields, never a human-facing derived number** — the frame-budget reconciliation established that descriptive intent (fps) is retained as prose while every CI assertion binds to a `metric.*` ms value; the four delegated caps (P-025/P-027/P-037/P-045) should follow the same discipline (per test-plan.md §10 Frame-budget assertion note).
- **Fixture factories over literals** for the seeded telemetry: `MockTraceSpan::builder()` / `MockArrowBatch::builder()` composed through `rstest` `#[fixture]`, with `tempfile::TempDir` + `ANDROMEDA_PULSE_DATA_DIR` per-test isolation (per test-plan.md §7 Seed strategies, §4 Fixture pattern at unit level).

## Anti-patterns to avoid
- NEVER `sleep(N)` to synchronize — wait on an explicit signal (`health`/status poll, channel event, log line). Especially load-bearing here: a sleep-based wait silently converts a timing-cap assertion into a tautology (per test-plan.md §11 E2E).
- NEVER mock what the read-back is supposed to prove — no mocked OTLP receiver, no mocked DuckDB at integration level, no stubbed sidecar; drive live loopback `:4317`/`:4318` and a real subprocess (per test-plan.md §11 Integration + Mocking).
- NEVER admit a manual/visual verification step or a human-approved screenshot as the closure evidence for this cap, and NEVER emit raw payloads/secrets into test output (per test-plan.md §11 Universal (agent-driven specific)).

- **tests ↔ obs (status endpoint).** `bash scripts/agent-run.sh status` remains the listed harness gate and must return the §3 status shape (`status`, `subsystems.*.status`, `subsystems.buffer.rows_ingested`, `pid`, `uptime_ms`); ingest confirmation for the seeded incident reads `rows_ingested` from it (per test-plan.md §3 Status endpoint shape).
- **tests ↔ security (log redaction).** test-plan.md §1 pending trigger `security-vector-coverage: MCP response body redaction` requires that a `query_traces`-shaped MCP call leave `result_content` OUT of `agent-latest.jsonl` (only `result_type` + `result_count`), binding to security-plan §Logging vector 4. This chunk newly populates `evidence_refs` that flow into the MCP response, so the absence check becomes non-vacuous for the first time — and the plan requires it to be an assertion, not an assumption.
- **tests ↔ security (gate forms).** test-plan.md §3 is authority for WHICH gates the chunk lists (and §11 Test Strategy bans skipping `cargo deny check bans`); the split `bans licenses sources` pass/fail form, the separately-observed advisories set, and the `cargo audit` 3-wrap re-run interval are security's authority (`rules/security.md` 2026-08-17) — tests carries them in the command list without redefining them.
- **tests ↔ arch (verification matrix).** test-plan.md §9 requires `cargo xtask verify:capability-matrix` to resolve every entry's ids / file-refs / grep-anchors and to fail CI on dangling ones, with new capabilities extending the matrix JSON in the chunk that lands them. Any P-075 matrix edit must keep its anchors resolvable; whether the 0.3.0 (P-061…P-082) matrix is wired into that same xtask is research's question.
