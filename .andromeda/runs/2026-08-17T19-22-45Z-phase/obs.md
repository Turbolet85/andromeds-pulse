# obs extract

## Relevance
Relevant — the chunk's own gradeability defect, the MCP read-back surface, and the four delegated timing caps all hinge on obs-owned surfaces (the JSON log family, `metric.*` events, and the §8 redaction registry).

## Constraints
- **A field the acceptance grades on must resolve to an EXACT allowlist leaf, or default-deny redacts it and it grades as absent.** obs-plan.md §8 (Default-deny posture) requires an exact leaf enumerating *all* fields an emit site emits, because `for_target`'s prefix fallback otherwise resolves a dotted target to an unrelated field set. This is the same vacuous-pass class the chunk exists to remove, one layer down: if the deterministic producer's populated fields (or a `degraded_mode`/evidence count) are emitted on `interpretation.incident.created` — recorded in §8 as a four-field exact leaf — the leaf must be extended in the same change, and no bare `interpretation` / `triage` / `incidents` / `corpus` prefix key may be introduced (§8).
- **Content-fidelity must be asserted on the MCP wire, never from the obs log.** §8 (Data classification: MCP response bodies) and §11 (Project-specific) require `result_type` + `result_count` only; the `mcp-server` allowlist in §8 is `method` / `result_type` / `result_count` / `feature_flag_enabled` / `duration_ms`. `evidence_refs` may become a count or type field; its content may not be logged.
- **rmcp stdio purity is a hard constraint on the drive recipe.** §3 (Logging stack) requires the sidecar's tracing writer forced to stderr-JSON with the TTY check disabled and a distinct `andromeda-pulse-mcp` service identity; §11 (Universal) bans any stdout write from any subsystem in that process. Conductor reads that stdout, so any stray print corrupts the read-back rather than failing it cleanly.
- **The MCP path must be gated open by both gates, and the gate state is itself the evidence.** §4 (Scenario P3) requires `mcp.feature.gate.check` carrying `feature_flag_enabled` + `env_var_mcp_enabled`, and §11 (Project-specific) bans the compile-time flag without the `ANDROMEDA_PULSE_MCP_ENABLED=true` runtime gate.
- **A timing cap is only assertable if it has a `metric.*` surface emitting raw per-event values.** §5 (Metric emission convention) fixes `metric.{module}.{measure}` with a numeric `value`/`duration_ms` field and agent-side percentile computation; §11 (Metrics) bans precomputed quantiles in the emission path. For any of the four caps measured in the webview, §3 (Frontend bridge) and §4 (desktop-webview row) require the value to reach the log *only* through a TauRPC `telemetry.frontend.*` command — there is no browser-side sink. Whether such surfaces exist for halo hue / constellation discovery / report render / counter refresh is research's question (scope premise 3).
- **The one field that would attest *which* L4 runner produced the incident is recorded as muted, and is owned elsewhere.** §8 (Muted-diagnostic backlog) lists `interpretation.model.load` → `inference_mode` among five targets measured redacted, owner = the "Diagnostics un-muting + harness-truth sweep" route entry. Whether it is still redacted at HEAD is research's question; §8's posture forbids silently widening a target owned by another entry.
- **Run-window hygiene applies to the drive itself.** §10 (SLO invariants + CI gates) requires zero `app.panic.fatal`, no >45s gap between consecutive ticks per tick target, and run-window scoping (`write_run_window_log`) so cross-session gaps do not produce false FAILs; §10 also fixes the two-state posture where an absent metric stream is NEUTRAL, not FAIL.

## Patterns to follow
- **Once-per-boot WARN with bounded static fields as the "this run is reduced-capability" disclosure** — §6 (`warn` row) and §8's leaves for `app.boot.buffer.degraded`, `corpus.keychain.fallback`, `triage.baseline.bootstrap_window.override`. This is the plan's established shape if premise 2 resolves as "`degraded_mode: true` is correct-by-design for a model-less runner": make the mode distinguishable rather than expecting a flag to flip.
- **Exact leaf + no-bare-prefix ban + guard test under `pulse-app/tests/`** — §8 records that a guard placed in `observability.rs`'s own `mod tests` compiles but never runs under `[lib] test = false`; the working precedents named there are `unit_observability_allowlist_incident_diagnostics.rs` and `unit_observability_allowlist_bootstrap_window.rs`.
- **Positive-reading tick counters instead of inference from downstream silence** — §1 (Heartbeat ticks) and §5 (tick-aggregated counter row) require `buffer.tick` to carry `span_events_seen` / `fingerprints_computed` / `observer_invocations`, with equality of the latter two as the signal that the storm detector's feed is actually fed. This is the shape for proving Conductor's storm reached the detector (scope premise 4).
- **The already-registered read-back stations** — §8 (Incident-path diagnostic leaves + corpus leaves) requires `incidents.list_active.request` → `item_count`, `triage.incident.persist`, `triage.incident.corpus_restore`, and `corpus.read.undecryptable` (one aggregate per query, never per row). These are the log-side checkpoints along exactly the path this chunk drives.
- **`jq` over `agent-latest.jsonl`, scoped to the run window, as the single aggregation path** — §10 (Performance budgets) and the `xtask/ci/heartbeat-gap-check.sh` gate pattern. An external harness's cap assertion should reuse this convention rather than introducing a second aggregation surface.

## Anti-patterns to avoid
- Logging MCP tool response content, raw OTLP attribute values, or DuckDB query parameters (§11 Logs + Project-specific; §8 vectors 1 / 4 / 5) — the content-fidelity assertion must not be satisfied by making the response body loggable.
- Any `println!` / `dbg!` / library stdout write from the rmcp sidecar while debugging the drive (§11 Universal) — it silently disconnects the MCP client.
- Treating an absent metric stream, or a soft/unenforced threshold, as a satisfied cap (§11 SLO; §10 two-state NEUTRAL posture) — zero samples is NEUTRAL, which is a decline, not a pass.

## Contract bindings
- **obs ↔ tests harness (log format):** §3 (Log format JSON schema) states the JSON-per-line shape is taken verbatim from the test plan's harness contract — obs aligns to tests, not the reverse; §6 fixes the required top-level keys (`timestamp` / `level` / `target` / `message` / `fields`) with new attributes riding inside `fields`.
- **obs ↔ external harness (Conductor, `dynamic-external`):** §2 (Agent-readable invariants) and §3 (Log file location) make the readable surfaces the JSON log file plus the MCP stdout stream — no dashboard. §3 also fixes the path default and the `ANDROMEDA_PULSE_DATA_DIR` override with per-platform locations and daily rotation, which determines where the harness (launching pulse-app outside its own repo) must read evidence from.
- **obs ↔ tests §Smoke (liveness):** §3 (Complementarity with the `health` command) requires ticks and the synchronous `health` command to coexist — the harness polls `health` for active boot liveness; ticks serve retroactive window analysis.
- **obs ↔ security §Logging & Monitoring:** §8 requires vectors 1–6 redaction enforced at both the `#[instrument(skip(...))]` source and the subscriber Layer.
- **obs ↔ CI (§9):** the log file is a per-job artifact (with the snapshot markdown on failure) and CI adds `ci.run.id` / `git.commit.sha` default fields — relevant if this chunk's evidence is landed as an artifact rather than only in-repo.

## Acceptance criteria contributions
- Every field the P-075 acceptance grades on resolves to an EXACT allowlist leaf covering all fields its emit site emits, guarded by a test under `pulse-app/tests/` (not src `mod tests`), with no bare `interpretation` / `triage` / `incidents` / `corpus` prefix key introduced (per obs-plan.md §8 Default-deny posture).
- The drive's log contains no MCP tool response body, raw OTLP attribute value, or query-parameter text; MCP events carry `method` / `result_type` / `result_count` / `feature_flag_enabled` / `duration_ms` only (per obs-plan.md §8 Data classification + §11 Project-specific).
- Each of the four delegated caps is graded from raw per-event `metric.*` values (or the MCP response) with a non-zero sample count inside the run window; a zero-sample stream is recorded NEUTRAL and the cap is declined, never claimed (per obs-plan.md §10 Performance budgets + §5 Metric emission convention).
- The drive window shows zero `app.panic.fatal` events and no >45s gap between consecutive `ingest.tick` / `buffer.tick` / `viz.tick` / `plugins.tick` events, with run-window scoping applied (per obs-plan.md §10 SLO Invariants & CI gates).
