# security extract

## Relevance
relevant — the chunk adds the engine's first way in besides telemetry and removes the MCP stdio vector; security-plan states the sidecar's surface and NO door surface (no listener, no caller-identity mechanism, no answer bound), so the door's surface is a boundary widening the plan does not yet cover and the wrap amends.

## Constraints
- **Owner-only has no mechanism in the plan.** security-plan §Threat Model Summary (Auth model; Attack surface → the loopback vector's trust boundary) states loopback binding as the only authorization boundary and states that it admits any local process; security-plan §Authentication & Authorization reads N/A by design. So P-126's refusal of another account on the same host cannot rest on loopback binding alone: the enforcement (how the caller's account is established and compared) is a new decision for the P4 boundary dialog, recorded PROVISIONAL with the founder's word owed, in the form security-plan §Security Anti-Patterns → Input uses for an operator-read widening.
- **Own host only.** security-plan §Security Anti-Patterns → API bans any non-loopback bind for the receivers and security-plan §Threat Model Summary (Infrastructure → Networking) states local-only networking with no inbound exposure; the door must not weaken either statement. If the door speaks HTTP on a loopback port, security-plan §API Security (Host header allowlist, CORS, Request size limit rows) names the browser / DNS-rebinding exposure and the size cap for `:4318` only — the chunk's plan either gives the door the same three controls or picks a transport a browser cannot reach, and says which.
- **Every call is validated at the boundary.** security-plan §Input Validation requires validation at ALL system boundaries; its MCP stdio inputs row gives the standing form for a tool surface (closed name dispatch, serde argument structs, unknown fields refused, bounded reads) and its DuckDB query parameters row requires prepared statements with placeholders and no user-named table or column. The door's tools take that form; whether the door can reuse the prepared-statement path the plan says the `query_*` tools share with `viz` is research's question.
- **What a call may reach and return.** A tool argument is a filter, never a path: security-plan §Input Validation (Published workspace key row) is the precedent for a value consumed only as an opaque string, never opened or joined. Nothing on security-plan §Secret Management ("What counts as secret") leaves through an answer or a record — the corpus key and the passphrase included. What an answer returns is redacted only by the write-boundary scrub of the cells security-plan §Security Anti-Patterns → Logging enumerates (the ring buffer is unencrypted; `span_events.exception_type` is a deliberate exclusion); whether every column a door tool selects is inside that covered set is research's question.
- **A new place on disk, a new variable or a new command word is a widening.** security-plan §Security Anti-Patterns → Input requires a product-read path variable to canonicalize and be confined under the data dir (the stated carve-outs are closed and none covers a door); security-plan §Data Protection (At rest → corpus-key lock file) counts exactly three product-written locations outside the data dir and records the shared-temp-dir pre-create residual, which a socket file placed in the temp dir would inherit; security-plan §Input Validation (Console program command line row) says a later command taking a value, a path or an address is a new question each time. Each one the door needs goes to the operator at P4.
- **Call records carry labels and bounds, never content.** security-plan §Logging & Monitoring ("What NEVER to log") bans tool response bodies, OTLP attribute values, query parameter values and full paths; security-plan §Security Anti-Patterns → Logging gives the form of a deliberate record boundary — its own exact allowlist leaf, closed labels and bounded numbers only, field set pinned in both directions. The door's call record takes that form (tool name from a closed set, a bounded outcome label, sizes and counts).
- **The sidecar's removal departs from standing MUSTs, and the plan says so.** security-plan §API Security (MCP feature double-gate row) and security-plan §Security Anti-Patterns → Code Patterns (the sidecar spawn ban) mandate the double gate and the preserved graceful-degrade warning; security-plan §Logging & Monitoring ("What to log") lists the feature-flag mismatch warning. The chunk removes what they guard: its plan names each as a departure for the wrap to amend (the masters are read-only at phase), together with the sidecar-naming statements in security-plan §Threat Model Summary (the MCP stdio vector, the three product binaries, the workspace-key read) and security-plan §Input Validation (MCP stdio and Published workspace key rows, `ANDROMEDA_PULSE_MCP_ENABLED`). Removing the `mcp.*` TauRPC procedures goes through security-plan §API Security (TauRPC capability authorization row): the `EXPECTED_PROCEDURES` pin and the staged bindings change in the same commit. Which of these the code holds today (the procedures, the settings field, a console-engine read of the variable) is research's question.

## Patterns to follow
- The bounded read-back shape of `retrieve_incident_events` — payload never selected, the kind coerced to a closed vocabulary on egress, a fixed row bound, a prepared statement — per security-plan §Input Validation (MCP stdio inputs row) and security-plan §Security Anti-Patterns → Logging (`incident_events` paragraph).
- The one write the door keeps reaches the single guarded status-update choke point, so its lifecycle row is written as for every other status writer, per security-plan §Security Anti-Patterns → Logging (`incident_events` paragraph).
- Existing envelopes only: security-plan §Error Handling (Error format) says no new envelope is invented and names the JSON-RPC 2.0 error object for the tool surface; a door form that departs from it is said to the operator, since the form is a contract with another project.
- Fail-closed directory resolution (trimmed, absolute, canonicalized, a directory, never a fallback) per security-plan §Input Validation (CLI / env var inputs row, corpus-key lock dir) is the precedent if the door's endpoint lives in the per-user runtime dir.
- The engine's one open corpus serves the door in-process; no second key fetch and no cross-process BLOB read is added, per security-plan §Secret Management (Storage → Runtime).

## Anti-patterns to avoid
- NEVER build SQL by interpolating a door argument — prepared statements with placeholders only (security-plan §Security Anti-Patterns → Input).
- NEVER pass a tool argument to a spawned command's argv (security-plan §Security Anti-Patterns → Code Patterns).
- NEVER log a tool response body, a query parameter value or a full path, and NEVER put a path, stack trace, struct name, library version, host name or IP into an error answer (security-plan §Security Anti-Patterns → Logging).

## Contract bindings
- **obs:** the call record's name and exact field set bind to obs-plan's log allowlist and its pin tests; the security side fixes what the record may never carry.
- **tests:** a planted-canary leg over the engine's log family, and the refused-caller leg for P-126, bind to test-plan's harness on claimed ports (never 4317 / 4318); the supply-chain and capability-drift gates are jobs of the one CI workflow.
- **arch:** the door's endpoint, any new variable and any new place on disk bind to architecture §Occupied Resources; the door's connect / call / answer / error form binds to architecture §Standard Contracts (read by Conductor).
- **capability record:** a deleted sidecar test file that a claimed record entry names is re-pointed in the same chunk, or `cargo xtask verify:capability-matrix` reads red.
- **docs:** the user-facing note that tool answers are an indirect prompt-injection surface (security-plan §Logging & Monitoring, hygiene block) names the sidecar's README section; its disposition belongs in the chunk's sidecar list.

## Acceptance criteria contributions
- Every door tool argument deserializes through a serde struct that refuses unknown fields and an unknown tool name is refused; every store read behind a tool is a prepared statement with placeholders; a search of the door's source finds no `format!`-built SQL (per security-plan §Input Validation).
- With a secret-shaped canary sent in telemetry and read back through a door call, the engine's whole log family holds the answer body 0 times, the canary 0 times and no full path, and the call record's field set equals its pinned allowlist leaf in both directions (per security-plan §Security Anti-Patterns → Logging).
- A refused or failed door call answers with a bounded error that carries no path, stack trace, struct name, library version, host name or IP (per security-plan §Error Handling).
- After the sidecar's removal and any dependency the door adds, `cargo audit` and `cargo deny check bans licenses sources` are green with `multiple-versions = "deny"` unrelaxed and no skip or ignore entry left standing for a crate that left the graph (per security-plan §Dependency Security).
