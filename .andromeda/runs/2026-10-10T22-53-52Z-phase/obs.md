# obs extract

## Relevance
relevant — the chunk adds a new inbound boundary inside the engine's process whose call records must be allowlisted, and removes the one surface (the stdio sidecar) that obs-plan's P3 must-trace path, its stderr sink and its double-gate span are written for.

## Constraints
- **One sink, the engine's own.** obs-plan §3 Logging stack requires a single JSON-per-line file sink for the app and no stderr or stdout `tracing` layer; a door inside the engine's process writes its call records to that sink with the default identity fields, and the sidecar's stderr-forced-JSON arrangement described in the same key has no carrier once the sidecar leaves. Whether the door's chosen transport touches stdout or stderr at all is P4's (the boundary dialog), not stated by the plan.
- **Default-deny: the call record needs an EXACT allowlist leaf.** obs-plan §8 PII Scrubbing → Default-deny posture requires every emitted field to be on the per-target allowlist or be redacted, and its leaf entries state that a target without its own exact leaf falls back to the first-`.`-segment key (a wrong field set, silently redacted) or to nothing (all fields redacted). The scope's "call records allowlisted" is this mandate: the door's record target gets its own exact leaf naming every field the emit site emits. Whether the production allowlist today holds a bare key that the door's chosen target name would fall back to (for example a bare `mcp` key, or none) is research's question.
- **Answers are never logged; metadata only.** obs-plan §8 PII Scrubbing → Data classification rules (the MCP response bodies row) requires the record of a tool answer to carry the result type and the result count and never the content. The plan words this for the MCP boundary; the door carries the same data class (stored telemetry, incident text) out of the same stores, so the mandate moves with the tools. obs-plan §1 Obs Scope Summary → Telemetry triggers (Vector 4) adds the negative test shape: call a telemetry tool, then read the log for the absence of the returned content.
- **Every tool call is traced as request → read → response.** obs-plan §4 Span / Trace Coverage → Scenario P3 requires a request span carrying the tool name from the closed tool-name set plus a params count, the per-tool read, and a response span carrying result type and count. The same scenario also requires a `mcp.feature.gate.check` span with the two gate fields; the chunk removes the double gate, so that span and its two fields have no object on the door. The scenario text describes the stdio form (stdin parse, stdout emit); what it reads once the door replaces the sidecar is a master amendment for the wrap, and the plan (P5) should say which span names the door keeps and which leave.
- **A door read of the ring buffer takes its own connection.** obs-plan §10 SLO Invariants & Telemetry Budgets → DuckDB Connection Isolation & Load-Profile Operational Constraints (Reference connection pattern) requires any DuckDB consumer that can run a multi-second statement to hold a dedicated `try_clone()` connection and never the shared appender connection. A door whose tools read the engine's in-memory store is such a consumer; the scope's "every answer is bounded in time" meets the same section's timeout rule (a timed-out blocking query is interrupted explicitly, not merely abandoned). Whether the code path the door would reuse already holds a dedicated read connection is research's question.
- **Query records carry ids and counts, not values.** obs-plan §6 Log Coverage → Boundary-call wrappers (the DuckDB query row) requires `query_id`, `param_count`, `row_count_returned`, `duration_ms` and never the query text or its parameter values. Two plan passages differ on the caller's filter values: §4 Scenario P3 lists `time_range_start`, `time_range_end` and `service_filter` as required span attributes, while §8 PII Scrubbing → Default-deny posture's `mcp-server` field set names only `method`, `result_type`, `result_count`, `feature_flag_enabled`, `duration_ms` (so the filter values would redact). Which one the door's leaf follows is to be stated in the plan; `service_filter` is caller-supplied text, and `feature_flag_enabled` describes a gate that leaves.
- **Refusals and cut answers are logged as boundary errors.** obs-plan §10 SLO Invariants & Telemetry Budgets → Standard+ invariants (Module-boundary error logging) requires every error at a module boundary to be logged at WARN or ERROR with an error category and no full stack trace. On the door that covers a call refused to another account (P-126), a request outside the stores, and an answer cut at its size or time bound: each a record with a closed category label, no caller-supplied text.

## Patterns to follow
- **Exact leaf + a guard where it runs.** obs-plan §8 PII Scrubbing → Default-deny posture gives the standing shape for a new target (its `app.boot.engine` and `app.exit` entries are the nearest precedents): an exact leaf, closed labels and aggregate numerics only, guarded by a test under `pulse-app/tests/` asserting exact-resolve, field-set equality in BOTH directions against the emit site, and a no-fallback discriminator; a guard placed in the library's own test module is stated there as one that never runs.
- **One emission site for all tools.** obs-plan §3 Snapshot / paste-to-AI integration (the MCP tools label) describes every tool emitting its request and response records through a single dispatch site, with the store-read child span belonging to the telemetry tools only. A door that keeps one dispatch site keeps one place to hold the metadata-only rule. Whether the sidecar's dispatch site can be carried into the engine's process or must be rebuilt is research's question.
- **Span naming and kind.** obs-plan §4 Span / Trace Coverage (Span naming convention; Span kind convention) requires `{module}.{operation}` names with no high-cardinality part and `span.kind = "server"` on inbound handlers, tool invocations named among them.
- **A boot-time decision is one closed-label record per boot.** obs-plan §6 Log Coverage → Log levels mapping records each boot posture (which program booted, which seat, which confinement) exactly once per `engine_boot::start`, off any hot path, with closed labels. The door's own boot facts (listening or not, the resolve write switched on or off) fit that shape; a socket path, if one is logged at all, is a basename (see Anti-patterns).
- **Counts fold onto an existing record.** obs-plan §8 PII Scrubbing → Default-deny posture (the `triage.incident.persist` entry) folds per-row outcomes once per cycle onto one record rather than emitting per row. Per-call records at INFO are the stated level for tool calls (obs-plan §6 Log Coverage → Per-module log levels); anything finer than per call (per row returned, per store read) folds.

## Anti-patterns to avoid
- **NEVER log a tool answer's content** — obs-plan §11 Obs Anti-Patterns → Project-specific (the MCP response-bodies ban) and → Logs (Vector 4): metadata only, in the engine's log as it was in the sidecar's stderr.
- **NEVER put caller-supplied or unbounded values in a record's name or labels** — obs-plan §11 Obs Anti-Patterns → Spans / Traces (high-cardinality span names; raw query text; full paths, basename only) and → Metrics (unbounded label cardinality): the tool name is one of a closed set, a rejected unknown method is logged as a closed category and not echoed, a peer's identity is a closed label (owner | other), never an account name.
- **NEVER let the door serve or mix the two surfaces** — obs-plan §11 Obs Anti-Patterns → Project-specific (the external snapshot pipeline versus the self-observation log) and → Universal (no OTel SDK in the self-observation runtime): the door answers from the stores that hold watched services' telemetry; the engine's own JSON log stays a file an agent reads, and the door's own records go to that file by `tracing` alone, never back through an OTLP receiver.

## Contract bindings
- **obs ↔ tests (the engine's graded log).** obs-plan §10 SLO Invariants & Telemetry Budgets → CI gates states that a console engine cycle's log family is graded by `cargo xtask check:engine-log` and `cargo xtask ci-gates` (zero-records, zero-panic), and obs-plan §9 CI Integration → Telemetry artifact handling states that family is uploaded whole as `logs-engine-Linux`. The door's records land in that family. Whether any arm of the engine check reads record targets against a closed set (so a new target would change a verdict) is research's question.
- **obs ↔ tests (heartbeat).** obs-plan §3 Heartbeat ticks names exactly three engine ticks and binds the engine check's `heartbeat-gap` arm to those three. The plan names no tick for a door listener and does not say whether the door's accept loop is a long-running subsystem owing one; adding a fourth tick changes that keyed contract and the arm's read set, so it is a P4 decision, not a mandate extracted here.
- **obs ↔ tests (P3 and the status surface).** obs-plan §1 Obs Scope Summary → Critical paths (the P3 row) takes its source from the tests plan's P3 scenario, which spawns with the double gate and pipes JSON-RPC over stdio; removing the sidecar changes both plans' P3 together. The same key's `health` complementarity (obs-plan §3 Heartbeat ticks) describes the synchronous status read as a TauRPC command the console engine does not carry; whether a status tool stands on the door at this chunk is the scope's open question, owned by a later route entry.
- **obs ↔ security.** The metadata-only rule (obs-plan §8 PII Scrubbing → Data classification rules), the default-deny allowlist (obs-plan §8 PII Scrubbing → Default-deny posture) and the basename-only path rule (obs-plan §11 Obs Anti-Patterns → Logs) are security-plan's logging vectors seen from the obs side; a new socket or on-disk location for the door adds a path the log may name only by basename.
- **obs ↔ arch (trace context).** obs-plan §3 Trace context propagation lists the HTTP, gRPC and TauRPC boundaries and names no door boundary. If the door's call form (the contract another project reads) carries a `traceparent`, that key's pattern is a plain string field on the handler span; the plan does not require the door's form to carry one.
- **Sidecar-standing passages, for the scope's disposition list (masters are the wrap's to amend).** Each describes something whose object leaves with the sidecar or the double gate: obs-plan §1 Obs Scope Summary (the mcp-server entity row; the P3 critical-path row); §3 Logging stack (the sidecar's stderr sink); §3 Snapshot / paste-to-AI integration (the MCP tools label); §4 Span / Trace Coverage (the MCP stdio surface row; Scenario P3; Scenario P7's `app.boot.workspace_key`, described as a publish for the sidecar); §6 Log Coverage (the `mcp.gate.check` WARN example; the `mcp-server` level row; the MCP stderr sink line); §8 PII Scrubbing → Default-deny posture (the `mcp-server` field set; `reconciled_count` on `triage.incident.persist`, defined as rows resolved by a writer outside the process, which is the sidecar); §11 Obs Anti-Patterns → Universal (the stdout ban for the sidecar) and → Project-specific (the double-gate ban). Whether the `app.boot.workspace_key` producer and the `reconciled_count` field leave here or with a later entry is research's question; the plan gives no answer.

## Acceptance criteria contributions
- Each door call leaves its record in the engine's log file under a target that resolves to its own exact allowlist leaf, the leaf's field set equal to the emit site's in both directions and no field redacted on a real call; a committed guard under `pulse-app/tests/` pins exact-resolve, set equality and the no-fallback discriminator (per obs-plan §8 PII Scrubbing → Default-deny posture)
- After a door call that returns stored telemetry holding a planted canary value, the engine's log family holds 0 occurrences of the canary, and the call's record carries the tool name, result type and result count only (per obs-plan §1 Obs Scope Summary → Telemetry triggers, Vector 4)
- A call refused to another account, a request outside the stores, and an answer cut at its bound each leave one WARN or ERROR record with a closed category label, no path beyond a basename and no caller-supplied text (per obs-plan §10 SLO Invariants & Telemetry Budgets → Standard+ invariants, Module-boundary error logging)
- A console engine cycle with the door built in and nothing calling it still reads PASS on `cargo xtask check:engine-log` and green on `cargo xtask ci-gates`, and its log holds no door call record — an obs-side reading usable as the check for the scope's "no reader at the door" sentence (per obs-plan §10 SLO Invariants & Telemetry Budgets → CI gates)
