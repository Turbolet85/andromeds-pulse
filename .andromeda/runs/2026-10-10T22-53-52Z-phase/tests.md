## Patterns to follow
- Witness the door on a real process, not in process alone: a `pulse-app/tests/integration_*.rs` arm that spawns the built `andromeda-pulse-engine run` under a cleared environment, its own TempDir data dir and claimed ports, reads readiness from accepting endpoints and awaits records by target under a bound, ends it by signal and reads the log family after the end; the `xtask/tests/` sibling is the form for anything the committed script or a built verb must do against the door (per test-plan §3 Per-chunk gate discipline → Spawned-program witness form). Each new arm is read red before green.
- Each refusal the door owes is a negative test paired with its positive arm, and the pair is what discriminates: owner answered beside another caller refused, a store read answered beside a request for the token / a configuration secret / a file outside the stores refused, an in-bound answer beside one cut at the size bound and one cut at the time bound, the resolve write applied beside the write switched off (per test-plan §1 Test Scope Summary → Coverage scope, the "OTLP anti-patterns rejection" and "Loopback-only OTLP binding" rows, and → Coverage triggers, the `MCP feature + runtime gating` row's two-sided shape). Whether a second account can be driven by an agent on the dev host and on the runner is research's question; where it cannot, the plan's preamble requires the surface be flagged untestable and handled by a boundary test, never by a manual check.
- Tool answers are asserted on CONTENT over rows the test itself sent through the live receiver, in both arms of a write (applied and guard-declined), with planted-canary absence read on stderr and on the file sink, and the call record asserted to carry metadata only, never the response body (per test-plan §1 Test Scope Summary → Pending coverage triggers, rows `mcp-incident-read-back-cross-process-coverage` and `security-vector-coverage: MCP response body redaction`). A `tools/list`-style name assertion is not a content guard.
- Test placement and data follow the standing forms: `pulse-app` probes live in `pulse-app/tests/*.rs` against `pub` + `#[doc(hidden)]` surfaces (the lib-source ratchet is a flat zero), library-crate units are co-located, telemetry comes from the `test_support::otlp` factories, and a narrowed `pulse-app` run is selected with `-E` under `--workspace`, not `-p` (per test-plan §2 Test Strategy → Test directory + naming conventions; §7 Test Data & Fixtures → Self-bootstrapping requirement; §3 5-command implementation → `run`). `test-support` is a dev-dependency of `buffer`, `pulse-app` and `xtask` only, held by the `test_support_edges` pins, so a door crate of its own taking the factories is a new edge the plan must state.
- A production call site that must USE a guard or a shared instance gets a committed assertion over the production composition, mutation-checked, not a one-time live reading: the plan's open wiring rows are the class to avoid adding to (per test-plan §1 Test Scope Summary → Pending coverage triggers, rows `viz-read-connection-router-wiring-coverage`, `l4-path-guard-callsite-wiring-coverage`, `discovery-observer-wiring-coverage`). For this chunk that is the door reading the stores `engine_boot::start` built (not a database of its own) and the owner check sitting on the path every call takes.

## Anti-patterns to avoid
- NEVER synchronise with `sleep(N)` or accept a readiness that is only "a port accepts": wait on an explicit signal, and read whose listener answered (per test-plan §11 Test Anti-Patterns → E2E; §3 5-command implementation → `boot` Readiness signal, the `foreign` reading).
- NEVER over-mock at the integration tier or mock the store under test: a door test that reads a stubbed store, or seeds by a pre-baked database instead of OTLP ingest or the factories, proves nothing about "tools read the engine's stores" (per test-plan §11 Test Anti-Patterns → Test Strategy, → Integration, → Test Data).
- NEVER leave a manual step, a retry, or an unowned `#[ignore]` standing for a refusal that is hard to drive (the other-account case), and NEVER let a test's output or a kept artifact carry a secret or raw payload (per test-plan §11 Test Anti-Patterns → Universal (agent-driven specific), → Quality).

## Contract bindings
- tests ↔ obs (log format and harness grading): the door's call records land in the engine's own `agent-latest.jsonl*` family, which `cargo xtask check:engine-log` and `cargo xtask ci-gates` grade — an ERROR record or a panic record in the family fails the cycle, so a refused call must not be logged at ERROR unless the plan intends the cycle red; the record's target must be on the obs allowlist (obs-plan §3) with a `pulse-app/tests/unit_observability_allowlist_*.rs`-form pin (per test-plan §3 Log format; §3 Per-chunk gate discipline → Engine cycle gate form; §9 CI Integration → Pipeline structure, Boot smoke row).
- tests ↔ obs / arch (the 5-command discipline): the set admits no sixth verb, the `status` and `harness:ready` verdict objects are member-pinned by set equality, and the "Status endpoint shape" is the TauRPC `health` payload reached only through IPC — which the console engine does not have (per test-plan §3 5-command implementation → `boot`, → `status`; §3 Status endpoint shape). Moving the harness or the status verb onto the door therefore changes pinned contracts whose full text is architecture §Occupied Resources → xtask CLI surfaces; the scope leaves that move to P3 / the later entries, and the plan must say which.
- tests ↔ security (harness boundary classes): the engine-cycle and pre-push child sets, the 24317 / 24318 binding and the witness arm are classified in security-plan §Security Anti-Patterns → Input, several PROVISIONAL; a door endpoint that a test or a harness verb opens or dials is a new member of that reading and goes to the P4 dialog (per test-plan §3 Per-chunk gate discipline, the `pre-push:linux` entry). The supply-chain gates run in the same workflow: dropping the sidecar's dependencies must leave `cargo deny check bans licenses sources` and `cargo audit` green (per test-plan §9 CI Integration → Pipeline structure, Supply chain row).
- tests ↔ arch (capability record): the record's form is a contract with another project (architecture §Standard Contracts) and its gate reads the working route (per test-plan §9 CI Integration → Capability verification matrix).
- tests ↔ a11y: none unless the removal of the window's sidecar settings touches `pulse-app/ui/**`; then the three webview gates join the gate set and the `a11y` job's zero-new-tuple diff applies (per test-plan §3 Per-chunk gate discipline, the webview-gates paragraph; §9 CI Integration → Pipeline structure, A11y suite row).
