# arch extract

## Relevance
relevant — the chunk adds an engine part and a new outward surface, and removes a registered binary, feature gate, IPC namespace and CI job; architecture.md holds NO section for the door's own transport or outward form (its only outward read surface on record is the stdio sidecar), so the door's form is a new decision, not an extraction.

## Constraints
- **Wired by the shared boot, never by an entry point.** architecture §Design Philosophy (Single-process modular monolith) requires every engine part to be wired by `pulse_app::engine_boot` (`init_process`, then `start`), neither entry point wiring a part itself, and the shared boot and the console module naming no window framework (the pin it names: `pulse-app/tests/unit_engine_boot_seam.rs`). A door "inside the engine's process" is an engine part under that rule. Both programs call the one boot, so whether the window app also gets a door follows from where the plan seats it — a P4 question, not settled by the plan section.
- **A third listening socket departs from the registered port state.** architecture §Occupied Resources → Network ports requires that both engine programs bind the two OTLP receivers "and nothing else", that the bind address is not configurable (the boot builds the loopback address itself from a validated port), and it names a spawned-engine test that reads the process's socket list as exactly those two. Any door endpoint that listens (TCP or Unix-domain) changes that row and the test it names; the row is amended at wrap. Whether that test's `/proc` reading counts a Unix-domain socket is research's question.
- **The locked MCP decisions name the transport this chunk removes.** architecture §Established Decisions [MCP Server Surface] and [API Style — MCP Server Surface 3] lock JSON-RPC 2.0 over stdio, hand-rolled, MCP-spec exactly and never a custom envelope, nine tools through one `dispatch_tool` site, behind `--features mcp-server`. No decision covers a non-stdio door. The door's transport and envelope therefore supersede a locked decision: it goes to the operator at P4 and the decision is amended at wrap, not assumed from this plan.
- **The one write stays behind the corpus write guard.** architecture §Established Decisions [Corpus Write Arbitration] requires every incident status write to traverse the guarded `CorpusWriter::update_incident_status` and to read a stale write as `DeclinedStale`, an outcome and not an error; it records the sidecar as the seventh writer, the only one bypassing `IncidentPersistence`, and a persist-cycle reconcile step built for that external resolve. The plan states which path the in-process door's resolve takes (the registry/trait path or the corpus directly) and what the reconcile step still serves once no second process writes; whether the code's reconcile depends on a cross-process writer is research's question.
- **Dependency direction and the reserved crate list.** architecture §Cross-cutting Patterns → Module dependency direction requires edges to flow toward `pulse-app`, no library crate depending on the binary crate, no sibling edge a declared contract does not require, and one DAG rooted at `pulse-app`. architecture §Occupied Resources → Cargo workspace crate names reserves seventeen names, `mcp-server` among them, and is the canonical list every count word defers to: removing, keeping or renaming that crate, or adding one for the door, changes that list and each count that cites it.
- **Every new place, name and switch is a registered resource.** architecture §Occupied Resources → Filesystem locations fixes the data-dir subpaths and counts exactly THREE product-written locations outside the data dir; a socket file outside the data dir would be a fourth. architecture §Occupied Resources → Environment variables is the reserved `ANDROMEDA_PULSE_*` list; a variable that enables the door or switches its write off is a new entry there, under the precedence of architecture §Cross-cutting Patterns → Config management.
- **The sidecar's footprint in the plan is the disposition list's floor.** Each of these names the sidecar or its gate and needs a stated disposition (removed here, or the later entry and why): architecture §Occupied Resources → MCP stdio surface · → Process / service identity (three product binaries, `andromeda-pulse-mcp`) · → Tauri IPC routes (`mcp.status` / `mcp.start` / `mcp.stop`) · → Environment variables (`ANDROMEDA_PULSE_MCP_ENABLED`) · → Filesystem locations (`run/workspace-key`, published for the sidecar; the corpus-key lock file's third writer) · → xtask CLI surfaces (`smoke:external-resolve`, which drives a real sidecar subprocess); architecture §Standard Contracts (`ready` → `mcp_server_enabled`, `app_info` → `features`, MCP server — spec-conformant); architecture §Cross-cutting Patterns → Feature-gate hygiene and → Tray icon policy; architecture §Infrastructure Patterns → Deployment model, → CI/CD approach (the `mcp-test` job and `boot`'s `--features mcp-server` release build, one of two pinned release-build witnesses) and → Project directory structure. Which of these the code still holds is research's question.

## Patterns to follow
- Loopback endpoint built by the boot from a validated value, a rejected value recorded as a failed bind and nothing started, the rest of the engine going on (per architecture §Occupied Resources → Network ports; ports as `u16` through `TryFrom` per architecture §Conventions → Configuration units).
- Read-back in tests: inject over real OTLP to the bound receiver, no in-process bypass and no test-only ingest path; a console-engine test reads from the spawned program's own surface or from the `EngineHandles` the boot returns (per architecture §Cross-cutting Patterns → Test-time telemetry injection), on ports claimed from the test range, never 4317 / 4318 (per architecture §Occupied Resources → Network ports).
- Bounded, closed-vocabulary answers as the existing tool contract shows them: a stated row limit with a `truncated` flag, a closed kind set coerced on egress, an encrypted payload column never selected (per architecture §Standard Contracts → MCP server — spec-conformant); response types `serde::Serialize` (per architecture §Cross-cutting Patterns → Cross-bridge data shape); the internal `seq` ordinal never in a response (per architecture §Conventions → Primary key convention).
- The console program's closed command line (`run` | `version`, anything else exit 2, nothing created): the door comes up under `run`; a new command word for a door client is a change of that registered grammar and is said as one (per architecture §Occupied Resources → Process / service identity → Console engine binary).
- Any new or changed `cargo xtask` verb is registered as a formalized CLI contract — exit codes, closed labels, members pinned by set equality, no path and no environment value in the verdict (per architecture §Occupied Resources → xtask CLI surfaces).

## Anti-patterns to avoid
- A store of the door's own: the telemetry the engine holds is the one in-memory `pulse_buffer` connection and the one `corpus/corpus.db` connection (per architecture §Occupied Resources → DuckDB database / schema names and → Corpus SQLite database / schema names); a door that opens a second database or connection of its own repeats the defect the scope names.
- Wiring the door in `main.rs`, `console.rs` or the binary's `main`, or naming a window framework from the code that starts it (per architecture §Design Philosophy).
- A bind address a caller or a variable can choose, or any non-loopback endpoint (per architecture §Occupied Resources → Network ports); and a library-to-binary or undeclared sibling edge taken to reach the stores (per architecture §Cross-cutting Patterns → Module dependency direction).

## Contract bindings
- **arch ↔ security:** the listening endpoint, its place on disk, its mode and owner check, and any new variable are registered by arch (§Occupied Resources) and classified by security-plan (boundary widening, path rule, owner-only); arch records no enforcement mechanism for "owner only".
- **arch ↔ obs:** arch names the boot and bind records readiness reads (`app.boot.engine`, the two `app.boot.otlp.*.bind` targets, §Occupied Resources → xtask CLI surfaces); the door's call record and any door bind record, and their allowlist leaves, are obs-plan's.
- **arch ↔ tests:** the pins arch names move with this chunk — the socket-list test in `integration_console_engine.rs`, `unit_engine_boot_seam.rs`, the workflow self-lint pins on the release-build witnesses and the job set (§Infrastructure Patterns → CI/CD approach), and the `EXPECTED_PROCEDURES` / staged-bindings gate when the `mcp.*` procedures leave (§Cross-cutting Patterns → Webview IPC capability policy).
- **arch ↔ another project (Conductor):** §Standard Contracts holds the capability record's form as a contract another repository reads; it holds no contract for the door. The door's outward form (how a reader connects, a call, an answer, an error) is a new Standard Contract entry, written at wrap; a P-040 change in the record keeps the three fields' form (§Standard Contracts → Capability record).
- **arch ↔ design:** the tray menu's MCP toggle and the window settings that enable the sidecar (§Cross-cutting Patterns → Tray icon policy) are design-owned surfaces the removal touches.

## Acceptance criteria contributions
- (arch) The door is started from `engine_boot::start`; neither entry point wires it and the boot-seam pin stays green (per architecture §Design Philosophy).
- (arch) A spawned console engine's listening endpoints are exactly the two OTLP receivers plus the door's one stated endpoint, none off the engine's own host, and the test arch names for the socket list asserts that set (per architecture §Occupied Resources → Network ports).
- (arch) The door's resolve write goes through the guarded status update, and a write older than the stored row reads declined, not failed (per architecture §Established Decisions [Corpus Write Arbitration]).
- (arch) Every plan row that names the sidecar, its binary, its feature flag, its runtime variable or its `mcp.*` procedures has a disposition in the chunk's plan, and the workspace graph is still one DAG rooted at `pulse-app` with no library-to-binary edge (per architecture §Occupied Resources → Process / service identity; per architecture §Cross-cutting Patterns → Module dependency direction).
