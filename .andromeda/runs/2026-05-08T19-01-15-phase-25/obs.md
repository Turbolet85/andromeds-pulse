## Patterns к follow

- Frontend → backend instrumentation flows uniformly via TauRPC `telemetry.frontend.record_*` commands → backend `tracing::info!(target: "metric.{name}", ...)` events → single JSON log file at `~/.andromeda-pulse/logs/agent-latest.jsonl` (per obs-plan §3 Frontend bridge + §12 Decisions Log "Frontend instrumentation"). Chunk #28 establishes `record_frame_ms`; later Epoch 5 chunks (#29 compute aggregation, #31 Halo Pulse) extend the same pattern (e.g., `record_compute_ms`, `record_halo_phase_ms` if needed).
- Span-naming convention `{module}.{operation}` applies: chunk #28 introduces `app.boot.gpu.check` (startup adapter probe), `webgpu.canvas.render` (per-frame render span — use sparingly; gate at `trace`), and the metric target `metric.webgpu.frame_duration_ms` (per obs-plan §2 Naming conventions + §4 P1 must-trace span list).
- Default subscriber fields (`service.name = com.andromeda.pulse`, `service.version = env!("CARGO_PKG_VERSION")`, `deployment.environment = production`) attach automatically to every `tracing` event via `Layer::with_default_fields(...)` — chunk #28's `record_frame_ms` resolver does NOT need to repeat these (per obs-plan §3 Service identity + §2 Default subscriber fields).
- Frontend-bridge resolver pattern matches chunk #25/#26 IPC boundary discipline: every TauRPC procedure emits a `tracing::info!(target: "ui-bridge.{procedure}", method_name, result_type, ...)` boundary event; for frontend telemetry resolvers, the boundary log is the metric event itself with `metric.*` target (per obs-plan §6 Boundary-call wrappers TauRPC invocation row + chunk #26 ui-bridge.* AllowList entries pattern).
- AllowList::production() in `pulse-app/src/observability.rs` MUST gain a new entry `metric.webgpu.frame_duration_ms` (and `app.boot.gpu.check`) when chunk #28's frontend-telemetry resolver lands, mirroring chunk #26's per-leaf-entry discipline (so each metric target wins exact-match resolution over `split('.').next()` fallback) (per obs-plan §8 Whitelist per module — `viz` allowlist + chunk #26 session-handoff convention).

## Anti-patterns к avoid

- NEVER instrument the per-frame inner render loop at `info` level — frame rate ≥30 fps means ≥30 events/sec just from frame-loop entry; this both spams the JSON file and violates §11 Logs anti-pattern "NEVER log in hot path at `info` level". Per-frame timing rides the `metric.webgpu.frame_duration_ms` event ONCE per frame as the sampled metric, NOT additional `info!` boundary spans.
- NEVER include raw OTLP attribute values, span/log/metric content payloads, or DuckDB query parameter values in WebGPU-related spans — even though chunk #28 substrate doesn't query DuckDB directly, downstream Epoch 5 chunks (#29 compute aggregation, #34 trace timeline) will read query results, and the chunk #28 substrate spans MUST not pre-introduce a leakage path (per obs-plan §11 Spans anti-pattern Vector 1, 5 + §8 Default-deny posture).
- NEVER link a browser OTel SDK (e.g., `@opentelemetry/sdk-trace-web`, `@opentelemetry/exporter-otlp-http`) into the React webview to "automatically" instrument WebGPU — this re-introduces the recursion concern this project chose to avoid by construction. All frontend telemetry flows through TauRPC bridge only (per obs-plan §11 Universal anti-pattern + §12 Decisions Log "Frontend instrumentation").
