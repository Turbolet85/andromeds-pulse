## Project signals (from arch + input)

- **Product type:** As arch §Project Intent records it today: a "cross-platform desktop application (Windows / macOS / Linux) shipped as native bundles. Not a web app, not a CLI", a modular monolith of "twelve Rust crates wired into one Tauri binary". That is the 0.3.0 system. This version's intent retires the desktop shell (P-083) and expects a console program on a Linux server (P-086); arch keeps the 0.3.0 wording until the chunk that removes each thing wraps.
- **Surfaces in current scope:** Four surfaces this version builds or re-bases, all named by requirements and none by arch §Project Intent: the OTLP receiver reached over a network behind a token (P-087, P-088); the agent's door inside the engine's process (P-092, P-093); the store on disk (P-091); the status command a desktop panel shows, with a system notification (P-099). Retired, and therefore given no surface epoch: the window — compact widget, full dashboard, tray, the floating findings and report windows (P-083); the stdio sidecar as a separate process is replaced by the in-process door (P-092).
- **Crates / modules:** 16 workspace members (arch §Occupied Resources → Cargo workspace crate names: 14 library crates + `pulse-app` + `xtask`). Which of them leave with the window or the model is the removal chunks' work, not a calibration input.
- **Capabilities (Established Decisions count):** 29 entries in arch §Established Decisions. This version's own capability count is 21 (P-083…P-103): 3 removals, 16 findings that add or change, 1 end-to-end scenario, 1 absorbed residual.
- **Standard Contracts:** 7 in arch §Standard Contracts (three Tauri IPC envelopes — `app_info` / `health` / `ready`; the OTLP receiver; the MCP server; the paginated-list envelope; the real-time push contract). Four of the seven are contracts of the window's IPC bridge.
- **Cross-cutting concerns:** 10 in arch §Cross-cutting Patterns. Four are policies of the window (OS notification policy, tray icon policy, webview IPC capability policy, cross-bridge data shape).
- **Security tier (cross-input):** Minimal — security-plan §Threat Model Summary (as the project's CLAUDE.md states it: local-first, loopback-only OTLP, no auth model). The tier rests on the loopback boundary that P-087 replaces with a token over an encrypted channel; the tier itself is the security master's to restate at the wrap of the chunk that changes it.
- **Project signals from input.md:** The 0.1.0 creator brief: a desktop glance-widget, GPU-accelerated charts, a one-click snapshot. Its primary surface is what this version retires. It lists persistent storage, multi-host collection and alerting as "out of v1 scope … a separate scope" — the three things 0.4.0 takes up. It carries no signal that widens 0.4.0 beyond the authored intent.
- **Existing Scopes:** `pulse-v0_2_0-route` (arch §Existing Scopes; the v0.2.0 evolution scope, closed work). No scope is minted for this version.

## Calibration outcome

- **Hierarchy depth:** 2 levels (epoch → chunks), with a sub-block tier inside the denser epochs for decomposition only.
- **Reasoning:** Four new or re-based surfaces against 16 existing workspace members and 21 capabilities that arrive already grouped into six themes by the intent puts the version in the band where an epoch per theme holds 3–7 leaves; a third persistent level would be an artificial tier, so findings serve as sub-blocks during decomposition and are dropped at linearization.

### Adjustments applied (optional)

- **The mid epochs are shaped from this version's requirements, not from the surfaces arch §Project Intent names.** `phase-0/calibration.md` derives mid epochs from arch's product-type surfaces and gives `requirements.md` an epoch-shaping role for an adopted project only; this project is greenfield-born, and its arch still names a desktop application. Following that letter would produce a "Desktop primary surface" epoch for a surface P-083 retires. On the operator's directive for this run, each mid epoch is named for the requirement ids it delivers — the shape the pipeline's last next-version outline on a greenfield-born project took (`conductor/.andromeda/runs/2026-09-11T06-27-07-route/complexity-outline.md`, five epochs, each named for its requirement ids; re-read for this run).
- **The retired surfaces get no surface epoch; their retirement is work inside the epochs the requirements shape.** The window (P-083), the local model (P-084) and the corpus's encryption at rest (P-085) are retired in Epoch 2, each by chunks whose titles name what they retire. No epoch installs, extends or polishes any of the three.
- **+1 epoch over the six themes:** the intent's Theme 0 ("what leaves") and the base the removals stand on (a headless entry point, a reachable end-to-end gate, CI and the pre-push check on Linux) would make one Foundation epoch of nine chunks, half again the median; it is split into Epoch 1 (the base) and Epoch 2 (the removals), which also keeps what replaces a surface ahead of the chunk that removes it.
- **No tier bump.** The security tier is recorded Minimal, not Hardened; arch carries no v2/v3 deferred-feature markers for this version; the target is one Linux node, not multi-platform native; input.md's rigor signals are the 0.1.0 brief's. The network receiver (P-087, P-088) and the door's admission (P-093) raise security weight inside Epochs 3 and 4 as concerns, not as an added level.

## Epoch outline (8 epochs)

### Epoch 1 — Foundation: a headless engine and its gates on Linux (P-086, P-103)

- **Scope:** The base every removal and every later theme stands on — the engine starts as a console program beside the window that still exists, an end-to-end gate reaches it in CI, and the build's checks run on Linux.
- **Drilldown depth:** 1
- **Estimated chunks:** 3
- **Concerns:**
  - A console entry point that boots ingest, the buffer, the detectors and the corpus with no display or desktop session, driven by commands (P-086; arch §Established Decisions [Platform] is what it replaces).
  - The reachability of the engine's own end-to-end gate: CI boots the headless engine, sends it OTLP, reads a finding back, to a recorded green verdict — the gate that grows with every later chunk, reached before the window's boot smoke is retired (P-086; `phase-1/synthesis-protocol.md` §Placement).
  - The local pre-push check and the base CI on Linux, over the stages that survive (P-103; intent §8 "every later chunk builds and tests on Linux alone").

### Epoch 2 — What leaves: the window, the local model, the corpus's encryption (P-083, P-084, P-085)

- **Scope:** The three ruled removals, each preceded by what replaces it and followed by a proof that detection still holds without it.
- **Drilldown depth:** 2
- **Estimated chunks:** 6
- **Concerns:**
  - The gates whose only subject is the window: the accessibility and boot-smoke CI jobs, the webview suite, the headful self-verify and the integration UX end-to-end, the bindings and capability gates, the npm channel gate, the desktop bundles (P-083).
  - The window itself: the Tauri shell, the webview interface, the IPC bridge, the capability files; no crate depends on the window toolkit; three masters whose whole subject it is (P-083).
  - An incident formed and worded from the engine's own facts with no model in its path — what must exist before the model leaves (P-084, a first slice of P-099).
  - The local model: the inference runtime, its grammar, its hardware probe, its deterministic stand-in, the decision probe and the latency grader; no gate needs a GPU (P-084).
  - The corpus's cell encryption and its credential-store key; the scrubber unchanged; the decision dated and marked to be looked at again (P-085).
  - Everything 0.3.0 detected is still detected once the three are gone (P-086's second clause; 0.3.0's P-074 and P-077 must still hold).

### Epoch 3 — The engine stands on its own node (P-087, P-088, P-089, P-090)

- **Scope:** Telemetry arrives from another host behind a token over an encrypted channel, the watcher reasons by event time, and the node's size is measured.
- **Drilldown depth:** 2
- **Estimated chunks:** 6
- **Concerns:**
  - The network receiver: a token, an encrypted channel, the loopback-only boundary it replaces (P-087).
  - What the receiver refuses: refusal before the body is read, recorded without the token's value; the token's life by engine command; a per-sender rate; plaintext from another host refused; the existing invariants and the scrubber applied to a remote sender (P-088 — controls proposed for the founder's review).
  - Event time in every check, with a stated lateness allowance (P-089).
  - A recorded stream played again gives the same result (P-089).
  - The 1 GB figure measured under a long run (P-090; its on-disk half waits for P-091's store).
  - The theme's check by the external harness, input to output (intent §6, P-102).

### Epoch 4 — Memory on disk and a working door (P-091, P-092, P-093)

- **Scope:** What was received survives a restart and is kept for days, and an agent reads the real data through a door inside the engine's process.
- **Drilldown depth:** 2
- **Estimated chunks:** 7
- **Concerns:**
  - Raw telemetry on disk for days, bounded in size under constant insert and delete — replacing the in-memory ring buffer (P-091, P-090).
  - What the watcher has learned survives a restart; a gap while the engine was down is not the service's silence (P-091).
  - The door inside the engine's process, reading the store the engine holds — replacing the sidecar that read its own empty database (P-092).
  - The door's questions: service, time range, trace and text filters, aggregates (P-092).
  - One incident whole, with its evidence (P-092; the empty span and timestamp evidence of `.andromeda/residuals.md:11`).
  - Who the door answers and what it may do: admission, store-only reads, bounded answers, the one write named and switchable (P-093 — controls proposed for the founder's review).
  - The theme's check by the external harness (intent §6, P-102).

### Epoch 5 — Keep what OpenTelemetry sends (P-094, P-095)

- **Scope:** The stored record keeps the meaning the sender gave it — for spans, metrics and logs.
- **Drilldown depth:** 2
- **Estimated chunks:** 6
- **Concerns:**
  - A span's name, kind, parent and status message; the service's version and environment (P-094).
  - The attributes that say which route, status code, database or peer — under both generations of the semantic-convention names, scrubbed before they are stored (P-094, P-088's last clause).
  - Who calls whom, answered from what is stored (P-094).
  - Histogram-family metrics stored so a percentile can be computed (P-095).
  - A log line and a metric point name their service; exception type, message and stack readable through the door (P-095).
  - The theme's check by the external harness (intent §6, P-102).

### Epoch 6 — Comparisons that work from the first minute (P-096, P-097, P-098)

- **Scope:** Findings that need no learned baseline: a new kind of error, a release against the one before, and silence told apart from an engine that received nothing.
- **Drilldown depth:** 1
- **Estimated chunks:** 5
- **Concerns:**
  - The first appearance of an error fingerprint for a service, and the return of one that had gone away (P-096).
  - A new version of a service is noticed, with the moment it appeared (P-097).
  - The new version compared with the previous one — error rate, new error kinds, latency (P-097).
  - Three states told apart — the service went quiet, no data reached the engine, the check could not be evaluated — and a recovery announced (P-098).
  - The theme's check by the external harness (intent §6, P-102).

### Epoch 7 — The voice (P-099, P-100)

- **Scope:** The engine says what it found — in one line a desktop panel shows, in a system notification, and in a report narrow enough for a large model to work from.
- **Drilldown depth:** 2
- **Estimated chunks:** 6
- **Concerns:**
  - The short report written without a model: what, where, since when, after which version, which errors are new (P-099).
  - The current state in one line from an engine command, shown by a panel module on the founder's desktop (P-099, ruled).
  - A system notification on a change of state, carrying the short report (P-099).
  - The report names its evidence by identifier; "not enough data" is an answer the engine can give (P-100).
  - A large model, given the report and the door, names the planted cause — measured (P-100).
  - The theme's check by the external harness (intent §6, P-102).

### Epoch 8 — Polish & ship (P-101, P-102)

- **Scope:** The version's one end-to-end scenario, a real service watched for days, and the close.
- **Drilldown depth:** 1
- **Estimated chunks:** 3
- **Concerns:**
  - One real service of the founder's watched for days, the engine's reports and silences read against what happened (P-101; the founder names the service before it is taken up).
  - The bad-version scenario end to end: Conductor, over the network, an engine on another host, a 1 GB node, silent through the healthy hours (P-102).
  - The version close: every capability verified or deferred on a measured basis, the full gate green on Linux.

## Notes for Phase 1 synthesis

- **What replaces a surface is reachable before the chunk that removes it** (the operator's hypothesis, his to review at Phase 4). The headless entry point and the engine's end-to-end gate (Epoch 1) precede the window's gates and the window (Epoch 2); an incident worded from the engine's own facts precedes the local model's removal (Epoch 2). The intent's §8 asks that the route's first entries remove the window and the local model so that every later chunk builds and tests on Linux alone: both removals sit in the first two epochs, ahead of every theme.
- **A gate retires before the surface it tests, in its own chunk.** A chunk that removed the webview while the accessibility and boot-smoke jobs still ran would leave CI red between two chunks; the window's gates therefore retire first, as stated work with a title that names them.
- **P-090 cannot be fully proven inside Theme 1.** Its OBSERVED clause is that memory "with a database on disk" has never been measured, and the store reaches disk in Epoch 4 (P-091). Epoch 3 carries the measurement and its first figure; Epoch 4's on-disk store chunk carries the bounded-growth proof; the scenario in Epoch 8 runs on the 1 GB node. The intent's theme order is kept; the capability's claiming chunk is the later one.
- **P-099 is advanced twice.** Epoch 2 needs an incident worded from the engine's own facts before the model can leave; the full short report (after which version, which errors are new) needs Epochs 5 and 6 and lands in Epoch 7, which claims the capability.
- **The six plans describe what this version retires.** In Phase 1 they are cited only where a chunk retires or replaces what they describe; the bootstrap merging map yields no chunk for a retired surface. Every chunk cites a requirement id plus the master section it builds on or retires.
- **A validator sees only the draft, its focus guide and its plan.** Each retirement must therefore be legible in the chunk's own title, inside the 25-word form.
- **The theme checks are Pulse-side entries of a paired advance.** Conductor's own work is in its repository; each check entry here is where its reading is received and recorded. Live legs are operator-gated; the ports 4317/4318 on the dev host are shared with the Conductor builder.
- **P-101 waits on the founder's word** (which real service). Its entry says so in its own text.
