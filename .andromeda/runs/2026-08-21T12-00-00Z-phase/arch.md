## Relevance
Relevant — instrumentation lands in reserved workspace crates and may add a TauRPC surface, so workspace placement, IPC procedure shape, capability registration, and self-observation discipline all apply.

## Constraints
- Emit sites must live in already-reserved workspace crates (`pulse-app`, `crates/ui-bridge`); the crate-name list is reserved at workspace level and cannot be reused or repurposed, and first-party features are added as new routers/methods **inside** an existing crate when they are not a new module (per architecture.md §Occupied Resources → Cargo workspace crate names, §Project Intent → How new functionality is added).
- Any new TauRPC procedure must use one of the two authorized shapes — `<router>.<verb>` dotted `snake_case` for per-crate routers — and must return `Result<T, AppError>` using the stable `AppError` variants (`Validation { field, reason }` for a rejected input, never a bespoke error type) (per architecture.md §Conventions → Endpoint naming + Error response schema (Tauri IPC); §Inherited Defaults → API style — internal IPC).
- §Cross-cutting Patterns → Webview IPC capability policy requires that adding a new TauRPC procedure carry **both** a router registration in the owning crate **and** an entry under `pulse-app/capabilities/`, or the bridge call is silently rejected at runtime. This is the arch-side statement of scope premise 2; whether a new *method* on the already-granted `telemetry.frontend` router is already covered by the existing `pulse:default` grant is research's question, not something this plan attests.
- The new timing observables must be emitted through the self-observation stack only — `opentelemetry-stdout` / file exporter under the resolved `logs/` subpath — and must never be routed as OTLP back into the product's own `:4317`/`:4318` (per architecture.md §Established Decisions → [Self-Observation]; §Cross-cutting Patterns → Self-observation discipline).
- Input validation for any new bridge method uses `serde` + smart enum types + `TryFrom` only — no validation library is in the stack (per architecture.md §Established Decisions → [Validation Library]; §Stack and Technologies → Validation). This bears directly on scope premise 3's "one parameterized procedure carrying a bounded enum discriminant".
- Module dependency direction is a DAG rooted at `pulse-app`: no library crate may depend on the binary crate, and no library crate may take a sibling dep unless its declared contract requires it (per architecture.md §Cross-cutting Patterns → Module dependency direction). A `crates/ui-bridge`-side mark therefore cannot reach into `pulse-app` for a start instant.
- Any type crossing the TauRPC bridge must be `serde::Serialize`, and the frontend consumes **only** TauRPC-generated `.ts` bindings — no manual TypeScript re-declaration of a command signature (per architecture.md §Cross-cutting Patterns → Cross-bridge data shape; §Conventions → Workspace API style).

## Patterns to follow
- Extend an already-registered namespace rather than mint a new one: `telemetry.frontend.record_frame_ms` is the registered frontend→backend telemetry procedure in architecture.md §Occupied Resources → Tauri IPC routes, and the plan's registry is canonical for the enumeration while §Conventions defines only the shape.
- The "add fields/methods to an existing procedure, then amend the envelope" precedent — the `ready` envelope gained three checks with no new procedure, namespace, or capability (architecture-amendments.md 2026-07-07), which is the cheapest registered path if the design fork lands on reusing an existing surface.
- Crate template shape: a public contract module as the only `pub` surface, `pub(crate)` internals, `thiserror`-derived error enum, TauRPC-router module mounted by `pulse-app` (per architecture.md §Project Intent → Template patterns; §Conventions → Module visibility discipline).
- Live span delivery to the webview is Tauri 2 IPC `Channel` carrying binary Arrow IPC on `pulse://stream/spans` (per architecture.md §Standard Contracts → Real-time push contract) — that is the surface scope premise 4 must be researched against for an existing span-arrival reference; the plan mandates the transport, not the payload's field set.
- Shared CI logic that needs Rust lives in the `xtask` crate, and the lint gate is `cargo fmt --check` + `cargo clippy --workspace --all-targets --all-features -- -D warnings` plus `tsc --noEmit` on the generated bindings (per architecture.md §Infrastructure Patterns → Build system, CI/CD approach) — the home of the `EXPECTED_PROCEDURES` / bindings-emission checks premise 2 raises.

## Anti-patterns to avoid
- Do not add a new workspace crate (or repurpose a reserved name) for instrumentation — new first-party functionality of this shape goes into an existing crate (per architecture.md §Occupied Resources → Cargo workspace crate names; §Project Intent).
- Do not construct the measurement via an in-process test-mode bypass, a test-only feature flag, or a mock-channel back-door; synthetic telemetry enters through the real OTLP receiver surface (per architecture.md §Cross-cutting Patterns → Test-time telemetry injection).
- Do not emit the product's own timing telemetry over an OTLP network exporter aimed at its own receivers, and do not introduce an "observer URL"-shaped variable that blurs outbound-observer vs inbound-receiver (per architecture.md §Established Decisions → [Self-Observation]).

## Contract bindings
- **arch ↔ obs** — arch owns crate placement, IPC procedure shape, and the self-observation exporter destination (§Cross-cutting Patterns → Self-observation discipline); obs owns the `metric.*` target names and their default-deny allowlist leaves. The new leaves are obs's call; the emit-site crate is arch's.
- **arch ↔ security** — every new TauRPC procedure binds to a `pulse-app/capabilities/` entry under `pulse:default` and to bounded input validation surfacing as `AppError::Validation` (§Cross-cutting Patterns → Webview IPC capability policy; §Conventions → Error response schema (Tauri IPC)).
- **arch ↔ tests** — the CI lint/typecheck gate and the `cargo xtask test` surface (§Infrastructure Patterns), plus OTLP-only synthetic injection (§Cross-cutting Patterns → Test-time telemetry injection), constrain how the observables can be exercised; a webview-side mark also binds to the frontend tooling under `pulse-app/ui/`, owned by the design specialist (§Infrastructure Patterns → Project directory structure).
- **arch ↔ external Conductor verification** — reproducible external runs are gated by the arch-registered `ANDROMEDA_PULSE_L4_DETERMINISTIC` env var (§Occupied Resources → Environment variables); if the observables must be reproducible under that mode, its registered semantics apply unchanged.

## Acceptance criteria contributions
- (arch) All emit sites land in already-reserved workspace crates (`pulse-app` / `crates/ui-bridge`); no new crate is added to the workspace and no reserved crate name is repurposed (per architecture.md §Occupied Resources → Cargo workspace crate names + §Project Intent → How new functionality is added).
- (arch) Any new TauRPC procedure uses the `<router>.<verb>` dotted `snake_case` shape, returns `Result<T, AppError>` with an existing `AppError` variant, and has both a router registration in its owning crate and a `pulse-app/capabilities/` grant covering it — whether the existing `telemetry.frontend` grant already covers a new method is research's question (per architecture.md §Conventions → Endpoint naming / Error response schema (Tauri IPC) + §Cross-cutting Patterns → Webview IPC capability policy).
- (arch) The three timing observables reach only the self-observation stack (tracing → stdout/file exporter under the resolved `logs/` subpath); no OTLP exporter is pointed at `:4317`/`:4318` and no new "observer URL"-shaped variable is introduced (per architecture.md §Established Decisions → [Self-Observation] + §Cross-cutting Patterns → Self-observation discipline).
- (arch) Every new TauRPC procedure, env var, or stream topic this chunk lands is registered in §Occupied Resources by a wrap amendment; instrumentation that adds none requires no registry change (per architecture.md §Occupied Resources — canonical registry; standing D-arch-resources duty per architecture-amendments.md 2026-05-09 / 2026-06-28 entries).
