# security extract

## Relevance
**Partial** — instrumentation-only, but it writes new events into the self-observation log sink (a redaction boundary) and may add a webview→backend IPC input boundary; it also carries this domain's ratified `cargo audit` deferral probe.

## Constraints
- **The self-observation log sink is a redaction boundary.** Every field on the three new `metric.*` events is subject to the NEVER-log list — no OTLP attribute values, no span/log/metric content payloads (per security-plan §Logging & Monitoring "What NEVER to log" + §Security Anti-Patterns → Logging, bullet 1). `service.name` is an OTLP **resource attribute**, i.e. user-controlled content from the instrumented host app per §Threat Model Summary → Data classification (user-content / telemetry payloads), so a per-service label on any of these events is banned by that bullet independently of the obs cardinality rule. Whether the two existing precedent emit sites already satisfy this is research's question.
- **Uniform scrubber invariant.** §Security Anti-Patterns → Logging (uniform-scrubber-coverage paragraph) requires that any attribute value crossing into the self-observation sink `agent-latest.jsonl` pass `security::scrubber::scrub_attribute` first, yielding `ScrubbedValue::Allowed(_)` or `ScrubbedValue::Redacted`. If any of the three observables must carry an attribute-derived string (e.g. to name the surface or the source), that path is required to route through the scrubber — the alternative that avoids the question entirely is a closed enum discriminant, which carries no attribute value at all.
- **The TauRPC bridge is a declared trust boundary, not an internal call.** §Threat Model Summary → Attack surface (IPC vector) and §Input Validation (TauRPC bridge row) require `serde` deserialization on every `#[taurpc::procedure]` argument, smart enum types rather than free-form strings for any discriminant field, and a Convention-mandated `AppError::Validation { field, reason }` returned on rejection. This binds directly on scope open premise #3: security's preference between "three near-identical methods" and "one parameterized procedure" is neutral, but the **discriminant must be a closed enum** either way — a free-form surface-name string would be webview-controlled content flowing into a log target.
- **Capability pairing is mandatory and its absence is silent.** §API Security → TauRPC capability authorization requires both enforcement pieces (router registration **and** the `pulse-app/capabilities/` entry) and names the `xtask` drift check as the enforcement mechanism, wired as CI per §Bootstrap phases → `dep-security-ci-gate`. Scope open premise #2 asks whether a new *method* on the existing `telemetry.frontend` namespace avoids new capability JSON — the plan does not resolve router-level vs per-procedure granularity, so that is research's question; the plan-level requirement is only that the drift gate ends clean.
- **Boundary-registry completeness.** §Input Validation's boundary table claims to be the complete enumeration of system boundaries, and its TauRPC row names `traces.*`, `metrics.*`, `logs.*`, `snapshot.*`, `plugins.*`, `mcp.*`, `workspace.*` — it does **not** name `telemetry.*`; nor does the §Threat Model Summary IPC-vector procedure list. Per the standing precedent in the amendment history (below), a chunk that lands a new external-input boundary must register it there.
- **Errors crossing the bridge stay sanitized.** §Error Handling → TauRPC bridge requires `Result<T, AppError>` with module-internal `thiserror` collapsing via `From` at the bridge, and §Security Anti-Patterns → Code Patterns bans serializing `anyhow::Error` across it.
- **Dependency gates are unchanged by an instrumentation chunk, but the deferral probe is not.** §Dependency Security → CI integration requires `cargo deny check bans licenses sources` to pass, and the *Standing deferral — `cargo audit` unrunnable* clause requires the interval probe to fire at its named point rather than be skipped silently.

## Patterns to follow
- **Backend-measured precedent** — a dedicated `metric.*` target emitted from a Rust resolver carrying a numeric-only field (`pulse-app/src/incidents_router.rs:561`, cited by the scope). This shape adds no new trust boundary at all, which is the security-cheapest side of the chunk's central design fork.
- **Webview-originated precedent** — validate-input → level-gate → emit (`crates/ui-bridge/src/telemetry.rs:99`, cited by the scope). This is the shape §Input Validation (TauRPC bridge row) requires of any new frontend→backend procedure; reusing its validate-first ordering is what keeps a new procedure inside the existing discipline rather than opening a new one.
- **Bounded-parse + named-rejection-test pattern** used by the four most recent boundary rows in §Input Validation (window-geometry, workspace-key, `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS`): bound the value, reject invalid input explicitly, never panic, and unit-test each rejection by name. Per the amendment precedent below, this is exactly what keeps a new boundary's registration *routine* instead of an escalation.
- **Negative-default registry discipline** — the obs allowlist in `pulse-app/src/observability.rs` is default-deny with exact-leaf resolution, structurally the same posture as Tauri's negative-default capability model that §API Security relies on. The security-relevant requirement is that each new target gets its own exact leaf and the registry is not widened to a bare prefix to cover all three at once.
- **`scrub_attribute` at the boundary**, not at the call site — §Security Anti-Patterns → Logging places scrubbing at every persistence/log boundary, and §Logging & Monitoring → Log format places field redaction at the subscriber layer rather than at log call sites.

## Anti-patterns to avoid
- **NEVER** put a raw OTLP attribute value, span/log/metric content payload, or per-service identifier on the new `metric.*` events (§Security Anti-Patterns → Logging).
- **NEVER** add a TauRPC procedure to a router crate without its matching `pulse-app/capabilities/` entry — the bridge call is silently rejected at runtime and becomes a hard-to-diagnose UX bug (§Security Anti-Patterns → API).
- **NEVER** serialize an `anyhow::Error` across the bridge, and never let stack traces, Rust struct names, file paths, or library versions reach `AppError::Internal { message }` (§Security Anti-Patterns → Code Patterns + → Logging).

## Contract bindings
- **security ↔ obs.** Same event fields, two owners: obs owns leaf registration + the aggregate-only cardinality rule (`.claude/rules/observability.md` 2026-05-17); security owns the field-content ban (§Security Anti-Patterns → Logging) and the scrubber invariant. They must agree per-field; obs's allowlist is the mechanism, security's NEVER-list is the content rule.
- **security ↔ tests/CI.** `cargo xtask capability-drift` is a security-owned control (§API Security → TauRPC capability authorization) that ships as a CI job (§Bootstrap phases → `dep-security-ci-gate`) — binds to tests §CI Integration as one gate, not two.
- **security ↔ arch.** Per the distilled rule the scope cites (`.claude/rules/security.md`, 2026-05-09), arch §Occupied Resources — not the xtask list — is the canonical TauRPC procedure source of truth; a namespace/method addition that skips it drifts the gate. Whether `telemetry.frontend` is currently enumerated there and in `xtask EXPECTED_PROCEDURES` at HEAD is research's question (the distilled rules record a chunk-#34 cleanup, but that is a note, not the code).
- **security ↔ tests (unit coverage).** The registry-completeness playbook rule scopes its escalate severity to *actually-unvalidated* boundaries — unit coverage of each rejection path is what evidences validation and keeps the §Input Validation registration routine.

## Acceptance criteria contributions
- No field on any new `metric.*` event carries an OTLP attribute value (including `service.name`), a span/log/metric content payload, or a per-service identifier into `agent-latest.jsonl`; any attribute-derived string that must appear passes `security::scrubber::scrub_attribute` first (per security-plan §Security Anti-Patterns → Logging + §Logging & Monitoring "What NEVER to log").
- If a frontend→backend telemetry procedure is added or extended: every argument is `serde`-deserialized and bounded, any surface discriminant is a closed enum rather than a free-form string, and rejection returns `AppError::Validation { field, reason }` (per security-plan §Input Validation, TauRPC bridge row).
- `cargo xtask capability-drift` exits 0 at wrap, with any new procedure paired to its `pulse-app/capabilities/` registration (per security-plan §API Security → TauRPC capability authorization + §Security Anti-Patterns → API).
- The session-31 `cargo audit` probe FIRES and its outcome is recorded in the chunk report — either the basis reproduces (deferral continues, interval resets) or `cargo audit` loads (deferral ends) — and the named overlap `cargo deny check advisories` is run with its finding count recorded against the expected 7 owned upgradeable IDs (per security-plan §Dependency Security → CI integration, Standing deferral clause).
