## Backend Framework Comparison

This project is a Rust desktop app receiving OTLP HTTP (`:4318`) and gRPC (`:4317`). The "backend framework" question reduces to: **what HTTP+gRPC server stack runs inside the Tauri Rust process to ingest OTLP?** Three viable stacks for Rust 2026:

**Option A — `tonic` 0.14.x + `axum` (shared `hyper` 1.x stack)** ([tonic crate](https://crates.io/crates/tonic), [axum docs](https://docs.rs/axum/))
- Tonic 0.14 (latest stable line; built on `hyper` 1.x and `tower`) is the de-facto Rust gRPC server, used by every OTel Rust example for OTLP transport. Plays directly with `prost` 0.14 codegen against `opentelemetry-proto`. ([tonic-prost-build](https://lib.rs/crates/tonic-prost-build))
- Axum 0.8.x reuses the same `hyper`/`tower` substrate, so a single Tokio runtime serves both `:4317` (gRPC) and `:4318` (HTTP/protobuf+JSON). Production patterns for hybrid Axum+Tonic on one socket are documented. ([axum + tonic + hyper hybrid](https://academy.fpblock.com/blog/axum-hyper-tonic-tower-part3/))
- Fits modular monolith: `ingest` crate exposes a `Server` builder; the Tauri app just calls `start()`. No microservice deploy assumptions to fight.
- Friction: tonic 0.14 does NOT yet ship with `opentelemetry-otlp` 0.31 (which still pins tonic 0.13 in some feature combinations) — read both crates' `Cargo.toml` before locking versions. ([opentelemetry-otlp 0.31](https://docs.rs/crate/opentelemetry-otlp/latest))

**Option B — `tonic` + raw `hyper` 1.x (no Axum)** ([hyper](https://crates.io/crates/hyper))
- Drops the Axum routing layer; fewer transitive deps, faster cold start. Reasonable because the OTLP HTTP receiver only needs three POST routes (`/v1/traces`, `/v1/metrics`, `/v1/logs`).
- Costs you ergonomic extractors, middleware, and tower-http compression — minor for a fixed 3-route surface.
- Best when binary-size matters (Tauri app distributed via Releases — every MB shows up in `.msi`/`.dmg`).

**Option C — `poem` 3.x or `actix-web` 4.x for HTTP + tonic for gRPC** ([poem](https://crates.io/crates/poem), [actix-web](https://crates.io/crates/actix-web))
- Two unrelated runtime substrates (poem on hyper, actix on actix-system). Forces two separate task pools in the Tauri process — wasted memory for a desktop app.
- No advantage over Axum for a 3-route receiver. **Likely deal-breaker for a Tauri-embedded receiver** because actix-web brings its own actor system that complicates `tokio::main` Tauri integration.

Status: tonic is at 0.14.5 actively maintained; axum 0.8 actively maintained; both are widely used in production (used by AWS, Discord, Cloudflare). Axum has community gravity an order of magnitude greater than poem.

## Database Comparison

Quiz I confirmed in-memory DuckDB ring buffer (5–10 min, configurable). The fork is *which embedded engine*, not whether to persist.

**Option A — DuckDB embedded via `duckdb` crate (1.10500.x, bundling DuckDB 1.5.x)** ([duckdb-rs](https://github.com/duckdb/duckdb-rs), [DuckDB Rust docs](https://docs.rs/duckdb/))
- Columnar OLAP engine, vectorized execution, multi-threaded — exactly what aggregating spans/metrics by service/time-bucket needs. ([DuckDB vs SQLite analytics](https://medium.com/@Quaxel/from-sqlite-to-duckdb-embedded-analytics-is-here-da79263a7fea))
- First-class Apache Arrow zero-copy: `Appender::append_record_batch()` ingests an `arrow::RecordBatch` directly; `stream_arrow()` returns query results as Arrow streams. Matches the planned Arrow ingest pipeline. ([Appender API](https://docs.rs/duckdb/latest/duckdb/struct.Appender.html), [DuckDB Arrow zero-copy](https://duckdb.org/2021/12/03/duck-arrow))
- The `1.MAJOR_MINOR_PATCH.x` versioning scheme means the Rust crate version mechanically tracks the bundled DuckDB version — pinning is unambiguous. ([duckdb-rs releases](https://github.com/duckdb/duckdb-rs/releases))
- Status: actively maintained by DuckDB Foundation; bundled DuckDB v1.5.1; Arrow 58 integration. Already in Quiz I — listed for completeness.
- Fit risk: DuckDB process model assumes one writer; ring-buffer eviction (`DELETE FROM spans WHERE ts < now() - 10min`) needs care under concurrent reads from `viz` queries — measure under target span rate.

**Option B — SQLite via `rusqlite` 0.32+ (with WAL mode)** ([rusqlite](https://crates.io/crates/rusqlite))
- Row-store, OLTP-tuned. Aggregating 10k spans/sec into per-service p99 series in SQL means full table scans every refresh — exactly the workload SQLite is worst at. ([SQLite vs DuckDB](https://motherduck.com/learn/duckdb-vs-sqlite-databases/))
- Wins on bundle size (~1MB) and battle-tested correctness, but the project's bar is "GPU-accelerated viz of 10k spans/sec" — SQLite makes the *query* the bottleneck instead. Likely deal-breaker for the metrics aggregation path.

**Option C — Pure in-memory Arrow + a query layer (DataFusion 43+ or Polars 0.43+)** ([datafusion](https://crates.io/crates/datafusion), [polars](https://crates.io/crates/polars))
- DataFusion: SQL over Arrow with vectorized exec — same query power as DuckDB without the C++ bundled binary. Pure Rust, smaller footprint, easier cross-compile.
- Polars: lazy DataFrame API, very fast aggregations, but lacks SQL surface that the v1 product description ("DuckDB SQL backend") and the user-extensible plugin system (snapshot custom SQL filter) explicitly want.
- Status: DataFusion is Apache top-level, very active; Polars active; both pure-Rust with no FFI. **Realistic alternative if DuckDB's C++ FFI complicates Tauri cross-compile** — the user input cites DuckDB as locked, but DataFusion is the only technically-credible swap-out.

## API Style & Conventions

Two distinct API surfaces in this project; the fork is per-surface.

**Surface 1 — OTLP receiver (external apps push to Pulse)**
- Wire format is fixed by the OpenTelemetry spec: `:4317` = gRPC over `opentelemetry-proto`; `:4318` = HTTP/protobuf or HTTP/JSON. No fork — implement the spec via `tonic` (gRPC) + `axum`/`hyper` (HTTP). ([opentelemetry-proto crate](https://crates.io/crates/opentelemetry-proto))

**Surface 2 — Tauri Rust ↔ webview frontend (internal commands + events)**
- **Option A: Plain `#[tauri::command]` + `app.emit_to(...)`** — stock Tauri IPC. Type contracts duplicated by hand on the frontend. ([Tauri commands](https://v2.tauri.app/develop/calling-rust/))
- **Option B: TauRPC** ([taurpc](https://lib.rs/crates/taurpc)) — derive macro generates fully-typed TypeScript bindings from the Rust command surface; eliminates drift. Worth the dep for an 8-module monolith with many commands.
- **Option C: Specta + tauri-specta** ([tauri-specta](https://github.com/oscartbeaumont/tauri-specta)) — alternative auto-typegen layer; commonly paired with React/Solid via TanStack Query.

**Surface 3 — MCP server (external AI agents)**
- JSON-RPC 2.0 over stdio per MCP spec. Use rmcp's macros; do not invent.

**Error handling pattern (cross-surface):**
- **`thiserror` 2.x for module-internal error enums**, **`anyhow` 1.x for the Tauri command boundary and main.rs** — Rust 2026 community consensus. ([Shakacode error handling](https://www.shakacode.com/blog/thiserror-anyhow-or-how-i-handle-errors-in-rust-apps/), [oneuptime guide](https://oneuptime.com/blog/post/2026-01-25-error-types-thiserror-anyhow-rust/view))
- **`miette` 7.x** is the optional upgrade for diagnostics with source spans — overkill for backend ingest, useful for plugin-loading errors where the user wants pretty WIT-resolution diagnostics. ([miette](https://github.com/zkat/miette))
- Tauri commands must return `Result<T, E: Serialize>` — wrap `anyhow::Error` in a `serde`-friendly `AppError` enum (lossy but explicit) or use one of the `tauri-plugin-anyhow` wrappers.

## Module Boundary Enforcement

Quiz I locks "Modular monolith — 8 Rust modules: ingest / buffer / viz / ui-bridge / snapshot / workspace-detector / plugins / mcp-server". The fork is *how to enforce the boundaries*.

**Option A — Cargo workspace with one crate per module** ([cargo workspaces](https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html), [Earthly workspaces guide](https://earthly.dev/blog/cargo-workspace-crates/))
- Each module = a library crate; `pulse-app/` is the binary that wires them. Boundaries enforced by `Cargo.toml` `[dependencies]` — `viz` cannot accidentally import `mcp_server` if it isn't listed.
- Compile-time visibility: `pub` only what the module's contract exposes; `pub(crate)` for in-crate utilities. The compiler is the enforcement mechanism.
- Bonus: incremental rebuild speed (separate crates compile in parallel).
- Strongly recommended for an 8-module project — single-crate `mod` directories let any internal `pub(crate)` leak across modules.

**Option B — Single crate with `mod ingest;` + `pub(crate)` discipline**
- Faster to start, slower to evolve. Module boundaries enforced by review, not the compiler. Suitable for a 3-module prototype, not an 8-module shipping app.

**Option C — `cargo-deny` 0.16+ with custom `bans` rules** ([cargo-deny](https://github.com/EmbarkStudios/cargo-deny))
- Lints workspace dependency graph; can ban e.g. "no crate may depend on `wgpu` except `viz`". Layered on top of Option A.
- CI-only check; doesn't replace workspace structure.

**Recommendation framing for Quiz II:** Workspace-of-crates (A) is mechanically the right choice for 8 modules with "modular monolith" stated intent; the open question is whether to add cargo-deny rules from day 1 or defer until a boundary is actually breached.

## Key Trade-offs Summary

1. **OTLP receiver stack: tonic+axum (shared hyper) vs tonic+raw-hyper — the stakes:** Axum gives you middleware/extractors and a familiar HTTP shape but adds ~30 transitive deps and a few hundred KB to the bundle. Raw hyper is leaner but you write three handlers by hand. For a desktop app where binary size affects download conversion, the size delta matters more than usual.

2. **Plugin runtime: WASM Component Model (wasmtime) vs Extism — the stakes:** Component Model is the standards path with WIT interfaces, type-safe host imports, capability-based sandboxing — matches input.md exactly, but Preview 2 / Preview 3 churn means more SDK migration over the next 12 months. Extism wraps wasmtime under a higher-level "PDK" model that supports Go/Rust/Zig/JS guests out of the box — easier for plugin authors, less standards-aligned. ([WASM 2026 status](https://blog.iamcristhian.dev/2026/04/webassembly-component-model-wasm-beyond-browser-2026), [extism vs component model](https://tartanllama.xyz/posts/wasm-plugins/))

3. **WebGPU surface: render-into-webview (`<canvas>` + `navigator.gpu`) vs native wgpu surface overlaid on Tauri window — the stakes:** Webview WebGPU is the simpler path (WebView2 has it on Windows; WKWebView in Tauri's stack supports it on macOS) — your WGSL runs unchanged and IPC pushes Arrow data into the canvas. Native wgpu (`wgpu` 25+ with raw window handle) is faster and avoids browser GC pauses but introduces flickering issues with Tauri 2's webview compositing ([flicker bug](https://github.com/tauri-apps/tauri/issues/9220), [wgpu overlay discussion](https://github.com/tauri-apps/tauri/discussions/11944)). The "GPU-accelerated, no jank at high cardinality" bar pushes toward native; the "ship it on three OSes with one codebase" bar pushes toward webview.

4. **Storage engine: DuckDB-bundled vs DataFusion (pure Rust) — the stakes:** DuckDB is locked in input.md and fits the columnar+SQL+Arrow trifecta, but it's a C++ dependency that complicates cross-compile and adds ~10MB to the binary. DataFusion is the pure-Rust alternative with the same SQL+Arrow surface — only worth raising if cross-compilation pain becomes a blocker. Otherwise DuckDB stays.

5. **Webview frontend type-bridge: stock `#[tauri::command]` vs TauRPC vs tauri-specta — the stakes:** Stock IPC means the frontend re-declares every command's signature in TypeScript; an 8-module app with 30+ commands creates drift bugs. TauRPC/tauri-specta auto-generate bindings — TauRPC is more opinionated (router-style), tauri-specta is more composable (per-command). The decision drives how much ceremony every new command requires.
