# design extract

## Relevance
**partial** — the chunk builds a driver harness (no new UI), but its one canonical leg presses a design-owned chrome control (custom-titlebar ✕) on the `desktop-webview` surface, so surface bans + control-identity rules apply.

## Constraints
- The titlebar is design-owned custom chrome (custom-drawn, not OS; fixed height; app icon + title + settings/aperture button + window controls; drag region defined) — the leg must press the *real* control inside that chrome, not a substitute (per design-system.md §Surface: desktop-webview → Component Patterns → Navigation / App Shell).
- The window-control set is platform-conditional by design mandate: Windows/Linux render right-aligned minimize/maximize/close; macOS renders traffic-light buttons on the left. Any selector the driver encodes is therefore platform-scoped, and a Windows-host leg is not a cross-platform claim (per design-system.md §Surface: desktop-webview → Platform-Specific Notes).
- All interactive elements must be Tab-navigable with `:focus-visible` focus rings — this is what makes a chrome control addressable by role/accessible name to a WebDriver/CDP driver rather than by pixel position. Whether the shipped close button already satisfies this is research's question (per design-system.md §Surface: desktop-webview → Focus / Keyboard Navigation).
- Hide-to-tray is the design-intended terminal state, not exit: the tray surface is "always-visible and passive" and clicking the tray icon restores the compact widget. The leg's observable (hidden, never process exit) is thus a design requirement, not only an implementation detail of `window.rs` (per design-system.md §Surface: desktop-native → Navigation Pattern + Component Patterns → Tray Icon).
- Compact-widget chrome is minimal-by-mandate ("every pixel of chrome counts"; icons clarify, not decorate) — no test-only visible affordance may be added to reach drivability (per design-system.md §Iconography → Rule, and §Surface: desktop-webview → Component Patterns → Navigation / App Shell).
- If any probe forces a UI change (scope says none expected), it must stay token-sourced — no hardcoded hex/px/duration introduced (per design-system.md §Self-Validation Protocol → 4. Token Test).
- Chrome motion is capped at 150–200ms with **no entrance animations** and instant-under-`prefers-reduced-motion` — so no design-sanctioned animation settle exists to wait on for a close action; long driver settle-waits would be masking something else (per design-system.md §Motion → duration scale + Accessibility).

## Patterns to follow
- Address the production control by its accessible role/name (the design system mandates a real keyboard-focusable button, not a hover-only or class-only affordance) rather than by CSS class or coordinates — per design-system.md §Surface: desktop-webview → Focus / Keyboard Navigation and §Anti-Patterns → Per-Surface Bans (desktop-webview).
- Keyboard actuation (Tab + activate) is a design-supported equivalent to click for every interactive element, so it is a legitimate second driver path if pointer synthesis proves flaky on WebView2 — per design-system.md §Surface: desktop-webview → Focus / Keyboard Navigation.
- Chrome iconography comes from the registered custom glyph set (`<Icon glyph="…" />` component registry) with a fallback library only for generic controls; glyph identity is therefore not a stable selector key — prefer accessible name — per design-system.md §Iconography.
- Judgment-shaped checks stay human: the Self-Validation Protocol's Squint / Signature / Contrast tests are "does it LOOK right" checks that a click-driver does not discharge — this matches the scope's boundary reserving operator legs for judgment items (per design-system.md §Self-Validation Protocol).

## Anti-patterns to avoid
- **NEVER ship visible Chromium/WebView2 artifacts** (devtools surface, context menu, text selection on non-text elements) on `desktop-webview`. Driver shape (b) turns on a remote-debugging port; design requires that any such enablement be harness-gated and absent from the default production build path (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview).
- **NEVER add a hover-only or pointer-only interaction without a keyboard alternative** — a "make it drivable" hook must not degrade the control below the keyboard mandate (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview).
- **NEVER add decorative/filler chrome to the compact widget** — a synthetic test button in the titlebar would violate the minimal-chrome + icons-clarify-not-decorate discipline (per design-system.md §Iconography → Rule; §Anti-Patterns → Universal Bans "color/ornament purely for decoration").

## Contract bindings
- **design ↔ tests:** design supplies the verification targets the tests plan lints against (motion durations/easings + the 7 motion hard limits, banned fonts, component hex/spacing/radius) per design-system-amendments.md §Downstream Readiness → "For tests specialist". This chunk's driver is a tests-plan artifact; design's contribution is the identity of the control under test and the bans the harness must not breach.
- **design ↔ a11y:** the accessible role/name that makes the control driver-addressable is a11y's conformance territory; design only mandates Tab-navigability + `:focus-visible` (§Surface: desktop-webview → Focus / Keyboard Navigation) and hands contrast/focus-ring targets to a11y per design-system-amendments.md §Downstream Readiness → "For a11y specialist".
- **design ↔ desktop-native surface:** the leg's asserted end state (widget hidden, tray remains the always-visible locus, tray signpost) binds the webview leg to §Surface: desktop-native → Navigation Pattern; a leg asserting process exit would contradict the tray mandate.
- **design ↔ security:** the webview-artifact ban is design's guard, but the CSP (`script-src 'self'`) and ACL/capability calls for any remote-debugging enablement belong to security-plan.md (referenced from design-system.md §Surface: desktop-webview → CSP policy).

## Acceptance criteria contributions
- (design) The proven leg actuates the production custom-titlebar close control by accessible role/name — no test-only affordance is added to widget or dashboard chrome (per design-system.md §Surface: desktop-webview → Component Patterns → Navigation / App Shell; §Iconography → Rule).
- (design) Whichever driver shape lands, no WebView2/Chromium artifact (devtools, remote-debugging port, context menu, text selection) is enabled on the default production build path; enablement is harness-gated only (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview).
- (design) The leg's control-selection is platform-scoped rather than assuming one universal control set/position, matching the mandated Windows/Linux vs. macOS window-control divergence (per design-system.md §Surface: desktop-webview → Platform-Specific Notes).
- (design) The asserted observable is "window hidden, tray remains the always-visible surface", never process exit; and the harness introduces no new design-token, motion, typography or chrome change (per design-system.md §Surface: desktop-native → Navigation Pattern; §Self-Validation Protocol → 4. Token Test).
