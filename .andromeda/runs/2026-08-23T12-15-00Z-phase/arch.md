# arch extract

## Relevance
Relevant — arch owns workspace/harness placement, the capability-grant policy the leg's mutation check exercises, the close-to-tray semantic the leg asserts, and registration of any new env var/port/file the driver lands.

## Constraints
- **Task surface is `cargo xtask`.** architecture.md §Infrastructure Patterns (Build system, CI/CD) requires all shared CI/verification logic that needs Rust to live in the `xtask` crate so the same command runs locally and in CI; §Cross-cutting Patterns → Development Style further requires agent-driven harnesses to expose deterministic invocations, machine-parseable output and schema-stable contracts. An xtask-shaped driver entry point is the arch-sanctioned shape; a JS-only harness under `pulse-app/ui/` must still be reachable through a stable, machine-parseable invocation.
- **Placement is locked.** architecture.md §Occupied Resources → Cargo workspace crate names reserves the 16 member names (incl. `xtask`, `pulse-app`); §Infrastructure Patterns → Project directory structure fixes `pulse-app/ui/` as the webview source root and `pulse-app/capabilities/` as the capability-JSON home. The driver must land inside existing members — a new workspace crate for a harness is not authorized by these sections.
- **Capabilities are negative-default at the *core-API* granularity, and that is exactly the mutation lever.** architecture.md §Cross-cutting Patterns → Webview IPC capability policy requires each `core:window:*` permission (`allow-close`, `allow-start-dragging`, `allow-set-size`, …) to be granted individually and states such calls ARE silently rejected at runtime when missing — while TauRPC procedures are gated by the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`, not by capability JSON. Whether `default.json` at HEAD already carries `core:window:allow-close` (the scope asserts it does) and whether `xtask capability-drift` inspects grants at all or only procedures is research's question.
- **Close means hide-to-tray, never process exit.** architecture.md §Cross-cutting Patterns → Tray icon policy requires that closing the main window minimizes to tray rather than terminating the process, with termination reserved for the explicit Quit item or an OS kill. The leg's assertion must be shaped to that mandate; whether `window.rs` already implements it is research's question.
- **No test-mode back-door.** architecture.md §Cross-cutting Patterns → Test-time telemetry injection forbids in-process test-mode bypasses, separate "test ingest" feature flags and mock-channel back-doors for E2E; tests speak the real external surfaces and read state back through the real query routers. Any "make the app drivable" change must be argued against this rule, not assumed.
- **New occupied resources must be registered.** architecture.md §Occupied Resources reserves the `ANDROMEDA_PULSE_*` env namespace, enumerates ports (`:4317`/`:4318`, both `127.0.0.1`-bound, with *no* frontend/dev port reserved at arch level) and data-dir subpaths. A CDP remote-debugging port (shape b) is a new occupied port; a driver env var is a new occupied env var; both require an §Occupied Resources entry at wrap, and the harness-only class must carry the "NOT consumed by production binary" tag.
- **Cross-platform commitment constrains CI wiring.** architecture.md §Project Intent (product type: Windows/macOS/Linux) and §Infrastructure Patterns → CI/CD (matrix over all three in `ci.yml`) mean a host-specific headful driver cannot become an ungated required CI step; the shape (a) macOS gap named in the scope is an arch-level platform-gating problem, not just a harness detail.

## Patterns to follow
- **Harness-only env var class with explicit tagging** — architecture.md §Occupied Resources → Environment variables already carries `ANDROMEDA_PULSE_PIDFILE` / `_LOGFILE` / `_DATA_DIR_KEEP` and the `PYTHONUTF8` / `PYTHONIOENCODING` relay, each marked as set/consumed by `scripts/agent-run.{sh,ps1}` and NOT by the production binary. A driver-side variable follows that precedent verbatim.
- **Bounded truthy env gate** — if the probe needs a test-only runtime gate, architecture.md §Occupied Resources documents the `ANDROMEDA_PULSE_L4_DETERMINISTIC` shape (truthy `1|true|yes`, default false, bounded parse per the `crates/mcp-server/src/feature_gate.rs` pattern) as the established form for verification-only switches resolved once at `pulse-app` boot.
- **Existing launch/observe harness contract** — architecture.md §Occupied Resources → Filesystem locations registers `run/andromeda-pulse.pid` (written by the production binary at boot, consumed by `scripts/agent-run.{sh,ps1}` for status/cleanup) and `logs/` as the self-telemetry sink under §Cross-cutting Patterns → Self-observation discipline. The driver should attach to that lifecycle rather than introduce a second, unregistered launcher/observer path.
- **Feature-gate hygiene** — architecture.md §Conventions → Feature flags + §Cross-cutting Patterns → Feature-gate hygiene require Cargo features to be `kebab-case` and off by default, with flag-specific deps entering the build graph only when enabled — the rule to apply if any driver support is expressed as a Cargo feature instead of an env gate.
- **Config precedence** — architecture.md §Cross-cutting Patterns → Config management fixes env vars > `config.toml` > built-in defaults; a driver that overrides runtime settings uses the env layer, which per the 2026-08-16 precedent needs no `Settings`/TauRPC/hot-reload surface.

## Anti-patterns to avoid
- **Do not open a drivability back-door into the app** — architecture.md §Cross-cutting Patterns → Test-time telemetry injection bans in-process test-mode bypasses and mock-channel back-doors for the E2E path.
- **Do not widen the core-API capability surface to make driving easier** — architecture.md §Cross-cutting Patterns → Webview IPC capability policy records that `fs` / `shell` / `dialog` / `http` are deliberately NOT granted to `pulse:default`; granting one to unblock a harness inverts the negative-default posture (the §Occupied Resources training-export entry cites "no native file picker" as the same discipline applied elsewhere).
- **Do not add a new workspace crate or a reverse dependency for the harness** — architecture.md §Occupied Resources → Cargo workspace crate names (reserved list) + §Cross-cutting Patterns → Module dependency direction (DAG with `pulse-app` as the only root; no library crate depends on the binary crate).

## Contract bindings
- **Capability grant set ↔ security** — the leg's mutation check deliberately revokes and then restores a registered `core:window:*` grant in `pulse-app/capabilities/default.json` (architecture.md §Occupied Resources → Tauri capability identifiers; §Cross-cutting Patterns → Webview IPC capability policy). Security owns whether a temporary revoke-and-rebuild is an acceptable procedure; arch requires the registered end state to be restored.
- **`xtask` task surface ↔ tests harness** — architecture.md §Infrastructure Patterns pins `cargo xtask <task>` as the one place shared verification logic lives; the test plan owns the leg's assertions, arch owns the invocation surface they hang off.
- **`pulse-app/ui/` devDeps + configs ↔ design specialist** — architecture.md §Infrastructure Patterns → Project directory structure and §Conventions → File naming both defer webview source conventions and frontend tooling to the design specialist; a driver landing in `pulse-app/ui/` inherits that ownership boundary.
- **Obs-log read path ↔ obs** — architecture.md §Cross-cutting Patterns → Self-observation discipline makes `logs/` under the resolved data root the only sink for the product's own telemetry; a driver that verifies effects by reading the obs log consumes obs's contract, and per §Occupied Resources the root is `ANDROMEDA_PULSE_DATA_DIR`-overridable.

## Acceptance criteria contributions
- (arch) Harness code lands only in existing reserved members — `xtask` and/or `pulse-app/ui/` — with no new workspace crate name and no library-crate → `pulse-app` dependency (per architecture.md §Occupied Resources → Cargo workspace crate names and §Cross-cutting Patterns → Module dependency direction)
- (arch) The canonical ✕ leg asserts the mandated close semantic: the window becomes hidden and the process stays alive, never a process exit (per architecture.md §Cross-cutting Patterns → Tray icon policy)
- (arch) Every new env var, listening port or data-dir file the driver introduces is registered in §Occupied Resources at wrap; a harness-only env var carries the "NOT consumed by production binary" tag, and any debugging port is `127.0.0.1`-bound and absent from the shipped default configuration (per architecture.md §Occupied Resources → Environment variables / Network ports and §Design Philosophy → Local-first, zero-infrastructure)
- (arch) After the mutation check, `pulse-app/capabilities/default.json` is restored to its registered grant set, and no core-API capability (`fs`/`shell`/`dialog`/`http`) was added to `pulse:default` to make the app drivable (per architecture.md §Cross-cutting Patterns → Webview IPC capability policy)
