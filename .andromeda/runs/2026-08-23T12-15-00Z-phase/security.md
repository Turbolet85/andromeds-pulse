## Relevance
Partial — no production behaviour change is expected, but the chunk mutates a `core:window:*` capability grant, may open a webview remote-debugging listener, and may add a test-only env gate plus new dependencies; each falls under a security mandate.

## Constraints
- The mutation check MUST end with `pulse-app/capabilities/default.json` restored to its exact prior grant set (recorded as `core:default` + seven `core:window:*` + `updater:default`, measured 2026-08-21) with the per-grant rationale text intact — a revoked `core:window:allow-close` left in the tree IS the silently-rejected dead-affordance state the ban names (per security-plan.md §API Security → TauRPC capability authorization; §Security Anti-Patterns → API).
- The driver MUST NOT obtain reach by widening capabilities: no Tauri core API (`fs`/`shell`/`dialog`/`http`) granted to `pulse:default` without an explicit per-feature addition + stated rationale, no `pulse:updater` exposure to webview JS, no widening of `pulse:notification` / `pulse:tray` / `pulse:plugin-fs` (per security-plan.md §Security Anti-Patterns → API).
- If shape (b) lands, `--remote-debugging-port=N` is a new loopback control channel into the webview, and the plan's standing lesson is that a loopback listener is not self-authorizing ("localhost is not a security boundary", Coder Agent API CVE 2025-09-19 / CVE-2025-66414). It MUST be off by default, absent from release configuration, and reachable only behind an explicit opt-in. Whether any such gate exists at HEAD is research's question (per security-plan.md §API Security → Host header allowlist; §Threat Model Summary → Attack surface, webview content vector).
- Any new `ANDROMEDA_PULSE_*` test/drivability gate MUST carry a bounded parse (bool = truthy-parse `1|true|yes`, default false; port = `TryFrom<u16>`) and MUST be registered in the env-var boundary enumeration, which claims to be the complete list. Any `*_PATH`/`*_DIR` variable additionally requires canonicalize-and-confine (per security-plan.md §Input Validation → CLI / env var inputs; §Security Anti-Patterns → Input).
- If drivability turns out to need an IPC surface, no TauRPC procedure may land without BOTH a validated argument struct and its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` — the per-procedure enforcement rests there, not on the capability layer (per security-plan.md §API Security → TauRPC capability authorization; §Security Anti-Patterns → API).
- Whatever the driver installs re-engages the dependency gates: `cargo deny check bans licenses sources` green, `multiple-versions = "deny"` never relaxed, any duplicate carve-out ID-scoped + owner-named + reasoned; any CI wiring references third-party Actions by 40-char SHA, never `@v2`/`@latest`. The folded `cargo audit` pin is CARRIED, not discharged — next interval point 40 (per security-plan.md §Dependency Security → CI integration + Standing deferral; §Bootstrap phases → `dep-security-ci-gate`).
- Harness capture artifacts (screenshots, page dumps, CDP/WebDriver traces, copied obs-log excerpts) inherit the NEVER-log list — raw OTLP attribute values, snapshot/clipboard contents, full paths — and must not be committed; `.gitignore` + the secret-scanning gate cover whatever the harness writes (per security-plan.md §Logging & Monitoring → What NEVER to log; §Secret Management → Secret scanning in CI).

## Patterns to follow
- Explicit per-feature capability entry with inline rationale text — the existing shape for each `core:window:*` grant; any restore or addition follows it (per security-plan.md §API Security → TauRPC capability authorization).
- Bounded truthy-parse env gate, default false, no unbounded string — the `ANDROMEDA_PULSE_L4_DETERMINISTIC` shape, plus its registration in the §Input Validation env-var row as the routine follow-through (per security-plan.md §Input Validation).
- Two-piece TauRPC enforcement (validated argument struct + `EXPECTED_PROCEDURES` pin), verified by the shipped `xtask capability-drift` check that fails CI on mismatch (per security-plan.md §API Security).
- SHA-pinning convention `<owner>/<repo>@<40-char-SHA> # vX.Y.Z` for every third-party Action, with Dependabot bumping SHA + comment together (per security-plan.md §Bootstrap phases → `dep-security-ci-gate`).
- `.gitignore` coverage for `*.p12`/`*.pem`/`*.cer`/`.env*`/`*.key` plus the pre-commit + per-PR secret-scanning step (per security-plan.md §Bootstrap phases → `secret-scanning-ci-gate`).

## Anti-patterns to avoid
- NEVER grant a Tauri core API or a `core:window:*` permission without an explicit per-feature capability addition with stated rationale — corollary here: never leave the mutation-check revocation in the tree (per security-plan.md §Security Anti-Patterns → API).
- NEVER reference a third-party GitHub Action by floating tag, and NEVER commit `.env*` / `*.key` / `*.pem`-class files the harness or driver install may drop (per security-plan.md §Security Anti-Patterns → Secrets).
- NEVER log or persist raw OTLP attribute values, snapshot contents, clipboard contents, or full file paths — harness capture output is the same leakage class as the log sink (per security-plan.md §Security Anti-Patterns → Logging).

## Contract bindings
- **tests §CI Integration** — the CI security gate (`cargo deny check bans licenses sources` + `xtask capability-drift`) is a job in the one workflow; it must stay green across the mutation-check window, and any driver CI wiring rides that same workflow under the SHA-pinning convention.
- **obs (self-observation sink)** — the leg observes via the `agent-latest.jsonl*` date-suffixed family; the §Logging NEVER-log list and the obs-side PII scrubbing cross-cut govern what the harness may read out, retain, or attach to a report.
