## Constraints

Whether that component already carries a live-region role is research's question.
- A wedged-vs-healthy indicator rendered in the UI must not be conveyed by color alone — a11y-plan §6 (State color tokens, not-color-alone) and §11 (Visual) require every state color (`--color-accent` error / `--color-feedback-success` ok) to be paired with a text label or icon supplement, verified by a custom Playwright assertion (axe-core does not detect this).
- Any new UI text for the observable must meet a11y-plan §6 (Color contrast pairs) SC 1.4.3 — `--color-text-primary / --color-base` at 4.5:1, `--color-text-secondary / --color-base` at 3:1; `--color-text-tertiary` is large-text-only.
- a11y-plan §3 (Harness wiring & conventions, "Adding a surface" standing rule) requires that every new route/modal ship its axe spec in the same chunk, with POPULATED fixtures (an empty fixture renders nothing and the sweep passes by comparing nothing) — a stall/health state added to an existing dashboard surface must be exercised in that surface's existing spec, not left unfixtured.
- a11y-plan §10 (SLO Invariants) requires zero *new* WCAG AA violations per PR versus the base-branch `baselines/a11y-violations-summary.json`; this gate applies to any chunk that changes rendered DOM, including an incidental status-line change.
- P4 (Real-time push) per a11y-plan §1 (Critical paths) requires that live updates do not steal focus and that roving-`tabindex` row focus survives re-polls — if the chunk changes ingest cadence or push behaviour reaching the trace list, that focus-stability contract is the constraint it must not break.

## Patterns to follow
- Status/live-region pattern per a11y-plan §4 (Status / Alert row) + §7 (Live regions): `status` / `aria-live="polite"` for non-blocking progress, `role="alert"` for blocking errors; announced on change, no keyboard interaction.
- Deliberate `role="status"` omission precedent per a11y-plan §7 (Landmark roles, constellation summary): a ~1s-poll element paired with an existing dashboard live region deliberately omits `role="status"` to avoid stacked announcements — a recurring poll-driven counter should follow that reasoning rather than adding a second live region.
- Structured violation JSON per a11y-plan §3 (Structured violation JSON schema): a11y emissions ride the obs log format (`target: "a11y::assertion"`, `fields.{wcag_criterion, violation_type, severity, surface, selector, remediation, tool, tool_result_id}`) into `~/.andromeda-pulse/logs/` — the same obs schema this chunk's new field must satisfy on the obs side.
- Tauri IPC mock pattern per a11y-plan §3 (Harness wiring): a11y specs reach backend state only through `tests-a11y/helpers/mock-tauri.ts` (`TauRPC__<router.path>`) + `helpers/v02-fixtures.ts`, with `__mockReject` / `__mockDelayMs` sentinels for error and in-flight states — a "stalled consumer" UI state would be auditable via `__mockDelayMs`, not by driving real ingest.
- Suite-health check per a11y-plan §3: `npx playwright test --list` before trusting a green a11y run (a list-time import failure once silently disabled the whole suite).

## Anti-patterns to avoid
- NEVER convey the wedged/healthy distinction by color alone if it reaches the UI — text or icon supplement is mandatory (a11y-plan §11 Visual, SC 1.4.1).
- NEVER add excessive ARIA noise or a second stacked live region for a polled counter (a11y-plan §11 Screen Reader; §7 landmark-roles precedent).
- NEVER claim a11y conformance for a changed surface without machine-verifiable evidence, and NEVER defer it post-merge (a11y-plan §11 CI + Strategy).
