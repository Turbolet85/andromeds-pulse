## Constraints
- **Module-boundary errors must be logged.** `.andromeda/obs-plan.md` §10 (Standard+ invariants) requires every module-boundary error — explicitly including DuckDB errors and receiver rejections — to be logged at WARN or ERROR with trace context and an error category. The measured wedge's 0 ERROR / 0 `app.panic.fatal` is the signature of that requirement being unmet on this seam; whether the `try_send` → `ResourceExhausted` rejection path and the consumer's error arms already emit at WARN/ERROR is research's question.
- **Stall detection as the plan defines it does not cover this wedge.** §3 (Heartbeat ticks) and §10 define stall as *tick absence >45s*, enforced by the §10 CI gate (`xtask/ci/heartbeat-gap-check.sh`). A consumer wedge in which `{ingest,buffer}.tick` keep firing is liveness-positive and progress-negative, so it is outside what that mandate detects. §3's `health` complementarity paragraph requires ticks and the `health` IPC command to stay independent mechanisms — neither may be collapsed into the other. Whether §3/§10 need an amendment to name a progress-vs-liveness signal is a P4 decision this chunk must make explicitly.
- **Any new field needs its own EXACT allowlist leaf.** §8 (Default-deny posture) requires default-deny with per-module whitelists; the delegated-timing block records that for `metric.*` the invariant is *per-target-own-leaf*, because `for_target`'s first-`.`-segment fallback keeps `value` and silently redacts every label. This confirms the scope's `[inferred]` premise as a standing plan rule, not an inference.
- **The `buffer.tick` field set is restated at three sites.** §1 (Heartbeat ticks), §5 (tick-aggregated Counter rows) and §8 (`buffer` whitelist) each enumerate it; §6's `warn` row separately enumerates once-per-boot WARN targets. A single-site amendment leaves the others stale — the dual/triple-site rule is stated in the 2026-08-22 and 2026-08-24 amendment entries.
- **Emission must stay off the hot path.** §11 (Logs) bans `info`-level logging in hot paths; §5 records per-span-event / per-field emission as barred by that rule for both tick-aggregated counter families. Any progress signal on the ingest→buffer seam must be tick-aggregated or transition-scoped, not per-batch or per-span.
- **§10 bounds "stop vs slow" from the obs side.** §10 *Characterized-not-fixed* records that the append path can block a single `spawn_blocking` append >60s on a ~12.7M-row table, with the mpsc absorbing the pause, declared "degraded-but-functional, zero L0 loss, in-spec"; §10 *Load-profile constraints* set the sustained-profile drain as maintenance-tolerant with a hard 420s cap. Whichever observable half B adds must not fire on that in-spec pause — the scope's stop-vs-slow research question inherits this threshold.
- **Ingest/buffer fields are counts and bounded labels only.** §8 whitelists `ingest` → `span_count`, `service` and `buffer` → the counter set, with the standing qualifier that the tick counters are aggregate counts only, never service/span/fingerprint identity.

## Patterns to follow
- **Tick-aggregated counter as a FIELD on the existing 15s tick** (`span_events_seen` / `fingerprints_computed` / `observer_invocations`, `redactions_applied`), folded once per batch and ridden out on `buffer.tick` rather than as separate `metric.buffer.*` targets — per §5 Conceptual instrument types. This is the lowest-risk shape for a drain-progress signal.
- **The positive-reading counter-pair pattern** — §5 records that *equality* of `observer_invocations` with `fingerprints_computed` is what makes a live feed a POSITIVE reading, replacing inference from downstream silence. That is structurally the same problem as half B's "something must read `rows_ingested` and `buffer_capacity_pct` together and say so."
- **Once-per-transition WARN with bounded static `reason` + `consequence`** for a condition otherwise indistinguishable from health — §6 `warn` row: `app.boot.buffer.degraded` (fallback drains and discards ingest batches while ingest's own counters keep climbing) and `app.boot.window.navigation`. The `app.boot.buffer.degraded` rationale is the closest existing precedent to this chunk's silent wedge.
- **Exact leaf + guard test under `pulse-app/tests/`, mutation-checked** — §8 records that a src-level guard in `observability.rs`'s own `mod tests` compiles but never runs under `[lib] test = false`; every recent leaf (`unit_observability_allowlist_delegated_timing.rs`, `..._redaction_counter.rs`, `..._window_navigation.rs`) lives under `pulse-app/tests/` with a mutation result recorded.
- **`jq`-over-`agent-latest.jsonl` post-run assertion as the enforcement path**, NEUTRAL-tolerant and run-window-scoped (§10 CI gates + Load-profile constraints; `write_run_window_log`).

## Anti-patterns to avoid
- **No per-batch / per-span / hot-path `info` emission** for the new signal (§11 Logs; §5 per-field-emission bar) — a stall observable that spams the appender loop trades one defect for another.
- **No bare-prefix allowlist key** for `ingest`/`buffer`/any new family, and no reliance on `for_target`'s fallback (§8 Default-deny posture; §11 PII Scrubbing) — a prefix key widens every sibling target to one field set, and its absence silently redacts every label.
- **No raw OTLP attributes, `service_name` labels, or query text on the new field** (§11 Spans/Metrics; §8 `ingest` whitelist = `span_count` + `service` only) — counts and bounded static labels only; §11 SLO additionally bans a soft budget, so the observable must fail a gate rather than merely exist.

## Contract bindings
- **obs ↔ tests harness:** §3/§6 state the log-format JSON schema as *verbatim from the tests Test Harness Contract* and binding in that direction (obs aligns to tests). Any new field must be assertable from `agent-latest.jsonl` under that schema, with `timestamp` / `level` / `target` / `message` / `fields` plus the §3 default service-identity fields.
- **obs ↔ CI (tests-owned gates):** §10 CI gates own the heartbeat gap analysis (`xtask/ci/heartbeat-gap-check.sh`, ≤45000ms deltas per tick target). A progress-based gate is a *new* gate alongside it, and §10 Load-profile constraints require any xtask check script over `agent-latest.jsonl` to be NEUTRAL-tolerant (absent stream ≠ failure).
- **obs ↔ arch:** §10 *DuckDB Connection Isolation* is the governing invariant the scope names (write/sweep/read isolation via `Connection::try_clone()`; any multi-second consumer takes a dedicated connection). The scope's "no new backpressure policy — `try_send` → `ResourceExhausted` stays" is an arch-declared behaviour, not an obs one.
- **obs ↔ ui-bridge / tests:** §3 requires the `health` IPC command to expose the same subsystem fields synchronously for active liveness probing. If half B lands a progress field, whether `health` must carry it too follows from that complementarity clause.
- **obs ↔ security/PII:** §8 leaf registration is the security-facing half of any new field (bounded labels, aggregate counts, no identity).

## Acceptance criteria contributions
- Every field the new observable emits resolves to its OWN exact allowlist leaf enumerating the emit site's full field set, with no bare `ingest`/`buffer` prefix key introduced, and its guard test placed under `pulse-app/tests/` (per `.andromeda/obs-plan.md` §8 Default-deny posture / per-target-own-leaf rule).
- A wedged consumer — saturated channel and/or `rows_ingested` static while the feed is live — surfaces at WARN or ERROR with a bounded `error_category` / `reason` field, not only as a still-healthy tick (per `.andromeda/obs-plan.md` §10 Standard+ module-boundary error logging invariant, with the target registered at BOTH §6 log-levels mapping and §8 per the dual-site rule).
- The new emission is tick-aggregated or transition-scoped — never per-batch, per-span, or hot-path `info` (per `.andromeda/obs-plan.md` §5 tick-aggregated Counter rows and §11 Logs hot-path ban).
- The condition is caught by a machine assertion over `agent-latest.jsonl` that fails rather than reports, and does not fire on the in-spec >60s append-maintenance pause inside the 420s sustained-drain cap (per `.andromeda/obs-plan.md` §10 CI gates + §10 Characterized-not-fixed / Load-profile constraints; NEUTRAL-tolerant per the same section).
