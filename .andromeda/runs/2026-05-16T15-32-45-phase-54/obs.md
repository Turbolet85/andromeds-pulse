## Chunk relevance

## Constraints

- All `#[tracing::instrument]` decorators in `dedupe`, `anomaly`, `critical_path`, and `aggregation` modules MUST be preserved verbatim through the move; removal or drift constitutes instrumentation regression against must-trace path P2 (`snapshot.generate.request` → `duckdb.query.aggregation` → `snapshot.render.markdown`) (per obs-plan §4 Span/Trace Coverage, Scenario P2).
- Structured log `target` strings in moved modules encode the module path (e.g., `snapshot::dedupe`). After migration to `crates/curation/`, targets MUST be updated to reflect the new crate identity (e.g., `curation::dedupe`) so the JSON log file continues to be agent-greppable by module path (per obs-plan §6 Log Coverage, per-module log levels table — `snapshot` row applies to what will become the `curation` module family).
- Snapshot-curation metric events (`metric.snapshot.token_count_ms`, `dedup_count`, `anomaly_markers` fields) are emitted by the curation pipeline functions. These metric event emissions MUST survive the refactor — any silent loss of `tracing::info!(target: "metric.snapshot.token_count_ms", ...)` calls from the moved modules breaks the p99 ≤ 500ms SLO CI gate (per obs-plan §10 SLO Invariants, snapshot generation p99 budget row).
- The `snapshot` crate's external surface remains unchanged (per chunk spec). The existing `snapshot` module-level instrumentation (`info!(target: "snapshot.generate.request", ...)`) continues from the `snapshot` crate. The new `curation` crate's internal boundary calls must log at `info` (summary) / `debug` (pipeline detail) per the level discipline established for curation-adjacent logic (per obs-plan §6 per-module log levels, `snapshot` row pattern applied to the new `curation` crate).
- PII scrubbing constraints on the moved code are unchanged. The moved `aggregation` module queries DuckDB results; it MUST continue emitting `query_id` + `param_count` (NOT raw query parameter values) per logging-sensitive Vector 5 (per obs-plan §8 PII Scrubbing, DuckDB query parameters row, and §11 Anti-Patterns Logs block).

## Patterns to follow

- Span naming convention `{module}.{operation}` applies to the new crate: internal curation operations should use `curation.dedupe`, `curation.anomaly.detect`, `curation.critical_path.extract`, `curation.aggregation.compute` span names after relocation (per obs-plan §4 Span naming convention, §2 Naming conventions).
- `info` log level for boundary-call summaries (e.g., dedup count result, anomaly marker count), `debug` for internal pipeline detail (per-record processing), consistent with the existing snapshot module pattern (per obs-plan §6 Log Coverage, per-module log levels table).
- Default subscriber fields (`service.name`, `service.version`, `deployment.environment`) are registered once at subscriber init — the new `curation` crate inherits these automatically with no per-call boilerplate (per obs-plan §3 Service identity, Default subscriber fields).
- The `snapshot` crate's P2 must-trace boundary spans (`snapshot.generate.request`, `snapshot.token.count.validate`) remain in `snapshot`; the child spans for moved operations become `curation.*` spans that inherit context via `tracing::Span::current()` — this parent-child inheritance pattern is the established cross-crate span propagation model (per obs-plan §3 Trace context propagation, internal async boundaries).

## Anti-patterns to avoid

- NEVER silently drop `#[tracing::instrument(skip(...))]` decorators during module moves — missing `skip(...)` on curation pipeline functions that receive DuckDB result rows or anomaly-detected attribute values would cause PII (raw OTLP attribute values from the anomaly detection pass) to appear in span fields, violating Vector 1 (per obs-plan §11 Anti-Patterns, Spans/Traces block: "NEVER include raw OTLP attributes in span attributes").
- NEVER leave stale `target` strings in the moved modules (e.g., keeping `target: "snapshot::dedupe"` after relocating to `crates/curation/`) — stale targets break agent `jq`-filter grep-ability of the JSON log file, the sole agent-readable self-observation surface (per obs-plan §11 Anti-Patterns, Universal block: "the JSON file at `~/.andromeda-pulse/logs/agent-latest.jsonl` IS the canonical agent surface").
- NEVER add `tracing` instrumentation to the per-record tight-loop paths inside `dedupe` or `aggregation` during this refactor — the refactor is scope-neutral; over-instrumentation of hot paths (DuckDB result-row iteration, Arrow record batch iteration) contradicts the established "profile before adding spans to tight loops" rule (per obs-plan §11 Anti-Patterns, Telemetry Strategy block).

## Contract bindings

- **obs ↔ tests (snapshot P2 instrumentation):** The curation crate's moved modules are exercised by the test-plan P2 critical path ("Populate buffer with 500 synthetic spans... invokes TauRPC `snapshot.generate({token_budget: 25000})`... asserts `response.dedup_count`"). If the moved instrumentation (`dedup_count`, `anomaly_markers` span fields) is dropped, P2's post-test `jq` log assertions will produce false-pass (no matching events) — the refactor must be test-verified against P2 to confirm span emission continuity (per obs-plan §1 Critical paths table, P2 row; §10 CI gates, snapshot generation p99 gate).

If the `aggregation` module move loses the emission call, the CI gate silently passes vacuously (no events = no p99 = no assertion). This is a fragile contract: tests domain should verify event presence post-refactor, not just non-zero response (specialist plan §10 is silent on "verify event count > 0 for moved modules specifically"; orchestrator may need to surface this to user as a gap).
