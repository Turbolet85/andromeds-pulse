# obs extract

## Relevance
Relevant (partial) — obs owns the verdict surface every new stage's obs half reads and the registration cost of any new target; it owns no product behavior in this chunk.

## Constraints
- The obs half of each stage must match the app's own JSON-per-line records by `target` / `level` / `fields`, in the schema obs-plan §3 (Log format JSON schema) + §6 (Required fields) declare binding — a verdict may not rest on prose, exit status, or absence of an exception (per obs-plan §3, §6).
- Default-deny is structural: obs-plan §8 (Default-deny posture) requires an EXACT allowlist leaf per target, since `for_target`'s prefix fallback otherwise resolves a dotted target to an unrelated field set and redacts the very fields a stage would assert. A stage asserting a field on an unleafed target reads a redacted value. Whether each target the new stages want already carries a leaf is research's question (per obs-plan §8).
- Any new leaf must enumerate EVERY field its emit site emits (a partial leaf leaves the target partly redacted), must not introduce a bare prefix key that widens siblings, and — where a `metric.*` target is involved — must be its own leaf, because a bare `metric` key legitimately exists (per obs-plan §8, delegated-timing + incident-path leaf blocks).
- The widget↔dashboard↔tray path is already specified: obs-plan §4 Scenario P5 requires `ui.layout.transition` (`layout_mode_from`, `layout_mode_to`, `duration_ms`), `tray.visibility.toggle` (`tray_visible`) and `ipc.health.check` (`health.status`, `health.subsystems`). Whether the code already emits the tray and health members of that chain is research's question (per obs-plan §4 P5, §1 Critical paths P5 row).
- Tray / notification affordances are boundary-only: obs-plan §4 (Instrumentation per surface, desktop-native row) sanctions `tray.visibility.toggle` / `tray.menu.interaction` / `tray.notification.dismiss` / `tray.notification.action` and bars telemetry from OS notification-center internals — so a close-to-tray + toast stage's obs half can only rest on those boundary events (per obs-plan §4, §1 desktop-native surface row).
- Nothing observed only in the webview can reach the log directly: obs-plan §3 (Logging stack → Frontend bridge) and §1 (desktop-webview surface row) require frontend signals to travel TauRPC `telemetry.frontend.*` → backend `tracing`. This is the constraint that decides open scope question #2 — if a native context menu is unobservable to WebDriver, an obs-half verdict for it needs a backend emission with a leaf, or the stage is declined (per obs-plan §3, §1).
- Continuous window gestures are hot paths: obs-plan §11 (Logs) bars `info`-level emission per event, and §5 restates the ban for per-field emission — a drag or live-resize signal must be folded once per gesture (settle-delayed) or ridden as fields on an existing tick, never one record per `Moved` / `Resized` (per obs-plan §11, §5).

## Patterns to follow
- P5's existing chain as the template for window-mechanics stages: TauRPC command → `ui.layout.transition` → `tray.visibility.toggle` → `ipc.health.check`, each with its enumerated attribute set (per obs-plan §4 Scenario P5).
- Fields-on-an-existing-tick instead of a new target — obs-plan §5 (Conceptual instrument types) records the fold-once-per-batch, ride-out-as-`buffer.tick`-fields pattern precisely as the way to add a signal without a new target and its leaf cost.
- Once-per-boot / once-per-transition emission with bounded static labels, the discipline obs-plan §6 (Log levels, `warn` row) applies to `app.boot.buffer.degraded`, `corpus.keychain.fallback`, `triage.baseline.bootstrap_window.override`.
- Boot-readiness signals for the `launch` flake: obs-plan §1 (multi-platform-exporter-compat trigger) names `app.boot.webview.init`, `app.boot.gpu.check`, `app.boot.tray.init` as the platform startup spans, and obs-plan §3 (Complementarity with the `health` command) assigns synchronous `health` polling to boot liveness and ticks to retroactive analysis — the two must not be conflated when making the leg deterministic around a startup race.
- Bounded-label discipline for window identity: the four window labels are an enumerable set, which is what obs-plan §5 (Metric label cardinality discipline) requires of any product-internal label.

## Anti-patterns to avoid
- Per-event INFO spam on the drag/resize path — obs-plan §11 (Logs) bans hot-path `info` logging; a live-resize stage that emits one record per OS event violates it even though the record makes the stage easy to assert.
- Retry-once around the flake — obs-plan §11 (SLO) bans retry-once policies as failure-masking and names the parallel to tests' zero-flakiness invariant; "owning" the `launch` flake may not mean wrapping it in a retry.
- High-cardinality target names or labels for geometry (no per-position, per-size, per-trace-ID naming) — obs-plan §11 (Spans, Metrics) and §5 bar unbounded label cardinality and high-cardinality span names.

## Contract bindings
- **obs ↔ tests harness:** obs-plan §3 (Log format JSON schema) states the schema is verbatim from the tests plan's Test Harness Contract and that obs aligns to tests, not vice versa — the leg's obs half is a direct consumer of that shape, so any change to what a stage matches on is a change against the tests-owned contract.
- **obs ↔ tests smoke/liveness:** obs-plan §3 (Heartbeat ticks + complementarity) and §10 (Standard+ invariants) define 15s ticks, >45s = stall, and `health` as the harness's synchronous boot probe — the binding the `launch`-flake work draws on.
- **obs ↔ security:** obs-plan §8 (Data classification, plugin/query/path rows) and §11 (Spans) require basename-only, never full canonicalized paths — applies to any path-bearing field a new window or workspace-adjacent stage would assert.
- **obs ↔ CI:** obs-plan §9 / §10 define the log-artifact and gate posture. This chunk's boundary declines CI wiring, so obs adds no new CI gate here; §10's existing NEUTRAL-tolerant, run-window-scoped script rule still governs any check script the chunk touches.

## Acceptance criteria contributions
- Every new stage's obs half resolves against `~/.andromeda-pulse/logs/agent-latest.jsonl` records carrying the required `timestamp` / `level` / `target` / `message` / `fields` shape, and asserts named `fields` members — not record presence alone (per obs-plan §3 Log format JSON schema, §6 Required fields).
- Any obs target this chunk newly introduces ships an EXACT §8 allowlist leaf enumerating every field its emit site emits, introduces no bare prefix key, and is guarded by a test under `pulse-app/tests/` (not a src-level `mod tests`, dead under `[lib] test = false`) that is mutation-discriminated (per obs-plan §8 Default-deny posture).
- No new drag/resize/window signal emits per OS event at `info`; gesture signals are folded once per gesture or ridden as fields on an existing tick (per obs-plan §11 Logs, §5 Conceptual instrument types).
- The headful drive's run window contains zero `app.panic.fatal` records and no >45s gap in `ingest.tick` / `buffer.tick` / `viz.tick` (per obs-plan §10 Always-required SLO invariant + Standard+ invariants).
