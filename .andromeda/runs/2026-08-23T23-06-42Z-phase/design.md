## Relevance
**Partial** — the chunk ships no new UI, but five of its seven CARRYs assert affordances that design-system.md mandates (custom titlebar + drag region, resizable widget, browser-chrome suppression, widget↔dashboard toggle + close signpost, traces table scroll), so the stage predicates must match the design spec rather than invent one.

## Constraints
- Suppressing WebView2 browser chrome is a design **ban**, not a nicety: no visible context menu, no devtools, no text selection on non-text elements (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview). CARRY #3's stage exists to assert that ban; whether `use-suppress-browser-chrome.ts` already prevent-defaults in a **production** (non-dev) build is research's question — design only mandates the end state.
- The compact widget and full dashboard MUST both remain resizable (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview, "NEVER make the window non-resizable"). CARRY #2's 1.4–2.1 aspect band is therefore a **clamp**, not a lock — a stage that passes on "size did not change" would assert the banned state.
- The titlebar is custom-drawn at 32px with the drag region spanning full titlebar width **except** the buttons, and the compact widget carries snap-to-edge + always-on-top (per design-system.md §Surface: desktop-webview → Component Patterns → Navigation / App Shell). CARRY #1's pointer drag must originate inside that region and outside the control cluster.
- Every interactive control needs a keyboard path — Tab-navigable, `:focus-visible` always shown, plus the named shortcuts (Esc, Cmd/Ctrl+Shift+P, Cmd/Ctrl+K) (per design-system.md §Surface: desktop-webview → Focus / Keyboard Navigation and §Navigation Pattern). CARRY #4 exercises the titlebar button *and* the shortcut; design requires both routes to work, so both warrant a verdict.
- Chrome transitions are capped at 150ms hover / 200ms ease-out fade, entrance animations are none, and ALL motion must degrade under `prefers-reduced-motion: reduce` (per design-system.md §Motion and §Motion → Accessibility). Any timing tolerance the toggle stage adopts should budget against those numbers; whether the shipped `ui.layout.transition` already honors the reduce-motion override is research's question.
- The close "still running" signpost is a notification, and notifications must be OS-native, terse (≤2 lines), in the contemplative observational voice — never a web notification library, never `alert()`/`confirm()`/`prompt()`, never a UI-thread-blocking dialog (per design-system.md §Surface: desktop-native → Notifications and §Anti-Patterns → Per-Surface Bans, both surfaces).
- No new hardcoded hex or px may enter anything this chunk touches; values trace to the token tables (per design-system.md §Anti-Patterns → Universal Bans and §Self-Validation Protocol → Token Test). The scope declares no product-source change beyond a comment cleanup, so this is a guardrail on incidental drift, not new work.
- The Halo State Pulse canvas layer is SPECIFIED but measured unbuilt on desktop-webview; what ships is the constellation dot's severity hue (per design-system.md §Brand Identity → Signature element and §Motion → High-impact moments 1). No new stage may assert a halo canvas on the webview surface — build-or-retire is owned by the separate "Halo State Pulse canvas disposition" route entry.

## Patterns to follow
- **App-shell pattern** (per design-system.md §Surface: desktop-webview → Component Patterns → Navigation / App Shell): compact widget = quarter-screen, frameless, always-on-top, snap-to-edge; full dashboard = expanded window, same custom titlebar; expansion via settings icon *or* keyboard shortcut. CARRYs #1/#2/#4 are all assertions against this one pattern — keep their stage `what` text framed in its vocabulary.
- **Telemetry table pattern** (per design-system.md §Surface: desktop-webview → Component Patterns → Tables): native `<table>`, JetBrains Mono 12px tabular numerals in data cells, instant (no-transition) row hover, 1px subtle row borders. CARRY #5's internal-scroll stage should target this existing primitive; the `.trace-row` class is its row unit.
- **Icon pattern** (per design-system.md §Iconography): titlebar controls are monochrome custom glyphs (`aperture` at 20px) rendered as `<Icon glyph="…" />` — they carry no visible text, so the accessible name IS the only stable human-meaningful anchor. That is the design-side reason CARRY #9's re-point onto accessible names is the more durable selector, matching the scope's own "preference change, not repair" reading.
- **Footer/summary-line pattern** (per design-system.md §Surface: desktop-webview → Navigation Pattern → Compact widget, item 3): the widget footer is read-only status text with no interactions. CARRY #7's connection-status line stage should assert presence/content, not interactivity.
- **Empty + honest-error state pattern** (per design-system.md §Surface: desktop-webview → Component Patterns → Loading / Empty States): shared `EmptyState` with decorative glyph + Secondary-token message, error variant checked BEFORE the empty branch. The leg's already-shipped `empty-states` stage rests on this; the chunk does not re-verify it, and new stages must not contradict it.

## Anti-patterns to avoid
- Do NOT resolve a failing suppression probe by relaxing the suppression — visible WebView2 context menu / text selection on non-text elements is a standing ban (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview). If the native menu is unobservable to WebDriver, decline the stage with a recorded reason rather than weaken the product side.
- Do NOT introduce any web-style dialog or notification path while asserting the close signpost — no `alert()`/`confirm()`/`prompt()`, no web notification library, no blocking modal (per design-system.md §Anti-Patterns → Per-Surface Bans, desktop-webview + desktop-native).
- Do NOT let harness fixtures, injected styles, or stage detail strings carry raw hex/px or banned font families (Inter, Roboto, Arial, Helvetica, Open Sans, Lato, system-ui, Space Grotesk) (per design-system.md §Anti-Patterns → Universal Bans).

- **design ↔ tests** — the design→tests handoff already enumerates motion lint targets (150/200/250/350ms, ease-out / ease-in-out) and the 7 motion hard-limit bans plus the banned-font list for static lint; this chunk's new stages are the **headful** counterpart to that static surface and should not restate it (per design-system-amendments.md §Downstream Readiness → For tests specialist).
- **design ↔ obs** — obs may instrument transitions into/out of loading/error visuals without touching visual tokens; the halo frequency/color hooks named in the handoff have no webview render site to fire from today, so this chunk should not open an obs allowlist leaf for halo (per design-system-amendments.md §Downstream Readiness → For obs specialist; design-system.md §Brand Identity → Signature element).

- (design) The browser-chrome stage asserts the ban **positively** — the native context menu never appears and/or the event is `defaultPrevented` — and never records a pass from "the press threw no exception" (per design-system.md §Anti-Patterns → Per-Surface Bans → desktop-webview).
