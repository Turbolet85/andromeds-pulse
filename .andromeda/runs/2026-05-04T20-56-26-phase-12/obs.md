## Patterns to follow

- Frontend-side telemetry pattern: capture in JS (`performance.now()` / `requestAnimationFrame` callback) → TauRPC `telemetry.frontend.record_*` command → backend `tracing::info!(target: "metric.{name}", ...)`; this is the unified self-observation surface (per obs-plan §1 desktop-webview row + §3 Logging stack frontend bridge).
- Cardinality discipline for any motion-mode label: `motion_mode` field bounded to enumerated `{full, reduced}` (default-deny posture; no per-user / per-session labels) (per obs-plan §5 metric label cardinality discipline + §11 Metrics "NEVER use unbounded label cardinality").

## Anti-patterns to avoid

- NEVER emit `tracing::info!` per-frame at info level from the canvas frame loop — at 60 Hz this generates 3,600 log lines/min and saturates the JSON file sink; the existing `metric.webgpu.frame_duration_ms` event is already at info level by spec, but any ADDITIONAL per-frame instrumentation this chunk wires (e.g., motion-state transition logging) MUST be at `debug` or below, level-gated (per obs-plan §11 Logs "NEVER log in hot path at info level" + Metrics "level-gating in hot paths").
- NEVER bypass the TauRPC bridge with direct browser file access or a browser-side OTel SDK shim for motion telemetry (per obs-plan §11 Universal "NEVER link an OTel SDK into the product's self-observation runtime").
- NEVER hardcode the reduced-motion mode value into `service.name` / `deployment.environment` default subscriber fields — those are compile-time-stable identity per obs-plan §3 Service identity; motion-state belongs in per-event field map.
