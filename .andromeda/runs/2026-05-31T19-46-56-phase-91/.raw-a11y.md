The a11y-relevant surfaces are: (a) the new conditionally-visible "Send to agent" button in the Diagnostic Report toolbar (chunk #88 surface, alongside existing "Copy markdown"); (b) optionally an `[mcp.enable]` toggle control in the existing Settings modal. Both are desktop-webview (Assertable per a11y plan §1).

## Constraints

- The "Send to agent" button MUST be a native `<button>` with an accessible name (visible text label preferred; `aria-label` only if icon-only) carrying `aria-busy` during the async send; activatable by Enter / Space (per a11y plan §4 Button pattern row + SC 4.1.2 Name, Role, Value).
- Conditional visibility ("visible only when MCP configured AND agent connected") MUST be implemented by conditionally rendering / removing the button from the DOM, NOT by `aria-hidden="true"` on a still-focusable element and NOT by leaving it in the tab order when hidden (per a11y plan §11 Screen Reader: "NEVER hide important content from assistive tech … axe-core `aria-hidden-focus` rule catches elements hidden from SR but focusable"). If a disabled-state variant is chosen instead of removal, the disabled button must still expose its name/role/state (per a11y plan §11 ARIA conflicting-states ban).
- Button placement in the Report toolbar MUST preserve natural left-to-right / top-to-bottom focus order alongside the existing "Copy markdown" action; no `tabindex > 0` (per a11y plan §5 focus order + §11 Keyboard ban on positive tabindex).
- The button's `:focus-visible` state MUST render the `--border-focus` token outline meeting ≥3:1 non-text contrast; never `outline: none` without a replacement indicator (per a11y plan §6 Focus ring tokens, §11 Keyboard, SC 2.4.7 + SC 1.4.11).
- Button label/icon text MUST meet SC 1.4.3 4.5:1 contrast against its background and, if state is signaled by color (e.g., connected-active accent), it MUST be paired with text or icon — not color alone (per a11y plan §6 Color contrast pairs + §1 visual-discrimination trigger, SC 1.4.1 / SC 1.4.3).
- Interactive target area for the button MUST be ≥24×24 CSS px per `--target-button-min` (per a11y plan §6 Target size tokens + §1 target-size trigger, SC 2.5.8).
- If an `[mcp.enable]` control is added to the Settings modal, it MUST follow the Switch pattern (native checkbox or Headless UI Switch, `aria-checked`, Space toggles, focus stays on switch) with an associated `<label>`, and slot into the existing settings-modal Tab order without breaking the Esc-closes-restores-focus trap (per a11y plan §4 Switch row + §5 settings-modal focus order + §3 critical path P3/P7).

## Patterns к follow

- Reuse the existing chunk #88 Report-toolbar button pattern ("Copy markdown") for the new "Send to agent" button — same native `<button>` + `aria-busy` async convention (per a11y plan §4 Button pattern catalog).
- Settings modal `[mcp.enable]` toggle, if added, mirrors the existing P3/P7 MCP-toggle Switch already specified for the settings modal — Tab-to-switch, Space toggles, focus remains on switch (per a11y plan §3 critical path P3 + §5 settings-modal focus order).
- Semantic HTML first, ARIA second — do not add `role="button"` to the native `<button>`; do not add redundant ARIA to native form controls (per a11y plan §11 ARIA + §2 Robust row eslint-plugin-jsx-a11y gate).
- Modal focus trap unchanged: if the Report renders inside a dialog, the new button participates in the existing focus trap with Esc-closes-restores-to-trigger behavior; do not introduce a second trap (per a11y plan §5 Focus trap + Focus restoration).

## Anti-patterns к avoid

- NEVER hide the conditionally-rendered "Send to agent" button via `aria-hidden="true"` or CSS `display`/visibility while leaving it focusable in the tab order — remove from DOM when not configured/connected (per a11y plan §11 Screen Reader, `aria-hidden-focus`).
- NEVER signal "agent connected" state by color alone — pair with text/icon (per a11y plan §11 Visual, SC 1.4.1).
- NEVER suppress the focus indicator (`:focus { outline: none }` without `--border-focus` replacement) on the new button (per a11y plan §11 Keyboard, SC 2.4.7).
- NEVER ship lint-only a11y for the new surface — runtime axe-core / Lighthouse / pa11y must cover the rendered button (per a11y plan §11 CI).
