## Constraints

- Self-observation runtime is `tracing` 0.1 + `tracing-subscriber` 0.3 JSON + `tracing-appender` daily + `tracing-error` SpanTrace ONLY. The new poller, LastIngestTracker, TauRPC handler, and panic-hook integration MUST NOT introduce an OTel SDK Meter / Counter / Gauge or any opentelemetry-rust SDK runtime dependency (per obs-plan §1 Standard tier justification + §3 Tracing init "NO OTel SDK linked into the product binary for self-observation" + §11 Universal anti-pattern row 4).
- The 1-2s poller is a long-running subsystem and MUST emit a heartbeat tick `tracing::info!(target: "connection.tick", state=<enum>, last_span_ago_ms=N, "heartbeat")` on a `tokio::time::interval` rhythm so stall detection (>45s gap) works; per-tick payload fits the existing heartbeat tick format (per obs-plan §3 Heartbeat ticks + §1 telemetry triggers heartbeat row). If tick frequency is sub-15s (matching the 1-2s poller), pick a separate cadence than `ingest.tick` so the heartbeat budget isn't doubled, but keep emission strictly bounded к tick events (not per-poll-with-no-change).
- Every state transition (Listening → Receiving / Receiving → Idle / Idle → Stalled / ReceiverFailed) MUST emit a structured `tracing` event with `from_state` + `to_state` + `last_span_ago_ms` + `trigger_reason` fields at `info` (normal transitions) or `error` (panic-triggered ReceiverFailed) level — boundary state transitions are the must-log category per obs-plan §6 Log levels + §10 Standard+ invariants Module-boundary error logging.
- The LastIngestTracker update MUST live in the ingest hot path WITHOUT introducing a `tracing` event per ingest call — atomic store on every OTLP receive is acceptable, but `tracing::info!` per receive would violate the "NEVER log in hot path at info level" anti-pattern (per obs-plan §11 Logs row 4 + §11 Telemetry Strategy row 1 over-instrumentation ban). Per-receive observability comes from existing `otlp.grpc.export.request` / `otlp.http.export.request` spans, not from the tracker.
- Receiver-task panic-hook MUST flow through the existing `std::panic::set_hook` → `tracing::error!(target: "app.panic.fatal", ...)` + `tracing-error` SpanTrace path; if the panic-hook also drives a `ReceiverFailed` state transition emission, that transition is а SECOND event (sanitized fields only: `from_state`, `to_state="ReceiverFailed"`, NO panic_message in the transition event since `app.panic.fatal` already carries it). Per obs-plan §7 Panic hook + §10 SLO zero-unlogged-panics + §11 Errors row 4 ("local panic hook + tracing::error log MUST always work").
- The new TauRPC procedure `connection.current_state` MUST instrument with `#[tracing::instrument(skip_all, fields(traceparent = %tp))]` and return sanitized state — the response payload may include `last_span_ago_ms` numeric but MUST NOT include raw OTLP attribute values or upstream client identifiers (per obs-plan §3 Trace context propagation IPC boundaries + §5/§6/§11 redaction discipline for any field derived from external client telemetry).

## Patterns to follow

- Long-running subsystem heartbeat pattern: `tokio::time::interval(...)` loop emitting `tracing::info!(target: "{module}.tick", ...)` with module-specific gauge fields. Mirrors `ingest.tick` / `buffer.tick` / `viz.tick` / `plugins.tick`; new `connection.tick` slots into the existing family (per obs-plan §1 telemetry triggers + §3 Heartbeat ticks + §10 Standard+ invariants heartbeat row).
- Boundary-call span wrapping pattern: existing TauRPC routers carry `#[tracing::instrument(skip_all, fields(traceparent = %tp))]` so trace context propagates from IPC envelope into the handler. Apply identically to `connection.current_state` resolver (per obs-plan §3 Trace context propagation IPC boundaries + §4 Instrumentation per surface IPC-internal row).
- Broadcast channel emission pattern: existing `pulse://stream/{spans,metrics,logs,snapshot-progress,plugin-events}` topics emit via `tracing::info!(target: "tauri.channel.emit", channel_name=..., ...)` boundary span carrying schema attestation (`schema_match` field). Apply identically to `pulse://stream/connection-state` emission — payload schema validated at emission time, attribute on the same emit span (per obs-plan §4 P6 scenario `tauri.channel.emit` cleanup pattern + §1 telemetry triggers cross-surface-trace-propagation row).
- Default subscriber fields propagation: `service.name=com.andromeda.pulse` + `service.version` + `deployment.environment=production` are attached at subscriber init via `Layer::with_default_fields(...)`. New code does NOT need к re-pass these on each emission (per obs-plan §2 Naming conventions Default subscriber fields).
- Panic-hook to-tracing pattern: existing `std::panic::set_hook(Box::new(panic_to_tracing_error))` at boot. Wiring а receiver-task panic к flow through this hook (rather than catching the panic inline в the receiver task) preserves the zero-unlogged-panics SLO automatically (per obs-plan §7 Panic hook 5-line snippet + §10 always-required SLO row).

## Anti-patterns to avoid

- NEVER `tracing::info!` on every ingest hot-path call (the LastIngestTracker update is per-receive; logging at that frequency is the documented over-instrumentation ban). Atomic store only; rely on poller + spans for observability (per obs-plan §11 Telemetry Strategy row 1 + §11 Logs row 4).
- NEVER emit `connection.tick` events at the 1-2s poller cadence if the state has not changed AND the heartbeat interval is sub-15s — would multiply log volume by an order of magnitude versus existing ticks. Either emit ticks at the same 15s cadence as siblings (with last_span_ago_ms snapshotted) AND emit а separate state-transition event ONLY when state actually changes, OR use the 1-2s poller exclusively for change-detection and rely on the existing 15s heartbeat budget. Per obs-plan §11 Metrics row 1 (cardinality / volume discipline) + §3 Heartbeat ticks cadence convention.
- NEVER include raw last-seen OTLP attribute values, client IPs, or upstream client `service.name` strings в the `connection.current_state` response, `pulse://stream/connection-state` payload, or any `connection.tick` field — the connection state is the product's own runtime telemetry, but any field derived from upstream client telemetry inherits Vector 1 scrubbing (per obs-plan §11 Spans row 1 + §11 Project-specific row 4 surface separation).
- NEVER use а high-cardinality label like `last_span_trace_id` on the connection-state span / tick / TauRPC payload — `trace_id` is unbounded by definition and would explode the JSON file (per obs-plan §11 Spans row 2 + §11 Metrics row 1).
- NEVER allow the receiver-task panic к terminate the poller / TauRPC handler silently; if the panic-hook fires AND the receiver task exits, the poller MUST transition к `ReceiverFailed` state on the next tick (or sooner if signaled) — silent disconnect violates §10 zero-unlogged-panics invariant + §11 SLO row 1.
