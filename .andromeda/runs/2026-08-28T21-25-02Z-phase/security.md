## Constraints
- The repair site is the write boundary the scrub mandate names. `security-plan.md` §Security Anti-Patterns → Logging mandates that five persisted client-controlled ring-buffer cells (`spans.service_name` via the `extract_service_name` choke point, `span_events.name`, `metrics_points.metric_name`, `log_records.severity_text` via push-site `scrub_otlp_field`, and `metrics_points.labels` via the joined `key=value` ∪ bare-value shape) pass the scrubber before write, and asserts `append_record_batch_to_table` is the ONLY DuckDB write path in `crates/buffer`. Any fallback/quarantine/per-row retry path the repair introduces MUST carry the same coverage, or that enumeration claim goes stale. Whether the repaired path preserves all five is research's question (per security-plan §Security Anti-Patterns → Logging).
- The loud failure must not echo content. §Logging & Monitoring → What NEVER to log bans raw OTLP attribute values, span/log/metric content payloads, and DuckDB query parameter values ("log query identifier + parameter count instead"). A per-batch reject may report table, counts, and a bounded reason only — never the rejected rows' client-controlled column values, and never a raw DuckDB constraint-error string that echoes the conflicting key (per security-plan §Logging & Monitoring + §Security Anti-Patterns → Logging).
- A returned error must be sanitized at the boundary it crosses. §Error Handling requires module-internal `thiserror` enums to collapse to the `serde`-friendly `AppError::{Storage, Ingest}` variants, with no stack traces, Rust struct names, file paths, or library versions in what reaches the webview (per security-plan §Error Handling + §Security Anti-Patterns → Logging).
- Any SQL the repair introduces (e.g. a conflict-tolerant or per-row insert as the "connection stays usable" fork) must use `Connection::prepare` with `?` placeholders; identifier interpolation is banned outright and table/column names are spec-fixed, never input-named (per security-plan §Input Validation, DuckDB query-parameters row + §Security Anti-Patterns → Input).
- The ring buffer must remain the in-memory `:memory:` `pulse_buffer` connection. A repair that recreates or reconfigures the connection must not make it disk-backed and must not enable DuckDB at-rest encryption (CVE-2025-64429 is banned surface) (per security-plan §Data Protection → At rest, DuckDB ring buffer + §Security Anti-Patterns → Data Protection).
- Item 2's cross-restart identity source is a new input boundary if it is externalized. §Input Validation requires an env var to take a bounded, whitespace-trimmed parse with a graceful default and never a panic, and a persisted state file to take a bounded read + graceful default + atomic `.tmp`+rename with canonicalize-and-confine on write — and either MUST be added to the boundary enumeration, which claims to be the complete list. Changing `trace_id`/`span_id` derivation also leaves the receive-side post-`prost`-decode invariant (16-byte trace_id, 8-byte span_id) in force (per security-plan §Input Validation + §Security Anti-Patterns → Input).
- Dependencies added for identity generation or error handling must clear `cargo deny check bans licenses sources`; `multiple-versions = "deny"` is never relaxed, the `tonic` canary is never skipped, and any new duplicate carve-out must be ID-scoped, owner-named and reasoned in `deny.toml [bans] skip` with its closing condition (per security-plan §Dependency Security → CI integration + §Bootstrap phases `dep-audit-tooling-install`).

## Patterns to follow
- Bounded-category failure labels: the `validate_prompt_bounded` → `PromptRejection::label()` shape, where the only thing reaching the log is a bounded category, and the `interpretation.inference.error` leaf carrying `io_error` / `stdout_utf8_invalid` as categories with no output bytes. This is the plan's existing template for "fail loudly without disclosing payload" (per security-plan §Input Validation, L4-argv row + §Security Anti-Patterns → Code Patterns).
- The three scrub shapes already established in `crates/buffer/src/appender.rs`: choke-point (`extract_service_name`, one fn feeding three consumers), push-site (`scrub_otlp_field`), and joined `key=value` ∪ bare value for `metrics_points.labels`. A new write path should reuse the shape appropriate to its consumer count rather than inventing a fourth (per security-plan §Security Anti-Patterns → Logging).
- Bounded-parse-with-graceful-default registration precedent for anything item 2 externalizes: `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` (env), `<data_dir>/window-geometry.json` (self-written file, corrupt ⇒ default, no panic), `<data_dir>/run/workspace-key` (cross-process file, bounded + UTF-8 + control-char reject ⇒ `None` fallback) (per security-plan §Input Validation).
- Deferred-gate discipline: `cargo deny check advisories` is the named overlap signal standing in for the unrunnable `cargo audit`, and a between-point wrap re-verifies basis + overlap and records the skip explicitly — never silently (per security-plan §Dependency Security → CI integration, Standing deferral).

## Anti-patterns to avoid
- NEVER `format!("… WHERE x = '{}'", …)` against the `duckdb` `Connection` — prepared statements with `?` binding only, for any SQL the constraint-violation repair adds (per security-plan §Security Anti-Patterns → Input).
- NEVER surface raw OTLP attribute values, content payloads, or DuckDB parameter values in the `duckdb.append` ERROR, the `reject_reason` field, or any new failure leaf; NEVER expose stack traces / struct names / file paths in `AppError::Internal { message }` (per security-plan §Security Anti-Patterns → Logging).
- NEVER enable DuckDB at-rest encryption on the ring buffer, and do not reach a "usable connection" by giving it a disk path (per security-plan §Security Anti-Patterns → Data Protection).
