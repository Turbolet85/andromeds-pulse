## Chunk relevance

- route#4 "xtask agent-run harness — 5-command discipline (boot/run/status/cleanup/logs) + health TauRPC command (status/subsystems/pid/uptime_ms) + PID file + JSON log format" — relevant. Touches three security surfaces: (1) introduces the first TauRPC procedure (`health`) requiring capability JSON entry + `AppError` boundary; (2) writes a PID file under the per-platform data dir requiring path canonicalization; (3) wires the JSON log format that the `logging-redaction-wire` bootstrap phase pivots on; (4) the `xtask` harness spawns the `pulse-app` binary, hitting the `Command::arg(user_input)` ban for any string sourced from env/CLI.

## Constraints

- The `health` TauRPC procedure MUST be registered in BOTH the owning `ui-bridge` router AND `pulse-app/capabilities/default.json` — Tauri 2 capabilities are negative-default; missing entry = silent runtime rejection (per security plan §API Security TauRPC capability authorization + §Anti-Patterns API ban "NEVER add a TauRPC procedure to a router crate without a matching entry in `pulse-app/capabilities/`").
- The `health` procedure MUST return `Result<HealthEnvelope, AppError>` — `AppError` is the `serde`-friendly enum (`Validation`/`NotFound`/`Internal`/`Plugin`/`Storage`/`Ingest`); module-internal `thiserror` 2.x errors convert via `From` impls; never serialize `anyhow::Error` directly across the bridge (per security plan §Error Handling TauRPC bridge + §Anti-Patterns Code Patterns ban).
- PID file path resolution MUST canonicalize via `strict-path` and assert the resolved path lives under the resolved per-platform data dir (or under `ANDROMEDA_PULSE_DATA_DIR` override) before write — CWE-22 path-traversal class defense (per security plan §Input Validation env-var row + §Anti-Patterns Input ban "NEVER read `ANDROMEDA_PULSE_*_PATH` / `*_DIR` env vars without `std::path::Path::canonicalize()` + an assertion").
- The `xtask` agent-run harness MUST NOT pass any externally-sourced string (CLI args, env vars not under the project's control) into `tokio::process::Command::new(...).arg(...)` without prior validation — MCP STDIO command-injection class (CVE-2025-49596 / CVE-2025-54994 / CVE-2025-54136 / CVE-2026-22252) (per security plan §Anti-Patterns Code Patterns ban).
- JSON log format MUST apply field redaction at the `tracing-subscriber` Layer (not at log call sites) and the NEVER-log list MUST be enforced from day 1: no full plugin paths, no DuckDB query parameters, no OTLP attribute values, no clipboard contents, no MCP response bodies, no stack traces / Rust struct names / file paths / library versions in any error surfacing (per security plan §Logging & Monitoring "What NEVER to log" + `logging-redaction-wire` bootstrap phase).
- The `health` envelope MUST sanitize internal subsystem identifiers to the stable Standard-Contract strings (`otlp_grpc_receiver`, `otlp_http_receiver`, `buffer`, `ingest_channel`); failure reasons MUST collapse to short strings with no Rust struct names, file paths, or library versions (per security plan §Error Handling external responses + §Anti-Patterns Logging "NEVER expose stack traces, Rust struct names, file paths, or library versions").
- `xtask` MUST NOT launch the `pulse-app` binary with secrets passed as CLI args or in env vars that would land in the JSON log stream — secrets continue to live in Azure Key Vault / GitHub Environment `production-release` only; nothing the harness boots leaks into local logs (per security plan §Secret Management "Never in code" + §Anti-Patterns Secrets bans).

## Patterns to follow

- TauRPC procedure pattern with `AppError` boundary: every `#[taurpc::procedure]` returns `Result<T, AppError>`; module-internal `thiserror` 2.x enums collapse to `AppError::{Validation, NotFound, Internal, Plugin, Storage, Ingest}` at the bridge via `From` impls (per security plan §Error Handling TauRPC bridge + Conventions Error response schema).
- Path env-var canonicalization pattern: any `ANDROMEDA_PULSE_*_PATH` / `*_DIR` env var (here `ANDROMEDA_PULSE_DATA_DIR` for PID file location) flows through `strict-path` canonicalize + confine-under-data-dir assertion before any I/O — same pattern that plugin loader (route#7-block) and config loader will reuse (per security plan §Bootstrap phases `input-validation-library-install`).
- Capability-JSON pairing pattern: the `xtask capability-drift` task (which lands here as part of agent-run discipline) introspects `taurpc` derives and diffs against `pulse-app/capabilities/*.json`; CI fails on mismatch — same enforcement covers every future TauRPC procedure (per security plan §Bootstrap phases `dep-security-ci-gate` xtask drift check + §API Security capability authorization).
- Structured-logging redaction pattern: `tracing` + `tracing-subscriber` JSON layer with redaction filter applied at the subscriber, not at call sites — keeps NEVER-log enforcement uniform across all crates (per security plan §Logging & Monitoring "Field redaction is applied at the subscriber layer").

## Anti-patterns to avoid

- NEVER expose stack traces, file paths, Rust struct names, or library versions in `AppError::Internal { message }` content surfaced to the webview via `health` — full chain stays in internal log via `tracing-error` SpanTrace; sanitize at the `From<thiserror::Error> for AppError` impl (per security plan §Anti-Patterns Logging).
- NEVER read `ANDROMEDA_PULSE_DATA_DIR` (resolving the PID file path / log file path) without `Path::canonicalize()` + assertion the canonical path starts under the resolved per-platform data dir — CWE-22 traversal class (per security plan §Anti-Patterns Input).
- NEVER `tokio::process::Command::new(...).arg(user_input)` against any string sourced from env vars, CLI input, or workspace-detector output in the `xtask` harness — covers `xtask agent-run boot` / `run` / `status` / `cleanup` / `logs` subcommand argument handling (per security plan §Anti-Patterns Code Patterns).
