## Patterns to follow

- Cross-cutting envelope procedure shape: `health` is a top-level bare `snake_case` verb (no `<router>.<verb>` prefix), grouped with `app_info` / `ready` / `get_settings` / `update_settings` and owned by the `ui-bridge` crate (per architecture.md §Conventions "Endpoint naming" + §Occupied Resources "Tauri IPC routes").
- Subsystem key naming inside the `subsystems` map mirrors the existing examples in §Standard Contracts: `otlp_grpc_receiver`, `otlp_http_receiver`, `buffer`, `ingest_channel` — additions for chunk-#4 (e.g., a process-uptime descriptor) extend the same `snake_case` shape rather than introducing camelCase or kebab-case.
- Module-internal error types are `thiserror` 2.x enums; the `xtask` binary uses `anyhow::Result` at top-level (`main`) per architecture.md §Established Decisions "[Error Handling Pattern]" and §Conventions "Error response schema (Tauri IPC)" — `xtask` is non-IPC, so `anyhow` is the boundary, not `AppError`.
- `xtask` lives at workspace root alongside `pulse-app/` (per the architecture.md §Infrastructure Patterns project directory structure tree); its subcommand surface is the contributor-facing parity layer for CI steps so contributors can run identical commands locally.
- Module dependency direction: `xtask` may depend on workspace member crates downward (toward leaves) but no library crate depends on `xtask` or on `pulse-app`; the dependency graph is a DAG with `pulse-app` as the only binary-crate root (per architecture.md §Cross-cutting Patterns "Module dependency direction").
- Configuration precedence applies to harness inputs as well: env vars (`ANDROMEDA_PULSE_*`, `RUST_LOG`) > user `config.toml` > built-in defaults (per architecture.md §Cross-cutting Patterns "Config management" + §Occupied Resources reserved env var list).
- The `agent-driven` development style explicitly calls out "deterministic harness invocations, machine-parseable outputs, schema-stable contracts, `cargo xtask` task surfaces" — chunk-#4's status output and JSON log format are downstream of this principle (per architecture.md §Cross-cutting Patterns "Development Style").

- Do not rename the `xtask` crate, the `health` procedure, or any of the four locked subsystem keys exemplified in the §Standard Contracts JSON; the canonical names are reserved and renaming requires a scope-arch event, not an in-chunk decision.
- Do not introduce an OTel SDK or OTLP network exporter to emit the JSON logs — pointing the product's own telemetry exporter at its own `:4317`/`:4318` is the architecturally-banned infinite-loop pattern (per architecture.md §Established Decisions "[Self-Observation]").
