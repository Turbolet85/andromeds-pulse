# obs extract

## Relevance
partial — the chunk changes prompt/digest TEXT and adds a real-model reading leg; obs-plan owns no part of the framing itself, but it bounds what the triggering service may touch on the self-observation wire and names the log signals the reading leg leaves behind.

## Constraints
- The triggering service is client-controlled OTLP content: obs-plan §8 PII Scrubbing (Default-deny posture) requires that it reach no `tracing` field on the L4 path. The `interpretation.incident.created` and `interpretation.incident.skipped` leaves each state a ban on `scope_id`, incident identity, title, digest, prompt and model text; the `triage.cue.tick` leaf bans `scope_id` and a service name. Moving the service onto the trigger line or into the framing instruction must add it to none of these records.
- obs-plan §11 Metrics bans unbounded label cardinality, and §5 Metric label cardinality discipline scopes the one `service_name` exception to the two query-time aggregation metrics only. A per-generation or per-digest record labelled with the triggering service is outside that exception.
- If the chunk adds or changes ANY emitted field or target (for example a bounded label saying whether the trigger line carried a service part), obs-plan §8 Default-deny posture requires an EXACT allowlist leaf carrying every field the emit site emits, with no bare `interpretation` / `triage` / `triage.cue` prefix key. Whether the chosen form needs any new field at all is the plan's to decide; the scope names none.
- obs-plan §10 Performance budgets (L4 constrained inference row) sets the per-profile p99 budget on `metric.pipeline.l4.inference_latency_p99_milliseconds`, whose `duration_ms` spans prompt assembly + generation. The trigger framing lies inside that timed scope, so the reading leg's log family is where the budget is read for the changed prompt; the row requires `hardware_profile` and a numeric `duration_ms` on every record (a record missing either FAILS the grader, never dropped).
- obs-plan §8 (Muted-diagnostic backlog bullet) records ONE open recurrence: `interpretation.constrained.generate` renders `raw_output_bytes` and `extracted_bytes` redacted, owned by the route entry "L4 generation records render unredacted". The scope's Boundaries put that entry outside this chunk, so a real-model leg's log is expected to carry that redacted pair and this chunk does not repair it.
- obs-plan §6 Log Coverage (Required fields, Log levels mapping) governs any record the chunk touches: the JSON-per-line shape, `target`, a `message` under the stated length, level by the mapping. obs-plan §11 Logs bans `info`-level emission on a hot path, so a per-cue or per-digest-line record is barred; a fold onto an existing per-cycle or per-generation record is the allowed shape.
- obs-plan §10 Always-required SLO invariant (zero unlogged panics) applies to the reading leg's run as to any run.

## Patterns to follow
- Exact-leaf + field-set-equality guard, placed under `pulse-app/tests/` where it runs: obs-plan §8 Default-deny posture describes it per leaf (resolve pin, set equality in BOTH directions, banned-field loop, no-bare-prefix discriminator) and records why a resolver-only probe cannot guard a partly redacted leaf. Any leaf this chunk adds or completes follows it.
- Bounded-label reporting of an L4 outcome: obs-plan §8 `interpretation.incident.skipped` and `interpretation.incident.created` leaves are the precedent — closed labels and bools only, emitted once per cleanly-parsed generation. They are the log's account of whether a generation in the reading leg formed an incident at all, which qualifies the reading's n without any model text on the wire.
- Transition-only emission for the generation damper: obs-plan §8 `interpretation.generation.damper` leaf (once per engage / release, with `reason` drawn from a closed set that includes an unchanged-digest value). Whether the trigger line's text takes part in the damper's unchanged-digest comparison, and so whether the new service part changes engage/release behaviour in the reading leg, is research's question.
- Tick-aggregated counters as FIELDS on an existing heartbeat rather than new per-event targets: obs-plan §5 Metric Coverage (Conceptual instrument types, the tick-aggregated rows) and the §8 `metric.pipeline.l4.backoff_remaining_seconds` leaf.
- Real-model leg latency grading by nearest-rank p99 per profile with the dev-host scripts, not CI: obs-plan §10 Performance budgets (L4 row).

## Anti-patterns to avoid
- Logging the trigger line, the framing instruction, the digest, the prompt, the first hypothesis or any other model text to make the reading "visible in the log" — banned by obs-plan §8 (`interpretation.incident.skipped` leaf's field bans) and §11 Logs / §11 PII Scrubbing (default-deny; raw OTLP-derived values never logged).
- Adding the triggering service (or `scope_id`) as a label on a metric or tick record — obs-plan §11 Metrics, §5 Metric label cardinality discipline.
- Registering a bare `interpretation` or `triage` prefix key, or narrowing an existing leaf below its emit site, to get a new field through — obs-plan §8 Default-deny posture (the `interpretation.incident.created` entry's recorded rationale).

## Contract bindings
- obs ↔ tests (the reading's evidence source): obs-plan §8 keeps hypothesis text, digest and prompt off the self-observation log, so the pre-registered bar cannot be graded from `agent-latest.jsonl*`; the hypothesis text has to be read from the product's incident surface, and the log contributes only the bounded outcome labels above. Which surface the leg reads is the test domain's and the plan's.
- obs ↔ tests (latency grader): the dev-host scripts `xtask/ci/l4-latency-p99.{sh,ps1}` consume the leg's log family per obs-plan §10 Performance budgets (L4 row); the `.ps1` half's owed run is recorded there against test-plan §1 `l4-latency-p99-ps1-run-coverage` and is not this chunk's.
- obs ↔ tests (guard placement): any allowlist guard lives under `pulse-app/tests/`, per the `[lib] test = false` rule obs-plan §8 cites on each leaf.
- obs ↔ security: obs-plan §8 PII Scrubbing (Data classification rules, raw OTLP telemetry row) binds to security-plan §Logging & Monitoring; the service name's scrub before it reaches the argv is the security domain's statement, not this plan's.
- obs ↔ route: the open `interpretation.constrained.generate` redaction is owned by the route entry "L4 generation records render unredacted" per obs-plan §8 (Muted-diagnostic backlog bullet).

## Acceptance criteria contributions
- The chunk's diff adds the triggering service, `scope_id`, trigger-line text, prompt text or hypothesis text to NO `tracing` field; across the reading leg's log family the triggering service's name appears 0 times in any `interpretation.*` or `triage.cue.tick` record (per obs-plan §8 PII Scrubbing, Default-deny posture)
- Every record the leg's log carries on `interpretation.incident.created`, `interpretation.incident.skipped` and `interpretation.generation.damper` renders its declared fields unredacted; the only `<redacted>` fields accepted on the L4 path are `raw_output_bytes` and `extracted_bytes` on `interpretation.constrained.generate`, the recorded open recurrence (per obs-plan §8 Default-deny posture, Muted-diagnostic backlog bullet)
- The leg's `metric.pipeline.l4.inference_latency_p99_milliseconds` records each carry `hardware_profile` and a numeric `duration_ms`, and the per-profile nearest-rank p99 reads within its budget under the dev-host grader — reported with its n, as a reading of the changed prompt (per obs-plan §10 Performance budgets, L4 constrained inference row)
- The leg's log family carries 0 `app.panic.fatal` records (per obs-plan §10 Always-required SLO invariant)
