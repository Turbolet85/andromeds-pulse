# security extract

## Relevance
partial — the chunk moves an OTLP-derived value (the triggering cue's service name) into the trigger framing of the L4 prompt, which is the one product path the plan admits from OTLP-derived text to a subprocess argv; no new IPC procedure, port, env var, capability, dependency or persisted shape is in scope.

## Constraints
- The service name is client-controlled content: any local process can post telemetry on the loopback receivers, so the value placed in the trigger framing is untrusted input, not first-party text (per security-plan §Threat Model Summary → Data classification, sensitivity note; → Attack surface, OTLP vector).
- security-plan §Input Validation (row "L4 inference argv prompt") requires OTLP-derived content in the `-p` operand to stay confined to the regions that row enumerates. A service name rendered on the digest's `TRIGGER:` line is inside that confinement only if the line is part of the digest payload; whether it is rendered there is research's question. A service name interpolated into the framing INSTRUCTION (the first-party template in `crates/interpretation/src/prompt.rs`) would put OTLP-derived text in a region the row does not list: that form is a boundary widening of the row and owes a plan amendment, on the plan's own precedent of recording such widenings with the founder's ratification. This bears directly on the P4 choice between the three forms.
- security-plan §Input Validation (same row) requires the composed prompt to pass `validate_prompt_bounded` before the `Command` is built: the byte ceiling, the control-character rejection with its three whitelisted layout characters, and reject-never-truncate. The added service text counts against the ceiling; what bounds the length of a cue's `scope_id` on its way into the digest is research's question.
- security-plan §Security Anti-Patterns → Code Patterns (the argv ban's admitted path) requires the OTLP-derived substring of the prompt to arrive already scrubbed upstream of the bound. The service name in the new position must be the masked form. Whether the scrub that covers the digest also covers the field the trigger line is rendered from, at the point the line is composed, is research's question.
- security-plan §Security Anti-Patterns → Logging (the `extract_service_name` choke-point paragraph) requires the service identity to be the scrubbed name at every consumer, and warns that a raw path desynchronises identities. The trigger framing must take the cue's scoped service from that scrubbed lineage, so a multi-word name can legitimately reach the model carrying a redaction placeholder; whether `AttentionCue.scope_id` descends from the choke point is research's question.
- security-plan §Input Validation (same row) and §Security Anti-Patterns → Code Patterns require `-p` to stay the one OTLP-derived argv operand and the last. The service name travels inside `-p` only; the chunk adds no operand (consistent with the scope's no-sampling / no-GBNF boundary).
- security-plan §Logging & Monitoring → What NEVER to log requires that no OTLP attribute value reaches the self-observation log, and §Security Anti-Patterns → Logging requires an argv-prompt rejection to carry a bounded category with no prompt text, excerpt or offending substring. Any record the chunk adds or changes, and anything the real-model leg emits through the product's log sink, stays inside that.

## Patterns to follow
- The prompt ceiling is derived from measured compositions, and the row keeps a dated measurement note per prompt composition (security-plan §Input Validation, row "L4 inference argv prompt"; mirrored in §Security Anti-Patterns → Code Patterns). A changed trigger framing is a new composition: measure it through the product's unchanged render → build → bound path without a model run, and expect the note as this chunk's plan amendment at wrap. The notes are measurements, never bounds.
- Shape-and-length control at the argv boundary, confidentiality upstream: the bound is not the redaction control (security-plan §Security Anti-Patterns → Code Patterns). Do not add a second scrub at the prompt builder as a substitute for sourcing the scrubbed name.
- Span-level masking keeps the non-secret part of a value byte-identical and each consumer keeps its own placeholder spelling (security-plan §Security Anti-Patterns → Logging, uniform-scrubber-coverage paragraph). A pin on the trigger line's text should hold for a masked service name too.
- Model output that echoes the service name reaches the corpus only through the per-string-leaf masked projection at the three incident-summary write paths (security-plan §Security Anti-Patterns → Logging, measured-reality paragraph). The chunk changes what the model is told, not that write boundary; leave it as it is.

## Anti-patterns to avoid
- NEVER pass OTLP-derived text to a subprocess argv outside the one bounded path: no new operand, no bypass of the bound at the single production caller, no truncation in place of rejection (security-plan §Security Anti-Patterns → Code Patterns).
- NEVER log raw OTLP attribute values, the prompt text or the model's output bytes; a rejection or failure on the L4 path is a bounded category only (security-plan §Security Anti-Patterns → Logging; §Logging & Monitoring → What NEVER to log).
- NEVER write a control-character guard over the multi-line prompt that drops the layout-character whitelist: it disables L4 while every rejection test stays green (security-plan §Input Validation, row "L4 inference argv prompt").

## Contract bindings
- security ↔ tests: the trigger-line and framing-instruction pins that move with this chunk are the tests domain's; the security contribution is that at least one pin exercises a secret-bearing service name and one measures the composed size against the bound. The pre-registered bar's fixture names (`conductor`, `conductor-canary`) are synthetic and carry no real PII.
- security ↔ obs: the prompt-assembly and inference records on the L4 path are obs-owned schemas; the security side is only that their fields stay bounded categories and sizes. "L4 generation records render unredacted" is a separate route entry and is not folded here.
- security ↔ arch: fault identity and the framing-versus-identity rule are arch decisions, not security-plan content; nothing is extracted for them.
- Not in this plan: the scope's "prompt template text stays ASCII" boundary has no anchor in security-plan (it rests on the project rule file `.claude/rules/security.md` §Session Additions, 2026-08-27). Nothing is cited from the plan for it.
- Not in this plan: the plan states no rule on line structure of OTLP-derived text inside the prompt. The bound whitelists newline, so a newline-bearing service name would pass it; whether such a name can reach the trigger line and forge a digest line is research's question, with no plan mandate behind either answer.

## Acceptance criteria contributions
- The prompt composed with the service-bearing trigger framing passes `validate_prompt_bounded`, and its measured byte size is recorded against the ceiling without a model run (per security-plan §Input Validation, row "L4 inference argv prompt")
- A triggering cue whose service name carries a catalog secret renders in the trigger framing masked, with the secret 0x in the composed prompt (per security-plan §Security Anti-Patterns → Code Patterns; → Logging, `extract_service_name` choke-point paragraph)
- The L4 argv operand set is unchanged: `-p` is still the only OTLP-derived operand and the last one (per security-plan §Input Validation, row "L4 inference argv prompt"; §Security Anti-Patterns → Code Patterns)
- No log record added or changed by the chunk carries prompt text, trigger-line text or model output, and the real-model leg's product log reads 0x for the full prompt and for any full product-consumed path (per security-plan §Logging & Monitoring → What NEVER to log; §Security Anti-Patterns → Logging)
