## Constraints

- **P3 critical path contract preservation** — chunk #49's TauRPC procedures (`mcp.status` / `mcp.start` / `mcp.stop`) are the backend data layer for a11y plan §3 Critical Paths P3 ("MCP server toggle in settings → notification on state change"). P3 requires (per a11y plan §3 Critical paths table): switch focus does not move during async state change; `aria-checked` reflects post-call state; SC 4.1.3 OS notification carries success/failure outcome. Chunk #49 IPC contract MUST therefore expose: (a) a synchronous-ish `mcp.status` returning current enabled/disabled state for the switch's `aria-checked` binding, and (b) `mcp.start` / `mcp.stop` returning `Result<MCPState, AppError>` so the UI can update `aria-checked` AND emit the SC 4.1.3 status message on completion. (Per a11y plan §3 Critical Paths P3 row.)
- **AppError shape preserves SC 3.3.1 surface** — per a11y plan §3 Critical Paths P3 + §5 ARIA Patterns dialog row, error states surfaced to the Settings modal must carry plain-language remediation text. Chunk #49's `mcp.start` / `mcp.stop` returning `Err(AppError::Internal { message })` or new variants MUST keep `message` field plain-readable (no Rust struct names / library versions / paths) so the consuming Settings modal can render the message to a `role="alert"` / `aria-live="assertive"` region per a11y plan §7 Live regions table. (This aligns with security plan error-sanitization; a11y dimension is that the sanitized message must remain comprehensible, not just safe.)
- **No new keyboard / focus / contrast surface introduced** — per focus guide §"Out-of-scope (do NOT extract): Backend / IPC / API concerns". Chunk #49 does NOT add new buttons / inputs / modals / animations to the webview; therefore no new SC 2.4.7 / SC 1.4.3 / SC 2.1.1 surface to cover.

## Patterns к follow

- **Status message linkage to SC 4.1.3** — per a11y plan §7 Live regions table, MCP state-change outcomes from `mcp.start` / `mcp.stop` flow into `aria-live="polite"` (non-blocking success) or `role="alert"` (blocking error) live regions in the consuming Settings modal. Chunk #49 procedures should return success/failure as discriminable enum variants (e.g., `Result<MCPState, AppError>` with success carrying enough context for "MCP server started successfully" announcement). Per a11y plan §3 Critical Paths P3 SC 4.1.3 binding.
- **OS notification linkage to P3** — when chunk #49's `mcp.start` succeeds, the broader system (likely separate notification emission path) should fire an OS toast per a11y plan §1 Surfaces "OS notification (toast)" row. Chunk #49's IPC contract just needs to expose the success/failure result enabling the notification path. Per a11y plan §3 P3 + §1 OS notification surface row.

## Anti-patterns к avoid

- **NEVER strip remediation hints from sanitized AppError** — per a11y plan §11 Anti-patterns "Screen Reader" + §3 Critical Paths P7 SC 3.3.1 ("Error Identification"): sanitization to remove paths / library versions / Rust struct names is correct, but the resulting `AppError::*::message` MUST still carry actionable remediation text (e.g., "MCP server failed to start: feature flag disabled" rather than `[redacted]`). The chunk #48 `sanitize_error_data` primitive's `[redacted]` placeholder is appropriate for free-form `data` payloads but NOT for the `message` field that becomes a user-facing status announcement.
- **NEVER expose internal MCP protocol error codes to the webview without translation** — per a11y plan §11 "Screen Reader" anti-patterns + design plan plain-language commitment (a11y §8 baseline disciplines). MCP returns JSON-RPC numeric error codes (e.g., `-32601 Method not found`); chunk #49 must translate these to plain-language `AppError` variants before crossing the TauRPC bridge for human-readable announcement.
