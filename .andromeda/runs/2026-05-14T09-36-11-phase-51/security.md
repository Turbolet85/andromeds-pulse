## Anti-patterns к avoid

- **NEVER `@v2` / floating-tag any new a11y/perf CI Action** per security plan §Security Anti-Patterns §Secrets row 3 — full 40-char SHA + `# vX.Y.Z` provenance comment, EVERY new `uses:` line. Workflow self-lint grep (`grep -E '^\s*uses: [^@]+@[^a-f0-9]'` returning zero matches) is the verification.
- **NEVER `tokio::process::Command::new(...).arg(user_input)`** in the perf SLO harness or a11y audit driver — covers the case where a violation-JSON baseline path or perf threshold value is sourced from an env var consumed by a shell-out to a CLI tool. Per security plan §Security Anti-Patterns §Code Patterns row 1 (MCP STDIO command-injection cluster CVE-2025-49596 / CVE-2025-54994 / CVE-2025-54136 / CVE-2026-22252 anchor).
- **NEVER bind perf SLO test infrastructure to `0.0.0.0`** per security plan §Security Anti-Patterns §API row 8 — loopback only, even in CI runners. The loopback discipline is the de-facto authorization boundary; any perf SLO test that needs to inject OTLP from a sidecar process MUST do so via `127.0.0.1:4317` / `127.0.0.1:4318`.
- **NEVER bypass the post-`prost`-decode invariants in the load generator** per security plan §Security Anti-Patterns §Input row 3 — synthetic spans MUST have valid 8-byte `span_id` + 16-byte `trace_id` + bounded attribute keys/values. A perf SLO load-gen that emits malformed OTLP to stress the "happy path" doesn't actually exercise the production receiver code; it exercises a degenerate path and produces false-confidence perf numbers.
- **NEVER widen `permissions:` to workflow-level `contents: write`** for the a11y/perf CI workflow per security plan §Security Anti-Patterns §Secrets row 4 — workflow-level stays `contents: read`; baseline-refresh / criterion-bench-publish step gets per-job `contents: write` only.
- **NEVER check in violation-JSON baselines or criterion-bench artifacts containing raw OTLP attribute values, span/log/metric content payloads, or DuckDB query parameter values** per security plan §Security Anti-Patterns §Logging row 1+3 + §Logging & Monitoring "What NEVER to log" list — incidentally captured secrets from synthetic load-gen seed data MUST be scrubbed / static-mocked at fixture build time.
