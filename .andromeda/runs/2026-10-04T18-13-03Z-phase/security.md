## Relevance
partial — the chunk changes the L4 `-p` argv prompt (the one admitted OTLP-derived-text-to-argv path) and adds a probe label beside model output; no new IPC, port, capability, env var, table or dependency is in scope.

## Constraints
- The L4 prompt reaches argv only through `validate_prompt_bounded`: the 16384-byte `MAX_PROMPT_BYTES` ceiling plus NUL / C0 / C1 rejection, with `\n` `\r` `\t` whitelisted. An over-long prompt is rejected and never truncated; the digest is skipped instead. Any added corpus-match or triggering-cue framing must keep realistic prompts under the ceiling (per security-plan §Input Validation, the "L4 inference argv prompt" row; §Security Anti-Patterns → Code Patterns, the `Command::arg(user_input)` ban and its one bounded admission). Research must answer how many bytes the new framing adds against the recorded maximum of 6,932 B.
- §Input Validation's "L4 inference argv prompt" row requires OTLP-derived prompt content to stay within a stated set: `digest.payload_summary`, `project_context` and the `<CITABLE_EVIDENCE_IDS>` section. Research must answer two questions. Does the `# Corpus Retrieval` block, or a triggering-cue name, bring content from outside that set into the prompt? Is that content OTLP-derived or model-authored? If either answer is yes, the row's enumeration needs an amendment (per security-plan §Input Validation).
- Prompt text from OTLP data must already be PII-scrubbed upstream (`Digest::scrubbed_clone`). The argv bound controls only shape and length; it is not a confidentiality control. Any corpus-match text the new framing quotes must come from the scrubbed projection: `Incident.resolution_summary_text` is a scrubbed JSON projection of `L4Output` (per security-plan §Security Anti-Patterns → Code Patterns; §Security Anti-Patterns → Logging, "MEASURED reality", the incident-summary corpus write boundary). Whether the corpus-retrieval inputs to `prompt.rs` are read from the scrubbed projection is research's question.
- No model output, prompt text, title text or raw OTLP attribute value may reach a log or the probe's record. The names-the-trigger result must be a closed, bounded label set (per security-plan §Logging & Monitoring, "What NEVER to log"; §Security Anti-Patterns → Logging).
- Prompt-rejection and inference-failure outcomes appear only as bounded categories on the existing `interpretation.inference.error` leaf. That leaf carries no prompt text, excerpt, offending substring or output bytes. No new free-text error field may be added (per security-plan §Input Validation, "L4 inference argv prompt" row, the Validation column).
- For the gated item 4 run, `ANDROMEDA_PULSE_LLAMA_CUDA_BIN_PATH` and `ANDROMEDA_PULSE_MODEL_PATH` are guarded product-consumed path vars. The guard rejects `..` before canonicalizing, bounds input to 4096 bytes, canonicalizes, and requires a regular file. Confinement under `ANDROMEDA_PULSE_L4_ALLOW_ROOT` is opt-in, and a root that is set but cannot be resolved fails closed. Logs may carry the basename only (per security-plan §Security Anti-Patterns → Input, the NARROWED EXCEPTION; §Logging & Monitoring, "What NEVER to log", full paths).

## Patterns to follow
- A bound that rejects at a boundary returns a bounded rejection value whose `label()` is the only thing logged. Use the `PromptRejection` shape for any new outcome the probe reports (per security-plan §Input Validation, "L4 inference argv prompt" row).
- A guard's character whitelist must match the layout characters the prompt producer emits. The new framing will be multi-line markdown, so the test must pin a realistic multi-line prompt as ACCEPTED, not only reject NUL-bearing input (per security-plan §Input Validation; `.claude/rules/security.md` Session Additions, 2026-08-26).
- Template text sent as argv stays ASCII, including role text the model may paraphrase. The pin is `composed_prompt_templates_are_ascii_clean_for_argv_transport` (per `.claude/rules/security.md` Session Additions, 2026-08-27; scope §Boundaries).
- To name the triggering cue, use the closed cue-kind vocabulary (`triage::contract::cue_cause_label(kind)`), not cue-scoped free text. That gives a non-OTLP label with a bounded set of values (per security-plan §Input Validation, the "L4 inference argv prompt" row's confinement of OTLP-derived content).

## Anti-patterns to avoid
- Do not silently truncate a prompt to fit the new framing under `MAX_PROMPT_BYTES`. Truncation corrupts model input, so the ceiling rejects instead (per security-plan §Input Validation, "L4 inference argv prompt" row).
- Do not put generated title, symptom or hypothesis text into the probe's record or into a log line as evidence for names-the-trigger. Only the closed label may appear (per security-plan §Logging & Monitoring, "What NEVER to log"; §Security Anti-Patterns → Logging).
- Do not pass corpus-match or cue text into the `Command` through any route other than the bounded `-p` operand (per security-plan §Security Anti-Patterns → Code Patterns, the `tokio::process::Command::new(...).arg(user_input)` ban).

## Contract bindings

Any new log leaf must be a closed set on the obs allowlist, with no model text (security-plan §Logging & Monitoring ↔ obs-plan, allowlist and leaf registration).
