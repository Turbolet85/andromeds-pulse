# a11y extract

## Relevance
Partial — enhances existing critical path (P7: investigation-modal form), no new surfaces but adds async progress/result states that must remain keyboard-accessible and screen-reader-announced.

## Constraints
- Per a11y-plan §1 P7, investigation-modal is must-be-accessible; focus management during form interaction is mandatory (SC 2.4.3)
- Per a11y-plan §1 P2 + P6, async operations must emit `aria-busy` state changes and `aria-live` status announcements without breaking focus (SC 4.1.3, SC 2.1.2)
- Per a11y-plan §5 focus management, Escape must still close the modal and return focus to the trigger button, even during in-flight async operations (SC 2.1.2 No Keyboard Trap)
- Per a11y-plan §4 Status/Alert patterns, result/error rendering must use `role="alert"` (aria-live="assertive") for errors or `aria-live="polite"` for completion messages (SC 4.1.3)
- Per a11y-plan §1 Critical Paths P7, form-state error messages must link via `aria-describedby` to inputs if validation occurs (SC 3.3.2, SC 4.1.2 Name/Role/Value)

## Patterns to follow
- Async progress pattern from P2 + P6: show `aria-busy="true"` on the action button during execution; flip to `aria-busy="false"` on completion; emit a polite status message announcing the result (a11y-plan §1 P2/P6 rows)
- Error surfacing pattern from P7: if per-action validation fails, use `role="alert"` wrapper or `aria-live="assertive"` to interrupt with the error; link error text to the input via `aria-describedby` (a11y-plan §4 Form input pattern)
- Focus stability: focus must remain on the action button throughout the async lifecycle; do not trap focus or move it to the result region (a11y-plan §1 P6 table "user-initiated row select...follows focus order rules"; P7 "focus cycles within modal")

## Anti-patterns to avoid
- Motion as sole state indicator (a11y-plan §9): if adding a loading spinner or progress animation, pair it with text content or an icon; verify under `prefers-reduced-motion: reduce` (SC 2.3.3 AAA)
- Dangling `aria-busy` or `aria-live` without semantic HTML (a11y-plan §4 "semantic HTML first"); use native `<button>` + aria-busy, not a div with role="button"
- Focus trap on result display: result must be announced/readable without stealing focus from the modal's normal Tab order (a11y-plan §5 focus-trap rule)

## Contract bindings
- **Tests harness** (a11y-plan §3 Bootstrap phases): if progress/result/error flow warrants new E2E tests, wire into Playwright suite alongside existing P7 investigation-modal spec (`keyboard-focus/widget-and-modals.spec.ts`); reuse mock-tauri + v02-fixtures for any new TauRPC procedure invocations (per §3 Harness wiring & conventions)
- **Obs binding** (a11y-plan §1 Structured Violation JSON; chunk scope "aggregate-only observability"): if emitting metrics for action execution, use bounded counts + enum tags only; never log prompt content / result bodies / user identifiers per cardinality + PII discipline

## Acceptance criteria contributions
- "(a11y) Focus and keyboard during async: Tab/Escape remain functional; focus stays on action button during progress state; modal closes via Esc (SC 2.1.2, SC 2.4.3)."
- "(a11y) Status messages: progress and error states announced via aria-busy or aria-live per P2/P6 pattern (SC 4.1.3)."
- "(a11y) Error rendering: if an action fails, result is announced via role='alert' or aria-live='assertive' (SC 4.1.3); error message linked to related input if applicable (SC 3.3.2)."
- "(a11y) No motion-only state: if a loading indicator animates, a text label or icon also conveys in-progress state (SC 2.3.3 AAA); animation respects prefers-reduced-motion (per a11y-plan §9)."
