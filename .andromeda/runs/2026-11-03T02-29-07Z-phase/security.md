# security extract

## Relevance
relevant: the chunk removes a whole attack-surface vector (the MCP stdio sidecar and its double gate), an env var, a dependency (`rmcp`) with its `deny.toml` entries, the window's `mcp.*` TauRPC procedures and the cross-process `run/workspace-key` publish. It also owns the undeclared-argument-member gap the plan assigns to this entry.

## Constraints
- The undeclared-argument-member gap belongs to this entry, and this chunk settles it. security-plan §Input Validation (MCP stdio inputs row) records that the argument structs (`QueryTracesArgs`, `QueryMetricsArgs`, `QueryLogsArgs`, `GenerateSnapshotArgs`, `IncidentIdArgs`) carry no `deny_unknown_fields`, that `dispatch_query_incident_list` parses no arguments, and that only the door refuses an undeclared member. Whichever refusal form is chosen must keep an undeclared member out of every query, path and log, for all nine tools. The plan text does not name "the two forms" outright. Settling them is P2/P3's job (per security-plan §Input Validation).
- Every refusal must carry a fixed message and never the tool's own error text. The door's request rules (closed methods, closed nine-tool set, `declared_only` `-32602` before any tool runs, the line/answer/time/idle/connection bounds, the `ANDROMEDA_PULSE_DOOR_RESOLVE` gate on `mark_incident_resolved`) stay as stated. Only the argument-member form may move (per security-plan §Input Validation, the console engine's door row).
- The door's admission must not change. The peer-account check through `door::admits` / `door::own_account` stays fail-closed for any other account, root included, and for an unreadable account, with no byte written (per security-plan §Authentication & Authorization).
- The double gate must leave together with the sidecar: the `mcp-server` cargo feature, `ANDROMEDA_PULSE_MCP_ENABLED`, `feature_gate.rs` and the `andromeda-pulse-mcp` `[[bin]]`. No sidecar binary may stay buildable or spawnable behind a single gate, because the plan bans a single-gate spawn (per security-plan §Security Anti-Patterns → Code Patterns). The plan's warn-on-mismatch mandate covers only the sidecar's gate. Removing it is master text the wrap amends, not a code regression (per security-plan §API Security, MCP feature double-gate row).
- Removing `rmcp` and its `deny.toml` entries must leave `multiple-versions = "deny"` unrelaxed and the `tonic` canary unskipped. A skip or advisory ignore that becomes unnecessary is pruned, not kept, because a stale skip hides the duplicate's return (per security-plan §Dependency Security).
- Removing the three `mcp.*` procedures means removing their `EXPECTED_PROCEDURES` pins in `xtask/src/main.rs` and regenerating `pulse-app/ui/src/bindings/index.ts`, so the worktree and git-index copies agree. The tray item's removal must not widen `pulse:tray` or any capability grant against `staged_gate::EXPECTED_GRANTS` (per security-plan §API Security, TauRPC capability authorization row).
- Removing `publish_workspace_key_for_sidecar` / `run/workspace-key` removes the cross-process read boundary in security-plan §Input Validation (published workspace key row). The door row requires that the door read no `run/workspace-key`. Whether any reader other than the sidecar exists is research's question (per security-plan §Input Validation).

## Patterns to follow
- The door's `declared_only` check: `arguments` must be an object whose every member the tool's `inputSchema.properties` declares, refused `-32602` with a fixed message before any tool runs. This is the existing refusal precedent for the argument-member form (per security-plan §Input Validation, the console engine's door row).
- The door's NO-SCRUB records `app.boot.door`, `door.call` and `door.refused` each sit behind an exact allowlist leaf, pinned in `pulse-app/tests/unit_observability_allowlist_door.rs`. The spawned arms of `pulse-app/tests/integration_door.rs` read a telemetry marker 0 times in the log family and no full data-dir path. The four rewritten `pulse-app` tests that read through the door follow that shape (per security-plan §Security Anti-Patterns → Logging).
- Dependency carve-outs in `deny.toml` are ID-scoped, owner-named and pruned when their reason ends, as with the `windows-core` / `windows-result` / `windows-strings` skips (per security-plan §Dependency Security).
- Procedure-surface changes go through the `cargo xtask capability-drift` + `cargo xtask check:staged-artifacts` pair in CI (per security-plan §Bootstrap phases, dep-security-ci-gate).

## Anti-patterns to avoid
- NEVER write a byte to a door peer before its account is read and found equal to the engine's own. NEVER admit root or an unreadable peer. NEVER widen `run/door/` beyond 0700 or `run/door/sock` beyond 0600 (per security-plan §Security Anti-Patterns → Authentication).
- NEVER log MCP tool response bodies, a call's arguments, its answer, the tool's own error text, the peer's account id or the socket/data-dir path on any door record. This applies to the rewritten tests' carriers and to any changed `initialize` answer or tool description (per security-plan §Security Anti-Patterns → Logging).
- NEVER relax `multiple-versions = "deny"` or skip the `tonic` duplicate canary while editing `deny.toml` (per security-plan §Security Anti-Patterns → Universal).

The door's vector stays PROVISIONAL and is not ratified by this chunk (per security-plan §Threat Model Summary, Attack surface, the door's vector).

That covers §Threat Model Summary (MCP stdio vector, door vector "two ways in", CLI input), §API Security (double-gate row), §Input Validation (MCP stdio row, published workspace key row, env-var row), §Data Protection and §Security Anti-Patterns → Input (lock-file readers going from "three product binaries" to two), and §Security Anti-Patterns → Code Patterns (sidecar spawn ban).
