# arch extract

## Relevance
relevant: the chunk removes a product binary, a cargo feature, a dependency, an env var, three TauRPC procedures and a CI job. It also changes text that the external reader Conductor depends on.

## Constraints
- architecture §Occupied Resources → Cargo workspace crate names reserves `mcp-server` as one of seventeen locked member names. architecture §Established Decisions [MCP Server Surface] requires `mcp_server::tools::call_tool` to be the door's dispatch. So the crate stays a workspace member that `pulse-app` links in every build; only the sidecar's `[[bin]]` and its feature-only code leave.
- architecture §Cross-cutting Patterns → Feature-gate hygiene and architecture §Conventions → Feature flags require `rmcp` to enter the build only under `--features mcp-server`, with default features kept minimal. Retiring the feature has to take `rmcp` out of the graph completely (the `Cargo.toml` requirement, `Cargo.lock`, `deny.toml`). `otap-ingest` stays the remaining off-by-default flag.
- architecture §Standard Contracts → Engine door defines a form that Conductor reads. It includes the `initialize` answer (`serverInfo.name` reads `andromeda-pulse-mcp`), fixed-message error codes that never carry the tool's own text, and `-32602` for an undeclared `arguments` member before any tool runs. Two things here change that form's text: renaming the server, and rewording the tool descriptions. Each is said to the operator before it lands. The door's admission, bounds, socket and codes stay as they are. Research has to answer whether a struct-level refusal of unknown fields (`deny_unknown_fields`) can surface as `-32603` (tool failed) instead of the door's `-32602`.
- architecture §Occupied Resources → Tauri IPC routes lists `mcp.status`, `mcp.start` and `mcp.stop`. architecture §Cross-cutting Patterns → Webview IPC capability policy requires a procedure change to touch three things together: the router registration, the Occupied Resources entry, and the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`. The regenerated `pulse-app/ui/src/bindings/index.ts` has to be staged with the pin, or `capability-drift` / `check:staged-artifacts` turns red. No capability-JSON edit is involved.
- architecture §Occupied Resources → Environment variables registers `ANDROMEDA_PULSE_MCP_ENABLED` as honored only under the feature. It leaves with the double gate. architecture §Occupied Resources → Environment variables also requires that no new `ANDROMEDA_PULSE_*` name is added. `ANDROMEDA_PULSE_DOOR_RESOLVE` stays as it is.
- architecture §Occupied Resources → Filesystem locations says both engine programs publish `run/workspace-key` through `engine_boot::publish_workspace_key_for_sidecar` and that the sidecar reads it. The same section lists the sidecar among the writers of the corpus-key lock file. Research's reader census decides whether the publish can go. The door reads no `run/workspace-key` (architecture §Standard Contracts → Engine door), and the product-written locations outside the data dir stay three.
- architecture §Infrastructure Patterns → CI/CD approach lists `mcp-test` (nextest with `--features mcp-server`) as one of six jobs. It also keeps `boot`'s `cargo build --workspace --release --features mcp-server` as one of two release-build witnesses, pinned by `ci_workflow_keeps_the_linux_release_build_witnesses`. Taking out the job and the feature has to leave a Linux release-build witness in `boot`, with its pin updated rather than dropped.

## Patterns to follow
- Read state back through the door: architecture §Cross-cutting Patterns → Test-time telemetry injection names `pulse-app/tests/integration_door.rs` as the model. It sends over real OTLP and reads back with a tool call on `run/door/sock`. This is the template for the four rewritten sidecar-spawning tests. Ports come from `test_support::ports::claim_port` (architecture §Occupied Resources → Network ports).
- The stdio way in is the relay `andromeda-pulse-engine door` (architecture §Standard Contracts → Engine door, Stdio). It passes the door's lines through unchanged, so a stdio caller sees the door's envelope, codes and bounds, never an envelope of the relay's own.
- Removing a procedure follows the same discipline as adding one: router, Occupied Resources, `EXPECTED_PROCEDURES`, and staged bindings move together (architecture §Cross-cutting Patterns → Webview IPC capability policy).
- Crate shape after the cut follows architecture §Project Intent → Template patterns: `mcp-server` keeps a public contract surface (`call_tool`, the nine tools, `jsonrpc.rs` envelope functions) and `pub(crate)` internals.

## Anti-patterns to avoid
- No new env var, port, listener, file, binary or log record. The door surface must not widen (architecture §Occupied Resources → Network ports, the door, PROVISIONAL).
- No test-mode bypass or mock back-door for the rewritten tests. Injection stays OTLP-only (architecture §Cross-cutting Patterns → Test-time telemetry injection).
- No custom envelope, and no tool text inside error messages (architecture §Established Decisions [API Style — MCP Server Surface 3]).
