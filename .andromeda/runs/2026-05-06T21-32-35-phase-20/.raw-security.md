## Chunk relevance

- route#23 "Broadcast fan-out + Tauri Channel API — tokio broadcast → pulse://stream/{spans,metrics,logs} binary Arrow IPC + _trace_context metadata + size cap" — **relevant**: introduces a new outbound IPC streaming surface (`pulse://stream/*` events) and a new Arrow IPC payload boundary; the size-cap discipline + capability-JSON registration + redaction of OTLP attribute values in payload-emission logs are all security-load-bearing.

## Constraints

- All five `pulse://stream/*` events MUST be enumerated in `pulse-app/capabilities/` JSON for the `pulse:default` capability — Tauri 2 capabilities are negative-default; an unlisted event name surfaces as a silent runtime rejection at the bridge (per security plan §API Security TauRPC capability authorization + §Anti-Patterns API ban "NEVER add a TauRPC procedure to a router crate without a matching entry"). Note: chunk #23 emits via `Channel::send` rather than registering a TauRPC procedure, but the capability-JSON-pairing discipline still applies — the `xtask capability-drift` check (route#23's downstream consumer per route#27 IPC introspection) MUST treat stream event names as part of the drift surface.
- Outbound Arrow IPC payloads emitted on `pulse://stream/{spans,metrics,logs}` MUST be size-capped before `Channel::send` — even though the bytes are first-party-produced by `viz`/`buffer` here, the cap is the architecture-mandated discipline that future plugin-sourced Arrow IPC re-emit MUST inherit (per security plan §Input Validation row "Tauri IPC Channel API streaming payloads" + §Anti-Patterns Input ban "NEVER trust plugin-returned Arrow IPC bytes without a size cap before re-emitting"). Recommended cap: 8 MB (matches OTLP receiver `DefaultBodyLimit` per §API Security Request size limit row) or smaller per per-batch sizing analysis.
- The `_trace_context` metadata column in Arrow batches MUST NOT carry OTLP attribute values verbatim — only the W3C `traceparent` / `tracestate` strings (which are constrained by the spec to opaque IDs) per session-handoff context "trace context propagation via Arrow `_trace_context` metadata column". Any incidental OTLP attribute value embedded in the metadata column would surface in webview JS scope and re-introduce the secret-leakage class that §Logging & Monitoring NEVER-log list defends against.
- Broadcast-emission tracing instrumentation MUST anonymize payload contents — log `event_name`, `subscriber_count`, `payload_bytes`, `dropped_count` (broadcast lag), `traceparent` (if present), but NEVER the Arrow batch contents, schema column values, attribute values, or OTLP-derived strings (per security plan §Logging & Monitoring "What NEVER to log" list + §Anti-Patterns Logging ban "NEVER log raw OTLP attribute values, span/log/metric content payloads"). This extends the chunk #22 query-router `query_id` + `param_count` + `param_types` precedent: emission events get `event_name` + `subscriber_count` + `payload_bytes` instead of payload content.
- `tokio::sync::broadcast::Receiver::recv` lag (subscriber dropped messages due to buffer overflow) MUST surface as a structured event with `dropped_count` cardinality but NEVER include the dropped batches' contents; lag itself is operationally relevant per §Logging & Monitoring "What to log" (analogous to "OTLP request rejections") even though chunk #23 is the producer side.
- AppError From conversion at the broadcast/Channel boundary MUST preserve the `From<viz::Error>` and `From<buffer::Error>` sanitization established in chunks #20–#22; any new error variant introduced for broadcast lag / Channel send failure MUST collapse to `AppError::Internal { message }` with a sanitized one-liner — no `BroadcastSendError<Vec<u8>>` debug payload, no Rust struct names (per security plan §Error Handling + §Anti-Patterns Code Patterns ban "NEVER serialize an `anyhow::Error` directly across the TauRPC bridge").
- The broadcast fan-out itself MUST stay loopback-confined — it operates over `tokio::sync::broadcast` (in-process channels, no network surface) and the Tauri `Channel` API (webview-internal IPC). NEVER add a network exporter / WebSocket / SSE bridge that would convert `pulse://stream/*` into an externally reachable surface (per security plan §Threat Model Summary loopback-only network classification + §Anti-Patterns API ban "NEVER bind the OTLP receivers to `0.0.0.0`" — the same loopback-only intent governs stream emission).

## Anti-patterns to avoid

- NEVER log Arrow IPC payload contents, OTLP attribute values, span/log/metric content payloads, or schema column data in broadcast-emission tracing — incidentally captured secrets from instrumented host applications surface verbatim per security plan §Anti-Patterns Logging "NEVER log raw OTLP attribute values, span/log/metric content payloads, snapshot file contents, clipboard contents, or MCP tool response bodies".
- NEVER `Channel::send` an Arrow IPC payload without a size cap, even for first-party-produced bytes — the cap is architecture-mandated discipline that future plugin-returned bytes MUST inherit; introducing the surface without the cap leaves a regression-shaped hole per §Anti-Patterns Input "NEVER trust plugin-returned Arrow IPC bytes without a size cap before re-emitting on the Tauri Channel API".
- NEVER convert the `pulse://stream/*` events into a network-reachable surface (WebSocket / SSE / TCP listener) — the architecture's "in-process channel" discipline is the loopback-only authorization boundary substitute per arch §Cross-cutting Patterns + §Anti-Patterns API loopback-only ban; converting in-process broadcast to network exposes Arrow IPC content that has no auth model.
- NEVER stuff OTLP attribute values into the Arrow `_trace_context` metadata column — the column is for W3C traceparent/tracestate strings only (opaque, spec-bounded); attribute values would re-introduce the secret-leakage class the snapshot/clipboard/MCP hygiene rules defend against per §Logging & Monitoring snapshot/clipboard hygiene.
