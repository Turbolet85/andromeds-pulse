## Relevance
Partial — the regression hunt itself (§1–§3) is not a security surface, but the §4 obs-allowlist repair, the incident corpus persistence boundary, and the ranked-suspect workspace-key seam are all governed by this plan.

## Constraints
- The four §4 obs leaves may carry **counts and bounded enum labels only**. `item_count`, `incident_count`, `restored_incident_count` are counts; `persist_kind` and `kind` must resolve from a closed enum domain, never a free-form string that could carry telemetry-derived text — raw OTLP attribute values, span/log/metric content payloads, and DuckDB query-parameter values are NEVER-log per security-plan.md §Logging & Monitoring ("What NEVER to log") and §Security Anti-Patterns §Logging. The same ban governs evidence artifacts committed to the chunk folder: no decrypted cell payloads, no captured log lines carrying attribute values.
- Any attribute value crossing into `incidents` / `incident_events` on the restored persist path must pass `security::scrubber::scrub_attribute` before write, returning `ScrubbedValue::Allowed(_)` or `Redacted` (per security-plan.md §Security Anti-Patterns §Logging "Uniform scrubber coverage" + §Data Protection → At rest → Persistent incident corpus). Note the plan's enumerated coverage names the buffer appender, Drain, BaselineState, ServiceRegistry and RetryStormState paths but **not** the incident tables — whether the incident-creation path already routes through the scrubber is research's question, and it becomes load-bearing the moment §3's fix restores writes to those tables.
- The published workspace key must stay an **opaque filter string** — never opened, joined, or otherwise used as a path (CWE-22 closed by construction); its read stays bounded to `MAX_WORKSPACE_KEY_BYTES` (4096), UTF-8-checked, newline-trimmed, empty/control-char-rejecting with any failure yielding `None` → `data_dir` fallback; its write canonicalizes and confines `run/` under the data dir with atomic `.tmp`+rename; only the basename is logged (per security-plan.md §Input Validation, published-workspace-key row). The ranked suspect (`resolve_workspace_for_incidents`, `digest_runtime.rs`) sits directly on this boundary, so any stamp/filter realignment must preserve the whole row, not just the byte-equality invariant.
- Corpus key material is secret-class: never logged, never exported, `#[tracing::instrument(skip(key))]` at all key-handling call sites; `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` is bounded-parse (non-empty, ≤ 1024 bytes, unset ⇒ not-configured), consumed only as KDF input, never canonicalized, never a path, never logged (per security-plan.md §Secret Management → Runtime + "What counts as secret"). The fresh-data-dir premise-check run and its recorded evidence must not surface key or passphrase material.
- `ANDROMEDA_PULSE_L4_DETERMINISTIC` — the premise-check's gate — is a bounded truthy-parse (`1|true|yes`, default false, no unbounded string) per security-plan.md §Input Validation (CLI / env var inputs row); the premise check exercises it and must not regress it. Likewise `ANDROMEDA_PULSE_DATA_DIR`, used for the fresh data dir, is canonicalize-and-confine per the same row.
- Scope declares no new capability surface; if §3's located fix nonetheless adds a TauRPC procedure, both enforcement pieces are required — router registration **and** an entry in `pulse-app/capabilities/` — with the xtask drift check as the mechanism (per security-plan.md §API Security, TauRPC capability authorization).
- Errors surfaced on the incident read/write path (`incidents.list_active`, MCP `query_incident_list`) sanitize at the boundary: `AppError::{Validation, NotFound, Internal, …}` with no stack traces, file paths, Rust struct names, or library versions; MCP errors use the JSON-RPC 2.0 error object (per security-plan.md §Error Handling).

## Patterns to follow
- `scrubbed_clone`-on-persisted-snapshot — the existing shape for pre-write scrubbing at a corpus persistence boundary (`BaselineState::scrubbed_clone`, `StormStateSnapshot::scrubbed_clone`), per security-plan.md §Security Anti-Patterns §Logging.
- Redaction applied at the subscriber layer, not at log call sites, with a named-leaf default-deny allowlist — the same repair shape §4 cites for `corpus.open.error` (per security-plan.md §Logging & Monitoring, "Log format").
- `workspace_detector::contract::{publish_workspace_key, read_published_workspace_key}` as the single canonicalize-and-confine-write / validate-on-read pair for the cross-process key (per security-plan.md §Input Validation).
- Keyless `sqlite3` ground-truth reads are consistent with the declared at-rest posture — table and column names are plaintext, BLOB cell payloads opaque without the key (per security-plan.md §Data Protection → At rest → Persistent incident corpus); the evidence discipline in §5 does not require key access and must not acquire it.
- Registry-completeness precedent: a newly landed, code-validated + unit-tested input boundary earns a §Input Validation row rather than an escalation (window-geometry 2026-06-29 precedent) — applies only if §3's fix introduces a new read boundary.

## Anti-patterns to avoid
- NEVER log raw OTLP attribute values, span/log/metric content payloads, snapshot or clipboard contents, MCP tool response bodies, or DuckDB query-parameter values (log query identifier + parameter count instead) — security-plan.md §Security Anti-Patterns §Logging; this is the ban the §4 leaves must clear.
- NEVER use the published workspace key as a path, and NEVER read an `ANDROMEDA_PULSE_*_DIR` / `*_PATH` env var without canonicalize-and-confine under the resolved data dir — security-plan.md §Security Anti-Patterns §Input + §Input Validation published-key row.
- NEVER add a TauRPC procedure to a router crate without the matching `pulse-app/capabilities/` entry — the call is silently rejected at runtime, an especially costly failure mode in a chunk whose whole subject is a silent zero (security-plan.md §Security Anti-Patterns §API).

## Acceptance criteria contributions
- Every field added to `incidents.list_active.request`, `triage.incident.persist`, and `triage.incident.corpus_restore` is a count or a closed-enum label; no OTLP attribute value, telemetry content payload, or DuckDB query-parameter value appears in any added leaf, and no evidence artifact in the chunk folder contains decrypted cell payloads (per security-plan.md §Security Anti-Patterns §Logging + §Logging & Monitoring).
- Attribute values written to `incidents` / `incident_events` by the restored path pass `security::scrubber::scrub_attribute` before write — whether this already holds on HEAD is research's question, since the plan's coverage enumeration does not name these tables (per security-plan.md §Security Anti-Patterns §Logging, uniform scrubber coverage).
- The published workspace key is still consumed only as an opaque filter string after any stamp/filter realignment, with the bounded + UTF-8 + control-char-rejecting read and `None` → `data_dir` fallback intact and only the basename logged (per security-plan.md §Input Validation, published-workspace-key row).
- The wrap records the `cargo deny check bans licenses sources` and `cargo deny check advisories` results and re-probes `cargo audit` once; the deferral ends the first time it loads (per security-plan.md §Dependency Security → CI integration, standing deferral).
