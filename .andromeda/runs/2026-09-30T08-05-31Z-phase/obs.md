## Relevance
relevant: the chunk's acceptance is graded on a self-observation wire record (`metric.constellation.discovery_ms`, P-027's observable), and the fix touches a triage path that may gain or change emit sites.

## Constraints
- P-027's observable is the exact leaf `metric.constellation.discovery_ms`. Its field set is `duration_ms` plus `discovered_count` (aggregate, clamped at 10_000 client-side and rejected above that by `validate_discovered_count`). `service` must never be a label on it (per obs-plan §8 PII Scrubbing, "The three DELEGATED TIMING leaves"). If research re-anchors the observable to a first-seen instant, any new or renamed field on the emit site must be added to that exact leaf in the same change. Otherwise the bare `metric` key's first-segment fallback keeps only `value` and silently redacts the new labels, which leaves the target partly redacted (same § paragraph, "A bare `metric` key DOES exist").
- P-025's observable `metric.constellation.hue_update_ms` keeps its defined semantics: `duration_ms` = paint instant minus `ServiceListItem.tier_effective_at_unix_nano`, one record per service whose tier changed, emitted only for changes witnessed after mount, and graded by `cargo xtask smoke:hue-shift` (per obs-plan §8, same delegated-timing paragraph). A shorter rise on a fresh boot is a consequence of the fix. It is not permission to change the anchor or the emission rule.
- The frontend timing marks reach the log only through the hand-rolled TauRPC `telemetry.frontend.*` bridge, which calls `tracing::info!(target: "metric.{name}", ...)` on the backend. This is the decided mechanism: no browser OTel SDK and no `web-vitals` (per obs-plan §3 Logging stack; §4 Desktop-webview row). Whether the discovery mark's bridge procedure needs a new argument to carry a first-seen anchor is research's question.
- Any new emit site on the discovery path is subject to default-deny allowlisting. Candidates are an event-driven "first sighting registers the service" record and a changed `triage.lifecycle.*` record. Such a site needs its own EXACT leaf naming every field it emits, and neither a bare `triage` nor a bare `triage.baseline` key may exist (per obs-plan §8 PII Scrubbing, the default-deny posture and the `triage.baseline.bootstrap_window.override` / `triage.cue.tick` entries). Field sets are asserted by equality in both directions in a guard under `pulse-app/tests/`, because `[lib] test = false` means a src-level guard never runs (same §).
- Emission on the registration path is aggregate and once per transition, never per span. First sighting sits on the span-ingest observer path, so any record is folded as a count or emitted once per newly registered service. It is never logged per span, and never at `info` in a hot loop (per obs-plan §11 Telemetry Strategy "NEVER over-instrument hot paths"; §11 Logs "NEVER log in hot path at `info` level"; §5 tick-aggregated counter convention).
- The wire record the live leg reads lives at `<data_dir>/logs/agent-latest.jsonl`, with `<data_dir>` from `resolve_data_dir()` / `ANDROMEDA_PULSE_DATA_DIR`. It is JSON-per-line with `timestamp` / `level` / `target` / `message` / `fields` (per obs-plan §3 Log file location; §6 Log format JSON schema / Required fields).
- The 15 s heartbeat cadence is a harness contract for long-running subsystems (per obs-plan §3 Heartbeat ticks; §10 Standard+ invariants "Heartbeat ticks"). Whether `triage.lifecycle.tick` is inside that contract, or only shares its interval, is research's question. It matters only if P4 weighs shortening the lifecycle tick against the scope's event-driven lean.

## Patterns to follow
- A delegated-timing leaf plus its guard: an exact leaf in `AllowList::production()` carrying every emit-site field, asserted set-both-ways plus fallback-discrimination by `pulse-app/tests/unit_observability_allowlist_delegated_timing.rs`, mutation-checked (per obs-plan §8, "The three DELEGATED TIMING leaves"). Extend that file if the discovery leaf's field set changes.
- Tick-aggregated counter as FIELDS on an existing heartbeat, instead of a new per-event target. Examples: `cues_latched` / `latch_tracked` on `triage.cue.tick`, `cycles_executed` on `cadence.tick` (per obs-plan §5 Conceptual instrument types). Use this if the fix wants a "services registered at first sighting" count.
- A once-per-transition diagnostic with bounded static labels, like `interpretation.generation.damper` (engage/release only, never per decision) (per obs-plan §8). This is the model for any registration-state record.
- A live-wire proof of un-redaction: the GREEN leg confirms the graded record's fields render as values, with 0 `<redacted>` on the target (per obs-plan §8, the muted-diagnostic backlog close, "live-verified unredacted at the wire").

## Anti-patterns to avoid
- Never label a metric event with the client-supplied service name. `service` is an OTLP resource attribute, which is unbounded and user-controlled, so a new registration record carries counts only (per obs-plan §8 delegated-timing leaves; §11 Metrics "NEVER use unbounded label cardinality"; §11 Logs "NEVER log raw OTLP attribute values").
- Never define a soft budget. The live leg must hard-fail when first-seen-to-dot exceeds 5 s, and must not report a number without grading it (per obs-plan §11 SLO "NEVER define soft SLO budgets").
- Never add an emit site without its exact allowlist leaf. A resolving prefix fallback lets every gate pass while the fields read `<redacted>` (per obs-plan §8 `interpretation.incident.created` mechanism note and the `triage.cue.tick` leaf-completion note).

## Contract bindings
- obs ↔ tests: the live leg and `cargo xtask smoke:hue-shift` both grade `metric.*` wire records in `agent-latest.jsonl`. The record shape (§6) and the leaf field sets (§8) are the contract they consume. A changed discovery anchor changes the graded contract rows with it (per obs-plan §3 Log format JSON schema; §8 delegated-timing leaves).
- obs ↔ security: the default-deny allowlist Layer (§8 Integration points, "At subscriber Layer") is the logging half of the security plan's never-log-raw-OTLP-attribute ban. The service name on the registration path is client-controlled content.
- obs ↔ ui-bridge / capability gate: if the discovery mark's `telemetry.frontend.*` procedure changes signature or a new one is added, it rides the TauRPC bridge (§3 Logging stack) and therefore the `EXPECTED_PROCEDURES` / capability-drift gate owned by security and tests.

## Acceptance criteria contributions
- The live leg reads `metric.constellation.discovery_ms` (or a first-seen-anchored successor) from the fresh-boot run's `agent-latest.jsonl`, window-scoped to that run. It hard-fails when `duration_ms` > 5000 on the GREEN reading, and it records the ~10 s RED reading at chunk base `71f3369`. (per obs-plan §3 Log file location; §8 delegated-timing leaves; §11 SLO)
- Every field on the graded discovery record, and on any new or changed triage registration or lifecycle record, renders unredacted at the wire (0 `<redacted>`). The fields are pinned set-both-ways in a guard under `pulse-app/tests/`, and no bare `triage` or `triage.baseline` key exists. (per obs-plan §8 PII Scrubbing default-deny posture and delegated-timing leaves)
- No new record carries a service name, scope id or OTLP attribute value as a field. Registration-path emission is at most once per newly registered service or once per tick (aggregate), never per span. (per obs-plan §11 Metrics / Logs; §5 tick-aggregated counter convention)
- `metric.constellation.hue_update_ms` keeps its field set and anchor (`tier_effective_at_unix_nano`) unchanged, and `cargo xtask smoke:hue-shift` still PASSes after the fix. (per obs-plan §8 delegated-timing leaves)
