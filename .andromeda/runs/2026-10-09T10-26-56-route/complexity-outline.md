## Notes for Phase 1 synthesis

- **The ruled order (intent §6):** what replaces a thing is reachable before the chunk that removes the thing; the door stands before the removals the sidecar is built on and is what every check from outside the process reads through. No chunk maintains a thing this version replaces (intent §8): after the door's Foundation entry no entry may touch the sidecar.
- **The corpus passphrase path, checked and not leaned on.** It exists in code — `crates/corpus/src/keychain.rs:282-301` serves a passphrase-derived key when the credential store errs and `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` is set — but nothing in `.github/`, `scripts/`, `xtask/src` or `pulse-app/tests` sets that variable (0 hits, measured at `7f99c38`), so no CI run has exercised it. The outline does not need it: the corpus-encryption entry follows the door directly and precedes the harness, the gate and the baseline, so every engine-level reading in CI happens on a store that needs no key.
- **Capabilities with halves in several epochs:** P-092 (first form in Epoch 1, reach in 4, full answers in 6); P-093 (own host in 1, admission and bounds in 4); P-090 (memory and log in 5, the disk file in 6); P-112 (record in 3, report form in 9); P-113 (CI legs and pre-push in 1, the resolver with P-118, the code in 2); P-105 (the key in 3, "two tokens, one incident" in 4); P-119 (consumers land in 7 and 8); P-116 (first-read records in 3, the posture and the loopback rule in 4); P-118 (the place in 1, token material in 4).
- **Gate reachability:** one Foundation chunk — the engine under a memory cap, a loopback sender, a finding read through the door, and a second host reaching a stub (the engine takes no sender from another host before the token exists).
