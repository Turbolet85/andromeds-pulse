## Relevant amendment history
- **2026-05-02** (externalized Security Decisions Log, initial entry) — Origin of the toolchain-floor ban. The open question was "`rust-toolchain.toml` minimum `1.84` predates Edition 2024 (1.85.0); bump to `1.85.0` minimum to align with `edition = "2024"`". So the Universal ban at security-plan:470 was always a Edition-2024 lower bound. It was never a statement of what the code needs. Raising the declared floor to ≥ 1.89 keeps the ban true, though stale. That is why amending it is a wrap-time correction and not a contradiction.
- **2026-06-28 — v3 normalization: externalize the Security Decisions Log** — When the Decisions Log was externalized, `rust-toolchain` ≥ 1.85.0 was listed among the current-truth items already in the body. That is where the §Security Anti-Patterns → Universal ban this chunk's wrap amends comes from. The entry also shows the sidecar discipline: the body holds only current truth, and the old 1.85.0 wording goes to this sidecar as history.
- **2026-10-04-corpus-key-creation-is-race-free** (entry 1, "locked create-or-read") — Landed the code that needs ≥ 1.89: the exclusive `std::fs::File::lock` on the content-free per-entry lock file. Its order is lock dir resolved before any keyring call, then lock, then get, then generate/set/read back only on `NoEntry`, then unlock. A lock-dir, open or lock failure maps to unit `KeychainError::Unavailable` / `Failed`, with no path and no OS error text. It also added the corpus-key lock dir and lock-file path to the full-path NEVER-log set. This is the code whose `#[allow(clippy::incompatible_msrv)]` this chunk removes. Because the lock is taken before the store call, the CARRY skip arm leaves a file behind. The CARRY fix must not reorder or weaken this sequence on the product path.
- **2026-10-04-corpus-key-creation-is-race-free** (entry 2, "XDG_RUNTIME_DIR lock dir and the content-free lock file") — Defined the contract the CARRY must respect. The lock file `andromeda-pulse-corpus-key-{h16}.lock` is per-user, content-free, mode 0600 and NEVER deleted. A set-but-unusable `XDG_RUNTIME_DIR` FAILS CLOSED, with no temp-dir fallback, and the dir is deliberately not data-dir-confined. This was a founder-ratified boundary widening. A test that redirects the lock dir must not bypass that resolution rule, and no product path may unlink the file. Its **Kept:** clause names this chunk directly. It kept "NEVER let the rust-toolchain drift below 1.85.0" as a true minimum-pin ban and wrote "the raise rides the route entry 'The declared Rust floor matches the code'". That is the hand-off this chunk discharges.
- **2026-08-15-corpus-key-persistence** — Gave `keyring` 3 its explicit platform feature set (it has no `default` feature) so a real OS credential store is linked. It made the passphrase fallback opt-in only. It added ID-scoped `[bans] skip` carve-outs for `core-foundation` and `security-framework`, which are duplicates internal to `keyring`. This is the store-reachability behaviour behind the CARRY test's skip arm, where no reachable store exists (for example under `env -i`). A floor raise that re-resolved `keyring`'s graph would touch these carve-outs.
- **2026-08-14-workspace-key-alignment** — Measured that `keyring` with no platform backend falls to a non-persisting mock store, which gives a per-process key. That is background for the CARRY test `corpus_key_survives_a_real_process_boundary`: its skip arm must recognise a truly unreachable store, not a silently mocked one.
- **2026-08-29-advisory-backlog** — Retired `strict-path`. `std` both-sides-canonicalize became the single product path primitive, and the lock-dir resolution rides on it. It also upgraded the whole owned advisory set (wasmtime, quick-xml, lru and others) to zero. Any lock-dir redirection in the CARRY test must keep the product's canonicalize-then-check resolution intact. The floor raise must not move any of these resolved versions.
- **2026-09-29-p-025-hue-shift-observable-made-gradable** (the `cargo audit` standing deferral ENDED) — `cargo audit` is a plain pass/fail gate again. It reads the advisory-db under `$CARGO_HOME`, and its findings are counted as distinct `RUSTSEC-` ids. The extract requires the `cargo audit` and `cargo deny` verdicts to stay unchanged after the floor raise, and this sets how that is measured.
- **2026-08-28-duplicate-span-replay-fails-loudly** — `[bans] skip` carve-outs are ID-scoped and come with a closing condition. Stale skips are pruned, not kept (the windows-* copies dropped by a bump). If cargo's MSRV-aware resolver re-resolves under the new `rust-version`, the duplicate set could shift. That would force skip edits under this discipline, so a re-resolution has to be detected, not absorbed.
- **2026-09-30-dual-license** — `cargo deny check licenses` covers all 16 workspace members (no `private` key in `deny.toml`). The `rust-version` edit lands in the workspace manifest that every member inherits. `bans licenses sources` must exit 0 unchanged.
- **2026-08-30-diagnostics-un-muting-harness-truth-sweep** — Made the never-log-full-paths rule categorical. Boot records emit basenames through `pulse_app::observability::log_basename`. Any CARRY-fix diagnostic that reaches the tracing sink may log the lock path's basename only.
- **2026-10-04-linux-launch-stays-up-on-nvidia-wayland** — Recorded that edition-2024 `unsafe set_var` is sound only while one thread exists, so `render_posture` sets the env before the runtime is built. This matters if the CARRY fix redirects the lock dir by mutating `XDG_RUNTIME_DIR` in a multi-threaded test process: that runs into the same soundness precondition. A private lock dir passed explicitly, or set on a child re-exec's environment, avoids it.
