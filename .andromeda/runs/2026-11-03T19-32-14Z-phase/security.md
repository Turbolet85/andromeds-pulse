## Relevance
relevant — the chunk is a supply-chain gate repair (`cargo audit` findings closed by upgrade, `deny.toml` dispositions, the `supply-chain` job's hidden steps), squarely security-plan §Dependency Security.

## Constraints
- A finding whose advisory states a safe upgrade is never ignore-listed; it takes the upgrade or a named owner. Only a no-safe-upgrade finding may take an ID-scoped `deny.toml [advisories] ignore` entry, and only with provenance and a closing condition (per security-plan §Dependency Security, `cargo audit` paragraph, "advisory findings carry visible dispositions"). A no-safe-upgrade id, or a MAJOR bump such as zip >= 9, is a product fork that goes to the founder (chunk scope §Boundaries). The plan does not authorize deciding either one inside the phase.
- Count findings as DISTINCT `RUSTSEC-` ids, never as error blocks; a crate at two lockfile versions raises one block per version. Advisory records carry no running "Nth consecutive" ordinal (per security-plan §Dependency Security, counting rules). The re-read at HEAD must use the advisory-db under `$CARGO_HOME`, which the gate reads. The copy at `$HOME/.cargo/advisory-db` proves nothing about the gate (per security-plan §Dependency Security, "Which database copy it reads").
- `multiple-versions = "deny"` is never relaxed and the `tonic` canary is never skipped. Any new `[bans] skip` carve-out that an upgrade forces must be ID-scoped, owner-named and reasoned: why the duplicate cannot be fixed in source, and what closes it. A skip that cargo-deny flags `unnecessary-skip` after a bump is pruned, not kept (per security-plan §Dependency Security, duplicate-version carve-outs; also security-plan §Bootstrap phases, `dep-audit-tooling-install`).
- The `cargo audit` step keeps its pinned shape: a plain `run: cargo audit`, with no `uses:`, no `with:`, no token, no `continue-on-error`, no `||`, no job-level `permissions:` and no `--deny warnings` (per security-plan §Dependency Security, CI integration). `cargo deny check bans licenses sources` stays a gate. Its `licenses` check covers the workspace's own members as well as their dependencies, so a bumped crate whose license is not in `[licenses] allow` turns it red (per security-plan §Dependency Security, CI integration).
- The build fails on any `cargo audit` finding above warning, on any `cargo deny check` failure, on `cargo xtask check:npm-supply-chain` exit 1 or 2, and on `cargo xtask check:staged-artifacts` exit 1 or 2. With the audit green, all of these steps must read green (per security-plan §Dependency Security, fail-condition roster).
- The wasmtime bump must keep Cranelift as the x86_64 backend. The plugin-host controls must survive any API change the bump forces: `ResourceLimiter`, `epoch_interruption`, and the `MAX_WASM_HTTP_FIELDS_SIZE_BYTES` attach path through `WasiHttpCtxBuilder::max_field_size` (per security-plan §API Security, "Plugin host capability sandbox" row). Whether the code already wires each of these, and whether 48.0.8 changes their API, is research's question.
- The declared `rust-version = "1.95"` is set by the resolved graph (wasmtime / cranelift / pulley) and is held equal to the pinned channel by `declared_floor_equals_the_pinned_channel`. If a bumped crate raises the declared floor, the floor and the pin must move together and never drift below 1.85.0 (per security-plan §Security Anti-Patterns → Universal). The rustls / webpki-roots / webpki-root-certs bumps must not override certificate verification on the updater's outbound TLS (per security-plan §Data Protection, "In transit").

## Patterns to follow
- Close advisories with in-range lockfile bumps and take no exception. This is the 2026-09-29 Rust precedent (the rustls 0.23.45 / quinn-proto 0.11.15 / wasmtime 48.0.3 bumps that returned `cargo audit` to exit 0) and the 2026-10-06 npm precedent (in-range bumps, `package.json` and policy untouched) (per security-plan §Dependency Security).
- Prune, don't keep: when an exception's or skip's closing condition fires, remove the entry in the same change (deepmerge-ts pruned; the stale `windows-*` skips pruned) (per security-plan §Dependency Security, npm channel and duplicate-version carve-outs).
- Write carve-outs in the existing `deny.toml` record shape, as in the `core-foundation` + `security-framework` and `ureq` entries: duplicate's origin, why it cannot be fixed in source, the owner, the closing condition (per security-plan §Dependency Security, duplicate-version carve-outs).
- The auditable release build (`cargo-auditable`) is the standing pair of `cargo audit` and must stay wired after the bumps (per security-plan §Supply chain integrity, Minimal-tier additions; security-plan §Bootstrap phases, `dep-security-ci-gate`).

## Anti-patterns to avoid
- NEVER ship with the `tonic` 0.14 vs `opentelemetry-otlp` / `tonic` 0.13 duplicate unresolved, and never silence it. `cargo deny check bans` is the enforcement (per security-plan §Security Anti-Patterns → Universal).
- NEVER add a non-Cranelift `wasmtime` feature flag (e.g. Winch) on x86_64 while bumping wasmtime (per security-plan §Security Anti-Patterns → Data Protection).
- NEVER reference a third-party Action by floating tag if a workflow step is touched. Pin by 40-char SHA with a version comment (per security-plan §Security Anti-Patterns → Secrets).
