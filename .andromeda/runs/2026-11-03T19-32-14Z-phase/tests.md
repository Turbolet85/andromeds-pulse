# tests extract

## Relevance
partial. The chunk upgrades dependencies and adds no test surface of its own. The test domain still owns the supply-chain gates the chunk must turn green, the per-chunk gate set, and the toolchain-floor pin that a bumped crate can move.

## Constraints
- test-plan §3 `Per-chunk gate discipline` requires the plan's `## Test Commands` to carry the full standard gate set without conditions. `cargo xtask capability-drift` runs before `cargo nextest run --workspace --profile ci`. The `emit_taurpc_bindings` regen is the last cargo-adjacent step, and the close is `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts`, because this chunk adds no procedure. The webview npm gates drop out only while no `pulse-app/ui/**` path is touched. An npm-side fix forced by the step 10–18 gate would bring them back.
- test-plan §3 `Per-chunk gate discipline` (the merge-base probe) requires the operator-leg probe `m="$(git ls-remote origin refs/heads/main | cut -f1)" && test -n "$m" && git merge-base --is-ancestor "$m" HEAD` to come directly before any build-branch push. A red goes to the operator. It is never cleared by a fetch, merge or rebase of the pass's own.
- test-plan §9 CI Integration (Supply chain row) requires `cargo audit` to stay a plain `run:` step with no action, token or soft-fail. Exit 1 (a vulnerability) and exit 2 (could not evaluate) both fail it, on push and on pull_request alike. In the same job, `cargo xtask check:npm-supply-chain` runs before `npm ci` / `npm run build`, and a red there skips the install, the UI build and `cargo auditable build --workspace --release`.
- test-plan §9 CI Integration (Cargo deny enforcement) requires `[bans] multiple-versions = "deny"` with the tonic 0.14.x duplicate canary. The build-failure list names `cargo deny check` ban violations. An upgrade that resolves two versions of a crate is fixed in the dependency graph, not by relaxing the rule.
- test-plan §4 Unit Test Strategy (Framework) records that the workspace `rust-version = "1.95"` is set by the resolved dependency graph (wasmtime 48.0.5, cranelift 0.135.5 and pulley 48.0.5 declare 1.95.0). The xtask test `declared_floor_equals_the_pinned_channel` holds it equal to the `rust-toolchain.toml` pin in every workspace run. Whether wasmtime ≥48.0.8, rustls ≥0.23.46, tokio or the zstd/zip bumps declare a newer `rust-version` is research's question. If one does, the pin, the declared floor and that test move together.
- test-plan §9 CI Integration (Cranelift-only WASM enforcement) requires the `supply-chain` job's step "Cranelift-only WASM backend assertion (test-plan §9)" to stay green over the bumped `wasmtime` lockfile resolution.
- test-plan §10 Quality Gates (Zero-flakiness budget) requires that a test which flakes after an upgrade is quarantined and root-caused, not retried. The coverage thresholds (≥75% line / ≥85% function) are never lowered to land the bump.

## Patterns to follow
- test-plan §9 CI Integration (Supply chain row) shows how to read the audit locally before a push: the runner image's own `cargo-audit`, exit 0 meaning clean (informational advisories allowed). Its red-on-finding arm was measured only on the dev host, with a control lockfile.
- test-plan §9 CI Integration (Release build row) says the release-profile witness is the `supply-chain` job's `cargo auditable build --workspace --release`, pinned by `ci_workflow_keeps_the_linux_release_build_witnesses` in `pulse-app/tests/quality_gate_workflow.rs`. Read it after the audit turns green, without editing the workflow.
- test-plan §3 `Per-chunk gate discipline` (`cargo xtask pre-push:linux`) describes the six-stage local check (`script-modes` · `source-lint` · `npm` · `clippy` · `test` · `ci-gates` over a real console engine cycle). It runs the bumped tokio, rustls and zbus stack end to end before a push. Its verdict is `all-stages-ok`, and a run whose provisioning is missing reads `cannot-evaluate`, never green.
- test-plan §3 `Per-chunk gate discipline` (Spawned-program witness form) and its door arms run inside `cargo nextest run --workspace`. A changed API in tokio or the rustls/zbus family that is forced into code reaches the spawned-engine, door and port-claim tests there, with no separate runtime smoke unless a boot path listed in §3's Boot-smoke gate is touched.

## Anti-patterns to avoid
- test-plan §11 Test Anti-Patterns (Test Strategy) bans skipping `cargo deny check bans`. The tonic 0.14 duplicate would cause linker conflicts.
- test-plan §9 CI Integration (the no-`continue-on-error` paragraph) bans any `continue-on-error` or soft-fail on a gate step. `ci_workflow_test_gates_no_continue_on_error` keeps `cargo audit` among its 14 listed gate commands.
- test-plan §11 Test Anti-Patterns (CI) bans lowering a coverage threshold to pass the build, and §11 (Quality) bans shipping with known test failures. All gates must be green.

## Contract bindings
- tests §9 Supply chain (`cargo audit` and `cargo deny` in the `supply-chain` job) binds to security-plan §Dependency Security. The rule that a finding with a stated safe upgrade is never ignore-listed, and the ID-scoped `[advisories] ignore` entries with provenance, live on the security side. The tests side holds the step shape and its exit semantics.
- tests §4 Framework (the `rust-version` = toolchain pin, held by `declared_floor_equals_the_pinned_channel`) binds to architecture §Stack and Technologies / §Inherited Defaults. The scope names those as master sentences carrying pinned versions. test-plan §4 Framework and §5 Integration Test Strategy (the plugins row, "lockfile-resolved 48.0.5") also name the wasmtime version, so a bump leaves them stale. They are amended through the wrap, never by a phase edit.

## Acceptance criteria contributions
- (tests) `cargo audit` exits 0 at HEAD (no vulnerability; informational warnings allowed), and the CI `supply-chain` job is green on the pushed tip with its later steps (`cargo deny check bans licenses sources`, `cargo xtask check:npm-supply-chain`, `cargo auditable build --workspace --release`) run and read, not skipped (per test-plan §9 CI Integration, Supply chain row).
- (tests) `cargo deny check bans licenses sources` exits 0 with `multiple-versions = "deny"` unchanged and no `[bans] skip` covering tonic (per test-plan §9 CI Integration, Cargo deny enforcement).
- (tests) The standard gate set passes in order, `cargo nextest run --workspace --profile ci` included (with `declared_floor_equals_the_pinned_channel` green), and the bindings close `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts` exits 0 (per test-plan §3 `Per-chunk gate discipline`).
- (tests) The `supply-chain` job's Cranelift-only WASM backend assertion step is green over the upgraded wasmtime (per test-plan §9 CI Integration, Cranelift-only WASM enforcement).
