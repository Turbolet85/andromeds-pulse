## Relevance
partial — the chunk changes no surface, crate or resource, but it moves dependency pins that architecture locks (toolchain floor, wasmtime line, keyring features, locked stack versions) and runs the CI supply-chain job that architecture defines.

## Constraints
- The toolchain stays pinned at rustc 1.95.0, with the declared `rust-version = "1.95"` equal to the pin and set by the resolved dependency graph, per architecture §Stack and Technologies (Primary language / runtime row). A bumped crate whose target version declares a `rust-version` above 1.95 cannot be taken under that pin. Raising the pin is a product fork for the founder's dialog, never a phase edit. Research must check whether any target version in the freight's solution table (`>=` ranges) declares a floor above 1.95.
- wasmtime stays on the 48.x line. Per architecture §Stack and Technologies (Plugin runtime row), 49.x is out of reach while the toolchain is pinned at 1.95, because 49.0.2 needs Rust 1.96. The freight's `>=48.0.8, <49.0.0` arm is the only arm open, and the Component Model + WIT choice stays as architecture §Established Decisions [Plugin Runtime] locks it.
- The locked stack lines keep their major/minor: Tauri 2.x, `tonic` 0.14.x, `axum` 0.8.x on `hyper` 1.x, DuckDB 1.5.x, `keyring` 3.x, `thiserror` 2.x / `anyhow` 1.x, per architecture §Inherited Defaults. The tonic/opentelemetry-otlp caveat stands per architecture §Established Decisions [Backend Framework — OTLP receiver]. A fix that needs one of these lines to move is a decision change and goes to the founder's dialog. It is not a lockfile patch.
- `keyring` 3 keeps its explicit platform feature set (`apple-native` / `windows-native` / `sync-secret-service` / `crypto-rust`). Per architecture §Stack and Technologies (Secret / key storage row), that set is load-bearing: a bare `keyring = "3"` links no backend and silently yields a per-process key. The zbus_names / zvariant / zvariant_derive advisories (no stated solution) therefore cannot be closed by dropping `sync-secret-service`. Research must establish whether those crates enter only through that feature.
- Dependencies keep flowing toward `pulse-app` as a DAG with `pulse-app` as the only root, and the only carve-out is the dev-only edge to `test-support`, per architecture §Cross-cutting Patterns → Module dependency direction. Flag-specific dependencies enter the graph only under their feature, while `mcp-server` stays a plain dependency in every build, per architecture §Cross-cutting Patterns → Feature-gate hygiene. A bump must not add a crate edge or a feature.
- Code changes that a bumped crate's changed API forces must pass `cargo clippy --workspace --all-targets --all-features -- -D warnings`, so all features are included (`otap-ingest`), per architecture §Infrastructure Patterns → Build system.
- cargo-deny license-checks the workspace's own crates as well as their dependencies under `MIT OR Apache-2.0`, set once at `[workspace.package]` and inherited by every member, per architecture §Established Decisions [License]. A bump must not touch member `license` inheritance.

## Patterns to follow
- Record pins in the plan's existing form: "Cargo.toml requirement X, lockfile-resolved Y as of {date}", the RUSTSEC ids closed, and "with no advisory ignore". The wasmtime row of architecture §Stack and Technologies is the precedent. The sentences change through the wrap's amendments, never in the phase.
- The CI `supply-chain` job runs `cargo audit` as a plain `run:` step (exit 0 clean · 1 a vulnerability · 2 could not evaluate, on the runner image's own `cargo-audit`) followed by the `cargo auditable build --workspace --release` smoke, and restores the `boot-Linux` cache read-only, per architecture §Infrastructure Patterns → CI/CD approach. A `pull_request` run builds the merge ref, so a green reading is of the branch merged with `main`.
- The npm gate is `cargo xtask check:npm-supply-chain`: exit 0 / 1 / 2, six named verdict arms, policy in `pulse-app/ui/npm-policy.json`, and exceptions that require ghsa/package/reason/owner/closing_condition, per architecture §Occupied Resources (xtask CLI surfaces). Read its verdict arm when steps 10–18 surface.
- Shared CI logic lives in `xtask`, so a supply-chain red can be reproduced locally with `cargo xtask <task>`, per architecture §Infrastructure Patterns → CI/CD approach.
- After a bump, use the existing manifest-reading pins as the regression net: `declared_floor_equals_the_pinned_channel` (architecture §Stack and Technologies, Primary language row), `license_check` (architecture §Established Decisions [License]) and `test_support_edges` (architecture §Cross-cutting Patterns → Module dependency direction).

## Anti-patterns to avoid
- Taking wasmtime 49.x, or raising `rust-toolchain.toml` / `rust-version`, to reach a patched release without the founder's dialog. Architecture §Stack and Technologies (Plugin runtime row) records 49.x as out of reach at the 1.95 pin.
- Weakening `keyring` to a bare `keyring = "3"`, or removing a platform feature, to drop zbus-family advisories. Architecture §Stack and Technologies (Secret / key storage row) bans this because it silently yields a per-process key.
- Reintroducing a feature gate or sidecar on the MCP path, such as `--features mcp-server`, an `mcp-test` job or `rmcp`, while reshaping dependencies. Architecture §Infrastructure Patterns → CI/CD approach pins its absence through `ci_workflow_holds_no_mcp_test_job_and_no_mcp_server_feature`, and architecture §Established Decisions [MCP Server Surface] says no `rmcp`.
