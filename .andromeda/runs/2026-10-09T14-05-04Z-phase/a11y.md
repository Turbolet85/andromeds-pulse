## Constraints
- a11y-plan §3 CI integration (Pipeline integration) requires the a11y assertions to run in the same `ci.yml` pipeline as the tests, as their own blocking `a11y` job parallel with the test jobs, in a fixed step order (UI build, Playwright chromium, the PR-only base download, `cargo xtask test:a11y`). The Linux leg that stays must keep that whole sequence and its blocking status: the edit removes runners, never a step.
- a11y-plan §3 CI integration (Pipeline integration) names the `a11y` job's matrix as three operating systems. This chunk makes that label untrue, so it is an expected amendment at the wrap; phase edits no spec source (scope, "The records that describe a three-system CI are corrected at the wrap").
- a11y-plan §9 CI Integration (Pipeline integration) describes the job as a "matrix job". After the chunk the job has one runner; whether the job keeps a one-value matrix or loses the key is the plan's choice, and the §9 wording follows it at the wrap.
- a11y-plan §3 CI integration (Artifact) requires the structured violation JSON uploaded as a CI artifact, and its Pipeline integration label requires the upload `if: always()` under per-OS names. The Linux names the scope lists (`a11y-violations-Linux`, `playwright-a11y-report-Linux`) must resolve unchanged, and the `if: always()` on the upload must survive the removal of the always-true `runner.os == 'Linux'` conditions.
- a11y-plan §3 CI integration (Per-PR regression detection) requires a pull-request run to download the base-branch summary under the name `a11y-violations-base` and to fail on any new `{surface, wcag_criterion, selector, severity}` tuple. Which leg of which event PRODUCES that base artifact is research's question: if a leg that leaves is its producer, the gate would compare against nothing.
- a11y-plan §10 SLO Invariants & A11y Budgets (Standard+ invariants) requires zero new violations per PR by artifact comparison, and its always-required invariant allows no retry-once policy. The matrix edit may add no retry, no `continue-on-error` and no `fail-fast` relaxation to the remaining leg.
- a11y-plan §9 CI Integration (per-pipeline-stage table) requires a Lint-stage `eslint-plugin-jsx-a11y` gate that fails CI, in a stage other than the `a11y` job. Whether that lint runs on the Linux leg of the job that hosts it (and so survives the removal of that job's other legs) is research's question.

Whether any file of the a11y harness (a spec, a config, `cargo xtask test:a11y`, the aggregator) branches on the operating system or reads a `ci.yml` matrix value is research's question; the scope already asks P3 for such a reader.
- The scope lists one `runner.os == 'Linux'` condition inside the `a11y` job's line range (`ci.yml:334`). a11y-plan §3 CI integration (Pipeline integration) requires every step of the sequence on the leg that stays, so removing the condition must leave that step unconditional, not remove the step. What the step is, is research's question.
- a11y-plan §10 SLO Invariants & A11y Budgets (Performance budget per a11y CI run) states the budget the `a11y` job's wall-clock is read against. The chunk's before/after table already carries the `a11y (ubuntu-22.04)` reading; record it as a reading beside that budget, not as a new gate.
- a11y-plan §3 Screen reader test pattern (Per-surface test spec, Supplemental to automated) describes per-platform MANUAL passes, supplemental and not CI legs. They are not this chunk's: the wrap corrects only text that states a three-system CI, never the manual-pass platform list.

If research finds any harness file in the chunk's diff, that command is the check that the suite still enumerates; the bare form reads the inert default config and proves nothing.

## Anti-patterns to avoid
- a11y-plan §11 A11y Anti-Patterns (CI) bans a soft a11y gate and bans deferring a11y to post-merge: the remaining `a11y` leg may not become non-blocking, optional or skipped as a side effect of the matrix edit.
- a11y-plan §11 A11y Anti-Patterns (SLO) bans a retry-once policy and bans skipping the per-PR diff at this tier: the base download and the tuple comparison stay on the leg that stays.
- a11y-plan §11 A11y Anti-Patterns (Strategy) bans a conformance claim without machine-verifiable evidence: after the chunk the CI evidence is the Linux leg's alone, so no record written at the wrap may cite a CI a11y reading for the Windows or macOS runners.
