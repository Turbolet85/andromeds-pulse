# security extract

## Relevance
partial — the chunk edits one workflow file (`.github/workflows/ci.yml`) and no product code; the security domain's stake is that every CI security gate and every workflow-hardening rule the plan mandates is still in force on the Linux-only workflow, and that the removed legs take no gate with them.

## Constraints
- security-plan §Bootstrap phases (`dep-security-ci-gate`) requires `step-security/harden-runner`, pinned by 40-char commit SHA, as the FIRST step of every job in `ci.yml`. Every job the chunk keeps (`lint-test`, `a11y`, `mcp-test`, `boot`, `supply-chain`, `coverage`) must still open with it after the matrix and `if:` edits; whether each job opens with it at `0b61bfb` is research's question.
- security-plan §Security Anti-Patterns § Secrets requires every third-party Action reference to be `<owner>/<repo>@<40-char-SHA> # vX.Y.Z`, never `@v2` or a floating tag. The chunk removes `uses:` lines with the legs; any line it rewrites or re-indents keeps the SHA and its version comment byte-for-byte.
- security-plan §Secret Management (GitHub Environment scoping) requires `permissions: { contents: read }` at the top of every workflow, with elevation per job only on a publish step. The chunk adds no `permissions:` key and widens none; the six remaining jobs have no publish step.
- security-plan §Dependency Security (CI integration) requires `cargo audit`, `cargo deny check bans licenses sources`, `cargo xtask check:npm-supply-chain`, the `xtask` capability-drift check and `cargo xtask check:staged-artifacts` to run in `ci.yml` and to fail the build. None of these may leave with a leg. Which job carries the capability-drift and staged-artifacts steps, and whether any of them sits under one of the `if: runner.os == 'Linux'` conditions the scope lists for removal (`ci.yml:122`, `:128`, `:132`, `:514`), is research's question: the condition may go, the step may not.
- security-plan §Dependency Security (Supply chain integrity) requires the `cargo-auditable` build (`cargo auditable build --release`) so a release binary carries its dependency tree. With the `release` job gone, the `supply-chain` job's auditable build is the one carrier left in `ci.yml` and must stay as it is; the scope names it the Linux release-build witness.
- security-plan §Secret Management (Secret scanning in CI) and §Bootstrap phases (`secret-scanning-ci-gate`) require a per-PR secret-scanning step, SHA-pinned, that fails the build on a detected secret. The scope counts `secret-scan` as the seventh check that stays; the chunk does not touch it.
- security-plan §Secret Management (GitHub Environment scoping) requires every signing secret and release credential to live in the `production-release` Environment behind a manual approval gate. The scope reads the removed `release` job of `ci.yml` as a build smoke with no secret and no environment; whether that job references any `secrets.*` value or an `environment:` key at `0b61bfb` is research's question, and a reference found there is a boundary question, not a silent deletion.

## Patterns to follow
- One job, one hardened opening: `harden-runner` first, then SHA-pinned checkout and setup actions, per security-plan §Bootstrap phases (`dep-security-ci-gate`). Collapsing a matrix to one runner changes `runs-on` and the matrix block only, never the step order above the first build step.
- Plain named `run:` steps for first-party gates (`cargo xtask check:npm-supply-chain`, `cargo xtask check:staged-artifacts`), which trigger no SHA-pinning convention, per security-plan §Bootstrap phases (`dep-security-ci-gate`) and §Dependency Security (CI integration). An edit that removes an always-true `if:` leaves such a step as an unconditional plain step.
- The npm gate reads the committed lockfile after SHA-pinned setup-node and runs no `npm ci`, per security-plan §Dependency Security (CI integration, npm channel). The `supply-chain` job is outside this chunk's edit set except for a redundant condition, so that shape stays as read.
- A Python 3 interpreter is a test-time requirement on every runner that runs the workspace tests, and a missing interpreter fails the test rather than skipping it, per security-plan §Dependency Security (CI integration, vendored test-only channel). The Linux `lint-test` leg is the one runner left that must provide it.

## Anti-patterns to avoid
- NEVER reference a third-party GitHub Action by `@v2` or a floating tag (security-plan §Security Anti-Patterns § Secrets) — applies to any line the edit retypes.
- NEVER grant `permissions: { contents: write }` at the workflow level (security-plan §Security Anti-Patterns § Secrets) — the chunk has no reason to touch the workflow-level block.
- NEVER ship a release without the `tonic` 0.14 vs 0.13 duplicate resolved, with `cargo deny check bans` as the enforcement (security-plan §Security Anti-Patterns § Universal) — the `bans` step stays in the remaining workflow; `multiple-versions = "deny"` and `deny.toml` are not this chunk's to touch.
