## Patterns to follow
- Reading a run's application log goes through the artifact, not the job log: obs-plan §9 CI failure → artifact triage workflow (download the log artifact by run id, filter the JSON lines by level and target). This is how the `boot smoke (ubuntu-22.04)` verdict of every run the chunk reads gets its log reading; the artifact is the boot job's (`logs-boot-Linux`), per obs-plan §9 Telemetry artifact handling.
- The `WATCH:`'s "no process-end record" is read against obs-plan §7 Error classes captured (Process-end cause): the plan requires exactly one `app.exit` record for every LOGGABLE end and names the ends that are unloggable by construction. A boot-smoke log that ends with neither `app.exit` nor `app.panic.fatal` is therefore read as "an end outside the loggable set, or the job's own stop", never as "no end happened". An observation only: the scope gives it no criterion, task or gate, and this extract adds none.
- A grader over the log is NEUTRAL-tolerant for an unrequired arm and fails a required empty one: obs-plan §10 Load-profile constraints. A step that expects samples names its arm; a step that reads the boot-smoke log requires none. The edit keeps each call's required set as it is.
- Artifact names are derived per job so two uploads in one run never collide: obs-plan §9 Telemetry artifact handling. If the edit replaces a `runner.os` expression by a literal, the literal is the value the Linux runner resolved (`Linux`), so the name every later reader uses is the same.

## Anti-patterns to avoid
- NEVER lose telemetry artifacts — obs-plan §11 CI. A log-upload step deleted or orphaned together with an OS condition, a matrix key or the `release` job is this ban.
- NEVER define soft SLO budgets (no enforcement) — obs-plan §11 SLO. A perf, panic or heartbeat gate step that leaves, turns `continue-on-error`, or loses its required arm while the conditions are being cleaned up turns an enforced budget into a soft one.
- NEVER add retry-once policies for panic handling — obs-plan §11 SLO. The plan scopes this ban to panic handling; the boot-smoke red of the `WATCH:` carries no panic record, so the plan does not state it for a job re-run. It is cited for its stated reason (a retry masks a real failure): the chunk adds no retry or re-run wrapper to the `boot` job.
