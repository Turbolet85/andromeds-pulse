# obs extract

## Relevance
Relevant — deliverable 1 ("live observation of the feed… whatever instrumentation this requires is part of the chunk") and the counter-based proof are self-observation work governed by this plan.

## Constraints
- Self-observation for the localization run must use the `tracing` ecosystem only, emitted JSON-per-line to `~/.andromeda-pulse/logs/agent-latest.jsonl` — no OTel SDK in the self-runtime and never the product's own `:4317`/`:4318` receivers as a telemetry sink (per obs-plan §3 Tracing init / Logging stack, §11 Universal). The scope's "self-observation (`tracing` only)" line matches this mandate.
- Every new or changed log line must carry the §6 required fields (`timestamp`, `level`, `target`, `message`, `fields{}`) with `service.name`/`service.version`/`deployment.environment` supplied as default subscriber fields — the schema is a binding contract taken verbatim from the test harness (per obs-plan §6 Log Coverage, §3 Log format JSON schema).
- Vector 1 forbids raw OTLP attribute values in self-observation logs. The region being instrumented is exactly the per-span-event `exception.type` / `.message` / `.stacktrace` extraction, so diagnostic emissions there are limited to counts / booleans / digests (`attributes_count`-shaped, `argument_digest`-shaped), never the attribute values themselves (per obs-plan §8 PII Scrubbing, §1 Telemetry triggers logging-sensitive Vector 1, §11 Logs).
- §8 runs a default-deny allowlist per module (`buffer`: `rows_ingested`, `eviction_count`, `memory_bytes`, `retention_window_seconds`); any new consumer/appender diagnostic field is an intentional allowlist extension, not an incidental addition (per obs-plan §8 default-deny posture).
- The appender inner loop and per-row operations are named hot paths: no `info`-level emission per span-event, and any expensive field formatting must be level-gated (`tracing::enabled!`) since field args evaluate regardless of the subscriber filter (per obs-plan §11 Telemetry Strategy, §11 Logs, §11 Metrics).
- The ingest→buffer hand-off crosses a `tokio` task boundary; §10 requires trace-context propagation on every cross-surface hop and §11 forbids holding a span guard across `.await` without `.in_current_span()`. Whether the existing consumer/appender path already propagates `tracing::Span::current()` across the mpsc hand-off — and therefore whether the dead region is even correlatable in one trace — is research's question (per obs-plan §10 Standard+ invariants, §11 Spans/Traces).
- Any counter/gauge the proof reads must be emitted as a `tracing` event with a `metric.{module}.{measure}` target and a numeric `value` plus enumerated label fields, with the agent computing aggregates by `jq` over the file (per obs-plan §5 Metric emission convention). Whether `storms_detected_total` / `fingerprints_evicted_total` / `tracked_fingerprints_count` already conform to that naming and are already file-readable is research's question.

## Patterns to follow
- P1's existing must-trace span chain `otlp.grpc.export.request` → `duckdb.append` → `viz.query.traces` is the spine the dead region sits inside; localization instrumentation belongs as child spans/fields on that chain rather than as a parallel ad-hoc channel (per obs-plan §4 Scenario P1, §1 Critical paths P1).
- Span naming `{module}.{operation}` with `span.kind` as an explicit field, and `#[tracing::instrument(skip(...), fields(...))]` with an explicit allowlist — the same shape already mandated for buffer/ingest handlers (per obs-plan §4 Span naming / Span kind convention, §8 Integration points "at source").
- Heartbeat ticks as `tracing::info!(target: "{module}.tick", …)` every 15s carrying live subsystem counters; the scope's storm-tick line is tick-shaped, and §3's complementarity rule says ticks and the `health` command are independent mechanisms that must both reflect live state (per obs-plan §3 Heartbeat ticks + Complementarity paragraph).
- Boundary must-log wrappers: DuckDB/buffer boundaries log `query_id` / counts / `duration_ms`, never payload or query text (per obs-plan §6 Boundary-call wrappers, §8 Vector 5).
- Evidence gathering over `agent-latest.jsonl` scoped to the run window and NEUTRAL-tolerant when a stream is absent, per the check-script convention (per obs-plan §10 DuckDB Connection Isolation & Load-Profile Operational Constraints).

## Anti-patterns to avoid
- No fingerprint value (or any per-span-event identity) used as a span name, target suffix, or metric label field — that is high-cardinality span naming and unbounded label cardinality (per obs-plan §11 Spans/Traces, §11 Metrics, §5 cardinality discipline).
- No raw `exception.*` values, no `anyhow::Error` / stack traces with Rust struct names crossing into logs while chasing the defect; use `tracing-error` SpanTrace and sanitized `AppError` instead (per obs-plan §11 Logs, §11 Spans/Traces, §8 Vector 2).
- No "temporary" `println!`/`dbg!` or unstructured stderr text as the localization instrument — unstructured output is unparseable by the agent and corrupts the rmcp stdio protocol if the sidecar path is exercised (per obs-plan §11 Logs, §11 Universal).

## Contract bindings
- **obs ↔ tests harness:** the §6 log-format JSON schema is verbatim from the test plan's Test Harness Contract (obs aligns to tests, not vice versa); the chunk's guard test and the counter-based proof both consume that shape (per obs-plan §3 Log format JSON schema, §6).
- **obs ↔ tests CI gates:** zero-`app.panic.fatal`, zero-spans-in-log, and ≤45s heartbeat-gap gates run as post-run `jq` checks in `xtask/ci/` over `agent-latest.jsonl`; the localization run's artifacts flow through the same gate set (per obs-plan §10 CI gates, §9 CI Integration).
- **obs ↔ security:** Vectors 1/2/5 redaction points (ingest attribute scrubbing, IPC `AppError` sanitization, DuckDB param anonymization) are enforced at the logger/instrument configuration this chunk touches (per obs-plan §8 PII Scrubbing, §1 Telemetry triggers).

## Acceptance criteria contributions
- (obs) Every log line added or changed on the ingest→consumer→appender→fingerprint path parses as NDJSON with `timestamp`/`level`/`target`/`message`/`fields` plus service identity defaults (per obs-plan §6 Log Coverage).
- (obs) Under the canary storm, no raw `exception.type` / `exception.message` / `exception.stacktrace` value and no raw OTLP attribute value appears in `agent-latest.jsonl` — only counts, booleans, or digests (per obs-plan §8 PII Scrubbing Vector 1, §11 Logs).
- (obs) No per-span-event emission in the appender loop at `info` level or above, and no ungated expensive field formatting in that loop (per obs-plan §11 Telemetry Strategy, §11 Metrics).
- (obs) The counters the proof depends on are readable by an agent from the JSON log file alone via `jq`, emitted under `metric.{module}.{measure}` or a `{module}.tick` line with bounded label fields; and the observation run shows zero `app.panic.fatal` with no >45s tick gap, NEUTRAL-tolerant where a stream is legitimately absent (per obs-plan §5 Metric Coverage, §2 Agent-readable invariants, §10 CI gates).
