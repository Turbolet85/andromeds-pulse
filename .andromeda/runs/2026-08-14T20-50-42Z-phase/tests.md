## Patterns to follow
- §5 boundary pattern `ingest → buffer`: send a valid OTLP payload via a `tonic` 0.14.5 client to loopback `:4317`, then assert by querying the in-memory DuckDB directly — the established shape for proving the canary storm crosses the region (per test-plan §5).
- §6 P1 explicit-signal polling: boot → send synthetic spans → poll `health` until `subsystems.buffer.rows_ingested` crosses a threshold within a bounded timeout → assert. This is the sanctioned substitute for sleeps when waiting on ingest (per test-plan §6 Scenario P1, §3 status-endpoint shape).
- §4 Rust unit conventions: co-located `#[cfg(test)] mod tests { … }` inside the crate source (no separate `tests/` dir), `#[test] fn test_<entity>_<scenario>()` naming, `#[rstest]` 0.26.1 `#[fixture]` composition for reusable builders (per test-plan §4 "Conventions" + "Fixture pattern at unit level").
- §7 isolation + clock control: `tempfile::TempDir` + fresh in-memory DuckDB per test; `#[tokio::test(start_paused = true)]` with `tokio::time::advance()` for anything touching the 60s retention/eviction window that `fingerprints_evicted_total` depends on (per test-plan §7 "Time-sensitive data", §8 "Time mocking").
- §3 `logs` agent-parsing signals as the localization evidence format — per-boundary log lines greppable by `target`/message, error extraction by `jq 'select(.level == "ERROR")'` (per test-plan §3 "Agent-parseable signals").

## Anti-patterns to avoid
- NEVER synchronize on `sleep(N)` and NEVER read a real clock (`Instant::now()` / `chrono::Utc::now()`) in the storm/eviction assertions — wait on an explicit signal and inject time (per test-plan §11 E2E + Universal).
- NEVER mock DuckDB at integration level and NEVER mock the OTLP receiver under test — use the in-memory instance and a live loopback `tonic` client (per test-plan §11 Integration + Mocking, §2 "over-mock at integration level").
- NEVER pin the guard test to private crate-internal functions of `appender.rs`/`fingerprint.rs`, and NEVER assert on raw OTLP protobuf bytes — assert at the public module boundary (the observer call and its decoded fields) (per test-plan §11 Unit + Integration).

## Contract bindings
- **tests ↔ obs (harness contract).** The 5-command discipline binds `status` to the obs-declared JSON shape and `logs` to the NDJSON `tracing` path (per test-plan §3 "Status endpoint shape" / "Log format" / bootstrap item `log-format-bind-with-obs`). The chunk's acceptance discriminators `storms_detected_total` and `fingerprints_evicted_total` are obs-owned counters; test-plan §3's documented status shape lists only `otlp_grpc_receiver` / `otlp_http_receiver` / `buffer` / `ingest_channel`, so **which agent-readable surface exposes the latched counters — status subsystems, a `tracing` line, or neither yet — is research's question**, and the guard test must bind to whichever obs designates.
- **tests ↔ arch/security (capability drift).** `cargo xtask capability-drift` runs unconditionally in the gate set, and §9 chains `cargo xtask verify:capability-matrix` after it in CI. The scope anticipates no new TauRPC procedure or capability grant [inferred], so no new P-0NN matrix entry is expected — but the drift check still gates.
