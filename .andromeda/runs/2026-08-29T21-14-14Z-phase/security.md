## Relevance
**Relevant** — this chunk is core security-domain work: the RustSec owned-set upgrades, the `cargo deny` / `cargo audit` gate surface, and a dependency-manifest decision about the plan's own declared validation primitive.

## Constraints
1. **Visible disposition is mandatory; green-by-ignore is banned.** Per security-plan §Dependency Security → CI integration, findings with a stated safe upgrade are never `[advisories] ignore`-listed — they get a named owner or the upgrade; only no-safe-upgrade findings may take an ID-scoped ignore entry with provenance. All 8 ids in this chunk's set are recorded as upgradeable, so none is ignore-eligible.
2. **`deny.toml` discipline is unrelaxable.** Per §Dependency Security → Duplicate-version carve-outs and §Bootstrap phases → `dep-audit-tooling-install`: `multiple-versions = "deny"` is never relaxed and the `tonic` canary `[[bans.deny]]` entry is never skipped; every `[bans] skip` is ID-scoped, owner-named, reasoned with why it is not source-fixable and what closes it; `[sources]` stays restricted to `crates-io` (no git/registry overrides); the `[licenses]` SPDX allowlist is load-bearing for the Homebrew/Scoop channels, so a major bump pulling a new license must not be waved through.
3. **Standing-deferral mechanics bind the wrap probe.** Per §Dependency Security → CI integration (Standing deferral — `cargo audit` unrunnable): the full-form probe runs at the ratified every-3rd-wrap interval (body currently names the next point as session 58), the exit is read DIRECTLY and never through a pipe, the basis is re-read first-hand, the overlap (`cargo deny check advisories`) is re-enumerated as **DISTINCT `RUSTSEC-` ids** — never a block count (counting rule (a): 10 blocks for 8 ids) and never a carried "Nth consecutive" ordinal (counting rule (c)). The deferral ends the first time `cargo audit` loads.
4. **The `wasmtime` bump must not weaken the plugin sandbox.** Per §API Security → Plugin host capability sandbox + §Input Validation → Plugin host inputs + §Anti-Patterns → Data Protection: Cranelift-on-x86_64 must remain the backend (the unaffected configuration for CVE-2026-34941 / CVE-2026-35195), with a per-`Store` `ResourceLimiter` memory/table/instance cap, `Config::epoch_interruption(true)`, and `MAX_WASM_HTTP_FIELDS_SIZE_BYTES` declared in `crates/plugins/src/engine.rs` (explicitly **not** a `wasmtime::Config` method). The plan states these against "wasmtime 25+"; whether wasmtime 46 still exposes them under the same names, and whether the code already satisfies them at HEAD, is research's question.
5. **The `rmcp` bump collides with two declared pins.** §Input Validation → MCP stdio inputs states the pin as `rmcp` **0.3.x** pending the open Inherited Defaults reconciliation, and §Dependency Security → Pinning carries that as open item (b) (`rmcp` "1.5.0" arch reference vs the published line), required to be resolved before tagging v0.1.0. A move to ≥1.4.0 must close item (b) explicitly rather than silently, and owes an amendment at both sites. The same row requires `serde` tool-argument structs and `query_*` tools sharing the `viz` prepared-statement code path — both must survive a `#[tool]` macro/API change. Whether HEAD is at 0.6 (as the scope asserts) rather than the documented 0.3.x is research's question.
6. **The `h2` fix rides `hyper` → `axum`, which is a pinned security surface.** §Input Validation (OTLP/HTTP `:4318` row) and §API Security pin `axum` 0.8.x and require `DefaultBodyLimit::max(8 * 1024 * 1024)`, deny-by-default `CorsLayer::new()`, and the Host-header allowlist middleware. A bump inside 0.8.x is consistent with the pin; whether those three controls are still in force after it is research's question.
7. **`strict-path` adopt-or-drop is not pre-decided by the plan.** §Bootstrap phases → `input-validation-library-install` carve-out (b) records the declared-but-unused state (workspace + five member manifests, zero `.rs` users) as awaiting its own cleanup entry, and §Anti-Patterns → Input names `strict-path` as "the intended primitive for the other product path boundaries" while recording that it was declined for the L4 guard. Either end state must leave the categorical canonicalize-and-confine mandate (§Anti-Patterns → Input) intact — that ban is primitive-agnostic. A DROP falsifies both clauses that name `strict-path` and owes an amendment plus Tier 2/3 re-derivation.

## Patterns to follow
- **Carve-out entry shape:** the two live `[bans] skip` entries are the templates — `core-foundation` + `security-framework` (duplicate internal to `keyring`, closes when keyring consolidates) and `ureq` (both copies `[build-dependencies]` only, closes when `crates/triage/build.rs` moves to `ureq` 3) — each naming owner, reason-not-source-fixable, and closing condition (per §Dependency Security → Duplicate-version carve-outs).
- **Prune, don't keep, a skip the bump made unnecessary:** the `windows-core` / `windows-result` / `windows-strings` precedent — cargo-deny flags `unnecessary-skip`, and a stale skip hides the duplicate's return (same §anchor).
- **Split gate pair:** `cargo deny check bans licenses sources` is the pass/fail gate; `cargo deny check advisories` is the separately-observed named overlap signal, with its exit read directly (per §Dependency Security → CI integration).
- **`std` both-sides-canonicalize on the `publish_workspace_key` precedent** is the incumbent confinement primitive of record, and the reason the L4 guard declined `strict-path` (zero repo-wide `.rs` users, unmeasured Windows `\\?\` behaviour) — the pattern any ADOPT would displace (per §Input Validation → published workspace key row + §Anti-Patterns → Input).
- **SHA-pinning convention** if any CI gate wiring is touched: `<owner>/<repo>@<40-char-SHA> # vX.Y.Z` for `EmbarkStudios/cargo-deny-action` and `actions-rust-lang/audit` (per §Bootstrap phases → `dep-security-ci-gate`, §Anti-Patterns → Secrets).

## Anti-patterns to avoid
- Ignore-listing any advisory that has a stated safe upgrade (per §Dependency Security → CI integration, visible-disposition clause).
- Relaxing `multiple-versions = "deny"`, skipping the `tonic` canary, or letting the `tonic` 0.14 ↔ `opentelemetry-otlp` 0.31 (`tonic` 0.13) duplicate go unresolved (per §Bootstrap phases → `dep-audit-tooling-install` + §Anti-Patterns → Universal).
- Adding a non-Cranelift `wasmtime` feature flag on x86_64 without re-checking the April 2026 advisory cluster (per §Anti-Patterns → Data Protection).

## Contract bindings
- **security ↔ tests:** the dependency gate is a job inside the single CI workflow (`ci.yml`), not a parallel pipeline (per §Dependency Security → CI integration + §Bootstrap phases → `dep-security-ci-gate`); the scope's entry-mandated plugin-host and MCP-sidecar verifications run through the tests harness (nextest), so the pass/fail wording is tests-owned and the security content is mine.
- **security ↔ obs:** `MAX_WASM_HTTP_FIELDS_SIZE_BYTES` doubles as the span field name `max_wasm_http_fields_size_bytes` per the 2026-05-11 amendment's obs-instrumentation note — if the wasmtime 46 bump relocates or renames that const, the obs field name moves with it.
- **security ↔ arch:** the manifests, `deny.toml` and the plugin Engine/Config + MCP double-gate posture are arch-owned capability decisions; this plan supplies the bans and required controls, not the capability choice.
- **security ↔ distillations:** `.claude/rules/security.md` §Input-validation and `.claude/docs/security-summary.md` re-derive from this plan via `/andromeda-setup-project --delta`; a `strict-path` DROP or an `rmcp` pin move makes them stale (recurring requirement across the amendment history).
