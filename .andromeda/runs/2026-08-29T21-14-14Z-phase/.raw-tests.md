## Relevance
Relevant — no new product surface, but the chunk's verification is entirely gate-shaped (cargo-deny gate pair, workspace suite, and entry-mandated plugin-host + MCP-sidecar legs), all of which the test plan owns.

## Constraints
- The **standard gate set is unconditional regardless of scope** — `cargo fmt --check` · `cargo clippy --workspace --all-targets --all-features -- -D warnings` · `cargo nextest run --workspace --profile ci` · `cargo xtask capability-widening-check` · `cargo xtask check:ingest-progress` · `cargo xtask capability-drift` (LAST) — and the webview trio is excluded only when the chunk touches zero `pulse-app/ui/**` paths (per test-plan §3 Per-chunk gate discipline). A manifest-only chunk does not earn a reduced list.
- `cargo deny check bans` is a **gate that may never be skipped**, with `multiple-versions = "deny"` and the tonic-vs-opentelemetry-otlp duplicate named as the reason (per test-plan §11 Test Strategy + §9 Cargo deny enforcement); §9 Build-failure conditions makes a `cargo deny check` violation a build failure alongside clippy/fmt.
- `wasmtime` must resolve with the Cranelift backend, asserted at build time — §9 specifies the CI step `cargo tree -p wasmtime | grep -q "cranelift" || exit 1`, and §1 mandates the `security-vector-coverage: Cranelift-only WASM` trigger as a build-time assertion (per test-plan §9 Cranelift-only WASM enforcement + §1 Coverage triggers). Whether that step is actually wired in `.github/workflows/ci.yml` today is research's question.
- The MCP surface carries a **compile-time + runtime double gate** that requires both a negative and a positive test (`--features mcp-server` AND `ANDROMEDA_PULSE_MCP_ENABLED=true`), and the feature-gated sidecar tests sit **outside** the default `--workspace` run (per test-plan §1 `security-vector-coverage: MCP feature + runtime gating` + §1 `mcp-incident-read-back-cross-process-coverage`). A green workspace run therefore does not attest the rmcp jump; whether the gated legs are also invoked is research's question.
- **Run scope must match build scope:** narrow a `pulse-app` run with `--filter-expr`/`-E` under `--workspace`, never with `-p`; `cargo test --test &lt;name&gt; -p pulse-app` remains the documented single-binary path (per test-plan §3 `run` → Test selection). The 2026-08-15 measurement of this failure named `wasmtime_internal_cache` and `libduckdb_sys` among the rlib-format crates — the exact dependency family this chunk bumps.
- **Zero-flakiness budget:** a test that flakes once is quarantined and root-caused, never retried; `#[ignore]` is reserved for flake quarantine and requires a tracking issue (per test-plan §10 Zero-flakiness budget + §11 CI/Quality). Post-bump intermittency is a defect, not a tolerance.
- Coverage thresholds stay at **≥75% line / ≥70% branch / ≥85% function**, and lowering a threshold to pass the build is banned (per test-plan §10 Coverage thresholds + §11 CI).

## Patterns to follow
- **Gate ordering:** `cargo xtask capability-drift` runs last because every command above it — including the list's own `nextest --workspace` — can regenerate `pulse-app/ui/src/bindings/index.ts`, and the assertion reads the STAGED copy (per test-plan §3 Per-chunk gate discipline).
- **Plugin-host boundary shape** for the entry-mandated wasmtime verification: fixture WASM staged under `tests/fixtures/plugins/`, loaded and invoked via `wasmtime::component` + `bindgen!`, with a negative arm attempting an unauthorized import (per test-plan §5 Boundary types → plugins → runtime; §6 P4 gives the TauRPC lifecycle form).
- **MCP sidecar boundary shape:** `tokio::process::Command` subprocess + a JSON-RPC 2.0 `serde_json` client over piped stdio, cleanup by SIGTERM with exit-code 0 and no zombie (per test-plan §5 Module ↔ MCP sidecar; §6 P3 steps + Cleanup). Committed cross-process coverage today is the 4 telemetry tools plus `mark_incident_resolved` content — the three remaining incident tools stay in-process (per §6 P3 Current residual).
- **Boot-smoke gate is conditional**, triggered by `pulse-app/src/main.rs`, `crates/ui-bridge/src/`, `pulse-app/src/observability.rs`, `tauri.conf.json`, or `pulse-app/capabilities/*.json` (per test-plan §3 Boot-smoke gate). Whether the `strict-path` ADOPT arm would land on one of those paths — and so pull in the smoke gate — is research's question.
- **Scenario legs are not gate members:** `cargo xtask smoke:gap-resume` and `cargo xtask smoke:external-resolve` are dev-host-only, prove their own preconditions, and report INCONCLUSIVE rather than a vacuous PASS (per test-plan §3 Per-chunk gate discipline). Reach for them only if a bump plausibly moves the ingest/consumer or sidecar-resolve surface.

## Anti-patterns to avoid
- NEVER skip `cargo deny check bans` — the tonic duplicate would surface as a linker conflict (per test-plan §11 Test Strategy).
- NEVER add retry-once policies, ignore a flake, or commit `#[ignore]` without a tracked reason to get past a post-bump failure (per test-plan §11 Quality + CI); relatedly, `smoke:gap-resume` arm A must never be weakened, removed, or `--expect-absent`'d to obtain a green wrap (per test-plan §3 Per-chunk gate discipline).
- NEVER lower a coverage threshold to pass the build (per test-plan §11 CI).

## Contract bindings
- **tests ↔ obs:** any smoke leg run for the plugin-host or sidecar verification takes its verdict from the app's own NDJSON records via the harness `logs` verb, which must resolve the ROTATED `agent-latest.jsonl*` family across three precedence-ordered bases — never a bare name, never a `*.log` glob (per test-plan §3 `logs` + §1 harness summary, binding obs-plan §3 Log file location).
- **tests ↔ security:** the cargo-deny gate pair, the Cranelift-only build assertion, and the MCP double-gate positive/negative are security-plan vectors that the test plan carries as coverage triggers (per test-plan §1 Coverage triggers). If `strict-path` is ADOPTed at a path boundary, its negative test binds to the §1 Path-canonicalization row's L4 rule: confinement is OPT-IN, so the test MUST set `ANDROMEDA_PULSE_L4_ALLOW_ROOT` or it passes **vacuously** as a confinement test.
- **tests ↔ CI:** §9 Build-failure conditions makes `cargo deny check` a first-class CI failure, and §9 records the Cranelift `cargo tree` step and the capability-matrix step in the same pipeline.
