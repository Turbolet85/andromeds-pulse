# arch extract

## Relevance
Relevant (bounded) — arch owns the locked Stack version families, workspace membership, and the two external surfaces the bumps cross (MCP sidecar, plugin host); it does not own advisory-disposition policy or the confinement rule behind `strict-path`.

## Constraints
- The five `strict-path`-declaring member manifests (`config-watcher` · `corpus` · `triage` · `workspace-detector` · `pulse-app`) are all reserved workspace members; the 16 crate names are reserved and cannot be added to, renamed, or re-purposed — this chunk is a `[dependencies]`-only edit (per architecture.md §Occupied Resources → Cargo workspace crate names; §Inherited Defaults → Module boundaries).
- Every upgrade target must land inside the family arch pins, or the Stack row is re-pinned in the same pass: `wasmtime` 25+ (floor), `anyhow` 1.x, `axum` 0.8.x on `hyper` 1.x + `tower`, `tonic` 0.14.x, `duckdb` requirement `1.10500` (caret, untouched) (per architecture.md §Stack and Technologies; §Inherited Defaults). The `h2` lock-only route via `hyper 1.9.0 → axum 0.8.9` stays inside `axum` 0.8.x / `hyper` 1.x and therefore requires no Stack edit.
- The tonic canary is an arch-stated caveat, not just a deny-config habit: §Established Decisions [Backend Framework — OTLP receiver] requires reconciling `tonic` 0.14 against `opentelemetry-otlp` 0.31's transitive `tonic` 0.13 pin before locking versions, and §Inherited Defaults states the only sanctioned resolution if the lock cannot hold — downgrade Stack to `tonic` 0.13.x and re-pin the Stack/Decisions/Defaults rows in the SAME iteration. Papering over a duplicate is not among the arch-authorized outcomes.
- `rmcp` ≥1.4.0 lands directly on an OPEN arch question: §Established Decisions [MCP Server Surface] and §Inherited Defaults → API style external MCP both require reconciling the "rmcp 1.5.0" reference against the published `0.3.x` line (forward-looking vs internal spec vs the unrelated `4t145/rmcp` fork), with "fall back to latest published `0.3.x` and re-pin Stack" as the stated fallback. Both sites are re-pin-owed at wrap if the ≥1.4.0 bump lands.
- Post-bump the MCP surface must still be exactly the 8 named `#[tool]` methods (`query_traces` / `query_metrics` / `query_logs` / `generate_snapshot` / `query_incident_list` / `retrieve_report` / `retrieve_telemetry_slice` / `mark_incident_resolved`) over JSON-RPC 2.0 on stdio, with rmcp's macros as the canonical surface and no invented wire format (per architecture.md §Standard Contracts → MCP server; §Conventions → External wire — MCP server; §Established Decisions [API Style — MCP Server Surface 3]).
- The `wasmtime` bump must preserve the Component Model + WIT posture and declared-host-imports-only capability scoping — a plugin may reach nothing its WIT does not declare (per architecture.md §Established Decisions [Plugin Runtime]; §Design Philosophy → Capability-scoped extensibility; §Inherited Defaults → Plugin runtime).
- Arch registers the RESULTING guard posture of each path input, not a confinement primitive: the three L4 path vars (traversal-reject-before-canonicalize + 4096-byte bound + `canonicalize()` + regular-file assert, plus `ANDROMEDA_PULSE_L4_ALLOW_ROOT` fail-closed), `run/workspace-key` (canonicalize-and-confine, ≤4096 bytes), and `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` (deliberately NOT confined) (per architecture.md §Occupied Resources → Environment variables / Filesystem locations). A `strict-path` ADOPT at any of those boundaries restates the affected registry entry; a DROP touches no arch-registered resource. Whether the shipped guards currently match these registry statements is research's question.

## Patterns to follow
- **Requirement-plus-resolved version recording** — the `duckdb` row's "Cargo.toml requirement `1.10500` (caret, untouched), lockfile-resolved **1.10505.0** as of 2026-08-28" shape, restated at all sites that carry it, is the established way a lockfile move is recorded (architecture.md §Stack and Technologies → Storage engine; §Inherited Defaults → Database).
- **Families, not exact pins** — arch states floors/families (`wasmtime` 25+, `thiserror` 2.x, `anyhow` 1.x, `axum` 0.8.x), so an in-family bump needs no arch edit and a family crossing does. `wasmtime` 43→46 stays true against the "25+" floor at all three sites, so the floor is drifted-but-not-false; re-pinning it is a wrap judgment, not a correctness fix.
- **Feature-gated dependency isolation** — flag-specific deps (`rmcp`, OTAP crates) enter the build graph only under their flag, preserving the small-binary baseline, while `cargo clippy --workspace --all-targets --all-features -- -D warnings` still compiles them, so an rmcp/wasmtime API break surfaces in the lint gate (architecture.md §Cross-cutting Patterns → Feature-gate hygiene; §Infrastructure Patterns → Build system).
- **New load-bearing dependency ⇒ a §Stack row** — the keyring row precedent (added because the runtime had never been registered AND because its feature selection, not its version, was load-bearing) is the shape an ADOPT of `strict-path` follows; the dev-only GUI-harness row is the shape for a devDep with no runtime/bundle impact (architecture.md §Stack and Technologies).
- **Shared Rust CI logic lives in `xtask`** so the same command runs locally and in CI (architecture.md §Infrastructure Patterns → CI/CD approach; §Established Decisions [CI Task Runner]).

## Anti-patterns to avoid
- Adding, renaming, or re-purposing a workspace crate as a side effect of the dependency pass — the 16 names are reserved (architecture.md §Occupied Resources → Cargo workspace crate names).
- Letting the `rmcp` 1.x bump pull rmcp into the default build graph, or replacing its macro surface with a hand-rolled JSON-RPC framing (architecture.md §Cross-cutting Patterns → Feature-gate hygiene; §Established Decisions [API Style — MCP Server Surface 3]).
- Naming `target/{profile}/andromeda-pulse*` in any verification or smoke command — the dev-build binary is `target/{profile}/pulse-app[.exe]`; `andromeda-pulse*` is the bundled artifact, and the only legitimate `target/` instance is the `andromeda-pulse-mcp` sidecar (architecture.md §Occupied Resources → Process / service identity, recorded 2026-08-26 after exactly this error in a chunk plan).

## Contract bindings
- **arch ↔ security (plugin host)**: arch fixes Component Model + WIT + capability-scoped host imports (§Established Decisions [Plugin Runtime]); the Engine/Config posture the scope names (Cranelift-on-x86_64, `epoch_interruption(true)`, per-Store ResourceLimiter) is security's rule enforced against arch's invariant — the wasmtime 43→46 verification is where they meet.
- **arch ↔ security/tests (MCP sidecar)**: arch fixes the 8-method stdio surface and the `--features mcp-server` gate (§Standard Contracts; §Cross-cutting Patterns → Feature-gate hygiene); the runtime half of the double-gate is `ANDROMEDA_PULSE_MCP_ENABLED`, which arch requires to warn-and-proceed rather than fail when the feature is absent (§Occupied Resources → Environment variables) — the cross-process MCP legs are the tests-side binding.
- **arch ↔ security (strict-path decision)**: the confinement RULE lives in security-plan §Input Validation / CLAUDE.md §Critical Warnings; arch's binding is registry-only — per-boundary guard posture in §Occupied Resources, plus a §Stack row owed on ADOPT. `strict-path` is named nowhere in architecture.md (grep-verified), so the DROP arm retires nothing arch registered.
- **arch ↔ tests/obs (deny surface)**: arch's ONLY `cargo-deny` statement is §Established Decisions [Module Boundaries] — "`cargo-deny` 0.16+ `bans` rules are added when a boundary is actually breached, not from day 1" — and arch registers no `deny.toml`, no advisories gate, and no `multiple-versions` policy. Whether that "Deferred" wording still holds against a live `bans licenses sources` gate is research's question; arch authorizes no relaxation either way.

## Acceptance criteria contributions
- (arch) The pass adds/removes/renames no workspace member — the 16 reserved crate names are unchanged and only `[dependencies]` / `Cargo.lock` move (per architecture.md §Occupied Resources → Cargo workspace crate names).
- (arch) Post-`rmcp`-bump, `tools/list` still exposes exactly the 8 named `#[tool]` methods over JSON-RPC 2.0 stdio, and rmcp still enters the build graph only under `--features mcp-server` (per architecture.md §Standard Contracts → MCP server + §Cross-cutting Patterns → Feature-gate hygiene).
- (arch) Post-`wasmtime`-bump, the plugin host is still Component Model + WIT with host imports limited to those a guest's WIT declares (per architecture.md §Established Decisions [Plugin Runtime]).
- (arch) Any bump that leaves a pinned Stack family (`tonic` 0.14.x, `axum` 0.8.x, `hyper` 1.x, `duckdb` `^1.10500`) re-pins the §Stack + §Established Decisions + §Inherited Defaults rows in the SAME iteration; in-family moves and the `h2` lock-only update require no arch edit (per architecture.md §Inherited Defaults → Backend framework; §Stack and Technologies → Storage engine precedent).
