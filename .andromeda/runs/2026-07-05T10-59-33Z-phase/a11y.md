# a11y extract

## Relevance
Relevant — this chunk modifies the desktop-webview Traces table (a P1/P4 must-be-accessible surface), adds a new interactive filter control, and applies a semantic error-state encoding: all three are core a11y concerns.

## Constraints
- Standard tier = WCAG 2.1 AA; the Traces table is a must-be-accessible path (P1 visualize / P4 real-time push), so the universal minimums SC 2.1.1 Keyboard + SC 2.4.3 Focus Order + SC 4.1.2 Name/Role/Value apply and zero new AA violations are allowed (per a11y-plan §1 Critical Paths P1/P4, §10 SLO Invariants — minimums span P1–P12).
- Semantic error flag must never be color-alone: the error state must pair the color with a text label OR icon (SC 1.4.1 Use of Color) — matches the scope's "color + badge/icon/text, never color-only" (per a11y-plan §6 State color tokens, §1 visual-discrimination trigger, §11 Visual).
- Error-token contrast: the error state pair (§6 lists `--color-accent` / `--color-base`) must meet SC 1.4.3 4.5:1 for text and SC 1.4.11 3:1 for any non-text badge/border (per a11y-plan §6 Color contrast pairs).
- The new filter control (toggle/chip) is keyboard-operable: reachable via Tab, activatable by Enter/Space, exposes role + state (`button`+`aria-pressed` for a toggle, or `switch`+`aria-checked`), semantic HTML first (per a11y-plan §4 Button/Switch rows, §1 keyboard-only trigger).
- The filter control must slot into the full-dashboard-traces focus order (skip-to-main → sidebar tabs → main/traces table) with Tab sequence matching visual order, and show the `--border-focus` ring on `:focus-visible` (SC 2.4.7) (per a11y-plan §5 Keyboard Navigation, §6 Focus ring tokens).
- Interactive-target size ≥ 24×24 CSS px for the filter control (SC 2.5.8; `--target-button-min` / `--target-input-min`) (per a11y-plan §6 Target size tokens).

## Patterns to follow
- Not-color-alone remediation already applied in this codebase: chunk #99 encoded severity as `text-primary` + severity-colored borders and used icon/label supplements (`<Icon />` or `<span aria-label="…">` alongside the state-color class) — reuse the same border+label encoding for the anomaly row rather than color fill alone (per a11y-plan §6 State color, §1 visual-discrimination trigger; amendments 2026-06-10 §3).
- Toggle control pattern: native `<button aria-pressed>` (Enter/Space) or Headless UI / React Aria `switch` with `aria-checked` (Space) — pick the one matching the existing dashboard controls; do not introduce the second ARIA library (per a11y-plan §4, §11 Universal).
- This chunk edits an existing surface (Traces table in full-dashboard) rather than adding a route, so it extends the existing traces axe spec + `keyboard-focus` spec instead of a new p-spec; mixed healthy+erroring data comes from the service fixtures in `helpers/v02-fixtures.ts`; verify suite health with `npx playwright test --list` (per a11y-plan §3 Harness wiring "Adding a surface").
- Live trace list is a P4 `aria-live="polite"` / `role="log"` region; re-sorting rows to surface anomalies must not break that live semantics or steal focus from the user's current target; if the filter emits a result-count message use `aria-live="polite"` (per a11y-plan §1 P4, §7 Live regions).

## Anti-patterns to avoid
- NEVER convey the anomaly/error state by color alone — the flag needs icon + text, not just `--color-accent` (per a11y-plan §11 Visual).
- NEVER put ARIA on non-semantic HTML or add redundant roles for the filter — use a native `<button>`/`<input>`, not `role="button"` on a `<div>` (per a11y-plan §11 ARIA).
- NEVER strip focus styles or set `tabindex > 0` on the filter — keep natural DOM order and the `--border-focus` outline on `:focus-visible` (per a11y-plan §11 Keyboard).
