## Patterns to follow

- Enforced loopback bind via explicit `SocketAddr::from(([127, 0, 0, 1], port))` literal at server-builder time (no `0.0.0.0` / `[::]` / `unspecified()` constructions) — capability-style narrow defaults match security plan §Threat Model "loopback-only binding is the de facto authorization boundary."
- Per-service-builder size cap pattern applied to all three OTLP services in a single configuration helper to prevent drift — single source of truth so adding a future `*ServiceServer` automatically inherits the 8 MB cap (per security plan §Input Validation row 1 "set on each `*ServiceServer` builder").
- gRPC-side rate limiting and per-source-port keying are deferred to chunk #19 (`tower_governor`); chunk #16 SHOULD architect the `tonic::transport::Server::builder()` chain so chunk #19 can attach a `tower::Layer` without restructuring (per security plan §API Security row 1 + route §2 chunk #19 scope).
- Tracing instrumentation at the receiver boundary uses `tracing::instrument` with allowlisted fields only (e.g., `service`, `request_id`, span counts) — never `attributes`, never raw payload bytes (per security plan §Logging & Monitoring "What to log" + CLAUDE.md self-observation discipline).
- Module-internal errors use `thiserror` 2.x; conversion to `tonic::Status` is at the receiver boundary; no `anyhow::Error` propagation across the gRPC service trait (per security plan §Error Handling "TauRPC bridge" cross-cutting pattern + Conventions Error response schema).

## Anti-patterns to avoid

- NEVER bind to `0.0.0.0`, `[::]`, or `Ipv4Addr::UNSPECIFIED` — even as a "temporary" debugging affordance behind a feature flag (per security plan §Security Anti-Patterns § API "NEVER bind the OTLP receivers to `0.0.0.0` or any non-`127.0.0.1` interface").
- NEVER omit `.max_decoding_message_size(8 * 1024 * 1024)` from any of the three `*ServiceServer` builders — default is 1 GB+ which is a documented memory-exhaustion DoS vector (per security plan §Security Anti-Patterns § Input "NEVER call `tonic::transport::Server::builder()...add_service(generated_server)` without `.max_decoding_message_size(8 * 1024 * 1024)`").
- NEVER log raw OTLP request / batch payloads, service-request bodies, attribute values, span/log/metric content, or `tonic::Status::message` strings derived from request data — the `ingest` crate sees user-controlled content and the product is the local observer (per security plan §Security Anti-Patterns § Logging + CLAUDE.md universal invariant).
