# a11y extract

## Relevance
partial — the chunk is backend-first (digest / prompt / incident creation); a11y applies only if the half-2 remedy changes what the p9 report window or the p8 findings rows RENDER (new or reshaped text, a new field/line, a cue-kind indicator). A remedy confined to model-authored string content inside existing fields adds no a11y obligation beyond keeping the existing p8/p9 specs green; which remedy shape ships is the P4 fork, and whether the render path is touched at all is research's question.

## Constraints
- The Diagnostic Report window (p9) and findings dropdown/window (p8) are must-be-accessible surfaces; any change to their rendered content keeps the universal minimums SC 2.1.1 / SC 2.4.3 / SC 4.1.2 (per a11y-plan §1 Surface set extension; §10 WCAG SC coverage report).
- If the remedy surfaces the triggering cue kind (e.g. "retry storm") as a new rendered element, it must be conveyed as TEXT, never by color/hue alone — SC 1.4.1 (per a11y-plan §6 State color tokens (not-color-alone); §11 Visual).
- Any new section/heading added to the report (e.g. a "Cause" / "Triggering cue" block) must keep the heading hierarchy sequential with no skipped level — SC 1.3.1 / SC 2.4.6 (per a11y-plan §7 Heading hierarchy).
- The report window stays `role="dialog"` with its focus trap, Esc/close, and cross-window focus restore to the findings window; a render change must not add a focus stop or break that sequence (per a11y-plan §5 report-window / Cross-window entries).
- Any new text in the report uses plain language (a human-readable cue name, not a raw `retry_storm scope_id=...` identifier dump) where it is user-facing prose (per a11y-plan §8 Baseline disciplines — plain language commitment).
- Any new text/token pair rendered must meet SC 1.4.3 contrast via existing design tokens (per a11y-plan §6 Color contrast pairs).

## Patterns to follow
- Fixtures for the report/incident payload live in `tests-a11y/helpers/v02-fixtures.ts`; if the Report payload shape gains a field the webview renders, the fixture is updated and POPULATED so the p9 sweep audits the new content rather than a blank region (per a11y-plan §3 Harness wiring & conventions).
- Mock the TauRPC report procedure through the existing `TauRPC__<router.path>` mock shape in `helpers/mock-tauri.ts` — no new procedure is expected (per a11y-plan §3 Harness wiring & conventions).
- Verify suite health with `npx playwright test --config=playwright-a11y.config.ts --list` after any fixture/type change, since a list-time import failure silently disables the suite (per a11y-plan §3 Harness wiring & conventions).
- Prefer semantic native elements (text in existing `<section>`/headings) over ARIA additions for any new report line (per a11y-plan §11 ARIA).

## Anti-patterns to avoid
- NEVER convey the retry/cause solely via a color or icon change on the report or findings row (per a11y-plan §11 Visual).
- NEVER claim the report remains accessible without machine output — the p8/p9 axe specs must run, not a manual look (per a11y-plan §11 Strategy / CI).
- NEVER add ARIA noise (e.g. `aria-label` duplicating visible cause text) for the new content (per a11y-plan §11 Screen Reader).

## Contract bindings
- a11y ↔ tests: the p8/p9 axe specs and `v02-fixtures.ts` are the test harness for any rendered-payload change; the CI a11y gate (axe critical/serious = fail, per-PR regression vs `baselines/a11y-violations-summary.json`) binds to the tests-plan CI workflow (per a11y-plan §3 CI integration; §9).
- a11y ↔ design: any new cue-kind indicator binds to design-system state color + label tokens (not-color-alone) and contrast pairs (per a11y-plan §6).

## Acceptance criteria contributions
- (a11y, conditional on the remedy touching the render path) The p9 diagnostic-report and p8 findings axe specs pass with zero critical/serious violations and no new regression tuple vs the baseline (per a11y-plan §3 CI integration; §10).
- (a11y, conditional) If a new report field/line is rendered, `v02-fixtures.ts` carries a populated value for it and the p9 spec audits it (per a11y-plan §3 Harness wiring & conventions).
- (a11y, conditional) The retry cause appears as visible text in the report (not color-alone) under a sequential heading level (per a11y-plan §6 State color tokens; §7 Heading hierarchy).
