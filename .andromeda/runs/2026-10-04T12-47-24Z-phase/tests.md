## Constraints
- The chunk plan's `## Test Commands` must carry the unconditional standard gate set, in its stated order: `capability-drift` runs BEFORE the default-features workspace nextest, and the `--features mcp-server` `emit_taurpc_bindings` regen is the last cargo-adjacent step. For a chunk adding no TauRPC procedure (scope Boundaries expect none), the close is `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts`. The webview npm gates apply only if `pulse-app/ui/**` is touched (per test-plan §3 Per-chunk gate discipline).
- Every test layer must be agent-runnable, deterministic and verdict-by-exit-code/structured-output, with no human reading a report to judge it (per test-plan §2 Agent-runnable invariants). A real-model generation cannot give a deterministic verdict, so the real-model probe class is dev-only and never a gate (per test-plan §1 Pending coverage triggers, `l4-decision-probe-arg-parse-unit-coverage`). On this host, the "model drops the retry" layer is therefore not a testable claim. The measurement and any remedy pin must ride the deterministic L4 path (`ANDROMEDA_PULSE_L4_DETERMINISTIC`). Whether that path exercises the same prompt/render code as the real model is research's question.
- New pulse-app tests live as `pulse-app/tests/*.rs` integration targets. Library-crate tests (triage, interpretation) are co-located `#[cfg(test)] mod tests`. Any `#[test]` in `pulse-app/src/` other than `main.rs` reds the flat-zero ratchet (per test-plan §2 Test directory + naming conventions; §4 Conventions).
- A live run taken as measurement evidence uses the direct-binary smoke form: a fresh `ANDROMEDA_PULSE_DATA_DIR` per leg, the deterministic-L4 env, seeding over the real receiver, verdict read from the run's own `agent-latest.jsonl*` family, and teardown by specific pid with :4317/:4318 confirmed released. The 0 `app.panic.fatal` / 0 `ERROR` assertion binds the GREEN leg only. Decide the defect's shape before choosing evidence (per test-plan §3 Boot-smoke gate → Direct-binary smoke variant). This defect is a CONTENT defect (interpretation text lacks the retry) that emits no ERROR, so a clean log passes it vacuously. The evidence of record must be the content field itself: the cue kind in the digest, the cue in the composed prompt, the report's Symptom/Title.
- The interpretation-crate prompt surface is pinned in-crate. Version lineage is asserted through the `PROMPT_VERSION_*` consts, never by literal duplication. The embedded schema's property ORDER is pinned (`primary_prompt_schema_lists_decision_and_severity_after_the_analysis`). A prompt-framing remedy must keep these pins green and bump through the consts (per test-plan §4 What unit tests cover → interpretation crate).
- The triage digest render (`OVERALL:` state word + cue parenthetical) is pinned by in-crate `overall_line_*` tests plus the pulse-app pin tying the scrub fixture to the real renderer. A digest-content remedy must extend or keep these pins, not fork the fixture from the renderer (per test-plan §4 What unit tests cover → triage crate).
- Zero flakiness and the Standard-tier coverage thresholds (≥75% line / ≥70% branch / ≥85% function) apply to new code. No retry policy, no `#[ignore]` without an issue (per test-plan §10 Quality Gates & Coverage Targets; §11 Quality).

## Patterns to follow
- Drive the REAL producer end-to-end in a pulse-app test rather than a hand-built incident. Precedent: `pulse-app/tests/e2e_p3_mcp_incident_events_content.rs` drives `create_incident_from_l4_output` into the real sidecar and asserts response CONTENT (per test-plan §1 Pending coverage triggers, `mcp-incident-read-back-cross-process-coverage`). It is the model for asserting that a retry_storm-born incident's report / MCP `retrieve_report` names the retry.
- Mutation-check each new pin. Revert the remedy and confirm the pin reddens, as the `overall_line_*` pins were checked (restoring the old render reds the cue-bearing pin) (per test-plan §4 triage crate). This keeps the fix out of the "one-time proof standing in for a gate" class, where a live observation is the only witness and a call-site revert leaves every test green (per test-plan §1, e.g. `l4-path-guard-callsite-wiring-coverage`, `discovery-observer-wiring-coverage`).
- If the measurement needs a live storm, follow the scenario-leg conventions: a finite, backgrounded `inject_demo`, because `--sustained` holds a constant rate and formed 0 incidents in 240 s; a self-proven precondition (no incident formed ⇒ INCONCLUSIVE, never PASS); and exit 0/1/2 (per test-plan §3 Per-chunk gate discipline → `smoke:external-resolve` / `smoke:hue-shift`). Whether `inject_demo` can form a `retry_storm` cue at all is research's question.
- Self-bootstrapping fixtures: seed via OTLP ingest or Rust builders at test runtime, using `rstest` fixtures (per test-plan §7 Test Data & Fixtures).

## Anti-patterns to avoid
- Never commit the Conductor d3 capture (`rm-capture-d3.txt`, a real run's report and log window) as a test fixture. It is external evidence to cite. Fixtures are synthetic and generated at runtime (per test-plan §11 Test Data).
- Never gate on real-model output or a real-time-dependent read. Use no `sleep(N)` synchronization and no un-injected `Instant::now()` (per test-plan §11 E2E; §11 Universal).
- Never assert the measurement with a check that passes in both worlds, such as a count or a clean log that holds whether or not the retry is named. Key the verdict on the content field, as `smoke:external-resolve` keys on `reconciled_count`, not `item_count` (per test-plan §3 Per-chunk gate discipline).

## Contract bindings
- obs ↔ tests: the measurement reads the app's own obs records through the §3 `logs` family resolution (`agent-latest.jsonl*`), e.g. `digest.assemble.request` `cue_kind` and `interpretation.incident.created`. A remedy adding a field to an existing record needs its exact allowlist leaf, plus an allowlist pin following the `pulse-app/tests/unit_observability_allowlist_*.rs` pattern (per test-plan §3 Log format; §4 Conventions).
- security ↔ tests: prompt template text stays ASCII, enforced by an in-crate pin in `crates/interpretation/src/prompt.rs` (security-plan argv-transport rule). Report text reaching the webview or MCP passes the scrubber. A remedy that grounds a report field from the cue keeps both pins green. Whether the report path already scrubs a cue-derived field is research's question.
- arch ↔ tests (§9 capability matrix): if the remedy adds or changes a P-0xx capability, the same chunk extends `docs/v0_2_0/capability-verification-matrix.json`, and `cargo xtask verify:capability-matrix` must stay green (per test-plan §9 Capability verification matrix).
- Conductor ↔ Pulse: `v3-09` grading is Conductor's matrix entry. Pulse's acceptance is its own deterministic pins, not Conductor's grade.
