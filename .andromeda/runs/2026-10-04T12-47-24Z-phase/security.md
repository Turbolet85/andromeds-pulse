# security extract

## Relevance
partial — the chunk changes what the L4 interpretation SAYS (digest content / prompt framing / deterministic grounding / render), which crosses three security surfaces the plan owns: the argv-transported prompt bound, the scrub boundary on persisted and rendered interpretation text, and the self-observation logging bans that a measurement instrument could breach. It adds no new trust boundary if the scope's "no new port / procedure / capability / table / MCP tool" boundary holds.

## Constraints
- Any change to the composed v2.3 prompt (re-ordering cues, adding a triggering-cue section, new framing text) MUST still pass `validate_prompt_bounded` before `Command` assembly. That means staying under the derived `MAX_PROMPT_BYTES` ceiling, with NUL and C0/C1 controls rejected and `\n` / `\r` / `\t` whitelisted. An over-long prompt is rejected and the digest skipped, never truncated. Per security-plan §Input Validation (the "L4 inference argv prompt" row) and §Security Anti-Patterns → Code Patterns (the one admitted OTLP-derived argv path). The ceiling was set from measured prompt sizes. A remedy that grows the prompt measurably must be re-measured against the ceiling, not assumed to fit.
- OTLP-derived content in the prompt is confined to `digest.payload_summary`, `project_context` and the `<CITABLE_EVIDENCE_IDS>` fingerprint ids. Any new prompt content derived from the cue must be either a closed label (e.g. the cue kind) or a value already scrubbed upstream. Per security-plan §Input Validation (the L4 argv row's confinement clause) and §Security Anti-Patterns → Code Patterns: the bound is a shape-and-length control, and confidentiality relies on the upstream `Digest::scrubbed_clone`. Whether a cue's `scope_id` (a service name) reaching the prompt is already the scrubbed `extract_service_name` output is a question for research.
- An interpretation field grounded DETERMINISTICALLY from the cue (Title / Symptom / Hypothesis text carrying the cue kind or `scope_id`) is persisted in `Incident.resolution_summary_text`. It MUST pass through the per-STRING-LEAF span-masking projection (`scrubbed_l4_json`) at all three write paths (creation, dedupe refresh, resolution final write), never masked as serialized JSON text. Per security-plan §Security Anti-Patterns → Logging (uniform scrubber coverage, the incident-summary corpus write boundary). Whether a deterministic field built outside the `L4Output` projection would bypass that projection is a question for research.
- The report egress (`assemble_report` and the MCP `retrieve_report` path) surfaces interpretation text to the webview, clipboard and an external LLM client. Any newly sourced field must reach those paths under the same scrub posture as the existing interpretation fields. Per security-plan §Logging & Monitoring (snapshot / clipboard / MCP-tool-response hygiene) and §Security Anti-Patterns → Logging (uniform scrubber coverage).
- The half-1 measurement instrument must not log prompt text, digest `payload_summary` text, L4 output text, report bodies or MCP tool response bodies. It may emit only closed labels (e.g. `cue_kind`), ranks, counts and byte sizes. Per security-plan §Logging & Monitoring ("What NEVER to log") and §Security Anti-Patterns → Logging (NEVER log raw OTLP attribute values / MCP tool response bodies). This also covers the prompt-rejection path: an argv-prompt rejection carries a bounded category only, with no excerpt.
- The identity tuple and the incident write paths are not reopened. If the remedy needs a new TauRPC procedure, MCP tool or capability grant, that is a new trust-boundary crossing and must be surfaced at P4 rather than absorbed. Per security-plan §Threat Model Summary (IPC / MCP stdio entry points) and §Input Validation (validated argument struct per boundary).

## Patterns to follow
- Per-leaf masking of the L4 JSON projection (`scrubbed_l4_json`) for anything persisted into `resolution_summary_text`, so a redaction keeps the summary parseable and does not push the report into the pending notice. Per security-plan §Security Anti-Patterns → Logging.
- Closed-vocabulary, no-scrub boundaries, where only bounded literals cross (the `incident_events` `event_kind` precedent). A cue kind surfaced as a fixed label is this shape. Per security-plan §Security Anti-Patterns → Logging (`incident_events` NO-SCRUB boundary).
- Bounded rejection categories on the existing `interpretation.inference.error` leaf (a `label()` only, no prompt or output bytes) if the remedy adds any new failure arm on the prompt or parse path. Per security-plan §Input Validation (L4 argv row).
- Upstream scrub at the choke point: `service_name` is scrubbed inside `extract_service_name`, so a deterministic field sourced from a cue's service identity inherits the scrubbed name rather than re-scrubbing ad hoc. Per security-plan §Security Anti-Patterns → Logging (choke-point form).

## Anti-patterns to avoid
- Logging the composed prompt, a prompt excerpt, the digest summary or the model's output to "see" where the retry fact is lost. Per security-plan §Logging & Monitoring ("What NEVER to log") and §Security Anti-Patterns → Logging.
- Silently truncating a prompt that a new framing section pushes past the ceiling, or loosening the control-character predicate. Per security-plan §Input Validation (L4 argv row: reject, never truncate; whitelist exactly `\n` / `\r` / `\t`).
- Building a deterministic interpretation string from raw (pre-scrub) cue or OTLP text, or masking the serialized JSON instead of its leaves. Per security-plan §Security Anti-Patterns → Logging.

## Contract bindings
- security ↔ obs: the `interpretation.prompt.assemble` / `digest.assemble.request` records any measurement reads or extends must keep their allowlisted fields bounded (labels, counts, bytes). New fields need an allowlist decision, not free text. Per security-plan §Logging & Monitoring, binding the obs-plan self-observation schema.
- security ↔ tests: a canary corpus for any newly grounded field needs both a keyed class (`password=…`) and a bare class (`sk_live_…`) in the service or scope text, asserted redacted at persistence and at report render. Prompt-template ASCII cleanliness stays pinned by the existing composed-template ASCII test (argv transport). Per security-plan §Security Anti-Patterns → Logging and §Input Validation (L4 argv row).
- security ↔ arch: no new procedure, MCP tool or capability is expected (scope Boundaries). Any addition triggers the `EXPECTED_PROCEDURES` pin and `capability-drift` pair. Per security-plan §Threat Model Summary.

## Acceptance criteria contributions
- The remedied composed prompt for a `retry_storm` digest passes `validate_prompt_bounded`. Its measured byte size is recorded against `MAX_PROMPT_BYTES`, and it stays ASCII-only in template text (per security-plan §Input Validation, the L4 inference argv prompt row).
- A deterministically grounded or newly surfaced interpretation field, seeded with a credential-shaped service or scope value (keyed and bare classes), appears masked in `resolution_summary_text` and in the rendered report / `retrieve_report` output, with the summary still parseable (per security-plan §Security Anti-Patterns → Logging, uniform scrubber coverage).
- No log record emitted by the chunk (measurement instrument or remedy) contains prompt text, digest summary text, model output text or a planted canary. A log-family grep reads 0 canary occurrences (per security-plan §Logging & Monitoring, What NEVER to log).
- If the remedy adds no TauRPC procedure, MCP tool or capability grant, `cargo xtask capability-drift` stays clean with `EXPECTED_PROCEDURES` unchanged; any addition is surfaced at P4 (per security-plan §Threat Model Summary).
