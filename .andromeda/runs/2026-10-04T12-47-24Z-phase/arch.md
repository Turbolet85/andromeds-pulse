## Constraints
- Incident identity stays the cue tuple `(kind, scope, scope_id)`; the remedy may change what an interpretation SAYS, never how incidents coalesce, and must not key anything on `L4Output.fingerprint` (model-authored, constant under the deterministic runner) — per architecture §Established Decisions [Fault Identity] (L2 COALESCE-PER-CUE-IDENTITY; the REJECTED arm).
- The L4 runtime is `llama.cpp` D1 spawn-per-generation behind `LlmInferenceRunner` (`crates/interpretation/src/contract.rs`), with GBNF `--json-schema-file` constrained sampling and bounded invocation (`-n`, `-st`, outer timeout); a prompt/schema remedy works inside that trait boundary, and only the concrete impl may change at the binary boundary — per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer] and §Inherited Defaults (LLM inference runtime).
- Code stays within the reserved crates: digest content in `triage`, prompt + embedded schema in `interpretation`, the producer (`create_incident_from_l4_output`) and report assembly in `pulse-app`, the `retrieve_report` read in `mcp-server`; no new crate, and the reserved names are not repurposed — per architecture §Occupied Resources (Cargo workspace crate names) and §Inherited Defaults (Module boundaries).
- Dependencies flow toward `pulse-app`; `triage` and `interpretation` must not gain a sibling edge the DAG does not already have (for example, `interpretation` reading a `triage` type it does not already depend on needs its contract to require it) — per architecture §Cross-cutting Patterns (Module dependency direction) and §Conventions (Module visibility discipline: cross-crate exposure only through each crate's contract module).
- The deterministic runner (`ANDROMEDA_PULSE_L4_DETERMINISTIC`) produces a canned `L4Output`, and the canned arrays are load-bearing for gradeability; a remedy that grounds a field deterministically from the cue must state how it behaves under the deterministic runner, because that is the only L4 path this host can exercise — per architecture §Occupied Resources (`ANDROMEDA_PULSE_L4_DETERMINISTIC`).
- The scope expects no new TauRPC procedure, MCP tool, port, env var, broadcast topic or corpus table; any that a remedy needs is an Occupied Resources addition and must surface at P4 — per architecture §Occupied Resources (Tauri IPC routes `incidents.get_report`; Tauri IPC events; Corpus reserved tables; env var list) and §Standard Contracts (MCP server, `retrieve_report`).
- Any change to the `retrieve_report` or `incidents.get_report` payload shape must stay `serde::Serialize` and conform to the MCP JSON-RPC 2.0 contract — per architecture §Cross-cutting Patterns (Cross-bridge data shape) and §Standard Contracts (MCP server — spec-conformant).

## Patterns to follow
- The trait-swap boundary: model-behaviour concerns sit behind `LlmInferenceRunner`, and deterministic and real runners are sibling impls at the binary boundary, so a remedy in the prompt or the producer applies to both runners alike — per architecture §Established Decisions [LLM Inference Runtime].
- The cue → `DigestCueRef` → producer threading already carries `fingerprint` from the triggering cue into `Incident` and the `citable_evidence_ids`. The cue's `kind` would travel the same path if a deterministic field is grounded from the cue. Whether `kind` already reaches the prompt or the report is research's question — per architecture §Established Decisions [Fault Identity] (SHIPPED 2026-08-17 threading; the 2026-08-26 citable-evidence note).
- The single producer join at `pulse-app/src/inference_runtime.rs` is where parsed `L4Output` meets cue-derived data (order-preserving union, with parsed refs first). This is the precedent for mixing model-authored and deterministic content without displacing either — per architecture §Occupied Resources (`ANDROMEDA_PULSE_L4_DETERMINISTIC` entry).
- `Report.degraded_mode = parsed_l4.is_none()`, and `resolution_summary_text` is written at creation and refreshed on re-generation, so a live incident renders the six-section brief from the persisted `L4Output` JSON. The render reads that persisted text, so a render-side remedy has to account for it — per architecture §Occupied Resources (`ANDROMEDA_PULSE_L4_DETERMINISTIC` entry, `degraded_mode` note).

## Anti-patterns to avoid
- Reopening the coalesce key, or adding the cue kind or a fingerprint to the incident identity, as a way to "name the retry" — per architecture §Established Decisions [Fault Identity] (L2 identity decided; per-fingerprint dedupe possible-but-declined).
- Absorbing a new surface (TauRPC procedure, MCP tool, env var, corpus table or column) into the remedy silently instead of registering it at P4 — per architecture §Occupied Resources.
- A remedy whose effect exists only under the real model, or only under the deterministic runner, without saying so. The two runners are interchangeable behind the trait, and the deterministic one is the reproducible-verification mode — per architecture §Established Decisions [LLM Inference Runtime] and [Fault Identity] (the REJECTED rationale: "a no-op in exactly the mode used for reproducible e2e verification").

## Contract bindings
- arch ↔ security: report and MCP text fields (Symptom / Title / Hypotheses) cross the TauRPC bridge and the MCP egress. Any deterministic text grounded from the cue joins the scrubbed-egress set (security-plan owns the scrub discipline). Arch requires only `Serialize` plus the MCP envelope (§Cross-cutting Patterns Cross-bridge data shape; §Standard Contracts MCP).
- arch ↔ tests: the deterministic L4 runner (`ANDROMEDA_PULSE_L4_DETERMINISTIC`) is the reproducible harness that Conductor grades against. A remedy changes what its graded output contains, so the canned-output fixture and the Conductor contract bind here (§Occupied Resources).
- arch ↔ interpretation prompt transport: the prompt and the embedded `schema.json` travel as argv to the `llama.cpp` subprocess (§Established Decisions [LLM Inference Runtime]). The ASCII-only template rule that follows from this belongs to the security rule set, not to arch.
- arch ↔ corpus: `Incident` is persisted as a bincode BLOB, and the MCP sidecar reads it cross-process (§Occupied Resources Corpus tables; §Established Decisions [Fault Identity] blast radius). If a remedy changes the `Incident` / `L4Output` shape, that shape change is a wire-compat question for both processes.

## Acceptance criteria contributions
- The incident identity tuple `(kind, scope, scope_id)` and the coalesce predicate are unchanged by the remedy. A storm incident still coalesces exactly as before (per architecture §Established Decisions [Fault Identity]).
- No new crate, TauRPC procedure, MCP tool, env var, broadcast topic or corpus table/column lands, unless P4 surfaced it and it is registered in §Occupied Resources at wrap (per architecture §Occupied Resources).
- The remedy keeps `LlmInferenceRunner` as the swap boundary and introduces no new sibling-crate dependency edge outside the existing DAG (per architecture §Established Decisions [LLM Inference Runtime] and §Cross-cutting Patterns Module dependency direction).
- Under `ANDROMEDA_PULSE_L4_DETERMINISTIC`, a retry-storm-triggered incident's report (both `incidents.get_report` and MCP `retrieve_report`) can be checked for whether it names the retry. If the remedy depends on the model, the criterion states that the deterministic path cannot prove it (per architecture §Occupied Resources `ANDROMEDA_PULSE_L4_DETERMINISTIC`; §Standard Contracts MCP server).
