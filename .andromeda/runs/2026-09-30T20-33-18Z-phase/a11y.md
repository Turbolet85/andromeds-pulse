## Constraints
- The chunk adds no surface to the must-be-accessible set P1–P14; per a11y-plan §1 (Critical paths → Surface set extension) the existing p9 / p12 / p14 axe specs remain the coverage for any surface whose rendered text changes, and the universal minimums SC 2.1.1 / SC 2.4.3 / SC 4.1.2 apply unchanged across P1–P14.
- a11y-plan §3 Harness wiring & conventions ("Adding a surface" standing rule) requires fixtures to be POPULATED — if research finds `tests-a11y/helpers/v02-fixtures.ts` (or an inline spec fixture) carries a whole-value placeholder string standing in for report / export / snapshot text, the audited surface must still render real non-blank content; whether any fixture encodes the old whole-value shape is research's question.
- a11y-plan §6 State color tokens (not-color-alone, SC 1.4.1) requires that IF the webview renders a redaction placeholder with distinguishing styling (color/highlight), the meaning is also carried by the placeholder text itself; whether any renderer styles placeholders today is research's question — plain-text rendering needs no new assertion.
- a11y-plan §11 Screen Reader bans hiding essential content from assistive tech — a span placeholder rendered in report / export text must stay in the accessible tree (no `aria-hidden` / `display:none` treatment of the placeholder or its surrounding retained text).
- a11y-plan §8 Cognitive Accessibility baseline (plain language) applies to any user-visible placeholder spelling chosen at the P4 placeholder-shape fork (`[REDACTED:{category}]` vs `[redacted:{category}]` vs `[redacted: {category}]`): the rendered form should read as a plain label, and one spelling across surfaces avoids inconsistent announcements; this is advisory, not a gate.
- a11y-plan §10 SLO Invariants requires zero new WCAG AA violation tuples vs the `baselines/a11y-violations-summary.json` baseline on every PR, so the chunk's CI `a11y` job must stay green even though no UI file is intended to change.
