## Relevance
Relevant (shared): the a11y substance is a11y's, but the gate set, selector discipline, determinism/agent-driven invariants, the headful-leg wiring, and the §1 trigger this chunk is named as owner of are all tests-domain.

## Constraints
- The **standard gate set** is unconditional for every phase-authored chunk plan's `## Test Commands`, and the three webview gates (`npm run lint` / `npm run typecheck` / `npm run test`, all `--prefix pulse-app/ui`) are excluded ONLY when zero `pulse-app/ui/**` paths are touched — this chunk's Surfaces list touches them, so all three are required (per test-plan §3 Per-chunk gate discipline).
- Selector discipline is **measured per surface**: bind to the accessible name wherever one ships, `data-testid` only where none does, never xpath and never a hashed/utility class — and measure the selector at HEAD *before* pinning it, because a name stated in a spec but absent from the product leaves the real control with no coverage anchor (per test-plan §6 Selector strategy; §11 E2E).
- Every layer must be agent-runnable: verdict from exit code plus structured output/artifacts, never a human confirming a result or approving a screenshot; headful GUI automation is in scope only in that agent-driven form (per test-plan §2 Agent-runnable invariants).
- Zero-flakiness is a hard budget — one flake means quarantine + root-cause, never a retry policy; any new a11y spec must be deterministic and not synchronised by `sleep` (per test-plan §10 Quality Gates; §11 E2E).
- Webview unit-level assertions live co-located as `*.test.tsx` under `pulse-app/ui/src/`, run by `vitest` 3 + `jsdom` + `@testing-library/react` 16, DOM-shape assertions only, emitting JUnit XML to `target/junit-ui.xml` (per test-plan §4 Framework (webview unit tests) + §4 Conventions → Test file location).
- For the headful `webview-drive` leg, a green exit code alone is **not** evidence the leg ran — an unset `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` is a clean SKIP (exit 0); evidence of record is the per-run `webview-drive-stages.json` stage report (per test-plan §6 Drivers per surface; §9 CI E2E stage).
- The **boot-smoke gate** fires only if the chunk touches `pulse-app/src/main.rs`, `crates/ui-bridge/src/`, `pulse-app/src/observability.rs`, `tauri.conf.json`, or `pulse-app/capabilities/*.json`; the scope's stated boundary (no capability-JSON edit, no backend surface) would leave it untriggered — confirming that boundary holds is research's question (per test-plan §3 Boot-smoke gate).
- test-plan §1 carries `traces-surface-a11y-semantics-absent` as an OPEN pending trigger asserting the Traces region label and `table` role are absent at HEAD, naming the **A11y verification** entry as owner; the plan states this as a requirement, not as verified current code — the scope reports measurement contradicting the absence claim, so confirming what the shipped surface actually exposes is research's question, and the plan-side reconciliation is a wrap-time amendment (per test-plan §1 Pending coverage triggers).

## Patterns to follow
- Webview component-level a11y contracts already have an established shape in `pulse-app/ui/src/components/`: DOM-shape assertions over `aria-*`/`role`/`focusable`, including the decorative-vs-meaningful ARIA flip and a banned-element grep — cell-level keyboard navigation and the Investigate busy/alert states fit this same unit tier (per test-plan §4 What unit tests cover → webview React components).
- The headful leg's **two-half verdict**: the `.mjs` driver presses and REPORTS only, the Rust caller (`xtask/src/webview_drive.rs`) asserts, and each stage reports `StageHalves{obs,dom}` independently so a failure distinguishes "telemetry did not land" from "did not reach the screen"; every predicate matches an effect FIELD, never the target alone (per test-plan §6 Drivers per surface).
- The browser-driven a11y chain (real Chromium against the built webview) is already load-bearing as part of P5's documented residual coverage — edits to that suite must not weaken it (per test-plan §6 P5 Current residual).
- Bookkeeping pattern for measured gaps: a gap gets a §1 pending trigger with its owner named, and closed rows are retained marked LANDED for audit trail rather than deleted (per test-plan §1 Pending coverage triggers, `capability-widening-check` precedent).
- Narrow a `pulse-app` run with `--filter-expr` / `-E` **under `--workspace`**, not `-p` — run scope must match build scope (per test-plan §3 `run` → Test selection).

## Anti-patterns to avoid
- NEVER xpath, NEVER a brittle hashed/utility-class selector — accessible name first, `data-testid` as the fallback; both bans are operative now that a DOM-driven leg exists (per test-plan §11 E2E).
- NEVER visual regression requiring human approval (Percy/Chromatic/Applitools), no "human reviews canvas", no pixel inspection — contrast and motion claims must be asserted by tooling/computed values, not by eye (per test-plan §11 E2E + §11 Universal).
- NEVER `sleep(N)` for synchronisation — wait on an explicit signal (per test-plan §11 E2E).

## Contract bindings
- **tests ↔ a11y harness:** `pulse-app/ui/tests-a11y/` + `npm run test:a11y` are specified by a11y-plan, not by test-plan; test-plan §3's standard gate set names only `lint`/`typecheck`/`test` for the webview, and §9's CI stage table does not list an a11y suite — whether `test:a11y` is currently wired into any gate or workflow, and whether this chunk must add it, is research's question.
- **tests ↔ obs:** the headful leg's obs half reads the app's own log; §3 Log format binds the harness's JSON-lines/`tracing` shape to obs-plan's log format, and the `ui.layout.transition {compact-widget → hidden}` record is the sole guard on `core:window:allow-close` (per test-plan §3 Log format; §6 P5).
- **tests ↔ capability matrix:** §9's `cargo xtask verify:capability-matrix` recognises an `automated-a11y` verification mode and fails CI on dangling ids/paths/anchors; the scope expects zero capability claims, so no new matrix entry should be owed — confirming that is research's question (per test-plan §9 Capability verification matrix).
- **tests ↔ security:** §9 build-failure conditions include `cargo deny check` bans; the chunk's `cargo audit` PREREQ probe is security-domain substance riding the same dependency-gate surface (per test-plan §9 Build failure conditions).
