- Stub procedure errors MUST return `Result<T, AppError>` using existing `serde`-friendly variants (`Validation { field, reason }` / `NotFound { resource }` / `Internal { message }`); the "not yet wired" failure mode collapses to `AppError::Internal { message: <sanitized one-liner> }` (per security plan §Error Handling TauRPC bridge bullet + Conventions Error response schema). ## Anti-patterns to avoid

- NEVER serialize `anyhow::Error` directly across the TauRPC bridge from the new stub — must convert to the `serde`-friendly `AppError` enum first (per security plan §Security Anti-Patterns §Code Patterns).
- NEVER log raw OTLP attribute values, snapshot file contents, clipboard contents, or any clipboard payload bytes — even from stub trigger handler tracing (per §Security Anti-Patterns §Logging + §Logging & Monitoring NEVER-log list). - NEVER add a new TauRPC procedure (including a stub/placeholder) without ALSO adding the matching entry in `pulse-app/capabilities/` JSON — silent runtime rejection becomes a hard-to-diagnose UX bug (per §Security Anti-Patterns §API entry on TauRPC capability gating).
