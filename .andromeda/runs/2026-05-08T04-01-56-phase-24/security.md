## Patterns to follow

- **TauRPC procedure → capability JSON pairing pattern**: every existing TauRPC procedure introduced via the chunk #25 router scaffolding follows the two-piece enforcement (router registration in owning crate + entry in `pulse-app/capabilities/` JSON). The 5 introspection procedures plus the existing `traces.*`/`metrics.*`/`logs.*`/`snapshot.*`/`plugins.*`/`mcp.*`/`workspace.*`/`streams.*` (D3 drift candidate) routers are the introspection target set (per security plan §API Security TauRPC capability authorization).
- **AppError sanitization on every TauRPC procedure boundary**: chunk #26 already shipped the From-impl matrix with `tracing::warn!` emission at every conversion site (3 existing + 4 placeholder). The 5 introspection procedures share this pattern — module-internal `thiserror` enum → `AppError` via `From` impl; full chain in `tracing` log via `tracing-error::SpanTrace`, sanitized one-liner crosses the bridge (per security plan §Error Handling boundary discipline).
- **Hardcoded SHA pinning for any third-party Action**: the xtask check itself runs in `ci.yml`; if it invokes any third-party Action (it shouldn't — pure Rust binary), that Action MUST be pinned by 40-char commit SHA per §Anti-Patterns Secrets `@v2`/floating-tag ban (per security plan §Bootstrap phases `dep-security-ci-gate` SHA-pinning convention).
- **Static-introspection at compile time, not runtime**: the `taurpc` derive macro generates router metadata at compile time; the xtask check should introspect this static metadata (e.g., generated `*.d.ts` bindings from chunk #25, or `taurpc::create_ipc_handler` registry walking) rather than spawning the app to enumerate procedures. Avoids the `AppError::Internal { message }` runtime-error class entirely (per security plan §API Security TauRPC capability authorization "introspected from the `taurpc` derive").
- **`xtask` task pattern follows existing harness discipline**: chunk #4 wired the xtask agent-run 5-command harness with structured/JSON output; the new `xtask capability-drift` task follows the same discipline (machine-parseable JSON / non-zero exit on mismatch / no Rust panics) (per security plan §Bootstrap phases `dep-security-ci-gate` + chunk #4 xtask agent-run harness).

## Anti-patterns to avoid

- NEVER add a TauRPC procedure to a router crate without a matching entry in `pulse-app/capabilities/` — silent runtime rejection per Tauri 2 docs. The xtask drift check is the enforcement mechanism; this chunk must not regress this discipline (per security plan §Anti-Patterns API).
- NEVER expose stack traces, Rust struct names, file paths, or library versions in `AppError::Internal { message }` content surfaced from `health`/`ready`/`app_info`/`get_settings`/`update_settings` to the webview — sanitize at the `From<thiserror::Error> for AppError` impl per chunk #26 discipline (per security plan §Anti-Patterns Logging).
- NEVER expose the Tauri updater Minisign private key, Azure Key Vault credentials, or any secret in `app_info` / `get_settings` response payloads — only the public Minisign key belongs in `tauri.conf.json` and never in IPC responses (per security plan §Anti-Patterns Data Protection + §Secret Management "Never in code").
- NEVER widen any of the 5 capability identifiers (`pulse:default`/`pulse:tray`/`pulse:notification`/`pulse:updater`/`pulse:plugin-fs`) as a side-effect of "fixing" drift — particularly NEVER expose `pulse:updater` to webview JavaScript or grant Tauri core APIs (`fs`/`shell`/`dialog`/`http`) to `pulse:default` (per security plan §Anti-Patterns API capability bans).
- NEVER reference any third-party GitHub Action in the new CI step by `@v2` / floating tag — pin by 40-char commit SHA per the `tj-actions/changed-files` CVE-2025-30066 retroactive-tag-rewrite class (per security plan §Anti-Patterns Secrets).
