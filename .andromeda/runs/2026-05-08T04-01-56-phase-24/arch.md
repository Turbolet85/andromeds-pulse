## Constraints

- The `app_info` / `health` / `ready` commands MUST conform exactly to the JSON envelopes specified in arch §Standard Contracts — `app_info` returns `{name, version, rust_version, tauri_version, features, build_profile}`; `health` returns `{status, checked_at, subsystems}` with `status ∈ {"ok", "degraded"}` and per-subsystem reason strings on failure (e.g., `"otlp_grpc_receiver": "bind_failed: address in use"`); `ready` returns `{ready, checked_at, checks}` with `checks` exposing `duckdb_connection`, `ingest_mpsc_capacity_pct`, `broadcast_subscribers`, `plugins_loaded`, `mcp_server_enabled`. Hard subsystem failure converts at the bridge to `Err(AppError::Internal { ... })` per the same section.
- All five top-level procedures (`app_info`, `health`, `ready`, `get_settings`, `update_settings`) MUST be `snake_case` bare verbs and registered in the `ui-bridge` crate per arch §Conventions "Endpoint naming" + arch §Occupied Resources "Tauri IPC routes" — they are explicitly listed under the ui-bridge top-level envelope, not under any dotted router namespace.
- Every TauRPC procedure registered in the workspace MUST have a corresponding entry (router-level, per security/Session Additions clarification) in `pulse-app/capabilities/` JSON — `xtask capability-drift` enforces; missing entry = silent runtime rejection per arch §Cross-cutting Patterns "Webview IPC capability policy". The drift check is the mechanical enforcement of the "two enforcement pieces required" rule.
- Every type returned by these five procedures MUST be `serde::Serialize` per arch §Cross-cutting Patterns "Cross-bridge data shape" — the `health` / `ready` envelopes' nested objects (`subsystems`, `checks`) must be serializable enums or structs, not opaque maps with non-serializable values.
- Errors crossing the bridge MUST collapse to the `AppError` variants from arch §Conventions "Error response schema (Tauri IPC)" — `Validation { field, reason }`, `NotFound { resource }`, `Internal { message }`, `Plugin { plugin_id, message }`, `Storage { message }`, `Ingest { message }`. `update_settings` rejection of malformed input belongs in `Validation { field, reason }`; nothing should leak `anyhow::Error` directly.
- `xtask capability-drift` lives in the `xtask` crate per arch §Occupied Resources "Cargo workspace crate names" — it is a Rust binary inside the same workspace per arch §Established Decisions "[CI Task Runner] cargo-xtask", invoked locally as `cargo xtask capability-drift` and wired into `ci.yml` per arch §Infrastructure Patterns CI/CD approach ("All shared CI logic that needs Rust lives in the `xtask` crate").
- `update_settings` MUST honor arch §Cross-cutting Patterns "Config management" precedence — env vars > `~/.andromeda-pulse/config.toml` > defaults. Writes from IPC land in the `config.toml` layer; env-var overrides at runtime stay authoritative until process restart. Settings field names use the units-explicit shape from arch §Conventions "Configuration units" (e.g., `retention_seconds`, ports as `u16` via `TryFrom<u16>`).

## Patterns к follow

- Each library crate exposes its public contract via a single `pub` contract module + `thiserror`-derived error enum + a TauRPC-router module mounted by `pulse-app` (per arch §Project Intent "Template patterns"). Chunk #27's five top-level procedures register on the `ui-bridge` router and convert sibling-crate errors at the bridge via `From` impls (already wired in chunk #26).
- The `AppError` From-impl matrix from chunk #26 (Buffer/Ingest/Viz tracing emission + Snapshot/Plugins/WorkspaceDetector/McpServer placeholder routes) is the conversion pattern; chunk #27's `health` / `ready` aggregation reads sibling-crate state via existing contracts and surfaces failures as `AppError::Internal { message }` per arch §Standard Contracts "When degraded" / "When not ready".
- Module dependency direction stays as a DAG with `pulse-app` as the only root per arch §Cross-cutting Patterns "Module dependency direction" — `ui-bridge` may depend on sibling crates' contract modules to read subsystem health; no library crate imports `pulse-app`. The `xtask` crate may shell out / parse JSON but must not link against library crates that link Tauri.
- Capability JSON files live at `pulse-app/capabilities/` (5 files per arch §Occupied Resources "Tauri capability identifiers": `pulse:default`, `pulse:tray`, `pulse:notification`, `pulse:updater`, `pulse:plugin-fs`). The drift check parses these files and the TauRPC router-export at compile-introspection — per security plan §Session Additions 2026-05-03, the granularity is router-level (TauRPC dispatches all methods through a single invoke handler), NOT per-procedure.
- `cargo xtask <task>` is the local-and-CI single-source pattern per arch §Infrastructure Patterns CI/CD ("contributors can run identical commands locally with `cargo xtask <task>`"). The drift check runs identically locally and in CI.

## Anti-patterns к avoid

- DO NOT deviate from the JSON envelope keys / values specified in arch §Standard Contracts — adding fields, renaming `status` → `state`, swapping `checked_at` ISO format, or moving `subsystems` into a top-level array would break the contract. Any envelope evolution requires `/andromeda-scope-arch`, not chunk implementation.
- DO NOT introduce per-procedure capability JSON entries (e.g., `"core:command:allow-health"` strings) — TauRPC integrates via a single invoke handler per security plan §Session Additions 2026-05-03; the drift check enforces router-level coverage, not per-method. Per-procedure granularity is a stock `#[tauri::command]` artifact and does not apply here.
- DO NOT add new env vars beyond those reserved in arch §Occupied Resources "Environment variables" without going through `/andromeda-scope-arch`. `update_settings` writes into `config.toml` only; its allowed keys map onto the existing `ANDROMEDA_PULSE_*` namespace.
- DO NOT introduce a new TauRPC procedure namespace prefix in `xtask capability-drift` (e.g., a debug-only `debug.*` namespace). The drift check reports drift from existing reserved namespaces (`app_info`/`health`/`ready`/`get_settings`/`update_settings` + `traces.*`/`metrics.*`/`logs.*`/`snapshot.*`/`plugins.*`/`mcp.*`/`workspace.*`); it does not invent new namespaces. The carry-over D3 `streams.*` namespace is NOT in arch §Occupied Resources — drift check MUST surface it as drift, not silently legitimize it.
- DO NOT have a library crate depend on `pulse-app` (binary crate) per arch §Cross-cutting Patterns "Module dependency direction" — the drift check belongs in `xtask`, which orchestrates introspection without inverting the DAG.
