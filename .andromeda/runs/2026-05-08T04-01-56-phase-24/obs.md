## Patterns to follow

- IPC-internal handler instrumentation pattern: `#[tracing::instrument(skip_all, fields(traceparent = %tp))]` already used by chunk #25's TauRPC routers; chunk #27's 5 introspection procedures extend the same pattern with `method_name = "app_info|health|ready|get_settings|update_settings"`, `argument_digest` (hash, not content), `result_type` (e.g., `"AppInfo"`, `"Health"`, `"Ready"`), `latency_ms` (per obs-plan §4 IPC-internal row + §6 boundary-call wrappers TauRPC row).
- Heartbeat tick contract reuse: `health` response `subsystems` map MUST mirror the field set already emitted by `ingest.tick` / `buffer.tick` / `viz.tick` / `plugins.tick` (`span_count`, `buffer_capacity_pct`, `broadcast_subscribers`, `rows_ingested`, `retention_window_active`, `eviction_count`, `query_latency_ms`, `subscribers_active`, `loaded_count`, `active_invocations`) — ready envelope echoes the same names so passive (tick) + active (probe) surfaces stay schema-identical (per obs-plan §3 Heartbeat ticks).
- Default subscriber fields ride: every introspection log line carries `service.name` / `service.version` / `deployment.environment` automatically via `Layer::with_default_fields(...)` — handlers do not repeat per-call (per obs-plan §3 Service identity + §6 Required fields).
- AllowList per-leaf entry discipline (project-specific lesson from session-handoff Tier 2): each new IPC procedure that emits structured fields needs an explicit AllowList entry at `pulse-app/src/observability.rs::AllowList::production()` keyed to the procedure's `target` — falling through `split('.').next()` collapses to crate-level entries with mismatched field sets and silently redacts allowed fields (per obs-plan §8 default-deny posture per-module whitelist + carried-over Tier 2 observability.md learning 2026-05-07).
- xtask capability-drift CI artifact pattern: emits a structured drift JSON to `target/capability-drift/report.json` + tail-friendly `tracing::info!(target: "xtask.capability_drift", ...)` line in `agent-latest.jsonl`; consumed by post-test `jq` aggregation matching the pattern used for SLO assertions (per obs-plan §9 CI Integration + §10 CI gates "Build fails if perf-budget p99 exceeds SLO" template).

## Anti-patterns to avoid

- NEVER log full setting values in `update_settings` — `ANDROMEDA_PULSE_*_PATH` / `*_DIR` env-var values are subject to Vector 6 (CWE-22 sanitizer); raw config blobs may incidentally contain user paths or future secret-typed fields (per obs-plan §11 Logs "NEVER log raw OTLP attribute values… or query parameters" pattern, generalized per Vector 6).
- NEVER use unbounded label cardinality on the new introspection procedures — `method_name` enum bounded to the 5 procedure names; `subsystems` keys bounded to the 4 known modules (`ingest`, `buffer`, `viz`, `plugins`) + optional `mcp-server` when feature-gated (per obs-plan §11 Metrics cardinality discipline + §5 Metric label cardinality discipline).
- NEVER serialize the full TauRPC procedure inventory or capability JSON body inside the `xtask capability-drift` `tracing::info!` event — emit only `missing_count` + `extra_count` + drift-summary fields (top 5 names with sanitized basenames if file-path-bearing); the full diff lives in the JSON CI artifact, not the inline log line (per obs-plan §11 Logs "NEVER use multi-line stack traces" + §11 Universal "NEVER use proprietary APM as ONLY exporter").
- NEVER run `xtask capability-drift` as a side-effect of every `tracing::info!` during normal app boot — it is a CI / xtask-time gate, not a runtime telemetry event; running it at boot would inflate the log file and re-introduce a fast-loop hot-path span issue (per obs-plan §11 Logs "NEVER log in hot path at info level").
