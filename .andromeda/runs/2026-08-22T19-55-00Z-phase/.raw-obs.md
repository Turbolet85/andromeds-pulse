# obs extract

## Relevance
Relevant — the chunk's claim contains the word "silently", and obs owns that half: whether a lost `log_records` write is observable at all, and what shape any drop counter takes.

## Constraints
- Module-boundary error logging is mandatory at Standard+: every error at a module boundary (explicitly including DuckDB write/query errors) must be logged at `WARN` or `ERROR` with trace context and an error category (per obs-plan.md §10 SLO Invariants → Standard+ invariants). If P3 determines the PK conflict produces no log line at all, that silence is itself a violation of this mandate, not merely a data defect — **whether the write path already emits anything on a PK conflict is research's question**, and it must be answered before the fix is designed.
- Buffer-path counters ride the existing 15s `buffer.tick` as FIELDS, folded once per batch, rather than as separate `metric.buffer.*` targets; per-record emission is barred outright (per obs-plan.md §5 Metric Coverage → the two tick-aggregated Counter rows, and §1 Heartbeat ticks). Any drop/collision counter this chunk mints must take that shape.
- The `buffer.tick` field set is restated at **three** sites — §1 Heartbeat ticks, §5 Metric Coverage, §8 default-deny `buffer` whitelist. A new tick field requires an amendment at all three; a §8-only apply leaves §1 and §5 stale (per obs-plan.md §8 PII Scrubbing → Default-deny posture, and the 2026-08-22 precedent below).
- Default-deny scrubbing: any new field or target needs an EXACT allowlist leaf enumerating **every** field its emit site emits, or `for_target`'s prefix fallback silently redacts the remainder; buffer counters are aggregate counts only — never record identity, never a `service_name` label, never the colliding key values (per obs-plan.md §8 PII Scrubbing → Default-deny posture, `buffer` whitelist).
- A log record's `body` is High-classification raw OTLP payload and may never be emitted to logs or span attributes (per obs-plan.md §8 PII Scrubbing → Data classification rules, Vector 1). This bears directly on the P4 fork: design option (c) widens the key with `body`, so any diagnostic that names the conflicting key would carry scrubbed-path content into the obs log. Options (a)/(b) carry no such coupling. Note also that the OTLP persistence path (`scrub_otlp_field`, covering log body + exception message + stacktrace) is the path the `redactions_applied` counter already meters — a key change touching `body` intersects the scrubber.
- The readback leg is constrained by the DuckDB query boundary contract: emit `query_id`, `param_count`, `row_count_returned`, `duration_ms` — never query text or parameter values (per obs-plan.md §6 Log Coverage → Boundary-call wrappers; §8 Vector 5). If the readback runs through the MCP `query_logs` tool instead, only `result_type` + `result_count` may be logged, never the response body (per obs-plan.md §11 Obs Anti-Patterns → Project-specific).
- `buffer.tick` must keep emitting with no &gt;45s gap through the measurement and the fix; a stall fails the build (per obs-plan.md §10 SLO Invariants → CI gates, `xtask/ci/heartbeat-gap-check.sh`).

## Patterns to follow
- **Fold-once-per-batch → tick field**: `BufferState::record_feed_counts` (feed counters) and `BufferState::record_redactions` (`redactions_applied`) are the two shipped precedents for metering a buffer hot path without per-record emission (per obs-plan.md §5, tick-aggregated Counter rows). A drop counter is a third fold of the same shape — and the scope asks the plan to name that shape for the diagnostics sweep to consume.
- **`app.boot.buffer.degraded` WARN** (per obs-plan.md §6 Log Coverage → `warn` row): the closest in-plan precedent for this exact defect class — it exists because a fallback "drains and discards ingest batches while ingest's own counters keep climbing, making a degraded boot otherwise indistinguishable from a healthy one." Bounded static `reason` + `consequence`, once per boot.
- **`corpus.read.undecryptable` WARN**: ONE aggregate per query, never per row (per obs-plan.md §6 `warn` row) — the shape to copy if the fix warrants a WARN rather than a counter, so a colliding burst degrades visibly instead of going dark without spamming the append loop.
- **EXACT allowlist leaf + guard test under `pulse-app/tests/`**, mutation-discriminated (per obs-plan.md §8 Default-deny posture). Guards placed in `observability.rs`'s own `mod tests` compile but never run under `[lib] test = false` — the plan records this as a live, unfixed hazard.
- **`duckdb.append` span** (`span.kind = "internal"`, attributes `duration_ms` + `rows_appended`) and P1's required log field `buffer.rows_ingested` (per obs-plan.md §4 Span/Trace Coverage → Scenario P1). This is the existing surface where a requested-vs-landed row divergence would surface; **whether `rows_appended` reflects rows requested or rows actually persisted is research's question**, and the answer determines whether a new counter is needed at all.

## Anti-patterns to avoid
- Never instrument the appender inner loop or per-row DuckDB operations, and never log in a hot path at `info` level (per obs-plan.md §11 Obs Anti-Patterns → Telemetry Strategy, Logs). A per-colliding-record log line is the wrong answer even though it is the most direct one.
- Never attach unbounded-cardinality labels to a buffer counter — no `service_name` (client-controlled via OTLP), no `trace_id`, no record identity (per obs-plan.md §11 → Metrics; §8 `buffer` whitelist, which bans exactly this for `redactions_applied`).
- Never emit raw OTLP attribute values, log-record `body`, or DuckDB query text (per obs-plan.md §11 → Logs, Vectors 1 and 5).

## Contract bindings
- **obs ↔ tests harness**: the log-format JSON schema in §3/§6 is verbatim FROM the test-plan harness contract and is binding in that direction — obs aligns to tests, not vice versa. Regression coverage in `buffer` that asserts on a counter must read the same field names off `agent-latest.jsonl` (per obs-plan.md §3 Observability Harness Contract → Log format JSON schema).
- **obs ↔ the "Diagnostics un-muting + harness-truth sweep" working entry**: the span-side drop-observability CARRY (a span rejected on `(trace_id, span_id)` reads as a dead feed) is that entry's, and the scope bars building it here. Obs's contribution is to state the counter/leaf **shape** so the sweep can adopt it. That same entry also owns migrating dead src-level allowlist guards into `pulse-app/tests/`.
- **obs ↔ security**: §8 Vectors 1 and 5 are the security plan's logging-sensitive vectors; the `body`-as-key question above is a joint obs/security input to the P4 fork.
- **obs ↔ CI**: the heartbeat-gap and zero-panic gates both run over `~/.andromeda-pulse/logs/agent-latest.jsonl` (per obs-plan.md §10 CI gates).

## Acceptance criteria contributions
- A colliding-record burst produces at most one aggregate emission per batch/tick — no per-record log line or span on the append path (per obs-plan.md §5 Metric Coverage tick-aggregated Counter rows + §11 Telemetry Strategy).
- If the fix mints a counter or target, it lands as an EXACT §8 allowlist leaf enumerating every field its emit site emits, is live-verified UNREDACTED in `agent-latest.jsonl`, and is guarded by a test under `pulse-app/tests/` (not a src-level `mod tests`) (per obs-plan.md §8 PII Scrubbing → Default-deny posture).
- Across the end-to-end measurement, zero occurrences in the obs log of the injected log-record `body` canary, any raw OTLP attribute value, or DuckDB query/parameter text (per obs-plan.md §8 Vectors 1 and 5 + §11 Logs).
- `buffer.tick` emits continuously with max consecutive gap ≤ 45s through both the measurement and the fixed write path (per obs-plan.md §10 SLO Invariants → CI gates).
