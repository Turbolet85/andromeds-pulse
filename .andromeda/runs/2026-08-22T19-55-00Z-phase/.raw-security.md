# security extract

## Relevance
**Partial** — no new trust boundary is crossed, but the chunk touches the OTLP ingestion write path, DuckDB query construction, the ring-buffer at-rest/retention posture, any new drop diagnostics, and carries a folded security-plan-owned deferral.

## Constraints
- Every `log_records` read/write the fix touches — the retention sweep, the `viz` `logs.*` router, the MCP `query_logs` tool — must use `duckdb` `Connection::prepare` with `?` placeholders; identifier interpolation is banned outright and user input must never name a table or column (per security-plan.md §Input Validation, DuckDB query parameters row; §Security Anti-Patterns → Input). A key change that shifts which columns are filtered on must not introduce a `format!`-built predicate.
- Option (c) widening the key with `trace_id`/`span_id` makes post-`prost`-decode invariants load-bearing for key correctness — §Security Anti-Patterns → Input requires the `ingest` crate to check `trace_id` is 16 bytes / `span_id` is 8 bytes before handing batches to `buffer::Appender`. Whether those checks exist at HEAD is research's question. Note the plan's own framing implies untraced log records carry zero-valued ids, so this direction does not by itself retire the collision class.
- Option (c) widening the key with `body` collides with the scrubber mandate: §Security Anti-Patterns → Logging records `log_records.body` as passing through `scrub_attribute` at the OTLP appender (measured 2026-08-22). Keying on it would make record identity depend on redaction output — two records differing only in a redacted credential would collide *after* scrubbing. Whether the scrub still sits on that path at HEAD is research's question. `severity_text` is named in the same section as one of five columns that do NOT reach `scrub_attribute`, owned by a different route entry and fenced out of this chunk.
- The failure-mode determination P3 must close has a direct security consequence: if a PK conflict aborts the whole batch, then per §Threat Model Summary → Attack surface (loopback OTLP: "any local process … can post telemetry", no auth at that surface) a single local producer can poison ingestion for well-behaved producers — the exact starvation the §API Security rate-limiting row exists to prevent. State which failure mode occurs before designing; do not assume.
- Any new drop/collision diagnostic must not carry raw OTLP attribute values, log-record bodies, snapshot/clipboard contents, MCP tool response bodies, or DuckDB query parameter values — the mandate is query identifier + parameter count instead (per security-plan.md §Logging &amp; Monitoring, "What NEVER to log"; §Security Anti-Patterns → Logging).
- Errors arising from a PK conflict must collapse to the sanitized boundary shapes before crossing: `AppError::{Ingest, Storage}` at the TauRPC bridge, `tonic::Status`/`Status` proto at the OTLP receiver, JSON-RPC 2.0 error object at MCP — with no raw DuckDB error string, Rust struct name, file path, or stack trace surviving the crossing (per security-plan.md §Error Handling; §Security Anti-Patterns → Logging).
- The ring buffer's at-rest posture is `:memory:` with no persistent disk database and DuckDB encryption-at-rest explicitly banned (CVE-2025-64429), which makes the `DELETE … WHERE ts &lt; cutoff` retention sweep the buffer's *only* data-lifecycle control (per security-plan.md §Data Protection → At rest / Data lifecycle; §Security Anti-Patterns → Data Protection). Option (b) — drop the PK on the grounds the sweep suffices — inherits that control as its sole guarantee, so the fix must keep `ts_unix_nano`-driven retention effective and must not enlarge the plaintext residency window.

## Patterns to follow
- Prepared statement + `?` parameter binding for every touched query; table/column names stay spec-fixed rather than parameterized (§Input Validation, DuckDB row).
- Boundary error collapse: module-internal `thiserror` 2.x enums convert to the `serde`-friendly `AppError` via `From` impls at the bridge; OTLP and MCP use their own spec-defined error envelopes — no new envelope is invented (§Error Handling; §Bootstrap phases `error-sanitization-wire`).
- Field redaction applied at the `tracing-subscriber` layer, not at log call sites; structured JSON to `agent-latest.jsonl` is the sole self-observation sink (§Logging &amp; Monitoring, Log format; §Bootstrap phases `logging-redaction-wire`).
- Scrub-before-persist at the write path — `scrub_attribute` returning `ScrubbedValue::{Allowed, Redacted}` is the plan's intended posture for any client-controlled value crossing into storage or the log sink, with the existing `extract_log_body` call site named as the in-repo `log_records` precedent (§Security Anti-Patterns → Logging). If the chosen discriminator derives from client-supplied content rather than being a synthetic per-batch index, this is the pattern it must follow rather than becoming a sixth uncovered column.
- If the key change ripples into a new or renamed TauRPC procedure, the enforcement pair is a validated argument struct plus an `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` — per-procedure capability-JSON entries do not exist in this project (§API Security, TauRPC capability authorization).

## Anti-patterns to avoid
- NEVER construct `log_records` SQL by interpolating a service name, attribute, or identifier into `format!` — the Dagster GHSA-mjw2-v2hm-wj34 / Vanna CVE-2024-5827 / dagster-duckdb CVE-2026-41490 cluster is named as the dominant 2026 DuckDB vuln class (§Security Anti-Patterns → Input).
- NEVER log the colliding or dropped record's body/attribute values, or DuckDB query parameter values, when adding drop visibility (§Security Anti-Patterns → Logging).
- NEVER flip DuckDB encryption-at-rest on the in-memory ring buffer as a side effect of a schema change — CVE-2025-64429 is documented against that feature and the `:memory:` connection avoids the surface entirely (§Security Anti-Patterns → Data Protection).

## Contract bindings
- **tests (fixtures):** the end-to-end OTLP measurement must use synthetic, non-real PII/secret payloads. This is not only hygiene — per §Security Anti-Patterns → Logging the scrubber's eight categories include an anchored bare-credential arm (`provider_key`) with a recall-over-precision posture, so a credential-shaped fixture body would be redacted at the appender and could confound a read-back comparison on `body`.
- **obs (diagnostics):** if the chunk names a shared drop-counter shape for the "Diagnostics un-muting + harness-truth sweep" to consume, the field *schema* is obs's; the NEVER-log list bounding what those fields may carry is mine (§Logging &amp; Monitoring).
- **tests (CI gate):** the `cargo audit` standing deferral and its named overlap `cargo deny check advisories` ride the single CI security gate job (§Dependency Security → CI integration; §Bootstrap phases `dep-security-ci-gate`).
- **route/wrap:** `log_records.severity_text` belongs to the "Ingestion scrub coverage" working-route entry; this chunk must neither absorb it nor emit body text contradicting it.
