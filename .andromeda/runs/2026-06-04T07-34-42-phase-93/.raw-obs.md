## Constraints

- Config load/reload is a boundary that MUST emit structured logs: success → `info` with structured fields (which keys reloaded, count, last-reload timestamp); validation/path failure → `warn` (e.g., `warn!(target: "config.load.path_validation", ...)` on CWE-22 rejection) per obs-plan §6 Log levels mapping (warn row + info row). Use `metric.*`/`{module}.{operation}` naming, not free-form targets (per §2 Naming conventions; §4 span naming `{module}.{operation}`).
- The new TauRPC handlers `config.reload` / `config.status` MUST be instrumented with `#[tracing::instrument(skip_all, fields(traceparent = %tp))]`, extracting the IPC-envelope `traceparent` and attaching it as a plain `tracing` span field so downstream config-apply calls inherit context (per obs-plan §3 Trace context propagation — IPC boundaries; §4 IPC-internal row).
- Config keys are Low-classification and OK to log structurally, BUT secret-shaped keys (naming convention `*_SECRET` / `*_TOKEN` / `*_KEY`) MUST be redacted, and file-path values MUST log basename only — never the full canonicalized `config.toml` / data-dir path (per obs-plan §8 Data classification table "Environment variables (config)" row + Vector 6 CWE-22 row).
- Malformed-config rejection (previous-valid-config retained) MUST be logged at `warn`/`error` with a sanitized one-liner (error category + which key range failed), NOT the raw file contents or a full deserialize stack trace; route through `AppError`/SpanTrace sanitization at the bridge (per obs-plan §7 Error classes + §6 warn row).
- If the `notify` watcher runs as a persistent long-running task, it falls under the heartbeat-tick / stall-detection invariant: either emit a `config.tick`-style heartbeat (15s) or document it as event-driven-only; absence of expected liveness signal for >45s is the stall threshold (per obs-plan §10 Standard+ invariants Heartbeat ticks; §3 Heartbeat ticks). Specialist plan does not enumerate a `config.tick` target by name — orchestrator may need к surface whether the watcher is tick-emitting or purely event-driven.
- `config.reload` perf is not on a creator-explicit SLO budget (only snapshot p99 ≤500ms / WebGPU frame p99 ≤33ms / buffer ≤512MB are enforced per §10 Performance budgets); the route's "≤2s hot-apply" target is a tests-domain assertion, not an obs SLO gate — do not invent a new CI perf gate for it.

## Anti-patterns к avoid

- NEVER log raw `config.toml` file contents, full canonicalized config/data-dir paths, or secret-shaped values on reload — basename-only for paths, redact `*_SECRET`/`*_TOKEN`/`*_KEY` (per obs-plan §11 Logs + PII Scrubbing; Vectors 3 & 6).
- NEVER emit a multi-line deserialize/`thiserror` stack trace on malformed-config rejection — use one-line sanitized SpanTrace; never serialize `anyhow::Error` across the `config.reload` IPC boundary (convert to `AppError` per Vector 2) (per obs-plan §11 Spans/Traces + Logs).
- NEVER let a tight `notify` debounce/event loop log at `info` per filesystem event — gate verbose per-event detail behind `debug`/`trace` (`ANDROMEDA_PULSE_LOG_LEVEL`); only the settled 500ms-debounced reload outcome warrants an `info` line (per obs-plan §11 Logs "NEVER log in hot path at info").
