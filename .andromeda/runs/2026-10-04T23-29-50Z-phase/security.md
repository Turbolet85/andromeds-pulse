## Relevance
partial — the chunk changes the L4 argv-transported prompt and/or digest rendering (a guarded OTLP-derived argv boundary) and commits real-model evidence; it adds no port, procedure, capability, env var, table or dependency.

## Constraints
- The L4 `-p` operand is the ONE product path admitted to pass OTLP-derived text to argv, and only through `validate_prompt_bounded` (16384-byte `MAX_PROMPT_BYTES` ceiling + NUL/C0/C1 rejection with `\n` `\r` `\t` whitelisted; over-long rejects, never truncates). Any reworded framing instruction, TRIGGER line content, corpus framing note or schema hypothesis description must keep every composed prompt (all four shapes, both arms, reflection prompt included) under that ceiling with the guard unchanged (per security-plan §Input Validation, L4 inference argv prompt row; §Security Anti-Patterns → Code Patterns).
- The ceiling is DERIVED from measured maxima (currently ~2.28× the 7,185 B v2.4 dev-probe composition); the chunk must not raise or retune `MAX_PROMPT_BYTES` to fit a larger prompt — that would be a security-plan amendment, not an in-chunk edit. If the remedy grows the prompt, the new observed maximum is a measurement note the wrap may record, never a bound (per security-plan §Input Validation, L4 inference argv prompt row, "How" column).
- OTLP-derived content in the prompt is confined to `digest.payload_summary` + `project_context` + the `<CITABLE_EVIDENCE_IDS>` section. A lever that surfaces new storm content in the prompt (e.g. error rate, p99, service names in the TRIGGER line) must draw it from the already-scrubbed digest (`Digest::scrubbed_clone` upstream); a new OTLP-derived prompt section outside that confinement widens the boundary and needs its own disposition. Whether the S2/S3 rendered content the remedy would lean on already flows only from the scrubbed digest is research's question (per security-plan §Input Validation, L4 inference argv prompt row; §Security Anti-Patterns → Code Patterns, `Command::arg(user_input)` ban and its bounded exception).
- Prompt-rejection and inference-failure surfacing stays on the existing `interpretation.inference.error` leaf as bounded categories — no prompt text, excerpt, offending substring or model output bytes (per security-plan §Input Validation, L4 inference argv prompt row; §Security Anti-Patterns → Logging, full-path bullet).
- No full product-consumed filesystem path may appear in any log record or in committed evidence — the model GGUF path, the two llama-cli binary paths and the `ANDROMEDA_PULSE_L4_ALLOW_ROOT` root surface as basename + env-var NAME only (per security-plan §Logging & Monitoring, "What NEVER to log"; §Security Anti-Patterns → Logging).
- The L4 path guard (`validate_path_input`: trim, pre-canonicalize `..` rejection, 4096-byte bound, canonicalize, regular-file assertion, opt-in both-sides-canonicalized confinement that fails closed) stays unchanged; the real-model leg consumes it, never modifies it (per security-plan §Input Validation, CLI / env var inputs row, PRODUCT-CONSUMED path boundary; §Security Anti-Patterns → Input, NARROWED EXCEPTION).
- If (and only if) `Cargo.toml` / `Cargo.lock` change, the supply-chain gates apply: `cargo deny check bans licenses sources` as the pass/fail gate and `cargo audit`, with advisories observed separately. Whether the remedy touches the dependency graph at all is research's question; the scope implies it does not (per security-plan §Dependency Security).

## Patterns to follow
- The bounded-parse guard shape at the argv boundary: a pure helper returning a bounded rejection whose `label()` is the only thing logged — reuse, do not fork (per security-plan §Input Validation, L4 inference argv prompt row).
- The layout-character whitelist in a content guard over multi-line text — a realistic multi-line prompt pinned as ACCEPTED, not only a NUL-bearing one as rejected (per security-plan §Input Validation, L4 inference argv prompt row; `.claude/rules/security.md` 2026-08-26 session addition).
- ASCII-only prompt template text — role/framing text, runtime-pushed literals, digest literals and embedded `schema.json` descriptions — pinned by `composed_prompt_templates_are_ascii_clean_for_argv_transport`, because the b9305 argv decode is ANSI on Windows and a paraphrased non-ASCII character poisons stdout decode (per `.claude/rules/security.md` 2026-08-27 session addition; security-plan §Input Validation, L4 inference argv prompt row, `stdout_utf8_invalid` category).
- Basename-plus-env-var-NAME emission for the L4 path vars (`path_basename` / `root_basename`) in any record the measurement leg reads or produces (per security-plan §Security Anti-Patterns → Logging).

## Anti-patterns to avoid
- NEVER pass OTLP-derived text to `Command::arg` outside the `validate_prompt_bounded` gate, and never weaken the gate (raise the ceiling, drop the C0/C1 rejection, or truncate instead of reject) to admit a longer remedy prompt (per security-plan §Security Anti-Patterns → Code Patterns).
- NEVER log or commit raw model output, prompt text or OTLP-derived digest content — model output is generated from OTLP-derived input and is treated as such; evidence carries bounded labels and verdict lines only (per security-plan §Logging & Monitoring, "What NEVER to log"; §Security Anti-Patterns → Logging).
- NEVER log or commit a full model / binary / allow-root path from the real-model leg (per security-plan §Security Anti-Patterns → Logging).

## Contract bindings
- security ↔ tests: the ASCII-clean pin (`composed_prompt_templates_are_ascii_clean_for_argv_transport`) and the prompt-bound accept/reject pins must stay green over any changed template, digest literal or schema description; a prompt version bump carries the sweep of tests pinning the old version literal (per security-plan §Input Validation, L4 inference argv prompt row).
- security ↔ obs: the `interpretation.prompt.assemble` byte measurement is the source the derived ceiling is re-based from, and `interpretation.inference.error` is the bounded-category rejection leaf; neither may gain a prompt-text or output-bearing field (per security-plan §Input Validation, L4 inference argv prompt row; §Logging & Monitoring).
- security ↔ arch: fault identity is arch's (§Established Decisions [Fault Identity]); security's only tie is that the cue-label grounding of `Incident.title` happens before the scrub — a remedy that changes title composition must keep the scrub after grounding (per security-plan §Security Anti-Patterns → Logging, incident-summary corpus write boundary).

- `composed_prompt_templates_are_ascii_clean_for_argv_transport` passes over the changed templates, and zero `stdout_utf8_invalid` categories appear across the real-model leg (per security-plan §Input Validation, L4 inference argv prompt row; §Security Anti-Patterns → Code Patterns).
