## Constraints

- Connection state MUST NOT be conveyed by dot COLOR alone — the dot needs a text/programmatic supplement (accessible name carrying the state, e.g. `aria-label="Connection: <state> — last span <ago>"`). Color-only state encoding fails WCAG 2.1 AA SC 1.4.1 (per a11y-plan §6 "State color tokens (not-color-alone)" + §11 Visual ban "NEVER convey information by color alone"). The existing FooterBand already follows this discipline (its `--color-accent` border is a paired affordance, the numeric value carries the meaning — `FooterBand.tsx` lines 11-14).
- The connection dot's color MUST meet SC 1.4.11 Non-text Contrast (≥3:1 against the titlebar `--color-base` background) since it is a graphical state indicator, not text (per a11y-plan §6 contrast pairs row `--color-accent / --color-base` 3:1 non-text + §11 Visual contrast ban).
- If the dot is interactive (focusable, with a hover/focus tooltip), it MUST be a native `<button>` (semantic HTML first) reachable via Tab, activatable by Enter/Space, and show the `--border-focus` outline on `:focus-visible` — never `outline: none` without replacement (per a11y-plan §4 Button pattern + §6 Focus ring tokens + §11 Keyboard "NEVER omit focus styles"). The existing titlebar Investigate/Settings buttons are the canonical reference (`Titlebar.tsx` lines 91-132).
- The tooltip content (current state + last-span-ago) MUST be available on BOTH hover AND keyboard focus, and remain visible/dismissable per SC 1.4.13 Content on Hover or Focus (per a11y-plan §1 WCAG list SC 1.4.13). NOTE: a11y-plan §1 currently marks SC 1.4.13 as "not applicable — app does not use hover-hidden tooltip patterns" (line 68); this chunk INTRODUCES the first hover/focus tooltip, so SC 1.4.13 becomes applicable here — orchestrator may need to surface this applicability shift to the user (the plan is silent on a tooltip pattern in the titlebar).
- Removing the `<footer role="status" aria-live="polite">` FooterBand removes a live region (SC 4.1.3). This is acceptable since the chunk deliberately discards the dashboard-mindset metrics, but any test asserting `getByRole("status")` / `getByTestId("footer-band")` on the compact widget MUST be updated; the new connection-dot accessible name is a static label, not a live region (per a11y-plan §7 Live regions + §11 Screen Reader "NEVER skip landmark roles").
- Any transition on the dot (color change on state transition, tooltip appearance) MUST respect `prefers-reduced-motion: reduce` and degrade to instant — state must still be conveyed via color + accessible-name text, not motion (per a11y-plan §6 Motion tokens + §11 Motion "NEVER use motion as ONLY signal"; SC 2.3.3 AAA escalation). The existing titlebar buttons carry the `motion-reduce:transition-none motion-reduce:duration-0` classes as the reference pattern (`Titlebar.tsx` lines 97, 118).

## Patterns к follow

- Native `<button>` + `aria-label` + 24×24 min target (`--target-input-min`) + `motion-reduce:` classes: the existing `Titlebar.tsx` Investigate (lines 91-113) and Settings (lines 114-132) buttons are the exact reference shape — reuse for the connection dot if it is interactive (per a11y-plan §4 Button pattern + §6 Target size).
- Drag-region exclusion: the titlebar is a `data-tauri-drag-region` `<header>`; interactive controls (buttons) must NOT carry the drag attribute and must be real hit-targets (per a11y-plan §7 Landmark roles `<header>` for compact-widget title bar; `Titlebar.tsx` comment lines 33-35). The connection dot button follows this — drag region carries no tabindex.
- Decorative-icon discipline: the app-icon `<span aria-hidden="true">` (lines 70-75) and icon glyphs inside buttons (`aria-hidden="true"`, e.g. line 111) are correctly hidden from AT because the button's `aria-label` carries the name — apply the same: if the dot is purely a visual glyph inside a labelled button, mark the glyph decorative; the accessible name lives on the button (per a11y-plan §4 Button + §11 "NEVER overuse aria-label").
- Focus order: the titlebar's tab stops are currently [Investigate, Settings, window-controls]; the connection dot's position in that Tab sequence must match its visual left-to-right placement (dot is near the app-icon, i.e. left of Investigate/Settings) per SC 2.4.3 (a11y-plan §5 compact-widget focus order "title / expand / minimize"; `tabbable(container)` ground-truth assertion).

## Anti-patterns к avoid

- NEVER encode connection state by dot color alone with no text/aria supplement — SC 1.4.1 violation (a11y-plan §11 Visual). The state word must appear in the accessible name (and/or tooltip text), not just the hue.
- NEVER use a `<div role="button">` or a non-focusable `<span>` with a click/hover handler for an interactive dot — semantic HTML first; a static element with interactions trips `eslint-plugin-jsx-a11y` `no-static-element-interactions` + `click-events-have-key-events` (a11y-plan §11 ARIA; rules/a11y.md Session Additions 2026-05-10). If the dot is non-interactive (status display only), keep it a labelled non-focusable element and do NOT attach click/keydown handlers.
- NEVER ship a hover-only tooltip with no keyboard-focus equivalent — SC 1.4.13 + design-tokens.md "NEVER use hover-only interactions without keyboard alternatives" (a11y-plan §11). Tooltip must surface on `:focus` as well as `:hover`.
