- a11y-plan §5 (findings-window) requires the FindingsCounter live badge's 0→N transition to announce **once, politely** (SC 4.1.3). A 122×-inflated trigger rate reaching that badge would be an announcement-storm class defect; whether the cadence→digest→incident path actually reaches that badge (and thus the accessible tree) is research's question.
- a11y-plan §7 (Landmark roles) states the anti-stacking principle directly: `role="status"` on the constellation summary is deliberately omitted because a ~1 s poll plus the dashboard's existing live region would stack announcements. Any new bound-state signal must not become a second announcement source on those surfaces.
- a11y-plan §10 (Standard+ invariants) requires zero new WCAG AA violations per PR versus the base-branch artifact, with no retry-once policy — so if this chunk touches the app-launch/runtime shape (`pulse-app/src/main.rs:276-279`) that the headful a11y leg starts, the suite must still reach its surfaces and hold the recorded baseline.
- If a bound-hit or throttled state ever renders in the UI, a11y-plan §4 (pattern catalog, Status/Alert row) requires role + accessible name/state, and §11 (Visual) bans conveying it by color alone.

## Patterns to follow
- Aggregate-only accessible-tree content: a11y-plan §7 records the constellation summary as carrying lifecycle counts + a findings tally only, with no service name reaching the accessible tree — the shape to reuse if any cadence/bound counter is ever surfaced.
- Stable literal accessible name, live state as description: a11y-plan §7 keeps landmark names as stable literals and routes churning state to an `aria-describedby` visually-hidden element, so the screen-reader rotor does not churn under high update rates.
- Documented-omission pattern: a11y-plan §7 records the omitted `role="status"` as a deliberate, reversible choice in the plan rather than silently — the precedent for how a rate/announcement decision made in this chunk should be recorded.
- Regression-baseline comparison: a11y-plan §3 (Harness wiring & conventions) + §10 anchor the gate on `baselines/a11y-violations-summary.json` re-established at the v0.2.0 re-audit; a11y evidence for this chunk is a diff against that baseline, not a fresh claim.
- Harness reuse, not a new runner: a11y-plan §3 (CI integration) requires the a11y chain to reuse the tests harness's build/start/status/cleanup path in the same pipeline.

## Anti-patterns to avoid
- Never add ARIA/live-region noise as the way to surface a new bound or throttle state (a11y-plan §11 Screen Reader — excessive ARIA noise; §7 anti-stacking).
- Never claim a11y conformance or "a11y unaffected" without machine-verifiable output (a11y-plan §11 Strategy + the §7 agent-driven invariant) — an assertion about the webview surviving the bound needs axe/Lighthouse/pa11y JSON, not reasoning.
- Never use a retry-once or quarantine-and-move-on response if a timing change from the bound makes an a11y assertion flake (a11y-plan §11 SLO).
