## Constraints
- The folded PREREQ is a security-plan obligation, not a formality: security-plan §Dependency Security → CI integration (Standing deferral — `cargo audit` unrunnable) requires the probe to actually RUN at its interval point, its exit status read DIRECTLY (never through a pipe), the DB-load basis re-verified, and the overlap signal `cargo deny check advisories` re-observed and recorded — with the owned set re-enumerated as DISTINCT `RUSTSEC-` ids rather than carried forward.
- If Deliverable B's ceiling introduces any crate (rate limiter, governor, semaphore, timer wheel), §Dependency Security (Pinning + CI integration) and §Bootstrap phases → `dep-audit-tooling-install` require an explicitly pinned version (never `"*"`/floating), a passing `cargo deny check bans licenses sources`, `multiple-versions = "deny"` left unrelaxed, the `tonic` canary unskipped, and any duplicate carve-out ID-scoped + owner-named + closure-conditioned in `deny.toml`.
- §API Security (Rate limiting row) requires a coarse global request-rate cap plus a per-source-port keyed limit on both `:4317` and `:4318` precisely so "a single rogue local producer cannot starve well-behaved producers" — the same starvation class this chunk fights from the internal side. Whether that layer is actually installed on the two receivers today is research's question; the chunk must not weaken or relocate it while adding its own ceiling.
- §Input Validation (OTLP/gRPC and OTLP/HTTP rows) requires the receiver-side load bounds — `.max_decoding_message_size(8 * 1024 * 1024)` per `*ServiceServer`, `DefaultBodyLimit::max(8 * 1024 * 1024)` / `RequestBodyLimitLayer` on `:4318` — to remain in force; the chunk's "no change to the ingest→buffer substrate" boundary means these are a don't-regress, not a target.
- §Logging & Monitoring (What NEVER to log) plus §Security Anti-Patterns → Logging require that any new trigger/cycle/shed diagnostic emit no raw OTLP attribute value and no DuckDB query parameter value — "log query identifier + parameter count instead". This binds directly to instrumenting the Q1–Q7 `drive_query!` path the flood multiplies.
- §Security Anti-Patterns → Logging (Uniform scrubber coverage) requires every client-controlled value crossing into the self-observation sink or corpus to pass `security::scrubber::scrub_attribute`, with `extract_service_name` named as the declared choke point for the three service-identity consumers. Whether a cue/cadence trigger carries client-controlled text (a service name, a fingerprint label) that a new diagnostic would emit is research's question.
- If a shed/rejected trigger ever surfaces across the TauRPC bridge, §Error Handling and §Security Anti-Patterns → Code Patterns require a `serde`-friendly `AppError` variant — never a directly serialized `anyhow::Error` — with `Internal { message }` free of stack traces, file paths, Rust struct names, and library versions.

## Patterns to follow
- Bound-at-admission with an observable rejection: the plugin host's `wasmtime::ResourceLimiter` cap + `Config::epoch_interruption(true)` timeout (§API Security → Plugin host capability sandbox) is the plan's canonical "ceiling where the work is admitted" shape, and §Logging & Monitoring (What to log) requires the cap-exceeded / timeout event be logged. Deliverable B's "enforce where the triggers originate" wants the same pair: a stated ceiling plus a countable shed event.
- Caps declared as named constants at the boundary rather than inline magic numbers — the `MAX_WASM_HTTP_FIELDS_SIZE_BYTES` / `MAX_WORKSPACE_KEY_BYTES` precedent (§Input Validation, plugin-host and workspace-key rows) is how this plan expresses substrate-level bounds.
- Per-source keying rather than a single global valve (§API Security → Rate limiting): the plan's stated reason is that a global-only cap lets one runaway producer starve the rest — the same reason the chunk rejects widening `max_blocking_threads`.
- Deferral discipline for anything this chunk cannot close: basis re-verified first-hand, a NAMED overlap signal that still runs, visible dispositions on the overlap's findings, and an explicit next interval point — never a silent skip (§Dependency Security → CI integration).
- SHA-pinned third-party Actions (`<owner>/<repo>@<40-char-SHA> # vX.Y.Z`) if any CI step is touched while wiring a gate (§Bootstrap phases → `dep-security-ci-gate`; §Security Anti-Patterns → Secrets).

## Anti-patterns to avoid
- NEVER log raw OTLP attribute values, span/log/metric content payloads, or DuckDB query parameter values in the new cadence/trigger diagnostics (§Security Anti-Patterns → Logging).
- NEVER report `cargo deny check advisories` ERROR BLOCKS as the owned-ID count — a crate at two lockfile versions raises one block per version, so enumerate distinct `RUSTSEC-` ids (§Dependency Security → CI integration, counting rule (a)).
- NEVER relax `multiple-versions = "deny"`, skip the `tonic` canary, or add an unreasoned `[bans] skip` entry to make a newly added dependency's duplicate pass (§Dependency Security → CI integration; §Security Anti-Patterns → Universal).

## Contract bindings
- security ↔ obs: any new bound/shed/trigger counters cross into obs's schema and cardinality authority, while the NEVER-log list and `scrub_attribute` coverage stay security's — PII scrubbing is the shared seam (§Security Anti-Patterns → Logging ↔ obs-plan §PII Scrubbing; the scope already names obs-plan §10 for the blocking-pool load constraints).
- security ↔ tests: the CI security gate is a job inside the single workflow, so a dependency added here must keep `cargo deny check bans licenses sources` green in the same `ci.yml` run tests owns (§Dependency Security → CI integration ↔ tests §CI Integration); fixtures for any load/soak leg must carry no real PII.
- security ↔ chunk report: §Dependency Security names the chunk report as the record of each deferral discharge — the probe result and re-enumerated set belong in this chunk's report, not only in the transcript.
