## Constraints
- Any change to the composed prompt (decision guidance, added digest content) must keep the `-p` operand admissible through `validate_prompt_bounded` at its single production caller BEFORE `build_llama_cli_args`: the `MAX_PROMPT_BYTES` ceiling is derived from measured prompt sizes, NUL/C0/C1 controls are rejected with `\n` `\r` `\t` whitelisted, and an over-long prompt is rejected (digest skipped), never truncated (per security-plan §Input Validation, L4 inference argv prompt row; §Security Anti-Patterns → Code Patterns). If the fix grows the prompt materially, re-basing the ceiling must cite a fresh live measurement and stay below the Windows `CreateProcess` 32767 limit; whether the current headroom absorbs the change is research's question.
- OTLP-derived content in the prompt is confined to `digest.payload_summary` + `project_context` + the `<CITABLE_EVIDENCE_IDS>` section, all reaching the prompt already scrubbed (`Digest::scrubbed_clone`) (per security-plan §Input Validation, L4 inference argv prompt row; §Security Anti-Patterns → Code Patterns). A fix that changes "what the digest carries into the prompt" must keep any new OTLP-derived field inside the scrubbed digest projection; whether a candidate field is already covered by `scrubbed_clone` is research's question.
- Sampling arguments added to `build_llama_cli_args` (`--seed` / `--temp` or similar) must be first-party constants or validated config, never a string sourced from an OTLP attribute, MCP tool argument or workspace-detector output (per security-plan §Security Anti-Patterns → Code Patterns, `Command::arg(user_input)` ban).
- Any incident that the changed creation predicate now admits must persist through the existing scrubbed projection: `resolution_summary_text` holds the per-string-leaf span-masked `scrubbed_l4_json` projection at its three write paths; a new or widened creation path must not bypass it (per security-plan §Security Anti-Patterns → Logging, MEASURED reality paragraph — incident-summary corpus write boundary; §Data Protection, at-rest corpus).

The existing `interpretation.inference.error` leaf carries bounded categories only, with no prompt text, excerpt or output bytes (per security-plan §Logging & Monitoring "What NEVER to log"; §Input Validation, L4 argv row). Where the justification must be retained as evidence, it lives in chunk evidence files, not the agent log; whether any current log site already emits model text is research's question.
- A measurement harness that invokes `llama-cli` outside pulse-app: the three product-consumed L4 path vars keep their guard (traversal-reject, length bound, canonicalize, regular-file, opt-in `ANDROMEDA_PULSE_L4_ALLOW_ROOT`) inside the product; a harness/xtask-only tool locator that never reaches the shipped binary takes the trim + `is_file()` + clean-skip carve-out instead, and logs basenames only (per security-plan §Security Anti-Patterns → Input, carve-out + NARROWED EXCEPTION; §Security Anti-Patterns → Logging, full-path ban).

## Patterns to follow
- The bounded-category rejection pattern: a pure bounded-parse helper whose `label()` is the only thing that reaches the log (`PromptRejection` precedent) — reuse it for any new measurement-time failure category (per security-plan §Input Validation, L4 argv row).
- Per-string-leaf masking of JSON payloads (`scrubbed_l4_json`), never masking the serialized text — any new persisted L4-derived JSON follows it (per security-plan §Security Anti-Patterns → Logging, MEASURED reality paragraph).
- ASCII-only prompt template text, pinned by `composed_prompt_templates_are_ascii_clean_for_argv_transport` — new decision-guidance wording must pass it (argv crosses an ANSI decode on the Windows llama.cpp build; scope §Boundaries already carries this, and the L4 argv row of security-plan §Input Validation owns the transport boundary).
- Harness-only path vars: trim + `is_file()` + clean SKIP with only the variable NAME in the message (per security-plan §Input Validation, CLI/env row, `ANDROMEDA_PULSE_MSEDGEDRIVER_PATH` precedent).

## Anti-patterns to avoid
- NEVER pass telemetry-derived text to a subprocess argv except through the `validate_prompt_bounded` gate, and never derive a sampling argument from it (per security-plan §Security Anti-Patterns → Code Patterns).
- NEVER log raw OTLP attribute values, span/log content payloads, or a full product-consumed path (model GGUF, `llama-cli` binary, allow-root) while recording the measurement (per security-plan §Security Anti-Patterns → Logging).
- NEVER reference a third-party GitHub Action by floating tag or elevate workflow-level permissions while editing ci.yml (per security-plan §Security Anti-Patterns → Secrets).
