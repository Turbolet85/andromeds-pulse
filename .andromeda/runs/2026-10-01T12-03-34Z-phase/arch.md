## Relevance
partial — arch governs placement and locked decisions for both halves (the L4 runtime args / incident-creation path, and the xtask/CI source-lint surface); the prompt's surface/dismiss wording and the measurement method are interpretation/tests substance, not arch.

## Constraints
- The L4 runtime is a LOCKED decision: `llama.cpp` prebuilt `llama-cli` at the b9305-pinned series, D1 spawn-per-generation, JSON-schema-constrained GBNF via `--json-schema-file`, plus the bounded-invocation set (`-n {max_tokens}` cap, `-st` single-turn, outer `tokio::time::timeout`, `kill_on_drop(true)`). A build bump is a deliberate chunk-scoped event, never tag drift. Adding sampling arguments (`--seed` / `--temp`) to the args vector is inside this decision; dropping or weakening any bounded-invocation member is not (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer]; §Inherited Defaults → LLM inference runtime).
- The swap boundary is `LlmInferenceRunner` in `crates/interpretation/src/contract.rs`, with the concrete llama.cpp impl ONLY at the `pulse-app` binary boundary. Sampling/CLI arguments therefore belong in `pulse-app/src/llamacli_inference.rs`. Prompt and decision-guidance text belongs in `crates/interpretation`, and digest composition in `crates/triage`. No llama.cpp-specific concept may move into the trait crate (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer] → Bus-factor / swap paths).
- L2 incident identity is coalesce-per-cue-identity `(kind, scope, scope_id)`. A fix at the creation predicate (`pulse-app/src/inference_runtime.rs`, the `Decision::Dismiss` skip) must not re-key creation on `L4Output.fingerprint`, which is model-authored and constant under the deterministic runner (per architecture §Established Decisions [Fault Identity]).
- Both `inference_runtime` L4 writers are among the SEVEN production writers arbitrated by the monotonic guard at the `CorpusWriter` choke point. Any creation-path change must keep the `Applied` / `DeclinedStale` outcome semantics, where a decline is a value and not an error (per architecture §Established Decisions [Corpus Write Arbitration]).
- Dependencies flow toward `pulse-app` as a DAG. The chunk's spread across `interpretation` / `triage` / `pulse-app` / `xtask` must add no new sibling edge between library crates, and each crate must expose only its contract module as `pub` (per architecture §Cross-cutting Patterns → Module dependency direction; §Conventions → Module visibility discipline).
- CI logic that needs Rust lives in the `xtask` crate, so contributors run the same command locally. Every xtask verb is registered under the formalized-CLI-contract rule: an exit 0 / 1 / 2 contract and one machine-parseable verdict on stdout, recorded in Occupied Resources. `pre-push:linux`'s registered contract names its stage list (`script-modes` · `npm` · `clippy` · `test` · `ci-gates`) and states it binds no port, starts no `pulse-app` and reads no new env var. Adding the Cyrillic check as a stage, or landing a new shared verb, changes that registered contract. Whether the inline `ci.yml` step or a shared verb is the right shape is the scope's P4 fork, and this mandate weighs toward the shared-verb arm (per architecture §Infrastructure Patterns → CI/CD approach; §Occupied Resources → xtask CLI surfaces (dev/CI gates)).
- Any new runtime knob (for example an env override for seed or temperature) is a reserved resource. It follows the config precedence env > `config.toml` > defaults and must be registered in the env-var list. `ANDROMEDA_PULSE_L4_DETERMINISTIC` selects the canned runner, so a deterministic-mode run is no evidence of real-model surfacing behaviour (per architecture §Occupied Resources → Environment variables; §Cross-cutting Patterns → Config management).

## Patterns to follow
- **Absorb runtime-specific changes in the concrete impl.** Change the args vector in the binary-boundary `build_llama_cli_args` and leave the trait surface unchanged (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer]).
- **Follow the formalized xtask verb shape.** Use exit 0 green · 1 red · 2 cannot-evaluate, one pretty-JSON verdict on stdout plus a `target/<verb>/report.json` twin, wired into `ci.yml` as a plain named `run:` step. `check:staged-artifacts` and `check:npm-supply-chain` are the precedents (per architecture §Occupied Resources → xtask CLI surfaces (dev/CI gates)).
- **Agent-driven development style.** Measurement harness outputs should be deterministic invocations with machine-parseable, schema-stable records, so the live dismissal measurement is gradable rather than eyeballed (per architecture §Cross-cutting Patterns → Development Style).
- **Settings extension over a new IPC namespace.** If a sampling value ends up user-configurable, extend the existing settings surface instead of adding a TauRPC procedure, which would also need an `EXPECTED_PROCEDURES` pin and an Occupied Resources entry (per architecture §Cross-cutting Patterns → Webview IPC capability policy; §Conventions → Endpoint naming).

## Anti-patterns to avoid
- Swapping the model or runtime, bumping off b9305, or replacing the GBNF/JSON-schema constraint path as a "fix" (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer] → Pin discipline).
- Keying incident creation or dedupe on `L4Output.fingerprint`. This is REJECTED in the plan (per architecture §Established Decisions [Fault Identity]).
- A reverse or sibling dependency edge, for example `interpretation` depending on `triage` or `pulse-app` internals, introduced to carry digest content into the prompt (per architecture §Cross-cutting Patterns → Module dependency direction).

## Contract bindings
- **arch ↔ tests:** `pre-push:linux`'s stage list and CI's lint-test jobs must cover the same source-lint check. That parity is the scope's PREREQ outcome. The headful leg's storm-incident stage runs under the deterministic-L4 gate, so a creation-predicate change is exercised there only through the canned output, never the real model (§Occupied Resources → xtask CLI surfaces; §Occupied Resources → Environment variables → `ANDROMEDA_PULSE_L4_DETERMINISTIC`).
- **arch ↔ security:** extending the args vector is bounded by the security-owned argv rules: the ASCII template text and the `-p` prompt bound. The three L4 path guards are untouched (§Established Decisions [LLM Inference Runtime]; §Occupied Resources → Environment variables → `ANDROMEDA_PULSE_MODEL_PATH` / `_LLAMA_*_BIN_PATH` / `_L4_ALLOW_ROOT`).
- **arch ↔ obs:** the decision record for each L4 generation, and any new xtask verdict JSON, are machine-parseable outputs that obs and tests consume (§Cross-cutting Patterns → Development Style).

## Acceptance criteria contributions
- **Bounded invocation survives.** After any sampling-argument change, the `llama-cli` invocation still carries `-n`, `-st` and `--json-schema-file`, runs under the outer wall-clock timeout with `kill_on_drop`, and stays on the b9305-pinned binary and the same model. Whether the args vector already lacks seed/temperature is a take-up-verified coordinate; research re-confirms it at HEAD (per architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer]).
- **Coalescing key unchanged.** Incident coalescing stays on `(kind, scope, scope_id)`. A creation-predicate change alters only WHETHER an incident is created, never its identity key (per architecture §Established Decisions [Fault Identity]).
- **Lint check is registered.** If the Cyrillic check becomes an xtask verb or a `pre-push:linux` stage, §Occupied Resources → xtask CLI surfaces is amended with its exit/verdict contract, and `pre-push:linux` still binds no port, starts no `pulse-app` and reads no new env var (per architecture §Occupied Resources → xtask CLI surfaces (dev/CI gates)).
- **No new crate edge.** No new inter-crate dependency edge is added. Code lands in `pulse-app` (args, predicate), `crates/interpretation` (prompt), `crates/triage` (digest), and `xtask` + `.github/workflows/ci.yml` (source lint) (per architecture §Cross-cutting Patterns → Module dependency direction).
