## Relevance
Relevant (bounded) — arch governs crate placement, the locked fault-identity/deterministic-L4 keying rules the damper's key selection must respect, env-var + registry discipline for any new tunable, and the OTLP-only injection contract the idle-scenario legs ride; arch does NOT own the damper algorithm or its rate bound.

## Constraints
- Damper code must land in the already-reserved crates `triage` and `pulse-app`; the 16 workspace crate names are reserved and cannot be reused or added to casually, and `Cargo.toml` deps flow toward `pulse-app` only (DAG, no library crate depends on the binary) — per architecture.md §Occupied Resources → Cargo workspace crate names + §Cross-cutting Patterns → Module dependency direction.
- Any damper identity/hash key must be derived from INPUT condition state (cue / digest), never from model-authored `L4Output` fields: arch explicitly REJECTED keying dedupe on `L4Output.fingerprint` on the ground that it is a constant under the deterministic runner, making per-key dedupe a no-op in exactly the mode used for reproducible e2e verification — per architecture.md §Established Decisions [Fault Identity] (REJECTED clause) + §Occupied Resources → Environment variables → `ANDROMEDA_PULSE_L4_DETERMINISTIC`. This applies directly to the scope's content-hash damper direction.
- L2 incident identity is locked as COALESCE-PER-CUE-IDENTITY on `(kind, scope, scope_id)`, with per-fingerprint dedupe recorded as possible-but-declined and explicitly REVISITABLE by a future entry — so the "hanging-incident churn" outcome may change the benign-window/reset behavior freely, but changing the coalesce predicate itself requires an arch amendment, not a silent edit — per architecture.md §Established Decisions [Fault Identity] (L2).
- If the chunk introduces a tunable (growing-refractory step, benign-window bound, damper TTL), arch requires the env-layer-only shape its nearest sibling `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` establishes: bounded parse, whitespace-trimmed, every rejection falling back to the default without a panic, resolved ONCE at boot into a single shared bound, no `Settings`/`config.toml` surface (hence no TauRPC contract, no hot-reload delta), and duration field names carrying explicit `_seconds` units — per architecture.md §Occupied Resources → Environment variables + §Conventions → Configuration units + §Cross-cutting Patterns → Config management.
- A new observable for outcome 3 must ride the self-observation path only (`opentelemetry-stdout` / file exporter to `&lt;data_dir&gt;/logs/`); the product never dials its own `:4317`/`:4318` — per architecture.md §Established Decisions [Self-Observation] + §Cross-cutting Patterns → Self-observation discipline.
- The L4 runtime stays untouched: `LlmInferenceRunner` (`crates/interpretation/src/contract.rs`) is the swap boundary, D1 spawn-per-generation with bounded `-n` + `-st` + outer wall-clock timeout is the locked invocation discipline. The damper is a decision upstream of `generate_constrained`, not a change to it — per architecture.md §Established Decisions [LLM Inference Runtime] + §Inherited Defaults.
- Anything the damper exposes across the TauRPC bridge must be `serde::Serialize`, with `thiserror` enums inside `triage` converting to `AppError` at the bridge; new types crossing out of `triage` go through its contract module (crates expose only their contract module; no cross-crate `pub use`) — per architecture.md §Cross-cutting Patterns → Cross-bridge data shape + §Conventions → Module visibility discipline + §Project Intent → Template patterns.

## Patterns to follow
- **Cadence's already-registered wire surface**: `pulse://stream/cadence-events` (`crates/triage/src/cadence/broadcast.rs`, chunk #80, the cadence coordinator's L6-visibility topic) and `pulse://stream/digests` (chunk #81) exist for exactly this subsystem — a damper decision that needs a wire surface reuses one rather than minting a topic (per architecture.md §Occupied Resources → Tauri IPC events + §Standard Contracts → Real-time push contract).
- **Env-knob precedent** — `ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS` (`crates/triage/src/cue/thresholds.rs` → `Thresholds::from_env` → one bound shared by silence evaluator / emitter counters / lifecycle registry, one WARN per boot on a non-default value): the exact template for any damper constant that becomes overridable, including its single-shared-bound property (per architecture.md §Occupied Resources → Environment variables).
- **Crate template shape** — public contract module as the only `pub` surface, `pub(crate)` internals, `thiserror` error enum, TauRPC router mounted by `pulse-app` (per architecture.md §Project Intent → Template patterns).
- **Procedure-addition ritual** if any IPC surface is added: router registration in the owning crate + §Occupied Resources entry + the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` — explicitly NOT a `pulse-app/capabilities/` edit, since TauRPC dispatches every method through one invoke handler (per architecture.md §Cross-cutting Patterns → Webview IPC capability policy).
- **Idle/sustained verification input** — the formalized `crates/ingest/examples/inject_demo` CLI contract (`--sustained` unbounded moderate error rate, `--minutes=N`, `--error-pct=0..100` range-checked, unknown arg rejected exit 2), with `--sustained` existing specifically to remove the finite-storm-ages-out false negative; note `xtask::webview_drive` threads NO arguments and passes `PULSE_INJECTOR` as a path only, so a headful idle leg would need that gap addressed (per architecture.md §Stack → GUI verification harness row + §Occupied Resources → `PULSE_INJECTOR`).

## Anti-patterns to avoid
- No new workspace crate and no reuse of a reserved crate name for the damper; no new workspace dependency (default features stay minimal, feature-gated deps only) — per architecture.md §Occupied Resources → Cargo workspace crate names + §Cross-cutting Patterns → Feature-gate hygiene.
- No in-process test bypass, mock-channel back-door, or "test ingest" feature flag to produce the idle/quiet scenario — synthetic telemetry enters over real OTLP on `:4317`/`:4318` only — per architecture.md §Cross-cutting Patterns → Test-time telemetry injection.
- No ad-hoc new `pulse://stream/*` topic, TauRPC procedure, corpus table or `SCHEMA_VERSION` bump smuggled in for damper bookkeeping; arch enumerates all four registries and any addition is an amendment obligation at wrap — per architecture.md §Occupied Resources (IPC events / IPC routes / Corpus SQLite schema names).

## Contract bindings
- **arch ↔ obs** — outcome 3's suppressed/reused-generation observable: arch fixes the transport (self-observation exporter to `&lt;data_dir&gt;/logs/`, never the product's own OTLP ports) and records the failure mode obs owns — a target without its OWN exact allowlist leaf falls back to the bare `metric` key carrying only `value`/`unit`/`module`, silently redacting every label (architecture.md §Occupied Resources → `telemetry.frontend.*` note). Leaf naming and allowlist entry are obs-plan's call.
- **arch ↔ tests** — the deterministic-L4 gate (`ANDROMEDA_PULSE_L4_DETERMINISTIC`, canned constant `L4Output`) is the mode the e2e legs run in; a damper keyed on generation OUTPUT would be a no-op there, so arch's keying constraint above is the binding tests must be able to exercise. The 15-stage `cargo xtask webview-drive` path and the `PULSE_*` relay set are the harness contract any new leg extends.
- **arch ↔ security** — a new env-var knob inherits the bounded-parse / never-panic / never-block-boot discipline arch records for every product-consumed var; secret-class and path-class rules do not apply here (no path input expected).
- **arch ↔ registry (wrap obligation)** — every new env var, IPC route, event topic or filesystem resource the damper lands must be amended into §Occupied Resources at wrap (D-arch-resources); whether this chunk lands any is a plan-time decision.

## Acceptance criteria contributions
- (arch) Damper code lives in `crates/triage` (cadence/cue seam) and `pulse-app`; no new workspace crate, no new workspace dependency, no library crate depending on `pulse-app` (per architecture.md §Occupied Resources → Cargo workspace crate names + §Cross-cutting Patterns → Module dependency direction).
