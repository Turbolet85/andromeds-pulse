## Constraints
- The L4 `-p` argv operand is admitted to `Command` ONLY through `validate_prompt_bounded` (16384-byte ceiling, NUL/C0/C1 rejected with `\n\r\t` whitelisted, reject-never-truncate) at a single production caller — per security-plan §Input Validation ("L4 inference argv prompt" row) and §Security Anti-Patterns → Code Patterns. A damper that adds a reuse, re-spawn, or short-circuit path around the existing generation seam must not create a second argv route that bypasses it. Whether every current spawn path already routes through that single caller is research's question.
- Every write of an L4-output-derived value into the incident brief must pass `security::scrubber::scrub_attribute` — §Security Anti-Patterns → Logging (uniform scrubber coverage) requires `Incident.resolution_summary_text` to hold a scrubbed JSON projection at THREE named write paths (`scrubbed_l4_json`), with `ScrubbedValue::Redacted` collapsing to the category marker in place. A "reuse the attached brief" direction re-enters that boundary; whether reuse re-writes or merely re-reads is research's question.
- Any new damper observable must carry no raw OTLP attribute value, span/log/metric content payload, snapshot content, or DuckDB query parameter — per security-plan §Logging &amp; Monitoring ("What NEVER to log") and §Security Anti-Patterns → Logging (first NEVER bullet). Damper decisions must reduce to bounded categories, counts, and non-reversible identities.
- No full product-consumed filesystem path may appear in a new leaf — basename of the canonicalized path only, per §Security Anti-Patterns → Logging (second NEVER bullet). The two carried exceptions (`app.boot.tracing.init` `log_dir`, `app.boot.pid` `path`) are owned by the diagnostics-sweep route entry, which the chunk's Boundaries explicitly exclude — this chunk must neither widen nor absorb them.
- A content-hash damper key must be derived over already-scrubbed content and must not mint a stable identifier of a secret — §Security Anti-Patterns → Logging records the content-INDEPENDENT discriminator rule, and §Code Patterns records that the OTLP-derived prompt substring is already scrubbed upstream by `Digest::scrubbed_clone`, so the bound there is a shape control, not a confidentiality fix.
- If a tunable (refractory ladder, damper window, benign-window override) is introduced as an env var, it takes the bounded-parse discipline AND must be registered in the §Input Validation CLI/env-var enumeration — per security-plan §Input Validation (CLI / env var inputs row), whose completeness claim is load-bearing.
- Dependency posture is unchanged: `cargo deny check bans licenses sources` must stay green, `multiple-versions = "deny"` is never relaxed and the `tonic` canary never skipped — per security-plan §Dependency Security → CI integration. The scope's `[inferred]` "no new workspace deps" aligns with this; adding one re-opens the carve-out discipline.

## Patterns to follow
- `scrubbed_l4_json` in `pulse-app/src/inference_runtime.rs` — the established scrub-at-write-boundary shape for L4 output projections, enumerated at three paths in §Security Anti-Patterns → Logging. A reuse/re-attach path follows the same shape rather than inventing one.
- `validate_prompt_bounded` returning a bounded `PromptRejection` whose `label()` is the only value reaching the log, surfaced on the existing `interpretation.inference.error` leaf with no prompt text, excerpt, or offending substring — per §Input Validation (L4-argv row). Any damper rejection/suppression reason should be a bounded label of the same class.
- Blake3 full-hex fingerprint as a non-PII-by-construction identity (`digest.attention_cues[].fingerprint`, per §Input Validation L4-argv row) — the in-plan precedent for a content-hash damper key.
- Bounded env-var parse with a documented default and no panic (`ANDROMEDA_PULSE_BASELINE_BOOTSTRAP_SECONDS`: trimmed, non-zero, range-checked, unset/empty/unparseable ⇒ default) — per §Input Validation CLI/env-var row; this is also the var the scope names as governing damper onset.
- Content-independent collision discriminator (a per-table monotonic ordinal never derived from the value) — per §Security Anti-Patterns → Logging, the pattern to reuse if damper state keys can collide.

## Anti-patterns to avoid
- NEVER pass OTLP-derived text to `Command::arg` outside the one admitted, bounded L4 `-p` path (per security-plan §Security Anti-Patterns → Code Patterns) — a reuse or re-spawn path that reconstructs a prompt without the guard reintroduces the banned construct.
- NEVER log raw OTLP attribute values or content payloads (per §Security Anti-Patterns → Logging) — the "suppressed vs. generated" leaf must not carry digest body text, silent-service payload text, or brief content.
- NEVER add a TauRPC procedure without its `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` AND a validated argument struct (per §Security Anti-Patterns → API) — applies only if damper state is surfaced over IPC; the scope's Boundaries suggest it is not.
