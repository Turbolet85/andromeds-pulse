# a11y extract

## Relevance
partial — the console program has no display and adds no surface the plan asserts; the a11y domain enters only through the scope's "window app stays whole" bullet (its a11y job stays green until `Window retired`).

## Constraints
- The console program is outside the plan's assertable set: a11y-plan §1 (A11y scope — entities) classes the OTLP receivers and the DuckDB storage as not-assertable, and §1 (A11y surfaces & assistive tech reach) names three surfaces only (desktop-webview, desktop-native tray, OS notification). The plan holds no mandate for a command-line surface or its output; none is extracted, and none may be inferred from the webview sections.
- The must-be-accessible set stays in force while the window stands: a11y-plan §1 (Critical paths, with the Surface set extension to P1–P14) requires each of those paths accessible, and the chunk removes no surface. Sharing the engine between two programs must leave every one of those paths served by the window app as before.
- a11y-plan §10 (Always-required SLO invariant) requires zero WCAG AA violations on the must-be-accessible paths, with no retry-once policy; the chunk's engine separation may not be absorbed by a retry or a quarantine in the a11y suite.
- a11y-plan §10 (Standard+ invariants) requires that a run holding a violation tuple the committed baseline lacks fails, and that an absent baseline fails; the chunk leaves `pulse-app/ui/tests-a11y/baselines/a11y-violations-summary.json` where it is and unchanged.
- a11y-plan §9 (Pipeline integration) requires the a11y run as its own blocking `a11y` job of `ci.yml` on `ubuntu-22.04`; a11y-plan §3 CI integration (Pipeline integration) names its step chain (webview build, Playwright chromium, `cargo xtask test:a11y`) and two uploads that fail on no file. A new workspace member, a moved crate or an xtask edit made for the console program must leave that chain and its paths resolving. Whether the chunk's cut touches `xtask`'s `test:a11y` verb, the `pulse-app/ui` path or the job's steps is research's question.
- a11y-plan §3 Harness wiring & conventions (Regression baseline) names two pins in `pulse-app/tests/a11y_perf_workflow.rs` that hold the baseline's presence and the detector's failure on its absence. If the chunk moves tests or code out of `pulse-app`, those two pins stay runnable in the suite the gate block runs. Whether the planned file moves reach that test file is research's question.
- a11y-plan §10 (Performance budget per a11y CI run) requires the a11y run plus tests E2E under 10 minutes. Whether a second program in the workspace lengthens the a11y job's own build is research's question; the plan gives no allowance for it.

## Patterns to follow
- Read what the a11y job's green witnesses before leaning on it: per a11y-plan §3 Harness wiring & conventions (Mock layer, Static serving) the suite audits the statically served SPA over a mocked Tauri IPC. Its green reads the webview source, the mock and the fixtures, not the engine or the bridge. It is not evidence that the window app still boots on the shared engine; the boot job carries that reading.
- Keep the bridge's shape stable where the mock names it: a11y-plan §3 Harness wiring & conventions (Mock layer) binds the specs to the `TauRPC__<router.path>` command shape and to fixture payloads in `helpers/v02-fixtures.ts`. If cutting `tauri` out of `crates/ingest`, `crates/triage` or `crates/ui-bridge` renames a router path, a procedure or a payload field, the mock and fixtures are corrected in the same chunk. Whether the cut changes any of those names is research's question.
- The standing rule for a new surface is not triggered and stays untriggered: a11y-plan §3 Harness wiring & conventions (Adding a surface) requires one axe spec per new route or modal in the same chunk. The chunk adds no route and no modal; a plan step that adds one to the webview brings that rule with it.
- Check suite health by the config-named listing when a workspace or path change lands: a11y-plan §3 Harness wiring & conventions (Adding a surface) gives the config-named `--list` form and warns that the bare form reads an inert config and that a list-time import failure once disabled the whole suite silently.

## Anti-patterns to avoid
- Making the a11y job conditional, path-filtered or non-blocking so the console program's commits pass it: a11y-plan §11 (CI) bans a soft or skipped a11y gate and a deferral to post-merge.
- Re-baselining or skipping the per-PR diff to turn a red a11y run green: a11y-plan §11 (SLO) bans a retry-once policy and a skipped regression diff, and requires failure on an absent baseline.
- Claiming the window's accessibility held through the separation without machine output: a11y-plan §11 (Strategy) bans a conformance claim with no machine-verifiable evidence; the evidence is the a11y job's run on the chunk's sha.

## Contract bindings
- a11y ↔ tests (harness): a11y-plan §3 Focus management test harness (Contract binding) and a11y-plan §9 (Pipeline integration) bind the a11y run to tests' five-command harness (`boot`, `run`, `status`, `cleanup`, `logs`). The scope leaves the five verbs' targeting of the console engine to `Agent harness drives the console engine`; this chunk does not re-point them, and a plan step that changes what `boot` starts moves the a11y binding with it and says so.
- a11y ↔ tests (CI): a11y-plan §9 (Per-pipeline-stage a11y artifacts) and a11y-plan §3 CI integration (CI gate) place the a11y gate in the same `ci.yml` as the test jobs. The gate this chunk ends with (the scope's open `[inferred]` item) is added beside the `a11y` job, never by editing it.
- a11y ↔ obs (log family): a11y-plan §3 CI integration (Command) and a11y-plan §9 (Per-pipeline-stage a11y artifacts) place the `a11y-*` result files in the data dir's `logs/`, in the obs log format bound by a11y-plan §3 Structured violation JSON schema. The console program keeps its log sink among its five records; where it writes that log under the same directory, its file names stay clear of the `a11y-*` family. Whether the two can meet in one directory in any run is research's question.
- a11y ↔ design / layouts: (none) — the chunk renders nothing, so no contrast, motion or focus-order binding is engaged.
