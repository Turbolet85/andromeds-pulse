# arch extract

## Relevance
relevant — the chunk adds a second program form over the shared engine crates; workspace placement, dependency direction, occupied resources and the start path all bind it, while the plan itself still describes one Tauri process and states no console form.

## Constraints
- **The plan carries no console-engine mandate; it describes the opposite shape.** architecture §Project Intent → Product type reads "Not a web app, not a CLI"; architecture §Design Philosophy → Single-process modular monolith names the `pulse-app` Tauri binary as the one program the fourteen library crates link into; architecture §Infrastructure Patterns → Deployment model gives the runtime topology as one Tauri process plus one optional `andromeda-pulse-mcp` sidecar. Nothing in the plan licenses, names or places a headless entry, so the plan constrains this chunk only through the rules below, and the three sections above are amended at wrap (the spec masters are read-only at phase). The plan must not cite architecture.md as describing the console program.
- **Workspace placement and names.** architecture §Occupied Resources → Cargo workspace crate names reserves sixteen member names and forbids their reuse; architecture §Occupied Resources → Process / service identity registers the binary names (`pulse-app` as the dev-build binary, `andromeda-pulse` as the bundled name, `andromeda-pulse-mcp` as the sidecar) and warns that the dev-build and bundled names are not interchangeable. A new workspace member or a new `[[bin]]` name is a new occupied resource: it collides with none of these and is recorded there at wrap. architecture §Design Philosophy → Single-process modular monolith defers every count word ("fourteen", "sixteen") to that list, so a new member moves the count in every restating site.
- **Dependency direction.** architecture §Cross-cutting Patterns → Module dependency direction requires that dependencies flow toward the `pulse-app` binary, that no library crate depends on the binary crate, that no library crate depends on a sibling unless its declared contract requires it, and that the graph is a DAG with `pulse-app` as the only root. A console program is a second root the plan does not yet name. Engine boot wiring that both programs share therefore cannot be reached by depending on `pulse-app`; where that wiring lives at the chunk base, and how much of it sits in `pulse-app/src`, is research's question. The convention itself puts the window framework inside module crates: architecture §Conventions → Workspace API style calls for one TauRPC router per module crate, and architecture §Project Intent → Template patterns gives each library crate "(where applicable) a TauRPC-router module mounted by `pulse-app`"; architecture §Occupied Resources → Tauri IPC routes places `app_info` / `health` / `ready` / `get_settings` / `update_settings` in the `ui-bridge` crate, and architecture §Occupied Resources → Environment variables (the `ANDROMEDA_PULSE_CONFIG_PATH` row) places the `Settings` type in `crates/ui-bridge/src/contract.rs`. Cutting a library crate's dependency on the window framework is thus a departure from a written convention, to be amended at wrap; which library crates depend on `tauri` or `taurpc` at the chunk base, and whether settings and liveness state are reachable without them, is research's question.
- **Occupied resources the program stays inside.** architecture §Occupied Resources → Network ports reserves `:4317` and `:4318`, each bound on `127.0.0.1` only, and no other port. architecture §Occupied Resources → Filesystem locations fixes the data dir root resolution, the `ANDROMEDA_PULSE_DATA_DIR` override and the subpaths (`config.toml`, `logs/`, `corpus/corpus.db`, `run/andromeda-pulse.pid` "written by production binary at boot", `run/workspace-key` published at boot for the sidecar), and names exactly THREE product-written locations outside the data dir. architecture §Occupied Resources → Environment variables is the closed registry of variables the product reads, and architecture §Cross-cutting Patterns → Config management fixes precedence env > `config.toml` > built-in defaults. A console program that shares the data dir shares one pid file, one log family and one corpus with the window app; whether the two may run at once against one data dir, and whether the console boot performs the `run/workspace-key` publish, is the plan's to state.
- **Corpus on a host with no desktop session.** architecture §Occupied Resources → Corpus SQLite database / schema names → At-rest posture requires the cell key to come from the OS credential store (Linux Secret Service) with the opt-in `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` fallback, and states that on a host with neither a credential store nor a configured passphrase "the corpus degrades to absent rather than inventing a key". architecture §Occupied Resources → Filesystem locations (the corpus-key lock file bullet) requires a set `XDG_RUNTIME_DIR` to be absolute, canonicalize and be a directory or lock-dir resolution fails closed. "Boots ... corpus with no display" therefore turns on which of the two registered key sources is present on the target host; a third source is outside the plan and outside the scope's boundary. Whether the code at the chunk base degrades as the plan requires when no Secret Service is reachable is research's question.
- **No model, and the incident producer sits behind the model's output.** architecture §Established Decisions [LLM Inference Runtime — L4 interpretation layer] makes `LlmInferenceRunner` the swap boundary with the concrete impl at the binary boundary, and records the carried form "the report on an event is assembled without a model" as unbuilt and owned by the next version. architecture §Occupied Resources → Corpus SQLite database / schema names names `pulse-app/src/inference_runtime.rs::create_incident_from_l4_output` as the producer of an incident's `created` event, and architecture §Established Decisions [Fault Identity] has the producer write the title as `{cue_cause_label(kind)}: {model title}` on the cue identity `(kind, scope, scope_id)`. What the console engine does at the point where the model was called is therefore also the question of whether it can produce an incident at all; whether any incident path exists at the chunk base that does not pass through an `L4Output` is research's question.
- **The window's start path and the workspace build stay as pinned.** architecture §Stack and Technologies → Xlib thread initialisation (Linux, product start path) requires `xlib_threads::init()` to be the SECOND statement of `pulse-app`'s `main()`, after `render_posture::apply_linux_default()` and before the tokio runtime builds any thread, its place pinned by `pulse-app/tests/unit_xlib_threads.rs`; architecture §Occupied Resources → Environment variables (the `__NV_DISABLE_EXPLICIT_SYNC` row) allows the env write only while one thread exists. A console entry reached through `pulse-app`'s `main()` runs after both; one reached through another `main()` needs neither. architecture §Infrastructure Patterns → Build system fixes the lint gate at `cargo clippy --workspace --all-targets --all-features`, so any Cargo feature the chunk introduces must compile with every other feature on (features additive, never mutually exclusive), named `kebab-case` and off by default per architecture §Conventions → Feature flags.

## Patterns to follow
- **The second-binary precedent.** architecture §Occupied Resources → Process / service identity and architecture §Infrastructure Patterns → Deployment model record `andromeda-pulse-mcp` as a second shipped program whose `[[bin]]` is declared by a library crate, gated by a default-off feature, and which opens the same corpus through `Corpus::open` (architecture §Occupied Resources → Filesystem locations, the lock-file bullet). It is the one existing shape of "a second program over the shared crates" in the plan.
- **Trait in the lower crate, adapter at the binary boundary.** architecture §Established Decisions [Corpus Write Arbitration] records `DurableActiveIncidents` as a narrow read port declared in `triage` and implemented at the `pulse-app` boundary over the same `Arc<dyn CorpusWriter>`, and `IncidentWriteOutcome` as a deliberate parallel type because `triage` sits below `corpus`. A second binary boundary needs the same adapters; the plan places them in `pulse-app`, so where they live for two programs to share them without a reverse edge is the plan's to state.
- **Crate template for any new library crate.** architecture §Project Intent → Template patterns: a public contract module as the only `pub` surface, `pub(crate)` internals, a `thiserror`-derived error enum; architecture §Conventions → Module visibility discipline forbids `pub use` re-exports across crate boundaries outside the contract module; architecture §Established Decisions [Error Handling Pattern] puts `anyhow` at `main.rs` and `thiserror` inside modules.
- **A closed command-line contract.** architecture §Occupied Resources → xtask CLI surfaces registers every verb with named verdict arms and a closed exit set (0 pass · 1 fail · 2 cannot-evaluate) under the formalized-CLI-contract rule, and architecture §Stack and Technologies → GUI verification harness records the injector rejecting an unknown argument with exit 2 rather than ignoring it. "Driven by commands" has these as its only in-plan precedents.
- **The pid file and the log family are the out-of-process handle.** architecture §Occupied Resources → Filesystem locations makes `run/andromeda-pulse.pid` content canonical for liveness, and architecture §Occupied Resources → xtask CLI surfaces has `harness:status`, `harness:ready` and `ci-gates` derive their verdicts from that file, the pid's liveness, the `agent-latest.jsonl*` family under `logs/` and a TCP connect on the two resolved OTLP ports. A command that ends a running engine cleanly has these registered resources to find it by and no listening socket.

## Anti-patterns to avoid
- Pointing any exporter of the program's own telemetry at its own `:4317` / `:4318`: architecture §Established Decisions [Self-Observation] and architecture §Cross-cutting Patterns → Self-observation discipline ban it; self-telemetry lands under the data dir's `logs/`.
- Feeding the console engine in its gate through an in-process test mode, a test-ingest feature flag or a mock channel: architecture §Cross-cutting Patterns → Test-time telemetry injection requires real OTLP on the receiver, non-default ports only through `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT`.
- Reaching shared boot code by making a library crate depend on `pulse-app`, or by widening a crate's `pub` surface past its contract module: architecture §Cross-cutting Patterns → Module dependency direction and architecture §Conventions → Module visibility discipline.

## Contract bindings
- **arch ↔ obs:** the five kept records (log sink, identity at boot, panic, heartbeat, process end) are obs-plan's shapes; architecture registers only where they land (architecture §Occupied Resources → Filesystem locations, `logs/` and `run/andromeda-pulse.pid`) and names `app.exit`, `app.panic.fatal` and `app.boot.*` in passing. architecture §Standard Contracts → `app_info` carries a `tauri_version` field and architecture §Standard Contracts → `health` / `ready` are defined as Tauri IPC commands; the plan gives no console-side form of either.
- **arch ↔ tests / harness:** architecture §Occupied Resources → xtask CLI surfaces defines `harness:settled` as needing an `app.boot.window.navigation` record for each of four window labels, which a program with no window cannot produce, so that verb cannot be this chunk's gate; `harness:status`, `harness:ready` and `ci-gates` read only the pid file, the log family and the two ports. architecture §Cross-cutting Patterns → Test-time telemetry injection sends buffer read-back through the TauRPC `traces.*` / `metrics.*` / `logs.*` routers, a route a console program does not have; the plan names no other read-back, so this chunk's gate takes its observable from the program's own log or exit.
- **arch ↔ tests / CI:** architecture §Infrastructure Patterns → CI/CD approach keeps the `boot` job's eight boots gating and pins two workspace release-build witnesses (`cargo auditable build --workspace --release`, `cargo build --workspace --release --features mcp-server`), so a new workspace binary is compiled by both; a new CI step for the console program is a change of that key, recorded at wrap.
- **arch ↔ security:** loopback-only binds (architecture §Occupied Resources → Network ports), the closed env-var registry and the three out-of-data-dir write locations (architecture §Occupied Resources → Filesystem locations), and corpus key custody with no Secret Service (architecture §Occupied Resources → Corpus SQLite database / schema names → At-rest posture) are the points where the scope's "halts for the founder's own word" boundary meets a registered resource.
- **arch ↔ wrap:** sections this chunk's landing makes stale: architecture §Design Philosophy, architecture §Project Intent, architecture §Infrastructure Patterns → Deployment model and → Project directory structure, architecture §Occupied Resources → Process / service identity and → Cargo workspace crate names.

## Acceptance criteria contributions
- (arch) The console program listens on the two OTLP receivers alone, each on `127.0.0.1` at `4317` / `4318` or the port its registered override variable names, and opens no other listening socket (per architecture §Occupied Resources → Network ports).
- (arch) No library crate depends on `pulse-app`, the workspace graph is a DAG, and any new workspace member or `[[bin]]` name differs from every reserved crate and binary name (per architecture §Cross-cutting Patterns → Module dependency direction).
- (arch) With `ANDROMEDA_PULSE_DATA_DIR` set, every file the console program writes lies under that root at a registered subpath, or is the registered corpus-key lock file; it reads no `ANDROMEDA_PULSE_*` variable absent from the registry (per architecture §Occupied Resources → Filesystem locations).
- (arch) `cargo clippy --workspace --all-targets --all-features -- -D warnings` passes with the console entry present, every Cargo feature on together (per architecture §Infrastructure Patterns → Build system); `pulse-app`'s `main()` still opens with `render_posture::apply_linux_default()` then `xlib_threads::init()` (per architecture §Stack and Technologies → Xlib thread initialisation).
