# obs extract

## Relevance
relevant — the entry's third clause (log, identity, panic, heartbeat, process-end records kept) is obs-plan's own harness contract applied to a second program; the plan itself names no console program anywhere, so every mandate below is the app's mandate read onto it, and each place where that reading does not carry over is marked as a question.

## Constraints
- **Init order.** obs-plan §3 Tracing init requires: level filter resolved (`ANDROMEDA_PULSE_LOG_LEVEL`, fallback `RUST_LOG`) → subscriber registry composed → panic hook installed → the log sink's `WorkerGuard` parked process-wide, the at-exit hook and (Unix) the SIGTERM/SIGINT listener installed → only then the two OTLP receivers bound. The same key words its last step and its exit path in the Tauri app's terms (the event loop's return code feeding the exit record, then the guard drop, then the process exit with the same code). It states no sequence for a program with no event loop: what stands in that place in the console program is the plan's to state. Whether the init / hook / guard functions can be called today from a program that does not link the window framework is research's question.
- **One sink, one format.** obs-plan §3 Logging stack requires a single sink for the app: the non-blocking daily-rolling JSON file, no stderr `tracing` layer, no pretty-print. obs-plan §3 Log file location requires that file at `<data_dir>/logs/agent-latest.jsonl` under the resolved data dir (no new place on disk follows from it). obs-plan §3 Log format JSON schema is the line shape, a binding contract with tests. Not stated by the plan: what happens when the window app and the console program run over one data dir and write one log family — research's question whether that can occur at this chunk, the plan's to state if it can.
- **Identity on every line.** obs-plan §3 Service identity requires `service.name` / `service.version` / `deployment.environment` as default subscriber fields registered once at init. It names one identity for the app and a distinct one for the stdio sidecar ("distinct process identity"); it names none for a console engine. Which identity the console program carries is not stated — the plan's to state, and a new identity value is a spec change for the wrap.
- **Panic record.** obs-plan §7 Panic hook requires the hook installed after the subscriber, writing one ERROR `app.panic.fatal` record (location + SpanTrace, no panic message by design) to the file sink, with the prior hook chained after it. obs-plan §10 Always-required SLO invariant requires zero unlogged panics and bans retry-once handling.
- **Exactly one process-end record.** obs-plan §6 Log levels mapping (the `app.exit` entry of the warn row) requires exactly one `app.exit` per loggable process end behind a process-wide once-flag, after which the emitter drops the only guard; a signal end is recorded off the handler and the same signal re-raised with its default disposition; the at-exit path hands off to a reporter thread with a bounded wait. obs-plan §8 PII Scrubbing (the `app.exit` leaf) fixes the record to four closed fields. Its `exit_class` vocabulary is closed at three labels, two of them named for the event loop: which label a console program's command-driven clean end and its non-zero end take is not stated — the plan's to state; adding or renaming a label changes a closed set and is not this extractor's to assume.
- **Heartbeat.** obs-plan §3 Heartbeat ticks requires a 15 s `{module}.tick` record from each long-running subsystem on the same file sink, and treats tick presence as liveness only; obs-plan §10 Standard+ invariants adds the progress half (`rows_ingested_delta` on `buffer.tick`, `buffer.consumer.stalled` once per transition) and the >45 s gap as the stall signal. Both name four tick targets — ingest, buffer, viz, plugins; the entry boots ingest, buffer, detectors and corpus. Whether `viz.tick` and `plugins.tick` are emitted by a program that boots neither is not stated; which tick targets the console program's boot path reaches today (the detector ticks `triage.cue.tick` and `cadence.tick` of obs-plan §5 Metric Coverage included) is research's question.
- **Default-deny redaction stays in the pipeline.** obs-plan §8 PII Scrubbing (Integration points) requires the allowlist layer at the formatter stage, before the file write, and its default-deny posture requires every target to resolve to an exact leaf naming every field its emit site emits. A console subscriber composed without that layer would write unscrubbed fields; a new target added for the console boot with no leaf would render every field `<redacted>`. Whether the allowlist layer is reachable from a program that does not link the window framework is research's question.

## Patterns to follow
- **A boot that differs from the healthy one says so once.** obs-plan §6 Log levels mapping (warn row) uses one bounded-label record per boot wherever a degraded or changed posture would otherwise read the same as the default (`app.boot.buffer.degraded`, `corpus.keychain.fallback`, `triage.baseline.bootstrap_window.override`). Two console-boot cases fall under that pattern: a server with no desktop session, where the corpus key may not come from an OS credential store (obs-plan §8 PII Scrubbing, the corpus key-custody leaves, already names the records), and the point where 0.3.0's flow called the model, for which the plan names no "no model" record — if the plan adds one, this is its shape.
- **Boot spans.** obs-plan §4 Span / Trace Coverage (the CLI / main binary row) puts a root `app.boot` span over `main` with child spans for config load and receiver startup; names follow `{module}.{operation}` per obs-plan §2 Telemetry Strategy (Naming conventions).
- **Counts ride the tick.** obs-plan §5 Metric Coverage (the tick-aggregated counter rows) folds a new count as a field onto an existing 15 s tick rather than a record per event; a field added to a tick must be added to that tick's leaf (obs-plan §8 PII Scrubbing, the `triage.cue.tick` entry, records what a narrowed leaf costs).
- **A leaf has a guard that runs.** obs-plan §8 PII Scrubbing pairs each exact leaf with a field-set-equality test in both directions plus a fallback discriminator, placed under `pulse-app/tests/` because a src-level test in that crate never runs. If the console program's observability code lands outside `pulse-app`, where its guard runs is research's question.
- **Records are bounded labels, names and basenames.** obs-plan §1 Obs Scope Summary (Telemetry triggers, Vector 6) and obs-plan §8 PII Scrubbing (data classification, environment variables row) allow an env var NAME and a path basename, never a path or a value; a command the program is driven by is logged, if at all, as a closed label under the same rule.

## Anti-patterns to avoid
- NEVER link an OTel SDK into the self-observation runtime or point any exporter at the program's own receivers — obs-plan §11 Obs Anti-Patterns (Universal).
- NEVER make stderr or stdout text the program's record of itself: a command-driven program prints to a terminal, and that output is not the log — every self-record is a JSON line in the file sink, and no hot-path record at `info` — obs-plan §11 Obs Anti-Patterns (Logs).
- NEVER hardcode a second service identity beside the single registered source, and NEVER write a full path, a raw OTLP attribute value or a query parameter into a boot or exit record — obs-plan §11 Obs Anti-Patterns (Universal; Logs).

## Contract bindings
- **obs ↔ tests (harness):** obs-plan §3 Log format JSON schema is the contract the harness reads. The five records this chunk keeps (`app.exit`, `app.panic.fatal`, the ticks, the identity fields, the file itself) are what the later entry `Agent harness drives the console engine` reads; that entry also owns the two obs-plan §10 CI gates readings that stand unmet (the heartbeat-gap check no CI step makes, and a test run with zero spans failing the build) — neither is this chunk's.
- **obs ↔ tests (status):** obs-plan §3 Heartbeat ticks (Complementarity with the `health` command) keeps a synchronous status probe beside the ticks, and that probe is a TauRPC procedure. The plan names no status surface for a program with no bridge; what this chunk's own gate reads for readiness is the plan's to state, and a new listening surface is a halt under the scope's Boundaries.
- **obs ↔ security (logging):** obs-plan §8 PII Scrubbing binds to security-plan §Security Anti-Patterns → Logging: basename-only paths, the corpus passphrase never as a value, a field or a presence flag, the allowlist layer as the last line before the file.
- **obs ↔ CI:** if this chunk's gate boots the console program on a runner and keeps its log, obs-plan §9 CI Integration requires an artifact name distinct within the run and an upload that fails on no file, and obs-plan §10 SLO Invariants & Telemetry Budgets (CI gates; Load-profile constraints) requires a read over that log to exit `cannot-evaluate` on an absent family, never pass. The end-to-end gate in CI itself is `Engine end-to-end gate reachable`'s.
- **obs ↔ a11y:** (none)

## Acceptance criteria contributions
- A boot of the console program with no display leaves an `agent-latest.jsonl*` family under the data dir's `logs/` in which every line parses as JSON with `timestamp`, `level`, `target`, `message`, `fields`, and carries the three identity fields; the program wrote no `tracing` record to stderr (per obs-plan §6 Log Coverage, Required fields; per obs-plan §3 Service identity; per obs-plan §3 Logging stack).
- A panic induced in the console program leaves one ERROR `app.panic.fatal` record in that family (per obs-plan §7 Error Capture & Reporting, Panic hook; per obs-plan §10 SLO Invariants & Telemetry Budgets, Always-required SLO invariant).
- Each loggable end the chunk builds — the command-driven clean end and a SIGTERM — leaves exactly one `app.exit` record, its four fields rendered and none `<redacted>`, as the family's last record, with no full data-dir path anywhere in the family (per obs-plan §6 Log Coverage, Log levels mapping, the `app.exit` entry; per obs-plan §8 PII Scrubbing, the `app.exit` leaf).
- A run held past two tick intervals holds `ingest.tick` and `buffer.tick` records with no consecutive gap over 45 s per target, `buffer.tick` carrying its drain-progress fields unredacted (per obs-plan §3 Heartbeat ticks; per obs-plan §10 SLO Invariants & Telemetry Budgets, Standard+ invariants). Such a run binds 4317 and 4318: the scope's Boundaries put the operator's word before it.
