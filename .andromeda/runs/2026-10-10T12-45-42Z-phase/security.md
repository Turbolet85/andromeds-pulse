## Relevance
relevant — the chunk adds a second product program that binds the two OTLP receivers, opens the encrypted corpus, reads product env vars and writes the self-observation log; the plan names no console form, so every rule below applies by the shared-engine reading and the plan's process roster is not coverage for the new form.

## Constraints
- The console program binds the two OTLP receivers on `127.0.0.1` only and adds no other listener; the plan's surface roster holds no further socket, and the loopback bind is the whole authorization boundary (per security-plan §Security Anti-Patterns → API; §Threat Model Summary → Attack surface, Auth model). A listener beyond the two is outside the plan and halts under the scope's Boundaries.
- The receivers the console program boots carry the same controls the plan requires of the pair: the 8 MiB decode / body caps, the Host-header allowlist and CORS default-deny on `:4318`, the rate limit, and the post-`prost` invariant checks (per security-plan §API Security; §Input Validation, the two OTLP rows). Whether the console boot path reaches the receivers through the one construction site that attaches these, so that neither program can boot without them, is research's question.
- Every environment value the console program reads is parsed as the plan's row for it says: ports through `TryFrom<u16>`, bounded retention, closed log-level enum, and any product-consumed `ANDROMEDA_PULSE_*_PATH` / `*_DIR` canonicalized on both sides and confined under the data dir (per security-plan §Input Validation, the CLI / env var inputs row; §Security Anti-Patterns → Input). `ANDROMEDA_PULSE_PIDFILE` / `_LOGFILE` sit in the harness-only carve-out only because no product binary reads them; a console program that read either would take it out of that carve-out and under the confinement rule (per security-plan §Security Anti-Patterns → Input). The plan has no row for a product command's arguments: the §Input Validation boundary statement (validate wherever untrusted data enters) is the only rule it gives them, and the row is the wrap's to add.
- Corpus key custody on a host with no desktop session: the key comes from the OS credential store, the passphrase fallback engages only when `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` is configured and warns once per boot, and a host with neither leaves the corpus absent, never on an unlocked or ephemeral key; the passphrase is secret-class, sourced from the environment, never logged (per security-plan §Secret Management → Runtime; §Secret Management → What counts as secret). A command argument or file carrying it would be a new credential path and halts under the scope's Boundaries. What a no-display Linux server launch gets from the Secret Service is research's question.
- The corpus-key lock dir is read from the system `XDG_RUNTIME_DIR` through `Corpus::open`, fail closed when set but unusable, the shared temp dir when unset; the plan's residuals for it are accepted under the single-user boundary and measured under a systemd user session only (per security-plan §Security Anti-Patterns → Input, the corpus-key lock dir carve-out; §Data Protection → At rest, the corpus-key lock file). Whether a background server launch has `XDG_RUNTIME_DIR` set, and so which residual it stands in, is research's question. The plan counts three product-written locations outside the data dir; the console program adds no fourth (per security-plan §Data Protection → At rest).
- The five self-records keep the plan's log rules: no full product-consumed path (basename only, categorical), no OTLP attribute value, no secret-class value, redaction at the subscriber layer, and the process-end record behind its own exact allowlist leaf with its closed four-field set, exactly one per process end (per security-plan §Logging & Monitoring → What NEVER to log, Log format; §Security Anti-Patterns → Logging, the `app.exit` boundary and the path-basename bullet). The log directory is owner-only on Unix (per security-plan §Logging & Monitoring → Access controls); whether the code sets that mode is research's question.
- Telemetry the console engine stores passes the same write-boundary scrub sites as today: the five ring-buffer cells, with `service_name` scrubbed at its choke point before the observer tap, and every corpus write path (per security-plan §Security Anti-Patterns → Logging, uniform scrubber coverage and the intended posture). Whether the console boot wires the appender, the observer tap and the corpus writers through the same code as the window app is research's question.

## Patterns to follow
- Boot identity records emit basenames through the one existing helper, with allowlist leaves named to match (per security-plan §Security Anti-Patterns → Logging, the path-basename bullet).
- A record that deliberately passes unscrubbed gets its own exact allowlist leaf over closed labels and bounded numbers, never a bare namespace key (per security-plan §Security Anti-Patterns → Logging, the `app.exit` and `ui.ipc.rejection` boundaries).
- Any write to the process environment happens before a thread exists, ahead of the runtime build (per security-plan §Input Validation, the CLI / env var inputs row; §Threat Model Summary → Attack surface, CLI input).
- Path inputs use the project's single path primitive, `std` both-sides-canonicalize on the published-workspace-key precedent; no new validation library (per security-plan §Bootstrap phases → input-validation-library-install).
- A crate the console program brings in (an argument parser, for one) lands under the standing gates: no relaxed `multiple-versions`, a duplicate only as an ID-scoped, owner-named, reasoned skip, an advisory with a safe upgrade never ignore-listed; a new workspace member falls inside the `licenses` check (per security-plan §Dependency Security → CI integration).

## Anti-patterns to avoid
- NEVER log, or run code needing thread-locals, from a C `atexit` handler or a signal handler on the ending thread; the signal path records from a runtime task, restores the default disposition and re-raises the same signal, so a command that ends the engine by signal still ends it by that signal (per security-plan §Security Anti-Patterns → Universal).
- NEVER give the console program an OTLP network exporter or an OTel SDK for its own records; `tracing` to the file sink only (per security-plan §Security Anti-Patterns → API; §Data Protection → At rest, Logs).
- NEVER add a second product path that passes OTLP-derived, MCP-derived or workspace-derived text to a spawned command; the plan admits one, the L4 prompt, and a console program with no model adds none and reads no model or inference-binary path (per security-plan §Security Anti-Patterns → Code Patterns; §Security Anti-Patterns → Input, the narrowed exception).

## Contract bindings
- security ↔ obs: the five records' field sets and retention are the obs plan's; the redaction layer, the never-log list and the exact-leaf boundaries are security's (per security-plan §Logging & Monitoring → Log format, Log retention).
- security ↔ tests: the CI security gates run in the one workflow (`supply-chain` job, capability-drift, staged-artifacts), and the no-full-path / one-process-end-record readings are test legs over the console program's log family (per security-plan §Bootstrap phases → dep-security-ci-gate; §Security Anti-Patterns → Logging).
- security ↔ arch: the console program is a product binary the plan does not name — its Threat Model Summary speaks of one Tauri process and two shipped binaries, and its tier justification of a single-user desktop app. Registering the new program, its commands and anything it reads belongs to arch §Occupied Resources and to this plan's Threat Model and Input Validation at the wrap (the masters are read-only at phase). The tier's premises hold for this chunk only while the scope's Boundaries hold: loopback alone, no new credential, nothing reachable from another host.
- security ↔ scope Boundaries: every widening in the plan carries a founder ratification (per security-plan §Security Anti-Patterns → Input); a new socket, place on disk or credential found necessary at research is a halt, not a plan step.
