Whether the existing arms of `pulse-app/tests/integration_exit_cause_record.rs` already cover the code path the console program ends through is research's question.
- New code sits inside the workspace coverage measure: the thresholds are cumulative, the only standing exclusions are generated code, fixtures, mocks and (temporarily) `xtask/`, and no exclusion is stated for a binary entry point (per test-plan §10 Coverage thresholds; test-plan §10 Cumulative across workspace). ## Patterns to follow
- Direct-binary smoke as the form for running the console program under a check: a fresh `ANDROMEDA_PULSE_DATA_DIR`, the binary launched by path, telemetry seeded over the real receiver, the verdict taken from the run's own log family, shutdown by specific pid with both OTLP ports confirmed released; the evidence shape is chosen before the run (per test-plan §3 Direct-binary smoke variant (accepted alternative form)). `boot` names optional ephemeral-port variables while the readiness verdict accepts only ports 1–65535 (per test-plan §3 `boot` → Command body; test-plan §3 `boot` → Readiness signal); whether a non-default port pair lets this chunk's run stay off the host's shared ports is research's question.
- Live-receiver integration tests: a `tonic` client (gRPC) and `reqwest` (HTTP, protobuf body only) against loopback, per-test `tempfile::TempDir` plus in-memory DuckDB, multi-thread tokio tests, no shared session (per test-plan §5 Driver(s); test-plan §5 Setup / teardown lifecycle; test-plan §5 Cross-module patterns covered; test-plan §7 Seed strategies).
- Narrow a `pulse-app` test run with `-E` / `--filter-expr` under `--workspace`, never `-p`, so the selection matches the build's feature resolution (per test-plan §3 `run` → Narrow a `pulse-app` run with `--filter-expr` / `-E` under `--workspace`, not with `-p`).
- Composition-in-`main` is the plan's named weak spot: the exit hook and signal listener installs, the observer composition and the render-posture placement are each pinned at lib level and unpinned as composed in `main.rs`, with a seam lifting the composition out of `main` as the stated remedy (per test-plan §1 Pending coverage triggers → `exit-hook-main-composition-coverage`, `discovery-observer-wiring-coverage`, `render-posture-main-placement-coverage`). A second entry point composes the same parts again; whether it does so through an assertable seam, and whether a console end makes the owed composition assertion reachable, is research's question.
- Where the console engine replaces the model call with something else, the replacement is a constructor-injected `Arc<dyn Trait>` of a trait the project owns, stubbed by hand or `mockall`; no runtime patching (per test-plan §8 Anti-monkey-patching; test-plan §8 Mocking libraries).

## Anti-patterns to avoid
- A green that read nothing: a clean-log assertion passes vacuously over a run that emitted no record, and an exit code alone is not evidence a leg ran — the smoke must show positive records from the console program, and `check:ingest-progress` reads NEUTRAL, never PASS, where no tick stream exists (per test-plan §3 Direct-binary smoke variant (accepted alternative form); test-plan §3 Per-chunk gate discipline).
- NEVER synchronise by `sleep(N)` or read real time without injection; wait on an explicit signal (per test-plan §11 E2E; test-plan §11 Universal (agent-driven specific)). NEVER `std::env::set_var` mid-test without cleanup — env-driven boot configuration is exercised through injection or a child process (per test-plan §11 Mocking).
- NEVER mock the OTLP receiver under test or DuckDB at integration level, and NEVER let a receiver bind off loopback — a test asserts the rejection (per test-plan §11 Mocking; test-plan §11 Integration; test-plan §11 Project-specific (andromeda-pulse)).

## Contract bindings
- tests ↔ obs — the log family the harness reads is the date-suffixed `agent-latest.jsonl*` under the data dir's `logs/`, JSON lines with the stated members; the five kept records are graded from that family (per test-plan §3 Log format; test-plan §3 `logs` → Command body ↔ obs-plan §3 Log file location). `check:ingest-progress` keys on the tick stream's progress (per test-plan §3 Per-chunk gate discipline ↔ obs-plan §3 / §10). No CI step makes the heartbeat-gap check (per test-plan §9 Pipeline structure → Boot smoke (harness)); the scope leaves it to a later entry.
- tests ↔ arch — the `status` and readiness verdicts derive out-of-process from the registered pid file, that pid's liveness, the log family's mtime and a TCP accept on both resolved OTLP ports; the app's own pid write is canonical (per test-plan §3 PID file → Location, Lifecycle; test-plan §3 `status` → Command body; test-plan §3 `boot` → Readiness signal ↔ architecture §Occupied Resources). The scope's closed list of five records does not name the pid file: whether the console program writes it at this chunk, or stays unreadable by those verbs until the harness entry, is the plan's to state. The TauRPC `health` envelope is reached only through IPC and is not the `status` verb's output (per test-plan §3 Status endpoint shape ↔ architecture §Standard Contracts), so a program with no bridge does not serve it.
- tests ↔ security — cutting the window framework out of engine crates changes the dependency graph the `bans` gate and the supply-chain job read (per test-plan §9 Cargo deny enforcement; test-plan §11 Test Strategy ↔ security-plan §Dependency Security). The loopback-only and path-env-var negative tests bind to any receiver bind and any path variable the console program reads (per test-plan §1 Coverage triggers → `security-vector-coverage: OTLP loopback-only binding`, `security-vector-coverage: Path canonicalization + confinement` ↔ security-plan §Security Anti-Patterns → Input).
- tests ↔ the capability record — a claimed entry names proof files that must exist with their `contains` anchor found, read in every workspace test run; a chunk that moves or renames such a test file re-points the entry in the same chunk or reddens the verb and its pin (per test-plan §9 Capability verification matrix).
- tests ↔ a11y — no a11y surface is added; the a11y job and its tree baseline stand untouched (per test-plan §9 Pipeline structure → A11y suite ↔ a11y-plan §3).
