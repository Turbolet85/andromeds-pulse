## Relevance
relevant — the chunk re-aims registered harness surfaces (the `scripts/agent-run.{sh,ps1}` verbs, the `harness:*` verbs, `ci-gates`, `perf:budget`) at the second product binary, and both ends are arch-registered resources.

## Constraints
- Workspace placement: the chunk's Rust lives in the `xtask` crate and its script half in `scripts/agent-run.{sh,ps1}`; the workspace member names are reserved and no new member is a harness home (per architecture §Occupied Resources → Cargo workspace crate names; architecture §Infrastructure Patterns → CI/CD approach, the "shared CI logic that needs Rust lives in `xtask`" line; architecture §Established Decisions [CI Task Runner]).
- The console program's path is `target/{profile}/andromeda-pulse-engine`, the second `[[bin]]` of the `pulse-app` package, whose `default-run` stays the window app; architecture §Occupied Resources → Process / service identity requires a harness to name a declared `[[bin]]` path and states that `target/{profile}/andromeda-pulse` exists on no host. The same bullet currently records `target/{profile}/pulse-app` as "the one the harness builds and spawns" — a sentence this chunk changes, so it is a wrap amendment target, not a fact to plan around.
- The engine's command line is closed at two words (`run` | `version`), it has no `stop` command and ends by SIGTERM or SIGINT, recorded as `app.exit` with class `signal` and the signal re-raised (per architecture §Occupied Resources → Process / service identity, Console engine binary; architecture §Infrastructure Patterns → Deployment model, "Not built"). A verb that ends the engine therefore uses a signal on a pid it already holds; a third command word is outside the registered surface.
- Both engine programs write `run/andromeda-pulse.pid` at the same path under the same default data dir, so the file holds the pid of whichever started last there, and both default to the same two ports (per architecture §Occupied Resources → Filesystem locations, the `run/andromeda-pulse.pid` subpath; architecture §Infrastructure Patterns → Deployment model). What keeps a verb from reading the other program's pid, log family or exit record is therefore the data dir it is given, not the file names. The plan states the pid readers "are not aimed at the console program although it writes the file" — whether any reader already serves it unchanged is research's question.
- The engine binds the two loopback receivers and nothing else, the bind address is not configurable, and a rejected port variable records the bind as failed with no receiver started (per architecture §Occupied Resources → Network ports). Non-default ports are resolved through `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT` (per architecture §Occupied Resources → Environment variables). The plan states that the absence of a third socket "was not measured from the process's socket list" — C5's socket census and rejected-port arm land on that bullet.
- Every harness verb is a formalized CLI contract registered with its verdict arms, exit codes and output members: `harness:status`, `harness:ready`, `harness:settled`, `harness:boot-series`, `ci-gates`, `perf:budget` and the `scripts/agent-run.{sh,ps1}` pair with its five verbs (per architecture §Occupied Resources → xtask CLI surfaces). A new verb, a new arm, a changed exit code or a changed output member is a registry change the wrap records. `cargo xtask check:ingest-progress` (C3) has no entry of its own in that registry — the plan names only `ingest_progress::evaluate`, through `smoke:gap-resume` — so arch states no contract for its NEUTRAL line. Two registered contracts are window-shaped as written: `harness:settled`'s `settled` arm requires a navigation record for each of four window labels, and `boot` pre-builds and spawns the window binary by name — whether the code offers an engine form of either is research's question.
- Harness-only variables (`ANDROMEDA_PULSE_PIDFILE`, `ANDROMEDA_PULSE_LOGFILE`, `ANDROMEDA_PULSE_DATA_DIR_KEEP`) are registered as NOT consumed by the production binary, and every `ANDROMEDA_PULSE_*` name is reserved at arch level (per architecture §Occupied Resources → Environment variables). A variable that selects which program a verb drives is a new registered name; harness-written files under `logs/` and `run/` are registered one by one (per architecture §Occupied Resources → Filesystem locations), so a new file there is a new registered place.

## Patterns to follow
- The scripts reach a STATUS verdict only through xtask (`status` via `harness:status`, the boot poll via `harness:ready`), while `cleanup` judges liveness independently from pidfile content plus a TCP handshake on the resolved ports and emits one bounded token (per architecture §Occupied Resources → Filesystem locations, the pid-file subpath; architecture §Occupied Resources → xtask CLI surfaces, the `scripts/agent-run.{sh,ps1}` entry).
- `boot` pre-builds under its own exported environment, then spawns the release binary BY PATH under a waiting wrapper that writes the pid to `run/andromeda-pulse.spawn` and the one-line end to `run/andromeda-pulse.exit`; no `cargo run` wrapper (per architecture §Occupied Resources → xtask CLI surfaces, the `scripts/agent-run.{sh,ps1}` entry). With `default-run = "pulse-app"` a bare `cargo run` starts the window app, which is the pattern's reason here (per architecture §Occupied Resources → Process / service identity).
- The verdict shape the registry holds every gate to: one JSON verdict (or fixed lines) of closed labels and counts, exit 0 / 1 / 2 with `cannot-evaluate` distinct from red, never a pass over an absent or empty input, no environment value and no path in the output (per architecture §Occupied Resources → xtask CLI surfaces, the `ci-gates`, `harness:status` and `harness:boot-series` entries).
- Per-boot isolation by data dir: `harness:boot-series` gives each boot its own data dir and removes `ANDROMEDA_PULSE_PIDFILE` / `_LOGFILE` from that boot's environment so both resolve under it (per architecture §Occupied Resources → xtask CLI surfaces, the `harness:boot-series` entry; architecture §Occupied Resources → Environment variables). It is the registered precedent for two programs sharing one harness without sharing a pid file.
- A test of the console program injects over real OTLP and reads state back from the program's own log records on a spawned run, or from the `EngineHandles` of an in-process arm; it mounts no TauRPC router (per architecture §Cross-cutting Patterns → Test-time telemetry injection). The agent-driven style asks for deterministic invocations, machine-parseable outputs and schema-stable contracts (per architecture §Cross-cutting Patterns → Development Style).

## Anti-patterns to avoid
- A verb whose target program is implied rather than named: both programs default to one data dir, one pid file path and one port pair, so a verb that resolves the default can grade whichever program started last (per architecture §Occupied Resources → Filesystem locations; architecture §Infrastructure Patterns → Deployment model).
- A check that can pass while reading nothing, or a status that cannot say "not running": the registry records both as defects already removed (`ci-gates` over an absent family, the earlier in-process health envelope) (per architecture §Occupied Resources → xtask CLI surfaces, the `ci-gates` and `harness:status` entries).
- A harness arm that widens the engine: a third listening socket, a non-loopback bind, an in-process ingest bypass, or a harness variable read by `pulse-app` or `crates` code (per architecture §Occupied Resources → Network ports; architecture §Cross-cutting Patterns → Test-time telemetry injection; architecture §Occupied Resources → Environment variables).

## Contract bindings
- arch ↔ obs: the checks read the self-observation log family under the data dir's `logs/` and the records `app.exit`, `app.panic.fatal` and `app.boot.engine` (per architecture §Occupied Resources → Filesystem locations; architecture §Occupied Resources → Environment variables, the `ANDROMEDA_PULSE_L4_DETERMINISTIC` bullet). The registered `ci-gates` contract says it prints no perf-budget, frame or heartbeat line; a heartbeat-gap or budget arm built here changes that registered contract and binds to obs-plan §10 CI gates.
- arch ↔ tests: the `boot` job's steps and the workflow's Linux-only and release-build-witness shape are pinned by workflow tests (per architecture §Infrastructure Patterns → CI/CD approach); the window's `boot` job stands, and any engine step added beside it binds to those pins and to test-plan §3's harness and §1's pending-coverage row. The lock file's placement for the console program is stated as "not asserted by a test" (per architecture §Occupied Resources → Filesystem locations, the corpus-key lock file) — C5's third reading.
- arch ↔ security: the harness-only variable class and the harness-written state-file class are arch-registered names whose classification is security-plan §Security Anti-Patterns → Input's; a new variable, a new kept file or a new command word is a boundary question for the operator before it is an arch registry entry.
- arch ↔ tests (ps1 lockstep): the registry states the sh and ps1 drivers move in lockstep but for the sh-only exit-witness arm (per architecture §Occupied Resources → xtask CLI surfaces, the `scripts/agent-run.{sh,ps1}` entry) while no CI job runs a non-Linux system (per architecture §Infrastructure Patterns → CI/CD approach); whether the ps1 half follows this chunk is the plan's to state, and the registry sentence is the wrap's to keep true.
