# a11y extract

## Relevance
partial — the chunk adds no UI surface and triggers no WCAG criterion; it changes the five-verb harness that a11y-plan binds its own harness to, and the log family beside which a11y results are written.

## Constraints
- a11y-plan §1 A11y Scope Summary (entity table) classes the OTLP receivers, the storage and the IPC bridge as not-assertable and names no console or terminal surface; the console engine therefore carries no a11y assertion of its own, and no SC, ARIA role, focus order or contrast pair is extracted for it.
- a11y-plan §9 CI Integration (Pipeline integration) requires the a11y suite to reuse tests' `boot` / `run` / `status` / `cleanup` / `logs` harness. A verb re-aimed at the console engine changes what that reuse reaches; the plan's answer to "how the five verbs serve both programs" must leave a window-app path for it until `Window's gates retired`. Whether the a11y job invokes any of the five verbs today is research's question.
- a11y-plan §3 Focus management test harness (Contract binding) requires the focus harness to reuse tests' E2E driver under the five-command discipline; a11y-plan §1 A11y Scope Summary (Focus Management Test Harness) states that `boot` starts the Tauri app. A `boot` that starts a program with no webview does not satisfy that sentence; the masters are read-only at phase, so a verb that changes target lists this sentence for the wrap.
- a11y-plan §1 A11y Scope Summary (Screen Reader Test Pattern, step 1) requires the manual pass to launch the app via `boot`; the same either-or applies (a window-app `boot` stays, or the sentence is a wrap amendment).
- a11y-plan §3 CI integration (Pipeline integration) requires the `a11y` job to stay its own blocking job on `ubuntu-22.04`, with its build, browser and `cargo xtask test:a11y` steps and its two uploads that fail on no file; a `ci.yml` edit made for the engine's checks leaves that job's steps, its gating and its artifact names as they are.
- a11y-plan §3 CI integration (Command) requires a11y result JSON to be emitted to the product's `logs/` directory in obs log format. A check built here over the console engine's log family must select the engine's own files and records, so that an a11y result file in the same directory is neither counted as an engine record nor removed by a verb's cleanup. Whether the a11y files land in a directory an engine check reads is research's question.
- a11y-plan §10 SLO Invariants & A11y Budgets requires the per-PR regression read against the baseline committed in the tree, failing on an absent baseline; the chunk leaves `pulse-app/ui/tests-a11y/` (baseline included) untouched.

## Patterns to follow
- a11y-plan §3 Harness wiring & conventions (Mock layer, Static serving): the a11y specs are specified against a statically served SPA with a mocked IPC layer, not a live engine — keep the a11y chain independent of a booted console engine; do not make it wait on the engine's verbs.
- a11y-plan §3 Harness wiring & conventions (Adding a surface, standing rule): one axe spec per new route or modal in the same chunk — the chunk adds neither, so no spec is owed; if P3 finds a webview change in the modify list, the rule applies.
- a11y-plan §3 Harness wiring & conventions (Adding a surface): the config-named Playwright `--list` probe is the cheap suite-health read after any edit to a shared harness script or to `pulse-app/ui`.
- a11y-plan §9 CI Integration (Per-pipeline-stage a11y artifacts): artifact file names and the upload name are fixed per stage; a new engine-check artifact takes a name outside that set.

## Anti-patterns to avoid
- a11y-plan §11 A11y Anti-Patterns (CI): never turn the a11y gate into a warning or a conditional step while restructuring the workflow — it is fail-fast and gates the merge.
- a11y-plan §11 A11y Anti-Patterns (SLO): never add a retry to an a11y leg and never skip the per-PR regression read, including on a run that only re-aims harness verbs.
- a11y-plan §11 A11y Anti-Patterns (Strategy): never state WCAG conformance without machine output — the chunk's report claims nothing about accessibility for the console engine.

## Contract bindings
- a11y ↔ tests (harness): a11y-plan §9 CI Integration (Pipeline integration) and §3 Focus management test harness (Contract binding) bind to the five-command harness of test-plan §3 — the object this chunk re-aims. Any change in what `boot` starts is a change on both sides of that binding; the a11y-side sentences (a11y-plan §1 Focus Management Test Harness; §1 Screen Reader Test Pattern) are the wrap's to amend.
- a11y ↔ obs (log format): a11y-plan §1 A11y Scope Summary (Structured Violation JSON Schema) binds violation records to the obs structured log format (`target` `a11y::assertion`, level, `fields`), and a11y-plan §9 CI Integration (CI-specific resource attributes) tags them like obs records. The panic, record-count and process-end reads this chunk builds bind to obs-plan §10; they must tell an engine record from an a11y record by file or by target.
- a11y ↔ tests (CI): a11y-plan §9 CI Integration places the a11y job in the same `ci.yml` as the test jobs; a11y-plan §10 SLO Invariants & A11y Budgets holds a joint wall-time budget for the a11y run plus tests E2E.
