## Constraints
- The verb set is closed at five: test-plan §3 `boot` requires that no sixth verb be added, and §3 Per-chunk gate discipline places any further check outside `scripts/agent-run.*` as a `cargo xtask` verb (the `pre-push:linux` precedent). Aiming the harness at `andromeda-pulse-engine`, and the four log checks, must fit inside `boot` / `run` / `status` / `cleanup` / `logs` or be xtask verbs. How two programs share five verbs until Epoch 2 is the plan's to state; test-plan gives no rule for it.
- Each verb keeps its stated verdict contract whichever program it drives: §3 `boot` requires a pre-build outside the timed window, a spawn of the built binary by path, readiness read from the `harness:ready` verdict (the status verdict AND a TCP accept on both resolved OTLP ports), its exit codes and the failure-diagnosis lines; §3 `status` requires the out-of-process verdict JSON with its four verdicts and exit 0 / 1 / 1 / 2; §3 `cleanup` requires one bounded verdict token taken from independent probes only (pid liveness + both resolved ports), exit 0 on `clean` alone, idempotent; §3 `logs` requires the rotated `agent-latest.jsonl*` family across the three precedence-ordered bases, never a bare name. Whether `harness:ready` / `harness:status` / the cleanup probes already work unchanged against the console program is research's question. Note for research: §3 `boot` lists port `0` as an optional env while §3 `boot` → Readiness signal reads a port variable outside 1 to 65535 as `cannot-evaluate` — the chunk's legs need concrete picked ports (not 4317 / 4318, per scope).
- One pid path serves both programs: test-plan §3 PID file → Lifecycle states that both product programs write the same `<data_dir>/run/andromeda-pulse.pid`, so the file holds whichever started last on that data dir, and that `status` / `cleanup` act on whatever pid it holds. Nothing in that contract tells the two programs apart; what forbids a verb from grading or ending the wrong program must be built or stated by this chunk. Whether the spawn / exit recorder files (`run/andromeda-pulse.spawn`, `.exit`) of §3 PID file → Lifecycle are written for an engine boot is research's question.
- The standard gate set is unconditional: test-plan §3 Per-chunk gate discipline requires the full listed set in the plan's `## Test Commands`, with `capability-drift` before the default-features workspace nextest, the `--features mcp-server` `emit_taurpc_bindings` regen as the last cargo-adjacent step, and the bindings close probe named against the chunk base (`8394da4f`, no procedure added); the webview gates drop only when no `pulse-app/ui/**` path is touched; the merge-base probe sits directly before the push entry as an operator leg. `cargo xtask check:ingest-progress` is a member of that set, so a change to its NEUTRAL arm (scope C3) changes what every later chunk's gate block reads.

The CI smoke's middle verb, `harness:settled`, is defined in test-plan §9 Pipeline structure → Boot smoke (harness) over window-navigation records; whether an engine boot can ever satisfy it, and so whether that verb stays the window's, is research's question.

## Patterns to follow
- A pure decision function pinned per arm, with its probe pinned separately against a real loopback listener and a closed port: the `decide_ready` and `classify` shape of test-plan §3 `boot` → Readiness signal and §3 `status` → Exit code semantics. A verdict arm added or re-aimed here takes the same two-layer pin.
- The Spawned-program witness form of test-plan §3 Per-chunk gate discipline: built binary, cleared environment with no display and no session bus, own TempDir data dir, two picked loopback ports through the registered port variables, pid from the child handle, readiness from both ports accepting, records awaited by target under a bound, the log family read only after the end.
- The Process-end witness form of test-plan §3 Per-chunk gate discipline for any claim that a record survives the process ending (the engine's own panic and at-exit records, scope C4): re-exec children, child-ran proof in-arm, the log read after the child has ended, RED at base being the block-shaped absence of the record.
- A graded check with a closed arm set and exit 0 PASS / 1 FAIL / 2 cannot-evaluate, where an empty input is never PASS: the `perf_budget` arm semantics recorded in test-plan §1 Pending coverage triggers → `perf-slo-check-arm-coverage`, the `ci-gates` arms of §9 Pipeline structure → Boot smoke (harness), and the four arms of `check:ingest-progress` in §3 Per-chunk gate discipline. A check whose window cannot reach its own failure threshold refuses up front as INCONCLUSIVE (the `observe_window_supports_verdict` guard of §3 Per-chunk gate discipline) — the direct answer to "a boot of six seconds could never fail them".
- Measure-first legs per test-plan §3 Per-chunk gate discipline → Direct-binary smoke variant: decide whether the RED leg is reject-shaped or block-shaped before choosing its evidence; a block-shaped RED (a heartbeat stall) carries 0 ERROR and 0 panic, so its evidence is absence of progress, never a clean log.

## Anti-patterns to avoid
- NEVER synchronize a harness leg or test with `sleep(N)`, and NEVER grade a time-based check (the heartbeat gap) from the wall clock — wait on an explicit signal and read time from the constructed log's own timestamps (per test-plan §11 Test Anti-Patterns → E2E and → Universal (agent-driven specific)).
- NEVER let a one-time hand-driven leg stand in for a gate: the class test-plan §1 Pending coverage triggers → `harness-cleanup-verdict-and-boot-spawn-shell-coverage` names for the existing verbs. A verdict arm this chunk claims as pinned needs a committed test that reddens when the arm is removed.
- NEVER obtain green by weakening a check — no retry, no soft-fail key, no `#[ignore]` without an issue, no lowered threshold, no arm removed or `--expect-absent`'d (per test-plan §11 Test Anti-Patterns → CI and → Quality; the standing instruction in §3 Per-chunk gate discipline). Scope C1's "retire the sentence" outcome is a wrap amendment with a reason, not a silent drop.
