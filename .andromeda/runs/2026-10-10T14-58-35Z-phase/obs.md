# obs extract

## Relevance
relevant — the chunk builds the checks that grade the console engine's own log (panic, heartbeat gap, process end, budget) and rules on the two readings obs-plan §10 CI gates states as unmet and carried to this entry (scope C1).

## Constraints
- **The heartbeat-gap reading is this chunk's to build or retire, and nothing is retired before the plan rules.** obs-plan §10 CI gates (the heartbeat bullet) states the >45 s stall signal stands, that no CI step makes the gap check, and that its CI enforcement is unmet and carried on the working route; it also fixes the analysis (per tick target, consecutive `timestamp` deltas, a maximum bound, exit 1 over it). The same bullet records why the former CI step could not fail: a log holding one tick per target has no consecutive pair. A check built here therefore has to grade a log that holds at least one consecutive pair per graded target — whether a harness boot of the console engine lives long enough for that against the tick interval obs-plan §3 Heartbeat ticks (Tick interval) fixes is the plan's question; whether `xtask/ci/heartbeat-gap-check.sh` can grade a console log as it stands is research's question.
- **The gap check reads a console log against the ticks the console program emits.** obs-plan §3 Heartbeat ticks (Tick interval) requires the console program to emit the three engine ticks and never the window's two, and says their absence in a log whose `app.boot.engine` record reads `program: console` is by design, not a stall; obs-plan §10 Standard+ invariants (Heartbeat ticks) repeats it. The two sections do not name the same graded set: obs-plan §10 CI gates (the heartbeat bullet) names `ingest.tick` / `buffer.tick` for either program, obs-plan §3 Heartbeat ticks names a third engine tick, `connection.tick`. Which targets the engine check grades is for the plan to state; which targets the existing script reads is research's question.
- **The zero-records reading has two halves, one met for the window's boot log and one unmet.** obs-plan §10 CI gates (the zero-records bullet) requires a log family with no record to fail (exit 1) and an absent log family to be `cannot-evaluate` (exit 2), never a pass; and it states the other reading — a TEST RUN that produces zero spans fails the build — is made by no CI step, stands unmet and is carried on the working route. This chunk's plan rules whether the engine version is built or the sentence retired (scope C1 (b)); a retirement is a master amendment at the wrap, not a phase edit.
- **Zero unlogged panics, graded over the engine's log.** obs-plan §10 Always-required SLO invariant and obs-plan §10 CI gates (the zero-panic bullet) require a build to fail on any `app.panic.fatal` record at level ERROR in the graded log family, and require the failure line to carry the member's file name and line number only, never the record's text or a path. obs-plan §7 Panic hook requires the hook to be installed after subscriber init and the record to go to the file sink only. Whether a panic of the console program itself (not a re-exec child of `engine_boot::init_process`, scope C4) leaves that record in its own log family is research's question.
- **"Exactly one record of how the process ended" holds only for a loggable end.** obs-plan §7 Error classes captured (Process-end cause) requires exactly one `app.exit` record per LOGGABLE process end and lists the ends that are unloggable by construction (SIGKILL and `_exit` among them); obs-plan §6 Log levels mapping (the `app.exit` entry of the warn row) fixes the once-per-process-end rule and the level per exit class; obs-plan §3 Tracing init (Init order) requires the console program to end by SIGTERM or SIGINT with one `app.exit` of class `signal`. A process-end check over a harness-ended engine is therefore conditioned on HOW the verb ends it: whether `cleanup` (or whichever verb ends the engine) sends SIGTERM first, and what it does on escalation, is research's question, and an end the check cannot see must not be read as a pass.
- **The budget arms keep the perf grader's two-state posture, and a required arm is named.** obs-plan §10 CI gates (the perf-budget bullet) requires the gate to fail on an arm over budget, on a graded field that is not a JSON number, and on a `--require`d arm with no sample, and never to pass over empty input; obs-plan §10 Load-profile constraints requires an UNREQUIRED arm over an absent stream to read NEUTRAL and says that tolerance is not a licence for a gate to pass over an absent input. obs-plan §10 Performance budgets (the Buffer memory row) adds that a memory sample of 0 counts but is not informative and that a required arm holding only zeros fails. Which arms have a producer in the console program's log at all (the frame arm is webview-originated per obs-plan §10 Performance budgets, the frame row; whether a console run emits a snapshot sample, and a non-zero memory sample within a harness boot's life, is research's question) decides which arms this chunk can require.
- **The verbs read one file sink, located by the data dir.** obs-plan §3 Log file location (Path, Rotation) fixes the log at `<data_dir>/logs/agent-latest.jsonl` with daily rotation, so a check grades the `agent-latest.jsonl*` family, not one file. obs-plan §1 Telemetry surfaces (the CLI row) requires a console `run` to write its records to that single file sink with none on stderr or stdout, and `version` and a refused command line to write no record and create no data dir — so no verb may take the engine's stdout or stderr as its log, and a refused command line leaves nothing for a check to grade.

## Patterns to follow
- **The log names its own program.** obs-plan §6 Log levels mapping (the `app.boot.engine` entry of the warn row) requires exactly one `app.boot.engine` record per boot of either program, and obs-plan §8 Default-deny posture (the `app.boot.engine` leaf) fixes its three fields as closed labels with `program` one of `window` | `console`. That record is the in-log discriminator available for the directive's "what forbids a verb from quietly grading the wrong program" (scope, inputs#I1 item 2): a check can refuse, or grade against the right tick set, by reading it rather than by trusting which path it was pointed at.
- **Scope a graded log to the run's window.** obs-plan §10 Performance budgets (the frame row) records that `perf:load-profiles` scopes its log to the run's time window (`write_run_window_log`) to avoid false cross-session heartbeat-gap FAILs. A data dir reused across boots holds earlier sessions' ticks in the same daily file; a gap check over the engine's log follows the same scoping, or a fresh data dir per run.
- **Three exits, and an absent input is never a pass.** obs-plan §10 CI gates (the perf-budget bullet) gives the shape `cargo xtask ci-gates` already has: 0 PASS · 1 FAIL · 2 cannot-evaluate when no log family member exists. New engine-side arms take the same three-way shape so "verdict arms pinned by tests" has one closed set to pin.
- **Liveness and progress are two signals.** obs-plan §3 Heartbeat ticks (Stall detection) and obs-plan §10 Standard+ invariants (Heartbeat ticks) require the drain-progress read (`rows_ingested_delta`, `buffer.consumer.stalled`, asserted by `cargo xtask check:ingest-progress`) beside tick presence. Scope C3's reading — that verb exiting 0 with a NEUTRAL line over a log family with no `buffer.tick` — is to be judged against obs-plan §10 Load-profile constraints: NEUTRAL is for an arm no caller requires; a progress read the harness requires over the engine's log fails or reads cannot-evaluate on no tick.
- **A failure line carries coordinates, not content.** obs-plan §10 CI gates (the zero-panic bullet) prints member file name and line number; every new verdict line a check prints over the engine's log follows it (closed labels, counts, file name, line).

## Anti-patterns to avoid
- NEVER define a soft SLO budget — a check that cannot fail on the log it reads is not enforcement (obs-plan §11 SLO); the scope's "shown red on a constructed log before it is trusted green" is this ban applied per arm.
- NEVER skip the zero-unlogged-panics invariant or add a retry-once around a panic read (obs-plan §11 SLO) — a harness verb that re-boots the engine after a failed boot must not hide the first boot's panic record from the check.
- NEVER lose telemetry artifacts, and NEVER rely on colored or unstructured terminal output for CI parsing (obs-plan §11 CI) — if this chunk adds a CI step that boots the console engine, its log family is uploaded under its own artifact name; and no verb or check takes unstructured stderr text as the engine's log (obs-plan §11 Logs).

## Contract bindings
- **obs ↔ tests (harness):** the five verbs and the four checks consume the log format and location obs fixes — obs-plan §3 Log format JSON schema, obs-plan §3 Log file location, obs-plan §6 Required fields (`timestamp`, `level`, `target`, `fields`) — and the heartbeat analysis parses `timestamp` per obs-plan §10 CI gates (the heartbeat bullet). The verbs' own contract (their verdict labels, the pid and exit state files) is test-plan §3's; obs supplies only what the log holds.
- **obs ↔ tests (smoke / heartbeat presence):** obs-plan §3 Heartbeat ticks (Complementarity with the `health` command) keeps tick history and synchronous readiness as two mechanisms. The `health` command it names is a TauRPC procedure; what the `status` verb asks of a console engine that has no webview bridge is tests' and arch's to state, and whether the console program answers any readiness probe today is research's question.
- **obs ↔ tests (CI):** obs-plan §9 Telemetry artifact handling (the Log file row) binds any new upload — a distinct artifact name within the run, `if-no-files-found: error`, `if: always()` — and obs-plan §9 Pipeline integration (the `xtask test` row) records that the console program's log family written by `integration_console_engine` sits under the test's own data dir and is uploaded by no step. The two obs-plan §11 CI bans on a snapshot and a test-job log kept on failure are owned by the route entry `Engine end-to-end gate reachable` per obs-plan §9 Telemetry artifact handling (the Snapshot markdown row), not by this chunk.
- **obs ↔ security (logging):** obs-plan §8 Default-deny posture requires an exact allowlist leaf for any new product log target and no bare `app` key. This chunk's scope is harness-side; if the plan adds a product-emitted record for the harness to read, that leaf and its pin are part of the same change. Verdict lines and kept harness files carry no environment value and no path (security-plan §Security Anti-Patterns → Input holds the classification).
- **obs master amendments:** a reading this chunk retires or builds changes obs-plan §10 CI gates (the zero-records and heartbeat bullets) and, if a CI step is added, obs-plan §9; those edits are the wrap's, the masters being read-only at phase.

## Acceptance criteria contributions
- (obs) Each check built over the console engine's log is pinned red on a constructed log before it is trusted green: a gap over the bound between two consecutive ticks of one graded target exits 1, and a log with fewer than two ticks of a graded target does not read PASS (per obs-plan §10 CI gates, the heartbeat bullet).
- (obs) Over a log whose `app.boot.engine` record reads `program: console`, the absence of `viz.tick` and `plugins.tick` is not graded a stall, and a check aimed at the console engine does not pass over a log whose record reads `program: window` (per obs-plan §3 Heartbeat ticks, Tick interval · obs-plan §8 Default-deny posture, the `app.boot.engine` leaf).
- (obs) An engine ended by the harness with SIGTERM leaves exactly one `app.exit` record of class `signal` in its log family, and the process-end check exits non-zero on zero records and on two; an `app.panic.fatal` record at ERROR in that family fails the panic check with a line naming file and line only (per obs-plan §7 Error classes captured, Process-end cause · obs-plan §10 CI gates, the zero-panic bullet).
- (obs) Every check over the engine's log exits 2 `cannot-evaluate` on an absent `agent-latest.jsonl*` family and never PASS over empty input; a budget arm the chunk requires fails when it holds no sample or only zero memory samples, and an arm with no producer in the console program is not listed as graded (per obs-plan §10 CI gates, the zero-records and perf-budget bullets · obs-plan §10 Performance budgets, the Buffer memory row).
