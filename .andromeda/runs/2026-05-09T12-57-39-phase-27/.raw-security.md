# security extract — phase-27

## Chunk relevance

- **route#30 "Compact widget shell"** — Partially in-domain. This chunk introduces a new Tauri window (native window configuration, always-on-top policy, snap-to-edge persistence) and a custom titlebar. Security concerns apply around: (1) Tauri capability gating for the new window surface, (2) window-level IPC authorization since the compact widget is a distinct webview context, (3) close-to-tray process lifecycle policy (no silent termination that could orphan sockets). No network surfaces introduced; no plugin host; no storage writes; no OTLP path touched. Security footprint is moderate-low but non-trivial due to the new Tauri window + capability scoping questions.

## Constraints

**Tauri capability gating (negative-default)**
Per security plan §Tauri Capability Gating:
- The compact widget shell is a new Tauri webview window. If it shares the `pulse:default` capability, it inherits the full TauRPC procedure surface — confirm this is intentional and documented. If it runs under a separate capability, that capability must be explicitly defined in `pulse-app/capabilities/` with stated rationale.
- Any new TauRPC procedures registered for the widget window (e.g., geometry persistence, always-on-top toggle) require BOTH router registration AND a capability JSON entry. The `xtask capability-drift` check (chunk #27) enforces router ↔ capability sync and must exit 0 after this chunk lands.
- NEVER grant `fs`, `shell`, `dialog`, or `http` Tauri core APIs to the widget window's capability without explicit per-feature rationale.

**Window geometry persistence**
Per security plan §Input Validation / path env vars:
- If snap-to-edge position is persisted to disk (`config.toml` or a per-display sidecar file), the write path MUST be resolved via `strict-path` and confirmed to live under the resolved data dir (`ANDROMEDA_PULSE_DATA_DIR` or platform default). CWE-22 applies even to geometry files.
- If position is stored in DuckDB (unlikely but possible), prepared statements with `?` placeholders are required — no `format!()` SQL.

**Process lifecycle / close-to-tray**
Per security plan (§Tauri Capability Gating + arch Cross-cutting Patterns tray icon policy):
- The close-to-minimize-to-tray policy means the Tokio runtime, OTLP receivers (`:4317`/`:4318`), and broadcast sockets remain live after the widget window is closed. This is expected behavior but must not inadvertently expose a wider network surface — the loopback-only bind constraint (security plan §Loopback-only network surfaces) is unaffected by window close events and must not be re-evaluated or widened at runtime.

**Self-observation discipline**
Per security plan §Self-observation:
- Any `tracing` instrumentation added for window geometry events, always-on-top toggles, or snap-to-edge state changes MUST NOT log user-derived display configuration values that could be sensitive (e.g., precise coordinates could leak multi-monitor topology). Log event names + success/fail only; no coordinate values.

## Patterns to follow

- **Capability-first window design** (per security plan §Tauri Capability Gating): decide capability assignment for the widget window before writing any IPC-invoking frontend code. The xtask drift check will catch router mismatches but cannot catch a window receiving the wrong capability bundle.
- **`strict-path` for geometry persistence** (per security plan §Input Validation §Path env vars): follow the same canonicalize-then-assert-under-data-dir pattern used for plugin paths and snapshot paths.
- **`tracing` event shape** (per security plan §Self-observation + obs plan §3): window lifecycle events use structured `tracing::info!(event = "widget.window.opened", ...)` — no raw coordinate values in the event payload.
- **Existing capability JSON pattern** (per security rules.md 2026-05-03 session addition): `pulse-app/capabilities/*.json` `permissions` array carries `core:default` + plugin-level perms — NOT per-procedure strings. The widget window capability follows this same shape.

---

## Anti-patterns to avoid

- **Do NOT bind a new tray-interop IPC surface to `pulse:default`** (per security plan §Tauri Capability Gating): `pulse:notification` and `pulse:tray` are outbound-emit-only; input-event handlers for tray menu actions or notification callbacks require a separately-named capability. If the compact widget registers tray click → window restore logic, the handler must not reuse `pulse:default` as its inbound trust scope.
- **Do NOT widen `pulse:tray` to include write or execute permissions** (per security plan §Tauri Capability Gating static analysis gap note): `pulse:tray` scope must remain outbound-emit only. The documented static analysis gap (no automated enforcement yet) means author discipline is the only gate — do not silently add permissions.
- **Do NOT log display geometry values** (per security plan §Logging & Redaction): monitor count, display bounds, and window coordinates are environment topology data; logging them verbatim could leak infrastructure information in shared-log scenarios. Log only event names and boolean state changes.
- **Do NOT introduce `0.0.0.0` bind** (per security plan §Loopback-only): the always-on-top and snap-to-edge features have no network component, but any future "display info" IPC that queries OS display APIs must not open a new network listener.
- **Do NOT use `format!()` SQL for geometry storage** if DuckDB is used (per security plan §Input Validation DuckDB anchor).

## Contract bindings

- **TauRPC ↔ capability-drift gate** (security plan §Tauri Capability Gating + xtask chunk #27): any new TauRPC procedures introduced for the widget shell (e.g., `widget.get_position`, `widget.set_always_on_top`) must appear in both the router registration and the capability JSON before `cargo xtask capability-drift` exits 0. This is a hard CI gate binding security constraints to tests/CI domain.
- **Arch §Occupied Resources** (per session-learnings rule 2026-05-09): if new IPC procedures are added under a new router namespace for the widget shell, arch §Occupied Resources must be updated via `/andromeda-scope-arch` BEFORE the chunk merges — the xtask hardcoded list catches (a) router ↔ capability sync but does NOT enforce (b) arch registry sync.
- **`strict-path` ↔ filesystem write** (security plan §Input Validation / path env vars): any geometry persistence write path is a cross-domain binding — the `buffer` crate's path-canonicalization pattern is the reference implementation to follow.

## Acceptance criteria contributions

1. **Capability gating**: `cargo xtask capability-drift` exits 0 after chunk #30 merges — all TauRPC procedures introduced for the compact widget shell appear in `pulse-app/capabilities/*.json` with no extras or missing entries.
2. **Window capability assignment documented**: `pulse-app/capabilities/` JSON for the widget window explicitly lists only the authorized procedure surface; any deviation from `pulse:default` sharing is accompanied by a rationale comment in the capability file.
3. **Geometry persistence path safety**: if window position/geometry is persisted, the write path is canonicalized via `strict-path` and asserted under the resolved data dir; a direct code review check (grep for `std::fs::write` / `tokio::fs::write` / DuckDB geometry storage) confirms no raw path is used.
4. **No coordinate values in logs**: `tracing` events emitted by window open/close/move/resize handlers contain only event names and boolean state (e.g., `always_on_top = true`); no raw coordinate or display-bounds values appear in structured log output.
5. **Loopback bind unchanged**: `cargo grep` / code review confirms no new `TcpListener` or socket bind is introduced by the compact widget shell code path; OTLP receivers remain `127.0.0.1`-only.
6. **Close-to-tray lifecycle**: Tokio runtime and OTLP receivers remain live after widget window close; no `AppHandle::exit()` or `process::exit()` call is triggered by the window close event handler (test: send OTLP span after closing widget window → span appears in buffer).
