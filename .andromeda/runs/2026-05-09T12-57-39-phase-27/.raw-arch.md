## Constraints

- The compact widget shell runs under the `pulse-app` binary crate — window management code belongs in `pulse-app/src/` (or a new submodule therein); no library crate (`ingest`, `buffer`, `viz`, `ui-bridge`, etc.) may depend on the binary crate per arch §Module dependency direction. Module dependency direction: library crates flow toward `pulse-app`; `pulse-app` is the only root.

- Close-window action on the compact widget MUST minimize to tray rather than terminate the process. Process termination requires an explicit Quit menu item or OS-level kill. This is a locked policy per arch §Cross-cutting Patterns §Tray icon policy: "Tray click on the icon focuses or restores the main window; closing the main window minimizes to tray rather than terminating the process."

- Any new TauRPC procedure introduced for widget state (e.g., widget position persistence, always-on-top toggle) MUST have a matching entry in `pulse-app/capabilities/` JSON. Tauri capabilities are negative-default — a missing entry causes silent runtime rejection (per arch §Cross-cutting Patterns §Webview IPC capability policy and §Occupied Resources Tauri IPC routes). The `xtask capability-drift` check enforces this in CI.

- New TauRPC procedure namespaces introduced by this chunk (if any) MUST be registered in arch §Occupied Resources via `/andromeda-scope-arch` BEFORE the chunk merges — the capability-drift gate catches capability JSON gaps but does NOT enforce arch §Occupied Resources sync (per security.md §Session Additions 2026-05-09 entry). If no new procedures are introduced, existing occupied-resources list remains canonical.

- Snap-to-edge per-display memory (persisted widget position) MUST NOT introduce new env vars beyond the reserved set in arch §Occupied Resources §Environment variables. If a new path or config field is required, it must be expressible via `ANDROMEDA_PULSE_DATA_DIR` / `config.toml` pattern; a new `ANDROMEDA_PULSE_*` variable requires arch registry update.

- `ANDROMEDA_PULSE_CONFIG_PATH` / `ANDROMEDA_PULSE_DATA_DIR` govern where `config.toml` lives; widget position persistence stored in `config.toml` under `~/.andromeda-pulse/` (platform-resolved per arch §Occupied Resources §Filesystem locations) inherits the strict-path canonicalization requirement for path env var overrides (per arch §Inherited Defaults and security rules).

## Patterns to follow

- Single Tokio multi-threaded runtime owned by `pulse-app/src/main.rs` — any async work spawned by window management (e.g., persisting position on move) uses the existing runtime; library crates do not spawn their own runtimes (per arch §Inherited Defaults "Single Tokio multi-threaded runtime").

- TauRPC router per owning crate pattern: if widget-specific IPC procedures are introduced (e.g., toggle always-on-top), they belong on the `ui-bridge` crate's router (which owns `get_settings` / `update_settings` / `app_info` / `health` / `ready`) rather than ad-hoc raw `#[tauri::command]` declarations (per arch §Conventions "TauRPC routers, one per module crate"; `ui-bridge` is the established cross-cutting envelope crate).

- Config precedence pattern — env vars > `config.toml` > built-in defaults — applies to widget geometry defaults (quarter-screen sizing, initial snap edge). Any hardcoded defaults must be overridable via `config.toml` fields, not new env vars (per arch §Cross-cutting Patterns §Config management).

- Frameless window with custom titlebar + drag region: arch §Established Decisions §Tauri 2 desktop shell and Epoch 4 ("Tauri webview shell — frameless + custom titlebar with drag region") establish this as the project pattern. Compact widget follows the same frameless+custom-titlebar discipline; do not deviate to OS-native chrome.

## Anti-patterns to avoid

- NEVER introduce a new Tauri core API grant (`fs`, `shell`, `dialog`, `http`) to `pulse:default` for widget persistence — persisted position belongs in `config.toml` read/written by Rust side, not via webview `fs` capability (per arch §Cross-cutting Patterns §Webview IPC capability policy: "Tauri core APIs beyond the enumerated TauRPC surface are not granted to `pulse:default`").

- NEVER bind to or expose a new network port for widget state synchronization — the compact widget shell is a local Tauri window; inter-process state (if any future need arises) uses in-process channels, not new sockets (per arch §Occupied Resources §Network ports: only `:4317` and `:4318` are reserved; no frontend dev server port is reserved at arch level).

- NEVER add a sibling library crate dependency that violates the module DAG — `pulse-app` may depend on any library crate, but no library crate introduced for widget helpers may depend on `pulse-app` or on peer library crates that do not have a declared contract relationship (per arch §Established Decisions §Module Boundaries and §Module dependency direction).
