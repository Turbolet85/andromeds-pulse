# obs extract

## Relevance
Partial — the chunk ships no product telemetry surface (xtask + tests + CI/wrap wiring only), but obs binds at two points: the CI-gate placement / artifact-integrity boundary, and the fact that both pinned artifacts (the `mcp` bindings namespace, the capability grants) carry obs evidence chains the plan mandates.

## Constraints
- Obs tier is Standard, and instrumentation-depth mandates attach to product modules/surfaces (per `.andromeda/obs-plan.md` §1 Obs Scope Summary). An xtask gate is not a listed instrumentable entity, so no span/metric/log coverage obligation attaches to it *unless* it emits through the product's subscriber — whether this chunk emits any `tracing` target at all is research's question.
- If the assertion does emit any new `tracing` target, §8 (Default-deny posture) requires it to have its OWN exact allowlist leaf enumerating every field the emit site emits, with the no-bare-prefix / own-leaf rule per family; without one, fields either redact silently or resolve into a set never meant for them (per `.andromeda/obs-plan.md` §8).
- The new CI step joins a pipeline whose contract is that every job's telemetry artifacts (`logs/agent-latest.jsonl`, failure snapshot, criterion JSON) remain downloadable for agent triage (per `.andromeda/obs-plan.md` §9 CI Integration, Telemetry artifact handling + CI failure → artifact triage workflow). A gate that hard-fails the job must not preempt those uploads.
- The enumerated obs CI gates are log-derived and NEUTRAL-tolerant *by scope*: §10's rule that "any future xtask check script over `agent-latest.jsonl` must be NEUTRAL-tolerant" is scoped to the log stream (per `.andromeda/obs-plan.md` §10 Load-profile constraints). A staged-copy assertion reads git objects, not the log stream, so that tolerance must NOT be generalized to it — a missing/unparseable staged subject is a deterministic FAIL, not a NEUTRAL.
- The `mcp` namespace the gate pins is the TauRPC surface whose boundary observables the plan constrains to result METADATA only (`method`, `result_type`, `result_count`, `feature_flag_enabled`, never `result_content`), with the double-gate state carried as a field on `mcp.feature.gate.check` (per `.andromeda/obs-plan.md` §8 `mcp-server` allowlist + §11 Project-specific). §1 requires the mcp surface be instrumented at its boundary; whether the shipped bindings/procedures already carry those observables — and therefore what a clobbered namespace silently removes from the obs surface — is research's question.
- Path emission discipline is basename-only and is NOT scoped to `*_PATH` / `*_DIR` names or to a single enforcement site (per `.andromeda/obs-plan.md` §1 Vector 6 row, as broadened, and §8 Data classification). If the gate's diagnostics are routed into any persisted log line or CI artifact, they must not carry full canonicalized developer filesystem paths.

## Patterns to follow
- Mutation-discrimination as the proof of a guard, not the guard's existence: the §8 leaf guards are each mutation-checked (leaf deleted / narrowed / renamed → RED, restore → GREEN), and `buffer.consumer.stalled` explicitly carries a fallback discriminator "without which the guard would pass vacuously after the leaf was deleted" (per `.andromeda/obs-plan.md` §8). The chunk's RED/GREEN staged-copy discipline is the same shape.
- Assert the SET, not that the subject resolves: §8's recorded lesson from `triage.cue.tick` is that a resolver-only probe PASSES while a narrowed set silently partly-redacts (per `.andromeda/obs-plan.md` §8). Transfers directly to the expected-grants baseline — pin the grant set, not merely that the capability file parses.
- Field-set equality asserted in BOTH directions, which is what catches a narrowed entry (`triage.incident.persist` guard, per `.andromeda/obs-plan.md` §8). Matches the scope's gap that `capability-widening-check` covers only the widening direction.
- Guards live where they actually run — under `pulse-app/tests/` rather than a src-level `mod tests`, which `[lib] test = false` compiles but never executes (per `.andromeda/obs-plan.md` §8, stated at multiple leaves). Directly relevant to the chunk's "wired so it cannot be skipped" requirement.
- CI diagnostics are for an agent, not a reader: §9's triage workflow assumes machine-parseable failure output an agent downloads and filters (per `.andromeda/obs-plan.md` §9 CI failure → artifact triage workflow).

## Anti-patterns to avoid
- Colour-/diff-only CI verdicts: "NEVER rely on colored terminal output for CI parsing — CI artifacts MUST be structured (JSON) + machine-readable" (per `.andromeda/obs-plan.md` §11 → CI).
- Gate placement that loses telemetry artifacts: "NEVER lose telemetry artifacts (log file + snapshot on failure)" and "NEVER skip snapshot generation on test failure" (per `.andromeda/obs-plan.md` §11 → CI) — an unconditional early-failing step must not sit ahead of the artifact-upload steps.
- Making an artifact-integrity gate silently pass when its subject is absent — the analogue of §11 → SLO's "NEVER define soft SLO budgets (no enforcement)" (per `.andromeda/obs-plan.md` §11 → SLO); absence of the staged subject is a failure, not a skip.

## Contract bindings
- **obs ↔ security/capabilities:** the capability grants this chunk pins are load-bearing for obs evidence. §8's `tray.signpost.shown` leaf records its live wire-proof as "the webview-drive widget-close stage matches the record BY the label field", and §8's `app.boot.window.navigation` leaf exists so a plain boot's window measurement does not read as all-zeroes (per `.andromeda/obs-plan.md` §8 + §6 `warn` row). A left-revoked `core:window:allow-close` therefore silences an obs record the plan mandates, not only a security posture — whether the shipped `pulse-app/capabilities/default.json` still carries that grant is research's question.
- **obs ↔ tests harness:** the JSON log format is verbatim FROM the tests harness contract and obs aligns to tests, not vice versa (per `.andromeda/obs-plan.md` §3 Log format JSON schema); any log line the new gate contributes must satisfy that schema.
- **obs ↔ CI (§9):** the gate's placement in ci.yml/wrap is bound by §9's per-job artifact handling and by §10's enumerated CI gates, which are log-derived and a different class from this artifact gate.
- **obs ↔ mcp surface:** the `mcp` bindings namespace ties to §8's `mcp-server` allowlist and §11's MCP double-gate / no-response-body rules.

## Acceptance criteria contributions
- (obs) The gate's failure verdict is structured and agent-actionable — names the subject file, the missing namespace or grant, and staged-vs-expected — never colour- or diff-only (per `.andromeda/obs-plan.md` §11 → CI).
- (obs) A run in which the gate FAILS still yields the agent-readable CI artifacts (`logs/agent-latest.jsonl`, failure snapshot); the gate's wiring position does not preempt their upload (per `.andromeda/obs-plan.md` §9 CI Integration + §11 → CI).
- (obs) The expected-grants baseline retains every grant the headful obs evidence chain depends on — `core:window:allow-close` for the `tray.signpost.shown` wire proof, and the window grants behind `app.boot.window.navigation` — asserted by set equality in both directions so a narrowed grant set reds (per `.andromeda/obs-plan.md` §8 default-deny leaves).
- (obs) No full canonicalized filesystem path from the gate reaches any persisted log line or CI artifact; repo-relative or basename only (per `.andromeda/obs-plan.md` §1 Vector 6 row + §8 Data classification rules).
