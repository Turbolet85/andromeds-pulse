# arch extract

## Relevance
Relevant — the chunk lands a new dev/CI gate inside the reserved `xtask` workspace member, touching arch's xtask-CLI-surface registry, the webview capability policy, and feature-gate hygiene.

## Constraints
- Code lands in the reserved workspace member `xtask` (arch §Occupied Resources → Cargo workspace crate names; §Established Decisions [CI Task Runner]) — arch requires shared CI logic needing Rust to live in `xtask` so a contributor runs the identical `cargo xtask <verb>` locally (§Infrastructure Patterns → CI/CD approach). The chunk's "no production `.rs`" boundary is consistent with this; the gate must not become a dependency of any library crate or of `pulse-app` (§Cross-cutting Patterns → Module dependency direction: DAG with `pulse-app` as the only root).
- A new/changed xtask verb with a formalized CLI contract is an arch registry item — arch §Occupied Resources → xtask CLI surfaces (dev/CI gates) is the canonical list, and both entries there (`check:npm-supply-chain`, `harness:status`) state the same contract shape: exit-code arms with a named meaning per arm plus one machine-parseable verdict object on stdout. Whether this chunk adds a NEW verb or extends the existing `capability-drift` verb decides whether the wrap owes a new entry or an amendment to an existing surface; either way the contract must be stated, not implicit.
- The subject the assertion guards is arch-canonical, not incidental: `mcp.status` / `mcp.start` / `mcp.stop` are registered as mcp-server-crate procedures reachable "only when `--features mcp-server`" (arch §Occupied Resources → Tauri IPC routes), while §Cross-cutting Patterns → Feature-gate hygiene requires `mcp-server` off by default. The committed bindings artifact must therefore be the feature-bearing superset even though the plan-mandated default-features run cannot regenerate it — that mismatch is the defect class, and the gate must encode it rather than the default build's output.
- The per-procedure gate is the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs`, which `capability-drift` diffs against; `pulse-app/capabilities/` holds NO per-procedure entries because TauRPC dispatches every method through one invoke handler (arch §Cross-cutting Patterns → Webview IPC capability policy). Anything the new assertion pins about procedures must sit beside that pin, not in capability JSON.
- Capability JSON grants are a genuinely different, silently-failing class: core API surfaces (`fs`/`shell`/`dialog`/`http`) and each `core:window:*` permission ARE granted individually and ARE silently rejected at runtime when missing (arch §Cross-cutting Patterns → Webview IPC capability policy). That is the arch basis for the chunk's second deliverable — a left-revoked `core:window:allow-close` produces a silent runtime failure, not a build error.
- The expected-grants baseline belongs xtask-side, NOT in arch §Occupied Resources: arch registers capability IDENTIFIERS only (`pulse:default`, `pulse:tray`, `pulse:notification`, `pulse:updater`, `pulse:plugin-fs`, `pulse:clipboard`; §Occupied Resources → Tauri capability identifiers), and the 2026-06-30 core-perm registry rule keeps individual grants and window labels out of that section. A new capability FILE or a new capability IDENTIFIER would be registrable; a grant-inventory pin is not.
- Any new env var the gate consumes (e.g. a skip/override switch) must be registered in arch §Occupied Resources → Environment variables and classed correctly — the `ANDROMEDA_PULSE_*` prefix is reserved for product-consumed vars, and harness/dev-only names that never cross into the product take the unprefixed `PULSE_*` form (per the registered relay set). Whether the chunk needs any env var at all is a P4 shaping question.

## Patterns to follow
- The two registered xtask gate contracts are the template: named verdict arms + distinct exit codes (0 green / 1 red / 2 cannot-evaluate) + one JSON verdict object on stdout, with a policy/expectation input held as a committed file or an in-code pin (arch §Occupied Resources → xtask CLI surfaces). Following it makes the wrap registration mechanical.
- CI wiring precedent: `check:npm-supply-chain` is wired as a plain `run:` step in ci.yml's `supply-chain` job beside the existing audit/deny verbs (arch §Occupied Resources → xtask CLI surfaces; §Infrastructure Patterns → CI/CD approach lists the ci.yml step chain). The chunk's "unskippable wiring" target should reuse that placement rather than invent a new job shape.
- Agent-driven development style — deterministic harness invocations, machine-parseable outputs, schema-stable contracts, `cargo xtask` task surfaces (arch §Cross-cutting Patterns → Development Style). The gate's output must be parseable by the wrap, not prose-only.
- Existing pins live in `xtask/src/main.rs` (`EXPECTED_PROCEDURES`, per §Cross-cutting Patterns → Webview IPC capability policy); a grants pin is the natural sibling. Whether `capability-drift` currently reads the worktree copy of `pulse-app/ui/src/bindings/index.ts` rather than the index is research's question — arch states only that the gate diffs the bindings-derived procedure set against the pin.

## Anti-patterns to avoid
- Do not add per-procedure entries to `pulse-app/capabilities/*.json`, and do not treat a capability-JSON edit as the gate for a new TauRPC procedure — measured false and corrected in arch (§Cross-cutting Patterns → Webview IPC capability policy).
- Do not let the gate widen the default build graph: feature-gated deps must enter only under their flag, and a dev/CI gate must add no runtime or bundle weight (arch §Cross-cutting Patterns → Feature-gate hygiene; the dev-only-devDeps precedent in §Stack → GUI verification harness).
- Do not introduce an unregistered resource — a new xtask verb, env var, or capability identifier that ships without its arch §Occupied Resources entry is registry drift the wrap must then chase (the pattern behind every "D-arch-resources closure" amendment).

## Contract bindings
- **tests harness ↔ arch**: the plan-mandated default-features workspace run is what rewrites the bindings artifact via `taurpc`'s `export_types()`; the gate's unconditional trigger is defined by that gate set, so arch's xtask-surface contract and the tests plan's gate list must agree on invocation point and exit-code meaning.
- **security ↔ arch**: the capability-grants half rides §Cross-cutting Patterns → Webview IPC capability policy (negative-default, core APIs granted individually and silently rejected when absent); security's `capability-widening-check` covers only the NEVER-widen set and only in the widening direction, so the not-narrowed direction is the uncovered half.
- **obs ↔ arch**: none expected — a dev/CI gate emits to stdout/exit code, not to the product's tracing log (arch §Cross-cutting Patterns → Self-observation discipline governs the product's telemetry only).
