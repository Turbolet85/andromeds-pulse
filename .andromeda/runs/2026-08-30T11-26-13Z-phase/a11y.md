# a11y extract

## Relevance
Partial — the chunk is xtask/CI plumbing with no UI surface, but two a11y-owned contracts touch it: the capability-grant baseline it pins includes the grant backing P5's keyboard escape path, and its "unskippable wiring" lands in the same `ci.yml` that carries the a11y fail-fast gate.

## Constraints
- The compact-widget's `button[aria-label="Close to tray"]` (titlebar ✕, also triggered by Esc) and the widget's Esc-to-tray escape path are required a11y contract under SC 2.1.1 / SC 2.1.2 / SC 2.4.7 (per a11y-plan §1 Critical paths → P5 row, §5 Keyboard Navigation → compact-widget). The chunk's expected-grants pin must therefore encode the OS-window grants for that path in their granted state — a baseline captured from a left-revoked tree would pin the escape path away. Whether `core:window:allow-close` is the specific grant P5's ✕/Esc path depends on is research's question.
- The a11y chain must remain a hard, non-skippable, in-pipeline gate: a11y-plan §11 → CI bans "skip a11y on CI failure (a11y is FAIL-fast gate, not warning)" and "defer a11y to post-merge". Wiring a new unconditional xtask assertion into `ci.yml` / the `capability-drift` invocation path must not make the a11y step conditional, warn-only, or ordered such that it is bypassed.
- a11y assertions are required to run in the SAME `ci.yml` pipeline as tests' E2E, reusing the 5-command `boot`/`run`/`status`/`cleanup`/`logs` driver (per a11y-plan §3 → CI integration, §9 → Pipeline integration). Any restructuring of the shared CI/wrap invocation path must preserve that integration point.
- The per-PR regression gate compares current violation tuples against `baselines/a11y-violations-summary.json`, where a clean full-chain pass = 0 violation tuples (per a11y-plan §3 → Harness wiring & conventions → Regression baseline; §10 → "Zero new violations per PR"). A chunk that changes no UI requires that baseline to stay byte-unchanged; re-baselining is permitted only off a clean full-chain pass.
- The a11y Playwright suite mocks the TauRPC surface as `TauRPC__<router.path>` via `tests-a11y/helpers/mock-tauri.ts`, and any new TauRPC procedure a fixture consumes must be mocked in the same chunk (per a11y-plan §3 → Harness wiring & conventions → Adding a surface). Since this chunk asserts the bindings artifact rather than changing procedures, no mock change should be owed — a needed mock edit would be evidence the procedure inventory actually drifted.
- No new route or modal is added, so the standing "every new route/modal adds one axe spec in the same chunk" rule (a11y-plan §3 → Adding a surface) does not attach; it attaches immediately if the chunk's "no webview code changes expected" boundary is broken.

## Patterns to follow
- Verify a claimed absence against the component that actually OWNS the surface, not a sibling — a11y's own retraction (amendments 2026-08-23-a11y-verification) is the precedent for this chunk's "hypotheses to re-verify at P3" discipline.
- Tuple-diff pinning: the a11y regression gate's shape is an expected-set vs actual-set comparison on `{surface, wcag_criterion, selector, severity}` with any tuple absent from baseline = FAIL, and a `regression-set.json` audit artifact emitted alongside (per a11y-plan §3 → Per-PR regression detection). The EXPECTED_PROCEDURES / expected-grants pin can follow the same shape.
- Guard against a vacuously-passing gate: a11y's suite was silently dead for sessions behind a list-time import failure while the regression gate "guarded nothing" (amendments 2026-06-10), which is why §3 mandates the cheap `npx playwright test --list` health check and POPULATED fixtures. The staged read must FAIL when its subject is missing/unreadable, never pass on nothing.
- Machine-runnable over remembered: a11y-plan's agent-driven invariant (preamble + §11 Universal) requires every rule to have a machine-verifiable path and bans human-only review without machine output — the chunk's "a check the wrap RUNS beats a discipline the author must REMEMBER" ruling is the same principle applied to a sibling artifact.

## Anti-patterns to avoid
- Never soften or make conditional an a11y CI gate while re-wiring the pipeline — a11y-plan §11 → CI ("NEVER skip a11y on CI failure"; "NEVER defer a11y to post-merge"; no soft gates).
- Never leave an invariant that backs a WCAG-covered path (the P5 escape-path grants) as prose discipline only — a11y-plan §11 → Universal + §10 hard gates require machine-verifiable enforcement, not remembered discipline.
- Never apply a retry-once / tolerate-flake policy to a gate whose subject is an a11y-relevant artifact — a11y-plan §11 → SLO ("NEVER use retry-once policy... masks real failures"; quarantine-investigate-fix instead).

## Contract bindings
- **a11y ↔ security/capabilities:** `pulse-app/capabilities/*.json` grants are the substrate for P5's keyboard escape path (a11y-plan §1 P5 + §5); the expected-grants baseline this chunk shapes is shared with security's NEVER-widen caps and `capability-widening-check`. a11y's stake is grant PRESENCE for the ✕/Esc path, not the widening direction.
- **a11y ↔ tests/CI harness:** a11y-plan §3 → Focus management test harness states "Contract binding: reuses tests' E2E driver per upstream-context Section 5 Test Harness (5-command discipline)"; §9 places the a11y chain in the same `ci.yml`. Placement of the new gate is tests/CI-owned; a11y's requirement is only that the chain stays in-pipeline and fail-fast.
- **a11y ↔ obs:** the structured violation JSON schema (§3, `target: "a11y::assertion"`, `fields.wcag_criterion` / `violation_type` / `severity` / `surface` / `selector` / `remediation` / `tool` / `tool_result_id`) is NOT produced by this chunk's gate — bindings/grant-drift output must not be written into `a11y-violations-summary.json` or the a11y JSONL artifacts.

## Acceptance criteria contributions
- (a11y) The expected-grants baseline pins the OS-window grant(s) backing P5's `Close to tray` ✕ / Esc escape path in their GRANTED state, and a staged revocation of that grant reds the gate (per a11y-plan §1 Critical paths → P5 row + §5 compact-widget focus order). Which grant that is — `core:window:allow-close` or another — is research's question.
- (a11y) After the new wiring, the a11y chain (`npm run test:a11y` / `cargo xtask test:a11y`) still runs in `ci.yml` as a hard merge-blocking gate, not downgraded to a warning nor made conditional on the new assertion (per a11y-plan §9 CI Integration + §11 → CI).
- (a11y) `baselines/a11y-violations-summary.json` is byte-unchanged by this chunk — no UI surface is added, and a re-baseline is permitted only off a clean full-chain pass (per a11y-plan §3 → Regression baseline + §10 → Zero new violations per PR).
- (a11y) No new axe spec and no `tests-a11y/helpers/mock-tauri.ts` mock addition is owed; if either becomes necessary it is evidence the chunk crossed its no-webview-change boundary and §3's standing rule attaches in-chunk (per a11y-plan §3 → Adding a surface).
