# security extract

## Relevance
Relevant — the chunk hardens the exact mechanism `security-plan` names as the *only* per-procedure enforcement at the TauRPC trust boundary, and adds the revocation-direction check on Tauri capability grants.

## Constraints
- The drift gate must be strengthened, never relaxed: `security-plan` §API Security (TauRPC capability authorization) makes router registration + the `EXPECTED_PROCEDURES` pin in `xtask/src/main.rs` the two enforcement pieces for a new procedure, and §Security Anti-Patterns → API requires `xtask capability-drift` to fail CI on an unpinned procedure. A staged-copy assertion must be strictly ADDITIVE — trimming the pin or loosening the drift gate to stop clobber noise is banned. (Whether the `mcp` namespace can legitimately be absent from a default-features regen, given the compile-time `mcp-server` feature gate per §API Security MCP feature double-gate, is research's question.)
- The capability-grants baseline must pin BOTH directions: §Security Anti-Patterns → API bans granting a Tauri CORE API (`fs`/`shell`/`dialog`/`http`) or any `core:window:*` permission without an explicit per-feature addition with stated rationale, and §API Security records those are *silently rejected at runtime when missing* — so a left-revoked grant is a dead-affordance bug the plan requires a mechanism to catch, not only a widened grant.
- Never-widen capabilities must be encoded in that baseline, not assumed: §Security Anti-Patterns → API separately bans exposing `pulse:updater` to webview JS, widening `pulse:notification`/`pulse:tray` beyond the outbound emit subset, and widening `pulse:plugin-fs` beyond the host's read of the resolved plugin dir.
- Any new fail condition owes a roster entry: `security-plan` §Dependency Security → CI integration enumerates the complete build-failure roster (`cargo audit` / `cargo deny check` / clippy / `cargo xtask check:npm-supply-chain` exit 1|2) and §Bootstrap phases `dep-security-ci-gate` is the named home of the capability-drift check. Neither currently names a staged-bindings or capability-grants arm — whether one already exists is research's question; if the gate ships, both enumerations must stay complete.
- Any new or edited CI wiring inherits the supply-chain rules: §Security Anti-Patterns → Secrets requires every third-party Action be `<owner>/<repo>@<40-char-SHA> # vX.Y.Z` (never `@v2`/floating tag) and workflow-level `permissions: { contents: read }` with per-job elevation only on publish; §Bootstrap phases `dep-security-ci-gate` restates the SHA convention plus `harden-runner` as first step of every job.
- Path inputs stay first-party constants unless justified: §Security Anti-Patterns → Input scopes the harness/xtask-only tool-locator carve-out (trim + `is_file()` + clean skip) to vars the shipped binary never reads; a product-consumed `ANDROMEDA_PULSE_*_PATH`/`*_DIR` var requires canonicalize-and-confine. This bites only if the assertion parameterizes its subject paths.
- The folded PREREQ is a security-plan obligation, not bookkeeping: §Dependency Security → CI integration (Standing deferral — `cargo audit` unrunnable) makes session 61 the owed FULL-FORM interval point — probe run, exit read DIRECTLY (never through a pipe), basis re-verified, overlap re-enumerated FROM SCRATCH by DISTINCT `RUSTSEC-` id, never a silent skip; the deferral ends the first time `cargo audit` loads.

## Patterns to follow
- The `EXPECTED_PROCEDURES` pin as the baseline model (`security-plan` §API Security, TauRPC capability authorization) — the scope's [inferred] "expected-grants baseline on the EXPECTED_PROCEDURES model" matches the plan's own precedent for a committed-artifact pin that fails CI on mismatch.
- The npm-gate shape as the most recent xtask-gate-in-`ci.yml` precedent (§Dependency Security → CI integration): a plain `run:` step in the supply-chain job behind SHA-pinned setup actions, with an explicit tri-state exit contract — 0 green / 1 findings-red / **2 cannot-evaluate as its own arm, never a findings pass**. A staged read has an obvious cannot-evaluate arm (no index, shallow or detached checkout, subject absent) that must not green under this precedent.
- Prune-not-keep on baseline entries (§Dependency Security → Duplicate-version carve-outs; npm-channel bullet) — a stale pin hides the real drift's return, the same reasoning that pruned the `windows-core`/`windows-result`/`windows-strings` skips.
- Basename-only path emission if the gate logs resolved absolute paths (§Security Anti-Patterns → Logging, categorical since 2026-08-30). The rule is scoped to *product-consumed* paths, so repo-relative first-party subjects in an xtask message sit outside it — it applies only if the gate resolves and prints an absolute path.

## Anti-patterns to avoid
- NEVER relax, trim, or feature-condition `EXPECTED_PROCEDURES` / the `capability-drift` gate to make the clobber stop reporting (`security-plan` §Security Anti-Patterns → API — the ban is on an unpinned procedure, and §API Security names this gate the per-procedure enforcement).
- NEVER leave a `core:window:*` or core-API permission revoked or added without an explicit per-feature capability entry with stated rationale (§Security Anti-Patterns → API, second clause — retargeted and operator-guardrailed per the 2026-08-21 amendment below).
- NEVER add CI wiring that references a third-party Action by floating tag, or that raises workflow-level `permissions` to `contents: write` (§Security Anti-Patterns → Secrets).

## Acceptance criteria contributions
- A staged (git-index) read of `pulse-app/ui/src/bindings/index.ts` — never the worktree — fails the build when the committed bindings do not carry the pinned procedure set, with `EXPECTED_PROCEDURES` and `xtask capability-drift` left unrelaxed (per security-plan §API Security, TauRPC capability authorization + §Security Anti-Patterns → API).
- The capability assertion reds on a left-REVOKED `core:window:*` / core-API grant in `pulse-app/capabilities/*.json` *and* on an added grant to `pulse:updater` / `pulse:notification` / `pulse:tray` / `pulse:plugin-fs`, proven by RED/GREEN mutation (per security-plan §Security Anti-Patterns → API + §API Security, Updater capability isolation / Plugin host capability sandbox).
- Any new or edited CI wiring pins every third-party Action by 40-char commit SHA with a version comment and keeps workflow-level `permissions: { contents: read }`; the new fail condition appears in the build-failure roster (per security-plan §Security Anti-Patterns → Secrets + §Dependency Security → CI integration + §Bootstrap phases `dep-security-ci-gate`).
- The session-61 FULL-FORM `cargo audit` probe is discharged and recorded in the chunk report: exit read directly (never through a pipe), basis re-verified, `cargo deny check advisories` re-enumerated from scratch by DISTINCT `RUSTSEC-` id with a visible disposition on any new finding, no "Nth consecutive" ordinal, never a silent skip (per security-plan §Dependency Security → CI integration, Standing deferral).
