# obs extract

## Relevance
relevant — every candidate form puts a new stdio hop in front of the door's tool path. That hop has its own stdout discipline, sink and process identity, and the door's call records must still be what a stdio call leaves. Which of these the code already meets for a given form is research's question. The form is P4's to choose.

## Constraints
- A tool call that reaches the door must leave the door's own record, whatever carrier sits in front of it. Per obs-plan §4 Scenario P3 (Two carriers), that is one `door.call` {`method`, `tool`, `outcome`, `write`, `result_type`, `result_count`, `answer_bytes`, `duration_ms`} for each answered request, written before the answer line, INFO for `ok` and WARN otherwise, never ERROR. A refused connection or line leaves `door.refused` {`reason`, `peer`} at WARN. A stdio path does not move these field sets or levels. Whether a given form leaves exactly one `door.call` per agent call (rather than none or two) is research's question.
- The door's three records are EXACT allowlist leaves, each carrying every field its emit site emits. Per obs-plan §8 PII Scrubbing (the `app.boot.door` / `door.call` / `door.refused` leaves), no bare `door` key and no bare `app` key may exist. Any new log target a bridge adds (for example a bridge-start or bridge-end record) needs its own exact leaf whose field set is closed labels, bools and numbers only. Without one, the target redacts whole.
- No argument, answer, socket path, account id, error text or the `ANDROMEDA_PULSE_DOOR_RESOLVE` value may reach any record. That holds for the door (per obs-plan §8 PII Scrubbing, the door leaves) and for any process the stdio hop adds (per obs-plan §1 Obs Scope Summary, the `logging-sensitive` row: tool response bodies are never logged, only `result_type` and `result_count`).
- The sink of the new stdio component is not stated by the plan. Per obs-plan §3 Logging stack, the app has a single JSON file sink with no stderr `tracing` layer. Only the stdio sidecar is stated to force stderr JSON, because stdout is reserved for JSON-RPC 2.0 framing. A bridge inside the engine binary or a separate bridge program must say which sink it writes and where. If that sink is a log family of its own, the plan must say so (per obs-plan §3 Log file location, `<data_dir>/logs/agent-latest.jsonl`).
- Process identity is a default subscriber field with a single source of truth. Per obs-plan §3 Service identity, the sidecar carries its own `service.name` = `"andromeda-pulse-mcp"`, distinct per process. A new bridge process, or a new command word of `andromeda-pulse-engine`, states its identity there and never hardcodes it (per obs-plan §11 Universal (agent-driven specific)).
- What a console command line emits is enumerated per command. Per obs-plan §4 Span / Trace Coverage (the CLI / main binary row), `run` writes the boot and door records, while `version` and a refused command line emit nothing. A new command word changes that enumeration and must state its own records.
- The sidecar's observability stays as it is. Per obs-plan §4 Scenario P3, its `mcp.tools.call.request` → `mcp.feature.gate.check` → per-tool read → `mcp.tools.call.response` chain is unchanged. Per obs-plan §11 Project-specific (andromeda-pulse), the double-gate ban stands for the sidecar alone, and the door's admission is read from `app.boot.door` and `door.refused`. The door's surface and records are PROVISIONAL (obs-plan §4 Scenario P3) and are built on without widening.

## Patterns to follow
- The door's emit-site helpers (`door::emit_boot`, `door::emit_call`, `door::emit_refused`, per obs-plan §4 Span / Trace Coverage, the door row): one helper per record. A record a bridge adds follows the same shape.
- The exact-leaf allowlist test with set equality in both directions against a capture of the emit site, plus a `for_target("{prefix}").is_none()` check. The door's form is `pulse-app/tests/unit_observability_allowlist_door.rs` (per obs-plan §8 PII Scrubbing), placed under `pulse-app/tests/` per the `[lib] test = false` rule.
- The negative reading for response bodies: plant a marker in OTLP content, have the owner's `query_logs` return it, and assert it stands 0 times in the engine's log family (`pulse-app/tests/integration_door.rs`, per obs-plan §1 Obs Scope Summary, the `logging-sensitive` row). The stdio path is read the same way, over every log family the path writes.
- The sidecar's stdio discipline (per obs-plan §3 Logging stack): stdout carries only JSON-RPC 2.0 framing, and any `tracing` output goes elsewhere as JSON with no TTY pretty-print.

## Anti-patterns to avoid
- NEVER write to stdout from any subsystem of a process that speaks JSON-RPC over stdio. A stray `println!` / `dbg!` / library write corrupts the protocol and silently disconnects the client. The plan states this ban for the `andromeda-pulse-mcp` sidecar (per obs-plan §11 Universal (agent-driven specific)). Its mechanism applies to any stdio carrier this chunk adds.
- NEVER log MCP tool response bodies or arguments in any log file (per obs-plan §11 Project-specific (andromeda-pulse)), and never use unstructured stderr text instead of JSON per line (per obs-plan §11 Logs).
- NEVER use an unbounded or high-cardinality field (account id, socket path, request content) on a new record, and never register a bare prefix key that widens sibling targets (per obs-plan §11 Metrics; per obs-plan §8 PII Scrubbing on the no-bare-key rule).

## Contract bindings
- obs ↔ security: the door's three exact leaves are the logging half of security-plan §Security Anti-Patterns → Logging (the door's NO-SCRUB boundaries). They are part of the door's single PROVISIONAL item (obs-plan §4 Scenario P3; security-plan §Threat Model Summary → Attack surface). A new stdio carrier's records join that discipline.
- obs ↔ tests: obs-plan §9 CI Integration (the `xtask test` row) enumerates the test binaries that start the console program, each under a cleared environment. A new test binary or arm that drives the stdio way is a new member of that row. `cargo xtask check:engine-log` grades the engine's log family (obs-plan §9 CI Integration, the triage workflow), so new records must not break it. Whether they would is research's question.
- obs ↔ architecture: the `service.name` default field (obs-plan §3 Service identity) is tied to arch's process-identity convention. The door's form is a contract Conductor reads (architecture §Standard Contracts → Engine door). It is read, not changed.

## Acceptance criteria contributions
- An agent's `tools/call` sent over the stdio way leaves exactly one `door.call` record in the console engine's log, with every field rendered (never `<redacted>`) and written before the answer line. A refused connection leaves `door.refused` with `peer` a closed label (per obs-plan §4 Scenario P3).
- A marker planted in OTLP content and returned by `query_logs` over the stdio way stands 0 times in the engine's log family and 0 times in any log or stderr the stdio component writes (per obs-plan §1 Obs Scope Summary, the `logging-sensitive` row).
- The stdio component's stdout carries only JSON-RPC 2.0 lines, and no `tracing` record ever appears there (per obs-plan §11 Universal (agent-driven specific)).
- Any new log target the chunk adds has an exact allowlist leaf, a set-equality test in both directions against its emit site, and no bare prefix key. If the chunk adds no target, the plan says so (per obs-plan §8 PII Scrubbing).
