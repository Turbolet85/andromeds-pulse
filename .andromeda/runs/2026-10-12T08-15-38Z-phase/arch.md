# arch extract

## Relevance
relevant — the chunk adds a stdio way to the door, so it touches the engine-door contract, the MCP wire style, the binary/process identity set, and the runtime topology. It must not move the door's own surface.

## Constraints
- The door's form is a contract an outside reader (Conductor) depends on. Connect, admission, call, methods, the one write, answer, bounds, errors and records stay as stated, so a stdio way reaches the door as a door client and changes nothing of it. Whether a candidate form needs any door change is research's question (per architecture §Standard Contracts → Engine door).
- The door is one Unix-domain socket and no TCP port. The engine's listeners are the two OTLP receivers plus the door, so a form that adds any listener, port or socket is a separate widening. The door is PROVISIONAL as a single item, and every statement of it rests on that one sentence, so whatever this chunk builds on the door inherits the PROVISIONAL status (per architecture §Occupied Resources → Network ports).
- The wire stays MCP-spec JSON-RPC 2.0 using the same `jsonrpc.rs` envelope functions, never a custom envelope. The envelope has two transports today: stdio for the sidecar and line-delimited JSON over `run/door/sock` for the door. A stdio relay must carry that envelope unchanged in both directions, including the door's three fixed-message codes `-32001` · `-32002` · `-32003` (per architecture §Established Decisions [API Style — MCP Server Surface 3]).
- The "MCP stdio surface" is recorded as the `andromeda-pulse-mcp` sidecar's (`initialize`, `tools/list`, `tools/call`, `notifications/*`), and the door surface has four methods (`initialize` · `tools/list` · `tools/call` · `ping`). A stdio form that reaches the door therefore exposes the door's method set, not the sidecar's, and P5 must say what each one reaches (per architecture §Occupied Resources → MCP stdio surface; §Occupied Resources → Engine door surface).
- The product binaries are exactly three (`pulse-app`, `andromeda-pulse-engine`, `andromeda-pulse-mcp`), and `andromeda-pulse-engine` has a closed two-word command line (`run` | `version`, anything else exits 2 and creates nothing). Each P4 form changes something different in this record: a new engine command word extends the closed grammar; a separate bridge program adds a fourth product binary, or a dev or example binary whose class must be stated; the agent dialling the socket itself adds no binary (per architecture §Occupied Resources → Process / service identity; §Project Intent → Product type).
- The runtime topology on the user's machine is enumerated: one engine program, plus the optional sidecar under its double gate. A bridge process the agent starts is a new item in that topology, so P4 must name it (per architecture §Infrastructure Patterns → Deployment model).
- "With no sidecar" binds to the build graph. `rmcp` and the sidecar binary enter only under `--features mcp-server`. The `mcp-server` crate itself is linked in every build, so a way that uses its `jsonrpc.rs` layer is not built on the sidecar, but one that needs the feature or `rmcp` is (per architecture §Cross-cutting Patterns → Feature-gate hygiene).

## Patterns to follow
- The console program's entry: `pulse-app/src/bin/andromeda-pulse-engine.rs` hands its arguments to `pulse_app::console::main`. Any new engine command word belongs in `console.rs`'s grammar. Engine parts are never wired outside `engine_boot`, which `pulse-app/tests/unit_engine_boot_seam.rs` pins (per architecture §Design Philosophy → Single-process modular monolith; §Infrastructure Patterns → Project directory structure).
- The door client locates the socket from the resolved data dir: `ANDROMEDA_PULSE_DATA_DIR` overrides the root, with an identical subpath layout under it, so the socket is `{data dir}/run/door/sock`. The path is canonicalized and confined to the data dir, and must be shorter than 108 bytes. Reuse that resolution and add no new path variable (per architecture §Occupied Resources → Filesystem locations; §Occupied Resources → Environment variables (reserved at arch level)).
- Read-back through the door is an accepted test path. `pulse-app/tests/integration_door.rs` injects over real OTLP and reads back with a `query_logs` call on `run/door/sock`. A stdio-way test follows the same shape: OTLP in, a tool call out through the new way, with no test-mode bypass (per architecture §Cross-cutting Patterns → Test-time telemetry injection).
- New code lives in `pulse-app` (the binary crate, which owns `door.rs` and `console.rs`) or in `mcp-server` (the envelope layer). Dependencies flow toward `pulse-app`, and no library crate gains a sibling edge its contract does not need (per architecture §Cross-cutting Patterns → Module dependency direction).

## Anti-patterns to avoid
- No custom envelope or re-framing that alters request or answer content between stdio and the socket. In particular, never cut an answer: the door refuses an over-bound answer with `-32003` rather than truncating it (per architecture §Established Decisions [API Style — MCP Server Surface 3]; §Standard Contracts → Engine door).
- Never route the new way through the sidecar's parts or gates: the `--features mcp-server` binary, `rmcp`, `run/workspace-key`, or the corpus open. The door uses the engine's own handles and opens no database and no corpus (per architecture §Standard Contracts → Engine door; §Established Decisions [MCP Server Surface]).
- No new listener, TCP port or network surface of any kind, and no widening of `run/door/` or `run/door/sock` (per architecture §Occupied Resources → Network ports; §Occupied Resources → Filesystem locations).

## Contract bindings
- arch ↔ security: the door's owner-only admission (a kernel-read peer account equal to the engine's own) holds for whatever process the agent starts. A relay runs as the agent's account, so admission is unchanged only when that account is the engine's owner. Whether a relay weakens any of the three layers is security's to rule (per architecture §Standard Contracts → Engine door, Admission).
- arch ↔ obs: every door call writes `door.call` and every refusal writes `door.refused`, closed labels only. A stdio way reaches these records through the door and must add no record carrying arguments, answers or paths. Any new record's field set is obs-plan's (per architecture §Standard Contracts → Engine door, Records).
- arch ↔ Conductor (external reader): the door's form is read by Conductor. The scope forbids changing what a Conductor run sees, and this chunk only reads §Standard Contracts → Engine door (per architecture §Standard Contracts → Engine door).
- arch ↔ tests: a new product binary or command word changes the record of product binaries and the console grammar. The CI and harness rows that enumerate binaries or command words are test-plan's to update (per architecture §Occupied Resources → Process / service identity; §Infrastructure Patterns → CI/CD approach).
