## Patterns to follow
- The door's three-depth test layout — a seated door over a stand-in `Tools` in process (`pulse-app/tests/unit_door.rs`), the door seated by `engine_boot::start` (`integration_engine_boot.rs`), and a spawned `andromeda-pulse-engine run` reached by a `tokio::net::UnixStream` client (`pulse-app/tests/integration_door.rs`, ports via `test_support::ports`) — is the home a stdio-way arm sits beside (per test-plan §1 Test Scope Summary, Surfaces under test, the console engine door row).
- A stdio peer is driven by `tokio::process::Command` with stdin/stdout piped, JSON-RPC 2.0 frames written to stdin and line-delimited JSON parsed from stdout, the verdict from the exit code plus the parsed `result`/`error` (per test-plan §5 Integration Test Strategy, Driver(s); per test-plan §8 Mocking & Stubbing Discipline, Process mocking row).
- `pulse-app` unit-shaped probes live as `pulse-app/tests/*.rs` files reaching internals through `pub` + `#[doc(hidden)]`; a `#[test]` in `pulse-app/src/` reds the ratchet (`main.rs` exempt) (per test-plan §2 Test Strategy, Test directory + naming conventions).
- Where the form adds anything run by the real shell or an `xtask` verb, the `xtask/tests/` sibling of the spawned form (real `bash`, cleared environment, claimed ports) is the shape (per test-plan §3 Per-chunk gate discipline, Spawned-program witness form).

## Anti-patterns to avoid
- NEVER synchronise with `sleep(N)` — wait on an explicit signal (ports accepting, a record awaited under a bound) (per test-plan §11 Test Anti-Patterns, E2E).
- NEVER over-mock at integration level: the "answered from the running engine's own stores" claim is not shown by a stand-in `Tools` alone; mock only traits the project owns (per test-plan §11 Test Anti-Patterns, Test Strategy; per test-plan §11 Test Anti-Patterns, Mocking).
- NEVER commit an `#[ignore]` test without an open issue, nor add a retry-once for a flake (per test-plan §11 Test Anti-Patterns, Quality).

- tests ↔ security: the `lint-test` step `Door refuses another account` (one nextest selection, no soft-fail, its three-layer sentence required) holds the door's PROVISIONAL owner-only reading; a stdio way that reaches the door must leave that step's selection and verdict unchanged (per test-plan §9 CI Integration, Build failure conditions).
- tests ↔ harness: the 5-command `agent-run` discipline admits no sixth verb — a form that adds a harness command word is said so at P4 rather than added in passing (per test-plan §3 5-command implementation; per test-plan §3 Per-chunk gate discipline).
- tests ↔ arch: the door's wire form is architecture §Standard Contracts → Engine door, read and not changed; the test asserts it as is (per test-plan §1 Test Scope Summary, the console engine door row).
