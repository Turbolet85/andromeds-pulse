# obs extract

## Relevance
relevant — the chunk's subject is a process end the product's own exit record did not capture, and what the CI boot job's telemetry artifact must keep to name it; obs-plan owns the exit record (§6, §7), its allowlist leaf (§8), the sink and its drain (§3 Tracing init, §3 Logging stack) and the boot job's artifact (§9).

## Constraints
- obs-plan §7 (Error classes captured → Process-end cause) requires every LOGGABLE process end to write exactly one `app.exit` record before the process goes, and lists the ends that are unloggable by construction (SIGKILL, `_exit`, failures before the sink exists; stderr / `boot.log` at most). A run that reads "an exit, code 1, no `app.exit`" is therefore, by §7's own partition, either an end from the unloggable list or an end where the mandate did not hold; which of the two the red run was is research's question, and the plan cannot answer it.
- obs-plan §7 (Error classes captured → Process-end cause) states that a main-thread panic keeps `app.panic.fatal` and is followed by one `outside_event_loop` record "by construction — recorded, not measured". The chunk may not lean on that sentence as a measurement; whether the code already holds it is research's question.
- obs-plan §6 (Log levels mapping → warn row, `app.exit`) requires the record EXACTLY ONCE per process end behind a process-wide once-flag, with the emitter then dropping the only `WorkerGuard`; the `outside_event_loop` path is the `atexit` hook handing off to a `pulse-exit-reporter` thread with a bounded wait (≤ 2 s), carrying `exit_code` 0 with `exit_code_known: false`. Any instrument the chunk adds on the exit path must leave the once-flag, the bounded wait and the single drain as §6 states them, and must not produce a second record.
- obs-plan §8 (Default-deny posture → `app.exit` leaf) fixes the record at four closed fields and bans a path, a panic payload, an error `Display` and any native message on it. A caller name, a stack or a trace therefore cannot be added to `app.exit`; if the chunk records the ending call through the product's own log, §8 requires a NEW exact leaf of its own (no bare `app` key is registered, so an unregistered `app.*` target redacts every field), bounded fields only, guarded by a field-set-equality test under `pulse-app/tests/`.
- obs-plan §3 Tracing init (Init order) makes `WorkerGuard::drop` the non-blocking file sink's only drain, reached only by exit paths that can log. A product record written at or just before an end that bypasses those paths is not guaranteed to reach the file; whether the red run's last records were lost undrained or never written is research's question (the scope's "log ending 0.072 s after `ui-bridge.ready`" is a reading of the file, not of the emit sites).
- obs-plan §3 Logging stack (Sink) gives the app a SINGLE sink, the JSON file, with no stderr `tracing` layer; obs-plan §7 (Panic hook) adds that stderr carries only what the chained prior hook prints. So `boot.log` (the app's stdout + stderr) is the only surface for an end the sink cannot see, and anything an out-of-process instrument records is harness evidence beside the log, not a `tracing` record.
- obs-plan §9 (Telemetry artifact handling → Log file row) describes the Linux `boot` job's artifact `logs-boot-${{ runner.os }}` as five named files, uploaded `if: always()`, `run/` not uploaded, 14-day retention. Every file the chunk makes the job keep changes that row (amended at the wrap, not here) and must be uploaded under the same `if: always()` so a red run keeps it.
- obs-plan §9 (CI-specific default fields) records that `git.commit.sha` on a `pull_request` run is the merge commit, not the pushed tip. An "equal source" reading counted from the log's own fields must compare that merge sha, which moves when either tip moves.

## Patterns to follow
- The "otherwise indistinguishable" rationale of obs-plan §6 (Log levels mapping → warn row): a record is added once per boot or once per end, off any hot path, exactly where two states would otherwise read the same (`app.exit`, `app.boot.window.navigation`, `app.boot.render.posture`). A new signal that names who ended the app follows that shape: bounded, once, closed labels.
- The exact-leaf registration pattern of obs-plan §8 (Default-deny posture → `app.exit` and `app.boot.window.navigation` leaves): every field the emit site emits is in the leaf, the set is asserted by equality in both directions with a no-bare-prefix discriminator, and the guard lives under `pulse-app/tests/` because a src-level test never runs.
- The harness-written-file precedent of obs-plan §9 (Telemetry artifact handling → Log file row): `harness-settled.json` (closed labels, a pid, a count, the bounded exit record) and `xvfb.log` (a third-party tool's own error output) ride the boot artifact without being product-read. An instrument's output file joins the artifact in that class.
- The "a run names its cause from its own log" pattern of obs-plan §10 (Performance budgets → WebGPU canvas frame row): the cause line is derived from records the same run's log holds, printed as a closed set of readings including "no record in this log", never inferred from another run.
- The agent triage path of obs-plan §9 (CI failure → artifact triage workflow): the artifact is downloaded with `gh run download` and read by `jq` / grep; what the chunk keeps must be readable that way.

## Anti-patterns to avoid
- obs-plan §11 (SLO) bans retry-once policies and soft, unenforced budgets; obs-plan §10 (Always-required SLO invariant) repeats "NO retry-once" for panic handling. A boot retried until green, or a red read as tolerated, is the banned shape (it agrees with the scope's own boundary).
- obs-plan §11 (Logs) bans unstructured stderr text as a log surface and multi-line stack traces without one-line serialization (SpanTrace instead of a raw backtrace). A stack captured at the exit must not enter `agent-latest.jsonl` as multi-line text; in the product log it is one JSON line of bounded fields.
- obs-plan §11 (Logs) and obs-plan §8 (Default-deny posture) ban full paths, native messages and raw values in records; obs-plan §11 (CI) bans losing telemetry artifacts and relying on non-machine-readable output. An exit-time instrument whose output carries environment values, full data-dir paths or a watched service's telemetry breaches them, and the scope's own boundary halts on such an artifact.

## Contract bindings
- obs ↔ tests harness: obs-plan §9 (Telemetry artifact handling) and obs-plan §10 (CI gates) bind to the boot job's steps (`boot` → `cargo xtask harness:settled` → `status` → `cleanup`, then `ci-gates`). §10 (Performance budgets → WebGPU canvas frame row) records that a run whose smoke step fails SKIPS `ci-gates`, so on a red run no obs gate line is printed; whatever names the cause on a red run must be kept by a step that runs `if: always()`, not by `ci-gates`.
- obs ↔ tests harness, the several-boots question: obs-plan §3 Log file location puts every boot that shares a data dir into one daily-rolled `agent-latest.jsonl` family, and obs-plan §10 (CI gates) grades that family whole (the `app.panic.fatal` grep, the > 45 s heartbeat-gap check per tick target, `perf:budget` with no arm required). Several boots in one job therefore either share a log family that those readers see as one run, or need one data dir per boot; §10 (Performance budgets → WebGPU canvas frame row) names `write_run_window_log` as the existing answer to cross-session heartbeat-gap false FAILs in `perf:load-profiles`. Whether `ci-gates` over a multi-boot family reads differently is research's question.
- obs ↔ tests harness, heartbeat: obs-plan §3 Heartbeat ticks sets a 15 s tick and keeps tick presence separate from the synchronous `health` probe the harness polls at boot. A boot that lives a few seconds may hold no tick, so tick absence is not a witness of this early end.
- obs ↔ security: obs-plan §8 (Default-deny posture) and obs-plan §1 (Telemetry triggers → logging-sensitive rows, Vectors 2, 3 and 6) bind any new exit-path record or kept file to basename-only paths and sanitized error text; the security plan owns whether a new kept file is routine harness evidence or a boundary widening.
- obs ↔ arch: obs-plan §9 (CI-specific default fields) cites architecture §Infrastructure Patterns → CI/CD approach for the merge-commit reading of `git.commit.sha`.

## Acceptance criteria contributions
- A run in which the app ends by itself keeps, in the uploaded boot artifact, a machine-readable record that names the ending call and its caller; the step that keeps it runs `if: always()` and does not depend on `ci-gates` (per obs-plan §9 Telemetry artifact handling; obs-plan §10 Performance budgets → WebGPU canvas frame row).
- The named cause is classified against the loggable / unloggable partition: the report states which listed end it was, or that the `app.exit` mandate did not hold on that path, from the run's own artifact (per obs-plan §7 Error classes captured → Process-end cause).
- `app.exit` still renders exactly its four fields, exactly once per loggable end, with no path and no native text; any new product record on the exit path resolves to its own exact allowlist leaf with a field-set-equality guard, and reads with 0 `<redacted>` fields and 0 full paths at the wire (per obs-plan §6 Log levels mapping → warn row; obs-plan §8 Default-deny posture → `app.exit` leaf).
- No retry, soft-fail key or timing pad is present in the boot job, and the consecutive-green count is stated against the merge sha each run's log carries (per obs-plan §11 SLO; obs-plan §9 CI-specific default fields).
