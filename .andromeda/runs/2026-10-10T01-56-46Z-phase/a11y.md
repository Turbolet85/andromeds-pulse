## Constraints
- a11y-plan §3 CI integration (Pipeline integration) requires the a11y assertions to run as their own blocking `a11y` job in the same `ci.yml`, parallel with the test jobs; the chunk's edits to the boot job's steps leave that job's steps, their order and its blocking status as they are.
- a11y-plan §3 CI integration (Pipeline integration; Per-PR regression detection) requires the a11y artifacts under fixed names, one of them downloaded by name for the per-PR comparison; whatever the boot job newly uploads takes a name disjoint from those and renames none of them.
- a11y-plan §9 CI Integration (Pipeline integration) requires the a11y suite to reuse the tests' `boot` / `run` / `status` / `cleanup` / `logs` harness, while a11y-plan §3 Harness wiring & conventions (Mock layer; Static serving) requires the audits to run against a statically served SPA with mocked IPC. Whether the `a11y` job in the code actually passes through the `boot` wrapper the chunk may instrument is research's question; if it does, the instrument is on the a11y gate's path and its cost and failure modes are read there too.
- a11y-plan §10 SLO Invariants & A11y Budgets (Always-required SLO invariant) requires no retry-once policy on the a11y gate; if the chunk's design holds several boots in one run, nothing of that repetition reaches the `a11y` job as a retry.
- a11y-plan §10 SLO Invariants & A11y Budgets (Performance budget per a11y CI run) requires the a11y run plus tests E2E inside its stated wall-time budget; an instrument's timing cost counts against it only where the instrument lands in a step the a11y job shares — which steps are shared is research's question.

## Patterns to follow
- A job keeps its own evidence on a red run: a11y-plan §3 CI integration (Pipeline integration) requires the a11y artifacts uploaded unconditionally under per-job names — the shape a boot-job record that must survive a self-ended app follows.
- A flake is investigated, never smoothed: a11y-plan §11 A11y Anti-Patterns (SLO) requires quarantine, investigate, then fix or delete — the a11y domain's own form of the chunk's no-retry / no-soft-fail / no-timing-pad boundary.
- Records carry the run and the commit: a11y-plan §9 CI Integration (CI-specific resource attributes) requires a11y emissions tagged with the run id and the commit sha for cross-correlation — the precedent for a kept record that must be attributable to one run of one source.

## Anti-patterns to avoid
- NEVER make the a11y gate soft or skip it on a CI failure (a11y-plan §11 A11y Anti-Patterns → CI): no workflow-level `continue-on-error`, soft-fail key or conditional introduced for the boot job may reach the `a11y` job.
- NEVER a retry-once policy on the a11y gate (a11y-plan §11 A11y Anti-Patterns → SLO): a multi-boot or re-run construct stays inside the boot job.
