# security extract

## Relevance
partial — the chunk touches no receiver, bridge, plugin or MCP surface; the security domain binds it at four places: the boot job's workflow shape, what a new instrument's output may carry into a kept artifact, any record the product binary gains at its end, and any environment input an instrument is switched by.

## Constraints
- The boot job's edit adds no workflow-level `contents: write`, no job-level elevation outside a publish step, and no reference to a signing or release secret outside the `production-release` environment (per security-plan §Security Anti-Patterns → Secrets). The scope's own halt on "a new workflow trigger, a new permission, a secret" sits on top of this; the plan requires the read-only workflow posture independently of it.
- Any third-party action the instrument brings is referenced by 40-char commit SHA with its version comment, and `step-security/harden-runner` stays the first step of the boot job; a tool fetched at run time passes that job's egress policy (per security-plan §Bootstrap phases, `dep-security-ci-gate`). Whether the chosen instrument is already on the runner image or has to be installed is research's question (inputs#I1 item 3a names "the runner image as it is").
- Every file the boot job newly keeps is a member of the harness-only class and needs its content class stated the way the two registered members are: either closed labels with a pinned field set carrying no environment value and no path, or third-party text that passes no scrubber, read whole before it is trusted and held under a standing stop (per security-plan §Security Anti-Patterns → Input). That section records the earlier two classifications as the pc overseer's own, not the founder's word; a new member's classification needs its author named the same way.
- No kept artifact may carry a secret-class value: the corpus encryption key and `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` are never logged and never exported (per security-plan §Secret Management, "What counts as secret"). An instrument whose output holds process memory, the process environment or argv (a core, a syscall trace, a debugger dump) can carry either. Whether the booted app in the CI job holds a corpus key or reads a passphrase is research's question; the answer decides whether such an instrument is admissible at all.
- If the product binary gains a record of its own end, it sits behind its own exact allowlist leaf with closed labels and bounded scalars only; a panic payload, an error `Display`, a native message and every path stay excluded, as the `app.exit` boundary requires (per security-plan §Security Anti-Patterns → Logging). A record that "names the ending call and its caller" by symbol, frame or source location is wider than any leaf that section admits; whether the instrument needs a product-side record at all is research's question.
- No logging, and no code that needs thread-locals, runs from a C `atexit` handler or a signal handler on the thread ending the process; a signal end is re-raised as the same signal, never replaced by an exit code (per security-plan §Security Anti-Patterns → Universal). An instrument hooked into the exit path is bound by this.
- An environment variable the PRODUCT binary reads to switch an instrument on is a new product-consumed input: bounded parse, value never logged, and a path-shaped one canonicalized and confined; one read by xtask or the wrapper alone follows the harness-only readers' shape — presence or closed labels, no value printed or written (per security-plan §Input Validation, the CLI / env var inputs row). The product's write of the process environment happens only before any thread exists, and the webview's child processes inherit it — an instrument installed at the head of `main()` must not break that ordering (same row; per security-plan §Threat Model Summary, CLI input vector).

## Patterns to follow
- The bounded-grammar read of a harness state file: one line, at most 48 printable ASCII characters, anything else read as no record — the shape for any new exit or child-status record the wrapper writes (per security-plan §Security Anti-Patterns → Input, boot-recorder state files).
- The verdict document with a pinned member set carrying no environment value and no path, and system variables read by presence into closed labels (`reachable` · `gone` · `unset` · `unknown`) — the shape for extending what the settle verdict says (per security-plan §Input Validation, the CLI / env var inputs row, `xtask::harness_ready`).
- The deliberate NO-SCRUB record: one record per event, its own exact allowlist leaf, no bare parent key, pinned in both directions by an allowlist test — the shape if the product must say more about its end (per security-plan §Security Anti-Patterns → Logging, the `app.exit` paragraph).
- The exit hand-off: the record is handed to a thread spawned at install with a bounded wait, and the signal path records from a runtime task (per security-plan §Security Anti-Patterns → Universal).
- A CI step as a plain named `run:` line with no `with:`, no token and no `continue-on-error`, its shape pinned by a workflow test (per security-plan §Dependency Security → CI integration, the `cargo audit` step).

## Anti-patterns to avoid
- NEVER reference a third-party action by a floating tag, and NEVER raise `permissions:` at the workflow level to make an instrument work (per security-plan §Security Anti-Patterns → Secrets).
- NEVER write a full product-consumed filesystem path, raw OTLP attribute values or a secret-class value into the product's log to explain an end — basename plus the variable's name only (per security-plan §Logging & Monitoring, "What NEVER to log").
- NEVER bind the receivers to a non-loopback interface when a local boot moves them off 4317 / 4318; the two port variables change the port, never the `127.0.0.1` bind (per security-plan §Security Anti-Patterns → API).

## Contract bindings
- security ↔ obs: a new product log record needs its allowlist leaf and event row in the obs plan; the `app.exit` boundary's stated blind set — the ends it cannot see, `_exit` and pre-sink failures among them (per security-plan §Security Anti-Patterns → Logging) — is the security-side statement of what the freight's "no app.exit record" can mean. Whether this run's end lies inside that set is research's question, not an inference.
- security ↔ tests: the settle verdict's pinned field set, the workflow-shape pins and the soft-fail ban's gate list live in the test plan's harness; a new kept file or step extends those pins (per security-plan §Security Anti-Patterns → Input; §Dependency Security → CI integration).
- security ↔ arch: a new environment variable, kept file or product-written location is registered in arch §Occupied Resources beside the security-plan rows; the scope moves those corrections to the wrap, so the plan carries them as owed amendments (per security-plan §Threat Model Summary, CLI input vector).
- security ↔ dependencies: a new Cargo dependency for the instrument passes the Rust supply-chain gates; a runner-installed system tool sits in no scanned channel the plan names (per security-plan §Dependency Security → CI integration).
