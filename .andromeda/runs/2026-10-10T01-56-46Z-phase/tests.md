# tests extract

## Relevance
relevant — the chunk works inside the CI `boot` job and the harness `boot` cycle, both specified by test-plan §9 and §3; test tier Standard (per test-plan §1 Test Scope Summary).

## Constraints
- The boot job's smoke step is specified as one ordered cycle inside ONE `xvfb-run` (`boot` → `harness:settled` → `status` → `cleanup`, cleanup running whatever the two before it returned, the data dir's `logs/` uploaded `if: always()`, no soft-fail key on the step), and test-plan §9 names four workflow tests in `pulse-app/tests/quality_gate_workflow.rs` as its pins. Any step this chunk adds, moves or wraps must leave those pins holding or re-point them in the same change. Whether the four pins exist as described, and which of them a given step edit trips, is research's question (per test-plan §9 Pipeline structure → Boot smoke (harness)).
- The boot job is GATING: the step passes only when the whole cycle exits 0, and a `harness:settled` verdict of `ended`, `not-settled` or `cannot-evaluate` is a build failure. An instrument added to keep the ending call may not change which of those verdicts fail the job (per test-plan §9 Build failure conditions).
- A flake gets a root-cause investigation, never a retry budget; the chunk's boundary "no retry, no soft-fail key, no timing pad" is the plan's own standing rule, not only the operator's (per test-plan §10 Zero-flakiness budget).
- The chunk plan's `## Test Commands` must carry the whole standard gate set unconditionally, in the stated order (`capability-drift` before the default-features workspace nextest, the `--features mcp-server` bindings regen as the last cargo-adjacent step), closing with the bindings probe named against the chunk base `8936f976`, never HEAD, for a chunk that adds no TauRPC procedure. The webview gates join only if `pulse-app/ui/**` is touched (per test-plan §3 Per-chunk gate discipline).
- If the plan touches a boot/setup path (`pulse-app/src/main.rs`, `crates/ui-bridge/src/`, `pulse-app/src/observability.rs`, `tauri.conf.json`, `pulse-app/capabilities/*.json`), a runtime smoke gate is additionally required. Whether naming or closing the cause reaches one of those paths is the plan's to state once research names the instrument (per test-plan §3 Per-chunk gate discipline → Boot-smoke gate (conditional)).
- The harness has five verbs and admits no sixth: a new instrument is an `xtask` verb or lives inside the existing `boot` cycle, and anything the readiness poll shells must be pre-built BEFORE the timed readiness window, whose default the plan requires to stay honest. An instrument that wraps or attaches to the app is measured against that window on a green boot before it is trusted (per test-plan §3 `boot` → Timeout; the no-sixth-verb rule per test-plan §3 Per-chunk gate discipline).
- Every test layer must end in a machine-parseable verdict with no human in the loop: "who ended the app" has to be readable by an agent from what the job keeps (an exit code, a JSON verdict, a log record), not from a person reading a trace (per test-plan §2 Agent-runnable invariants).

## Patterns to follow
- Verdict verbs: one pretty-JSON object on stdout with a closed verdict set, exit 0 / 1 / 2 with 2 reserved for `cannot-evaluate`, the decision lifted into a pure fn pinned per arm and its probe parsers pinned too. A new or widened verdict (for example a member added to the settle verdict) follows the same shape (per test-plan §3 `status` → Exit code semantics; the `harness:ready` instance per test-plan §3 `boot` → Readiness signal).
- Harness-written state lives beside the pidfile under the data dir's `run/` and `logs/`, is written by the harness and never by the product binary, and the exit record is read through a bounded one-line grammar. A new kept record follows that placement and bound (per test-plan §3 PID file → Lifecycle).
- Local boots use the direct-binary form: a fresh `ANDROMEDA_PULSE_DATA_DIR` per leg, receivers moved through `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT`, shutdown by the specific pid, both resolved ports confirmed released. Decide the defect's shape BEFORE choosing evidence: the self-end the freight describes carries no `app.panic.fatal`, so a clean-log assertion over such a run can pass vacuously and the evidence of record is the settle verdict and what is absent (per test-plan §3 Per-chunk gate discipline → Direct-binary smoke variant).
- If the chunk adds a product-side record meant to survive the process ending, its witness is cross-process: re-exec children each on their own TempDir data dir, the parent reading the child's log family only after the child has ended, child-ran proof in-arm (per test-plan §3 Per-chunk gate discipline → Process-end witness form (integration tier)).
- New tests sit where the plan puts them: `xtask` pins colocated in `xtask/src/`, anything for `pulse-app` as `pulse-app/tests/*.rs` (no `#[test]` under `pulse-app/src/` outside `main.rs`), and a narrowed `pulse-app` run goes through `--workspace -E '…'`, not `-p` (per test-plan §2 Test directory + naming conventions; the narrowing rule per test-plan §3 `run`).

## Anti-patterns to avoid
- NEVER add a retry-once policy for a flaky test or job, and NEVER ignore a flake: a retry on the boot step, or a re-run counted as a reading, is this ban (per test-plan §11 Test Anti-Patterns → Quality; §11 → CI).
- NEVER use `sleep(N)` for synchronization: a wait placed in the boot cycle to make the self-end rarer is the timing pad the scope forbids; wait on an explicit signal (per test-plan §11 Test Anti-Patterns → E2E).
- NEVER reference a third-party GitHub Action by floating tag: an instrument brought in as an action is pinned by 40-char SHA, and a plain `run:` step is the plan's shown preference where one suffices (per test-plan §11 Test Anti-Patterns → CI).

## Contract bindings
- tests ↔ obs: the settle verdict reads obs-owned records (`app.boot.window.navigation` per window, the `app.exit` record) out of the `agent-latest.jsonl*` family, so a new record that names the ending call is an obs schema/allowlist matter first and a harness read second (test-plan §9 Pipeline structure → Boot smoke (harness); the family resolution per test-plan §3 `logs` → Command body, which binds to obs-plan §3 Log file location).
- tests ↔ obs: the boot job's `ci-gates` frame line is printed only on a run whose smoke step passes; a step reorder or a new `if: always()` step changes what a red run prints, which obs-plan §10's frame row describes (test-plan §1 Coverage triggers → performance-budget: WebGPU canvas throughput).
- tests ↔ security: the uploaded `logs-boot-Linux` artifact's file set and the harness-only state files are classified in security-plan §Security Anti-Patterns → Input; anything new the job keeps is that boundary's to classify, and the scope halts for the founder where it could carry more than the app's own log and exit record (test-plan §9 Pipeline structure → Boot smoke (harness) names the kept files).
- tests ↔ architecture: the job's cache key and the cache readings live in architecture §Infrastructure Patterns → CI/CD approach (pointed to by test-plan §9 Pipeline structure → Release build); several boots in one job, the second research question, share that job's one build and cache.
- tests ↔ route: the plan itself records the cause of the app ending shortly after ready on a runner as not named and held by the route's P-129 record (test-plan §3 `boot` → Readiness signal); this chunk is that record's work, and the plan text is corrected at the wrap, not here.
- tests, own open trigger: the sh `boot` waiting wrapper, its failure-diagnosis branch and the live `harness:settled` arms are listed as shipped with no committed shell-level test; harness arms this chunk adds without one widen that trigger, to be said at the wrap (test-plan §1 Pending coverage triggers → `harness-cleanup-verdict-and-boot-spawn-shell-coverage`).
