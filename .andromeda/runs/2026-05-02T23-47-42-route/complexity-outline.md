## Project signals (from arch + input)

- **Product type:** Cross-platform desktop application (Tauri 2 + Rust). Single-process modular monolith, single-machine, single-user — not a web app, not a CLI, not a microservice fleet (arch §Project Intent).
- **Surfaces in current scope:** 3 surfaces — (1) OTLP receiver (`:4317` gRPC + `:4318` HTTP), (2) TauRPC IPC bridge to webview (hosting compact widget + full dashboard UI modes + tray icon + OS notifications), (3) MCP server stdio (feature-gated, default off). Deferred surfaces excluded: persistent storage, distributed tracing, alerting, saved searches, dashboard customization, plugin marketplace UI.
- **Crates / modules:** 10 workspace members — 8 library crates (`ingest`, `buffer`, `viz`, `ui-bridge`, `snapshot`, `workspace-detector`, `plugins`, `mcp-server`) + `pulse-app` binary + `xtask` task-runner (arch §Occupied Resources Cargo workspace crate names).
- **Capabilities (Established Decisions count):** ~25 architectural decisions covering platform / language / receivers / database / channels / plugin runtime / WebGPU / IPC bridge / MCP / OTLP wire format / error handling / validation / module boundaries / snapshot defaults / plugin distribution / retention / self-observation / deployment / signing / distribution channels (arch §Established Decisions).
- **Standard Contracts:** 7 contracts — Tauri IPC introspection envelope (`app_info` / `health` / `ready`), OTLP receiver spec-conformance, MCP spec-conformance, paginated list envelope, real-time push contract via Tauri `Channel` API with binary Arrow IPC payloads (`pulse://stream/spans|metrics|logs|snapshot-progress|plugin-events`).
- **Cross-cutting concerns:** 8 patterns — config layering (env > config.toml > defaults), self-observation discipline (NEVER dial own OTLP ports — stdout/file exporter only), feature-gate hygiene (`mcp-server` / `otap-ingest` off by default), cross-bridge serde::Serialize requirement, OS notification policy, tray icon policy, webview IPC capability policy (`pulse:default` add-only), module dependency direction (DAG rooted at `pulse-app`), test-time telemetry injection (no test-mode bypass — tests speak OTLP via real receiver ports).
- **Security tier (cross-input):** Standard (estimated — local OSS desktop, no auth, no PII, no regulated industry; plugin sandbox managed by WASM Component Model capability scoping; code signing via Azure Key Vault + Apple Developer ID is distribution rigor not Hardened tier). Will be confirmed in Phase 1 specialist plan reads.
- **Project signals from input.md:** Strong multi-surface intent (compact widget as primary surface NEW in v2, plus full dashboard, plus optional MCP server); HIGH brand sophistication ceiling (explicit references to Apple Watch Activity rings, Cleanshot X, Things 3, Linear, tldraw — portfolio-quality polish bar; GPU-accelerated visualization is a core differentiator); explicit must-work scenarios (10k+ spans/sec ingest, smooth animation at high cardinality, token-efficient curated snapshot ≤25k tokens, self-observation edge case — app IS the observer); 6 deferred features carried for future scopes; agent-driven Development Style.
- **Existing Scopes:** None — new project. Scopes will be added via /andromeda-scope-arch (arch §Existing Scopes).

## Calibration outcome

- **Hierarchy depth:** 3 levels (epoch → sub-block → chunk in dense epochs; epoch → chunk in lighter epochs).
- **Reasoning:** Medium-complex project per heuristic — 3 surfaces × 10 crates × ~25 Established Decisions falls in the mid-band where 3 levels accommodate the visualization + plugin + snapshot domains without forcing artificial depth. Most epochs decompose to depth 2 (sub-blocks) for balanced sibling weight; lighter epochs (Ingest pipeline, Polish & ship) sit at depth 1.

- **Concerns:**
  - Cargo workspace + `rust-toolchain.toml` (rustc 1.84+) + 10 crate stubs (arch §Established Decisions [Module Boundaries]; arch §Occupied Resources Cargo workspace crate names)
  - Tauri 2 scaffold + bundle identifier `com.andromeda.pulse` + 5 capability JSON files (`pulse:default` / `pulse:tray` / `pulse:notification` / `pulse:updater` / `pulse:plugin-fs`) (arch §Occupied Resources Tauri capability identifiers)

### Epoch 2 — Ingest pipeline

- **Scope:** OTLP receivers (gRPC `:4317` + HTTP `:4318`) decoding into the in-process mpsc channel that feeds the buffer; per-protocol error responses; local-bind-only enforcement; port override env vars.
- **Drilldown depth:** 1
- **Estimated chunks:** 4
- **Concerns:**
  - tonic gRPC receiver on `:4317` implementing `TraceService` / `MetricsService` / `LogsService` from `opentelemetry-proto` (arch §Standard Contracts OTLP receiver spec-conformance; arch §Stack tonic 0.14.x)
  - axum HTTP receiver on `:4318` exposing `POST /v1/traces` / `POST /v1/metrics` / `POST /v1/logs` (protobuf + JSON; arch §Stack axum 0.8.x on hyper 1.x + tower)

  - Per-protocol error responses (HTTP `Status` proto / tonic::Status codes per arch §Conventions error response schema OTLP receiver) + local-bind on `127.0.0.1` only + `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `ANDROMEDA_PULSE_OTLP_HTTP_PORT` overrides

### Epoch 3 — Storage & query

- **Scope:** DuckDB in-memory ring buffer (5–10 min retention, configurable) with Arrow zero-copy appender; periodic retention enforcement; query routers feeding the visualization layer; broadcast fan-out for live UI subscribers.
- **Drilldown depth:** 2
- **Estimated chunks:** 4 (2 sub-blocks × 2 chunks each)
- **Concerns:**
  - Sub-block 3a Buffer (DuckDB connection bootstrap + 7 reserved tables (`spans` / `span_events` / `span_links` / `metrics_points` / `log_records` / `resources` / `instrumentation_scopes`) with `TIMESTAMPTZ` + sibling `ts_unix_nano BIGINT` + OTLP-native composite primary keys; Arrow appender wire via `Appender::append_record_batch()` / `stream_arrow()`; periodic `DELETE WHERE ts < now() - INTERVAL` retention task driven by `ANDROMEDA_PULSE_RETENTION_SECONDS`)

## Notes for Phase 1 synthesis

- **Foundation's `xtask` agent-run harness chunk feeds every downstream feature epoch.** Sequence the harness chunk early in Foundation so all later epochs can drive their work via `cargo xtask test` / `cargo xtask <task>`.
- **OTel SDK self-observation init (Foundation 1c) precedes every observability instrumentation point.** Per-crate `tracing`/metrics emissions (in Ingest / Storage / Snapshot / Plugin / MCP epochs) all depend on the SDK being wired with the stdout-NOT-OTLP exporter discipline (arch §Established Decisions [Self-Observation]; obs plan §Bootstrap).
- **Design tokens bundle (Foundation 1c) precedes any UI chunk.** All Visualization surfaces chunks consume the tokens; sequence Foundation completion before Epoch 5 begins.
- **A11y tooling install (Foundation 1c) precedes any UI chunk that has interactive surface area.** Ensures axe-core + ARIA primitives + focus management primitives are in place before compact widget / full dashboard / tray menu chunks add interactive elements.
- **Webview shell + TauRPC bridge (Epoch 4) must precede Visualization surfaces (Epoch 5).** All visualization surfaces consume TauRPC routers + AppError + introspection envelope — Epoch 4 is the substrate.
- **Storage & query (Epoch 3) must precede Visualization (Epoch 5) AND Snapshot (Epoch 6) AND MCP server (Epoch 7b).** All three read from the buffer via the query API surface; broadcast fan-out feeds live UI subscribers.
- **Ingest pipeline (Epoch 2) must precede Storage & query (Epoch 3).** Storage receives via the ingest mpsc channel; without ingest there is nothing to buffer.
- **Snapshot pipeline (Epoch 6) shares its curation pipeline with MCP server's `generate_snapshot` tool method (Epoch 7b).** Sequence Epoch 6 before Epoch 7b sub-block so the curation pipeline is testable standalone before MCP wraps it.
- **Plugin runtime (Epoch 7a) is independent of MCP server (Epoch 7b)** but they share the epoch since they are both feature-gated extension surfaces and have similar capability-sandbox concerns; they can land in either order within Epoch 7.
- **Polish & ship (Epoch 8) E2E chunk depends on EVERY feature epoch having landed first.** This is implicit in the epoch ordering but worth surfacing — E2E injects real OTLP and queries the full vertical, requiring all of Ingest / Storage / Visualization / Snapshot / Plugin / MCP to be functional.
- **Self-observation discipline applies cross-epoch.** Any chunk that adds instrumentation (ingest receiver lifecycle metrics, buffer row-count metrics, snapshot curation timing metrics, plugin invocation metrics, MCP tool call metrics) must use the stdout/file exporter — NEVER point an OTLP exporter at `:4317`/`:4318`. Phase 1 chunks that add per-feature instrumentation should cite the obs plan + arch §Established Decisions [Self-Observation].
- **rmcp version caveat carried forward.** Input.md cites `rmcp 1.5.0` while arch documents the published `0.3.x` line as the reconciliation target. Phase 1 MCP server chunks should reference the resolved version; if Phase 4 user review surfaces preference, that would feed into chunk text refinement.
