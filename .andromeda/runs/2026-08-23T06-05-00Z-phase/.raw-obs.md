## Relevance
Partial — the chunk's implementation is buffer/security-domain, but its counter observable (`redactions_applied` on `buffer.tick`), its §8 allowlist posture, and its "measured RED→GREEN at the wire" proof all read through obs surfaces, so obs constrains the observable and the proof, not the scrub logic itself.

## Constraints
- The `redactions_applied` counter is registered as a tick-aggregated Counter ridden out as a FIELD on the existing 15s `buffer.tick`, folded once per batch by `BufferState::record_redactions` — NOT as a separate `metric.buffer.*` target, and per obs-plan.md §5 (tick-aggregated Counter row) its current registered scope is the OTLP persistence path via `scrub_otlp_field` (log body + exception message + exception stacktrace). Extending scrub coverage to the four ring-buffer columns raises the question of whether that fold's stated scope still describes what the counter counts — whether the code already folds column-scrubs into the same counter is research's question.
- obs-plan.md §5 and §11 (Telemetry Strategy / Logs) require the counter stay tick-aggregated: per-field or per-column emission on the appender path is barred by the hot-path rule ("NEVER over-instrument hot paths (appender inner loop, per-row DuckDB operations)"; "NEVER log in hot path at `info` level"). Any new per-column visibility must ride an existing tick, not a per-row event.
- obs-plan.md §8 (default-deny posture, `buffer` whitelist) requires the `buffer` leaf carry aggregate counts ONLY for `redactions_applied` — never the matched value, its category, the attribute key it came from, or a `service_name` label. This directly forbids the tempting "which column leaked" breakdown label if that label carries client-controlled text.
- obs-plan.md §8 requires field-set COMPLETENESS per leaf: a leaf must enumerate every field its emit site emits, or the target is left PARTLY redacted (the `triage.incident.persist` two-vs-three-field precedent). If this chunk widens `buffer.tick`'s field set, §8's `buffer` list plus the §1 Heartbeat-ticks and §5 restating sites must all name the new field — a §8-only apply leaves §1 and §5 stale (established at 2026-08-22).
- obs-plan.md §11 (PII Scrubbing) forbids single-location scrubbing rules: coverage must hold at source (`skip(...)` / explicit `fields(...)`) AND at the subscriber Layer allowlist. A column-level scrub added only at the appender does not discharge the log-surface half; the two layers must agree.
- obs-plan.md §8 (UI-vocabulary exemption) constrains how the chunk's PII proof greps: the assertion must key on secret FORMATS (regex envelopes such as `Bearer [a-zA-Z0-9]{40,}`, `sk-…`, `ghp_…`, `password=…`), not on the literal words "token"/"password"/"key", or the check produces false positives on legitimate UI vocabulary.
- obs-plan.md §5 (cardinality discipline) and §11 (Metrics) bar unbounded label cardinality on product-internal metrics. `service_name` and `metric_name` are client-controlled by design — neither may become a label on any `buffer`-family tick field the chunk adds, notwithstanding the §5 query-time-aggregation exception, which is scoped to `metric.trace.*` only.

## Patterns to follow
- The tick-field fold pattern for a new aggregate counter: fold once per batch in `BufferState`, ride an existing 15s `buffer.tick`, keep the fold deliberately separate when the producing path differs — the precedent obs-plan.md §5 sets for `record_redactions` vs `record_feed_counts` (log-record path applies redactions while producing no feed counts).
- The EXACT-leaf allowlist pattern (obs-plan.md §8): a target gets its own leaf enumerating every emitted field, because `for_target`'s prefix fallback otherwise resolves a dotted target to an unrelated field set and silently redacts. For `metric.*` targets the guard is per-target-own-leaf (a bare `metric` key legitimately exists); for family prefixes such as `triage`/`corpus`/`interpretation` the guard is no-bare-prefix-key.
- The allowlist-guard placement pattern: guard tests live under `pulse-app/tests/` where they actually run — a src-level `mod tests` in `observability.rs` compiles but never executes under `[lib] test = false` (obs-plan.md §8, the bootstrap-window and delegated-timing entries). The 2026-08-22 sibling guard `pulse-app/tests/unit_observability_allowlist_redaction_counter.rs` is the nearest model.
- Mutation-discrimination of the guard (obs-plan.md §8, delegated-timing + redaction-counter entries): neutralize the leaf, confirm guards turn RED, restore, confirm GREEN — the same discriminating-proof discipline the chunk's scope demands of its smoke.
- Log-line contract for any assertion the chunk makes at the wire (obs-plan.md §6 Required fields): `timestamp` / `level` / `target` / `message` / `fields`, JSON-per-line to `~/.andromeda-pulse/logs/agent-latest.jsonl`; the file IS the agent-readable surface, so a "credential absent" claim is greppable over that file.

## Anti-patterns to avoid
- Emitting per-column or per-row redaction detail on the appender path (obs-plan.md §11 Telemetry Strategy + Logs — hot-path over-instrumentation and info-level hot-path spam).
- Letting any client-controlled column value (`service_name`, `metric_name`, `span_events.name`, `severity_text`) reach a log field, a metric label, or a span attribute as raw text (obs-plan.md §11 Spans/Traces "NEVER include raw OTLP attributes"; §11 Logs "NEVER log raw OTLP attribute values (Vector 1)"; §11 Metrics unbounded-cardinality ban).
- Adding a new emitting target or new tick field without its §8 allowlist leaf / field-set update (obs-plan.md §8 default-deny) — the shipped config and the doc would disagree, and the `for_target` fallback would redact the new field in production while the plan claims it is visible.
