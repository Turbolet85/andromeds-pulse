## Relevance
Partial — arch owns the workspace placement, the DuckDB table/column conventions the four target columns live under, and the OTLP-wire test-injection discipline the RED→GREEN proof must use; the scrub-treatment decision itself is the security specialist's.

## Constraints
- Code lands in the locked crates `buffer` and `security` (and only those two of the reserved set) per architecture.md §Occupied Resources → Cargo workspace crate names; `crates/security` is already the scrubber's home and `crates/buffer` owns the appender — no new crate for this chunk, and the reserved names cannot be repurposed (§Project Intent → How new functionality is added).
- Cross-crate direction: if `buffer` needs a key-safe scrub entry point it must consume it through `security`'s public contract module only — `pub`-contract-only surface, no `pub use` re-export across crate boundaries, dependencies flowing toward `pulse-app` in a DAG (per architecture.md §Conventions → Module visibility discipline and §Cross-cutting Patterns → Module dependency direction). `security` must not gain a dependency on `buffer`.
- The four target columns are covered by the DuckDB naming/typing conventions in architecture.md §Conventions → Database entity naming / Nullable patterns: table names and `snake_case` columns in the reserved set (`spans`, `span_events`, `metrics_points`, `log_records`) are fixed; a treatment that renames, adds, or drops a column changes a reserved-table shape and needs an explicit decision.
- `metrics_points.metric_name` is a declared identity component — architecture.md §Conventions → Primary key convention names metric-point identity as `metric_name` + `ts_unix_nano` + `resource_hash`. Any treatment that rewrites `metric_name` mutates a primary key, and the same section's measured note (Arrow Appender enforces the key at `flush()`; a colliding pair failed the ENTIRE batch) means a key-mutating scrub can fail whole batches, not single rows.
- Ingest→appender hand-off stays on the locked substrate: `tokio::sync::mpsc` into the DuckDB `Appender` with Arrow zero-copy `append_record_batch()` (architecture.md §Established Decisions [In-Process Channel Architecture] + [Database] + §Inherited Defaults → Columnar interchange). Scrubbing must sit inside the existing record-batch build path, not introduce a new stage, a new channel, or a row-at-a-time write path.
- Validation stays on `serde` + smart enum types + `TryFrom` — architecture.md §Established Decisions [Validation Library] locks "no validation library" and states the upgrade trigger explicitly (plugin manifest cross-field rules / &gt;~10 fields). A bounded-vocabulary treatment for `log_records.severity_text` must use that toolset, not pull in `garde`.
- No new env var, IPC procedure, broadcast topic, or capability is warranted by this scope; architecture.md §Occupied Resources is the canonical registry and every addition there is a registered, amended event. If the observable needs widening, `buffer.tick`'s existing `redactions_applied` field is the in-registry surface.

## Patterns to follow
- Boundary-scrub-at-the-appender: `scrub_otlp_field` already sits at the buffer boundary with a `redactions_applied` counter threaded to `state.record_redactions`; extending coverage to the four columns follows the established in-crate placement rather than adding a pre-ingest stage (architecture.md §Occupied Resources → `crates/buffer` placement; §Design Philosophy → single-process modular monolith, microsecond ingest→buffer path).
- Defense-in-depth egress precedent: `storage.export_for_training` re-applies `security::scrubber::scrub_attribute` at the egress boundary *on top of* the producer-side scrub (architecture.md §Occupied Resources → Out-of-data-dir egress sink). Layered scrubbing at more than one boundary is an established, sanctioned shape here.
- OTLP-wire test injection: the RED→GREEN proof must speak OTLP to the running receiver on `:4317`/`:4318` — architecture.md §Cross-cutting Patterns → Test-time telemetry injection bans in-process bypasses, test-mode feature flags, and mock-channel back-doors, and directs port resolution through `ANDROMEDA_PULSE_OTLP_GRPC_PORT` / `_HTTP_PORT`. Buffer-state readback goes through the `traces.*` / `metrics.*` / `logs.*` TauRPC query routers.
- Local-first / zero-egress framing: architecture.md §Design Philosophy → Local-first, zero-infrastructure is the reason a plaintext in-memory ring buffer is tolerable at all; whether the buffer's plaintext-at-rest posture is stated anywhere in arch as a bounded risk is not something this extract can attest.
- Error shape: any new fallible path uses a `thiserror`-derived module enum in `buffer`/`security`, converting at the bridge via `From` into `AppError` (architecture.md §Conventions → Error response schema (Tauri IPC); §Established Decisions [Error Handling Pattern]).

## Anti-patterns to avoid
- Do not add a test-only ingest path, feature flag, or mock channel to stage the RED assertion — architecture.md §Cross-cutting Patterns → Test-time telemetry injection bans all three by name.
- Do not introduce a UUID or random surrogate key to work around a scrub-induced identity collision — architecture.md §Conventions → Primary key convention forbids surrogate keys, with `log_records.seq` as the ONE declared exception.
- Do not register a new Cargo feature flag, env var, or IPC procedure to gate the scrub treatment; architecture.md §Cross-cutting Patterns → Feature-gate hygiene keeps flags off-by-default and minimal, and §Occupied Resources treats every new resource as a registered amendment.

## Contract bindings
- **arch ↔ security** — the scrubber lives in the locked `security` crate; arch fixes the crate boundary and the contract-module-only public surface, security owns the per-class treatment rule and the recall-vs-precision posture.
- **arch ↔ tests** — the RED→GREEN proof binds to arch's OTLP-wire injection discipline (`:4317`/`:4318`, port env vars, TauRPC readback routers), which is the same harness contract §Cross-cutting Patterns imposes on every e2e.
- **arch ↔ obs** — `redactions_applied` on `buffer.tick` is an existing observable; if the treatment adds a counter or a WARN, its shape lands under obs's allowlist rules while arch only requires no new IPC/event registry entry.
- **arch ↔ security (identity)** — `spans.service_name` and `metrics_points.metric_name` are consumed as grouping/lookup keys (Q1/Q2/Q4/Q5 in `crates/triage/src/baseline/sql.rs`, `WHERE metric_name = ?1` in `crates/corpus/src/contract.rs`); arch's §Conventions → Primary key convention makes `metric_name` load-bearing for metric-point identity, so the treatment decision is jointly constrained.
