## Relevance
**Relevant** — this chunk is the impl half of a mandate `security-plan.md` §Security Anti-Patterns → Logging explicitly names by route-entry title; PII scrubbing at a persistence boundary is core domain.

## Constraints
- **Uniform scrubber coverage is the INTENDED posture and this entry owns closing it here.** security-plan.md §Security Anti-Patterns → Logging requires any attribute value crossing into persistent storage or the self-observation sink to pass `scrub_attribute()` and return `ScrubbedValue::Allowed(_)` or `ScrubbedValue::Redacted`; the same section records a MEASURED 2026-08-22 gap on five client-controlled DuckDB columns and names this chunk's working-route entry as the owner. The requirement on this chunk is that the covered columns stop reaching DuckDB unscrubbed — whether any of the four live targets already route through the scrubber at HEAD is research's question.
- **`span_events.exception_type` must stay excluded.** security-plan.md §Security Anti-Patterns → Logging records it as a deliberate exclusion ("class identifier, not user content"), a decision rather than a gap. Extending coverage to it would contradict a recorded decision, not merely exceed scope.
- **Encryption is not an available remedy at this substrate.** security-plan.md §Data Protection (At rest → DuckDB ring buffer) fixes the buffer as an in-memory `:memory:` connection with encryption N/A, and §Security Anti-Patterns → Data Protection bans enabling DuckDB encryption at rest (CVE-2025-64429). Scrubbing at the write boundary is therefore the only control the plan permits for this exposure.
- **The catalog is eight categories with a bounded recall-over-precision posture.** security-plan.md §Security Anti-Patterns → Logging states the eighth arm (`provider_key`) is anchored-prefix + length-floor, ordered after the keyed arms and before `credit_card`, bounded by a false-positive corpus that keeps ordinary high-entropy identifiers `Allowed`. Any per-class treatment this chunk chooses must preserve that ordering and that bounding property; a new arm is a change to a security-load-bearing catalog, not a local tweak.
- **Values never leave via logs or observables — counts only.** security-plan.md §Logging & Monitoring (What NEVER to log) bans logging OTLP attribute values and DuckDB query parameter values; §Security Anti-Patterns → Logging repeats it as a NEVER bullet. Redaction evidence must be numeric/categorical, never the offending string, including in RED-proof diagnostics.
- **The ingest boundary carries its own pre-existing obligations.** security-plan.md §Input Validation (OTLP/gRPC `:4317` and OTLP/HTTP `:4318` rows) requires post-`prost`-decode invariant/bounds checks — including bounded attribute keys/values — before batches reach `buffer::Appender`, and §Security Anti-Patterns → Input bans skipping them. Work on the appender path must not weaken or bypass that upstream check.
- **The `cargo audit` probe is due and must actually run.** security-plan.md §Dependency Security → CI integration (Standing deferral — `cargo audit` unrunnable) fixes an every-3rd-wrap probe interval, requires the basis and the named overlap signal (`cargo deny check advisories`) to be re-verified, requires the absorbing chunk's report to record either the probe result or an explicit `probe skipped per ratified interval (next: {point})`, and forbids ignore-listing any finding that has a stated safe upgrade.

## Patterns to follow
- **Scrub at the producing/write boundary, not at readers.** security-plan.md §Security Anti-Patterns → Logging enumerates the covered sites as the OTLP appender's own writes (`log_records.body` via `extract_log_body`; `exception_message`/`exception_stacktrace` on both tables) — new coverage belongs at the same `crates/buffer` write boundary. The scope's read-path consumers (`crates/triage/src/baseline/sql.rs`, `crates/corpus/src/contract.rs`) are consulted for the consumer map, not modified.
- **Whole-struct scrubbed projection at a persistence boundary** — security-plan.md §Security Anti-Patterns → Logging names `BaselineState::scrubbed_clone` and `StormStateSnapshot::scrubbed_clone` as the existing corpus-persist precedent for producing a scrubbed value at the boundary rather than mutating in place.
- **Redaction applied at a layer, not at call sites** — security-plan.md §Logging & Monitoring (Log format) states field redaction attaches at the subscriber layer rather than each log call; the analogous discipline for this chunk is one boundary helper covering all four columns rather than four ad-hoc call-site edits.
- **INTENDED vs MEASURED separation in the plan body** — security-plan.md §Security Anti-Patterns → Logging already carries both a posture clause and a measured-gap clause naming an owner. Per the scope, the wrap's amendment is a posture flip of that clause, not new prose; phase is read-only on specs.

## Anti-patterns to avoid
- **NEVER log raw OTLP attribute values, span/log/metric content payloads, or DuckDB query parameter values** (security-plan.md §Security Anti-Patterns → Logging; §Logging & Monitoring NEVER-log list) — this binds the RED-proof assertions and any new/widened counter: the canary value must not appear in `buffer.tick`, in a WARN, or in test output that ships as a log.
- **NEVER enable DuckDB encryption at rest on the in-memory ring buffer** (security-plan.md §Security Anti-Patterns → Data Protection, CVE-2025-64429) — the plaintext-at-rest property is the reason the gap matters and is explicitly out of scope as a fix.
- **NEVER build DuckDB SQL by `format!` interpolation of a column value** (security-plan.md §Security Anti-Patterns → Input; §Input Validation DuckDB row) — if any per-class treatment or RED-proof query touches the read side, it goes through `Connection::prepare` with `?` placeholders.

## Contract bindings
- **obs** — the `redactions_applied` observable on `buffer.tick` (scope §Touchpoints) is the non-leaking evidence channel this domain requires; security fixes only that evidence must be counts, never values (§Logging & Monitoring). Whether the field needs widening (per-column/per-class breakdown) and what its schema becomes is the obs plan's call, not security's.
- **tests** — the RED→GREEN wire proof must use synthetic credential-shaped canaries; no real PII in fixtures. The CI security gate half of the folded PREREQ (`cargo audit` probe + `cargo deny check advisories` overlap) belongs in the one CI workflow as a security job per tests §CI Integration.
- **arch** — the four target columns are locked schema in Occupied Resources; a treatment that renames, retypes, or drops a column is an arch decision, not a security one. Security's mandate is the value written, not the column's shape.

## Acceptance criteria contributions
- A credential-shaped canary placed by a host app in each covered client-controlled ring-buffer column is not stored verbatim in DuckDB, asserted on the real OTLP path (per security-plan.md §Security Anti-Patterns → Logging — INTENDED posture plus the MEASURED-gap clause naming this entry as impl owner).
- `span_events.exception_type` remains outside the scrub path, and the chosen treatment does not alter the eight-category catalog's arm ordering or its false-positive bounding corpus (per security-plan.md §Security Anti-Patterns → Logging).
- No raw column value appears in any log line, tracing field, or emitted observable on the new path — redaction evidence is a count (per security-plan.md §Logging & Monitoring, What NEVER to log).
- The `cargo audit` probe is RUN this chunk with its result and re-verified basis recorded, `cargo deny check advisories` is re-observed, and every finding carries a visible disposition with no safe-upgrade finding ignore-listed (per security-plan.md §Dependency Security → CI integration, Standing deferral).
