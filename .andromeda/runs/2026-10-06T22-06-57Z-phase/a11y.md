# a11y extract

## Relevance
partial — the chunk adds no UI surface and triggers no new WCAG criterion; a11y applies only because the lockfile it changes is the one the a11y toolchain and the audited SPA build resolve from, and the a11y CI job gates the same commits.

## Constraints
- The tier is Standard, WCAG 2.1 AA with the SC 2.3.3 escalation (per a11y-plan §1 A11y Scope Summary). The chunk creates no component, binds no key, renders no new text or state and animates nothing, so §4 ARIA Patterns & Roles, §5 Keyboard Navigation, §7 Screen Reader Support and §8 Cognitive Accessibility contribute nothing here.
- a11y-plan §10 SLO Invariants (Standard+ invariants) requires zero new violations per PR against the base branch. A dependency move is not exempt: the chunk's commits are held to it like any other.
- a11y-plan §9 CI Integration and §3 `CI integration` (Pipeline integration) require the a11y assertions to run in the same `ci.yml` as a blocking `a11y` matrix job that builds the UI and then runs the chain. A lockfile change therefore re-runs that job on a different installed tree; "the gate reads green on CI" does not cover a11y unless that job is read too. Whether the `a11y` job was green on the three red shas is research's question (the scope confirms only the supply-chain failure).
- a11y-plan §1 (A11y surfaces & assistive tech reach, desktop-webview row) and §3 `A11y testing tool pick` name the tool majors the harness is specified against, and the §1 row records the standing ruling for an advisory fix that crosses one of those majors: upgrade and re-baseline in the same chunk. Whether the `seroval` or `source-map-js` fix (upgrade or `overrides`) moves any a11y tool, or any package those tools resolve, is research's question — it falls out of the holder set P3 re-derives from the lockfile.
- a11y-plan §3 `Harness wiring & conventions` (Static serving) ties the audit server's SPA-fallback and the route paths configured for pa11y and Lighthouse to the router's browser-history behaviour. The scope places `seroval` under the router, so a fix that moves the router version changes the application every a11y spec loads; the configured routes are required to keep resolving.
- a11y-plan §6 Visual Design Verification (Color contrast pairs · Motion tokens) requires the contrast and reduce-motion assertions to hold on the built SPA's computed styles. The scope places `source-map-js` under the CSS/bundler build chain, so a fix that moves that chain is held to the same assertions on its output.
- a11y-plan §1 (desktop-webview row) states that the pa11y copy nested inside pa11y-ci is covered by the npm-policy `extract-zip` exception. The scope leaves those two exceptions standing unless the change fires their closing condition; if it does, that §1 statement no longer describes the tree and an a11y-plan amendment is owed.

## Patterns to follow
- The precedent the plan records for exactly this class of work: an advisory-driven upgrade, then the full a11y chain, then the violation tuples compared against the baseline before the baseline is declared held (per a11y-plan §1, desktop-webview row).
- Run the chain the way CI does — UI build first, then `cargo xtask test:a11y` (per a11y-plan §3 `CI integration`, Pipeline integration · Command).
- Check suite health after the lockfile moves with the config-named Playwright list, never the bare one: a list-time import failure disables the whole suite silently, and the bare form reads an inert config (per a11y-plan §3 `Harness wiring & conventions`, Adding a surface).
- Judge regression by the tuple comparison the plan defines, against the committed baseline file (per a11y-plan §3 `CI integration`, Per-PR regression detection; §3 `Harness wiring & conventions`, Regression baseline).

## Anti-patterns to avoid
- Never treat a red a11y job on the chunk's commit as outside the chunk, or defer it to a follow-up (per a11y-plan §11 A11y Anti-Patterns → CI).
- Never retry an a11y failure to get a green run after the dependency move; a flake is investigated, not re-run (per a11y-plan §11 A11y Anti-Patterns → SLO).
- Never narrow the axe rule set to absorb a finding a moved tool version newly reports, without a Decisions Log entry (per a11y-plan §11 A11y Anti-Patterns → Strategy).

## Contract bindings
- a11y ↔ tests: the `a11y` matrix job lives in the same `ci.yml` and installs from the same `pulse-app/ui` lockfile under the same Node/npm major as the UI gates the scope re-runs (per a11y-plan §9 CI Integration; §3 `CI integration`).
- a11y ↔ security: the a11y toolchain's nested pa11y copy is tied to the npm-policy `extract-zip` exceptions (per a11y-plan §1, desktop-webview row); a change to those exceptions is a change to a fact the a11y plan states.
- a11y ↔ design: contrast and reduce-motion assertions read token values through the CSS build chain the `source-map-js` holders belong to (per a11y-plan §6 Visual Design Verification).
- The violation-JSON ↔ obs binding is untouched: the chunk emits no new violation record and changes no schema.

## Acceptance criteria contributions
- (a11y) The `a11y` matrix job reads green on the chunk's commit, read from the run itself and not inferred from the supply-chain job (per a11y-plan §9 CI Integration; §3 `CI integration`, CI gate).
- (a11y) The full chain on the changed lockfile produces zero violation tuples absent from the committed baseline (per a11y-plan §10 SLO Invariants, Standard+ invariants; §3 `Harness wiring & conventions`, Regression baseline).
- (a11y) After the lockfile change the config-named Playwright list reports a non-empty suite with exit 0, at the test count it reported before the change (per a11y-plan §3 `Harness wiring & conventions`, Adding a surface).
- (a11y) The chunk report states whether any a11y tool major named in the plan moved and whether the `extract-zip` exceptions changed; either one is flagged as an a11y-plan amendment, and a major move carries its re-baseline in the same chunk (per a11y-plan §1, desktop-webview row; §3 `A11y testing tool pick`).
