## Constraints
- test-plan §9 Pipeline structure → **Supply chain** requires `cargo xtask check:npm-supply-chain` to run as a plain `run:` step of ci.yml's `supply-chain` job with a three-way exit contract (0 green · 1 findings/policy red · 2 cannot-evaluate), over `pulse-app/ui` with the policy at `pulse-app/ui/npm-policy.json`. Only exit 0 is green; a cannot-evaluate reading is not a pass.
- The same §9 row requires that job to stay lockfile-only: deliberately NO `npm ci`, `node_modules` never installed there. So whatever disposition the chunk takes must be carried by the COMMITTED `package-lock.json` / `npm-policy.json`; a fix that exists only in an installed tree does not reach the gate. Whether the gate at HEAD reads the lockfile alone on every arm (advisory · license · ban) is research's question.
- test-plan §3 `Per-chunk gate discipline` requires the plan's `## Test Commands` to carry the full standard gate set UNCONDITIONALLY — it is not waived for a chunk with no Rust change — in the stated order: `capability-drift` before the default-features workspace nextest, the `--features mcp-server` `emit_taurpc_bindings` regen as the last cargo-adjacent step, then the `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts` close (the form for a chunk adding no procedure, which the scope's Boundaries declare this one to be).
- The same §3 key requires the three webview gates (`npm run lint` / `typecheck` / `test` with `--prefix pulse-app/ui`) whenever the Files-to-modify / New-files lists touch any `pulse-app/ui/**` path. `package.json`, `package-lock.json` and `npm-policy.json` all sit under `pulse-app/ui/`, so the exclusion does not apply to this chunk.
- test-plan §4 Framework (webview unit tests) and §1 Surfaces under test → desktop-webview unit tests pin the webview test toolchain: `vitest` 4.x (with `@vitest/mocker` 4.x — §4 records the vitest 3 mocker as vulnerable), `jsdom` 26, `@testing-library/react` 16, `npm run test` exit 0 as the signal. An upgrade or `overrides` entry on the `source-map-js` holders (the `vite` → `postcss` and `@tailwindcss/*` chains named in scope) must leave those majors where §4 puts them. Whether any candidate fix moves `vite` / `vitest` / `postcss` across a major is research's question.
- test-plan §9 Pipeline structure → **A11y suite** requires that job to run `npm ci` + `npm run build --prefix pulse-app/ui` before Playwright on all three OSes, with unchanged gate conditions (axe critical/serious = 0, Lighthouse ≥ 90, pa11y 0 errors, zero new baseline tuples). It is the CI job that actually INSTALLS the changed lockfile, so a lock the runner's npm refuses, or a moved runtime package (`seroval` rides `@tanstack/react-router`, prod-reachable per scope) that breaks the build, reds there and not in `supply-chain`. Whether the runner's npm accepts a lock written by the host's npm is research's question (scope Boundaries already assign the Node-major read to P3).
- test-plan §10 Build failure conditions make any test failure, a lint / typecheck failure and coverage below 75 % line / 70 % branch / 85 % function build-failing. §10 measures coverage with `xtask/` excluded (temporarily), so an edit confined to `xtask/src/npm_gate.rs` — if the plan makes one — does not move the measured figure; the gate still runs on the chunk's commits.

## Patterns to follow
- Verdict-from-exit-code with a named cannot-evaluate arm: §9 Supply chain's 0/1/2 contract is the same shape §3 `Per-chunk gate discipline` records for `check:staged-artifacts` and `perf:budget`. Evidence for this chunk reads the gate's printed arm plus its bare exit code, before and after the change.
- Lockfile-as-subject, measured twice: §9 separates the lockfile-only read (`supply-chain`) from the installed read (`a11y`: `npm ci` + `npm run build`). The scope's "measure the installed tree after the change" maps onto that split — one reading per side, neither standing in for the other.
- The local install-and-build leg has a written shape in §3 `Per-chunk gate discipline`: the `npm` stage of `cargo xtask pre-push:linux` is `npm ci` + `npm run build`. The verb itself is NOT a gate for this chunk — §3 states it requires a Windows host with WSL and cannot run on the current dev host — so the stage's two commands are run directly, not through the verb.
- Agent-runnable invariants (§2): every check ends in a machine-parseable signal (exit code + structured stdout); no step of the plan is a human reading `npm audit` prose and judging it.
- If the plan adds or changes a test for `xtask/src/npm_gate.rs`, §4 Conventions put Rust unit tests co-located in the crate's source, and §8 What to mock keeps the filesystem real (`tempfile::TempDir`) with fixture data built at test runtime (§7 Seed strategies).

## Anti-patterns to avoid
- §11 Quality: NEVER ship with known test failures, and NEVER a retry-once policy. The red here is advisory-feed-driven with no in-repo cause (scope CONTEXT 3), so a re-run that happens to read green is not a disposition — §10 Zero-flakiness budget rules out retry as a remedy.
- §11 Universal: NEVER real network calls in tests without loopback stubs, and NEVER a manual smoke step. Any committed test of the gate's logic feeds it recorded advisory / lockfile fixtures; the live `npm audit` call belongs to the gate run, never to a `#[test]`.
- §11 CI: NEVER a floating-tag third-party action. Binds only if the plan edits `.github/workflows/ci.yml` (for example the `setup-node` pin §9 names as SHA-pinned); a Node-major change keeps the 40-char SHA form.

## Contract bindings
- tests ↔ security: §9 Supply chain is the CI carrier of security-plan §Dependency Security's npm channel (exception form, never-except-a-fixable-finding). Tests owns that the step exists, runs lockfile-only and exits 0/1/2; security owns what counts as a valid exception. An `npm-policy.json` edit is judged by both.
- tests ↔ a11y: §9 A11y suite binds a11y-plan §3's harness to the same lockfile — it is the job that installs and builds it on three OSes, so the a11y gate conditions are an indirect acceptance surface of this chunk.
- tests ↔ obs: (none) — the chunk boots no app, so the §3 `5-command implementation` / `Log format` / `Status endpoint shape` bindings are not exercised; §3 Boot-smoke gate (conditional) triggers only on its listed boot/setup paths, none of which the scope names.

## Acceptance criteria contributions
- `cargo xtask check:npm-supply-chain` exits 0 with its green arm printed on the changed lockfile, locally and as the `supply-chain` job's step on the chunk's own CI run — exit 2 (cannot-evaluate) is not accepted as green (per test-plan §9 Pipeline structure → Supply chain)
- The standard gate set runs whole and in order, including `npm run lint`, `npm run typecheck` and `npm run test` with `--prefix pulse-app/ui`, each exit 0, and closes with `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts` exit 0 (per test-plan §3 `Per-chunk gate discipline`)
- `npm ci` then `npm run build --prefix pulse-app/ui` succeed on the changed lockfile on the dev host, and the CI `a11y` job — the runner-side install of the same lock — is green on the chunk's commits on all three OSes (per test-plan §9 Pipeline structure → A11y suite)
- After the change the webview test toolchain still resolves `vitest` 4.x / `@vitest/mocker` 4.x / `jsdom` 26 / `@testing-library/react` 16, read from `package-lock.json` (per test-plan §4 Framework (webview unit tests))
