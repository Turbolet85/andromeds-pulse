## Patterns to follow
- The spawned-program witness form is the shape for the three engine-boot readings: the built `andromeda-pulse-engine` spawned under a cleared environment with no display variable and no session bus, a TempDir data dir, two picked loopback ports through the registered port variables, the pid from `Child::id()`, readiness from ports accepting, records awaited by target under a bound, the log family read after the end. A chunk touching `pulse-app/src/console.rs` or the engine `[[bin]]` takes that test as its runtime gate; a plan touching `pulse-app/src/engine_boot.rs` takes the conditional boot-smoke gate — whether this chunk edits those sources or adds tests alone is research's question (per test-plan §3 Per-chunk gate discipline → Spawned-program witness form; → Boot-smoke gate (conditional)).
- Shell scripts already have committed pins that run inside `cargo nextest run --workspace`: tests that run a script with `bash` over constructed scratch roots and assert its exit code and output (the coverage-threshold witnesses in `pulse-app/tests/quality_gate_workflow.rs`, the `empty_input_tests` quarantine pins in xtask). That is the precedent for pinning `scripts/agent-run.sh` arms so they run on every push rather than by hand (per test-plan §9 CI Integration → Lint + tests row).
- The lock file's directory has an in-tree precedent for how it is read: a re-executed child under `env_clear()` with `XDG_RUNTIME_DIR` set to a fresh TempDir and a count of `andromeda-pulse-corpus-key-*.lock` there, beside the Linux lock-dir rule pins (unset or blank → the temp dir; a directory → it, canonicalized; otherwise an error). Whether a spawned engine under the witness form's environment (no session bus, no runtime dir) writes a lock file at all, and in which directory, is research's question (per test-plan §4 Unit Test Strategy → What unit tests cover → corpus crate).
- Mutation evidence is recorded per mutation: the product line changed, the pins that redden, and the green reading after the revert — a failing-input pin red against a stub that grades nothing is the reading the row calls insufficient. Pairs that discriminate only together are named as pairs (per test-plan §1 Pending coverage triggers → `engine-log-arm-mutation-and-engine-cycle-glue-coverage`; test-plan §4 Unit Test Strategy → What unit tests cover → security crate).
- Verdict objects and constructed child environments are pinned by set equality, and refusal labels through a pure decision function where one exists (three of the cycle's seven labels are pinned through `refusal`); whether the four labels `drive` alone returns can be reached through a pure seam or only by driving `drive` is research's question (per test-plan §3 Per-chunk gate discipline → Engine cycle gate form; test-plan §1 Pending coverage triggers → `engine-log-arm-mutation-and-engine-cycle-glue-coverage`).

## Anti-patterns to avoid
- NEVER synchronize by `sleep(N)`: a census, a readiness wait or a shell pin waits on an explicit signal under a bound — ports accepting, a record by target — never a sleep for a count (per test-plan §11 Test Anti-Patterns → E2E; test-plan §3 Per-chunk gate discipline → Spawned-program witness form).
- NEVER mutate the test process's own environment mid-test (`std::env::set_var` without cleanup) to reach an arm such as `home-unset` or `path-unset`; reach it through a child process's constructed environment or an injected seam (per test-plan §11 Test Anti-Patterns → Mocking).
- NEVER let a check read PASS over an input it cannot grade, and never leave a one-time hand-driven RED→GREEN leg standing in for a gate: a leg that proves its precondition absent reports cannot-evaluate, and a stage that grades a record it wrote itself is the class the chunk exists to close (per test-plan §3 Per-chunk gate discipline → Engine cycle gate form; test-plan §1 Pending coverage triggers → `harness-log-family-resolution-coverage`).
