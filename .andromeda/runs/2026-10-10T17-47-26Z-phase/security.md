relevant — the chunk adds no product surface, but all three of its readings test security mandates (validated ports, loopback-only listeners, the corpus-key lock file's place), and its harness work (the pre-push sixth stage, shell pins, mutations, refusal labels) sits wholly inside the harness-only class security-plan §Security Anti-Patterns → Input states member by member.

## Constraints
- **Rejected port.** security-plan §Input Validation (row "CLI / env var inputs") requires that the two OTLP port variables yield validated ports only, that the bind host is never an input (the boot builds the loopback address itself), and that a rejected port records the bind as failed with the `invalid_port` reason and starts no receiver. The chunk's spawned reading asserts exactly these three clauses; whether the code already does each is research's question (no committed test drives it, per the scope's C2).
- **Socket census.** security-plan §Threat Model Summary (Attack surface → "public API"; Infrastructure → Networking and Hosting) states the console program's network surface as the two receivers bound to `127.0.0.1` and nothing else (no window framework, no TauRPC bridge, no plugin host; MCP is stdio, no socket), and security-plan §Security Anti-Patterns → API bans any non-loopback bind. The census is the first measurement of that statement on a spawned engine; a listener beyond the two, or one on a non-loopback address, is a finding against these anchors, recorded and brought at P5, not repaired here. The census must say whether it counts listening sockets only: per security-plan §Secret Management (Storage → Runtime) an engine on the credential-store primary holds an outbound session-bus client connection, which is not a listener.
- **Lock file's place.** security-plan §Data Protection (At rest → "Corpus-key lock file") and security-plan §Security Anti-Patterns → Input (carve-out "the corpus-key lock dir") require: the directory is `XDG_RUNTIME_DIR` when set (absolute, canonicalized, a directory, else FAIL CLOSED, never a temp-dir fallback) and the canonicalized temp dir when unset or blank; the file is content-free, mode `0o600`, never deleted. The assertion on the lock file's directory is made against that rule for the environment the engine was spawned with. A lock file found in the shared temp dir under an environment with no runtime dir is the plan's own stated residual (2) of that §Data Protection bullet, founder-ratified as accepted; it is recorded as read, and is not by itself "something that should not stand" beyond what the plan already records. Whether the code's resolution matches the rule on a spawned engine is research's question.
- **The lock file's path is not in the log.** security-plan §Logging & Monitoring (What NEVER to log) and security-plan §Security Anti-Patterns → Logging forbid any full product-consumed path in the log, the corpus-key lock dir and lock-file path named explicitly (failures surface as unit error variants with no path). So the directory reading is taken from the filesystem, never from a log record, and the chunk adds no log emission that would name it.
- **Pre-push stage, environment and writes.** security-plan §Security Anti-Patterns → Input (the `pre-push:linux` member of the harness class) and security-plan §Input Validation (row "CLI / env var inputs", third harness-only reader) state the check's contract: `HOME` / `PATH` read by value and neither printed nor written; every probe and stage child under a CLEARED environment plus a set pinned by set equality (session bus address, runtime dir and display variables outside it, so no stage reaches an OS credential store); writes confined to its per-run area and the report twin; the report carrying no environment value and no path. A sixth stage that runs a real engine cycle changes three of these stated facts: the pinned child set (a cycle needs the port, retention and passphrase variables that the same section lists for `harness:engine-cycle`), the "writes only" sentence (a cycle writes a data dir, and the engine itself writes the lock file to the temp dir when the runtime dir is outside the set), and the standing statement that the check starts no program. Each is a change to a member the plan records as the operator's reading, not the founder's word; it goes to the operator at P4 with the P-103 question, and the master is amended at wrap, not at phase.
- **Ports and refusals.** security-plan §Input Validation (row "CLI / env var inputs", fifth harness-only boundary) requires `harness:engine-cycle` ports parsed as `u16`, 4317 and 4318 refused as `shared-port`, and every refusal made before anything starts as `cannot-evaluate`, exit 2, one closed label on stderr, from the closed label set that section lists. The four pins of the labels only `drive` returns hold that shape (closed label, nothing started, no environment value, no path). A refusal for a port already taken is not in that closed set: if the chunk adds one it is a new closed label the plan must gain at wrap; what the cycle and the verbs do today on a taken port is research's question.
- **Secret-class passphrase.** security-plan §Secret Management (What counts as secret) makes `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` secret-class (never logged, never exported), and security-plan §Security Anti-Patterns → Input (member (b) of the console-engine harness) requires the cycle's passphrase made per run and never printed or written. Any spawned leg or stage this chunk adds that needs a corpus key keeps both: no passphrase in a verdict, a report, a kept log or a shell-test transcript.
- **No new command word, no arm reclassified.** security-plan §Input Validation (row "Console program command line") holds the engine's grammar closed at two words, any later command being a new question each time; security-plan §Security Anti-Patterns → Input holds the exit-witness arm PROVISIONAL, awaiting the founder's own word, with the console engine's spawn line reading no witness variable and carrying no preload. The chunk adds no engine word, and a shell pin that touches the witness branches (the row's clause (d), if P4 takes it) pins the arm as it stands and classifies nothing.

## Patterns to follow
- The cleared-environment child with a pinned variable set held by a set-equality test (security-plan §Security Anti-Patterns → Input, the `pre-push:linux` and `harness:engine-cycle` members) is the form for any child this chunk spawns from xtask; extend the pin with the set, never spawn outside it.
- Closed-label verdicts: a verdict or report document with a pinned member set, carrying no value of an environment variable and no path (security-plan §Input Validation, row "CLI / env var inputs", harness-only readers). Mutation and refusal pins assert labels, not text; `check:engine-log` keeps the pinned property that no line of it holds a record's text or a path.
- The shell script's closed word set with usage and exit 2 before any directory is made (security-plan §Input Validation, fifth harness-only boundary) is the behaviour the word-arm pins hold; the plan itself names the missing committed shell-level test as owed to test-plan §1 `harness-cleanup-verdict-and-boot-spawn-shell-coverage`.
- State files read through the existing bounded readers only (security-plan §Security Anti-Patterns → Input, the boot-recorder state-file class: the exit record's one-line bounded grammar, the pid reader); a new pin or stage reuses them and adds no reader of its own.
- A test-only tool that no scanner sees is vetted by a hash pin and its licence beside it (security-plan §Dependency Security → CI integration, "Vendored test-only channel"); a shell-test runner brought in for the shell pins follows that precedent or the scanned channels.

## Anti-patterns to avoid
- NEVER bind, or let a harness leg cause a bind, on anything but `127.0.0.1`, and never use 4317 / 4318 from the harness (security-plan §Security Anti-Patterns → API; security-plan §Input Validation, `shared-port`).
- NEVER read a product-binary path variable without the canonicalize rule, and never widen the harness carve-out beyond harness-only, not-product-consumed members: no test hook, variable or reader added to `pulse-app/src` to make a reading easier (security-plan §Security Anti-Patterns → Input).
- NEVER log or print a full product-consumed path or a secret-class value from a new leg: the lock dir, the data dir beyond what the boot verb's own ready line already prints, the passphrase (security-plan §Security Anti-Patterns → Logging; security-plan §Secret Management).
