## Relevance
relevant — the chunk adds no product surface, but every proof it commits is a reading against a registered arch resource (the two loopback receivers, the corpus-key lock file's place, the harness ports) or a formalized CLI contract (`pre-push:linux`, `ci-gates`, `harness:engine-cycle`, `check:engine-log`, `scripts/agent-run.sh`), and the pre-push sixth-stage question turns on clauses of one of those contracts.

## Constraints
- **Workspace placement, no new member.** architecture §Occupied Resources → Cargo workspace crate names reserves the sixteen names; the chunk's code belongs in `xtask` (verb code and its pins), `pulse-app` (its `tests/`, for spawned-engine and workflow tests) and `scripts/`. architecture §Cross-cutting Patterns → Module dependency direction requires that no library crate gains a dependency for a harness proof.
- **The two receivers and nothing else.** architecture §Occupied Resources → Network ports requires that an engine program binds the two loopback receivers and nothing else, that the bind address is not configurable, and that a rejected port variable records the bind as failed with `reason = "invalid_port"` and starts no receiver. The same bullet records the "no third socket" claim as by construction and not measured from the process's socket list: the chunk's census is the measurement that bullet says is missing. Whether the code already satisfies the mandate is research's question; a census that shows a third socket is a finding to record, not a repair.
- **Harness ports.** architecture §Occupied Resources → Network ports registers 24317 / 24318 as the harness-only defaults of `harness:engine-cycle` and requires 4317 and 4318 to be refused (`shared-port`), with no port added to the product. A leg that needs any other default port lands a new entry there (amended at wrap) and falls under the scope's halt boundary.
- **The lock file's place.** architecture §Occupied Resources → Filesystem locations (Out-of-data-dir lock file) fixes the file's name form and its location rule (the runtime dir on Linux when set and usable, fail closed when set and unusable, the canonicalized temp dir when unset or blank), counts it as one of THREE product-written locations outside the data dir, and records that for the console program the file was read on a hand run and its placement is not asserted by a test. The chunk's reading is that missing assertion; it must not create a fourth product-written location. Which directory a spawned engine resolves depends on the environment the test hands it — architecture §Occupied Resources → Environment variables records that `harness:engine-cycle`'s child set holds no runtime dir and no session bus address, and that the key path the engine then took was not read — so whether a lock file is created at all under that environment, and where, is research's question.
- **`pre-push:linux` is a formalized CLI contract.** architecture §Occupied Resources → xtask CLI surfaces (`cargo xtask pre-push:linux`) requires: six stages in a named order ending in `ci-gates`; a six-member verdict pinned by set equality; a reason list stated as complete; a cleared child environment pinned by set equality; a per-run area that is the verb's own with nothing else under `target/pre-push/` touched; "binds no port and starts no `pulse-app`"; dev-host only, not wired into CI. A sixth stage that reads a real engine cycle changes the port clause plainly and may change the child set, the reason list (a taken port needs a label) and the written area; each changed clause is a contract change the plan states at P4 and the wrap amends. Whether the "starts no `pulse-app`" clause is read as covering the console program is part of that question, not settled by the plan text.
- **The engine-harness verbs are held as written.** architecture §Occupied Resources → xtask CLI surfaces (`cargo xtask check:engine-log`, `cargo xtask harness:engine-settled`, `cargo xtask harness:engine-cycle`) requires seven check arms in a fixed order with fixed line shapes and no record text or path in any line; a closed refusal-label list returned before anything starts; an eight-member cycle verdict and a child environment each pinned by set equality; and names the cycle's callers (the CI step, a chunk's gate block). Mutations and label pins prove these clauses; they do not re-word them. A pre-push stage that calls the cycle is a new caller to register. The same entry's `data-dir-holds-a-log-family` refusal constrains which data dir such a stage may hand the cycle.
- **`scripts/agent-run.sh` is a sibling formalized contract.** architecture §Occupied Resources → xtask CLI surfaces (`scripts/agent-run.{sh,ps1}`) requires five unchanged verbs; `cleanup`'s single bounded token out of four with exit 0 on `clean` alone, derived from independent probes; `boot`'s failure lines (no spawn record, the app-ended line, the still-running line, the receivers line only after a `refusing` verdict); and the sh-only word arms of `boot` / `status` (none, `engine`, any other word: usage, exit 2). The shell-level pins hold those arms as written. That entry gives the `logs` verb no clause beyond its name; the family it resolves is registered at architecture §Occupied Resources → Environment variables (`ANDROMEDA_PULSE_LOGFILE`), so what the family branch does today is research's question.

## Patterns to follow
- **Spawned-engine read-back.** architecture §Cross-cutting Patterns → Test-time telemetry injection: a test of the console program injects over real OTLP and reads state from the program's own log records on a spawned run, or from the `EngineHandles` of an in-process arm; a non-default port is resolved through the two port variables.
- **Script pins run the script itself.** architecture §Stack and Technologies → Gate-script pins (test-only): existing pins run a committed script with `bash` over scratch roots, a missing `bash` FAILS and never skips, and no Cargo or npm dependency is added. A shell test framework would be a new test-only tool and a new Stack row at wrap.
- **Verb verdict shape.** architecture §Occupied Resources → xtask CLI surfaces (`cargo xtask harness:engine-cycle`): exit 0 · 1 · 2, closed labels, one JSON object on stdout pinned by set equality, no path and no environment value in it, a refusal before anything starts reading `cannot-evaluate` with one closed label. The taken-port precedent is the `cargo xtask perf:frame-sample` entry of that bullet, which reads exit 2 when the ports are already accepting rather than waiting or stopping the holder.
- **Cleared child environment.** architecture §Occupied Resources → Environment variables (`HOME` · `PATH`): harness verbs read the two by value only to build a cleared child set, print and write neither, and pin the set by equality.
- **Shared gate logic lives in xtask, and workflow steps are pinned by tests.** architecture §Infrastructure Patterns → CI/CD approach: Rust-needing CI logic is an xtask verb runnable locally, and the `boot` job's steps are held by workflow tests in `pulse-app/tests/quality_gate_workflow.rs`.

## Anti-patterns to avoid
- No leg binds 4317 or 4318, and no leg asks for a non-loopback bind (architecture §Occupied Resources → Network ports).
- No in-process bypass, mock channel or test-only feature flag standing in for a spawned reading (architecture §Cross-cutting Patterns → Test-time telemetry injection).
- No new command word and no `stop` path for the console program — it is a closed two-word command line ended by SIGTERM or SIGINT — and no spawn that names `target/{profile}/andromeda-pulse`, which exists on no host; the console binary's path is `target/{profile}/andromeda-pulse-engine` (architecture §Occupied Resources → Process / service identity).
