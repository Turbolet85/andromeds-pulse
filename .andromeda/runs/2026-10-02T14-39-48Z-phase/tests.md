relevant: a new MCP sidecar read surface over corpus `incident_events` falls squarely under the P3 MCP path, the open `mcp-incident-read-back-cross-process-coverage` trigger and the per-chunk gate set.

## Constraints
- Test tier is Standard, per test-plan §1 Test Scope Summary. New code is held to the §10 Quality Gates thresholds (≥ 75% line / ≥ 70% branch / ≥ 85% function, xtask temporarily excluded), and §11 Test Strategy bars lowering a threshold to pass.
- The chunk plan's `## Test Commands` must carry the unconditional standard gate set, per test-plan §3 Per-chunk gate discipline. That covers fmt, clippy `--all-features`, `capability-widening-check`, `check:ingest-progress`, `check:staged-artifacts`, `capability-drift` BEFORE the workspace nextest, the workspace nextest, then the `--features mcp-server` `emit_taurpc_bindings` regen as the last cargo-adjacent step. A chunk adding no TauRPC procedure (scope §Boundaries) closes with `git diff --quiet <chunk-base> -- pulse-app/ui/src/bindings/index.ts`. The webview npm gates are excluded only if research confirms zero `pulse-app/ui/**` paths.
- The boot-smoke gate is conditional, per test-plan §3 Per-chunk gate discipline. It binds only if the plan touches `pulse-app/src/main.rs`, `pulse-app/src/observability.rs`, `crates/ui-bridge/src/`, `tauri.conf.json` or `capabilities/*.json`. The stderr-sink CARRY is a spec correction. Whether it (or anything else) also edits `observability.rs` is research's question, and that answer decides whether the smoke is owed.
- Incident-tool response CONTENT is guarded only when a real `andromeda-pulse-mcp` subprocess reads it back, per test-plan §1 Pending coverage triggers → `mcp-incident-read-back-cross-process-coverage` and §6 P3 "Current residual". In-process `dispatch_tool` assertions and live smoke evidence are named as non-regression-guards there. A new events read surface (a ninth tool or an extended `retrieve_report` / `query_incident_list`) adds owed cross-process content to that open row unless the chunk commits it.
- A feature-gated test sits outside the default `--workspace` gate, per test-plan §1 (the `e2e_p3_mcp_resolve_content` note) and §9 CI Integration (`mcp-test` job: `cargo nextest run --workspace --features mcp-server --profile ci`). Any `--features mcp-server` test the chunk adds must be named and run explicitly in Test Commands, not assumed covered by the workspace run.
- The MCP double gate must be asserted both ways (negative AND positive), per test-plan §1 Pending coverage triggers → `security-vector-coverage: MCP feature + runtime gating` and the §1 MCP stdio sidecar surface row. Whether existing tests already cover the gate for a new tool path is research's question.
- Unit coverage of the new pieces lives co-located in their library crates, per test-plan §4 Unit Test Strategy Conventions. For `mcp-server` that means JSON-RPC frame parsing, tool routing and schema validation. For `corpus` it means the new events read path (an in-crate `#[cfg(test)]` module). §4 names `pulse-app` as the `tests/*.rs` exception.

## Patterns to follow
- The committed cross-process content leg `pulse-app/tests/e2e_p3_mcp_resolve_content.rs`, per test-plan §1 → `mcp-incident-read-back-cross-process-coverage` (NARROWED note). It spawns the real sidecar against a shared on-disk encrypted corpus, opens the corpus with `OsKeychainBackend::new("com.andromeda.pulse")` (the sidecar's own backend + service id) and skips cleanly only where no credential store exists. It asserts content in every response arm (here that likely means events present / unknown incident id).
- Module ↔ MCP sidecar through `tokio::process::Command` with piped stdin/stdout and JSON-RPC 2.0 frames, per test-plan §5 Integration Test Strategy Drivers and §8 Mocking & Stubbing (Process mocking row). If a ninth tool is added, the `tools/list` name assertions in `crates/mcp-server/tests/sidecar_subprocess.rs` (named in §1 / §6 P3) are the existing site that enumerates tools.
- Self-bootstrapped data, per test-plan §7 Test Data & Fixtures (per-test `tempfile::TempDir`, data generated at runtime). Seed the events through the production writer path (a status VALUE change through `update_incident_status`), not hand-inserted rows. The "oldest first, bounded count" ordering needs a deterministic time source, per §11 Universal (no un-injected real time).
- Constructor-injected `Arc<dyn Trait>` for any new reader surface the sidecar consumes, so tests stub it without monkey-patching, per test-plan §8 Anti-monkey-patching.

## Anti-patterns to avoid
- Never count in-process `dispatch_tool` assertions or a live smoke as the cross-process content guard for the new surface, per test-plan §1 `mcp-incident-read-back-cross-process-coverage` ("smoke evidence is not a regression guard").
- Never pre-populate the corpus from a `.sql` script or SQLite snapshot, and never share mutable state across parallel tests, per test-plan §11 Test Data.
- Never use `sleep(N)` for sidecar or corpus synchronization, never use `unwrap()` without an `expect` reason, and never commit `#[ignore]` without a tracking issue, per test-plan §11 E2E / Unit / Quality.

## Contract bindings
- tests ↔ obs/security: the MCP response-body ban. Per test-plan §1 → `security-vector-coverage: MCP response body redaction`, a tool call must leave no response content in `agent-latest.jsonl`, only result-type + result-count metadata. The events read's tracing (scope: the `result_type_label` / `result_count_for` pattern) is what that assertion would grade. If the new tool emits a record, it may also need an obs-plan allowlist leaf.
- tests ↔ obs: the stderr-sink CARRY amends obs-plan §1/§3 to a file-only app sink. test-plan §3 Log format still shows `Stream: RUST_LOG=debug cargo nextest run --workspace 2>&1 | tee test.log` with agent-parseable greps over that stream, and the §3 Per-chunk direct-binary smoke reads `<data_dir>/logs/agent-latest.jsonl*`. Research must decide whether the §3 Log format stream reading depends on an app stderr sink. If it does, a test-plan §3 amendment rides this chunk's `Expected amendments (wrap)` alongside the obs-plan one.
- tests ↔ Conductor (P-075 CARRY): per test-plan §1 / §6 P3, the external Conductor round is a verification ref recorded on the overseer's word, not a committed in-repo test. It complements the cross-process content leg and does not replace it.
