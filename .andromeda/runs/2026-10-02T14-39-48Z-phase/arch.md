# arch extract

## Relevance
relevant — the chunk adds an external MCP wire surface (or extends one) in the `mcp-server` crate, reading the `corpus` crate cross-process; both are arch-owned resources.

## Constraints
- Workspace placement: the tool/dispatch code belongs in the locked `mcp-server` crate and the events read path in the locked `corpus` crate; no new crate name (per architecture.md §Occupied Resources → Cargo workspace crate names; §Inherited Defaults → Module boundaries).
- Dependency direction is a DAG rooted at `pulse-app`; no library crate gains a sibling edge its contract does not require. The `mcp-server → corpus` edge is the one the read may ride; the scope proposes no new edge, and whether the sidecar's existing corpus contact (`load_incident_row`) already goes through a reader surface usable for events is research's question (per architecture.md §Cross-cutting Patterns → Module dependency direction; §Established Decisions → Corpus Write Arbitration, which records `mcp-server → corpus` as an existing edge).
- The wire stays MCP-spec JSON-RPC 2.0 exactly over stdio, through the hand-rolled `jsonrpc.rs` layer plus `tools.rs` name-dispatch. No custom envelope, and no adoption of rmcp macros, which remain an anchor dependency only (per architecture.md §Established Decisions → MCP Server Surface; → API Style — MCP Server Surface 3; §Inherited Defaults → API style — external MCP).
- Errors are standard JSON-RPC 2.0 error objects with a stable numeric `code`, a `message` and optional `data`, honoring the MCP-spec codes. An unknown incident id therefore maps to the same code and shape as the existing missing-incident path (per architecture.md §Conventions → Error response schema (MCP)).
- Every type appearing in an MCP tool response must be `serde::Serialize` (per architecture.md §Cross-cutting Patterns → Cross-bridge data shape).
- Feature-gate hygiene: the surface exists only under `--features mcp-server` (default off) plus runtime `ANDROMEDA_PULSE_MCP_ENABLED=true`. No new Cargo feature and no new env var. `ANDROMEDA_PULSE_MCP_ENABLED` keeps its graceful-degrade warn (per architecture.md §Cross-cutting Patterns → Feature-gate hygiene; §Occupied Resources → env vars `ANDROMEDA_PULSE_MCP_ENABLED`; §Infrastructure Patterns runtime topology).
- No corpus DDL and no `SCHEMA_VERSION` change: `incident_events` is a reserved v2 table whose sole production writer is `CorpusWriter::update_incident_status`. That writer records one row per status VALUE-change (`event_kind` = new status label, empty encrypted payload) and records nothing on a same-status refresh or a `DeclinedStale` write. The read must treat `payload` as an encrypted BLOB, opaque without the key, never surfaced raw (per architecture.md §Occupied Resources → Corpus SQLite database / schema names → Reserved tables; → At-rest posture).

## Patterns to follow
- Tool registration follows the chunk #94 corpus-backed tool family (`query_incident_list` / `retrieve_report` / `retrieve_telemetry_slice` / `mark_incident_resolved`). Any ninth tool is a name-dispatch addition in `tools.rs` and a `tools/list` entry (per architecture.md §Standard Contracts → MCP server — spec-conformant; §Conventions → External wire — MCP server).
- Role-separated corpus trait views: a read belongs on the corpus crate's reader surface (`CorpusReader` or an equivalent read trait declared in `corpus`), not on `CorpusWriter`, mirroring how `storage.inspect` binds a read-only `CorpusReader` (per architecture.md §Occupied Resources → Tauri IPC routes `storage.inspect`). Whether `CorpusReader` already exposes an events method, or any production `SELECT … FROM incident_events`, is research's question.
- The sidecar filters incidents by the `run/workspace-key` the app publishes, an opaque, bounded filter string never joined as a path. An events read for a named incident should respect the same workspace identity the other incident tools use (per architecture.md §Occupied Resources → Subpaths under the resolved root → `run/workspace-key`).
- Cross-process conformance is proven by real-subprocess legs against the `andromeda-pulse-mcp` binary, the same way the existing wire contract is proven (per architecture.md §Established Decisions → MCP Server Surface; → API Style — MCP Server Surface 3).

## Anti-patterns to avoid
- Never add a custom envelope or a non-JSON-RPC error shape for the new read (per architecture.md §Established Decisions → API Style — MCP Server Surface 3).
- Never introduce a reverse or sibling dependency edge to reach the events, such as `corpus → mcp-server`, `mcp-server → pulse-app` or `mcp-server → triage` beyond what already exists (per architecture.md §Cross-cutting Patterns → Module dependency direction).
- Never add a TauRPC procedure, port, capability grant or env var for this surface. It is stdio-sidecar only, and any such addition would be an unscoped §Occupied Resources entry (per architecture.md §Occupied Resources → Tauri IPC routes / Ports / Environment variables).

## Contract bindings
- arch ↔ security: the new MCP response crosses the stdio boundary. MCP tool response bodies are never logged, error messages are sanitized, and the double-gate holds. The encrypted `payload` cell binds to the at-rest posture (architecture.md §Occupied Resources → At-rest posture → security-plan §Data Protection §At rest).
- arch ↔ tests: the MCP wire surface (tool list and error schema) is what the cross-process subprocess legs and the Conductor P-075 round assert against. A new or extended tool contract changes the fixture surface the round's content-fidelity check reads.
- arch ↔ obs: the read's tracing carries bounded counts and type labels only. The stderr-sink CARRY is an obs-plan amendment, not an arch one, so arch has no role in it.
- Wrap amendment owed (arch): if a ninth tool lands, the 8-tool enumerations in architecture.md §Stack and Technologies (MCP server row), §Established Decisions → MCP Server Surface, §Conventions → External wire — MCP server and §Standard Contracts → MCP server — spec-conformant all go stale. The same holds for the `incident_events` reserved-table note if the table gains a production reader. These belong in this chunk's Expected amendments (wrap).

- (arch) The new or extended read surface lives in `crates/mcp-server` (dispatch) and `crates/corpus` (read path), with no new workspace crate and no new crate-graph edge; `cargo tree` shows `mcp-server`'s workspace deps unchanged (per architecture.md §Cross-cutting Patterns → Module dependency direction; §Occupied Resources → Cargo workspace crate names).
- (arch) A real `andromeda-pulse-mcp` subprocess answers `tools/list` and `tools/call` for the events read with MCP-spec JSON-RPC 2.0 framing. An unknown incident id returns a standard JSON-RPC error object with the same numeric `code` the existing missing-incident path uses (per architecture.md §Conventions → Error response schema (MCP); §Standard Contracts → MCP server — spec-conformant).
- (arch) No corpus DDL delta and `SCHEMA_VERSION` stays 2; no new env var, port, TauRPC procedure or capability JSON entry, and `EXPECTED_PROCEDURES` and `capability-drift` are unchanged (per architecture.md §Occupied Resources → Corpus SQLite database / schema names; → Tauri IPC routes).
- (arch) The response never contains the raw encrypted `payload` bytes of an `incident_events` row (per architecture.md §Occupied Resources → At-rest posture).
