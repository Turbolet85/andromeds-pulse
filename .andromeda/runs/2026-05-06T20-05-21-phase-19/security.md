## Chunk relevance

- route#22 "Query routers (traces/metrics/logs) — viz crate prepared statements (no format-string SQL), query_id + param_count anonymized logging" — relevant (DuckDB query parameter injection class is dominant 2026 vuln cluster; query result paths feed both TauRPC bridge and MCP `query_*` tools; logging redaction load-bearing for query-parameter values)

## Constraints

- All `viz` crate query handlers MUST use `Connection::prepare` + `?` placeholders + `Statement::execute([&param])` parameter binding; `format!("SELECT … WHERE service_name = '{}'")` and any string-interpolated SQL is banned per security plan §Input Validation row 5 and §Anti-Patterns Input row 2 (Dagster GHSA-mjw2-v2hm-wj34, Vanna CVE-2024-5827, dagster-duckdb CVE-2026-41490 cluster).
- Table and column identifiers MUST come from compile-time constants only — user input never names a table or column per security plan §Input Validation row 5 ("Table/column names are spec-fixed in Occupied Resources"). The 7 reserved tables are the source of truth.
- Every TauRPC procedure argument struct for `traces.*`/`metrics.*`/`logs.*` MUST go through `serde::Deserialize` and use smart enum types / `TryFrom<u16>` for bounded numeric inputs (limit, offset, time-range) per security plan §Input Validation row 3 (TauRPC bridge boundary).
- Every TauRPC procedure landed in `viz` crate MUST have a matching entry in `pulse-app/capabilities/` JSON — silent runtime rejection otherwise per security plan §API Security row 7 and §Anti-Patterns API row 3. The `xtask capability-drift` check (chunk #25) is the enforcement.
- Query handlers MUST collapse module-internal `thiserror` errors to `AppError::{Validation, Storage, Internal}` at the bridge via `From` impls, with sanitized one-liners — no stack traces, file paths, library versions, Rust struct names, or DuckDB internal error text leak per security plan §Error Handling and §Anti-Patterns Logging row 4.
- Query-handler logs MUST emit `query_id` + `param_count` + `param_types` (or equivalent enum tags) instead of parameter values; raw OTLP-derived parameter strings (service names, span names, attribute values, log severity bodies) NEVER appear in tracing fields per security plan §Logging & Monitoring "What NEVER to log" row 3 and §Anti-Patterns Logging row 3.
- The MCP `query_traces`/`query_metrics`/`query_logs` tools (chunk #44) MUST share the same prepared-statement code path defined in this chunk — no parallel string-interpolated implementation per security plan §Input Validation row 7 ("the `query_*` tools share the `viz` crate's prepared-statement code path").

## Patterns to follow

- Prepared-statement boundary pattern established for `buffer` crate retention (chunk #21) and ring-buffer DELETE constants — viz query handlers extend the same discipline (per-query `const` strings parallel to `RESERVED_TABLES`/`DELETE_BY_CUTOFF`); cutoff parameters bound via `?` placeholders, never `format!`.
- Module-internal `thiserror` enum + `From<viz::Error> for AppError` impl at the bridge — mirror the existing `From<BufferError> for AppError` pattern (chunk #21 handoff: `BufferError::Retention => AppError::Storage`) per security plan §Error Handling TauRPC row.
- AllowList target registration discipline from chunk #21 — every new tracing target (`viz.query.traces.*`, `viz.query.metrics.*`, `viz.query.logs.*`, `metric.viz.query.duration_ms` if applicable) gets an explicit AllowList entry with field allowlist; no field passes through unless registered, mirroring `crates/.../observability.rs::AllowList::production()` extension pattern.
- TauRPC procedure shape per arch §Conventions: `<router>.<verb>` dotted namespace, `snake_case`, with bounded numeric enums (`limit: u32` with explicit upper bound, `offset: u64`, time-range as `(start_ns: u64, end_ns: u64)` validated via `TryFrom`).
- Sanitization at `From` impl boundary — strip DuckDB error message text via match on error kind (e.g., `duckdb::Error::QueryReturnedNoRows => AppError::NotFound { resource: "..." }`, `duckdb::Error::SqliteFailure(...) => AppError::Storage { message: "query failed" }`), never propagate `e.to_string()` directly per chunk #21 ui-bridge sanitization test precedent.

## Anti-patterns to avoid

- NEVER `format!("SELECT … WHERE {col} = '{val}'")` or any `to_string()` / `to_rfc3339()` SQL composition in `viz` source — chunk #21's `format!`-grep gate `grep -rnE "format!.*(CREATE|SELECT|INSERT|UPDATE|DELETE)" crates/viz/src/` MUST return empty (per security plan §Anti-Patterns Input row 2).
- NEVER log DuckDB query parameter values or echo OTLP-attribute-derived strings (service names, span names, attribute keys/values) into tracing fields — use `query_id` + `param_count` only per security plan §Anti-Patterns Logging row 3 and §Logging "What NEVER to log" row 3.
- NEVER expose stack traces, Rust struct names (e.g. `viz::QueryError::DuckDb`), file paths, or library version strings in `AppError::Internal { message }` content — sanitize at the `From<viz::Error> for AppError` impl per security plan §Anti-Patterns Logging row 4.
- NEVER serialize an `anyhow::Error` directly across the TauRPC bridge from a `viz` procedure — convert to `AppError` enum first per security plan §Anti-Patterns Code Patterns row 4.

## Contract bindings
