## Open questions

- **Should `DEFAULT_MAX_TOKENS` differ for fallback tier?** Primary uses 1024 (well above the ~250-token typical L4 JSON output). Fallback's reduced output (single hypothesis + ≤2 steps) is structurally smaller — а 512-token cap would be defensive. However, the schema constraint already bounds output to `L4_OUTPUT_MAX_BYTES = 16KB` post-generation + `LLAMA_CLI_MAX_OUTPUT_BYTES = 64KB` subprocess cap. Lowering `max_tokens` is a defense-in-depth refinement, not a correctness requirement. **Plan default:** keep 1024 unchanged; defer per-tier max_tokens to Phase 6 user review.
- **Should `validate()` be split into `validate_primary` / `validate_fallback`, OR extended in-place?** In-place extension preserves а single entry point — `parse_bounded()` calls `validate()` which dispatches tier-conditionally based on the parsed `model_tier` field. Splitting would require the L4 subscriber к know the tier at parse time, which is а minor coupling. **Plan default:** extend `validate()` in-place; keep single entry point.
- **Tier selection at boot — out of chunk #85 scope?** The `LlamaCliInference::new(tier, profile, broadcast)` constructor at `llamacli_inference.rs:115` requires the tier passed in at boot. Currently the boot wiring (`pulse-app/src/main.rs`) chooses `ModelTier::Primary` unconditionally (per chunk #82/#83 — verified via grep). To actually exercise the fallback path in production OR end-to-end testing, the boot wiring needs к map `HardwareProfile::CpuFallback` → `ModelTier::Fallback` (and possibly `CpuPrimary` → conditional `Fallback` based on user config OR hardware-capacity heuristic). Per chunk #85 spec "Specialist plan touches: test-plan (fallback-tier scenarios)" + the spec's silence on boot-time tier-selection logic, the boot mapping appears к be deferred. **Plan default:** chunk #85 implements the prompt + schema validation + L4-subscriber-tier-dispatch substrate. Boot-time tier-mapping logic in `pulse-app/src/main.rs` is а separate concern — leave the boot wiring к explicitly select `ModelTier::Primary` for now, and add а follow-up chunk OR Phase 6 user-driven plan amendment if boot mapping is in scope.
- **Token-count budget assertion methodology:** chunk #85 spec calls for ~500-700 token fallback prompt vs ~800-1000 primary. Without а tokenizer dep (`tokenizers` crate not yet in `crates/interpretation/Cargo.toml` per chunk #81 deferral comment in `prompt.rs:21`), the assertion uses `prompt.len()` as а byte-count proxy. Typical English тext is ~3.5 chars/token, so 500-700 tokens ≈ 1750-2450 bytes. **Plan default:** assert `prompt.len() < 2500` bytes for fallback as а pragmatic lower-cost proxy; precise tokenizer-based assertion deferred until tokenizer dep lands at chunk #81+ if applicable.
- **Fallback prompt corpus retrieval section behavior:** primary's `build_primary_tier_prompt` conditionally includes the corpus retrieval section if non-empty. Should fallback also support corpus retrieval, OR drop the corpus section entirely к conserve token budget? **Plan default:** mirror primary's conditional inclusion (preserve consistency); fallback callers can pass empty corpus_retrieval string к suppress the section.
