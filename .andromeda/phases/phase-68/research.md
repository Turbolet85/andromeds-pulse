## Open questions

- **Storm state serialization shape**: `DashMap<[u8;16], FingerprintState>` doesn't derive `Serialize`/`Deserialize` directly (DashMap is a wrapper around RwLock<HashMap>); plan must either (a) serialize a Vec<(KeyBytes, FingerprintState)> derived view, or (b) serialize a HashMap<[u8;16], FingerprintState> snapshot. The `FingerprintState` struct itself (storm.rs:78-90) needs `#[derive(Serialize, Deserialize)]` added — currently has only `Debug`. Confirm at Phase 4 plan that adding serde derives to `FingerprintState` is in scope.
- **Storm load: empty fingerprint case** — if corpus blob exists but contains 0 fingerprints (e.g., previous session had no storms), should the load return `Some(empty)` or `None`? Semantically equivalent for in-memory state but affects test assertion shape. Recommendation: return `Some(empty StormStateSnapshot)` to distinguish "we have a record" from "no record" → CorpusRestore counter emits +0 events vs cold-start path.
- **CorpusRestore event emission cadence**: lifecycle emits one `ServiceLifecycleEvent` per restored service; storm has no broadcast topic for restore events (storm events flow through `pulse://stream/attention-cues` only; restore is NOT an attention cue). Plan should specify: lifecycle emits N CorpusRestore events on `pulse://stream/service-lifecycle` (one per restored service); storm emits aggregate-only metric `metric.triage.pattern.storm.corpus_restore_count_total` value=N + tracing event `triage.pattern.storm.corpus_restore` (new target) with `[restored_fingerprint_count, duration_ms]` fields. No broadcast event for storm restore.
- **set_state_on_corpus_restore return type**: `Option<ServiceLifecycleEvent>` matches `set_state_on_restart` shape, but the restore is conceptually a no-transition (state stays the same as what was persisted). Should the event use `from_state == to_state` (self-loop with CorpusRestore trigger as a marker)? Existing FSM gate `is_valid_transition` rejects self-loops at line 187. Resolution paths: (a) emit the event WITHOUT routing through `is_valid_transition` (Corpus restore is a special boot-path event, not a runtime transition); (b) treat as `from_state: Unknown → to_state: restored_state` (cold-start-shaped event); (c) skip event emission entirely on restore and emit a separate `metric.triage.lifecycle.corpus_restore_count_total` aggregate only. The v0_2_0 route §71 line 374 says "emit synthetic CorpusRestore lifecycle transitions per service so constellation observers cascade" — implies (a) or (b). Plan should pick one explicitly and document the rationale.

Recommendation: defer to chunk #72 (per route#71 chunk description: "must scrub via #72 OR document as structural-metadata per P-048"); document in plan's Acceptance Criteria → Deferred section.
