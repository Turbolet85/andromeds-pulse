## Combined goal

Add a cross-cutting configuration hot-reload layer (capabilities P-055 / P-056) so a developer can edit `~/.andromeda-pulse/config.toml` and have tuning keys re-applied to the running process within ~2s without a restart. A new `crates/config-watcher/` crate runs a `notify` filesystem watcher on `<data_dir>/config.toml` with a 500ms debounce; on each settled change it re-loads + re-validates through the existing `ui_bridge::Settings` + `Settings::validate()` surface (malformed/out-of-range config is rejected and the previous valid config is retained), classifies the changed keys into a **hot** set vs a **restart-required** set, publishes the validated `Settings` on a `tokio::sync::watch` channel, and emits aggregate-only events on the new `pulse://stream/config-events` broadcast topic (per arch §Standard Contracts real-time push + obs-plan §6, security-redacted per security plan §Logging) — see `combined.md §Chunk route#96`.

Two live consumers re-read their config from the watch channel this chunk: the **cadence coordinator** (#80 — the only consumer whose source comment explicitly says "hot-reload deferred к chunk #94") rebuilds its tier-3 / reflection intervals on change, and the **service-lifecycle heartbeat** (#67) re-reads its dormant/archived thresholds each tick. Application is **prospective by default** (P-056): a hot threshold edit changes evaluation going forward only — it does NOT reset baselines, replay missed cadence ticks, or retroactively re-classify services. A separate opt-in `diagnostics.reevaluate_recent_window()` TauRPC action performs the explicit FULL retrospective pass — re-classifying every registered service against the new lifecycle boundaries (using each service's existing activity history) and forcing one immediate cadence cycle with the new config. Restart-required keys (Drain params, `mcp_server_enabled`, retention, plus the conceptual model-path / OTLP-ports / storage-path init-time substrate) are NOT applied live; they raise a restart-required notice via `config-events` + `config.status()` rather than mutating arch-locked startup decisions mid-run (per arch §Established Decisions [Database] / [Telemetry Retention] / [LLM Inference Runtime]). Two new `config.*` TauRPC procedures (`config.reload` manual trigger + `config.status` last-reload/errors/pending-restart-keys) round out the surface. Per the breadth decision the only user-visible consumer this chunk is the backend `config-events` topic + `config.status` (a Diagnostics view that renders them is a separate later chunk) — so this is a backend-only chunk: design/layouts/a11y bindings stay dormant (combined.md §Cross-domain binding reconciliation "a11y conditional").

## Implementation notes

- **DAG discipline:** keep triage FREE of `ui-bridge`. The cadence coordinator + lifecycle heartbeat take triage-side config types (`CadenceConfig`, `LifecycleThresholds`) via `watch::Receiver`; pulse-app owns the `Settings → consumer-config` fan-out at the binary boundary. config-watcher is the only new crate that depends on `ui-bridge` (for `Settings`).
- **Prospective by construction:** `watch::Sender::send_replace` (latest-value, no backlog) is what makes application prospective — consumers see only the newest value at their next tick; missed cadence ticks are never replayed (skip-first-tick after interval rebuild). The ONLY retrospective path is the explicit `reevaluate_recent_window()` action.
