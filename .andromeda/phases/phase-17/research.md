## Conventions to follow

- **Crate body imports**: workspace deps via `name.workspace = true`; sibling crate via `name = { path = "../sibling" }`; dev-deps separate. Buffer's Cargo.toml needs an `ingest = { path = "../ingest" }` edge to use the `Batch` type. **This is a NEW sibling-crate edge** — verify against arch §Module dependency direction. Per arch: "buffer MUST NOT depend on a sibling crate unless a declared contract requires it". The Batch type IS the cross-crate contract for ingest → buffer hand-off, so this edge is sanctioned.
- **Module visibility**: `pub` only in contract module; everything else `pub(crate)`. Buffer's `schema` / `appender` / `consumer` modules expose `pub(crate) fn ...` callable from buffer's contract module wrapper, OR `pub fn ...` if pulse-app needs to call directly. Recommendation: `pub fn run_consumer(receiver, state, ...)` in `consumer.rs` since pulse-app spawns it.
- **Error mapping at bridge**: `From<buffer::Error> for AppError` lives in `crates/ui-bridge/src/contract.rs` (NOT in the buffer crate) — same-file as the existing `From<IngestError> for AppError` at line 37-50.
- **AllowList target naming**: dotted-target format `{module}.{operation}.{outcome}`. Buffer chunk #20 targets: `buffer.schema.init`, `buffer.schema.init.error`, `duckdb.append`. Stay consistent with chunk #19's `config.load.port_validation` and `ingest.{grpc,http}.rate_limit.rejected` shape.
- **DuckDB connection identity**: `:memory:` connection string with `pulse_buffer` as in-memory database alias (per arch §Occupied Resources). DuckDB rust crate's `Connection::open_in_memory()` returns the equivalent — no explicit alias unless schema-namespacing required (which it isn't, since we're using single `main` schema).
- **Static DDL strings**: schema module exposes `pub(crate) const CREATE_SPANS: &'static str = "CREATE TABLE IF NOT EXISTS spans (...)";` with one constant per table, then a single `pub fn create_schema(conn: &Connection) -> Result<(), Error>` that runs all 7 in sequence via `conn.execute_batch(...)`. NEVER `format!`-style interpolation, even for the table list.
- **Test pattern**: `#[cfg(test)] mod tests` co-located in each module file; `#[rstest] #[case(...)]` for parameterized cases (e.g., per-table schema introspection); `#[tokio::test(flavor = "multi_thread")]` for async consumer tests; `duckdb::Connection::open_in_memory()` per test for isolation.

## Open questions

- **Q1 — `duckdb` crate features**: `bundled` (statically links DuckDB C++ — large binary, cross-platform reproducible, no system dep) vs unbundled (system DuckDB required). Recommendation: `features = ["bundled"]` for Tauri portability. /implement should verify the binary size impact (`cargo build --release -p pulse-app && ls -lh target/release/pulse-app.exe`) — DuckDB 1.5.x adds ~30-50 MB, acceptable for a desktop app. **Decision: surface to user at Phase 6 review.**
- **Q2 — Arrow crate version pin**: testing.md mentions `arrow-rs 55.x`. The `duckdb` 1.10500.x crate's Arrow integration may pin a specific arrow-rs version. /implement runs `cargo add duckdb@1.10500 --features bundled && cargo tree -p buffer | grep arrow` to discover the pinned version, then declares `arrow.workspace = true` matching that pin. Defer details to /implement.
- **Q3 — `BufferConnectionStatus` health envelope extension**: extend `HeartbeatState` + `current_health` with explicit init-status tracking (mirrors `BindStatus` for OTLP receivers), OR rely on the existing `last_tick_at`-based liveness signal (init failure means no ticks ever fire, which itself signals degradation). Recommendation: **extend** with `BufferConnectionStatus` for clarity (init failure surfaces as `subsystems.buffer.status = "init_failed"` + `error_msg = Some(reason)` instead of just stale last_tick). **Decision: surface to user at Phase 6 review.**
- **Q4 — Sync vs spawn_blocking for DuckDB calls**: DuckDB Rust `Connection` is `!Send + !Sync`. Two paths: (a) `Arc<Mutex<Connection>>` shared between consumer task + heartbeat reads — simple but blocks tokio worker on `append_record_batch`; (b) consumer task owns `Connection` exclusively, runs in `tokio::task::spawn_blocking` per batch — non-blocking on tokio runtime. Recommendation: **(b) spawn_blocking per Arrow append call** — matches DuckDB's blocking-IO semantics + keeps tokio runtime healthy. Heartbeat reads `BufferState` (lock-free atomics) so DuckDB Connection access doesn't fight heartbeat. /implement details deferred.
- **Q5 — Composite key encoding for `(trace_id, span_id)`**: DuckDB BLOB type with `PRIMARY KEY (trace_id, span_id)` two-column composite. Alternative: hash to `BIGINT`/`UBIGINT` via xxhash for primary key + raw BLOB columns — but loses OTLP-native identity. Recommendation: **two-column composite BLOB primary key**, accept the storage overhead for identity preservation. /implement confirms via `PRAGMA table_info('spans')` post-create.
- **Q6 — Ingest crate dep edge from buffer**: per arch §Module dependency direction, buffer MUST NOT depend on sibling crate unless contract requires it. The `Batch` enum IS the contract — chunk #20's buffer crate adds `ingest = { path = "../ingest" }` to consume the type. Alternatives considered: (a) move `Batch` to a new shared `crates/contracts` crate — too invasive for chunk #20; (b) duplicate the `Batch` shape in buffer — violates DRY + arch §Established Decisions. Recommendation: **direct sibling edge sanctioned by contract**. Document in plan.md notes per arch §Cross-cutting Patterns.
- **Q7 — Where does OTLP → Arrow conversion live**: in buffer crate (canonical schema authority) per arch contract binding. Each `Batch::Spans` etc. converts to `arrow::record_batch::RecordBatch` matching the corresponding DuckDB table schema. Conversion functions `pub(crate) fn batch_spans_to_record_batch(spans: &[ResourceSpans]) -> RecordBatch` etc. live in `appender.rs`. /implement details deferred.
