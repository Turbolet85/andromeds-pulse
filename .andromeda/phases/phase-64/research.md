## Patterns detected

- **New-crate scaffold template** (`crates/curation/src/lib.rs` 5 lines + `crates/curation/Cargo.toml` 18 lines): minimal `pub(crate) mod {internals}; pub mod contract;` shape with `serde + thiserror + tracing` deps + `proptest + rstest + serde_json` dev-deps. Chunk #68 corpus crate WILL be larger (needs `db`, `schema`, `encryption`, `keychain`, `scrubber` modules) — but the same `lib.rs` exposes-only-contract discipline holds.
- **TauRPC router at binary boundary** (`pulse-app/src/{connection,services,plugins,mcp,viz}_router.rs`): always `pulse-app/src/{namespace}_router.rs`, never inside the owning library crate. Library crate provides trait abstractions + concrete impls; router file uses `#[taurpc::procedures(path = "namespace")]` + `ApiImpl { state: Arc<dyn Trait> }` + `#[taurpc::resolvers] impl`. Adapter-from-Tauri-side patterns (HeartbeatBindStatus in connection_router.rs) when the resolver needs state from a Tauri-aware crate (e.g., ui-bridge HeartbeatState).
- **Cross-crate state via trait-in-lower** (`ingest::connection::ReceiverBindStatus` + `pulse-app::connection_router::HeartbeatBindStatus` adapter; `triage::lifecycle::ServiceRegistry` + `pulse-app::services_router::ServicesApiImpl` direct injection): lower crate defines `pub trait Foo: Send + Sync + Debug`; pulse-app constructs impl + threads `Arc<dyn Foo>` through resolver constructor. Preserves arch §Cross-cutting Module dependency direction (deps flow toward pulse-app).
- **Deterministic time discipline** (`triage::lifecycle::registry::tick_all(&self, now_unix_nano: i64, ...)`): pure functions over time parameters; no `chrono::Utc::now()` reads inside business logic. Tests inject explicit nanosecond timestamps via `1_000 * NANOS_PER_SEC`-style constants.
- **Schema-versioned persistence with size caps + canonical-path-traversal defense** (`triage::baseline::corpus.rs::resolve_corpus_path` + `load_state`): `fs::canonicalize(data_dir)` + assert `canonical_subpath.starts_with(canonical_data)` before any I/O. Schema version embedded in serialized struct + read-back check before deserialization. Size cap on file before `read_to_end`. Chunk #68 SQLite path resolution will mirror this discipline.
- **Co-located test convention with helper builders** (`pulse-app/src/services_router.rs::tests::make_impl()`, `triage::lifecycle::registry.rs::tests::fresh_registry() + snapshot_with()`): test helpers as private module functions; full test coverage for trait impls + boundary cases.
- **Atomic write via tmp + rename** (`triage::baseline::corpus.rs::persist_state` lines 54-67): write to `<path>.tmp` then `fs::rename(<path>.tmp, <path>)`; on rename error, remove `.tmp` to avoid orphan. Chunk #68 SQLite schema migration on first launch will likely NOT need atomic write (rusqlite handles transactions), but any side-files (e.g., key derivation salt file if used) MUST follow this pattern.
- **Specta cfg-feature-gated derive** (`triage::lifecycle::registry.rs:36-37` `#[cfg_attr(feature = "taurpc-runtime", derive(specta::Type))]`): TauRPC bridge types need `specta::Type` derive for TS binding emission; optional gate keeps the crate buildable without taurpc dep. ## Open questions

1. **Encryption approach: SQLCipher vs. OS-keychain-key + age-encrypted DB file vs. application-level cell encryption?** SQLCipher is the canonical SQLite encryption-at-rest solution but adds C-side dependency (requires building with `-DSQLITE_HAS_CODEC=1` + SQLCipher source). Alternative: OS-keychain-stored encryption key + `age` (or libsodium) encryption of the entire SQLite file at open/close boundaries (less granular but simpler dep graph). Phase 4 plan must choose ONE; recommend Phase 4 evaluate trade-offs + document the decision in the chunk plan's "Implementation Steps" section.
2. **Scrubber crate placement: `crates/corpus/src/scrubber.rs` vs. NEW `crates/security/` workspace crate?** v0.2.0 plan §69 wording is "security-crate PII scrubber primitive" — implies a new `crates/security/` workspace crate. But arch §Occupied Resources currently does NOT enumerate `security` as a reserved crate name; adding it requires /andromeda-evolve --allow-arch-registry amendment. Recommend Phase 4 surface this to user at Phase 6 review — two paths: (a) create `crates/security/` as a NEW workspace crate, register via Registry Update (correct per v0.2.0 plan language); (b) place scrubber in `crates/corpus/src/scrubber.rs` for now, defer extraction to a follow-up chunk when other consumers (Sentry before_send, subscriber Layer redaction) need it (smaller scope, faster ship).
3. **CorpusReader / CorpusStore trait shape — what does `storage.inspect()` actually return?** v0.2.0 plan §69 says "read-only corpus query" but doesn't specify the query language or filter shape. Phase 4 plan must define: structured filter args (e.g., `IncidentFilter { workspace: Option<String>, status: Option<IncidentStatus>, limit: u32 }`) + envelope shape (`StorageInspectPayload { items: Vec<InspectionRow>, total: usize, next_cursor: Option<String> }`). Recommend starting MINIMAL — chunk #68 ships `inspect()` with empty filter returning corpus metadata (record counts per table + total bytes) + `path()` returning the path string; richer query DSL deferred to chunk #70 incident records + chunk #71+ digest pipeline integrations.
4. **Heartbeat tick: does corpus subsystem need `corpus.tick` heartbeat emission?** obs extract recommends emission ("if corpus subsystem maintains background tasks"). Chunk #68 scaffold may NOT have background tasks (synchronous open + on-demand write + lazy schema migration on first launch) → tick emission deferred to chunk #70+ when persistent incident tracking adds write loops. Recommend Phase 4 documents this decision explicitly (no `corpus.tick` in chunk #68; emit on first background-task introduction).
5. **First-run keychain prompt UI: in-app modal vs. OS-native dialog only?** design + layouts extracts both flag this as "if materialized in-app modal" vs. "if OS-native". Per a11y extract: a11y deferral assumed no in-app modal in chunk #68. Recommend Phase 4 CHOOSES OS-native only for chunk #68 (`keyring` crate surfaces the OS dialog; no Pulse-owned wrapper); in-app explainer modal (showing what the OS prompt will ask for) deferred to a follow-up chunk that introduces the full Settings → Storage UI. This collapses design + layouts + a11y surfaces to zero new UI files in chunk #68 (matching the a11y "No domain coverage" assessment).
6. **`storage.path()` return type: bare String vs. structured envelope?** TauRPC convention prefers structured envelopes (`StoragePathPayload { path: String }` allows future expansion like `{path, size_bytes, last_write_at, schema_version}` without breaking change). Recommend Phase 4 chooses structured envelope from start.
7. **`storage.inspect()` write-rejection by typing?** security rot warning surfaced no explicit test for "verify storage.inspect signature has only read-typed inputs." Recommend Phase 4 makes `inspect()` take NO arguments in chunk #68 scaffold (returns corpus metadata only); future filter-bearing inspect variant goes through a separate procedure (e.g., `storage.query_incidents(filter)`) that maintains the read-only-by-design discipline.
