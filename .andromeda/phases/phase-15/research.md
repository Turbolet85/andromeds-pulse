## Open questions

- **Where does `From<ingest::contract::Error> for AppError` live?** Arch §Conventions Error response schema says `ui-bridge` hosts `From` impls. Following that adds `[dependencies] ingest = { workspace = true }` to `ui-bridge/Cargo.toml`. This is a sibling-crate edge — permitted by arch §Cross-cutting Patterns "no library crate depends on a sibling unless its declared contract requires it" — and the From impl IS the declared contract. **Recommend Phase 4: ui-bridge depends on ingest, From impl lives in `crates/ui-bridge/src/contract.rs`.**
- **mpsc channel capacity (`MPSC_CAPACITY`)?** No specialist plan section pins a number. obs-plan §10 perf budget WebGPU 10k spans/sec implies sustained 10k/sec ingest; backpressure should not bite on normal load. A starting capacity of 1024 messages (each carrying a `Vec<Span>` batch of variable size, but capped per OTLP message at 8MB / typically <100 spans per Export call) gives ~10s of buffering at 100 batches/sec or ~1s at 1000 batches/sec. **Recommend Phase 4: 1024 starting; introduce `MPSC_CAPACITY: usize = 1024` constant in `crates/ingest/src/channel.rs` so future tuning has one knob.**
- **What is the `Batch` payload sent through the channel?** Options: (a) `Vec<u8>` raw protobuf bytes (zero-copy from the receiver); (b) decoded `ResourceSpans` / `ResourceMetrics` / `ResourceLogs` enum; (c) Arrow RecordBatch already (premature — buffer crate's job in Epoch 3). **Recommend Phase 4: decoded `enum Batch { Spans(Vec<ResourceSpans>), Metrics(Vec<ResourceMetrics>), Logs(Vec<ResourceLogs>) }`** — the receiver decodes once, validates invariants, then hands off the decoded vectors. Arrow conversion lands in Epoch 3 buffer chunk.
- **Does the `ready` envelope need a TauRPC procedure now?** Arch §Standard Contracts schema says `ready.checks.ingest_mpsc_capacity_pct` is a field. But the TauRPC `ready` IPC procedure is not yet wired (no `ReadyApi` analog to `HealthApi` in `ui-bridge`). **Recommend Phase 4: defer `ready` IPC procedure to Epoch 4 chunk #22 (Webview shell + TauRPC bridge); chunk #18 only stores the data, doesn't expose it.** The data path through `IngestState::snapshot()` is the hook — chunk #22 reads it.
- **Should mpsc capacity tracking be reactive (atomic-set on every send) or pull (Sender::capacity() called on read)?** Pull is simpler (no extra atomic write per ingest) and `tokio::sync::mpsc::Sender::capacity()` returns the live free capacity. **Recommend Phase 4: pull-mode — add a method on the `IngestSender` wrapper that exposes `capacity_pct()` returning a `f64` derived from `Sender::capacity()` / `MPSC_CAPACITY`.** Heartbeat tick reads this directly.
