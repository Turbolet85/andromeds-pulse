## Patterns detected

### Pattern 1 — Per-table appender triplet

The canonical pattern across `crates/buffer/src/appender.rs` for each reserved table:

```rust
pub(crate) fn build_<table>_record_batch(
    batch: &[Resource<T>],
) -> Result<Option<RecordBatch>, Error> {
    let mut col_a: Vec<...> = Vec::new();
    // ... per-column accumulators
    for outer in batch {
        for inner in &outer.scope_<T> {
            for item in &inner.<items> {
                if item.<id_a>.is_empty() || item.<id_b>.is_empty() {
                    continue; // defensive skip per chunk #18 receiver guarantee
                }
                col_a.push(item.<field>.clone());
                // ... per-column extraction
            }
        }
    }
    if col_a.is_empty() {
        return Ok(None);
    }
    // Build Arrow arrays + schema + RecordBatch with `.map_err(|e| Error::Append { reason: format!(..., short_err(...)) })`
}
```

Chunk #65 introduces `build_span_events_record_batch(batch: &[ResourceSpans])` using the same shape: outer loop on `rs in batch` → middle loop on `ss in &rs.scope_spans` → inner loop on `span in &ss.spans` → INNER-INNER loop on `(event_index, event) in span.events.iter().enumerate()`. Defensive skip applies at both span level (existing) AND event level (parent span_id/trace_id already validated by the span-level skip; events themselves have no own IDs).

### Pattern 2 — Dispatch in `consumer::dispatch_batch`

The production hot path (consumer.rs:78-121) handles ONE batch variant per call. For Batch::Spans:

```rust
Batch::Spans(s) => {
    let Some(rb) = build_spans_record_batch(&s)? else {
        return Ok(());
    };
    let encoded = encode_or_log(broadcast::encode_spans(&rb), STREAM_NAME_SPANS);
    let rows = append_record_batch_to_table(&guard, "spans", rb)?;
    (rows, &senders.spans, encoded)
}
```

Chunk #65 extends this branch to ALSO build + append span_events under the SAME `guard` lock (avoid second mutex acquisition). The broadcast remains spans-only per source plan "Broadcast topics delta: none / consumed via existing span broadcast". Recommended shape:

```rust
Batch::Spans(s) => {
    let Some(rb) = build_spans_record_batch(&s)? else {
        return Ok(());
    };
    let encoded = encode_or_log(broadcast::encode_spans(&rb), STREAM_NAME_SPANS);
    let rows = append_record_batch_to_table(&guard, "spans", rb)?;
    // chunk #65: span_events append on same connection; do not fail the batch
    // if span_events build returns Err — log + drop (parent spans already durable)
    if let Some(events_rb) = build_span_events_record_batch(&s)? {
        let _ = append_record_batch_to_table(&guard, "span_events", events_rb)?;
        // span_events row count NOT added to `rows` — `rows` is parent-spans count
        // mirroring the per-table semantic of BufferState::rows_ingested
    }
    (rows, &senders.spans, encoded)
}
```

Open design question for plan.md: do span_events rows count toward `BufferState::rows_ingested` (the heartbeat field) or NOT? Existing pattern is per-batch-type (Batch::Logs increments separately from Batch::Spans because they're different Batch variants). Span events are derived from a Batch::Spans batch — analogous to how OTLP-spec `Span.events` are nested INSIDE Span. Recommended: do NOT add span_events to `rows_ingested` (preserves the metric's "spans-or-metrics-or-logs ingested" semantic; future chunk #66 can surface span_events count via a different field if needed). Surface as `span_events_appended` log field on the `duckdb.append` event (already part of the existing field shape).

## Conventions to follow

1. **Schema DDL parity** — chunk #65 MUST update BOTH `CREATE_SPAN_EVENTS` const AND the SCHEMA_DDL concat string at `schema.rs:116-123` in lockstep; the `ddl_constants_match_concatenated_schema` test enforces parity. Forgetting one fails compile-test.
2. **Composite PK silent-drop trap** — per testing rules 2026-05-14, the buffer schema's composite PK silently drops duplicates. Test fixtures emitting N events per (trace_id, span_id) MUST use distinct `event_index` 0..N-1 (no duplicates); the round-trip assertion uses `SELECT COUNT(*) WHERE trace_id = ? AND span_id = ?` and asserts exactly N rows.
3. **Defensive-skip idiom** — per chunk #18 precedent + existing appender.rs:42-46 pattern, the appender skips items with empty parent IDs without panic. For span_events: skip the WHOLE span (no events appended) when parent span has empty trace_id/span_id. Per-event additional skip if needed: events with `time_unix_nano == 0` likely indicate malformed input (events SHOULD have non-zero timestamps per OTLP spec) — defensive choice: still append (capture user-content as-is per the at-rest data-classification per security plan §Data Protection); rely on receiver-side invariant to reject before reaching appender.
4. **Vendored proto stubs** — per testing rules 2026-05-04, use `ingest::grpc::proto::opentelemetry::proto::trace::v1::span::Event` (chunk #16 vendored stubs); never re-add `opentelemetry-proto` to deps. The `Span::Event` proto inner-message resolves through proto-generated tokio module nesting — verify exact path at impl time.
5. **`#[tracing::instrument]` skip discipline** — per obs rules 2026-05-11 + Session Addition wasmtime types: any new function taking `&[ResourceSpans]` MUST `skip(batch)`; explicit `fields(...)` allowlist if any aggregate counters are exposed (recommended: `fields(events_decoded, events_dropped)` if exposed at all; in this chunk the design recommendation is to NOT add a sub-span — the `duckdb.append` event from the dispatch boundary is the only emission).
