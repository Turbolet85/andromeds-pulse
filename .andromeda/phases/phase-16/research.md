## Open questions

- **Q1: Invalid port behavior — fail-startup vs fall-back-to-default?** Current `pulse-app/src/main.rs::resolve_grpc_port` falls back to `DEFAULT_GRPC_PORT` on parse failure with a `tracing::warn!`. Combined.md (security acceptance criterion) implies invalid port should FAIL the receiver startup with a sanitized one-liner. The two policies are incompatible. Surface to user at Phase 6 review:
  - **Option A (security-strict):** invalid env-var → `Error::InvalidPort` → `BindStatus::Failed("invalid_port")` → receiver does not start → health envelope degrades. User must fix the env var or unset it.
  - **Option B (compatibility-soft):** keep fall-back-to-default behavior; emit a structured `config.load.port_validation` warn event per Vector 6 with `env_var_name` + `reject_reason`; receiver starts on default port; health envelope stays "ok" but the warn is grep-able.
  - **Recommendation:** Option A — per security plan §Input Validation CLI/env-var row + arch §Established Decisions Validation Library "ports MUST go through TryFrom<u16>"; silent fallback masks misconfiguration. Compatibility cost: a typo in `ANDROMEDA_PULSE_OTLP_GRPC_PORT` now blocks startup instead of silently using `:4317`. Tests update accordingly.
- **Q2: `tower_governor` exact version.** crates.io has multiple 0.x versions. The plan should pin a specific version compatible with `tower 0.5` + `axum 0.8` + `tonic 0.14`; verify no transitive `tower 0.4` ↔ `tower 0.5` duplicate by running `cargo tree` post-add. Defer to /implement.
- **Q3: Rate threshold value.** combined.md (security) suggests "e.g., 50k req/min" — per security plan §API Security row 1. Plan.md should propose a concrete number (e.g., `RequestsPerMinute(50_000)`), defer to user override, or make it a code constant in `crates/ingest/src/lib.rs`. Recommendation: code constant `pub const OTLP_GRPC_RATE_LIMIT_PER_MINUTE: u32 = 50_000;` + `pub const OTLP_HTTP_RATE_LIMIT_PER_MINUTE: u32 = 50_000;` co-located with `MAX_DECODING_MESSAGE_SIZE` etc. — no new env var per arch §Occupied Resources discipline.
- **Q4: Per-source-port keying.** combined.md (security) calls for "per-source-port keying" — `tower_governor` supports custom key extractors. The KeyExtractor should compute the source's TCP port (not IP — all are loopback) so different local producers don't starve each other. Verify `tower_governor::key_extractor::SmartIpKeyExtractor` or similar handles loopback case correctly; if not, write a custom `LocalPortKeyExtractor`. Defer to /implement.
