## Combined goal

Promote the chunk #4 starter tracing scaffold (live in `pulse-app/src/main.rs:38-94`) into a dedicated `pulse-app/src/observability` module that satisfies the obs-plan §3 binding contract end-to-end: every JSON line carries the canonical service-identity envelope (`service.name` / `service.version` / `deployment.environment`, plus `ci.run.id` / `git.commit.sha` when present), the `tracing` ecosystem stack stays the only self-observation runtime (no OTel SDK linked), and a custom `FormatEvent` injects the default fields at serialization time so chunk #9's heartbeat ticks and chunk #15+'s a11y `target = "a11y::assertion"` events inherit identity automatically. Then layer in chunk #8's PII scrubber as a `tracing-subscriber::Layer` between `EnvFilter` and the JSON formatter, enforcing a per-module field allowlist (obs-plan §8 default-deny posture) so the security plan §Logging Vectors 1-6 NEVER-log list cannot leak through call-site discipline regression.

The plan is intentionally additive against the existing scaffold rather than a rewrite — chunk #4 already wired the daily file appender at `~/.andromeda-pulse/logs/agent-latest.jsonl`, the `EnvFilter` precedence (`ANDROMEDA_PULSE_LOG_LEVEL` → `RUST_LOG` → "info"), the `ErrorLayer::default()` for SpanTrace capture, and the `app.panic.fatal` hook that xtask `ci-gates` already greps. Chunks 7-8's scope is to (a) move the init body into a module so the scrubber can compose cleanly, (b) replace per-event identity emission with a default-fields injection so identity rides every line, (c) add CI env-var bounding + Unix mode-0700 hardening on the logs dir, (d) introduce the scrubber Layer + per-module allowlist, (e) add a `log_basename` helper for forthcoming plugin-path emitters, and (f) document a Sentry `before_send` shape as a comment-only stub (Sentry dep deferred per arch §Conventions feature-gate hygiene). Net result: the harness `logs` command (test-plan §3) sees fully-attributed JSON lines with PII scrubbed, and the `app.panic.fatal` xtask gate continues to pass without regression.

## Implementation notes

- **Order sensitivity:** implement chunk #7 steps 1-9 in order *before* starting chunk #8 step 1. Chunk #8's `PiiScrubLayer` composes into the registry that chunk #7 builds — without the registry refactored to take Layer composition, chunk #8 can't insert cleanly. The single-PR approach is fine; just keep commits sequenced.
- **Layer ordering is testable and load-bearing.** The `EnvFilter` → `PiiScrubLayer` → `json_layer_with_default_fields` → `ErrorLayer::default()` ordering is locked. A unit test that constructs a registry with the layers in the wrong order should fail (e.g., an EnvFilter after the scrubber would let scrubbed-but-still-emitted events through; a json_layer before the scrubber would serialize unscrubbed fields). This isn't strictly required for the chunk to pass, but it documents the invariant.
- **Custom `FormatEvent` vs root-span pattern (research.md Open Question 1):** the plan recommends custom `FormatEvent`. If the implementation phase finds the FormatEvent API too thorny against `tracing-subscriber 0.3.x`, the fallback is the root-span pattern (info_span! at main scope + `with_current_span(true)` already set on the layer at `main.rs:53`). Either approach satisfies the obs-plan §3 binding; the FormatEvent path is preferred because it doesn't require every tokio task to use `.in_current_span()` to inherit identity.
- **`temp_env` crate for env-isolated tests:** the CI env-var validation tests need to set/unset `GITHUB_RUN_ID` and `GITHUB_SHA` per-test without leaking state between tests. The test-plan §7 recommends `temp_env` 0.3 or `serial_test` 3 for env-isolation. If `temp_env` is not yet in workspace deps, add it under `[dev-dependencies]` in `pulse-app/Cargo.toml` for chunk #7. Verify after implementation.
- **Sentry deferral decisively:** do NOT add `sentry-rust` or `sentry-tauri` to workspace deps in this phase, even off-by-default. The arch decision is "Sentry feature decision deferred"; honoring that means zero dep-tree pollution. Activation is a future scope-arch entry. The comment-only stub in `observability.rs` is the entire chunk #8 Sentry deliverable.
- **Windows mode-0700 deferral with TODO:** the security plan §Logging "Access controls" specifies "ACL-restricted to current user on Windows" but `%APPDATA%` already inherits a user-restricted ACL by default. Adding explicit `windows-permissions` crate dependency to chmod-equivalent the logs dir would expand the dependency surface for limited security gain at this stage. The TODO comment marks the gap for a future security-scope-arch entry.
- **Daily-rotation test deferred to file-name-pattern check:** per research.md Open Question 6, full rotation behavior is not deterministically testable without a clock injection layer that `tracing-appender 0.2` doesn't natively expose. The unit test asserts the appender is constructed with the correct directory + file-name prefix; real rotation is verified operationally over a multi-day CI run (which won't happen until production deploys land — out of scope for chunks 7-8).
- **Boot-line slim down (chunk #7 step 8):** the existing `tracing::info!(target: "app.boot.tracing.init", service_name = ..., service_version = ..., deployment_environment = ..., log_dir = ?logs_dir, ...)` event at `main.rs:62-69` becomes redundant once default-fields injection is active (every event carries those identity fields). The replacement event (`target: "app.boot.tracing.init"`, fields: `log_dir = ?logs_dir`, `default_fields_active = true`) keeps the boot-line marker for grep'ing the harness boot moment but avoids restating identity that's already on every line.
