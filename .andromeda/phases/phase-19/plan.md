## Combined goal

Build out the `viz` crate's pull-query layer: introduce 3 TauRPC routers (`traces.query` / `metrics.query` / `logs.query`) that issue prepared-statement DuckDB SELECTs against the in-memory ring buffer, return the locked paginated envelope `{ items, total, next_cursor }`, and emit `query_id` + `param_count` + `param_types` anonymized self-observation logs (NEVER raw parameter values). The viz crate currently ships only a stub `Error::Placeholder` and a `VizHeartbeat::default()` payload — chunk #22 grows it into a fully-typed query surface mirroring the buffer crate's chunk #20/#21 patterns: per-query SQL constants, `Connection::prepare(sql) + stmt.execute([params])` parameter binding, `tokio::task::spawn_blocking` for the blocking DuckDB FFI, `tracing::info!` instrumentation with allowlisted fields only.

The acceptance gates converge from four domains. **Security**: the `format!`-grep gate over `crates/viz/src/` returns empty (no string-interpolated SQL); per-handler tracing emits `query_id`/`param_count`/`param_types` only; the new `From<viz::Error> for AppError` impl in `crates/ui-bridge/src/contract.rs` strips DuckDB error text / library versions / file paths / Rust struct names per chunk #20/#21 sanitization-test precedent. **Arch**: code lives entirely in `crates/viz/`; `cargo tree -p viz --depth 1` shows `buffer` as the only sibling crate dep (plus optional `ui-bridge` behind the `taurpc-runtime` feature for the AppError type — feature-gated so cycle resolves via cargo feature graph); every TauRPC procedure conforms to the locked `<router>.<verb>` shape and returns `Result<T, AppError>`; list responses use the `{items, total, next_cursor}` envelope with opaque-string cursor. **Tests**: co-located unit tests for each query function + integration test seeding ephemeral DuckDB and exercising each TauRPC router via `tauri::test::mock_builder()` + SQL-injection negative test (literal-binding assertion) + log-leakage test (no parameter values in tracing JSON capture); workspace `cargo nextest run` passes including new viz coverage. **Obs**: per-target allowlist in `pulse-app/src/observability.rs` extended with `time_window_seconds`/`traceparent`/`param_types` for the `viz` registry entry plus new `metric.trace.latency_percentiles` and `metric.trace.error_count` events; `viz.tick` heartbeat now reflects real `VizState` (subscribers_active + query_latency_ms rolling); `From<duckdb::Error>` conversion sanitizes at the viz boundary; trace context propagation via `traceparent` field on `viz.query.*` spans.

Per `combined.md §Cross-domain binding reconciliation`: the prepared-statement-only invariant established at the buffer crate (chunks #20/#21) extends here under co-ownership of arch §Established Decisions ORM/Migrations + security plan §Input Validation 2026 DuckDB CVE cluster; the `query_id`+`param_count` anonymization is the convergent enforcement point of security plan §Logging Vector 5 + obs-plan §6 Boundary-call wrappers. Chunk #22 deliberately ships a minimal-viable column shape (the 4 chunk #20 columns: `trace_id`, `span_id`, `ts`, `ts_unix_nano`) to keep scope tight; richer columns (service_name, duration_ms, status_code) require either a buffer schema extension (Trigger 4 amendment) or follow-up chunk wiring of a richer appender path — both are deferred from chunk #22.

## Implementation notes

- **Step ordering matters.** Build viz crate (steps 1-6) BEFORE ui-bridge changes (steps 7-9) BEFORE pulse-app changes (steps 10-12). Each layer adds dependencies that lower layers don't need; avoiding cross-layer recompiles during dev iteration speeds the loop.
- **Feature-flag cycle break.** viz depends on ui-bridge (for `AppError` type) only when `taurpc-runtime` is enabled; ui-bridge depends on viz (for `Error` type) unconditionally. Verify cargo resolves: `cargo build -p viz --no-default-features` must succeed; `cargo build -p viz` (with default `taurpc-runtime`) must succeed; `cargo build -p ui-bridge` must succeed in both modes.
- **taurpc 0.7 multi-router merge** — verify exact API at implement-time. If `taurpc::Router::new().merge(...).merge(...)` doesn't exist in 0.7, fall back to: define a single `#[taurpc::procedures]` super-trait in pulse-app combining health/traces/metrics/logs methods, and have a single `PulseApiImpl` that delegates to the per-crate impls. This is more boilerplate but ships if the merge form is missing.
- **Minimal-viable column shape.** Chunk #22 returns the 4 chunk #20 columns only (trace_id, span_id, ts, ts_unix_nano). Richer columns (service_name, duration_ms, status_code) require schema extension which is out of chunk #22 scope — DOCUMENT this in implementation comments + commit body so reviewers don't expect rich rows.
- **SQL-injection negative-test surface.** Since `time_window_seconds` is `u64` (not String), the cursor `Option<String>` is the actual user-controlled string surface where injection would manifest. Test seeds a payload like `Some("' OR 1=1 --".to_string())`, calls query_traces, and asserts: (a) the call returns `Ok(_)` (not a SQL error — the cursor is decoded as opaque string, not parsed as SQL); (b) `spans` table still exists post-call (DROP TABLE didn't execute); (c) the returned `items` reflect the literal cursor value being interpreted as a starting position (likely zero rows since no row matches the payload's bytewise interpretation as a `ts_unix_nano`).
- **AllowList `viz.query.traces` resolver behavior.** The `for_target` resolver in observability.rs:464-485 falls back from `viz.query.traces` → `viz.query` (no entry) → `viz` (existing entry). So the existing `viz` allowlist applies to `viz.query.traces` events without explicit registration. New target-specific entries (`viz.query.error`, `metric.trace.latency_percentiles`) DO need explicit registration — they don't fall back to `viz` since prefix-strip stops at the first dot/colon.
- **Pagination cursor encoding.** Simple choice: `next_cursor = base64(format!("{}:{}", last_row.ts_unix_nano, hex(last_row.trace_id)))`. The decode: parse the base64, split on `:`, parse u64 + hex bytes. NEVER expose this format to clients (opaque); tests should verify clients can roundtrip the cursor (pass it back, get next page) but should NOT depend on its internal structure. If pagination feels heavyweight for chunk #22, an alternative is "no cursor support yet, total = items.len() means single-page-only" — Phase 4 leans toward shipping cursor support since it's <50 LOC and the contract requires it.
- **Heartbeat tick parameterization regression risk.** Chunk #21 changed `emit_buffer_tick` signature; chunk #22 changes `emit_viz_tick` signature. Both are pure functions taking `&HeartbeatState` + new state arg — should be straightforward to extend tests. The existing `emit_viz_tick_emits_target_and_fields` test passes a fresh `HeartbeatState::new()`; new arg pattern `emit_viz_tick(&state, &viz_state)` requires a `viz_state = VizState::new()` setup line. Mechanical edit.
- **`.claude/rules/security.md` Session Addition 2026-05-03 reading.** Note line: "TauRPC integrates at the Tauri IPC channel level — a single invoke handler dispatches ALL router methods. Capability JSON `permissions` array contains `core:default` + plugin-level perms (e.g. `updater:default`), NOT per-procedure entries (no `"health"` / `"app_info"` strings). This is a tension with arch §Cross-cutting Patterns 'Webview IPC capability policy' which assumes per-procedure capability JSON pairing." The rolling-bucket aggregator (sliding window p50/p95/p99 per service) is documented in obs-plan §5 but not load-bearing for chunk #22; defer to chunk #46 (Obs CI gates) or a follow-up chunk.
