## Conventions to follow

- **Module visibility:** `pub mod {module};` + `pub use {module}::{public_types};` in lib.rs; everything else `pub(crate)`. (`crates/buffer/src/lib.rs` template.)
- **Error sanitization pattern at bridge boundary:** `From<viz::Error> for AppError` arms map to constant `"viz query failed"` / `"viz parameter validation failed"` / etc.; tests assert no DuckDB / version / path / struct-name leakage in serialized AppError. (`crates/ui-bridge/src/contract.rs:144-222` tests.)
- **Co-located unit tests via `rstest` fixtures + `tempfile::TempDir`:** `#[rstest]` + `#[fixture] fn fresh_conn() -> Arc<Mutex<Connection>> { ... }` + per-test in-memory DuckDB. (`crates/buffer/src/retention.rs:163-167` `fresh_conn_with_schema()`.)
- **`#[tokio::test]` (default `current_thread`) for paused-clock work**, `#[tokio::test(flavor = "multi_thread", worker_threads = 4)]` for actual concurrency assertions; per `.claude/rules/testing.md` Session Additions 2026-05-06, NEVER combine `start_paused = true` with `flavor = "multi_thread"` — drop one. (Buffer state.rs:110 + retention.rs:337-396 patterns.)
- **`tracing::info!(target: "{module}.{operation}", field = value, ...)` with allowlisted fields only**; raw OTLP-derived parameter values NEVER as fields. AllowList registration in `pulse-app/src/observability.rs::AllowList::production().by_target` is mandatory; `for_target` resolver supports prefix-strip + `.tick`-strip + exact match. - **Cargo dep additions: prefer `.workspace = true`** when the dep is already in `[workspace.dependencies]` (Cargo.toml lines 24-91). New deps need addition to the workspace section first.
- **Static SQL string constants** (`crates/buffer/src/retention.rs:14-22` + `crates/buffer/src/schema.rs:25-94`); never `format!`-built. Identifiers come from compile-time constants only.
- **Health envelope extension follows the BufferConnectionStatus pattern (`crates/ui-bridge/src/health.rs:30-34, 219-234`)**: `Ok / InitFailed(String) / RetentionFailed(String)` enum + `record_*` setter on HeartbeatState + match arms in `current_health()` for both healthy and degraded statuses.
- **TauRPC handler composition in `pulse-app/src/main.rs:208`**: currently `taurpc::create_ipc_handler(HealthApiImpl.into_handler())` accepts a single handler. ## Open questions

- **viz dep on ui-bridge or vice versa?** Established pattern (BufferError → AppError) uses ui-bridge depending on viz with `From<viz::Error> for AppError` impl. Chunk #22 follows that. viz `runtime.rs` returns `Result<T, AppError>` from TauRPC procedures, so viz needs ui-bridge for the `AppError` type. This creates `viz → ui-bridge` dep BUT also `ui-bridge → viz` for the From impl — circular. Resolution: viz depends on ui-bridge (for AppError type) gated by `taurpc-runtime` feature; ui-bridge depends on viz (for the Error type) unconditionally. The runtime module is feature-gated so viz crate built without `taurpc-runtime` does NOT pull ui-bridge. Workspace builds default to `taurpc-runtime` enabled, so cargo resolves the cycle via the feature graph. **Phase 4 will verify this works** at implement time; alternative is to put the `From<viz::Error>` impl in viz crate behind feature flag (less clean).
- **Multi-router invoke_handler composition in taurpc 0.7**: the `taurpc::create_ipc_handler(SingleApi.into_handler())` form takes a single handler. Verify the merge/router composition idiom exists in taurpc 0.7; if not, the runtime module may need to compose a single super-trait combining health + traces + metrics + logs. Phase 4 reviews taurpc API docs at implement-time.
- **Initial query shape — what columns does `traces.query` return?** spans table schema has `trace_id BLOB, span_id BLOB, ts TIMESTAMPTZ, ts_unix_nano BIGINT` (chunk #20 minimal). Real trace rows for the webview need at minimum service_name + duration_ms + status_code + parent_span_id, but those columns DO NOT EXIST in the chunk #20 schema. **Chunk #22 must either:** (a) extend the spans table schema to include service_name/etc. (architectural — likely needs a Trigger 4 spec amendment); OR (b) return only the columns chunk #20 actually shipped (trace_id, span_id, ts, ts_unix_nano) and defer richer query results to a future chunk where the appender writes more columns. **Recommended Phase 4 decision:** option (b) — minimal-viable query returning the existing 4 columns — keeps chunk #22 scope tight and lets the appender's column extension land separately. Document as "follow-up chunk" if needed.
- **Pagination cursor opacity:** arch §Standard Contracts says `next_cursor` is "opaque string". For chunk #22's first iteration, `next_cursor = base64(last_row_ts_unix_nano + last_trace_id)` is a simple opaque encoding that supports keyset pagination on `(ts_unix_nano DESC, trace_id)`. **Phase 4 picks** the exact encoding; tests assert cursor opacity (frontend shouldn't parse).
