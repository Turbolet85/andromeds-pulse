- **Order sensitivity:** step 1 (rename HealthApi → IntrospectionApi) MUST land before step 7 (wire IntrospectionApi in pulse-app/src/main.rs) — otherwise the test harness `emit_taurpc_bindings` fails. Step 5 (AllowList entries) can land independently and is verified by step 6's test before step 7 wires the actual emitters.

The TS file should be re-committed as part of chunk #27 (same pattern as chunk #25). Verify `git diff pulse-app/ui/src/bindings/index.ts` shows the 5 new procedures.
- **D3 drift surfacing intent:** when step 11's `cargo xtask capability-drift` runs, the `streams.*` namespace WILL appear in the `extra` set. This is intentional — chunk #27 surfaces; resolution is a follow-up architectural decision (either `/andromeda-scope-arch` to legitimize streams.* OR revert chunk #23). Document the result in the wrap-session handoff as a follow-up; do NOT proactively resolve in chunk #27 (per session-handoff D3 carry-over note).
- **Compile-time `app_info.tauri_version` resolution:** there is no built-in `CARGO_PKG_VERSION_TAURI` env var. Options: (a) parse `[workspace.dependencies] tauri = "2.x"` from `Cargo.toml` at build time via build.rs; (b) hardcode in a constant updated when Tauri version changes; (c) expose via `tauri::VERSION` if available at runtime. Orchestrator picks during implementation; (b) is simplest with a `// keep in sync with workspace tauri dep` comment.
- **Settings persistence path:** the `~/.andromeda-pulse/config.toml` location is resolved by `pulse-app/src/main.rs::resolve_data_dir()`. To avoid duplicating logic in ui-bridge (which is a library crate), preferred path: extract `resolve_data_dir()` to a small `ui-bridge` helper module (e.g., `crates/ui-bridge/src/config_path.rs`) that depends only on `std::env` + `std::path`; pulse-app re-imports. This keeps the DAG clean (ui-bridge owns config-path resolution; pulse-app consumes).
- **xtask `tracing` init:** the existing xtask doesn't initialize tracing (commands print directly to stdout/stderr). Step 8.8's `tracing::info!` emission requires either (a) initializing a minimal `tracing-subscriber` for the duration of capability-drift command, OR (b) writing the structured event directly to stdout as JSON. **Recommendation: option b** for chunk #27 — keeps xtask boundary simple and matches the existing `harness:status` pattern. The obs criterion ("emits a `tracing::info!` line in `agent-latest.jsonl`") can be satisfied by writing a single JSON line that conforms to the obs schema, without needing a tracing subscriber. Document the choice in the implementation.
- **CI step placement:** the `cargo xtask capability-drift` step belongs in the lint job (cheap, no test runtime needed), not the test matrix job (would re-run 3× across OS targets unnecessarily). Place after `cargo clippy` and before `cargo test`. Upload artifact step uses `actions/upload-artifact@<SHA>` — SHA pinning lookup is a 5-minute github.com fetch task during implementation.
