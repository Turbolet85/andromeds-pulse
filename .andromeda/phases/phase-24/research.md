## Patterns detected

- **TauRPC procedure declaration pattern** (`crates/ui-bridge/src/health.rs:284`, `pulse-app/src/streams.rs:14`, `pulse-app/src/viz_routers.rs`): `#[taurpc::procedures(path = "name")] pub trait NameApi { async fn method(...) -> Result<T, AppError>; }` + `#[taurpc::resolvers] impl NameApi for NameApiImpl { ... }` + `pub use runtime::{NameApi, NameApiImpl}` re-export under `#[cfg(feature = "taurpc-runtime")]` mod runtime block. Existing routers always provide a `path = "..."` namespace — top-level (no path) hasn't been used yet but is supported per `taurpc::procedures` macro semantics.
- **`current_health()` direct-call pattern** (`xtask/src/main.rs:100`): xtask invokes `ui_bridge::health::current_health()` directly without going through the TauRPC IPC roundtrip — possible because ui-bridge is built without `taurpc-runtime` for xtask (Tauri runtime DLLs unavailable on Windows xtask without WebView2). Chunk #27's xtask drift command can reuse this pattern: link ui-bridge minimally + introspect procedure list via a compile-time constant or JSON-bindings parse, no IPC handshake.
- **AppError From-impl matrix with tracing emission** (`crates/ui-bridge/src/contract.rs:43-97`): every From impl emits `tracing::warn!(target: "ui-bridge.error.{variant}", error_category, source_kind, source_crate, "{message}")` BEFORE constructing the AppError variant. Chunk #27's 5 introspection procedures inherit this discipline — sibling-crate errors flow through these From impls, full chain stays in `tracing-error::SpanTrace` log only.
- **AllowList per-leaf entry discipline** (`pulse-app/src/observability.rs:580-643`): each new TauRPC procedure emitting structured fields needs an explicit AllowList entry keyed by exact target string. Existing entries: `ingest`, `buffer`, `viz`, `plugins` (heartbeat ticks), `app.boot.*`, `tray.*`, `app.panic.fatal`, `a11y::assertion`, `metric`. Chunk #27 needs 6 new entries: `ui-bridge.app_info`, `ui-bridge.health`, `ui-bridge.ready`, `ui-bridge.get_settings`, `ui-bridge.update_settings`, `xtask.capability_drift`.
- **TauRPC bindings file as introspection artifact** (`pulse-app/ui/src/bindings/index.ts:31-38`): the `ARGS_MAP` constant at line 31 (single-line JSON-encoded string) and the `Router` type at line 32-38 both enumerate all (router, method) pairs across the workspace. Both are emitted atomically by `Router::into_handler()` in dev mode. Parsing either gives the canonical procedure list at chunk #27's drift-check time.
- **`taurpc::Router` merge pattern** (`pulse-app/src/main.rs:226-238`): the binary mounts every router via `.merge(NameApiImpl::new(...).into_handler())`. Chunk #27 introduces a new top-level `IntrospectionApi` trait + impl (or extends existing HealthApi) and merges it into the same Router. ## Conventions to follow

- **Procedure naming convention** (per arch §Conventions "Endpoint naming"): bare `snake_case` verbs at top-level for cross-cutting envelope (`app_info`, `health`, `ready`, `get_settings`, `update_settings`); `<router>.<verb>` dotted for per-crate routers (already established in chunks #22, #23, #25). Chunk #27's 5 introspection procedures MUST conform to top-level shape — this requires either (a) reorganizing `HealthApi { check }` to top-level `health` OR (b) adding a new `IntrospectionApi` without `path = "..."` for top-level emission. Currently chunk #25 emitted `health.check` as a regression of arch convention — chunk #27 should fix this OR document the deviation.
- **TauRPC envelope JSON shape per arch §Standard Contracts**: `app_info` returns `{name, version, rust_version, tauri_version, features, build_profile}`; `health` returns `{status, checked_at, subsystems, [pid, uptime_ms]}` (impl already extends with pid/uptime per test-plan §3 + verification-harness.md status shape); `ready` returns `{ready, checked_at, checks}` with `checks.{duckdb_connection, ingest_mpsc_capacity_pct, broadcast_subscribers, plugins_loaded, mcp_server_enabled}`. The implementation may extend (pid/uptime) but cannot rename or omit the documented keys.
- **Settings field naming** (arch §Conventions "Configuration units"): `snake_case` + units-explicit (e.g., `retention_seconds`, not `retention`); ports as `u16` validated via `TryFrom<u16>` (existing pattern at `pulse-app/src/main.rs:86-117`); enums for bounded choices (e.g., `theme: Theme::Dark | Theme::Light | Theme::Auto`).
- **Test colocation** (per testing.md §File placement): `#[cfg(test)] mod tests { ... }` within each crate's `src/` — chunk #27 tests live in `crates/ui-bridge/src/health.rs` (extending existing module), `crates/ui-bridge/src/contract.rs` (if Settings struct lands there), `xtask/src/main.rs`, `pulse-app/src/observability.rs` (allowlist verification).
- **Tracing `#[instrument]` discipline** (per observability.md "Span discipline"): `#[tracing::instrument(skip_all, fields(traceparent = %tp, method_name, argument_digest, result_type, latency_ms, span.kind = "server"))]` on every TauRPC handler; `argument_digest` is a hash, NOT raw payload (per obs PII Vector 6).

## Open questions

1. **Top-level vs `path = "health"` reorganization** — chunk #25 emitted `health.check` (dotted) but arch §Occupied Resources lists `health` as top-level. Chunk #27 should fix the convention drift. Three options to surface in Phase 6 user review:
   - **Option a**: Remove `path = "health"` from HealthApi, rename `check()` → `health()`, regenerate bindings (preferred — minimal scope, conforms to arch).
   - **Option b**: Add new top-level `IntrospectionApi { app_info, health, ready, get_settings, update_settings }` and deprecate `HealthApi.check` (parallel convention; cleaner separation but doubles surface).
   - **Option c**: Keep `health.check` as-is and update arch §Occupied Resources to list `health.check` (drift-down-to-impl; arch loses authority).
   
   **Recommendation: option a** — chunk #25's `health.check` was a chunk #25 implementation choice not an arch decision; the bindings file is a dev-only artifact (no shipping webview yet) so renaming is mechanical (test fixtures + 1 binding regen). Arch §Standard Contracts wins.

2. **xtask drift-check introspection mechanism** — bindings.ts parse vs static expected-list. Two options:
   - **Bindings.ts parse**: parse the `ARGS_MAP` line (regex `^const ARGS_MAP = (\{.+\})`) → JSON.parse → enumerate `(router, method)` pairs. Compare against arch §Occupied Resources (hard-coded constant in xtask). Pro: bindings.ts IS the canonical taurpc-generated artifact; updates atomically. Con: depends on taurpc binding format — if taurpc 0.8 changes the JSON shape, the parser breaks.
   - **Source-grep**: walk `crates/*/src/*.rs` + `pulse-app/src/*.rs` looking for `#[taurpc::procedures(path = "X")]` or `#[taurpc::procedures]` + extract `async fn` method names. Pro: no dependency on bindings.ts format. Con: brittle text parsing of Rust source.
   
   **Recommendation: bindings.ts parse via JSON.parse on the `ARGS_MAP` line** — bindings.ts is already gated by chunk #25 typecheck (`tsc --noEmit`); if ARGS_MAP shape changes, typecheck catches it before the drift check runs. Single source of truth.

3. **Settings struct scope at chunk #27** — the design extract specifies `theme: dark|light|auto` is required (with `dark` default); arch §Cross-cutting Patterns Config management says writes go to `~/.andromeda-pulse/config.toml`. But the full Settings field list isn't enumerated in any extract — design suggests `widget_position`, obs implies `mcp_server_enabled` + `notifications_enabled`, arch §Occupied Resources Environment variables suggests `retention_seconds` (parallel to `ANDROMEDA_PULSE_RETENTION_SECONDS`). For chunk #27 plan:
   
   **Recommendation: minimum viable Settings struct** — `theme: Theme (default Dark)`, `widget_position: WidgetPosition (default TopRight)`, `retention_seconds: u64 (default 600, validated 60..=86400)`, `mcp_server_enabled: bool (default false)`, `notifications_enabled: bool (default true)`. All other fields deferred to chunk #34 (Settings modal form) where webview UI surfaces them. This keeps chunk #27's wire-shape focused on what the IPC introspection contract requires NOW; future fields don't need new procedures, just struct field additions.
