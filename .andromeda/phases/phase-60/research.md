## Open questions

1. **Histogram interpretation — bucket-of-density OR bucket-of-quiet-streaks?** pulse-v0_2_0-route §64 wording "Per-service activity histogram (24h rolling, bucketed by 5-min intervals, 288 buckets)" admits two readings:
   - (a) Each bucket counts observations in its 5-min wall-clock slot of the day. Quiet-duration tracking is a separate concern (per-service `last_observed_unix_nanos` field). p95-historical is computed over a `TDigestPair`-backed distribution of observed inter-observation gaps. **This requires two distinct data structures** (the bucket histogram for activity-density observability metric + a TDigest of gap durations for the p95 gate).
   - (b) The 288-bucket histogram IS the quiet-duration distribution: each bucket = "number of observed quiet durations falling into this size class" (bucket k = `[k*5min, (k+1)*5min)` quiet-duration range). p95 read directly from histogram cumulative-density. **This is one data structure** but loses the "activity-by-time-of-day" diagnostic.
   - **Recommendation for plan**: interpretation (a) — use a `RollingWindow<u32>`-style 288-bucket array indexed by `(now_nanos / 5min_nanos) % 288` for the activity density (24h rolling automatic since the array wraps), PLUS a `TDigestPair` over observed quiet-duration gaps for the p95 gate. Two structures, but each is well-precedented (chunk #61 already uses both `RollingWindow<u32>` and `TDigestPair` patterns) AND the activity-density buckets serve the obs `metric.triage.activity_floor.bootstrap_state` deliverable. User confirms or redirects at Phase 6 review.
2. **Min-persistence gate for ServiceWentSilent?** ErrorRateSpike + LatencyRegression use `min_ewma_samples` (warm-up) + `min_persistence_seconds` (Autonomous-tier gate). ServiceWentSilent has its own warm-up (the 1h bootstrap window) but does it need a separate min-persistence gate? Spec says "current quiet duration > p95 historical quiet duration" — no second gate mentioned. **Recommendation**: no second gate; rely solely on the bootstrap window + p95 comparison. User confirms at Phase 6.
3. **Cardinality cap for activity-floor data?** Security extract recommends "per-instance cardinality cap (e.g., 256 services) and a deterministic eviction policy". The existing `DEFAULT_SERVICE_COUNT_CAP = 1024` (baseline/corpus.rs:8) caps the DashMap entry count at corpus-load time but does NOT enforce a cap at observe-time (an in-process flood between persists could overflow). **Recommendation**: chunk #64 adds an `observe()`-time cap check in `BaselineState::observe_span` — if `self.services.len() >= DEFAULT_SERVICE_COUNT_CAP` AND the incoming service is not already present, increment a `service_cap_exceeded_total` counter + drop the span. Eviction policy: LRU OR FIFO — DECISION POINT for plan. Per security extract 2026-05-17 §Threat Model OTLP user-content boundary, this guard belongs in chunk #64 (the cap is currently advisory at corpus-load only).
4. **Do we add `tokio = { features = ["test-util"] }` to triage's dev-deps?** Required only if the 1h bootstrap-window test wants paused-clock simulation. **Recommendation**: NO — pass `now_nanos` explicitly to all `BaselineState::*` methods (already the established pattern at chunks #61-#63); tests construct synthetic timestamps for sub-second + multi-hour scenarios without needing paused clock. Avoids the testing.md 2026-05-06 `start_paused × multi_thread` incompatibility entirely.
