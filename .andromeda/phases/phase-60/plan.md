## Combined goal

Add per-service activity-floor learning to the L1b streaming distillation layer (`crates/triage/baseline/`) so the platform can emit `ServiceWentSilent` attention cues only when a service's current quiet duration meaningfully exceeds its own learned historical quiet-duration distribution — solving the "developer-on-lunch" false-positive class while preserving chunk #63's restart-window discipline. Each per-service tracker maintains a 24h rolling activity-density histogram (288 buckets of 5-min intervals) plus a streaming distribution of observed inter-observation gaps used as the p95 gate; ServiceWentSilent emission is universally suppressed during the first 1-hour bootstrap window for that service (cold-start blindness elimination per pulse-v0_2_0-route §64). Cardinality is bounded per-instance (security plan §Input Validation OTLP user-content boundary) to prevent the local desktop process from OOMing under malicious or buggy instrumented hosts emitting unbounded distinct service identifiers.

Implementation extends the existing `ServiceBaseline` struct in `crates/triage/src/baseline/mod.rs` with one new field (`activity_floor: ActivityFloor`), routes the per-span observation through the new tracker via the existing `BaselineState::observe_span()` entry point (no new SpanObserver adapter — chunk #62's `BaselineObserverAdapter` already delivers spans here), and adds a sibling pure synchronous evaluator `evaluate_service_went_silent` consumed by the existing 1-2s `run_one_emit_cycle` tick. ServiceWentSilent cues piggyback on the chunk #62 `pulse://stream/attention-cues` broadcast topic + the `AttentionCue` envelope using the already-declared `CueKind::ServiceWentSilent` variant (chunk #60 scaffold) — zero new broadcast topics, zero new TauRPC procedures, zero new env vars, zero new workspace crates per pulse-v0_2_0-route §64 "all deltas: none". The chunk #63 surgical-suppression filter `evaluate_with_suppression` already passes ServiceWentSilent cues through unchanged (it only filters `CueKind::ErrorRateSpike`), so no integration change at the suppression layer.

Per arch §Cross-cutting Patterns "Self-observation discipline" + obs plan §3, all new instrumentation uses the `tracing` ecosystem (NO OTel SDK link); new tracing targets follow the established `triage.baseline.{operation}` naming convention and require corresponding `AllowList::production()` entries in `pulse-app/src/observability.rs` per the default-deny + per-leaf-registry pattern (testing.md 2026-05-07 lesson). Per arch §Cross-cutting Patterns "Module dependency direction", no new sibling-crate dependency is introduced (triage continues to depend only on serde / thiserror / tracing / tdigest / dashmap / tokio per the chunk #61 dep set).
