## Open questions

- **Env var naming convention compliance**: arch §Occupied Resources Environment variables sub-section names every other path-shaped var с `_PATH` or `_DIR` suffix (`ANDROMEDA_PULSE_CONFIG_PATH`, `ANDROMEDA_PULSE_DATA_DIR`, `ANDROMEDA_PULSE_PLUGIN_DIR`, `ANDROMEDA_PULSE_MODEL_PATH`). The new vars introduced by session 144's arch text are `ANDROMEDA_PULSE_LLAMA_CUDA_BIN` + `ANDROMEDA_PULSE_LLAMA_CPU_BIN` — both lack `_PATH` suffix despite being binary-file paths. Plan should decide: (a) rename to `ANDROMEDA_PULSE_LLAMA_CUDA_BIN_PATH` + `ANDROMEDA_PULSE_LLAMA_CPU_BIN_PATH` for full convention adherence (preferred per arch §Conventions); (b) document the deviation rationale at /implement time + register the bare-form vars in arch.md §Occupied Resources via `/andromeda-evolve --allow-arch-registry` follow-on amendment. (a) is mechanically trivial — only the LlamaCliInference source + the two test cases touch the env var name; no production env-var docs reference them yet.
- **Strict-path canonicalization model**: chunk #41's `canonicalize_plugin_dir` confines under а bounded root dir (the data dir); binary paths have no analogous "must live under data dir" confinement (the user picks any install location like `/tmp/llamacpp-cuda/llama-cli.exe`). Recommendation: implement а simpler `canonicalize_llama_bin_path(path) -> Result<PathBuf, InferenceError>` that does (1) `Path::canonicalize()` (resolves symlinks + ".." segments) + (2) `metadata().is_file()` assert (ensures the resolved path is а regular file, not а directory / symlink loop / nonexistent). This matches the spirit of the security extract requirement ("canonicalize via `strict-path` and assert points at an executable") without forcing an artificial confinement root. Plan should confirm the looser model is acceptable OR opt into а defined "allowed binary parents" list (e.g., `/usr/local/bin`, user home, an `ANDROMEDA_PULSE_LLAMA_BIN_ROOT` if added later).
- **Subprocess timeout default**: combined.md does NOT specify а default wall-clock timeout for the `tokio::time::timeout` wrap. The empirical L4 invocation rate (1-4/min per session 144 analysis) + observed warm-cache invocation time (~4.3s for 530-byte L4 JSON under GBNF constraint) suggest а timeout in the 30-90s range strikes balance: large enough к accommodate cold-start (~5s CUDA load) + large prompts + safety margin; small enough к surface а runaway/hang within а few cadence cycles. Plan should choose а default (recommend 60s) + decide whether to expose as а Settings field for tuning (chunk #84 plan default: hardcode the 60s constant + defer Settings extension к а follow-up chunk if needed).
