## Open questions

1. **SnapshotApiImpl location: stay in `ui-bridge` or relocate to `pulse-app/src/snapshot_runtime.rs`?**
   - **Stay in ui-bridge**: requires adding `buffer` + `viz` deps to `crates/ui-bridge/Cargo.toml` (or wiring through a trait abstraction with a small adapter); requires deferred-AppHandle pattern (`Arc<OnceCell<AppHandle>>`) since SnapshotApiImpl is currently constructed before setup closure. **Pro**: minimal `main.rs` churn. **Con**: ui-bridge gains heavyweight deps (buffer pulls duckdb, viz pulls query infrastructure) — increases the substrate-crate footprint contrary to its role.
   - **Relocate to pulse-app**: mirrors `viz_routers.rs` + `streams.rs` precedent; `SnapshotApiImpl::new(Arc::clone(conn), Arc::clone(&viz_state), app_handle)` constructable inside setup closure with all needed handles; ui-bridge reduces back to trait-only (or drops `snapshot_ipc` entirely if pulse-app provides the trait via its own module). **Pro**: matches existing convention, keeps ui-bridge substrate-pure, AppHandle injection straightforward. **Con**: larger `main.rs` patch (`use ui_bridge::snapshot_ipc::...` → `mod snapshot_runtime;`); requires re-exporting `SnapshotApi` trait from `pulse-app/src/snapshot_runtime.rs` to satisfy `#[taurpc::procedures(path = "snapshot")]` macro placement constraints.
   - **Recommendation**: Relocate to pulse-app (matches established pattern + cleaner architecture per arch §Cross-cutting Patterns Module dependency direction). Surface to user at Phase 6 for confirmation.

2. **Should `InvestigationContext` be extended with `snapshotResult` state, OR should `InvestigationModalForm` hold result state locally?**
   - **Extend context**: matches phase-40/plan.md step 11 recommendation; allows other components (e.g., tray menu showing "Recent snapshot: 2.5k tokens") to consume result state. **Con**: requires provider-wrap audit (chunk #42 caught 3 files); larger test-fixture-update surface.
   - **Keep local**: simpler scope for chunk #44; only InvestigationModalForm uses the result currently. **Con**: future use cases would need to refactor.
   - **Recommendation**: Keep local for chunk #44; extend context only when a second consumer appears. Less risky surface area; matches "smaller chunks" preference in route discipline.

3. **Span-load entry point for snapshot.generate runtime body**: query DuckDB directly via the held `Arc<Mutex<Connection>>`, OR call into the existing `viz` crate's query functions?
   - **Direct DuckDB**: simpler one-shot SQL query `SELECT * FROM spans WHERE ts > now() - INTERVAL '{retention} minutes'`; requires duplicating Row → SpanRecord materialization that the viz crate already does.
   - **Via viz crate**: reuses existing materialization (trace row → SpanRecord); adds dep on viz from snapshot resolver code (already imported by pulse-app at line 22 `use viz::VizState`).
