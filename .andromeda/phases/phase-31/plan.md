Fill the TracesRoute placeholder (currently a chunk #31 side-by-side composition of the substrate `<CanvasContainer>` + chunk #31 `<HaloCanvas>`) with the wireframe-mandated three-region stack: a per-service constellation map in the hero region, a sortable trace data table in the main region, and (deferred to a later chunk) a footer status bar. The chunk is webview-mostly with two small Rust touch points: extending the `TraceRow` struct in the `viz` crate to add `service: String, duration_ms: u64, error_count: u32` (the table needs columns the current 3-field shape doesn't carry), and extending `xtask/src/main.rs::EXPECTED_PROCEDURES` to clear the persistent D3 capability-drift carry-over from chunks #23/#29 (per session-handoff Priority 3 — coupling D3 cleanup with chunk #34 since #34 consumes those procedures heavily). No new TauRPC procedure namespace is introduced; capability JSON is unchanged.

Per security plan §Input Validation + §Logging anti-patterns: any new sort/filter parameter shape must use `serde`-deserialized argument structs with bounded enums (no free-form `String` flowing into DuckDB), and any tracing instrumentation in the rendering pipeline must NEVER interpolate raw OTLP attribute values (`service.name`, error messages) into log fields. Per obs plan §10: the per-frame `metric.webgpu.frame_duration_ms` p99 ≤ 33ms SLO must hold across multi-service rendering load, achieved by reusing chunk #31's `recordFrameMs(...)` bridge + a single WebGPU canvas with N draw calls per frame (rather than N independent canvases). ## Implementation notes

- **TraceRow extension precedence:** locate the struct definition first (Step 1) before extending; chunk #34 should not break any existing query.rs / state.rs callers. The 3 new fields (`service`, `duration_ms`, `error_count`) are additive — existing call sites unpacking `(trace_id, span_id, ts_unix_nano)` continue to compile.
- **DuckDB query path:** the existing `traces.query` resolver uses prepared statements with `?` placeholders (per chunk #25 baseline + security plan §Input Validation row "DuckDB query parameters"). The extension MUST preserve this; add new `SELECT service_name, ((end_time_unix_nano - start_time_unix_nano) / 1_000_000) AS duration_ms, ...` columns to the existing prepared SELECT, NOT a new `format!()` SQL string.
- **D3 cleanup ordering:** extend `xtask/src/main.rs::EXPECTED_PROCEDURES` BEFORE running `cargo xtask capability-drift` for the first verification — otherwise it'll show the same 4 extras as chunk #32 baseline (no regression, just no progress). After the extension, expect 0 extras / 0 missing.
- **WebGPU multi-instance rendering choice:** simplest path for v1 is N `pass.draw(6)` calls per frame with per-call uniform writes (chunk #31 pattern repeated N times). Instanced rendering (`pass.draw(6, N)` + per-instance storage buffer) is more performant for large N but adds complexity. v1 = N draws; defer instancing if perf SLO tightens with realistic service counts (typically 5-50, well within budget).
- **Live-update batching:** Arrow IPC payloads from `streams.subscribe_spans` arrive at irregular cadence. Per-service refs (analogous to chunk #31's `throughputHzRef` / `errorRateRef`) hold latest aggregated values; the rAF loop reads from refs each frame. Aggregation (count + error_count per service over a sliding window) happens in `useConstellationData` hook on each subscribe callback.
- **Boot-smoke gate caveat:** per test-plan §12 amendment, the gate is triggered specifically by changes to `pulse-app/src/main.rs` / `crates/ui-bridge/src/` / `pulse-app/src-tauri/tauri.conf.json` / `pulse-app/capabilities/*.json`. Chunk #34 strictly only modifies `crates/viz/src/` (Rust) + `xtask/src/main.rs` (xtask) + webview files. The gate is INCLUDED in this plan as a defensive measure because TraceRow flows through TauRPC bridge — but if the implementation hits no boot-path code, the gate may be skipped per the amendment letter; flag at Phase 6 user review for confirmation.
- **Fallback strategy when navigator.gpu undefined:** ConstellationCanvas renders `<Fallback />` (chunk #28 component); the trace table below remains fully functional (table rendering doesn't require WebGPU). Users without WebGPU still get the chunk #34 value via the table; only the constellation visual is degraded.
