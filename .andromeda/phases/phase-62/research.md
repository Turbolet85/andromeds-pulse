## Open questions

1. **Storm-detector evaluation cadence**: chunk spec implies "1-2s cadence" (per `triage::cue::DEFAULT_TICK_INTERVAL` chunk #62 precedent for emitter) but the cleanest design is inline detection at observer hook time (storm cue emits within microseconds of the 5th/10th occurrence rather than waiting для the next tick). Plan.md proposes inline detection. Tick task purpose narrowed к heartbeat-only (`triage.pattern.storm.tick` every 15s reporting tracked-count + evicted-count) — no per-tick threshold scan. **Decision:** inline detection + 15s heartbeat tick (mirrors chunk #63 RestartDetector pattern exactly).

2. **Storm-cue dedup window**: spec says "≥5/30s → Suggested, ≥10/30s → Autonomous" but doesn't specify whether the 6th/7th/8th/9th occurrence (still in Suggested tier) emits additional cues OR if Suggested fires ONCE per fingerprint per 60s rolling window. Plan.md proposes one-shot dedup: per (fingerprint, tier) — Suggested fires on 5th crossing; Autonomous fires on 10th crossing; subsequent occurrences silent until count drops below 5 then re-crosses. **Decision:** one-shot per-tier dedup with `last_emitted: Option<(i64, PriorityTier)>` per fingerprint state. Re-emit only if `now - last_emitted.0 > window_seconds * 1e9` OR escalating to higher tier.

3. **AttentionCue magnitude/absolute_value derivation for storm cues**: the chunk #62 `AttentionCue` shape has `magnitude: f64` + `absolute_value: f64` + `confidence: f64` fields that don't have natural analogs для discrete-count storm detection. Plan.md proposes: `magnitude = occurrence_count as f64 / DEFAULT_SUGGESTED_THRESHOLD as f64` (so 5 occ → 1.0, 10 occ → 2.0, 20 occ → 4.0); `absolute_value = occurrence_count as f64`; `confidence = (occurrence_count as f64 / DEFAULT_AUTONOMOUS_THRESHOLD as f64).min(1.0)` (so 5 occ → 0.5, 10 occ → 1.0). `persistence_seconds = (now_nanos - oldest_timestamp_nanos) / 1e9 as u64`. **Decision:** populate these fields per the derivation above для downstream consumers (model interpretation per P-020 may use them); but `priority_tier` is set directly from threshold crossing (NOT via `classify_priority` — short-circuits to ensure 5+ occ → Suggested, 10+ occ → Autonomous regardless of classify_priority's standard thresholds).

4. **EvidenceRefs population для storm cues**: chunk #66 spec doesn't explicitly mention EvidenceRefs; but the `AttentionCue` shape requires it as inherent field? Re-reading: `AttentionCue` does NOT have an EvidenceRefs field — that's on `Incident` (downstream of cue interpretation per P-020). Storm cues populate `scope_id = Some(service_name)` + the fingerprint hash is implicit via `kind = CueKind::RetryStorm` + magnitude/count fields. **Decision:** no EvidenceRefs payload changes для chunk #66; downstream chunks (P-020 interpretation) may attach fingerprint_hash to derived Incident records.

5. **Workspace dep migration test для blake3**: chunk #66 adds a new workspace dep (`blake3 = "1"`). Security extract requires `cargo deny check bans licenses sources` to pass. Verify pre-implementation: (a) blake3's license is MIT/Apache-2.0 (compatible с workspace SPDX allowlist; blake3 is dual-licensed Apache-2.0/CC0); (b) blake3's transitive deps don't introduce new banned-multiple-versions duplicates (chunk #66 plan Phase 2b will `cargo tree -p buffer | grep blake3` post-add to verify). **Decision:** add gate-failure recovery path к plan.md (if cargo deny rejects blake3, fallback к `sha2 = "0.10"` already in lockfile as transitive — same fingerprint contract, slightly slower but no new dep audit needed).
