## Open questions

- **Path A vs Path B at Phase 6:** the user chose Path B for chunk #34 (full schema extension). For chunk #35, the equivalent Path B doubles the cross-crate ripple (metrics_points + log_records, vs chunk #34's spans only). Path A preserves UI shell quickly but ships placeholder log content (no body, no trace_id correlation possible — undermining the "log stream with span correlation" route description). **Recommendation:** surface Path B as preferred (preserves the chunk's stated capability "span correlation + severity colors" — the trace_id is required for span correlation; severity_text is the natural label paired with severity_number for not-color-alone signaling), with Path A as opt-out if the user wants to defer.
- **Metrics chart aggregation model**: pure client-side aggregation over query result rows (sum/count/avg per bucket) vs server-side `viz.query.metrics.aggregated` route returning bucketed series. v1 chunk #35 preference is client-side (no new TauRPC procedure → no triple-binding cost); server-side aggregation is a future scope (chunk #35+) when query result row counts exceed reasonable client-side aggregation budget.
- **Log search/filter implementation**: client-side filter over loaded rows (simpler, scales to LIMIT_DEFAULT=100 / LIMIT_MAX=1000) vs server-side `LogsQueryArgs` extension with `body_search: Option<String>` + `severity_filter: Vec<i32>` (more capable, requires LogsQueryArgs extension + SELECT_LOGS query extension + tests). v1 chunk #35 preference is client-side. If user wants server-side, that requires extending `LogsQueryArgs` (no new TauRPC procedure name, just args struct extension — but TauRPC bindings auto-regenerate; still backward-compatible).
- **Log severity tier mapping**: OTLP `severity_number` ranges 1-24 (TRACE 1-4, DEBUG 5-8, INFO 9-12, WARN 13-16, ERROR 17-20, FATAL 21-24). chunk #35 severity-color mapping needs design decision on how to bucket: 6 tiers? 4 tiers (TRACE+DEBUG → muted, INFO → primary, WARN → border-only-accent, ERROR+FATAL → accent text)? Combined.md design extract suggests ERROR/FATAL → accent + WARN → accent border + INFO → primary + DEBUG/TRACE → tertiary; that's 4 visual tiers. Recommend explicitly adopting 4-tier mapping at plan.md level; chart fixture/test seeds use the boundary values.
- **`--color-secondary / --color-base` contrast pair gap**: a11y plan §11 flagged this pair as undefined in design tokens. If WARN severity uses `--color-secondary` (Stellar Indigo), the contrast must be defined first OR fall back to `--color-text-primary` paired with `--color-accent` border for WARN. Recommend the latter (preserves locked palette + matches design extract's "WARN → `#C7556A` border + `#E8EEF7` text" guidance).
- **Server-pushed live log stream subscription**: chunk #23 substrate provides `streams.subscribe_logs` for Arrow IPC live stream. v1 chunk #35 can ship with periodic polling (refetch on TIME_WINDOW_SECONDS interval) for simpler test surface; live subscription is a defer-to-chunk-#36+ option. Combined.md obs extract notes "Log stream tail-mode level discipline" assuming the live path; document as deferred from v1 if polling is chosen.
