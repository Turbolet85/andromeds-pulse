## Combined goal

Replace the compact-widget aggregated service badge (`AggregatedBadgeCanvas.tsx`) with a per-service constellation: one dot per service from the service registry, positioned by a stable `hash(service_name)` seeded scatter, with **brightness = activity** (lifecycle-state tier) and **hue = true per-service incident severity**, Dormant dimmed / Archived hidden, and a hover/focus tooltip (name + lifecycle state + activity). Per the **user-confirmed scope decision (2026-05-29, Phase 3 AskUserQuestion ×2): one big chunk, full faithful path** — including the backend plumbing required to make per-service severity real. Codebase research (research.md) established that the shipped `ServiceListItem` carries no severity and the `Incident` model has no `scope_id` (only the `AttentionCue` does, and it is dropped at incident creation), so this chunk first adds service attribution to incidents + a per-service severity join, then renders.

The work spans three crates and is intentionally ~2× a normal chunk: (A) backend — add `Incident.scope_id` (service attribution) with serde-default corpus-BLOB backward-compat, thread it from the originating cue through the incident-construction path; (B) resolver — inject the incident registry into `services.list_with_states` and compute per-service max-severity, surfaced as a new `severity` field on `ServiceListItem`; (C) webview — a new `ConstellationCanvas` consuming the extended payload via a PULL-poll hook, rendering with the post-#90 severity/activity model (`severity-to-halo.ts`) + seeded scatter. Per arch §Established Decisions [WebGPU Visualization Surface] + §Cross-cutting Module dependency direction (resolver join at the binary boundary, `triage` stays Tauri-free), design-system §Motion Decisions Log 2026-05-29 (severity hue / activity breathing), a11y-plan §1/§6/§11 (canvas a11y + not-color-alone + reduced-motion), and the chunk #86 `resolution_summary_text` serde-default persistence precedent. No new TauRPC procedure, broadcast topic, crate, env var, or corpus column — `services.list_with_states` gains a payload field only; `xtask capability-drift` stays clean.

## Implementation notes

- **Sequencing (hard):** do backend before webview. Steps 2→3→4→5 must land + bindings regen before Step 6-9 (the webview `ServiceListItem.severity` type only exists after the bindings regen). Within backend: contract field (2) → creation threading (3) → resolver join (4) → boot wiring + bindings (5).
- **scope_id threading is the discovery risk:** `DigestCueRef` (contract.rs:418) carries only `{kind, priority_tier, summary}` — it drops `scope_id`. If incidents are created downstream of the digest, /implement must decide the attribution source at Step 1 (thread scope_id onto DigestCueRef; OR attribute from the digest's dominant `DigestServiceRow.service`; OR source from the cue directly if upstream of the digest). The faithful choice is the cue's own `scope_id`; record the decision in the commit body. If this proves larger than expected, the backend portion is independently committable (the webview swap can follow in the same session or a tight follow-up).
- **serde-default backward-compat (corpus BLOB):** `Incident.scope_id` + any persisted `ServiceListItem.severity` use `#[serde(default)]` so pre-existing corpus rows / baseline state deserialize without migration — the chunk #86 `resolution_summary_text` + chunk #70 migration-safety precedents.

This changes the constructor → update BOTH the production `main.rs` wiring AND the `emit_taurpc_bindings` test construction (CLAUDE.md 2026-05-12 four-place binding) — capability-drift will report stale until both land + bindings regen via the mcp-server-feature path (CLAUDE.md 2026-05-17).
