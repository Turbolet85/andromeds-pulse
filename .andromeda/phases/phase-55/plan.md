## Combined goal

Chunk #59 substrate's the orthogonal "connection health" domain (capability P-004) decoupled from the existing throughput/error rate visualization. The implementation extends `IngestState` with a single new atomic timestamp (`last_ingest_at_nanos`) updated by the existing `record_spans` / `record_log_records` / `record_metric_data_points` hot-path methods (zero new touch points in `crates/ingest/src/grpc.rs` or `http.rs`). A new `crates/ingest/src/connection` module defines the 5-state FSM (`Listening` / `Receiving` / `Idle` / `Stalled` / `ReceiverFailed`), a `tokio::sync::broadcast` topic carrying `ConnectionStatePayload` events on state changes only (NEVER per-tick — preserves future webview `aria-live` discipline per a11y plan §11), and a 1-2s `tokio::time::interval` poller that reads the atomic + checks bind-status + transitions state accordingly. A new `pulse-app/src/connection_router.rs` exposes the `connection.current_state` TauRPC procedure (point query returning current state; sanitized `Result<ConnectionStatePayload, AppError>` per arch §Conventions Error response schema). The heartbeat task gains a 5th sibling `run_connection` at the standard 15s cadence (matching `ingest.tick` / `buffer.tick` / `viz.tick` / `plugins.tick` per obs-plan §3) emitting `connection.tick` with current state + last_span_ago_ms — separate from the 1-2s FSM detector loop's transition events.

Receiver-task panic detection rides the existing `std::panic::set_hook → app.panic.fatal` infrastructure (per CLAUDE.md observability rules) + the existing `HeartbeatState::otlp_{grpc,http}_bind = Failed` flag — no new panic hooks installed. The FSM poller transitions to `ReceiverFailed` when EITHER bind-status is Failed OR last-ingest staleness exceeds the threshold while bind-status is Failed; otherwise stale ingest with healthy bind status maps to `Stalled`. This combined heuristic preserves arch §Cross-cutting Patterns "Self-observation discipline" (tracing-only, no OTel SDK) and security plan §Anti-Patterns §Logging row 1 (no raw panic payloads in state broadcast — the `ReceiverFailureReason` enum closes the failure-reason field set).

The four-place TauRPC binding discipline (router registration + capability JSON entry + `xtask EXPECTED_PROCEDURES` + `emit_taurpc_bindings` test) applies per `.claude/rules/security.md` Session Additions 2026-05-12. Capability JSON requires NO edit (default.json uses `core:default` per chunk-#22 router-level granularity rule); `EXPECTED_PROCEDURES` gains one entry; `emit_taurpc_bindings` test merges the new `ConnectionApiImpl`. Implementation order ensures the consuming code (xtask EXPECTED_PROCEDURES extension) lands in the same commit as the new namespace per security.md 2026-05-10 cleanup-with-consuming-chunk pattern.
