## Patterns detected

- **Scrub-at-persistence-boundary, render-as-marker** (`crates/buffer/src/drain.rs:600-603`): the canonical existing pattern is `match scrub_attribute(&raw_text) { Allowed(s) => s, Redacted{category} => format!("[REDACTED:{}]", category) }`. Chunk #72 replicates this exact pattern at each new scrub site. The marker format `[REDACTED:{category}]` is the de-facto convention preserved across appender chunk #69 canary tests + drain.rs tests.
- **Producer-side scrub at adapter** (vs corpus-side scrub at impl): every existing persistence adapter (`drain_persistence` / `baseline_persistence` / `lifecycle_persistence` / `storm_persistence`) lives at the pulse-app binary boundary. They bincode-serialize their domain payloads + delegate to `CorpusWriter::save_pipeline_metric`. The scrub must happen BEFORE bincode (or at snapshot_state for drain) to ensure the bytes carry already-scrubbed content; defensive scrub inside the Corpus impl is INFEASIBLE for bincode bytes (would require re-decoding the payload which violates layer separation).
- **Trait-in-lower-crate + adapter-in-pulse-app** (session-learnings 2026-05-16): `CorpusWriter` lives in crates/corpus; adapter (`CorpusDrainPersistence` / `CorpusLifecyclePersistence` / etc.) lives in pulse-app binding `Arc<dyn CorpusWriter>`. Chunk #72 follows this pattern — no new traits introduced; scrub wiring happens at each adapter's save method.
- **N-trait-from-single-Arc** (session-learnings 2026-05-19): `Corpus` impls both `CorpusReader` + `CorpusWriter`; pulse-app derives `Arc<dyn CorpusReader>` + `Arc<dyn CorpusWriter>` from one `Arc<Corpus>` intermediate. No structural change for chunk #72.
- **Free-function map_err at adapter boundary** (session-learnings 2026-05-18): `corpus_error_to_buffer_error` / `corpus_error_to_lifecycle_error` / `corpus_error_to_storm_error` are free fns in each adapter file. No changes for chunk #72; sanitization stays the same.
- **PII negative-canary test pattern** (precedent from `crates/buffer/src/appender.rs::drain_pii_canary_email_redacted_in_log_templates` lines 1086-1162): seed OTLP fixture with canary substring (e.g., `canary-secret-email@example.com`) → drive through ingestion path → query the persisted column → assert raw canary absent + `[REDACTED:{category}]` marker present.
- **CapturingSubscriber tracing-layer canary** (precedent from `crates/buffer/src/appender.rs::append_span_events_batch_does_not_log_exception_canaries` lines 1501-1544): wraps test body in `tracing::subscriber::with_default(CapturingSubscriber, || { ... })` to assert canary substrings don't leak into tracing field emissions across the test scope. Pairs with the PII canary fixture test for defense-in-depth (storage + observability layers both verified).
- **Aggregate-only tracing fields, no per-record events** (obs CLAUDE.md USER:session-learnings 2026-05-17 session 84): new appender + adapter spans MUST emit only bounded counts (e.g., `attributes_scrubbed_count`, `redacted_category_counts`) on the wrapping `duckdb.append` span, never per-attribute events. Existing `duckdb.append` span at appender.rs:471-478 is the wrapping site.

## Open questions

- **Question 1: snapshot_state scrub granularity** — scrub each `token: String` independently (preserves per-token structure) OR join tokens, scrub the joined string, re-tokenize on whitespace (matches `write_template_to_table` at drain.rs:599-602)? Recommendation: **join-scrub-rejoin** (single string for scrub passes; preserves bincode round-trip semantics — the loaded DrainState has the same token count as if it were scrubbed at write_template_to_table time). Tests will confirm at impl time.
- **Question 2: defensive scrub in corpus impl, or producer-side only?** — combined.md security extract proposes runtime `debug_assert!(value.is_scrubbed())` + tracing::warn at the trait impl. Research finds this is **infeasible for bincode bytes** (would require decoding payload to inspect; layer violation). For `save_service_registry_row`, defensive scrub of `service_name` inside the impl IS feasible but **double-scrubs** in the common case (adapter scrubs + impl scrubs). The security extract's idempotence guarantee (scrubber Allowed result of an already-scrubbed value is a no-op) makes this safe but redundant. Recommendation: **producer-side only via adapter wiring**; assertions live in PII negative-canary tests per call site. No runtime assertion in CorpusWriter impl. Document the rationale in the CorpusWriter trait docstring.
- **Question 3: storm/baseline payload shape investigation deferred к /implement** — the exact field path for `FingerprintState.service` and `BaselineState`'s per-service-keyed tracker structure isn't read in this Phase 3 research (would require reading `crates/triage/src/pattern/storm.rs` + `crates/triage/src/baseline/mod.rs`). /implement Phase 1 reads these to determine the scrub-then-clone pattern (in-place mutation in a cloned snapshot vs custom serialization path). Plan acceptance criteria specify the OUTCOME (canary test passes) not the exact path; impl chooses.
- **Question 4: exception_type scrubbing** — chunk plan spec mentions only `exception.message + exception.stacktrace` (per capability P-006). exception_type is currently the class identifier (e.g., `java.lang.RuntimeException`). The scrubber regex set would only redact it if it matched email/JWT/etc. — typically false-positive-free. **Recommendation: leave exception_type unscrubbed.** Spec compliance achieved.
- **Question 5: `service_name` aggregation impact of scrubbing** — if a service_name is PII-shaped (e.g., user accidentally configured `service.name=user@example.com`), scrubbing replaces it with `[REDACTED:email]` in the corpus. Per-service trackers, lifecycle states, and storm fingerprints keyed by service_name would then collapse all PII-shaped names into the same `[REDACTED:email]` bucket. This is **acceptable** (security > attribution for misconfigured services); document in the chunk plan AC. The typical case (service_name like `web-api`, `auth-service`) is unaffected. No test needed beyond the canary tests (which assert redaction; the aggregation-collapse is a documented behavior, not a regression).
