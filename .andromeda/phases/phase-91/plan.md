## Combined goal

Expose the existing incident/report machinery (chunk #78 incident records + chunk #88 Diagnostic Report markdown) to AI agents over the MCP stdio sidecar as a THIRD output channel, alongside (1) the in-app Diagnostic Report and (2) clipboard markdown. The chunk extends the EXISTING `crates/mcp-server/` (a reserved, locked workspace crate — NOT a new crate) with four `#[tool]` methods (`query_incident_list`, `retrieve_report(id)`, `retrieve_telemetry_slice(id)`, `mark_incident_resolved(id)`), extends the existing `mcp.status()` TauRPC return shape with a connected-agent label, adds a default-off `[mcp.enable]` config flag, and adds one conditionally-visible "Send to agent" button to the Diagnostic Report toolbar. Per arch §Established Decisions [MCP Server Surface] + [API Style — MCP Server Surface 3], the surface stays spec-conformant JSON-RPC 2.0 over stdio; per security plan §API Security the double-gate (`--features mcp-server` + `ANDROMEDA_PULSE_MCP_ENABLED`) is preserved and `[mcp.enable]` composes above it; per obs-plan §4 P3 each tool emits boundary spans with `result_type`/`result_count` only (never response bodies, Vector 4); per P-038 the MCP report markdown is byte-identical to the clipboard markdown.

**Architecture decision (Phase 1 user-approved, Option A "Corpus-backed subprocess"):** the MCP sidecar is a SEPARATE process (`andromeda-pulse-mcp`) with its own empty ephemeral DuckDB and no live handle to the main process's `IncidentRegistry` or ring buffer (research.md confirms cross-process buffer sharing was deferred). The four new tools therefore read/write the on-disk `corpus/corpus.db` (cross-process accessible via `CorpusReader`/`CorpusWriter`), which the sidecar already locates via `resolve_data_dir()`. Consequences accepted by the user: `retrieve_telemetry_slice(id)` returns persisted incident context (evidence refs + digest), NOT live telemetry rows; `mark_incident_resolved` is eventually-consistent vs the in-memory registry (durably correct in corpus; re-hydrated at next boot); `mcp.status()` "connected" = sidecar-running. The chunk spec's "MCP = one of three equal-tier output channels" arch.md §Established-Decisions BODY change is STRUCTURAL and OUT OF SCOPE here (registry-only `--allow-arch-registry` cannot apply it) — it stays deferred to a deliberate `/andromeda-arch` touch (record this in the wrap-session handoff). P-038 identity is preserved by moving only the ~135-line `assemble_report` glue from `pulse-app/src/incidents_router.rs:567` into `interpretation::markdown` (where `serialize_report` already lives); the only new Cargo dep edge is `interpretation → security`.

## Implementation notes

- **P-038 single-source discipline is the load-bearing invariant.** Implement Step 1 (move `assemble_report`) FIRST so both `incidents.get_report` and the MCP `retrieve_report` tool call the exact same `interpretation::markdown::assemble_report` + `serialize_report`. The content-identity test then guards against future divergence. Do NOT write a parallel markdown formatter in the mcp-server crate.
- **bincode config parity (Open Question #4) is a silent-failure risk** — verify at Step 0 that the sidecar decode uses the identical config to the pulse-app encode, else `retrieve_report`/`mark_incident_resolved` silently fail to decode the Incident BLOB. If `incident_persistence.rs` uses `bincode::Options`-customized encode, extract a shared `encode_incident`/`decode_incident` pair.
- **Eventual consistency is accepted, not a bug** — `mark_incident_resolved` via the sidecar writes corpus.db; the main process's in-memory `IncidentRegistry` won't reflect it until next boot re-hydration. Document this in the tool description + the chunk's wrap notes. Do NOT attempt a sidecar→main IPC to live-sync the registry (that's the deferred in-process arch).
- **Sidecar corpus-open must be non-fatal** — keychain unavailability or corpus-open failure logs a warn + continues with tools returning JSON-RPC errors; never abort the sidecar (mirrors the existing `mcp.boot.buffer.init` resilience).
- **bindings.ts regen is the classic wrap trap** — run the `--bin pulse-app --features mcp-server` emit_taurpc_bindings regen as the FINAL pre-commit step after all default-features test runs (per CLAUDE.md 2026-05-17/2026-05-25).
- **Windows rlib-race** — if the workspace nextest hits the `libduckdb_sys ... rlib format` error on a cold build, run `cargo build -p pulse-app` first to de-race (per CLAUDE.md 2026-05-31 session 165).
