### Chunk route#94: "MCP server + tool exposure"

**Capabilities:** P-039 (MCP Delivery When Configured), P-040 (MCP Independence — verified by configurable off-by-default).
**Depends on:** #78 (incident records), #87/#88 (Report content + markdown serialization). Both landed.
**Summary:** MCP server exposes four tools — `query_incident_list`, `retrieve_report(id)`, `retrieve_telemetry_slice(id)`, `mark_incident_resolved(id)`. Server enabled via `[mcp.enable]` config (default false). Connected agent identity tracked; "Send to agent" button in the Diagnostic Report toolbar visible only when both configured AND agent connected. MCP delivery markdown content IDENTICAL to clipboard delivery (P-038).

**Constraints across domains:**

- (arch) The `mcp-server` crate is a LOCKED reserved workspace member that ALREADY EXISTS — EXTEND it, do NOT create a new crate nor rename. - (arch) MCP surface stays spec-conformant: JSON-RPC 2.0 over stdio; new tools via standard `tools/list` + `tools/call`; no custom wire format (per arch §Conventions External wire — MCP server + §Established Decisions [API Style — MCP Server Surface 3]).
- (arch) MCP errors use the standard JSON-RPC 2.0 error object (numeric `code`, `message`, optional `data`) — NOT the AppError enum on the stdio surface (per arch §Conventions Error response schema (MCP)).
- (arch / security) The new `mcp.status()` TauRPC procedure follows `<router>.<verb>` dotted `snake_case` AND requires BOTH router registration AND a `pulse-app/capabilities/` entry (router-level granularity) or it is silently rejected at runtime; `xtask capability-drift` enforces. `mcp.status` already appears in §Occupied Resources as part of `mcp.{status,start,stop}` — verify whether this chunk EXTENDS the existing procedure's return shape (connected-agent identity) vs adds a sibling (per arch §Cross-cutting Patterns Webview IPC capability policy + §Conventions Endpoint naming; security plan §API Security TauRPC capability authorization).
- (security / arch) Preserve the MCP double-gate: compile-time `--features mcp-server` AND runtime `ANDROMEDA_PULSE_MCP_ENABLED=true`; the new `[mcp.enable]` config (default `false`, P-040) is an ADDITIONAL enablement layer whose relationship to the env-var gate MUST be resolved at plan time (config precedence: env > config.toml > defaults). Preserve the graceful-degrade `warn` (env/config set against a no-feature build) — do not fail-startup (per security plan §API Security MCP double-gate + §Code Patterns ban 3; arch §Stack MCP server).
- (security) The 4 tools' telemetry/incident reads route through `Connection::prepare` + `?` placeholders (and/or the corpus reader's parameterized path) — NEVER `format!`-interpolated SQL; agent-supplied `id` never names a table/column (per security plan §Input Validation + §Anti-Patterns §Input ban 2).
- (security) `mark_incident_resolved(id)` MUST NOT pass any agent-supplied string into `tokio::process::Command::new(...).arg(...)` — route the mutation through the existing typed `incidents.mark_resolved` resolver / `IncidentPersistence`, not a shell/subprocess (per security plan §Anti-Patterns §Code Patterns ban 1).

- (obs) mcp-server is boundary-only instrumentation: spans at the stdin/stdout JSON-RPC boundary; tool handlers get `#[tracing::instrument]` but tool RESPONSE BODIES are never logged (per obs-plan §1 instrumentation-scope + §4 P3).

- (layouts) The button lives in the Diagnostic Report toolbar (modal-class surface) co-located with the existing chunk-#88 "Copy markdown" action as a peer toolbar action — NOT a new modal/panel/tab; the optional `[mcp.enable]` control belongs in the existing Settings modal form-section stack as a checkbox+label+helper-text (per layout-templates.md §Component — Investigation modal + §Component — Settings modal).
