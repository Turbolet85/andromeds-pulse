### Existing prepared-statement DuckDB query pattern (the canonical seam)

- **`crates/viz/src/query.rs`** (1052 lines) — `query_traces` / `query_metrics` / `query_logs` functions. Pattern:
  ```rust
  pub fn query_traces(state: &VizState, start_ns: i64, end_ns: i64, limit: u32)
      -> Result<TracesResponse, Error>
  {
      let guard = state.connection().lock()?;
      let count: i64 = {
          let mut stmt = guard.prepare(COUNT_TRACES)?;
          stmt.query_row([start_ns, end_ns], |row| row.get::<_, i64>(0))?
      };
      let mut stmt = guard.prepare(SELECT_TRACES)?;
      let rows = stmt.query_map([start_ns, end_ns, i64::from(limit)], |row| { ... })?;
      // collect rows
      drop(stmt);
      tracing::info!(target: "metric.viz.query.latency_ms", ...);
      Ok(TracesResponse { ... })
  }
  ```
  - SQL constants are `const SELECT_TRACES: &str = "..."` with `?` placeholders.
  - `prepare()` + `query_map([params], |row| ...)` for SELECTs; `query_row()` for single-value COUNT.
  - `drop(stmt)` before tracing emission releases the connection lock — important for parallel queries.

## Patterns to follow (project-specific)

1. **Prepared-statement pattern from `viz/query.rs:96-175`**:
   - SQL constants as `const Q{N}_TEMPLATE: &str = "..."` per query (q1, q2, ..., q7, q7_fallback)
   - `INTERVAL ?` placeholders pass `Duration` via `[duration_param]` array
   - `guard.prepare(QN_TEMPLATE)?` → `stmt.query_map([params], |row| { decode_row(row) })?`
   - `drop(stmt)` before `tracing::info!` emission
   - Return typed structs (e.g., `Q1RedRow { service_name: String, request_count: i64, error_count: i64, error_rate: f64, p50_ns: i64, p95_ns: i64, p99_ns: i64 }`)

2. **spawn_blocking discipline** from `buffer/retention.rs:80` + `buffer/consumer.rs:62`:
   - Public API exposed as `pub async fn run_q{n}(state: &TriageState, window: Duration) -> Result<Vec<Q{N}Row>, SqlError>`
   - Internally: `tokio::task::spawn_blocking(move || run_q{n}_blocking(&conn_clone, window_param)).await`
   - Returns `Result` from spawn_blocking + Result from query — flatten via `?` or explicit join handling

3. **Q7 timeout (200ms)** — implementation strategy options (choose at /implement time):
   - **Option A** — `tokio::time::timeout(Duration::from_millis(200), spawn_blocking_q7).await` → on Elapsed error, abort handle + run Q7-fallback. Simplest; spawn_blocking thread may continue running briefly after timeout (cooperative).
   - **Option B** — DuckDB `interrupt_handle()` API (if `duckdb` crate 1.10500.x exposes it) — call from а timeout task spawned via `tokio::spawn`; on timeout fire, call `interrupt_handle.interrupt()` to deterministically cancel the query.
   - Option A is simpler + matches existing `spawn_blocking` discipline. Verify `duckdb::Connection::interrupt()` API availability at /implement time; if available, prefer Option B for true cancellation.

4. **thiserror error enum** from `crates/triage/src/baseline/error.rs:1-40`:

## Conventions identified

- **DuckDB SQL conventions:**
  - All SQL templates as `const` `&str` with `?` placeholders — NEVER `format!()` interpolation (per CLAUDE.md §Critical Warnings DuckDB row + arch §Established Decisions [Database]).
  - Table + column name references hardcoded literal in SQL (caller cannot name a table).
  - Window-duration parameter passed as `Duration` via the array, NOT as string interpolated literal.
  - `drop(stmt)` before tracing emission к release connection lock for parallel queries.

- **Module structure:**
  - New SQL templates module lives at `crates/triage/src/baseline/sql.rs` (or `crates/triage/src/baseline/queries.rs` — orchestrator note: chunk spec says "SQL templates module" so `sql.rs` clearer naming intent; `queries.rs` ambiguous with HTTP query). Either works; orchestrator weak preference for `sql.rs`.
  - Module exports `pub fn run_q{n}(...)` async API + `pub struct Q{N}Row { ... }` result types via `pub use` from `baseline/mod.rs`.
  - Error type `SqlAggregationError` co-located in module OR extended into `BaselineError` enum. Orchestrator weak preference: new enum в module to keep `BaselineError` focused on persistence concerns.

- **Tests:**
  - Co-located `#[cfg(test)] mod tests` in `crates/triage/src/baseline/sql.rs`.
  - Each Q1-Q7 has one happy-path test + Q7 has additional bounds tests (depth limit, row limit, timeout, fallback).
  - SQL injection negative test as a single `#[test] fn test_sql_injection_via_service_filter()` — but note: chunk #79 spec has Q1-Q7 take ONLY duration parameter, NOT service_filter; so the "SQL injection" test surface is the duration parameter parsing if anything. Practical test: assert that the prepared-statement boundary correctly rejects non-Duration types at compile time (this is type-system, not runtime SQL injection — Q1-Q7's only user-controlled input is the Duration window). Document as "no service_filter parameter in Q1-Q7 surface — `param_count = 1` (the duration only); SQL injection negative test verifies the bind site fails on non-Duration input via type system, OR is skipped if no string parameters exist".

- **Observability:**
  - Manual `#[tracing::instrument(skip(state), fields(query_name = "q1", query_id = "q1", param_count = 1, row_count_returned))]` on each public async function.
  - All metric events use `tracing::info!(target: "metric.pipeline.l1a.*", ...)` pattern; no precomputed quantiles in emission.
  - Per-module allowlist entries needed in `pulse-app/src/observability.rs` for new fields (deferral acceptable per chunk #78 precedent).

## Open implementation questions (defer к /implement)

1. **Duration parameter type:** chunk spec says "INTERVAL ?". DuckDB SQL `INTERVAL ?` accepts STRING like `'60 seconds'` or `'1 minute'`. The `?` placeholder binds а string-typed parameter. Implementation passes `Duration` к а helper that formats as `format!("{} seconds", dur.as_secs())` then binds the STRING via parameter array. CAUTION: this is still parameter-bound (safe from SQL injection) because DuckDB treats the bound value as а literal, not as SQL syntax. Verify at /implement time that DuckDB rejects `'1; DROP TABLE spans; --'` as а malformed INTERVAL literal (parser rejects, not executor — still safe).

2. **Q7 worst-case enforcement mechanism:** `tokio::time::timeout` (Option A) vs DuckDB `interrupt_handle()` (Option B). Implementation defaults to Option A unless DuckDB crate exposes interrupt API cleanly. Add deferred follow-up: verify `duckdb::Connection::interrupt()` availability + benchmark cost vs Option A.

3. **Connection acquisition:** Q1-Q7 need а shared `Arc<Mutex<Connection>>` (same shape as `viz::VizState`). Where does triage get this from? Two options:
   - **Option A** — pass `Arc<Mutex<Connection>>` explicitly via а new `TriageSqlState` struct constructed at boot in `pulse-app/src/main.rs` (mirrors `VizState`).
   - **Option B** — re-export existing `BufferState` / `VizState` accessor; `triage` already has access to `buffer` crate dependencies.
   - Option A more explicit; Option B less wiring but tighter coupling. Defer to /implement.

4. **`MockArrowBatch::builder()` existence:** combined.md tests extract references it but research did not confirm. Search at /implement time; if absent, write direct `Connection::execute("INSERT INTO spans ...", ...)` test fixture helper inline.
