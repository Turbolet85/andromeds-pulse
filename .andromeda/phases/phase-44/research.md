## Open questions

1. **`plugins.invoke` semantics — full export call vs capability-handshake**: combined.md acceptance criterion phrases `plugins.invoke({plugin, capability: "transform_spans"})` as if capability is a `wasmtime`-callable export. But the 3 WIT files declare exports with hyphen-case (`render`, `transform`, `render-template`) and no `transform_spans`. **Recommendation:** chunk #47 implements `invoke` as a capability-handshake only — verify the requested capability name matches a known export of the plugin's category WIT; return `Ok(allowed: true)` for the happy path and `AppError::Plugin { plugin_id, message: "capability rejected: <name>" }` for the negative path. Actual wasmtime export invocation (running the export function) deferred to a future chunk that introduces `wasmtime::component::bindgen!` per-category type generation. Plan.md should make this scope-boundary explicit.

2. **Category inference from filename**: how does loader classify a `*.wasm` file into one of the 3 categories? **Options:** (a) filename prefix convention (`data-transform-*.wasm` / `custom-dashboard-*.wasm` / `snapshot-template-*.wasm`); (b) per-category subdirectory (`~/.andromeda-pulse/plugins/data-transform/*.wasm`); (c) WIT introspection at load-time (parse the Component's WIT signature, match against known categories). **Recommendation:** option (b) — per-category subdirectory — simpler than filename parsing, more explicit than WIT introspection, aligns with the WIT file naming pattern under `crates/plugins/wit/`. Plan.md should specify this discovery layout.

3. **Built-in plugin templates as compilable .wasm vs README scaffolds**: chunk #47 text says "built-in templates"; design extract enumerates token-usage constraints "if any UI rendering"; the WITs declare exports but no host-import-required host imports today. **Recommendation:** chunk #47 ships README scaffolds + WIT category contracts only — no compilable .wat/.wasm artifacts. The template authoring guide explains how to build a plugin against each category's WIT. Plan.md scopes templates as documentation deliverables, not runtime-loadable WASM.

4. **`plugins.tick` heartbeat field set — `active_invocations` semantics**: combined.md says "every 15s with `loaded_count` + `active_invocations` fields". `loaded_count` is unambiguously the registry size. `active_invocations` is less clear: (a) currently-executing wasmtime `Instance::call` count (requires invocation-tracking state machine), or (b) total invocations since boot (cumulative counter). **Recommendation:** chunk #47 implements (b) cumulative counter — simpler, no synchronization tax on the call path. Resets at process restart. Plan.md should call this out as a chunk-47 simplification with the note that a future chunk introducing real export invocation may add a concurrent gauge for (a).

5. **strict-path API surface — `try_resolve` vs `join`**: strict-path 0.2 has both `PathBoundary::try_new(base)` + `.try_resolve(path)` (canonicalizes-then-confines) and helper APIs. **Recommendation:** read strict-path 0.2 docs at /implement time to confirm exact API; existing workspace-detector usage should be the template. If strict-path 0.2 API differs from workspace-detector's pattern, surface at /implement time before writing loader.rs.
