## Open questions

- **Q1: Extend `Digest` struct in-place vs introduce `DigestV2` companion?** Recommendation: extend-in-place. Rationale: 5 existing fields; no external consumers serialize the v1 shape (chunk #44 snapshot generator uses snapshot crate's own `SnapshotResponse` type, not `triage::Digest`); the field additions are non-breaking (adding fields with default `None` / empty `Vec` / `false`). Decision authority: plan author judgment + Phase 6 user review.
- **Q2: Tokenizer choice for chunk #81 (pre-LLM-runtime resolution)?** Three options: (a) commit GPT-2 BPE tokenizer.json (~1.5 MB; widely available; future-binds to chunks #82+ if LLM choice is OpenAI-compatible); (b) commit Llama-3 tokenizer (~3 MB; future-binds to chunks #82+ if LLM choice is Llama-family per dist-arch v3 §L4 hardware profile matrix); (c) commit a placeholder tokenizer (small custom BPE, ~50KB; clearly marked for replacement at chunk #82 LLM-runtime resolution). Recommendation: (b) Llama-3 tokenizer, because pulse-distillation-architecture v3 §L4 explicitly references Llama-3 family for the primary tier (1-3B models for GPU-primary, 3-4B for GPU-fallback). The tokenizer asset size adds ~3 MB to the build (acceptable per arch §Established Decisions distribution-size budget). Decision authority: Phase 6 user review.
- **Q3: Sync or async `ProjectContextProvider::current_context()`?** Filesystem-only inspection (workspace_detector `.git/HEAD` + framework signal detection from Cargo.toml / package.json presence) is synchronous + fast (sub-ms). Git activity inspection (`git log` for recent commits) is async if using `tokio::process::Command` (spawn-overhead bounded) OR sync if using `gix` crate in-process. Per security extract, prefer `gix` in-process over subprocess spawn to avoid CVE-class concerns. Recommendation: sync `current_context()` returning `Result<ProjectContextSnapshot, Error>` using `gix` for git inspection — keeps the digest assembler's async surface minimal (token counting + corpus retrieval are the only intrinsic async dependencies). Decision authority: research direction + Phase 6 user review.
- **Q4: Should `workspace-detector` add a `gix` dep for git activity inspection?** `gix` is a large crate; alternative is plumbing through `git2` (already in workspace? Verify). If neither present, adding `gix` introduces a meaningful workspace deps delta (route §81 declares "+tokenizers only"). Resolution options: (a) `workspace-detector` already handles VCS detection via filesystem-only `.git/HEAD` parse per chunk #43; extend with `.git/refs/heads/main` HEAD-history readback for "last N commits" (still filesystem-only, no gix dep); (b) defer git activity inspection to a follow-on chunk and ship chunk #81 with workspace/framework signals only (degraded PROJECT line per Appendix C). Recommendation: (a) — extend filesystem-only git inspection in workspace-detector to read `.git/refs/heads/{branch}` + walk `.git/objects/{sha}` for parent chain (~50 LOC). Keeps workspace deps delta at strictly `+tokenizers`. Decision authority: Phase 6 user review.
