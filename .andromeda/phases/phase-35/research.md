## Patterns detected

- **Inline-token style pattern** (`pulse-app/ui/src/components/Modal.tsx:103-216`, `SettingsRoute.tsx:9-31`, `dashboard/router.tsx:118-128`): React components use inline `style={{ background: "var(--color-raised-3)", ... }}` with CSS custom property references rather than Tailwind utility classes. Tailwind v4 `motion-reduce:` variants applied via `className` (e.g., `Modal.tsx:105 "motion-reduce:transition-none motion-reduce:duration-0"`). All design tokens flow through `var(--token-name)`.
- **Modal primitive composition** (`Modal.tsx`): expects parent to manage `open` boolean state + `triggerRef` for focus restoration; children render arbitrary form content. The Modal already wires focus trap + Esc + close button + ARIA + reduced-motion overlay class. Consumers just supply `titleId`, `title`, and `children`.
- **Settings extension pattern** (`crates/ui-bridge/src/contract.rs:84-127`): each new field added with `#[serde(default = "default_X")]` or `#[serde(default)]` annotation enabling partial deserialization (missing fields fall back to defaults — verified by `settings_partial_deserialize_uses_defaults_for_missing_fields` test). New enum types follow `#[derive(Debug, Clone, Copy, Default, Serialize, Deserialize, PartialEq, Eq)]` + `#[serde(rename_all = "lowercase"|"kebab-case"|"snake_case")]` per existing `Theme` (lowercase) + `WidgetPosition` (kebab-case) precedent.
- **Co-located test pattern** (`crates/ui-bridge/src/contract.rs:367-1183`): each Settings field has dedicated tests for serde round-trip + default value + validate (where bounds apply). New fields follow `#[test] fn settings_<field>_<scenario>()` naming; capture-subscriber pattern for asserting `tracing::warn!` event emission (lines 382-414).
- **Tracing instrumentation pattern** (`crates/ui-bridge/src/contract.rs:189-201` etc.): every `From<E> for AppError` impl emits `tracing::warn!` at conversion boundary BEFORE returning lossy variant. Uses `target: "ui-bridge.error.{variant}"` (per allowlist resolver `for_target` exact-match per testing.md Session Additions 2026-05-07). Settings validation failures route through `AppError::Validation { field, reason }` (not a `From` impl currently — `validate()` returns `Result<(), AppError>` directly).
- **TanStack Router /settings tab route** (`router.tsx:176-180`, `Dashboard.tsx`, `App.tsx`): `/settings` is one of 5 tabs in the dashboard surface; TabNav navigates between them. Currently `SettingsRoute` is the registered component for `/settings`. Tab change announces via `aria-live="polite"` status region in `DashboardShell` (router.tsx:80).

## Open questions

- **Q1 (tray → settings navigation):** how does the tray "Open Settings" menu item navigate the webview to `/settings`? Two options: (a) Tauri event emission + webview listener that calls `router.navigate`; (b) webview `eval()` of a navigation script. Option (a) is cleaner but adds a new event channel; option (b) requires `core:webview:eval` capability which may not be granted. Recommendation: defer Q1 to user/Phase 6 review — CAN be deferred if the tray menu just focuses main window (existing behavior); user reaches Settings via the dashboard tab nav. **Pragmatic answer: skip tray-driven /settings navigation in chunk #38; tray "Open Settings" continues to focus main window (current behavior); user manually clicks Settings tab.**
- **Q2 (SettingsRoute as modal vs inline form):** chunk title says "Settings modal form", but existing /settings is a TanStack tab route. Three options: (a) /settings tab renders Modal-wrapped form (modal opens when route is active, closes navigates away); (b) /settings tab renders form inline (no Modal wrapper); (c) Modal is overlay on top of /settings tab content (open=true on route mount). Recommendation: (b) — render the form inline within the SettingsRoute. The chunk #37 Modal primitive is built for cases where opening from elsewhere (tray gear icon, command palette item, etc.) — those launch points belong to a future chunk if/when needed. Forced "modal-on-route" semantics adds awkward Esc-navigates-elsewhere behavior. The form's accessibility (focus management, aria-labelledby, aria-live) does NOT require a modal wrapper. Per Phase 6 review: ASK USER to confirm.
- **Q3 (snapshot fields shape):** combined.md mentions "snapshot-preset+budget+format" — three semantic concepts. Options: (a) one enum `SnapshotPreset { Conservative, Balanced, Detailed }` with budget derived from preset (10k/25k/50k); (b) separate `snapshot_preset` enum + `snapshot_budget: u32` with budget editable when Custom preset chosen; (c) just `snapshot_budget: u32` + `snapshot_format` (no preset enum). Arch §Established Decisions says "Balanced — 25k tokens" is default; doesn't mandate preset enum. Recommendation: (a) — simplest; budget derived from preset; user picks via radiogroup; format separately enum (`Markdown` default + `Json`). Future "Custom" budget can be added when use case emerges.
- **Q4 (react-aria-components installed?):** a11y plan + `.claude/rules/a11y.md` reference `react-aria-components@1.17.x` for `RadioGroup`/`Radio`/`Switch`. Confirm package presence in `pulse-app/ui/package.json` before committing to those primitives. If absent, native HTML `<input type="radio">` + `<input type="checkbox">` (with custom `role="switch"` ARIA) works as fallback.
