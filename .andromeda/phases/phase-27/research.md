## Patterns detected

- **Window labels are bounded constants** (`pulse-app/src/window.rs:10-11`): `MAIN_WINDOW_LABEL = "main"`, `COMPACT_WIDGET_LABEL = "compact-widget"`. Any new code referencing window labels MUST use these constants. `sanitize_window_label()` collapses unknown labels to `"unknown"` for obs cardinality discipline.
- **Tauri lifecycle hooks are the integration point** (`pulse-app/src/main.rs:255-379`): `tauri::Builder::default().on_window_event(...).setup(move |app| { ... }).run(...)`. `setup` runs once after Tauri context generation — natural location for "read settings, apply window geometry, show window" sequence.
- **Settings persistence is config.toml at data_dir root** (`crates/ui-bridge/src/health.rs:303-486`): atomic write via `path.with_extension("toml.tmp")` then `fs::rename`. `get_settings` returns `Settings::default()` on file-not-found (silent fallback, not error).
- **Tracing event shape for layout transitions** (`pulse-app/src/window.rs:78-88`): `info!(target: "ui.layout.transition", layout_mode_from, layout_mode_to = "hidden", tray_visible = ...)`. Same target reused for any future widget position change events; obs allowlist already tolerates this target via the `.tick`/`.split('.').next()` resolver pattern.
- **Webview window controls bridge to Tauri JS API** (`pulse-app/ui/src/hooks/use-window-controls.ts:7-21`): `import { getCurrentWindow } from "@tauri-apps/api/window"` + `.minimize()` / `.toggleMaximize()` / `.close()`. This same import surface exposes `getCurrentWindow().setPosition()` / `.setSize()` / `.setAlwaysOnTop()` / `.outerSize()` / `.outerPosition()` — Tauri 2's window API is rich enough to handle snap-to-edge from the JS side too, but the existing pattern keeps window state changes Rust-side (window.rs owns `handle_close_to_tray`).
- **Default-deny tracing field allowlist** (`pulse-app/src/observability.rs::AllowList::production()` per session-additions): each tracing target needs an entry naming its allowed fields. New widget-state fields (`always_on_top`, `widget_position`, `display_id`) emitted under `ui.layout.transition` need to land in the existing allowlist entry for that target. **Critical**: per session-additions 2026-05-07 lesson, the resolver order is `for_target` exact-match → `.tick` strip → `split('.').next()` → `split("::").next()`; new sub-namespace `ui.layout.transition.position` would resolve to `ui` (not present → fallback). Stick with the existing `ui.layout.transition` target and extend its allowlist.
- **specta + serde + TOML round-trip discipline for Settings** (`crates/ui-bridge/src/contract.rs:84-117`): `#[cfg_attr(feature = "taurpc-runtime", derive(specta::Type))]` + `#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, Eq)]` + `#[serde(default = "fn_name")]` for backward-compat optional fields. Extending Settings is mechanical.
- **Validation surface in `Settings::validate()`** (`crates/ui-bridge/src/contract.rs:125-135`): currently checks `retention_seconds` bounds. Adding `always_on_top: bool` requires no new validation (boolean has no out-of-range states). Adding `display_id: Option<String>` (for per-display memory) needs no validation (Option<String> is structurally bounded; opaque string).
- **TauRPC dispatches all router methods through one invoke handler** per security rules.md §Session Additions 2026-05-03 — capability JSON `permissions` array is router-level, not per-procedure. Adding new IPC procedures only requires (a) trait method + resolver, (b) [if new namespace] new capability JSON entry. Extending an existing trait (IntrospectionApi) needs neither.

## Conventions to follow

- **Window-level Rust code lives in `pulse-app/src/window.rs`** — established by chunk #24. Add `apply_widget_settings()` / `position_widget_at_corner()` helpers there alongside `show_compact_widget()`.
- **Tauri 2 window manipulation API** — use `tauri::Window::set_position(Position)`, `set_size(Size)`, `set_always_on_top(bool)`. Position computation uses `tauri::Window::current_monitor()` (returns `Option<Monitor>`); Monitor exposes `position()` + `size()` + `scale_factor()` for display-aware geometry.
- **Settings extension pattern**: add field to `Settings` struct in `crates/ui-bridge/src/contract.rs` with `#[serde(default = "...")]`, no migration needed for existing config.toml files (missing field falls through to default).
- **Tracing target reuse**: extend `ui.layout.transition` for widget position changes + always-on-top toggles rather than introducing new targets — keeps obs allowlist surface small.
- **Atomic config write**: existing `update_settings` impl uses tmp + rename. Don't bypass with direct fs::write.
- **Specta TS bindings emission**: `taurpc::Router::into_handler()` regenerates `pulse-app/ui/src/bindings/index.ts` automatically when struct changes. The chunk #25 baseline test `emit_taurpc_bindings` enforces emission. Settings struct change → bindings regenerate → frontend type-checks new field.

## Open questions

- **Per-display memory complexity**: route chunk text says "snap-to-edge per-display memory" — strict reading implies storing position per-display (HashMap<display_id, WidgetPosition>) and restoring per current display. Loose reading: snap relative to current display's edges (no per-display state needed; widget always snaps to a corner of whichever display it's on). **Recommendation for plan.md**: implement loose reading first (snap relative to current display via `current_monitor().position() + size()`); per-display HashMap is a follow-up if user reports needing different positions on different displays. This aligns with the existing 4-corner `WidgetPosition` enum without serde-breaking changes.
- **9-position grid vs 4-corner enum**: layout-templates §Component — Settings modal mentions a 9-position radio grid; current `WidgetPosition` enum has 4 corners. **Recommendation for plan.md**: keep 4 corners for chunk #30 (matches existing chunk #27 contract); 9-position grid lands at chunk #38 (Settings modal form) when the form needs the radio inputs.
- **Always-on-top toggle UI placement**: titlebar (intrusive but discoverable) vs settings modal (deferred to chunk #38) vs system tray menu (deferred to chunk #36). **Recommendation for plan.md**: minimum viable for chunk #30 is the IPC + persistence + apply-on-startup; UI surface can be the settings modal at chunk #38. The Settings struct change is sufficient to count chunk #30 acceptance criteria as met (verifiable via `update_settings` integration test).
- **Quarter-screen sizing accuracy**: current hardcoded 480x270 is a chosen size (16:9 close enough to "quarter screen" on common 1920x1080); display-aware sizing would compute `monitor.size().width / 2` × `monitor.size().height / 2` and clamp to reasonable min/max. **Recommendation for plan.md**: keep hardcoded 480x270 for chunk #30 (already shipped in tauri.conf.json); display-aware sizing can be a follow-up if user reports it on a 4K display being too small. The "quarter-screen" language in route is aspirational; 480x270 is the practical baseline.
- **Position-change persistence loop**: when user drags widget to a corner manually, should the position be auto-detected and persisted? Tauri 2's `WindowEvent::Moved` fires on every move (high frequency); debouncing + snap-detection is non-trivial. **Recommendation for plan.md**: defer — chunk #30 only applies persisted position on startup (read-only direction). User changes position via Settings modal at chunk #38 (explicit selection).
