## Implementation notes

- **"Per-display memory" interpretation**: the route chunk text "snap-to-edge per-display memory" is implemented via the loose interpretation (snap relative to current display computed via `current_monitor().position() + size()`) rather than the strict interpretation (HashMap<display_id, WidgetPosition>). Rationale: simpler model, matches existing 4-corner `WidgetPosition` enum without serde-breaking changes, and "per-display" semantics are preserved (widget always snaps to a corner of whichever display it's currently on). Follow-up trigger: if user reports needing different positions on different displays in distinct sessions, extend `Settings` with `widget_positions: HashMap<String, WidgetPosition>` + `widget_display_id: Option<String>` in a future chunk.

- **Always-on-top toggle UI placement**: the IPC + persistence + apply-on-startup is sufficient for chunk #30 acceptance criteria (verifiable via `update_settings` integration test). User-facing toggle UI lands at chunk #38 (Settings modal form). Don't add intrusive titlebar UI for it now; the Titlebar.tsx `onSettingsClick` callback prop (currently unused) will trigger the settings modal at chunk #38.

- **9-position grid vs 4-corner enum**: layout-templates §Component — Settings modal mentions a 9-position radio grid; current `WidgetPosition` enum has 4 corners only (locked at chunk #27). Chunk #30 honors the 4-corner enum; if/when the Settings modal at chunk #38 needs 9-position UI, extending the enum is a separate scope (serde-breaking; needs rebuild of any persisted config.toml files).

- **Quarter-screen sizing**: keep hardcoded 480x270 in tauri.conf.json (chunk #2 baseline). Display-aware sizing (`monitor.size().width / 2 × monitor.size().height / 2`) is a follow-up if user reports it on a 4K display being too small; for chunk #30 acceptance, 480x270 is sufficient (the route language "quarter-screen" is aspirational, not literal — modern monitors are 1920x1080 or larger, and 480x270 is a reasonable widget size that fits on any).

- **Carry-over D3 carry forward**: chunk #30 does not extend `xtask/src/main.rs::EXPECTED_PROCEDURES`. The 4 missing entries from chunks #23 (3× `streams.subscribe_*`) + #29 (`telemetry.frontend.record_frame_ms`) remain in the carry-over D3 state until a future user-driven follow-up edits the hardcoded list (per session 32 wrap Priority 2 carry-over). Chunk #30 acceptance criterion "no expansion of capability-drift gap" is satisfied; the gap is unchanged.

- **No `/andromeda-scope-arch` needed**: per security.md §Session Additions 2026-05-09 binding, NEW TauRPC namespaces require arch §Occupied Resources update before merge. Chunk #30 introduces NO new TauRPC namespaces (extends existing `Settings` IPC). Therefore no arch registry update is needed; this is captured in the "Files к leave untouched" section.

- **Order in setup closure**: `show_compact_widget(app)` MUST run before `apply_widget_settings(app, &settings)` because position can only be set on a visible window per Tauri 2 API contract. Reverse order would result in `set_position` being a no-op or raising a runtime warning.

- **Test isolation**: integration test for `apply_widget_settings` should use `tempfile::TempDir` + `ANDROMEDA_PULSE_DATA_DIR=$TMPDIR/test-$$` per test-plan §7 to avoid leaking persisted settings across parallel tests. The `tauri::test::mock_builder()` from chunk #25 baseline supports this isolation pattern.
