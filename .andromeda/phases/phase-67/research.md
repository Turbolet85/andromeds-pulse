## Schema decision recommendation (resolves combined.md rot warning #2)

**Option A: Reuse `pipeline_metrics` blob slot** — `metric_name="baseline_state"`, `layer="l1b"`, payload = `bincode::serialize(&BaselineState)`. PROS: (a) mirrors chunk #69 Drain precedent EXACTLY — same code shape, same testing harness, same observability path; (b) no `CorpusWriter` trait extension needed (uses existing `save_pipeline_metric` / `load_pipeline_metric`); (c) no `crates/corpus/src/schema.rs` changes (table exists; reusing existing methods means schema unchanged); (d) preserves the full `BaselineState` shape including DashMap-of-services + DashMap-of-operations + AtomicI64 timestamp; (e) simpler to test (one blob round-trip vs N per-service rows). CONS: (a) no per-service queryability — load fetches the entire serialized state (mitigated: triage already loads all-at-once); (b) the empty `baseline_state` table at corpus/schema.rs:35-42 remains unused at chunk #70 close (could be removed in chunk #74 batch).

**Option B: Populate dedicated `baseline_state` table per-service** — requires extending `CorpusWriter` trait with `save_baseline_state(service_name, operation, payload) -> Result<(), Error>` + `load_baseline_state(...) -> Result<Vec<(String, Vec<u8>)>, Error>`. PROS: (a) per-service queryability (future per-service deletion / inspection); (b) populates the empty pre-allocated table. CONS: (a) substantially more code (~3-4× delta); (b) requires custom load logic к rehydrate the DashMap from N rows + handle partial-load failures; (c) diverges from chunk #69 precedent (one-off pattern); (d) per-row encryption nonces increase storage overhead modestly.

**Recommendation: Option A.** Audit Section 1.A persistence triple-mechanism closure is the primary goal; minimal divergence from chunk #69 precedent reduces review surface + risk. Empty `baseline_state` table cleanup goes to chunk #74 arch registry batch.
