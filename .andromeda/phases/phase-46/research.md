- **TauRPC router shape per crate** (sources: `pulse-app/src/plugins_router.rs:48-202`, `pulse-app/src/main.rs:317`): each new namespace is a single Rust file at `pulse-app/src/{namespace}_router.rs` that defines specta::Type DTOs + `#[taurpc::procedures(path = "{namespace}")]` trait + `{Namespace}ApiImpl` struct + `#[taurpc::resolvers] impl {Namespace}Api for {Namespace}ApiImpl` with `#[tracing::instrument]` per resolver. Resolvers take `self` by value (Clone-able impl), lock shared state via `Arc<Mutex<...>>`, emit terminal `tracing::info!(target: "{namespace}.{method}.{result}", ...)`. Chunk #49 will create `pulse-app/src/mcp_router.rs` following this shape.
- **AppError From impl pattern** (source: `crates/ui-bridge/src/contract.rs:244-608`): each library error type that crosses the bridge has a `From<{Crate}Error> for AppError` impl that matches each variant to `(message: &'static str, source_kind: &'static str)`, emits `tracing::warn!(target: "ui-bridge.error.{category}", error_category, source_kind, source_crate, "{message}")`, returns the appropriate `AppError` variant (Ingest / Plugin / Storage / Internal). Round-trip-no-leak tests verify no Rust struct names / file paths / library versions leak in the `message` field.
- **AllowList target resolution** (source: `crates/mcp-server/src/tracing_setup.rs:82-103`): `for_target(target)` resolves via 4-step cascade — exact match → strip `.tick` suffix → split-`.`-first segment → split-`::`-first segment. Chunk #49 can either (a) add new fields to the `mcp` target allowlist if the cascade is desired OR (b) add explicit per-leaf entries (e.g., `mcp.tools.call.request`, `mcp.tools.call.response`) for tighter isolation. Plan author chooses; the simpler choice (cascade via `mcp` parent) suffices for chunk #49 unless field divergence emerges.
- **Stderr-forced JSON tracing init** (source: `crates/mcp-server/src/tracing_setup.rs:224-270`): the sidecar's `init(data_dir)` builds a registry with `fmt::layer().event_format(JsonWithDefaults).with_writer(std::io::stderr)` (no TTY check) — stdout reserved for JSON-RPC 2.0 framing. - **Sidecar buffer access**: chunk #49's `query_*` MCP tools need to read from the in-memory DuckDB buffer. The sidecar runs as a separate process (`andromeda-pulse-mcp` binary) spawned via stdio — it does NOT share memory with the main Tauri process's buffer. **Design decision needed**: (a) sidecar opens its own ephemeral `:memory:` DuckDB connection (would be empty — no shared state; useless for `query_*` tools), OR (b) sidecar communicates with the main Tauri process via some IPC mechanism to fetch buffer data (architecturally heavy), OR (c) the `query_*` MCP tools run **inside the main Tauri process** rather than the sidecar (the rmcp ServerHandler hosts in-process; the sidecar binary is just a thin stdio↔ServerHandler bridge that forwards `tools/call` to the main process). Option (c) is most aligned with chunk #48's substrate (the sidecar binary already has the dispatch_line skeleton; chunk #49 fills in the dispatch arms) AND with arch §Established Decisions (mcp-server is a "stdio sidecar" of the main process; the rmcp ServerHandler can be hosted in either process). **Plan author should choose**; option (c) is likely.

  Likely resolution: the `mcp.start` IPC handler in the main Tauri process spawns the `andromeda-pulse-mcp` sidecar binary as a child process; the sidecar's `tools/call` handler issues IPC calls back to the main process (or shares the buffer Arc<Mutex<Connection>>) to access the live DuckDB state. The simpler implementation is to embed the buffer Connection arc into the sidecar binary at spawn time — but the sidecar is a separate process, so true memory sharing isn't possible. Alternative: the sidecar binary itself reads from a shared file or socket exposed by the main process. **Open question for plan author** — pick simplest viable: most likely the sidecar binary's stdio loop runs entirely in-process (not as a separate child) when invoked via the rmcp library's in-process transport — but the current chunk #48 substrate IS a separate-process binary, so this would require a re-design. Conservative path: chunk #49 implements tool dispatch INSIDE the sidecar binary process, which opens its own ephemeral DuckDB connection that's populated by the parent process via a shared file path or stdin-prefixed seed data. **Defer to plan author for the right resolution.**

- **`mcp.start` and `mcp.stop` semantics**: do these IPC commands actually spawn / kill the sidecar binary subprocess (since the sidecar IS the rmcp stdio server), or do they enable / disable an in-process rmcp ServerHandler that listens on stdio of the main process? The chunk #48 substrate built the sidecar binary as a separate executable, but the binary is currently designed to be invoked by an MCP CLIENT (Claude Code, etc.) via `andromeda-pulse-mcp.exe` direct command, NOT spawned by the main Tauri process. **Plan author should clarify**: is `mcp.start` toggling a feature within the main process (rmcp ServerHandler in-process, separate stdio channel) OR spawning the sidecar binary as a managed subprocess? The latter is more aligned with chunk #48's substrate; the former simplifies buffer access.

- **`pulse://stream/snapshot-progress` from MCP `generate_snapshot`**: design extract specifies the user-facing clipboard-write event MUST NOT regress when chunk #49 wires response-body redaction. For MCP-side `generate_snapshot` invocations, should this event ALSO fire? Layouts extract says NO ("MCP clients are headless; OS toast for AI-initiated snapshots is out-of-scope for the layout surface"). **Confirmed: the `pulse://stream/snapshot-progress` event fires only for the IPC-side `snapshot.generate` codepath, NOT for the MCP `generate_snapshot` tool invocation**. This means the shared curation pipeline needs a parameter or context distinguishing the two callers (e.g., `emit_user_events: bool`).
