## Implementation notes

- **Open Question — cross-process buffer access**: chunk #49's sidecar binary runs as a separate process (chunk #48 substrate). For `query_*` tools, the sidecar needs DuckDB access. Plan commits to: sidecar opens its OWN ephemeral `:memory:` DuckDB connection at boot + initializes the standard buffer schema. The ephemeral buffer starts empty — `query_*` tools return empty paginated results. Live cross-process buffer sharing (sidecar ↔ main process DuckDB ring buffer) is OUT OF SCOPE for chunk #49; deferred to Epoch 8 or a follow-up chunk. This is the minimal-viable substrate that lands the chunk's stated intent (tool dispatch + IPC + redaction + quadruple binding) without blocking on a complex cross-process IPC design. The integration tests verify dispatch routing + envelope shapes + response-body redaction; they do NOT verify live data integration (which requires the deferred architecture). Plan author may revisit at Phase 6 review.
- **`mcp.start` subprocess semantics**: spawn the `andromeda-pulse-mcp` binary as a child process of the main Tauri process via `tokio::process::Command`. Hold `Child` in `Arc<Mutex<Option<Child>>>` in `McpApiImpl`. `mcp.stop` kills the child. The child inherits NO stdio from parent (its stdio is reserved for MCP client connection, but since the child is spawned by the main process and not by an MCP client, the child's stdio is effectively dangling — MCP clients invoke the binary directly, NOT via `mcp.start`). The `mcp.start` IPC is therefore primarily a USER-FACING TOGGLE that records "MCP server enabled" state for UI (Settings modal checkbox + tray menu); the actual MCP client connection happens out-of-band when the client (Claude Code) spawns the binary directly. This is a documented quirk; user may want to revisit at Phase 6 review.
- **Order sensitivity**: implement steps 1-4 (mcp-server crate substrate extensions) BEFORE step 5 (bin entry modification) BEFORE step 6 (mcp_router.rs in pulse-app) BEFORE steps 7-9 (pulse-app + xtask + capability JSON wire-up) BEFORE steps 10-12 (test extensions). The `From<McpServerError> for AppError` extension (step 10) must happen AFTER step 1 (new Error variants) — chunk #48 plan-gap lesson preserved.
- **Resolver state sharing**: `McpApiImpl` holds `Arc<Mutex<Option<Child>>>` for the sidecar process state + `Arc<PathBuf>` for the binary path. The state is constructed once at boot in `pulse-app/src/main.rs` setup and shared into the router via Arc clones. Tests construct stub state with `Mutex::new(None)` + `PathBuf::from(env::temp_dir().join("andromeda-pulse-mcp"))`.
- **Build matrix**: the chunk's mcp-server crate changes ONLY take effect under `--features mcp-server`. Default builds (`cargo build --workspace`) MUST continue to succeed with the new code behind cfg gates. Verify via `cargo nextest run --workspace` (no feature flag) before re-running with the flag.
- **Capability JSON update is description-only**: the `permissions` array stays unchanged (`["core:default", "updater:default"]`); only the `description` text is extended. This matches the chunk #47 precedent (default.json was updated for plugins.* without adding new permission entries).
