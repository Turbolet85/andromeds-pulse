## Implementation notes

- **HTTP/JSON content-type scoping confirmation:** the OTLP HTTP spec requires both `application/x-protobuf` AND `application/json` content-types. The vendored prost-generated types do NOT have `serde::Deserialize` derives by default. Two paths: (a) add `pbjson` codegen to `crates/ingest/build.rs` to generate JSON-compatible wire types alongside protobuf; (b) defer HTTP/JSON to a follow-on chunk and ship chunk #17 with HTTP/protobuf as the canonical decoding (which is what the chunk title's `application/x-protobuf` literal mentions). **Recommend Phase 6 user review choice:** "ship HTTP/JSON in chunk #17 (full spec conformance now)" vs "defer HTTP/JSON" (matches chunk title literal + reduces scope creep). If user picks "ship HTTP/JSON," `crates/ingest/build.rs` gains a `pbjson-build` invocation alongside `tonic-prost-build`, and handlers add a `Content-Type` dispatch arm. If "defer," handlers reject non-`application/x-protobuf` with HTTP 415 (Unsupported Media Type).
- **Implementation order:** steps must be sequential because each builds on the previous: deps first (1-2) → module + tests (3-4, can be parallel for unit tests vs lib.rs) → ui-bridge slot pattern (5) → main.rs spawn (6) → observability allowlist (7) → integration tests (8) → supply-chain + verification (9-10). The ui-bridge slot pattern (step 5) is a precondition for `record_otlp_http_bind` in step 6; the observability allowlist (step 7) is a precondition for the integration tests (step 8) to assert PII fields are passed/redacted.
- **Tower middleware ordering pitfall:** `tower::ServiceBuilder` applies layers outermost-first. The order in step 3 (`TraceLayer` → host allowlist → DefaultBodyLimit → CorsLayer) means: (a) tracing wraps everything (so all rejected requests still emit boundary spans for observability); (b) Host allowlist runs early to short-circuit on rebind attempts before body read; (c) DefaultBodyLimit runs before parsing (essential — bypassing this is the JFrog axum-core advisory root cause); (d) CORS innermost is fine for default-deny since it never adds permissive headers — its job is only to NOT echo `Access-Control-Allow-Origin`. Verify ordering at /implement time by reviewing axum 0.8 `ServiceBuilder` ergonomics; `axum::middleware::from_fn` for the Host allowlist is recommended over a custom `tower::Layer` impl per research.md Open question #2.
- **Span guard discipline across `.await`:** axum handlers are async — never hold a `tracing::Span` guard across `.await` without `.in_current_span()`. The `#[tracing::instrument]` macro handles this correctly. If hand-rolling spans for the inner `parse.protobuf` block, use the `.entered()` form (returns an `Entered` guard that's safe at sync points) and DROP it before any `.await` (per `.claude/rules/observability.md` §Span discipline + combined.md anti-patterns).
- **Edition 2024 unsafe wrapping:** `protoc-bin-vendored` build.rs invocation in chunk #16 required `unsafe { std::env::set_var(...) }` per Edition 2024's `set_var` unsafe contract. No new build.rs additions in chunk #17 (vendored proto compilation is reused), so this contract does not surface again.
- **`tower` 0.5 vs `tower` 0.4 transitive risk:** `axum` 0.8 targets `tower` 0.5 + `tower-http` 0.6 + `hyper` 1; `tonic` 0.14 ALSO targets `tower` 0.5 + `hyper` 1, so the transitive risk for `tower` duplicate is low. If `cargo deny check bans` fires anyway (e.g., a transient transitive pulls 0.4), add a provenance entry to `deny.toml [bans] skip` per chunk #16 pattern — do NOT relax `multiple-versions = "deny"`.
- **Axum 0.8 macros feature:** the `axum/macros` feature enables `#[debug_handler]` for clearer error messages on handler signatures. Recommended for development; not required for production. Include in workspace deps to ease debugging, then optionally trim at chunk #17 review if footprint matters.
