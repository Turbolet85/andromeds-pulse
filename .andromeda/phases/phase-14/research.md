## Patterns detected

- **`try_bind(addr) -> std::net::TcpListener` + `serve_on(listener, state) -> Future` split** (`crates/ingest/src/grpc.rs:249-290`): the canonical bind/serve split for ingest receivers. Splitting allows `pulse-app/src/main.rs` to record `BindStatus::Ok` synchronously after listener accepts before the long-running serve future yields. Implementation uses `tokio_stream::wrappers::TcpListenerStream` to bridge `TcpListener` → tonic's `serve_with_incoming`. For axum HTTP, the equivalent is `axum::serve(listener, app.into_make_service())`. Same pattern shape, same `Result<(), Error>` return type using existing `Error::BindFailed` + `Error::ServeFailed` variants.

Mirrors at HTTP boundary as `parse.protobuf` (for `Content-Type: application/x-protobuf`) and `parse.json` (for `Content-Type: application/json`).

## Open questions

1. **HTTP/JSON decoding strategy** — OTLP spec accepts `application/json` per the `:4318` HTTP profile; the JSON encoding of OTLP messages is well-defined (snake-case field names, base64 for `bytes` fields like `trace_id` / `span_id`). The vendored prost-generated types do NOT have `serde::Deserialize` derives by default. Two options: (a) add `pbjson` codegen to `crates/ingest/build.rs` to generate JSON-compatible types alongside protobuf; (b) hand-code `serde::Deserialize` impls or use a thin per-handler decoder. **Recommendation for chunk #17:** scope HTTP/JSON to a follow-on chunk if `pbjson` integration is non-trivial, OR implement `pbjson` codegen now since it's a one-time build.rs addition. Per OTLP spec compliance, BOTH content-types are required for full conformance — but `application/x-protobuf` is the de-facto SDK default and meets the chunk title's primary spec-bar. **Surface to user at Phase 6 review:** confirm whether HTTP/JSON ships in chunk #17 or deferred.
2. **Host-header allowlist as custom `tower::Layer` vs request-extractor pattern** — `tower-http` does not provide a built-in Host-header allowlist. Cleanest implementation is a small custom `tower::Layer` + `tower::Service` impl that inspects `HeaderMap`, returns `axum::http::StatusCode::FORBIDDEN` body if rejected. Alternative: `axum::middleware::from_fn` callback. **Recommendation:** use `axum::middleware::from_fn` (idiomatic in axum 0.8, simpler than custom Layer/Service); function inspects `Host` header against allowlist `["127.0.0.1:{port}", "localhost:{port}", "[::1]:{port}"]`; reject with `StatusCode::FORBIDDEN`. Plan.md should specify this.
3. **CORS layer placement order** — `tower::ServiceBuilder` ordering matters: `DefaultBodyLimit` + Host-header allowlist + CORS deny + tracing instrument. Order should be: outermost = tracing (so all spans see request); then Host allowlist (reject early before body read); then DefaultBodyLimit (reject oversize bodies before parsing); then CORS (innermost — only matters for browser requests, which are blocked by Host allowlist anyway, but spec-correct posture). **Recommendation:** confirmed order in plan.md.
4. **Whether `http_loopback.rs` should reuse `make_span` / `make_export_request` from `grpc_loopback.rs`** — currently the helpers are local to grpc_loopback.rs.
