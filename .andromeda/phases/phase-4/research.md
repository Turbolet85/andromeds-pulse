## Conventions to follow

- **`workspace.dependencies`-first pattern**: any new direct version pin MUST go through `Cargo.toml [workspace.dependencies]` and be referenced via `crate.workspace = true` in member crates (per `xtask/Cargo.toml:14-18`). For chunks #5/#6, this means `cargo-llvm-cov` (if invoked from xtask code) or any new workspace-level deps follow this pattern.
- **xtask kebab:case subcommand naming**: `xtask/src/main.rs:15` uses `#[command(name = "harness:status")]`. New subcommands follow same shape — `cargo xtask test`, `cargo xtask audit`, `cargo xtask deny-bans`, `cargo xtask ci-gates` (or `xtask ci:zero-panic` / `xtask ci:zero-spans` per-gate). Plan picks single-token vs colon-namespaced based on per-tool semantics.
- **`.cargo/config.toml [alias]`-relative invocation**: every `cargo xtask <task>` resolves through the alias. Workflows + scripts use `cargo xtask <task>` form, NEVER `cargo run -p xtask -- <task>` (loses `--quiet` and adds Cargo build noise).
- **`ANDROMEDA_PULSE_DATA_DIR` env discipline** (`scripts/agent-run.sh:21` + `pulse-app/src/main.rs:16`): override-friendly per arch §Occupied Resources. CI workflow MUST set this to `$RUNNER_TEMP/andromeda-pulse-ci-data` (or equivalent platform-stable temp path) so artifact upload paths are predictable. Sub-paths under override are identical to per-platform default (`logs/`, `run/`, `snapshots/`, `plugins/`).
- **`deny.toml` skip-list provenance comment format**: `# {upstream} (route#{N}, YYYY-MM-DD)` for each new entry (per `deny.toml:62-78` precedent). Chunk #6 `[[bans.deny]]` for `tonic` follows this comment shape with the OTLP-receiver context.
- **No-OTel-SDK-in-pulse-app workspace constraint**: per observability rule loaded into context, `tracing` ecosystem ONLY for self-observation. Supply-chain gate's `cargo deny check bans` enforces this transitively (any future PR pulling `opentelemetry-otlp` into pulse-app's closure trips the gate). Plan does NOT add an explicit `[[bans.deny]]` for `opentelemetry-otlp` because that crate is legitimately consumed elsewhere — but the canary stays the `tonic 0.14↔0.13` duplicate.
- **JSON Layer default fields registration deferred to chunk #7**: per binding contract in `.claude/rules/observability.md` "Register once at subscriber init via `Layer::with_default_fields([service_name, service_version, deployment_environment])`", current `pulse-app/src/main.rs` emits these as per-event fields (lines 62-69), not as Layer default fields. Chunk #7 (tracing self-observation harness) is the natural place to extend the Layer with `with_default_fields` + read `GITHUB_RUN_ID` / `GITHUB_SHA` / `deployment.environment` from env. **Chunk #5 lays the workflow env**; chunk #7 wires consumption.

## Open questions

1. **Explicit `[[bans.deny]]` for `tonic` vs implicit-via-`multiple-versions`?** The security extract AC requires `tomlq '.bans["multiple-versions"]' deny.toml` returns `"deny"` AND "explicit `[[bans.deny]]` entry naming `tonic`". The current `deny.toml:30` has `deny = []` (empty). Adding `[[bans.deny]] name = "tonic"` would make ANY `tonic` dep across the workspace fail — too aggressive (tonic 0.14 IS a legitimate workspace dep for the OTLP gRPC receiver in chunk #16+). The intent is to fail the build when **two versions** of tonic coexist, which `multiple-versions = "deny"` already does (catching the `tonic 0.14 ↔ opentelemetry-otlp 0.31's pinned 0.13` duplicate). Plan must reconcile: (a) leave `[[bans.deny]]` empty and rely on `multiple-versions = "deny"` (matches existing comment lines 32-35 but doesn't satisfy literal AC text); (b) add a `[[bans.deny]] name = "tonic", version = "<0.14"` entry to specifically deny pre-0.14 tonic (catches the duplicate while permitting the canonical 0.14); (c) reinterpret the AC as "explicit `[[bans.deny]]` mechanism scaffolded with at least one entry referencing the OTLP duplicate, even if the entry is currently a `# canary placeholder` style anchor". Recommend (b) — concrete + version-aware + canary-specific.
2. **Where to read `GITHUB_RUN_ID` / `GITHUB_SHA` envs into the tracing subscriber?** Per obs-plan §9 + observability rule, `with_default_fields([..., ci.run.id, git.commit.sha])` lives at subscriber init. But `pulse-app/src/main.rs:38-72` is the only init site, and chunk #5's primary scope is workflow YAML, not Rust code. Recommend deferring the actual `with_default_fields` wiring to chunk #7 (Tracing self-observation harness) and at chunk #5 only setting workflow-level env vars so they're available — chunk #7 then reads + attaches. This split is consistent with the obs extract distinction: chunk #5 lays the workflow env; chunk #7 consumes via subscriber extension.
3. **GitHub Environment `production-release` creation: file vs gh-CLI vs UI?** Environment is a repo-level GitHub config, not a checked-in file. Plan SHOULD include a runbook (analogous to `docs/runbooks/updater-key-rotation.md` from chunk #3) describing the `gh api repos/:owner/:repo/environments` POST that creates the Environment with `required_reviewers` rule. Pre-paid-component AC verification (security AC: "GitHub Environment `production-release` exists with manual approval gate") is achievable via the gh-CLI POST without needing Azure Key Vault / EV cert / Apple Dev ID populated yet — those remain DEFERRED per chunk #3 scope split. Plan must clarify.
4. **`xtask test` vs direct `cargo nextest` invocation in ci.yml?** Arch §Infrastructure Patterns CI/CD final paragraph mandates `cargo xtask <task>` for shared CI logic. But `cargo nextest run --workspace --profile ci --no-tests=pass --message-format libtest-json` is concise enough that an `xtask test` wrapper adds indirection without saving complexity. Recommend wrapping anyway (per arch convention) — `xtask test` exec's `cargo nextest run` and forwards args/exit code, which means local dev + CI invoke the same surface. Plan picks the wrapper approach.
5. **Coverage gate active enforcement vs warn-only at chunk #5?** Tests extract notes "At chunk #5 land time the Foundation epoch may not yet hit thresholds — gate enforcement MUST NOT be relaxed (a 'warn-only' mode is permissible only if explicitly documented as a deferred-to-route#X gate-flip)." With 0 tests in the workspace currently, line/branch/function coverage is technically 100% (no covered code). `cargo-llvm-cov` may emit `--no-tests=pass`-style behavior. Plan must verify: does cargo-llvm-cov treat 0-test workspaces as passing the threshold trivially, or does it fail? If trivially-passing, no gate-flip needed; if zero-coverage failure, plan documents `--no-tests=pass` flag for the coverage gate too, with explicit comment "gate flips to active enforcement at chunk #15 — first tests land".
