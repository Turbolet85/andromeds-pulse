## Combined goal

These two chunks materialize the project's CI substrate from cold-start: `.github/workflows/ci.yml` with a Linux/macOS/Windows matrix that runs the locked `cargo fmt → cargo clippy → cargo xtask test → cargo build --release` sequence on every PR and push to main, plus a coverage gate via `cargo-llvm-cov nextest` at the Standard tier (≥75% line / ≥70% branch / ≥85% function), plus the four supply-chain gates (`cargo-audit`, `cargo-deny check bans licenses sources`, `cargo-auditable`, `gitleaks` secret-scanning) wired into the same workflow with `step-security/harden-runner` as the first step of every job, every third-party Action SHA-pinned by 40-char commit, workflow-level `permissions: contents: read`, and `.github/dependabot.yml` configuring `cargo` + `github-actions` + `npm` ecosystems.

The chunks share a single workflow file because they're install-style with a shared milestone — chunk #5 lays the matrix shell + nextest + coverage gate + obs SLO scaffolding; chunk #6 layers in the supply-chain steps + Dependabot + gitleaks (per-PR + pre-commit) + GitHub Environment `production-release` scaffolding. The Environment is created as a named container with manual approval gate; population with paid components (Azure Key Vault Premium SKU, EV cert, Apple Developer ID enrollment, GitHub OIDC federation trust) remains DEFERRED per the chunk #3 scope split (see `docs/runbooks/production-release-environment.md` runbook landing in this phase).

Everything Rust-touching goes through `cargo xtask <task>` per arch §Infrastructure Patterns CI/CD ("All shared CI logic that needs Rust lives in the xtask crate so contributors can run identical commands locally"); the workflow YAML invokes `cargo xtask test` / `cargo xtask audit` / `cargo xtask deny-bans` / `cargo xtask ci-gates` rather than inlining cargo invocations. The obs zero-panic + zero-spans CI gates ride on the existing `tracing` JSON subscriber landed in chunk #4 (no new subscriber wiring at this phase — `with_default_fields([service.name, service.version, deployment.environment, ci.run.id, git.commit.sha])` is deferred to chunk #7 Tracing self-observation harness; chunk #5 only sets the workflow-level env so chunk #7 can read them).

## Implementation notes

- **Order of implementation within /implement:** chunk #5 (CI workflow shell + xtask test/coverage/ci-gates) first, then chunk #6 (supply-chain steps + Dependabot + gitleaks + production-release Environment runbook). The chunk #6 supply-chain steps mount onto the ci.yml workflow created in chunk #5 — implementing #6 first leaves no workflow file to mount onto.
- **Action SHA materialization:** the plan references `<40-char-SHA>` as a placeholder for every third-party Action. /implement MUST resolve to actual current SHAs at materialization time (e.g., via `gh api repos/step-security/harden-runner/git/refs/tags/vX.Y.Z` for each Action) and include the version-tag comment trailer (e.g., `# v2.10.4`). Do NOT use floating tags in the materialized YAML — the security AC enforces 40-char SHA pinning.
- **Coverage gate at 0-tests-state:** `cargo-llvm-cov nextest --no-tests=pass` is the gate-flip mechanism. With 0 tests in the workspace, lcov.info will show 0/0 for line/branch/function coverage; the parsing step needs to handle the divide-by-zero or 100% trivial case. Recommended: parse lcov.info; if total lines = 0, exit 0 (trivially passing); else apply 75/70/85 thresholds. This avoids a "warn-only" mode entirely — the gate is structurally real, just trivially passing today.
- **GitHub Environment creation idempotency:** the `gh api .../environments/production-release` POST is idempotent (creating an existing Environment is a no-op). The runbook should be runnable repeatedly without side effects.
- **gitleaks Action version SHA + pre-commit revision sync:** the security AC requires "both invocations resolve to the same tool release". /implement materializes both with the same gitleaks vX.Y.Z, then resolves Action SHA + pre-commit `rev` to match. Verification: `gitleaks/gitleaks-action@<SHA>` annotation matches `.pre-commit-config.yaml` `rev: vX.Y.Z`.
- **Heartbeat-gap script INACTIVE state semantics:** the script must exit 0 when no tick records are found in `agent-latest.jsonl` — at chunk #5/#6, the JSON log contains only `app.boot.*` events (chunk #4 init code) and no `{ingest|buffer|viz|plugins}.tick` events yet. The script's "no records → exit 0" path is the INACTIVE state. When `ingest.tick` first appears (chunk #16), the script's gap-detection logic activates organically.
- **xtask binary growth:** chunks #5/#6 add ~5 new clap subcommand variants. Future chunks will likely add more (`xtask capability-drift`, `xtask test:a11y`, `xtask release` per route#46). Plan does NOT split xtask into multiple modules at this phase — keep `src/main.rs` flat until clap dispatcher exceeds ~150 lines, then refactor into per-task modules.
- **DEFERRED secret population not in /implement scope:** Azure Key Vault Premium SKU + EV cert + Apple Developer ID + GitHub OIDC federation trust are pre-v0.1.0 release blockers but NOT chunk #5/#6 scope. /implement creates the Environment shell only; secret population is the user's manual responsibility per chunk #3 scope split (route Decisions Log 2026-05-03).
