## Open questions

- **Q1 (RESOLVED in Phase 4 plan)**: Should heartbeat tasks spawn before or after Tauri runtime starts? Tauri `Builder::run()` blocks main thread; tasks must spawn BEFORE `.run()` so they enter the tokio runtime. Current main.rs structure supports this — spawn just before the `tauri::Builder::default()` line, after `record_start()` and `write_pid_file()`.
- **Q2 (RESOLVED in Phase 4 plan via combined.md cross-domain reconciliation)**: How does `health` handler get the latest tick timestamps? Use a static `OnceLock<Arc<HeartbeatState>>` in `crates/ui-bridge/src/health.rs` (mirrors the existing `APP_START` `OnceLock<Instant>` pattern at line 10). pulse-app's main calls `ui_bridge::health::register_heartbeat_state(state.clone())` after constructing the state, before spawning tick tasks.
- **Q3 (RESOLVED via observability.rs research)**: Does the existing `tokio::time::interval` discipline already cover graceful shutdown? Yes — tokio runtime drops outstanding tasks on shutdown; tick tasks have no resources to clean up beyond the shared state Arc, which drops with the runtime. The harness `cleanup` 5s SIGTERM window is satisfied because `tokio::time::interval` is cancellation-safe at every `await` point (per tokio docs).
- **Q4 (FOR PHASE 6 USER REVIEW — NEEDS CONFIRMATION)**: The combined.md surfaces an arch-level concern about adding `viz` + `plugins` to `SubsystemStatuses`. The verification-harness rule (`.claude/rules/verification-harness.md` §Status endpoint shape) lists exactly 4 subsystems. Phase 4 plan proposes adding 2 more additively, AND updating the rule to match. **Decision к confirm at user review:** is rule-edit acceptable, OR does user prefer keeping `viz` and `plugins` heartbeats out of the health envelope and relying solely on the log-file gap-analysis (xtask ci-gates heartbeat-gap-check) for stall detection? Plan defaults to additive extension since the obs ↔ arch binding explicitly cites "the `health` IPC command MUST expose the same fields synchronously" and the heartbeat-gap CI script already targets `viz.tick` + `plugins.tick`.
