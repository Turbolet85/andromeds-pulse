## Open questions

1. **Design ambiguity — sub-task 3 (P-010 baseline-relative semantics)**: capability spec P-010 says "short-term (30-second window) error rate exceeds its baseline by factor of 3.0 or more". Current `ServiceMetricSnapshot.error_rate` IS the EWMA baseline (5-min window per chunk #61). There is no separate short-term tracker. To implement the spec correctly requires EITHER (a) add a second EWMA tracker per service with shorter window (e.g., 30s alpha) — non-trivial baseline-state extension; OR (b) interpret the existing snapshot.error_rate as "current" and compare against `BaselineState::error_rate(service_name)` accessor result captured at sample-start (would be self-referential — they're the same value at the same time). Path (a) is the spec-correct path but extends baseline tracker. Path (b) requires "baseline" to mean something different than "current EWMA". /implement Phase 2 must resolve which path; surface to user at Phase 6 review.
2. **Design ambiguity — sub-task 5 (P-012 per-operation t-digest p99 read)**: spec says "current p99 latency for an operation exceeds baseline p99 by factor of 2.5 or more". Current `OperationMetricSnapshot.latency_at_percentile` is the t-digest at the percentile parameter — same value at all sample times for a stable distribution; the "baseline" vs "current" comparison again requires distinguishing short-term vs long-term distributions. Same path A/B dilemma as sub-task 3. Recommend Path (b) for both: reinterpret threshold semantics from "absolute" to "relative against rolling reference window" with the reference window snapshot being captured periodically rather than via a separate tracker.
3. **MIN_QUIET_SECONDS placement**: const in thresholds.rs (hard floor; not user-configurable) vs field on `Thresholds` struct (configurable, hot-reload-able per chunk #86 future scope). Recommend const for chunk #73 (matches "compile-time constants" security extract guidance); upgrade to field if a user-need surfaces.
4. **Panic-atomic placement**: module-level `static AtomicBool` in observability.rs (simplest; tests can reset via `pub(crate) fn reset_panic_signal()`) vs `Arc<AtomicBool>` threaded explicitly through boot wiring (more testable; matches Arc-based dependency injection precedent of `HeartbeatState`). Recommend module-level static + `pub(crate) fn reset_panic_signal()` for tests — minimal API surface change; integration test still works via the public `panic_signaled()` accessor.
5. **`compute_state` signature change for panic signal**: currently takes `any_receiver_failed: bool`. After sub-task 2, derive_reason needs to distinguish bind-failed vs panic. Options: (a) extend signature to `compute_state(last, now, any_receiver_failed: bool, receiver_panicked: bool)` — clean separation; (b) merge into trait read with `compute_state(last, now, bind_status: &dyn ReceiverBindStatus)` — coupling to trait; (c) compute the failure category higher up (start_poller) and pass the reason directly. Recommend (a) — preserves pure-function purity of compute_state for testability; start_poller reads both flags and passes.
6. **Threshold-bump test impact**: chunk #50's `pulse-app/tests/perf_slo_10k_spans.rs` may have implicit timing assumptions about IDLE/STALLED transitions — needs verification. The boundary tests in `crates/ingest/src/connection.rs::tests::compute_state_age_at_idle_threshold_boundary_returns_idle` + `compute_state_age_between_idle_and_stalled_returns_idle` (using hardcoded 10_000_000_000 and 60_000_000_000) should be reviewed after the constant change — the test at line 395 (10s = new IDLE_THRESHOLD boundary) still returns Idle correctly; the test at line 409 (60s past = new STALLED_THRESHOLD boundary) still returns Stalled. No test rewrites needed if hardcoded values happen to land on the right side of new boundaries.
