Known pitfalls discovered in research:

- **Hardening the panic hook FIRST without adding the atomic signal causes a regression** where panics no longer expose the full payload but ReceiverPanicked is still unreachable. The two changes are intentionally bundled in sub-task 2.
- **Don't add `panic_signaled` as a NEW trait method without a default impl** — would break any out-of-tree impls if they exist. The default-impl approach is backward-compatible.
- **Don't add operation_name to AllowList for any triage tracing target** — would silently violate the aggregate-only convention. Verify by grepping new tracing macro call sites after sub-task 4.
- **The static `PANIC_SIGNAL: AtomicBool` is per-process global state** — tests resetting it must use `observability::reset_panic_signal_for_tests()`. Concurrent tests running in the same process could see panic signals from sibling tests; mitigate via nextest's per-process isolation (default) OR by serial-only test grouping if `start_paused` shared state surfaces. Per test-plan §3 cargo-nextest provides per-process isolation by default — should be fine.
- **`%info` field format** captures PanicInfo's Display impl which prints `panicked at 'msg', file:line` — the `'msg'` portion IS the panic message but flows through Display formatting which is the canonical "safe" form per Rust convention (vs raw payload downcast which exposes literal `panic!()` argument).
- **The 45s heartbeat-CI-alarm and 60s STALLED threshold are now in REVERSE precedence vs the pre-bump 45s alarm > 30s STALLED ordering** — after bump, the CI alarm fires BEFORE the FSM transitions to Stalled. This is acceptable because they measure different things (ticks vs OTLP spans); the docstring rewrite at sub-task 1 documents this independence explicitly so future readers don't re-derive the coupling.
