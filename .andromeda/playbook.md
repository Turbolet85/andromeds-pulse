## Rules
- pattern: Foundation-sequencing deferral — a drift-detector flags a gap (a tool not yet installed, a capability not yet hardened, a dependent not yet wired) whose resolution is a LATER, still-pending chunk's defined job — e.g. `cargo-audit` used before the audit-gate chunk; a struct landed before its validation chunk; an endpoint before its auth chunk.
  verdict: routine
  note: greenfield builds land capabilities first and harden / depend on them in later chunks — expected bootstrap ordering, NOT spec drift (the spec is right; the resolving chunk just hasn't run yet). Apply silently. Auditable caution — it is sequencing ONLY if a later chunk genuinely owns the resolution; a gap with NO resolving chunk anywhere in the route is real drift → escalate.

- pattern: New env var (or similar bounded config input) registration — a drift detector flags that a new env var the chunk added is absent from a spec registry (arch §Occupied Resources env vars; security-plan §Input Validation table), AND the report shows the input is code-validated (bounded enum / truthy / `TryFrom` parse) + unit-tested.
  verdict: routine
  note: a code-validated + unit-tested env var is registry-completeness drift, NOT an unvalidated-boundary security hole — apply the registration silently. D-security-input's escalate-severity is for ACTUALLY-unvalidated boundaries; an env var the report shows validated + tested does not need a HALT. (Codified 2026-06-28 from the P-073 deterministic-L4 env-var registration; escalated once, then ruled routine WITH the user.)

- pattern: Drift proposal documenting a PRE-EXISTING hot-path / operation / span / metric the chunk did NOT introduce — the report's Changes mark the surface's instrumentation present (✓) and the proposal's named symbols (span / metric targets) do NOT appear in the report's Changes, OR the path traces to earlier chunks rather than this one.
  verdict: routine
  note: routine-REJECT (false positive / over-reach, not this chunk's drift). A detector may fire on an existing instrumented pipeline that the current chunk only extends internally (e.g. threading a value through an already-traced carrier); documenting that pipeline now mis-attributes earlier chunks' work to this marker AND risks recording symbols that do not exist. The wrap STILL records a genuine pre-existing doc gap (if any) as a handoff note for a future targeted touch-up — never as this chunk's amendment. (Codified 2026-06-28 from the P-074 D-obs-instrumentation over-reach: proposed a "P8 incident-coalescing" path with invented span names — `cadence.trigger.emit` / `digest.assemble.incident` — for the chunks #80–#92 cadence→digest→incident pipeline that P-074 only threaded a cue through; rejected WITH the user.)

- pattern: Drift proposal documenting a surface / region / element / span / metric / operation the chunk did NOT introduce — GENERALIZES the obs-scoped 2026-06-28 pre-existing-hot-path rule to ANY detector (layout / a11y / design / arch / obs). The named thing does NOT appear in the report's Changes as NEW this chunk (it pre-existed an earlier chunk, OR the chunk only adds states / refinements WITHIN an already-documented surface).
  verdict: routine
  note: routine-REJECT (false positive / over-reach). A detector may fire on an existing documented surface the current chunk only extends internally (e.g. adding result/error render states within an already-wireframed modal). Documenting it now mis-attributes earlier chunks' work to this marker AND may apply inaccurate text. The wrap STILL records a genuine PRE-EXISTING doc gap (if any) as a handoff note for a future targeted touch-up — never as this chunk's amendment. (Codified at the 2026-06-28-investigate-actions-functional wrap (P-072) from the D-layout-surface over-reach: proposed rewriting layout-templates §Investigation modal for the 4 action buttons [pre-existed chunk #43] + result/error panels [within-surface states, not a new wireframe surface per the phase layout specialist]; the doc ALSO carries a separate pre-existing modal-vs-reality divergence this chunk did not cause. Rejected WITH the user; generalizes the 2026-06-28 obs rule to all detectors.)

- pattern: Drift proposal FIXING a real but PRE-EXISTING cross-spec harness-bind inconsistency (e.g. test-plan §3 ↔ obs-plan §3 — log filename / status-endpoint shape / 5-command discipline) that the chunk's work merely EXPOSED but did NOT introduce or touch, where the inconsistency spans MULTIPLE artifacts the chunk did not change (the spec + its impl + a sibling reader), so amending the one artifact the detector named is INCOMPLETE.
  verdict: routine
  note: routine-HANDOFF (neither apply-under-this-marker nor the 2026-06-28 routine-REJECT). Distinct from the over-reach rules (which reject FALSE / inaccurate proposals about pre-existing surfaces): here the proposal is ACCURATE and the drift is REAL — but it pre-exists the chunk, and fixing only the artifact the detector named (while the impl + sibling readers keep the old form) creates a NEW spec-vs-impl mismatch worse than the status quo. Record the FULL inconsistency family as a handoff note for a targeted cleanup chunk; do not amend under this marker. The chunk's own new code is already correct (it does not share the bug). (Codified 2026-06-29 WITH the user at the predictable-close-self-verify wrap from the D-tests-obs-harness finding: the new self-verify harness exposed test-plan §3 logs `*.log` ≠ agent-run.sh bare `agent-latest.jsonl` ≠ reality `agent-latest.jsonl.<date>` [+ `smoke.rs::run_smoke` same bare-name bug]; handoff-bundled with the smoke.rs cleanup rather than amend test-plan §3 in isolation.)

- pattern: Drift proposal (D-arch-resources) registering an individual Tauri CORE permission (`core:window:*` / `core:webview:*` / `core:app:*` etc.) — granted WITHIN an existing capability file (`pulse:default`) — into arch §Occupied Resources §Tauri capability identifiers. That arch list enumerates the project's `pulse:*` capability IDENTIFIERS (the capability JSON FILES), NOT the individual core perms granted inside them.
  verdict: routine
  note: routine-REJECT (registry mis-categorization, not drift). Core Tauri perms are granted in `pulse-app/capabilities/default.json` WITH a stated rationale per arch §Webview IPC capability policy (which already covers "an explicit per-feature capability addition with a stated rationale"); they are NOT arch §225 entries. P-061's `core:window:{allow-start-dragging,minimize,toggle-maximize}` set the precedent — granted in default.json, never added to arch §225 — so a newly-granted sibling (`allow-close`, future chrome-suppression perms) follows the same pattern. The doc is not wrong; the detector over-reached by treating a core perm as a capability identifier. (Codified 2026-06-30 WITH the user at the 2026-06-29-window-size-constraints wrap from the D-arch-resources proposal to add `core:window:allow-close` to arch §225.)

- pattern: Drift proposal (D-obs-instrumentation) demanding instrumentation for — OR proposing to document an instrumentation EXEMPTION for — a frontend DOM event handler that only calls `preventDefault()` (no state mutation, no data processing, not on a P1–P7 critical path), e.g. a `contextmenu` / `dragstart` / `selectstart` suppression handler.
  verdict: routine
  note: routine-REJECT (false positive / over-reach). A `preventDefault()`-only DOM suppression handler is NOT an instrumentable hot path — it carries no data flow and is none of the obs §4 desktop-webview targets (web-vitals / component lifecycle / WebGPU frame-timing / empty-error counters); instrumenting it would VIOLATE the obs §5 anti-pattern "NEVER emit high-frequency telemetry inside DOM event handlers (frame-budget cardinality)". The obs-plan is not wrong (it never required instrumenting chrome-suppression handlers), so adding an exemption clause for a non-required thing is unnecessary spec-bloat. Distinct from the 2026-06-28 over-reach rules (which cover PRE-EXISTING operations the chunk did not introduce): this covers a handler NEWLY introduced by the chunk that legitimately needs no telemetry. (Codified 2026-06-30 WITH the user at the 2026-06-30-browser-chrome-suppression wrap from the D-obs-instrumentation proposal to add a §10 exemption subsection for the `useSuppressBrowserChrome` preventDefault-only handler.)

- pattern: Drift proposal (D-tests-framework / D-tests-coverage) to WEAKEN test-plan §3's always-run gate baseline because a chunk DEFERRED a standard gate (e.g. `cargo nextest run --workspace`) at /implement — where that deferred gate then RAN GREEN at the wrap light gate (P7).
  verdict: routine
  note: routine-REJECT (false drift). The wrap P7 light gate re-runs the chunk's plan Test Commands, so a gate deferred at /implement is RUN at the wrap gate — test-plan §3's "list + run the full gate set" mandate is SATISFIED for the chunk (the gate ran, just later in the pipeline), NOT skipped. Weakening §3 would defeat the chunk-gate-baseline-coverage trigger (testing.md 2026-05-10) that keeps the baseline always-run. The /implement↔wrap split is a source-delta-proportional timing choice, not a coverage gap; testing.md §3 stays unchanged. (Codified 2026-06-30 WITH the user at the 2026-06-30-widget-to-dashboard-navigation wrap: D-tests-framework proposed amending §3 to permit nextest deferral; the full nextest had already run green at the wrap light gate.)

- pattern: Drift proposal registering an ACCURATE this-chunk addition/correction WITHIN an already-documented doc structure — a new §Component / pattern entry, or a token-value / prose correction, for a surface / element / state the CURRENT chunk genuinely introduced or changed (its named symbols / values DO appear in the report's Changes as this-chunk work), landing inside an existing section (design-system §Component Patterns, layout-templates §Component, etc.).
  verdict: routine
  note: routine-APPLY (register current truth) — the APPLY-SIDE dual of the 2026-06-28/06-30 over-reach REJECT rules (which target INACCURATE / mis-attributed / PRE-EXISTING content). Here the addition is accurate + THIS chunk's + on-topic, so amending the doc to match shipped reality is correct, not over-reach. Distinct from the 2026-06-29 pre-existing-inconsistency HANDOFF (which defers a gap the chunk did not cause AND whose one-artifact fix would worsen a spec↔impl mismatch); here fixing the doc ALIGNS it with the chunk's shipped code. (Codified 2026-07-08 WITH the user at the self-explaining-empty-states wrap (P-071): applied a layout-templates §Component entry for the new empty/error-state region + a design-system §Loading/Empty-States token Tertiary→Secondary correction; recurrence of the P-070 §Component—Footer ConnectionStatusLine apply-both — the candidate rule the P-070 handoff deferred to recurrence.)

- pattern: Drift proposal ACCURATELY correcting a doc claim that a PRE-EXISTING reality falsifies, where the IMPL is already correct and only the doc is wrong — so the fix completes in ONE artifact (no impl half, no sibling reader, still carrying the old form).
  verdict: routine
  note: routine-APPLY (register current truth). This is the DISCRIMINATOR between the two rules that otherwise both match a pre-existing gap. The 2026-06-29 routine-HANDOFF defers a pre-existing inconsistency because fixing the one artifact the detector named — while the impl + sibling readers keep the old form — creates a NEW spec-vs-impl mismatch worse than the status quo. That reasoning does not apply when there is nothing else to fix: the impl already embodies the exception, the doc alone misstates it, and amending it strictly improves alignment. The test is one question: is there an impl half to fix? NO → APPLY. YES → HANDOFF (record the full family, defer to a targeted cleanup chunk). Distinct also from the 2026-06-28/06-30 over-reach REJECT rules, which target INACCURATE or mis-attributed proposals — here the proposal is accurate and the drift is real. (Codified 2026-08-14 WITH the user at the fingerprint-feed-capture-repair wrap: D-tests-framework proposed documenting the pulse-app `[lib] test = false` test-location exception; the claim "no separate `tests/` directory" was false against 59 files already in `pulse-app/tests/`, the impl needed no change, and the gap had already cost two session learnings plus this chunk's plan step 9.)

- pattern: External-decay gate failure — a gate cannot RUN (not: runs and fails) because an artifact OUTSIDE the repo is broken or unavailable, no code change can clear it, and the failure reproduces on retry.
  verdict: routine
  note: routine-BOUNDED-WAIT. Distinct from the Foundation-sequencing deferral (no LATER CHUNK owns this — an UPSTREAM does) and from a `tooling.environmental` soft-exit (there the chunk cannot finish; here the chunk is otherwise green and only one gate is unrunnable). Requires ALL FOUR of: (a) the fault is external + reproduced on retry; (b) a NAMED overlap signal covering the same class still runs, with its result recorded; (c) a COMPACT standing entry — origin · ratified-at · one-line basis · named overlap · origin-report pointer; (d) a probe re-run interval. Absent any of the four → escalate. The overlap signal's own findings get their standing disposition made VISIBLE (the signal's value is detecting NEW findings, so an undifferentiated red defeats it): findings with a stated safe upgrade are NEVER ignore-listed — they get a named owner — and only no-safe-upgrade findings take an ID-scoped ignore entry. (Codified 2026-08-15 WITH the user at the corpus-key-persistence wrap: `cargo audit` could not load the RustSec DB at all — `parse error: duplicate advisory ID: RUSTSEC-2026-0244`, reproduced — the same upstream event Conductor hit; `cargo deny check advisories` was ratified as the named overlap, its 3 no-safe-upgrade IDs ignore-listed and its 7 upgradeable ones routed to an owner rather than accepted.)

- pattern: Drift proposal ACCURATELY correcting a doc claim that a MEASUREMENT disproved, where an impl half DOES exist but is too large to ride this chunk (it needs its own route entry) — so the 2026-08-14 discriminator ("is there an impl half to fix? YES → HANDOFF") would defer the doc fix too.
  verdict: routine
  note: routine-APPLY-AS-MEASURED — the THIRD disposition for a pre-existing gap, beside routine-APPLY (2026-08-14, doc-only fix) and routine-HANDOFF (2026-06-29, defer both halves). Amend the body to record BOTH the INTENDED posture and the MEASURED reality, state the consequence plainly (incl. any data-loss implication), and NAME the route entry that owns the impl fix. The 2026-06-29/2026-08-14 HANDOFF reasoning assumes a one-artifact doc fix would CREATE a new spec↔impl mismatch — that assumption fails when the amendment explicitly records the gap AND its owner, because the doc then describes reality more accurately than before, not less. The discriminator is therefore two questions, not one: (a) is there an impl half? NO → plain APPLY. (b) YES → does the amendment record the gap + name its owner? YES → APPLY-AS-MEASURED. NO → HANDOFF. Keep the three routes separated: the amendment records measured truth, the report's "Spec claims disproved by measurement" bullet carries the disposition, and a NEW route entry owns the fix. (Codified 2026-08-15 WITH the user at the workspace-key-alignment wrap: architecture.md §Occupied Resources + security-plan §Secret Management both declared an OS-keychain-sourced corpus key; `keyring 3.6.3` resolves with `[log, zeroize]` only — the non-persisting mock store — so the key is per-process ephemeral and every payload written by an earlier process is orphaned. 8 proposals across 6 restating sites applied as measured; the impl fix went to a new "Corpus key persistence" route entry.)

- pattern: Drift proposal (D-obs-pii, escalate severity) registering a NEW self-observation logging target the CURRENT chunk introduced into obs-plan's §8 allowlist / §6 log-level enumeration — where the report shows the target's fields are bounded non-PII (counts / enum labels / bounded static strings), it already has an EXACT leaf with no bare prefix key, and a guard test asserts both field-completeness and the PII bans.
  verdict: routine
  note: routine-APPLY (registry completeness, not a PII hole). D-obs-pii's escalate severity exists for RAW user input / PII reaching the log — an allowlist-leaf registration whose fields the report measures as bounded and non-PII does not need a HALT. Exactly parallel to the 2026-06-28 new-env-var rule, which likewise scopes D-security-input's escalate severity to actually-unvalidated boundaries. Two conditions are load-bearing and must BOTH hold, else escalate: (a) the leaf enumerates EVERY field the emit site emits — a partial leaf leaves the target partly redacted and every gate still passes (the 2026-08-15 `triage.incident.persist` `duration_ms` lesson); (b) the guard test lives where it actually RUNS — in `pulse-app` that means `pulse-app/tests/*.rs`, never `observability.rs`'s own `mod tests`, since `[lib] test = false` makes a src-level guard compile, pass clippy, and never execute. Remember the duplicate-occurrence half: a once-per-boot WARN is registered in BOTH §6 and §8, so a §8-only apply leaves §6 stale. (Codified 2026-08-16 WITH the user at the baseline-family-reachability wrap, from the D-obs-pii pair for `triage.baseline.bootstrap_window.override`; the chunk's own guard was initially written into the dead src-level module, which is why condition (b) is stated.)

- pattern: Drift proposal (D-obs-pii) registering an allowlist leaf whose FIELD-COMPLETENESS guard exists but sits in a DEAD test module (in `pulse-app`, `observability.rs`'s own `mod tests` under `[lib] test = false`), so the 2026-08-16 rule's load-bearing condition (b) — "the guard test lives where it actually RUNS" — is unmet, while the PII half IS separately guarded by a running test and the leaf's fields are measured bounded non-PII.
  verdict: routine
  note: routine-APPLY-AS-MEASURED (not escalate). Resolves a collision between two existing rules that both match this shape: the 2026-08-16 D-obs-pii rule says "both conditions must hold, else escalate", while the 2026-08-15 rule routes "an impl half too large to ride this chunk" to APPLY-AS-MEASURED. The discriminator is that writing/migrating a running guard IS an impl half — so the 2026-08-15 disposition governs, PROVIDED the amendment (a) registers the leaf's full field set, (b) states plainly that the completeness guard does not execute and which half IS live-guarded, and (c) NAMES the route entry owning the migration. Any of the three missing → escalate. Rationale: the amendment then describes reality MORE accurately than the silent status quo, which is exactly the test the 2026-08-15 rule sets; refusing to apply would instead leave §8 asserting that emitted fields are redacted. Keep the leaf-registration and the guard-migration as SEPARATE obligations — applying the doc must never read as the guard being fixed. (Codified 2026-08-17 WITH the operator at the fault-identity-semantics-decided wrap, from the `interpretation.incident.created` leaf: condition (b) was the pivot on TWO consecutive chunks — `triage.baseline.bootstrap_window.override` the wrap before — which is the recurrence bar for codifying.)

- pattern: Wrap-time gate ORDERING for a chunk whose session ran ANY regenerating operation — a default-features `cargo nextest` / `cargo run` / test-execution that rewrites a committed GENERATED artifact (canonically `pulse-app/ui/src/bindings/index.ts`, rewritten to the no-mcp shape by `taurpc`'s `export_types()` on every `Router::into_handler()`).
  verdict: routine
  note: routine-ORDERING (a check, not a judgment). `cargo xtask capability-drift` runs LAST in the P7 light gate — after every regenerating op, including the light gate's own `nextest --workspace` — and the assertion reads the **STAGED** copy (`git show :pulse-app/ui/src/bindings/index.ts | grep -c '"mcp":'` ≥ 1), never the worktree: the worktree can be correct at regen time while the index carries a clobbered version, which is exactly how a green-looking wrap ships a red gate. Codified 2026-08-22 at the log-records-identity wrap after commit `70344d5` shipped bindings in the no-mcp shape while its handoff recorded capability-drift clean — the FIFTH occurrence, against FOUR existing rule entries describing the same defect (`rules/testing.md` 2026-05-13 / 05-17 / 2026-08-15, `rules/security.md` 2026-06-12). Recurrence-despite-learning is the reason this is an ordering rule in the judgment basis rather than a fifth restatement in a rules file: the operator's ruling was that a check the wrap RUNS beats a discipline the wrap author must REMEMBER. The mechanical half — an xtask assertion that fails when the staged bindings lack the `mcp` namespace — is owned by its own markerless route entry; until it lands, this rule is the interim.

- pattern: Cascade leaf-enumeration for an `architecture.md` amendment — deciding WHICH `.claude/docs/*.md` distillations to re-derive.
  verdict: routine
  note: routine-ENUMERATE-BY-PROVENANCE. Enumerate arch's leaves by grepping the provenance header the generator writes (`_Extracted from `.andromeda/architecture.md`_` in the first ~5 lines of each `.claude/docs/*.md`), NOT from a hardcoded list. Today that yields exactly `{conventions.md, stack.md}`; the amendment-flow reference's cascade table names only `stack.md` (plus the CLAUDE.md `GENERATED:setup:*` blocks), so a table-driven walk silently skips `conventions.md` — which distills arch §Conventions verbatim and therefore carries every §Conventions claim. Codified 2026-08-22 at the log-records-identity wrap: the arch §Primary key convention amendment left `conventions.md:32` restating the retired "timestamp + resource hash + name" wording; the arch detector's own duplicate sweep was correct but scoped to arch alone, so only the orchestrator's cross-master grep caught it. The provenance header is a mechanical enumerator that stays correct as leaves are added or removed, unlike a second list to maintain.

- pattern: An ESCALATE-severity detector (D-security-input · D-security-deps · D-obs-pii — the three that carry `severity: escalate`) fires on a finding OUTSIDE the class that severity exists to guard, and the report affirmatively substantiates the actual class: e.g. D-security-deps on a stale measured COUNT while Dependencies reads "none added, none bumped"; D-security-input on registry completeness for an input the report shows code-validated + tested; D-obs-pii on allowlist-leaf registration whose fields the report measures bounded non-PII.
  verdict: routine
  note: routine-APPLY-BY-ACTUAL-CLASS. GENERALIZES the two narrow predecessors — 2026-06-28 (D-security-input scoped to actually-unvalidated boundaries) and 2026-08-16 (D-obs-pii scoped to raw PII) — rather than minting a third detector-specific sibling. The escalate severity is attached to the DETECTOR, not to each finding it can produce, so a detector whose invariant spans several classes will sometimes raise a routine one at escalate severity; that is a severity-granularity artifact, not a signal about the finding. Disposition: classify by the finding's ACTUAL class and apply the rule that governs it (usually 2026-08-14 routine-APPLY for a doc-only correction). TWO conditions are load-bearing and must BOTH hold, else escalate: (a) the escalate condition is affirmatively ABSENT in the report — not merely unmentioned (no banned/unvetted dependency · no unvalidated boundary · no raw PII reaching a log); (b) the finding's actual class has its own governing disposition, so "not an escalate" never means "apply unexamined". (Codified 2026-08-23 WITH the operator at the a11y-verification wrap, from D-security-deps proposing the owned-advisory-ID count 7 → 8 while the report's Dependencies bullet read "none added, none bumped" and `cargo deny check bans licenses sources` was recorded ok — the THIRD instance across three different escalate-severity detectors, which is this playbook's recurrence bar for codifying.)
