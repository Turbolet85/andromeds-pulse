## 1. Obs Scope Summary

**Obs tier:** Standard (1)

**Justification:**
- **Cross-platform desktop scope:** Tauri 2 desktop app (Windows/macOS/Linux) with 8 instrumentable modules (ingest, buffer, viz, ui-bridge, snapshot, workspace-detector, plugins, mcp-server), 8 major surfaces (desktop-webview, desktop-native, IPC-internal, API service gRPC, API service HTTP, CLI, library-only plugin host, MCP stdio), and 7 critical user-facing must-trace paths (P1–P7: receive-and-visualize OTLP, curated snapshots, MCP tool queries, plugin lifecycle, UI layout transitions, real-time Arrow IPC push, workspace detection).
- **Standard-tier drivers:** security_tier=Minimal (loopback-only binding, no user accounts, in-memory data, no compliance); tests_tier=Standard (span coverage across 19 testable entities, 7 critical paths, 28+ rejected attack vectors, agent-driven deterministic signals). Obs matches tests at Standard — the multi-surface complexity, perf-budget enforcement, and PII-scrubbing rigor warrant rich structured `tracing` instrumentation.
- **Multi-surface trace propagation:** cross-surface W3C `traceparent` correlation — span fields at receiver entry, IPC envelope `traceparent` carried into TauRPC handler spans, Arrow metadata `_trace_context` field on push streams.
- **Creator perf-budget SLOs:** token-efficient curated-snapshot guarantees plus frontend telemetry (web-vitals + WebGPU frame timing) flow into the same `tracing` JSON log via the TauRPC bridge as `metric.*` events; the security plan's 6 logging-sensitive vectors drive `#[tracing::instrument(skip(...))]` field exclusion + custom subscriber Layer redaction.
- **Architectural choice (self-observation runtime):** uses ONLY the `tracing` ecosystem (`tracing` 0.1 + `tracing-subscriber` 0.3 JSON formatter + `tracing-appender` daily file sink + `tracing-error` SpanTrace) — NO OTel SDK is linked into the product binary for self-observation. External OTLP receiving (`tonic`/`axum`/`prost`/`opentelemetry-proto`) is unaffected (wire-format parsing only, no OTel SDK runtime required). By construction there is no exporter to misconfigure and no recursion concern — the JSON file at `~/.andromeda-pulse/logs/agent-latest.jsonl` IS the agent-readable surface.

**Observability harness specification:**

- **Tracing init:** `tracing` 0.1 + `tracing-subscriber` 0.3 with JSON formatter as the SOLE self-observation runtime — NO OTel SDK linked into the product binary for self-observation (the product's CORE function of receiving external OTLP via `tonic`/`axum`/`prost`/`opentelemetry-proto` is unaffected; those crates handle wire format only and don't require an OTel SDK). Initialization order: (1) Load config + validate log level (`ANDROMEDA_PULSE_LOG_LEVEL` env var with fallback `RUST_LOG`), (2) build `tracing-subscriber::registry()` composing `fmt::layer().json().with_writer(std::io::stderr)` + `fmt::layer().json().with_writer(non_blocking_file_appender)` + `EnvFilter::from_env(...)`, (3) install panic hook calling `tracing::error!(target: "app.panic.fatal", ...)`, (4) spawn Tauri app + bind OTLP receivers. Boot-time before HTTP/gRPC bind. Why this approach: by not linking an OTel SDK into the self-runtime, the "OTel monitoring an OTel monitor" recursion concern disappears by construction — there is no exporter to point anywhere, and the file-sink JSON line IS the agent-readable surface.

- **Service identity:** `service.name` = `com.andromeda.pulse` (compile-time: Tauri bundle identifier, arch excerpt Section 1); `service.version` = `env!("CARGO_PKG_VERSION")` at compile time (or runtime read from `tauri.conf.json` for the desktop bundle build); `deployment.environment` = `production` (hardcoded for desktop app; no staging/dev distinction at runtime). Embedded as default fields on every `tracing` event via `tracing_subscriber::fmt::Layer::with_default_fields([service_name, service_version, deployment_environment])` so every JSON log line carries identity without per-call boilerplate.

- **Logging stack:** `tracing` 0.1 + `tracing-subscriber` 0.3 JSON formatter + `tracing-appender` 0.2 daily-rolling file sink + `tracing-error` 0.2 SpanTrace for sanitized error chains. Dual sink: (1) stderr (JSON when not a TTY, pretty when TTY for dev convenience), (2) file `~/.andromeda-pulse/logs/agent-latest.jsonl` always JSON-only. For mcp-server sidecar (rmcp 0.6 over stdio), stderr is forced JSON (TTY check disabled) — stdout is reserved for JSON-RPC 2.0 framing and ANY accidental stdout write would corrupt the protocol.

- **Log format JSON schema:** Verbatim from tests excerpt Section 5 Test Plan Excerpt → Test Harness Contract Summary (binding contract — obs aligns to tests, not vice versa):
```json
{
  "timestamp": "2026-05-02T16:18:34.567Z",
  "level": "INFO",
  "target": "ingest::grpc",
  "message": "TraceService.Export received 10 spans",
  "fields": {
    "span_count": 10,
    "service": "my-app"
  }
}
```
Optional fields supported per `fields` map: `trace_id` / `span_id` (W3C traceparent treated as plain string fields when extracted from external client headers), `duration_ms`, `span_count`, plus per-trigger context fields (e.g., `plugin_path_basename`, `query_id`, `param_count`, `token_count_actual`, `token_budget_limit`, `body_size_bytes`, `webview_backend`, `tray_api`, `wgpu_backend`). Log entry structure matches JSON-per-line convention for agent paste-to-AI workflows.

- **Log file location:** `~/.andromeda-pulse/logs/agent-latest.jsonl` (arch excerpt Obs-Relevant Conventions: log file location pattern); configurable via `ANDROMEDA_PULSE_DATA_DIR` override (per-platform: `%APPDATA%\Andromeda Pulse\logs\` on Windows; `~/Library/Application Support/com.andromeda.pulse/logs/` on macOS; `~/.local/share/com.andromeda.pulse/logs/` on Linux); agent paste-to-AI workflow reads this file for debugging. Daily rotation via `tracing-appender::rolling::daily(...)`.

- **Snapshot / paste-to-AI integration:** Two cleanly separated surfaces.
  - **External-OTLP snapshot** (the product's CORE feature): `snapshot.generate` TauRPC command produces curated markdown from EXTERNAL clients' OTLP data stored in DuckDB ring buffer, saved to `~/.andromeda-pulse/snapshots/{timestamp}.md` per creator brief Section 6 pipeline (time window → filter → curate (dedup, anomaly markers, critical-path extraction, p50/p95/p99 aggregation) → format → token budget enforced ≤ 10k/25k/50k). MCP tools (`query_traces`, `query_metrics`, `query_logs`, `generate_snapshot`) over rmcp stdio expose the same pipeline to AI clients. Tool response bodies NEVER logged in self-observation file (security plan vector 4); only `result_type` + `result_count` metadata captured.
  - **Self-observation paste-to-AI** (the product's debug surface): the agent reads `~/.andromeda-pulse/logs/agent-latest.jsonl` directly (JSON-per-line; greppable / jq-able / paste-to-LLM-able). No separate snapshot needed — the JSON log file IS the snapshot. The two surfaces NEVER intersect: external OTLP data lives in DuckDB; self-observation lives in the JSON file.

- **Trace context propagation:** W3C `traceparent` header (HTTP) and gRPC metadata (`grpc-trace-bin`) extracted at receiver entry per arch Standard Contracts. The extracted traceparent is attached to the local `tracing` span as a regular field (`%traceparent`); downstream `#[tracing::instrument]` calls inherit via `tracing::Span::current()` so a single trace_id ties together the gRPC ingest span → DuckDB append span → TauRPC `traces.query` span → frontend channel emit. IPC envelope (TauRPC command struct) carries optional `traceparent` field; receiver handlers extract and attach to span fields. Real-time push streams (`pulse://stream/spans`, etc.) carry trace context in Arrow metadata column (`_trace_context` schema field) for end-to-end correlation. NOTE: this propagation is for correlation across the product's internal pipeline — the `traceparent` value is treated as an opaque string in `tracing` events, not bound to any OTel SDK trace context.

- **Heartbeat ticks:** Long-running subsystems emit `tracing::info!(target: "{module}.tick", ...)` events every 10–30 seconds via `tokio::time::interval`: `ingest.tick` (`span_count`, `buffer_capacity_pct`, `broadcast_subscribers`), `buffer.tick` (`rows_ingested`, `retention_window_active`, `eviction_count`, `span_events_seen`, `fingerprints_computed`, `observer_invocations`, `redactions_applied`, `rows_ingested_delta`, `last_append_age_seconds`), `viz.tick` (`query_latency_ms`, `subscribers_active`), `plugins.tick` (`loaded_count`, `active_invocations`). **Stall detection has TWO signals, and tick presence is only the first.** (a) LIVENESS — missing tick for >45s = stall signal (agent reads recent ticks via tail of JSON file). (b) PROGRESS — a consumer can keep ticking while it drains nothing: measured 2026-08-26, `rows_ingested` froze while `{ingest,buffer}.tick` emitted normally for 16 minutes and every liveness check read healthy. `rows_ingested_delta` staying 0 while the ingest channel still holds queued work is that condition, surfaced as `buffer.consumer.stalled`; `last_append_age_seconds` dates the most recent append. `health` IPC command exposes the same fields synchronously for active liveness probing per arch Standard Contracts — and, being tick-derived, it reports liveness rather than progress for the same reason.

## 2. Telemetry Strategy

**Telemetry signal pyramid (per tier):**

| Signal | Coverage focus | Tier-specific depth |
|--------|---------------|---------------------|
| Spans / Traces | Critical paths (P1-P7) + module boundaries (ingest, buffer, viz, plugins, snapshot) | Standard: all 7 must-trace paths covered via `#[tracing::instrument]` attribute on each handler; trace context inherited via `tracing::Span::current()`; spans serialize to the JSON log file as enter/exit events with span IDs |
| Structured Logs | Boundary calls + state transitions + errors | Standard: JSON-per-line via `tracing-subscriber` JSON formatter; logging-sensitive vectors (Sec 5) apply `#[instrument(skip(...))]` field exclusion + custom subscriber Layer redaction; heartbeat ticks emit `info`-level events |
| Errors | Captured panics + module-boundary errors | Standard: `std::panic::set_hook` → `tracing::error!`; `tracing-error` 0.2 SpanTrace for sanitized error chains (user-defined spans only, no Rust struct names per Vector 2); optional `sentry-rust` 0.46 / `sentry-tauri` 0.5 (opt-in via `ANDROMEDA_PULSE_SENTRY_DSN`, default off; uses Sentry's own SDK, no OTel bridge) |
| Metrics | Counters / histograms / gauges per critical path | Standard: emitted as `tracing::info!(target: "metric.{name}", value = N, ...)` events with `metric.*` target convention; agent computes percentiles from the event stream when reading the JSON log file; offline regression assertion via `criterion` 0.5 in `xtask benches/` for SLO-critical budgets |
| Audit Logs | Compliance trail for privileged ops | N/A — security_tier=Minimal, no compliance triggers |

**Agent-readable invariants (apply across all signals):**
- Every signal produces machine-parseable output: JSON-per-line via `tracing-subscriber` JSON formatter to a single file (`~/.andromeda-pulse/logs/agent-latest.jsonl`); the file IS the agent surface
- No human-only dashboards, no Grafana / Kibana / Datadog UI as sole consumption
- No proprietary APM SDKs as primary exporter (Sentry is opt-in, not default)
- No human-review-gated log analysis ("ops team reviews daily")
- Every panic captured with structured SpanTrace (via `tracing-error`, no full Rust struct names per Vector 2)
- Every cross-surface call attaches W3C traceparent as a plain `tracing` span field at the boundary (gRPC metadata extraction via manual middleware on tonic; HTTP header extraction via manual `tower::Layer` or `tower-http::TraceLayer` on axum; IPC envelope `traceparent` field on TauRPC commands; Arrow `_trace_context` metadata column on push streams) — propagation downstream via `tracing::Span::current()` so a single trace_id ties together the entire pipeline
- NO OTel SDK linked into the self-observation runtime — recursion-free by construction (the only tools that touch OTLP wire format are `tonic` + `axum` + `prost` + `opentelemetry-proto`, which decode incoming external client telemetry; none of those require an OTel SDK runtime)

**Naming conventions:**
- **Span naming:** `{module}.{operation}` pattern (e.g., `ingest.grpc.export.request`, `duckdb.append`, `plugin.invoke.request`, `snapshot.generate.request`); avoid high-cardinality names
- **Metric event naming:** `metric.{module}.{measure}` target prefix on `tracing` events (e.g., `metric.snapshot.token_count_ms`, `metric.buffer.ingest_throughput_spans_per_sec`, `metric.webgpu.frame_duration_ms`, `metric.trace.latency_percentiles`, and the three frontend-bridged delegated-timing observables `metric.constellation.hue_update_ms` / `metric.constellation.discovery_ms` / `metric.findings.counter_refresh_ms`)
- **Log fields:** structured JSON with required fields per Section 6 (timestamp, level, target, message, fields with trace_id/span_id when available)
- **Default subscriber fields:** every event carries `service.name` (`com.andromeda.pulse`), `service.version` (from `Cargo.toml`), `deployment.environment` (`production`) — set once at subscriber init via `Layer::with_default_fields(...)` so individual `tracing::info!` calls don't repeat the boilerplate

## 3. Observability Harness Contract

Architecture committed to the harness pattern (verbatim from upstream-context Architecture Excerpt's Observability Hints): "`opentelemetry-stdout` (or file exporter targeting `~/.andromeda-pulse/logs/`) is the only exporter the product itself uses for its own telemetry". This obs plan strengthens that commitment by going one step further: NO OTel SDK is linked into the self-observation runtime at all. The product's own debug telemetry uses ONLY the `tracing` ecosystem with a JSON file sink. The product's external surfaces (OTLP receivers ingesting third-party clients) continue to use `tonic` + `axum` + `prost` + `opentelemetry-proto` for wire format parsing — those crates parse OTLP without requiring an OTel SDK runtime, so the two pipelines remain cleanly separated.

### Tracing init

- **Crate set:** `tracing` 0.1 (macro-driven instrumentation; `#[instrument]` attribute on router/handler methods) + `tracing-subscriber` 0.3 (JSON formatter + Layer composition + `EnvFilter`) + `tracing-appender` 0.2 (daily-rolling file sink, non-blocking writer) + `tracing-error` 0.2 (SpanTrace for sanitized error chains)
- **Init order:** Before Tauri app spawn; before HTTP/gRPC server bind. Sequence: (1) Load env vars + config → validate log level via `EnvFilter::from_env("ANDROMEDA_PULSE_LOG_LEVEL")` with fallback `RUST_LOG`, (2) Build the `tracing_subscriber::registry()` composing stderr layer + non-blocking file appender layer, (3) Install panic hook calling `tracing::error!(target: "app.panic.fatal", ...)` with `tracing-error` SpanTrace, (4) Spawn Tauri app + bind OTLP receivers (tonic + axum)
- **Init body sketch (≤ 5 lines):**
```rust
let (file_writer, _guard) = tracing_appender::non_blocking(rolling::daily(log_dir, "agent-latest.jsonl"));
tracing_subscriber::registry()
  .with(fmt::layer().json().with_writer(file_writer))
  .with(EnvFilter::from_env("ANDROMEDA_PULSE_LOG_LEVEL"))
  .with(ErrorLayer::default()).init();
std::panic::set_hook(Box::new(panic_to_tracing_error));
```
- **Why this approach:** by NOT linking an OTel SDK into the self-runtime, the "OTel monitoring an OTel monitor" recursion concern disappears by construction — there is no exporter to point anywhere, and the file-sink JSON line IS the agent-readable surface.

### Service identity

- **service.name:** compile-time constant `"com.andromeda.pulse"` (Tauri bundle identifier; fallback `env!("CARGO_PKG_NAME")` = "pulse-app"); for mcp-server sidecar: `"andromeda-pulse-mcp"` (distinct process identity per arch convention)
- **service.version:** compile-time `env!("CARGO_PKG_VERSION")` (or runtime read from `tauri.conf.json` for the bundled desktop build)
- **deployment.environment:** hardcoded `"production"` (desktop app, no staging/dev distinction at runtime)
- **Default subscriber fields:** registered once at subscriber init via `tracing_subscriber::fmt::Layer::with_default_fields([service_name, service_version, deployment_environment])` — every emitted JSON line carries identity in the `fields` map without per-call boilerplate

### Logging stack

- **Library:** `tracing` 0.1 + `tracing-subscriber` 0.3 + `tracing-appender` 0.2 + `tracing-error` 0.2 (versions tracked in obs-research catalog; pinned at workspace level)
- **Format:** structured JSON-per-line matching binding contract (Section 6 log format JSON schema); agent-readable, machine-parseable; produced by `tracing_subscriber::fmt::Layer::json()`
- **Sink:** Dual sink for app: (1) stderr (JSON when not a TTY, pretty-printed when TTY for dev convenience), (2) file `~/.andromeda-pulse/logs/agent-latest.jsonl` always JSON-only via `tracing-appender`. For mcp-server sidecar (rmcp 0.6 over stdio), stderr is forced JSON (no TTY check) — stdout is reserved for JSON-RPC 2.0 framing and ANY accidental stdout write would corrupt the protocol
- **Frontend bridge:** `web-vitals` callbacks + WebGPU frame timing + skeleton-pulse durations from the React webview flow through TauRPC `telemetry.frontend.*` commands which call `tracing::info!(target: "metric.{name}", ...)` on the backend — single JSON file is the unified self-observation surface

### Log format JSON schema

Verbatim from upstream-context Section 5 Test Plan Excerpt → Test Harness Contract Summary (binding contract):
```json
{
  "timestamp": "2026-05-02T16:18:34.567Z",
  "level": "INFO",
  "target": "ingest::grpc",
  "message": "TraceService.Export received 10 spans",
  "fields": {
    "span_count": 10,
    "service": "my-app"
  }

```

Extensions (optional fields per Section 5 telemetry triggers):
- `trace_id` / `span_id` — W3C traceparent string fields, attached at receiver entry from external client headers; treated as opaque strings by `tracing` (no OTel SDK trace context binding)
- `duration_ms`, `span_count`, `service`
- Per-trigger fields: `plugin_path_basename`, `query_id`, `param_count`, `token_count_actual`, `token_budget_limit`, `body_size_bytes`, `webview_backend`, `tray_api`, `wgpu_backend`, `dedup_count`, `anomaly_markers`, `p50_ms`/`p95_ms`/`p99_ms`/`max_ms`, `error_rate_percent`, `value` (metric event payload)
- `service.name` / `service.version` / `deployment.environment` — populated as default subscriber fields per Service identity above

### Log file location

- **Path:** `~/.andromeda-pulse/logs/agent-latest.jsonl` (default); configurable via `ANDROMEDA_PULSE_DATA_DIR` override: `%APPDATA%\Andromeda Pulse\logs\` (Windows), `~/Library/Application Support/com.andromeda.pulse/logs/` (macOS), `~/.local/share/com.andromeda.pulse/logs/` (Linux) per arch Obs-Relevant Conventions
- **Rotation:** Daily rotation via `tracing_appender::rolling::daily(log_dir, "agent-latest.jsonl")`; previous day's file read by agent if current not yet created

### Snapshot / paste-to-AI integration

Two cleanly separated surfaces:

**External-OTLP snapshot** (the product's CORE feature — the thing users invoke):
- **Path:** `~/.andromeda-pulse/snapshots/{timestamp}.md` (curated markdown, not raw OTLP JSON); timestamp format `YYYY-MM-DDTHH:MM:SSZ`
- **Schema:** Curated markdown with header (`## Snapshot from {time_range_start} to {time_range_end}`), metadata (`token_count`, `dedup_count`, `service_filter`, `anomaly_markers` like "⚠ latency spike" / "🔴 error cluster"), aggregated metrics (p50/p95/p99/max per service), critical-path top-slow-spans, trace IDs for drill-down. Deduped (identical span trees counted once with emission count). NOT raw OTLP JSON dump (per tests excerpt P2 + creator brief Section 6)
- **Trigger:** TauRPC `snapshot.generate({time_range, token_budget: 10000 | 25000 | 50000})` from webview; span `session.snapshot` wraps the pipeline; child spans emit token-budget telemetry (Section 5 perf-budget-instruments)
- **MCP tools (rmcp 0.6 over stdio):** `query_traces`, `query_metrics`, `query_logs`, `generate_snapshot` — JSON-RPC 2.0 interface to the same external-OTLP query pipeline; tool method spans emit `mcp.tools.call.request` (parent) → `duckdb.query.{traces|metrics|logs}` (child) → `mcp.tools.call.response` (emit result metadata only, NOT result_content per security plan vector 4)

**Self-observation paste-to-AI** (the product's debug surface — the thing developers/agents read):
- **Path:** `~/.andromeda-pulse/logs/agent-latest.jsonl` (the same JSON log file from Logging stack above)
- **Format:** JSON-per-line, immediately greppable / `jq`-able / paste-to-LLM-able
- **No separate snapshot needed** — the JSON log file IS the self-observation snapshot

The two surfaces NEVER intersect: external client OTLP data lives in DuckDB and is curated into the markdown snapshot; the product's own runtime telemetry lives in the JSON log file. By separating them, no recursion is possible.

### Trace context propagation

- **HTTP boundaries (`:4318` OTLP/HTTP receiver on axum 0.8):** W3C `traceparent` header extracted at request entry via manual `tower::Layer` (or `tower-http::TraceLayer` for plain `tracing` spans, NOT OTel-flavored); attached as a regular field on the inner `#[tracing::instrument]` span (`fields(traceparent = %tp)`) — downstream calls inherit via `tracing::Span::current()`
- **gRPC boundaries (`:4317` OTLP/gRPC receiver on tonic 0.14):** gRPC metadata (`grpc-trace-bin` header) extracted at gRPC service method handler entry via manual interceptor; attached as a `traceparent` field on the local `#[tracing::instrument]` span; same propagation pattern as HTTP
- **IPC boundaries (TauRPC):** TauRPC router handlers manually extract optional `traceparent` field from IPC envelope; initialize the local span with `fields(traceparent = %tp)` so downstream `tracing::Span::current()` calls inherit
- **Internal async boundaries:** `tokio::spawn` calls use `.in_current_span()` extension trait (from `tracing` 0.1) to propagate span context into spawned tasks
- **Real-time push streams:** `pulse://stream/spans` etc. carry trace context in Arrow metadata column (`_trace_context` schema field) for end-to-end correlation. NOTE: `traceparent` value is treated as an opaque string in `tracing` events, not bound to any OTel SDK trace context

### Heartbeat ticks

- **Tick interval:** 15s for long-running subsystems (ingest, buffer, viz, plugins) via `tokio::time::interval(Duration::from_secs(15))`; 100ms for the realtime throughput counter (separate high-frequency ticker for animation smoothness per creator brief)
- **Tick event format:** `tracing::info!(target: "{module}.tick", span_count=N, buffer_capacity_pct=M, broadcast_subscribers=X, "heartbeat")` — ride the same JSON file sink as the rest of the app
- **Stall detection (two signals — liveness AND progress):** (a) LIVENESS — agent reads recent ticks via tail of JSON file or CLI `logs` command; missing tick for >45s = stall signal; `health` IPC command exposes the same fields synchronously for active liveness probing per arch Standard Contracts. (b) PROGRESS — tick presence does not certify that work is moving: a wedged buffer consumer keeps ticking while `rows_ingested` stays frozen, which every liveness check reads as healthy (measured 2026-08-26). The companion signal is `rows_ingested_delta` remaining 0 across consecutive `buffer.tick`s while the ingest channel still holds queued work, announced once per transition on `buffer.consumer.stalled` and asserted by `cargo xtask check:ingest-progress`

**Complementarity with the `health` command:** Heartbeat ticks (asynchronous, 15s emission to the JSON log) and the TauRPC `health` command (synchronous status polling) serve different purposes and must not be conflated. Heartbeat ticks enable retroactive log analysis ("was the subsystem alive during this interval?"); the `health` command enables active liveness probing during boot (the test harness polls synchronously until status ok) and at runtime. Implementations emit tick events independent of `health` invocations, and return synchronous `health` status independent of tick history; both mechanisms remain and operate in parallel.

## 4. Span / Trace Coverage

**Span naming convention:** `{module}.{operation}` (e.g., `ingest.grpc.export.request`, `duckdb.append`, `snapshot.generate.request`, `plugin.invoke.request`). Avoid high-cardinality span names (no per-user-ID names, no per-trace-ID names).

**Span kind convention** (`tracing` 0.1 has no native `SpanKind` enum — encoded as a `span.kind` field on the `#[tracing::instrument]` attribute, e.g., `#[tracing::instrument(fields(span.kind = "server"))]`):
- `span.kind = "server"` — inbound handlers: `ingest.grpc.export.request` (gRPC), `ingest.http.export.request` (HTTP POST), TauRPC command handlers, MCP tool invocations
- `span.kind = "internal"` — internal operations: `duckdb.append`, `snapshot.generate.request`, `plugin.invoke.request`, `buffer.tick`, `workspace.detect`
- `span.kind = "client"` — not heavily used (app is receiver, not client); may appear for query/invoke spans if modeled as request-response

**Instrumentation per surface (manual `#[tracing::instrument]` throughout — NO OTel SDK auto-instrumentation crates linked):**

| Surface | Hook strategy | Manual instrumentation | Notes |
|---------|---------------|------------------------|-------|
| API service gRPC `:4317` | Manual `#[tracing::instrument(skip(req), fields(rpc.system = "grpc", rpc.service, rpc.method, span_count, traceparent))]` on each tonic gRPC service method handler | `gRPC` interceptor extracts `grpc-trace-bin` metadata header at request entry, attaches as `traceparent` span field; OTLP payload `span_count` attribute populated post-protobuf parse | tonic 0.14.x compatibility via plain `tracing` integration; no OTel-flavored crate needed |

## 5. Metric Coverage

**Metric emission convention:** every metric is emitted as a `tracing::info!` (or `tracing::trace!` for high-frequency 100ms ticks) event with target prefix `metric.{module}.{measure}` and a numeric `value` field plus enumerated label fields. The agent computes percentiles / counters / gauges by reading the JSON log file with `jq` or by tailing it during a debug session. NO OTel SDK Histogram/Counter/Gauge instruments are used — the `tracing` event stream is the single observability primitive.

**Conceptual instrument types** (mapped onto `tracing` events for consumption convention):

| Conceptual type | Use case | Example tracing targets |
|-----------------|----------|-------------------------|
| Counter (monotonic) | Count of events accumulated over time | `metric.buffer.evicted_span_count` (per tick increment), `metric.ingest.span.count` (per heartbeat) |
| Counter (monotonic, tick-aggregated as FIELDS) | Fingerprint-feed throughput — `span_events_seen` / `fingerprints_computed` / `observer_invocations`, folded once per batch by `BufferState::record_feed_counts` and ridden out as fields on the existing 15s `buffer.tick` rather than as separate `metric.buffer.*` targets. Counts only, no labels. Equality of `observer_invocations` with `fingerprints_computed` is the signal that the storm detector's feed is actually being fed, rather than that being inferred from downstream silence. Per-span-event emission is barred by the §11 hot-path rule | fields on `buffer.tick` |
| Counter (monotonic, tick-aggregated as FIELDS) | PII-redaction throughput — `redactions_applied`, folded once per batch by `BufferState::record_redactions` and ridden out as a field on the same 15s `buffer.tick`. Deliberately a SEPARATE fold from `record_feed_counts`, because the redaction paths and the fingerprint-feed paths do not coincide (the log-record path applies redactions while producing no feed counts). Aggregate count only — never the matched value, its category, the attribute key, or a `service_name` label. **Scope is FIVE scrub sites across the four `buffer::appender` record-batch builders** (widened 2026-08-23 by chunk `2026-08-23-ingestion-scrub-coverage` from the `scrub_otlp_field` log/exception paths to the four column boundaries — `spans.service_name`, `span_events.name`, `metrics_points.metric_name`, `log_records.severity_text` — then to a fifth by chunk `2026-08-23-metrics-points-labels`: `metrics_points.labels`). The BUILDER count is still four; only the scrub-site count moved. **Unit: one increment per REDACTED LABEL PAIR, not per persisted cell** — a single data point can carry several redacted pairs inside one `labels` cell, and each counts. **Counts redactions to PERSISTED cells ONLY — structurally, since chunk `2026-08-23-metrics-points-identity`:** each builder RETURNS its per-batch tally (`Result<Option<(RecordBatch, u64)>, Error>`) and `record_redactions` is folded at each table's OWN post-append site in `consumer::dispatch_batch`, so a batch the appender rejects at `flush()` contributes zero. Per-table granularity is load-bearing: in the spans arm a `span_events` failure must not discard the count for rows `spans` already stored. (`build_spans_record_batch` consequently takes no `&BufferState` at all.) Before that chunk the fold fired INSIDE the builders and the rule did not hold — measured live at `redactions_applied: 2` with `rows_ingested: 0` on a rejected batch. A scrub applied purely for identity consistency on a non-stored path is likewise UNCOUNTED — `extract_service_name` takes an `Option<&mut u64>` and its two non-storing callers (the storm `FingerprintObserver`, the baseline `SpanObserver` tap) pass `None`, which is why a canary in all five scrubbed cells reads 5 and not 6 (one redacted pair in the `labels` cell). The drain/template path calls `scrub_attribute` directly and carries its own tick fields. Makes P-047 scrubber recall gradeable from outside the process rather than only by reading stored rows back. Per-field emission is barred by the §11 hot-path rule | field on `buffer.tick` |
| Counter (monotonic, tick-aggregated as FIELDS) | Drain progress — `rows_ingested_delta` (rows landed since the previous tick) and `last_append_age_seconds` (whole seconds since the most recent append, derived from `BufferStateSnapshot.last_append_at_nanos`), both ridden out on the same 15s `buffer.tick`, bringing that tick's field set to 14. These exist because `rows_ingested` ALONE cannot separate a stalled consumer from an idle producer — both leave it static, which is precisely why the 2026-08-26 wedge read as healthy for 16 minutes. The discriminator is the ingest channel's occupancy: an idle producer drains it to empty, a stalled consumer leaves work queued. `last_append_at_nanos` refreshes on EVERY append and is deliberately distinct from the latch-once `first_append_at_nanos` (a latching age would climb on a perfectly healthy buffer). One clock read per batch, never per row; per-batch emission is barred by the §11 hot-path rule | fields on `buffer.tick` |
| Counter (monotonic, tick-aggregated as FIELDS) | Cue-admission bound — `cues_latched` (cues the `CueLatch` refused this cycle because their condition was already signalled, had not escalated, and was inside the refractory window) and `latch_tracked` (live conditions the latch holds after the cycle's eviction pass), folded onto the existing `triage.cue.tick` heartbeat and bringing its field set to 9. Cue evaluators re-derive from current state, so a persistent condition yields an identical cue every tick, and BOTH cadence entry points are fed by emission — Suggested cues via `CadenceTriggerChannel`, Autonomous cues via the general cue broadcast — which is why the bound sits at emission and one mechanism covers both (chunk 2026-08-26-cadence-runaway-blocking-pool; measured wedge 4,590 cues → 2,671 immediate cycles → 26,821 L1a queries in 16 min, against 220 in a matched control). `latch_tracked` is the field that makes the residual visible: the bound limits repetition PER CONDITION, not the number of distinct conditions. Per-cue emission is barred by the §11 hot-path rule | fields on `triage.cue.tick` |
| Counter (monotonic, tick-aggregated as FIELDS) | Cadence cycle rate — `cycles_executed`, folded onto the existing 15s `cadence.tick` heartbeat and bringing its field set to 8. The value was already accumulated in `cumulative_cycles` and then DISCARDED via `let _ =`, so the rate could only be read by counting per-trigger `cadence.trigger` records out of the log family — the forensic read chunk 2026-08-26-cadence-runaway-blocking-pool exists to remove. Aggregate count only; per-trigger emission is barred by the §11 hot-path rule (and `cadence.trigger` itself, at one record per cycle, is why the wedge log reached 131 MB) | field on `cadence.tick` |
| Distribution / "histogram" | Per-event value samples; agent computes p50/p95/p99/max from event stream | `metric.snapshot.token_count_ms`, `metric.webgpu.frame_duration_ms`, `metric.buffer.memory_bytes`, `metric.trace.latency_percentiles` |
| Gauge | Current state value sampled per tick | `metric.ingest.channel.broadcast_subscribers`, `metric.buffer.rows_active`, `metric.plugins.loaded_count` |

**Naming conventions:** `metric.{module}.{measure}` target prefix (e.g., `metric.snapshot.token_count_ms`, `metric.buffer.memory_bytes`). Cardinality discipline applies: label fields bounded to enumerated values only (no per-trace-ID labels, no per-user-ID labels, no per-arbitrary-request-path labels).

**Why `tracing` events instead of an OTel Meter:** the unified JSON file is sufficient for agent paste-to-AI workflows. Aggregation happens in two places: (1) the snapshot pipeline (which already curates external client OTLP data and can the same way curate self-observation events), (2) the test harness post-test analysis (`jq` over the log file for SLO assertions). For runtime SLO enforcement, `criterion` 0.5 in `xtask benches/` provides offline regression assertion with statistically-grounded thresholds — no OTel Meter dependency needed.

**Metric label cardinality discipline:** Labels bounded to enumerated values only for product-internal metrics (`wgpu_backend` to {vulkan, metal, dx12}; `webview_backend` to {WebView2, WKWebView, GTKWebKit}; `retention_window_seconds` to {300, 600}; `event_type` to {span, metric, log}; `error_type` to a known category list). **Exception** for query-time aggregation metrics (`metric.trace.latency_percentiles`, `metric.trace.error_count`): `service_name` is intentionally unbounded — external OTLP clients control their own `service.name` attribute, and the product cannot constrain it. These metrics are emitted ONLY at query time (per `viz.query.traces` invocation) and consumed immediately by the requesting view; they are NOT time-series-stored, so cardinality explosion is scoped to a single query's memory rather than long-term metric retention. No per-trace-ID, per-user-ID, or per-arbitrary-request-path labels in any metric.

## 6. Log Coverage

**Log format JSON schema:** Verbatim from upstream-context Section 5 Test Plan Excerpt → Test Harness Contract Summary (binding contract):
```json
{
  "timestamp": "2026-05-02T16:18:34.567Z",
  "level": "INFO",
  "target": "ingest::grpc",
  "message": "TraceService.Export received 10 spans",
  "fields": {
    "span_count": 10,
    "service": "my-app"
  }
}
```

**Required fields (every log line):**
- `timestamp` (ISO 8601 format: `YYYY-MM-DDTHH:MM:SS.fffZ`)
- `level` (debug / info / warn / error)
- `target` (module path, e.g., `ingest::grpc`, `buffer::appender`, `plugin::host`, or `metric.{module}.{measure}` for metric events)
- `message` (human-readable summary, <200 chars)
- `fields` (map of structured attributes — always present, may be empty `{}`)
  - `service.name` / `service.version` / `deployment.environment` — populated as default subscriber fields
  - `trace_id` (optional, W3C 32 hex chars; populated when traceparent extracted at receiver entry — treated as plain string field)
  - `span_id` (optional, W3C 16 hex chars; same as above)
  - Per-trigger fields per Section 5 (span_count, service, duration_ms, token_count_actual, value, etc.)

**Log levels mapping:**

| Level | Use case | Example |
|-------|----------|---------|
| `error` | Module-boundary errors + captured panics + unrecoverable failures | `error!(target: "app.panic.fatal", "panic")`, `error!(target: "ingest.grpc.parse.error", ...)` on malformed OTLP |
| `warn` | Recoverable errors + degraded performance + retry-able | `warn!(target: "config.load.path_validation", "path canonicalization rejected")` on CWE-22 violation; `warn!(target: "mcp.gate.check", "MCP enabled but feature flag absent")`; `warn!(target: "app.boot.buffer.degraded", reason, consequence)` — fires ONCE per boot when the buffer connection is absent, because the fallback drains and discards ingest batches while ingest's own counters keep climbing, making a degraded boot otherwise indistinguishable from a healthy one; `warn!(target: "corpus.keychain.fallback", backend_kind, reason, consequence)` — ONCE per boot when the passphrase branch serves the corpus key instead of the OS credential store, for the same reason (a reduced-custody boot is otherwise indistinguishable from a keychain-primary one); `warn!(target: "corpus.orphan.disposition", disposition_outcome, rows_purged, tables_affected)` — once per boot pass, aggregate counts only; `warn!(target: "corpus.read.undecryptable", query_id, rows_skipped)` — ONE aggregate per QUERY, never per row (§11 hot-path spam ban), so a corpus holding undecryptable rows degrades visibly instead of going dark; `warn!(target: "triage.baseline.bootstrap_window.override", resolved_seconds, default_seconds, reason)` — ONCE per boot and only when the resolved cold-start window differs from the 3600s default, because an env-shortened (or env-rejected) bound silently changes when every service becomes eligible for silence detection, making such a boot otherwise indistinguishable from a default one; `warn!(target: "buffer.consumer.stalled", reason, consequence, stalled_seconds, buffer_capacity_pct)` — emitted by the drain-progress classifier ONCE per healthy→stalled transition and once again on recovery, never per batch, because a wedged consumer keeps emitting `buffer.tick` and is otherwise indistinguishable from a healthy one (measured 2026-08-26: `rows_ingested` frozen 16 minutes, 0 ERROR, all ticks normal); fires only after 30 consecutive non-draining ticks (450s), deliberately above §10's 420s sustained-drain cap so an in-spec drain cannot trip it (chunk 2026-08-26-ingest-consumer-stall-under-sustained-load); `warn!(target: "app.boot.window.navigation", window_label, navigated, reason)` — at most ONCE PER WINDOW PER BOOT (bounded by the 4-entry declared-window set), fired post-settle and off any hot path, INFO when the window navigated and WARN when it is still on `about:blank`, because a webview that loses its initial navigation is never re-navigated (`show()` is not navigation) and surfaces as a blank window on first open, which no other signal distinguishes from a healthy boot (chunk 2026-08-24-headful-mechanics-probe-race-disposition); `warn!(target: "interpretation.model.allow_root", confinement, root_basename)` — EXACTLY ONCE per boot, WARN when `confinement = "unconfined"` (no `ANDROMEDA_PULSE_L4_ALLOW_ROOT` set, so the L4 model/binary paths resolve unconfined) or `"unresolvable"` (set but not a directory ⇒ fail-closed, every candidate rejected), and INFO when `"enforced"` — because an unconfined L4 boot is otherwise indistinguishable from a confined one, which is precisely what made the prior posture a silent convention; ## 7. Error Capture & Reporting

**Default error path (mandatory, always-on, no external service):** `std::panic::set_hook` → `tracing::error!(target: "app.panic.fatal", ...)` with `tracing-error` SpanTrace for sanitized error context. No external SaaS required for Standard tier; the JSON log file at `~/.andromeda-pulse/logs/agent-latest.jsonl` IS the error capture surface, agent-readable directly.

**Optional external platform (opt-in only, default OFF):** `sentry-rust` 0.46 + `sentry-tauri` 0.5; Sentry uses its OWN SDK directly (NO OTel→Sentry bridge), running independently of the always-on `tracing` path and honoring the same scrubbing rules. Enable via `ANDROMEDA_PULSE_SENTRY_DSN` env var or Settings UI toggle (empty/unset = no-op); default-off per creator brief ("every byte of telemetry stays on the developer's machine").

**`before_send` scrubbing pattern** (REQUIRED if Sentry enabled):
- Scrub OTLP request payloads (may contain user code fragments per Vector 1)
- Strip stack traces of file paths beyond project root (kernel/stdlib paths redacted)
- Sanitize `AppError` stack traces — remove Rust struct names, library versions; use `tracing-error` SpanTrace (user-defined spans only) per Vector 2
- Redact plugin file paths (basename only per Vector 3)
- Redact DuckDB query parameters (query_id + param_count only per Vector 5)
- MCP response bodies NEVER captured per Vector 4 (explicitly check event source before capture)
- Pattern: `before_send: Box::new(|event| { scrub_otlp_payloads(&event); scrub_file_paths(&event); scrub_query_params(&event); event })` (sentry-tauri callback)

**Panic hook:**
- `std::panic::set_hook(...)` installed at boot (after `tracing-subscriber` registry init), calling `tracing::error!(target: "app.panic.fatal", panic_message = %info, location = ?info.location(), spantrace = ?SpanTrace::capture(), "panic")`
- Panic message + SpanTrace logged to both stderr + JSON file sink
- If Sentry is enabled, the panic hook ALSO calls `sentry::capture_message(...)` after the `tracing::error!` line — both surfaces capture the panic
- Brief illustrative snippet (≤ 5 lines):
```rust
std::panic::set_hook(Box::new(|info| {
  tracing::error!(target: "app.panic.fatal", message = %info, location = ?info.location(), spantrace = ?SpanTrace::capture(), "panic");
  if sentry_enabled() { sentry::capture_message(&format!("{info}"), sentry::Level::Fatal); }
}));
```

**Error classes captured:**
- Unhandled panics (always via panic hook)
- Module-boundary errors: explicit `tracing::error!(...)` at boundary; Sentry capture (if enabled) for high-severity boundaries (IPC bridge, receiver parse failures, plugin load failures)
- Tauri command errors: `AppError` enum serialization at IPC boundary (sanitized per Vector 2)

**Error → span correlation:**
- Errors emitted within an active `tracing` span automatically inherit `trace_id` / `span_id` field values via the surrounding `#[tracing::instrument]` context — no additional bridge needed
- Sentry SDK (if enabled) attaches its own event-id; agent correlates Sentry events with `tracing` log lines by timestamp + message hash (no shared trace-context propagation between the two surfaces, by design — they are independent pipelines)

## 8. PII Scrubbing & Compliance

### PII Scrubbing

**Data classification rules** (from upstream-context Section 2 Security Plan Excerpt → Data Classifications):

| Data type | Classification | Obs handling | Scrubbing mechanism |
|-----------|---------------|--------------|---------------------|
| Raw OTLP telemetry payloads (trace spans, metrics, logs) | High | scrub-required | `span.attributes` dict redacted from logs (only `attributes_count` + `service_name_tag` emitted); scrubber at ingest boundary via `#[instrument(skip(...), fields(...))]` |
| `AppError` enum variants (IPC bridge) | High | scrub-required | `before_send` callback (Sentry) strips stack traces + Rust struct names; use SpanTrace (tracing-error) for user-defined context only |
| Plugin file paths | High | scrub-required | Basename-only logging via `path.file_name().and_then(\|s\| s.to_str())` before field emission |
| DuckDB query parameters | High | scrub-required | Query anonymizer: `query_id` + `param_count` emitted, NOT `params` list; prepared statements enforced (never `format!` SQL) |
| MCP response bodies | High | scrub-required | Response redaction: `result_type` + `result_count` emitted, NOT `result_content`; explicitly check span event type per vector 4 |
| Environment variables (config) | Low | OK to log structured | Config keys (ANDROMEDA_PULSE_*) logged structurally; secrets MUST be identified by naming convention (`*_SECRET`, `*_TOKEN`, `*_KEY`, `*_PASSPHRASE` redacted). `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` and any key derived from it are never emitted as a value, a field, or a presence flag — the fallback WARN carries bounded static strings only (chunk 2026-08-15-corpus-key-persistence) |
| Plugin binaries (WASM) | High | scrub-required | Plugin path basename only in logs; WASM binary content NEVER logged |

**Scrubbing libraries** (from obs-research):
- `tracing` 0.1 `skip(...)` macro parameter: excludes sensitive fields at the source (e.g., `#[instrument(skip(secret_token))]`) — first line of defense, prevents the data from ever entering the span
- `tracing-subscriber` 0.3 custom Layer: redacts regex-matched field patterns at log formatter stage (last line of defense before file write)
- `sentry-rust` 0.46 `before_send` callback: scrubs Sentry event fields pre-transmission (if Sentry enabled)
- `tracing-error` 0.2 SpanTrace: captures user-defined span context only (no Rust stdlib/library names) per Vector 2

**Integration points:**
- **At source** (preferred): `#[tracing::instrument(skip(...))]` parameter list + explicit `fields(...)` allowlist on each handler — sensitive parameters never enter the span
- **At subscriber Layer** (defense-in-depth): custom `tracing-subscriber` Layer wrapping the JSON formatter; iterates emitted event fields, redacts based on a per-module allowlist (e.g., `if !ALLOWLIST[module].contains(field_name) { redact() }`); applies before serialization to file
- **At Sentry boundary** (if enabled): `before_send` callback strips event fields before transmission (parallel to subscriber Layer; both layers MUST agree on the same scrubbing rules)

NO retry-once policies for panic handling — masks real failures. Verify in CI: grep log file for `app.panic.fatal` spans; fail build if panic unlogged.

### DuckDB Connection Isolation & Load-Profile Operational Constraints
At sustained extreme load (50k spans/s), three production defects were identified and fixed. **A fourth was OPEN and is now CLOSED (2026-08-28) — closed by a dependency bump, not by a code change in this repo**, so read defect 4 for the mechanism rather than for an in-repo fix to audit. It is listed here for continuity of the investigation, NOT as a connection-isolation violation: it was measured 2026-08-28 to be an appender failure-recovery defect, and the reference-connection mandate is satisfied by the shipped code.
1. **Retention-sweep mutex holding** — the sweep task held the shared DuckDB connection mutex across multi-second DELETE sweeps, starving the appender. Fixed via a dedicated sweep connection (`Connection::try_clone()`) + `MissedTickBehavior::Delay`.
2. **Timeout abandonment** — `tokio::time::timeout` wrapped a `spawn_blocking` query holding the mutex but could not cancel it on timeout. Fixed via a dedicated read connection + explicit `interrupt_handle().interrupt()` on timeout.
3. **L1a read starvation** — queries queued behind append-path row-group maintenance on the shared connection (500–700ms Q1 p99 tails). Fixed via a dedicated read connection in `TriageSqlState::new`.
4. **Consumer block on a duplicate-key replay — CLOSED 2026-08-28 by a dependency bump; mechanism corrected TWICE.** Fixed at chunk `2026-08-28-duplicate-span-replay-fails-loudly`; reproduced on demand beforehand via `cargo xtask smoke:gap-resume`. **The mechanism as finally measured** (the account below supersedes the 2026-08-28 "first fails loudly, the NEXT hangs" chain, which was itself a correction and was ALSO wrong): the producer restarts and replays span identities already stored, and at libduckdb-sys **1.10502** the **FIRST** replayed batch's `Appender::flush()` **blocked unbounded** while holding the shared connection mutex — it never returned and never produced an error, so there was no loud first failure at all. ## 11. Obs Anti-Patterns (NEVER do these)

### Telemetry Strategy

- NEVER over-instrument hot paths (appender inner loop, per-row DuckDB operations) — span overhead matters; profile before adding spans to tight loops
- NEVER skip spans on critical user-facing paths (P1-P7) — agent loses debug ability
- NEVER let signal pyramid drift toward logs-only (spans give request-scoped context logs alone can't; metrics give distribution, trends)
- NEVER use vendor-lock OTLP schemas (Datadog APM SDK / NewRelic agent / AppDynamics); if you use error reporting platform (Sentry), ensure `before_send` scrubbing + local log export always works

### Spans / Traces

- NEVER include raw OTLP attributes in span attributes (Vector 1 scrubbing) — include only `attributes_count` + `service_name_tag`
- NEVER use high-cardinality span names (per-user-ID names, per-trace-ID names, per-arbitrary-request-path) — kills distributed tracing storage
- NEVER skip trace context propagation across surface boundaries (IPC envelope, gRPC metadata, HTTP headers) — agent loses trace continuity for multi-surface debugging
- NEVER hold a `tracing::Span` guard across `.await` points without `.in_current_span()` — span context bleeds into unrelated tasks scheduled by tokio, breaking trace_id correlation and bloating memory until the holder drops
- NEVER serialize `anyhow::Error` directly across IPC boundary — convert to `AppError` enum + sanitize per Vector 2
- NEVER log full canonicalized plugin file paths (Vector 3) — basename only
- NEVER emit raw DuckDB query text in span attributes (Vector 5) — query_id + param_count only

### Metrics

- NEVER use unbounded label cardinality in `tracing` event fields (service_name mapped to infinity, trace IDs, arbitrary request paths) — explodes per-line JSON size and `jq`-aggregation cost downstream; enumerate label values upfront (exception: query-time aggregation events emit unbounded `service_name` per Section 5 cardinality note — single-query scope only, not time-series-stored)
- NEVER format expensive `tracing` event payloads inside hot paths without level-gating — wrap heavy serialization in `if tracing::enabled!(Level::DEBUG) { ... }` for tight loops; field arg evaluation happens regardless of subscriber filter when the macro is reached
- NEVER skip p50/p95/p99 coverage on perf-budget metrics — emit raw per-event `value` field via `tracing::info!(target: "metric.*")`; agent computes percentiles by tailing the JSON file (no precomputed quantiles in the emission path — agent-side `jq` aggregation is the convention)
- NEVER use metrics as sole SLO signal without span tracing (need both for end-to-end visibility)

### Logs

- NEVER use unstructured stderr text (agent can't parse fields) — always JSON-per-line to file sink
- NEVER skip `trace_id` / `span_id` fields in logs (when available) — agent loses correlation between logs and spans
- NEVER use multi-line stack traces without one-line serialization — breaks JSON-per-line parsing; use SpanTrace (tracing-error) instead of raw backtrace
- NEVER log in hot path at `info` level — spam costs throughput; use `trace` / `debug` gated by `ANDROMEDA_PULSE_LOG_LEVEL` env var
- NEVER log raw OTLP attribute values (Vector 1), stack traces with struct names (Vector 2), full paths (Vector 3), MCP response content (Vector 4), or query parameters (Vector 5)

### Error Reporting

- NEVER ship a real Sentry DSN in dev / committed to repo — security leak; use `ANDROMEDA_PULSE_SENTRY_DSN` env var only
- NEVER skip `before_send` scrubbing (if Sentry enabled) — PII leaks to external service
- NEVER enable error reporting by default — privacy violation; opt-in only (per creator brief: "every byte stays on developer's machine")
- NEVER use Sentry as the ONLY error sink — local panic hook + tracing::error log MUST always work even with Sentry disabled

### PII Scrubbing

- NEVER include PII in logs / spans / metrics by default (default-deny posture) — scrub at source via `skip(...)` macro or redact at processor stage
- NEVER scrub only at sink stage (Sentry `before_send`) — scrub at processor stage so failures upstream don't leak; apply at multiple layers
- NEVER hardcode scrubbing rules in a single location — rules applied at multiple layers: `#[tracing::instrument(skip(...))]` at the source, custom `tracing-subscriber` Layer at the formatter stage, Sentry `before_send` at the network egress (if Sentry enabled)
- NEVER log plugin-returned Arrow IPC payloads (untrusted) — size-cap + schema validation only
- NEVER log snapshot file contents to stdout (security plan anti-pattern) — snapshot file write emits non-suppressible toast event

### CI

- NEVER lose telemetry artifacts (log file + snapshot on failure) — uploaded as CI artifacts with retention
- NEVER use human-review-gated log analysis ("ops team reviews daily") without machine-parseable export — agent locked out
- NEVER skip snapshot generation on test failure — first-class debugging artifact
- NEVER rely on colored terminal output for CI parsing — CI artifacts MUST be structured (JSON) + machine-readable

### SLO

- NEVER skip zero-unlogged-panics invariant — most basic obs guarantee; every panic logged with structured backtrace
- NEVER add retry-once policies for panic handling — masks real failures (parallel to tests' zero-flakiness invariant)
- NEVER define soft SLO budgets (no enforcement) — formal SLOs MUST trigger build / deploy failure when exhausted (e.g., p99 frame duration > 33ms = release build fails)
- NEVER defer error budget decisions to humans ("team will review monthly") — agent-driven SLO assertions in CI

### Universal (agent-driven specific)

- NEVER use proprietary APM as ONLY exporter (Datadog APM SDK / NewRelic agent / AppDynamics as primary) — vendor schemas break paste-to-AI workflows; the JSON file at `~/.andromeda-pulse/logs/agent-latest.jsonl` is the canonical agent surface
- NEVER use dashboards-only obs (Grafana / Kibana / Datadog UI as sole consumption surface) — every signal must have agent-readable consumption path (the JSON log file is the primary path; the curated markdown snapshot is the secondary path for external client OTLP data)
- NEVER use human-review-gated log analysis without machine-parseable export — blocks agent-driven debugging
- NEVER link an OTel SDK into the product's self-observation runtime — the `tracing` ecosystem alone produces JSON-per-line that the agent can read directly; adding an OTel SDK on top would only re-introduce the recursion concern this project already chose to avoid by construction
- NEVER hardcode service identity (`service.name = "myapp"`) — use compile-time `env!()` or runtime config per Section 3, with a single source of truth registered as a default subscriber field
- NEVER skip `before_send` scrubbing in error reporting (if Sentry enabled) — PII → external service = privacy violation
- NEVER write to stdout from any subsystem when running as the rmcp stdio sidecar — stdout is reserved for JSON-RPC 2.0 framing; ALL `tracing` output forced to stderr (JSON formatter); ANY accidental `println!` / `dbg!` / library stdout write corrupts the protocol and silently disconnects the MCP client
