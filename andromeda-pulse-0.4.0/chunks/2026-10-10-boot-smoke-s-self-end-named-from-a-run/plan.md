## Goal
The CI boot smoke has read red on four of twelve pull-request runs of the build branch, the last one on this
chunk's own base (`ci#38014971549`). In each the app ended by itself a fraction of a second after its webview's
first calls: an exit and not a signal, code 1, no `app.exit` record, nothing new on its output, its display and
session bus still accepting. The job says how the app ended. It does not say who ended it.

**Which plan this is (inputs#I3): it names, and the closing is the next entry.** A run can name the cause only
after the operator's pre-CI commit, and past that commit no plan revision is offered, so the change that closes the
cause cannot be planned here from a record that does not exist yet. This plan builds what makes a run name the
ending call and its caller, reads its runs, and stops at the first witnessed self-end. P-129 is not claimed.

It delivers three things:

1. **An exit witness.** A small C library, loaded into the app process alone on the harness's spawn line, records
   the call that ends the process with its caller, and says so for each way a process can end with a code: a call
   through the linker, a direct `_exit`, `main` returning, and an end it cannot see at all, which reads as its own
   named verdict and never as nothing (inputs#I3, condition 1). It keeps itself out of the webview's child
   processes (condition 2).
2. **The settle verdict says what the witness recorded**, as one closed label, and the job keeps the witness's own
   file beside the log.
3. **A series.** After the smoke the `boot` job boots seven more times, each boot on a fresh data dir, its own
   display server and empty per-user data and cache directories, each recorded with its ordinal. A boot that ends
   by itself reds the job. One run then reads eight boots instead of one.

Research measured the instrument on the dev host (research.md, "The instrument"; the phase run dir's
`p3-measurements.md`): on a known member of the silent `exit 1` class it named `_exit(1)`, called from a static
function of `libgdk-3.so.0` entered from Xlib's `_XIOError`, 2 of 2; on six green boots against six without it no
timing difference was visible. Its cost on the runner is not measured: the first run under this plan reads it on
green boots before a red one is trusted to it.

No product code changes. The window is not repaired or rewritten (inputs#I1 item 6).

## Implementation Steps
1. **Write the pins first and read them red.** The in-file tests of steps 4 and 6 in the two new xtask modules,
   one per arm; the moved member pin of step 5; the workflow pins of step 8. Run the workspace suite once and keep
   the red reading in `evidence/red-before-green.md`.
2. **The library, `scripts/exit-witness.c`.** One C source with no dependency beyond the C library.
   - At load it opens the file named by `ANDROMEDA_PULSE_EXIT_WITNESS_FILE` for append, close-on-exec, and writes
     one `loaded` line (pid, process name). It registers an exit handler. It then removes `LD_PRELOAD` and
     `ANDROMEDA_PULSE_EXIT_WITNESS_FILE` from the process environment, so no process the app starts inherits
     either. With the variable unset or the file not openable it stays inert: every interposed call passes
     through.
   - It interposes `exit`, `_exit`, `_Exit`, `quick_exit` and `abort`. At the call it writes one `end` line: pid,
     thread id, process name, the call, its code, `errno`, and up to 23 caller frames, each as module basename,
     exported symbol (empty for a static function) and offset in the module. Then the real call runs with the same
     code.
   - Its exit handler writes one `runtime-exit` line: the C runtime's own exit path ran.
   - Every line is one JSON object written by one `write`, at most 4096 bytes. A line holds no environment value,
     no argument, no path beyond a basename and nothing of the process's memory.
   - The line patterns, measured on the scratch probe (`p3-measurements.md`, "P4 control"): a call to `exit`
     through the linker leaves `loaded`, `end`, `runtime-exit`; a direct `_exit` leaves `loaded`, `end`; `main`
     returning leaves `loaded`, `runtime-exit`; a direct system call leaves `loaded` alone.
3. **The boot verb loads it onto the app, and only the app.** In `scripts/agent-run.sh`, at the spawn line (`:79`,
   the command whose `$!` the wrapper records as the app's pid): read `ANDROMEDA_PULSE_EXIT_WITNESS_LIB`, trimmed.
   Unset or blank: the app is spawned as today. Naming a regular file: that one command runs with `LD_PRELOAD` set
   to it and `ANDROMEDA_PULSE_EXIT_WITNESS_FILE` set to the data dir's `logs/exit-witness.jsonl`. Set and not a
   regular file: `boot: exit witness library not found` on stderr and exit 1 before anything is spawned, so a
   mistyped path cannot run a job without its witness. No other verb changes; the pid, the parent and the reaper
   stay as they are. The script stays git mode 100755. `scripts/agent-run.ps1` is not changed: a preloaded
   library has no form there, nothing runs that script here or in CI, and it leaves with "Other operating systems
   retired from the code".
4. **The witness's reader, `xtask/src/harness_witness.rs`.**
   - A bounded reader of `logs/exit-witness.jsonl`: at most 64 lines, each at most 4096 bytes of printable ASCII
     holding one JSON object whose `kind` is `loaded`, `end` or `runtime-exit`. Anything else reads as
     `unreadable`, never as a partial record.
   - A pure decision over the app's pid, the wrapper's exit record and the lines for that pid, with these arms:
     `unset` (no file) · `unreadable` · `loaded` (a `loaded` line, no `end` and no `runtime-exit` line, and the
     exit record is absent or a signal) · `exit-call` (an `end` line) · `runtime-exit` (a `runtime-exit` line and
     no `end` line) · `no-record` (a `loaded` line alone while the exit record reads `exit N`: the process ended
     by a path the library cannot see).
   - Pins: one per arm over synthetic lines, among them the control's real line from `p3-measurements.md`, and the
     reader's bounds.
   - Controls on the built library, Linux only, in the same module: the test builds `scripts/exit-witness.c` and
     four children of a few lines of C with `cc` into a temp dir, runs each child under the library and asserts
     its line pattern and the label the decision gives it: `exit(7)` through the linker, `_exit(7)`, `main`
     returning 7, a direct `exit_group` system call. A fifth control is the child boundary: a parent under the
     library starts a child that reports its environment; the file holds one `loaded` line, the parent's, and the
     child holds neither variable. Its known positive: the same parent starting the child with `LD_PRELOAD` set
     again leaves two `loaded` lines. A missing compiler fails these tests; it never skips them.
5. **The settle verdict gains one member, `exit_witness`.** In `xtask/src/harness_ready.rs`, `run_settled` reads
   the witness after the verdict, where it already reads the exit record and the log evidence, and
   `settled_payload` carries the label of step 4. The verdict set, the exit codes and the other seven members are
   unchanged. `settled_payload_carries_the_closed_field_set` moves to eight members in the same change.
6. **The series, `cargo xtask harness:boot-series --count N`** (`xtask/src/harness_series.rs`, declared and
   dispatched in `xtask/src/main.rs`).
   - It boots N more times, ordinals 2 to N+1, the smoke being ordinal 1. `--count` outside 1 to 16, a system
     other than Linux, an unresolved data dir or no `xvfb-run` reads `cannot-evaluate`.
   - Each boot gets its own data dir `series/boot-{ordinal}/` under the resolved data dir and its own
     `XDG_DATA_HOME` and `XDG_CACHE_HOME` inside it, and runs the smoke's cycle under its own display server:
     `boot`, `harness:settled`, `status`, `cleanup`, with `cleanup` run whatever the others returned. The child's
     environment drops the package variables `cargo run` injects, as `cargo_command()` does.
   - What each boot keeps is copied file by file into the job's uploaded `logs/series/boot-{ordinal}/`: the log
     family, `boot.log`, `harness-settled.json`, `xvfb.log`, `exit-witness.jsonl`. Nothing of a boot's `run/` is
     copied.
   - A boot whose `cleanup` does not read `clean` ends the series there as `cannot-evaluate`: the next boot would
     meet its ports.
   - One JSON verdict on stdout, also written to `logs/boot-series.json`: `{verdict, boots, settled, ended, other,
     per_boot}`, each `per_boot` entry `{ordinal, cycle, verdict, ended, app_exit_record, windows_settled,
     exit_witness}`. `all-settled` exits 0; `self-ended` (a boot's settle verdict read `ended`) and
     `not-all-settled` exit 1; `cannot-evaluate` exits 2. The verdict is decided over the boots the verb ran. When
     the smoke's own `logs/harness-settled.json` is there, it is listed as ordinal 1 so one file holds every boot
     of the run.
   - The decision is a pure function pinned per arm; the member set and the kept-file list are pinned.

## Implementation notes
- **What the series does not reset between boots** (inputs#I3). Each later boot starts with a fresh data dir, a
  fresh display server and empty `XDG_DATA_HOME` and `XDG_CACHE_HOME`, so the webview's own state and the per-user
  caches that honour the cache variable start empty, as on the first boot of a fresh runner (measured on this
  host: the webview's state lands under the moved data directory and the app settles, one boot). Shared and not
  reset: the kernel's file cache, which is warm after the first boot; system-wide caches (the system font cache
  among them); everything under the runner's home that those two variables do not govern (the per-user
  configuration directory, any cache a library keeps elsewhere); leftovers under `/tmp` and `/dev/shm`; the
  session bus and whatever service the first boot left running on it. The first boot differs from the later ones
  in one more way: it runs without the two variables set. So the first boots and the later boots are two series,
  read apart.
- **What the library cannot see, by construction.** An end by a signal. A direct system call, which reads
  `no-record`. A static caller has no symbol and is named as module and offset; the exported frames around it
  carry names, and the app binary's own frames carry none, since the release profile strips symbols
  (`Cargo.toml:258-261`).

  (`gh api …/workflows/ci.yml/runs`, re-derived at P3); under the present smoke step six readings, two red. At
