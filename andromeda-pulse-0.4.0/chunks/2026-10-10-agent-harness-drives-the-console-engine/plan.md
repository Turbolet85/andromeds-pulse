## Goal
The console engine, `andromeda-pulse-engine`, has existed since the chunk before this one, and the agent harness
still builds, spawns and grades the window app alone. This chunk aims the harness at the engine: `boot engine`
starts it, `status engine` says whether it is up, `cleanup` ends it by signal and `logs` reads its log, and a
check over that log grades the run on the four readings the entry names (no panic, no heartbeat stall, exactly
one process-end record, the memory budget) plus the drain-progress reading the entry carries (per test-plan §3
5-command implementation, obs-plan §10 CI gates, obs-plan §3 Heartbeat ticks).

Research found that most of the harness already serves either program: `status`, `cleanup`, `logs` and
`harness:ready` act on the pid file, the log family and the two ports, which both programs write the same way.
Only `boot` names a binary, and only `harness:settled` waits for window records. So the work is three things.
First, `boot` and `status` take the program as a word, and the verdict they read names the program the log
itself records, so a verb pointed at the wrong program's data dir says so instead of grading it. Second, a new
check reads the engine's log after the run has ended, with every arm pinned red on a constructed log, and a
second new verb holds the run until its log holds what the check reads — a boot of a few seconds holds one tick
per target and could never fail a gap check. Third, one cycle verb runs the whole sequence on its own data dir
and ports; the gate block runs it on the dev host and the `boot` CI job runs it on every push, which is what
makes the heartbeat reading of obs-plan §10 enforced by a CI step again.

## How five verbs serve two programs until Epoch 2 (inputs#I1 item 2)
- `boot` with no word starts the window app, as today. `boot engine` starts the console engine. Any other word
  is usage, exit 2.
- `status` with no word reads the window app's run; `status engine` reads the engine's.
- `cleanup` and `logs` take no word. They act on the data dir they are given: the pid the pid file holds, the
  two resolved ports, the log family. What keeps them on the right program is the data dir, one per run.
- `run` is the test suite, unchanged; it already runs the engine through `integration_console_engine`.
- `cargo xtask harness:settled` stays the window's until `Window's gates retired` (`working-route.md:48`): its
  verdict needs four window records. The engine's counterpart is `harness:engine-settled`.
- What forbids a verb from quietly grading the wrong program: every verdict that grades a run reads the
  `app.boot.engine` record of that run's own log, whose `program` field is `window` or `console`
  (`pulse-app/src/engine_boot.rs:415`), and compares it with the program it was asked for. `boot` and `status`
  always ask (the bare word asks for `window`), so nothing is implied. A mismatch is the verdict
  `wrong-program`, exit 1; a log with no such record is a mismatch too.

## Finding and ending the engine (inputs#I1 item 4)
The verbs find the engine by `run/andromeda-pulse.pid` under the data dir they are given, which the engine
writes itself, and end it with SIGTERM through `cleanup` (SIGKILL after five seconds). `One place on a node`
(`working-route.md:39`) replaces both: operator-set places for the pid file, the stores and the log, and a
`stop` command. No command word is added here.

## Implementation Steps
Each new arm's pin is written first and run red before the code that turns it green (the targeted entry of the
gate block is the vehicle; both readings go to `evidence/`).

1. **The injector takes its port from the registered variable.** In `crates/ingest/examples/inject_demo.rs`
   the endpoint port comes from `ANDROMEDA_PULSE_OTLP_GRPC_PORT` (unset: 4317, as today; a value that is not a
   port from 1 to 65535: a usage error, exit 2, nothing sent). The host stays `127.0.0.1`. The decision is a
   pure function with pins in the example's own `mod tests`, which the workspace run collects
   (`crates/ingest/Cargo.toml:74-77`).
2. **The status verdict names its program.** In `xtask/src/harness_status.rs` add a pure reader that returns
   the `program` of the LAST `app.boot.engine` record in the log family (`window`, `console`, or `unknown` when
   the family holds none or the field is anything else). The verdict JSON gains a seventh member, `program`.
   `run` takes the asked program as an optional argument: when one is asked and the reading differs, the
   verdict is `wrong-program`, exit 1. `cannot-evaluate` (paths unresolvable) and `not-running` (no pid, or a
   dead one) keep precedence: a run that is not there is not graded. `classify` keeps its signature
   (13 test sites call it; research, Graph impact). Pins: the reader on a constructed family (last record
   wins, none is `unknown`, a non-family file beside it is not read), and the decision per arm.
3. **Readiness carries the same reading.** In `xtask/src/harness_ready.rs` `run_ready` takes the asked program
   and passes it on; its JSON gains the `program` member; `decide_ready` maps a `wrong-program` status to the
   verdict `wrong-program`, exit 1. `run_settled` and its eight-member verdict are not touched. Pins per arm.
4. **The engine's log check and its settle read**, new file `xtask/src/engine_log.rs`, two verbs.
   - `cargo xtask harness:engine-settled [--timeout-seconds N]` (default 60; below 20 refused as
     `cannot-evaluate`, since one tick interval is 15 s). It polls the pid and the log family until the log is
     gradeable: the boot record reads `console`, the pid is alive, the family holds at least two records of
     each of `ingest.tick`, `buffer.tick` and `connection.tick`, and at least one `metric.buffer.memory_bytes`
     sample with a non-zero `value`. Verdicts: `settled` exit 0 · `ended` (the pid is dead) exit 1 ·
     `wrong-program` (the record reads `window`) exit 1 · `not-settled` (the timeout passed) exit 1 ·
     `cannot-evaluate` exit 2. One JSON object on stdout with the members
     `verdict`, `pid`, `program`, `ingest_ticks`, `buffer_ticks`, `connection_ticks`, `memory_samples_populated`.
     It writes no file.
   - `cargo xtask check:engine-log` reads the log family under the resolved data dir after the run has ended,
     and the harness's exit record beside the pid file through the existing bounded reader `read_ended`. It
     prints one line per arm and a last line `engine-log: PASS`, `engine-log: FAIL` or
     `engine-log: cannot-evaluate`; exit 0 · 1 · 2. A FAIL on any arm is exit 1; with no FAIL, a
     cannot-evaluate on any arm is exit 2. Lines carry closed labels, counts, a member's file name and a line
     number — never a record's text, a path or an environment value. The arms, in order:
     - **family** — no `agent-latest.jsonl*` member: cannot-evaluate, nothing else graded. Members that hold no
       record: FAIL.
     - **program** — the family holds exactly one `app.boot.engine` record and it reads `console`: PASS. It
       reads `window`: FAIL. None: cannot-evaluate. More than one: cannot-evaluate (one cycle per data dir; a
       gap read across two boots would be false).
     - **panic** — an `app.panic.fatal` record at ERROR: FAIL, named by file name and line. The predicate is
       the one `ci_gates.rs:85` holds; share it, do not copy it.
     - **heartbeat-gap** — for each of the three engine tick targets: fewer than two records is
       cannot-evaluate; a gap over 45 000 ms between two consecutive records of one target is FAIL, naming the
       target and the gap; else PASS with the largest gap. `viz.tick` and `plugins.tick` are not graded.
     - **progress** — `ingest_progress::evaluate` over the family: a stall announcement that is not a recovery
       is FAIL; no `buffer.tick` is cannot-evaluate; and a run whose largest `rows_ingested` is 0 is FAIL (no
       span landed).
     - **process-end** — exactly one `app.exit` record, and it is the last record of the family: PASS. Two or
       more, or a record after it: FAIL. None: FAIL, on one of two named arms — `unloggable-end` when the
       harness's exit record reads `signal 9 (KILL)`, `end-not-recorded` otherwise.
     - **budget** — the memory arm of `perf_budget` (`grade_arm`, `xtask/src/perf_budget.rs:166`), required:
       over 512 000 000 B, a non-numeric field, no sample or only zero samples are each FAIL. One line says the
       frame and snapshot arms are not graded for a console engine, which has no producer for either.
   Pins, each a constructed log family in a temp dir: every arm red on its failing input, green on a passing
   one, and every cannot-evaluate input; the whole check green on one complete console log; the same verdict
   with an unrelated file beside the family; the exit code per overall verdict; the floor of the settle
   timeout. A red input for the heartbeat arm holds no ERROR record: the defect is block-shaped.
5. **The two verbs and the two flags are wired** in `xtask/src/main.rs`: the module lines, `--program` on
   `harness:status` and `harness:ready` (values `window`, `console`), `harness:engine-settled`,
   `check:engine-log`, and the cycle verb of step 7.
6. **`boot` and `status` take the program word**, in `scripts/agent-run.sh` (git mode 100755 kept).
   - `boot` with no word: as today, and its readiness poll now asks `--program window`.
   - `boot engine`: pre-builds `cargo build --bin andromeda-pulse-engine --release` and xtask outside the timed
     window, spawns `target/release/andromeda-pulse-engine run` by path under the same waiting wrapper (the
     spawn record and the exit record are written as for the window app), and polls
     `cargo xtask harness:ready --program console`. It never reads `ANDROMEDA_PULSE_EXIT_WITNESS_LIB`: the
     engine's spawn line carries no preload whatever the variable holds, and no witness file is created.
   - `status engine` threads `--program console`; `status` with no word threads `--program window`.
   - The usage text names the two forms. `cleanup`, `logs` and `run` are not edited.
   `scripts/agent-run.ps1` is not edited: no job and no host runs it, and it leaves with `Other operating
   systems retired from the code`. The engine arm is sh-only, like the exit-witness arm before it.
7. **One cycle as a verb**, new file `xtask/src/engine_cycle.rs`:
   `cargo xtask harness:engine-cycle [--data-dir DIR] [--grpc-port N] [--http-port N]`. Defaults: a fresh
   `target/engine-cycle/` directory named by the UTC second it starts, ports 24317 and 24318. It refuses, as
   `cannot-evaluate` exit 2 and before anything is started: port 4317 or 4318, a data dir that already holds a
   log family, a host that is not Linux. Then, in order: build the injector
   (`cargo build -p ingest --example inject_demo`); `bash scripts/agent-run.sh boot engine`; start
   `target/debug/examples/inject_demo --sustained --error-pct=0` by path; `harness:engine-settled`; end the
   injector by its own child handle; `bash scripts/agent-run.sh status engine`;
   `bash scripts/agent-run.sh cleanup`; `check:engine-log`. `cleanup` runs whatever the verbs before it
   returned, and after a failed `boot` the verbs between are skipped. Every child gets a cleared environment
   plus a fixed set, pinned by set equality: `HOME`, `PATH`, `ANDROMEDA_PULSE_DATA_DIR`,
   `ANDROMEDA_PULSE_OTLP_GRPC_PORT`, `ANDROMEDA_PULSE_OTLP_HTTP_PORT`,
   `ANDROMEDA_PULSE_RETENTION_SECONDS` (60, so the first retention sweep, which sets the memory gauge, runs at
   10 s) and `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` (a value made for the run, never printed or written), and
   `ANDROMEDA_PULSE_EXIT_WITNESS_LIB` only when the verb's own environment holds it — passed on so that the
   run shows `boot engine` ignoring it. No session bus, runtime dir or display variable, so no child reaches
   the credential store. The verdict is one JSON object with the members `verdict` (`pass` | `fail` |
   `cannot-evaluate`), `boot`, `settled`, `status`, `cleanup`, `check` (each the verb's exit, or null when
   skipped), `error_records` (the count of ERROR records in the family) and `witness_file` (`absent` |
   `present`). `pass`, exit 0, needs all five exits 0, `error_records` 0 and `witness_file` `absent`. The
   children's own output passes through, so the check's lines are in the verb's output. Pins: the refusals,
   the child environment's set, the verdict decision per arm, and the member set.
8. **The pre-push seed's doc comment is made true** in `xtask/src/pre_push.rs:30-31`: it says the seed holds
   one boot record and two ticks and that the stage reads the record count and the panic read over it. The
   stage itself is not changed here.
9. **The `boot` job runs the cycle and keeps the engine's log**, in `.github/workflows/ci.yml`, after the
   `cargo xtask ci-gates` step: a step named `Console engine cycle` with `if: always()` running
   `cargo xtask harness:engine-cycle --data-dir "$RUNNER_TEMP/andromeda-pulse-engine-data"`, and after the
   existing upload a second upload with `if: always()`, the name `logs-engine-` followed by the runner's
   system, the path of that data dir's `logs/` and `if-no-files-found: error`. No soft-fail key, no
   third-party action beyond the upload action already pinned by sha, no word `windows` on any line. The job's
   release build already builds the engine binary. Pins in `pulse-app/tests/quality_gate_workflow.rs`: the
   step exists in the `boot` job, runs that verb on a data dir of its own, runs whatever the steps before it
   returned, sits after `ci-gates`, carries no soft-fail key; the upload exists under its own name.
10. **The live readings.** Run the cycle entry of the gate block on the dev host and keep its output in

  read the family a moment before the record lands and read `wrong-program` once; `boot` keeps polling until
  `ready` or its timeout, so that reading is transient there. `status` is one read, taken after `ready`.
