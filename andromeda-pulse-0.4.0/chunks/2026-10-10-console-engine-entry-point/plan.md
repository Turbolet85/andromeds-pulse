## Goal
The engine exists today only inside the window app: one `fn main()` in `pulse-app/src/main.rs` builds its state
and spawns every one of its tasks from the Tauri setup closure. This chunk lifts that boot into one function and
adds a second program, `andromeda-pulse-engine`, that calls it with no window. The console program boots the two
loopback OTLP receivers, the ring buffer, the detectors and the corpus, is driven by a command (`run`), and keeps
the same five records of itself that the window app keeps: its log, its identity at boot, its panic record, its
heartbeat and exactly one record of how the process ended.

**It fits one chunk, and no crate's dependency on the window framework is cut.** Research measured that none of
the engine-wiring modules imports the window framework and that a binary which links the `pulse_app` library
without building the window needs none of the window's shared libraries at load (0 of 103 test binaries; the
window binary needs 6). So the console program is a second `[[bin]]` of `pulse-app`, sharing the engine code in
place. `tauri` leaves the crate's manifest at `Window retired`, with nothing for this chunk to undo.

**One engine serves both programs until Epoch 2** because both call the same boot function and neither wires an
engine part itself. Three things forbid drift: a source pin that reddens when either entry point names an engine
task or the shared boot names the window framework; one in-process test of the boot function; and two programs
run on every push (the window by the boot job and its eight boots, the console by a test in the workspace run).

**No local model in the console program** (inputs#I1 item 5, inputs#I2). It starts, loads and waits for none and
reads no model variable. At the point where 0.3.0 called the model it follows the registered variable
`ANDROMEDA_PULSE_L4_DETERMINISTIC`: set, it seats the canned runner and an incident forms; unset, it seats
nothing, so cues and digests are produced and no incident forms, and its boot record says why. The unset arm's
owner is `Incident is the engine's own record` (`working-route.md:65`). The window app's own seat is not moved.

1. **Move the boot helpers into the library.** `resolve_data_dir`, `resolve_port`, `resolve_grpc_port`,

   `init_buffer` leave `pulse-app/src/main.rs` for the new `pulse-app/src/engine_boot.rs`, unchanged in behaviour,
   `pub` + `#[doc(hidden)]`. Their 14 tests leave `main.rs`'s `mod tests` for
   `pulse-app/tests/unit_engine_boot_env.rs`, same names, same assertions (a test left beside them in a library
   source never runs). `resolve_mcp_sidecar_binary_path` and `emit_taurpc_bindings` stay in `main.rs`.
2. **One process-start function.** `engine_boot::init_process(data_dir)` does, in this order, what `main` does
   today at `main.rs:298-303`: the log sink and its guard, the at-exit hook, the Unix signal listener, the start
   instant, the pid file. It is called with the tokio runtime entered (the signal listener needs one).
3. **One engine boot function.** `engine_boot::start(config, inputs)` builds the engine state and spawns its
   tasks: everything `main` does today between `main.rs:307` and `:916` and inside the setup closure at
   `:1152-1573` that is not window, router, plugin-host or model-selection code. It takes:
   - a config value holding the data dir, the two receiver addresses and the retention seconds, with a
     constructor that reads the environment through step 1's resolvers, so a test can pass its own ports;
   - the program label, closed: `window` | `console`;
   - the corpus key backend (the programs pass the OS one; a test passes the fake);
   - the hardware profile source for the cadence coordinator;
   - the interpretation seat: a runner with its closed label (`model` | `deterministic`), or none.
   It returns the handles the window's routers and tray need (the same values `main` holds today) and, hidden for
   tests, the digest broadcast. With a seated runner it spawns the interpretation subscriber and the two L4
   heartbeats as today; with none it spawns neither, and the digest assembler and persister still run. It spawns
   with `tokio::spawn`, never through the window framework. It emits one boot record (step 5).
4. **Split the heartbeat spawn.** `heartbeat::spawn` (`pulse-app/src/heartbeat.rs:85`) becomes the engine's three
   ticks (`ingest.tick`, `buffer.tick`, `connection.tick`), called by `engine_boot::start`, and the window's two
   (`viz.tick`, `plugins.tick`), called by `main`. Callers: `main()` at `pulse-app/src/main.rs:1557` and
   `pulse-app/tests/unit_heartbeat_ticks.rs:25` and `:474` (research, Graph impact); the five-handle test becomes
   a three-handle and a two-handle test. The window app still emits all five.
5. **The boot record.** Target `app.boot.engine`, emitted exactly once per boot by `engine_boot::start`, fields
   `program` (`window` | `console`), `interpretation` (`model` | `deterministic` | `none`) and `reason`
   (`window_runs_model` | `deterministic_gate_set` | `deterministic_gate_unset`). WARN when `interpretation` is
   `none`, its message saying that no incident forms until the engine keeps its own incident record and naming
   the variable; INFO otherwise. Its own exact allowlist leaf in `pulse-app/src/observability.rs` beside
   `app.boot.render.posture`, guarded in `pulse-app/tests/unit_observability_allowlist_boot_engine.rs`: exact
   resolve, field-set equality both ways, the no-bare-`app` discriminator, and an emit-site capture equal to the
   leaf for each of the four program and seat combinations.
6. **The window's `main` calls the two functions.** After its first two statements and its own runtime build,
   which stay where they are, `main` calls `init_process`, then its own `window::emit_boot_spans()` and
   `render_posture::emit_posture(..)`, then selects its runner exactly as today (`main.rs:512-559`, the
   `interpretation.model.load` record included) and calls `engine_boot::start` with program `window`, the OS key
   backend, the hardware profile detector and that runner. Routers, the plugin host, `VizState`, the window
   geometry, the Tauri builder and the event-loop tail stay in `main`. The setup closure keeps only window work.
7. **The console program.** `pulse-app/src/console.rs` holds a closed command grammar and the run function;

     Then it waits; a SIGTERM or SIGINT ends it through the existing listener, which records the end and

## Constraints & rejected approaches
- A new workspace crate holding the engine, free of `tauri` in its manifest — rejected: it moves most of the 25
  files of `pulse-app/src` that do not name the framework for a state `Window retired` reaches by deleting
  dependencies; the console binary already loads without the window's libraries.
- A Cargo feature that makes `tauri` optional in `pulse-app` — rejected: features are additive and off by
  default (architecture §Conventions → Feature flags), and a second feature graph doubles the native build.
- A switch inside the window's `main()` instead of a second program — rejected: it would run after the render
  posture and the Xlib init, in a binary that needs the window libraries at load.
- A `stop` command — not built: the engine ends by signal, and finding it needs the pid file, whose place is
  `One place on a node`'s.
- Do not edit `.github/workflows/ci.yml`, `scripts/agent-run.sh`, any `xtask/` source, any capability file, or
  the bindings. Do not move, rename or reorder `main()`'s first two statements or its runtime build.
- Do not add a dependency, a listening socket, an environment variable, or a file outside the registered
  locations. Do not make the console program read `ANDROMEDA_PULSE_PIDFILE`, `_LOGFILE`, a model path variable
  or `ANDROMEDA_PULSE_HARDWARE_PROFILE`.
- Do not add a log layer on stderr or stdout to the console program.
- Do not change `interpretation.model.load` or how the window selects its runner.

## Implementation notes
- The tokio runtime must be entered before `init_process` and `start` in both programs: the signal listener
  returns silently without one, and a spawn outside a runtime is the "no reactor running" boot panic.
- Engine tasks now start before the Tauri builder instead of inside its setup closure. The window's records keep
  their order up to the engine boot (`app.boot.tracing.init`, `app.boot.pid`, the three window boot records, the
  render posture).
- A process ended by a re-raised signal writes no coverage profile; `integration_engine_boot` is what covers
  `engine_boot::start`. Last recorded coverage: `Line: 33992/38252 = 88.9%`, `Function: 3565/4055 = 87.9%`
  (`chunks/2026-10-10-no-gate-stands-while-reading-nothing/evidence/gate-census.md:38`).
