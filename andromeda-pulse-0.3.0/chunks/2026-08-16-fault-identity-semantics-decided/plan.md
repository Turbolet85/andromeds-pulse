## Goal

This is a **DECIDE chunk**: it settles what makes two faults the same fault, then makes impl, docs and
tests state one answer. Three forks were put to the operator at P4 with research in hand; all three
recommendations were accepted, and the decisions are now fixed:

**Layer 1 — fingerprint normalization: TOKEN-LEADING (fix the impl).** `is_absolute_path_start`
(`crates/buffer/src/fingerprint.rs:186`) fires on *any* `/` followed by a path character, and because
`is_path_char` (`:216-218`) itself includes `/` and `\`, `skip_absolute_path` then swallows the whole
remaining token — so only the leading path segment survives and `src/a.rs` normalizes identically to
`src/b/c.rs`. Both docs already state absolute-only (`:28`, `:134-137`), so **the docs were right and
the implementation is the defect.** The fix restricts the Unix arm to a genuine token-leading `/`.
Decisive supporting facts from research: normalization's stated purpose is host-stability, which
absolute-path stripping serves and relative-structure stripping does not; and the blast radius is
contained — the normalization chain has zero callers outside `fingerprint.rs`, and the fingerprint
value reaches only `appender.rs` / `consumer.rs` / `storm_observer.rs` / `main.rs:648` / 2 e2e tests,
never viz, MCP, corpus or UI (`span_events.fingerprint` is never SELECTed). This moves storm grouping
and nothing else.

**Layer 2 — incident identity: COALESCE-PER-SERVICE (decide and document the status quo).** The
predicate at `pulse-app/src/inference_runtime.rs:664` keys on the cue tuple
`(kind, scope, scope_id)`; `Incident.fingerprint` is populated (`:687`) but is not part of the key.
Research established this is not a one-line change to "fix": `synthesize_cue`
(`crates/triage/src/pattern/storm.rs:309-319`) hardcodes `kind`/`scope` and sets `scope_id = service`
and carries **no fingerprint field** — the detector keys state per-fingerprint then discards the
distinction — so every storm cue from one service is tuple-identical by construction. Keying on the
only fingerprint that *is* in scope (`L4Output.fingerprint`) was rejected: it is LLM-authored and the
deterministic runner hardcodes it to a constant, so per-fingerprint dedupe would be a no-op in exactly
the mode used for e2e verification. And incident-per-identity buys no correctness today — every
downstream surface is already N-safe (the constellation join reduces by `max_by_key(tier_rank)` over
all matching incidents, `pulse-app/src/services_router.rs:97-104`; the digest reads `list_active` only
as a boolean, `crates/triage/src/digest/assembler.rs:221-224`). So the semantic is **recorded as
decided**, documented at the predicate, and pinned by a test — no behavioural change.

**The dead `fingerprint_match` arm — document and narrow in-chunk.** `select_corpus_matches`
(`crates/triage/src/digest/retrieval.rs:86-94`) compares `Incident.fingerprint` (an LLM-authored
string) against `current_fingerprints`, which the assembler builds as `hex_lower(Q3 blake3 bytes)`
(`assembler.rs:283-288`). Nothing bridges the two namespaces — `crates/interpretation/src/prompt.rs`
mentions fingerprint **zero** times — so the arm cannot fire in production and only `scope_match` ever
does. Its unit tests pass only because they supply symbolic strings on both sides. This is a
fault-identity mechanism that does not work, so it belongs to this chunk: the arm is narrowed to the
truth and its tests stop implying production behaviour.

## Implementation Steps

1. **Restrict the Unix absolute-path arm to a token-leading `/`.** In
   `crates/buffer/src/fingerprint.rs::is_absolute_path_start`, the Unix branch must additionally
   require that the `/` sits at a token boundary — position 0, or preceded by a byte that is not a
   path character. The Windows drive-letter branch is already absolute-anchored by its
   `[A-Za-z]:[\\/]` shape; give it the same token-boundary precondition so both branches state one
   rule. Do not change `skip_absolute_path` — once a genuine absolute path is detected, consuming
   through embedded separators is correct.
2. **Make the token-boundary rule explicit in the docs.** The existing absolute-only claims at `:28`
   and `:134-137` become true and need no correction; add a short note naming the token-boundary
   precondition as load-bearing, so a future reader does not "simplify" it back to any-slash. Update
   the inline comment at the call site (`:151`) if it restates the old behaviour.
3. **Pin Layer 1 with boundary-pair unit tests** in the existing co-located `mod tests`
   (`fingerprint.rs:238`), per test-plan §4's assert-at-and-either-side-of-the-boundary shape:
   relative multi-segment paths are preserved and produce **distinct** fingerprints
   (`src/a.rs` ≠ `src/b/c.rs` — the regression the decision turns on); a true-absolute Unix path is
   still stripped; a true-absolute Windows drive path is still stripped; a `/` at position 0 is
   treated as absolute. Keep the two existing normalization tests (`:369`, `:375`) green.
4. **Verify the existing storm/e2e tests against the new grouping.** `pulse-app/tests/e2e_storm_detection.rs`
   and `pulse-app/tests/e2e_drain_template_assignment.rs` consume `FingerprintObserver`; confirm their
   fixtures do not depend on two relative-path frames collapsing to one fingerprint. If any does,
   update the fixture — not the assertion — and say so in the report.

   `pulse-app/src/inference_runtime.rs:659-664`, replace the current "Re-emission dedup on the identity
   tuple" comment with the decided semantic stated as a decision: incident identity is
   **coalesce-per-(cue-identity)**, which for storms is per-service; a distinct-fingerprint storm on an
   already-incident service is absorbed by design, not by omission. Name why fingerprint is not in the
   key (the cue does not carry one) so the next reader does not "fix" it. Correct the doc-comment at
   `:620-622` in the same pass.
6. **Pin Layer 2 with a test** in `pulse-app/tests/unit_incident_producer.rs` (the established host
   file — **never** a src-level `mod tests`, which cannot run under `[lib] test = false`): two
   successive digests carrying the same cue tuple but **different** `L4Output.fingerprint` values

   converts the measured canary surprise into an intentional pinned semantic. Existing dedupe tests

   `reflection_dedups_one_per_workspace`) stay unchanged and green.
7. **Narrow the dead `fingerprint_match` arm.** In `crates/triage/src/digest/retrieval.rs::select_corpus_matches`,
   remove the unreachable `Incident.fingerprint`-vs-hex comparison and state in the doc comment that
   corpus-match selection is **scope-based**, naming the two-namespace reason (blake3 digest vs
   LLM-authored string, unbridged by the prompt) so the removal is not re-added as a "missing feature".
   Leave `select_previously_seen` (`:103-120`) functionally intact — it compares
   `Incident.fingerprint` to `Incident.fingerprint`, same namespace, so it is genuinely live — but note
   the deterministic-mode caveat (see Implementation notes).
8. **Retarget the misleading retrieval tests.** `select_corpus_matches_keeps_fingerprint_matches_only`
   (`:176`) and `select_corpus_matches_empty_fingerprint_never_matches_empty_set_entry` (`:211`) assert

9. **Write the decision record** at `andromeda-pulse-0.3.0/chunks/2026-08-16-fault-identity-semantics-decided/decision.md`:
