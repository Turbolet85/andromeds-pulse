## Goal

Make a corpus resolution stick. Today `crates/corpus/src/contract.rs:603` runs an **unconditional**
`UPDATE incidents … WHERE id = ?5`, and seven production writers share it. One of them —
`run_incident_persist_cycle` (`crates/triage/src/incident/persistence.rs:170`) — holds a `list_active`
snapshot for its whole write span, so any fresher writer that lands inside that span is silently
overwritten with stale rows. Every UPDATE succeeds, `rows == 0` never fires, and nothing logs; because
the cycle lists actives only, a row reverted to `active` never re-enters the snapshot and stays a
**permanent zombie-active** for every corpus reader and for next-boot restore.

The fix is a **monotonic write guard at the one choke point all seven writers traverse**: the UPDATE
gains a bound `AND updated_unix_nano <= ?2` predicate, so a write carrying an older `updated_at` than
the stored row is declined instead of applied. This works because every registry mutator bumps
`updated_at_unix_nano` to `now` (`registry.rs:266,278,343,359`), making the stale snapshot's value
necessarily smaller. A status-based predicate was rejected on measurement: `attach_resolution_summary`
*requires* `status == Resolved` (`registry.rs:336`) and is the documented final write, so
`status != 'resolved'` would break it. Placement is the corpus layer rather than the `triage` trait
because the MCP sidecar (`crates/mcp-server/src/tools.rs:461`) calls `CorpusWriter::update_incident_status`
**directly** from another process; per architecture.md §Cross-cutting Patterns → Module dependency
direction this costs no new crate edge (`mcp-server → corpus` and `pulse-app → corpus` already exist),
and per architecture.md §Established Decisions [ORM / Migrations] it needs no DDL — `status` and
`updated_unix_nano` are already plaintext scalar columns (`crates/corpus/src/schema.rs:65-74`), so the
predicate is expressible without relaxing the at-rest posture (security-plan §Data Protection → At rest).

Because a declined write becomes a **normal outcome** rather than a fault, the current sole error arm
must be re-interpreted — arch, security and obs converged independently on this. The write therefore
returns an explicit applied/declined outcome instead of collapsing both into `IncidentError::NotFound`,
and the persist cycle folds a per-cycle decline count onto its existing record (obs-plan §11 bans
per-row emission on this path).

## Implementation Steps

1. **Add the guard predicate at the corpus choke point.** In `crates/corpus/src/contract.rs`, extend the
   `update_incident_status` statement with `AND updated_unix_nano <= ?2` — a **bound** parameter reusing
   the incoming `updated_unix_nano`, never interpolated (security-plan §Input Validation). `<=` (not `<`)
   so an unchanged row re-persisting at the same timestamp still applies, which is the ordinary
   persist-cycle case.

2. **Classify the zero-row result instead of collapsing it.** `rows == 0` now means either "row absent"
   or "write declined as stale". Inside the SAME `conn.lock()` guard, follow a zero-row UPDATE with a
   cheap `SELECT 1 FROM incidents WHERE id = ?1`: row present ⇒ declined-stale; row absent ⇒ the existing
   missing-row error. (The classification is not cross-process atomic; that is benign — it decides which
   of two log categories is emitted, never correctness.)

3. **Return the outcome as a value, not an error.** Introduce `IncidentWriteOutcome { Applied,
   DeclinedStale }` in `crates/corpus/src/contract.rs` and change `CorpusWriter::update_incident_status`
   to return `Result<IncidentWriteOutcome, Error>`. A decline is a success value so the type forces each
   caller to consider it; encoding it as an `Error` variant would make "log it as a failure" the default,
   which is exactly wrong (obs-plan §10 Module-boundary error logging — a declined stale write is an
   expected outcome, not a module-boundary error).

4. **Mirror the outcome across the crate boundary WITHOUT a new dep edge.** `triage` does not depend on
   `corpus` (graph-confirmed: inbound edges to `corpus` are `mcp-server` and `pulse-app` only), so
   `triage::incident::persistence` declares its OWN parallel enum in its contract surface and
   `pulse-app/src/incident_persistence.rs` maps corpus's → triage's in the adapter. This is the
   established cross-crate delivery shape (architecture.md §Conventions → Module visibility discipline);
   a `corpus` → `triage` or library → `pulse-app` edge is forbidden.

5. **Thread the outcome through all seven production call sites** (enumerated from the code-graph impact
   query, not from memory — research.md §Graph impact):
   - `crates/triage/src/incident/persistence.rs:170` — count declines; do **not** log per row.
   - `pulse-app/src/incident_observer.rs:73` · `pulse-app/src/incidents_router.rs:238,309` ·
     `pulse-app/src/inference_runtime.rs:638,825` — a decline means a fresher writer won; stop routing it
     to `triage.incident.persist.error` (a genuine `Err` still logs there unchanged).
   - `crates/mcp-server/src/tools.rs:461` — `dispatch_mark_incident_resolved` must **not** report
     `{"resolved": true}` when its write was declined; return the honest not-applied result via the
     existing `Error::ToolDispatchFailed` shape with a bounded reason (security-plan §Error Handling —
     bounded category, no SQL text, no payload).

6. **Fold a per-cycle decline count onto the existing persist record.** Add `declined_count` to the
   `triage.incident.persist` emission in `run_incident_persist_cycle`, counted **after** each call
   returns so a decline contributes only when it actually happened (obs-plan §5, the `redactions_applied`
   post-write fold rule). One field per cycle — never per row — which also keeps the permanent-decline
   case (below) rate-safe.

7. **Extend the EXACT allowlist leaf and its guard in the same step.** `pulse-app/src/observability.rs`
   `triage.incident.persist` goes from three fields to four; `pulse-app/tests/unit_observability_allowlist_incident_diagnostics.rs`
   asserts the new field SET both ways plus the prefix-fallback discriminator (obs-plan §8 — a partial
   leaf silently redacts, and a resolve-only probe passes vacuously). The guard lives under
   `pulse-app/tests/` because `pulse-app` is `[lib] test = false`.

8. **Sibling-violator sweep — execute as an explicit NO-OP and say so.** `run_lifecycle_persist_cycle`
   and `run_storm_persist_cycle` are whole-state single-call saves, each with exactly one production
   writer (graph-confirmed). The defect needs two writers to one row with a stale snapshot, so neither can
   exhibit it. **Invent no edit to satisfy this step** — record the finding in the chunk report, per the
   `2026-08-26-ingest-consumer-stall-under-sustained-load` precedent.

9. **RED first, deterministically.** Add an integration test that reproduces the clobber with **no sleep
   and no interval**: seed an Active incident into a real corpus + registry, then run
   `run_incident_persist_cycle` against a test `IncidentPersistence` wrapper whose first
   `update_incident_status` call invokes `AutoResolveObserver::run_one_tick(now)` *before* delegating to
   the real adapter. That places the resolution precisely inside the cycle's write span. Pre-fix the
   corpus reports the incident active while the registry says Resolved; post-fix the corpus stays
   resolved. A second test covers the MCP shape: write `resolved` directly through `CorpusWriter` (as the
   sidecar does), then run the cycle against a registry that still holds the row Active.

10. **Mutation-check the pins.** Reverting the predicate must redden the new pins; record which pins and
    that the reversion was restored (test-plan §10 — a pin is trustworthy only once it is shown to fail).

## Constraints & rejected approaches

- **`status != 'resolved'` predicate — REJECTED on measurement.** `attach_resolution_summary`
  (`registry.rs:336`) requires `status == Resolved` and is the documented final write, so a status-only
  guard would break the resolution-summary path (site 5).
- **Guard at the `triage::IncidentPersistence` layer — REJECTED.** Covers six of seven writers; the MCP
  sidecar calls `CorpusWriter` directly and would keep losing every agent-driven resolution.
- **Delta-persist restructure — REJECTED for this chunk.** Larger change, needs new dirty-tracking state
  with crash-loss semantics, and does nothing for the cross-process path, which is not a snapshot problem.
- **Do NOT encode "declined" as an `Error` variant** — it makes logging-as-failure the default at seven
  call sites.
- **Do NOT add a per-row or per-decline log line** — the permanent-decline case below would flood it.
- **Do NOT touch `pulse-app/src/main.rs`, incident identity/dedupe semantics (arch §Fault Identity), or
  the `read_unix_nano` BLOB-vs-column divergence** — all explicitly out of scope per `scope.md`.
- **Do NOT read `payload` in the read-back leg** — plaintext `status`/`workspace` only; no key, no PII.
