## Goal

Give the full dashboard a **human-readable connection-status line** that states, in words, how many sources are
connected, whether telemetry is arriving (spans/s), and the buffer state — e.g. *"Receiving from 5 services ·
~540 spans/s · buffer 2 min / 10 min"* (P-070 · intent F10). Today the UI conveys connection only through the
`ConnectionDot` color + a live constellation; nowhere does it *say* the state in plain language. This closes the
last "State honesty & legibility" gap of Epoch 3 — the worded complement to the visual dot/constellation, so a
user never infers connection health from color alone (arch §Standard Contracts; design-system §Typography;
a11y-plan §1 not-color-alone).

Per the P4 scope decision (operator-selected "Full line + small backend delta"): the **connected-source count**
is derived frontend-side by reusing `services.list_with_states` + the P-067 `isServiceLive` recency gate (so the
worded count and the constellation dots agree by construction). The **ingest rate** and **buffer fill** are NOT
on any IPC surface today (the raw data lives in `crates/buffer` `BufferState` but is heartbeat-log-only), so this
chunk exposes them by **extending the existing top-level `ready` envelope's `ReadyChecks`** (obs-plan §3 "use the
sync command, not log-tailing") — adding FIELDS to a procedure already in Occupied Resources, which mints no new
namespace, capability JSON, arch entry, or `xtask capability-drift`/`EXPECTED_PROCEDURES` change (arch extract
C1; 2026-05-09 Settings-extension precedent applied to the ready envelope). The frontend polls `ready()` at 1s
and derives spans/s from the cumulative `rows_ingested` delta.

The chunk also folds the working-entry **CARRY**: make the `ConnectionDot` recency honest — its
`formatLastSpanAgo(0)` renders "just now" on a fresh boot with zero telemetry (`state==="Listening"` is the
no-ingest sentinel), which dishonestly implies a span just arrived. The fix routes an honest "no spans yet" into
the dot's accessible name + tooltip on that sentinel (a11y-plan §1 SC-1.4.13 line — honest recency in the
accessible NAME, not just the aria-hidden tooltip; the P-067 dual for the connection surface).

## Implementation Steps

1. **Backend — expose the two missing data points on `ReadyChecks` (`crates/ui-bridge/src/contract.rs`).** Add
   three fields to `ReadyChecks`: `rows_ingested: u64` (cumulative spans appended), `buffer_used_seconds: u64`
   (honest span-of-buffered-data, capped at the retention window), `retention_seconds: u64` (the configured
   window). All are `specta::Type`-friendly `u64` (specta `BigIntExportBehavior::Number` keeps them TS `number`;
   no `#[serde(default)]` — `ready()` always fully constructs them). Cross-bridge shape stays `Serialize` (arch
   extract C2).

2. **Backend — an honest `buffer_used_seconds` source (`crates/buffer/src/state.rs`).** Add a set-once
   `first_append_at_nanos` to `BufferState` (an `AtomicU64`, 0 sentinel, stored on the FIRST `record_rows_appended`
   only — a store-if-zero), surfaced in `BufferStateSnapshot`. This is the buffer's oldest-data anchor; combined
   with the retention cap it yields the honest data-span WITHOUT a DuckDB `MIN(ts)` query. **Do NOT use app
   uptime as a proxy** — an uptime-derived "5 min" when only 30s of data is buffered is the same dishonesty class
   as the CARRY (Epoch-3 honesty invariant). Implement computes `buffer_used_seconds = if rows_ingested == 0 ||
   first_append == 0 { 0 } else { min((now_nanos - first_append)/1e9, retention_seconds) }` (once
   `now - first_append >= retention`, retention eviction pins the span to exactly the window → the value is
   correct at the full-window limit).

3. **Backend — populate the fields in `ready()` (`crates/ui-bridge/src/health.rs`).** Thread `Arc<buffer::BufferState>`
   and the resolved `retention_seconds: u64` into `IntrospectionApiImpl` via its constructor (it already holds
   `broadcast_senders`; add two params). In `ready()`, snapshot `BufferState`, read `retention_seconds` (the
   resolved running value passed at construction — do NOT re-read `config.toml` in the 1s-polled resolver), compute
   `buffer_used_seconds` per Step 2, and set the three new `ReadyChecks` fields. Keep the resolver in-memory-only
   (no new DuckDB query). No new `tracing` fields beyond the existing `ui-bridge.ready` allowlist (obs extract — no
   raw values; counts only).

4. **Backend — boot wiring (`pulse-app/src/main.rs`).** Pass the existing `Arc<BufferState>` and the resolved
   retention (already computed for the buffer at boot) into `IntrospectionApiImpl::new(...)`. This regenerates

## Implementation notes
- **`retention_seconds` source:** pass the RESOLVED running value into `IntrospectionApiImpl::new` (main.rs already resolves it for the buffer at boot) — do NOT re-read `config.toml` in the 1s-polled resolver (per health.rs `get_settings` disk-read cost; config hot-reload rarity).
- **spans/s first sample:** `null` until 2 polls exist (no fabricated 0-rate); humanize ("~540 spans/s"); when rate is 0 + Listening → the empty phrasing, not "0 spans/s".
- **buffer_used cap:** the `min(…, retention_seconds)` cap is load-bearing for honesty — once the buffer warms, eviction pins the data-span to the window; `retention_window_active` (already on `BufferStateSnapshot`) may be used to short-circuit `used == retention` once latched.
- **bindings regen:** the `ReadyChecks` field additions regenerate `bindings/index.ts` (expected); it adds no procedure, so `EXPECTED_PROCEDURES`/capability-drift are unaffected. Follow the standard wrap bindings-regen-via-mcp-server-feature discipline at commit (grep `'"mcp":'` ≥1).
