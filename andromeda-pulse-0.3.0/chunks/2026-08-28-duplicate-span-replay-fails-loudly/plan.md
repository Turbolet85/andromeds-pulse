## Goal

A constraint-violating flush must cost one batch, not the pipeline. Today the first duplicate-key batch fails
loudly and correctly — one `duckdb.append` ERROR carrying `reject_reason: "append_failed"` — and the **next**
one hangs unbounded inside `Appender::flush()` while holding the shared connection mutex, wedging ingest at
0 ERROR and 0 panics thereafter. A retrying OTLP exporter resending spans is ordinary client behaviour that
reaches this hang, so it is a production defect, not a harness artifact. This chunk makes the append path
survive a rejected batch and keep draining, per obs-plan §10 defect 4 (which names this entry as owner) and
its Standard+ requirement that every module-boundary error be logged with a bounded category rather than
disappear.

Two supporting items ride with it. The demo injector currently manufactures the collision itself — `seq` is a
pure function of a batch counter that restarts at 0 in every process (`inject_demo.rs:277`), so process 2
replays process 1's exact primary keys. Removing that self-collision turns `smoke:gap-resume` arm A from an
accidental reproduction into the deliberate retry-resend shape it was always meant to model. And the leg's
verdict is currently readable in a window that cannot reach the threshold it reads: `ingest_progress::evaluate`
keys on `buffer.consumer.stalled`, announced only after 30 non-draining ticks (450 s), while `--observe-minutes`
takes any value — measured 2026-08-28 at `--observe-minutes=3` reporting PASS over a consumer that had in fact
stopped (test-plan §3 records this as an open gap owned by this entry).

The isolation topology is explicitly **not** re-opened: obs-plan §10 and `.claude/rules/observability.md` both
record the reference-connection mandate as satisfied by shipped code, and the earlier reading that implicated
the shared connection was measured false at the predecessor chunk.

## Implementation Steps

**Step 1 — Discriminate the hang mechanism before repairing it (probe, not inference).**
Research narrowed the residual to the connection: the first violating flush returns cleanly (the ERROR is
logged, so `spawn_blocking` joined and the `Appender` dropped), and the next hangs. Write a bounded in-crate
probe in `crates/buffer` that appends a violating batch, observes the `Err`, then appends a second batch —
**on a worker thread under an explicit `recv_timeout`**, per the established hang-safe form
(`appender::tests::append_logs_batch_same_tick_same_severity_keeps_both_records`), so a hang FAILS rather than
wedges the suite. Never a bare duplicate-INSERT probe: `crates/buffer/src/schema.rs:320–323` records that shape
as a documented hang on libduckdb-sys 1.10502. Determine which holds:
- **M1** — connection-level residual state (a leftover transaction or table lock) the next flush waits on, and
  which our code can clear.
- **M2** — an upstream lock the connection cannot clear.

**Step 2 — Repair: leave the connection usable (the selected fork).**
In `append_record_batch_to_table` (`appender.rs:632`), on a `flush()` error, reset the connection's residual
state before returning `Error::Append`, so the next call's flush proceeds normally. Keep the existing return
type and the existing `Error::Append` variant — `consumer::describe_error` already maps it to the bounded
category `"append_failed"` the leg reads, and `run_consumer` already logs it and **continues** the `while let`
loop (`consumer.rs:76–93`). No new error variant, no new obs field, no new leaf: the repair's whole job is
making the second flush return.

**Fallback, only if Step 1 proves M2:** take the terminal-and-reported half of the entry's fork — announce
once with bounded `reason`/`consequence` tokens on the obs-plan §6 warn-row shape, mark the append path
terminal, never hang. That widens the touchpoints to `consumer.rs` + `contract.rs` + a new §8 exact leaf and
its guard. **Surface the M2 finding to the operator before building the fallback** — it changes the product's
behaviour from "loses a batch" to "stops ingesting", which is the operator's call, not the plan's.

**Step 3 — The repair must hold for every table `append_table_traced` serves.**
`dispatch_batch`'s `Batch::Spans` arm appends `spans` (`consumer.rs:111`) *and* `span_events`
(`consumer.rs:125`) on the same guard, both `?`-propagated; replayed spans replay their events, and
`span_events` PK `(trace_id, span_id, event_index)` collides identically. The repair lives in the shared fn, so
it covers all four tables by construction — assert that rather than assuming it.

**Step 4 — Injector: process-unique span identity, emission profile untouched.**
`seq` drives **three** things in `inject_demo.rs`: identity (`trace_id(seq)` :224 / `span_id(seq)` :231), the
error pattern (`error_roll(seq)` :242, gating `is_err` :304), and duration (`jitter = (seq * 7) % eff_base`
:302). Fold a per-process nonce into **only the two identity functions** — never into `seq` itself — so batch
count, span count, error count and durations stay exactly as they are. This is what preserves
`architecture.md` §Stack's arg-less-default requirement for the headful leg, whose `PULSE_INJECTOR` relay
threads only the path (`webview_drive.rs:728`). The nonce must be bounded-parsed with a graceful default and
never panic if it is externalized (security-plan §Input Validation); prefer a source needing no new env var or
state file, since either would owe a §Input Validation boundary-enumeration entry and an arch §Occupied
Resources registration in this same chunk.

**Step 5 — Injector: a deliberate replay flag, so arm A still exercises the defect.**
Once Step 4 lands, arm A would exit 0 **because the collision is gone, not because the hang is fixed** —
research confirmed this as a real gap. Add an opt-in flag that makes the injector deliberately re-emit a prior
run's span identities, modelling a retrying OTLP exporter. Follow the formalized CLI contract exactly
(`architecture.md` §Stack): range-checked value, unknown argument REJECTED with exit 2, and the **arg-less
default unchanged**. Register the flag in arch §Occupied Resources at wrap.

**Step 6 — Arm A opts into the replay, and its verdict requires the failure path was exercised.**
Point `smoke:gap-resume` arm A at the new flag so it drives storm → replay → recovery. Arm A's PASS then
requires positive evidence on **both** halves: the `duckdb.append` ERROR carrying
`reject_reason: "append_failed"` present in the run window (proving the violation actually happened), and
`buffer.consumer.stalled` **absent** (proving it did not wedge). Presence of neither is the vacuous shape, not
a pass. Arms B (`--sustained`) and `--reconnect-only` keep their own non-borrowable preconditions unchanged.

**Step 7 — The observe-window guard.**
Make the leg refuse to report PASS when its observe window cannot reach the 450 s / 30-tick threshold
`ingest_progress::evaluate` reads. `DEFAULT_OBSERVE_MINUTES = 9` (540 s) already clears it; the gap is that
`observe_minutes: Option<u64>` (`xtask/src/main.rs:73`, defaulted at :210) accepts any value with no lower
bound. Report INCONCLUSIVE (the existing non-PASS outcome), never PASS — matching the NEUTRAL-tolerant posture
obs-plan §10 requires of every check over `agent-latest.jsonl`. Cover the boundary by unit test, not by a
timed run.

**Step 8 — Pins.**
The Step 1 probe becomes the permanent in-crate pin (worker thread + `recv_timeout`), so `buffer`'s
"no tracked in-crate gap remains" status stays true. Add the injector's first `#[cfg(test)] mod tests` covering
the new flag's parse arms and the **default-preservation invariant** (arg-less emission unchanged), which
partially discharges test-plan §1's `inject-demo-arg-parse-unit-coverage` trigger. Add a unit pin for the
observe-window guard's boundary.
