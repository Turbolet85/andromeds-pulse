## Goal

The ingest consumer stops draining on the first batch after a producer restart and never appends again —
`rows_ingested` frozen at 3,240, the ingest channel climbing 0 → 85.7 %, 24k+ accepted spans unpersisted,
`ingest.channel.full` fired, `buffer.consumer.stalled` announced at 450 s, all at **0 ERROR and 0 panics**
because nothing returns. The predecessor made this reproducible on demand (`cargo xtask smoke:gap-resume`,
arm A red by design) and measured that the `CueLatch` + damper amplifier bound does **not** prevent it. This
chunk attributes the block and repairs it, so accepted spans stop being silently dropped.

**The plan does not prescribe the fix, and that is deliberate.** Scope §4 fixes an ordering — separate the
trigger, then attribute, then repair, then green the leg — and the plan honours it because the predecessor's
own carried lesson is that a chunk built to CONFIRM a fix disproved it, and could only do so because the
scenario was built before the conclusion. What the plan prescribes instead is the **decision procedure**: a
discriminating probe whose two outcomes select between enumerated repair shapes that share one acceptance.

Research already re-aimed the field, and this is the plan's most load-bearing input. All three durable
artifacts describing the defect (the working entry, obs-plan §10 defect 4, `rules/observability.md`) state the
mechanism as *"`dispatch_batch` holds `conn.lock()` across every append, so BOTH shared-connection users die —
the consumer and the retention sweep."* **The second half is false at HEAD**: `run_retention` has held a
dedicated `try_clone()`d connection since chunk #99 (`crates/buffer/src/retention.rs:72-86`), touching the
shared `conn` exactly once to make that clone. The shared appender connection has exactly **one** production
user — `dispatch_batch`. So retention's death cannot be explained by the Rust mutex, and the leading
candidate becomes an ENGINE-level DuckDB block that queues retention's `DELETE` behind the stuck append on
its own connection — the class chunk #99 already recorded ("L1a reads queued behind append-path row-group
maintenance"). Per arch §Established Decisions [In-Process Channel Architecture] + obs-plan §10 (connection
isolation) + test-plan §3 (the leg is the acceptance test and must never be weakened).

## Implementation Steps

### Step 1 — Separate the trigger (the mandated first arm)

Add a **reconnect-without-gap** mode to `cargo xtask smoke:gap-resume`. Arm A changes two variables at once
(180 s of idle **and** a new gRPC connection, since `inject_demo` connects once per process); nothing yet
separates them.

The drive shape is already expressible (`GapResumeOptions.gap_seconds`, `xtask/src/gap_resume.rs:49`, and
`drive()` at `:246` sleeps that value between two injector runs), **but the verdict is not**:
`gap_resume::judge` (`:134`) has exactly two arms — `sustained`, where a storm is a control FAILURE, and gap,
where the absence of a storm is INCONCLUSIVE. A reconnect run has no storm by construction and is not
`sustained`, so today it is judged INCONCLUSIVE whatever the consumer does.

So the arm needs three things: a mode discriminant on `GapResumeOptions` + the CLI (`xtask/src/main.rs:63`,
dispatch `:198`); a third `judge()` arm; and **its own stated precondition** — the analogue of
`StormEvidence::fired()` (`:78`) that makes ITS verdict countable. A reconnect arm's precondition is that the
producer genuinely disconnected and reconnected (two injector processes completed, and the post-reconnect
feed actually delivered spans), not that a storm formed. Per test-plan §3's self-proving-precondition rule,
which the leg already honours for both existing arms.

**This arm is a real, permanent third arm, not a throwaway probe** — scope §5 puts it in scope and test-plan
§3 registers the leg; a mode that disappears after one run cannot guard the reconnect path later.

### Step 3 — Repair, shape selected by Step 2

Do not pre-commit. The enumerated shapes, each with the same acceptance:

- **If HELD (candidate c).** The appender path is the last production user of the shared connection while
  every other consumer already has its own. Give the append path a dedicated connection and/or bound the
  DuckDB call so a stuck engine operation cannot hold the loop open-endedly. Copy the established
  dedicated-clone shape verbatim — clone once at construction, `tracing::warn!(target: …, fallback =
  "shared_connection")` on failure (`retention.rs:72-86`; mirrored in `viz::query::read_connection` and
  `TriageSqlState`) — per obs-plan §10. A bound that can expire creates a boundary that obs-plan §10 and
  arch §Established Decisions [Error Handling Pattern] require to produce a **typed error, not a silent
  degrade**: the defect's whole signature today is that nothing returns, so nothing reports.
- **If FREE and the tap is implicated (candidate a).** Move `observe_spans_for_baseline` off the async task.
  **Security constraint, load-bearing:** the tap is one of the three consumers of `extract_service_name`, and
  the scrub lives INSIDE that fn precisely so the column, the storm `FingerprintObserver` and this tap all
  see the same scrubbed identity (security-plan §Security Anti-Patterns → Logging;
  chunk `2026-08-23-ingestion-scrub-coverage`). Relocating the tap must keep it downstream of that fn — a
  move that reads raw span data is the exact failure the choke-point placement prevents. obs-plan §5 also
  records `observer_invocations == fingerprints_computed` as the positive live-feed reading that must survive
  the move.
- **If FREE and the pool is implicated (candidate b).** Bound or isolate the blocking work. Arch constrains
  this hard: one shared multi-threaded runtime serves both OTLP ports and IPC, so any thread change has
  whole-app blast radius (arch §Stack → Async runtime). No second runtime, no channel-substrate swap.

Whatever the shape, `dispatch_batch`'s **per-table post-append redaction fold** must survive — each
`state.record_redactions` fires after its own table's append (`consumer.rs:112`, `:126`, `:133`, `:150`) so a
batch rejected at `flush()` contributes zero. obs-plan §5 records this siting as structural and names the
regression signature: `redactions_applied: 2` with `rows_ingested: 0`.
