## Graph impact (rust plane, `db_state: fresh`, 10 rows)
- **`push_metric_row` / `collect_metric_points` / `build_metrics_record_batch`** — the caller set is a single closed chain inside one crate: `consumer/dispatch_batch()` (`consumer.rs:131`) → `appender/append_metrics_batch()` → `appender/build_metrics_record_batch()` → `appender/collect_metric_points()` (5 call sites, `appender.rs:681-748`, one per OTLP data kind) → `push_metric_row`. The only other caller is the test `appender/tests/redaction_counter_folds_once_per_batch_across_all_four_builders()` (`appender.rs:1229`).
- **Meaning for the change:** zero cross-crate blast radius on the WRITE side — the threading is entirely `crates/buffer`. The read side is reached by DTO shape, not by call edge, so it does not appear in this query (see Caller threading below).

## Patterns detected
- **Return-and-fold, already in place for metrics** (`appender.rs:144`, `consumer.rs:131-137`): `build_metrics_record_batch` returns `Result<Option<(RecordBatch, u64)>, Error>` and `dispatch_batch` calls `state.record_redactions(redactions)` *after* `append_table_traced(&guard, "metrics_points", rb)?`. **This answers the obs extract's research question: the metrics builder already routes its tally the required way.** A label scrub adds to the existing `redactions_applied` accumulator inside the same builder; no restructuring is needed and `consumer.rs` likely needs no edit at all.
- **Scrub cardinality differs between name and label** (`appender.rs:158-160`): the metric name is scrubbed **once per metric** with the explicit comment "every point of one metric shares the name". Label sets are **per data point**, so a label scrub fires inside the point loop — a different call rate and a different contribution to the tally.
- **Six parallel `Vec` columns + a `seq` block** (`appender.rs:146-195`): the builder accumulates six `Vec`s, then reserves one `seq` block per batch (`state.reserve_metric_seq_block(len)`) and zips them into a 7-field Arrow schema. A label column is a 7th `Vec` and an 8th `Field`.
- **The Arrow batch is also the broadcast payload** (`consumer.rs:133`): `broadcast::encode_metrics(&rb)` encodes the *same* `RecordBatch` onto `pulse://stream/metrics`. A new column therefore reaches the live stream automatically — no separate wiring, but also no opt-out.
- **`scrub_otlp_field(value, &mut redactions) -> String`** (`appender.rs:354-362`) is the reusable push-site scrub: `Allowed` passes through, `Redacted { category }` increments and yields `[REDACTED:{category}]`.
- **`hash_resource` is keys-only and toolchain-unstable** (`appender.rs:789-802`): it hashes `kv.key` for each resource attribute plus `dropped_attributes_count` through `DefaultHasher` — never a value. Confirms the scope's cautionary reading of the precedent.

## Conventions to follow
- **Three DDL representations must move together** — `schema.rs:70` (per-table const) and `schema.rs:168` (concatenated `SCHEMA_DDL`) are forced to agree by `ddl_constants_match_concatenated_schema` (`schema.rs:462`); `crates/viz/src/query.rs:481` is a third, **structurally unguarded** copy (`viz` has no `buffer` dep). Same three-site shape the identity chunk handled.
- **PK/column assertions go through `information_schema`** — `metrics_points_primary_key_includes_seq_ordinal` (`schema.rs:402-430`) reads `key_column_usage` rather than probing with a duplicate INSERT (a documented hang on this build).
- **Ingest already bounds attributes** (`invariants.rs`): `MAX_ATTRIBUTES_PER_SPAN = 128` is enforced per metric data point in every arm, and `validate_attributes` bounds `MAX_ATTRIBUTE_KEY_BYTES = 256` and `MAX_ATTRIBUTE_VALUE_BYTES = 4096`. **This answers the security extract's research question: data-point attribute count and per-key/value size are already bounded before `buffer::Appender`.** The chunk inherits the bound rather than adding one — but 128 labels × 4096 B is the per-point worst case a storage shape must tolerate.
- **`capability-drift` keys on procedure NAMES only** (`xtask/src/main.rs:1070-1078`): `parse_bindings` extracts the `ARGS_MAP` keys from `bindings.ts` and set-diffs them against `EXPECTED_PROCEDURES` (a list of name strings). **This answers the arch extract's research question and verifies the scope premise** — a DTO field change cannot move that set. (The gate still runs unconditionally per test-plan §3; it simply will not fire on this.)

**Seam facts:** the type crossing the package boundary is `MetricRow` (`crates/viz`, `serde::Serialize + Deserialize + specta::Type`), consumed by `crates/mcp-server` (normal dep, shipped code) and by the webview through generated bindings. `viz` has **no `buffer` dependency** — that is why its DDL copy is structurally unguarded, and closing that by adding a dep is an arch-DAG contract question, not a convenience (arch extract, §Constraints).

**The load-bearing equality:** the design needs *"two data points of one metric that differ only by label set read back distinguishably"*. Verified this is decided at exactly one place — `SELECT_METRICS`'s column list (`query.rs:24`) and the `MetricRow` it fills. Nothing else on the read side inspects labels: `MetricsChart` aggregates only `ts_unix_nano` and `value` into time buckets (`MetricsChart.tsx:180-195`), and `MetricsRoute` renders the chart or an `EmptyState`. **There is no metrics table, legend, or per-row surface in the webview.**

## Open questions
- **Representation — a scrubbed label column on `metrics_points` vs a side table.** → blocks: **plan-decision**. Research supplies the evidence but not the verdict: the side-table shape's only in-schema instance (`resources`) is producer-less and dead, and a new table trips the retention drift guard; a hashed key over label content is barred by security-plan's content-independent-discriminator rule unless computed over already-scrubbed values, and would be **opaque at the only witness surface that exists** (see below). P4 resolves with the operator.
- **Label KEY disposition — scrubbed like values, or allowed as bounded identifiers?** → blocks: **plan-decision**. Keys are client-controlled and already bounded at 256 B, but the scrub mandate is written for VALUES. obs bars keys from telemetry either way, so this is purely a storage question.
- **Does anything render labels in the webview?** → blocks: **implementation-scope**. Measured: no. `MetricsChart` uses two fields; the a11y mock returns `"metrics.query": { items: [], … }` (`mock-tauri.ts:79`), so the `/metrics` route — which **is** in the audited set (`pa11y-ci-config.json:15`, `axe/p13-empty-states.spec.ts`) — renders only its empty state during audits and has no populated metrics fixture at all. So a label field changes nothing the a11y chain can see, and the design/layouts/a11y constraints stay dormant unless P4 elects to build a UI surface — which the directive does not ask for (it names the e2e read-back as the proof).
