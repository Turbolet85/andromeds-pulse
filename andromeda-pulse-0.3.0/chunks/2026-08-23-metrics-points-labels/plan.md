## Goal

A metric data point's label set survives ingestion and reads back, so two data points of one metric that
differ only by their labels stop arriving indistinguishable. This is the declared other half of
`2026-08-23-metrics-points-identity`: that chunk gave the pair a `seq` ordinal so both rows persist, but
`metrics_points` stores no attributes column and `push_metric_row` takes no attributes parameter, so both
rows land label-less. Identity closed; information loss open — and *made silent*, because the whole-batch
`duckdb.append` ERROR was the only signal the dimension was being dropped.

The representation is the decision, and it is settled by operator ruling at the P4 gate: **a scrubbed
`labels` column on `metrics_points`**, keys stored verbatim and values passed through
`security::scrubber::scrub_attribute`. Both alternatives were weighed and declined (see §Constraints &
rejected approaches). The deciding fact is measured, not assumed: read-back is the **only witness of any
kind** this project has — `MetricsChart` aggregates only `ts_unix_nano` and `value` into time buckets and
there is no metrics table, legend, or per-row surface anywhere in the webview — so a representation whose
read-back is opaque could not be shown to work at all. The proof therefore lives entirely Pulse-side;
verified first-hand at Conductor HEAD `fb8a8a5`, no external witness exists (`conductor-emit` has no metrics
module and a grep for the metrics symbols across all 9 conductor crates returns zero files).

The work rides infrastructure that already exists. `build_metrics_record_batch` already returns
`Result<Option<(RecordBatch, u64)>, Error>` and `dispatch_batch` already folds that tally at the
`metrics_points` post-append site, so the new scrub joins the persisted-cells-only path with no
restructuring (per obs-plan §5). Ingest already bounds data-point attributes at 128 per point, 256 B per key
and 4096 B per value (`crates/ingest/src/invariants.rs`), so the bound half is inherited rather than built
(per security-plan §Input Validation). Per architecture.md §Conventions → Primary key convention the key
stays the settled four columns — `labels` is **not** part of it — and per §Cross-cutting Patterns →
Test-time telemetry injection the RED and GREEN legs both run over the real OTLP receiver.

## Implementation Steps

1. **Add the `labels` column to all THREE DDL representations.** `crates/buffer/src/schema.rs:70` (the
   per-table `CREATE_METRICS_POINTS` const) and `:168` (the concatenated `SCHEMA_DDL`) are forced to agree by
   `ddl_constants_match_concatenated_schema`; `crates/viz/src/query.rs:481` is a third, structurally
   unguarded copy (`viz` has no `buffer` dep). Column is `labels VARCHAR NOT NULL DEFAULT ''`, `snake_case`,
   `NOT NULL` with an empty-string default because a data point with no attributes is the ordinary case and
   the OTLP-spec-optional rule reserves nullability for genuinely absent spec fields (per architecture.md
   §Conventions → Nullable patterns / Database entity naming). **The PRIMARY KEY is unchanged.**

2. **Centralise the label encoding, and scrub the JOINED form.** One crate-internal helper in
   `crates/buffer/src/appender.rs` turns a `&[KeyValue]` into the stored string: stable ordering so two points
   with the same label set encode identically, each pair rendered `key=value`, pairs joined by a separator,
   empty attribute set ⇒ empty string. Non-string `AnyValue` variants need a defined rendering — take the
   shape `extract_string_attribute` (`appender.rs:364`) implies and define the rest explicitly rather than by
   accident.

   **The scrub input is the joined `"{key}={value}"` string, NOT the bare value** — this is load-bearing and
   was corrected at the P5 review. `scrub_attribute` (`crates/security/src/scrubber.rs:41`) takes
   `value: &str` and matches the catalog against that one string, but **two of the eight arms require the key
   name to be inside it**: `secret_kv` is `(?i)(password|passwd|secret|token)[\s=:]+\S+` (`:83`) and `api_key`
   is `(?i)(api[_\-]?key|access[_\-]?token|secret[_\-]?key|auth[_\-]?token)[\s=:]+[\w\-]{12,}` (`:77`). A
   label `{password: "hunter2"}` presents only `hunter2` to a value-only scrub and matches **nothing** — the
   whole keyed class would leak while only bare-shape values (the eighth arm) were caught.

   **Evaluate the union — joined form first, then the bare value; redact if EITHER matches.** No arm in the
   catalog uses `^` or `$` (verified), so joining with `=` is a superset in practice for the `\b`-anchored arms
   (`provider_key`, `credit_card`, `ssn`) as well; the union is cheap insurance that stays correct if an
   anchored arm is ever added. On a `Redacted { category }` verdict the pair is reconstructed as
   `{key}=[REDACTED:{category}]` — **the key stays verbatim**, preserving the operator ruling, because
   `ScrubbedValue::Redacted` carries a category and no content, so the key comes from the `KeyValue` we already
   hold. Over-redaction when the KEY alone trips the match (`password=1`) is accepted per the catalog's stated
   recall-over-precision posture (`scrubber.rs:56-58`).

3. **Thread `p.attributes` through the collector.** `collect_metric_points` (`appender.rs:667`) holds `p` in
   scope in all five OTLP arms — Gauge(0) / Sum(1) / Histogram(2) / ExponentialHistogram(3) / Summary(4) —
   and passes it nowhere today. Each arm forwards `&p.attributes`; `push_metric_row` (`appender.rs:768`)
   takes the encoded label string and pushes it onto a new parallel `Vec<String>`. Note the **cardinality
   difference from the metric name**: `metric_name` is scrubbed once per metric (`appender.rs:158-160`, "every
   point of one metric shares the name"), whereas labels are scrubbed **per data point**.

## Constraints & rejected approaches
- **Side table `metrics_point_labels` — REJECTED** (operator ruling, P4): the schema's only instance of that
  shape (`resources`) is producer-less and dead, one of three retention DELETEs sweeping permanently-empty
  tables; a new table must earn a producer AND a `DELETE_BY_CUTOFF` entry or trip the drift guard at
  `retention.rs:369-372`, and arch's acceptance bars a fourth producer-less table.
- **Hashed label-set key — REJECTED** (operator ruling, P4): opaque at the only witness that exists, so it
  cannot show a label survived; security-plan bars a stable identifier derived from unredacted client content;
  and the in-schema precedent `hash_resource` is cautionary — keys-only, never values, through `DefaultHasher`
  which is not stable across Rust releases.
- **Scrubbing label KEYS (replacing a key with a placeholder) — REJECTED** (operator ruling, P4): two distinct
  keys redacting to one placeholder would reproduce exactly the collision class
  `2026-08-23-metrics-points-identity` just closed, and keys are already bounded at 256 B by ingest. **Note the
  ruling's original rationale was partly WRONG and is corrected here** (P5 review): it claimed the
  `secret_kv`/`api_key` arms being key-name-anchored meant a credential under a key name was "caught through
  the VALUE path regardless". The opposite is true — those arms require the key name to be *inside* the
  matched string, so a split `{password: "hunter2"}` matches nothing value-only. The ruling stands unchanged
  (keys are stored verbatim, never replaced by a placeholder); what changed is the scrub INPUT, now the joined
  `key=value` form, which reaches the keyed class without touching how keys are stored.
- **Value-only scrubbing of labels — REJECTED** (P5 review): it leaves two of the eight catalog arms
  structurally unreachable and would ship a RED leg that passes while the keyed class leaks.
- **Adding a `buffer` dependency to `viz`** to guard the third DDL copy — OUT OF SCOPE: an arch-DAG contract
  question (§Cross-cutting Patterns → Module dependency direction), not a convenience for this chunk.
- **Do not put `labels` in the PRIMARY KEY** — the key is settled at four columns; widening it would reopen
  the identity question this chunk's predecessor closed.
- **Do not build a webview surface for labels.** Measured: none exists (`MetricsChart` reads two fields), and
  the directive names the e2e read-back as the proof. Leaned per the operator directive's own framing. A
  Metrics label surface would be genuinely new user-facing territory — layout-templates.md has never drawn the
  Metrics wireframe — and belongs to its own chunk.
- **Do not add a third `EmptyState` variant** for "ingested but lossy": design-system.md and
  layout-templates.md authorise exactly two (honest-error checked before empty), and a Metrics-only divergence
  is barred by the shared-component mandate.

## Implementation notes
- **`consumer.rs` needing no edit is a FINDING, not an oversight** — verify it rather than assume it. The
  per-table post-append fold already exists because `2026-08-23-metrics-points-identity` moved it there.
- **Order sensitivity:** the three DDL sites must move together. Sites 1 and 2 are guarded by
  `ddl_constants_match_concatenated_schema`; site 3 in `viz` is **not** guarded by anything — a one-sided edit
  there fails only at the `viz` query tests, and possibly not at all.
- **Encoding determinism matters for the pin:** two points with the same label set in a different attribute
  order must encode identically, or the distinguishability pin measures ordering noise rather than labels.
- **State the `redactions_applied` counting UNIT explicitly.** The `labels` column is ONE persisted cell, but
  a single data point can carry several redacted pairs. Decision: **count once per redacted label PAIR**, not
  once per cell — it is the more informative reading and `scrub_otlp_field` already increments per call.
  This does not violate obs-plan §5's persisted-cells-only rule, whose purpose is that a batch rejected at
  `flush()` contributes zero; the cell did persist. It does refine what the counter's unit MEANS, so it rides
  the obs-plan amendment below rather than passing silently.
- **The live leg is not `agent-run.sh run`.** That verb is `cargo nextest run --workspace` (the test suite),
  not an OTLP send — the OTLP producer is the `inject_colliding_metrics` example, invoked by path against the
  booted app. Measured from `.claude/rules/verification-harness.md` §5-command discipline.
- **The a11y chain is unaffected but must still pass.** `/metrics` IS an audited route
  (`pa11y-ci-config.json:15`, `axe/p13-empty-states.spec.ts`), but its mock returns
  `"metrics.query": { items: [] }`, so the audit renders only the empty state and has no populated metrics
