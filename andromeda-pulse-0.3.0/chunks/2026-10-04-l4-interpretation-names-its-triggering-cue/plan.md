## Goal
Make the L4 interpretation describe the cue that triggered it rather than whatever else the digest shows. Two framing
changes land in the text the model reads. Research found that production never fills the prompt's own
`# Corpus Retrieval` block: `corpus_retrieval` is `""` at `pulse-app/src/inference_runtime.rs:412-427` and at
`investigate_router.rs:248`. Past incidents therefore reach the model only as the digest's `CORPUS MATCHES:` lines
(`crates/triage/src/digest/assembler.rs:687-692`), so both changes act on the digest text and on prompt text that
describes it.

1. **The digest names its trigger.** `render_payload` writes a `TRIGGER: {cue_cause_label(kind)}` line for the
   digest's first cue. That is the cue whose kind becomes the incident's identity (`inference_runtime.rs:815`). It uses
   the closed ASCII vocabulary that already prefixes incident titles (`triage::contract::cue_cause_label`,
   `contract.rs:203-212`). It carries the kind label only, never `scope_id` (overseer, founder-delegated, 2026-10-04).
2. **The digest frames corpus matches as other incidents.** One ASCII note line directly under the `CORPUS MATCHES:`
   header marks the lines below it as other or past incidents, context only.
3. **The prompt states the rule.** A shared ASCII framing instruction in all three tiers' Output Instructions says that
   the title, the symptom and the first hypothesis describe the TRIGGER line's signal, and that CORPUS MATCHES lines are
   other incidents never to be described as the current signal. It is conditional on the line being present, so a
   reflection digest or an `investigate.run_action` payload without one reads correctly. The three prompt lineages bump
   together.

The measurement itself is the gated part. `pulse-app/examples/l4_decision_probe.rs` gains:
- a closed, bounded names-the-trigger label computed in-process from the parsed output (no model text leaves the probe);
- a d3-like corpus-carrying retry shape;
- a no-framing counterfactual arm.

The pre-registered rule (overseer, founder-delegated, 2026-10-04): the `shipped` arm's rank-1 hypothesis names the retry
in at least 36 of 40 generations, with the `nf` arm recorded beside it, unthresholded. It runs once a Linux CUDA
llama-cli exists. Identity, coalescing and the title grounding are untouched (architecture §Established Decisions
[Fault Identity]). The argv prompt gains no OTLP-derived content class (security-plan §Input Validation, the L4
inference argv prompt row).

  for what the digest TRIGGER line carries with no signature change.

  (`corpus_retrieval = ""` at every production call), so framing there would ship an emitter that never fires. They
  stay as they are; their removal is not this chunk's.
- Renaming the `CORPUS MATCHES:` header — rejected. It breaks 3 pins and 3 comments (research §Sweeps) for no gain over
  a note line under an unchanged header.
- Putting `scope_id` (a service name) in the TRIGGER line or the instruction — rejected per the overseer's ruling: the
  kind label only, so the argv content set does not widen.
- Grading names-the-trigger from a deterministic-mode generation — rejected. The deterministic runner never reads the
  prompt, so its canned rank-1 hypothesis is constant (architecture §Occupied Resources → `ANDROMEDA_PULSE_L4_DETERMINISTIC`).
- Printing, logging or writing any model text (title, symptom, statement) from the probe — banned. Only the closed
  label and counts leave the process.
- Firing either gated entry before the block clears, or against the Windows `AI-Model/llama-b9305-cuda/llama-cli.exe`.
  It is a PE32+ image and cannot run on this host.
