## Goal

Close the COVERAGE half of the PII-scrubber gap: the client-controlled DuckDB ring-buffer columns that a host
app can fill with arbitrary text currently reach storage unscrubbed, and the ring buffer is unencrypted, so a
credential placed in one of them is stored and read in plaintext. `security-plan.md` §Security Anti-Patterns →
Logging already carries the MEASURED-reality clause naming this working-route entry as the owner of the impl
half, so this chunk is load-bearing for that amendment rather than optional cleanup; encryption is not an
available alternative (§Data Protection bans DuckDB at-rest encryption, CVE-2025-64429), which makes
write-boundary scrubbing the only control the plan permits.

The live target set is **four** columns, not the five the entry names: `spans.service_name` ·
`span_events.name` · `metrics_points.metric_name` · `log_records.severity_text`. Research proved the fifth
(`instrumentation_scopes.scope_name`/`.scope_version`) has **no producer** — `append_record_batch_to_table` is
called for exactly four tables — so scrubbing it would ship an emitter that never fires. Per the P4 operator
decision it is dispositioned as documented-vacuous with zero code, and the spec's five-column clause is
corrected at the wrap.

Treatment is **uniform scrub across all four** (operator decision), but applied at two different sites for one
measured reason: `service_name` is scrubbed inside `extract_service_name` because that single `pub(crate)` fn
feeds **three** consumers — the `spans` column, the storm `FingerprintObserver`, and the baseline
`SpanObserver` tap — and scrubbing only the column would leave two raw paths into `triage` AND desynchronise
DuckDB's service identity from the baseline/registry identity the constellation joins against (research §F2).
The other three scrub at their push sites through the existing `scrub_otlp_field` helper. The one accepted risk
is `metrics_points.metric_name`, the only target inside a PRIMARY KEY: two distinct credential-shaped names
redacting identically at the same `ts_unix_nano` + `resource_hash` would collide and fail the whole batch —
loud (ERROR at `flush()`), never silent, and unrelated to the corpus `pipeline_metrics` lookup, which holds the
app's own internal metric names in a separate database.

  absence asserted first passes for the wrong reason.
