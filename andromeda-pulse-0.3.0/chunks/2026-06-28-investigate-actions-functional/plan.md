## Goal
Make each of the 4 Investigate actions (diagnose latency outlier / find error correlation / trace failed
request / summarize service health) run a **real L4-LLM-backed analysis with visible progress and a surfaced
result or error — never a silent no-op** (per intent F12 / requirements P-072). Today the modal auto-generates
the snapshot correctly, but each action button only copies a prompt template to the clipboard
(`InvestigationModalForm.tsx:127 handlePresetPick`); from the user's POV the product's core AI-debug value is
dead. This chunk wires the buttons to a new backend resolver that builds a curated-telemetry context, runs the
L4 inference, and returns a structured analysis the modal renders.

**Decision locked (P4 user dialogue):** reuse the existing incident `L4Output` schema + parse path rather than
introduce a new free-form analysis contract. The new resolver calls the EXISTING
`LlmInferenceRunner::generate_constrained(prompt, L4_OUTPUT_JSON_SCHEMA)` (the only inference entry point;
`crates/interpretation/src/contract.rs:183`) and `interpretation::schema::parse_bounded`, then maps the parsed
`L4Output` to a transient result DTO — **no `LlmInferenceRunner` trait change, no `interpretation`-crate change,
no change to the just-landed P-073 deterministic runner.** The investigate path is an ADDITIVE second consumer
of `generate_constrained` (today's only production caller is `inference_runtime::handle_digest_outcome @
pulse-app/src/inference_runtime.rs:336` — code-graph confirms zero blast radius). It deliberately does NOT call
`create_incident_from_l4_output` — the result is transient (no incident persisted/broadcast per click).

Backend path is in-process L4 (not MCP): MCP is feature-gated/off-by-default and would not run under the
deterministic-L4 acceptance, so it is considered-and-rejected here (per intent §5 MCP-compliance deferral).
Reproducibility comes from the deterministic-L4 mode (`ANDROMEDA_PULSE_L4_DETERMINISTIC` truthy, P-073): under
it the runner returns the canned `L4Output` for every action, so the acceptance test is deterministic with no
GPU/model. With a real model the 4 distinct prompt framings yield 4 distinct analyses.

## Implementation notes
- **Deterministic-mode consequence (accepted):** under `ANDROMEDA_PULSE_L4_DETERMINISTIC` the runner ignores the
  prompt → all 4 actions render the SAME canned `L4Output`. The acceptance is "a visible result, reproducibly,"
  not "4 distinct results," so this is correct; real-model distinctness comes from the 4 prompt framings.
- **No incident on click** — explicitly skip `create_incident_from_l4_output`; the investigate result is
  transient (no corpus write, no `pulse://stream/incidents` broadcast). This is the key behavioral boundary vs
  the digest→L4→incident path that shares `generate_constrained`.
- **Shared context helper** — factor `curated_context()` from `snapshot_runtime.rs` rather than duplicating the
  span-load/curate/format chain; keep the existing snapshot tests green (the extract is a refactor, not a
  behavior change).
- **bindings.ts staleness** — the regen-and-verify-staged-copy discipline is load-bearing here (new namespace);
  verify both `"investigate"` and `"mcp"` appear in the staged `index.ts` before commit.
- **Full button-click tauri-driver e2e** is the dedicated P-076 chunk (integration UX e2e); P-072's own
  acceptance is proven by the deterministic-L4 backend integration test + the webview DOM-flow unit tests.
