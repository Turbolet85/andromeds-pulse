## Goal
Make a sustained identical-fingerprint hard-signal storm yield **exactly ONE incident, reproducibly**. Phase-3
research falsified the intent's "elastic queue / TIER1_QUEUE_CAP=3 drops 75%" mechanism (the `LwwQueue` is a
dead side-channel — `drain_all` has zero production callers; the L4 feed is the broadcast). The real defect is
that the **triggering cue is never threaded cadence→digest**: `spawn_cadence_subscriber` calls
`assemble(mode, None, …)` (`pulse-app/src/digest_runtime.rs:125`), so a storm's Tier1 digest carries
`attention_cues == []`, and `create_incident_from_l4_output` (`inference_runtime.rs:648-654`) returns early —
**no incident is ever created from a storm.** This chunk threads the cue so the digest→L4→incident chain
completes, confirms the existing coalescing (storm one-shot, `pattern/storm.rs`) + incident dedup
(`inference_runtime.rs:661-682`) yield exactly one, and amends the falsified P-074 premise to reality. Per the
user dialogue at P4: fix the real bug, do NOT revive the queue or add a heartbeat-drain, and amend the
acceptance (not "0 dropped-by-cap" — that is premised on the dead queue and contradicts coalescing).

A hard constraint shapes the mechanism: `CadenceEvent` IS the `pulse://stream/cadence-events` L6-visibility
topic and is deliberately **PII-free** (chunk #80 carries a negative-canary test asserting `scope_id` never
appears in its JSON; per security-plan §Logging + the triage aggregate-only cardinality discipline). The cue
identity includes `scope_id`, so it MUST reach the assembler **off** that topic — never by adding `scope_id`
to `CadenceEvent`.

## Implementation Steps
1. **Deliver the triggering cue to the assembler off the L6 topic.** The cadence coordinator already holds the
   full `AttentionCue` (`run_one_coordinator_cycle(… , triggering_cue: Option<&AttentionCue>)`). Add a
   dedicated, non-L6 in-process carrier from the coordinator to the digest-assembly adapter that conveys the
   full cue for cue-triggered cycles (Tier1/Tier2), while the existing `pulse://stream/cadence-events`
   broadcast continues to emit **labels-only** for L6 visibility unchanged. Recommended shape (HOW is
   /implement's call): a `triage`-side trigger channel `{ mode, window-relevant timing, Option<AttentionCue> }`
   consumed by the digest adapter — keeping the cue (with `scope_id`) off the PII-free topic. Alternative: the
   digest adapter subscribes to the existing `pulse://stream/attention-cues` broadcast (which already carries
   full cues incl. `scope_id` as the product surface) and pairs it with the cadence trigger. Choose the path
   with the least correlation fragility; default to the dedicated carrier.
2. **Pass `Some(&cue)` into `assemble`.** `spawn_cadence_subscriber` (`pulse-app/src/digest_runtime.rs`)
   rebuilds the cue from the carrier and calls `assemble(mode, Some(&cue), …)`. The assembler already maps
   `triggering_cue → DigestCueRef { kind, priority_tier, summary, scope, scope_id }` into
   `Digest.attention_cues` (`assembler.rs:261-275`) — no assembler change needed beyond confirming the mapping.
3. **Confirm dedup → exactly ONE incident; close a gap only if the test exposes one.** Verify the chain:
   storm detector one-shots ~2 cues per fingerprint/window → cue-triggered digests carry the same
   `(kind, scope, scope_id)` → `create_incident_from_l4_output` creates on first, `observe_reemission`-dedups
   on subsequent. The L4 subscriber is a **single-consumer serial recv loop** (`spawn_l4_inference_subscriber`),
   so there is no create-race. The Suggested(Tier2) + Autonomous(Tier1) pair both resolve to the same identity
   → one incident (Tier2 may be skipped on cpu-primary; the Autonomous/Tier1 path is the guaranteed one). Only
   if the acceptance test proves a genuine duplicate/loss path does this step add a fix (still cheaper than a
   queue).
4. **Observability (minimal, aggregate-only).** Add a cue-threaded / coalesce counter only if it adds
   diagnostic value; reuse the `metric.pipeline.l3.*` family; never per-service identifiers; allowlist any new
   target in `pulse-app/src/observability.rs`. Most of the needed obs already exists.
5. **Amend the verification matrix P-074** (at P5.4): correct `requirement` / `observed_gap` / `acceptance` to
   the cue-passthrough reality + "exactly one incident, reproducibly"; set `chunk` to this marker; add a
   `notes` field recording the premise-correction.
6. **Flag the dead `LwwQueue` Tier1 path as a REMOVAL candidate** — a one-line note in the wrap report for a
   future cleanup chunk. Do NOT action removal here unless trivially safe; do NOT revive `drain_all`.
7. **Acceptance integration test** (new file): drive ≥100 identical-fingerprint occurrences through the real
   storm detector → cue → cadence → digest → **deterministic-L4 (`ANDROMEDA_PULSE_L4_DETERMINISTIC`)** path and
   assert exactly ONE incident in the registry, reproducibly across repeated runs. Plus triage unit tests for
   the cue carrier (incl. a PII negative-canary test proving the cue's `scope_id` still does NOT leak into the
   `pulse://stream/cadence-events` JSON).
