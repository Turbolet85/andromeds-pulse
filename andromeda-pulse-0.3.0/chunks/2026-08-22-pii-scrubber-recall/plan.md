## Goal

Close the bare-credential recall gap in the P-047 scrubber catalog — and prove it end-to-end at the stored
field, not at the regex. The catalog's four credential arms are all key-name-anchored (`api_key` requires the
`api[_-]?key|access[_-]?token|…` alternation before the value; `secret_kv` requires `password|passwd|secret|token`;
`bearer` requires the literal `bearer`; `jwt` keys on the `eyJ` header shape), so a standalone `sk_live_…` /
`sk-proj-…` provider token matches nothing (`crates/security/src/scrubber.rs:63–104`, verified at HEAD).

**This chunk is measure-first, and the measurement is mechanically enforced by the step order.** Research
established that the claim is precisely testable: the DuckDB schema has no generic attributes column, and every
client-controlled string that reaches it is either scrubbed through `scrub_otlp_field` (log body, exception
message, exception stacktrace, template content) or deliberately raw (`exception_type` — "class identifier, not
user content", `appender.rs:365–367`). So a bare key placed in a log body **does** pass through
`scrub_attribute`; if it lands verbatim in DuckDB, the defect is unambiguously catalog recall with boundary
coverage already proven. Step 1 writes the post-fix assertion and runs it **before** any catalog change: its
failure output IS the measurement. If it passes cold, the premise is corrected, the catalog change is dropped,
and the chunk reports that instead (per security-plan §Security Anti-Patterns → Logging, which states the
coverage invariant but says nothing about the catalog's recall).

The chunk also lands CARRY #10 (operator-selected at P4): a tick-aggregated redaction counter on the buffer
path, making P-047 gradeable from outside the process — the same shape this project used at
2026-08-14-fingerprint-feed-capture-repair (per obs-plan §5 tick-aggregated row + §8 default-deny posture).

**The recall-vs-false-positive tension is DECIDED: anchored-prefix + length floor, not entropy scoring.**
Leaned per obs-plan §8 (which names the exact shape family `sk-[a-zA-Z0-9]{40,}` · `ghp_[a-zA-Z0-9]{36}` ·
`AKIA[0-9A-Z]{16}` · `Bearer [a-zA-Z0-9]{40,}` · `password=[^\s]+` and warns that over-broad patterns
false-positive) and per the catalog's own stated posture at `scrubber.rs:55–58` ("recall over precision — false
positives are acceptable (over-redaction); false negatives leak secrets"). Honest qualifier recorded in scope:
the obs §8 passage was authored for grep-based CI heuristics, not the runtime catalog, so it supplies a named
shape vocabulary and a strong analogical lean rather than a direct mandate. Entropy/length-only scoring is
rejected below.

## Implementation notes
- **Two batch builders, one counter — resolve explicitly.** `scrub_otlp_field` is called from the log-record
  body path (`appender.rs:291`, inside `extract_log_body`) and the span-event exception path (`:368`–`:369`),
  which are built by different functions, while the `record_feed_counts` fold sits at `:411` on the spans path.
  The counter must either be folded from **both** paths or have its coverage stated honestly in the field's doc
  comment. Do not let it silently count one path and read as if it counted all — that is the same
  "passes for the wrong reason" class this project has hit repeatedly.
