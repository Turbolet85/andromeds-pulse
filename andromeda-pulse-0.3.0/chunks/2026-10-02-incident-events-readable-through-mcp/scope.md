## What it builds
- An MCP read surface over the corpus `incident_events` table: an incident's lifecycle events (the rows `CorpusWriter::update_incident_status` records on every status VALUE change, inside the guarded transaction — `event_kind` = the new status label, `occurred_unix_nano`, an empty encrypted payload) become readable through the `andromeda-pulse-mcp` stdio sidecar for a named incident.
- The surface shape is open at scope time: a NEW MCP tool (a ninth tool beside the eight at `crates/mcp-server/src/tools.rs:45-62`) or a widening of an existing incident tool's response. `query_incident_list` lists ACTIVE incidents only, so it can never show a resolved incident's `resolved` event; Conductor's readiness gate pins required tools against a contract manifest (Conductor `.andromeda/architecture.md:93`). P4 resolves the fork (a contestable lean → AskUserQuestion). The founder ruling 2026-10-02 (relayed by the pc overseer) fixes THAT the events become MCP-readable in 0.3.0, not the tool shape.
- [premise-corrected: research.md §Files inspected — `CorpusReader` carries only `inspect`/`path` (`contract.rs:186-192`); every incident read the sidecar performs is a `CorpusWriter` method and `IncidentToolContext` binds `Arc<dyn CorpusWriter>` (`tools.rs:70-74`)] A corpus read path for the events: the only `SELECT … FROM incident_events` today is the test helper `event_kinds` inside `#[cfg(test)]` (`contract.rs:1404-1416`) — no production reader exists. The read lands beside its sibling incident reads (`load_incident_by_id` et al.) on the `CorpusWriter` surface the sidecar already binds, NOT on `CorpusReader`; one impl (`Corpus`, `contract.rs:464`), no mock implements the trait, no new crate edge (`mcp-server → corpus` exists).
- The read is bounded and honest: the events of ONE incident, oldest first (`ORDER BY id`), with a bounded count; `event_kind` is a closed status-label set — every production writer passes a `triage` `status_label` value (`active` / `acknowledged` / `resolved`), and a value outside it is coerced to a sentinel on egress, never passed through. [premise-corrected: the payload is empty by construction (`cell_encrypt(key, &[])`, `contract.rs` `update_incident_status`) and carries no information, so the read does not SELECT the payload column at all — nothing to decrypt, no ciphertext reachable] An unknown incident id reuses `load_incident_row`'s existence check and returns the same `"incident not found"` error (JSON-RPC -32603) as `retrieve_report`.

## Boundaries
- The sidecar's double gate holds: compile-time `--features mcp-server` AND runtime `ANDROMEDA_PULSE_MCP_ENABLED=true` (security.md §MCP feature double-gate).
- MCP tool response bodies are NEVER logged (CLAUDE.md Critical Warnings); the new read's tracing carries a bounded result count and type label only (the `result_type_label` / `result_count_for` pattern at `tools.rs:562/576`).
- MCP errors stay standard JSON-RPC 2.0 error objects with sanitized messages (`short_reason`).
- No TauRPC procedure, port, capability JSON or webview change is in scope — the surface is the stdio sidecar only.
- No corpus schema change: `incident_events` already exists (SCHEMA_VERSION 2, `schema.rs:69-77`) and has a production writer since chunk 2026-08-30-diagnostics-un-muting-harness-truth-sweep. Measured: an incident's CREATION records NO event — `save_incident` inserts the incident row only, and `status_value_change_records_one_lifecycle_event_per_transition` pins an empty event list right after it (`contract.rs:1419-1440`). The read surface therefore shows status transitions only; an incident read before its first transition has zero events, so P-075's events assertion is non-vacuous only AFTER a transition (the round's `mark_incident_resolved` produces exactly one `resolved` event). Whether to also record an opening event is a P4 fork.
- The incident tools read an id without a workspace filter (`load_incident_by_id`, used unfiltered by `retrieve_report` / `retrieve_telemetry_slice` / `mark_incident_resolved`); the events read follows the same posture.
