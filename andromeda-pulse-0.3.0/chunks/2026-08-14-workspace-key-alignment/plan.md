## Goal

The MCP sidecar filters incidents by a workspace key it derives as `data_dir.to_string_lossy()`
(`crates/mcp-server/src/bin/andromeda-pulse-mcp.rs:74`), while the app stamps and filters by the
**detected project root** since P-079 (`pulse-app/src/digest_runtime.rs:109`). The sidecar's own comment
still asserts parity with the app — a claim that was true before P-079 and is stale now. Consequence:
`query_incident_list` returns zero rows against a corpus that holds active incidents, which is the
false-pass-as-empty condition Conductor's arm reports.

Research corrected the obvious fix. Both processes' `resolve_data_dir()` are byte-identical raw
`PathBuf::from(env)` copies, so the **fallback** branch already agrees cross-process; only the
detected-root branch diverges, where the sidecar never calls `detect` at all. And simply calling
`detect(current_dir())` in the sidecar does **not** fix Conductor's arm: Conductor spawns the sidecar
with `ANDROMEDA_PULSE_DATA_DIR` propagated but **not** cwd, so the sidecar's cwd is Conductor's own repo
root — a different wrong key. The one value both sides already agree on is the data dir, which
Conductor's contract mandates propagating. So the app **publishes** its resolved key under the data dir
at boot and the sidecar **reads** it, falling back to `data_dir` when absent (operator-selected at P4).
The derivation itself still moves down into `workspace-detector` — a leaf crate with zero outbound
workspace edges and no edge either way with `mcp-server` today, so the new `mcp-server →
workspace-detector` edge cannot form a cycle (`pulse-app` depends on `mcp-server`, which is what closes
the naive import direction).

Per architecture.md §Cross-cutting Patterns (Module dependency direction) + §Established Decisions
[Module Boundaries] for the crate home, security-plan §Input Validation (CLI / env var inputs) for the
published-file boundary, obs-plan §8 (default-deny allowlist) + the chunk-#43 `workspace.detect`
basename-only precedent for any emission, and test-plan §3 (per-chunk gate discipline + boot-smoke) for
the gates.

## Implementation Steps

1. **Host the shared derivation in `workspace-detector`.** Add the workspace-key derivation to that
   crate's contract surface: given `Option<&WorkspaceContext>` and the data dir, return the key string
   and the canonical-path value the producer stamps — preserving the P-079 single-call shape so filter
   and stamp cannot drift. Do **not** re-canonicalize: `detect` already canonicalizes exactly once and
   the key is that output verbatim (see §Constraints).

2. **Add the normalization unit.** Co-located `#[cfg(test)] mod tests` in `workspace-detector` (a
   library crate, so co-located tests do run). Assert that two *entry forms* of the same directory —
   a raw path and its `\\?\` verbatim-prefixed form — reach **one** key through the single
   `canonicalize()` inside `detect`, and that the fallback branch yields `data_dir` on both halves.
   This closes the Windows verbatim-prefix question by construction rather than by observation on one
   host.

3. **Delegate the app side.** `pulse-app/src/digest_runtime.rs::resolve_workspace_for_incidents`
   delegates to the shared derivation (keeping its name and signature so the 7 existing callers and the
   P-079 contract are untouched in meaning).

4. **Publish the resolved key.** At boot, after the key is resolved (`pulse-app/src/main.rs` ~line 691),
   write it to a small file under the data dir using the atomic `.tmp`-then-rename discipline already
   used for `window-geometry.json`. Write failure is non-fatal — log a warn and continue; the sidecar's
   fallback covers it. Follow the existing `write_pid_file` shape (`pulse-app/src/main.rs:204`), which
   already creates `{data_dir}/run/`.

5. **Read it in the sidecar.** `init_incident_context` reads the published key and uses it as
   `workspace_root`, falling back to `data_dir.to_string_lossy()` when the file is absent or unreadable
   — which preserves today's behaviour exactly for a sidecar running without a live app. Delete the
   stale parity comment at lines 70–73 and replace it with one that states the real contract. Add the
   `workspace-detector` path dependency to `crates/mcp-server/Cargo.toml` if the read helper lives
   there; if the helper is a plain file read, the dependency is still needed for step 1's shared
   derivation to be callable from this crate.

6. **Observe before the fix lands.** Produce the before-evidence: seed a data dir with incidents
   (`cargo run -p ingest --example inject_demo` against a running app — ~10s warmup, then the storm
   crosses the Autonomous threshold in ~1s), then drive `query_incident_list` over the sidecar's stdio
   (both gates set — see the firing form on the `(evidence)` criteria) and record **two** numbers
   together in `evidence/before-query-incident-list.json`: the tool's `total` (expected `0`) and an
   independent read of the same corpus's incident count (expected non-zero). Both numbers are needed —
   `total: 0` alone is indistinguishable from "no incidents were created". Record **counts only**, never
   response bodies (obs-plan §11 Project-specific, Vector 4). This capture cannot survive the fix, so
   the permanent guard is step 7.

6b. **Re-run the same query after the fix.** With steps 3–5 landed, re-issue the **identical**
   invocation against the **identical** data dir and record `evidence/after-query-incident-list.json`.
   The `0 → N` pair across one unchanged command is the chunk's outcome evidence. Keep the capture data
   dir for this — recreating it changes the workspace key and voids the comparison.

7. **Add the permanent parity regression.** A test that asserts the app-published key and the
   sidecar-read key are byte-equal for a detected workspace — the assertion that survives the fix and
   fails if either side drifts again. Place it per the test-home rule: `pulse-app/tests/*.rs` if it
   reaches pulse-app internals, co-located in the library crate otherwise.

8. **Run the Conductor arm-zero leg (operator-scheduled).** With the new `buffer.tick` feed counters,
   one Conductor arm re-run names the second open mystery on sight: `span_events_seen=0` → nothing
   reached the appender; `fingerprints_computed=0` with `span_events_seen>0` → attributes lost in
   ingest; `observer_invocations=0` with `fingerprints_computed>0` → wiring. Conductor is the
   instrument: run its preflight from its own repo root, launch `pulse-app` outside that repo, and land
   **all** evidence in this chunk's folder as `evidence/arm-zero-classification.md`. Never write into
   Conductor's tree. If the arm no longer reproduces (this chunk's fix being the plausible cause),
   record that verbatim as the classification — a non-reproducing arm is a result, not a skip.
