# Scope — Corpus key creation is race-free

**Marker:** `2026-10-04-corpus-key-creation-is-race-free` · **Version:** andromeda-pulse-0.3.0 · **Epoch:** Epoch 4 — Polish & ship: verification

**Working entry (verbatim title + hint):** Corpus key creation is race-free — concurrent first-run processes end up sharing one corpus key

## What it builds
- First-ever corpus key creation in `OsKeychainBackend::fetch_from_os_store` (`crates/corpus/src/keychain.rs:155-172`) becomes a **locked create-or-read**, as the founder ruled on 2026-10-04. Today the function calls `entry.get_password()` and, on `keyring::Error::NoEntry`, generates a random key and calls `entry.set_password(...)` with no compare-and-set. Each concurrent first-run process that sees `NoEntry` mints its own key, and the last write wins.
- The outcome: when N processes resolve the corpus key concurrently against an EMPTY credential store, every one of them ends with the SAME 32-byte key, and that key is the one the store holds afterwards. No process returns a key the store no longer holds.
- The lock has to work ACROSS processes (the measured case is concurrent test processes; the production case is a first-boot app plus its MCP sidecar). An in-process `Mutex` alone cannot close it. An exclusive `std::fs::File::lock` held across get → (generate → set) → read-back closes it: the API is stable on the pinned 1.95.0, and a second handle on the same path is excluded even in the same process (research.md §Measured, `lockprobe.rs`).
- After the set, the key the process returns is the key read back from the store (or is verified equal to it), so a write that still lost a race the lock did not cover can never hand back a key the store does not hold. `get_password` after `set_password` is available on the same `keyring::Entry` (`keychain.rs:156-166`).
- [premise-corrected: the race is keyed on the credential ENTRY `(com.andromeda.pulse, corpus-key)`, one per OS user, not on the data dir — every cross-process test leg opens that one entry from a DIFFERENT per-test data dir, and the measured symptom came from exactly such processes (research.md §Measured)] The lock's location must be a function of the credential entry for the outcome above to hold for ALL concurrent first-run processes. A lock under the resolved data dir closes only processes that resolve the same data dir (the default app + sidecar pair) and leaves the measured case open. `OsKeychainBackend::new(service)` already holds the entry identity (service, plus the `service_id` passed per call), so a per-entry lock needs no new constructor input and no change at the construction sites (`pulse-app/src/main.rs:340`, `crates/mcp-server/src/bin/andromeda-pulse-mcp.rs:66`). Where the lock file lives (per-user location vs the data dir) is P4's fork (research.md §Open questions).
- A witness that reproduces the race and goes RED on HEAD's get-then-set: several real processes (or a barrier-synchronized set) resolving a key against one shared, initially empty store must agree on one key. It must not pass vacuously: if the platform store is absent, the witness either skips with a `[skip]` line or runs against a store the test controls; it never reads as a green.
- The passphrase fallback (`resolve_key`, `ANDROMEDA_PULSE_CORPUS_PASSPHRASE`; `derive_key_from_passphrase`, `keychain.rs:241`) is deterministic (BLAKE3-derived) and so has no create race. It stays as it is. The lock covers only the OS-store creation path.

## Boundaries
- No change to the key format (`encode_key` / `decode_key`, 32 bytes hex), the service / account naming, the cell-level AES-256-GCM scheme, the corpus schema or `SCHEMA_VERSION`.
- The fail-closed posture stays: a transient store failure with no passphrase configured still surfaces the store's error and never invents a key (doc comment on `OsKeychainBackend`). A lock that cannot be acquired is a failure, not a reason to fall through to an unlocked create.
- `corpus::disposition` (the boot-time inventory-then-purge of rows orphaned under a lost key) is untouched. This chunk prevents NEW orphaning at creation; it does not change how existing orphans are retired.
- Logging: no key material, no full path (a lock-file path, if one is added, is logged by basename only, per `.claude/rules/security.md` §Logging & redaction).
- Path discipline: a lock-file directory taken from any environment variable (a data dir, or a per-user runtime/temp dir) is canonicalized before use and asserted to be a directory. The lock file holds no content. No new `ANDROMEDA_PULSE_*_PATH` var is introduced unless P4 finds one necessary.
- No TauRPC procedure, port, capability JSON, webview or MCP tool change. Workspace deps: none — `std` file locking on the pinned 1.95.0, and `blake3` (already a `corpus` dep) if the lock name hashes the entry identity (research.md §Files inspected).
