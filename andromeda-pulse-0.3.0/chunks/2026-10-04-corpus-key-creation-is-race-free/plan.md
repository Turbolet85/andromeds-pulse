## Goal
The first-ever corpus key is created by a get → generate → set sequence with no compare-and-set (`crates/corpus/src/keychain.rs:155-172`). Concurrent first-run processes each mint and store their own key, and the last write wins. Measured at HEAD (research.md §Measured): in 5 of 5 rounds, 8 concurrent children against one empty test-scoped entry minted 8 distinct keys, and 7 of the 8 returned a key the store no longer held. A process that encrypts rows under such a key hands its peers undecryptable rows. The 2026-10-02 MCP leg read them as `incident not found`, and the boot disposition retires them as orphans.

This chunk makes creation a **locked create-or-read**, per the founder ruling of 2026-10-04 (fix it with a locked create-or-read):
- `OsKeychainBackend` takes an exclusive `std::fs::File::lock` on a lock file whose name is a function of the credential entry. The name embeds the first 16 hex characters of BLAKE3 over service + account.
- The lock file lives in a per-user directory: `$XDG_RUNTIME_DIR` on Linux, `std::env::temp_dir()` elsewhere.
- Under the lock the process gets the entry. On `NoEntry` it generates, sets, and **reads back**. It returns the key the store holds, then unlocks.

Every concurrent first-run process therefore ends on one key, the one the store holds afterwards. The lock covers separate processes and threads in one process alike: `File::lock` excludes a second handle on the same path, measured on rustc 1.95.0 (research.md §Measured).

The lock location is a **boundary widening the founder ratified live on 2026-10-04 (relayed by the overseer)**. It is a second product-written artifact outside the resolved data dir, after the `~/Downloads` export sink. The location is keyed to the credential entry because research falsified the data-dir premise. The race is keyed on the ONE per-user credential entry `(com.andromeda.pulse, corpus-key)`, and the measured symptom came from processes with DIFFERENT data dirs. A data-dir lock would have left that case open.

The change is confined to `crates/corpus/src/keychain.rs`:
- The constructor, the `KeychainBackend` trait, the `Corpus::open` mapping (any `KeychainError` → `Error::KeyringUnavailable`) and both construction sites (`pulse-app/src/main.rs:340`, `crates/mcp-server/src/bin/andromeda-pulse-mcp.rs:66`) are unchanged.
- The fail-closed custody posture holds (per security-plan §Secret Management → Runtime; architecture §Occupied Resources → Corpus SQLite → At-rest posture).
- Lock failure surfaces through the existing boot records (`corpus.open.error` in the app, `mcp.boot.corpus.init` in the sidecar). No new log target is added (per obs-plan §8 corpus leaves).

2. **Locked create-or-read in `fetch_from_os_store`** (`keychain.rs:155`):
   - Resolve the lock path (Step 1) BEFORE any keyring call.
   - Open the lock file: create, write, no truncate; on Unix mode `0o600` via `std::os::unix::fs::OpenOptionsExt`. Take `File::lock()` (exclusive, blocking).
   - Under the lock: `get_password` → `Ok` decodes and returns. `NoEntry` → `generate_random_key` → `set_password` → `get_password` again, return the READ-BACK decoded key. A read-back that fails or does not decode → `Err(KeychainError::Failed)`.
   - Release the lock explicitly (`unlock`) before returning on every arm. Drop also releases it.
   - Failures map into the existing unit variants: lock-dir resolution failure → `Unavailable`; open or lock failure → `Failed`. They carry no path, no key bytes and no `Display` of an OS error.
   - The lock file is never deleted by the product: deleting it after unlock would let a later opener lock a different inode than a waiter. It holds no content.
   - `resolve_key` is unchanged. A lock failure is a store-side `Err`, so it degrades exactly like an unreachable store: the passphrase fallback only when configured, otherwise the error. That keeps the fail-closed side (security-plan §Secret Management → Runtime). No unlocked generate-and-set path remains.

## Constraints & rejected approaches
- A lock under the resolved data dir — rejected by founder ruling 2026-10-04. The race is keyed on the per-user credential entry, and processes with different data dirs (the measured case) would stay racy.
- An in-process `Mutex` / `OnceLock` alone — rejected: the topology has at least two processes on one entry (arch extract anti-pattern).
- Read-back alone, with no lock (set, then adopt whatever the store holds) — rejected: a process may already have returned and used its own key before a later writer overwrote it, so it only narrows the window. Measured: 7 of 8 returned a key the store no longer held.
- Falling through to an unlocked generate-and-set, or to an ephemeral per-process key, on a lock failure — banned. It reproduces the orphaning (security-plan §Secret Management → Runtime). A lock failure is a store-side `Err` and nothing else.
- A third-party file-lock crate — not needed. `std::fs::File::lock` is stable on the pinned 1.95.0 and its exclusion was measured (research.md §Measured).
- Deleting the lock file after use — rejected: it creates a new-inode race between a waiter and a later opener. The file is content-free and persistent.
- Running the MCP legs against a FRESH production entry — rejected as destructive. Deleting `com.andromeda.pulse/corpus-key` would orphan the operator's real corpus. The fresh-store concurrency claim is proven by the test-scoped witness instead, and the MCP legs run as a regression check with the entry present.
- Changing `OsKeychainBackend::new`, the trait, or the construction sites — unnecessary. The backend already holds the entry identity (service plus the per-call account).

## Implementation notes
- **Residuals (durable form, not confined by any mechanism):**
  - (1) Two processes of one user that disagree on Linux `XDG_RUNTIME_DIR` (one set, one unset) take different lock files, so their first creation is not serialized. This was measured under a systemd user session only; exposure elsewhere is unmeasured. Owner: the wrap's residual record.
  - (2) The Linux `temp_dir` fallback is the shared `/tmp`. Another local user could pre-create the lock name and make first creation fail closed (denial only; the file carries no content, and the lock opens without truncate). This is accepted under the Minimal tier's single-user trust boundary.
  - (3) With `ANDROMEDA_PULSE_CORPUS_PASSPHRASE` configured, a lock failure degrades to the passphrase key exactly as an unreachable store already does. That is the existing opt-in posture, unchanged.
