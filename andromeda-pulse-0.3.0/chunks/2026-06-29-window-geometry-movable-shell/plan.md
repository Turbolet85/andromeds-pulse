## Goal
Make Pulse open as a properly-placed, movable shell. The live dogfood (intent F1) reported the window
"opens tiny, pinned to the top-left corner, cannot be moved." Research **corrects the intent's stated
mechanism**: the custom frameless titlebar's `data-tauri-drag-region` markup has existed since chunk #24
(`Titlebar.tsx`, rendered by `CompactWidget.tsx:55`) — so we are NOT building a drag region. The real defect is
that `pulse-app/capabilities/default.json` grants only `["core:default","updater:default"]`, and Tauri 2's
`core:window:default` (inside `core:default`) is **read-only getters + `allow-internal-toggle-maximize` only** —
it omits `core:window:allow-start-dragging`. So the existing drag region's `startDragging()` IPC is **silently
rejected** (this project's negative-default model, CLAUDE.md §Critical Warnings; Tauri's "Window Customization"
guide names exactly this permission). The same root cause silently breaks the titlebar's minimize / maximize
buttons (`use-window-controls.ts:17-18` call `allow-minimize` / `allow-toggle-maximize`, also absent).

This chunk (a) grants the window permissions a frameless custom-titlebar app needs — `allow-start-dragging`
(F1 movability) plus `allow-minimize` + `allow-toggle-maximize` (the orphaned, same-root-cause titlebar
controls; user-chosen in-chunk fix; `close` is left to P-063); (b) gives the dashboard a sane default via
`"center": true` and hardens the compact-widget's existing TopRight corner-snap so a monitor-unavailable snap
no longer silently lands at the OS top-left; and (c) adds **remembered free position** — capture each window's
post-drag position and restore it at boot, falling back to center/snap when none is stored. Per arch
§Cross-cutting "Webview IPC capability policy" the capability addition carries a stated rationale; per
layout-templates §Custom titlebar + design-system §Custom titlebar the titlebar stays a drag region with
interactive controls clickable; per a11y-plan §6 the window-control buttons keep their ≥24px target + names.

3. **Harden the compact-widget snap fallback.** In `pulse-app/src/window.rs::apply_widget_settings`, the

4. **Remembered free position — capture + restore (Rust-side; NO new capability).**

     `Settings` struct + `update_settings` form path** (see Implementation notes — avoids the form-clobber
     bug and keeps the TauRPC `Settings`/bindings contract unchanged). Shape: optional `(x:i32, y:i32)` per

     `SettingsModalForm` (the fallback — folding into `Settings` — is acceptable only if the form provably
     round-trips unedited fields; integer-only either way, per the `Settings` `Eq` derive / 2026-05-19).
   - **Restore at boot:** after window show, if a remembered position exists for a window, apply it via the
     Rust-side `window.set_position(...)` (same pattern as the existing snap in `window.rs`); else fall back
     to center (`main`) / corner-snap (`compact-widget`). Rust-side `set_position` needs **no** capability
     (capabilities gate only webview JS → core IPC).
   - **Capture moves:** extend `pulse-app/src/window.rs::on_window_event` (`@ main.rs:1012`, single caller) to

     `handle_close_to_tray` path) so the chatty per-pixel Moved stream does not hammer the config file.

5. **Tests + gates.** Add runnable unit coverage in `pulse-app/tests/*.rs` (NOT pulse-app source `mod tests`

## Implementation notes
- **Premise correction (do NOT re-add the drag region):** `Titlebar.tsx` already carries
  `data-tauri-drag-region` (chunk #24); the fix is the capability grant, not new markup. Re-adding it would be
  duplicative. Record this premise correction in the wrap report (the intent's "build a drag region" mechanism
  was falsified; outcome — a movable shell — is unchanged).
- **`allow-set-position` is NOT required** (refines the Q1 preview): remembered-position restore runs Rust-side
  at boot via `window.set_position`; capabilities gate only webview JS → core IPC, so the capability surface is
  exactly the Q2 three. This is a simplification in the user's favor — surfaced at P5 review.
- **Avoid the Settings-form clobber bug** (refines the Q1 preview's "Settings += win_x/win_y"): if remembered
  geometry lived in the webview `Settings` struct, an `update_settings` from `SettingsModalForm` that omits the
  geometry fields would reset them to default on every Save (the form doesn't edit geometry). Recommended:
  keep remembered geometry as Rust-owned persisted state separate from the webview `Settings` contract (zero
  bindings churn, no clobber). /implement reads `SettingsModalForm` and confirms; the Settings-field fallback
  is allowed only if the form provably preserves unedited fields.
- **Debounce Moved persistence** — `WindowEvent::Moved` fires continuously during a drag; capture latest
  in-memory and flush on close-to-tray / a debounce, never per-event file writes.
