## Patterns detected
- **One shared append helper for every table** (`appender.rs:535-556`): `append_record_batch_to_table` does `conn.appender(table)` → `append_record_batch` → **`flush()`**, each arm mapping to `Error::Append`. `append_table_traced` (`consumer.rs:176`) wraps it. `metrics_points` uses the identical helper as `spans` / `log_records` — so the sibling's flush-time enforcement finding transfers by construction, not by analogy.
- **Whole-batch rejection surfaces as one constant-valued ERROR** (`consumer.rs:78-83`): `dispatch_batch`'s `?` propagates out, the loop's `Ok(Err(e))` arm emits `tracing::error!(target: "duckdb.append", reject_reason = %describe_error(&e), "appender returned error")`. `record_rows_appended` (`consumer.rs:161`) sits *after* the append inside `dispatch_batch`, so it is skipped on rejection.
- **`describe_error` is a closed 10-arm match returning `&'static str`** (`consumer.rs:259-271`) — `Error::Append` becomes the literal `"append_failed"`. The `Error::Append.reason` string (which does carry `flush(metrics_points): …` truncated to 120 chars by `short_err`, `appender.rs:808`) is **never emitted to the sink**.
- **The metric name is scrubbed once per metric, above the point loop** (`appender.rs:160-163`), with an in-code comment stating why: every point of one metric shares the name. So the redacted-name collision needs **two distinct metrics**, not two points.
- **Metric-point attributes are never read** (`appender.rs:764-779`): `push_metric_row` takes `name, ts_ns, resource_hash, value, kind` and nothing else. Every `.attributes` access in the file is resource-level (`:133`, `:786`, `:800`) or span-event exception (`:403-407`).
- **The sibling's test shape** (`schema.rs:360` + `appender.rs:1364`): the key contract asserted via `information_schema.key_column_usage`, and the behavioural collision test run on a worker thread under `recv_timeout(30s)` so the documented libduckdb hang (`schema.rs:311-318`) fails rather than wedges.
- **The fixture-side ordinal precedent** (`viz/query.rs:509-513`): a `static SEED_LOG_SEQ: AtomicI64` + `next_log_seq()`, sitting immediately above `seed_metric_full` (`:516`).
- **The Metrics view's error-before-empty order is correct but cannot see this failure** (`pulse-app/ui/src/dashboard/routes/MetricsRoute.tsx`): it branches `error !== null` → `"Couldn't load metrics"` **before** `!isLoading && rows.length === 0` → `"No metrics received yet"` + the `:4318`/`:4317` exporter hint, satisfying layout-templates §Component — Empty / error state. But `error` is the **query** error from `useMetrics`; a batch rejected at `flush()` is not a query failure — the query succeeds and returns zero rows. So a collision **already** renders as the exporter-hint empty state, telling the user to point an exporter at a port they are already using successfully. Answers the layouts extract's research question: the rule is satisfied, and it is structurally unable to help, because no rejection signal reaches the frontend.

## Conventions to follow
- **A PK edit must land in both `schema.rs` representations**: `ddl_constants_match_concatenated_schema` (`crates/buffer/src/schema.rs:420`) asserts `SCHEMA_DDL` equals the concatenation of the table consts. One-sided edits go red.
- **The third DDL site is structurally unguarded**: `crates/viz/src/query.rs:481` is an independent copy — `viz`'s dependency set (`crates/viz/Cargo.toml:9-17`: thiserror, tokio, tracing, tracing-error, duckdb, serde, specta, chrono) contains **no `buffer`**, so it cannot import the DDL and nothing cross-checks it. Grep for `SCHEMA_DDL|schema::` in `viz/query.rs` returns zero.
- **Every production reader names its columns**: `SELECT_METRICS` (`viz/query.rs:25`) selects `metric_name, ts_unix_nano, resource_hash, value, data_point_kind`; `COUNT_METRICS` (`:37`) and the retention `DELETE` (`crates/buffer/src/retention.rs:26`) key on `ts_unix_nano` alone. An added ordinal column is invisible to all of them.
- **Both `viz` fixture INSERTs name their columns** (`:526` all six, `:608` four with the defaulted pair omitted) — a `NOT NULL` `seq` with no DEFAULT breaks both, exactly as it did for logs, and the fix is the adjacent `next_log_seq` pattern.
