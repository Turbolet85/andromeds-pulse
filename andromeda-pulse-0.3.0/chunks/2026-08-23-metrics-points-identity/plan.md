## Goal

`metrics_points` is keyed on `(metric_name, ts_unix_nano, resource_hash)` and stores no attributes column,
so two data points of one metric differing only by label set are byte-identical on every key column. Since
`2026-08-23-ingestion-scrub-coverage` a second source exists: the metric name is scrubbed once per metric
(`crates/buffer/src/appender.rs:163`), so two *distinct* credential-shaped names redact to one placeholder
and collide at the same tick and resource. Both pairs fail the **whole batch** at `flush()` — the Arrow
`Appender` enforces the key, `dispatch_batch`'s `?` propagates, and the consumer emits one constant-valued
`duckdb.append` ERROR with `record_rows_appended` skipped (`crates/buffer/src/consumer.rs:78-83`, `:161`).

This chunk closes both with the ordinal shape the sibling `log_records` chunk proved — a buffer-global
monotonic `seq` reserved once per batch, added to the key — per architecture.md §Conventions → Primary key
convention, which names `seq` as *the one declared exception* to the no-surrogate-keys rule and explicitly
REJECTS a per-batch-resetting `event_index`-style ordinal for a table with no unique parent. `metrics_points`
has no such parent, so the rejection applies here identically.

Two decisions were taken with the operator at P4 and bind the scope. **The label half CARRIES.** The entry's
title asks for survival "with their labels", and research confirmed the identity half is fully separable —
the ordinal closes both collisions without ever reading `p.attributes`, which `push_metric_row`
(`appender.rs:764`) never does. Choosing a representation touches arch §Occupied Resources, the `viz`
response shape and security's scrub remit; it is a co-equal second feature, not a fix, and the arch extract
warns a producer-less side table would reproduce an already-named defect class. **The `redactions_applied`
fold moves in-chunk.** Research measured that `state.record_redactions(…)` fires *inside* all four builders
(`appender.rs:73`, `:184`, `:273`, `:468`) — before the append can fail — so a rejected batch counts cells
that never persisted, contradicting obs-plan §5's persisted-cells-only rule. This chunk is where that is
discovered and where the harness to prove it exists, so it is fixed here rather than deferred.

## Implementation Steps

**Sequencing is load-bearing: the RED measurement runs at HEAD, before any fix.** It must capture BOTH
observed facts — the whole-batch rejection AND the redaction over-count — because step 2 removes the second
one, and a RED leg run after the fix can no longer witness it.

1. **Build the live-leg producer.** New `crates/ingest/examples/inject_colliding_metrics.rs`, modelled on
   the sibling's `inject_colliding_logs.rs` (98 lines). It emits, over gRPC `:4317`, both pairs in a single
   export: (a) two Gauge data points of ONE metric sharing `time_unix_nano` and resource, differing only by
   their `attributes` label set, with distinguishable non-credential values; (b) two DISTINCT metric names
   of `provider_key` anchored-prefix shape that redact to the same placeholder, at the same
   `ts_unix_nano` + resource. Include a control pair that must never collide, so the GREEN leg proves
   selectivity rather than blanket survival. Build it OUTSIDE any timed section and invoke the binary by
   path — a `cargo run` inside a timeout spends the budget compiling and sends nothing (the sibling's
   module docs record this).

2. **RED measurement at HEAD.** Boot the binary directly against a fresh `ANDROMEDA_PULSE_DATA_DIR`
   (test-plan §3 Direct-binary smoke variant), run the producer, then read the run's own artifacts and
   record: zero metric rows readable through the `metrics.*` query router, `rows_ingested` not advancing
   for the batch, a `duckdb.append` ERROR carrying `reject_reason: "append_failed"`, and
   `redactions_applied` having advanced despite nothing persisting. **This leg deliberately produces an
   ERROR line** — see Constraints for how that is reconciled with the smoke variant's clean-log assertion.

3. **Move the redaction fold to the persist site (all four builders).** Have each builder RETURN its
   redaction count alongside its `RecordBatch` instead of folding it internally (a small named struct or a
   tuple — /implement's call), and call `state.record_redactions(…)` at each append site immediately after
   THAT table's own `append_table_traced(…)` succeeds. Per-table granularity matters: in the spans arm
   `spans` and `span_events` append separately under one guard, so a `span_events` failure must not discard
   the count for rows `spans` already persisted. **Preserve the existing empty-batch behaviour** — the
   metrics builder returns `Ok(None)` before folding when no rows were produced (`appender.rs:180-184`),
   which is already correct under the persisted-cells rule. Update the `#[cfg(test)]` wrappers
   (`append_spans_batch` `:564`, `append_metrics_batch` `:585`, `append_logs_batch` `:608`) and the existing
   pin `redaction_counter_folds_once_per_batch_across_all_four_builders` (`:1212`). Also refresh the now-stale
   `redactions_applied` doc comment on `BufferState` (`crates/buffer/src/state.rs:25-29`), which still names
   only the three log-side scrub sites.

4. **Add the metrics ordinal allocator.** A dedicated `metric_seq: AtomicU64` beside `log_seq`
   (`state.rs:32`) with a `reserve_metric_seq_block(n)` mirroring `reserve_log_seq_block` (`:124`).
   *Leaned dedicated-per-table rather than one shared counter, per architecture.md §Conventions → Primary
   key convention, which frames `seq` as a per-table ordinal; a shared counter would couple two tables'
   allocation for no gain.* It must stay **non-observable**: absent from `BufferStateSnapshot`,
   `buffer.tick`, and every read path.

5. **Thread the ordinal through the metrics builder.** In `build_metrics_record_batch`
   (`appender.rs:144-215`) reserve ONE block per batch, add `seq` to the Arrow `Schema` and the builder
   vectors. `collect_metric_points` (`:658`) and `push_metric_row` (`:764`) carry it through — the graph
   shows **five** `push_metric_row` call sites (`:671, 688, 705, 722, 739`), one per OTLP data shape
   (Gauge / Sum / Histogram / ExponentialHistogram / Summary); all five thread.

6. **Change the key in all three DDL representations.** `crates/buffer/src/schema.rs:70-78` (const) and
   `:167-175` (live `SCHEMA_DDL`) — these are pinned to each other by
   `ddl_constants_match_concatenated_schema` (`:420`), so a one-sided edit goes red. The third,
   `crates/viz/src/query.rs:481-489`, is an **independent copy with no guard**: `viz` does not depend on
   `buffer` (`crates/viz/Cargo.toml:9-17`), so nothing cross-checks it. Edit it by hand and add
   `next_metric_seq()` + a `SEED_METRIC_SEQ` static mirroring `next_log_seq` (`viz/query.rs:509-513`), then
   supply `seq` in both fixture INSERTs (`:526`, `:608`) — both name their columns, so a `NOT NULL` column
   with no DEFAULT breaks both.

7. **Regression coverage, in-crate.** Per test-plan §4 (Conventions → Test file location), `buffer` is a
   library crate so pins live in `crates/buffer/src/`:
   - `schema.rs` — the four-column key asserted via `information_schema.key_column_usage`, mirroring
     `log_records_primary_key_includes_seq_ordinal` (`:360`). **Not** a duplicate-`INSERT` probe: that path
     is a documented hang on this build (`schema.rs:311-318`).
   - `appender.rs` — behavioural pins beside `append_logs_batch_same_tick_same_severity_keeps_both_records`
     (`:1364`), one per collision source, run on a worker thread under an explicit `recv_timeout` so a hang
     fails rather than wedges.
   - `state.rs` — a **direct** unit assertion of the new allocator (monotonicity, block width, one

     exactly ONE caller and is proven only transitively — that is open trigger

8. **Mutation check.** Neutralize the ordinal (drop `seq` from the key) and confirm the new pins go RED; the

## Constraints & rejected approaches
- **Per-batch-resetting ordinal (`event_index` mirror) — REJECTED.** `metrics_points` has no unique parent
  scoping the key, so two same-tick points in different export batches would both take index 0 (per
  architecture.md §Conventions → Primary key convention, which records this rejection explicitly for the
  sibling table).
- **Dropping the primary key — REJECTED.** Would close the class but leave the table without identity and
  make true duplicate re-sends permanently undetectable; the sibling rejected it on the same ground.
- **A collision-safe redacted placeholder derived from the secret — BANNED.** A hash/suffix/prefix of the
  credential-shaped name is explicitly rejected in security-plan §Security Anti-Patterns → Logging. Do not
  reach for it to separate the redacted-name pair; the ordinal already does.
- **Reverting or bypassing the `metric_name` scrub to avoid the collision — BANNED.** Named as the other
  rejected alternative in the same section.
- **Widening the key with `value` / `data_point_kind` — REJECTED.** Both are payload, not identity, and two
  points of one metric can legitimately share both.
- **A duplicate-`INSERT` PK probe — UNAVAILABLE.** Documented to hang on this build
  (`crates/buffer/src/schema.rs:311-318`); every behavioural assertion goes through the Appender path under
  an explicit timeout.
- **Importing the DDL into `viz` to close the fixture-drift gap — OUT OF SCOPE.** It would add a
  `viz → buffer` dependency edge for a test fixture. The gap is recorded for a future guard chunk; edit the
  copy by hand here.
- **Do not add a labels/attributes column in this chunk.** Operator decision at P4 — the label half CARRIES.
